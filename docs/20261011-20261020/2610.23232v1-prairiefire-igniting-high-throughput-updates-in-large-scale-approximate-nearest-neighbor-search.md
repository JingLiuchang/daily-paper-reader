## 摘要
现代 NVMe SSD 阵列的带宽正接近内存，同时每 GB 成本低得多。因此，在推荐、搜索和检索增强生成等应用中，面向十亿级向量的近似最近邻搜索（ANNS）越来越多地运行在基于 SSD 的系统上。然而，由于现有基于 SSD 的解决方案更新吞吐有限，索引语料库无法跟上数据和嵌入模型的持续修改，从而阻碍了其在更多场景和更大规模上的广泛部署。瓶颈在于 CPU 密集的更新路径：前台插入会引发频繁的 SSD 访问，后台重分配会反复迁移每个向量，即使耗尽可用硬件也难以实现高更新吞吐。本文通过缓冲更新和批量局部重建，开发了 PrairieFire，并结合级联调整、并发控制以及 CPU-GPU-SSD 协同。这些协同设计避免了前台更新中的频繁 SSD 访问和繁重的后台重分配，在保持优异搜索性能的同时实现高更新吞吐。评估表明，与最先进系统相比，PrairieFire 可维持约 3-35 倍的更新吞吐，同时保持约 3-5 倍的搜索吞吐。它还实现了约 1.5-8.7 倍的成本效率。PrairieFire 已在 RedNote 的生产环境中部署两个月，通过更高的数据新鲜度提升了业务指标，且无需频繁重建索引。

## Abstract
Arrays of modern NVMe SSDs are approaching memory in terms of bandwidth while offering much lower cost per gigabyte. Hence, approximate nearest neighbor search (ANNS) for billion-scale vectors in applications such as recommendation, search, and retrieval-augmented generation increasingly runs on SSD-based systems. Unfortunately, due to the limited update throughput of existing SSD-based solutions, the indexed corpus cannot keep pace with continuous modifications to data and embedding models, thus hindering broader deployment across more scenarios and larger scales.   The bottleneck lies in CPU-intensive update paths, where foreground insertions incur frequent SSD accesses and background reassignments repeatedly relocate each vector, making high update throughput difficult to achieve even by exhausting available hardware. In this paper, using buffered updates and batched local rebuilds, we develop PrairieFire with cascaded adjustments, concurrency control, and CPU-GPU-SSD cooperation. These co-designs avoid frequent SSD accesses in foreground updates and heavy background reassignments, achieving high update throughput while maintaining excellent search performance.   Evaluations show that, compared with state-of-the-art systems, PrairieFire can sustain approximately 3-35x update throughput while maintaining approximately 3-5x search throughput simultaneously. It also achieves approximately 1.5-8.7x cost efficiency. PrairieFire has been deployed in RedNote's production environments for two months, improving business metrics by higher freshness without frequent index rebuilds.

## 1. 核心问题与研究动机

- **背景**：现代 NVMe SSD 阵列的单机带宽已接近 DRAM，但每 GB 成本低得多，因此十亿级向量 ANNS（推荐、搜索、广告、RAG）正从纯内存方案转向 SSD 方案（DiskANN、SPANN、SPFresh、OdinANN、Helmsman 等）。
- **核心矛盾**：真实语料高度动态——商品/内容持续增删，embedding 模型以小时级甚至更细粒度重训上线，索引必须"实时吸收"插入与删除。以 0.1B 索引每小时全量刷新、或 1B 索引每 10 小时刷新估算，需要约 **30K QPS 的更新吞吐**，已与在线搜索吞吐同量级，更新成为"一等性能目标"。
- **瓶颈定位**：现有 SSD ANNS 的更新路径是 **CPU 密集型**的：
  - **图方案 OdinANN**：每次插入需在 SSD 图上多跳搜索约 100 个邻居（4–7 ms，占总时间最多 80%），再加节点锁竞争，仅 2–3 KQPS。
  - **分区方案 SPFresh**：前台每次插入对 posting list 做 read-modify-write 往返 I/O；后台 split/merge 后逐向量 reassignment 反复搬移；即使 64 核全用于更新也只有约 12 KQPS，仅达目标的 6%–40%。
- **关键反直觉发现**：**加 SSD 带宽没用**。10 块 Gen5 SSD 提供约 120 GB/s，但实际带宽占用 <1 GB/s；理论上需 128–256 核才能达标，远超可用硬件。CPU 周期分解显示前台更新占 59–62%、后台重建占 38–41%，其中质心图遍历约 30–35%，其余主要是往返 I/O 与列表更新。

## 2. 方法论

### 2.1 核心思想
用**缓冲更新（buffered updates）**摊薄前台逐向量的 read-modify-write 往返 I/O；用**批量局部重聚类（batched local rebuild）**替代后台逐向量重分配。二者与现有"面向搜索"的设计存在三处冲突，需配套改造。

### 2.2 三处冲突（动机实验）
- **内存膨胀**：SPFresh 质心数达向量数的 12–16%，每 list 加 2→16 个缓冲会使 13 GB 数据集的内存从 1.5× 涨到近 3×。
- **伪缓冲**：SPANN 式冗余放置（每向量最多进 8 个簇）使缓冲失效——缓冲 2 个时 SSD 访问概率仍近 100%，缓冲 16 个仍有约 40%。
- **计算负担**：直接对 64 个邻近簇做 10–15 轮 Lloyd 迭代重聚类，CPU 开销远高于逐向量重分配，需要更多后台核。

### 2.3 关键设计
**(a) 三级分区索引结构**
- **Level-2 向量分区（VP）**：正常粒度（数据集 1–2%，每簇约 50–100 向量），单副本放置；每分区自带内存缓冲 + SSD 上连续页（如 4 页 / 16 KB / 128 条 128 维 SIFT 向量）；缓冲向量 ID 与落盘向量 ID 分两个连续数组存放。
- **Level-1 分区质心（PC）**：内存中的质心簇。
- **Level-0 路由质心（RC）**：GPU 常驻切片 + 主机侧一一映射 shadow，采用**惰性同步**（在两次批量 GPU kernel 之间用低延迟 store 指令下发），允许质心值短暂滞后，对召回几乎无影响。

**(b) 前台操作路径**
- **Search**：L0（GPU 全切片批量化）→ L1 → L2（同时扫描内存缓冲与 SSD 向量）。
- **Insert**：只定位最近的一个 VP，追加到其缓冲，并在哈希表中记录 `vector ID → partition ID`。
- **Delete**：查映射表；若在缓冲中用 **swap-last-pop** 保持连续布局，若已落盘则仅将 ID 置 −1（墓碑），搜索时过滤、flush 时惰性 GC。

**(c) Flush / 局部重建 / 级联调整**
- **Flush**：缓冲满或墓碑过多时触发，将缓冲向量与 SSD 上有效向量合并写回同一 SSD 区域。
- **局部重建**：分区过小/过大时，直接对失衡分区及其邻近最多 64 个分区**整体重聚类**，一次性生成新质心与新列表，替代 SPFresh 的逐向量条件重分配。
- **级联调整**：flush/重建后，用三种统一原语（in-place update / append / swap-last-pop）更新 L1 质心，再传播到 L0 host shadow 并惰性同步到 GPU，使上层质心保持代表性、数组保持紧凑（利于 SIMD 与 GPU 距离计算）。

**(d) 细粒度并发控制**
- 三级解耦锁：**G0**（PC 簇 + 对应 RC）每簇锁；**G1**（VP + 父 PC ID）每簇锁 + 版本号；**G2**（向量 → 父 VP ID）**按槽位哈希锁**（ID mod 槽数），把 10 亿把锁降到约 10 万把。
- 三条原则：记录级即时可见性；**分阶段解耦 + 版本校验**（跨粒度切换前释放锁，下一阶段校验版本，失配则回退或跳过）；**有序加锁**（先高层后低层、同层按 ID 升序）防死锁。

**(e) CPU-GPU-SSD 软硬协同**
- **L0 批量距离计算**：把搜索与插入的孤立 GEMV 打包成动态批 GEMM，复用 RC 读取，避免每请求 1.8–3.8 TB/s 的显存带宽需求。
- **L2 并行扫描**：CPU 扫内存缓冲、GPU 直读 SSD 扫落盘部分，二者重叠后按距离归并 top-k。
- **微尺度融合聚类核**：质心（64×128 FP32，32 KB）常驻共享内存，每线程处理一向量、原子累加计数与向量和，省去中间全局内存流量与多次 kernel 启动，重建 <5 ms。

## 8. 局限与讨论

- **硬件门槛较高**：方案依赖 2 块 GPU 与 10 块 Gen5 SSD，整机 TCA 约 $47K、TDP 约 1250 W；虽然作者用成本效率、能效与存储成本效率指标论证其经济性，但对无 GPU 或 SSD 数量受限的部署环境，收益可能缩小。

- **对比覆盖不均衡**：与 SVFusion 的 GPU 基线对比仅覆盖一个工作负载；FreshDiskANN 因内存开销被排除，虽合理，但也意味着与图类更新方案的对比并不完整。
- **设计复杂度与调参成本**：三级分区、三类锁、缓冲预算、flush 阈值、墓碑比例、局部重建邻域大小（最多 64 个分区）等参数较多，论文虽给出敏感性分析，但不同数据分布下的最优配置仍需工程调优；系统正确性依赖分阶段解耦与版本校验，实现与验证成本较高。
- **精度机制的上界**：单副本放置配合多簇扫描可在吞吐不受损时维持召回，但召回仍受分区粒度与扫描簇数约束；级联调整最多挽回约 3% 召回，说明上层质心滞后与局部重建仍存在精度代价。
- **适用边界**：方法面向“高更新率 + SSD 容量远大于内存”的十亿级 ANNS；对于更新稀疏、可全内存容纳或对硬件成本极度敏感的场景，传统内存索引或更简单的 SSD 图方案可能更合适。

## 10. 总体评价

- **贡献定位**：论文准确抓住“动态语料使更新成为一等性能目标”这一趋势，并用 CPU 周期分解与带宽利用率数据证明瓶颈在 CPU 侧的往返 I/O 与逐向量重分配，而非 SSD 带宽，问题诊断具有说服力。
- **方法创新**：缓冲更新、批量局部重聚类、三级分区与细粒度解耦锁形成了一套自洽的系统设计；L0 动态批 GEMM、L2 CPU-GPU 并行扫描与微尺度融合聚类核体现了较强的软硬协同工程能力。
- **证据强度**：端到端对比、逐技术消融、硬件归因、成本/能耗/存储效率与生产验证构成较完整证据链；主要短板在于基线改造的公平性、GPU 与非 GPU 基线不完全对等，以及部分对比覆盖较窄。
- **总体判断**：这是一篇面向真实部署的系统性工作，核心价值不只是“更快”，而是重新定义了 SSD ANNS 在动态负载下的性能目标与设计范式；其结论对十亿级、强更新场景具有较强参考价值，但落地时需结合硬件预算与运维复杂度权衡。
