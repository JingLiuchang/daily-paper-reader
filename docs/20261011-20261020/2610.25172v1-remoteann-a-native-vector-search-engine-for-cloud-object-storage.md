## 摘要
构建于云对象存储之上的向量搜索引擎近年来受到学术界与工业界的日益关注。这类系统通常采用存算分离架构，将主要向量数据持久化于对象存储（如 Amazon S3）中，同时在计算节点上保留紧凑的索引元数据。然而，传统向量索引结构并未针对云对象存储显著的网络延迟和按请求计费的访问成本进行原生适配，从而导致网络 I/O 放大、查询吞吐下降以及更高的 API 开销。为解决这些挑战，我们提出 RemoteANN，这是一种在索引与查询层面均与云对象存储协同设计的向量搜索引擎。为缓解主要的网络 I/O 瓶颈，RemoteANN 将倒排文件（IVF）索引与 RaBitQ 量化相结合，并进一步通过簇间与簇内数据重排进行优化，以提升数据局部性。基于这一定制化数据布局，RemoteANN 的查询引擎融合了簇剪枝、细粒度 Range-GET 请求、请求合并以及本地 NVMe SSD 缓存，在不牺牲精度的前提下显著减少离散存储请求与网络传输量。为应对索引构建瓶颈，我们进一步提出 QGKMeans，在不损害聚类质量的情况下大幅降低构建延迟。在真实数据集上的大量评估表明，与代表性基线相比，RemoteANN 在 97% 目标召回率下实现了最高 5.9 倍的吞吐加速，同时对象存储请求数最多减少 16.1 倍。

## Abstract
Vector search engines built on cloud object storage have drawn growing attention from both academia and industry. These systems typically adopt a disaggregated storage-compute architecture, persisting the primary vector payload in object stores (e.g., Amazon S3) while retaining compact index metadata on compute nodes. However, conventional vector indexing structures are not natively tailored to the pronounced network latency and per-request access costs of cloud object stores, resulting in network I/O amplification, degraded query throughput, and higher API expenses.   To resolve these challenges, we present RemoteANN, a vector search engine explicitly co-designed for cloud object storage across indexing and querying. To mitigate the dominant network I/O bottleneck, RemoteANN couples an Inverted File (IVF) index with RaBitQ quantization, further optimized by inter-cluster and intra-cluster data reordering for improved data locality. Building on this tailored data layout, RemoteANN's query engine combines cluster pruning, fine-grained Range-GET requests, request merging, and local NVMe SSD caching, dramatically reducing discrete storage requests and network transfer volume without sacrificing accuracy. To address the index construction bottleneck, we further develop QGKMeans, which substantially reduces construction latency without compromising clustering quality. Extensive evaluations on real-world datasets demonstrate that, compared with representative baselines, RemoteANN achieves up to a $5.9\times$ throughput speedup while issuing up to $16.1\times$ fewer object storage requests at 97% target recall.

# RemoteANN 论文结构化总结

## 1. 核心问题与研究动机

- **背景**：云对象存储（Amazon S3、Azure Blob、Torch Object Storage 等）因弹性扩展、高持久性与低成本，成为现代数据库的存储后端。向量检索系统（Amazon S3 Vectors、Turbopuffer、Lance、Databricks）也普遍采用**存算分离架构**：紧凑索引元数据留在计算节点，海量高维向量载荷放在远端对象存储。
- **核心矛盾**：传统向量索引并非为对象存储而设计，直接迁移会导致两类问题：
  - **TTFB 网络延迟主导**：对象存储的 time-to-first-byte 通常达数十毫秒，且在小载荷请求中主导总下载延迟。因此图索引（HNSW、DiskANN、NSG）的多跳迭代路由会产生累积的往返延迟，实际系统多改用**簇类索引**（IVF、SPFresh），以便单轮往返取回目标簇。
  - **按请求计费**：云厂商按离散请求数收费，这是本地索引设计从未考虑的代价维度；朴素实现会触发海量请求，导致 API 费用不可接受。
- **研究空白**：现有工作没有**同时**针对对象存储的延迟与成本特性去联合优化「索引布局—索引构建—查询执行」。
- **论文目标**：提出 RemoteANN，一个与云对象存储**原生协同设计（algorithm–system co-design）**的向量搜索引擎，系统性缓解网络 I/O 放大。

## 2. 方法论

### 2.1 总体思路
- 采用 **IVF + RaBitQ 量化**的组合，配合面向查询的物理数据布局，使查询侧的 I/O 优化（剪枝、范围读取、请求合并、缓存）在物理层面“可被解锁”。
- 明确限定在**热查询（warm query）范式**：高精度向量常驻对象存储，索引元数据常驻计算节点 DRAM；冷启动可通过交互信号（如用户打字）异步预取来掩盖。

### 2.2 三层存储布局（异构分层）
- 计算节点 DRAM 存**质心向量**与 **1-bit RaBitQ 前缀**；对象存储存 **8-bit 后缀**；本地 NVMe SSD 作为频繁访问簇后缀的中间缓存。
- 采用 **9-bit RaBitQ 编码**（论文依据：9-bit 在多个数据集上接近未压缩精度），并拆成 1-bit 前缀 + 8-bit 后缀，目的是把“可用于剪枝的信息”全部放进内存，把“仅用于精算的信息”留在远端。
- 内存中的 1-bit 码既支持簇级剪枝，也支持请求范围界定。

### 2.3 QGKMeans：加速 IVF 构建
- 传统 k-means 的**向量—质心重复分配**是构建瓶颈；已有工作用 ANN 搜索加速分配。
- QGKMeans 在每轮 k-means 迭代中，对当前质心构建 **SymphonyQG 图索引**，再用每个数据向量做近似最近质心查询；质心更新后重建索引。
- 效果：在保持 WCSS 与下游 IVF 召回基本不变的前提下，聚类时间低于 Faiss、SuperKMeans、SeededANN（SIFT 上较最快基线 1.4×，Cohere 上 5.5×；Cohere 204.2s vs SeededANN 1128.4s；Deep-1B 上其余方法均超 12 小时阈值）。

### 2.4 数据重排（提升局部性）
- **簇间重排**：把“常被同一查询共同选中”的簇放近，即最小化相邻簇质心距离之和 → 建模为**最小权 Hamiltonian 路径**问题（NP-hard）。利用欧氏距离满足三角不等式，采用多项式近似：
  - 最近邻启发式（O(log n) 最坏近似）；
  - MST-doubling（2-近似）。
  - 对照基线：Hilbert / Z-order 空间填充曲线（因维度灾难先做 PCA 降到 3 维）。
  - 实测在 6 个数据集上**最近邻启发式**路径长度最短（尽管 MST 理论界更好），故设为默认。
  - 可扩展性：对大规模质心先用**递归二分 k-means 分区**，各分区内局部执行 NN 启发式，再按层次树遍历顺序拼接；262,144 个质心整体重排 < 1 分钟。
- **簇内重排**：按向量到簇质心的欧氏距离升序排列。理论依据来自 RaBitQ 的距离分解
  `‖o_r − q_r‖² = ‖o_r − c‖² + ‖q_r − c‖² − 2‖o_r − c‖·‖q_r − c‖·⟨o, q⟩`，
  估计误差等于内积误差乘以 `2‖o_r−c‖·‖q_r−c‖`；对固定查询与簇，`‖o_r−c‖` 越大误差界越松、越难剪枝。因此把“难剪枝”的外围向量聚集为连续区域，使范围读取的字节区间更小。

### 2.5 查询引擎的四个协同组件
1. **基于 RaBitQ 的簇剪枝**：
   - 由无偏估计与误差界得 `dist_up = dist_est + err`、`dist_lo = dist_est − err`。
   - 因真实 `dist_k` 未知，取所有候选向量的**第 k 小上界** `dist^u_k`（满足 `dist^u_k ≥ dist_k`）作为保守阈值；若某向量（或整簇所有向量）满足 `dist_lo > dist^u_k` 则剪除。
   - 激进变体用 `dist^e_k`（第 k 小估计距离），剪枝率更高但可能损失召回（实测 97% 基线下召回损失 < 0.5%）。
   - **动态剪枝**：请求发出后，随异步返回结果更新运行期阈值 `dist^c_k`，跳过仍在途的无效簇；不减少已发请求数（成本不变），但可削减网络长尾、提升端到端吞吐。
   - 与 SPANN/SPFresh 的比值启发式相比：有理论误差界、无需额外超参数调优。
2. **范围优化（Range Optimization）**：只下载覆盖所有未剪枝候选的**最小连续字节区间**，而非整簇。实测在关闭范围优化时，下载量已减少至少 44%；簇内重排进一步降低（如 GIST 30.7% → 19.3%）。
3. **请求合并（Request Merging）**：在固定阈值 T（默认 600 KB）下把相邻字节区间合并为一次 Range-GET。
   - 用**动态规划**求解：按起始偏移排序，`D[j] = min_{i: L(i,j) ≤ T} (K_{i−1}+1, B_{i−1}+L(i,j))`，先最小化请求数、再最小化下载字节；论文给出归纳法最优性证明。超阈值请求不参与合并、单独发出。
   - 与簇间重排强耦合：随机顺序下合并效果差；NN 重排在多数数据集上请求数最少，验证了 Hamiltonian 路径长度可作为空间局部性的代理指标。
4. **本地 NVMe SSD 缓存**：簇粒度、4 KB 页对齐、单一大文件 + `O_DIRECT` 绕过页缓存、best-fit 空闲区映射并动态合并；准入用 TinyLFU 思想 + 老化 LFU（计数周期性减半）；读写经 `io_uring` 异步化，插入与查询关键路径解耦。
   - 与范围优化存在粒度冲突，用**自适应回退阈值 γ（如 0.8）**解决：优化后区间小于整簇 γ 比例才走范围读取，否则整簇下载以填充缓存。

### 2.6 流程（Algorithm 1 / 2）
- 建索引：QGKMeans 聚类 → 簇间与簇内重排 → 按簇质心做 RaBitQ 量化，前缀留计算节点、后缀写对象存储（遵循重排后的物理顺序）。
- 查询：选 top-n_probe 簇 → 用 1-bit 码估计距离 → 簇剪枝 → 缓存命中者本地读取 → 范围优化 → 请求合并 → 发 Range-GET → 等待 I/O → 后台更新缓存 → 更新结果集。

  - 有官方查询划分则用默认，否则从基集采样 1,000 条查询；k = 10，目标召回 97%。
- **对比基线**：
  - **Lance-RQ**：Lance v13.0.0 的 IVF-RQ 索引（IVF + RaBitQ），按 RemoteANN 的数据放置把元数据与 1-bit 码放 DRAM，全精度向量留对象存储做重排（refine_factor ∈ {5,10,20}，Deep-1B 扩到 {5,10,20,40,80}）。
  - **RemoteSPANN**：以开源 SPANN 替换本地磁盘 I/O 为同一套对象存储层（因 Turbopuffer 闭源、Amazon S3 Vectors 为闭源服务，未直接对比）。
