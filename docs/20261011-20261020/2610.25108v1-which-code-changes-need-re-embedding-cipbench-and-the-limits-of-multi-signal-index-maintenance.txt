Which Code Changes Need Re-embedding? CIPBench and the Limits of
Multi-Signal Index Maintenance

Repository-level retrieval-augmented generation systems must keep vector indexes synchronized with continuously evolving code,
yet there is no principled basis for deciding which changed code units actually need new embeddings. We ask whether the retrieval
impact of a code change can be anticipated before that embedding is computed.
Across 10 open-source repositories in Python, Go, and JavaScript, we characterize how a change propagates from syntactic
substantiality through embedding displacement to retrieval impact. The links are informative but not deterministic: syntactic class
separates displacement sharply, yet impact depends on a unit’s retrieval exposure as much as on how far its representation moves,
and recurring counterexamples bound what any single signal can decide. We formalize the decision as CIPBench, a benchmark that
scores maintenance policies under a strict pre-embedding information boundary.
Prediction works, and one signal exhausts it. A ranker using only a unit’s change history substantially reduces retrieval harm
relative to random and recency-based scheduling. Combining it with three further signals — individually discriminative and largely
unassociated with one another — leaves the decision statistically unchanged across every budget we evaluate, for reasons we trace to
the structure of the score rather than to its tuning. What does pay off is not ranking but filtering: units whose text is unchanged from
the indexed state can be skipped with no risk and, in the most reversion-heavy project, at nearly half the embedding cost. Signal-level
informativeness is therefore not evidence of decision-level value, and separating the two requires evaluating the decision a signal
produces rather than its association with the outcome.

Introduction
Modern software repositories evolve continuously, while repository-level retrieval-augmented generation (RAG) systems
rely on vector indexes built from particular repository snapshots [47, 53]. As code changes, these indexes become stale:
a modified function may no longer be represented by the vector stored in the index, causing the retriever to return
outdated context to the downstream large language model. Keeping the index synchronized with the repository is
therefore a recurring maintenance task in repository-level code intelligence systems.
The straightforward solution is to re-embed every changed code unit, but at repository scale this wastes computation.
Full re-embedding scales with corpus size, while per-change incremental re-embedding still recomputes a representation
for every observed update—including changes with little or no effect on retrieval. The shape of the problem is familiar
from predictive test selection, where a change arrives, a budget constrains the downstream work it triggers, and a signal
derived from the change must decide what to spend that budget on [26, 34]. Here the downstream work is embedding,
and the decision is: when a code unit changes, does its representation actually need to be recomputed?
Answering this is less straightforward than it appears. A natural intuition is that the syntactic nature of a change
should serve as a signal: a formatting or documentation edit may be less consequential than a modification to a function
body or signature. Prior work already cautions against taking that correspondence for granted—Fluri and Gall showed
that textual edits need not correspond to substantive program changes [11], and Kawrykow and Robillard documented
how much of a version history consists of non-essential modifications [22]—but the gap that matters here opens one
layer further downstream. The maintenance objective is not syntactic substantiality but whether a change alters the
unit’s representation enough to affect retrieval, and these need not coincide. A syntactically substantial edit may leave
the embedding almost unchanged; an embedding may move substantially without altering any relevant top-𝐾result;
and a small movement may change retrieval when the unit lies near a ranking boundary. The question is therefore not
whether code has changed, but how a change propagates from syntax, through embedding space, to retrieval outcomes.
Existing research supplies pieces of this problem without characterizing the propagation end to end. Fine-grained
code-change analysis—ChangeDistiller [12], GumTree [8], non-essential-change detection [22]—describes what changed
and relates it to defects, tests, refactorings, or affected program entities, but never to embedding displacement or retrieval
impact. Approaching from the other side, code-search benchmarks such as CodeSearchNet [20] and CoSQA [19] and
RAG evaluators such as RAGAS [7] and ARES [35] assume a fixed indexed corpus, while dynamic vector-index systems
such as SPFresh [51], Ada-IVF [30] and Quake [29] begin after the new vector exists, optimizing how it is incorporated
rather than whether computing it was necessary. Drift-aware retrieval such as DeDrift [1] likewise responds to drift
once it has occurred. This leaves an upstream decision unevaluated: which changed units should be re-embedded at all?
We study that decision as an empirical and evaluative problem, characterizing a three-layer funnel from syntactic
substantiality through embedding displacement to retrieval impact across 10 open-source repositories in Python, Go and
JavaScript—2,366 function-level units and 8,936 real updates—with key measurements replicated over three embedding
models. The layers turn out to be related but not interchangeable. Change type separates displacement sharply, yet
displacement alone does not determine retrieval: the effect is jointly moderated by a unit’s position in the retrieval
space. Recurring counterexamples—documentation edits that move an embedding without moving retrieval, comment
edits that remain retrieval-relevant despite leaving executable syntax untouched, reversions that move nothing at
all—mark the boundaries of any single-signal rule. Change history supplies a further inexpensive prior, following the
persistence that Gîrba et al. observed for change-prone entities [15].

These findings expose a second problem: no standard way exists to evaluate the re-embedding decision itself. A code-
search benchmark asks whether a system retrieves the right code from a snapshot. An index-maintenance benchmark
must ask whether a system can decide, before observing the updated embedding or its retrieval effect, which changes
deserve recomputation. We therefore introduce CIPBench(open-source code available at https://github.com/nnzhaocs/
CIPBench), which turns evolving-index maintenance into a reproducible decision problem under a strict pre-embedding
information boundary, with two tracks: filtering, which exposes the safety–savings trade-off when changed units are
skipped, and budget-constrained scheduling, which evaluates which units to prioritize when only a fraction can be
re-embedded.
Finally, we ask whether these regularities are operationally useful, and the answer separates cleanly. Prediction
works: a single historical signal, computable before re-embedding, cuts retrieval harm substantially relative to both
random and freshness-based scheduling. Combining signals does not. Adding three further signals to that one leaves
the decision statistically unchanged across every budget we evaluate. Filtering, by contrast, does work: skipping units
whose text is unchanged from the indexed state is safe by construction and avoids up to half of all re-embedding
computations in the most reversion-heavy project.
That contrast is the paper’s main empirical lesson. The signals are discriminative and, with one exception related
by construction, unassociated with one another—exactly the condition under which combining features is standard
practice—and combining them still changes no decision. Signal-level informativeness and decision-level relevance are
different properties, and telling them apart requires an evaluation that scores decisions rather than signals.
In summary, this work makes four contributions:
• An empirical characterization of how code changes propagate into retrieval impact. We study the relationship
among syntactic change type, embedding displacement, and retrieval outcomes across 10 repositories, 8,936 real
updates, three programming languages, and three embedding models, establishing both the predictive structure of
this propagation and the recurring counterexamples that bound it.
• CIPBench, an evaluation that separates informative signals from useful ones. Existing practice validates a
maintenance signal by showing it correlates with the outcome. CIPBench instead scores the decision a signal produces,
under a strict pre-embedding information boundary, across two tracks and five reference baselines. That distinction is
what makes the saturation in Section 6 visible: the signals that pass a correlational test there still change no outcome.
The benchmark ships with an open toolchain and human-validated change labels (Cohen’s 𝜅= 0.786; classifier
accuracy = 88.7%).
• A negative result on multi-signal scheduling, with its mechanism. On the full 20-point Track B grid a weighted
combination of four pre-embedding signals is statistically equivalent to history alone, and a 130-point sweep spanning
budgets from 5% to 100% finds no budget at which that changes. The combination is invariant to the substantive
weight and unimproved by the orthogonal exposure signal. Cross-validation discards retrieval exposure entirely in
eight of the ten repositories, so the combination reduces in practice to the single signal it was built to improve on.
• A measured, deployable filter. Track A shows that hash-identity skipping is safe by construction in all 10 repositories
with savings up to 49.2%. A Python docstring rule applies to only eight units across the benchmark and misses one,
too few to validate; we give a label-free probing guard for deploying it but cannot exercise that guard on this data.
Both rules are detectable from the changed text alone, so the filter stage costs a hash comparison and a tree-sitter
parse and consumes no GPU.

Related Work
Three bodies of work bear on the re-embedding decision: code-change analysis, which characterizes what changed and
what it predicts; code retrieval and repository-level RAG, which evaluate retrieval quality over a repository snapshot;
and dynamic index maintenance, which incorporates updated vectors into an index efficiently. Each stops one step
short of the decision this paper studies, and for a different reason.
2.1
Code Change Analysis and Impact Prediction
Fine-grained code-change analysis has long sought to characterize source-code modifications beyond line-level textual
differences. ChangeDistiller extracts fine-grained source-code changes and organizes them into a detailed taxonomy [12];
Fluri and Gall showed that textual edits do not necessarily correspond to substantive program changes [11]; and
Kawrykow and Robillard systematically studied non-essential changes in version histories [22]. GumTree later provided
a widely used language-independent AST differencing technique [8], while RefactoringMiner and its extensions identify
structured refactorings across successive program versions [43, 44]. These approaches provide increasingly precise
descriptions of what changes between software revisions.
Code changes have also been used to predict downstream maintenance outcomes. Change-impact analysis relies on
program dependencies, slicing, and semantic relationships to identify entities that may be affected by a modification [3,
18, 33]. Fine-grained change features have been studied for defect prediction [14] and just-in-time quality assurance [21].
Historical evolution provides another useful signal: Gîrba et al.’s Yesterday’s Weather observation shows that entities
that changed recently are more likely to continue changing [15].
Predictive test selection is the closest structural analogue to our setting. It estimates which tests are likely to be
relevant to a given code change in order to reduce execution cost [26, 40], and regression-test selection similarly
balances safety against the cost of rerunning a suite [34]. Both share the shape of the problem studied here: a change
arrives, a budget constrains how much downstream work can be done, and a signal derived from the change must
decide what to spend it on. Section 8 returns to this analogy, because the failure mode we identify is one that any
budget-constrained selection mechanism can exhibit.
Recent work has extended code-change analysis to large language models. Fan et al. [9] evaluate LLMs on several
code-change-related tasks, including code review generation, commit-message generation, and just-in-time comment
updating. Their study examines how effectively LLMs reason about differences between program versions. Our study
considers a different downstream consequence of change: whether a modification alters the code representation and,
ultimately, the retrieval results produced from that representation.
Prior change-impact studies therefore provide both the change representations and the predictive perspective
used in our work, but their outcomes are typically defects, tests, refactorings, or affected program entities. Neural
retrieval introduces a different form of impact. Its behavior depends on continuous similarity scores and competition
among ranked candidates, so a code unit may move in embedding space without changing any top-𝐾result, while a
comparatively small movement may affect retrieval near a ranking boundary. We study this propagation from syntactic
change to embedding displacement and retrieval impact.

Code Retrieval and Repository-Level RAG
A large body of work has studied learned representations of source code. CodeBERT [10], GraphCodeBERT [17],
CodeT5 [49], UniXcoder [16], and CodeSage [52] incorporate programming-language structure, data flow, identifiers,

or large-scale code pretraining into code representations. General-purpose encoders such as Sentence-BERT [32] and
MiniLM [48] are also widely used as transferable embedding backbones. In this work the embedding model is not itself
the optimization target; we study how the representation produced by such a model behaves as the underlying source
code evolves.
Code-search benchmarks evaluate whether learned representations support effective retrieval. CodeSearchNet [20]
and CoSQA [19] provide code–query pairs for semantic code search and question answering. More recent benchmarks
and systems move toward repository-level context. RepoBench [25] and CrossCodeEval [6] evaluate repository-level
or cross-file code completion, while RepoCoder [53] combines iterative retrieval with code generation. CodeRAG-
Bench [47] evaluates the contribution of retrieval to code generation, and general RAG evaluation frameworks such
as RAGAS [7] and ARES [35] assess retrieval and generation quality more broadly. Repository-level RAG research
has also investigated how retrieval itself can be improved; Tan et al. [42], for example, combine multiple retrieval
perspectives and adaptively select useful context for code completion. These studies primarily evaluate retrieval over a
given repository snapshot.
Recent work has begun to study retrieval under evolving corpora explicitly. Zhang et al. [55] evaluate generative
retrieval as new documents are added to a dynamic corpus, while GradNormIR [23] detects corpus-level distribution
shift to determine when a dense retriever should be updated. FlowRAG [54] instead continually adapts the retriever
under non-stationary corpora. These works address retrieval adaptation at the corpus or retriever level, rather than
deciding whether the representation of an individual changed code unit should be refreshed.
Our setting differs in both granularity and timing. Once an indexed code unit changes, the stored representation
may no longer correspond to its current content. Existing code-search and code-RAG benchmarks generally measure
whether relevant code can be retrieved from a snapshot; they do not evaluate whether an individual representation
should be refreshed after the underlying code changes. Drift-oriented retrieval work such as DeDrift [1] studies how
search can remain robust after content drift has occurred; we instead examine whether the retrieval consequence of an
observed change can be anticipated before the updated embedding is computed.
2.3
Dynamic Index Maintenance and Refresh Scheduling
Dynamic vector indexes support efficient search while the indexed collection changes over time. DiskANN [41] and
FreshDiskANN [37] study graph-based approximate nearest-neighbor search under large-scale and streaming workloads.
SPFresh [51] supports incremental in-place updates for billion-scale vector search, while Ada-IVF [30] and Quake [29]
adapt index organization as vectors are inserted, deleted, or updated. These systems address the structural cost of
maintaining a dynamic ANN index.
A key assumption in these systems is that the updated vector is already available. Their concern is how that vector should
be incorporated into the index efficiently. In code-RAG maintenance, however, obtaining the updated vector may itself
be expensive. After observing a source-code change, a system must first decide whether recomputing the corresponding
representation is worthwhile. A re-embedding policy can therefore precede dynamic-index maintenance: selected
code changes produce new vectors, which are then processed by SPFresh-, Quake-, or graph-based index-maintenance
mechanisms.
A complementary line of work reduces representation-maintenance costs under model or distribution drift. AU-
RORA [36] adapts retrieval indices under distribution shift through lightweight continual adaptation and uncertainty-
aware routing. Drift-Adapter [45] addresses embedding-model upgrades by mapping queries from a new embedding

simply whether content changed, but whether the observed change warrants recomputing its representation.

conditions that no prior setting combines: code changes continuously, retrieval quality is the quantity at stake, and the
new vector does not yet exist.
3
Empirical Analysis
We investigate how code changes propagate through the three layers introduced in Section 1: syntactic substantiality
→embedding displacement →retrieval impact. The central question is whether information available when a code
change occurs can anticipate its downstream retrieval consequence before the updated embedding is computed. We
organize the analysis around four research questions:
• RQ1—Change and representation: How does the syntactic nature of a code change relate to embedding displace-
ment?
• RQ2—Representation and retrieval: When does embedding displacement translate into retrieval impact?
• RQ3—Context and predictability: Which temporal, retrieval-exposure, and repository-level signals provide infor-
mation about retrieval impact before re-embedding?
• RQ4—Failure boundaries: Under what conditions do the three layers fail to align?

3.1
Study Setup
The study covers 10 open-source repositories in Python, Go, and JavaScript, comprising 2,366 function-level units
and 8,936 real updates organized as issue-driven evolution streams, with 74–983 ground-truth queries per repository.
Section 4 documents how these streams are constructed and released. This subsection defines the three quantities
measured for every update, which are used throughout the paper.
We record three quantities, which are not all defined at the same granularity. Change type is a property of an update:
each update in a unit’s history carries a syntactic category. Displacement and retrieval impact are properties of a unit:
one 𝛿and one 𝐼per unit, measuring net movement and net retrieval consequence across that unit’s whole observed
history. The decision a maintenance policy makes is likewise per unit (Section 4), so where an analysis relates change
type to the other two it attributes to each unit the most severe class in its history.
Change type. A tree-sitter-based classifier assigns six fine-grained change levels. For readability these are grouped
into three analysis tiers: non-substantive, implementation-body, and function-signature changes, where signature changes
include modifications to parameters, return types, and type annotations. A lexical fallback is used only when syntactic
parsing is unavailable, and accounts for at most 2.8% of updates in any repository.
Embedding displacement. Let 𝐸(·) be the encoder mapping source text to a vector. Displacement is measured per unit
rather than per update: writing 𝑥first for a unit’s source text before its earliest observed update and 𝑥last for its text after
the latest, we define
𝛿= 1 −cos(𝐸(𝑥first), 𝐸(𝑥last)) ,
the cosine distance between where the unit’s representation started and where it ended. This is 0 when the two coincide
and grows toward 2 as they become dissimilar. Measuring net movement rather than the size of individual steps is what
makes the reversion cases of Section 3.2 visible: a unit edited and then restored has 𝛿= 0 exactly, however large the
intermediate steps were. The per-update step displacements are retained separately and are used only where movement
must be decomposed across a sequence, as in the cumulative-drift case of Section 3.5.1 The primary experiments use
MiniLM-L6-v2 [48];MPNet-base-v2 [38] and BGE-base-en-v1.5 [50] are used for cross-model robustness checks.
Retrieval impact. Impact compares top-𝐾retrieval before and after replacing the changed unit’s vector, with 𝐾= 10.

3.2
RQ1: How Does Change Type Relate to Embedding Displacement?
We first examine the link between syntactic change and movement in representation space. If different change types
induce systematically different displacement, syntax provides information about representation change without requiring
the updated embedding itself.
Each unit contributes one displacement, attributed to the most severe change class observed anywhere in its history;
Table 2 reports the median over the units in each class. The ratio compares the larger of the median signature- or
implementation-change displacement with the median non-substantive displacement. Categories with 𝑛< 5 are
excluded from this ratio to avoid unstable denominators.
Across repositories, signature changes generally induce larger displacement than implementation-body changes,
while implementation changes tend to exceed non-substantive edits. The separation can be large: in cobra, the median
displacement for signature changes is 85× the non-substantive median. A Kruskal–Wallis test confirms a strong
difference across the three classes, and all three pairwise comparisons survive multiplicity correction with rank-biserial
effect sizes between 0.39 and 0.68; Appendix D gives the test statistics. Each unit enters the comparison once, since
displacement is a unit-level quantity; the dependence that remains is in the class label rather than the observation
count, because a unit whose history spans several classes is assigned only its most severe.

One possible explanation is that signature edits disproportionately modify identifier-bearing tokens—function names,
parameter names, and return/type annotations—whereas implementation changes are distributed over a larger token
sequence. We treat this as a hypothesis rather than a demonstrated mechanism; direct probing of encoder sensitivity is
outside the scope of this study.
The aiohttp results illustrate an important boundary. Of 43 signature-change units, 28 (65%) have exactly zero net
displacement. Inspection reveals repeated 𝐴→𝐵→𝐴patterns in which type annotations are changed and later
restored. These reverts are retained in the stream as real repository events; a sensitivity analysis excluding exact
text-level reverts is provided in the artifact. Syntactic substantiality therefore indicates that a meaningful edit occurred,
but does not guarantee that the final representation differs from its earlier state.
Finding 1. Change type is a usable proxy for displacement but not a substitute for it. The class separation is large enough
to act on (up to 85× in median displacement), yet 65% of aiohttp’s signature changes move the representation not at all—so
syntax identifies edits that could matter, not edits that did.
3.3
RQ2: When Does Embedding Displacement Affect Retrieval?
The first link in the funnel is strong, but representation movement is useful for maintenance only if it translates into
retrieval change. We therefore examine displacement together with the unit’s position in the existing retrieval space.
For a unit 𝑢, we define 𝑘-occ as the number of ground-truth queries for which 𝑢appears among the current top-𝐾

3.4
RQ3: Which Pre-Embedding Signals Are Informative?
RQ1 and RQ2 identify two sources of pre-embedding information: the current syntactic change and the unit’s existing
retrieval exposure. We now examine two additional sources—change history and repository context—and then compare
the four inexpensive signals directly.
3.4.1
Temporal Persistence. Prior software-evolution work has reported persistence in change behavior. In particular,
Gîrba et al.’s Yesterday’s Weather observation suggests that entities undergoing substantial change in the recent past
are likely to remain change-prone in subsequent versions [15]. Motivated by this observation, we test a related form of
persistence for substantive updates.
For every unit with multiple updates, we compute the probability that later updates are substantive conditional on
whether the first observed update is substantive. Table 4 reports the results.
Across repositories, a unit whose first observed update is substantive has a 91.1–99.3% probability that later updates
are also substantive. The contrast with initially non-substantive units varies considerably. aiohttp, click, and pylint
show differences of +66 to +94 percentage points, whereas gin and express provide little contrast because nearly all
updates in those repositories are substantive.

3.5
RQ4: Where Does the Three-Layer Relationship Break Down?
Aggregate relationships can hide precisely the cases that matter most to a maintenance decision. We therefore examine
recurring mismatches among syntax, embedding displacement, and retrieval impact. They are not isolated noise:
each exposes a distinct limitation of single-signal reasoning. Table 7 summarizes the recurring failure types and their
maintenance implications. The case studies below come from a targeted inspection of extreme recall-loss events and of
units whose syntactic class and retrieval outcome disagree; they are intended as design constraints, not as an exhaustive
census of failures.
3.5.1
Four Mismatches, Four Different Causes. Table 7 gives the evidence for the first four failure types. What it cannot
give is why each occurs, and the reasons do not generalize to one another.
Docstring-only edits move the embedding without moving retrieval because the affected units have low exposure:
a representation can shift noticeably while leaving the top-𝐾results unchanged if the unit rarely enters a relevant

drops, but through two different mechanisms.
The first is cumulative drift. For the query “add config and docs for limits,” associated with flask/wrappers.py::max_content_length,
four consecutive updates accumulate a displacement of 𝛿= 0.1773, while the largest individual step is 0.1118. Recall

This exposes a limitation of per-update gating: individually moderate changes can accumulate until their combined
displacement becomes consequential, and a rule evaluating each update independently may not detect the pattern
before the accumulated drift crosses a retrieval boundary.
The remaining two cases arise through position rather than accumulation. Two units associated with issue #2935 fail
at their first observed update, with displacements of only 0.0546 and 0.0192, yet recall falls from 1.00 to 0.50—the top-𝐾

position.
Together, the three cases account for 2.3% of flask’s 128 ground-truth queries. They are rare, but they expose two
different limitations of displacement-based reasoning: cumulative movement over time and sensitivity to retrieval
position.
Finding 6. The mismatches among syntax, displacement, and retrieval impact have recurring structure (Table 7). We
observe retrieval-irrelevant embedding movement, text-sensitive non-substantive changes, cross-language variation, net-zero
reversions, cumulative drift, and top-𝐾boundary effects. No single layer is therefore sufficient for reliable maintenance
decisions.
These counterexamples provide design constraints rather than ready-made policy rules. They motivate conservative
treatment of apparently low-impact changes, an explicit net-zero check, and a separate mechanism for cumulative drift.
3.6
Summary of Findings
The empirical results support the three-layer funnel as an organizing model, but not as a deterministic chain. Change
type predicts how far a representation moves (Finding 1); retrieval exposure determines whether that movement
becomes consequential (Finding 2); change history supplies an additional temporal prior (Finding 3); repository
temperature bounds the headroom available to any change-based rule (Finding 4); and of the four inexpensive signals
three discriminate impacted units while neighbourhood similarity does not, with only one associated pair among the
six (Finding 5). The counterexamples then show why no single layer suffices (Finding 6).

4
CIPBench: A Benchmark for Re-embedding Decisions
Section 3 shows that code changes differ systematically in their embedding and retrieval consequences, but also
that no single observable signal perfectly identifies consequential updates. CIPBench formalizes this problem as a
benchmark for deciding whether and when a changed code unit should be re-embedded. The benchmark records the
eventual representation and retrieval consequences of each update for evaluation, while restricting candidate methods
to information available before the updated embedding is computed.
The measurements are defined in Section 3.1 and are not restated here; recall that change type is recorded per update
while displacement and impact are recorded per unit. This section contributes what is specific to the benchmark: the
information boundary that separates deployable methods from oracles, the construction of the evolution streams, the
two evaluation tracks and their metrics, and the reference baselines.
4.1
Task Definition and Information Boundary
Consider an evolving repository with a sequence of code updates 𝑢1,𝑢2, . . . ,𝑢𝑇distributed over a set of code units. The
decision object is the unit: a maintenance policy decides whether to recompute a unit’s representation, and CIPBench
scores that decision. Updates are the evidence stream from which the decision is made—they supply each unit’s
change history—but they are not themselves scored. Accordingly the benchmark records, for each unit, its cumulative
displacement 𝛿and its retrieval impact 𝐼, together with the sequence of change types observed across its updates.
The central constraint is temporal and operational. At the time a maintenance decision is made, a method may use
• the old and updated source text;
• repository metadata and the unit’s accumulated change history up to the refresh point; and
• the state of the existing retrieval index.
It may not use the updated embedding, the true displacement 𝛿(𝑢), or the true retrieval impact 𝐼(𝑢). These quantities
become available only after performing the computation that the maintenance decision is intended to avoid, and are
therefore reserved for evaluation or oracle baselines. Figure 1 places each quantity at the point in time at which it
comes into existence.
This information boundary distinguishes the prediction problem from ordinary post-update analysis, and it is
representational rather than temporal. CIPBench models periodic index maintenance: at a refresh point, a set of units
has accumulated changes since the last refresh, and the policy decides for each whether to recompute its vector. The
decision point is therefore after that unit’s accumulated evolution is known and before any embedding is computed
from it. What the boundary excludes is everything derived from the new representation—𝐸(𝑥new), 𝛿, and 𝐼—not the
earlier part of the unit’s own change history. Repository evolution beyond the refresh point remains unavailable, as it
must: no feature may be computed from updates the policy has not yet seen.

Dataset Construction
4.2.1
Issue-Driven Evolution Streams. CIPBench is constructed from issue-driven repository evolution. Each issue
provides an externally meaningful evolution event: its title and body form a natural-language retrieval query, while the
code units associated with the issue form the corresponding ground-truth target set.
This construction serves two purposes. First, it preserves a connection between repository evolution and an explicit
retrieval intent. Second, it reduces the number of updates for which no issue-level semantic context is available. The
resulting stream is not intended to reproduce an unconstrained production commit stream, and this distinction is
treated as an external-validity boundary in Section 7.
The benchmark contains 10 repositories in Python, Go, and JavaScript. Table 8 summarizes the retained function-level
units and updates. Repositories carry between 74 and 983 ground-truth queries. That range matters for reading the
results: Hurt@B is a fraction of a repository’s own query set, so a given harm value rests on a denominator that differs
by more than an order of magnitude across the benchmark, and a small value in a query-poor repository can correspond
to a single affected query.
Repositories were selected to cover active projects over multi-year histories, at least 100 issue-level events before
benchmark filtering, a broad range of retained repository sizes, and multiple projects within each language. The resulting
benchmark contains between 23 and 678 retained units per repository.

the associated code units serving as retrieval ground truth.

5
Track A: Conservative Filtering
Track A asks whether a changed unit can be skipped outright, before any ranking question arises. Section 3.5 supplies
two candidate rules: the 𝐴→𝐵→𝐴reversions, in which a unit’s text returns to the state the index already represents,
and the docstring-only edits, the strongest observed instance of “embedding moves, retrieval does not.” Both are cheap
to detect before re-embedding. This section measures what they save and what they cost.
5.1
Rules and Measurement
We evaluate two rules over the 2,366 units of all 10 repositories, using each unit’s change history to decide:
(1) Hash-identity skip. Skip a unit whose text at the refresh point is hash-identical to the text represented by the
currently indexed vector (Section 3.2).
(2) Python docstring skip. Additionally skip a unit whose accumulated changes are confined to Python docstrings
(Section 3.5).
Both rules are stated over units because that is the decision object, but the evidence they consult is update-level:
the first compares the unit’s current text against what the index holds, and the second inspects the change types of
the updates that produced it. A unit qualifies for the second rule only if every update in its accumulated history is
docstring-only; a single implementation change disqualifies it.
We evaluate both rules with the Track A metrics of Section 4, Savings and MissRate, writing 𝑆reembed for the set there
denoted 𝑆to keep it distinct from the set a rule skips.
We report the two rules separately rather than pooled. Hash-identical skips are non-impacting by construction—
identical text yields an identical embedding, which cannot change any ranking—so they contribute zero misses by
definition. Pooling them with the docstring rule would divide the docstring rule’s misses by a denominator inflated
with cases that cannot miss, overstating its safety.

5.3
A Label-Free Deployment Guard
The requests miss creates a design problem. Hard-coding a repository exclusion would overfit the benchmark, and a
deployed system cannot consult retrieval-impact labels— computing them requires exactly the embeddings the filter
exists to avoid. We therefore express the rule as a guard that a deployment can evaluate from its own observations:
Enable the docstring filter for a repository only after periodic probing has accumulated at least 𝑁= 20
observed docstring-only updates with zero measured impact; disable it permanently at the first observed
miss.
Probing re-embeds a small random sample of filtered units and measures their true impact, so the guard is self-
supervising: it pays a bounded sampling cost to maintain the evidence its own safety depends on. 𝑁= 20 is a deployment
parameter and we state it explicitly, because leaving it unspecified would reintroduce the overfitting objection in a
vaguer form.
We must be clear about what the benchmark can say regarding this threshold, which is less than we would like. The
docstring rule applies to eight units in total across the ten repositories—four in flask, three in pylint, one in requests—so
no repository here accumulates anything close to twenty clean observations within the observed window. On this
benchmark the guard would therefore enable the rule nowhere; it excludes requests not by tripping on the miss but by
never reaching the evidence threshold at all. The guard is a deployment mechanism whose counts accumulate over a
production stream far longer than an issue-linked evolution window, and the benchmark can demonstrate its logic but
cannot exercise it.
This bounds the Track A result. The hash-identity rule carries essentially all of the measured savings and is safe by
construction; the docstring rule rests on eight candidate units, one of which is impacted, and should be read as a design
sketch supported by the counterexample analysis of Section 3.5 rather than as a validated rule.
5.4
Deployment Cost and Interface
The filter is the first stage of a per-unit decision path whose second stage, scoring, is the subject of Section 6. We
give the whole path here because the two stages share one traversal of the update. Algorithm 1 states it. The decision
respects the CIPBench information boundary throughout: it consults the indexed text, the updated source text, prior
change history, and the old index, and never the updated embedding, true displacement, or retrieval-impact label.
The two filter stages are inexpensive by construction. A hash comparison is 𝑂(1) in the length of the unit, and
tree-sitter classification is millisecond-scale on CPU, so an update that the filter skips leaves the path having consumed
neither a GPU nor an index traversal—which is the entire point of placing the filter first.
The scoring stage is where the cost sits. Historical counts are 𝑂(1) once maintained in memory, but computing 𝑘-occ
requires a query–unit ranking pass over the old index at 𝑂(𝑛𝑞𝑛𝑢log𝑛𝑢), by a wide margin the most expensive step.
Whether a deployment must pay it depends on the weight its repository’s cross-validation assigns to 𝑘-occ: Section 6
reports that weight as zero in eight of the ten repositories, where the pass can be omitted without changing any decision,
and small but non-zero in the remaining two.

6
Track B: History Alone Captures the Available Predictability
Filtering removes updates that provably cannot matter. Track B asks the harder question that remains: among the units
that survive the filter, which should be re-embedded first when only a fraction of them can be?
Section 3 leaves a prior worth testing here. Four signals—syntactic substantiality, retrieval exposure (𝑘-occ),
substantive-change history (𝑛𝑠𝑢𝑏), and old-index neighborhood similarity (nn_sim)—are the inexpensive signals available
at the boundary. Three of them discriminate impacted units and nn_sim does not (Finding 5); we retain it so that the
combination is tested with everything the boundary permits rather than with a set pre-filtered on the outcome. Five of
the six pairings are weakly associated (Appendix A); the exception, change type versus history, is the pair Section 6.1
shows to be related by construction. Standard practice would take that as sufficient reason to combine them. This
section asks whether the combination actually improves the re-embedding decision, measured against the strongest
deployable single signal rather than against an arbitrary baseline.
Prediction works here, and one signal does all of it. Section 4 already establishes that the history baseline YW-hist
reduces mean harm by 3.3 percentage points relative to Random and 3.7 relative to Recency—a substantial and deployable
margin under the pre-embedding boundary. What the combination adds to that margin is nothing. On the complete
20-point operating grid a weighted combination of all four signals is statistically indistinguishable from YW-hist alone,
and the conclusion survives every perturbation of the score we could apply. The available predictability is real; it is
simply exhausted by a single cheap signal.

6.6
Why the Displacement Oracle Is Not a Ceiling
Two operating points look striking in isolation: at aiohttp 𝐵=30 the weighted policy matches the True-𝛿oracle (.022 vs.
.022), and at lodash 𝐵=50 it beats it (.015 vs. .027). Neither is a success of the combination—YW-hist attains exactly the
same harm at both points.
The observation still matters, because it confirms Finding 2 at the policy level. Displacement alone does not
characterize retrieval impact, so an oracle that ranks by displacement is not a retrieval-aware scheduler and its harm
is not a lower bound on what a deployable policy can achieve. This is a property of the task, and it is one reason the
Recency-to-oracle gap reported in Section 4 should not be read as headroom that a better ranker is guaranteed to
capture.

Summary
A single cheap historical signal captures essentially all of the predictability available before re-embedding. Three further
signals—two of them discriminative, all largely unassociated with one another, and combined under cross-validated
weights—add nothing to it. The result holds across the full budget range, from 5% to 100%, and is invariant to the

7
Threats to Validity
Several aspects of the study affect how broadly its findings can be interpreted, including the choice of embedding model,
change labeling, dataset construction, and repository coverage. We discuss six threats below, focusing on the scope of
the conclusions they affect and the evidence available to assess them.
T1—Embedding-model dependence. The main analysis uses MiniLM-L6-v2, so some observed relationships may
depend on the embedding model. We assess this by repeating the displacement and retrieval-impact measurements
with MPNet-base-v2 and BGE-base-en-v1.5 across all 10 repositories.
Displacement rankings are highly consistent across the three models: over 30 repository–model comparisons the
mean Spearman correlation is 𝜌= 0.905 (range 0.82–0.97), with language-level means of 0.903, 0.901, and 0.915 for
Python, Go, and JavaScript. Retrieval impact is not. The impacted sets produced by MPNet and BGE overlap only partially
with those from MiniLM: mean Jaccard overlap 0.232 across 20 comparisons, ranging from 0.07 to 0.38. The relative
displacement patterns therefore transfer well across the tested encoders, whereas the exact set of retrieval-impacting
updates does not.
Two caveats bound the second measurement. The cross-model retrieval analysis differs slightly from the main
pipeline for five repositories—flask, cobra, echo, gin, and lodash—where a stricter impact implementation produces
impacted fractions 2–16 percentage points lower; the remaining five use matching definitions. This does not affect the
main MiniLM results, but it means we can characterize the relative stability of displacement and the model sensitivity
of impact without claiming exact transfer rates. Together these imply that the standard CIPBench impact labels are
MiniLM-specific: the encoder is a parameter of the benchmark, and labels for a target encoder must be regenerated
with the released pipeline rather than transferred.
T2—Change-label reliability. The empirical analysis relies on automatically assigned change categories. Section 3.1 re-
ports the validation results—Cohen’s 𝜅= 0.786 between annotators [24] and 88.7% classifier agreement with adjudicated
labels; what matters for validity is the structure of the disagreement rather than its magnitude.
Disagreements concentrate on a small number of recurring classification boundaries rather than spreading uniformly.
More than half (23/45) involve lex_substantive. Agreement is also lower in cobra and lodash (𝜅= .555 and .494),
where two specific ambiguities recur: Go template strings containing embedded DSL syntax, and local parsing failures
in the large runInContext wrapper.
Adjudication assigns 31 disagreements to implementation changes, eight to signature changes, and six to string-literal-
only changes; none remains in the lex_substantive category. We subsequently clarified the annotation protocol so that
local parsing failures with identifiable semantics are assigned to their semantic change class, while lex_substantive is
reserved for cases that cannot be classified reliably from the parsed structure. Following standard inter-rater-reliability
practice [27], we retain the original independently obtained 𝜅rather than recomputing agreement after this clarification.

T3—Issue-linked evolution streams. CIPBench follows issue-linked repository evolution rather than an unconstrained

generalization question is instead whether the observed temporal persistence, repository-level heterogeneity, and policy
behavior remain similar under natural production commit streams; replication on bot-filtered commit histories would
provide complementary evidence.
T4—Repository and language coverage. The benchmark contains five Python, three Go, and two JavaScript repositories,
which vary substantially in size, change history, and retrieval behavior but remain 10 projects in three languages.
Our conclusions should be read as cross-repository evidence within the studied ecosystems rather than as universal
language-level laws. The qualification is sharpest for findings involving signatures, type annotations, comments, and
string literals, whose roles differ across languages and coding conventions.
T5—Statistical multiplicity and repository-level sample size. Several parts of the analysis involve repeated statistical
comparisons. For the three pairwise change-type comparisons underlying Table 2, we use a Bonferroni-adjusted

than through a pooled count of significant tests.
Repository-level meta-feature correlations (Appendix B) serve a different purpose. They are computed over the 10
repositories to characterize possible sources of heterogeneity, not to establish population-level relationships, and no
policy in this paper consults them.
The temporal-persistence analyses of Section 3.4 take the update as the unit of observation—both the first-update
conditional probabilities and the consecutive-class persistence rates of Appendix C—even though a unit contributes
several updates and may revert (e.g., aiohttp’s 𝐴→𝐵→𝐴annotation restorations, retained as real events). Their
figures should be read as descriptive of the pooled update population rather than as exact inference over independent
samples.
The remaining analyses are not affected in that way, because they are unit-level: displacement, retrieval impact, and
three of the four signals are defined per unit, and change type is aggregated to the unit before use. Their dependence is
of a different kind—a unit spanning several change classes is assigned only its most severe—which affects the class
labels rather than the observation count.

be read as a typical outcome.
8
Discussion, Conclusion, and Future Work
8.1
Discussion
8.1.1
Informative Signals Are Not Necessarily Useful Ones. The result we did not expect is that signals can be informative
about retrieval impact, be largely unassociated with one another, and still combine into a policy that changes no decision.
This is worth dwelling on, because the reasoning that led us to attempt the combination is standard and, on its own terms,
sound. We measured per-signal discrimination, found that three of the four separated impacted from unimpacted units
while neighbourhood similarity did not, checked that the discriminating signals were not redundant with one another,
Manuscript submitted to ACM


32
Nannan Zhao, Jiameng Zhang, Taoyu Zhong, Hao Wang, and Bo Wang
and concluded that combining them should help. Every step of that argument is common practice in software-analytics
work. The conclusion was still wrong.
The gap is between two properties that correlational validation cannot distinguish. A signal is informative if knowing
it reduces uncertainty about the outcome. A signal is decision-relevant if knowing it changes what a system does. Our
results separate these in two ways, and the second is the more general.
The first is redundancy. A signal that is individually informative can carry no information the system does not
already have. The substantive flag discriminates impacted units in seven of ten repositories (Finding 5), yet it changes
no re-embedding decision at any budget a deployment would impose, because the history term already reproduces its
ordering (Results 3 and 5). Correlational validation cannot detect this, since it evaluates each signal against the outcome
rather than against the other signals in the presence of which it will be used.
The second is objective mismatch, and it survives even when a signal is not redundant. Retrieval-impact prediction
and re-embedding scheduling are different problems: ranking by 𝑃(𝐼> 0) maximizes the number of impacted units
re-embedded, whereas Hurt@B counts the queries left visibly degraded, and the updates most likely to be impacted are
not the units whose staleness degrades the most queries. A signal validated against the first can therefore misallocate a
budget spent on the second.
We think the second pattern generalizes past our benchmark. Wherever a maintenance mechanism spends a budget,
the quantity being predicted and the quantity being optimized tend to differ: predictive test selection estimates which
tests are likely to fail, while the objective is fault detection per unit of execution time; crawl scheduling estimates
which pages have changed, while the objective is the freshness a user observes. A signal validated against the predicted
quantity can be entirely correct and still misallocate the budget. The methodological implication is that a maintenance
signal should be evaluated by the decision it produces under the objective it will face, not by its association with a
proxy for that objective. Such an evaluation needs an artifact like CIPBench, which fixes the information boundary, the
budget, and the metric so that two policies can be compared on decisions rather than on scores.
8.1.2
Why Filtering Succeeds Where Ranking Saturates. The two tracks fail and succeed for opposite reasons, and the
contrast is instructive. Ranking saturates because the discriminative work is already done: history reproduces the
substantive ordering exactly, and exposure adds nothing on top. Filtering succeeds because it exploits a property no
ranking signal captures—textual identity between the new state and the indexed one. That property is not a better
predictor of impact; it is a proof of non-impact. An update whose text is unchanged cannot move its embedding, so it
cannot change any ranking, and the miss rate is zero by construction rather than by measurement.
This suggests a design principle for maintenance policies more broadly. Where a decision admits a structural
certificate—an argument that an action is safe rather than an estimate that it is probably safe—that certificate is worth
more than any amount of signal engineering, and it should be sought first. Our largest single saving, 49.2% in aiohttp,
comes from a hash comparison. The four-signal weighted score that occupied most of our design effort produces none.
8.2
Conclusion
This paper asks whether a changed code unit necessarily needs to be re-embedded. It does not, but the useful answer
turned out to lie in a different place from where we looked for it.
Across 10 repositories in Python, Go, and JavaScript we find a consistent progression from syntactic change to
embedding displacement to retrieval impact, with links that are informative rather than deterministic. CIPBench turns
that observation into an evaluation problem by requiring a policy to decide before observing the updated embedding
Manuscript submitted to ACM

or its retrieval effect. Under that constraint, combining the available pre-embedding signals into a ranking policy is
statistically equivalent to using the single strongest signal, for a structural reason we identify; conservative filtering, by
contrast, avoids real computation at zero measured risk.
The broader implication is that repository freshness need not be reduced to a choice between refreshing everything
and refreshing whatever changed most recently. A code change can be treated as evidence whose importance depends
on its syntax, its history, and its position in the retrieval workload—but only where the maintenance mechanism is
actually sensitive to that evidence. Establishing where it is sensitive is what an index-maintenance benchmark is for.
8.3
Future Work
Speculative re-embedding with read-time validation. Our policies decide once, at write time, and a wrong decision is
silent: a unit skipped in error stays stale until something happens to surface it. An alternative architecture would treat
the skip as a speculation and detect the misprediction afterwards, in the manner of branch prediction. The obstacle is
that naive detection is circular— establishing whether a skip was wrong requires 𝐼(𝑢), which requires the embedding
the skip avoided—so the check costs exactly what it saves.
Finding 2 of Section 3 suggests an escape. A stale unit that is never retrieved cannot manifest its staleness, and
most skipped units are never retrieved. Validation could therefore move from write time to read time: retrieve 𝐾′ > 𝐾
candidates from the stale index, re-embed only the deferred units that surface within 𝐾′, and re-rank before returning
𝐾. The cost is then bounded by 𝐾′ embeddings per query rather than one per update, and is paid only for staleness that
reaches a user. What this cannot catch is a unit whose fresh embedding would enter the top-𝐾while its stale embedding
sits below 𝐾′; that residual miss rate is measurable from CIPBench’s existing labels as a function of 𝐾′, and bounding
it—perhaps by per-change-class empirical bounds on 𝛿, generalizing the exact certificate that hash identity already
provides—is the substantive open problem.
We regard this as the most promising direction, and as a systems problem rather than a prediction problem: it needs a
query workload with timing, a cost model in wall-clock rather than embedding counts, and end-to-end retrieval quality
under deferral.
Generality across languages and encoders. Extending CIPBench to Java, Rust, C++, and TypeScript would show how
type systems and language-specific conventions affect the observed relationships, and evaluating code-specialized
retrieval encoders would show whether the comment and string-literal sensitivities persist when the representation
model is designed for source code. A harmonized cross-model impact pipeline would also permit a cleaner measurement
of how impact labels transfer between encoders than Section 7 can report.
Broader evolution and query workloads. Issue-linked streams give CIPBench a natural connection between repository
evolution and retrieval intent, but they are not production commit histories. Replication on bot-filtered natural commit
streams would show whether the temporal patterns and repository-level differences persist under a less curated
process. The impact definition is likewise tied to ground-truth repository queries; question answering, semantic code
search, and completion-oriented retrieval expose different parts of a repository and may therefore warrant different
maintenance decisions. Developer intent is a further unexploited signal: issue text is available but the current per-update
representation carries no validated intent label, and we preferred to exclude intent rather than introduce a heuristic we
could not evaluate under the same protocol.

Metric sensitivity and cumulative drift. The default 𝐾= 10 and the binary impact predicate warrant comparison
against graded relevance measures such as NDCG change and against other values of 𝐾, and the leave-one-repository-
out grid was refined only near 𝑤1 = 0. Separately, the present policies evaluate a unit once per refresh and carry nothing
between refreshes. A unit passed over at several consecutive refreshes accumulates staleness that Hurt@B charges
but that no term in Eq. 1 anticipates. A drift-aware variant would escalate a unit’s priority with its deferral count,
restricted to units with retrieval exposure to lose; the Track A probing guard of Section 5 already provides the sampling
machinery such a policy would need to calibrate itself.
