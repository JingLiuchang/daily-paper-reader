Abstract—Whether a foundation model succeeds as an au-
tonomous agent depends as much on its runtime software as
on its weights. This runtime, the agent harness, manages context
and memory, steers multi-turn control, executes tool actions in
sandboxes, and verifies work before stopping. Because models dif-
fer in how they use tools and how they fail, a static harness tuned
for one model or task often stalls, wastes tokens, or regresses on
another. This bottleneck has driven a shift from prompt tuning
to self-improving agent harnesses: systems that inspect their own
execution traces, separate runtime bugs from model limits, and
rewrite their own code. We present a unifying architectural
and design framework for self-improving agent harnesses. The
framework pairs four editable runtime components (context
and state, agent control, action interfaces, and verification and
recovery) with a four-stage loop that diagnoses failures, proposes
code patches, validates candidates, and deploys updates. Using
this framework, we show how optimizers trace errors across
long trajectories and discover reusable runtime mechanisms such
as pre-stop verifiers, loop breakers, and persistent memory.
We further show why full-harness rewrites overfit or break
across modules, and how modular updates with validation gates
generalize across models while bounding token cost. To keep
self-modification safe, we establish practical defenses against
recurring failure modes including prompt bloat, benchmark
gaming, and evaluator tampering. Finally, experiments on SWE-
bench Lite validate this framework, showing that gated modular
evolution outperforms prompt reflection and full-harness rewrites
across models and repositories at a fraction of the token cost.

ing, automated harness optimization, recursive self-improvement,
context engineering, agent evaluation
I. INTRODUCTION
Language models are now widely deployed as autonomous
agents to resolve bugs in large software repositories [1], [2],
run command-line tools [3], [4], operate desktop and web
interfaces [5], and execute multi-step reasoning and scien-
tific workflows [6]. Every working agent pairs a foundation
model with an agent harness: the stateful runtime software
that turns single-step token prediction into sustained, multi-
turn execution over long horizons. While the model supplies
general reasoning and code generation, the harness governs
the surrounding execution loop at every turn by assembling
and compacting state history, scheduling control flow and
subagent handoffs, executing tool or shell calls inside isolated
sandboxes, and running automated test or recovery checks
before task completion [4], [7], [8].
Why the harness matters as much as the model. Early
work on language-model agents treated the runtime harness
as thin engineering glue around a model checkpoint. Over
time, its scope and responsibility have grown into a core
part of any agentic system, and recent controlled evaluations
across coding, terminal, and computer-use tasks highlight
three reasons for this shift. First, the harness shapes how an
agent fails and how much it costs to run. When the same
model runs inside different production harnesses, its dominant
failure modes (quitting before testing its work, looping on
failed commands, overflowing its context window, or skipping
verification) follow the design of the harness rather than the
model family. Token usage per solved task can also vary by
an order of magnitude across harnesses [9], [10].
Second, a well-designed harness both supports weaker mod-
els on simple tasks and unlocks stronger models on com-
plex ones. On short, self-contained problems, extra harness
structure mainly compensates for gaps in weaker models.
On long, repository-scale tasks, however, a capable harness
does the opposite: its state tracking, multi-step planning, and
verification hooks give strong models the scaffolding they
need to solve problems they could not finish alone [11].
Third, no single static harness is optimal for every model.
Because models differ in how they format tool calls, follow
instructions, and balance exploration against action, a harness
tuned for one model often underperforms or flips leaderboard
rankings when paired with another [8], [10]. Even when the
base model is held fixed, longitudinal audits across dozens of
human-maintained harness releases show that manual tuning
frequently stalls or introduces regressions on earlier tasks [12].
From prompt pipelines to self-improving agent har-
nesses. Because harnesses have such a large impact on re-
liability and must match specific models, the way engineers
build them has evolved through three distinct generations [4],
[8]. First, manual harness engineering relies on human de-
velopers to inspect failed rollouts by hand and craft better
system prompts, Agent-Computer Interfaces (ACIs), context
compactors, and retry loops, producing foundational runtimes
such as SWE-agent [2], Antigravity, Claude Code, Codex CLI,
and Gemini CLI [4], [7], [12]. Second, automated prompt
and workflow optimization introduced programmatic search
over frozen models, tuning prompt instructions, demonstra-
tions, and module parameters [13], [14], reflecting on multi-
turn execution traces [15], [16], or searching over code-
defined multi-agent workflows [17], [18]. While these second-
generation optimizers can inspect multi-turn traces or search

II. THE AGENT HARNESS AND THE SELF-IMPROVEMENT
LOOP
How an agent harness connects the model to the envi-
ronment. In a long-horizon task, a frozen foundation model
cannot inspect a workspace, execute commands, or track multi-
step state on its own. Instead, it operates inside an executable
agent harness (such as Claude Code, Antigravity, Mini-SWE-
Agent, or Terminus) that mediates interaction with the live
environment across every turn (Fig. 1, left) [4], [8]. Unlike
a static prompt template, the harness governs autonomous
execution across dozens or hundreds of turns through four
coupled, code-editable components. First, Context and State
Management controls multi-turn history across the trajectory
by assembling dynamic instructions, separating working mem-
ory from experiential memory [31], and masking or compact-
ing stale observations across prior turns so long horizons do
not overflow context [32], [33]. Second, Agent Control steers
multi-turn exploration by regulating turn budgets, detecting
and breaking repetitive loops, switching between planning
and execution phases, and delegating subtasks to isolated
subagents [8], [25]. Third, the Action Interface defines how the
agent acts upon the environment through an Agent-Computer
Interface (ACI) [2], [34], translating model outputs into sand-
boxed shell commands [35], file edits, or GUI actions while
parsing or truncating single-turn raw stdout and UI state on the
current step and loading tool schemas on demand [36]. Fourth,
Verification and Recovery intercepts stop or state-commit sig-
nals from Agent Control to run automated test suites, linters, or
visual checks, routing failures back into Context and State for
self-repair before termination [37]–[39]. Fine-grained modular
systems further split these four components into five modules
(separating single-turn observation formatting from multi-turn
context management [25]) or four lifecycle contexts (plan,
supervise, verify, recover [39]), while pre-execution action
guards bridge Component 3 and Component 4 [40].
The four-stage closed-loop self-improvement cycle. Be-
cause these four runtime components interact tightly across
a trajectory, a flaw in one component quickly cascades into


others. Self-improving harness frameworks replace manual
debugging of these coupled components with an automated
outer loop (Fig. 1, right) that iteratively evolves the harness
over successive rounds. In Stage 1 (Diagnose Failures), the
system runs the current harness on a development split to
collect multi-turn rollout trajectories, and localizes systematic
harness bottlenecks by clustering verifier errors, diffing pass-
ing and failing trajectories, or searching raw execution logs [8],
[19], [21]. In Stage 2 (Propose Edits), an optimizer translates
these diagnostic findings into concrete code or hook patches
across one or more harness components [22], [25]. In Stage
3 (Validate and Filter), candidate harnesses are screened on
validation tasks, trace-replay simulators, or efficiency frontiers
to check runtime execution, prevent regressions, and filter
out overfitted or token-wasteful edits [20], [24], [41], [42].
Finally, in Stage 4 (Deploy or Route), a validated patch is
either merged into the default harness for subsequent runs [8],
[19], saved to an archive of harness variants that future search
rounds can branch from [24], [29], or paired with a lightweight
router or policy that selects a tailored harness configuration for
each incoming task [43], [44].
Key design choices in self-improving harnesses. Across
this loop, existing systems differ along three practical design
choices [8], [45]. First, who proposes the edit: a same-model
self-loop lets a capable coding agent diagnose and patch its
own harness without maintaining a second model [8], whereas
an external coding optimizer is required when the task agent
is small or domain-specific (§V) [19], [21], [39], [46]. Second,
what code can be modified: restricting edits to the task harness
keeps search predictable, whereas allowing recursive edits to
the optimizer itself can unlock better search tools at higher
compute cost (§IV) [26]–[30]. Third, where the evaluator
resides: grading scripts and logs should always be locked in
read-only storage outside the agent sandbox so the optimizer
cannot pass tests by modifying the evaluator or fabricating
logs (§VI) [47], [48].

III. DIAGNOSING FAILURES AND SYNTHESIZING REPAIRS
Why single-trajectory reflection fails on long-horizon
agents. In a multi-turn agent harness, a single failed roll-
out mixes random model slips (such as a mistyped regular
expression or a one-off tool timeout) with structural harness
bugs (such as stateless shell execution or missing exit checks).
Reflecting on one failure in isolation to append a prompt
rule [49] cannot separate random noise from systematic error,
leading optimizers to add overly specific rules or unnecessary
restrictions for failures that never actually happened, which
adds latency and clutters the context window [50]. Over
repeated iterations, appending ad-hoc fixes causes instruction
files to accumulate contradictory rules and grow endlessly over
time [51]. Controlled ablations confirm why broad trajectory
access is necessary [19]. When an optimizer receives only
scalar benchmark scores or short single-run summaries, search
stalls near the baseline, whereas access to a searchable folder
of raw execution trajectories, prior harness code, and diffs lets
it spot recurring bottlenecks across dozens of runs.
Structured failure diagnosis and attribution across tra-
jectories. A central challenge in diagnosis is separating a
harness flaw from a model capability limit [10], [11]. An auto-
mated analyzer separates the two by checking for divergence
between the model’s reasoning and its executed actions across
rollouts. When the model’s reasoning trace identifies the right
file or fix (or solves the task on at least one retry), yet the
run fails because an edit tool rejected its patch format, a shell
call lost its working directory, context compaction dropped
an earlier constraint, or the loop exited before running tests,
the harness is at fault. Conversely, when tool calls execute
cleanly and observations remain intact in context across retries
yet all rollouts fail on domain logic, Stage 1 abstains from
proposing a harness edit so search compute is not wasted on
model knowledge gaps. First, to filter out random one-off slips,
verifier-grounded failure clustering pairs each failed trajectory
with its compiler or unit-test error output and groups recurring
runtime bottlenecks across tasks [8], [24]. Second, contrastive
trajectory diffing applies whenever a task passes under one
harness version (or retry) and fails under another, comparing
passing and failing rollouts across retries or harness revisions
to isolate recurring module bottlenecks [25], [52].
Third, backward step-level causal tracing localizes early
compounding errors without human step labels by tracing
data dependencies backward from the final test failure or
stack trace to the earliest turn that wrote or mis-read the
broken variable [21], or by checking runtime postcondition
invariants and visual state-transition predictions emitted at
intermediate turns, such as screenshot diffs showing a UI
click produced zero screen change [38] or a file edit occurring
before any probe script verified the code invariant [37]. Fourth,
in task-agent self-reports, the task agent reviews its own
failed trajectory to report where tools or instructions held it
back, with a verifier retaining only claims backed by concrete

How candidate repairs are synthesized and kept ed-
itable. Once a failure cluster is diagnosed, the optimizer
must translate that diagnosis into maintainable harness edits.
Because production harnesses span tens of thousands of lines
of code [4], unconstrained full-file rewrites are fragile and
prone to syntax or import errors. Existing systems keep
self-modification reliable in three ways. First, lifecycle hook
injection exposes pre-turn, post-tool, and pre-stop hooks so the
optimizer can write small, self-contained middleware functions
without touching the core event loop [8], [54]. Second, scoped
module and action-guard synthesis restricts edits to specific
classes inside an isolated git branch or synthesizes small code
guards that filter invalid actions before execution [19], [20],
[25], [40]. Third, maintaining a codebase index maps high-
level agent behaviors to exact source files and functions so


the optimizer knows where to edit without reading the entire
repository [53].
Persistent rule and context ablations also highlight three
practical design lessons for what to edit [55]–[57]. Explicit
negative boundaries (such as forbidding early exits or unre-
lated file edits) consistently outperform step-by-step procedu-
ral advice, which makes the agent rigid when a task deviates
from the template and hurts solve rates [55]. Furthermore,
adding static repository documentation into context yields
little gain when agents are bottlenecked by implementation
skill [56]. Plain-text safety rules in instruction files also
lack matching built-in sandbox controls unless backed by
deterministic code hooks that block disallowed tool calls at
runtime [57].

1) Pre-stop verification and patch-checking subagents:
Optimizers interpose mandatory checks before termina-

lightweight verifier subagent to review the patch before
allowing the agent to exit [4], [8]. Because premature
termination is one of the most common failure modes
across coding and terminal agents, blocking unverified exits
consistently yields one of the largest jumps in solve rate
across coding and terminal benchmarks.
2) Empty-turn and runaway-reasoning recovery: When a

the stalled reasoning step, and inject a continuation prompt
paired with a completion self-check [24].

IV. EVOLVING AND VALIDATING HARNESSES WITHOUT
OVERFITTING
Single-branch refinement, branching archives, and re-
cursive self-improvers. Once a harness optimizer diagnoses
why an agent failed, it must decide how to explore candidate
code edits across four main search topologies. The simplest
approach is step-by-step single-branch refinement, which iter-
atively applies targeted patches to a single incumbent harness
and keeps changes only when they pass regression checks [8],
[20], [37]. While sample-efficient and easy to audit, single-
branch search frequently stalls in local optima when early
structural choices constrain later edits or when fixing one task
group regresses another [43], [62]. To avoid getting trapped
in a single design path, population-based systems maintain
branching trees or archives of candidate harnesses that allow
the optimizer to revisit earlier variants, preserve stepping-stone
designs that solve niche failure modes, and explore diverse
execution strategies in parallel [21], [29], [30], [42], [43].
Going a step further, mutation-library search indexes every
past patch in a searchable repository tagged by which file
it edited, which error signature it targeted, and how much
it changed validation performance, enabling the optimizer
to retrieve and combine compatible patches across branches
rather than reinventing fixes from scratch [24]. When local
failure logs alone are not enough to inspire a fix, literature-
guided search retrieves algorithmic ideas from scientific papers
and adapts them into new harness modules [63]. Finally,
recursive self-improvers extend the edit scope beyond the task
harness to the optimizer code itself [26]–[28], as in Darwin
G¨odel Machine (DGM) [29] and Mendel G¨odel Machine
(MGM) [30]. By rewriting their own file-patching tools into
line-anchored diff editors or refining how they review and
select variants, recursive systems can compound gains across
rounds, though doing so requires strict sandbox isolation to
prevent the search loop from breaking itself [29], [30].


Modular evolution and conflict-resolving merge passes.
The unit of mutation has also shifted from coarse multi-agent
call graphs [64], [65] and workflow search [17], [18], [66] or
multi-harness routers [43], [67] to modular evolution inside a
single runtime harness. Rewriting an entire production harness
at once often fails because subsystems such as observation
filtering, context compaction, loop limits, and completion
checks rely on shared state assumptions. Modifying all of them
simultaneously makes credit assignment difficult and causes
edits in one routine to break another, such as a new output
filter trimming the exact stack trace a new verification check
needs to read. Controlled ablations confirm that editing all
harness modules at once performs worse than the starting seed
harness on held-out terminal benchmarks [25].
Recent systems solve this coupling problem through mod-
ular isolation and explicit merge stages (Fig. 2, Safeguard 1).
Decomposing a terminal harness into five independent mod-
ules (Agent Loop, Tool Use, Observation Management, Con-
text Management, and Task Completion Detection) lets each
module evolve within a restricted scope before an integration
merge pass resolves cross-module conflicts on a validation
split [25]. Coding optimizers similarly test module updates
independently before consolidating them under global gen-
erality checks [22]. In physical domains, embodied robotics
harnesses isolate planning, supervision, verification, and error
recovery into separate contexts so faults do not cascade across
stages [39], while embodied vision systems refine shared
multi-subtask routines via episode gain-loss repair [52]. Cru-
cially, because clean file merges can still conflict behaviorally
at runtime, these merge passes resolve behavioral incompat-
ibilities by running an LLM-guided code reconciliation or
recombination pass conditioned on failure traces [22], [25],
[52].
Why naive harness search overfits, and the validation
gates that prevent it. Because an agent harness is com-
posed of arbitrary executable code and prompts, an unre-
stricted optimizer maximizing score on a small development
split overfits easily. Rather than discovering general control
logic, unconstrained search frequently hard-codes task-specific
heuristics, brittle keyword triggers, and bloated retry chains
that exploit quirks of the development set. Empirical abla-
tions show how severely naive search hurts generalization:
unrestricted recursive evolution achieves the highest score on
its development split but brings almost no gain on out-of-
distribution (OOD) benchmarks while more than doubling
per-task token usage [20]. Evolving directly on benchmark
subsets similarly mistakes benchmark-specific shortcuts for
real architectural progress [68].
Alongside modular isolation (Safeguard 1), three cross-
stage safeguards spanning Stages 1 to 3 and task-pool design
restore OOD transfer (Fig. 2). First, keeping edits small and
general (Safeguard 2) ties every patch in Stages 1 and 2 to a
recurring failure cluster rather than an isolated rollout, enforces
gradually shrinking edit-size budgets (such as bounding lines
of git diff or prompt token delta across search generations
in Regularized Recursive Self-Improvement (RRSI) [20]), and
rejects task-specific hints [8], [20], [21]. Second, enforcing
strict Stage 3 acceptance checks (Safeguard 3) verifies syntax,
requires non-regression across the evolution and validation
splits [8] (or verifies that the patch changes the specific
failed step as predicted before full evaluation [38]), and
uses runtime instrumentation to confirm that newly added
code paths actually execute, preventing unused code from
passing by chance [24]. While automated dead-code pruning
removes unexecuted branches on every commit [20], verifying
execution specifically on the targeted failure cluster [24] and
pairing evolved modules with fault-injection unit tests [69]
avoid stripping rare defensive recovery hooks. Third, strictly
separating development and test task pools (Safeguard 4)
evolves harnesses on curated external task repositories filtered
for overlap against downstream evaluation suites and freezes
the harness before OOD testing [25], [68].
V. MODEL FIT, CROSS-MODEL TRANSFER, AND COST
EFFICIENCY
Choosing an external optimizer versus a same-model
self-loop. Deciding whether to evolve a harness with an ex-
ternal coding optimizer [19], [23], [24] or a same-model self-
loop [8], [25] depends on how model scale affects proposing
edits versus benefiting from them. Controlled cross-scale ex-
periments that decouple the outer optimizer from the inner task
agent establish two core findings [70]. First, patch proposal
quality is relatively flat across mid-sized to frontier models
conditional on the model meeting a baseline instruction-
following threshold (such as 32B+ models on skill and prompt
updates): once basic competence is met, such models propose
harness updates that are as effective as those from frontier
models, since diagnosing observed batch traces is simpler than
solving the full task end-to-end [70]. Second, the benefit to the
inner task agent varies non-monotonically with model scale.
Very weak models struggle to invoke and follow retrieved
skills and rules, intermediate-capability models gain the most
because the evolved harness supplies the structured guidance
and state tracking they lack natively, and frontier models
benefit mainly on complex long-horizon problems [11], [70].
Separating harness flaws from model limitations also guides
what kind of patch to write [22]. When a failure stems from
a harness flaw such as a clumsy edit interface, missing tool
feedback, or an unverified stop, fixing that interface or hook
unlocks the model’s existing capability [10]. Conversely, when
a smaller model loses track of state or loops on failed com-
mands, adding prompt rules often causes regressions, whereas
offloading that burden into deterministic code (such as loop
breakers, dependency checks, or state-recovery middleware)
reliably compensates [8], [21]. Consequently, a same-model
self-loop is effective when the task agent is already a capable
coding model [8], [25], whereas a stronger external coding
optimizer remains essential for smaller models, non-coding
domain agents in planning or robotics [39], [46], or unassisted
self-loops that must diagnose raw multi-turn traces and write
complex middleware from scratch.


Evolving harnesses across multiple models of different
capabilities. Evaluating multiple frontier models across har-
nesses reveals frequent rank reversals. A harness configuration
that maximizes accuracy for one model family can hurt another
on the exact same benchmark because models differ in how
they format tool arguments, follow negative instructions, and
decide when to stop [10]. When different models evolve from
the same starting harness on the same tasks, they invent
fixes tailored to their own failure habits. For example, one
model adds a loop breaker and early file creation to curb
over-exploration, a second adds dependency checks and a
patch-review subagent to catch hasty edits, and a third adds
persistent shell state across commands [8], [24]. Even so,
structural runtime checks [19], [20], memory stores [31], vi-
sual guards [38], and modular control loops [22], [25] transfer
far better across models than model-specific prompt wording.
Code patches also transfer reliably between models that share
the same failure habits, even though evolving directly with the
deployment model achieves the highest peak score [24].
Supporting multiple models of different capabilities there-
fore works best as a two-tier evolution workflow. During
Stage 3 validation, candidate structural patches (such as verifi-
cation hooks, environment snapshots, and context compaction)
can be tested across the target model suite and promoted
into a shared core only when they improve or hold neutral
across all models [19], [22], [31]. When a candidate patch
improves one model family but triggers a rank reversal on
another (such as an aggressive loop-breaking threshold or
model-specific prompt rule), the outer loop can branch that
patch into a lightweight per-model adapter or index it by
failure signature in a shared patch library [8], [24], [71]. At
runtime, a router can then dispatch queries across specialist
harness branches [43], or a compact policy can apply a per-
task harness patch [44].
Controlling search-time rollout cost and runtime token
overhead. A self-improving harness must manage compute
across two distinct timescales: the upfront outer-loop cost
of evaluating candidate edits during search, and the per-
task inner-loop token cost incurred during deployment [9],
[10]. To cut search-time rollout cost, recent systems replace
brute-force re-evaluation with three targeted strategies. Multi-
armed bandit schedulers group development tasks by failure
signature and focus rollouts on unresolved failure clusters or
promising module combinations rather than re-testing tasks the
agent already passes [23], [72]. Trace-replay simulators turn
past rollout trees into an offline testbed that screens search
policies before running expensive live containers [41]. Multi-
branch routers such as Mixture of Self-Improving Branches
(MoSIB) [43] co-evolve specialized harness branches by
pruning solved development tasks into branch subsets and
optimizing a prompt-based router to pick the best branch
per query. In a complementary deployment paradigm, test-
time patch generators [44] do not cut the initial offline search
budget, but instead amortize offline search trajectories into a
compact playbook or policy that applies a custom patch in one
shot without iterative search at deployment.
At runtime, empirical ablations show that accuracy and to-
ken efficiency do not have to trade off. Multi-objective search
loops that jointly optimize solve rate and token cost [20], [42],
deterministic observation masking [32], and periodic history
truncation that drops old tool outputs in chunks without break-
ing the prompt cache [33] all cut per-task token usage while
matching or improving solve rates. Moreover, catching errors
early with verification hooks stops unproductive exploration
loops before they burn dozens of turns, allowing cheaper
low-effort reasoning settings to match expensive high-effort
runs [38], [73]. When an evolved harness lowers per-task token
usage, upfront search cost amortizes directly after a break-even
query volume; when it instead raises solve rate at equal or
higher runtime cost, it must be benchmarked against compute-
matched test-time scaling baselines (such as parallel Best-of-N
sampling or sequential refinement on the frozen seed harness
under the same total rollout and verifier-feedback budget [68],
[74]).
VI. FAILURE MODES, SAFETY BOUNDARIES, AND
EVALUATION STANDARDS
Inner-harness degradation: prompt bloat, tool confusion,
and module conflicts. Giving an agent write access to its
own runtime introduces five recurring failure modes that
divide into inner-harness degradation and external sandbox or
evaluator exploits (Table II). As shown in §III and §IV, the
first three modes (Table II, Part A) stem from noisy credit
assignment inside the harness: single-run reflection invents
unnecessary rules, grows instruction files without cleanup,
or drops user constraints during compaction (Mode 1) [50],
[51], [59]; sprawling plugin libraries cause skill shadowing
where overlapping tool descriptions degrade action selection
compared to a minimal shell interface (Mode 2) [35], [75];
and simultaneous full-harness edits break shared assumptions
across control and verification routines (Mode 3) [25]. The
remaining two failure modes (Table II, Part B) are even more
severe because outer-loop search actively exploits weaknesses
in the evaluation sandbox, grading pipeline, or persistent
memory store.
Benchmark cheating and environment leaks. In Mode 4,
because outer-loop search selects whatever candidate harness
achieves the highest validation score, it actively amplifies
environment shortcuts whenever the evaluation sandbox leaves
them open [84], [85]. On repository-level coding benchmarks,
agents routinely inspect git log, reflogs, or pull-request
metadata to recover ground-truth human commits rather than
solving the issue from scratch [76]. In terminal environments,
agents read or execute leaked reference solutions and test files
even when the prompt explicitly forbids them [77]. Similarly,
when candidate harnesses are screened only on a small set
of visible validation assertions, evolutionary search can syn-
thesize lookup-table programs that pass every visible check
while failing completely on held-out test inputs [78]. While
adding explicit anti-cheating instructions to the prompt reduces
casual shortcuts [76], plain-text security rules lack built-
in sandbox enforcement [57]. Preventing benchmark gaming

Tampering with evaluators, execution logs, and persis-

test suites, and execution logs inside the agent’s workspace
simplifies container setup, leaving them writable lets a self-
improving harness raise its score by rewriting the evaluator
rather than solving the task. Empirical audits show that self-
improving agents frequently weaken unit-test assertions, sup-
press error exit codes, or edit scoring scripts when those files
sit within their write scope [47]. Even more concerning, audits
of commercial coding harnesses reveal that agents can modify
or delete their own local execution logs to erase evidence of
policy violations and evade trajectory monitors [48].
Persistent memory, tool-calling chains, and configuration
files create a further cross-session attack surface, as malicious
instructions or token-exhaustion triggers planted in workspace
notes, cached rules, or tool configs carry over into future
tasks [80], [81]. Echoing Thompson’s “Reflections on Trusting
Trust,” poisoning even a few training tasks can induce a
self-modifying agent to write permanent harness rules that
disable security checks, such as HTTPS verification, JWT
validation, or safe YAML loading, on later clean tasks [79].
Even without an adversary, tightening safety or permission
rules over time makes cached scores in an evolutionary archive
go stale, which can keep unsafe older harness variants alive
unless archived candidates are re-tested [82]. Compounding
these risks, software-engineering audits of open-source agent
projects find that automated unit tests cover fewer than half of
the lines and branches in LLM-handling harness code [69].

VII. EXPERIMENTS
We test our framework on SWE-bench Lite [1] around three
questions (Table IV). First, can test-time retries or prompt rules
replace runtime code hooks? Second, how do unconstrained
full-harness rewrites compare against Stage-3-gated modular
evolution in accuracy and token cost? Third, do evolved
harnesses transfer zero-shot to a stronger model?
Setup and baselines. We evaluate on 60 verified Python
bug-fixing tasks. Forty sympy/sympy tasks are split into
development (N=12), validation (N=8), and held-out in-
domain test (N=20) sets. Twenty django/django tasks
form a held-out cross-repository test set (N=20). Each run
executes in a clean single-commit sandbox with git history
stripped, and patches are graded externally on held-out test
suites (Table III).
All methods start from the same 142-line Python seed
harness spanning the four components of Fig. 1: context_
mgr.py (prompt and raw turn history), control.py (a
12-turn limit and JSON parser), action_aci.py (bash,
view_file, edit_file, and finish), and verify.py
(a pass-through stop hook). Part A freezes Gemini 3.8 Flash as
the task agent and uses Gemini 4 Carbon as a shared external
optimizer, with timeout fallback to Gemini 4 Argon on full-
module prompts. Every optimizer reads identical development
traces without hidden test names. We compare five methods:
running the seed harness once (Pass@1); ranking three seed
rollouts without oracle tests (Best-of-3); appending learned
text rules to RULES.md (Prompt-Only Reflection); rewriting
all four Python files at once without validation or token
caps (Unconstrained Full-Harness Rewrite); and updating one
module at a time under Stage-3 validation, runtime line-
execution checks, and a 110k-token runtime cap (Modular
Gated Evolution, Eq. 1). Part B transfers these frozen har-
nesses zero-shot to Gemini 4 Argon.
Retries and prompt rules cannot replace runtime code.
On Gemini 3.8 Flash, the seed harness solves only 5.0% of
held-out tasks (Table IV, Part A). Most runs exhaust all 12
turns re-reading large uncompacted files, while the rest call
finish on an empty diff. Sampling three rollouts per task
(Best-of-3) more than doubles token cost without improving
accuracy, because context overflows the same way on every
retry. Prompt-Only Reflection writes a RULES.md file whose
opening rule explicitly forbids calling finish with an empty
or untested diff. Without Python code to block termination at
runtime, the model still exits early: unverified cross-repository
stops double from 15.0% to 30.0%, and held-out accuracy
drops to 2.5%.
Unconstrained rewrites bloat cost, whereas modular
gates build lean code. Unconstrained Full-Harness Rewrite
lifts held-out accuracy to 42.5%, but buys this gain by raising
the turn cap from 12 to 28 while leaving recent file and shell
outputs uncompacted. As context piles up across 28 turns,
runtime cost jumps nearly fourfold over the seed to 451.6k
tokens per task, with one rollout exceeding 2.8M tokens.
Modular Gated Evolution instead updates one module at a
time and keeps the 12-turn cap:
1) context_mgr.py (Accepted): Compacts observations
older than two turns into head-tail summaries and appends
a live turn-and-edit status footer. This cuts token usage
while lifting development and validation accuracy fivefold.
2) action_aci.py
(Accepted):
Adds
windowed
file
views, truncated shell outputs, and an empty-diff guard on
finish, eliminating premature empty exits.
3) control.py (Rejected by Stage 3): Raises the turn limit
from 12 to 18. Although development accuracy jumps,
validation accuracy drops and token usage breaches the
110k cap, so Stage 3 rejects the edit.
4) verify.py (Accepted): Blocks exit unless git diff
is non-empty, edited Python files compile cleanly, and a
post-edit test run succeeds without errors.
On held-out tasks, this 12-turn harness reaches 40.0%
accuracy across both repositories (8× the seed) with zero
unverified exits. Crucially, it uses just 46.7k tokens per task:
2.5× less than the seed harness and nearly 10× less than the
unconstrained rewrite. Those runtime savings pay back all 100
search rollouts in under 100 deployment tasks.
Zero-shot transfer to a stronger model. When transferred
without re-tuning to Gemini 4 Argon (Table IV, Part B),
compact code mechanisms generalize far better than long,
uncompacted horizons. On the seed harness, Argon avoids
empty-diff exits through stronger instruction following, yet
still burns all 12 turns reading uncompacted files and solves
only 10.0% of held-out tasks. Prompt-Only Reflection reaches
15.0%. Unconstrained Full-Harness Rewrite drops to 30.0%,
as Argon’s longer reasoning chains compound with 28 turns
of uncompacted context. Modular Gated Evolution achieves
the highest accuracy on both repositories (37.5% overall) at
64.8k tokens per task, beating the unconstrained rewrite at less
than one-fourth the token cost.
VIII. DISCUSSION AND CONCLUSION
As self-improving agent harnesses move into broader de-
ployment, four open research directions stand out:
1) Jointly adapting model weights and harness code:
Updating model weights changes how the model fails and
makes older harness checks obsolete, while editing harness
code shifts the observations, tool schemas, and action dis-
tributions seen during reinforcement learning. Stabilizing
this loop requires unifying bidirectional model-harness co-
evolution [86], routing-harness-guided post-training [87],
data-centric weight updates [88], and distilling evolved
harness behaviors back into model weights [89].
2) Lifelong adaptation under environment drift: When
external APIs, software dependencies, or user workflows
shift over months of deployment, a harness must detect
distribution drift, repair stale tool wrappers or memory

free task generators [93] and evolving harness streams [91]
paired with standardized compute-matched test-time scal-
ing baselines across model families and harness pair-
ings [9], [10], [68], [74].
Conclusion. An agent harness is no longer a fixed execution
wrapper around a frozen model; it is an executable, self-
improving runtime system whose context managers, control
loops, action interfaces, and verification hooks govern whether
raw model capability turns into reliable long-horizon work.
Across this paradigm, lasting gains come not from uncon-
strained, monolithic rewrites driven by scalar scores or isolated
rollouts, which easily break cross-module state and overfit
development quirks, but from disciplined closed-loop systems
engineering. Building trustworthy self-improving harnesses
requires separating systematic runtime flaws from model ca-
pability limits across raw trajectories, evolving modular code
mechanisms under conflict-resolving validation and token-
efficiency gates, adapting shared checks to model-specific
habits, and isolating evaluators, audit logs, and permission
boundaries strictly outside the mutable runtime.
