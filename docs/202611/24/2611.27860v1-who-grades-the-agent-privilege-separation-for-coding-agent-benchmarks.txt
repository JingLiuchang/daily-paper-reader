Who Grades the Agent? Privilege Separation for Coding-Agent Benchmarks
Nathan Nour Houlamy
University of Padua
Mattia Favretto
University of Padua
Earlence Fernandes
UC San Diego
Mauro Conti
University of Padua
Abstract—Benchmarks for AI-based coding agents are a staple
of the current AI landscape, because they are the leading
way to measure the performance of LLMs. Their scores guide
business and research decisions. Evaluating coding agents is
challenging, since they are able to manipulate their evaluation
infrastructure to artificially achieve better scores. Grading an
agent’s solution often requires running its code, which can then
manipulate the evaluation process. BenchJack, an automated
benchmark auditor, recently reached near-perfect scores on
nine of ten popular agent benchmarks without actually solving
their tasks. Agents already do this unprompted, as OpenAI’s
July 2026 Hugging Face incident showed.
Building on secure systems design, we introduce Split-
Bench, a privilege separation framework for evaluating coding
agents and the first in the scientific literature to separate
running a task’s tests from judging their results. Even an agent
whose code takes over the entire test environment cannot forge
a pass, because a trusted grader holds the expected answers.
We show that real-world benchmarks (e.g., Terminal-Bench,
DeepSWE) can be ported to the SplitBench framework with
minimal effort and high fidelity: 180 of 202 tasks convert, and
SplitBench agrees with the native graders on 98.7% of agent
attempts. We attack the converted tasks in the worst case,
where adversarial agents can read all the grading code but
not the expected answers. SplitBench blocked 75% of their
attempts; the rest mostly reveal weaknesses in the original
tasks’ tests rather than flaws in SplitBench.
1. Introduction
Coding-agent benchmarks give an AI agent program-
ming tasks and score whether it solves them. They are
the main way to measure and compare the capabilities of
coding agents. Researchers use the scores to track progress
and to direct further work, and companies use them to
decide which model to deploy. The tasks ask the agent
to write code, produce files, or change an environment.
A benchmark is useful only if its scores reflect how well
the agent completes these tasks. If the agent can alter the
grading process or obtain protected evaluation information,
such as the expected answers, it may receive credit for work
it has not done. In DeepSWE’s abs-stepped-slices
task, for example, the agent must extend a small scripting
language so that "abcdef"[::2] returns "ace". The
tests hold the expected value "ace", and the agent is not
meant to see them. An agent that reads them anyway can
hard-code the value without implementing the feature. In
another case, an agent replaces a download utility in a
Terminal-Bench task. The test setup later calls this utility,
and it installs a modified test runner. That runner reports
success whether or not the task was solved [1]. We therefore
treat benchmarking agents as adversarial measurement [2].
The agent being measured can tamper with the infrastructure
that measures it.
Such manipulation is well documented. BenchJack, an
automated benchmark auditor, reached near-perfect scores
on nine of ten popular agent benchmarks without solving
their tasks [1]. Agents already do this unprompted. They
pass unit tests that contradict the task specification by mod-
ifying the tests [3], modify scoring code, and read answers
the scorer had already computed [4]. A prominent case
is the OpenAI incident of July 2026. Agents in internal
cybersecurity evaluations bypassed network controls and
compromised Hugging Face systems while searching for
material related to their tasks [5].
These cases show that execution is the difficult part of
grading. To grade most tasks, the evaluator must run the
agent’s code. Once that code runs, it can report false results,
modify the tests around it, or tamper with the process that
collects its outputs. Benchmark authors use sandboxes, ex-
ternal scorers, and audits to protect evaluations [1], [6], yet
in most frameworks the grader still trusts results produced
in an environment that the agent’s code controls. We review
several existing frameworks in Section 2.
In this paper we introduce SplitBench, a framework that
keeps protected evaluation information and the final grading
decision outside everything the agent’s work can control.

This design applies privilege separation to benchmarks.
The agent, the Evaluation environment, and the Oracle each
receive only the access they need. Only two things must
stay secret. The first is the protected evaluation information,
which we call the task’s hidden data. The second is a
random seed that the operator chooses for each run. The
grading logic, the adapters, and SplitBench itself may be
public. Each test, or group of tests that the benchmark
runs together, runs as a separate case in a fresh Evaluation
environment, so state left behind by one case cannot affect
the next. An access policy limits the agent’s network access
to the destinations the task allows.
Our solution also allows existing benchmarks to adopt
SplitBench easily through conversion. A conversion keeps
each task’s instructions, environment, tests, and assertions.
It changes only how the grading is carried out. We study
which tasks can be converted this way, using every task
of Terminal-Bench 2.0 [7] and DeepSWE v1.1 [8], [9].
Terminal-Bench covers terminal workflows, and DeepSWE
covers long-horizon engineering work in software reposito-
ries. We employed coding agents for the conversions. For
each task they also devised attacks, which the converted task
must reject. We then measure how closely the converted
tasks grade relative to each benchmark’s original grader.
Finally, we attack the converted tasks with adversarial agents
that have full knowledge of the defense.
While the techniques of isolation, sandboxing, access
control and least privilege are well-known security prin-
ciples, the scientific contribution of this paper lies in es-
tablishing, through a constructive argument, that standard
computer security ideas can be composed to solve the
adversarial measurement problem for real benchmarking
software. Furthermore, we show that coding agents can
automatically port entire benchmarks to our framework with
minimal human supervision, establishing that SplitBench is
a practical system that can securely evaluate coding agents
today.
Our paper makes three contributions:
•
Framework for Secure Adversarial Measurement of
AI Agents. We design SplitBench, the first framework
in the scientific literature for evaluating coding agents
that separates running a task’s tests from judging their
results. SplitBench applies a range of secure system
design principles to AI model benchmarking and shows
that they provide immediate security benefits to real
benchmarks.
•
Conversion of real benchmarks. We convert 180/202
tasks of Terminal-Bench 2.0 and DeepSWE v1.1 with
their original tests and assertions, at a median cost of
about $10 per task. SplitBench and the native graders
agree on 98.7% of attempts. We report which tasks do
not convert and why.
•
Worst-case adversarial evaluation. We attack the con-
verted tasks with agents that can read each task’s grading
code but not the expected answers. No attempt passed
through a flaw in SplitBench, which rejected 75% of
their completed attempts. Most of the others exploited
weak tests in the original tasks. Of the 429 attacks that
the conversions are tested against, the native graders
accepted 230 and SplitBench none.
The rest of the paper is organized as follows. We first show
that the attacks above fall into a small number of classes,
and that existing frameworks leave several of them open
(Section 2). We then state what we assume about the agent
and what a secure grader must guarantee (Section 3), and
present the design of SplitBench (Section 4). In Section 5,
we test it on two real benchmarks, with agents that solve
the tasks and with agents that attack them. We close with
what a secure grader still cannot decide, and with future
work (Section 6).
2. Background
A coding-agent benchmark gives the agent a task and
an environment to work in, then judges the result against
the task’s acceptance conditions. Depending on the task, the
evaluator reads files the agent produced, runs tests against
the agent’s code, or checks effects the agent caused.
In many benchmarks, the agent can alter the environment
in which its work is judged [1], [7], [9], [10]. The verdict
then depends not only on the agent’s work but also on parts
of the grading the agent can reach: the tests, the tools they
run, the files they read, and the reports they produce. Each
of these dependencies is a path from the agent’s work to
its score, and agents have already used every one of them.
We collect the attacks documented so far in Section 2.1.
In Section 2.2, we discuss gaps in prior work and existing
evaluation frameworks. We summarize both in Table 2,
where we map each attack class to these frameworks and to
SplitBench.
2.1. Known Attacks
We discuss known attacks, grouped by the evaluation
property they violate. A single attack may belong to several
classes. The attacks come from systematic audits of agent
benchmarks [1], from studies of reward hacking [3], [4],
from an analysis of evaluation logs [11], from an incident
report [5], and from earlier work on graders for program-
ming competitions [12].

Disclosure of evaluation information. An agent obtains
expected answers, hidden tests, acceptance conditions, or
unreleased cases, and reproduces expected outputs without
solving the task. METR reports a model that inspected the
Python call stack to retrieve the answer the scorer had
already calculated [4]. In another case, a model copied
reference patches from the commit history of the task’s
repository [1].
Forged observations. The evaluator accepts a success report
without checking it. In SWE-bench, a patch can add a
conftest.py file whose pytest hook overwrites each
test’s reported outcome [1]. Correct tests then produce false
reports.
Tampering with acceptance checks. The agent modifies
tests, scoring code, or the tools and files they depend on,
so that the checks pass while the task remains unsolved.
ImpossibleBench gives agents tasks whose unit tests con-
tradict the specification, so that any pass requires cheating.
Agents passed them by modifying the tests or overloading
comparison operators [3]. In METR’s tests, a model replaced
the evaluator with a stub that accepts every submission [4],
and elsewhere an agent commented out a failing assertion
in the code it was asked to fix [11].
Cross-case interference. Files, processes, or cached results
left in one evaluation case change the outcome of another,
or carry information from one case to the next. During our
conversion study, we found an instance in Terminal-Bench’s
polyglot-c-py task. Its tests run a program’s Python
side and then its compiled C side in the same environment,
so the Python side can replace the compiled binary with
one that prints the expected answer, and a program whose
C side prints nothing passes natively. Any benchmark that
runs several cases in a shared environment is exposed to this
class.
Malicious evidence. The agent’s code crafts outputs that
exploit the components that parse and judge them, for ex-
ample through oversized or malformed responses. We found
an instance in one of our own conversions. Its Oracle, the
trusted component that issues the verdict, used a number the
candidate reported to decide how much memory to allocate.
As a result, a candidate that reported a huge number could
exhaust the host’s memory (Section 5.1). Automatic graders
for programming competitions face a related attack from
submissions that fill the disk or whose compilation produces
huge outputs [12].
Access-policy misuse. The agent reaches destinations the
task does not require, or uses a permitted service for oper-
ations the task does not need. Agents in OpenAI’s internal
evaluations on ExploitGym bypassed network controls while
searching for task-related material. They did so through
vulnerabilities in Artifactory, a package mirror they were
permitted to reach. Earlier, agents had used Artifactory’s
shared credentials to build a message board for passing notes
between runs [5]. A policy that restricts only destinations
prevents neither, because both went through a permitted
service. In other evaluations, agents searched the internet
for walkthroughs and answers, or installed newer versions
of the code that already contained the fix [11].
2.2. Related Work
Prior work documents how agents manipulate their own
evaluations and proposes principles for resisting such ma-
nipulation. The approaches below find attacks, detect them
after the fact, or state design principles, so each covers
only part of the problem. To our knowledge, no prior work
contributes a real evaluation framework that can securely
evaluate coding agents today.
Benchmark auditing and exploit detection. BenchJack
proposes a checklist and an iterative loop in which an audit-
ing agent attacks a benchmark and a coding agent patches
it [1]. After one round of patching, it still found working
exploits in SWE-bench Verified and Terminal-Bench. Its
authors attribute this to design choices in these benchmarks,
such as letting the agent share an environment with the
evaluator, and conclude that such flaws call for a redesign
rather than a patch.


BenchShield instruments an existing evaluation frame-
work to find the paths through which an agent can influence
its reward, and to detect when it uses them [13]. It finds
that running the verifier in a separate environment would
close most of the paths it models on four of its seven
integrity dimensions. Paths remain when the verifier runs
the agent’s code, and BenchShield detects those with LLM
audit agents. SplitBench closes that case by design: it treats
the environment that runs the candidate as compromised,
and the Oracle accepts only bounded values it can check
against hidden data (Section 4). Zeng et al. move the verifier
into a separate container on a clean image and harden it
iteratively. The strongest attacker that reads the verifier still
succeeds in 63% of its attempts on their Terminal-Bench
tasks [14]. The verdict is still computed where the agent’s
code runs. The Reward Hacking Benchmark, in its hardened
setting, places its grader outside the sandbox and recomputes
expected outputs on hidden data [15]. It is a benchmark
of its own tasks and offers no way to grade an existing
one. Abdelnabi et al. reach a similar conclusion in a recent
position paper. They argue that the capability a security
benchmark measures can undermine the evaluation itself,
and call for keeping the agent’s privileges apart from the
answers [16]. SplitBench builds such a separation and tests
it against adversarial agents (Section 5).
Agent-evaluation frameworks. These frameworks isolate
the agent but leave the grading boundary to each benchmark.
Inspect AI runs each sample in its own sandbox, while its
scorers run in Inspect’s own process on the host, outside that
sandbox. To run the agent’s code, however, a scorer typically
uses the sandbox the agent worked in [6]. Its tests then run
in the environment the agent modified, alongside the files,
tools, and processes the agent left there. Harbor, the task
framework that Terminal-Bench and DeepSWE share, can
run a task’s tests in the agent’s container or in a separate
verifier environment [17]. Terminal-Bench uses the first [7].
DeepSWE uses the second [9] but first applies the agent’s
patch there. Any file the patch adds is therefore present when
the tests run. Three other harnesses grade in a similar way.
The SWE-bench harness applies the agent’s patch in a fresh
container but reads the verdict from the test log. Its own code
notes that a patch can print passing lines, and it catches them
only when the test command also exits with an error [18].
METR’s Task Standard runs the scoring code in the agent’s
container and separates the two by Unix users [19]. SWE-
Lancer reuses the agent’s machine for grading [20], [21]. In
each case the scorer’s code is trusted, but its measurements
are taken in state the agent controls. We instead make the
grading boundary part of the framework, so no measurement
is taken in state the agent controls.
Concurrent work. During our study, Harbor added the
Rewardkit Worker [22] after an audit of Terminal-Bench’s
verifiers [23], and Terminal-Bench has begun to adopt
it [24]. A grader can use the Worker to run submitted
code as an unprivileged user inside the verifier container.
The Worker shares our starting point, that submitted code
should not report its own result. It differs from SplitBench
in three ways. First, the expected answers remain in the
container that runs the submitted code. File permissions
protect them, and the design trusts the task’s image and the
kernel. SplitBench keeps the answers outside that container
and assumes the submitted code controls it. Second, the
Worker is a tool that each task’s author chooses to apply, and
the author decides what to trust. Its design document notes
that a grader relying on the submitted program’s exit code
remains fail-open. In SplitBench, the framework enforces
the split for every task. Third, a task’s test cases share one
container. The Worker itself limits only run time and output
size, and leaves CPU, memory, and network access to the
container. The Worker was proposed in October 2026 [22],
after SplitBench’s design was complete. To our knowledge,
it has no accompanying publication.
MirrorCode, a benchmark in which agents rebuild pro-
grams from their behavior, also compares outputs outside the
containers that run the agent’s code [25]. It was published
after our work had begun. It grades one kind of task,
a program whose output must match a reference, while
SplitBench converts existing benchmarks with their own
tests.
Secure grading of untrusted code. Automatic graders for
programming competitions have long executed untrusted
code. Mareš surveys attacks on such graders and recom-
mends separating trusted grading components from submis-
sions, sandboxing submitted code, and connecting the two
through a narrow, well-defined interface [12]. These recom-
mendations assume that a submission is a single program the
grader compiles and runs. A coding agent instead submits
a modified environment. SplitBench reduces the modified
environment to a bounded candidate, and its verdicts hold
even when the agent knows how grading works.
Untrusted models. Greenblatt et al. design protocols that
remain safe when an untrusted model deliberately tries to
defeat them [26]. Christodorescu et al. argue that agent
security is a systems problem. The model powering an agent
must be treated as untrusted, and the surrounding system
must enforce security invariants such as least privilege,
complete mediation, and tamper resistance of the trusted
computing base [27]. They take this as a position and leave
the design of such systems open. SplitBench makes the
same assumption about the agent under evaluation, but its
concern is the integrity of a measurement, not the safety of
a deployment. It does not monitor or edit the agent’s output.
Sandbox technology. Agent benchmarks run tasks in sand-
boxes, often Docker [6], [7], [18]. Containers share the
host’s kernel, so their security rests on how they are config-
ured, and current models can already exploit a misconfig-
ured one [28]. Stronger mechanisms, such as Firecracker
microVMs, isolate each workload in its own lightweight
virtual machine [29]. We build SplitBench on Docker so that
existing benchmark images run unchanged, and we harden
its configuration. Because SplitBench defines its boundaries
independently of the mechanism, a microVM backend could
replace Docker without changing the design.


3. Threat Model and Security Goals
The attacker is a coding agent whose performance is
evaluated on a benchmark. The agent works on a computer
with associated tools, which it uses to produce a solution to
a given task. The grader’s job is to evaluate the proposed so-
lutions in a trustworthy manner. As we show in Section 2.1,
an agent can convince a grader to accept a non-solution in
many ways. We therefore treat the agent and its environment
as untrusted, including any code the agent produces and any
file it touches.
We assume an attacker that may know how its work
will be graded, and that keeps acting through its code
after it stops working (Section 3.1). Against it, we trust
only the isolation mechanism, the benchmark authors, and
the framework’s own components (Section 3.2). From the
known attacks, we derive four security goals that SplitBench
must meet (Section 3.3), and we state which threats we leave
out of scope and why (Section 3.4).
3.1. Attacker Capabilities
The agent knows the public task and can run its own
tests. In Figure 1, we show what it can do in most existing
benchmarks. It may also know how its work will be graded,
because the benchmark’s published material can appear in
its training data or on a site it is allowed to reach. We
assume it knows everything about the grading except its
hidden test data, such as expected answers and unreleased
cases, and any randomness used to generate test inputs.
Any communication path its environment permits, such as
allowed network destinations or the model provider’s API,
which also offers services such as file storage and web
search, is open to misuse.
Grading often runs the agent’s code, so the agent keeps
acting through that code after it stops working. The code
can take over the environment that runs it. It can fabricate
outputs and reports, including outputs in the format the
grader expects, and craft them to exploit the components
that parse and judge them.

3.2. Trust Assumptions
We trust that isolation mechanisms, such as containers
and virtual machines, enforce the boundaries they are con-
figured with. Although cyber-capable agents have escaped
containers [28] and found new bugs in virtual machines [30],
we assume that such bugs are patched through emerging
programs such as OpenAI’s Daybreak and its Patch the
Planet initiative, which use cyber-capable agents for defen-
sive purposes [31].
We also trust the benchmark authors, their task spec-
ifications, and the grading code they write to check the
acceptance conditions. However, we do not trust how the
benchmark executes that code. Many benchmarks run their
tests in the environment the agent modified and so ex-
pose them to these attacks. Finally, we trust the evaluation
framework’s own components, such as those that orchestrate
an evaluation, parse what the agent’s code returns, and
control the agent’s network access. A vulnerability in these
components may compromise evaluation integrity, so attacks
on them remain in scope, such as a malformed file sent to
a parser, an output that makes the grader exhaust memory,
or a request that tries to bypass the network controls.
3.3. Security Goals
SplitBench’s high-level goal is to be a framework that
benchmark authors can adopt. Under this threat model, and
based on the known attacks, we aim for SplitBench to have
the following properties. In Table 3, we map each attack
class of Section 2.1 to the goal it falls under.
•
G1: Mutual Isolation. The agent and the grader run
in separate environments. The agent’s work reaches the
grader through one defined channel, and nothing else
passes between them.
•
G2: Verdict Integrity. Only the grader decides whether
an attempt passes. A false success report from the
agent’s code must not produce a pass, and neither must
data crafted to break the grader. This holds even when
that code controls the environment that runs the tests.
•
G3: Test Case Isolation. If there are multiple test cases
in a benchmark, each case must be isolated from other
cases.
•
G4: Access Control. The agent may only access re-
sources that are explicitly allowed by a configurable
security policy.

3.4. Non-Goals
Some threats are outside the scope of SplitBench.
•
Vulnerabilities in the isolation mechanism. Escapes
that exploit a bug in the isolation technology itself, such
as a vulnerability in the kernel or the container runtime.
SplitBench is responsible for configuring that technol-
ogy so that the agent cannot leave its environment. An
escape made possible by this configuration, such as
through excessive privileges, an exposed host service,
or a missing network rule, is a flaw in SplitBench and
remains in scope.
•
Misuse of an allowed service. A policy over network
destinations cannot control what the agent does within
a service it is allowed to reach (Section 6.2). Besides
reading published material there, an agent could store
data on the service for a later run to retrieve, as agents
were reported to do with a package mirror (Section 2.1).
•
Hardware side channels. We exclude side channels
based on hardware timing or resource contention. Leaks
through software, such as files shared between runs,
remain in scope.
•
Weak acceptance conditions. Whether a benchmark’s
acceptance conditions fully capture the intended task is
the task author’s responsibility. If they are too weak,
an agent can meet them without solving the task as
intended, for example by guessing the answer or taking
a shortcut the authors did not foresee. A grader that
checks only the result cannot tell such a pass from an
intended solution.
•
Published benchmark material. A framework can
keep hidden data out of the agent’s reach but cannot
hide what the benchmark has already published, such as
its tests and solutions. An agent can recall this material
from its training data or look it up on an allowed site,
then reproduce it without solving the task.
4. SplitBench Design
SplitBench isolates the agent under test from the grading
process. The agent works in one environment and its work
is tested in another, and neither of them holds the expected
answers. These stay with a trusted Oracle, which receives
only what the tests return and decides the verdict outside
both. We first walk through this architecture with a running
example (Section 4.1). We then show how SplitBench meets
each of our security goals. We describe what may pass be-
tween the agent and the grader (Section 4.2), how the Oracle
reaches a verdict from results it cannot trust (Section 4.3),
how one test is kept from affecting another (Section 4.4),
and what the agent may reach on the network (Section 4.5).
4.1. Architecture Overview
Every evaluation has two sides (Figure 2). The untrusted
side is the agent and everything it produces. This covers its
workspace, the candidate it leaves behind and the Evaluation
environment that runs the candidate. The trusted side is
the Oracle and SplitBench’s other components. The Oracle
holds the task’s hidden data and issues the verdict. Hidden
data includes expected answers and held-out test inputs. The
other components start the environments, move data between
them and control the agent’s network access.
We call this design split verification. It separates three
activities: working on the solution, running the candidate
and judging it. The Agent environment provides the public
task materials and a workspace in which the agent works on


its solution (step 1 in Figure 2). After the Agent environ-
ment stops, SplitBench captures the files the agent changed
(step 2). These files form the candidate.
SplitBench runs the task’s tests as cases. We call the
original benchmark upstream. A case is one test, or a
group of tests that upstream runs together. For each case,
the candidate receives a challenge. The challenge holds
what the test feeds to the code, without the results the
test expects. A task examines the candidate with one or
more checks (Section 4.3). There are two kinds. A passive
check reads the candidate’s files. An active check runs it.
For an active check, SplitBench first replays the candidate
(step 3): it copies the candidate’s files onto a fresh copy
of the task’s baseline. The baseline is the task’s original
environment image. SplitBench then runs each case in a
fresh Evaluation environment. There, an adapter runs the
candidate on the challenge that the Oracle releases (step 4)
and returns what happened as an observation. SplitBench
reads the observation and, after the case, collects the output
files the task declares (step 5). It validates the resulting
evidence (step 6), and the Oracle judges it (step 7). For a
passive check, steps 3 to 5 are skipped, and the evidence is
the candidate’s files. For an active check, it is the adapter’s
observation and the collected output files.
As a running example, we follow DeepSWE’s abs-
stepped-slices task, introduced in Section 1, through
these steps. ABS is a small scripting language whose inter-
preter is written in Go, and the task asks the agent to add
a step to its slices, as in Python: "abcdef"[::2] must
yield "ace", and [0, 1, 2, 3, 4, 5][::-1] must
return the reversed array. While working, the agent can run
the interpreter on its own expressions, but these runs do not
count toward the verdict (step 1). The candidate is the set
of changes the agent made to the interpreter’s source code
(step 2). SplitBench replays these changes onto the baseline
(step 3), and a setup step builds the modified interpreter
once. The challenge lists ABS expressions taken from the
benchmark’s tests, such as "abcdef"[::2] (step 4). The
adapter runs the interpreter on each expression and returns
the values it produces, without checking them (step 5). After
SplitBench validates the observation (step 6), the Oracle
checks that every value matches the expected one in the
hidden data, such as "ace" (step 7). In Appendix C, we
show one upstream test of this task next to its conversion.
Only the candidate and the evidence can influence the
verdict. The agent reaches the outside through two trusted
components only. A relay forwards its requests to the model
provider. An egress proxy admits only the sites the task
allows. The agent receives no feedback from evaluation.
SplitBench reports results only to the benchmark operator,
the person or team running the evaluation.
4.2. Candidate Capture and Visibility (Mutual
Isolation)
From the agent to the grader. To capture the candi-
date, SplitBench compares every file in the task’s scope,
the directories meant to hold the agent’s work, with the
baseline. Each changed file is recorded in a list called the
manifest, with a digest of its content, and the task limits
how many files and bytes the manifest may hold. In the
running example, the scope is the interpreter’s repository. It
excludes the repository’s Go test files and its build cache,
so test changes and compiled files the agent made during
development stay behind.
The Capture environment reads files the agent controls,
so we treat it as possibly compromised. It runs without
network and executes nothing from the workspace. Split-
Bench then checks what the Capture environment returns
against the scope and limits, and builds the manifest itself.
A manifest that passes describes only files the agent could
have written itself, so compromising the Capture environ-
ment gains the agent nothing. Nothing that was running
in the Agent environment becomes part of the candidate.
Evaluation starts from the baseline and this candidate alone.
The candidate is therefore the only thing that crosses from
the Agent environment into evaluation. This also defeats
the Terminal-Bench attack from Section 1. The replaced
download utility lies outside the scope, so it stays behind in
the Agent environment, where evaluation never runs.
From the grader to the agent. The agent sees only what
the task makes public. Every task resource belongs to one of
three visibility classes. Public materials are mounted in the
Agent environment. Evaluation inputs, such as the adapter,
the setup script, and other helper programs, are mounted
only in the Evaluation environment. Hidden materials, the
expected answers and unreleased cases, never leave the
trusted side.
The Oracle releases only the current challenge. In the
running example, the challenge lists the expressions to
evaluate, such as "abcdef"[::2], while their expected
values stay on the trusted side. The agent itself never sees
a challenge, because it has stopped before evaluation starts.
Its candidate does see the challenge but cannot pass it on.
The Evaluation environment has no network access and is
destroyed when the case ends (Section 4.4).
4.3. Checks, Evidence, and the Oracle (Verdict
Integrity)
The candidate controls the Evaluation environment, so
it can replace the adapter and return any observation. A
forged observation must not decide the verdict. SplitBench
therefore splits each test in two. The adapter runs the code
and reports the values it produced. The Oracle compares
those values with its hidden data.
The adapter contains no expected answers and makes
no decision about correctness. In the running example,
upstream’s Go test runs "abcdef"[::2] through the
interpreter and checks that the result is "ace". The adapter
keeps only the first step. It runs the modified interpreter on
each expression in the challenge and returns what came out,
such as the string "ace" or an error message. The check
against "ace" moves to the Oracle.
Because the Oracle compares values, a falsified report
that the tests passed has no effect on the verdict. Our


conversions make one exception, for regression tests (Sec-
tion 6.2). Among the attacks we run against every conversion
before admitting it (Section 5.1), a candidate that adds a
test file printing a pass for every expected test passes the
native grader and fails SplitBench. A fabricated observation
therefore passes only if it contains the correct outputs for
a challenge the candidate first sees during evaluation. For a
well-tested task, producing those outputs means solving the
task.
A passive check reads the candidate’s files within a size
limit and parses them. It never imports or executes candidate
code. An attempt passes only if every check and every case
passes.
For example, Terminal-Bench’s chess-best-move
task asks the agent to identify winning moves from a board
image and write them to a file. A passive check reads the
captured file within a declared byte limit, and the Oracle
compares its move tokens against the benchmark’s expected
moves, held on the trusted side. Verification does not execute
any program the agent used to find its answer. By contrast,
the ABS task requires an active check because the modified
interpreter must be built and run on each challenge.
Benchmark authors write an Oracle for each task. It
consists of two functions:
•
plan reads the task’s hidden data and the run seed and
produces the list of cases. Each case pairs a challenge
to release with a context that stays on the trusted side,
such as the expected values. The operator must choose
the run seed and keep it secret. When an upstream test
draws random inputs, plan draws them from the seed,
so an agent that knows the Oracle’s code still cannot
predict them.
•
judge compares one case’s evidence with its context
and returns a pass or a failure. It is deterministic.
SplitBench stores the evidence of every case, so any
verdict can be recomputed later. The Oracle’s author
keeps every expected answer in the hidden data and out
of the code. The code then shows how a task is graded
without revealing any answer.
SplitBench restricts what the Oracle can do. It checks the
Oracle’s code before any run and admits only imports that
compute, such as math. This check guards against mistakes
by the Oracle’s author. It does not confine a hostile Oracle.
The Oracle runs on the host in its own process, under limits
on time and memory. If evidence drives judge into a crash,
a hang or a huge allocation, the case fails and the host is
unaffected.
Everything the Evaluation environment returns is adver-
sarial input, crafted by a candidate that knows the public task
and the current challenge. SplitBench accepts evidence only
through a narrow interface. The adapter’s observation must
be a single strict JSON value within a size limit, and it must
match the task’s observation schema. The schema declares
which fields an observation may contain and bounds each
of them, and SplitBench checks against its own copy of
it. An observation never states which case it belongs to.
SplitBench started the environment of each case and reads
the observation from it directly, so it labels the evidence
itself. A compromised adapter therefore cannot present one
case’s evidence as another’s.
Errors inside an Evaluation environment count against
the candidate, because the candidate controls everything
there. An adapter crash, a timeout, a memory kill or a
malformed observation fails the case like a wrong answer.
Only an infrastructure error, such as a failure of the container
runtime, makes an attempt invalid. An invalid attempt has
no verdict and never counts as a pass.
4.4. Fresh Evaluation Environments (Test Case
Isolation)
One case must not affect another. Terminal-Bench’s
polyglot-c-py task shows the risk (Section 2.1). Its
original tests run a program’s Python side and its compiled
C side in one environment, so the Python side can replace
the C binary. Each case of an active check runs in a fresh
Evaluation environment. In the running example, a case
covers the tests that upstream runs together in one go
test command, and evaluates all their expressions in a
single run of the interpreter. Some work does not depend
on any case’s challenge, such as building the interpreter.
SplitBench runs such work once, as a setup step on the
replayed candidate, and saves the resulting environment as a
snapshot. Each case’s environment starts from its own copy
of that snapshot and is destroyed, with everything it wrote,
when the case ends. The setup step receives no challenge,
so cases share only what it built from the candidate. No
environment is ever reused, so a case can leave nothing
behind for the snapshot, another case or a later run. In
polyglot-c-py, the Python side and the C side now
run in separate environments, and the attack fails.
4.5. Network Access Policy (Access Control)
The agent reaches only what the task’s policy allows.
Each task declares one list of allowed network domains
that its Agent environment may reach, such as a package
repository the agent needs. No environment has a direct
route outside itself. The Agent environment has at most
two ways out, both on a private network of its own: the
relay and, for a task that allows any domain, the proxy. The
proxy rejects an allowed name that resolves to an internal
address or whose TLS server name points to a different host.
An allowed name therefore cannot hide another destination.
The relay forwards the agent’s model requests and adds the
provider credentials itself, so the agent never holds a key
it could use elsewhere. By default it forwards only model
inference. This closes two other routes that a provider’s API
offers. The first is storage on a shared account, where one
run could leave objects for another. The second is provider-
hosted tools such as web search or code execution, whose
traffic never passes through the proxy. Firewall rules that
the operator installs on the machine running SplitBench stop
the relay and proxy from reaching that machine or private
address ranges, even if they are compromised.


An allowed domain still gives access to the whole ser-
vice, because the proxy sees where a connection goes but
not what it carries. Section 6.2 discusses this gap.
5. Evaluation
We evaluate SplitBench on tasks converted from existing
benchmarks, and ask three questions:
RQ1
How many tasks of an existing coding-agent
benchmark can be converted to SplitBench, and
why do the others not convert?
180 of the 202 tasks convert. Most of the
others need more than a set of files, such as
a running service, or set a speed target (Sec-
tion 5.1).
RQ2
Does conversion to SplitBench preserve a task’s
verdicts and its difficulty?
Yes. The two graders agree on 98.7% of com-
parisons, and agents pass about as many tasks
under SplitBench as natively (Section 5.2).
RQ3
Can an agent exploit SplitBench’s evaluation
infrastructure to pass a task it has not solved?
Adaptive evaluations found no bypass in
SplitBench. No attempt passed through a flaw
in SplitBench. Most passes exploited weak tests
in the original tasks (Section 5.3).
5.1. Converting the Benchmarks (RQ1)
We convert tasks from two benchmarks that evaluate
frontier coding agents: Terminal-Bench 2.0 [7], which cov-
ers terminal workflows, and DeepSWE v1.1 [8], [9], which
covers long-horizon engineering work in software reposito-
ries. Both use the Harbor task format, and one harness, Pier,
runs and grades both. We call this original grading native.
So that we do not pick the tasks that suit SplitBench, we
sort each benchmark’s tasks by a hash of their names and
attempt them in that order. We learn whether a task converts
while converting it. A task that does not convert is excluded
for one of four reasons: it needs something SplitBench does
not support by design (Section 6.2); it exceeds a limit of
our machine or of task size; the solution that the benchmark
ships with the task fails the benchmark’s own tests; or the
safeguards of the converting model stopped the work.
Converting a task means rewriting how it is graded. The
tests must run without the expected answers, and an Oracle
must judge what they return. By hand, this is engineering
work on every task. We give it to AI coding agents. If
agents can convert a benchmark with little human effort, an
existing benchmark can move to SplitBench without being
rebuilt. We report what the conversion cost at the end of
this subsection.
Two agents share each task. A converter writes the con-
version, and a reviewer that did not write it looks for ways
to break it. The reviewer returns its findings, the converter
fixes them, and the two repeat until the reviewer approves.
Each agent works from a written prompt (Appendix D). We
release both prompts, so others can repeat the conversion or
apply it to another benchmark. Every agent is Claude Opus
5.5 at high reasoning effort.
The converter reads its prompt and the whole upstream
task. The prompt explains how SplitBench grades, the con-
version rules, and how to test a conversion. Its central rule
is that a conversion keeps exactly the upstream task’s cases
and assertions. The converter writes three things: the task
pack, which is the task in SplitBench’s format; a set of test
candidates, described below; and a fidelity record, which
lists every remaining difference from native grading.
The reviewer reads the converter’s prompt, the upstream
task, and the conversion. It asks what a hostile candidate
could do to the conversion, and works through a checklist.
For example, a candidate must not be able to rewrite the
tests, no expected value may leak, and every upstream
assertion must be kept.
A conversion is admitted only after qualification: the
converter’s test candidates run through both SplitBench and
the native harness. There are four kinds. The solution that
ships with the upstream task must pass both graders. A
candidate that changes nothing must fail both. Mutants,
which are plausible wrong implementations, must receive
the same verdict from both graders. They target the conver-
sion’s checks that differ most from the upstream assertions,
for example a tool the conversion reimplements or a numeric
tolerance. Attacks try to pass by tampering with the grading,
for example by rewriting a test’s outcome. The converter
writes them during conversion and tailors them to the task.
Each must fail SplitBench, and we note whether the native
grader accepts it. Mutants test whether the conversion grades
wrong work as upstream does, and attacks test whether its
grading can be tampered with.
Our own part was to write the prompts and to decide
what they left open. We updated the conversion rules during
the campaign, as conversions met situations the rules did
not yet cover. Whenever a rule changed, a fresh agent
brought every earlier conversion it affected in line with it,
and another agent reviewed the result.
Across the 180 conversions, agents spent a median of
just under two hours per task, and most conversions were
approved after two review rounds. We ran the campaign on
two Claude Max subscriptions. At Anthropic’s public API
prices, the converter and reviewer agents would have cost a
median of about $10 per task, and about $3,000 for all 180
tasks. They used 4.8 billion tokens, a median of more than
18 million per task. Of these tokens, 92% are cached context
that an agent rereads at each step. These figures count the
converter and the reviewers of each conversion we kept.
They leave out the coordinating agents and the later work
on a conversion after a rule change.
In Table 4, we report the outcome for every task.
The study supports three conclusions. First, most tasks
convert: 180 of the 202. The largest group of tasks that
do not convert are Terminal-Bench tasks that need more
than a set of files, such as a running service or a priv-
ileged configuration, or that set a speed target. Second,
the native graders are easy to tamper with. Across the


conversions, qualification ran 429 attacks; the native grader
accepted 230 of them, including an attack on Terminal-
Bench’s fix-code-vulnerability task that deletes
the vulnerable file instead of fixing it, and SplitBench ac-
cepted none. Third, conversion needs the loop. The reviewer
returned findings on 173 of the 180 conversions before
approving them. Most findings concerned the fidelity record
or made grading stricter or more lenient than upstream. In
67 tasks at least one was a security problem. One review,
for example, found the memory-exhaustion flaw described
in Section 2.1, which led us to put every Oracle under a
memory limit. One caveat applies to the first conclusion: 87
of the 112 DeepSWE conversions keep upstream’s grading
for their regression tests (Section 6.2).

5.2. Fidelity of the Converted Tasks (RQ2)
A converted task should grade like the original. We test
two properties. The first is verdict agreement: given the
same work, SplitBench and the native grader reach the same
verdict. The second is equal difficulty: agents pass as many
tasks under SplitBench as natively.
We use two agents from different providers: Claude
Sonnet 5.5 through Claude Code, and GPT 6.1 Sol through
Codex. Both run at medium reasoning effort. Each agent
attempts all 180 converted tasks natively and under Split-
Bench. We ran the study twice, so each agent makes two
attempts per task on each side. We then grade every attempt
a second time with the other grader, on a copy of the files
the attempt left. Each attempt gives one comparison between
the two graders on the same files.
Five tasks are left out of the comparison. Their native
tests check something that a copy of the files does not carry:
a server the agent left running, software installed outside
the task’s files, or a file’s permission bits. A copied attempt
always fails these tests, whatever the work. SplitBench still
grades the five tasks; only our comparison cannot cover
them.
Verdict agreement. On the other 175 tasks, the two runs
together give 1,374 comparisons, and the graders agree on
1,356 of them (98.7%): 99.4% for Sonnet and 97.9% for
GPT. Each run has nine disagreements and agrees on 98.7%
by itself. The 18 disagreements fall on eight tasks, and none
comes from an error in a conversion or in SplitBench. In
Table 5, we list them by cause.
In five disagreements, the native grader is wrong: the
tests crashed, and it still counted them as passed. All five
are on one DeepSWE task, claude-code-by-agents-
recursive-delegation. In twelve others, the agent
had changed the test files to fit its own code, or added
tests of its own that do not compile. SplitBench grades
every candidate with upstream’s tests. The native grader runs
whatever test files the agent left, so its verdict differs. In
the last disagreement, the candidate is timing-dependent: its
concurrent parts do not always run in the same order, so the
same files pass on one run of the tests and fail on the next.
The comparison covers only attempts that both graders
graded. Seven GPT comparisons on two tasks are missing
from it. SplitBench rejected their files outright, because they
contained symbolic links that these two conversions do not
accept. This is the same error in both conversions, and the
agreement figure does not reflect it. Another 19 comparisons
on seven tasks are missing for other reasons, such as tests
that hang under both graders and attempts that the provider’s
safeguards refused.

5.3. Adaptive Adversarial Analysis (RQ3)
An adversarial agent tries to make the grader pass work
that does not solve the task. We ask whether it can do so
through SplitBench.
The attacker is Claude Opus 5.5 at high reasoning effort.
Its prompt is the task’s own instructions followed by a
short notice (Appendix D): this is an authorized test of our
benchmark, the goal is a passing verdict, and solving the
task does not count. The real adapter and Oracle grade every
attempt.
The notice also tells the attacker what not to attempt:
escaping its container, attacking the relay, the proxy or
the underlying machine, posting data to outside services,
and escalating privileges. We added this instruction because
the model’s safeguards otherwise stopped the attacker. We
reviewed the code of the relay, the proxy and the container
configuration separately. Escalating privileges inside an en-
vironment gains nothing, because SplitBench already treats
that environment as controlled by the attacker.
The attacker works at one of two levels of knowledge.
With limited knowledge, it has the task and a description
of SplitBench’s design. With full knowledge, it also has the
task’s adapter, the other files used during evaluation, and
the Oracle’s code. It never has the task’s hidden data. Full
knowledge is the worst case our threat model allows. The
attacker makes one attempt per task at each level, 360 in
total. In Table 6, we report how these attempts ended.
We ran the attacker with the Defense Access tier of
Anthropic’s Cyber Verification Program. This tier covers
defensive security work, so the model’s safeguards against
offensive tasks still apply. They stopped 53 of the 360
attempts, usually before the attacker had built anything. We
leave these attempts out, since they say nothing about the
grader.
An attempt succeeds if it passes without solving the task.
For each success we identify one of five causes:
1)
A flaw in SplitBench.
2)
An error in the conversion.
3)
Weak upstream tests. The task’s own tests are too loose
and accept work that does not solve the task. The
original benchmark has the same weakness.
4)
A faked implementation. The candidate takes over the
adapter and produces the observation without the im-
plementation the task asked for.
5)
Public answers only. The pass rests only on answers
that are already public, which the attacker hard-codes
after recalling them from training or finding them
online. Such a pass is out of scope.
Two agents classified each pass independently, from the
attempt’s files, its transcript and both graders’ verdicts on
those files. They gave the same class to all but one pass,
which we settled after a third agent’s opinion.

such as a server that a copy of the files does not carry. In
Terminal-Bench’s count-dataset-tokens, for exam-

the count to a file. The upstream test checks only that the
expected number appears somewhere in the file. One attempt

conversions. The errors show why the loop needs a second
check, and this campaign is that check: it covered every
converted task. A benchmark that adopts SplitBench without
such a campaign should have a person review each conver-
sion before use, as both errors would have been visible to
a careful reader of the conversion.
The last three passes are faked implementations, all
with full knowledge. In each, the candidate did not im-
plement what the task asks for. The adapter has to load
the candidate’s code in order to run it, so this code runs


inside the adapter’s process, and there it gave the tests
the answers they expect by other means. In DeepSWE’s
narwhals-rolling-window-suite, the task is to
add rolling-window statistics to the library narwhals. The
candidate handed the tests’ calls to pandas, a library that
already computes these statistics. In Terminal-Bench’s fix-
code-vulnerability, the task is to make a library
reject header values that contain line breaks. The candi-
date left the library unfixed. Instead, its code replaced the
adapter’s function with one that looks for a line break in
the input and reports a rejection. In DeepSWE’s kcp-go-
multiplexed-kcp-streams, the candidate did not let
the tests run. Its code wrote the observation itself, in the
form the adapter would have returned. The outcomes these
tests expect, such as an error or a blocked call, follow from
the task and the Oracle’s code, so it needed no hidden data
(Section 3.4).
These passes do not make SplitBench weaker than the
native grader. The native grader rejects all three candidates,
but only because their takeovers are written for the conver-
sion’s adapter and do nothing in the native test program. A
takeover aimed at the native grader is easier. The candidate’s
code runs inside the native test program too, and there it
could report a pass without producing any correct value
(Section 2.1). The passes show a limit of what SplitBench
checks: the Oracle judges the values a candidate returns, and
cannot see how the candidate computed them (Section 6.2).
These results answer RQ3. With the knowledge our
threat model allows, the attacker found no way through
SplitBench’s own mechanisms. What remains lies in the
tasks. In at least 34 of the 180, the upstream tests pass
unsolved work, and SplitBench inherits them (Section 3.4).
A smaller campaign on the native graders. We also
ran the attacker on the original tasks, with and without the
native grader’s scripts. The model’s safeguards intervened
in 264 of these 360 attempts, so the campaign covers too
few attempts to support a general claim. Of the 96 attempts
that completed, 71 pass the native grader without solving
the task. We regraded their files with SplitBench, which
rejected 55. Most of these rely on what SplitBench’s design
removes: files planted outside the task’s scope, test files and
test-runner settings supplied by the candidate, and a test
framework taken over by the candidate’s code. The other
16 pass both graders, through weak upstream tests or public
answers.
6. Discussion
Our evaluation shows that most tasks of two existing
benchmarks can be converted to split verification, and that
no attack in our campaign passed through a flaw in Split-
Bench. We now discuss why the design holds and where
it stops. We first ask whether a stronger sandbox alone
would have prevented the attacks of Section 2.1. We argue
that it would not, because these attacks use access that the
benchmark itself grants, and no sandbox takes that access
away (Section 6.1). We then set out what SplitBench and
our evaluation cannot do, including the passes that a grader
judging only outcomes cannot reject (Section 6.2), and turn
these limits into directions for future work (Section 6.3).
6.1. Isolation and Policy
Every SplitBench environment combines an isolation
mechanism, which enforces boundaries, and a policy, which
decides what the environment may reach. The attacks on
grading in Section 2.1 target the policy. The conftest.py
hook, the call-stack read, and the polyglot-c-py binary
swap all run inside the environment the benchmark provides
and use only access it grants: the grader runs where the
agent worked, or trusts what the agent wrote. A stronger
mechanism, such as a microVM, would enforce the same
boundaries more reliably and leave each of these attacks
intact. BenchShield reaches a similar conclusion: moving
the verifier into a separate environment removes most of
the exposure it measures on four of its seven integrity
dimensions, but is not sufficient alone [13]. Split verification
therefore changes the policy. It limits which files cross into
evaluation, what the candidate can reach while it runs, and
which evidence the Oracle accepts.
A policy cannot stop an exploit of the mechanism itself.
In the OpenAI incident, agents exploited a public Linux
kernel vulnerability to act outside a container and obtain
root access on the underlying machine [5]. On Docker,
such an exploit would defeat every boundary SplitBench
configures; our threat model assumes the mechanism holds.
A deployment needs both layers, with the mechanism kept
patched or replaced by a stronger one.
6.2. Limitations
Our evidence is empirical and bounded: two runs in
which the native graders and the converted tasks agree on
98.7% of comparisons, and the rejection of the attacks we
tested. It does not establish equivalence for every possible
candidate or resistance to every attack, and our conclusions
hold only for the qualified tasks, implemented policies, agent
configurations, and attack budgets we evaluated.
Two semantic gaps. SplitBench enforces its policies at
a coarser level than the intent of a task, in two places. The
first concerns access: the proxy admits network destinations,
while what a task needs is expressed as operations on those
destinations. This is an instance of the semantic gap that
Christodorescu et al. describe for agents, where a policy is
expressed at a different level of abstraction than where it
can be enforced [27]. An agent can therefore use a permit-
ted service for an unintended purpose, including reading a
published solution, or attack the service itself. Enforcement
at the level of requests, as ceLLMate does for browser
agents [32], would narrow this gap, at the cost of inspecting
encrypted traffic inside the trusted proxy. The second con-
cerns process: the Oracle judges what the candidate does,
never how the agent produced it. A candidate that meets the
acceptance conditions passes even when it departs from the
intended approach, for example by appending a new sorting
function that replaces the one the task asked the agent to fix.


The benchmark’s native grader would pass such a candidate
too. BenchShield calls this property semantic adequacy and
reports no improvement in any of the evaluated isolation
mechanisms [13].
The three faked implementations of Section 5.3 fall into
this gap. In each task, a candidate that knows the Oracle’s
code can produce the observation the Oracle accepts without
the code the task asked for. Keeping adapters private would
make the adapter harder to recognize but would not close the
gap, and our threat model assumes the agent may know how
it is graded (Section 3.1). Only stricter acceptance conditions
can reject such a candidate, and those are the task author’s
responsibility (Section 3.4).
SplitBench records what a review of the agent’s process
would need: the relay keeps a trusted record of every model
request, and the harness transcript is kept as untrusted data.
Neither affects the verdict because that is handled directly by
the Oracle based on the evidence alone. People or automated
monitors can review these logs to see how an agent solved
a task. CAISI used an AI tool of this kind to find cheating
in its own evaluation transcripts [11]. Such a review could
flag the faked implementations, since their takeover code
appears both in the transcript and in the stored candidate.
Its findings should inform a human decision and not change
the verdict automatically, because the agent writes its own
transcript and could mislead a monitor that reads it.
Public source benchmarks. Both benchmarks we con-
vert are public, as are their tests, so an agent can reproduce
their expected outputs without solving the task. A bench-
mark that needs this protection must keep its test inputs
unpublished, as held-out splits do.
Outcomes reported by upstream runners. Most Deep-
SWE tasks run regression tests, sometimes thousands of
them, which check that existing behavior still works. Con-
verting each one by hand would be costly and add little,
because these tests check behavior the task does not ask
to change, so their conversions accept each regression test’s
outcome as reported by upstream’s own runner. A candidate
can forge those outcomes, as it could natively; the tests of
the requested feature are still judged by value, so a forgery
alone cannot pass such a task.
Unsupported tasks. SplitBench judges only what a
candidate’s outputs show within one case, and the candidate
controls everything inside the Evaluation environment. It
therefore cannot judge a task that needs a trusted record
of effects outside those outputs, actions on the Evaluation
environment such as signals or clock control, a speed tar-
get, network access during evaluation, a property spanning
several fresh runs, or a property of how a computation ran.
Evaluation environments also keep no Linux capabilities,
and replay keeps only file content, type, and the executable
bit. Tasks that need privileged services, or that depend on file
ownership or other permission bits, are therefore excluded.
We report these exclusions in Section 5.1.
Provider-hosted tools. Tools that run on the provider’s
side, such as web search, are disabled by default; when an
operator enables them, their traffic leaves from the provider
and the network policy does not cover it.
6.3. Future Work
We see three directions for future work.
•
Finer network policies. A proxy that admits in-
dividual requests, as ceLLMate does inside the
browser [32], would limit what an agent can do on
a permitted service.
•
Reviewing agent trajectories. Monitors could re-
view the trajectory of each attempt to see how the
agent reached its result, as CAISI did for its own
evaluations [11]. The open question is how to use
their findings while the verdict stays independent of
what the agent writes.
•
Coverage. Our conversion of two coding bench-
marks is a proof of concept, and other benchmarks
could be converted in the same way. SplitBench does
not yet grade a task whose result is a running service.
Agents that operate a computer or a browser, as
in OSWorld [33], raise the same problem, because
many of their tasks end in the state of a running
system, and not only in a set of files.
7. Conclusion
Coding-agent benchmarks run their tests in an environ-
ment that the agent’s work controls, and agents already
exploit this to pass tasks they have not solved. SplitBench
addresses the problem with split verification. The tests run
on a copy of the agent’s work in a fresh Evaluation environ-
ment. A trusted Oracle, which holds the task’s hidden data,
decides the verdict outside that environment.
Existing benchmarks can adopt this design without being
rebuilt. AI coding agents converted 180 of 202 tasks from
Terminal-Bench 2.0 and DeepSWE v1.1, at a median cost
of about $10 per task, and the converted tasks grade like
the originals in 98.7% of comparisons. In an adversarial
campaign of 360 attempts, no attempt passed through a flaw
in SplitBench.
Most of the attempts that did pass exploited the tasks’
own tests. In at least 34 of the 180 tasks, these tests accept
work that does not solve the task, and the original bench-
marks have the same weakness. A secure grader removes
the attacks on grading and leaves this second problem open.
We release SplitBench, the conversion prompts, and the con-
verted tasks so that others can convert further benchmarks
and strengthen their tests.

We will release the full artifact upon publication: Split-

Our study involves no human subjects and no personal
data. All experiments ran inside containers we controlled,
and the adversarial agents worked only against graders
running there.

Bench 2.0 and DeepSWE v1.1 without solving them. Their

they put no user or system at risk. The weaknesses found in
the native graders are already public through earlier audits.

and the latest adopts a hardened grader.
Our release contains every passing attack, so the main-
tainers and others can check and fix the affected tests.

Appendix C.
A Conversion, Side by Side
In Figure 3, we show how one upstream test of our
running example, abs-stepped-slices, becomes part
of a SplitBench case. The upstream test keeps its inputs, its
expected values, and its assertions in one file, and that file
runs in the same environment as the agent’s code. The con-
version separates the three. The inputs and expected values
move to the task’s hidden data. The Oracle’s plan function
sends only the inputs to the Evaluation environment, as
the challenge. The adapter evaluates each input with the
candidate’s interpreter and reports the type and value of
each result. The Oracle’s judge function then applies the
upstream test’s three branches to that report.
The complete conversion covers upstream’s 12 tests and
their 109 inputs in four cases. Its adapter is 57 lines of
Python with a Go program of 244 lines that calls the
interpreter, and its Oracle is 259 lines of Python.
