Abstract—The growing complexity of electronic systems de-
mands efficient design flows, yet EDA scripting remains a bot-
tleneck: proprietary APIs are sparsely documented, and errors
often appear as silent failures or cryptic exceptions. Hand-
crafted knowledge helps but is difficult to maintain as toolchains
evolve. We present ZhuLong-SE (Self-Evolution), an execution-
grounded LLM agent that learns reusable knowledge from prior
task traces. Building on ZhuLong [1], it enhances the task-level
harness with API retrieval, documentation responses, isolated
sandbox execution, and static checking, then adds governed cross-
task self-evolution. Beyond solving individual tasks, ZhuLong-
SE distills past execution traces into a three-tier memory store
governed by ground-truth anchoring, disconfirmation filtering,
held-out rollback, and anti-leakage retrieval. On the 158-task
EDA-Eval-PyAether benchmark, the full task-level harness, with
self-evolution disabled, achieves 92.4% pass@1 and outperforms
ZhuLong on all five tested LLM backbones. On a harder
instance-disjoint test set, self-evolution from the bare config-
uration surpasses a human-crafted-experience baseline by 2.5
percentage points (80.0% vs. 77.5% pass@1).

I. INTRODUCTION
EDA scripting is challenging because tool APIs are tool-
specific, sparsely documented, and exposed through SWIG
bindings whose type rules differ from native Python. Zhu-
Long [1] is the first work that established an execution-
grounded LLM agent for EDA scripting that combines
API retrieval, documentation inspection, and sandbox ex-
ecution via unified MCP tools, augmented by an offline
API self-exploration mechanism that infers undocumented
API behaviors through counterfactual experimentation. On the
EDA-Eval-PyAether benchmark, the system achieved 78.5%
pass@1, substantially outperforming a pure LLM baseline
of 23.6%. However, a critical limitation remained: the agent
solved each task independently and did not learn from past
execution traces, so its performance on new tasks did not
improve over time.
Building on this task-level substrate, we introduce self-
evolution: an offline system that distills execution traces
into reusable knowledge and re-injects it into future tasks,
with reliability gates that prevent unverified experience from
misleading the agent. To provide reliable signals for self-
evolution, we introduce a precision-optimized static checker
for deterministic API misuse. It raises no error flags on
the 158 benchmark ground-truth solutions, a sanity check
limited to this reference-code set. Applying self-evolution
to EDA scripting introduces two challenges. First, feedback
is very sparse: the agent receives only a binary pass/fail
from the hidden verifier. This is different from methods like
SkillOpt [2], which assume dense per-step rewards. Without
careful verification, distilled experience can mislead. Second,
instance-disjoint evaluation risks cross-split answer copying: a
held-out task may copy a training sibling’s verbatim solution
rather than transferring the underlying method, a problem
recently observed in EvolveMem [3].
We present ZhuLong-SE (Self-Evolution), which extends
the ZhuLong task-level substrate with enhanced API retrieval
and documentation responses, improved sandbox isolation,
and precision-optimized static checking, and then adds a self-
evolution layer with reliability gating. To handle sparse feed-
back, we introduce ground-truth anchoring, scope-boundary
reflection, disconfirmation-based filtering, and a held-out val-
idation loop that rejects degrading rounds. Beyond post-hoc
evaluation gating, we design structural anti-leakage retrieval
via names-only injection and deterministic docstring general-
ization to reduce the risk of cross-split answer copying. These
mechanisms are designed to provide methodological signals
without injecting full call sequences, while an evolution round
is retained only when held-out validation does not degrade
beyond the acceptance threshold. On the held-out test set,
this design achieves a higher mean pass@1 than the human-
crafted-experience baseline.
Our contributions are as follows.
• Self-evolution as a design methodology for EDA au-
tomation. We establish self-evolution—distilling execution
traces into reusable knowledge and re-injecting them into
future tasks—as a systematic methodology for system-level
EDA scripting. To make it deployable under EDA’s sparse
feedback and opaque commercial APIs, we introduce three
governance rules: ground-truth anchoring, on-demand pitfall
retrieval, and validation-gated rollback.
• A rigorous evaluation protocol against cross-split leak-

age. We expose cross-split answer copying as a threat
to trustworthy self-evolution evaluation, and propose a

• Counterintuitive design insights from controlled abla-

II. RELATED WORK
A. LLM for EDA Scripting
LLMs for chip design have largely targeted RTL genera-
tion: ChipNeMo, RTLCoder, AutoChip, and CodeV-R1 [4]–
[7] domain-adapt or fine-tune models for Verilog, relying
on human-constructed testbenches, which is orthogonal to
operating an EDA tool’s API surface. The procedural-scripting
strand has grown quickly: ChatEDA, ChaTCL, EDA-Copilot,
iScript, FluxEDA, JARVIS, and AutoEDA [8]–[14] span
flow planning, Tcl/Q&A assistance, multi-agent collaboration,
single-turn generation, and execution infrastructure. Within
this strand, ZhuLong [1] is the direct precursor to our work:
it combines API retrieval, documentation inspection, sandbox
execution, and offline API self-exploration, but solves tasks
independently without reusing execution traces across tasks.
Another closely related system is OpenROAD Agent [15],
which adds execution-feedback self-correction on an open
physical-design tool, but fine-tunes the model and does not
externalize cross-task experience. Our scenario shares its
generate-execute-revise shape yet keeps the model frozen and
judges pass/fail by real sandbox execution with hidden tests—
addressing cross-task reuse through self-evolution rather than
fine-tuning. The Agentic EDA survey [16] situates this line at
L3 autonomy. Two gaps recur for a frozen-agent, hidden-test
setting: none externalizes cross-task experience into a reliable,
leakage-controlled store, and none carries a domain-level static
check beyond the tool’s own schema—both of which our
system addresses.
B. Self-Evolving Agents with Governed Memory
A broad family of works equips agents with reusable exter-
nal memory: skill libraries, cross-task insight distillation, hier-
archical memory, and cognitive architectures [17]–[20], with
CodeAct [21] unifying the action space as executable Python.
The survey by Zhang et al. [22] provides a comprehensive tax-
onomy of memory mechanisms for LLM agents. These works,
however, generally assume an open world or a train/test-
disjoint split, which sidesteps the same-task regression signal
that our fixed-set setting must surface. DemoEvolve [23] ex-
plicitly studies sparse terminal feedback in harness evolution,
but addresses it through human demonstrations—whereas our
setting assumes no such external guidance.
Treating the skill store as an optimization target, Skil-
lOpt [2] edits a single skill document under a held-out gate
and observes that “plausible textual diagnoses can still hurt,”
echoing our concern that unverified experience can mislead.
SkillOS [24] learns curation via RL with a four-dimensional
judge, and Trace2Skill has been explored in two complemen-
tary forms: Ni et al. [25] propose a general framework that dis-
tills execution trajectories into reusable skills through parallel
trajectory analysis and inductive pattern consolidation, using
a verifier primarily for quality filtering of the extracted skills;
Du and Pinckney [26] present a test-time scaling framework
for hardware agents where dense verifier feedback actively
drives the oracle-mutator-selector evolution loop. These works
optimize on disjoint splits with relatively dense signal, whereas
our sparse-pass/fail, fixed-set setting makes which-experience-
to-trust more pressing than how to edit a document.
Verifier-guided evolution brings the reward signal closer to
our hidden-test setting. ReVeal [27] self-generates test cases
for dense rewards, but self-generated tests can be gamed and
do not substitute for a hidden verifier. Du and Pinckney [26]
share our hidden-verifier, no-answer framing but run online per
task with physical isolation and task-wise skills; their finding
that cross-task transfer is unreliable for heterogeneous RTL
cautions how far logical-error knowledge should travel—a
concern we address through governed memory and anti-
leakage retrieval. EvoAgentBench [28], the most comparable
benchmark, formalizes this tension with an ability-supported
yet instance-disjoint split, finding that an Anchor Skill oracle
helps while no automatic method sustains the gain.
Several works inform the governance machinery underly-
ing our approach: MUSE-Autoskill [29] on refinement and
reflection, Externalization [30] and Reflexion [31] on memory
artifacts and same-task iteration, and Governing Evolving
Memory [32] on System-2 verification. LastingBench [33]
proposes counterfactual rewriting to safeguard benchmarks
against knowledge leakage, underscoring the importance of
our anti-leakage retrieval design. The central lesson is that
evolving memory requires an external gate grounded in ground
truth to remain reliable. Our method addresses this challenge
under sparse pass/fail supervision and strict anti-leakage con-
straints.

A. API Retrieval
ZhuLong provides a single search_apis MCP tool that
uses semantic retrieval [1]. ZhuLong-SE retains its embedding-
based semantic path, adds a dedicated keyword-oriented tool
(search_apis_by_keyword), and supplements matches
missed by the summary with a BM25 pass over the full
description text. The keyword path targets queries that the
semantic index handles poorly, such as abbreviations and
camel-case fragments. The index tokenizes each API name
by splitting on camel-case boundaries and stripping family
prefixes. The query is bidirectionally expanded for abbrevia-
tions (e.g., CV↔CellView, crt↔create), enabling matches on
abbreviated tokens inside API names. Depending on query
type, a router expands abbreviations, returns direct-match hints
for API-name fragments, or appends semantic results for
natural-language queries. Finally, a cross-family synonym map
links four functionally equivalent API families (db*, emy*,
goa*, ae*), so a hit in one family surfaces equivalents in the
others, addressing the failure mode where an agent recalls the
correct operation but selects the wrong interface family.
B. Documentation Enrichment
ZhuLong’s get_api_details returns parameter types,
return values, examples, and inferred constraints [1], but
its per-API pages do not expose class instance properties.
ZhuLong-SE therefore parses the raw documentation into
a property table and appends it to each detailed response,
so a queried class exposes its instance attributes alongside
its methods. Constructor notes also disambiguate ambiguous
calls: for example, emyPointArray accepts a plain list of
points, a fact the per-signature page does not state.
C. Sandbox Execution
We run multiple isolated sandbox endpoints, each with an
independent working directory, and dispatch requests through
a queue pool. A routine clears working directories before each
run and resets library files to minimal content, so prior runs do
not bias subsequent ones. This isolation ensures that execution
feedback reflects the current code under test, not residual
state from earlier tasks. The queue pool enables concurrent
evaluation without changing ZhuLong’s per-task interaction
protocol [1].
D. Static Checking
Because PyAether’s SWIG bindings expose all symbols at
import time regardless of whether the underlying function
exists at runtime, an agent may call a fabricated API or pass a
native Python value where a SWIG-wrapped type is required
without triggering any runtime error during self-test—yet the
submission fails the hidden test that exercises that path. To
catch such failures before submission, we introduce a static
checker that runs after the agent’s self-test and before final
submission.
The checker parses submitted code into an abstract syntax
tree, extracts API calls, and checks four documented misuse
patterns: (i) fabricated APIs, (ii) incorrect keyword argu-
ments, (iii) native Python values passed where explicit SWIG-
wrapped construction is required, and (iv) silently swallowed
exceptions. Actionable findings are returned to the agent for
repair before final submission. The rules are derived from
the API documentation and refined on real submissions. As
a reference-code sanity check, the checker raises no flags on
any of the 158 ground-truth solutions. This result is limited to
that set and is not a general zero-false-positive guarantee.
E. Human-Crafted Experience
ZhuLong-SE additionally injects four skills and one rule
file authored from PyAether development experience rather


than specific benchmark solutions. The skills cover API search,
command-family selection, interpretation of silent or ambigu-
ous sandbox feedback, and explicit SWIG type construction.
The rule file requires API-detail checks before use, post-
creation verification, and bounded search, providing a stable
prior that complements knowledge learned from the execution
traces.
IV. SELF-EVOLUTION
Unlike ZhuLong’s offline API self-exploration, which aug-
ments per-API documentation through counterfactual sandbox-
ing [1], ZhuLong-SE adds a cross-task offline self-evolution
system (the blue-highlighted block at right in Figure 1). It
distills task execution traces into reusable knowledge and re-
injects it into later tasks. Knowledge is organized in three tiers,
following the episodic-semantic-procedural memory distinc-
tion [20]: L0 holds raw traces, L1 stores aggregated patterns,
and L2 archives distilled skill versions. Within L1, patterns
are partitioned into four layers: solution (verified API routes),
pitfall (negative warnings), meta (effective query patterns), and
strategy (decision records). The write side runs offline after
each training batch, and the read side injects knowledge at
task formatting and on demand when the agent hits an error.
The write, promotion, and round-acceptance stages apply reli-
ability gates, as unvalidated experience can mislead [2], [18].
Distillation and state updates run offline. During inference,
the accepted memory is queried locally, without additional
evolution or distillation.
A. Distillation and Reflection
The write side routes each task to the appropriate reflection
path. We override the agent’s self-reported success with the
evaluator’s binary verdict before any reflection begins, follow-
ing Reflexion’s observation that reliable feedback is necessary
for reflection to help rather than harm [31]. Tasks that still
error on their final attempt take the error path; tasks whose
self-test passed but the evaluator failed take the contradiction
path instead. This distinction is critical because a self-test-
passed task’s error log contains only stale errors; mining
pitfalls from these would record already-solved bugs rather
than genuine gaps in the agent’s knowledge. Each L1 entry
carries a reliability tier: verified, unverified, or pitfall.
B. Knowledge Lifecycle with Reliability Gating
Extracted L1 patterns undergo aggregation, gating, aging,
and promotion to rules and skills. A verified entry is discon-
firmed only when a failed task is an API misuse precisely
attributed to that entry; at a count of two or more, the entry
is filtered out. Unverified traces cannot downgrade verified
entries, and entries not re-confirmed for five rounds drop
to unverified. Promotion is guarded by a four-dimensional
judge (abstraction, reusability, actionability, faithfulness) fol-
lowing SkillOS [24], and a MUSE-style create-evaluate-refine
loop [29] for low-scoring candidates. We add a zero-exception
generality gate that rejects rules whose always/never state-
ments do not hold across the entire API surface, ensuring that
distilled rules remain broadly applicable rather than overfitting
to specific task patterns.
C. Anti-Leakage Retrieval
Under an instance-disjoint split, naive retrieval risks cross-
split answer copying. We prevent this through three mech-
anisms. Names-only pre-injection reduces a solution entry
to API names only, dropping call order and parameters. De-
terministic docstring generalization strips task-identifying
specifics from both distillation and query sides. Problem-side
embedding matches on problem similarity while returning
solution metadata only at read time. Pitfalls are not pre-
injected; they enter through on-demand runtime queries keyed
to the agent’s actual error.
D. Held-Out Gated Evolution
After each training round, the agent generates on valida-
tion tasks (which never carry distillation). The round’s full
evolved state is accepted only if the validation pass rate does
not regress by more than 5 pp against the previous round.
Otherwise, it is rolled back. This extends SkillOpt’s held-out
criterion [2] from a single document to the entire evolved
state.
V. EXPERIMENTS
We evaluate ZhuLong-SE on EDA-Eval-PyAether, the 158-
task real-world PyAether scripting benchmark introduced by
ZhuLong [1]1. Each task is a natural-language docstring plus
a function signature, and a submission passes only if real
sandbox execution satisfies a hidden test (the black-box ver-
ifier). The primary model is DeepSeek-V4-Pro-Preview. The
human-crafted experience consists of four skills and one rule
authored by a senior EDA engineer with extensive experience
in PyAether development.
The experiments have two parts. First, on all 158 tasks, we
ask whether the enhanced ZhuLong-SE harness outperforms
the original ZhuLong across matched LLM backbones and
which measured harness components contribute to the gain.
Second, after removing human-crafted experience, we ask
whether governed self-evolution can match or surpass the
human-crafted-experience baseline.

crafted experience. We first compare this configuration with
the published ZhuLong baseline and then decompose the
measured components under the primary backbone. No self-
evolved knowledge is injected into any result reported in this
subsection. For each comparison, the backbone version and

B. Self-Evolution
To evaluate self-evolution without ceiling effects—the Bare
agent already passes 87% of the 158 tasks—and to support
held-out gating, we adopt an instance-disjoint challenge split
(train 98 / val 20 / test 40), in the spirit of EvoAgentBench’s
ability-supported yet instance-disjoint split [28]. The split is
stratified so that the test set concentrates more discriminative
tasks, identified by testbench code length and the number
of unique APIs used. Because the validation and test sets
are small, every self-evolution evaluation is the mean of five
independent runs with its standard deviation.

Ground-truth anchoring has the clearest observed effect:
without it, 12 of 24 tasks yield at least one falsely verified
entry because the trace’s self-reported success is trusted. The
net count rises by 11 rather than 12 because one such task
produces no entry under correct anchoring. Disabling the
contradiction path produces 17 additional entries by mining
stale, already-repaired errors, while disabling routing sends
failed tasks to the success branch and produces no pitfalls.
These entry-count results characterize how the three gates alter
reflection output. They do not constitute an end-to-end quality
comparison.
The remaining two write-side gates cannot be evaluated by
this design. Scope-boundary reflection changes the precon-
ditions and constraints recorded within an entry rather than
the entry count, so the reported metric cannot identify its
effect. The disconfirmation filter removes an entry only after
disconfirmation in at least two batches; no entry can reach
that threshold in this single-round replay. Their value therefore
remains unverified here and requires content-level assessment
and multi-round accumulation, respectively.
We also ablate each of the four read-side mechanisms
from Section IV-C (names-only pre-injection, docstring gen-
eralization, problem-side embedding, and the decision not
to pre-inject pitfalls) by freezing the Round 2 knowledge
and varying the injection configuration, then re-running the
agent on validation (baseline 88.0%±2.7). Table V isolates
each. Pre-injecting pitfalls is the most harmful (−8.0 pp):
a task’s description does not predict which API it will mis-
use, so a recalled pitfall is usually off-target, confirming the
choice to route pitfalls through the runtime query instead.
Docstring generalization (−6.3 pp when disabled) and names-
only injection (−4.7 pp when full-sequence injection is used)
each contribute—the former because disabling it breaks the
query-embedding symmetry, the latter because a full call
sequence over-specifies and misleads. The embedding strategy
(embedding the problem summary vs. the solution text) shows
no measurable effect here, which we attribute to names-only
injection: under this reduction, the retrieved content is the
same regardless of embedding, so the embedding choice is
dominated by the names-only reduction. The problem-side
embedding is therefore justified by its anti-leakage role rather
than by a measurable Pass@1 gain in this configuration.

VI. CONCLUSION AND FUTURE WORK
We presented ZhuLong-SE (Self-Evolution), which aug-
ments ZhuLong [1] with task-level harness enhancements and
governed cross-task evolution while keeping the backbone
frozen. On the 158-task EDA-Eval-PyAether benchmark, the
full task-level harness achieves 92.4% pass@1 in a single


full run and outperforms ZhuLong on all five backbone
comparisons. On the 40-task instance-disjoint challenge test,
self-evolution from the Bare configuration achieves 80.0%
mean pass@1, compared with 77.5% for the human-crafted-
experience baseline. The frozen-trace ablation identifies the
effects of ground-truth anchoring, contradiction handling, and
routing on reflection output, while leaving scope-boundary
reflection and multi-batch disconfirmation unverified under
its entry-count, single-round design. Future work will extend
the evaluation to additional EDA tool flows and languages,
including SKILL-based automation, and to larger task sets,
while investigating adaptive gating thresholds that adjust to
task difficulty.
