Rethinking ANNS on Commodity PIM: PIM-Native
Vector Search with Cooperative Filtering
Dawei Guo, Yizou Chen, Fan Yang, Hui Li, and Ming-Chang Yang
The Chinese University of Hong Kong
{dwguo25, chenyz, fyang24, hli, mcyang}@cse.cuhk.edu.hk
Abstract—Approximate nearest neighbor search (ANNS) is a
key primitive in modern data-intensive systems, and its memory-
bound vector-scanning stage makes processing-in-memory (PIM)
a promising acceleration platform. Existing PIM-based ANNS
systems largely transplant CPU-oriented distance evaluation and
top-k selection onto PIM, introducing arithmetic- and state-
heavy operations that poorly match lightweight, isolated PIM
cores. To address these mismatches, we present PIVOT, a PIM-
native Vector search system with cOoperative filTering, which
thoroughly rethinks how ANNS should be executed on commodity
PIM. First, PIVOT recasts PIM-side distance evaluation around
binary quantization to exploit PIM-native bitwise operations,
enabling LUT-free evaluation with low arithmetic cost and a
small local-memory footprint. Second, PIVOT redesigns PIM-side
candidate selection around threshold-guided cooperative filtering,
using a survivor-mass model to derive a conservative threshold
for CPU-side cluster filtering and PIM-side lower-bound filtering,
thereby reducing output traffic and eliminating per-core top-k
state. PIVOT organizes these stages into a cooperative workflow
that keeps query-global coordination and reranking on the
CPU while assigning memory-intensive, data-parallel filtering
to PIM. To efficiently realize this workflow and sustain high
utilization across devices, PIVOT further generates configuration-
specialized PIM kernels and pipelines CPU-side preparation
and reranking with PIM-side filtering across query batches.
Evaluations on real UPMEM hardware show that PIVOT filters
out 99.3–99.7% of probed vectors and achieves up to 18.8× and
10.2× the QPS of CPU and prior PIM baselines, respectively.
PIVOT also achieves higher recall than existing PIM systems and
remains effective on high-dimensional embeddings.
I. INTRODUCTION
Approximate nearest neighbor search (ANNS) has become
a key primitive in modern data-intensive systems, including
retrieval-augmented generation (RAG) [20], [28], [33], vector
databases [18], [50], [59], recommendation systems [9], [55],
and large-scale semantic retrieval [43], [45], [54]. Existing
ANNS methods are commonly grouped into cluster-based,
graph-based, and hashing-based families [1], [4], [51]. Among
them, cluster-based methods are widely used in billion-scale
and production systems, most commonly in the form of
inverted-file (IVF) indexes, due to their compact index struc-
tures, controllable search cost, and sequential, highly parallel
scan patterns [24], [25], [50]. At large scale, however, cluster-
based ANNS spends substantial time scanning IVF lists,
placing heavy pressure on memory bandwidth and expos-
ing the von Neumann bottleneck [6], [8], [36], [52], [53].
Processing-in-memory (PIM) therefore offers a promising way
to accelerate large-scale cluster-based ANNS by executing this
scan close to data [17], [21], [40].

Commodity PIM systems place many lightweight process-
ing units (PUs) close to memory, reducing data movement
and providing high aggregate memory bandwidth [10], [21],
[29], [30]. Their architecture, however, differs substantially
from that of CPUs. Because compute logic must coexist with
dense memory arrays under stringent area, power, thermal,
and timing constraints, commodity PIM typically integrates
simple memory-side cores with modest arithmetic capability
and limited local working memory for runtime state and
buffering. PUs also operate independently, with no shared
memory or direct inter-PU communication, making global
synchronization and distributed state management costly [10],
[21]. These characteristics limit the effectiveness of directly
transplanting CPU-oriented workflows. Fully exploiting PIM
therefore requires a PIM-native execution path that keeps
query-global control on the CPU and maps arithmetic-light,
state-light, and independently executable work to the PUs.
Existing PIM-based ANNS systems have demonstrated the
potential of memory-side acceleration for large-scale vector
search [6], [8], [36], [52]. These systems adapt conventional
IVF-based cluster-search pipelines to PIM through PIM-
specific designs for data placement, query scheduling, and
resource management. However, their vector-scanning and
candidate-selection workflow still retains two CPU-oriented
design choices that are poorly matched to commodity PIM
architectures, as summarized in Table I and examined in
Section III. First, distance evaluation often relies on floating-
point or multiplication-intensive computation and, in PQ-based
designs, query-dependent lookup tables, consuming substantial
processing cycles and local-memory capacity. Second, candi-
date selection retains a top-k ranking paradigm designed for
shared-memory CPUs, where ranking state can be efficiently
managed in shared memory. On PIM, however, distributing
a query across isolated PUs decomposes the global ranking
into replicated local top-k buffers with synchronized updates,
causing ranking state and partial-result traffic to grow with the

These observations lead us to rethink ANNS execution on
commodity PIM. We argue that a PIM-native ANNS pipeline
should follow two principles. First, the PIM-side distance-
evaluation kernel should favor arithmetic-light, PIM-native
operations and compact runtime state. Second, candidate se-
lection should replace distributed top-k ranking with a query-
specific threshold that enables stateless, independent filtering
across PUs. Realizing these principles requires careful CPU–
PIM work partitioning according to the strengths of each side.
Based on these principles, we propose PIVOT, a PIM-
native Vector search system with cOoperative filTering. For
PIM-native distance evaluation, PIVOT builds on RaBitQ-
style binary quantization and redesigns the corresponding
distance-evaluation kernel with centered query quantization
and reduced-precision FastFloat reconstruction, yielding a
LUT-free calculation dominated by PIM-native bitwise and
integer operations [13], [15], [16]. To eliminate distributed
top-k ranking, PIVOT replaces ranking with threshold-guided
cooperative filtering. Specifically, PIVOT introduces a query-
aware threshold estimator that combines per-cluster residual
statistics with query-to-centroid distances to derive a conserva-
tive query-specific radius τ and estimate the expected survivor
contribution of each probed cluster. Using these estimates, the
CPU first suppresses low-yield clusters before dispatch. The
PUs then stream PIM-resident compact codes, independently
reject candidates whose squared-distance lower bounds exceed
τ 2, and return only survivor identifiers for CPU reranking.
PIVOT further pipelines consecutive query batches, overlap-
ping CPU-side routing, threshold estimation, and reranking
with PIM-side filtering. Together, these mechanisms address
the two architectural mismatches while keeping the PIM-side
hot path arithmetic-light, state-light, and streaming-oriented.
This paper makes the following contributions:
• We identify two architectural mismatches in exist-
ing PIM-based cluster search: arithmetic-heavy, LUT-
dependent distance evaluation, and distributed top-k rank-
ing with synchronization, replicated state, and communi-
cation overhead (Section III).
• We propose PIVOT, a PIM-native ANNS system with
cooperative filtering. It combines a PIM-native lower-
bound evaluation kernel with a query-aware threshold
estimator to enable cooperative CPU-side cluster filtering
and independent PIM-side vector filtering (Section IV).
• We implement PIVOT on UPMEM with configuration-
specialized PIM kernels and pipelined CPU–PIM execu-
tion (Section V).
• We evaluate PIVOT on billion-scale datasets. Unlike
prior PIM systems whose PQ and local top-k designs
limit scalability toward practical high-recall operation,
PIVOT consistently delivers a stronger throughput–recall
tradeoff, with its throughput advantage widening as recall
increases. It achieves up to 18.8× and 10.2× the QPS
of the CPU and PIM baselines, respectively, making
commodity PIM more practical for real-world ANNS
workloads (Section VI).

II. BACKGROUND
A. Commodity PIM Architecture
Commodity PIM systems integrate many lightweight pro-
cessing units (PUs) close to DRAM banks to reduce off-
chip data movement and provide high aggregate memory
bandwidth [10], [29], [30]. UPMEM PIM [10], illustrated in
Figure 1, is the first publicly available programmable com-
modity DRAM-PIM system and the hardware substrate used
by most prior real-hardware PIM-based ANNS systems [6],
[8], [36], [52]. We therefore use UPMEM as a representative
evaluation platform, while our design principles target broader
commodity-PIM architectural tradeoffs and extend beyond this
specific platform.
A UPMEM-enabled system consists of a host CPU and
multiple PIM DIMMs connected through standard memory
channels. Each PIM DIMM integrates many DRAM Pro-
cessing Units (DPUs), each operating on a private 64 MB
DRAM bank referred to as MRAM. A DPU also contains a
lightweight in-order processor, 64 KB of software-managed
scratchpad memory (WRAM) for local state and buffering,
and 24 KB of instruction memory (IRAM). Multiple tasklets
share the DPU pipeline and WRAM, with their execution
interleaved to improve pipeline utilization and hide memory-
access latency [10], [21], [22].
Because compute logic must coexist with dense memory
arrays under tight area, power, thermal, and timing budgets,
commodity PIM trades per-core complexity, fast local storage,
and communication flexibility for large-scale memory-side
parallelism [29], [30], [39]. These tradeoffs directly shape the
PIM programming model:
Modest arithmetic capability: Complex arithmetic units
consume additional area and power, so memory-side cores
favor relatively simple instruction sets. On UPMEM, inte-
ger addition, bitwise operations, and shifts are efficiently
supported, whereas floating-point operations are emulated in
software and full-width multiplication and division require
longer instruction sequences [21], [47]. Kernels dominated
by floating-point or multiplication-intensive computation can
therefore quickly exhaust DPU arithmetic throughput [44].
Limited local runtime memory: SRAM is substantially
less dense than DRAM and becomes costly when replicated
across many memory-side cores. Commodity PIM therefore
provides only a small amount of fast local memory, such
as WRAM on UPMEM. Data processed by a DPU must be
explicitly transferred between MRAM and WRAM through
DMA operations [10], [22]. WRAM is shared by all tasklets
2


and must accommodate tasklet stacks, temporary buffers, and
runtime state. Large lookup tables or replicated per-tasklet
buffers can therefore exhaust WRAM, reducing tasklet con-
currency and limiting supported workload configurations [8],
[11], [21].
Restricted communication and coordination: Providing
coherent shared memory or direct communication among
thousands of memory-side cores would incur substantial hard-
ware overhead [41]. Consequently, different DPUs do not
share memory or communicate directly. Global reductions,
shared-state updates, and inter-DPU data exchange must be
mediated by the host CPU through explicit transfers [26].
Within a DPU, UPMEM supports synchronization among
tasklets, although frequent synchronization can reduce tasklet-
level parallelism [21], [47].
These characteristics create a programming model substan-
tially different from conventional CPU execution. Efficient
commodity-PIM execution therefore requires rethinking appli-
cation workflows and the CPU–PIM boundary, keeping global
control and coordination on the CPU while structuring PIM-
side execution around streaming, arithmetic-light, and low-
state kernels [26].
B. Cluster-Based ANNS
Given a query vector q, top-k ANNS seeks to return
the k database vectors closest to q. Cluster-based methods
commonly organize the search using an IVF index [24],
[25]. During indexing, database vectors are partitioned into
nlist clusters, typically using k-means, and each cluster is
represented by a centroid and an inverted list. The vectors
are typically encoded into quantized representations to re-
duce index size and distance-evaluation cost. At query time,
search typically proceeds in three stages. First, coarse routing
computes query-to-centroid distances and selects the nearest
nprobe lists. Second, vector scanning and candidate selec-
tion evaluates distances using the quantized representations in
these lists and retains the closest candidates in a bounded pool.
Third, because quantization introduces approximation error,
reranking reevaluates this pool using a more accurate repre-
sentation, such as a less compressed quantized representation
or the original full-precision vectors, before returning the final
results.
Vector quantization and evaluation kernels: Direct L2
evaluation over full-precision vectors performs floating-point
subtraction, multiplication, and accumulation across every di-
mension. Scalar quantization reduces storage and computation
costs by mapping each coordinate to a low-precision value,
such as INT8. To achieve higher compression and faster eval-
uation, product quantization (PQ) divides each vector into M
subvectors and encodes each with its nearest codeword [25].
For each query, PQ constructs query-dependent lookup ta-
bles and evaluates each vector through M lookups and ac-
cumulations. Binary quantization methods such as RaBitQ
further compress vectors into compact bit strings and estimate
distances mainly through bitwise operations and population
counts, together with limited auxiliary metadata [15], [16].
RaBitQ also provides a probabilistic error bound at a specified
confidence level, enabling a conservative lower bound on the
true squared Euclidean distance to be derived.
Top-k candidate selection: Conventional CPU-based IVF
search follows a score-then-rank workflow. As vector distances
are evaluated, the system maintains a bounded max-heap
containing the closest candidates found so far. The heap is
updated whenever a closer candidate is discovered. Bound-
based methods such as RaBitQ can use the largest retained
distance at the heap root as a dynamic pruning threshold.
If a vector’s distance lower bound exceeds this threshold, it
cannot enter the candidate pool, allowing further evaluation or
reranking to be skipped [15], [16]. When reranking is used,
the system retains more than k candidates, reevaluates them
using a higher-fidelity representation, and selects the final top-
k results according to the refined distances.
C. Existing ANNS Systems on Commodity PIM
The vector-scanning stage of cluster-based ANNS generates
substantial memory traffic and exposes abundant parallelism
across inverted lists and their vectors, making it a natural
target for commodity PIM. Existing PIM-based ANNS sys-
tems follow this approach by accelerating the scan stage of
IVF-based pipelines on memory-side processors [6], [8], [36],
[52], while retaining query-global operations such as coarse
routing and final result aggregation on the CPU. These systems
differ primarily in the representation and kernel used for vector
evaluation and in how top-k candidate selection is organized.
UPVSS performs floating-point L2 distance evaluation on
the PIM side and returns all evaluated vector distances and
identifiers to the CPU for global top-k selection [36]. Under
this design, the DPUs serve as parallel distance-evaluation
engines, while candidate selection remains entirely on the
host. UpANNS and DRIM-ANN instead use PQ-based vector
evaluation and perform partial top-k candidate selection within
the DPUs [6], [8]. UpANNS maintains a private candidate
heap for each tasklet and aggregates the tasklet-local heaps
into a DPU-level result. DRIM-ANN maintains a shared DPU-
level top-k priority queue that is cooperatively updated by
multiple tasklets. In both systems, the partial candidate sets
produced by different DPUs are subsequently merged by the
CPU.
Existing PIM-based ANNS systems retain the conventional
score-then-rank workflow. They either return all evaluated
vector distances for CPU-side top-k selection or maintain
partial ranking state on the PIM side. Section III examines the
resulting evaluation–kernel and search–paradigm mismatches
under the arithmetic, WRAM, communication, and coordina-
tion constraints of commodity PIM.

A. Evaluation–Kernel Mismatch: CPU-Friendly Kernels Are
Not PIM-Friendly
The first mismatch arises from the quantization methods and
corresponding distance-evaluation kernels used during vector
scanning. CPU-oriented IVF systems typically select quantiza-
tion methods based on storage efficiency and evaluation speed
on cache-rich, arithmetic-capable processors. On commodity
PIM, kernel efficiency also depends on whether its arithmetic
operations match lightweight memory-side cores and whether
its query-dependent state fits within limited local memory.
Figure 2(a) presents an empirical roofline of representative
distance-evaluation kernels on UPMEM. The x-axis reports
effective operations per MRAM byte, while the y-axis reports
effective throughput in millions of operations per second
(MOPS). The diagonal MRAM-bandwidth roof and horizontal
throughput ceilings for different DPU operation classes are
measured on real UPMEM hardware.
Conventional distance-evaluation kernels fall well below the
PIM performance roof because their arithmetic requirements
poorly match lightweight memory-side cores. Full-precision
L2 performs poorly because floating-point operations are
emulated in software. INT8 L2 removes floating point but
remains multiplication-intensive. PQ reduces the bytes scanned
per vector, but lookup-table construction (PQ-LC) resembles
dimension-wise L2 evaluation, while floating-point distance
accumulation (PQ-DA) remains expensive. Integer-quantized
PQ improves throughput, but still requires multiplication-
intensive LUT construction and introduces additional quan-
tization error. In contrast, binary distance evaluation relies
primarily on bitwise operations and population counts, moving
execution closer to the performance roof.
The mismatch also appears in WRAM usage. A PQ lookup
table with M subquantizers and 2nbits entries per subquantizer
requires M · 2nbits · sentry bytes, where sentry is the entry
size. With the common setting nbits = 8 and 32-bit entries,
the LUT alone occupies 1024M bytes. Figure 2(b) shows that

B. Search–Paradigm Mismatch: Distributed Top-k Selection
Is Not PIM-Friendly
The second mismatch stems from the stateful nature of top-
k candidate selection. On CPUs, worker threads share memory
and can efficiently manage ranking state for the current top-
k candidates. On commodity PIM, exploiting thousands of
isolated DPUs requires distributing each query’s scan across
DPUs, with multiple tasklets processing vectors within each
DPU. Because DPUs neither share memory nor communicate
directly, PIM-side top-k selection must be decomposed into
local rankings across DPUs or tasklets, followed by host-side
aggregation. We refer to this paradigm as PIM-side distributed
top-k.
Per-DPU top-k, as used by DRIM-ANN [6], maintains one
shared heap in each participating DPU. Across P DPUs, these
heaps collectively retain up to P ·k candidates for CPU aggre-
gation. As shown in Figure 3(a), this produces substantially
more output than CPU-global top-k. Multiple tasklets within
each DPU must also synchronize when updating the shared
heap, introducing serialized accesses into the scan hot loop.
Per-tasklet top-k, as used by UpANNS [8], assigns each
tasklet a private heap to avoid shared-heap synchronization.
With T tasklets per DPU, the retained capacity grows to P ·
T · k, amplifying candidate output while increasing WRAM
usage, PIM–CPU transfer, and CPU-side merge work.
Figure 3(b) shows that both organizations quickly exhaust
local memory as k increases. The per-DPU design exceeds
UPMEM’s 64 KB WRAM capacity at k = 1000, while the
per-tasklet design exceeds it at k = 100 because ranking state
4


is replicated across tasklets. This leaves insufficient space for
lookup tables, stacks, DMA buffers, and other runtime data,
limiting the supported k and workload configurations.
An alternative is to omit PIM-side top-k selection and
return the distance of every scanned vector to the CPU, as
in UPVSS [36]. This eliminates PIM-side ranking state and
synchronization but transfers excessive data. Figure 3(a) shows
that the returned candidate count grows rapidly with nprobe,
reaching up to 7813× that of CPU-global top-k. The resulting
PIM–CPU transfer and CPU-side selection overhead can offset
the benefits of memory-side scanning.
Distributed top-k also loses the globally updated prun-
ing threshold available in shared-memory CPU execution. In
lower-bound methods such as RaBitQ, the largest distance
in the current heap serves as a dynamic cutoff, allowing
vectors whose lower bounds exceed it to be discarded early.
Under PIM-side distributed top-k, each DPU observes only its
local ranking state, while maintaining a global cutoff would
require repeated host-mediated communication during scan-
ning. When all distances are returned to the CPU, the global
cutoff becomes available only after scanning and transfer are
complete. Neither organization therefore provides a timely
global cutoff for effective lower-bound pruning on PIM.
PIM-side distributed top-k incurs synchronization, repli-
cated ranking state, and candidate-output amplification, while
host-side global top-k incurs excessive communication and
CPU-side selection overhead. These limitations motivate inde-
pendent threshold-guided filtering on PIM, with global ranking
performed only over surviving candidates on the CPU.
IV. PIVOT DESIGN
A. Design Principles
Section III identifies an evaluation–kernel mismatch and a
search–paradigm mismatch when CPU-oriented ANNS work-
flows are mapped onto commodity PIM. PIVOT follows three
design principles to address these mismatches.
PIM-native distance-evaluation kernel: The evaluation–
kernel mismatch shows that PIM-side distance evaluation
should be arithmetic-light and state-light. PIVOT recasts dis-
tance evaluation around RaBitQ-style binary quantization,
enabling LUT-free computation dominated by XOR and
population-count operations [15], [16]. It further uses cen-
tered query quantization to reduce binary-side arithmetic and
introduces reduced-precision FastFloat to accelerate auxiliary
floating-point reconstruction. Together, these choices yield a
PIM-native lower-bound evaluation kernel whose per-vector
path is dominated by PIM-native operations (Section IV-C).
Cooperative filtering instead of distributed top-k: The
search–paradigm mismatch shows that PIM-side distributed
top-k incurs synchronization, replicated ranking state, and
candidate-output amplification. PIVOT instead derives a
query-specific radius τ(q) that enables independent, ranking-
state-free filtering across DPUs. Through threshold-guided
cooperative filtering, the CPU filters low-yield clusters before
dispatch, while each DPU independently rejects vectors whose
squared-distance lower bounds exceed τ 2(q) and returns only
survivor identifiers to the CPU for reranking (Section IV-D).
CPU–PIM work partitioning and pipelined execution:
PIVOT partitions work according to each side’s strengths.
Query-global control, threshold estimation, cluster filtering,
scheduling, and final reranking remain on the CPU, while the
DPUs perform bulk vector scanning and lower-bound filtering.
Consecutive query batches are pipelined so that CPU-side
preparation and reranking overlap with PIM-side filtering.
B. End-to-End Workflow
Figure 4 presents the end-to-end workflow of PIVOT.
Offline indexing phase: PIVOT constructs an IVF index
with multi-bit RaBitQ codes following the original indexing
procedure [15], [16]. Each vector contains a 1-bit base code
for PIM-side lower-bound filtering and refinement bits for
CPU reranking. For each cluster, PIVOT builds a residual-
norm histogram for survivor-mass estimation and calibrates
the threshold estimator using a small held-out query set.
Sampled database vectors can serve as surrogate calibration
queries when query traces are unavailable. The 1-bit codes and
auxiliary factors are placed in PIM, while the complete multi-
bit codes remain in host memory. Configuration-specialized
DPU kernels are generated according to the dataset and index
configuration and loaded before online execution. Section V
further describes the data layout and kernel specialization.
Online search phase: Queries are processed in batches.
❶The CPU performs IVF coarse routing and selects nprobe
clusters. ❷The calibrated survivor-mass estimator derives a
query-specific radius τ(q) and estimates the contribution of
each selected cluster. ❸Clusters with negligible expected
survivor mass are removed before dispatch. ❹The CPU
packages the query metadata and squared threshold τ 2(q) and
dispatches the remaining work to the resident DPUs. ❺Each
DPU applies the PIM-native lower-bound calculation to its
local 1-bit codes and filters vectors against τ 2(q). ❻The
DPUs return survivor identifiers, which the CPU reranks using
the complete multi-bit codes before selecting the final top-k
results. Consecutive batches are pipelined to overlap CPU-
side routing, threshold estimation, and reranking with PIM-
side filtering.
C. PIM-Native Distance-Evaluation Kernel
RaBitQ-style binary quantization represents each database
vector with a 1-bit code and derives a probabilistic squared-
distance lower bound in two steps [15], [16]. It first computes
an integer similarity term from the binary database code and
quantized query, and then combines this term with per-vector
and query–cluster auxiliary factors to reconstruct a squared-
distance estimate and its probabilistic error bound. The binary
calculation is well suited to PIM because it is LUT-free
and dominated by bitwise operations. Directly mapping the
complete distance path to a DPU, however, still requires a per-
code population count and software-emulated floating-point
reconstruction.

V. IMPLEMENTATION
We implement PIVOT in C++ on top of FAISS’s IVF–
RaBitQ index [12] and the UPMEM SDK [48]. We first
describe the PIM data path and scheduling, followed by
two execution optimizations: configuration-specialized DPU
kernels and pipelined CPU–PIM execution.
A. PIM Data Path and Work Scheduling
PIVOT adopts the list-slicing and hot-list replication strate-
gies used by prior PIM-based ANNS systems [6], [8], [52].
Large IVF lists are divided into contiguous slices and dis-
tributed across DPUs, while frequently accessed lists are
replicated so that concurrent queries can use different replicas.
The CPU retains the IVF–RaBitQ index, residual histograms,
and placement metadata. Each PIM-resident record stores the
vector identifier, 1-bit base code, and lower-bound factors
contiguously in MRAM. For each query–cluster pair that
survives cluster filtering, the CPU computes the query residual
and encoded query once and packages them with τ 2(q) and
the auxiliary query factors into DPU work records. Each
work item is assigned to a DPU containing the corresponding
slice. When multiple replicas are available, PIVOT selects the
resident DPU with the lowest assigned scan volume in the
current batch. Within each DPU, tasklets divide the scheduled
slices into disjoint portions for parallel scanning.
Each tasklet accumulates survivor identifiers in a private
DMA-sized WRAM buffer. When the buffer fills, the tasklet
briefly synchronizes to reserve space in a DPU-wide MRAM
output region and flushes the identifiers in one DMA transfer.

B. Configuration-Specialized DPU Kernel
A generic DPU kernel must support different vector di-
mensions, qb values, tasklet counts, and buffer configurations
at runtime. This introduces configuration-dependent branches
and generic loops into the scan hot path. Runtime-sized buffers
also require dynamic WRAM allocation on each kernel launch,
while PIM-side dynamic allocation incurs substantial over-
head and tasklet contention [31]. Conservative maximum-sized
buffers avoid allocation but waste scarce WRAM and limit
tasklet concurrency. Runtime-dependent loop bounds further
prevent the compiler from fully optimizing and unrolling the
distance-calculation path.
Because these parameters are fixed once the index and
configuration are known, PIVOT generates a specialized DPU
binary during index preparation. The generator specializes the
vector dimension, qb, tasklet count, DMA size, output-buffer
size, and FastFloat significand width. It statically allocates
tasklet-local buffers, providing a predictable WRAM foot-
print and more effective WRAM utilization. It also removes
configuration branches, fixes loop bounds, emits an unrolled
XOR–population-count path, and inlines the fused FastFloat
product into the lower-bound calculation. These choices reduce
allocation and control-flow overhead while exposing a straight-
line scan path that better sustains DPU pipeline utilization.
Generated binaries are compiled once, cached, and reused for
all searches with the same configuration.
C. Pipelined CPU–PIM Execution
A synchronous schedule serializes CPU preparation, PIM
filtering, survivor retrieval, and CPU reranking, leaving either
the CPU or DPUs idle. PIVOT instead pipelines consecutive
query batches, as illustrated in Figure 5. While the DPUs
filter batch i, the CPU prepares batch i + 1—including coarse
routing, survivor-mass estimation, cluster filtering, scheduling,
and query encoding—and reranks the survivors from batch
i−1. Once filtering of batch i completes, the host retrieves its
survivor identifiers and immediately launches batch i+1. The
CPU then parses and reranks batch i while the DPUs filter
batch i + 1, sustaining overlap across steady-state execution.

and qb = 8 curves remain close, while qb = 2 is more sensitive
to threshold calibration. Consistent with RaBitQ’s observation
that 4-bit query quantization introduces negligible error [16],
we use qb = 4 by default.
Figure 13 evaluates different top-k settings. PIVOT con-
sistently provides the highest QPS across different k, out-
performing FAISS-IVF-RaBitQ by 4.1–10.7× and DRIM-
ANN-Rerank by 2.6–4.9× at targets reached by both sys-
tems. DRIM-ANN-Rerank’s recall degrades as k increases.
At k = 100, it reaches only the 0.70 recall target because its
fixed 500-entry DPU-local pool provides limited oversampling
headroom and cannot be enlarged due to the WRAM limit. In
contrast, PIVOT maintains high recall without PIM-side top-k
state that grows with k.

VII. RELATED WORK
ANNS on PIM and near-data accelerators: UpANNS [8]
and DRIM-ANN [6] map IVFPQ search to commercial UP-
MEM hardware through PIM-aware data placement, schedul-
ing, and resource management. UpANNS maintains per-tasklet
candidate heaps, while DRIM-ANN uses a shared DPU-
local top-k queue. Both retain distributed ranking state and
query-dependent PQ lookup tables. UPVSS [36] performs
floating-point distance evaluation on DPUs and returns all
distances and identifiers for CPU-side selection, avoiding
PIM-side ranking but incurring substantial output traffic. PI-
MANN [52] improves utilization through persistent kernels
and fine-grained per-core scheduling. Its scheduling mecha-
nisms are orthogonal to PIVOT and could complement our de-
sign. Other work uses customized near-memory, near-storage,
or in-memory hardware [34], [35], [61], [62]. These designs
require specialized distance units, filtering logic, or data paths
unavailable on commodity PIM. In contrast, PIVOT runs on
unmodified UPMEM hardware and replaces distributed rank-
ing with a CPU-derived radius for CPU-side cluster filtering
and independent DPU-side lower-bound filtering.
ANNS on CPUs, GPUs, and FPGAs: CPU systems opti-
mize quantization- and graph-based ANNS through SIMD exe-
cution, multithreading, cache-aware layouts, and storage-aware
indexes. Representative systems include FAISS and ScaNN for
quantization-based search, HNSW and NSG for in-memory
graph traversal, and DiskANN and SPANN for billion-scale
search across memory and SSDs [7], [14], [19], [23], [24],
[38]. GPU systems exploit thread parallelism and device-
memory bandwidth for IVF and graph search [37], [42], [49],
[60]. FPGA and dedicated accelerators customize distance
units, pipelines, and memory access for higher throughput
and energy efficiency [32], [56]–[58]. These platforms offer
different architectural advantages and operate under different
constraints, and thus are not directly comparable to pro-
grammable commodity PIM.
Systems on commodity PIM: Prior work characterizes
UPMEM’s compute, memory, communication, and scaling
behavior [21], [22]. Architecture-aware systems redesign data
structures and runtimes for these constraints. PIM-tree and
PIM-trie use CPU–PIM work partitioning, data placement,
and skew-aware scheduling for ordered indexes [26], [27].
SimplePIM provides reusable programming and communica-
tion primitives, while PID-Comm optimizes collective com-
munication across isolated DPUs [5], [41]. Other work adapts
numerical workloads to the MRAM–WRAM hierarchy, studies
architecture-aware algorithm mapping, and reduces dynamic-
allocation overhead [11], [31], [44]. These efforts establish
the importance of work partitioning, communication reduction,
WRAM management, and PIM-friendly operations. PIVOT
applies these principles to redesign ANNS distance evaluation
and candidate selection.
VIII. CONCLUSION
This
paper
rethinks
ANNS
execution
on
commod-
ity PIM by addressing both the evaluation–kernel and
search–paradigm mismatches. PIVOT combines a PIM-native
distance-evaluation kernel with threshold-guided cooperative
filtering. The CPU derives a conservative query-specific radius
and filters low-yield clusters, while the DPUs independently
filter vectors and return only survivor identifiers for CPU
reranking. Configuration-specialized kernels and pipelined
CPU–PIM execution sustain high utilization across both sides.
On real UPMEM hardware, PIVOT filters out 99.3–99.7% of
probed vectors and provides up to 18.8× and 10.2× the QPS
of CPU and prior PIM baselines, respectively. It also preserves
high recall across different top-k settings and remains effective
on high-dimensional embeddings. These results show that
efficient PIM-based ANNS requires jointly redesigning the
distance-evaluation kernel and candidate-selection paradigm
for the underlying architecture, rather than directly transplant-
ing CPU-oriented workflows.
