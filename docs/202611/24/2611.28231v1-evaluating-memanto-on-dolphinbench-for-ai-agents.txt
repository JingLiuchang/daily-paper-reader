Abstract
Memory benchmarks built on question answer-
ing tell an agent which fact to recall. Work-
place requests often leave that need implicit: to
post an update in the team’s channel, an agent
must work out which channel from earlier in-
teractions and use it in a tool call. We evaluate
Memanto, a memory agent that ranks mem-
ories with an information-theoretic relevance
score, on DolphinBench, which tests memory
through 600 simulated workplace tasks, each
validated as requiring memory. Running in
the Hermes agent harness with GPT-6-Luna
and at most 6 iterations per conversation, Me-
manto completes 503 tasks (83.83%).
The
strongest configuration reported by the bench-
mark’s authors, Mem0 with GPT-5.6-Luna and
up to 60 iterations, completes 424 (70.67%).
Memanto’s run also has the lowest total cost
($10.86, against $61.48 for the cheapest re-
ported run) and the shortest median task la-
tency (15.32 s, against 37.69 s for the fastest
reported Hermes run). Grading uses the bench-
mark’s own judge, but the agent model dif-
fers, so these results compare complete systems.
The memory system affects both whether an
agent completes such tasks and what comple-
tion costs. Scripts and results: github.com/
moorcheh-ai/memanto-benchmark.

Introduction
AI agents increasingly carry out long-running
work such as software engineering, web tasks,
and customer service. This work depends on
information from earlier sessions and project
histories that no longer fits in the agent’s con-
text window. Memory systems retain this in-
formation and return it when the agent needs it
(Packer et al., 2023; Chhikara et al., 2025; Ras-
mussen et al., 2025), and memory benchmarks
measure how well they do so.

Most memory benchmarks pose questions
about a long conversation history (Maharana
et al., 2024). Later benchmarks added tempo-
ral reasoning, knowledge updates, and absten-
tion (Wu et al., 2025), and histories beyond a
million tokens (Tavakoli et al., 2025), but kept
the question-answering format. A question
names what to retrieve: “Which messaging
platform does the team use?” tells the system
what to recall. An instruction such as “Post an
update in the team’s channel” does not. The
agent must recognize that the request depends

on an earlier interaction, retrieve the right de-
tail, and use it correctly in a tool call. Eval-
uating memory for agents therefore calls for
tasks in which the needed information must be
identified, retrieved, and acted on.
Benchmark quality matters as much as for-
mat. An audit of LoCoMo found incorrect an-
swers in 6.4% of its non-adversarial questions
(99 of 1,540) (Penfield Labs, 2026), and com-
munity reports identified arithmetic errors and
mislabeled evidence in LongMemEval (Long-
MemEval contributors, 2025). BEAM uses
human review to check that its questions are an-
swerable (Tavakoli et al., 2025), but an answer-
able task need not require memory: a capable
model may solve it from the request alone.
DolphinBench (Rathi et al., 2026) addresses
both concerns. Its 600 tasks are workplace
actions carried out through simulated applica-
tions, and each task is kept only if an agent
passes it in two runs when given the relevant
history and fails it in two runs without that
history. Every task is therefore solvable and
depends on memory. The benchmark also re-
quires every result to report accuracy together
with total cost and median task latency, so
accuracy cannot be bought with unreported
spending or waiting time.

on DolphinBench (Figure 2).

Related Work
Memory benchmarks.
LoCoMo (Maha-
rana et al., 2024) and LongMemEval (Wu
et al., 2025) evaluate memory through ques-
tions about long multi-session conversations;
LongMemEval covers information extraction,
multi-session reasoning, temporal reasoning,
knowledge updates, and abstention. BEAM
(Tavakoli et al., 2025) extends conversations
beyond a million tokens. MemBench (Tan
et al., 2025) and MemoryAgentBench (Hu
et al., 2026) evaluate memory in LLM agents,
the latter by delivering information incremen-
tally over many turns.
A newer line of
work evaluates memory through agent tasks:
MEMTRACK (Deshpande et al., 2025) eval-
uates memory and state tracking across multi-
platform workplace environments, Memor-
yArena (He et al., 2026) links sessions so
that later subtasks depend on earlier ones,
and Mem2ActBench (Shen et al., 2026) tests
whether agents use long-term memory in task-
oriented actions. DolphinBench (Rathi et al.,
2026) belongs to this line and adds per-task
validation against memory and mandatory re-
porting of cost and latency.
Memory systems for agents.
MemGPT
(Packer et al., 2023) manages tiers of context
in the manner of an operating system. Mem0
(Chhikara et al., 2025) extracts and consol-
idates salient facts from conversations, Zep
(Rasmussen et al., 2025) organizes memory
as a temporal knowledge graph, and Hind-
sight (Latimer et al., 2025) structures mem-
ory around retaining, recalling, and reflect-

DolphinBench
DolphinBench (Rathi et al., 2026) evaluates
memory through task completion rather than
question answering. It covers three knowledge-
work personas: Morgan, a startup CEO; Alex,
an infrastructure engineer; and Riley, a product
manager. Each persona has a simulated history
spanning several years, with 3,400–5,128 user
messages (about 500k tokens). The histories
embed changing details in everyday conver-
sation, so an agent must notice what is rele-
vant, track updates, and tell current informa-
tion from outdated information.
After processing a persona’s history, the
agent completes 200 tasks for that persona, 600
in total. Tasks are workplace actions carried
out through simulated applications, such as No-
tion, Gmail, and GitHub, and calendar, email,
CRM, and deployment tools. The task request
and the application records give the immediate
context, but they do not say which earlier inter-
action holds the needed detail: the agent must
recognize that memory is needed and decide
what to retrieve. To validate a task, the bench-
mark authors ran GPT-5.6-Luna twice with the
relevant (oracle) messages and twice without
them; a task was kept only if both runs with
the messages passed every check and both runs
without them failed.
4
Memanto
Memanto (Abtahi et al., 2026b) is a memory
agent for long-horizon AI agents.
It gives
an agent two tools: remember, which saves
a memory, and recall, which returns the mem-
ories most relevant to a query. The agent de-
cides when to call them. Relevance is com-
puted with information-theoretic scoring (ITS)
from Moorcheh (Abtahi et al., 2026a), which
scores binarized representations exhaustively
rather than through an approximate nearest-
neighbour index, so the same query over the
same memories always returns the same rank-
3


ing.
Two settings control what reaches the agent.
A score threshold decides which memories
qualify, and a retrieval limit caps how many
enter the agent’s context. We use a threshold
of 0.1 and a limit of N = 50. On the ITS scale,
scores below 0.1 form the lowest relevance
band, labeled irrelevant (Moorcheh AI, 2026),
so this threshold removes only memories that
ITS rates as irrelevant, while the limit bounds
the size, and therefore the cost, of the agent’s
context.

Experimental Setup
Systems compared.
We ran Memanto in the
Hermes agent harness (Nous Research, 2026)
with GPT-6-Luna as the agent model.
We
compare it with the five memory configura-
tions that Rathi et al. (2026) evaluated in the
same harness: Hermes built-in memory, Mem0
(Chhikara et al., 2025), Honcho (Plastic Labs,
2025), Hindsight (Latimer et al., 2025), and
Supermemory (Supermemory, 2025). Their
figures are taken from Table 2 of Rathi et al.
(2026), where all five use GPT-5.6-Luna; we
did not re-run them. Per-persona scores and the
split of agent cost between ingestion and tests
come from the official run records released
with the benchmark (Mem0, 2026). Figure 1
also shows the official runs with MiniMax M3
in Hermes and with Claude Sonnet 5 in Claude
Code.
Agent settings.
Our run uses medium rea-
soning effort and in each stage, only the tools
that stage needs: Memanto’s remember during
ingestion, and the task’s simulated application
with Memanto’s recall during tests.
Protocol.
Our run has the two stages Dol-
phinBench defines: the full history of a per-
sona is processed before any test is taken. In-
gestion: as the official protocol requires, the
Hermes agent processes each persona’s his-
tory messages in order, one new conversation
per message. Its only tool is Memanto’s re-
member, and an ingestion instruction asks it to
save the information in the message, preserv-
ing dates, amounts, names, and corrections.
Automatic capture is disabled, so the mem-
ory holds only what the agent chooses to save,
and each write is confirmed to be searchable
before the run continues. The completed mem-
ory is then frozen: its contents are snapshotted
and hashed, and before testing the live mem-
ory is checked against the snapshot. Task ex-
ecution: for each task, the agent starts a new
conversation with the task’s application tools
and Memanto’s recall tool (ITS threshold 0.1,
N = 50), and completes the task through the
simulated applications. Memory writes are
blocked during tests. Freezing memory and
starting every task in a new conversation keeps
tasks independent: nothing learned while solv-
ing one task can help with another. The official
protocol requires both: a fresh conversation for
each test, and memory that tests cannot change
(Mem0, 2026). The scripts for both stages and
the results of our run are in the accompanying
repository.1
Metrics.
We report the three measures Dol-
phinBench requires. Accuracy is the percent-
age of the 600 tasks passed. Grading combines
deterministic checks, for requirements such as
tool calls, identifiers, dates, and values, with
an LLM judge for requirements that need se-
mantic interpretation (Zheng et al., 2023); a
task passes only when every check passes. As
in the reported runs, the judge is GPT-5.6-Sol,
the benchmark’s own, with its grading prompts
and verdict logic unchanged. Cost is the total
spent on ingestion and on the 600 tasks, split
into agent-model tokens, as estimated by Her-
mes from the recorded API usage, and memory
operations, measured as the Moorcheh Cloud
usage credits the run consumed. Latency is the
median time per task, including tool use.

Discussion
Why retrieval may matter for action.
One
possible explanation for these results is how
Memanto selects records for the agent. Ac-
tion tasks often depend on facts that change:
a request may depend on a preference stated
in one interaction and revised several sessions
later. If retrieval returns only the earlier pas-
sage, the agent can identify the right preference
and still act on an outdated value. A threshold
that admits every memory not rated irrelevant,
combined with a generous limit, makes it more
likely that both the original statement and its
revision reach the agent, which can then re-
solve the update before acting. We have not
isolated this effect; an ablation over the thresh-
old and the limit, and an analysis of the 97
failed tasks, would test it.
Where the cost and latency differences come
from.
In the reported Hermes runs, most
of the agent cost was spent during ingestion,
when the agent processed the persona histories.
The official run records put agent inference for
the 600 tests themselves at $3.23 (Mem0) to
$8.05 (built-in memory), out of $57.99–$96.56
in agent cost overall (Mem0, 2026). In our run
the agent also processed every history mes-
sage, yet its agent cost for ingestion and tests
together was $2.17. Several factors contribute:
the agent had a single tool and a short prompt
during ingestion; it used medium rather than
high reasoning effort and at most 6 rather than
60 iterations per conversation; bounded re-
trieval (at most 50 memories) kept its context
small during tests; and GPT-6-Luna and GPT-
5.6-Luna may differ in price and speed. The
same factors bear on latency. The iteration
limit and reasoning effort constrain the agent,
so they are more likely to lower accuracy than
to raise it, yet the run completed more tasks
than any reported run. Whether the reported
systems would keep their accuracy under the
same limits is untested; our data do not sep-
arate the effect of memory from that of the
model and settings, and a run of the baselines
with our settings, or of Memanto with theirs,
would.
Memory-side cost depends less on the agent.
Memanto’s $8.69 is the Moorcheh Cloud us-
age credits the run consumed, against $26.66–
$281.79 for the four external memory systems
in the reported runs. A self-hosted Moorcheh
deployment would remove this usage charge,
leaving only the cost of running its infrastruc-
ture.
8
Conclusion
We evaluated Memanto on DolphinBench,
where an agent must act on information from
earlier interactions without being told what
to retrieve.
In the Hermes harness with
GPT-6-Luna, Memanto completed 503 of 600
tasks (83.83%) at a total cost of $10.86 and
a median task latency of 15.32 s, each bet-
ter than every configuration reported by the
benchmark’s authors. It did so with at most
6 agent iterations per conversation, a tenth
of those allowed in the reported runs. Be-
cause the runs also differ in agent model,
the comparison is between complete sys-
6


tems; controlled runs with matched models
and settings, ablations of the retrieval set-
tings, and repeated trials are the natural next
steps.
We release the scripts and results
of this study at github.com/moorcheh-ai/
memanto-benchmark so that others can repeat
the run and carry out these comparisons; at
$10.86 for a full run, doing so is inexpensive.
Benchmarks such as DolphinBench, which val-
idate every task against memory and require
cost and latency alongside accuracy, make
such comparisons possible. They show that
the choice of memory system decides not only
what an agent can recall, but whether it com-
pletes the work, and at what cost.
Limitations
Different agent model and settings.
The re-
ported baselines used GPT-5.6-Luna with high
reasoning effort and up to 60 iterations per
conversation; our run used GPT-6-Luna with
medium reasoning effort. A different model
may complete more tasks, use fewer tokens, or
respond faster regardless of the memory sys-
tem, and tighter limits lower cost and latency,
so the gaps in Table 1 cannot be attributed to
Memanto alone.
Cost accounting.
Our agent cost is Hermes’s
own estimate from recorded API usage, with
retries not audited separately, and our memory
cost is Moorcheh Cloud usage credits. The
reported costs follow the benchmark’s own
accounting, so the two may differ in what they
include.
Reported, not re-run, baselines.
Baseline
figures come from Rathi et al. (2026). Harness
versions, provider prices, and infrastructure
may differ between their runs and ours.
Ethical Considerations
Several authors are affiliated with EdgeAI In-
novations Inc., which develops Memanto and
the Moorcheh retrieval engine it uses. To re-
duce the risk of bias, we use a public bench-
mark with fixed tasks, the benchmark’s own
grading checks, prompts, and judge, and base-
line figures reported by the benchmark’s au-
thors rather than our own runs of competing
systems, and we state the differences in agent
model and settings throughout. So that our
results can be checked independently, we re-
lease the scripts and results of this study in
the accompanying repository.1 DolphinBench
personas are synthetic, and no personal data
was used.
