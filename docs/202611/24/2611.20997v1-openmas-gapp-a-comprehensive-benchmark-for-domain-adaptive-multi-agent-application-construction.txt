Abstract
Constructing multi-agent system (MAS) applications across
domains requires translating diverse requirements into ex-
ecutable systems, involving task decomposition, agent and
tool selection, and execution organization. Existing stud-
ies have explored individual aspects of MAS construction,
including agent generation, architecture design, workflow
generation, and component selection. However, these meth-
ods are often developed and evaluated independently, using
different task specifications, component resources, and exe-
cution settings. This makes it difficult to compare their con-
struction capabilities or determine how they can be applied
to different domains. To address this problem, we propose
OpenMAS-GApp, a One-for-All benchmark for MAS appli-
cation construction across diverse domains. It standardizes
task inputs, component resources, construction interfaces,
and execution environments to support MAS construction
under consistent conditions. Within OpenMAS-GApp, we
provide Graph Harness as a reference construction method
that derives task dependencies, selects compatible agents
and tools, and organizes their interactions into executable
graphs. We evaluate construction methods across 19 bench-
mark datasets under 20 evaluation settings spanning four
application types and four professional domains.
1. Introduction
Pattern recognition techniques have been widely applied in
domains such as biomedicine, remote sensing, industrial in-
spection, and autonomous driving. Applications in these
domains often consist of multiple interdependent stages,
each requiring specific expertise and processing capabili-
ties. Multi-Agent Systems (MAS) address these require-
ments by assigning different tasks to specialized agents
and equipping them with appropriate tools [13, 30]. These
agents must exchange intermediate results and coordinate
their execution to complete the overall application [3, 22].
Figure 1. Illustration of Harness construction across domains.
Since the tasks, required capabilities, and dependencies
vary across applications, the agents, tools, and execution
workflows must be configured accordingly.
This calls
for methods that automatically construct MAS applications
based on domain-specific requirements.
To support automated MAS construction, existing stud-
ies have explored agent generation [14], architecture de-
sign [33, 36], workflow generation [34], and component
composition [23, 32]. These studies have introduced dif-
ferent methods for developing and assembling MAS, but
have largely evolved along separate research directions. In
particular, they adopt different task specifications, com-
ponent registries, and construction interfaces, with each
method typically evaluated within its own experimental set-
ting. These differences mean that MAS applications are
constructed according to method-specific procedures, rather
than a shared standard that applies across application do-
mains. Existing benchmarks assess agents through interac-

tive task execution [18, 19], general assistant questions [21],
and enterprise web tasks [7]. Consequently, there is no con-
sistent basis for specifying application requirements, select-
ing available components, organizing their execution, and
evaluating the resulting systems. This calls for a benchmark
that establishes a unified standard for MAS application con-

To this end, we propose OpenMAS-GApp, a One-for-
All benchmark for MAS application construction across
diverse domains. Specifically, OpenMAS-GApp integrates
19 benchmark datasets under 20 evaluation settings span-
ning four application types and four professional domains,
a shared registry of agents and tools, and domain-specific
resources.
It further establishes standardized application
requirements and construction interfaces, allowing differ-
ent methods to build MAS applications using the same
inputs and available components.
A unified execution
environment and evaluation protocol enable the resulting
applications to be assessed under consistent conditions.
Alongside the benchmark, we provide Graph Harness
as a reference method for constructing executable MAS
applications. A Harness specifies how selected agents and
tools are organized to perform application tasks, including
their operations, data exchanges, and execution relations.
Since these requirements vary across applications, a prede-
fined Harness may not cover all required operations or pro-
vide appropriate data and execution connections, as illus-
trated in Fig. 1. Graph Harness addresses this issue by con-
structing a separate Harness for each application through
three stages: Task Structure Derivation identifies the re-
quired tasks and their dependencies; Component Selection
retrieves suitable agents and tools based on their capabilities
and interface compatibility; and Graph Harness Construc-
tion organizes the selected components into an executable
graph with explicit data connections and control relations.

(1) Unified Benchmark.
We intro-

domain MAS application construction and evaluation. It in-
tegrates 19 benchmark datasets under 20 evaluation settings
spanning four application types and four professional do-
mains, with a shared component registry, standard construc-

Reference Construction Method. We provide Graph Har-

3. Benchmark Design
3.1. Domains and Application Types
OpenMAS-GApp covers four general application types and
four professional domains through 19 benchmark datasets
2


organized into 20 evaluation settings. The application types
include general reasoning, mathematical reasoning, read-
ing and question answering, and code generation.
The
professional domains are medicine, finance, science, and
law. BIG-Bench Hard contributes two evaluation settings,
BBH-Boolean and BBH-Mixed. We evaluate how construc-
tion methods address the knowledge requirements, reason-
ing steps, and objectives of these domains and application
types. Appendix D.1 gives the comparison scope.
Tables 1 and 2 list the datasets for professional domains
and general application types, respectively. Each dataset
provides individual problems with their input data and eval-
uation information. We use each problem to define an appli-
cation requirement specifying the objective and permitted
resources. We construct, execute, and evaluate one MAS
application per problem. We retain source passages, tables,
answer choices, and programming specifications.
The resulting application suite covers knowledge rea-
soning, mathematical problem solving, multi-hop question
answering, code generation, and domain-specific tasks in
medicine, finance, science, and law. These tasks differ in
their required capabilities, input resources, and expected
outputs. We evaluate a separate MAS application per prob-
lem to assess how construction methods organize compo-
nents for diverse requirements.

3.3. Experiments and Evaluations
All methods share application requirements, the component
registry, domain resources, and an LLM backbone. We ex-
ecute each constructed application and score its output with
the source dataset protocol. Appendix D.1 lists the datasets
and protocols for each comparison.
Construction Effectiveness.
We compare construction
methods across domains and application types. Ablations
examine task structure derivation, component selection,
graph construction, and interface constraints.
Orchestra-
tion comparisons hold the remaining construction process
fixed to assess how execution organization affects applica-
tion performance under shared resource budgets.
Scalability and Efficiency.
We vary registry size and
interface-description detail to assess scalability, and com-
pare task performance against mean construction tokens to
evaluate efficiency for each constructed application.
Robustness and Domain Adaptation. We test requirement
ambiguity, component metadata errors, distractor compo-
nents, and resource failures at two intensity levels. Medical
and legal cases examine how domain requirements shape
component assignments, resource connections, and execu-
tion structures of their generated Harnesses.
4. Experiments
We evaluate application construction on OpenMAS-GApp
through the following research questions:
Q1 (Perfor-
mance). How does Graph Harness compare with existing
construction methods across tasks and domains? Q2 (Har-
ness Necessity): To what extent is a harness-based orches-
tration paradigm necessary for MAS application construc-
tion Q3 (Construction Ablation). How do task structure
derivation, component selection, graph construction, and
interface constraints affect the quality of the constructed
MAS applications Q4 (Graph Organization): What role
does graph-based orchestration play in representing and co-
ordinating application capabilities, dependencies, and con-
straints Q5 (Scalability): How well does Graph Harness
scale as the component ecosystem becomes larger and more
diverse Q6 (Efficiency). How does Graph Harness balance
task performance and mean construction-token consump-
tion Q7 (Robustness): When construction conditions are
incomplete, noisy, or conflicting, does Graph Harness main-
tain stable application quality Q8 (Cross-Domain Appli-
cability). How does Graph Harness construct different Har-
nesses for individual problems across professional domains

Datasets.
We turn source questions and permitted con-
texts into construction instances with fixed components, do-
main resources, and budgets.
We execute each returned
application and score its output with the source evalu-
ator.
Direct answering provides a task-level reference.
For general knowledge and structured reasoning, we use
MMLU, MMLU-Pro, BBH-Boolean, BBH-Mixed, ARC,

4.2. Overall Performance (Q1)
To answer Q1, we compare Graph Harness with AFlow,
ADAS, GPTSwarm, and AgentSquare across 20 evaluation
settings. Figure 4(a) presents five representative datasets,
and Table 14 reports the complete results.
Graph Har-
ness achieves the highest score in 15 settings and an av-
erage score of 77.52%, with equal weight assigned to each
setting. Compared with AFlow, the strongest baseline by
average score at 69.13%, we obtain an average improve-
ment of 8.39 percentage points. Across the four profes-
sional domains, Graph Harness leads on all seven datasets.
On MedQA and CaseHOLD, its scores reach 87.49% and
79.00%, exceeding the strongest competitor, ADAS, by
6.56 and 11.00 percentage points, respectively. Compet-
ing methods obtain higher scores on MMLU-Pro, the two
BBH settings, HotpotQA, and HumanEval. These compar-
isons demonstrate strong overall application performance
and consistent gains across the evaluated professional do-
mains under the shared benchmark protocol.
4.3. Construction Paradigms (Q2)
To answer Q2, we compare Graph Harness with construc-
tion paradigms and a direct-answering reference, including
prompt-only planning, component-based assembly, plan-
based construction,
and workflow-based construction.
As shown in Figure 3, Graph Harness achieves the
highest score on all five datasets,
reaching 73.75%,
76.27%, 87.49%, 85.88%, and 59.50% on MMLU-Pro,
FinanceBench, MedQA, PubMedQA, and MuSiQue, re-
spectively. Compared with the strongest alternative on each
dataset, it improves by 20.65, 15.60, 41.69, 10.80, and 4.60
percentage points, with an average score of 76.58%. Direct
answering and prompt-only planning fluctuate substantially
across domains, while plan- and workflow-based methods
perform well on selected datasets but degrade on others.
These scores support using an explicit Harness layer to
organize requirements, tasks, capabilities, components,
resources, and constraints before MAS execution.
4.4. Ablation Study (Q3)
To answer Q3, we evaluate four ablated variants of Graph
Harness. As shown in Table 3, the complete framework
achieves the highest score on all eleven evaluation settings.
Removing task derivation reduces the mean by 4.16
percentage points. Replacing component selection with
generated configurations gives the largest mean decrease of
4.22 percentage points, including losses of 9.88 percent-
age points on MATH-500 and 8.33 percentage points on
MuSiQue. With the task graph and selected components
retained, sequential execution reduces the average score
by 3.72 percentage points.
Removing I/O constraints
causes an average decrease of 3.42 percentage points.
These results support the contributions of task derivation,
component selection, graph-based execution organization,
and interface compatibility checks.

with detailed descriptions.

D.4. Construction Ablation Protocol
Task structure derivation. The variant without task struc-
ture derivation supplies the original requirement directly to
component selection and Harness construction. It omits a
separate explicit Task Dependency Graph. Registry-based
component selection, Graph Harness synthesis, and inter-
face constraints remain in the ablation design. This inter-
vention tests the contribution of deriving tasks and depen-
dencies before subsequent construction.
Component selection. The variant without registry-based
component selection retains the task graph and uses gener-
ated agent responsibilities and tool configurations for subse-
quent synthesis. Those generated configurations are free of
the registry-membership requirement used by the complete
method. The task requirement, task structure, and model
backbone remain matched. Instantiate generated agent roles
through a common model-role factory.
Generated tool
configurations may call the same published generic prim-
itives exposed to other methods, using their declared invo-
cation interface. An unknown primitive returns an explicit
unknown-tool failure. Record the generated configuration
and callable mapping with the run.
Graph Harness construction. The sequential variant re-
tains the same task graph and selected components as the
complete method. It derives a fixed execution order from
those tasks and replaces the Graph Harness node and transi-
tion organization with that sequence. The design therefore
holds the preceding construction outputs fixed when chang-
ing the execution organization. Order independent tasks by
their fixed identifiers and take the highest-ranked retained
route for each task. Reuse the full method’s task and selec-
tion artifacts for the same problem and seed. Execute this
fixed sequence without task replanning.

E.1. Ablation Results by Task Group
Aggregation. For each dataset in Table 3, we subtract an
ablated score from the complete framework’s score. A posi-
tive difference denotes a decrease after ablation, and a nega-
tive difference denotes an ablated score above Full. We then
average these signed differences over the datasets within
each original table group, giving every dataset equal weight.
Table 10 reports the group differences in percentage points
and the complete framework’s group mean. In the main text,
we report the average difference across all eleven datasets.
Task structure.
Removing task structure derivation re-
duces the mean by 4.39 points on general/structured rea-
soning and 3.60 percentage points on multi-hop QA, giv-
ing the largest group decrease among the four ablations in
both cases. In the complete framework, we identify the op-
erations and prerequisites before selecting components and
generating execution nodes. The positive decreases across
all four groups support this explicit task-derivation step.
Component selection and execution organization. Re-
moving component selection reduces the mathematical-
reasoning mean by 6.81 percentage points, compared with
3.49 percentage points on multi-hop QA. The mathematical
group therefore shows the larger decrease under this sub-
stitution. Execution organization has a different distribu-
tion. Replacing Graph Harness construction with sequential
execution reduces the FinanceBench and SciBench group
mean by 5.70 percentage points, compared with 3.35 per-
centage points on multi-hop QA and 2.43 points on gen-
eral/structured reasoning. These comparisons show that the
effects of component selection and execution organization
vary across task groups.
Interface constraints.
Removing I/O constraints re-
duces the mathematical-reasoning mean by 5.66 percent-
age points and the FinanceBench and SciBench mean
by 3.26 percentage points.
The corresponding decrease
on multi-hop QA is 2.36 percentage points.
Every
group loses performance when the interface checks are re-
moved, supporting compatibility checks when assembling
components into executable applications.
