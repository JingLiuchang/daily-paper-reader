Abstract 

Emerging personal AI agents raise fundamen-tal scalability and privacy concerns for central-ized multi-agent systems (MASs), which rely on a global orchestrator with broad access to agents, resources, and communication. In de-centralized environments, global visibility is unavailable. Agents need to proactively dis-cover non-local resources (e.g. tools, skills), and collaborate with other agents to solve tasks. We study decentralized multi-agent collabora-tion under graph-constrained communication, a natural reflection of human structures. Each agent observes only its local state and can inter-act only with neighboring agents. We introduce a benchmark with synthetic scalable distributed tool calling with 100K+ tools. Our experiments reveal that recent LLM agents struggle to dis-cover non-local relevant resources and collab-orate in decentralized setting. Moreover, stan-dard reinforcement learning fails to reliably overcome this limitation, suggesting that de-centralized MAS needs more explicit harness mechanisms for effective collaboration, even using SOTA LLMs. We then present a strong baseline GraphHarness , combining topology-aware warmup with self-improving LLM-based routing. Results show that GraphHarness sub-stantially improves task success (+48.5) and produces higher quality collaboration (+30.6), while using fewer costs (+34.0) than baselines.

We study decentralized multi-agent collabora-tion , a novel regime to evaluate MAS on decen-tralized knowledge discovery and collaboration. In this setting, each agent only observes its lo-cal knowledge and its immediate neighbors on the communication graph, with zero global knowledge. 2 Related Work 

Multi-agent collaboration. LLM-based multi-agent systems (MAS) have been studied for col-laborative problem solving, where agents spe-cialize, communicate, and reach consensus (Guo et al., 2024; Tran et al., 2025). Prior work examines collaboration under information asym-metry (Liu et al., 2024), scientific idea genera-tion (Su et al., 2025), self-organizing role assign-ment (Chen et al., 2024), and delegation among agents and humans (Tomašev et al., 2026; Zhu et al., 2026). Yet the benefits of adding more agents are not guaranteed: several studies show that naive multi-agent teams can undermine strong individ-ual agents (Pappu et al., 2026), fail to explore one another’s knowledge (Choi et al., 2026), exhibit col-laboration gaps in open-world settings (Davidson et al., 2026), and expose weak links under adversar-ial prompting (Arora et al., 2025). This motivates mechanisms that make collaboration robust rather than merely larger. A growing body of work optimizes how agents are connected. Methods learn or prune commu-nication graphs (Li et al., 2025) and jointly opti-mize prompts and topologies (Zhou et al., 2026). Routing approaches decide which agent or context to invoke (Liu et al., 2025a; Zhang et al., 2025b; Shi et al., 2025; Yang et al., 2026b), including RL-trained routers (Zhang et al., 2025a) and de-centralized routing policies (Lozano-Cuadra et al., 2025). Decentralized designs coordinate agents without a central controller (Yang et al., 2025; Mao and Mirhoseini, 2026), and budget-aware formu-lations trade off performance against cost (Yang et al., 2026a). Our skill-graph formulation is clos-est to this line, treating topology as a first-class, adaptable object. 

Learning and self-evolution. Beyond fixed pipelines, agents can be trained to collaborate via multi-agent reinforcement learning (Liu et al., 2025b; Liao et al., 2025; Feng et al., 2026; Liu et al., 2026a), and can self-improve through shared experience (Weng et al., 2026), scaling (Qian et al., 2025; Shao et al., 2026), or test-time adapta-tion (Liu et al., 2026b). Most relevant to us, skill-centric systems co-evolve reusable competencies across agents (Pan et al., 2026; Nie et al., 2026; Zhang et al., 2026).

3 DecArena: A Benchmark for Decentralized Multi-Agent Collaboration 

We introduce a benchmark for evaluating large-scale decentralized collaboration among agents, where no agent has access to a global registry of resources. Instead, resources are distributed, and agents must solve tasks using only their own local resources and information obtained through com-munication. The benchmark therefore tests whether agents can discover, request, route to, and compose distributed resources under local observability. 

3.1 Problem Formulation Decentralized POMDP A Decentralized Par-tially Observable Markov Decision Process (Dec-POMDP) models multiple agents that act under partial observability and optimize a shared objective (Bernstein et al., 2002; Oliehoek et al., 2016). We use the tuple 

(A, S, {U i}ni=1 , T, R, {O i}ni=1 , O ), where • A = {A1, . . . , A n} is the set of agents • S is the global environment-state space • U is the action space • T (s′ | s, u) is the transition model under joint action u

• R(s, u) ∈ R is the shared reward • Oi is the local-observation space of agent Ai

• O defines the observation distribution after an environment transition The key property is decentralization. There is no controller that observes the complete state and chooses actions for all agents. Instead, each agent acts from its own local history hi,t =(oi, 1, u i, 1, . . . , o i,t −1, u i,t −1, o i,t ) using a local pol-icy ui,t ∼ πi (· | hi,t )

Graph-Constrained Dec-POMDP We extend the Dec-POMDP with a communication graph G =(A, E), where (Ai, A j ) ∈ E means that Ai and Aj

may communicate directly. The neighbor set of Ai

is Ni = {Aj ∈ A : ( Ai, A j ) ∈ E} . An agent can 3communicate only with its immediate neighbors. A request for a resource owned by a distant agent must be routed across multiple edges. Agents do not receive a global resource index, the full network topology, or the private states of other agents. 

Local observation. At round t, agent 

Ai observes only its local view oi,t =(xi,t , M i,t , Ki, Ni, 1[i = e]q), where xi,t is the local execution state, Mi,t contains messages received from neighbors, Ki is the set of local resources owned by Ai, e is the entry-agent index, and q is the task instruction. Only the entry agent observes the full task at the start of an episode. Other agents learn about the task only through messages they receive. 

Resources. Let K denote the full set of resources (tools). Each resource has an owner. A resource remains local unless its owner explicitly shares its content or executes it and returns the result. 

Tasks. A task is represented by T = ( q, z, GT ),where q is the instruction, z is the input, and GT

is a directed acyclic graph of required resources. Each node corresponds to one resource call, and its input is either the original task input or the outputs of preceding nodes. Independent resource calls can be executed in parallel, while dependent calls wait for their required inputs. 

Solution The solution is a collection of local poli-cies π = {πi}ni=1 . At each node visit, an agent may reject the request, return local resource content, re-turn an execution result, or forward the request to one or more neighbors. Returning content, re-turning a result, and forwarding may be combined. Reject is exclusive. A local policy acts from the agent’s current ob-servation, local interaction history, and optional per-sistent memory Wi ui,t ∼ πi (· | hi,t , W i), where 

hi,t denotes agent i’s within-task interaction history up to time t, and Wi denotes optional persistent memory accumulated across tasks. 

3.2 Task Construction 

We use synthetic tool calling as the primary bench-mark because it isolates decentralized collaboration from general language-model knowledge. Tool ex-ecution is deterministic and exactly verifiable, the construction scales to more than 100k+ tools, and private keyed behavior prevents an LLM from pro-ducing the correct output without accessing the required tool. 

Local resources. The atomic resource is a tool .We define two tool types: a transform maps one input string to one output string, while a merge 

maps two or more input strings to one output string. To give semantics to the tool names, we use the OpenAlex (Priem et al., 2022) hierarchy of sub-jects. Each tool is associated with a broad field and a subfield, such as transform_cs_ml_00123 and 

merge_math_algebra_00123 . Tools that share an-cestors in the taxonomy are semantically related, providing agents with useful but non-oracle sig-nals for routing. The actual output of each tool is determined by a private secret key and cannot be inferred from its semantic name. 

Tasks. Each task is a multi-step tool-composition pipeline over a single input string. Tools within the same step can execute in parallel, while later steps depend on outputs from earlier steps. Step 1 applies k ∈ { 1, 2, 3} transforms to the raw input, Step 2 optionally merges their outputs, and Step 3 optionally applies a final transform. We refer to these as level-1, level-2, and level-3 tasks, respec-tively. A task exposes the input, pipeline structure, and required tool names, while gold intermediate outputs and the final answer remain hidden and are used only for evaluation. 

Synthetic construction. Tools and tasks are gen-erated deterministically (Appendix A.1), making the benchmark fully reproducible and exactly veri-fiable. Each tool receives a secret key derived from its identifier. Given its inputs, the tool canonical-izes and concatenates them, applies a keyed hash, and returns a fixed-length token. A single input realizes a transform, while multiple inputs realize a merge. Higher-level tasks extend lower-level task families, providing controlled compositional depth while reusing the same underlying tools. Details are presented in Appendix A.2. 

Task difficulty. The full tool bank contains more than 100k+ tools distributed throughout the subject hierarchy. We instantiate 140 evaluation tasks, in-cluding 60 level-1, 40 level-2, and 40 level-3 tasks. The remaining tools form a large set of semanti-cally structured distractors. Many share subjects or higher-level ancestors with the required tools but are not useful for the task. Consequently, semantic similarity provides a meaningful routing signal but does not identify the correct tool or its owner, re-quiring agents to perform targeted discovery over a large distributed capability space. 43.3 Decentralized Environment Tool ownership and accessibility. Each active tool is assigned to exactly one agent. Since the secret key remains with the owner, a required tool can be executed only by its owner. The entry agent needs to locate the owner and request the corre-sponding result through the communication net-work. We ensure that every benchmark task is solvable from every entry point. Each required tool has an owner in the environment, and the communication graph is connected. We then stratify entry agents by the graph distance to required tool owners to measure how collaboration changes as resources become more remote. 

Local observability. Agents observe their own local resources and their immediate neighbors. There is no global tool registry, global graph view, or centralized router. Information about remote resources is obtained only through neighbor-to-neighbor communication. This prevents the bench-mark from reducing to centralized retrieval over a flat tool collection. 

Network topology and resource placement. We evaluate three graph families. In a random graph ,connectivity is independent of agent capabilities. In a semantic graph , agents are preferentially con-nected to others with similar capability profiles. In a scale-free graph , preferential attachment cre-ates a small number of hubs and many low-degree nodes. These topologies expose different routing challenges while preserving the same local inter-action protocol. Resource distribution over the network and network statistics are presented in Ap-pendix A.9. 

Action space. When an agent receives a request, it chooses actions using only the request and its local view. The primitive actions are: • Reject : decline the request and return no result; • Return : execute a local tool and return its result; • Forward : send a request to one or more neigh-bors; • Submit : stop and submit the final answer. 

Return and Forward may be combined. This al-lows an agent to provide a local result while con-tinuing to search for other required resources. In-efficient behavior is not prohibited and is instead reflected in the efficiency metrics. 

3.4 Evaluation 

We evaluate each run along three complementary dimensions: task success, collaboration quality, and efficiency. All case-level scores are aggregated over tasks and reported as percentages. 

Task success. Task success measures whether the agent system completes the full tool-composition pipeline and produces the exact gold output. Be-cause tool execution is deterministic, final answers can be verified exactly. We additionally report per-tool output accuracy as a diagnostic of par-tial progress on failed tasks, indicating whether the system successfully discovered and used some required tools even when the final task was not completed. 

Collaboration quality. Collaboration quality measures whether the system successfully iden-tifies, obtains, and correctly uses the remote re-sources required by a task. Specifically, it com-bines three aspects: whether required remote tools are queried, whether their execution results are suc-cessfully returned, and whether the returned results are used correctly in the task pipeline. The collab-oration score is the average of these three compo-nents. For tasks whose required tools are all local to the entry agent, no collaboration is necessary. We therefore report remote-only collaboration sep-arately to avoid inflating the headline score with local cases. 

Efficiency. Efficiency measures how economi-cally the system explores the network while solv-ing a task. It combines three normalized compo-nents. Visit efficiency measures how many agent visits are used relative to a distance-based refer-ence. Query focus measures how selectively re-quests are forwarded and penalizes unnecessary fan-out. Round efficiency measures the number of interaction rounds relative to an idealized reference that accounts for both tool distance and pipeline depth. Together, these metrics distinguish targeted collaboration from success obtained through broad or redundant exploration. Exact definitions are pro-vided in Appendix A.10.

5.3 Results 

The results in Table 1 show three consistent trends across the memory, tool, and skill tracks. First, cen-tralized access provides the strongest upper bound on task success. When the system is given an oracle resource owner or a global registry, performance is substantially higher than decentralized alterna-tives across all tracks. This confirms that the tasks are solvable when the required resources can be di-rectly identified. However, centralized settings do not measure collaboration quality, since agents do not need to discover or negotiate access to remote resources through the network. Second, fixed decentralized policies achieve moderate task success but incur nontrivial commu-nication cost. Policies that always return content or results improve over metadata-only sharing be-cause they expose more useful information to the requester. Always-forward policies further increase collaboration scores by expanding the search over the network, but this comes at a clear efficiency cost. The strongest fixed baseline is the policy that both returns content or results and forwards the request, suggesting that broad sharing and flooding can recover many required resources. However, its low efficiency indicates that this success is obtained through excessive communication rather than tar-geted collaboration. The budgeted fixed policy improves efficiency but reduces success, revealing the expected trade-off between resource discovery and communication cost. Third, fully decentralized agents are more chal-lenging to coordinate. The autonomous setting with only tool descriptions performs worst because agents must infer both the existence and useful-ness of neighbor communication. Explicit network briefing improves task success and collaboration quality, showing that agents benefit from being told that useful resources may exist on neighbor-ing nodes. Providing network metadata further improves success by helping agents route requests more effectively. Adding visited-node memory im-proves both success and efficiency, indicating that agents can avoid redundant exploration when they remember which nodes or resources have already been queried. Finally, imposing a communication budget increases efficiency but lowers success, sug-gesting that current autonomous agents still rely on relatively broad exploration to discover useful remote resources. Across tracks, the skill setting is consistently harder than memory and tool use. This is expected because skills require not only locating the correct remote resource, but also understanding when and how to apply procedural knowledge. Overall, these results highlight the central challenge of decentral-ized agent collaboration: centralized registries offer high success but bypass collaboration, fixed poli-cies provide useful but costly baselines, and fully decentralized agents must balance discovery, rout-ing, privacy-preserving access, and communication efficiency. 

5.4 Discussion Robustness to Adversarial Agents Adversarial agents substantially degrade decentralized collab-oration. When k adversarial agents deliberately forward requests to the least promising neighbor, task success drops from 53.7 to 3.2 and collabora-tion quality decreases from 57.1 to 25.7. Efficiency also declines from 71.5 to 33.8. The degradation is most severe when adversarial agents occupy struc-turally or semantically important positions, such as hubs in scale-free networks or nodes connecting se-mantically related regions. These results show that decentralized collaboration is sensitive not only to the presence of adversarial behavior, but also to where adversarial agents are located in the network, see Table 2. 

Robustness to Conflicting Information. We fur-ther study decentralized collaboration when agents receive conflicting routing information (Cheng et al., 2026; Sun et al., 2026). We use a ring net-work so that each agent has exactly two neighbors, which provides a controlled setting for isolating conflict resolution. For each resource request, an agent receives two local knowledge sources that recommend where the request should be forwarded. In the no-conflict condition, both sources identify the neighbor that lies on a shortest path to the re-quired resource owner. We propose a strong baseline, GraphHarness, which is topology-aware, experience-adaptive and performs efficient and high quality collaboration. DecArena provides a controlled and scalable testbed for developing agents that can collaborate effectively in increas-ingly large and distributed agent ecosystems. 

Limitations 

DecArena intentionally isolates decentralized re-source discovery and routing through synthetic, de-terministic tool-calling tasks, which enables exact verification and controlled scaling but does not cap-ture the full complexity of real-world collaboration involving ambiguous requests, heterogeneous APIs, 8natural-language expertise, changing permissions, execution failures, or strategic participants. The headline setting also assumes connected net-works, unique resource ownership, and reachable required resources, so failures measure discovery and coordination rather than network partition or resource unavailability. Our evaluated topologies represent only several stylized network structures, and experiments at up to 1,000 agents do not fully reproduce the dynamics of web-scale agent ecosystems. Finally, performance can depend on the under-lying LLM, prompting strategy, network construc-tion, and persistent routing state, while the cur-rent benchmark emphasizes resource discovery more than other decentralized challenges such as trust, authentication, incentive compatibility, asyn-chronous communication, and evolving ownership. Extending DecArena to real tools, dynamic net-works, heterogeneous agents, and richer adversarial or privacy-sensitive settings is therefore an impor-tant direction for future work. 

Ethical Considerations 

DecArena is designed primarily as a controlled re-search benchmark and uses synthetic tools with deterministic execution rather than human data, re-ducing risks related to personal information, an-notation labor, or sensitive real-world content. At the same time, advances in decentralized agent col-laboration may have broader societal implications. Systems that can autonomously discover and in-voke resources across organizational or ownership boundaries could improve scalability and enable capabilities to remain locally controlled, but they may also make distributed systems harder to au-dit and increase the risk of unauthorized resource access, information leakage, malicious routing, or propagation of incorrect information. The substan-tial degradation observed under adversarial agents and conflicting routing information further high-lights these concerns. Real-world deployment of such systems should therefore incorporate explicit authorization and consent, capability-level access control, provenance and logging, sandboxed exe-cution, communication limits, and mechanisms for detecting malicious or unreliable participants. We view DecArena as a setting for studying these chal-lenges rather than evidence that fully autonomous decentralized agent networks are ready for unre-stricted deployment.

12 A DecArena Benchmark Details 

This section provides the full construction and eval-uation details for DecArena. The benchmark is designed to isolate a specific capability: whether agents can discover and use resources that are dis-tributed across a communication network when no agent has access to a global resource registry or a global view of the network. We use syn-thetic tool calling as the primary task family be-cause it provides exact, deterministic verification while preserving the central difficulty of decen-tralized resource discovery, multi-hop routing, and distributed execution. 

A.1 Tool Construction Tool bank. We construct a large synthetic bank containing more than 100k tools. The bank con-tains two primitive tool types, transform and merge .Tool identifiers are unique across the bank. Only a small fraction of the full tool bank is required by the benchmark tasks, while the remaining tools act as semantically plausible distractors. The large tool space is intentional. If the envi-ronment contained only the tools required by the evaluation tasks, identifying a plausible tool de-scription would already provide substantial infor-mation about the correct route. Instead, DecArena places each required tool within a much larger capa-bility ecosystem containing many irrelevant tools with similar metadata. The resulting problem there-fore evaluates targeted resource discovery rather than enumeration over a small candidate set. 

Tool types. A transform consumes a single string and produces a single string, 

y = ft(x), (5) while a merge consumes two or more strings and produces a single output, 

y = ft(x1, . . . , x m), m ≥ 2. (6) Both tool types use the same underlying deter-ministic keyed transformation. They differ only in the number of inputs they consume. Each tool is associated with a unique identifier, a semantic category, a natural-language descrip-tion, an input schema, an output schema, and a private execution key. Tool identifiers are delib-erately semantically structured. For example, an identifier may contain lexical cues associated with its category or function. These cues give an LLM a meaningful routing signal without revealing the tool output. 

Private deterministic execution. Each tool t re-ceives a private secret key derived deterministically from a master seed and the tool identifier: 

key( t) = HMAC -SHA256 (master_seed , tool_id t). (7) Given input strings x1, . . . , x m, the execution procedure first canonicalizes the inputs by sorting them and concatenating them using a fixed delim-iter. The canonicalized input is then processed us-ing the private key. The resulting digest is Base32 encoded and truncated to a fixed-length output to-ken. For a transform, m = 1 . For a merge, m ≥

2. Therefore, the same deterministic construction supports both primitive types. This design has four useful properties. First, repeated execution of the same tool on the same inputs always produces the same output. Second, all intermediate and final outputs can be reproduced exactly by the evaluator. Third, outputs cannot be reliably inferred from tool names, descriptions, or semantic categories because the execution key is private. Fourth, two semantically similar tools still produce unrelated outputs because their keys differ. The private key remains with the tool owner. An agent that does not own a required tool cannot locally reconstruct its output. It must either obtain the result from the owner or, in resource-transfer variants of the benchmark, obtain the transferable resource itself. 

A.2 Task Construction Multi-step pipelines. Each benchmark task de-fines a directed acyclic computation graph over synthetic tools. A task begins with a single raw input string and requires one or more tools to be executed in a prescribed dependency structure. We organize tasks into three levels of composi-tional depth. A level-1 task applies k ∈ { 1, 2, 3} transform tools independently to the raw input. These calls can be executed in parallel. A level-2 task first executes the level-1 trans-forms and then applies one merge tool to their out-puts. 13 A level-3 task extends the level-2 pipeline with one additional transform applied to the output of the merge. For example: 

Input: Z4P3 Step 1 transform_green_river_00368(Z4P3) transform_amber_maple_00978(Z4P3) Step 2 merge_red_nova_00166(outputs from Step 1) Step 3 transform_blue_comet_00392 (output from Step 2) Return the output from Step 3. 

If Sj denotes the set of tools at pipeline stage j,tools within the same stage may be executed inde-pendently, while stage j + 1 becomes executable only after all required outputs from stage j have been obtained. The benchmark therefore requires not only resource discovery but also preservation and composition of intermediate results. 

Task families. Tasks are generated in families. A family fixes an input string together with a pool of tools used across multiple levels. Higher-level tasks extend lower-level tasks whenever the dependency structure permits. For example, a level-2 instance may reuse the transforms from a corresponding level-1 instance and append a merge. A level-3 instance may further append a final transform. This construction allows compositional depth to vary while holding much of the underlying semantic content fixed. As a result, differences between task levels primarily reflect the additional collaboration and dependency-management requirements rather than an unrelated change in tool semantics. 

Evaluation task set. The evaluation set contains 

140 tasks: 60 level-1 tasks, 40 level-2 tasks, and 

40 level-3 tasks. Collectively, these tasks reference 

186 distinct required tools. The number of benchmark tasks is intentionally much smaller than the size of the global tool bank. The benchmark therefore evaluates whether agents can locate a sparse set of relevant capabilities em-bedded in a much larger distributed resource space. 

Required tools and distractors. For each bench-mark environment, every tool required by the se-lected evaluation tasks is guaranteed to be present. The remaining resource slots are filled with distrac-tor tools sampled from the global bank. Distractors are fully valid tools. They have nor-mal identifiers, descriptions, categories, schemas, and executable implementations, but they are not required by the current evaluation tasks. They are therefore indistinguishable from useful tools based only on their status in the environment. The purpose of distractors is to prevent resource discovery from degenerating into simple category matching. Multiple tools may appear semantically related to the request even though only one exact tool produces the required output. As the tool bank grows beyond 100 ,000 tools, the ratio of relevant to irrelevant resources becomes increasingly sparse, creating a large-scale discovery problem similar to realistic capability ecosystems. 

Semantic categories. Tools are distributed across semantic categories. Category member-ship affects the semantic information available in tool metadata and, in the semantic network condi-tion, influences both network structure and resource placement. A configurable fraction of task families can be constructed so that their tools share a semantic cat-egory. The remaining families contain tools from multiple categories. This produces both seman-tically coherent tasks, for which routing toward a specialized region may be beneficial, and cross-domain tasks, for which the required resources may be distributed across different parts of the network. Importantly, category information never uniquely identifies the required tool. It provides only a routing prior.

A.4 Local Observability 

The defining constraint of DecArena is local ob-servability. No agent receives a global resource registry, the full adjacency matrix, or the mapping from tools to owners. An agent has direct access only to its own re-sources and can communicate directly only with immediate graph neighbors. A.5 Request and Interaction Protocol 

A task begins at an entry agent. The entry agent may already own some of the required tools, while other required tools may be located several graph hops away. When an agent receives a request, it chooses among the following primitive actions: • Reject : decline the request and return no re-sult • Return : execute an owned requested tool and return its output • Forward : propagate the request to one or more immediate neighbors • Submit : terminate the task and submit a final answer 

Return and Forward may be selected simultane-ously. For example, an agent may provide the result of one locally available resource while continuing to search for another required resource. We deliberately do not prohibit inefficient ac-tions. An agent may forward a request to several neighbors, revisit an earlier node, query an irrele-vant resource, or continue searching after receiv-ing a useful result. These behaviors are logged and penalized through the efficiency metrics rather than removed from the action space. This allows the benchmark to distinguish effective collabora-tion from success obtained through indiscriminate flooding. 16 Recursive decentralized routing. The default evaluation uses recursive routing. Once a request is forwarded to an intermediate agent, that agent independently chooses whether to answer, reject, or forward it to its own neighbors. The entry agent therefore does not centrally control every hop. For example, if A1 requests tool t from neighbor 

A2 and A2 does not own t, A2 may decide to for-ward the request to A5. Agent A1 need not know that A5 exists before the request reaches it. This distinction is central to the benchmark. The problem is not simply to choose a route over a known graph. The route itself emerges from a sequence of decisions made under different local observations. 

Remote execution. The headline tool benchmark uses remote execution. The owner of a requested tool executes it locally and returns only the output. The underlying private key and tool implementa-tion are not transferred. If agent Aj owns tool t, a successful remote call therefore has the form 

Ai → · · · → Aj : request( t, x ), (19) followed by 

Aj → · · · → Ai : ft(x). (20) This models resources that depend on private data, credentials, proprietary code, or specialized execution environments and therefore cannot sim-ply be copied to the requester. 

Intermediate results. Multi-stage tasks require outputs from earlier tools to be reused as inputs to later tools. Returned results are therefore added to the task state and may be included in subsequent requests. A level-3 task may require several remote discoveries across multiple sequential stages before the final answer can be produced.

A.8 Reproducibility 

Tool generation, task generation, topology con-struction, and resource placement are seeded and deterministic given the benchmark configuration. Tool execution is deterministic by construction. A.9.4 Comparison of the Three Network Families 

The three constructions independently stress dif-ferent aspects of decentralized collaboration. Ran-dom networks provide a neutral condition in which neither graph structure nor ownership conveys se-mantic routing information. Scale-free networks introduce strong structural heterogeneity and cor-relate resource ownership with degree. Semantic networks instead introduce local homophily be-tween capability categories and both communica-tion edges and resource ownership. Importantly, these conditions modify only the en-vironment. The agent interaction protocol is iden-tical across all three settings. An agent observes its own local resources and immediate neighbors, but receives neither a global adjacency matrix nor a global resource registry. A distant resource can therefore be discovered only through a sequence of neighbor-to-neighbor interactions.

B Details of Evaluated Agents 

We compare several agent designs that differ in the information available to the policy and in how rout-ing decisions are produced or adapted over time. Unless otherwise specified, all agents use the same base LLM, local observation space, structured ac-tion space, and neighbor-to-neighbor communica-tion protocol. In particular, changing the agent design does not change tool ownership, network connectivity, or the underlying task. At a visit to agent Ai at round t, the agent ob-serves its current local state oi,t , including its lo-cally owned tools, immediate neighbors, received requests or replies, and task information visible at that node. The policy then selects among the bench-mark actions Reject , Return , Forward , and, for the entry agent, Submit_Final . Except for the ex-plicitly privileged oracle baselines, agents do not observe the global graph or the mapping from tools to owners. 

B.1 Reflex Agent 

The Reflex agent is the simplest LLM-based de-centralized baseline. It makes each decision solely from the information currently visible at the node: 

ui,t ∼ πLLM (· | oi,t ) . (54) The agent does not maintain an explicit memory of earlier decisions. In particular, its prompt does not include a stored history of previously contacted nodes, previous forwarding actions, or outcomes from earlier requests. Any information available to the policy must therefore be present in the current observation. This baseline tests whether a pretrained LLM can infer useful decentralized routing behavior directly from local context. For example, if an agent does not own a requested tool, it must decide whether to reject the request or forward it to one of its immediate neighbors without access to a learned routing table or cross-task experience. 

B.2 Reflex + History 

Reflex + History augments the Reflex agent with an explicit record of its previous interactions. Its deci-sion can therefore condition on a local interaction history hi,t :

ui,t ∼ πLLM (· | hi,t ) . (55) For each previous visit, the history records the in-teraction round, agents from which messages were received, requested tool identifiers, selected actions, forwarding destinations, tools returned or executed, and execution or parsing errors when applicable. The history is rendered into the LLM prompt before the next decision. The purpose of this baseline is to isolate the value of explicit interaction memory. In particular, an agent can use its history to avoid repeatedly forwarding the same request to the same neighbor, recognize that a previous route did not return a useful result, or retain information about earlier successful interactions. Unlike the experience-conditioned methods be-low, Reflex + History does not perform explicit retrieval or learn a routing value function. It simply exposes the recorded interaction trace to the LLM and allows the model to reason over that trace di-rectly. 23 B.3 Collaborative Prompting 

Collaborative Prompting tests whether poor decen-tralized performance is primarily caused by LLMs being insufficiently willing to seek help. It uses the same observation, memory, and action space as the Reflex agent, but strengthens the system prompt with explicit collaboration instructions. The prompt encourages an agent to help when-ever possible, to return a local result when it owns a useful tool, and to forward a request when a neigh-bor may plausibly help. In particular, the policy is instructed to strongly prefer collaboration over rejection and to avoid Reject unless neither the current agent nor any plausible neighbor can con-tribute. Importantly, Collaborative Prompting does not specify which neighbor should be selected. The LLM must still infer the forwarding destination from its local observation: 

ui,t ∼ πLLM (· | oi,t , p collab ) , (56) where pcollab denotes the additional collabora-tion instruction. Thus, this baseline changes the agent’s behav-ioral incentive but provides no additional informa-tion about resource locations or network topology. It distinguishes failures caused by unwillingness to collaborate from failures caused by an inability to identify a useful route. 

B.4 Broadcast 

Broadcast provides a high-recall decentralized search baseline. The LLM is first queried using the standard local policy. The resulting action is then post-processed so that, whenever the agent has neighbors, the request is forwarded to all immedi-ate neighbors. More specifically, if forwarding is possible, 

Reject is removed from the final action set and 

Forward is added. For every tool-specific request being propagated, an equivalent request is created for each immediate neighbor. If the LLM has al-ready produced a valid forwarding request, its re-quested tool, input, and request type are reused. Otherwise, the forwarding request is reconstructed from the current incoming request. Broadcast does not prevent useful local compu-tation. An agent may simultaneously execute an owned tool and return its result while forwarding the request to its neighbors. The distinction from the other agents is that neighbor selection is no longer selective: 

Fi,t = Ni, (57) whenever forwarding is applicable, where Ni is the immediate-neighbor set of agent Ai.Broadcast therefore approximates exhaustive graph search while retaining the same local com-munication constraint. It provides a useful refer-ence for the maximum resource coverage obtain-able through aggressive decentralized exploration, while typically incurring substantially greater com-munication cost, forwarding fan-out, and redundant node visits. 

B.5 Oracle Route 

Oracle Route provides privileged routing informa-tion to the entry agent while leaving all other agents unchanged. For every tool required by the task, the benchmark computes a shortest path from the entry agent to an owner of that tool. The entry agent receives an additional routing section containing, for each required tool: • the tool identifier • its owner • a shortest path from the entry agent to that owner • the first neighbor on that path If a required tool is already owned by the entry agent, the hint explicitly identifies it as local. Let o(t) denote the owner of required tool t and let 

Pt = ( A0, A p1 , . . . , o (t)) (58) be a shortest path from entry agent A0 to that owner. Oracle Route reveals Pt to A0, including the first-hop recommendation Ap1 .Only the entry agent receives this privileged in-formation. Intermediate agents continue to make their own decisions from normal local observations. Oracle Route therefore removes uncertainty about initial resource location and route selection while preserving decentralized behavior after the first for-warding step. It serves as a diagnostic upper bound on how much performance can improve when the entry agent knows where the required resources are located. 24 B.6 Oracle Route All 

Oracle Route All is a stronger privileged baseline. It constructs the same oracle routing information as Oracle Route, but exposes this information to every agent that participates in the task. For each required tool, all visited agents can observe the owner and the shortest path computed from the original entry agent to that owner. Thus, an intermediate agent that lies on the supplied route can directly identify the next node on the oracle path rather than rediscovering the route from its ordinary local context. The oracle information is not recomputed into a new globally optimal route at every intermediate node. Instead, all agents receive the same entry-originated shortest-path description. This matches the implementation and preserves a single oracle reference route for each required resource. Oracle Route All therefore removes most of the resource-location and multi-hop routing un-certainty while retaining the benchmark’s edge-constrained communication mechanism. Messages must still traverse actual graph edges, tools remain locally owned, and remote tools must still be exe-cuted by their owners. The baseline is intended as a routing oracle rather than a realistic decentralized agent.

B.9 Comparison of Agent Information 

The evaluated agents can be understood by the ad-ditional information introduced beyond the current local observation. Reflex receives no additional state. Reflex + History exposes previous interac-tions. Collaborative Prompting changes only the behavioral instruction. Broadcast removes selec-tive neighbor choice by forcing full local fan-out. Experience-Conditioned routing retrieves struc-tured evidence from previous successful interac-tions. Numerical Q-Routing maintains an explicit learned neighbor-value table. Oracle Route and Oracle Route All introduce privileged ground-truth routing information and are included only as diag-nostic upper bounds. Crucially, except for the oracle baselines, none of these methods receives the global mapping from tools to owners or a globally searchable represen-tation of the communication graph. Differences in performance therefore reflect different mecha-nisms for using local observations, communication history, and accumulated routing experience rather than access to a centralized resource registry. 

B.10 Training Learned Collaboration Policies 

We study whether decentralized collaboration can be improved through policy post-training. We consider three complementary approaches: super-vised fine-tuning (SFT), on-policy self-distillation (OPSD), and group relative policy optimization (GRPO). SFT learns from previously collected suc-cessful collaboration trajectories. OPSD uses a stronger teacher to supervise states generated by the current student policy. GRPO directly optimizes the policy using rewards obtained from online in-teraction with the decentralized environment. All three methods train a single shared policy 26 that is used by every agent in the network. The model is therefore not specialized to a particular node identity. At each node visit, the shared policy receives only the local observation available to the acting agent and predicts the structured decision consumed by the environment. This parameter sharing allows a policy trained on small networks to be deployed to previously unseen agents and substantially larger communication graphs. 

B.10.1 Training and Evaluation Splits 

We separate policy training from evaluation along task, network-size, and topology dimensions. The training environments contain small graphs with network sizes N ∈ {10 , 50 } and use Random and Scale-Free topologies. Networks with N ∈{100 , 500 , 1000 } are reserved for size generaliza-tion, while Semantic networks are held out to eval-uate topology generalization. Within the training environments, we addition-ally reserve 10% of task identifiers as an in-distribution test set. The holdout is deterministic and based on a hash of the task identifier, ensur-ing that the same task is consistently assigned to the same split across network configurations and repeated experiments. Held-out task identifiers are excluded from all SFT examples and from online OPSD and GRPO training. This produces three evaluation regimes: in-distribution generalization to unseen tasks, size extrapolation to larger graphs, and topology trans-fer to a graph family not used during training. All trained policies are evaluated by executing them live in the corresponding held-out environments. 

B.10.2 Shared Local Policy 

A collaboration trajectory contains a sequence of visits to potentially different agents. At each visit, the acting agent receives a system instruction to-gether with its current local observation. Depend-ing on the benchmark configuration, this observa-tion contains the current request, locally owned tools, immediate neighbors, available intermediate results, and the interaction history visible to that agent. The model emits a structured decision specifying the actions to execute, such as returning a local re-sult or forwarding the request to selected neighbors. For offline SFT data, we train on the parsed deci-sion accepted by the environment rather than the teacher model’s unrestricted natural-language re-sponse. Accepted decisions are canonicalized into a consistent JSON representation. This removes stylistic variation among data-generating models and focuses learning on the action that changes the environment. The same structured action representation is used during online OPSD and GRPO. Consequently, dif-ferences among the three training methods arise from how training states and learning signals are obtained, rather than from differences in the under-lying agent interface.

Environment reward can be used to monitor or filter rollouts, but it is not the direct optimization signal.

B.10.6 Group Relative Policy Optimization 

GRPO directly optimizes collaboration outcomes through online environment interaction. As with OPSD, we initialize the policy from the SFT check-point. Unlike OPSD, no teacher action is provided. Sampling uses temperature 1.0.Each rollout executes the normal benchmark en-vironment. Each training round performs four stages: 1. create a servable snapshot of the current policy 2. execute grouped rollouts in the training envi-ronments 3. compute environment rewards and group-relative advantages 4. update the policy on the collected local deci-sions The updated policy is then used for the next rollout round. 

Parameter-efficient update. GRPO applies LoRA to the SFT model. We use rank 32 , scal-ing parameter 64 , and adapters on the query, key, value, and output projections. The underlying SFT parameters remain frozen. Configuration. The default configuration uses

B.10.7 Comparison of Training Signals 

The three methods differ primarily in where their training states and supervision originate. SFT uses a fixed offline state distribution gen-erated by previously collected high-quality trajec-tories and imitates their accepted actions. OPSD generates states using the current student policy but obtains the target action from a self-teacher with oracle routing information. GRPO also generates states using the current policy, but replaces teacher supervision with trajectory-level environment re-ward. Thus, the progression from SFT to OPSD to GRPO separates three increasingly interactive forms of policy improvement: offline imitation, on-policy imitation, and on-policy reward optimiza-tion.

C.2 Request Semantics and Within-Task Cache Request semantics. The headline tool bench-mark uses result requests. A queried owner ex-ecutes its local tool and returns only the output. This matches the benchmark action space in which 

Return exposes a tool result rather than the private tool implementation. We additionally support a content-transfer abla-tion. Under a content request, an owner may re-turn transferable resource content that the requester can mount and execute locally. Under a result 

request, execution remains delegated to the owner. The request specifies what the caller prefers, while the queried agent may still reject or forward ac-cording to its policy. This ablation separates open resource sharing from service-style delegation. 

Entry-agent cache. A task may require several resources across multiple pipeline stages. We there-fore distinguish a within-task cache from the cross-task experience memory used by GraphHarness. The within-task cache may store discovered re-source locations, previous responses, transferred resource bodies when transfer is enabled, and inter-mediate execution results. We compare three cache policies. Under agent ,the entry agent decides what to retain. Under lru ,eviction follows a fixed least-recently-used pol-icy. Under off , no reusable cache is maintained. This ablation measures whether explicit within-task memory reduces repeated queries and redundant execution. 

C.3 Routing and Coordination Ablation 

We compare two coordination regimes while pre-serving neighbor-only communication. 

Entry-controlled routing. The entry agent re-mains the decision maker for the route. Intermedi-ate agents expose only the local information needed for the entry agent to choose the next hop and then relay the request along that selected edge. Inter-mediate agents do not independently choose where to forward. This condition tests routing under a single task-level controller without granting global network access. 

Recursive routing. Each receiving agent inde-pendently decides whether to answer, reject, or forward the request to one or more of its own neigh-bors. The entry agent may therefore receive a result without observing every intermediate routing deci-sion. The first condition isolates the routing ability of the entry agent. The second evaluates genuinely distributed coordination among multiple local de-cision makers. Recursive routing is the default condition in the main benchmark. 

C.4 Memory and Network Dynamics 

Persistent routing information is useful only when it remains sufficiently aligned with the network. We therefore vary both cross-task memory and net-work dynamics. 

Cross-task memory. Under none , each task begins with an empty cross-task routing state. Under persistent , agents retain routing notes, resource-location estimates, previous outcomes, and neighbor-performance statistics across tasks. This memory is distinct from the within-task cache in Section C.2. Persistent-memory evaluation is an online adap-tation setting. All methods that retain cross-task state should observe the same task order. To reduce sensitivity to a particular order, results should be averaged over multiple task-order permutations. 

Static graph. Resource ownership and commu-nication edges remain fixed throughout evaluation. Persistent memory can therefore accumulate stable routing information. 

Dynamic graph between tasks. Between con-secutive tasks, a controlled fraction of communi-cation edges is perturbed and a controlled fraction of resources migrates to new owners. This setting tests whether agents learn transferable routing pat-terns or only memorize fixed locations. 

Dynamic graph within tasks. As a stronger stress test, edges or resource owners may change 31 between communication rounds while a task is be-ing solved. Each update preserves graph connec-tivity and exactly one owner for every active tool. Changes occur only at round boundaries so that the environment remains well defined. This condi-tion tests whether agents can detect stale routing information and recover online.
