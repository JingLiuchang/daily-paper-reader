## CoReMem: Cost-Internalizing Memory for Successive Coding Tasks with Prospective Valuation

Abstract 

Coding agents tackle successive tasks on an evolving repository, carrying forward edits and writing memory before the next task is known. Selecting memory for unknown next tasks re-quires balancing future usefulness against the costs of writing and reading it. The actor must also decide when acting on available memory saves effort as the task unfolds. We introduce 

Co ding-Re pository Mem ory ( CoReMem ), a cost-internalizing framework that guides mem-ory design and actor adaptation through mea-sured memory value on the next task. Prospec-tive segment valuation compares runs of the next task with and without individual trajectory segments from the same inherited repository state, guiding a compact memory built around 

anchors : repository locations and executable checks. Actor adaptation estimates on-policy memory value within rollout groups with and without memory, using a reward that prioritizes resolution and penalizes step count in success-ful runs. Provenance-gated value credit assigns the additional value term to steps identified as using memory-supplied anchors, while every step retains outcome credit. On ChainSWE, 

CoReMem raises the 27B actor’s resolve rate from 21 .0% to 25 .7% , with 17% fewer steps and 11% fewer total cache-aware tokens, in-cluding memory-module calls, relative to the untrained actor model without memory.

Given these mismatches in setting and objective, Challenge 1 is to determine, before the future task is known, what information is worth carrying across the task boundary .Memory’s value is realized only when the actor model uses it appropriately during execution. Ex-isting coding memory methods mainly optimize what is stored or retrieved, while typically leaving the model that reads it unchanged (Chhikara et al., 2025; Ouyang et al., 2026; Guo et al., 2026). Yet an agent’s information needs evolve as a task unfolds (Zhang et al., 2023; Shen et al., 2026), making task-start retrieval insufficient to determine how memory should be used during execution. Challenge 2 is therefore how to use memory efficiently during exe-cution to reduce the cost of solving unseen future tasks on the inherited repository .To address these challenges, we introduce 

Co ding-Re pository Mem ory ( CoReMem ), a cost-internalizing memory framework for successive coding tasks. Specifically, prospective segment val-uation of memory addresses Challenge 1 by first formulating the prospective value of a memory at a task boundary, then valuing each part of the cur-rent task’s trajectory by what it saves on the next task, and from these values inducing, through a sys-tematic procedure, a value-guided memory design for successive coding tasks. As a result, the value concentrates in anchors , references to repository locations and to executable checks, which later also mark the steps that act on the memory. To address Challenge 2, we propose on-policy adapta-tion for memory use with provenance-gated value credit, which adapts the actor model itself to act on the memory where that saves effort, in two steps. Cost-internalizing on-policy valuation trains the ac-tor model in groups of rollouts with the memory, without it and with a misplaced memory, under a reward that charges steps inside success, so that the average gap between the rollouts with the memory and those without it exposes the memory’s value to the current actor model. For the rollouts that run with the memory, step-level provenance-gated value credit then pays the memory value to the steps whose anchors came from the memory, so that memory use is pushed by its measured value while every step keeps its outcome credit, and we show analytically that this push vanishes when the same value is paid to every step. Our contributions are summarized as follows. • We propose prospective segment valuation of memory, a systematic procedure that values each part of a trajectory by what it saves on the next task and induces a value-guided memory design for successive coding tasks. • We propose on-policy adaptation for memory use with provenance-gated value credit, which measures the memory value on-policy within each group of rollouts and passes the memory’s value directly to the steps that act on it. • On ChainSWE, a benchmark of successive tasks, CoReMem raises resolve per token over no memory by 41% on average across three different actor models. 1

2 Preliminaries 

In this paper, we consider a repository worked on by a chain of tasks T1, . . . , T K , carried out one after another in a single persistent workspace (Jin et al., 2026). Each task runs as its own session of an 

actor , the model that acts in the repository, which leaves the repository state Sk its edits produced and the trajectory τk of its actions and observations. At the boundary bk = ( Sk, τ k, T k+1 ) the state per-sists, since the next task opens the tree this one closed, while the trajectory is lost, and a memory 

m = πwrite (τk), written once at the end of task 

k and before Tk+1 is issued, is the only text that crosses. Unlike cross-episode memory that resets each task to a base commit (Guo et al., 2026; Fan et al., 2026a), the state here is inherited (Figure 2), so a memory cannot be checked on its own task, whose answer the repository holds. 

Does existing memory save effort? We run the existing forms of cross-task memory, the full history of the earlier tasks (App. B), Mem0’s facts (Chhikara et al., 2025), MemOp’s guide-book (Guo et al., 2026) and ReasoningBank’s strategies (Ouyang et al., 2026), on the ChainSWE test set and count, for every form, the tokens of the acting model and of its memory module. Fig-ure 3 places each by its change in steps and tokens against no memory, first with the acting model’s tokens alone and then adding the tokens of the memory module (Tables 1 and 3 have every num-ber). Memory on successive tasks should lower the next task’s effort, its steps and the tokens they cost, yet no existing form reaches the quadrant where steps and total tokens both fall. Some buy resolution rather than effort, and each spends more tokens on its memory than it saves. Our aim is therefore a memory that lowers the effort of unseen future tasks without harming resolution, with what it keeps derived by valuing each part of a finished session by the effort it saves on these tasks and keeping what pays (§3.1, the star in Figure 3). 

Learning objective. A memory can only point at what the next task should reuse, and effort is saved only when the actor acts on it. An actor is trained to solve a task from scratch rather than to read what an earlier task left, so it may pass over a memory that would spare it work or follow one that does not apply (Liu et al., 2024; Shi et al., 2023), and whether a memory applies becomes clear only as the actor works through the task. 3 Cost-Internalizing Memory 

CoReMem is cost-internalizing in the sense of Eq. (1). The effort a memory changes on the next task is measured, and that measurement enters both what the memory keeps and how the actor model is adapted to use it, in two parts (Figure 4). §3.1 defines the value of a memory on unseen future tasks and lets it guide what the memory keeps, which turns out to be anchors. §3.2 adapts the actor model to use that memory during execution, measuring the value again on-policy and paying it, through the anchors, to the steps that use the memory, on top of the outcome credit.

Value-guided memory design. Removing the commands or the repository content read adds steps on the next task, while removing the reasoning text or the diff body adds no steps and saves tokens (Fig-ure 5). Shorter forms also work, as test commands with their exit codes save more steps than the full test output and the diff’s file list comes close to the full diff (App. J). What saves the next task effort is where to look and what to run, not the narrative, so we build the memory from the references that carry it and define them below as anchors. 

Definition 1 (Anchor) . An anchor is a reference, taken from a trajectory, to a specific place in the repository, a location , or to a specific command that runs or tests the code, a check , which the next task can act on as it stands. A(x) denotes the anchors that a text x contains. Locations are file paths with their lines and code names, such as rules/ast_if.py:34-58 ,and checks are commands that run or test the code and test identifiers, such as python -m pytest tests/ -k sim102 (App. K). Following (c), the template keeps each segment in the form Figure 5 lists, the commands and the repository content as main fields, the test output, the final diff and the outcome in reduced form, and it drops the reasoning text and the scratch files (App. L). Its main components are the checks and the locations of Definition 1, which potentially help the next task save the effort of finding what to run and where to look, and they mirror the vali-dation and localization phases of Agentless (Xia et al., 2024), which resolves issues cheaply without open-ended exploration. We further organize these components into two blocks. The task block holds what concerns the current task, what it changed and checked, and the repository block holds gen-eral context, how the repository is laid out and tested. The memory keeps the whole median step saving of M with 6% of its bytes. The procedure needs only paired runs on the next task and a split of the trajectory by role, so it applies wherever tasks follow one another on shared state, and the segments and anchors above are what it yields for coding. Anchors also make the memory traceable, since they mark the steps of a later session that use it, which §3.2 builds on. 

3.2 On-policy adaptation for memory use with provenance-gated value credit 

To use memory efficiently during execution, at steps that are not known in advance but emerge as the task unfolds (App. G), we adapt the actor model itself, so that it acts on the memory in its context where that saves effort, as Eq. (1) asks. To separate what the memory contributes from how a session went, each training group mixes sessions with and without the memory, so the memory’s value to the current actor model is measured on-policy, and that value is credited to the steps that acted on the memory.

4.1 Experimental setup 

We run ChainSWE (Jin et al., 2026) in mini-swe-agent, with its 100 task chains split into a training and a test half over disjoint repositories. We compare our memory with running without memory, with the full history of earlier tasks and with three memory layers, Mem0 (Chhikara et al., 2025), MemOp (Guo et al., 2026) and Reason-ingBank (Ouyang et al., 2026), and report the re-solve rate, steps per task, tokens per session and resolve rate per token. The detailed experimental setup, including the ledger, is in App. B, and results on SWE-bench Verified, external task chains and OpenHands are in App. E.

4.3 Detailed analysis 

We further conduct ablations on the three modules of §3: what the memory layer (M1) carries that the next task acts on, whether the cost-internalizing post-training (M2) lowers effort beyond outcome learning, and whether the provenance-gated value credit (M3) changes how the actor model treats memory; w/o training runs M1 on the frozen actor model, resolve-only RL trains on the resolution term alone and M1 +M2 trains without the value credit (settings in App. A and C). 

M1: the memory hands over anchors the next task uses. Our memory packs the most anchors per thousand injected characters, and the next task acts on 1.32 of them per thousand characters against 0.92 for MemOp, 0.19 for ReasoningBank and 0.14 for Mem0 (Table 2). 

M2: charging steps inside success lowers effort further. Figure 7 (top) places each variant on the effort–resolution plane. Resolve-only RL low-ers steps on 27B from 32 .6 to 30 .4 and on 9B from 91 .9 to 75 .5; charging steps inside success (M1 +M2) lowers them further, to 29 .7 and 63 .8,and the full method stays at 29 .2 and 72 .4.

M3: the value credit teaches when to act on memory. Paying the memory’s value to the steps that acted on it keeps the actor model from learning to follow any memory it is given (Figure 7, bottom): without the value credit a misplaced memory costs the 27B actor model 2.1 steps, while with it the cost shrinks to +0 .3, and the memory benefit grows from +1 .7 to +2 .3 points on 27B. 

5 Related Work 

Memory design and valuation. Coding memory spans cross-task experience (Ouyang et al., 2026), within-task compression and trace validation (Gao et al., 2026; Xu et al., 2026a); MemOp evaluates memory through source-task replay and VibeMem-Bench through target-aware experience (Guo et al., 2026; Fan et al., 2026a). 

Memory optimization. Reinforcement learning trains memory construction with outcome rewards (Wang et al., 2025b; Yan et al., 2026c), refines credit through shared-state rerollouts (Yan et al., 2026b) and localizes it to selected turns or response tokens (Xie et al., 2026; Cao et al., 2026). Our actor adaptation routes the memory’s on-policy value to provenance-marked steps on top of the outcome credit that every step keeps (§3.2). 

6 Conclusion 

Memory for successive coding tasks is what one task leaves for a task it has not seen. Its worth, measured by what the next task saves when it runs with the memory and without it, concentrates in a few anchors, the locations and checks the next task would otherwise rediscover on its own. A memory built around those anchors lowers the next task’s ef-fort on six actor models, and an actor model trained on that value, paid where it acts on them, lowers effort further without lowering resolution. 8Limitations 

Our main experiments use Python repositories in the mini-swe-agent harness, and post-training cov-ers the three open-weight actor models. Other pro-gramming languages and larger actor models re-main to be tested. We measure effort by steps and cache-aware tokens and do not report wall-clock latency or energy use. How memory should be accumulated and refreshed over longer repository histories is future work. 

Ethical Considerations 

This work uses publicly released benchmarks, built from open-source repositories, and models in ac-cordance with their licenses, and involves no hu-man participants. Every agent session runs inside the per-task container image of its benchmark. In deployment, a cross-task memory may retain repos-itory content such as file paths, commands and test output, so in private repositories it should follow the repository’s access control and retention policy, with secrets redacted before storage. As plain text, the memory can be audited and deleted.

Data. ChainSWE (Jin et al., 2026) provides 100

Resolve rate is the share of next tasks whose hidden tests pass on the working tree at the end of the session, reported overall and on the linked and unlinked boundaries. for 27B, 6 for DeepSeek, 3 for Gemma and Luna and 1 for Opus. Differences against the no-memory row of the same actor model are tested with paired chain-cluster bootstrap intervals over the 48 test chains, and the main text calls a difference signifi-cant when the 95% interval excludes zero. 

Post-training and checkpoint rule. The 27B and 9B actor models are post-trained with LoRA at a checkpoint chosen among the few saved during a run, on the training split and by a rule fixed in advance, resolution no lower than the base actor model’s and then the fewest steps. The Gemma actor model is post-trained for 8 updates with no checkpoint selection. App. A reports the 27B actor model at every checkpoint on the test sessions. 

C Ablation Details 

The ablation of §4.3 and Figure 7 reads each variant with its own memory, without memory and with a misplaced memory, averaging 18 /18 /6 replays of these arms for w/o training, 18 /9/6 for M1 +M2 and 6/6/3 for the full method on 27B, and 3/3/3

on 9B except the full method with 6/3/3; the 27B resolve-only arm comes from the run of App. A ( 3

replays in a later window). Memory benefit pairs a variant’s with-memory arm against its own no-memory arm, and misplaced cost pairs the same actor given another repository’s memory against that no-memory arm. Intervals are paired chain-cluster bootstrap 95% intervals over the 48 test chains ( 2000 resamples, seed 0), and an interval that excludes zero is what the main text calls sig-nificant. On the frozen 27B actor model the mem-ory raises resolution from 21 .3% to 23 .4% (+2 .1[+0 .4, +3 .7] ) and lowers steps from 35 .3 to 32 .6,and a misplaced memory changes steps by −0.1[−1.7, +1 .5] . Without the value credit (M1 +M2) a misplaced memory costs the 27B actor model +2 .1

steps [+0 .4, +3 .9] and with it +0 .3 [ −1.2, +2 .1] .On 9B the with-memory and no-memory arms of the untrained, M1 +M2 and full variants were read in one window, their misplaced-memory arms and the resolve-only variant in later ones. The trained variants differ from each other only in the reward and the credit rule; all share learning rate, update count, group shape, memory pool and serving path, and every variant’s untrained control shares that serving path.

G Provenance Calibration 

The gate of Eq. (6) reads the whole assistant mes-sage of a step, its reasoning text and its command, so an anchor named in the reasoning text counts as much as one in the command, and each anchor is credited at its first use. We calibrate provenance as training uses it, with the sibling veto over the first 

8 steps, on the post-trained 27B actor’s held-out sessions with its own memories ( 288 sessions over three replays). Under a real memory 3.46% of steps carry provenance and 169 of the 288 sessions have at least one. Memory-free sessions scored against the memory they would have seen give a leakage null of 1.61% of steps, and misplaced memories give 1.05% . Credited steps concentrate late in a trajectory, with deciles 7 to 9 at about twice the rate of deciles 4 to 6 (ratio 2.02 [1 .52 , 2.78] ), where the actor runs tests and the anchors it uses come from the memory’s TESTS and VERIFY lines. Steps that match the memory early, when the actor opens the files it names, are mostly steps that memory-free sessions also take, so the veto removes about 

88% of them and leaves about 3% of credited steps in the first decile. 

The early-window veto. The window K was fixed before the arm was trained, on the 480 own-memory rollouts of an earlier training run. With no veto 5.5% of steps are memory-driven, with the veto over the first 8 steps of the memory-free ses-sions 1.9% , and with a veto over their whole length 

0.65% . Memory-free sessions have a median of 

26 steps, so the first 8 are an early prefix, and a veto over their whole length would remove most of what the memory supplied. In practice, a test command the memory lists is memory-driven at the step that first runs it, and not if the session ran it earlier or the memory-free sessions reach it in their first steps; a memory-free session has ω ≡ 0.

Why not a likelihood ratio. The natural alter-native weights a step by the ratio of its message’s likelihood with and without the memory in con-text. This alternative is related to context attribu-tion (Cohen-Wang et al., 2024) and to probability contrasts used in context-aware decoding (Shi et al., 2024) and PMI-based summarization (van der Poel et al., 2022); their targets are attribution or faith-fulness rather than executable-task effort. On this actor that ratio carries no signal. In a pilot of 36 

sessions on the 27B actor its AUC is 0.506 for real against the null, and the weight moves with mes-sage length rather than with message content. A flat ratio next to a sharp anchor match says that the memory changes a few actions rather than condi-tioning the whole distribution, which is why the credit signal is provenance and not likelihood. 

H Segments of a Trajectory 

Each step of a trajectory is an assistant message, made of reasoning text and a shell command, fol-lowed by the output of that command. The com-mand goes to the commands segment together with the exit code of its step, and the output goes to one segment by what produced it, under rules fixed before the study (the first match wins). Output of a command that prints a diff ( git diff , git show , a patch file) goes to the change segment; out-19 put of a test runner ( pytest , tox , unittest 

and the like), of a script written in the session or of inline Python that contains an assert goes to the test segment; all other output goes to the repository segment, including that of linters such as flake8 ,which the list does not name. The change the task left in the tree joins the change segment. The out-come and the scratch files come from the boundary, not from the transcript, and harness format mes-sages ( 0.05% of the material) are left out. Each segment is cut to a fixed quota ( 4,000 characters, 

200 for the outcome and 800 for scratch files), so a segment is the same text in every arm that contains it. None of these assignments reads what the text says, since each segment is read off what the har-ness records, the assistant message, the command and its exit code, its output, the diff and the end of the session. Table 7 defines the seven segments with an example from one real session, shown in Figure 9. Three compressed forms are valued alongside the segments and decide how a kept segment is written: the failing commands with their output (here steps 1 and 2, a search that found nothing and a grep on a missing file), the tests with their exit codes but no output, and the file list of the change. The exit code is recorded once per step, so when a command pipes into tail (steps 9 and 10) it is the code of the pipeline, and the test’s own result is in its output. The example comes from the first task of a three-task chain on flake8-simplify in the training split, run by the frozen 27B actor. M Design Choices and Their Alternatives 

This section sets out the alternatives to three design choices and what the paper’s own measurements say about them. 

Adapting the actor rather than training a sep-arate memory reader. A separate reader, or a retrieval policy, decides what memory to hand the actor, either before the task or between its steps. In our setting the memory is short, at most ten lines, and already sits in the actor’s context, so the open question is not which memory to show but whether and when the actor acts on it. Which steps use the memory emerges as the task unfolds. What a coding agent needs is often not evident from the task description and surfaces as it ex-plores and executes, so a single retrieval keyed on the task input falls short of multi-step repository exploration (Trivedi et al., 2023; Yang et al., 2024; Zhang et al., 2026a), retrieval from the unfinished code alone misses what a draft reveals (Zhang et al., 2023), and memory retrieved per subtask during execution outperforms memory retrieved by whole-task similarity (Shen et al., 2026). Retrieval stays compati-ble with this choice, since a retrieval policy decides what memory enters the context and the adaptation changes what the actor does with it. Related con-trollers decide when to inject reminders (PMA; Wu et al., 2026), whether to retrieve or abstain (RSCB-MC; Iscan, 2026), and how to navigate memory at different granularities (NapMem; Xu et al., 2026b). These choices concern memory access, whereas our update targets execution after a short memory is already present. 

A LoRA adapter rather than a separate model or full fine-tuning. A separate memory model leaves the actor untouched but cannot change how it acts on memory, and full fine-tuning can move the actor’s general coding behaviour. A LoRA adapter on frozen base weights is the middle ground, a low-rank update that bounds how far the actor moves while letting it adapt its use of memory. Whether general capability survives is a measurement, not a property of the adapter. On SWE-bench Verified, with no memory in context, the adapted 27B and 9B actors resolve 4.5 and 6.4 points more than their untrained counterparts with 7% and 22% fewer steps (Table 4), so on this benchmark the adaptation cost no general capability. 

Paying the value through provenance rather than leaving it to the outcome reward. Out-come reward already favours whatever raises R,including a good use of memory, but it spreads one scalar over every step of a session, and the steps that use the memory are about three percent of them (App. G). Proposition 1 shows that paid to every step the measured value is a baseline, while paid through the gate it becomes a push on how often the actor acts on the memory, sized and signed by the on-policy measurement. Figure 7 compares this credit with whole-trajectory credit under the same reward. A gate read from how much the memory raised a step’s likelihood is the natural alternative to anchor provenance and carried no signal on this actor (App. G). 

N Related Work 

Agent memory beyond coding. Agent memory encompasses reflective feedback and extracted ex-perience (Shinn et al., 2023; Zhao et al., 2024), reusable workflows and executable skills (Wang et al., 2025c, 2024), and adaptive inference-time experience (Suzgun et al., 2025; Tang et al., 2025). Other systems organize episodic or conversational information through reflection, retrieval, memory hierarchies and linked records (Park et al., 2023; Zhong et al., 2024; Packer et al., 2023; Xu et al., 2025). MemOS and EverMemOS address memory organization and lifecycle management (Li et al., 2025; Hu et al., 2026); Zhang et al. (2024) survey the broader design space. 

Memory for coding agents. Memory systems keep different forms of experience: Mem0 extracts facts from conversations (Chhikara et al., 2025), ReasoningBank and SWE-Exp distill lessons from past trajectories (Ouyang et al., 2026; Chen et al., 2025), Repository Memory and MemCoder mine commit history for localization and development knowledge (Wang et al., 2026; Deng et al., 2026b), and MemOp maintains a per-repository guidebook with a trained writer (Guo et al., 2026). These ap-proaches emphasize retained experience or repos-itory knowledge; our setting additionally carries the actual edited repository state. AdaRepair-Mem selects repair experience by coverage, qual-ity and repair stage (Luo et al., 2026b). Repos-itory context files also require empirical evalua-tion: AGENTS.md studies find that added instruc-tions need not improve success and can increase cost (Gloaguen et al., 2026). Persistent project in-formation appears in deployed assistants through Claude Code’s auto memory and Codex’s cross-session memory generation and injection (An-thropic, 2026a; OpenAI, 2026a). Within one task, SWE-MeM and CompactionRL learn context com-pression jointly with issue resolution (Gao et al., 2026; Li et al., 2026c), and the concurrent Mem-Trace re-validates stored execution traces against the evolving repository (Xu et al., 2026a); these memories do not outlive the task. CAMG-RL like-wise learns file-based memory operations across context boundaries within an episode (Luo et al., 2026a). Between the two lies the boundary a de-ployed agent meets, a memory written before the next task is known and read in the repository state the last task left. 25 Broader memory evaluation. LoCoMo and LongMemEval test long-term conversational mem-ory (Maharana et al., 2024; Wu et al., 2025), StateMemBench tests evolving-state tracking (Fan et al., 2026b), and MemoryArena couples mem-ory with interdependent multi-session actions (He et al., 2026). LongCodeBench evaluates long-context code comprehension and repair (Rando et al., 2025). These settings probe memory reten-tion and use, while our evaluation measures the effort saved on an unseen coding task from inher-ited repository state. 

Evaluating memory on executable tasks. SWE-bench grades each issue from its own snapshot (Jimenez et al., 2024), whereas ChainSWE chains fixes in a shared workspace (Jin et al., 2026) and SWE-Milestone reports resolve falling from above 80% to 38% once state is carried (Deng et al., 2026a); SWEContextBench and Handoff Debt study reuse across related issues and the cost of resuming an interrupted one (Zhu et al., 2026; KC and Budathoki, 2026). Memory-specific evalua-tions isolate the retained information: MemOp reruns the source task with and without a candi-date memory (Guo et al., 2026), VibeMemBench pairs memory-off and memory-on runs of one tar-get whose history is summarised with the target in view (Fan et al., 2026a), and Decision-Aware Memory Cards score evidence by a heuristic esti-mate of its effect on the next action (Guan et al., 2026). Related proxies include interventions on candidate memories for answer quality (Srivastava, 2026), answer-conditioned information gain (Han et al., 2026), and Shapley-based context filtering for code completion (Huo et al., 2026). MemDelta emphasizes controlled model and retrieval compar-isons and write-path cost accounting (Wang, 2026). These evaluations complement our paired runs of an unseen next task from the inherited tree, which measure resolution and effort and attribute savings to trajectory segments (§3.1). 

Learning memory construction and use. Rein-forcement learning has been applied to both sides of the memory interface. Writers are trained from outcome reward or neighbourhood-level marginal utility (Wang et al., 2025b; Yan et al., 2026c; Ye et al., 2026), with finer credit from rerolling at a shared memory state (Yan et al., 2026b), hindsight-filtered utility on writing tokens (Yan et al., 2026a), or token-level attribution (Li et al., 2026a); RoMeRL notes the outcome-broadcast trap but treats paired rollouts as infeasible (Yang et al., 2026). On the reading side, ECHO routes outcome credit to the turns a policy selects back into context (Xie et al., 2026), and MemCalib localises credit by atom ablation (Cao et al., 2026). End-to-end memory learning also includes recurrent consoli-dation in MEM1 (Zhou et al., 2025), chunk-wise processing in MemAgent (Yu et al., 2025), self-memory policies in MemPO (Li et al., 2026b), and operation-tree credit in Mem-T (Yue et al., 2026). These methods optimize different memory inter-faces and credit granularities. Our contribution pairs on-policy valuation on executable next tasks with provenance-gated routing of the additional memory-value term, while retaining outcome credit at every step (§3.2). 

Credit assignment beyond memory. Classical RL assigns hindsight credit to past actions (Haru-tyunyan et al., 2019) or uses counterfactual base-lines to separate action contributions (Foerster et al., 2018; Mesnard et al., 2021). For language mod-els, process supervision supplies intermediate la-bels (Lightman et al., 2024), VinePPO estimates step values with sampled continuations (Kazem-nejad et al., 2025), GiGPO groups repeated states for local advantages (Feng et al., 2025), and C3 replays downstream continuations after message interventions in agent teams (Chen et al., 2026). These methods address action or message utility; our provenance gate identifies traceable memory use and routes measured memory value without estimating each step’s causal effect. 

Efficient coding and policy training. SWE-Gym and SWE-smith expand executable training tasks and agent trajectories (Pan et al., 2025; Yang et al., 2025), while SWE-RL trains on software-evolution data (Wei et al., 2025). SWE-Edit re-duces overhead through editing-interface decom-position (Zhang et al., 2026b); L1 and efficient-reasoning RL shape generation length and infer-ence compute (Aggarwal and Welleck, 2025; Arora and Zanette, 2025).
