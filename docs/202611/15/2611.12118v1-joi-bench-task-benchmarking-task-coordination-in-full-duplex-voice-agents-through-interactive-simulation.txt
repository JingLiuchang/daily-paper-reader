# Joi-Bench-Task: Benchmarking Task Coordination in Full-duplex Voice Agents through Interactive Simulation 

Xiangheng He †, Mingjun Zhao †, Zhehao Fan, Zhengjia Li, Xiaopeng Sun, Qingqing Xiao, Haolan Chen ‡, Yu Xu 

Platform and Content Group, Tencent 

Abstract 

Full-duplex voice agents enable natural, hands-free interaction, allowing users to refine re-quests, redirect ongoing work, and seek clari-fication while the agent is speaking. However, existing voice-agent benchmarks insufficiently isolate coordination between task execution and conversation. We introduce a benchmark that assesses this coordination by examining whether agents track what is being executed, what has been completed, what has been com-municated, and what remains to be reported as the conversation evolves. We propose an interactive user simulator that introduces con-figurable interventions at designated timing in tool execution and spoken result delivery, sup-porting controllable and reproducible evalua-tion conditions. We evaluate five leading com-mercial voice agents along three dimensions: execution responsiveness, coordination under request changes, and coordination under inter-ruptions. Agent evaluations reveal persistent coordination failures. Under request changes, the highest result completion rate is only 55%, indicating difficulty for current voice agents adapting to new requests while preserving ear-lier obligations. After user interruption, four of the five agents exhibit average information omission rates of at least 23%. These find-ings highlight task coordination as a central challenge for current voice agents in complex, evolving conversations.

Large language model (LLM) agents combine rea-soning, planning, and tool use to accomplish com-plex tasks (Yao et al., 2023). Full-duplex voice agents extend these capabilities to spoken inter-action, processing speech while speaking and en-abling users to interrupt at any moment (Défossez et al., 2024). Advances in speech interaction and tool use are moving voice agents beyond real-time dialogue prototypes toward prac-tical assistants for complex everyday tasks (Ray et al., 2026). Recent voice-agent benchmarks jointly assess conversational dynamics and task performance (Ray et al., 2026; Lin et al., 2026a), with GPT-Live-1 achieving 84.7% completion on English tasks (Sierra, 2026). Yet task success alone does not establish whether agents can coordinate ongoing work with evolving dialogue. While tools are still running, agents must promptly answer progress in-quires and reconcile task additions, cancellations, or priority changes with ongoing operations. Like-wise, when interrupted while reporting tool results, agents must accurately track what users have heard and resume after follow-ups or pauses without omit-ting key information. Evaluating these capabili-ties requires interventions timed to tool execution and speech playback, alongside assessment of how agents maintain execution and communication state across them. Existing evaluations insufficiently iso-late this coordination. Evaluating this coordination requires an inter-active, controllable user simulator that acts as a proxy for a human user throughout the conversa-tion. In realistic interactions, users may revise or expand their requests as tasks unfold, while also answering clarification questions from the agent. A simulator must therefore generate contextually ap-propriate responses and control when specific user behaviors occur. The timing of these behaviors is particularly important: adapting ongoing work should be tested during tool execution, whereas in-terrupting and resuming unfinished communication should be tested during result delivery. Our contributions are threefold: 1. 3 Method 

3.1 Benchmark Framework 

Our benchmark evaluates whether full-duplex voice agents adapt to evolving requests while track-ing task and communication progress. Tasks fall into two groups: (1) coordination during task exe-cution, including a baseline without interventions, status inquiries, priority changes, request withdraw, and task addition; and (2) coordination during spo-ken result delivery, including pause-resume and inquiry-resume interactions during unfinished an-nouncements. Table 2 summarizes task conditions, prescribed user behaviors, and successful agent be-haviors. Figure 1 illustrates the benchmark framework, comprising a user simulator, an API-based voice agent, and an asynchronous tool environment. The simulator streams user speech to the agent, which produces spoken responses and tool calls. The en-vironment executes these calls and returns their re-sults while speech interaction continues. Recorded interactions support evaluation of execution respon-siveness and coordination under request changes and interruptions. 

3.2 Controllable User Simulator Tick-based Simulation Clock Following τ -Voice, we decouple simulated conversational time from wall-clock computation by pausing the simula-tion during non-realtime LLM response genera-tion and TTS synthesis. Audio is exchanged in fixed-duration ticks (e.g., 200 ms), each advanc-ing simulated time by that duration regardless of preparation latency. Both participants can speak within the same tick, enabling overlap and interrup-tions. This allows an LLM-TTS pipeline to sim-ulate a full-duplex user with independent control over language generation, speech synthesis, and user behavior. 

User Simulator Architecture As illustrated in Fig-ure 2, our user simulator comprises an observation module, an intervention controller, an LLM, and a TTS component. The observation module main-tains the conversation history and tracks tool exe-cution events and audio playback progress. Using these observations and the case specification, the in-tervention controller determines which prescribed user behavior to initiate and when. The LLM gen-erates contextually appropriate utterances, which TTS converts into speech for buffering and stream-ing to the agent through the tick-based interaction loop. 

Intervention Timing Control Controlling inter-vention timing is essential to achieving our coor-dination evaluation objectives. As shown in Fig-ure 2, the intervention controller manages three tim-ing aspects: (1) the tool execution window, identi-fied from tool events, with interventions scheduled at configured offsets; (2) the spoken result deliv-ery window, detected through incremental ASR of played audio after tool results become available; and (3) content-based interruption points within re-sult delivery, triggered when ASR transcripts match specified content cues. Timing follows the shared simulation clock and reflects actual execution and playback progress.

Each scenario groups related requests around a shared practical goal, such as preparing for a journey, organizing a meal, or managing family schedules. Request changes and interruptions have contextually plausible motivations: a user may pri-oritize charging availability when the battery is low, withdraw a check after a family member supplies the answer, or pause a report to attend to another activity. We instantiate these scenarios as 140 test cases. 20 multi-tool scenarios each yield a baseline with no request changes and three request-change variants-priority change, task withdraw, and task addition-producing 80 cases. 20 single-tool scenar-ios include user inquiries during execution, produc-ing 20 cases. The remaining 20 result-delivery sce-narios each yield pause-resume and inquiry-resume variants, producing 40 cases. Each interaction con-dition includes 20 cases, with variants of the same scenario sharing the initial request and tool config-uration to support controlled comparisons as user requests change or result delivery is interrupted. We assign controlled tool execution durations to represent operations with different response times and create opportunities for interaction while work is ongoing. In multi-tool scenarios, the five initial tools have execution durations of 60, 15, 5, 5, and 5 seconds, allowing some results to become available while other operations remain in progress. These durations are identical across the baseline with no request changes and the three request-change vari-ants; the additional tool in task-addition cases takes 15 seconds. Single-tool waiting scenarios use a 60-second duration, providing a window for users to ask status during execution. For pause-resume and inquiry-resume scenarios, tools return five-item re-ports without an artificial execution delay, allowing evaluation to focus on coordination during spoken delivery. These controlled settings support consis-tent comparisons of how agents manage ongoing execution, available results, and evolving user re-quests. 

4.2 Configurations for API-based Voice Agent 

We evaluated five top-tier application-level close-source voice agents, all accessed through their of-ficial APIs. We evaluate these five voice agents in English using the same scenario definitions, tool in-terfaces, and reporting instructions. Each agent re-ceives the complete set of 80 tools and is instructed to initiate independent tool calls concurrently, re-port available results promptly, and resume unfin-ished result delivery after interruptions. The eval-uation includes 140 cases per agent, yielding 700 conversations, with a maximum conversation dura-tion of 480 seconds. Realtime 1.5, Realtime 2, Grok Voice 3.0, and Gemini 3.8 Live share a tick-based simulation clock, with each representing 0.2 seconds. All four use default VAD settings and interruption handling supported by their official API protocols. When an interruption is detected, the framework stops local playback and discards unplayed audio. Tool execution and result delivery follow each API’s supported protocol. Realtime 2 uses high reason-ing effort with parallel tool calling enabled, while Realtime 1.5 retains its default tool-calling con-figuration. Both receive tool results as they be-come available, with explicit requests to continue responding. Gemini uses non-blocking function calls and WHEN_IDLE result scheduling, allow-ing results to arrive independently while schedul-ing their announcement after the current response. Grok also executes tool calls asynchronously, but its protocol requires all outstanding function results to be submitted before requesting a spoken continu-ation. We additionally wait for ongoing playback to finish because preliminary attempts to announce in-dividual results immediately produced overlapping speech. GPT Live 1.0 uses its native continuous audio interface, paired with GPT-5.6-Terra as the reasoning and tool-use backend, with parallel tool calling enabled and no separately configured VAD component. It requires a continuous input audio stream paced in real time, preventing the use of the same pausable tick-based simulation clock as the other four APIs. 

4.3 Configurations for User Simulator 

The user simulator uses GLM-5.3 with temperature 1.0 to generate contextually appropriate responses, including answers to clarification questions, and Qwen3-TTS-12Hz-1.7B-Base to synthesize En-glish speech with a shared reference voice. Dia-logue context is constructed from playback-aligned assistant transcripts. For inquiry-triggered interrup-tions, Qwen3-ASR-1.7B transcribes played assis-tant audio, and GPT-5.6-Terra determines whether the designated result content has been reached. 

4.4 Configurations for Auto-evaluation 

For automated evaluation, we transcribe recorded client-side playback using Qwen3-ASR-1.7B and obtain word-level timestamps with Qwen3-ForcedAligner-0.6B, using Whisper-large-v3 as a fallback when transcription or timestamp vali-dation fails. The transcripts are combined with tool-call records, returned results, and interruption events to assess tool-call correctness, compliance with changed requests, resumption, and informa-tion coverage. Claude Opus 5 first serves as the semantic evaluator, identifying relevant utterances and matching announced information against the re-quired tool results. Latencies and aggregate scores are then computed programmatically from recorded timestamps and validated annotations. GPT 6 Astra subsequently reviews the annotations and evalua-tion outputs for correctness, with any necessary corrections incorporated into the final reported re-sults.

5.2 Multi-Tool Scheduling and Coordination 

Table 5 with tool-start latency and announcement latency results in Table 4 reveals limitations in scheduling both tool invocation and result deliv-ery. Realtime 1.5 invokes tools sequentially, wait-ing for the preceding tool result before initiating another tool call. This sequential scheduling re-sults in a concurrency met score of 0%, compared with 100% for the other four voice agents, and con-tributes to its high multi-tool start latency of 37.37 s. Grok Voice 3.0 supports concurrent tool invo-cation, but following the provider’s documented protocol, it should be configured to wait for all tool results to arrive and any ongoing speech to finish before announcing the results. We also tested an-nouncing each result as it became available, but this caused overlapping announcements that severely disrupted result delivery. This result delivery wait-ing contributes to Grok’s highest multi-tool result announcement latency of 51.16 s. Across all five systems, multi-tool workloads yield lower Pass@1 and higher tool start latency and result announcement latency than single-tool tasks. These results suggest that multi-tool tasks impose greater demands on user intent understand-ing and coordination between tool invocation and result delivery. Our qualitative review of the record-ings reveals more frequent requests for clarification of tool arguments in multi-tool tasks, including requests for users to explicitly spell out param-eter values. This behavior suggests that agents have greater difficulty resolving the required tool arguments when handling multiple tools, consistent with the lower first-attempt accuracy. Clarification exchanges can also increase result-announcement latency: when one tool returns its result, the agent may still be clarifying arguments for another tool, delaying the announcement of the available result.

5.4 Coordination Under Interruptions 

Table 7 evaluates two complementary aspects of coordination after an interruption. Resumption rate measures whether agents return to unfinished re-sult delivery. Information omission rate assesses whether agents accurately track where result de-livery was interrupted, distinguishing what had al-ready been communicated from what still needed to be reported to the user. Although the agent’s system prompt explicitly requires it to resume exe-cution in both pause–resume and inquiry–resume tasks, all five agents achieve lower resumption rates after an inquiry. Averaged across agents, the rate falls from 74% under pause-resume to 49% under inquiry-resume. A possible explanation is that a pause more clearly signals the intention to con-tinue the interrupted delivery, whereas an inquiry introduces another conversational objective that the agent must address while retaining its earlier reporting obligation. Indeed, every agent success-fully answers the intervening inquiry, but this does not ensure a return to unfinished delivery. All five agents exhibit varying degrees of dif-ficulty accurately tracking the interruption point and distinguishing what has already been commu-nicated from what remains to be reported. To track this point accurately, agents must notice the client’s actual playback progress and the user’s accurate barge-in position within the result announcement. Audio transmitted to the client may not yet have been played, so treating all transmitted audio as already communicated can cause agents to skip in-formation the user has not heard. GPT Live 1.0 resumes result delivery most effectively, with infor-mation omission rates of 0% under pause-resume and 7% under inquiry-resume. Realtime 2 per-forms worst on both metrics, with resumption rates of only 5% and 0% and information omission rates of 78% and 80% under pause-resume and inquiry-resume, respectively. Moreover, resuming speech does not ensure that all required information is an-nounced: Gemini achieves a resumption rate of 90% after a pause but an information omission rate of 43%. These findings highlight two chal-lenges for voice agent design: reliably resuming interrupted result delivery and ensuring that all re-maining information is communicated to the user. 

5.5 User Simulator Controllability 

We assess whether the user simulator can reliably deliver prescribed behaviors at designated stages of the interaction while responding to clarifica-tion requests. Across 700 conversations, the sim-ulator achieves a behavior delivery rate and an intervention-window hit rate of 99.86% (699/700). In the single problematic case, the agent made in-correct tool calls and repeatedly requested clarifica-tion of a parameter until the time limit was reached, preventing complete delivery of the scheduled user behaviors. Among the 69 conversations in which agents asked clarification questions, the simulator successfully answered all 92 questions, yielding a clarification-response rate of 100%. These re-sults demonstrate reliable control over user behav-ior and intervention timing in the evaluated con-versations, while retaining the flexibility to answer agents’ questions as the interaction unfolds. 

6 Conclusion 

We introduced Joi-Bench-Task, a benchmark for evaluating how full-duplex voice agents coordinate ongoing task execution and spoken result delivery as user requests evolve. Our proposed user sim-ulator reliably controls intervention content and timing while remaining interactive during conver-sations, establishing controllable and reproducible conditions for evaluating voice-agent coordination. Evaluating five leading commercial voice agents reveals persistent coordination failures. Multi-tool experiments indicate that handling multiple tasks places a greater burden on agents’ request inter-pretation and coordination of tool execution and result delivery. Experiments under request changes reveal difficulties adapting to revised requirements while preserving unaffected obligations. Interrup-tion experiments expose failures to resume unfin-ished result delivery and communicate complete information. These findings point toward improv-ing how voice agents track and coordinate ongoing execution, completed work, information commu-nicated, and information remains to be reported. Joi-Bench-Task provides a framework for evaluat-ing this coordination throughout evolving conver-sations. 

Limitations 

Our benchmark currently focuses on English inter-actions. Extending the evaluation to additional lan-guages would help assess whether the observed co-ordination patterns hold across different linguistic settings, including variations in how users express requests, seek clarification, and interrupt ongoing speech. Future work will explore multilingual eval-uation to broaden the coverage of user interactions. Our evaluation also uses audio without added background noise or environmental sounds, provid-ing controlled acoustic conditions for studying task coordination. Everyday interactions may involve traffic noise, household sounds, or background con-versations, which could influence request under-standing and interruption handling. We plan to incorporate realistic environmental audio tailored to different usage scenarios, such as in-car assis-tance and cooking, to better represent the settings in which users interact with voice agents. Finally, the tool environment uses mock func-tions with manually specified execution durations. This design supports reproducible comparisons and controlled interventions during ongoing execution. Integrating real tools and databases would comple-ment this setup by introducing naturally varying response times and data-dependent results. Future work will explore these integrations to assess coor-dination in practical workflows while retaining the benchmark’s controllability and reproducibility. References
