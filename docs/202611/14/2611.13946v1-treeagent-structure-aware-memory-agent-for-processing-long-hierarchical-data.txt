Abstract
Practical Web applications increasingly require agents to interpret
long conversations or documents. As the data length goes beyond
the context windows of base large language models (LLMs), recent
research proposes memory agents to process the input segment
by segment and retain information from previous segments within
a bounded memory. However, existing memory agents typically
divide the input into flat token segments without preserving its
structure or recording its hierarchy, leading to three limitations
when processing structured data such as API responses or HTML
documents. First, fixed-length token segmentation can separate
the fields belonging to the same structured record, breaking their
inherent relationships. Second, individual segments lack hierar-
chical information, making their structural context and positions
unclear. Third, successive memory updates may discard the de-
tails from earlier necessary sibling records for reasoning on later
segments. To address these limitations, we propose TreeAgent, a
structure-aware agent that uses the input hierarchy to guide both
segment-wise context processing and access to past information.
Specifically, TreeAgent constructs segments from complete subtrees
and groups of adjacent sibling subtrees to preserve local structural
relationships. We provide theoretical guarantees on segment counts
to guide token budget selection toward matching the segment count
of fixed-length segmentation. We further attach structural paths to
the segments for the agent to identify their ancestors and hierar-
chical positions. We also introduce residual memory links from the
segments of low-level children to the segments of high-level par-
ents, enabling direct information flows beyond successive memory
updates. We evaluate TreeAgent with four representative memory
agents on eight retrieval and aggregation tasks. The inputs are
derived from real-world application data in JSON, HTML, YAML,
and JavaScript and range from 8K to 1M tokens. TreeAgent im-
proves the average score across the four datasets for all four agents,
with 3.61% performance gain on average. Our code is available at
https://github.com/ZJU-LLM-Safety/TreeAgent.

Introduction
Large language model (LLM) agents have made significant advances
across diverse domains in recent years [18, 26, 41, 47, 49]. As these
agents process increasingly long inputs, the input length can exceed
the context windows of their underlying models [32]. To address
this over-length issue, recent research has introduced memory
agents, which process the input segment by segment and continu-
ally update a bounded memory to retain relevant information for
subsequent reasoning. Memory agents have demonstrated strong
performance on question-answering tasks involving documents far
longer than the LLMs’ native context windows [42, 48].
However, when processing long structured data such as API
responses and HTML documents in Web applications[5, 52], exist-
ing memory agents exhibit the following three limitations. First,
existing methods typically split the input into fixed-length token
segments, which can separate related fields within the same record,
so associations already represented in the original structure may
need to be reconstructed across segments. Second, existing mem-
ory agents process each segment without an explicit indication of
its position in the input hierarchy. Without this information, the
agent may form incorrect associations between segments, leading to
flawed subsequent reasoning [5, 17]. Third, successive updates and
compression of bounded memory may discard information needed
for subsequent reasoning across segments and records [36, 42].
To address these limitations, we propose TreeAgent, a structure-
aware agent that uses the input hierarchy to guide both segment-
wise processing and access to historic information. TreeAgent pre-
serves complete subtrees or groups of adjacent sibling subtrees
within a segment whenever the token budget permits, making their
local structural relationships available within a single memory up-
date. Starting from the entire input tree, TreeAgent recursively
applies this segmentation strategy to its subtrees whenever the
current tree exceeds the token budget. Grouping adjacent sibling
subtrees reduces the number of small segments that would other-
wise be emitted separately. However, preserving subtree bound-
aries can still leave unused capacity, producing more segments than
fixed-length segmentation at the same token budget. We analyze
the optimality of greedy sibling grouping and establish the budget
needed to compensate for unused capacity within a sibling sequence.
Based on the theoretical guarantees derived from this analysis, we
adjust the token budget to keep the segment count close to that
of fixed-length segmentation. Each segment is augmented with a
structural path that explicitly links its local content to the enclosing
structure, enabling the agent to interpret the current input within
its hierarchical context for reasoning across related segments.
TreeAgent further introduces residual memory links to bring
fine-grained information from historic memory into reasoning at
higher levels. During segment-wise processing, TreeAgent saves the
memory after each segment and uses the parent–child relationships
in the original input to link historic memories associated with

We evaluate TreeAgent with four representative memory agents:
MemAgent, InfMem, MemReread, and ReMemR1. The evaluation
uses structured inputs derived from real-world application data
in JSON, HTML, YAML, and JavaScript. Input lengths range from
8K to 1M tokens. Across these formats, we assess eight retrieval
and aggregation tasks that require locating values and reasoning
about their structural relationships. The tasks include retrieving
multiple fields from one record, retrieving fields across records,
counting matching records, identifying frequent values, and find-
ing numerical extrema. For each agent, we compare TreeAgent
with its corresponding fixed-length segmentation baseline while
keeping the model parameters and existing memory update and
answering procedures unchanged. The baselines retain each agent’s
native retrieval, rereading, or callback operations when available,
allowing the comparisons to assess the benefit of TreeAgent within
the existing workflows. TreeAgent improves each agent’s average
score across the four datasets, with a mean gain of 3.61% over the
corresponding baselines. Sequential ablations show that structural
paths and residual memory provide further improvements beyond
structural segmentation alone.
Our contributions are summarized as follows:
(1) We propose TreeAgent, a structure-aware agent that par-
titions long hierarchical inputs into subtree sections and
equips each section with an explicit structural path, preserv-
ing local structural relationships and hierarchical context
throughout recurrent memory processing.
(2) We introduce residual links in TreeAgent to directly trans-
mit historic evidence relevant to the question from low-level
child subtrees to high-level parents, mitigating information
loss across successive memory updates.
(3) We evaluate TreeAgent on retrieval and aggregation tasks
over long structured inputs derived from real-world appli-
cation data. Comparative experiments with four representa-
tive memory agents and component ablations demonstrate
its effectiveness across diverse structured formats.

TreeAgent: A Structure-Aware Agent for
Reasoning over Hierarchical Data
TreeAgent uses the input hierarchy to organize both the content of
each observation and access to historic evidence (Figure 1). Struc-
tural sectioning keeps fitting subtrees intact and groups adjacent
siblings to control the section count. Structural paths identify where
each section belongs, while residual memory links make memo-
ries associated with processed children available when the final
segment of their parent is processed. Together, these components
supply local content, its hierarchical context, and relevant historic
evidence to the agent’s existing memory update procedure.
3.1
Sectioning Hierarchical Inputs
TreeAgent favors complete subtrees when constructing sections
so that fields within each retained subtree are available together
during a single memory update.

Residual Memory Links
Combining information across segments can require historic evi-
dence that is no longer retained in the current memory. TreeAgent
retrieves relevant evidence from previously saved memory states
through residual memory links organized by the input hierarchy.
After processing each segment 𝑠𝑡, TreeAgent saves the updated
memory 𝑚𝑡under the segment index 𝑡. For a node 𝑣∈𝑉, let ℓ(𝑣)
denote the index of the final segment containing content from its
subtree. TreeAgent associates 𝑣with the saved memory state 𝑚ℓ(𝑣),
which contains the agent’s cumulative memory after that segment
has been processed. For a leaf split across multiple text spans, ℓ(𝑣)
identifies the segment containing its final span.

boundaries between consecutive segments. For each parent 𝑝and

segment of 𝑝, provided that the source memory is available before

4
Experiments
We evaluate whether TreeAgent improves existing memory agents
across structured input formats, context lengths, and task types
without additional training. Component ablations and computa-
tional measurements further assess the contributions of its struc-
tural components and the associated inference costs.
4.1
Evaluation Data and Tasks
We collect publicly available structured data from real-world appli-
cations, including API responses, web pages [5], interface specifica-
tions [1], and static structured data from open-source repositories.
The data cover four formats: JSON, HTML, YAML, and JavaScript.
The JSON dataset contains API responses from USGS [38], NVD
[23], NIH [24, 25], GBIF [9], Crossref [6], Contracts Finder [10],
and USAspending [39], covering earthquake events, vulnerabilities,
research funding and clinical trials, biodiversity, scholarly metadata,
and public procurement and spending. The HTML data include web
pages and DOM records from sources such as WebSRC, while the
5


Gu et al.
YAML data include OpenAPI specifications from sources such as
APIs.guru. The JavaScript data include object and array initializers
extracted from open-source repositories [2, 8, 22, 27, 37, 43], rep-
resenting static structured state in applications. Inputs retain the
syntax and hierarchical structure of their respective formats.
The evaluation comprises eight tasks that range from retrieval
within a single record to retrieval across multiple records and ag-
gregation within a specified scope. Three tasks retrieve one, two,
or four fields from a single specified record, testing whether agents
associate the requested fields with the correct entity. Two further
tasks retrieve the same field from two or four specified records, re-
quiring agents to distinguish entities and collect the corresponding
information. The remaining three tasks require aggregation over
records within the scope specified by the question: counting records
that satisfy a condition, identifying the most frequent values, and
finding a numerical extremum.
The evaluation uses four datasets, one per format, covering eight
input lengths from 8K to 1M tokens. Natural language questions are
formulated from the records in each input according to the eight
task definitions, with 50 test examples per task and input length.
4.2
Experimental Setup
Memory agents. We evaluate MemAgent-7B [48], InfMem-4B
[42], MemReread-4B [16], and ReMemR1-7B [36]. We integrate
TreeAgent into their inference procedures without additional train-
ing. Within each agent, Flat and TreeAgent share model parameters
and the original memory update and answer procedures.
Evaluation protocol. Within each agent, Flat and TreeAgent share
the test examples and evaluation protocol. Flat uses a segment bud-
get of 5,000 tokens, and TreeAgent adjusts its token budget to ap-
proximate Flat’s segment count using the procedure in Section 3.1.
Metrics. We report mean answer scores. Single-value and numer-
ical answers receive a score of one if correct and zero otherwise. For
multi-value answers, the score is the number of correctly matched
values divided by the larger of the predicted and reference list
lengths, with answer order enforced when required by the question.
Dataset scores average equally over tasks and input lengths; overall
scores further average equally over datasets and agents.
4.3
Main Results
Overall performance. Table 1 shows that TreeAgent increases the
overall mean answer score from 39.49% to 43.10%, yielding a gain
of 3.61%. All four memory agents improve when averaged across
the four datasets. InfMem-4B and MemReread-4B obtain gains of
5.65% and 6.35%, respectively, while MemAgent-7B and ReMemR1-
7B improve by 0.85% and 1.58%. TreeAgent outperforms Flat in 14
of the 16 comparisons across agents and datasets. Averaging over
agents, gains are positive on all four datasets. These results show
improvements across agents and input formats, with substantial
variation in their magnitude across agents.
Performance across context lengths. Figure 2 reports mean answer
scores as inputs grow from 8K to 1M tokens. Both methods generally
score lower on longer inputs. Nevertheless, TreeAgent outperforms
Flat in 31 of the 32 comparisons across agents and context lengths,
including all four agents at 1M tokens. For MemReread-4B, the gain
increases from 2.43% at 8K to 8.40% at 1M.
Performance across task types. We use the JSON evaluation set
to examine how the overall improvements are distributed across
the eight tasks. Figure 3 reports TreeAgent’s gains over Flat for
each memory agent, with each result averaged equally over the
eight context lengths. Averaging equally across the four agents,
TreeAgent improves all eight tasks, with gains ranging from 3.41% to
9.81%. The mean gains for retrieval within a record, retrieval across
records, and aggregation are 6.40%, 6.53%, and 6.84%, respectively.
These comparable gains show that the benefits extend from field
retrieval within individual records to tasks requiring information
collection and aggregation across records.
InfMem-4B gains 10.46% and 14.12% on retrieval from two and
four records, respectively, exceeding its gains on all three tasks
involving retrieval within a single record. MemReread-4B also ob-
tains substantial gains of 10.48% and 16.26% on these two tasks. For
both agents, the improvement is larger when retrieving from four
records than from two. These results demonstrate benefits when
agents must collect information from several records, consistent
with TreeAgent’s design objective of organizing current inputs
while providing access to historic information.
MemReread-4B improves on all eight tasks, including gains of
28.00% on single-field retrieval and 23.50% on numerical extrema.
Its improvements span field retrieval, retrieval across records, and
aggregation. ReMemR1-7B exhibits a different pattern: its largest
gains occur in conditional counting and frequent-value identifica-
tion, at 8.75% and 3.96%, while changes in tasks requiring multiple
fields or records are smaller. InfMem-4B improves on seven tasks
but loses 1.75% on frequent-value identification. These results show
that both the distribution and magnitude of task-level gains depend
on the underlying memory agent.

Related Work
Memory agents. Recurrent Memory Transformer passes learned
memory tokens across text segments to maintain information across
processing steps [3]. At the agent level, MemAgent processes long
inputs segment by segment and updates bounded memory before
producing an answer [48]. Subsequent work extends memory main-
tenance and access through gating for updates and stopping, re-
trieval, memory-guided rereading, and operations over memory
banks [35, 50]. InfMem incorporates retrieval into memory control
[42], MemReread uses existing memory to guide rereading [16],
and ReMemR1 enables callbacks to historic memory states during
memory updates [36]. TreeAgent complements these mechanisms
by using the input hierarchy to organize the segments and his-
toric evidence available at each update, while retaining the agent’s
memory update and answer procedures.
Structured document understanding. Document structure has
been used to improve content representations and reading com-
prehension. MarkupLM encodes XPath information in document
representations [17], while DOM-LM and WebFormer also exploit
webpage structure to model relationships among content elements
[7, 40]. WebSRC studies the roles of textual semantics and struc-
tural information through question-answering tasks that require
understanding webpage structure [5]. TreeAgent examines how
this structure can support the processing of long inputs segment by
segment. It preserves complete subtrees that fit the budget so that
locally related fields are available within a single memory update,
and attaches structural paths to identify each segment’s hierarchical
position when it is presented separately from the full input.
Hierarchical retrieval and reasoning. Hierarchical structures also
organize retrieval and reasoning over long documents. RAPTOR
constructs retrieval trees through recursive clustering and summa-
rization [33], while Chen et al. use discourse relations for hierar-
chical retrieval [4]. ToM exploits document hierarchies to generate
rationales at child nodes and aggregate them at parent nodes for
bottom-up reasoning [11]. TreeAgent likewise uses hierarchical rela-
tions to organize information integration, operating on cumulative
memory states formed during segment-wise processing. Parent–
child relations in the input tree link the historic state associated
with a child to the final segment of its parent. The structural re-
lations determine which historic states are accessible and when,
while the question guides the selection of relevant evidence within
those states. Information retained in historic states can therefore
contribute again to reasoning at higher structural levels without
having to survive every intervening memory update.
6
Conclusion
We presented TreeAgent for processing long hierarchical inputs
using recurrent memory agents. TreeAgent uses the input hierarchy
to organize sections, identify their structural locations, and retrieve
relevant evidence from historic memory states, while retaining the
underlying agent’s memory update and answer procedures. Our
theoretical analysis establishes upper bounds on segment counts
and guides the selection of a token budget to keep these counts
close to those of fixed-length segmentation. Residual links allow
relevant historic evidence to bypass intermediate memory updates
and inform reasoning at higher structural levels. We evaluated
TreeAgent on retrieval and aggregation tasks across four formats
and input lengths from 8K to 1M tokens. Without additional train-
ing, TreeAgent improves the average score across datasets for all
four evaluated agents, with an overall gain of 3.61%. Sequential
ablations show additional average gains from structural paths and
residual memory links with retrieval beyond those from sectioning
alone. Together, these findings support using input hierarchy to
guide both the organization of current observations and access to
historic memory when reasoning over long structured data.

B
Benchmark and Data Appendix
The main paper defines the shared tasks, answer contract, and
evaluation grid. This appendix provides the additional informa-
tion needed to inspect the benchmark data: source provenance
and licenses, parser units, construction and validation procedures,
and dataset inventory. Representative native-format excerpts are
provided in our code repository.
B.1
Benchmark Sources, Construction, and
Validation
We selected source collections whose native syntax exposes an
explicit hierarchy and whose visible records support deterministic
lookup and aggregation. The four benchmarks therefore test the
same capabilities without converting the original JSON, HTML,
YAML, or JavaScript syntax into a common representation.
JSON dataset. The JSON dataset contains API responses from
seven source groups. USGS provides earthquake events and their
attributes [38]; NVD provides CVE vulnerability records, scores, and
references [23]; and NIH provides research funding projects through
RePORTER and clinical trial records through ClinicalTrials.gov
[24, 25]. GBIF provides species occurrence records and taxonomic
information [9], while Crossref provides metadata on scholarly
works, authors, and references [6]. Contracts Finder provides UK
procurement and contract records [10], and USAspending provides
US federal contract spending records [39].
The parser unit is a JSON value inside an ordered response list.
Construction selects supporting records, generates a question in
natural language and a reference specification, and adds distractor
payloads. Validation executes the reference specification over the
complete visible context and checks answer uniqueness, with ag-
gregation restricted to the scope specified by the question. The 32K
training and development splits are used for model development;
the test split, which contains all eight length buckets, is held out.
Multimodal clinical reasoning is outside this benchmark [12, 14].
HTML dataset. The HTML dataset uses pages from the WebSRC
v1.0 test archive [5], which declares CC BY 4.0. Its parser units are
HTML tables, lists, and DOM subtrees; text, element order, and
native markup remain visible to the model. Construction derives
lookup and aggregation questions from records with unique visible
descriptions and fills the target length with additional WebSRC
pages. Independent validation reparses every context, executes the
stored reference specification, checks source identifiers and answer
uniqueness, and verifies the length constraints under the tokenizers
used during construction. The dataset contains only test examples.
YAML dataset. The YAML dataset uses OpenAPI documents in-
dexed by the APIs.guru directory [1]. For each document, we record
its source identifier and available license metadata. A parser unit is
one YAML OpenAPI document; paths, operations, parameters, and
responses supply records. Canonical documents are deduplicated
before construction. Lookup examples preserve their target fields
and supporting documents across lengths, whereas aggregation
answers are recomputed after distractor documents are added. An
independent validator reparses the YAML, replays the document
paths and reference specifications, and checks source composition
and context lengths. The dataset contains only test examples.
JavaScript dataset. The JavaScript dataset evaluates static struc-
tured state written in JavaScript syntax; it does not evaluate pro-
gram execution or general program understanding. The dataset
is built from statically extractable object and array initializers in
six repositories distributed under the MIT License: ESLint, web-
pack, three.js, Plotly.js, Babel, and Lodash [2, 8, 22, 27, 37, 43]. Calls,
functions, spreads, identifier references, computed keys, parse er-
rors, sensitive strings, and ambiguous records are rejected. Every
accepted initializer is checked by a Tree-sitter parser and an inde-
pendent JSON5 interpretation, which must produce the same static
value without executing source code. Each initializer retains its
source repository, license, and location. The dataset contains only
test examples and measures static record retrieval and aggregation.
B.2
Dataset Inventory
The four benchmarks contain 29,200 unique examples: 19,600 for
the JSON dataset, including its training and development splits,
and 3,200 test examples for each of the HTML dataset, the YAML
dataset, and the JavaScript dataset. The evaluation in the main text
uses the 3,200 held-out test examples from each benchmark.

C.2
Controlled Comparison
Within each memory agent, Flat and TreeAgent use the same exam-

control actions, answer interface, decoding parameters, and evalu-

During recurrent reading, Flat supplies the current text sec-

TreeAgent supplies a structural section, its structural path, and
query-relevant spans retrieved from the saved states indexed by L𝑡,
while retaining the original agent’s context and control procedure.
The source indices follow the residual links defined in the main
paper: a child state associated with ℓ(𝑣) is eligible at 𝑡= ℓ(𝑝) only
when ℓ(𝑣) < 𝑡. At most four spans are supplied per update, each
limited to 96 tokens. Retrieval precedes the memory update, and
the updated state is saved under the current section index.

C.4
Evaluation and Aggregation
The primary metric is the mean answer score defined in the main
paper. The evaluator first extracts the final answer containing only
the requested values and then applies the rule for the corresponding
task. Matching respects the requested order for ordered retrieval
tasks and ignores order for the frequency ranking task. Text match-
ing is insensitive to case and surrounding formatting. Numerical
matching allows a tolerance equal to the larger of 0.01 and 0.1% of
the reference magnitude.
An unavailable model response is represented by an empty ex-
tracted answer; empty or malformed extracted answers receive zero.
Scores are first averaged over the 50 examples in each combination
of benchmark, task, context length, memory agent, and method.
The score for each benchmark averages the eight tasks and eight
lengths equally. The reported average over benchmarks gives equal
weight to the JSON dataset, the HTML dataset, the YAML dataset,
and the JavaScript dataset. Thus, the aggregate is not weighted by
context tokens or by the number of model calls.

D
Exploratory Fine-Tuning
We conduct an exploratory experiment to assess whether addi-
tional training improves InfMem-4B when used with TreeAgent.
Starting from the released checkpoint, we optimize the model with
Group Relative Policy Optimization (GRPO) [13, 34] on 16,000 JSON
training examples at 32K tokens. We select the checkpoint with
the highest mean answer score on a separate development set of
400 examples at 32K. The selected checkpoint and the checkpoint
before training are evaluated on the same JSON test set, using the
same TreeAgent observation process, greedy decoding, and answer
scoring.
Training runs for 30 steps with 64 prompts per batch and four
rollouts per prompt. We use a learning rate of 5 × 10−6 and apply
LoRA to all linear modules with rank 32, scaling factor 32, and
zero dropout. Training examples are shuffled with seed 42, and
checkpoints are saved every five steps. The reward combines the
answer score with two auxiliary terms of 0.05 each for a valid
interaction and completion of the memory update. Safety-aware
fine-tuning remains future work [29, 31, 44].

E
Evidence Scope and Statistical Interpretation
The evaluation concerns recurrent memory agents on explicit hi-
erarchies in JSON, HTML, YAML, and static JavaScript initializers,
excluding visual authenticity assessment [19–21, 51]. These four
native formats provide complementary tests of record binding, hier-
archical lookup, and aggregation across sibling records. TreeAgent
uses the hierarchy exposed by the corresponding parser, so the com-
parison focuses on how structured observations affect recurrent
memory updates.
The comparison without additional training uses greedy decod-
ing. The paired confidence intervals on the JSON dataset quantify
variation in the score difference between TreeAgent and the Flat
baseline over matched examples, complementing the aggregate
results across agents, formats, tasks, and context lengths.
