Discovering Effective Agent Memory Designs through Program Evolution
Xinheng Ding1, Seyyed Saeid Cheshmi1, Ziyang Zhang1, Tairan Chen2
Wenya Xie1, Yu Hou1, Rui Zhang1, Zirui Liu1
1University of Minnesota
2Stevens Institute of Technology
Abstract
Program evolution provides a promising ap-
proach to discover agent memory designs and
study the choices underlying their effective-
ness. We introduce MAPE, a framework that
evolves whole memory programs from mini-
mal seeds through a standardized lifecycle inter-
face and an iterative diagnosis–proposal loop.
Experiments on LoCoMo and LongMemEval
yield an absolute accuracy gain of up to 12%
over manually designed baselines at 35% of
the serving cost, with further evaluations sup-
porting transfer across serving backbones and
benchmarks. Empirical analyses and ablations
identify and validate two recurring design pat-
terns: retaining raw conversations as retriev-
able evidence preserves details omitted from
extracted memories, while composing retrieved
evidence according to query intent helps the
answering model use it effectively. Transplant-
ing the composition module into five existing
memory systems improves accuracy across all
five.
Beyond these patterns, the search ob-
jective shapes where computation goes: op-
timizing serving cost alongside accuracy shifts
computation from LLM-based memory con-
struction to selective processing at query time
while retaining competitive accuracy. Together,
these findings offer empirical lessons for agent
memory design. Code is available at https:
//github.com/ash-ding/MAPE.

Introduction
Agents powered by large language models, such
as personal assistants and conversational compan-
ions (Wang et al., 2024; Xi et al., 2023), increas-
ingly depend on persistent memory of user in-
formation to maintain continuity across conversa-
tions. Agent memory systems (Packer et al., 2023;
Chhikara et al., 2025; Xu et al., 2025; Rasmussen
et al., 2025; Liu et al., 2026a) address this need
by transforming interaction history into memory
units, organizing them in a persistent store, and
retrieving relevant information to support subse-
quent responses. Prior work has advanced memory
representation, organization, maintenance, and re-
trieval (Zhang et al., 2024), yet these components
are often designed and refined through human ex-
pertise.
Meanwhile, LLM-driven evolutionary search has
emerged as a tool for automated scientific discov-
ery and algorithm design (Romera-Paredes et al.,
2024; Liu et al., 2024; Ma et al., 2024). Systems
such as AlphaEvolve (Novikov et al., 2025) em-
ploy an LLM to propose program modifications
and automated evaluation to guide subsequent pro-
posals, yielding mathematical constructions and
algorithms that outperform established designs. Re-
cent work extends this paradigm to agent memory,
evolving prompts, configurations, or executable
pipelines to improve memory performance (Deng
et al., 2026; Liu et al., 2026b; Liu et al., 2026c).
These approaches often constrain the search
space to selected components or start from estab-
lished memory architectures, and primarily empha-
size accuracy. We explore a complementary direc-
tion: evolving entire memory programs from mini-
mal seeds to study the designs that emerge under
different optimization objectives. Beyond finding
better programs, we seek to understand how evolu-
tion implements effective memory design choices,
whether their benefits extend to other memory sys-
tems, and how different optimization objectives
shape those choices. Explicitly considering serving
cost also allows us to study how evolution allocates
computation across the memory lifecycle. Specifi-
cally, we ask: ❶What effective memory system de-
signs can whole-program evolution discover from
minimal seeds? ❷How do different optimization
objectives shape the evolutionary process and the
resulting designs?
To investigate these questions, we develop MAPE,
a framework that evolves agent memory systems
through whole-program evolution, as illustrated in

We run MAPE on LoCoMo (Maharana et al.,
2024) and LongMemEval (Wu et al., 2025) under
both objectives, yielding four experimental settings.
For each, we analyze the evolutionary trajectory
and the resulting memory system. All selected
systems outperform the evaluated human-designed
baselines on their respective benchmarks. On Lo-
CoMo, we observe an absolute accuracy gain of
up to 12% at 35% of the serving cost. Further
evaluations include cross-backbone validation us-
ing GPT-4.1 mini and Qwen3-30B-A3B-Instruct-
2507 (Yang et al., 2025), as well as bidirectional
cross-benchmark transfer between LoCoMo and
LongMemEval, all without additional evolution.
These results support the transferability of the dis-
covered memory designs across serving backbones
and benchmarks.
Across the discovered systems, we identify two
recurring design patterns: retaining raw conver-
sations as retrievable evidence and processing re-
trieved evidence through intent-specific scaffolds
before answering. A case study and component
ablations examine the contribution of each pat-
tern in a representative system.
Retaining raw
evidence helps preserve details omitted from ex-
tracted memories, while error attribution across
human-designed systems identifies incomplete re-
trieved information as a major bottleneck. The com-
position module routes queries to intent-specific
scaffolds that combine targeted extraction, deter-
ministic computation, and deliberation to support
the answering model. Transplantation experiments
test this composition strategy across five human-
designed memory systems, improving accuracy in
every case and demonstrating its utility beyond the
evolved program.
Comparing the two objective settings reveals dif-
ferences in both search behavior and computation
allocation. In the observed runs, accuracy-only
search progressively adds operations, accepting
substantial cost increases for marginal accuracy
gains. The illustrated joint accuracy–cost trajec-
tory maintains lower serving costs and explores
more branched candidate lineages, retaining inex-
pensive alternatives as starting points for further
evolution. The resulting designs differ in where
they spend computation. The selected accuracy-
only programs invest in LLM-based memory con-
struction, whereas the selected accuracy–cost pro-
grams reduce reliance on it in favor of selective
computation at query time, using 90% and 40%
fewer serving calls on LongMemEval and LoCoMo
while retaining strong evaluation-set accuracy.
Our contributions are threefold:
• We introduce MAPE, a framework for discov-
ering and studying agent memory designs
through whole-program evolution from mini-
mal seeds under a standardized lifecycle inter-
face.
• We identify raw-conversation retention and
query-dependent composition as recurring
design patterns, validate their contributions
through ablations, and demonstrate the trans-
ferability of composition by transplanting it
into five human-designed systems.
• We show how optimization objectives shape
evolutionary trajectories and computation al-
location, with joint accuracy–cost search shift-
ing computation from LLM-based memory
construction to selective processing at query
time.

2.2
Program Search Space
We construct a program search space for explor-
ing diverse memory system designs under a com-
mon lifecycle interface I. Candidate programs
implement memory construction and retrieval and
can additionally define how retrieved evidence is
composed into the answer context. Evolution can
modify these stage implementations and their sup-
porting code. This allows evolution to explore alter-
native representations, retrieval mechanisms, and
evidence-processing procedures, including coordi-
nated changes across stages. Appendix A provides
a simplified Python class interface.
The resulting search space MI is bounded by
interface compatibility and a fixed answering proce-
dure. Within each evaluation setting, the answering
model, prompt, and evaluation protocol are held
constant, enabling comparisons among the discov-
ered memory designs under shared evaluation con-
ditions.
2.3
Search Objectives
Throughout an evolutionary run, each candidate
program m is evaluated on a fixed search set D.
Serving LLM and embedding calls use the same
designated LLM and embedding model, respec-
tively, across all lifecycle stages. This shared con-
figuration enables controlled comparisons of can-
didate programs in terms of answer accuracy and
lifecycle serving cost.
Accuracy.

judge (Zheng et al., 2023) to evaluate answer cor-

With both metrics recorded, we run the evolu-
tionary search in two modes: MAPE-A optimizes
accuracy alone, whereas MAPE-P treats accuracy
and lifecycle serving cost as separate objectives.
Its Pareto frontier contains programs for which no
other evaluated candidate achieves at least equal
accuracy and no greater cost, with a strict improve-
ment in at least one objective (Deb et al., 2002).
The proposer uses this frontier to guide subsequent
proposals, while the archive retains all evaluated
candidates.
2.4
Evolutionary Search Loop
MAPE begins by evaluating the seed programs and
placing them in an archive. At each iteration, the
proposer consults archived implementations, eval-
uation results, and diagnoses, selects parent pro-
grams, and produces a new candidate with a de-
sign hypothesis. The hypothesis states the intended
change and its expected benefit, providing a basis
for subsequent diagnosis.
The candidate first undergoes a small sanity eval-
uation to identify execution errors. The proposer
can repair these errors within a fixed budget, and
candidates that pass are evaluated on the full fixed
search set to obtain accuracy and lifecycle serving
cost. A separate diagnosis agent then examines
the implementation, design hypothesis, evaluation
results, and available execution traces to assess the
observed outcome and identify potential causes of
failure. The diagnosis informs subsequent propos-
als without modifying the evaluated candidate.
After evaluation and diagnosis, the candidate im-
plementation, parent references, hypothesis, results,
traces, and diagnosis are added to the archive. All
evaluated candidates are retained, including dom-
inated designs, allowing later proposals to revisit
earlier implementations rather than extend only the
current best program. Search continues until the
proposal budget is exhausted. The evaluation set
remains unavailable throughout evolution and is
used only afterward in the program-selection pro-
cedure described below. Figure 1 illustrates the
loop, and Appendix B.1 provides the initialization,
search budgets, and execution settings.
2.5
Program Selection
After evolution, we shortlist candidates using
search-set accuracy for MAPE-A and the search-
set accuracy–cost Pareto frontier for MAPE-P,
with additional inclusion criteria described in Ap-
pendix B.2. The shortlisted programs are frozen
and evaluated on a larger evaluation set that re-
mains inaccessible during evolution.
We then
inspect their implementations and exclude pro-
grams with impractical scaling behavior, such as
exhaustive LLM processing of the history during
retrieval. For each setting, we report the remaining
program with the highest evaluation-set accuracy.
The selected programs are denoted MAPE-ALCM,
MAPE-PLCM, MAPE-ALME, and MAPE-PLME, where A
and P indicate the accuracy-only and joint accuracy–
cost search objectives, and LCM and LME denote
evolution on LoCoMo and LongMemEval, respec-
tively.

Results and Analysis
4.1
Performance Evaluation
On the LoCoMo evaluation set with GPT-4.1 mini,
MAPE-ALCM and MAPE-PLCM achieve overall accu-
racies of 87.94% and 85.18%, respectively, as
shown in Table 1.
MAPE-ALCM outperforms all
baselines across every question category, while
MAPE-PLCM retains competitive accuracy at approx-
imately 28% of its counterpart’s lifecycle serving
cost. On LongMemEval with Qwen3-30B-A3B-
Instruct-2507, MAPE-ALME and MAPE-PLME achieve
77.00% and 72.25% accuracy, respectively, both
exceeding RAG, the strongest baseline at 66.00%.
MAPE-ALME achieves an absolute accuracy gain of
11.00% over RAG, as shown in Table 2.
Replacing the serving backbone of the LoCoMo-
evolved programs, including the QA model, with
Qwen3-30B-A3B-Instruct-2507 preserves strong
performance without further evolution. Under this
backbone, MAPE-PLCM achieves 81.33% accuracy,
an absolute gain of 12.01% over SimpleMem at
35% of its serving cost. The ranking between the
two evolved programs reverses, with MAPE-ALCM
achieving 78.58%. This reversal is driven by tem-
poral questions: MAPE-ALCM drops from 79.84%
to 43.80%, whereas MAPE-PLCM retains 70.93%.
MAPE-ALCM leaves the final date-resolution step to
the QA model, while MAPE-PLCM explicitly converts
relative time expressions into absolute dates before
answering, which may help preserve temporal ac-
curacy across backbones. A concrete example is
illustrated in Figure 4.
We further evaluate the selected programs on
the other benchmark without additional evolution,
using the fixed input adapters described in Ap-
pendix D.1. As shown in Table 6, MAPE-ALCM and
MAPE-PLCM achieve 65.50% and 64.25% accuracy
on LongMemEval, respectively. Both transferred
programs outperform the five evaluated memory
systems, while RAG achieves 66.00% accuracy.
In the other direction, MAPE-ALME and MAPE-PLME
achieve 75.90% and 74.67% accuracy on LoCoMo,
respectively, exceeding all baselines in Table 7.
These results support the transferability of the
discovered memory designs beyond their search
benchmarks, suggesting that their gains are not
solely attributable to benchmark-specific adapta-
tion.
4.2
Comparing Evolution under Different
Objectives
Search trajectories.
The observed runs exhibit
different patterns of refinement and exploration. In
the illustrated accuracy-only trajectories, search
progresses from simple strategies toward increas-
ingly elaborate designs, adding operations to ad-
dress remaining errors. As accuracy approaches
a plateau, further gains come with substantial in-
creases in serving cost. As shown in Figure 5, in-
troducing per-session note extraction at build time
from step 13 increases cost approximately sixfold
for additional search accuracy. Figure 6a illustrates
the predominantly additive nature of this process,
with successive revisions extending a dominant
chain. The illustrated joint accuracy–cost trajectory
maintains lower serving costs and exhibits a more
branched lineage, as shown in Figure 6b, exploring
alternative designs and removing costly operations.
Lower-accuracy candidates can remain nondomi-
nated and serve as starting points for subsequent
revisions.

The selected pro-

the memory lifecycle. MAPE-ALME extracts atomic

accuracy–cost designs instead retrieve raw con-
versation text and compute selectively at query
time:
MAPE-PLME uses BM25 (Robertson and
Zaragoza, 2009) without build-time model calls,

tracted facts only for aggregation questions. These

4.3
Emergent Memory Designs and
Component Analysis
Across the two benchmarks and optimization ob-
jectives, the discovered memory systems exhibit
two recurring design patterns: retaining raw con-
versational content and retrieving it as evidence,
and routing queries to different composition strate-
gies according to question type. To examine these
patterns in detail, we conduct a case study and
component analysis of MAPE-ALME, a representative
design that incorporates both.
Figure 2 illustrates the workflow of MAPE-ALME,
highlighting two core designs. (1) It organizes
memory hierarchically while retaining both ex-
tracted and raw evidence. During construction,
an LLM extracts atomic notes (Chen et al., 2024)
from each session, while the original conversation
is preserved as individual rounds; both are jointly
indexed using dense and lexical retrieval. At re-
trieval time, item-level scores are aggregated to
rank sessions, and the system returns session-level
note bundles alongside up to five highest-ranked
raw conversation rounds. (2) Query-Routed Scaf-
folding (RQS) conditions composition on query
type. RQS routes each query by intent and runs
an intent-specific scaffold that pairs LLM extrac-
tion with deterministic computation, for instance
date arithmetic for temporal queries and per-session
item extraction followed by programmatic counting
for aggregation queries. A final deliberation call ap-
plies intent-specific instructions to produce a draft
answer, which is passed alongside the evidence to
the fixed QA model for final answer generation.

the difficulties in temporal reasoning and counting
identified by the proposer and diagnosis agents dur-

evaluation protocol, as shown in Figure 3. Mem0
shows the smallest improvement, at 2.75%. Our er-
ror analysis suggests that its failures are dominated
by missing retrieved information, whereas RQS pri-
marily addresses cases in which sufficient evidence
is available but the QA model fails to identify or
use it effectively.

Related Work
Agent memory design and empirical analysis.
Agent memory systems organize interaction his-
tories through reflection, selective updates, and
hierarchical storage, as exemplified by Genera-
tive Agents, MemoryBank, and MemGPT (Park
et al., 2023; Zhong et al., 2024; Packer et al.,
2023). Mem0 extracts and consolidates memories
(Chhikara et al., 2025), while Zep and A-Mem orga-
nize them through temporal knowledge graphs and
linked networks, respectively (Rasmussen et al.,
2025; Xu et al., 2025). LightMem combines topic-
based organization with offline consolidation (Fang
et al., 2025). SimpleMem combines semantic com-
pression with intent-aware retrieval (Liu et al.,
2026a). Mem0, Zep, A-Mem, LightMem, and
SimpleMem serve as baselines in our empirical
analysis.
Prior work has explored preserving conversa-
tional histories and processing evidence after re-
trieval. CoM combines lightweight memory con-
struction with query-oriented organization of re-
trieved fragments into inference chains (Xu et al.,
2026). CoM also informs our inclusion of a pro-
8


grammable composition stage.
DeferMem and
LazyMem shift evidence processing to query time,
using learned models to produce relevant evidence
from retrieved histories (Yin et al., 2026; Yu et al.,
2026). ReFind instead enables an agent to search
raw conversation logs directly (Li et al., 2026).
These approaches differ in whether they primarily
improve access to evidence or transform retrieved
evidence for answering.
Recent empirical studies further examine the
value of memory construction relative to raw-
history retrieval. Raw-RAG demonstrates the com-
petitiveness of dense retrieval and reranking over
raw histories (Bao et al., 2026). Memory Tax dis-
tinguishes the benefits of memory transformation
from losses caused by removing or obscuring use-
ful evidence (He et al., 2026). These findings pro-
vide complementary evidence for the importance
of preserving and accessing source information.
MAPE examines memory design choices through
program evolution and evaluates the resulting com-
ponents through ablation and transplantation. Its
query-routed scaffolding combines intent-specific
evidence processing with deterministic computa-
tion and deliberation.
Evolution of agent memory systems.
MetaMem
evolves knowledge-utilization guidance (Xin et al.,
2026). MemTrace uses attribution of failures across
memory operations to guide prompt optimization
(Deng et al., 2026), while EvolveMem adapts re-
trieval and answer-generation configurations (Liu
et al., 2026b). MemEvolve jointly evolves experi-
ential knowledge and memory architectures within
a modular design space (Zhang et al., 2026). At the
level of agent capabilities, Mem2Evolve couples
experience distillation with the creation of reusable
tools and expert agents (Cheng et al., 2026). Mem-
Pro extends this direction to system-level evolution,
treating memory construction–retrieval pipelines
as executable programs subject to failure-guided
revision (Liu et al., 2026c). MemScope uses exe-
cution traces and runtime memory state to guide
localized code repairs to an existing memory archi-
tecture (Su et al., 2026). These studies span the
evolution of stored experience, reusable capabili-
ties, and memory system code. MAPE starts from
minimal seeds and permits coordinated changes
across memory construction, retrieval, and com-
position. By comparing accuracy-only and joint
accuracy–cost objectives, we examine how search
objectives shape memory designs and the alloca-
tion of computation across stages. Beyond evalu-
ating the resulting programs, we use component
ablations and transplantation across existing mem-
ory systems to assess which design choices con-
tribute to their effectiveness and transfer beyond
the evolved implementation.
6
Conclusion
We introduced MAPE to study agent memory design
through whole-program evolution from minimal
seeds. Across two benchmarks, the evolved pro-
grams instantiate two recurring design patterns: re-
taining raw conversations as retrievable evidence
and processing retrieved evidence through intent-
specific scaffolds before answering.
Ablations
highlight the value of preserving raw evidence,
while transplanting the evolved composition mod-
ule improves all five evaluated human-designed
systems. Under the evaluated workloads, incor-
porating serving cost into the search objective fa-
vors selective query-time processing over LLM-
based memory construction, while retaining com-
petitive accuracy. Together, these findings illustrate
how program evolution, combined with component
analysis and transplantation, can produce effective
memory systems and empirically grounded design
lessons.
Limitations
Our findings concern conversational memory on
two QA benchmarks, with detailed component anal-
ysis centered on one representative program. Trans-
fer and transplantation experiments extend the eval-
uation across models, benchmarks, and memory
systems, while applicability to experiential memory
and open-ended agents remains to be established.
Evolutionary trajectories and resulting programs
can vary across runs, and program selection and
design interpretation involve empirical judgment.
Our cost comparisons cover serving token charges
for LLM and embedding calls, excluding search
expenses, local computation, and latency. Their
implications depend on workload, particularly how
memory construction costs are amortized across
queries.

B
Evolutionary Search Details
B.1
Search Configuration
Initialization.
MAPE-P is initialized with no-
memory and full-context seeds, representing min-
imal memory overhead and unrestricted access to
conversation history, respectively. These seeds pro-
vide contrasting starting points for exploring the
trade-off between accuracy and cost. MAPE-A starts
only from the no-memory seed to reduce architec-
tural anchoring on full-context inference and en-
courage exploration beyond incremental revisions
to that design.
Search budget.
We perform three evolutionary
runs per setting on LoCoMo and one per setting on
LongMemEval. Each run consists of 20 steps, with
one candidate program proposed at each step.
Execution and repair.
Before full evaluation,
each proposed candidate undergoes a sanity check
using three questions from one search conversa-
tion on LoCoMo or two search instances on Long-
MemEval. If the check fails, the proposer receives
the error trace and can repair the program up to
twice, with a new check after each repair. Can-
didates that still fail are not evaluated on the full
search set. Candidates that pass are evaluated on
the entire search partition without progressive fil-
tering or resampling between steps. Each proposer
invocation allows up to 80 agent turns and 45 min-
utes, while each diagnosis invocation allows up to
40 turns and 30 minutes.
Search objective.
MAPE-P jointly optimizes QA
accuracy and lifecycle serving cost as two sepa-
rate objectives. The proposer uses the accuracy–
cost Pareto frontier to guide candidate generation.
MAPE-A optimizes QA accuracy alone.
Search models.
Both the proposer and diagnosis
agents use Claude Opus 4.8 with reasoning effort
set to xhigh throughout the evolutionary loop. Dur-
ing search, GPT-4.1 mini serves as the backbone
for both LLM-based memory operations and QA
generation on LoCoMo, while Qwen3-30B-A3B-
Instruct-2507 serves these roles on LongMemEval.
We use text-embedding-3-small for all embedding
calls across both benchmarks.
B.2
Program Selection
Shortlisting.
For MAPE-A, we shortlist the top
20% of candidates ranked by search-set accuracy.
For MAPE-P, we shortlist all candidates on the
search-set accuracy–cost Pareto frontier.
Each
shortlist additionally includes the program with
the most direct children in that run’s lineage, if it
is not already included. On LoCoMo, we pool the
shortlists from the three runs within each setting
before final selection. Shortlisted programs are
frozen and evaluated on the larger evaluation set,
which remains unavailable throughout evolution.
Implementation screening and final selection.
After evaluation, we manually inspect the short-
listed implementations and exclude programs with
impractical scaling behavior, such as reliance on
full-history inference or exhaustive LLM-based
processing of the history during retrieval. For each
setting, we report the remaining program with the
highest evaluation-set accuracy. The evaluation
set is thus used for final selection, but provides no
feedback for program evolution.

Serving models.
We use GPT-4.1 mini and
Qwen3-30B-A3B-Instruct-2507 as serving back-
bones for evaluation-set comparisons.
Within
each setting, the designated backbone handles both
LLM-based memory operations and answer gen-

beddings. Qwen is served locally on eight NVIDIA
H100 GPUs.
Selected programs and baselines
share the same designated models and benchmark-
specific answering procedure. The QA prompt tem-
plates are provided in Appendix E.1.
Accuracy.
GPT-5 mini judges each predicted an-
swer against the ground-truth answer using the
benchmark-specific rubric. For reported bench-
mark results, we pool the resulting binary correct-
ness judgments across all evaluated queries to ob-
tain overall accuracy. The judge prompt templates
are provided in Appendix E.2. Reported accuracy
gains and drops are absolute differences.
Generation settings.
The shared QA wrapper
sets a completion limit of 16,384 tokens and leaves
temperature, top-p, and the generation seed unspec-
ified, using API or serving defaults. Calls within
memory programs can override wrapper defaults.
The GPT-5 mini judge uses low reasoning effort
and a 16,384-token completion limit. If a length-
limit error occurs without visible output, the judge
retries once with a 32,768-token limit.
Lifecycle serving cost.
We record LLM input,
LLM output, and embedding token usage across
build, retrieve, compose, and answer, and apply the
corresponding per-token prices of the designated
models. Following §2.3, we amortize the total
cost over the answered queries for each history and
take an unweighted mean across histories, reporting
dollars per 1,000 queries. Judge and search-agent
calls, general-purpose computation, and storage are
excluded.

on OpenAI1 and Alibaba Cloud Model Studio2 list
prices. The rates below are in USD per million

D.5
Query-Routed Scaffolding: Design,
Ablation, and Transplant
Design.
Query-Routed Scaffolding (RQS) imple-
ments the compose stage of MAPE-ALME, as shown
in Figure 2. It processes retrieved evidence through
three steps: routing, scaffolding, and deliberation.
Route. Rules based on the query wording assign
each question to one of six intents: temporal, ag-
gregation, difference, current-value, preference, or
direct lookup. The assigned intent determines the
subsequent processing strategy.
Scaffold. For temporal questions, the scaffold ex-
tracts event dates and explicitly stated durations. It
anchors relative expressions such as “last week” to
the relevant session date and resolves them through
date arithmetic. For aggregation questions, it ex-
tracts matching items from each session, removes
duplicates, and counts or sums the items in code.

Prompt 4: LoCoMo Judge
Your task is to label an answer to a question as CORRECT (1) or WRONG (0). You will be given the
following data:
(1) a question (posed by one user to another user),
(2) a 'gold' (ground truth) answer,
(3) a generated answer
which you will score as CORRECT (1) or WRONG (0).
The point of the question is to ask about something one user should know about the other user based
on their prior conversations.
The gold answer will usually be a concise and short answer that includes the referenced topic, for
example:
Question: Do you remember what I got the last time I went to Hawaii?
Gold answer: A shell necklace
The generated answer might be much longer, but you should be generous with your grading - as long
as it touches on the same topic as the gold answer, it should be counted as CORRECT (1).
For time related questions, the gold answer will be a specific date, month, year, etc. The
generated answer might be much longer or use relative time references (like "last Tuesday" or "next
month"), but you should be generous with your grading - as long as it refers to the same date or
time period as the gold answer, it should be counted as CORRECT (1). Even if the format differs (e.
g., "May 7th" vs "7 May"), consider it CORRECT if it's the same date.
Now it's time for the real question:
Question: {query}
Gold answer: {reference}
Generated answer: {prediction}
First decide CORRECT or WRONG. Output ONLY a JSON object:
{"reason": "<one sentence explanation>", "score": <1 if CORRECT else 0>}

Evolutionary Search Prompts
We present selected excerpts from the proposer and diagnosis prompt templates used in the evolutionary
search. Wording is preserved, with line wrapping adjusted and omissions marked by [...]. The proposer
excerpts are grouped by role and objective, interface and constraints, proposal strategy, and output
requirements. Group headings are editorial. The two objective blocks are alternatives selected by the
search setting. Template placeholders and escaped braces are retained. The diagnosis output instructions
are placed last for readability.
Prompt 9: Proposer: Selected Excerpts
ROLE AND SEARCH OBJECTIVE
You are a researcher designing memory systems for AI agents.
[...]
How it does that — what it stores, in what structure, and how it finds things again — is yours to
decide.
Accuracy-only:
WHAT COUNTS AS A BETTER DESIGN, on this run: a higher `accuracy_<dataset>` than the best harness
already has, compared at the same `stage_<dataset>`. That is the entire criterion.
Accuracy--cost:
WHAT COUNTS AS A BETTER DESIGN, on this run: a candidate that NO existing harness beats on BOTH
axes at once — one that would join the Pareto frontier. Pushing EITHER edge outward counts, and
they count equally: more accurate at the same cost, the same accuracy for fewer tokens, or a trade-
off nobody occupies yet.
[...]
INTERFACE AND CONSTRAINTS
Class inheriting from `forge.memo_class.MemoClass`, implementing the two required hooks, and

The diagnosis agent attributes findings to build, retrieve, compose, answer, judge, or data, and uses
unattributed when the evidence is insufficient. Its core analysis and reporting instructions are shown
below.
Prompt 10: Diagnosis: Selected Excerpts
You are handed ONE harness that has finished evaluation. Say what happened and why, from the
evidence, and leave the next proposer something it could not have worked out on its own.
You do not propose a design. You do not write harness code.
[...]
## Method
1. **Read the hypothesis, then the diff.** What did this candidate change relative to its parent,
mechanically — not what its docstring claims.
2. **Read the numbers on every axis this run records**, against the parent. `metrics.json` splits
the dollars by phase, so a cost change can be placed in build, retrieve or answer.
3. **Attribute the failures.** Go through the wrong answers. Group them, then for each group follow
the evidence to the earliest operation that made the outcome inevitable. Cite what you read: a `qa
` record, a `call` record, a line of the harness's code.
4. **Write the leads.** What the evidence says is worth trying next, each one attached to the
finding that motivates it.
[...]
If the evidence does not settle it, use **unattributed** and say what would settle it (a level the
run did not record, a call that was truncated).
[...]
Exactly two files, both under `diagnostics/`, and nothing else anywhere:
diagnostics/<<ANALYST_ID>>.md
prose, for the next proposer to read
diagnostics/<<ANALYST_ID>>.json
