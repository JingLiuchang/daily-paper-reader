Abstract—Web agents extend LLMs from text generation to
real-world web interaction by relying on execution harnesses
that interpret user goals, perceive webpages, plan actions, and
ground model decisions into browser operations. While prior
work has recognized that agent security depends on more than
the backend model alone, how harness design quantitatively
shapes web-agent security remains insufficiently measured.
To systematically study web-agent harness security, we first
characterize web-agent harnesses as a four-stage execution
workflow covering goal interpretation, webpage perception,
reasoning and planning, and action execution. Based on this
abstraction, we build WEBTRAP FARM*, a systematic and
extensible evaluation framework covering three representative
attack categories: malicious user prompts, malicious prompt
injection, and deceptive web design. To avoid conflating security
with task capability, we use paired usability calibration tasks to
separate genuine defensive behavior from capability limitations.
Our evaluation shows that existing web-agent harnesses
remain vulnerable to typical attacks, with some unsafe behaviors
occurring even without explicit attack content, revealing harness-
intrinsic security failures (RQ1). Statistical analysis further
shows that both harness and backend model significantly affect
security outcomes, indicating that deployed-agent security is
jointly shaped by the harness and backend model (RQ2). Finally,
we localize where defensive behavior emerges across workflow
stages and identify more secure design mechanisms, providing
actionable guidance for building more robust web agents (RQ3).
These findings highlight the web-agent harness as an important
security boundary and motivate moving beyond model-centric
defenses toward harness-level security design.
1. Introduction
Large language models (LLMs) are increasingly inte-
grated into agents that autonomously interact with real web
environments. Unlike chatbots, web agents automate practical
tasks such as information retrieval, online transactions, and
appointment scheduling [1, 2, 3, 4]. However, exposing
LLMs to untrusted webpages and connecting model out-
puts to real-world actions introduce broad security threats,

including malicious user prompts [5, 6], webpage prompt in-
jection [7, 8, 9, 10], and deceptive webpage designs [11, 12].
Prior studies have shown that web agents can be easily
attacked, but they provide limited insight into why unsafe
actions are executed. Most evaluations focus on the ro-
bustness of backend models against malicious instructions
or adversarial webpage content [8, 13]. Although recent
academic and industry efforts have recognized that system-
level design choices beyond the backend model can affect
agent security [14, 15, 16], how harness design quantitatively
shapes web-agent security across different systems and attack
surfaces remains insufficiently measured.
Existing evaluations provide limited support for such
measurement because they often entangle harness-level secu-
rity with model robustness and task capability. Specifically,
these works face three limitations. First, they often focus on
a specific type of attack, making it difficult to understand the
overall security exposure of web agents across different attack
surfaces. Second, they may conflate attack failures caused by
insufficient task capability with successful defenses, which
overestimates the agent’s security resilience and introduces
bias into the evaluation. Third, existing benchmarks are often
coupled to specific agent harnesses, imposing substantial
manual effort on cross-harness and systematic evaluation.
Our Work. Therefore, we present WEBTRAP FARM, a uni-
fied framework for quantitatively measuring and dissecting
security resilience in web agents. WEBTRAP FARM enables
systematic cross-harness evaluation while separating secu-
rity behavior from task incapability and localizing where
defensive behavior emerges in the execution workflow. It
includes an extensible benchmark covering three major
attack categories across different attack surfaces: Malicious
User Prompts, Malicious Prompt Injection, and Deceptive
Website Design. To avoid conflating security with task failure,
WEBTRAP FARM introduces paired usability calibration tasks
that distinguish defense success from cases where an agent
simply cannot complete the original task. It also provides
a cross-harness execution and monitoring suite based on
webpage instrumentation, enabling consistent evaluation
without additional manual effort. We conduct experiments
around three research questions:
RQ1: How vulnerable are web-agent harnesses and
backend models under different attack surfaces? We

first evaluate the end-to-end vulnerability of both open-

representative harnesses with multiple backend models and
measure their attack success rates, including naive attacks that
contain no explicit injected instruction or deceptive content.
This design allows us to test whether unsafe execution
depends on specific harnesses or models, and whether it
can arise from ordinary task execution. Our results show
that vulnerabilities persist across the open-source harnesses,
with an overall attack success rate of 32.55%. The evaluated
commercial systems achieve lower attack success rates but
still exhibit meaningful vulnerabilities.
RQ2: How much does the web-agent harness matter
for agent security resilience? We next examine the effects
of harness and backend model on security resilience. Using
usability calibration, we apply a mixed-effects logistic regres-
sion to quantify harness and model effects while accounting
for repeated tasks and attack-category effects. Our results
show that the harness, backend model, and their interaction
all have significant effects on security outcomes (p < 10−45),
and remain robust under sensitivity analyses for capability-
dependent missingness. These results show that deployed-
agent security is jointly shaped by the harness and backend
model, rather than being determined by either factor alone.
RQ3: Where does defensive behavior emerge within web-
agent harnesses, and which design mechanisms strengthen
security? Finally, we localize observed defensive behavior
across the four workflow stages. Using execution traces, we
identify effective defenses after excluding attacks mitigated
at earlier stages. The resulting stage-level analysis reveals
different defensive patterns across attack surfaces, which we
further examine through controlled ablations. For user-side
attacks, the ablations support the security benefits of fine-
grained intent interpretation and risk-aware reasoning. For
web-side attacks, they support perception filtering and goal-
anchored planning. These results provide concrete guidance
for designing more secure web-agent harnesses.

• A systematic and extensible framework for eval-

WEBTRAP FARM, a framework for quantitatively measur-

surfaces. WEBTRAP FARM combines usability calibration,
harness-independent monitoring, and unified metrics,
while supporting the incorporation of emerging attacks

• A quantitative evaluation of how harness and model
jointly shape web-agent security. We systematically
evaluate diverse harness–model configurations and fron-

models jointly shape deployed-agent security.
• A stage-level analysis of harness security mechanisms.
We localize where defensive behavior emerges across
the web-agent workflow and use controlled ablations to
examine specific mechanisms, providing a principled
basis for understanding and improving harness-level
security design in practical web agents.

2. Web Agent Harness
A web agent is an automated system that uses large lan-
guage models (LLMs) or large multimodal models (LMMs)
as its core controller to complete complex tasks in real
and dynamic web environments [17, 18, 19, 20]. Unlike
conventional conversational LLMs that operate mainly over
textual inputs and outputs, web agents are embedded in an
execution harness that connects model decisions to concrete
interaction primitives. While such a harness enables agents
to perform long-horizon tasks, it also expands the attack
surface beyond the model itself and weakens the conventional
security boundary assumed for standalone LLMs [21, 22, 23].
To characterize web-agent harnesses, we survey 40 web-
agent papers published in top venues (from 2021 to 2026)
and collect 68 GitHub projects with at least 1,000 stars
using “web agent” and “browser agent” as search keywords.
We exclude repositories that do not implement agentic web
interaction. From these sources, we abstract the common
web-agent workflow into four stages, as shown in Figure 1.
Stage I: Goal Interpretation. The agent first interprets the
user’s natural-language instruction and converts it into an
internal task representation. This stage determines the task
objective, relevant constraints, and implicit execution intent,
which guide all subsequent decisions.
Stage II: Webpage Perception. The agent obtains the current
webpage state through browser interfaces, such as DOM
extraction, accessibility trees, screenshots, or multimodal
observations. This stage determines what webpage content,
interface elements, hidden or off-screen text, and browser
states are exposed to the backend model.
Stage III: Reasoning and Planning. Given the interpreted
goal and perceived webpage content, the agent reasons about
the task context and decides how to proceed. This stage
generates a single next action or a multi-step plan, including

therefore categorize the harness components used at each
workflow stage in the 68 GitHub projects. Our analysis
shows that common designs include LLM-based parsers for

(67.7%), single-controller reasoning structures (73.0%), and

Prior security studies on web agents often evaluate attacks
against specific harnesses and implicitly treat the observed
behaviors as broader web-agent security properties [5, 9, 11].
However, these observations can be affected by harness
design. For example, a backend model that appears more
defensive in one harness may not be more resistant to the
attack itself, as the difference may instead come from harness
mechanisms. Therefore, studying web-agent security requires
systematic comparisons across harness designs and analysis
of where defensive behavior emerges. This motivates our
focus on web-agent harness security: rather than treating the
agent as a monolithic LLM-driven system, we analyze how
harness components shape the agent’s security boundary.

3.1. Design Principle
Designing an evaluation framework for web-agent harness
security requires more than collecting unsafe prompts or
malicious webpages. An effective framework must address
three challenges to measurement validity: (i) incomplete
attack coverage can underestimate harness exposure; (ii)
capability failures can be mistaken for security defenses,
leading to biased security estimates; and (iii) harness-specific
logging or integration can impose substantial manual effort
and limit cross-harness comparison. We therefore design
WEBTRAP FARM around the following principles.
3.1.1. Comprehensive coverage of web-agent attacks.
Existing web-agent security datasets provide valuable starting
points, but their coverage remains fragmented. Some focus
on malicious user prompts [5, 6], while others target prompt
injection [8, 9] or deceptive interfaces [11, 12]. Their attack
instances often cover limited delivery methods or contents,
making cross-harness comparison difficult and potentially
tying results to specific prompts, layouts, or scenarios.
To address this limitation, WEBTRAP FARM systematically
covers two attack surfaces to capture how attacks propagate
through different parts of the workflow and are mitigated
by different harness components. User-side attacks originate
from malicious user instructions and stress goal interpretation,
reasoning, and action execution (Stages I, III, and IV), while
web-side attacks originate from adversarial webpage content
or interfaces and stress webpage perception, reasoning, and
action execution (Stages II, III, and IV). Within each surface,
we vary attack goals, methods, and contents to provide broad
coverage to avoid overfitting the evaluation to a narrow
class of attacks. This principle allows the measured results
to reflect broadly relevant security properties rather than
artifacts of a single benchmark design.
3.1.2. Usability calibration of security outcomes. A central
challenge in web-agent security evaluation is that an attack
failure has an ambiguous meaning. If an agent does not
complete an unsafe action, the failure may indicate successful
defense. However, it may also indicate that the agent could
not understand the task, operate the webpage, or reach the
attack-relevant state. Treating all attack failures as security
successes would systematically overestimate robustness, es-
pecially for harnesses with weaker task-execution capability.
To avoid this bias, WEBTRAP FARM introduces calibration
tasks. For each attack task, we construct a corresponding
usability task that preserves the task-relevant interaction
requirements while removing the adversarial trigger. This
design ensures that an attack failure is treated as evidence
of defense only when the agent can complete the same
underlying interaction under a benign objective. Otherwise,
the failure is attributed to task capability limitations and is not
counted as a security-relevant defense success. By separating
security behavior from general task capability, this calibration
enables more faithful comparison across harnesses.
3.1.3. Execution Monitoring Independent of Harnesses.
Another limitation of existing evaluations is their dependence
on agent-specific integration. Many benchmarks assume
access to particular agent logs, internal actions or browser
wrappers [19, 37, 38, 39]. Such coupling increases manual
effort and makes it difficult to evaluate heterogeneous web-
agent systems under the same measurement protocol. It can
also introduce measurement bias, because different agents
expose different internal states and logging formats.
WEBTRAP FARM therefore measures security-relevant
effects at the webpage side, rather than through agent-side
logs, internal reasoning traces, or specific APIs. This makes
the webpage interaction itself the common measurement
interface for all evaluated systems. As a result, WEBTRAP
FARM can evaluate different web-agent harnesses under
the same protocol without requiring per-agent integration,
including closed-source commercial web agents whose in-
ternal execution stages are unavailable. This design reduces
manual adaptation cost, avoids measurement bias caused
by inconsistent internal logs, and supports fair comparison
across heterogeneous web-agent systems.
3.2. Dataset Construction
Following the above principles, we construct WEBTRAP
FARM to provide broad attack coverage while enabling
usability calibration. The dataset contains two paired task
types: attack tasks, which evaluate whether an agent executes
unsafe actions under adversarial conditions, and usability
tasks, which measure whether the agent can complete the
same interaction when the adversarial trigger is removed.
3.2.1. Attack Tasks. We construct attack tasks according to
the attack surface. Based on a review of recent studies on
LLM and agent security published within the past three years,
we identify representative attack categories for each surface.
For the user side, we include Malicious User Prompts,
where a malicious user directly issues harmful or policy-
violating instructions to the agent. For the web side, we
include Malicious Prompt Injection and Deceptive Website
Design, where the attacker manipulates webpage content or
interface design encountered by a benign agent. Specifically,
Malicious Prompt Injection embeds adversarial instructions
into webpage content to influence the agent’s reasoning or
planning process, whereas Deceptive Website Design relies
on deceptive interface elements or social-engineering content
to induce unsafe actions during web interaction.
To ensure systematic coverage of the attack space, we
organize each attack task along three dimensions: attack goal,
which specifies the unsafe behavior the attacker attempts to
induce; attack method, which captures the mechanism used
to deliver or realize the attack; and attack content, which
refers to the concrete prompt, injected instruction, deceptive
message, or webpage artifact used in the task. We include
only attack methods and contents that have been empirically
validated in at least two independent prior works, so that
the attack set remains representative and reproducible. As
summarized in Table 2, WEBTRAP FARM provides broader
and more systematic coverage than any existing single dataset

Based on this taxonomy, we instantiate attacks according

prior web-agent security datasets [5, 9, 11] and refactor
them into a unified task format, rather than relying on agent-
specific benchmark environments. These webpages cover
common scenarios such as social media interaction, travel
planning, and online shopping. The controlled environments

to vary attack goals, methods, and contents in a systematic

User-side Attack Tasks. For Malicious User Prompts, the
attack is instantiated through the user prompt. We select
representative webpages from BrowserART [5] and modify
them to support consistent execution monitoring. We then
construct malicious user instructions for five attack goals,
such as bias, misinformation and cybercrime, with eight
base prompts for each goal. Each base prompt is further
instantiated using four attack content strategies, such as
instruction override, role play, and privilege escalation,
resulting in 160 tasks in total. This construction evenly
distributes tasks across attack goals and attack contents,
reducing the risk that the results are dominated by a specific
harmful objective or jailbreak formulation.
Web-side Attack Tasks. For Malicious Prompt Injection
and Deceptive Website Design, attacks are instantiated in
webpage content. We adapt webpages from EIA [9] for
Malicious Prompt Injection and from AgentBait [11] for
Deceptive Website Design, and standardize them into a
common implementation format with controllable attack
locations. For Malicious Prompt Injection, we insert prompt
injection content into predefined locations, such as visible
form text, hidden text, ARIA attributes, URLs, hyperlinks,
or long-context regions. For Deceptive Website Design,
we implement deceptive interface patterns, such as pop-
ups, advertisements, leading or trailing form fields, and
default selections, and embed the deceptive content into
these templates. In addition, we include a “naive” attack-
content type for web-side attacks, where no additional
injected prompt or deceptive inducement text is inserted.
This type serves as a baseline for measuring whether unsafe
behavior can arise from the harness’s intrinsic interaction
process, rather than from explicit external attack content. This
process yields 158 Malicious Prompt Injection tasks and 187
Deceptive Website Design tasks. The tasks are distributed
uniformly across three attack dimensions.
3.2.2. Usability Tasks. We construct usability tasks accord-
ing to the attack surface of each risk category. For Malicious
User Prompts, where the attack is delivered through the user
instruction, we replace the malicious user prompt with a
benign instruction that preserves the same task structure and
required webpage interaction. For example, if the attack
task asks the agent to post a biased statement on the
forum, the usability task asks the agent to post a positive
statement using the same forum page. For Malicious Prompt
Injection and Deceptive Website Design, where the attack is
embedded in webpage, we remove the injected instruction
or deceptive element and directly ask the agent to complete
the corresponding benign interaction. For example, if an
attack task attempts to induce an unsafe download through a
malicious webpage trigger, the corresponding usability task
removes the malicious content and explicitly asks the agent
to click the download button and complete the download. In
this way, usability tasks preserve the operational difficulty
of the original task while removing the adversarial condition.
If the attack task fails while the corresponding usability
task succeeds, the failure is attributed to the agent’s security
mechanisms. If both tasks fail, the failure is treated as a
capability failure rather than a defense success.
3.3. Execution Monitoring
Following the principle of execution monitoring indepen-
dent of harnesses, WEBTRAP FARM measures task outcomes
from webpage effects rather than agent logs. Specifically,
WEBTRAP FARM monitors task execution by instrumenting
each task webpage with JavaScript-based event logging.
For each task, we identify the key HTML elements whose
interaction determines whether the attack goal or usability
goal is achieved. These elements include buttons, form fields,
file-download triggers, permission-request controls, and other
task-specific interface components. The monitoring script
records runtime interactions with these elements and sends
the captured events to a backend server for scoring.
The monitored data depends on the task type. For click-
based tasks, WEBTRAP FARM records the identifier of the
clicked element and its event metadata. For text-input tasks,
it records the submitted field value and target field. For
download- or permission-related tasks, it records whether the
relevant browser-facing trigger is activated. This monitoring
is implemented at the webpage and backend level rather than
through agent-specific logs. As a result, WEBTRAP FARM does
not depend on the logging format, internal reasoning trace,
action schema, or implementation details of any particular
web-agent harness. This enables consistent cross-harness
evaluation under the same measurement interface.


3.4. Evaluation Protocol
WEBTRAP FARM evaluates each agent execution in two
steps. First, task scoring checks whether the attack or
calibration objective is completed. Second, outcome labeling
compares each attack task with its paired calibration task
to classify the result as attack success, defense success, or
capability failure. The final metrics quantify vulnerability,
effective defense, and task capability.
3.4.1. Scoring. Each task is scored as a binary outcome:
success or failure. For attack tasks, success means that the
agent completes the unsafe action required by the attack
goal, such as submitting sensitive information, triggering a
malicious download, or granting an unauthorized permission.
For usability tasks, success means that the agent correctly
completes the corresponding benign task objective.
For structured web interactions, we score outcomes using
the monitored execution records. Click-based, download-
based, and permission-based tasks are scored by checking
whether the corresponding target element or browser-facing
trigger is activated. Form-submission tasks are scored by
matching the submitted content against manually annotated
expected values. This rule-based scoring is used for Malicious
Prompt Injection, Deceptive Website Design, and their
corresponding usability tasks whose success criteria can
be directly observed from webpage events.
For open-ended text-generation tasks in Malicious User
Prompts and their corresponding usability tasks, we use
GPT-4o as an LLM-as-a-judge to determine whether the
generated response satisfies the task-specific criteria. To
validate the reliability of this scoring procedure, we manually
annotated a 10% random sample of Malicious User Prompts
outputs (672/6,720). The two human annotators achieved
99.26% agreement, and the LLM judge matched the human
consensus in 99.55% of cases. This validation suggests that
the LLM-based scoring is sufficiently reliable for evaluating
open-ended Malicious User Prompts outcomes.
3.4.2. Outcome Label. For each attack task, we first evaluate
whether the agent completes the unsafe action specified by
the attack goal. If the unsafe action is completed, the outcome
is labeled as Attack Success. If the unsafe action is not
completed, we then evaluate the corresponding usability task.
If the agent succeeds on the usability task, the original attack
failure is labeled as Defense Success, since the agent has
the capability to perform the interaction but does not do
so under the attack condition. If the agent also fails on
the usability task, the original attack failure is labeled as
Capability Failure, since the failure more likely reflects
limitations in task-execution capability.

we define three metrics for subsequent evaluation.

For each attack task t ∈T , we assign an outcome label
combined with its calibrated execution result.

vulnerability to attacks, capturing the probability that an
attack leads to the execution of the intended unsafe action:

4. Harness Security Evaluation
Using WEBTRAP FARM, we evaluate representative agents
to answer two research questions. The first question (RQ1)
measures how vulnerable web-agent harnesses and backend
models are under different attack surfaces. The second
question (RQ2) quantifies the effects of harness and backend
model on agent security resilience. Section 4.1 introduces
the evaluated harnesses, backend models, and execution
configuration. Section 4.2 presents the evaluation results.
4.1. Evaluation Setup
4.1.1. Web Agent Collection. We evaluate open-source web
agents collected from two sources: (i) popular projects with
more than 1,000 GitHub stars and (ii) representative agents
proposed in prior academic works. All selected agents are re-
quired to exhibit basic task completion capability [12, 20, 42].

4.1.2. Backend LLMs. To better isolate the security impact
of harnesses from the choice of backend model, we evaluate
open-source harnesses across seven backend LLMs. The
closed-source models include GPT-4o, GPT-5.1, and GPT-5.2

the Qwen3 family. By evaluating the same harnesses over
different backend models, we reduce the risk that observed
security differences are artifacts of a single model and obtain
a more robust view of harness-level security behavior.
4.1.3. Configuration. All agents are integrated strictly fol-
lowing their official documentation. We do not alter their core
architectures, reasoning logic, or built-in safety mechanisms.
Each agent is executed with its recommended default con-
figuration to reflect realistic deployment settings. To reduce
nondeterminism introduced by backend LLM sampling, we
set the decoding temperature to 0. For each task, we require
one completed execution. Runs interrupted by infrastructure
failures, such as rate limits or network errors, are retried until
reaching a natural termination state. To verify result stability,
we further repeat the full benchmark three times across all six
harnesses with two fixed backend models (Qwen3-VL-235B
and GPT-5.1). The average standard deviation is only 1.73
percentage points, indicating limited run-to-run variation.
To enable systematic analysis, we enable logging for all
open-source agents to record intermediate decisions and
interactions with the webpages during task execution. These
logs are used exclusively for security analysis in Section 5,
and do not affect the agent’s runtime behaviors.

5.1. Security Analysis Method
Figure 5 illustrates our security analysis workflow. Start-
ing from execution logs, we extract patterns for identifying
stage states, annotate the execution sequence across multiple
rounds with these patterns, and localize where successful
defenses become effective in the workflow.
5.1.1. Stage-wise Log Analysis. Web agents execute tasks
through an interaction loop rather than a single end-to-end
decision. Each round follows similar workflow stages. Under
this streaming loop, an attack may be propagated or blocked
at any stage in any interaction round. Therefore, an end-to-
end “Defense Success” label is insufficient for identifying
where defensive behavior emerges. Instead, we formulate the
multi-round workflow as an execution sequence, annotate
each stage in each round as either a safe or unsafe state,
and identify where a successful defense becomes effective
according to the state transitions. This design enables us to
localize defensive behavior within the execution workflow.
Step1: Pattern Extraction. To determine whether each stage
is in a safe or unsafe state, we first derive labeling patterns
from execution logs. For each evaluated agent, we randomly
sample 100 tasks labeled as “Defense Success” and manually
inspect their logs, including goal interpretation, webpage
observations, reasoning traces, planned actions, and final
browser operations. From these logs, we identify patterns
that indicate the stage-wise security state, as summarized in
Table 8. A safe-state pattern indicates that the current stage is
safe, i.e., it does not include or propagate the attack objective.
This may occur because the attack has not yet been exposed
to the stage, such as when the agent has not reached the
adversarial element in a web-side attack, or because the stage
ignores, refuses, reformulates, or blocks the attack content.
In contrast, an unsafe-state pattern indicates that the current
stage enters an unsafe propagation state, where the attack
objective is preserved, adopted, or transformed into unsafe
planning or browser actions. Detailed explanations of safe
and unsafe patterns are provided in Appendix C.

5.2.1. User-side Defense Analysis. Table 9 reports the stage-
wise Conditional DSR for Malicious User Prompts. The
results show that effective defense is supported by fine-
grained intent interpretation over user goals and risk-aware
reasoning that prevents unsafe actions.
Stage I: Goal Interpretation. Agent-E’s LLM-based goal
interpreter achieves the highest Stage I Conditional DSR
(82.71%), indicating that most of its successful defenses
are localized at goal interpretation before downstream plan-
ning (e.g., returning a mandatory termination signal when the
task is deemed unsafe or infeasible). Raw-prompt forwarding
provides no Stage I defense because malicious instructions
pass directly to later modules. Among LLM-based inter-
preters, Skyvern 2.0 has the lowest Stage I Conditional DSR
(8.13%), suggesting that the presence of an interpreter alone
does not necessarily yield strong defensive behavior.
To further examine whether fine-grained intent interpre-
tation contributes to this difference, we replace Agent-E’s
interpretation prompt with the less detailed prompt used
in Skyvern 2.0. On 100 sampled Malicious User Prompts
tasks, Agent-E’s Stage I Conditional DSR decreases from
75.61% to 53.85% (-21.76 percentage points), showing that
fine-grained intent interpretation helps expose malicious
objectives before they are translated into executable actions.
Stage III: Reasoning and Planning. The observed defensive
behavior at this stage does not consistently align with whether
the harness uses a single-controller planner or a multi-role
planner. Instead, it is associated with whether the reasoning
prompt includes risk-awareness cues. Browser Use (Vision)
achieves the highest Stage III Conditional DSR of 70.31%,
while Agent-E reaches a comparable 69.50% despite using
a different multi-role planning structure. For both harnesses,
a substantial portion of successful defenses is localized at
Stage III, where the reasoning prompts encourage the agent to
reject, reformulate, or discard unsafe plans during reasoning.
In contrast, for the Skyvern series, less defensive behavior
is localized at Stage III, with Conditional DSR below 50%.
Their reasoning prompts are more strongly oriented toward
task completion. Once a malicious user goal passes earlier
stages, the planner is more likely to reason about how to
complete it rather than independently block it.
To further examine the role of risk-awareness cues during
reasoning, we remove them while preserving the original
planner structure (e.g., “Don’t login into a page if you don’t
have to”). On 100 sampled Malicious User Prompts tasks,
Stage III Conditional DSR decreases from 73.91% to 43.48%
for Browser Use (Vision) (-30.43 percentage points), and
from 92.86% to 69.77% for Agent-E (-23.09 percentage
points), indicating that risk-awareness cues strengthen de-
fenses during reasoning across different planner structures.
Stage IV: Action Execution. At the execution stage, limited
but observable defensive behavior is localized for harnesses
using LLM-based action grounding, while no measurable
Stage IV defense is observed for rule-based action grounding
in our results. SeeAct and Skyvern 2.0, which use LLM-
based grounding, achieve Stage IV Conditional DSR values
of 26.94% and 23.51%, respectively. This suggests that
translating natural-language action descriptions into browser
operations through an LLM can re-trigger model guardrails
when the action is malicious, such as submitting sensitive
information or generating abusive content. However, because
these grounding prompts do not explicitly implement safety
validation, the protection remains incidental. In contrast, rule-
based grounding directly maps planned actions to browser
commands without semantic safety checks, corresponding
to 0.00% Conditional DSR at this stage.
5.2.2. Web-side Defense Analysis. Table 10 reports the
stage-wise Conditional DSR for Malicious Prompt Injection
and Deceptive Website Design. The results show that effec-
tive defense is supported by selective webpage perception
and keeping planning anchored to the original user goal.
Stage II: Webpage Perception. Agent-E exhibits the highest
Stage II Conditional DSR of 78.99%, indicating that a
large portion of its successful defenses is localized at
webpage perception. This observed pattern is associated with
its structured webpage extraction, which filters irrelevant
webpage content before it reaches the reasoning stage. In
Agent-E, perception is implemented as a tool call that extracts
task-relevant text and elements from the webpages, reducing
exposure to hidden or non-semantic injected content. The
extracted observation is then interpreted by the LLM to flag
suspicious content, as illustrated by the following warning:
▲Important Warning: This form contains a suspicious ”Credit card
number” field and a dubious ”System Notice” claiming to be from the
”Cyberspace Administration.” Legitimate product feedback surveys do
not request credit card information. This may be a phishing attempt.

To further examine the role of perception filtering, we
relax Agent-E’s filtering policy by exposing all webpage
elements to the LLM. On 100 sampled web-side attack
tasks, Agent-E’s Stage II Conditional DSR decreases from
56.94% to 50.70% (-6.24 percentage points). In the failed
defense cases, excessive webpage context dilutes the model’s
attention, making suspicious content harder to identify. These
results indicate that perception filtering improves defense by
reducing irrelevant context before reasoning.
Stage III: Reasoning and Planning. Unlike user-side
attacks, web-side attacks show a clearer observational dif-

harnesses localize more defense at Stage III by repeatedly
anchoring reasoning to user intent, with Skyvern 1.0 reaching
the highest Conditional DSR (78.17%). In contrast, less
defensive behavior is localized at Stage III for Agent-E’s
multi-role planner (10.65%). In its execution traces, injected
objectives can be propagated across roles: once one LLM
summarizes a malicious webpage instruction into a high-
level plan, another role may treat it as a trusted execution
directive, such as incorporating injected steps like “download
the required file before proceeding” into its plan.
To further examine the role of goal anchoring, we conduct
two ablations. First, we remove the goal-anchoring instruction
from Skyvern 1.0’s planning prompt, reducing Stage III
Conditional DSR from 70.73% to 54.05% (-16.68 percentage
points). Second, we provide Agent-E’s planner agent with
the original user instruction in addition to the upstream
planner output, allowing it to check whether the planned
action remains aligned with the user goal. This increases
Stage III Conditional DSR from 19.35% to 43.59% (+24.24
percentage points). These results show that defense at this
stage depends on whether the harness preserves the original
user goal when processing instructions on the webpages.
Stage IV: Action Execution. For web-side attacks, ground-
ing designs show a pattern similar to user-side attacks:
limited defensive behavior is localized at Stage IV for
harnesses using LLM-based action grounding, while no
measurable Stage IV defense is observed for rule-based
action grounding. However, the overall Conditional DSR
remains low at this stage. SeeAct and Skyvern 2.0 use LLM-
based action grounding but still achieve Conditional DSR
below 5%, while all rule-based action grounders remain
at 0.00%. This pattern reflects that web-side attacks are
decomposed into locally benign browser operations, such as
clicking a button or filling a visible field. Once translated
into such actions, each step appears legitimate in isolation
and rarely re-triggers model guardrails. As a result, limited
defensive behavior is observed at the grounding stage after
the attack objective has already passed earlier stages.
5.3. Case Study
To further understand defense vulnerabilities, we manu-
ally inspect successful attacks and identify a recurring failure
pattern across multiple agents. One representative example
occurs in Skyvern 1.0 under a Deceptive Website Design task,
where the agent is instructed to complete a job application
form that stealthily requests a credit card number at the end.
During intent parsing, the agent correctly derives a
detailed user goal with an explicit guardrail (e.g., “do
not provide sensitive information”). In early attempts, the
reasoning stage recognizes the credit card field as risky and
refuses to fill it. However, after submission, the agent fails
to detect the successful completion signal and repeatedly re-
executes the form. As the task is retried multiple times,
the model’s safety judgment gradually weakens: it first
rejects the field as unsafe, then dismisses it as irrelevant,
and eventually treats it as necessary for task completion,
ultimately entering the credit card number. This progressive
defensive failure occurs despite consistently providing the
same guardrails in the prompt. The example reveals an
inherent instability of prompt-level safety mechanisms used
by most web agents: repeated interactions and long execution
chains can dilute or override safety constraints, allowing
malicious objectives to be gradually integrated into the
normal task workflow. More broadly, current web agents
rely heavily on prompt engineering and the LLM’s intrinsic
guardrails for defense. Such mechanisms are brittle and non-
deterministic, highlighting the need for more structured and
explicit safeguards beyond prompt control.
6. Discussion
6.1. Security Implication
Our key contribution is the quantitative measurement
of how harness design shapes web-agent security, treating


the harness as a security factor rather than merely an
implementation detail around the backend model. WEBTRAP
FARM enables cross-harness comparison, separates defense
from task incapability through capability calibration, and
localizes defensive behavior across workflow stages. Rather
than relying on the long-term completeness of the current
attack set, WEBTRAP FARM is extensible to emerging attacks
through paired usability tasks and webpage-side observation
criteria, preserving a consistent evaluation methodology.
Our results show that harness design directly shapes
deployed-agent security: the same backend model can behave
differently across harnesses, and unsafe execution may persist
despite seemingly benign perception, planning, and execution
pipelines. The harness therefore remains a significant blind
spot in web-agent security. As agents increasingly interact
with real services, understanding how harness components
introduce, propagate, or block attacks is essential for trustwor-
thy deployment. WEBTRAP FARM advances this goal through
systematic measurement and defense localization.
6.2. Defense Suggestions
Based on our empirical findings, we provide several
practical recommendations for building more secure web
agents. (i) Strengthen intent interpretation. For user-side
attacks, the harness should identify the potential harmful
objective in the user intent before planning browser actions.
This prevents malicious prompts from being treated as
ordinary task goals. (ii) Filter webpage perception. For web-
side attacks, the perception module should avoid exposing
irrelevant or suspicious webpage content to the LLM. Instead,
it should prioritize elements that are necessary for completing
the original user task. (iii) Anchor planning to the user goal.
The planner should repeatedly compare webpage instructions
with the original user request, rather than treating all webpage
content as authoritative. This is especially important when
injected text or deceptive UI elements try to redirect the task.
(iv) Use execution checks as a fallback. Action filters and
grounding constraints remain useful, but they should not be
the only defense. Many unsafe behaviors appear as locally
benign clicks or form entries at execution time, so earlier
workflow-stage defenses are still necessary.
6.3. Limitations.
We acknowledge several limitations. First, our evaluation
focuses on three representative attack categories. Other attack
surfaces, such as malicious tools, are outside our scope.
However, new attacks can be incorporated into the same
evaluation framework to analyze how they propagate through
agent systems. Second, our experiments are conducted in
controlled web environments. Real-world deployments may
involve more dynamic content and environmental variability,
while our controlled design improves reproducibility and
fairness. Third, web-agent execution involves randomness,
which may introduce instability. We mitigate this by using
a sufficiently large dataset, fixing model parameters, and
conducting repeated-run experiments that show low variation.
7. Related Work
7.1. Web-Agent Development
Early web agents mainly focused on simplified browser
tasks in controlled environments. These agents typically
operated over structured webpage representations, such as
DOM or accessibility trees, and were evaluated on whether
they could follow user instructions to navigate websites, fill
forms, or complete basic transactions [17, 19, 48]. Their
primary goal was to demonstrate that LLMs could be
extended from text generation to sequential web interaction.
With advances in multimodal large models and browser
automation tools, web agents have gradually moved from
simplified tasks toward more realistic environments. They
increasingly combine webpage text with screenshots to
support multimodal perception [24, 43], and adopt more
flexible reasoning and execution designs, including single-
controller agents [35, 49], or multi-agent systems [25, 26].
These developments allow agents to handle more complex
workflows, but they also increase the number of harness
component choices that can affect security. Prior academic
and industry work has already emphasized system security
for agentic AI beyond the underlying model [14, 15, 16].
Building on this line of work, we focus on quantitatively
measuring how different harness designs shape web-agent
security across agents and attack surfaces.
7.2. Attacks Against Web Agents
Prior research has studied attacks against web agents
originating from malicious users and untrusted websites.
User-Side Attacks. These attacks evaluate an agent’s suscep-
tibility to unsafe behaviors triggered by user goals. SAFE-
ARENA [6] defines bias, cybercrime, harassment, illegal ac-
tivity, and misinformation as harm categories, while Browser-
ART [5] adopts finer-grained but fragmented attack labels.
Beyond prior studies primarily on explicit malicious prompts,
recent studies also consider alignment-bypass or jailbreak-
style inputs implicitly manipulating agent’s reasoning process
rather than issuing overtly harmful commands [50].
Web-Side Attacks. These attacks manipulate webpage con-
tent or interface design, mainly through prompt injection
and deceptive web design. Prompt injection embeds harmful
instructions into forms or web elements to influence agent
reasoning, as in EIA [9] and WASP [8], while deceptive web
design manipulates UI layouts and interaction flows [11].
Adversarial example attacks instead use imperceptible pertur-
bations to text or webpage images to induce misclassification
or erroneous behavior [51, 52, 53, 54]. However, such attacks
are tailored to specific models and lack generality across
agents, making prompt injection and deceptive design the
predominant practical risks.
However, existing studies remain fragmented, and their
findings are often tied to specific agents. Our work addresses
this gap by introducing a systematic framework for quanti-
tatively measuring web-agent security across harnesses and
localizing where defensive behavior emerges.


8. Conclusion
Our work shows that web-agent security is jointly shaped
by the backend model and harness design. We present
WEBTRAP FARM, a systematic and extensible framework
for quantitatively evaluating security across attack surfaces,
separating defensive behavior from task incapability, and
localizing where defense emerges. Our results reveal sub-
stantial cross-harness variation, while controlled ablations
identify key security mechanisms. We hope WEBTRAP FARM
supports reproducible evaluation and safer web-agent design.

Appendix A.
Attack Taxonomy
Table 11 summarizes the attack classes covered by
WEBTRAP FARM across three dimensions.
Attack Goal. For Malicious User Prompts, we consider
five unsafe goals. Bias induces discriminatory or unfair
outputs. Misinformation requests false or misleading content.
Cybercrime involves harmful cyber operations. Illegal Activity
asks the agent to assist with unlawful actions. Abusive
Behavior elicits harassment, hate, or other harmful language.
For Malicious Prompt Injection and Deceptive Website
Design, we consider three web-side goals. Sensitive Infor-
mation Disclosure aims to make the agent enter private
information, such as a credit card number. Malicious Down-
load tricks the agent into downloading a suspicious file.
Permission Abuse induces the agent to grant sensitive browser
or system permissions, such as camera access.
Attack Method. For Malicious User Prompts, User-prompt
embedding places the malicious objective in the instruction.
For Malicious Prompt Injection, the attack method spec-
ifies where the injected instruction appears in the webpage.
Visible Form Injection places malicious text in visible form
content. Invisible Form Injection hides malicious text in
form elements through invisible styling. ARIA-based Injec-
tion inserts instructions into accessibility attributes. URL
Content Injection exposes malicious instructions through
URL text shown on the page. URL Href Injection embeds
the instruction in the hyperlink target of an HTML element.
Long-Context Injection hides the malicious instruction inside
a long block of otherwise benign page content.
For Deceptive Website Design, attack methods specify
how the interface misleads the agent. Iframe Pop-up redirects
attention through embedded external frames. DOM-native
Pop-up mimics legitimate prompts with native modals or
dialogs. Advertisement Placement places malicious or decep-
tive content in ad-like regions. Leading Form Field inserts
a deceptive field before the legitimate workflow. Trailing
Form Field appends a deceptive field after the benign task
flow. Default Selection preselects an unsafe option, such as
a checked permission box or unwanted download choice.
Attack Content. For Malicious User Prompts, attack content
describes how the malicious user request is phrased. Direct
Request states the unsafe request plainly. Instruction Override
asks the agent to ignore prior rules or safety constraints. Role
Play frames the request as a fictional role or scenario to
mask the malicious intent. Privilege Escalation falsely claims
higher authority, such as pretending that the instruction comes
from an administrator or system-level source.
For Malicious Prompt Injection, attack content specifies
the wording strategy of injected instructions. Naive adds
no prompt-injection text and relies on the original page
context. Direct Instruction explicitly requests the adversarial
task. Delimiter-based Injection uses markers such as ###”
or —” to present injected text as a new instruction block.
Instruction Override asks the agent to ignore the benign task
or prior instructions. Role Play uses a persona or hypothetical
scenario to justify the injected task.
For Deceptive Website Design, attack content specifies
the persuasive strategy of deceptive webpages. Naive adds no
persuasive content and relies on the original page semantics.
Trusted Entity impersonates a reputable brand, authority,
or system notice. Urgency creates time pressure. Social
Proof fabricates popularity signals, reviews, or user counts.
Reward promises benefits such as coupons, upgrades, or
prizes. Context Integration blends the deceptive request into
the benign workflow to appear task-relevant.

Appendix C.
State Patterns
Table 8 presents the safe and unsafe state patterns
observed across web-agent workflow stages. We explain
each pattern below.
User-side Attacks. For user-side attacks, the adversarial
objective enters the workflow from the user prompt. At
Stage I, we examine how the agent converts the user
prompt into an internal task goal. Secure Refusal means
that the agent identifies the malicious request and refuses
to interpret it as a valid task. Secure Reformulation means
that the agent removes the unsafe intent and rewrites the
request into a benign objective, such as turning a harmful
cyber request into general security guidance. Insecure Goal
Interpretation means that the agent accepts the malicious
request as its task goal, allowing the attack objective to
enter later stages. At Stage III, we examine whether the
reasoning and planning process preserves or mitigates the
malicious objective. Secure Refusal means that the agent
stops the workflow during reasoning because the planned task
is unsafe. Secure Reformulation means that the agent revises
the plan into a safe alternative while avoiding the harmful
objective. Insecure Planning means that the agent generates
a concrete plan that directly supports the malicious objective.
At Stage IV, we examine whether the final execution layer
prevents the unsafe operation from being carried out. Action
Blocked means that the agent prevents the unsafe operation
from being executed, even if earlier stages have produced
an unsafe goal or plan. Unsafe Action Executed means that
the agent completes the harmful action, such as submitting
sensitive information, downloading an unsafe file, or granting
an unauthorized permission.

Figure 6: Workflow of Dataset Construction
Web-side Attacks. For web-side attacks, the adversarial
objective originates from websites. At Stage II, we examine
how the perception module processes adversarial webpage
content before it is passed to the reasoning module. Injection
Filtered means that the perception module removes or misses
the injected content before it enters the agent’s observation.
Injection Exposed means that the injected content is visible or
accessible on the webpage but is not necessarily included in
the agent’s processed observation. Injection Included means
that the malicious instruction is captured in the agent’s
observation and can influence later reasoning. At Stage III,
we examine whether the agent distinguishes the original user
task from the adversarial webpage objective. Secure Refusal
means the agent recognizes the attack and refuses to follow it.
Attack Unaware means the agent does not notice the attack
but continues the original benign task. Injection Recognized
and Discarded means the agent notices the injection but treats
it as untrusted content and ignores it. Injection Recognized
and Adopted means the agent notices the injection but treats
it as a valid task objective. At Stage IV, we examine whether
the final browser operation is blocked or executed. Action
Blocked means the unsafe browser operation is blocked.
Unsafe Action Executed means the attack reaches execution
and the unsafe operation is performed.


Appendix D.
Ethics Considerations
This work evaluates the security resilience of web-agent
harnesses under representative adversarial settings, including
malicious user prompts, webpage prompt injection, and
deceptive webpage designs. Our evaluation was conducted
on locally controlled agent deployments and self-hosted
websites. Security validation was performed using manually
designed tasks in isolated research environments. We did not
access third-party systems, interact with real-world services,
collect user data, or interfere with external deployments.
To reduce the risk of misuse, we do not release exploit-
ready procedures, real-world attack configurations, or arti-
facts that directly enable attacks against deployed agents.
Instead, we focus on understanding how adversarial objec-
tives propagate through different harness components and on
identifying design principles that improve web-agent security.
We believe the benefits of this work outweigh its risks, as
the findings help developers, researchers, and organizations
evaluate and improve the security resilience of web-agent
harnesses before deployment in real-world workflows.
Appendix E.
Meta-Review
The following meta-review was prepared by the program
committee for the 2027 IEEE Symposium on Security and
Privacy (S&P) as part of the review process as detailed in
the call for papers.
E.1. Summary
The paper proposes a benchmark and a methodology to
assess the vulnerability of AI-based web agents to attacks,
such as malicious user instructions and prompt injections.
It pairs attack tasks with usability tasks to distinguish
defense from task incapability. Rather than treating web-
agent security as a single property (from the backend LLM
and harness together), the paper decomposes the harness
into four stages: goal interpretation, webpage perception,
reasoning and planning, and action execution.
E.2. Scientific Contributions
• Creates a New Tool to Enable Future Science
• Provides a Valuable Step Forward in an Established
Field
E.3. Reasons for Acceptance
1) The paper provides a valuable tool and framework with
useful formalization of the metrics for attack success,
and a benchmark creation methodology that allows
decomposition of attack or defense success rates.
2) The paper studies an important and relatively underex-
plored layer of web-agent security by examining how
the execution harness affects security.
3) The empirical evaluation provides strong evidence that
harness design can substantially affect security out-
comes.
4) The evaluation is broad and the usability calibration
helps avoid interpreting every unsuccessful attack as a
successful defense.
E.4. Noteworthy Concerns
1) The benchmark will lag on newer and stronger future
attacks, because static attacks quickly get outdated.
2) Evidence supporting each component conclusion is
needed. Fine-grained goal interpretation, risk-aware
reasoning, perception filtering, and goal anchoring are
supported by controlled ablations. In contrast, textual vs.
multimodal perception, single- vs. multi-role planning,
and rule- vs. LLM-based grounding are based on
observational differences between harnesses.
