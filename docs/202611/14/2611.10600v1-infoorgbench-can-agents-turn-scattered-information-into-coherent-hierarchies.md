## 摘要
当智能体将记录组织到文件夹中时，它们可能正确地将设计提案的摘录分组，却把该提案放在错误的所属组下。现有智能体基准并未直接衡量此类更高层次的错误。我们提出 InfoOrgBench，一个包含 150 项任务的基准，其中智能体将来自会议纪要、问题讨论串和设计提案的零散记录组织成层级结构。完整性检查验证每条记录均被保留，结构得分则在每一层级衡量与源层级结构的一致性，且不受文件夹名称和顺序影响。我们评估了 45 个系统，这些系统由九种模型与五种智能体运行框架两两组合而成。最佳系统得分为 83.2（满分 100），但没有系统在会议纪要或问题讨论串上超过 78。模型选择对得分的影响远大于运行框架选择：模型均值跨度约 27 分，而每种运行框架的平均效应低于 1 分。更重要的是，在三个领域中，父级关系的错误率均高于叶级关系。在设计提案中，按层级分析的所有输出中近一半恰好犯有此类错误。这些结果表明，评估信息组织需要将更高层级关系与记录保留和局部归类分开衡量。

## Abstract
When agents organize records into folders, they may correctly group the excerpts of a design proposal yet place the proposal under the wrong owning group. Existing agent benchmarks do not directly measure such higher-level errors. We introduce InfoOrgBench, a benchmark of 150 tasks in which agents organize scattered records from meeting recaps, issue threads and design proposals into hierarchies. Integrity checks verify that every record is preserved, and a Structure Score measures agreement with the source hierarchy at every level, independent of folder names and order. We evaluate 45 systems that pair nine models with five agent harnesses. The best system scores 83.2 out of 100, but no system exceeds 78 on meeting recaps or issue threads. Model choice affects scores far more than harness choice: model means span about 27 points, whereas the average effect of each harness is below one point. More importantly, parent-level relations have higher error rates than leaf-level relations in all three domains. In design proposals, nearly half of the outputs analyzed by level make exactly this kind of error. These results show that evaluating information organization requires measuring higher-level relations separately from record preservation and local grouping.

# InfoOrgBench 论文结构化总结

## 1. 核心问题与研究动机

- **背景**：智能体越来越多地替人收集、整理会议纪要、issue 讨论、设计文档等记录。把相关条目放进同一文件夹只是第一步，每个组还必须挂在正确的父级之下，因为人们依赖文件夹层级来检索信息、规划项目分解。
- **问题**：这两个要求可能脱节。智能体可以把某份设计提案的所有摘录正确聚成一个文件夹，却把该提案挂到错误的所属组（如错误的 SIG）下。此类**高层级（父级）组织错误**在现有基准中无法被直接测量：
  - 清单式完整性检查只验证记录是否保留，会把上述输出判为“完整”；
  - 二元精确匹配则把“局部全对、父级挂错”与“整个层级被打乱”判为同等失败。
- **含义**：评估信息组织能力，必须把**记录保留、局部分组、高层关系**三者分开、分级衡量。论文据此提出 InfoOrgBench。

## 2. 方法论

### 2.1 核心思想
- 构造“把散落记录整理成层级”的任务：智能体看到**不透明 ID 的记录文件 + 组织准则**，参考层级由评估器隐藏持有；智能体通过 harness 工具读取、搜索、移动记录，**最终磁盘状态**（独立捕获）即评分对象。
- 参考层级由公开来源中**既有的层级关系确定性重建**（非人工标注），因此可复现、无需 LLM 参与评分。

### 2.2 任务家族（三个）
- **Recap**：AMI 会议摘要句子 → 按“会议 / 摘要章节 / 句子”组织。
- **Thread**：Jira 子任务描述与评论 → 按“父 issue / 子任务 / 记录”组织。
- **Design**：Kubernetes Enhancement Proposal 摘录 → 按“所属 SIG / 提案 / 摘录”组织（摘录中被剔除直接点名所属组或提案的内容，迫使模型从内容推断）。

### 2.3 评估指标
- **完整性/有效性**：每条记录恰好出现一次、字节不变、层级合法；无效输出记 0 分。
- **结构一致性**：用 **rooted triples** 比较输出树与参考树，只依赖记录身份，**忽略文件夹名称与兄弟顺序**。
  - 每个三元组按其**在参考中分离的层级**归为父级或叶级；
  - 每层分别算 recall（参考能区分的三元组中被正确复现的比例）与 precision（输出区分的三元组中与参考一致的比例）；
  - **层级均衡 F1（F₁^bal）**：先对各层 recall、precision 做宏平均，再取调和平均，防止数量占优的父级三元组主导得分；扁平输出 F₁^bal = 0。
- **文件夹经济性惩罚**：
  - E(O,R) = 1 − λ·max{0, u(O) − u(R)} / n(O)，其中 u 为单子文件夹数、n 为输出文件夹数、λ = 0.2，用于惩罚多余的单子文件夹。
- **Structure Score**：S(O,R) = F₁^bal(O,R) × E(O,R)，统一缩放到 0–100；另报告 pooled Triplet F1 与经济性惩罚 100(1−E)。
- **补充诊断**：clade F1（完整组重合度）与 exact recovery（是否精确复现参考树）。

### 2.4 系统矩阵
- 9 个模型（Claude Haiku 4.5 / 5.5、Claude Sonnet 5.5、GPT-5.6 Luna/Terra、GPT-6 Luna、GPT-6.1 Sol、Grok 4.7、MAI-Code-1.1-Flash）× 5 个 harness（自建 ReAct-FC、Pi、Deep Agents、DeepSeek Harness、Codex CLI）= **45 个系统**。

## 3. 实验设计

- **数据规模**：150 个任务，每家族 50 个；每任务 36–60 条记录（Recap 2,436、Thread 2,421、Design 1,800 条记录出现次数）。Design 每个包固定 4 个 owner × 3 个提案 × 3 条摘录 = 36 条。
- **Benchmark 特性**（表 1 对比）：需要文件系统操作、无需 VM/容器、输出为多条目分组、参考层级先于基准存在、**评估全程不调用 LLM**——这几点是相对 WebArena、OSWorld、SWE-bench、Workspace-Bench、HSCodeComp、TExEval-2 的差异点。
- **对比方法**：
  - 45 个模型–harness 系统两两组合，全部在 150 任务上各跑 1 个 episode；
  - **纯文本基线**：TF-IDF + 平均连接层次聚类，含“全部平铺”“固定距离切分”“随机形状”“轮廓系数选切分”四种；
  - **重复性实验**：GPT-5.6 Terra + Codex 三次相同 medium 设置 + 一次 high 推理努力；
  - **错误分层分析**（25/21/25 个有分层数据的系统）、任务属性相关性分析（31 项特征检验，Holm 校正）、token 使用分析、clade/精确复现诊断。

## 4. 资源与算力

- 论文**未报告 GPU 型号、数量或训练时长**，因为这是纯推理评估基准，不涉及模型训练。
- 仅报告了推理开销：GPT-5.6 Terra + DSH 在 150 个任务上共 **924 次 provider 调用、859 万 tokens**；附录 L 给出各模型每任务 token 中位数（如 Sol 在 Thread 上约 97.9 万 tokens/任务，Sonnet 5.5 约 18.5 万）。
- 明确声明**不报告货币成本**，且不同 harness 的 token 统计口径不同（如缓存输入），跨 harness 的 token 对比仅供参考。

## 5. 实验数量与充分性

- **规模**：45 系统 × 150 任务 ≈ 6,750 次 episode；外加 4 组文本基线、1 个系统的 4 次重复运行、分层错误统计、clade F1 诊断、token 分析。
- **充分性亮点**：
  - 45 系统矩阵足以分离“模型效应”与“harness 效应”；
  - 有重复运行来标定噪声水平；
  - 用固定规则（第 10 百分位任务）挑选案例，避免挑样例；
  - 用发布版 scorer 重跑 17 个系统的输出，能复现全部已发表的任务分数。
- **不足与偏差风险**：
  - **每个系统每任务只跑一次**（仅 1 个系统做了 3 次重复）；实测单任务两次运行平均差 5.9 分，约 1 分的 harness 差异与运行噪声同量级，因此 harness 结论不够稳健；
  - 任务之间存在**来源重叠**（Thread 全部复用同 3 个父 issue；Design 600 个提案槽位来自 294 个唯一提案），**无 held-out、来源不相交的划分**，任务数不等于独立样本量；
  - 仅英文、仅 3 个公开来源，跨领域/语言的可迁移性未知；
  - 参考层级唯一，“其他同样合理的组织方式”未被评估。

## 6. 主要结论与发现

- **整体分数**：最佳系统 GPT-6.1 Sol + DSH 得 **83.2**，最差 52.5。按家族，最高分别为 Recap 77.8、Thread 77.9、Design 95.8——**没有任何系统在 Recap 或 Thread 上超过 78**。
- **模型 ≫ harness**：模型均值跨度约 **27.2 分**（Sol 82.3 → Haiku 4.5 55.1），而每个 harness 的平均效应在 **−0.7 到 +0.6 分**之间；9 个模型中有 7 个在不同 harness 间差异 ≤ 2.3 分。
- **父级错误率普遍高于叶级**（三个家族一致）：
  - Recap：父级错误 63% vs 叶级 32%，且以 **conflicting** 为主（35%）——智能体按“主题/项目阶段”而非“来源会议”分组，54% 的输出文件夹混入多个会议的记录；
  - Thread：父级 54% vs 叶级 13%，以 **unresolved** 为主——**一半输出完全缺失父 issue 层**，把每个子任务做成顶层文件夹；
  - Design：父级 61% vs 叶级 1%——96% 的 KEP 组被正确恢复，但近半数输出把完整提案挂到错误的 SIG 下（1,250 个输出中 596 个只有 SIG 级错误）。
- **测试时算力收益有限**：提高推理努力使均值 −1.0 分（95% CI [−3.0, +0.7]）；三次运行做共识/投票仅 −0.2 / +0.5 分而 token 成本 ×3；用参考挑最佳运行的上界也只有 +4.5 分。
- **关系一致 ≠ 完整组恢复**：clade F1 远低于 Structure Score（Sol 在 Recap 35.1 / Thread 36.1），Sol 在 50 个 Recap 或 Thread 任务中最多只有 1–2 个精确复现参考层级。
- **任务难度与证据可分性相关**：Recap 分数与会议词汇可分性 ρ=0.48，Thread 与子任务可分性 ρ=0.67（Holm 校正后显著）；Thread 中低信息量记录（42 个任务至少含 1 条）与低分相关。

## 7. 优点

- **问题切分清晰**：把“记录保留 / 局部分组 / 高层关系”显式拆成三个可分别测量的量，直击现有基准的盲区。
- **指标设计讲究**：triple 比较忽略命名与顺序，层级均衡避免父级三元组数量优势，经济性惩罚抑制“空壳文件夹”，并附 clade F1 / 精确复现作为补充诊断。
- **参考确定性可复现**：参考树由源数据路径确定，非人工标注；重建 1 个 Recap 与 1 个 Design 任务能字节级复现 packet 与 reference。
- **评估无 LLM 依赖**，成本低、可审计；代码开源。
- **系统矩阵大且分析细**：45 系统 + 分层错误分解 + 重复运行噪声标定 + 任务属性相关性，结论有层次。
- **诚实报告负面结果与局限**：明确写出算力无增益、任务不独立、单次运行、参考≠人类可用性等。

## 8. 不足与局限

- **统计独立性弱**：150 个任务高度共享来源，无 held-out 划分；Thread 仅 3 个父 issue；Design 结构完全固定（4×3×3），形状单一，可能低估真实场景多样性。
- **运行次数不足**：每系统每任务仅 1 次；仅 1 个系统做了重复实验，导致约 1 分级别的系统/harness 差异无法与运行方差区分。
- **效度边界**：分数衡量“与源层级的一致度”，而非“对人类是否有用”；作者自己指出这需要单独的用户研究。
- **数据泄漏风险**：来源公开，部分记录可能已出现在预训练数据中，论文未测量该影响。
- **任务形状受限**：参考固定为两层（父级 + 叶级）结构；附录 D.3 指出输出在参考组内进一步细分仍可拿满分，说明指标对“过细划分”不敏感（靠 clade 诊断弥补）。
- **覆盖范围**：仅英文、3 个来源（AMI、Jira、Kubernetes KEP），跨语言、跨领域推广性未知；Jira 记录因许可问题未随仓库分发，仅保留重建说明。
- **成本信息缺失**：无 GPU/成本报告，跨 harness 的 token 统计不可比，算力–效果结论只能定性。
