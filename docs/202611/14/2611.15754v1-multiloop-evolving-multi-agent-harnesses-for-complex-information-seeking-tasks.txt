Abstract
The performance of LLM-based agents depends not only on the underlying model
but also on the harness: the prompts, tools, and orchestration logic around it.
Recent works automate harness optimization with coding agents that analyze
execution traces, diagnose failures, and edit the harness code; however, those
focused on single-agent systems. Multi-agent harnesses are harder to optimize as
fixing them requires changing how agents interact in addition to how each behaves.
We study whether automated harness optimization can diagnose and repair failures
in multi-agent systems through a case study on complex information-seeking
tasks from DeepSearchQA [Gupta et al., 2026]. We apply MULTILOOP, a simple
optimization loop in which a coding agent iteratively analyzes, evaluates and edits
the harness. With only 10 training samples, the evolved harness improves accuracy
by 4.6% over the base harness and by 3.2% over the best single-agent system.
However, a taxonomy of failure modes before and after optimization shows that
the orchestration failures that characterize multi-agent systems largely persist. Our
findings motivate harness optimization methods that encourage structural changes
to how agents delegate tasks and share information.

Introduction
Agentic behavior in large language models (LLMs) is typically enabled by a “harness”: the sur-
rounding infrastructure that defines prompts, access to tools, and orchestration flow. As agentic
systems grow more complex and produce longer trajectories, manually identifying harness failures
has become impractical, motivating recent efforts to automate both detection and mitigation. These
works automate harness optimization using coding agents to iteratively analyze execution traces,
diagnose failures, and improve the harness code [Lee et al., 2026, Lou et al., 2026, Zhang et al.,
2026b]. Crucially, for these optimizers to accurately diagnose failures and propose updates, they
require full visibility into historical code changes, execution traces, and evaluation results. This
optimization process, however, has been primarily studied for single-agent systems.
Multi-agent harnesses, where an orchestrator agent delegates work to subagents, are a common
and effective design for long-horizon tasks [Zhu et al., 2024, Grand et al., 2025, Schroeder et al.,
2025, Zhang et al., 2026a, Anthropic, 2025, Alzu’bi et al., 2026]. However, shifting from single-
to multi-agent harnesses complicates harness optimization. For example, reading the full rollouts
of many subagents can overwhelm the optimizer’s context window [Zhang et al., 2025b]. More
fundamentally, failures may also cascade from poor orchestration, such as delegating overly broad
tasks, parallelizing dependent ones, or sharing too little context between agents, which leads to
redundant work and long verification loops [Cemri et al., 2026, Wang et al., 2026b]. Unlike in
single-agent systems, fixing these would require changing not only how individual agents behave but
also how they interact. To our knowledge, no prior work has examined whether automated harness
optimization can diagnose and repair such failures.

In this work, we take a first step toward answering this question through a case study on automatically
evolving a multi-agent harness for complex information-seeking tasks, using Google’s DeepSearchQA
benchmark [Gupta et al., 2026]. This is a natural setting as it produces long, complex trajectories
involving reasoning, tool use, and sandboxed environments. In addition, these tasks have been shown
to benefit from multi-agent systems with subagent delegation which alleviate long-context issues and
enable decomposition of sub-tasks [Zhang et al., 2026a].
Rather than proposing a new optimization strategy, we apply an existing paradigm to a multi-agent
harness to understand which failures it resolves and which remain. Following Lee et al. [2026],
Zhang et al. [2026b], we employ MULTILOOP, a simple automated optimization loop where a coding
agent iteratively improves a base multi-agent harness. In each iteration, an Optimizer agent evaluates
the latest rollouts on a small training set of examples to identify weaknesses and failure modes in
the current harness. With access to the history of past scores and prior harness edits, the agent
consolidates recurring issues among different rollouts and executes targeted code edits to yield a new,
optimized harness. Finally, the proposed harness is evaluated, and the loop repeats.
We find that harness optimization does transfer to the multi-agent setting: the evolved harness
improves accuracy by 4.61% over the base harness and outperforms the best single-agent system
by 3.19%. However, these improvements come from prompt refinements, such as stricter answer
formatting and instructions for processing tool outputs programmatically, and from the addition of a
new tool, rather than from structural orchestration changes that improve coordination between agents.
As a result, the orchestration failures characteristic of multi-agent systems largely persist. We support
this with a taxonomy and qualitative evaluation of the failure modes before and after optimization.
Ultimately, our findings motivate future work on harness optimization that encourages structural
changes to multi-agent harnesses, such as redesigning how the orchestrator delegates tasks or what
information agents pass to one another.

Harness Optimization
Algorithm 1 MULTILOOP: automated multi-agent harness optimization
1: Input: training set X, base harness H0, iterations N, LLM M
2: A0, R0 ←EVALUATE(H0, M, X)
▷Evaluate base harness on training set to get initial accuracy A0 and rollouts R0
3: L ←{(H0, A0, R0)}
▷Stores all harness versions, and their training set accuracy and rollouts
4: for t = 1 . . . N do
5:
Ht ←OPTIMIZE(Ht−1, At−1, Rt−1, L)
▷Optimizer proposes a new harness based on previous evaluation and history
6:
At, Rt ←EVALUATE(Ht, M, X)
▷Evaluate the new harness on the training set
7:
L ←L ∪{(Ht, At, Rt)}
▷Add the new harness, accuracy, and rollouts to the history
8: return arg maxHt{At | (Ht, At, Rt) ∈L}
This section presents our method for autonomous optimization of multi-agent harnesses. Algorithm 1
implements MULTILOOP as an agentic workflow with two subroutines: EVALUATE and OPTIMIZE.
We initialize MULTILOOP with a simple harness in which an orchestrator delegates tasks to subagents,
each executing tool calls in its own context (see Appendix C, Figure 3 for a visualization).
EVALUATE
Given a harness Ht, EVALUATE runs the current agentic system independently on
every training example in X, producing a rollout per example, collectively denoted Rt. To make
these rollouts consumable by the Optimizer, each is programmatically converted into a markdown
file that distinguishes orchestrator steps from subagent steps and renders every step’s model thoughts,
tool calls, tool outputs, and generated answer. Finally, accuracy At is computed over the training set
(explained in § 3) and appended to a running history of harness versions with their accuracies and
rollouts, L, allowing the optimization loop to rollback from a bad harness version.
OPTIMIZE
The Optimizer is a coding agent that reads the evaluation outputs in L and proposes
code edits to the harness. It is implemented with the Antigravity coding-agent SDK, which configures
an agent with a system prompt (found in Appendix D), and a set of tools for filesystem navigation
(file viewing, directory listing, and grep-based text search), code editing (file editing and creation),
and shell execution (for checking code compilation and performing version-control operations).

Experiments
Experimental Setup
We evaluate MULTILOOP on DeepSearchQA [Gupta et al., 2026], a recent
900-prompt benchmark for evaluating agents on difficult multi-step information-seeking tasks. As
iterative harness optimization is costly, the training set includes 10 challenging examples that all
of the unoptimized agent systems in Table 1 could not solve, and the test set is the remaining 890
examples. This is motivated by recent evidence that meaningful optimization signal can be extracted
from a small number of well-chosen examples [Wang et al., 2025], and significant experimental costs
as described in Appendix E. Across all experiments, we used Gemini-3-Flash as the model in the
evaluated harness, and Gemini-3.1-Pro with the Antigravity harness as the Optimizer [Gemini Team,
Google DeepMind, 2025].

Baselines
To evaluate our approach, we first
compare against three baselines without any
optimization. (1) Search Agent, a multi-step
agent which only has access to a Google search
tool; (2) Search Plus Other Tools (SPOT) Agent,
which adds tools for website scraping, PDF
scraping, and Python execution; and (3) Orches-
trator with SPOT subagents, our baseline multi-
agent harness. We then run three optimization
experiments. First is (4) SPOT + harness op-
timization, showing the effect of optimization
on a single-agent harness, (5) is Orchestrator w/
SPOT subagents + harness optimization which
optimizes the multi-agent harness, and finally (6) Orchestrator w/ SPOT subagents + prompt opti-
mization, an ablation experiment which only optimizes the system instructions, injected messages,
and function declarations. All optimization loops are run for 10 iterations.
Evaluation
We measure the percentage of fully correct (FC) responses, defined as an exact semantic
match to the ground-truth entity set (i.e., identifying all correct answers with zero incorrect ones)
using Gemini-3-Flash [Gemini Team, Google DeepMind, 2025] and the DeepSearchQA [Gupta et al.,
2026] grader prompt. Results show the average FC and 95% confidence interval averaged across two
runs on the 890-question test set, which is disjoint from the training set.
Results
Table 1 shows that adding additional tools on top of the search tool improves performance,
with the SPOT agent outperforming the Search Agent by 10.34%. Adding the naive multi-agent
harness on top of that does not show immediate benefits, with the unoptimized Orchestrator with
SPOT subagents underperforming the single SPOT agent by 1.42%. Applying MULTILOOP improves
multi-agent performance by 4.61% to 71.88%, which is the best result we obtained on the test set. On
the single-agent harness, optimization degraded the performance by 3.15%. For the ablation allowing
only prompt optimization to the multi-agent harness, we see a performance decrease of 2.65%.

Analysis
We now unpack the factors behind these results: why optimization degrades single-agent performance
yet improves multi-agent performance, and which harness changes drove that improvement and how
they reshaped the distribution of failures over the course of optimization.
Optimization harms single agent performance
We find that the single-agent degradation stems
from an optimization step that added 30K-character truncation for tool outputs, which did not
generalize to the test set. This suggests that a larger training set could be useful, however we kept the
training set minimal at 10 samples due to compute constraints (see Appendix E).

Full harness optimization makes the system do more work overall: the orchestrator takes more
steps (6.3 vs. 4.3), spawns more subagents (14.0 vs. 10.9), and each subagent runs longer (17.9 vs.
13.9 steps), yielding 250 subagent steps and 236 subagent tool calls per question versus 152 and
141 for the unoptimized harness. Prompt-only optimization instead spawns the fewest subagents
(7.7 per question), but each one issues the longest trajectories: 20.6 steps and 19.6 tool calls on
average, compared with 13.9 steps and 12.9 tool calls without optimization and 17.9 and 16.9 with
full optimization, and 46% of prompt-only subagents hit the 30-step limit compared with 19% and
35%, respectively. As a result, the prompt-only system does roughly the same total subagent work as
the unoptimized one (158 vs. 152 steps per question) while being less accurate. This suggests that
prompt-only optimization overfit on the train set, and pushed individual subagents into longer, less
effective trajectories rather than better delegation, pointing at the value of allowing the optimizer to
make structural changes. Because full optimization increases total inference, part of the gain may
reflect additional compute rather than better harness design—a compute-matched comparison [Tran
and Kiela, 2026] is left for future work.

Taxonomy and Distribution of Failure Modes
We manually analyzed 11 trajectories from the Or-
chestrator with SPOT subagents run where the final
output shifted from fully incorrect to fully correct (or
vice versa) post-optimization. By cross-referencing
observations with the Trajectory Audit Categories
proposed by Li et al. [2026], we established 7 cat-
egories, fully detailed in Appendix F: Bad Orches-
tration (poor decisions about when, how, and how
many subagents to dispatch); Ineffective Tool Usage
(mechanical failures in tool selection and execution);
Retrieval Scope Drift (losing track of key task con-
straints mid-task); Criterion Mismatch (applying an
incorrect decision rule, field definition, or time win-
dow to an otherwise relevant source); Tool Output
Misreading (misreading a value, label, or field from
the correct source); Retrieval Dependency Errors (failing to connect correct intermediate results
across sources or subagents); and Final Answer Composition (verbose final answers when a concise
one is required).
To better understand how MULTILOOP resolves specific errors, we analyze the rollouts over the
training set from the Orchestrator w/ SPOT subagents setting, by counting the number of examples
that contain at least one instance of a given error category. As illustrated in Fig. 2, the baseline model
(No Opt.) has the highest overall frequency of errors, dominated by bad orchestration, ineffective
tool usage, and final answer composition failures. The intermediate stage (Before Best Opt.) shows
incremental progress. The best optimization configuration (Best Opt.) reduces overall failures,
primarily by resolving final answer composition errors, retrieval dependencies, and retrieval scope
drift. Orchestration and tool usage errors were not alleviated with harness optimization, indicating
that these may require model improvements or more dedicated optimization logic.

Harness Changes Made by MULTILOOP
As
outlined in Appendix G, Tables 2 and 3, the
adjustments to the Orchestrator w/ SPOT sub-
agents harness were primarily at the prompt-
level (e.g., system instructions, function declara-
tions, and error message propagation to agents).
The only architectural change was the addition
of a new tool (download_file) for retrieving
files from the internet. The majority of the modi-
fications focused on refining subagent tool usage
by clarifying use-cases. To address orchestra-
tion deficits, the orchestrator’s system prompt
was updated to recommend query decomposi-
tion, parallel delegation across subagents—mirroring the delegation principle in Anthropic’s Claude

multi-agent system [Anthropic, 2025] and the supervisor/worker pattern in LangGraph [LangChain
AI, 2024]—and specific tool use behavior for subagents. Further, to mitigate tool output misreading,
the subagents were given explicit directives on how to parse raw string outputs into JSON objects
for programmatic analysis—similar to what Schick et al. [2023] and Hong et al. [2024] solve with
typed structured schemas—and included an example of composing multiple tool calls within the
python sandbox. Finally, errors in final answer composition were addressed through instructions that
encouraged concise responses. The jump to the Best Opt. score of 71.88% stemmed specifically
from refinements to the download tool and stricter final-answer formatting instructions. Consistent
with Ursekar et al. [2026], aside from introducing the download tool, the optimizer avoided deeper
structural changes (e.g., modifying the response schema between subagents and the orchestrator) in
favor of surface-level prompt and formatting adjustments.
Analyzing Changes in System Behavior
Building on our analysis of the harness changes, we also
look at how the agent’s behavior changed after harness optimization. 9 questions improved from
fully incorrect to fully correct, while 2 regressed. Appendix H, Tables 4 and 5 showcase behavioral
differences observed between the rollouts before and after optimization: improvements were mainly
driven by programmatic processing of outputs via the download_file tool (6 examples) and better,
sequential orchestration of dependent tasks (3 examples), while the 2 degraded examples failed
because the orchestrator became trapped in long verification loops.

Related Work
Issues with Multi-Agent Harnesses
Multi-agent harnesses are a common design for long-horizon
tasks because they give each subtask a fresh context window and let independent subtasks run in
parallel [Anthropic, 2025, Zhu et al., 2024, Schroeder et al., 2025, Zhang et al., 2026a, Alzu’bi
et al., 2026]. However, these systems require careful multi-agent coordination and communication.
Kim et al. [2026] find that coordination helps on decomposable tasks, hurts on sequential ones, and
propagates errors across agents unless a central coordinator catches them. Tran and Kiela [2026] show
that under fixed compute, a single agent matches or beats multi-agent systems, due to information
loss in hand-offs. Ou et al. [2025] find that structured information sharing and a reflective orchestrator
can improve performance of multi-agent systems. Failure taxonomies place most multi-agent errors
in task specification and inter-agent misalignment [Cemri et al., 2026], and even attributing a failure
to the responsible agent and step is hard [Zhang et al., 2025b]. Our taxonomy in Appendix F, is
consistent with these findings: bad orchestration dominates our failure distribution, and it is a category
that harness optimization struggles to improve.
Automatic Harness Optimization
Earlier methods optimize prompts from LLM-generated feed-
back [Yang et al., 2024, Yuksekgonul et al., 2024, Agrawal et al., 2026] or search over agentic
workflows represented as code [Hu et al., 2025, Zhang et al., 2025a]. Recent work treats the full
harness code as the optimization variable and uses a coding agent to propose and implement harness
edits in an iterative loop [Lee et al., 2026, Zhang et al., 2026b, Ursekar et al., 2026, Zhang et al.,
2026c, Lou et al., 2026, Lin et al., 2026, Nie et al., 2026, Chen et al., 2026, Karten et al., 2026]. Two
limitations of this paradigm are directly relevant to our study. First, evolved harnesses may overfit
the training set, with gains that shrink or vanish on held-out tasks [Wang et al., 2026a, Xia et al.,
2026]. Second, optimizers favor surface-level edits such as prompt rewrites over structural changes
[Ursekar et al., 2026, Xia et al., 2026]. A concurrent work, RRSI [Xia et al., 2026] mitigates both by
regularizing proposal and selection.
6
Conclusions and Future Work
We present a case study in which we apply MULTILOOP, a simple harness-optimization loop, to a
multi-agent system for complex information-seeking tasks. On DeepSearchQA [Gupta et al., 2026],
MULTILOOP improves the multi-agent harness, but the gains come from prompt refinements and a new
tool rather than from changes to how agents delegate work or share information, and the orchestration
failures that characterize multi-agent systems largely persist. Future work includes larger-scale
experiments, compute-matched comparisons against single-agent baselines, and optimization methods
that explicitly encourage structural changes to orchestration, such as redesigning task decomposition
or the information passed between agents.

Limitations
For technical reasons, we were restricted to use Gemini models and Antigravity during the course of
this work. It would be interesting to extend such experiments to additional models and harnesses.
Another limitation is that we only used DeepSearchQA, and extending our evaluation to additional
benchmarks would be appealing. Other knobs we would have liked to explore altering with more
time and compute available is the number of optimization iterations, and the number and composition
of the samples in the training set.

Price Breakdown of Experimental Setup
We limited the number of optimization steps, and training examples due to budget constraints. A
single evaluation over the test set (890 questions × 2 runs) costs about $7.3K for the unoptimized
harness, $12.9K for the fully optimized harness, and $9.5K for the prompt-only harness (mean $4.25,
$7.15, and $5.25 per question), and each evaluation of the 10-question training set costs $104 and
$213 for the unoptimized and optimized harnesses (mean $10 and $21 per question, since these are
the hardest examples).
F
Failure Mode Taxonomy
Bad Orchestration The orchestrator makes poor decisions about when, how, and how many subagents
to dispatch. This includes spawning parallel subtasks that have logical dependencies, sending overly
broad or keyword-style prompts to subagents, spawning redundant subagents, over-parallelizing
subagents, and falling into verification loops instead of outputting the final answer. Ineffective Tool
Usage Agents fail at the mechanical level of tool selection and execution, such as picking the wrong
tool for the content type (e.g. using the browse tool to examine pdfs), being blocked by sandbox
limitations, not following through on stated tool intentions, and using the Python tool to simply call
existing tools without further analysis of their results. Retrieval Scope Drift The agent loses track of
key constraints mid-task, or fails to validate that all required entities satisfy those constraints before
producing a final answer. Criterion Mismatch The agent reaches a relevant source but applies an
incorrect decision rule, field definition, aggregation level, or time window. The resulting answers
often contain locally correct values bound to the wrong criterion, like using data from the wrong
year. Tool Output Misreading The agent reaches the correct page or data source but misreads a
local value, label, or field. Some common examples are misinterpreting tool outputs like flattened
tables, confusing similar-looking fields or rows, or struggling to extract data from interactive charts
and paginated results that require dynamic interaction. Retrieval Dependency Errors The agent
obtains correct intermediate results from individual sources but fails to properly connect them, such
as failing to resolve conflicting data across sources or failing to join datasets from separate subagents
into a comparative table. Final Answer Composition Agents produce verbose final answers with
markdown tables, caveats, and paragraph explanations when a specific, concise answer is required.
