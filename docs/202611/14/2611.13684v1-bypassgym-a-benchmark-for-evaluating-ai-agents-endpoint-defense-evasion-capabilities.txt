Abstract
Artificial intelligence agents increasingly automate cybersecurity
tasks, including offensive operations. Frequent attacks across the
web make endpoint detection and response (EDR) a critical defense,
but whether AI agents can evade it remains unclear. Benchmarks
evaluate the offensive capabilities of large language model (LLM)
agents in areas such as penetration testing and vulnerability discov-
ery. One important capability that these benchmarks do not address
is defense evasion, specifically whether an agent can develop a pro-
gram that executes a payload without being blocked or terminated
by a deployed EDR. We introduce BypassGym, to our knowledge
the first benchmark to systematically evaluate this capability on real
endpoints. Given command-and-control (C2) shellcode, an agent
must generate and compile a loader that executes the payload with-
out being blocked or terminated. A supplementary evasion knowl-
edge skill provides domain knowledge and supports comparisons
with and without this input. BypassGym is built on Proxmox VE
(PVE), so the evaluation environment runs real Windows systems
and EDR products inside virtual machines and returns structured
detection feedback to the agent. We evaluate 5 lightweight model
backends against 6 EDR products and 3 payloads, and find that
even these simple models generate successful submissions, with
DeepSeek-V4.1 Flash reaching 17/18 successful runs and Bitde-
fender allowing only 5 of 15 runs to pass. These results provide a
systematic measurement of current AI agents’ endpoint defense
evasion capabilities and identify areas for defenders to investigate.

Introduction
Large language model (LLM) agents have quickly progressed from
answering questions to autonomously carrying out software engi-
neering tasks involving multiple steps [15, 37], and cybersecurity
is one of the domains where this progress is most consequential
[9, 36]. The same capability that lets an agent navigate an unfamiliar
codebase also lets it write, compile, and iteratively debug offensive
tooling. As generative AI lowers the expertise barrier for malware
development [4], understanding these capabilities under realistic
conditions becomes a pressing question for model providers, end-
point security vendors, and policymakers alike. Frequent attacks
across today’s diverse web ecosystem make EDR a critical defense,
raising a pressing question: can AI agents autonomously bypass it?
BypassGym measures this capability.
This is no longer a hypothetical concern. LAMEHUG, reported
by Ukraine’s CERT-UA in July 2025, integrates an LLM directly into
its attack workflow, querying a public LLM endpoint to generate
reconnaissance and data theft commands on the fly [8]. Google’s
Threat Intelligence team documented PROMPTFLUX, a malware
family that queries Gemini to dynamically rewrite its own code in
an attempt to evade detection [12]. Anthropic disclosed a threat
actor with only basic programming skills who used a frontier model
to develop and sell ransomware variants that evade detection, en-
crypt files, and hinder recovery [4]. Together, these cases show that
LLMs are already being used in real malware workflows, includ-
ing attempts to evade endpoint defenses, namely the antimalware
scanning and EDR systems deployed on real hosts.
Despite these reported uses, existing evaluations provide limited
insight into agents’ ability to evade deployed endpoint defenses.
Studies of malware generation and evasion with AI assess gener-
ated samples through scanner services, sandboxes, or offline de-
tectors, or focus on constrained rewriting tasks [2, 18, 31]. agentic
cybersecurity benchmarks primarily measure penetration testing,
vulnerability discovery, or reproduction [11, 20, 35, 36, 38]. These
evaluations do not systematically measure whether an agent can
turn diverse evasion techniques into a functional loader whose
payload actually runs on a real endpoint under a deployed EDR.
Addressing this gap requires a benchmark that evaluates evasion
under comparable, realistic conditions, which poses three chal-
lenges. 1) Standardizing the task without constraining the agent.
The benchmark must hold the task conditions fixed across models,
scaffolds, and knowledge conditions so that results are comparable,
while leaving the loader design entirely open so that task stan-
dardization does not artificially cap the capability being measured.
2) Evaluating on real endpoints. Offline scanning cannot establish
whether a submission executes its payload while evading a deployed
EDR. Evaluation must support different EDR products, and restore

3) Measuring the impact of domain knowledge. Agents may lack
specialized evasion knowledge, which can limit their performance.
Supplementary domain knowledge must be a controllable input so
that its effect can be measured by comparing runs with the same
model, task, and iteration budget.
We present BypassGym, a benchmark for evaluating whether
AI agents can evade deployed endpoint defenses. BypassGym has
three modules. The Evasion Task Setup module provides a fixed
shellcode payload from an open-source command-and-control (C2)
framework and a curated evasion knowledge skill. The Shellcode
Loader Development module gives the agent a Windows compila-
tion toolchain for building and revising a shellcode loader, then
packaging it as a bundle with one entry executable and any required
dependencies. The EDR Evaluation and Feedback module first runs
the bundle on a Windows 11 VM without EDR, referred to as Win-
dows 11 NoEDR, to verify that the payload executes and the process
remains alive. Candidates that pass this functional test are then run
on a separate Windows VM with the target EDR installed. Both
stages return structured results, which the agent uses to revise its
submission in the next iteration. We summarize our contributions
below.
• An end-to-end benchmark for EDR evasion. We intro-
duce BypassGym, which evaluates whether an AI agent
can generate a loader that executes a supplied shellcode
payload on a Windows endpoint protected by a deployed
EDR. The benchmark fixes the payload, available tools, and
iteration budget while leaving the loader implementation
open.
• Automated EDR evaluation and feedback. We build
an automated EDR evaluation and feedback service that
executes generated loaders on real endpoints, assesses their
behavior under deployed EDR systems, and returns struc-
tured execution results. By making EDR evaluation and
feedback repeatable, the service enables agents to revise
and improve their loaders over multiple iterations.
• Evasion knowledge skill. We provide a curated evasion
knowledge base as a native agent skill with configurable
richness levels, enabling direct measurement of how exter-
nal knowledge affects agent performance under the same
model, task, and iteration budget.
We evaluate five model backends against six EDR products and
three C2 payloads. In 71 of 90 runs (78.9%), an agent generates a
loader that executes the payload and passes the endpoint checks.
Success varies with both the model and the EDR. DeepSeek-V4.1
Flash performs best, whereas Bitdefender is the hardest defense to
bypass. Our controlled studies examine what helps agents improve.
Supplied evasion knowledge gives agents workable strategies, while
the value of the agent scaffold depends on the model and increasing
reasoning effort alone does not reliably improve results. When a
submission fails, detailed endpoint feedback helps the agent identify
how to revise it. A binary pass/fail signal alone does not.

Background
Endpoint evasion and shellcode loaders. EDR products monitor
changes to the file system and runtime behavior [22] and can quar-
antine artifacts or terminate processes [24]. A shellcode payload
produced by a command-and-control (C2) framework cannot run
on its own. It requires a loader to prepare and execute it on the
target host [13, 29]. BypassGym therefore asks the agent to con-
struct the shellcode loader. A submission is successful only if the
payload executes, survives the endpoint checks, establishes a usable
C2 session, and completes the required command and file-transfer
checks.
Evasion knowledge skill. Agents may lack specialized knowledge
of endpoint defenses and evasion techniques. We provide curated
public knowledge as supplementary task input and vary its avail-
ability to assess its effect on evasion performance. We collect and
deduplicate public techniques, organize them by loader stage, and
normalize their descriptions. The resulting knowledge base con-
tains 37 individual techniques, three complete reference projects
(AceLdr [19], gargoyle [16], and BOAZ [33]), and six templates
for DLL hijacking [25]. The catalog covers environment checks,
defense weakening, memory allocation, payload writing and exe-
cution, process injection [26], and supporting stealth techniques.
We package the knowledge base as a native agent skill, a file tree
headed by a SKILL.md manifest following the OpenAI Codex skills
documentation [27]. Our benchmark exposes it through native skill
support, giving agents access to the same supplied materials under
a given knowledge setting. Techniques can be added or removed
without changing the agent loop. Agents may develop solutions
beyond it and use web search when their scaffold supports it. We
define three input conditions. The full condition supplies the com-
plete skill. The partial condition removes all README.md files but
retains source files, binaries, and loader projects. The none con-
dition supplies a SKILL.md containing only metadata. Agents in
this condition rely on model knowledge and any search capability
available through their scaffold.
4
The BypassGym Benchmark
BypassGym evaluates AI agents’ endpoint defense evasion capabil-
ities. Figure 1 summarizes the three modules. This section defines
the benchmark task and describes the architecture used to evaluate
submissions.
4.1
Evasion Task Setup
A task pairs a fixed C2 shellcode payload with one target EDR prod-
uct. The agent receives the payload, the knowledge skill under the
selected condition, and a README specifying the deliverable. Ap-
pendix A reproduces a representative initial prompt and describes
how the README is incorporated into the task. The agent can
inspect these inputs and create source files in a writable workspace
with a Windows compilation toolchain. The current benchmark
instantiation uses Havoc, AdaptixC2, and Sliver payloads, and pack-
ages the knowledge skill as complete loader projects, individual
evasion techniques, and DLL-hijacking templates. The three knowl-
edge conditions are defined in Section 3. The current agent output
is a candidate. The packaged ZIP may contain subdirectories and
required dependencies, but it must contain exactly one file with the
.exe suffix. This unique executable is the entry point, and each up-
load of the bundle is a submission. The entry must use the PE32+ /
x86-64 Portable Executable (PE) format [23] and may load a separate
loader DLL. Missing dependencies and an incorrect architecture
are detected during NoEDR testing. Shellcode in the bundle must
be stored in encrypted form.
4.2
Shellcode Loader Development
This module runs in a container with a configurable agent scaffold
and model backend. The experiments use Codex CLI, Claude Code,


Yuan et al.
and OpenCode [3, 5, 28] with GPT, Gemini, GLM, DeepSeek, and
Qwen backends. The agent builds and revises a shellcode loader
across iterations, then packages it as a ZIP archive for evaluation.
The workspace persists across iterations, and supported scaffolds
retain state.
Runs and iterations. A run is one agent’s attempt to solve a
task with a fixed payload and target EDR, with its own workspace
and feedback history. A run allows up to 10 iterations. In each
iteration, the agent constructs or revises a candidate and submits it
to the NoEDR VM. The candidate must pass the Endpoint Execution
Check there before it can reach the selected Target EDR VM. On
the target, it must pass both the Endpoint Execution Check and
the C2 Functionality Check. If a NoEDR check fails, the agent may
make up to 10 repair submissions within the same iteration. If the
repair budget is exhausted, or if either check group fails on the
target, the run advances to the next iteration. The run succeeds at
the first target submission for which all required checks pass. It is
counted as a failure if all 10 iterations are exhausted without such
a submission, or if it terminates earlier without one.
4.3
EDR Evaluation and Feedback
This module uses PVE virtual machines managed by the Evaluation
Service through Proxmox VE [30]. It contains a NoEDR VM and
Target EDR VMs with one EDR product installed on each.
Evaluation oracle. The oracle is defined by functional execution
and survival. A submission passes if its payload actually executes
on the target EDR endpoint and the launched process is neither
blocked nor terminated throughout the observation window. De-
tection alerts are deliberately excluded from the verdict. Because
no product exposes complete alert telemetry through a consistent
public interface, a submission that a product silently logs or flags
but does not stop still counts as a pass. Moreover, an actual attacker
may not care whether an alert is raised. What matters is whether
commands execute and files upload and download successfully.
The oracle combines two complementary check groups, listed
in Table 2. The Endpoint Execution Check runs on the endpoint VM.
The C2 Functionality Check runs on the C2 server. The NoEDR VM
runs only the Endpoint Execution Check. A candidate that passes
it is submitted to the selected Target EDR VM, where both checks
are applied. A run succeeds only when both pass on the target. The
VM controller restores a clean snapshot before each test, so every
submission starts from the same endpoint state. Workspaces and
feedback histories remain separate across runs.

The four phases of the Endpoint Execution Check run on the
Endpoint VM. Static Check requires the entry executable to remain
present after extraction. Process Check launches the entry point and
checks process survival after a 10-second execution wait. Traffic
Monitor observes the tracked process for 60 seconds and requires
an outbound connection. Delayed Check waits a further 10 seconds
and requires the process to remain alive. All four phases must pass.
The Guest Agent runs this four-phase monitor inside each VM. The
C2 Functionality Check runs on the C2 server during the target EDR
stage, after the endpoint check, and verifies the execution end to
end. For all three C2 payloads, lab-orchestrator.service dis-
patches a common playbook to each newly established session. The
playbook executes whoami, uploads a file to the endpoint, reads it
back through a shell command, and downloads it to the server. A
session that completes this playbook demonstrates that the payload
reached the endpoint and established a usable session, executed
a remote command and returned its output, and supported bidi-
rectional file transfer. These three behaviors correspond to the C2
Communication, Command Execution, and File Download/Upload
checks respectively. Together, the two groups provide independent
endpoint and C2 vantage points.
5
Experimental Evaluation
5.1
Experimental Setup
Our evaluation addresses three research questions.
• RQ1. How successfully do current LLM agents evade the
evaluated EDRs, and what execution patterns accompany
their outcomes?
• RQ2. How do external knowledge, agent scaffold, and rea-
soning effort affect their capability?
• RQ3. Can endpoint feedback help agents improve subse-
quent attempts?
We evaluate five model backends, namely GPT-6 Luna, Gemini
3.1 Flash Lite, GLM-5.3 Flash, DeepSeek-V4.1 Flash, and Qwen3.7
Plus. Experiments use isolated Windows virtual machines on Prox-
mox VE [30], with fixed payloads generated with AdaptixC2 [1],
Havoc [13], and Sliver [6]. The six endpoint products are Windows
Defender Antivirus (hereafter, Windows Defender) [22], Kasper-
sky [17], Elastic [10], Trend Micro Deep Security (hereafter, Trend
Micro) [34], Sophos [32], and Bitdefender [7]. The NoEDR VM is a
separate Windows 11 VM with Windows Defender removed. Exact
OS, product, tool, and payload versions are listed in Appendix C.
Before evaluating agents, we ran a functional baseline to verify
that the configured endpoints and C2 environment were operational.
For each framework, we generated its default EXE directly from
the C2 server, with no agent, custom loader, or manual rewriting,
and submitted the executable. Table 3 reports 15 failures and three
passes across the 18 EDR cells. All three default executables passed
the Endpoint Execution Check on the NoEDR VM.

5.2
Effectiveness and Execution Analysis (RQ1)
For RQ1, we follow the run and iteration budgets defined in Sec-
tion 4.1, using the NoEDR VM for the Endpoint Execution Check and
debugging. RQ1 comprises 5 × 6 × 3 = 90 runs, covering five model
backends, six EDR products, and three C2 payloads, with one run
per combination. Every run used Codex CLI [28]. Table 4 presents
the individual RQ1 runs.
Across all 90 RQ1 runs, 71 generated a passing submission (78.9%).
Every evaluated model generated passing submissions. DeepSeek-
V4.1 Flash is the strongest (17/18), while Qwen3.7 Plus is the weakest
(10/18). The defenses differ sharply. Windows Defender admits all
15 submissions, whereas Bitdefender is the hardest target, allowing
only 5/15 runs (33.3%). Payload difficulty also varies. Sliver is the
easiest (27/30), Havoc reaches 24/30, and AdaptixC2 is the hardest
at 20/30. All five models fail Havoc on Bitdefender, indicating a
shared hard case in this tested setting.
Model execution patterns. Table 5 summarizes each model’s
working style and success rate. Of the 71 passing submissions, 50
(70%) use DLL side-loading through the signed ssvagent.exe host,
and 7 pass after switching from a standalone loader that failed its
Target EDR test.
Each model has 18 runs. We count a repair run when it re-
quires at least one NoEDR repair. The repair totals include all
calls in the NoEDR repair loop, including refusals without code
changes. These working styles are supported by first-turn tool
use and initial entry choices. DeepSeek used a median of 33.5
shell calls in the first turn. 16/18 first turns used grep, 16/18 used
objdump, and 16/18 used strings. All 18 recorded initial candi-
dates used ssvagent.exe. GPT used a median of 7.5 shell calls, and
14/17 recorded initial candidates used loader.exe. Gemini used
loader.exe in 15/18 candidates and cat in 18/18 first turns. By
contrast, rg, grep, find, and objdump did not appear in its first
turns. GLM used ssvagent.exe in 17/18 candidates, with rg in
14/18 first turns. Qwen’s initial entries were 10 ssvagent.exe, 6
lghub_updater.exe, and 1 loader.exe. It used objdump in 2/18
first turns.

Limitations and future work. BypassGym currently measures
evasion of six commodity EDR products on Windows. Extending
the task formulation to other operating systems and to evasion
applied to the shellcode payload itself, rather than only to the
loader, is a natural next step. The knowledge skill is deliberately
limited in coverage and focuses on loaders, so absolute success
rates should be read as lower bounds on agent capability under
the given knowledge conditions. The current design also cannot
fully separate detection of the loader from detection of the payload.
Differences between payloads should therefore not be interpreted
as a measure of agents’ ability to evade detection through loader
design alone.
Future work should extend the knowledge skill into a composi-
tion map of evasion techniques, recording which techniques com-
bine and which conflict, with the validity of each combination
established empirically through agent generation and testing. Our
traces raise the question of how to automatically and precisely
identify why a submission was detected.
7
Conclusion
We presented BypassGym, a benchmark for measuring whether
AI agents can turn a fixed C2 shellcode payload into a loader that
executes on a real Windows endpoint protected by a deployed EDR
product. Across five model backends, six EDR products, and three
payloads, 71 of 90 runs produced a passing submission, showing
that this capability is already broadly available. The lower-cost Flash
and Lite backends matched or exceeded GPT-6 Luna, and DeepSeek-
V4.1 Flash achieved the strongest overall result with 17 of 18 runs
passing. These results show that low-cost defense evasion is already
effective in practice. BypassGym provides a reproducible baseline
for this ongoing assessment, and we offer it to both EDR vendors
and agent developers as a shared benchmark for strengthening
cybersecurity.
Reproducibility
After the review process, we will release all information required
to reproduce this work, including but not limited to the benchmark
framework source code and the complete experimental data. We
cannot redistribute licensed EDR installations, credentials, raw C2
shellcode, or directly executable submissions, so users must supply
their own authorized EDR and C2 environments.
Ethics and Privacy Statement
This work studies dual-use offensive capability only in isolated
environments maintained for our experiments and does not target
third-party systems. The benchmark is intended to inform model
