Abstract 

Agent Skills—file-based packages of procedural knowledge that a coding agent can discover and load on demand—are now shipped by every major agent harness, yet the evidence for how much they help comes almost entirely from settings in which the right Skill is hand-picked for the task and the agent starts from a blank slate. Neither holds in deployment, where an agent chooses from whatever library happens to be installed and frequently carries memory from earlier work. We present SkillBuffBench, a benchmark and paired evaluation protocol that treats Skill access as a three-level factor (no Skill, a curated Skill, and automatic invocation from an installed library), crosses it with memory (off and on), with four agent harnesses and with multiple models (the state-of-the-art proprietary models from Anthropic, Google and OpenAI, and the state-of-the-art open-weight models from Chinese providers), every model being run under every harness, and evaluates the result on research tasks contributed by domain experts together with the Skills they use, currently in materials science and biology, with the suite extended on a rolling basis. Every run is marked by a deterministic verifier; uncertainty is reported with a paired, task-level bootstrap; and cost, agent rounds and wall-clock time are reported alongside the score rather than folded into it. This version of the paper describes the design of the benchmark, its evaluation protocol and its current tasks and Skills. The evaluation is in progress: results will be added once the runs are complete, and the task suite, results and analysis will continue to be updated on a rolling basis. 

# 1 Introduction 

Language-model agents are increasingly judged not by what the underlying model knows but by what the system around it lets the model do. A large part of that system is now written in plain files. An Agent Skill [2] is a directory containing a short description, a set of instructions and, optionally, scripts, templates and reference material; the agent harness —the program that runs the tool loop, manages the workspace and decides what enters the context window—advertises the descriptions of the installed Skills to the model and loads the body of one only when the model asks for it. The idea of giving an agent a reusable library of procedures is older than the format [34], but the format has made such libraries cheap to write and easy to share. An agent in deployment now commonly runs with a library of Skills installed, most of them irrelevant to the task at hand. Whether those Skills help is an empirical question, and it has only recently been asked carefully. A parallel line measures what agents can do in cybersecurity, from capture-the-flag challenges to finding, exploiting and patching vulnerabilities in real codebases [30, 35, 39–41], and another measures how long a task an agent can sustain [17] and whether it holds to its deployment policy under attack [11, 43]. These benchmarks share a protocol: a sandboxed environment, a well-defined task, a deterministic check of the final state, and a comparison across models and, sometimes, across harnesses, tool sets or retrieval methods. What they hold constant is the procedural knowledge available to the agent. They vary the agent and fix its augmentation, and, to our knowledge, none treats persistent memory as an experimental variable. SkillsBench [19] inverted this, holding the task, model and harness fixed and varying only whether curated Skills are available. Across 87 tasks and 18 model–harness configurations it found that curated Skills raise the mean score by 16.6 percentage points, that the gain varies widely by domain and by harness, that 13 tasks get worse with Skills, and that Skills written by the model itself did not substitute for curated ones. That study establishes that Skills can matter. It leaves open three questions that decide whether they matter in use. 

Curated access is an upper bound, not a deployment condition. In a curated-Skill condition a person who knows the task has already solved the hardest part of the problem: deciding which knowledge is relevant. A deployed agent receives no such help. It sees the descriptions of every installed Skill, must recognise that one of them applies, must choose it over plausible distractors, and must then follow it. Each step can fail, and loading the wrong Skill can be worse than loading none. The gap between the right Skill, supplied and a library, searched is the quantity a practitioner needs, and it cannot be read off a curated-versus-none comparison. 2Memory is an uncontrolled second source of procedural knowledge. Modern harnesses persist information between sessions: project instructions, notes the agent wrote for itself, records of what worked last time. Memory and Skills overlap in function—both carry procedure into a fresh context—so an experiment that does not control memory cannot attribute an improvement to either. Worse, repeated trials of one task are no longer independent if the second trial can read what the first one learned. Whether a Skill still helps an agent that already remembers a successful attempt, and whether memory alone recovers the benefit of a Skill, are open questions. 

Model and harness effects are confounded. Skill discovery and loading are implemented by the harness, not the model, and harnesses implement them differently. Most existing evidence pairs each model with its vendor’s own harness, or varies the model inside a single harness, so a difference between two rows of a results table may be due to the model, the harness, or their interaction. Separating them requires running the same models under different harnesses. This paper introduces SkillBuffBench, a benchmark and evaluation protocol built to answer these three questions. Its design is a full factorial: three Skill conditions (none, curated, and automatic invocation from an installed library), two memory modes (off and on), four harnesses, and multiple models from different providers, each run under every harness, with every cell evaluated on the same tasks and repeated three times. The tasks are research problems contributed by domain experts, each with the Skill that expert uses for it. They currently come from materials science and biology: extracting oxygen transport coefficients from isotope-exchange depth profiles, identifying a crystalline phase and refining its unit cell from a powder diffraction pattern, prioritising candidate regulatory targets of a gene for experimental follow-up, and measuring the structure of a cell spheroid and the distribution of its cells from three-dimensional microscopy images. Such workflows depend on procedural knowledge that is specialised, written down somewhere, and unevenly represented in what models already know, and they require professional software and data rather than a general-purpose programming environment. The suite is extended on a rolling basis. Every run is marked by a deterministic verifier against versioned inputs, so that scores are reproducible and comparable across harnesses.

# 2 Methodology 

2.1 Research questions and design overview 

SkillBuffBench measures whether Skills raise task success for agents working in realistic conditions, and whether that effect survives changes of harness, task domain and memory setting. Three questions organise the design: 

RQ1 Does a curated Skill improve task success over no Skill? 

RQ2 Does automatic invocation from an installed Skill library improve task success over no Skill, and how much of the curated gain does it retain? 

RQ3 Does memory change task success, cost, number of agent rounds or wall-clock time, and does it change the effect of Skills? The experiment is a full factorial over four factors, summarised in Table 1 and Figure 2, evaluated on a fixed suite of 4 tasks with three repeats per cell. A configuration is a (harness, model) pair; within a configuration, the only things that vary between the runs of a task are the Skill condition and the memory mode. All comparisons that support RQ1–RQ3 are therefore paired on task, harness and model.

The harnesses handle Skills in the same broad way, which follows the open Agent Skills format [1, 2]. A Skill is a directory containing a SKILL.md file whose header gives the Skill’s name and a short description. When a session starts, the harness scans its Skill directories and places only these names and descriptions in the model’s context. The model itself decides, from the descriptions, whether a Skill applies to the task at hand; only then is the body of that Skill loaded, and any scripts or reference files it bundles are read as they are needed [4, 25, 27]. Selection is thus made by the model, but on terms set by the harness: which directories are scanned, how the descriptions are presented, and how many fit in the context. Memory follows a common pattern as well. Each harness reads persistent instruction files from the project and from the user’s configuration ( CLAUDE.md in Claude Code, AGENTS.md in Codex and OpenCode) into the context at the start of every session, and Claude Code in addition keeps notes that the agent writes for itself and reloads in later sessions [3, 24, 26]. Rather than pairing each harness with its vendor’s model, every harness is driven by the same pool of models. The pool has two groups: the state-of-the-art proprietary models of the three major international providers (Anthropic, Google with its Gemini family, and OpenAI), and the state-of-the-art open-weight models released by Chinese providers. From each international provider we take its two most capable generally available models, and from each Chinese provider its single most capable open-weight model. The pool is not fixed: as new state-of-the-art models are released they are added to it and run under the same protocol, so n changes with successive versions of the benchmark, and each version of the results states the pool it was run on. Results are reported per harness–model pair. Comparisons between harnesses are made only at a fixed model, and comparisons between models only at a fixed harness, so that a model difference is never read as a harness difference or the reverse. 52.3 Skill conditions 

Each task is run under three Skill conditions inside each configuration. 

∅ — No Skill. No Skill is installed. The agent completes the task with the harness’s default capabilities and the task’s toolset. This is the baseline. S — Curated Skill. The Skills most relevant to the task, selected by a person, are made available. This isolates the value of Skill content when the selection problem has been solved for the agent. A — Automatic invocation. The agent runs with a Skill library installed, as it would in production, and the harness’s own mechanism decides which Skills, if any, are retrieved and invoked. This adds the cost of discovery and the risk of selecting a wrong or irrelevant Skill. The difference between S and ∅ bounds what Skills can contribute; the difference between A and S is what is lost to discovery. In all three conditions the task prompt is identical and does not name any Skill. Skills are held to the same leakage rule as in prior work [19]: a Skill must serve a class of problems. It may not contain the output of a particular task, task-specific paths or constants, or commands that solve one instance directly. Reference solutions, golden values and verifier code are never visible to the agent. 

What is disclosed about Skills. Several of the Skills evaluated here were contributed by collaborators and remain their property. This paper therefore describes the benchmark tasks in full and each Skill only by its purpose : the class of problems it serves. The text of a Skill, its instructions, scripts, templates and reference material are not reproduced. Section 3 gives that purpose for each contributed Skill. 

2.4 Memory modes 

Every Skill condition is run under two memory modes. M0 — Memory off. Each run starts as a new agent: a new session, a new working directory and a new memory namespace. M1 — Memory on. The agent may use memory of successful task completions accumulated under the same experimental definition. Headline results use M0. M1 is reported separately, as a contrast that quantifies what memory itself contributes and how it interacts with Skills (RQ3). We make M0 the default because it is the only mode in which the three repeats of a cell are exchangeable and in which an improvement can be attributed to the Skill condition alone. 

Isolation procedure. To make “memory off” true in practice, each M0 run is launched under the following rules. 1. A new temporary workspace is created for the run. 2. The session is never resumed from, or continued into, another session. 3. History directories, cache directories and memory namespaces are not shared between runs. 4. General memory is disabled or, where a harness cannot disable it, the run is given a fresh namespace. 5. After the run, only artifacts, logs and metrics are collected. Nothing a run produced is written back into the context of a later run. 6API credentials may be reused. What may not be reused is session history, working-directory state, the memory namespace, and any project memory that the harness loads automatically. 

2.5 Task suite 

The tasks are contributed by domain experts among the authors, each together with the Skill that expert uses for it. Section 3 introduces the tasks and Skills; this subsection states the rules that every task follows, whatever its domain. 

Verifier families. Across the suite, verifiers take one of three forms, and a task may combine them. Reference-value verifiers compare quantities extracted from the agent’s output with values from a reference solution, within a tolerance stated in the task. Withheld-label verifiers score a frozen prediction against outcomes the agent never saw, using a metric fixed before the run. 

Artifact and behaviour verifiers check that the required files exist and are well formed, and that the agent’s report makes the claims the evidence supports and no others, including declining to conclude when the evidence is insufficient. All three are deterministic: no verifier relies on a language model’s judgement. A verifier need not return a bare pass or fail. Where the result of a task is a continuous quantity, its verifier returns a graded score (Section 2.9). 

Leakage. Tasks built on published data carry the risk that an agent with network access retrieves the answer instead of producing it. For such tasks the outcomes are separated from the inputs before the run and the agent’s runtime excludes the outcome files. Network access is restricted as well. By default a run has no access to the open internet: the sandbox allows outbound connections only to the model’s API. A task may declare the external services its work requires, such as a crystal-structure database, and only those are opened, for every harness and condition alike. The publication a task is drawn from, and the repositories that hold its data, are never among them. Every network request a run makes is recorded in its trajectory; a run that attempts to reach a blocked source is flagged and reported, and its result is not counted. 

Task package. A task consists of (i) a prompt, written by a person, that states the goal and the artifacts to leave behind; (ii) the input assets the agent receives; (iii) a declared toolset with pinned versions; (iv) a reference solution that the verifier must accept; (v) golden values derived from the reference solution; and (vi) a deterministic verifier. Items (iv)–(vi) are never shown to the agent. Task inputs, tool versions, data sources and verifier rules are versioned, and their cryptographic hashes are recorded with every result so that a score can be traced to the exact inputs that produced it and so that inputs cannot drift between runs. 

Toolsets belong to tasks, not harnesses. Each task declares the tools it permits and their versions. Every harness is mapped onto that same set of equivalent tool entry points, and a tool that only one harness offers is not enabled. Without this rule a harness with a richer built-in toolset would appear to benefit less from Skills simply because it needed them less.

2.7 Controlled variables 

Within a configuration, the following are held fixed across Skill conditions, memory modes and repeats: the model name and version; the sampling parameters (temperature, top-p and seed, set to 0, 1 and a fixed seed wherever the provider exposes them); the limit on output tokens; the toolset and tool versions; the input assets, datasets, task prompt and verifier; the layout of working, cache and memory directories; and the order in which tasks are run. Every run starts from a freshly reset sandbox. Budgets on agent rounds, wall-clock time and tokens are identical across conditions. The harness version, toolset version and task-input version are recorded as hashes in each run’s configuration record. 

2.8 Run protocol 

Every (task, harness, model, Skill condition, memory mode) cell is run three times. For each model the full matrix is 4 harnesses × 3 Skill conditions × 2 memory modes × 4 tasks × 3 repeats = 288 runs ,

of which the 144 runs under M0 form the headline results. The whole experiment is n times this. With the current pool of n = 11 models that is 11 × 288 = 3168 runs, of which 1584 are under M0. 8Infrastructure failures. A run ends in one of three ways. If the verifier accepts or rejects the result, the run is scored. If the run is interrupted by something outside the agent’s control— an API timeout, a network fault, a refused software licence or a crashed runner—it is an infrastructure failure. Such runs are re-run or flagged; they are never charged to the model. If infrastructure failures recur for a cell, the cell is reported as not comparable. 

2.9 Metrics 

Per-run outcome. Let yir denote the verifier’s outcome for task i ∈ { 1, . . . , N }, N = 4, on repeat r ∈ { 1, . . . , R }, R = 3, within one cell of the design. We take yir ∈ [0 , 1] to be the score assigned by the task’s deterministic verifier, and report alongside it the binary outcome 

bir = ⊮[yir ≥ τi], where τi is the pass threshold of task i: a run passes if its score reaches the threshold and fails otherwise. A graded outcome is compatible with everything that follows, none of which requires yir to be integral, and it reduces the variance that makes three repeats uncomfortable: a nearly-correct run contributes 0 .7 rather than swinging between 0 and 1. 

Task-specific criteria, one common scale. The tasks do not share a notion of quality, and we do not force one on them. What makes a diffusion fit good (small residuals between the fitted and the measured profile, an interval that covers the true value) is not what makes a phase identification or a ranking good. Each task therefore brings its own criteria, chosen by the expert who contributed it, and the outcome of a run is in general continuous and not a bare pass or fail. The only requirement the benchmark imposes is that a task’s verifier maps its criteria onto a score in [0 , 1] by a rule fixed before any run, where 1 means that every criterion is met in full. All scores then live on one scale, and the aggregation, gains and intervals below apply to every task unchanged. Section 3 states the criteria of each task. Each task also has a pass threshold τi ∈ (0 , 1] on that score, set by its contributor at the level below which a practitioner would not accept the result, and fixed, like the mapping, before any run. The continuous score is the primary outcome and is what the gains below are computed from; the threshold turns it into the pass or fail that the reliability measures need.

3.1 Materials science 

3.1.1 SIMS data analysis: oxygen tracer diffusion from isotope exchange Why it matters. Secondary-ion mass spectrometry (SIMS) answers two questions about an element inside a solid: how much of it is there, and where it sits. In semiconductor manufacturing those are the questions asked of every dopant, since a chip works only if the right amount of the right element has gone to the right depth, and SIMS depth profiling is how that is checked. The same measurement serves materials research more broadly. In the task here it follows an oxygen isotope into an oxide, which gives the rate at which oxygen moves through the material and across its surface: the tracer diffusion coefficient D∗ and the surface exchange coefficient k∗. In both settings the raw data are easy to collect and easy to misread. 

The task. The agent receives the raw 16 O and 18 O data from an isotope-exchange experiment, as a line scan or a depth profile, together with the acquisition metadata and the fitting software a researcher would use. It is asked for D∗ and k∗, and for an account of how far those values can be trusted: whether the data are sound, whether the surface has been placed correctly, and whether the fit describes the measurement. What makes the task hard is that a fit can converge and still be wrong. Producing two numbers is straightforward; knowing when not to believe them is the skill being tested. 

The Skill. The Skill supports the analysis of SIMS data. It is designed for researchers who need to know how much of an element is in a material and how it is distributed, whether that is a dopant in a chip material or an isotope tracer in an oxide. It helps them turn raw line scans and depth profiles into quantities they can defend, by checking the quality of the data, reviewing the fit, and judging how far the result can be trusted. 11 Verification. The result of this task is continuous, and so is its assessment. The fitted curve and the measured profile are both one-dimensional, so the first criterion is the residual at every point of the profile: an array with one entry per depth, which shows not only how large the misfit is but where it lies. The second summarises that array in one number, the root-mean-square (RMS) of the residuals, taken after each residual is divided by the uncertainty of its data point so that a value near one means the fit agrees with the data to within their noise. The third concerns the reported uncertainty: the agent must give a 95% confidence interval for D∗ and for 

k∗, and on data whose ground truth is known the verifier checks both how close the fitted values are to the reference values and whether the intervals contain them. An agent that reports a tight interval around a wrong value is penalised for it. The fourth looks at the two parameters together. D∗ and k∗ are fitted jointly and their errors are correlated, so separate intervals can mislead. The verifier therefore also considers the joint 95% confidence region of the pair, and the misfit evaluated over the plane of (log D∗, log k∗) around the optimum: a compact minimum means the data determine both parameters, while a long valley means they determine only a combination of the two, and an agent that claims both values with confidence in the second case is wrong even if its fit is good. A later version may add a map of the residual at each point of the profile across the same parameter plane. These criteria are combined into the task’s score in [0 , 1] (Section 2.9). In addition, parsing and unit handling are checked deterministically, and the agent’s diagnostic findings are compared with annotated cases; reporting that the evidence is insufficient is, where true, the correct answer. 

3.1.2 XRD refinement: phase identification and unit-cell parameters Why it matters. X-ray diffraction reveals the crystal structure of a material: which phases are present, and the dimensions of their unit cells. It is how a researcher finds out whether what was made is what was intended. In semiconductor manufacturing and thin-film growth the question is whether a grown film has the expected structure; after a synthesis in the laboratory it is simply what was made. Phase identification and cell refinement are among the most frequently performed analyses in materials science, and much routine time goes into them. 

The task. The agent receives a powder diffraction pattern and the elements known to be in the sample, with access to a crystal-structure database [14] and to GSAS-II [33]. It is asked to identify the crystalline phase and to report its refined unit-cell parameters from a Le Bail fit [18], with fit statistics and a refinement figure. The difficulty lies in judgement as much as in computation: several candidate structures may fit a pattern about equally well, and a numerically good fit does not by itself establish the right structure. 

The Skills. Two Skills accompany this task, one for each stage, and together they support the analysis of a material’s crystal structure. The first is designed for researchers who hold a diffraction pattern and know which elements went into the sample. It helps them decide which phases the measurement actually supports, for example whether a grown film is the phase that was intended. The second takes over once the phase is known. It is designed for researchers who need unit-cell parameters precise enough to report, and it helps them carry the refinement through to a result and judge whether the fit is good enough to stand behind.

3.2 Biology 

3.2.1 Regulatory target prioritisation Why it matters. Most of the genetic variation associated with disease lies outside genes, in the regulatory elements that control when and where genes are switched on. Working out which elements regulate which gene, in which cell type, is an early and expensive step in deciding what to test as a drug target. The evidence is scattered across perturbation experiments and predictive models, it is incomplete, and each experiment that would fill a gap costs weeks. Choosing the next experiment well is where the time is won or lost. 

The task. The agent receives a table of candidate enhancer–gene pairs in one cell context, with published predictive scores, drawn from a public CRISPR perturbation study [13]. The experimental outcomes are withheld. It is asked to rank the candidate regulatory links for each gene, to summarise the evidence and state plainly what is missing, and to propose the follow-up experiment that would be most informative. 

The Skill. The Skill supports early-stage drug target discovery. It is designed for research teams that have identified a candidate gene and want to understand how it may be regulated in a particular cell type. The Skill helps teams assess the evidence for potential regulatory relationships, identify gaps in that evidence, and prioritise directions for experimental follow-up. 

Verification. The agent’s ranking is frozen and scored against the withheld outcomes by average precision, reported together with its coverage. Predictions must cover exactly the records supplied, and the agent runs without access to the outcome files. 

3.2.2 Spheroid imaging: structure and cell distribution in three dimensions Why it matters. A spheroid is a ball of cells grown in three dimensions, a few hundred micrometres across. Unlike cells on a flat dish, the cells of a spheroid sit at different depths and receive different amounts of oxygen, nutrients and drug, as they do in a tumour, which is why spheroids are widely used as tumour models and in drug screening. What a spheroid tells the researcher is therefore spatial: how large it is, what shape it has, and where its cells are, from the rim to the core. Microscopes now produce such image stacks by the plate, far faster than they can be analysed by hand. The analysis is also easy to get wrong, because light is lost on its way into dense tissue: the centre of a spheroid looks dark whether or not cells are there. 13 The task. The agent receives a three-dimensional fluorescence microscopy image stack of a spheroid, for example from a confocal or light-sheet microscope, together with what is known about its acquisition: the order of its axes, the voxel spacing in physical units, and which channel shows the nuclei. It is first asked to say which analyses the image supports. For those that it does, it is asked for the envelope of the spheroid, as a three-dimensional mask and a surface with volume and surface area; for the positions of the nuclear centres; for the density of nuclei as a function of distance from the centre and of depth below the surface; and for the distances between neighbouring nuclei. It must also provide images in which each result can be checked against the original data. The difficulty is that every one of these quantities can be computed from any image, good or bad. A stack without calibrated spacing gives no volume in physical units, and a two-dimensional picture gives no volume at all. A count of detected nuclei is not a count of cells. A low density in the core may be biology or may be an imaging artifact, and nuclei that lie close together are not thereby cells in contact. The agent has to tell the reader which claims the data support, and declining an analysis that the image cannot support is a correct answer. 

The Skill. The Skill analyses microscopy images of spheroids to measure spheroid structure and cell distribution. It is designed for researchers who image spheroids in quantity and need numbers they can compare across wells and conditions. It helps them check that an image stack is fit for analysis, delineate the spheroid and reconstruct its envelope and surface in three dimensions, locate the nuclei, and describe how the cells are arranged, both radially and relative to their neighbours. Its results are offered as candidates for the researcher to review, with each stage of the analysis left open to inspection, and it keeps apart what was measured from what would need independent confirmation. 

Verification. The envelope is compared with a manually drawn reference by its overlap, the distance between the two surfaces and the relative error in volume. Nuclear centres are matched one to one with manually annotated centres within a fixed physical distance; where only part of a stack is annotated, only that part is marked. The radial and neighbourhood tables are compared with the same quantities computed from the reference. The required artifacts must be present, and a run fails outright if it reports a three-dimensional measurement from an image that cannot support one, or states a detected count as a cell count. The reference annotations are kept where the agent cannot read them. 

3.3 What the tasks have in common 

The tasks come from different fields, but they make the same demands. Each depends on specialised software or data that a general-purpose coding environment does not provide. Each rests on procedure that is written down in the specialist literature and passed on in laboratories, but is thinly represented in what a model already knows. And in each, the hard part is not producing an answer but knowing how far to trust it: recognising a fit that converged for the wrong reason, a candidate that matches by coincidence, a measurement that reflects the imaging more than the sample, or evidence too thin to support a conclusion. This is the kind of knowledge a Skill is meant to carry, which is why these tasks are a demanding test of whether Skills help.
