## Abstract 

Multimodal agents can now control robot arms by calling tools and writing code. Existing benchmarks fall short in three ways: most test one or two arms on short tasks, many pause the world while the agent thinks, and many give it ground-truth object positions. We present RoboTeam , a simulated benchmark where agents control 4 to 16 robot arms in real time from camera images alone. Its 36 tasks are long jobs that the arms must do together, such as pass-ing timbers or building a picture from hundreds of cubes. We start from the most flexible agent system, the adaptive system, where one agent decides when to fork delegates. With it, gpt-6.1-sol and opus-5.5 complete 28 and 27 tasks, and four other models at most 3. But at a high price: a typ-ical task takes gpt-6.1-sol 3.5 hours and 218 million input tokens, and a third of its steps fail at least once and must be retried. We then compare it with three fixed systems: single-agent, hierarchical, and decentralized. All four complete a similar number of tasks but differ in time and tokens. The hierarchical and decentralized systems are faster but use up to 1.9 times the tokens, and the single agent uses fewer tokens but takes 1.6 times as long, so the adaptive system lies between them. Even so, no model or system is yet fast, cheap, and reliable at once . RoboTeam measures these lim-its where earlier benchmarks cannot: long multi-arm jobs, camera images only, and a world that never pauses.

## 1. Introduction 

In the Spider-Man stories, Doctor Octopus controls four ex-tra arms as easily as his own hands. Real robots are far from this, but multimodal agents are getting closer: frontier mod-els can increasingly control robots through tools and gener-ated code [7, 11, 16, 24, 25, 39, 42, 46]. Vision-language-action (VLA) policies [2, 19, 54] typically map camera im-ages directly to robot actions. Agents can do more: they reason about a task [47], write tools [41], recover from fail-ure [26], and communicate [49]. Existing benchmarks capture these strengths only in part, and they fall short in three ways (Tab. 1). First, most test one or two arms on short tasks, whether the con-troller is a trained policy [17, 28, 33] or a language-model agent [15, 45, 46]. Multi-robot studies compare agent systems but simplify the physical task [4, 6, 37]. Sec-ond, many simulated benchmarks pause the world while an agent thinks [32, 46], which a real robot cannot do. Third, many give agents the ground-truth positions of ob-jects [6, 11, 27, 37], which a real robot must estimate from its sensors. We therefore still do not know how far agents are from controlling many arms at once, or which agent sys-tem suits them. To study this question, we present RoboTeam, a simu-lated benchmark where agents control 4 to 16 arms in real time from camera images alone (Fig. 1). Agents move the arms through one robot tool with simple commands, and a sandbox keeps them away from the simulator and the evaluator, which pre-vents cheating [12, 40, 52]. ## 2. Related work 

Agents for robot control. Frontier agents now control robots through software agent frameworks [39], generated code [11], and simple action interfaces [7, 24]. Robot-World [46], RoboColiseum [15], and EmbodiedBench [45] evaluate such agents broadly, but one model makes the de-cisions and controls at most two arms. The concurrent Em-bodied First Exam [42] also has a setting where the world keeps running, but one coding agent handles each task. 

VLA and other policy benchmarks. VLA policies are usually trained from demonstrations [2, 19, 54] and react many times per second, so their benchmarks focus on skills of hundreds of control steps [28, 33, 50]. These bench-marks do not ask a model to divide work, talk to team-mates, or write tools, so RoboTeam complements them. ReflexBench [8] also keeps its world moving, but it tests whether a fast policy reacts in time. RoboTeam tests the op-posite case, whether slow, deliberate agents can still finish long tasks in a moving world. Overview camera

Software studies compare communica-tion structures [53] and create sub-agents on demand [31, 35]. RoboTeam tests these ideas with agents that see only through cameras and must share arms while the world keeps moving. To our knowledge, RoboTeam is the first benchmark where multiple agents control many arms while the world keeps running as they think. 

## 3. The RoboTeam benchmark 

3.1. Tasks

Mosaic. As in robotic bricklaying [9, 14, 22], the arms build a reference picture from colored cubes, with one cube in each cell. The cells are pockets (Level 1), printed lines (Level 2), or unmarked (Level 3).

Second, tasks must be hard but feasible: every action is physically possible for the Franka Emika Panda arm and its parallel gripper [48]. 

3.2. Environment 

Three choices define the environment: real time, what agents perceive, and how they act. The first choice is real time: the world advances with the clock and never waits for an agent. A real robot would not wait for a model, and pausing for one agent would also stop its teammates. The world is simulated in MuJoCo [38] with a 2 ms physics step. The second choice is what agents perceive. Some bench-marks give agents ground-truth object positions [6, 27, 37] or offer them as a separate setting [11], and agents do well with this access [39]. A real robot must estimate positions from its sensors, so our agents get only two kinds of live data. The first is RGB images from fixed cameras, which agents request by name and which each camera renders at 

1280 × 800 pixels (Fig. 4). MuJoCo’s OpenGL renderer draws an image in about 30 ms on a laptop GPU, in a sep-arate process, so looking does not slow the world. A task has 14 to 69 cameras: two at every arm, four overviews of the scene, and close-ups of the task objects. The task file also gives the position and the field of view of every cam-era, so agents can relate several views. The second is the state of the arms, such as the pose and width of each grip-per. Agents never receive object positions, depth, or contact information. The third choice is how agents act. Earlier interfaces have two problems. When agent code drives the simulator directly [11, 39], it can also read hidden state. When agents call fixed high-level skills [4, 11], the skills hide low-level failures. We instead give every model one robot tool, and arms move only through it. Its commands are simple: move an arm to a pose, or open, close, or grasp with a gripper. This keeps agents away from the simulator and makes every failed motion or grasp visible. Unless a condition removes them, agents also have code tools: a shell, file editing, and their own Python code (Fig. 1). They use these tools, for ex-ample, to measure object positions in an image. 3.3. Agent systems 

We compare four agent systems (Fig. 1). The adaptive sys-tem is the most flexible, because the agents decide during a task how to divide the work. It starts as one controller that holds every arm. When work can be shared, the controller forks itself into delegates and hands them arms. When a delegate finishes its job, it returns its arms and ends. Two rules make this work in real time. A delegate is a fork of the controller. Unlike sub-agents with curated or separate con-text [13, 35], it starts with the controller’s full history and does not have to relearn the task while the arms wait. Each arm belongs to one agent at a time, so two agents never command the same arm. The other three systems keep a fixed structure during a task. In the single-agent system, one agent controls every arm. Following earlier work [6, 20], the hierarchical system has one worker per arm under a controller. The decentralized system has the same workers without a controller, so they coordinate directly. In every system, agents can also write lessons to one shared skill file [36, 41, 51], which starts empty in every run. 

3.4. Metrics 

RoboTeam does not end a task at its first failed step, as scor-ing a single attempt would. Agents may retry, so a task that ends correctly can still contain many failures. We therefore report whether a task was completed, how often its steps and grasps failed on the way, and what the run cost in time and input tokens. 

Completion. A task is completed when its final state is correct, for example when every Mosaic cube rests on its cell. We also count the tasks completed within 3, 6, 12, and 24 hours, which shows how fast a condition works. A 3-hour budget is a cheaper measure, since a task not done by then is already a weak result. 

Atomic failure rate. An atomic step is the smallest unit of progress. In Mosaic it is one cube placed on its cell. In Transport it is one item delivered to its target or handed to another arm. In Relay it is one arm taking hold of a timber in a handover. In Dial it is one knob turned to a new position. A step fails if any attempt at it goes wrong, for example when an object is dropped. We find these failures after a run in the records of the robot tool and the simulator, not in the agents’ reports. A step still counts as failed even if it is completed later. The atomic failure rate of a run is the share of its steps that fail at least once, and we report its median over the 36 tasks. 

Grasp failure rate. A grasp fails when the gripper closes on a width that does not match the object. The grasp failure rate of a condition is the share of all its grasps that fail. 

## 4. Experiments 

4.1. Setup 

We test six models: gpt-6.1-sol, opus-5.5, kimi-k3.1-pro, qwen3.8-flash, deepseek-v4.1-flash, and glm-5.3-flash. All use high reasoning effort and a 300,000-token context window. Agents run in a coding-agent harness, either Codex [30] or Claude Code [1]. Our runtime connects the harness to the world and records every call. In both har-nesses, agents get the same robot tool, instructions, camera images, and sandbox. Unless a condition changes them, agents run gpt-6.1-sol in Codex with code tools. In all, there are 14 conditions in four groups and a reference (Fig. 2), and each runs the 36 tasks once. The first group runs the four agent systems of Sec. 3.3, and all other conditions except the Oracle use the most flexible of them, the adaptive system. The second changes what the agent perceives or may use: robot tool only removes the code tools, and low resolution reduces ev-ery camera image to 128 × 80 pixels (Fig. 4). gpt-6.1-sol and opus-5.5 run in their providers’ harnesses, Codex and Claude Code, and the other four models in Codex. To test the harness, we swap the two: the third group runs gpt-6.1-sol and opus-5.5 in Claude Code, and the fourth runs the other models, opus-5.5 among them, in Codex. The Oracle uses the single-agent system and receives the ground-truth position of every object instead of camera im-ages (Tab. S3). 4.2. Main results 

The best models complete most tasks, and the other four almost none. Figure 2 shows how many tasks each of the 14 conditions completes. gpt-6.1-sol completes 27 to 29 of the 36 tasks under the four agent systems, and opus-5.5 completes 27 in Claude Code and 26 in Codex. The other four models complete at most 3 tasks and no Level 3 task. The Oracle completes all 36, so every task is feasible. This gap between models is not a matter of budget (Fig. 6). deepseek-v4.1-flash uses 25.0 billion input tokens and 316 hours. This is close to the 27.0 billion tokens and 258 hours of gpt-6.1-sol, but it completes one task. For the adaptive system, team size makes tasks harder than level does (Fig. 7). By level, it completes 9, 9, and 10 of the 12 tasks. By team size, it completes 11, 10, and 7 on small, medium, and large teams. The levels matter much more once the agent sees less or computes less (Sec. 4.5). 

Repeated runs. Two more runs of the adaptive system on the 12 Level 3 tasks complete 8 and 9 of them, against 10 in the first run, and no task fails in all three (Sec. B). A second run can thus differ by one or two tasks, so we read only larger differences as real.

With the robot tool only, the agent sees the same images but loses computation, scripted control, and its working files, so this condition shows what code tools contribute as a whole. With low resolution, it keeps its code tools but sees every image at 128 × 80 pixels (Fig. 4). The two losses look alike: both conditions com-plete no Mosaic task, and both fall as the level rises. At Level 3 each completes 2 of the 12 tasks, against 10 with both (Fig. 7a). Their grasps also fail more often, 31% and 41% of the time against 23% (Fig. 5b). Both are needed for one reason. An agent can act on an object only if it knows the object’s position to within millimeters, and it gets this position by measuring images. In 31 of its 36 adaptive runs, gpt-6.1-sol writes code for this. One script, for example, finds an object by its color in two views and triangulates its 3D position. 4.6. Models and harness 

The two best models work in different ways, and each keeps its way of working in both harnesses. With the adaptive system, gpt-6.1-sol completes 28 tasks in Codex and opus-5.5 completes 27 in Claude Code, and each com-pletes some that the other does not. gpt-6.1-sol divides the work, and its controller delegates 13 times in the median task. opus-5.5 rarely delegates, and in 20 of the 36 tasks it never does. Instead, it thinks less and computes more. It spends 35% of agent time thinking and 19% in code tools, against 58% and 5% for gpt-6.1-sol (Fig. 5a). Working mostly as one agent, it needs 176 hours for the 36 tasks, less than half the time of the single agent of gpt-6.1-sol. The me-dian atomic failure rates of the two models are almost the same, at 34% and 33% (Fig. 5b). Both models keep their way of working in the other har-ness. The median task of gpt-6.1-sol has 184 messages in Codex and 115 in Claude Code, and that of opus-5.5 has none in either. opus-5.5 spends 35% and 40% of agent time thinking, against 58% and 57% for gpt-6.1-sol (Fig. 5a). In Codex, opus-5.5 drives all 12 arms of a Transport task it-self, noting that neighboring arms share handover positions. The four combinations complete 25 to 28 tasks, and of the reliability measures only the grasp failure rate follows the harness: opus-5.5 fails 13% of its grasps in Claude Code and 23% in Codex (Fig. 5b). The other four models fail at basic manipulation. Their median atomic failure rate is 79–90%, and 59–94% of their grasps fail (Fig. 5b). They spend the largest share of their time thinking, 63–77%. Repeated failure rarely changes their behavior, however, and one deepseek-v4.1-flash arm failed 51 grasps in a row. Figure 11 gives two examples. In Mosaic, deepseek-v4.1-flash leaves a dropped cube leaning on its neighbors, and in Relay, kimi-k3.1-pro lifts a timber with one arm and drops it. 

## 5. Conclusion 

In simulation, RoboTeam shows that the best agents can complete hours-long work across many robot arms, but only at a high price. With the adaptive system, gpt-6.1-sol and opus-5.5 complete 28 and 27 of the 36 tasks, while the other four models still fail at basic manipulation. Even the best model needs hours and hundreds of millions of tokens per task, and it retries a third of its steps. Fixed agent systems do not remove this price: they trade time for tokens with no detectable difference in completion, and the adaptive sys-tem lies between them. What holds the agents back is re-covering accurate positions from images: with ground-truth positions every task is completed, and without sharp images or code tools only about half as many are. Our cross-harness runs suggest that how a model divides its work depends on the model more than on the harness. No model or agent system is yet fast, cheap, and reliable at once, and making them so is the next challenge. 

Limitations. Our results come from simulation, and transfer to real robots is future work. The 36 tasks are variants of only four task types. Because one condition takes billions of tokens, each ran once apart from the repeats of Sec. 4.2, so differences such as 28 versus 29 tasks are not reliable. ## A. The 36 tasks 

Figure S1 shows each of the 36 tasks at its start. The label on a picture gives the number of arms and the amount of work, such as the number of cubes. In Dial, Level 1 uses one arm per dial. Levels 2 and 3 use two arms per dial, because one arm must hold the module while another turns its knob. The task file tells the agents when a task counts as com-pleted. The rules differ by task type. 

Transport. Every item must stand upright in its target. An item carries its label on its top face and on two opposite side faces, so that cameras above and beside it can read it. The top face must face up, with a tilt of at most 5 degrees. The item must sit at the right height, within 1.5 mm, and it must be released and at rest. At Level 1, the whole item must also lie inside the 70 mm square of its target. 

Mosaic. At Level 1, every cube must sit flat inside its pocket. At Levels 2 and 3, the center of every cube must lie within 6 mm of the center of its cell. The cubes must be at rest. 

Relay. At least 70% of every timber must lie in the goal region, and every arm must have released it. On the way, a timber must stay clear of the table and the floor, so every handover between arms happens in the air. When a timber is dropped, the arms must pick it up again. 

Dial. All dials must be within 4 degrees of their correct positions at the same time.

## E. What an agent starts with 

Every agent starts with the same written material. It gets the rules of the benchmark, which say what it may read and use and how a run ends. It gets a short instruction for its role, such as controller, worker, or delegate. It gets a gen-eral guide to working with the arms and with other agents, together with the reference of the robot tool. It gets a guide for the task type, for example on placing and releasing cubes in Mosaic. It also gets the public task file. None of this ma-terial holds object positions. 

The skill file. The skill file is separate from these guides. It starts empty in every run, and only the agents write to it. The general guide asks for one format (Fig. S4). The heading of an entry states its conclusion, so that a reader can tell from the heading alone whether the entry matters. The body gives the content, the conditions under which it holds, the evidence, and the confidence. An agent never changes an earlier entry. It adds a revision below it and says what the revision changes. The second box of Fig. S4 shows one entry as an agent wrote it.

## F. The robot tool 

Agents act through one tool with a small set of operations (Tab. S8). Every motion command must state its speed and acceleration, and the tool accepts only values within the limits of the real Franka Panda. A command returns whether it completed or failed, with the reason. With the robot tool only, agents have no file tools. Two further operations then let them read the task material and read and extend the skill file. 

## G. Cameras 

Table S9 gives the number of cameras in a task. Each arm has one camera in front of it and one at its side. Three of the four overview cameras look across the scene, and one looks down from above. The other cameras are close-ups of the task objects, such as the target boards in Transport or the dials in Dial. An agent asks for images by naming cameras, and it may name several at once. 

## H. Aligning Codex and Claude Code 

In both harnesses, a delegate of the adaptive system is a fork of the controller’s session. Its history ends at the controller’s delegate call, and its first input is the delegate message. The two harnesses differ in how they create this fork. Codex keeps one app-server process alive, which serves the robot tool and forks a session on request. Claude Code re-ceives the robot tool as an MCP server. It creates a fork by resuming the parent session under a new session, so a fork exists only once its first turn runs. A gate holds the fork’s tool calls until the runtime has checked its copied history. When a model runs in the harness of the other provider, gpt-6.1-sol in Claude Code or opus-5.5 in Codex, a connec-tor passes the model calls of the harness to the model’s API. The cross-harness runs test whether the harness explains the differences between the two best models (Sec. 4.6). 

## I. Scope and cost of the experiments 

One model carries the comparisons. The experiments aim to learn how agents control many arms, not to rank models, so most runs use one model. gpt-6.1-sol runs eight of the 14 conditions (288 runs of up to 24 hours, plus 24 repeated runs at Level 3), and every comparison of agent systems, tools, and image resolutions is made within it. 

One run per condition. A full condition takes hundreds of hours and billions of tokens, so each ran once apart from the Level 3 repeats of Sec. B, and we draw conclusions only from large differences. 

Cost. The 14 conditions used 302 billion input tokens and about 3,060 hours of runs in total (Tab. S3), not count-ing the repeated runs. The eight conditions of gpt-6.1-sol used 226 billion of these tokens. 

Four task types. We kept the set small because today’s models need hours and billions of tokens for it, but new variants can be added in the scene files without changing the task logic. As models improve, the same tasks can measure how cheaply they are completed, not only whether they are.
