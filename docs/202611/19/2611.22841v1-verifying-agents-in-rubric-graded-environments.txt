# Verifying Agents in Rubric-Graded Environments 

Markus Dücker 1, Vaibhav Kumar 1, Yi Liu 1, Ronak Chaudhary 1, Andreas Plesner 1,2 ,Francisco Guzmán 1 and Anish Athalye 1

> 1

Handshake AI Research, 2ETH Zürich 

As AI agents take on increasingly open-ended and complex tasks, verifying their outputs has proven to be difficult. Rubric-graded agent environments, where a verifier judges multiple natural-language criteria against the deliverables and environment state changes produced by the agent, have emerged as a popular paradigm. We conduct the first systematic study of verifiers for rubric-graded agent environments. First, we create BankerVerifierBench (BVB), a meta-evaluation dataset of 2,464 human-judged rubric criteria across 24 investment-banking tasks. Next, we develop a methodology that derives from any rubric corpus the capabilities a verifier should possess, yielding a nine-capability taxonomy that we distill into three general design principles—reactive verification, environment alignment, and domain guidance—which we implement in Gandalf, an open-source verifier. Finally, we evaluate Gandalf against three existing verifiers on BVB. Gandalf matches or exceeds every baseline’s F1 at lower cost: with Gemini 3 Flash it matches the strongest baseline’s F1 (0.864 vs. 0.852) at one-fifth of its cost, and with GPT-5.4 models it improves F1 by over 0.12 at lower cost. Gandalf also generalizes to OpenClaw, a structurally different personal-productivity environment, where it again achieves the highest F1 (0.955 vs. 0.934 for the best baseline). We release BVB, Gandalf, and the code and data to reproduce our experiments. 

# 1. Introduction 

Modern AI agents are systems that use large language models (LLMs) to interact with tools and environments in pursuit of a goal (Gao et al., 2023; Schick et al., 2023; Yao et al., 2023). As these agents have grown increasingly capable and reliable, so has the need to measure and optimize their performance. Measurement and optimization go hand-in-hand: agents are evaluated within environments , and these same environments can be used for reinforcement learning (RL) to train improved models (Luo et al., 2025). While some agentic benchmarks such as GDPval (Patwardhan et al., 2026) are human-graded using pairwise preferences, enabling comparison between agents on leaderboards, the vast majority strive for automated pointwise grading, facilitating both benchmarking and reinforcement learning by using the grade as the reward signal. Both uses depend on a verifier whose grades can be trusted. Early efforts, encouraged by the success of reinforcement learning with verifiable re-wards (RLVR) (Shao et al., 2024; Guo et al., 2025), focused on verifiable domains where deterministic automated verification is possible. For example, SWE-bench (Jimenez et al., 2024) uses unit tests to verify software engineering, HotpotQA (Yang et al., 2018) uses exact-match scoring for multi-hop question-answering, and WebArena (Zhou et al., 2024) uses programmatic checks for browser use. Such environments trade off verifiability against scope, open-endedness, and realism. Recently, agent evaluation has expanded into semi-verifiable domains where judgment is required. Benchmarks such as BankerToolBench (Lau et al., 2026), APEX-Agents (Vidgen et al., arXiv:2611.22841v1 [cs.AI] 17 Nov 2026 Verifying Agents in Rubric-Graded Environments 

2026), CoreCraft (Mehta et al., 2026), and ClawBench (Zhang et al., 2026b) use natural-language rubrics —fine-grained binary criteria that are objectively gradable—as a technique to define and capture correctness (Viswanathan et al., 2025; He et al., 2025; Gunjal et al., 2026). Verifying agent rollouts in such environments is a challenging task in its own right. Agents may produce multi-file deliverables (e.g., an Excel spreadsheet and a PowerPoint presentation) and invoke tools with side effects (e.g., sending an email). Verification requires checking diverse properties such as whether an email was sent, whether an Excel model’s formulas propagate correctly across tabs, and whether a PowerPoint’s charts are internally consistent with the underlying data. Verifiers for rubric-graded environments span a broad design space, ranging from using an LLM-as-a-judge on the trajectory (Mehta et al., 2026) to making the verifier itself agentic: an 

agent-as-a-judge (Zhuge et al., 2025; You et al., 2026). Agentic judges themselves range from workflows (e.g., Archipelago (Vidgen et al., 2026)) to fully reactive agents (Yao et al., 2023) (e.g., ClawBench (Zhang et al., 2026b)). Despite growing interest from both research and industry, existing benchmarks treat the verifier as a subproblem—a means to grade rollouts or supply training rewards—rather than as an object of study. This gap, combined with the broad design space, motivates studying these verifiers in their own right. To the best of our knowledge, we conduct the first systematic study of verifiers for agents in rubric-graded environments. To enable this, we produce a dataset of human annotations, analogous to prior work on meta-evaluation of LLM judging and rubric-based evaluation (Tan et al., 2025; Pan et al., 2026). The dataset consists of agent trajectories and final environment states (containing file deliverables), along with rubric criteria and human-produced judgments, across a number of tasks in the BankerToolBench (BTB) (Lau et al., 2026) agent environment. We call this verifier evaluation dataset BankerVerifierBench (BVB). BVB consists of 2 ,464 judgment instances across 24 tasks, each judged independently by two domain experts and adjudicated by a senior reviewer. We publicly release BVB together with the code to reproduce our experiments, to facilitate future work on evaluating and improving verifiers for rubric-graded environments. We develop a methodology to analyze rubrics and identify the raw capabilities a verifier needs to judge the criteria in a dataset. Applying this methodology to BVB, we identify nine capabilities that lead us to three general design principles for verifiers in rubric-graded environments. We implement these principles in Gandalf 1, a new open-source verifier for agent environments. Our evaluation against three existing verifiers shows that Gandalf offers the best accuracy– cost tradeoff on BVB (§7): for every baseline configuration, a cheaper Gandalf configuration is at least as accurate. Across all nine capabilities on BVB, no baseline is reliably more accurate than Gandalf (§8.2). On OpenClaw, an internal dataset from a structurally different personal-productivity environment, Gandalf again achieves the highest accuracy (§8.1). No other verifier is near the top on both datasets: Archipelago comes close on BVB but falls behind on OpenClaw, and AutoRubric does the reverse. 

# 2. Background 

In a rubric-graded agent environment , an agent receives a task and acts within a structured environment (e.g., a filesystem, a set of tools, and access to external data) to produce a deliverable, which may consist of one or more files together with changes to the environment. A verifier is then asked to assign a binary met/unmet judgment to each criterion in the task’s natural-language rubric. This contrasts with deterministically graded agent benchmarks, where

criteria reduce to executable checks. Rubric-graded criteria are open-ended natural-language descriptions whose judgment often requires inspection of the deliverable, domain knowledge, and qualitative assessment. We adopt BankerToolBench (BTB) as the basis for our study and select three representative verifiers as objects of study. 

BankerToolBench (BTB) environment. We use version 1.1 of BTB (Lau et al., 2026), a recently released benchmark of 100 end-to-end analytical workflows performed by junior investment bankers, including discounted cash-flow analyses, leveraged-buyout models, trading comparables, and merger models. Each task is long-horizon, taking a banker 5 hours on average. The agent receives a task description, a data room of pre-loaded files, and a fixed set of tools: a market-data platform, an SEC EDGAR API, and a company brand-assets API for logos, alongside a filesystem and pre-installed libraries such as openpyxl and python-pptx . It must produce multi-file deliverables in standard office formats ( .xlsx , .pptx , .docx , .pdf ), which are graded against an expert-authored rubric of binary, weighted criteria. BTB rollouts are a demanding setting for verification: judging a single criterion may require joint reasoning across multiple heterogeneous artifacts. 

Verifiers for rubric-graded environments. We study three open-source verifiers that engage with the deliverable to different degrees. AutoRubric (Rao & Callison-Burch, 2026) grades each criterion in an independent LLM call over the full agent trajectory, including recorded tool calls with their arguments and outputs, but has no direct access to the deliverable files. 

Archipelago (Vidgen et al., 2026), released with APEX-Agents, captures a filesystem diff between initial and final environment states, extracts the content of changed documents via the Reducto document extraction service, and grades each criterion in an independent LLM call over the diff and extracted content without interacting with the deliverable directly. Agent-as-a-Judge (Zhuge et al., 2025) employs a workflow-based agent as the evaluator, planning and executing steps such as locating and reading files to reach a verdict. 

# 3. BankerVerifierBench: Meta-evaluation for rubric-graded environments 

We introduce BankerVerifierBench (BVB), the first meta-evaluation dataset for verifiers in rubric-graded agent environments. BVB extends prior meta-evaluation work for LLM judges (Tan et al., 2025; Pan et al., 2026) and agent trajectories (Lù et al., 2025) to settings where criteria require inspecting multi-file binary deliverables and tool-mediated environment state rather than text alone. The dataset consists of 24 tasks drawn from the BTB task distribution, spanning the product groups and task types described in §2. We randomly sampled 24 of BTB’s 100 tasks, choosing the largest sample our annotation budget allowed. Each task ships with an expert-authored rubric of binary criteria, weighted by importance and tagged with one of six categories; rubrics range from 67 to 128 criteria per task (median 104), totaling 2 ,464 criteria across the corpus. Each task is paired with one selected agent rollout, generated using Gemini 2.5 Pro or GLM-5 (12 tasks each, to avoid tying the labels to one agent’s failure modes) with OpenCode 1.17.9 as the agent harness. Rollouts average 25.5 tool calls (median 24, range 3–52), and generating the 24 released rollouts cost $14.36 in model API usage (mean $0.60, median $0.29 per rollout). Costs are as charged via OpenRouter and reflect prompt-caching discounts (Appendix A.1). Each rollout includes the complete trajectory (messages, tool calls, tool responses) and the final workspace, including all deliverable files in their native binary formats. Two practicing investment bankers, compensated at or above prevailing US market rates, independently judged each criterion in the native deliverables with a binary met/unmet verdict, with a raw inter-annotator agreement of 92 .1% and a Cohen’s 𝜅 (Cohen, 1960) of 0 .82. A senior reviewer adjudicated the labels, resolving disagreements and correcting judgements where necessary. The final adjudicated labels serve as our evaluation ground truth; 66 .3% of criteria are met.

# 4. Deriving requirements for verifiers from data 

Tasks in rubric-graded agent environments come paired with a rubric of natural-language criteria. Rather than fixing a verifier architecture in advance and determining its capabilities, we start from the rubric and ask what capabilities does a verifier need to have. We describe a general methodology for deriving verifier requirements from any rubric corpus, then apply its taxonomy to BVB. The methodology produces a taxonomy of verifier-side capabilities : each capability names a kind of check the verifier must perform to judge a criterion correctly. The taxonomy is verifier-side (labels describe what a verifier must check, not what the agent must produce) and architecture-agnostic (labels do not name a specific runtime, library, file format, or data source), so it applies across verifier types. 

Methodology. Our pipeline takes a corpus of natural-language rubrics and produces a taxonomy of capabilities in three stages. Stage 1 generates open-ended natural-language tags for each criterion describing what a verifier needs to do to verify it. Stage 2 clusters these tags and merges them into a small set of canonical capabilities. Stage 3 re-tags every criterion with one to three of the canonical capabilities, ranked by relevance. We provide more details about the methodology in Appendix B. 

Application to BVB. We retain the nine capabilities induced from an earlier BVB rubric corpus and apply them to the released criteria. 2 Table 1 reports their primary-tag distribution. Across the released corpus, the largest, audit quantitative metric calculation , accounts for 21 .2%; the smallest, audit accounting logic and convention , accounts for 4 .6%. In the BVB setting, these abstract capabilities take concrete form. Audit quantitative metric calculation ranges over EV/EBITDA multiples and transaction fees; audit accounting logic and convention covers sign rules and balance-sheet identities; audit governance and strategic narrative covers disclaimers, regulatory boilerplate, and acquisition-rationale claims. The same capability labels might carry to other domains although with different instantiations: for example, a clinical workflow would instantiate audit accounting logic and convention as dosage and contraindication checks against clinical guidelines; a productivity workflow would instantiate audit governance and strategic narrative as escalation policies and tone norms. 

# 5. Design principles for verifiers 

Reading the taxonomy as a specification surfaces three structural patterns in the capabilities: (i) the verification path varies across criteria, (ii) judging requires inspecting artifact-internal structure or environment state that text serialization erases, and (iii) judging requires domain knowledge not in the criterion text. These patterns arise from natural-language rubrics over rich agent environments, not specifically from the financial setting of BVB. We address each with a design principle.

The pattern is intrinsic to natural-language rubrics rather than a quirk of BVB: any domain that admits rubrics over open-ended deliverables will exhibit it. Our first principle is that the verifier should be a reactive agent (Yao et al., 2023) that, given a criterion, autonomously decides which artifacts to open, which tools to invoke, and in what order, terminating once it reaches a verdict. A workflow verifier fixes these steps when it is designed, while a reactive verifier lets the model choose them for each criterion. Every capability in the taxonomy exhibits this variation, so P1 applies to all nine. 

Principle 2 (P2): Environment alignment. Several capabilities reduce to inspecting proper-ties of the agent’s artifacts (formula structure, layout metadata, cross-file references) that do not survive flattening to text or rendering as images. Six capabilities in the taxonomy exhibit this pattern. We expect it in any environment with binary files, stateful tools, or structured data, which have analogous properties that serialization erases. Our second principle is that the verifier should run in the same environment as the rollout agent, with access to its final state through the same filesystem, libraries, and tools (including domain-specific Model Context Protocol (MCP) (Hou et al., 2026) tools). Unrestricted access would let the verifier modify what it grades. Its access must therefore be read-only, so that verification always sees the agent’s original, unaltered output (§6). Running in the agent’s environment also makes the verifier portable, because applying it to a new environment automatically provides access to that environment’s existing tools, and there is no dependency on domain-specific parsers. 

Principle 3 (P3): Domain guidance. Several capabilities require knowledge that does not appear in the criterion text, such as accounting sign conventions or disclosure standards for an investment memo. Two capabilities in the taxonomy exhibit this pattern. Every domain has analogous conventions, such as clinical standards in medical workflows, citation rules in legal workflows, and communication norms in productivity workflows. # 6. Gandalf: a verifier for rubric-graded environments 

We implement the design principles of §5 in Gandalf , a portable Python application that grades a rollout with an agent, the judge . For each criterion, the judge returns a met/unmet verdict with its reasoning and the evidence it checked (Appendix C). 

Reactive verification (P1). Gandalf instantiates P1 by making the judge a reactive agent, built on the open-source OpenHands SDK (Wang et al., 2025b). Equipped with a terminal and a file editor, the judge decides for itself which files to open and which checks to run for each criterion. 

Environment alignment (P2). To satisfy P2, Gandalf is designed to run inside the rollout’s environment. There, the judge opens the agent’s files in their native formats, runs code with the installed libraries, and calls the environment’s MCP tools. Running in the agent’s environment requires keeping the judge and the graded agent apart. The judge starts only after the rollout has finished and works on a temporary copy of the workspace under a strictly scoped separate Unix user. Its tools also cannot modify the agent’s work or the environment’s data, so the judge cannot change what it grades. 

Domain guidance (P3). Gandalf supports P3 through a guidance channel. Domain guidance, written once for an environment rather than per task, enters the judge’s prompt alongside the task instruction, the rollout agent’s final message, and the criteria. 

Beyond the principles. Two further settings affect cost and accuracy. The choice of the judge’s model lets a benchmark designer trade grading accuracy against cost (§7.3). Batching lets one session grade many criteria, so the judge reuses the files it has already inspected instead of opening them again for each criterion. A rubric can also be split into several batches that are graded in parallel. 

# 7. Evaluation 

We evaluate Gandalf along with three baselines described in §2: Archipelago (serialize-then-grade), Agent-as-a-Judge (AAAJ; workflow-based file inspection), and AutoRubric (trajectory-only grading without access to the deliverable). The evaluation answers three questions: (1) how do verifiers compare on accuracy and cost (§7.1); (2) what do Gandalf ’s domain guidance and MCP tools contribute (§7.2); and (3) how do batch size and backing model trade accuracy against cost (§7.3). 

Setup. In the verifier and model comparisons, Gandalf grades each task’s rubric in two agent sessions, each covering approximately half the criteria. §7.3 examines how batch size and backing model affect F1 and model API cost. Gandalf receives domain guidance and access to the environment-aligned MCP tools, using Gemini 3 Flash unless stated otherwise. 

Metrics. In BVB, 66.3% of criterion–rollout pairs are met, so a verifier that always predicts “met” reaches 66.3% accuracy without detecting any unmet criteria. We therefore report F1 on the unmet class (UNMET F1) as our main evaluation metric; throughout the paper, F1 refers to UNMET F1. It is zero for the always-“met” verifier and rewards both finding unmet criteria (recall) and avoiding false alarms on met ones (precision). We evaluate every task three times per configuration, or once where indicated, and compute a single F1 over all criterion verdicts from these evaluations. # 8. Discussion 

We now step back and ask two questions about the evaluation results: (1) does Gandalf generalize beyond BVB (§8.1); and (2) why do different verifiers perform differently (§8.2)? 

> 8Verifying Agents in Rubric-Graded Environments

8.1. Gandalf generalizes beyond BVB 

To investigate whether Gandalf generalizes, we collected another internal dataset analogous to BVB in a new domain: we additionally evaluate on an OpenClaw (OPC) benchmark of persona-driven personal-productivity workflows: managing schedules, coordinating with contacts, planning lifestyle tasks. OpenClaw differs from BVB in domain (consumer), tool surface (messaging clients, calendar and booking services, a weather API), and evidence type (many OpenClaw tools are stateful, so verification depends on determining if the environment has changed such as whether a message was sent or an event created). This dataset consists of 396 criteria judgments across 24 tasks. As on BVB, we report UNMET F1. Most OpenClaw criteria are unmet (59.6%, vs. 33.7% on BVB), so a verifier that always predicts unmet scores 0.747 here and 0.504 on BVB; absolute F1 values are therefore not directly comparable across the two datasets. Appendix E reports confusion counts for the Gemini 3 Flash verifiers. Table 3 reports F1 and cost across all four verifiers on the OpenClaw dataset. Gandalf achieves F1 of 0.955, leading the next-best verifier (AutoRubric with Gemini 3 Flash, 0.934) by 0.021 F1, and is again Pareto optimal on observed F1 and model API cost. AutoRubric costs $1.43 per pass against Gandalf ’s $7.68; Archipelago with GPT-5.4-Mini is cheaper still ($0.70, F1 0.841). Gandalf with Gemini 3 Flash has the highest observed F1 among the evaluated configurations, but AutoRubric’s competitive result shows that the accuracy–cost tradeoff depends on the environment. 

8.2. Verifiers’ errors are consistent with gaps in capabilities

AutoRubric. AutoRubric has no artifact access and no domain guidance. It grades each criterion in an isolated LLM call over the agent’s trajectory. Its errors concentrate on capabilities where the criterion depends on how the deliverable turned out, not on what the agent did to produce it. On BVB, errors are lowest on verify literal data point accuracy (5.9%) and verify structural component inventory (7.0%), capabilities where a specific tool call maps to a specific check: writing a value or creating a section is recorded in the trajectory. Errors are highest on 

inspect visual presentation and style (17.0%) and audit accounting logic and convention (16.2%), capabilities where the criterion depends on properties of the final rendered or structured output that no single tool call captures. The same split holds on OPC, where errors are also high on reconcile cross-component data linkage (20.0%) and audit governance and strategic narrative (17.2%).

# 9. Related work 

Agent environments. Agent benchmarks frequently rely on deterministic checks against final state, expected tool calls, or unit tests (Wang et al., 2024; Li et al., 2026a; Patil et al., 2025; Qin et al., 2024; Chen et al., 2024; Li et al., 2023; Patil et al., 2024; Yao et al., 2025; Liu et al., 2024; Jimenez et al., 2024; Li et al., 2026c; Malay et al., 2026). In pursuit of greater scope and realism, recent benchmarks in semi-verifiable domains have embraced rubric-based grading. Such benchmarks include BankerToolBench (Lau et al., 2026), APEX-Agents (Vidgen et al., 2026), CoreCraft (Mehta et al., 2026), GTA-2 (Wang et al., 2026), ClawBench (Zhang et al., 2026b), Claw-Eval (Ye et al., 2026), and AgencyBench (Li et al., 2026b). Across both lines, these works treat the verifier as a means to an end, not the object of study. 

Rubrics. Rubrics are a popular approach to defining correctness in semi-verifiable do-mains (Lin et al., 2025; Sirdeshmukh et al., 2025). Rubrics may be authored by domain experts (Arora et al., 2025; Starace et al., 2025; Akyürek et al., 2026) or generated synthet-ically (Cook et al., 2024; Liu et al., 2025; Wadhwa et al., 2025; Raghavendra et al., 2026). RubricBench (Zhang et al., 2026a) evaluates rubric generators themselves against human pref-erences. A line of work investigates rubrics in the context of training (Viswanathan et al., 2025; Gunjal et al., 2026); some of this work investigates training with synthetic rubrics (Rezaei et al., 2025; Shao et al., 2025; Huang et al., 2025b; He et al., 2025). Rubric-ARM (Xu et al., 2026b) jointly optimizes a rubric generator and a judge, optimizing judgment accuracy for matching human preference ranking. Unlike these works, we take rubrics as a given and study the verifiers that consume them. 

Verifier designs. Verifiers, both inside and outside the context of environments, cover a broad design space (Guan et al., 2024; Li et al., 2025; You et al., 2026). A line of work optimizes LLM-as-a-judge for evaluating text through prompting or training (Liu et al., 2023; Kim et al., 2024a; Kim et al., 2024b; Zhu et al., 2025b), and a related line decomposes evaluation into per-criterion judgments via rubrics (Hashemi et al., 2024; Lee et al., 2025; Rao & Callison-Burch, 2026; Zhou & Tan, 2026; Saad-Falcon et al., 2025). Benchmarks commonly apply such techniques for outcome grading in agent environments by evaluating a serialized trajectory or serialized output files (Mehta et al., 2026; Ye et al., 2026). In contrast, some environments propose workflow-based agents as verifiers (Zhuge et al., 2025; Vidgen et al., 2026; Zhu et al., 2025a; Findeis et al., 2025; Peng et al., 2025; Han et al., 2025; Sun et al., 2025), while others propose reactive agents (Lin et al., 2026; Avraham et al., 2026; Cui et al., 2026; Dai et al., 2026; Wang et al., 2025a; Ding et al., 2026; Xu et al., 2026a; Ma et al., 2026). Despite the broad design space, no principled account describes which design choices matter for which verification capabilities. Concurrently with this work, RewardKit in Harbor (Harbor Framework Team, 2026) adopted a similar reactive, in-environment verifier design; Appendix D compares the two at matched models. 

Meta-evaluation of verifiers. Motivated by the importance of verifiers in benchmarks, meta-evaluation benchmarks evaluate verifiers themselves, covering LLM-as-a-judge for preference rankings (Zheng et al., 2023; Tan et al., 2025; Lambert et al., 2025; Malik et al., 2026) and LLM-as-a-judge for rubric grading (Pan et al., 2026). Verifiers can be domain-specific, motivating domain-specific benchmarks such as AgentRewardBench (Lù et al., 2025) for 

> 11 Verifying Agents in Rubric-Graded Environments

web agents and meta-evaluations such as TinyV (Xu et al., 2025) and Huang et al. (2025a) for mathematics. BVB is the first meta-evaluation dataset that covers rubric-graded agent environments, where rubric criteria cover deliverable files and side-effecting tool calls. 

# 10. Conclusion 

Gandalf offers a strong accuracy–cost tradeoff across two rubric-graded environments. Our results motivate reactive verification, while leaving the conditions under which guidance and environment-aligned tools improve performance open for further study. We hope that the public release of BVB will help facilitate continued research on building verifiers for agents, and that the open-source release of Gandalf will unlock more realistic benchmarks for agents. 

Limitations. The BVB dataset contains a single rollout per task; we did not evaluate the sensitivity of verifiers to the rollout distribution. Our study measures verifier F1 score against human labels; we did not evaluate whether verifier accuracy advantage translates to better-trained agents through RL. Our study covers 24 tasks in each of two environments; the internal OpenClaw dataset is not publicly reproducible. Cross-verifier comparisons evaluate whole systems and do not isolate the causal contribution of individual design principles. Generalization beyond these settings remains to be established.

# B. Taxonomy Construction 

The taxonomy was originally produced from an earlier BVB corpus using the three stages below. For the released corpus, we retained the output of Stages 1–2 and reran Stage 3. All LLM calls in this pipeline use Gemini 3 Flash, and embeddings use Google’s text-embedding-005 .

Stage 1: Free-text discovery. For each rubric criterion, an LLM receives the agent-facing task brief and the criterion text, and emits one to three short capability labels along with a one-sentence rationale per label. Three constraints are enforced programmatically: (i) the rationale must begin with “the verifier needs to . . . ” and quote a phrase from the criterion text, which enforces verifier-side framing; (ii) labels must not contain tokens naming a specific runtime, library, file format, or data source, which enforces architecture-agnosticism; and (iii) labels must follow a fixed lexical form. 

Stage 2: Canonicalization. Each unique Stage 1 label is embedded and partitioned by agglomerative clustering into 80 fine-grained micro-clusters. An LLM names each micro-cluster and produces a definition, a diagnostic signal, a worked example, and a set of non-examples contrasting it with its nearest siblings. A final LLM call merges the 80 named micro-clusters into the canonical taxonomy under three hard constraints: between 8 and 10 canonical capabilities, no single capability covering more than 40% of corpus criteria, and every input micro-cluster mapped to exactly one canonical capability. 

Stage 3: Closed-vocabulary tagging. Every criterion is re-tagged against the closed canoni-cal taxonomy. An LLM receives the criterion, its task brief, and the full taxonomy (canonical names, definitions, diagnostic signals, non-examples), and emits one to three canonical capabil-ity tags per criterion ranked by relevance. # E. Over-acceptance and over-rejection 

With UNMET as the positive class (§7), a false positive is an over-rejection : the verifier marks unmet a criterion the human judged met. A false negative is an over-acceptance : the verifier marks met a criterion the human judged unmet. F1 weights the two equally, but their consequences differ. Over-acceptance credits deficient outputs: if the verifier supplies rewards, a policy may be reinforced toward outputs the rubric fails, and in benchmarking it inflates the scores of deficient systems. Over-rejection withholds credit from correct outputs: it can slow learning or deflate benchmark scores, but it does not reward failures. We do not measure either effect here. Table A6 reports both error types for the four Gemini 3 Flash verifiers. We compare each baseline with Gandalf using nominal 95% paired task-bootstrap intervals for the per-pass difference (10,000 draws; uncorrected for multiple comparisons). We report F1 intervals for context but make directional claims only when an interval excludes zero. Verifiers with similar F1 can differ in error direction.
