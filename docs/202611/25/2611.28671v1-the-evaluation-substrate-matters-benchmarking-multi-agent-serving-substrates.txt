## ABSTRACT 

Multi-agent systems (MAS) usually coordinate heterogeneous models and tools to solve complex tasks, creating a growing need for reliable evaluation. However, a multi-agent workflow that is fastest in one serving environment can lose its advantage in another, even when its models, prompts, and task remain fixed. This makes a benchmark result conditional on how the workflow is executed. We introduce MASS YS , a benchmark for measuring this dependence in multi-agent large language model (LLM) systems. MASS YS executes the same candidate–task pairs across serving substrates and load regimes, using five workload families spanning software repair, research synthesis, financial analysis, interactive control, and diagram generation. It records task quality alongside delivery, latency, cost, resource pressure, and failure evidence. In a controlled motivation diagnostic, the Star workflow falls from first to fourth in mean-latency rank under KV-cache pressure, while Chain rises from fourth to first. The substrate sweeps further show that increasing load creates long runtime tails and timeout pressure. In several task families, quality among evaluated outputs changes less than effective quality over submitted jobs: the system delivers fewer usable results even when the surviving outputs remain competitive. Tool and runtime traces reveal that these outcomes involve both model serving and non-model execution. Together, the results motivate evaluating MAS designs over explicit operating conditions and reporting which tasks are delivered, how well they are solved, and where execution breaks down. 1

## 1 INTRODUCTION 

Large language models (LLMs) are increasingly deployed as components inside agentic systems that plan, call tools, exchange intermediate results, and coordinate multiple specialized roles. Modern multi-agent systems (MAS) make this trend explicit: a user request may be decomposed by a planner, dispatched to code, search, finance, visualization, or critique agents, and then merged by a verifier or manager. Frameworks such as AutoGen and CAMEL popularized conversational and role-based multi-agent programming, while graph- and state-oriented frameworks make it practical to build long-running, tool-using, multi-actor workflows (Wu et al., 2024; Li et al., 2023). In parallel, agent benchmarks such as AgentBench, GAIA, SWE-Bench, and MultiAgentBench have shifted evaluation beyond static question answering toward interactive environments, tool use, software engineering, and collaboration or competition among agents (Liu et al., 2024; Mialon et al., 2024; Jimenez et al., 2024; Zhu et al., 2025).

This progress changes what a benchmark score means. For a multi-agent application, the score is no longer only a property of the underlying LLM: it also depends on topology, role prompts, model allocation, tool access, memory, error handling, and orchestration. Recent system-level evaluation work makes this point explicit. MASEval (Emde et al., 2026), for example, argues that the complete agentic system should be the unit of analysis, and shows that framework and implementation choices can materially affect multi-agent benchmark results. This is an important step beyond model-centric leaderboards. However, it leaves a lower layer largely implicit: the serving substrate on which the multi-agent system is executed. An agent can fail a coding benchmark before writing any solution code. On the Terminal-Bench task bn-fit-modify , Anthropic reports that installing a data-science stack can exhaust a tightly constrained container’s memory. Across resource configurations, its Terminal-Bench 2.0 score differed by six percentage points with the same model, harness, and tasks (Segato, 2026). The execution environment can therefore determine whether a chosen solution strategy can even proceed. The same issue appears across successive turns. Manus reports an average input-to-output token ratio of approximately 100:1, making reuse of accumulated context consequential for latency and cost (Ji, 2025). Continuum studies the related serving problem: an agent pauses to run a tool, and retaining its KV cache competes with admitting other requests (Li et al., 2025b). These observations motivate treating resource allocation, queueing, cache management, and tool execution as part of the conditions under which an agent is evaluated. We use serving substrate to refer to the runtime, backend, request load, queueing policy, resource budget, cache behavior, timeout/retry policy, and orchestration mechanism that mediate execution between a MAS design and the underlying models and tools. Existing agent and MAS benchmarks typically fix this layer and attribute score differences to the model, scaffold, or candidate system. Fig. 1 illustrates why this is unsafe: the same workflow candidates change latency rankings under KV-cache, CPU, GPU, and mixed pressure, while serving cells exhibit different window-completion and P95-runtime trade-offs across offered loads. MASS YS adopts this system-level view and moves one layer lower: after the MAS candidate is fixed, it measures whether substrate choices change task outcomes, service behavior, and failure evidence. 

LLM serving and agentic/application serving. LLM serving systems make backend behavior a primary systems problem. vLLM, SGLang, Orca, DistServe, Sarathi-Serve, TensorRT-LLM, TGI, and LightLLM optimize memory management, structured-program execution, batching, prefill/decode scheduling, throughput, and latency (Kwon et al., 2023; Zheng et al., 2024; Yu et al., 2022; Zhong et al., 2024; Agrawal et al., 2024; NVIDIA, 2023; Hugging Face, 2023; ModelTC Team, 2023). These systems optimize how workflows are served. ## 3 MASS YS : S UBSTRATE -AWARE MAS E VALUATION BENCHMARK 

MASS YS is a benchmark and evaluation framework for studying how serving substrates affect multi-agent LLM systems. The benchmark is organized around three principles. First, the evaluated object is a complete MAS candidate, including its topology, number of agents, role prompts, model allocation, tools, and orchestration policy. Second, a serving substrate is a first-class experimental variable, covering backend/runtime choice, request load, queueing behavior, resource pressure, cache behavior, and scheduling policy. Third, every run records both task-level and service-level outcomes, so that a completed execution is not mistaken for a correct solution and a low-latency execution is not mistaken for a robust MAS design. Fig. 2 summarizes the evaluation pipeline that connects workload sampling, MAS candidate construction, substrate execution, and trace processing. MASS YS evaluates complete MAS candidates under controlled serving substrates. Each candidate includes topology, agent count, role prompts, model assignment, tool access, memory, and orchestra-tion policy. Each substrate cell specifies backend/runtime, offered load, queueing behavior, resource budget, cache policy, and timeout/retry policy. ## 4 EXPERIMENTS 

We evaluate MASS YS on mixed MAS workloads under controlled substrate sweeps. The goal of this section is not to produce a single leaderboard of MAS candidates, but to characterize how backend, runtime, load, and orchestration conditions change the feasibility and trace behavior of the same class of multi-agent jobs. Unless otherwise stated, succeeded denotes execution success: the job completed and returned a usable final artifact under the service condition. 4.1 EVALUATION SETTINGS 

We evaluate MASS YS with paired substrate sweeps over five serving cells: vLLM-style serving, SGLang-style serving, Continuum-style serving, Orla over vLLM, and Orla over SGLang. Table 3 summarizes the hardware-specific model allocation. These two regimes represent capacity-matched deployment tiers instead of an isolated GPU-count ablation: both share Qwen-image-2512 for image generation and multimodal Qwen3.5-27B for vision and text on two GPUs, while 4 ×H200 adds Qwen2.5-14B-Instruct and Qwen3-Coder-30B-A3B-Instruct on two additional GPUs. All substrate comparisons hold the model pool and arrival schedule fixed within each tier. In the main sweeps (seed 42, 1,200 s per-job deadline), MAS plans are generated by a GPT-5.4 plan agent, and jobs arrive via a Poisson process over a 30-minute window at 0.005, 0.01, 0.02, 0.05, and 0.10 JPS on 2×H200 (0.01–0.10 JPS on 4 ×H200). Result 1: Load turns MAS serving into a tail-latency problem. Increasing load affects the entire MAS execution graph beyond isolated model calls. Fig. 6 shows that, as offered load increases, completion and execution-success rates decline in several substrate cells, while mean job runtime, P95 runtime, runtime-threshold exceedance rate, run-completion elapsed time, KV-cache pressure, and P95 concurrency increase. The effect is visible in both 2 ×H200 and 4 ×H200 regimes. This pattern matters for MAS evaluation because multi-agent jobs contain multiple dependent calls, tool invocations, and aggregation steps. A delayed branch can block downstream agents or the final response, making tail behavior an integral part of the benchmark outcome. To assess statistical robustness across independent workload realizations (seeds 42–44), we added 50 runs covering all five serving cells and five loads on 2 ×H200 and 12 runs covering native vLLM, SGLang, and Continuum at 0.05 and 0.10 jobs/s on 4 ×H200 (Appendix E). On 2 ×H200, increasing load from 0.05 to 0.10 jobs/s reduces mean completion by 31.98–40.38 percentage points across cells (all five paired 95% CIs exclude zero) and raises run-level P95 runtime in every cell (three of five CIs exclude zero). Result 2: backend/runtime choices change the service envelope. Fig. 1(c) and Fig. 6 show that substrate choice changes the completion-latency-reliability trade-off observed by the same mixed MAS workload. Fig. 7 (Appendix C) shows that this service envelope also changes reported task quality. Effective quality is most sensitive in task families where serving failures remove many jobs from the evaluated set, with high-load drops especially visible for SWE-Bench, PinchBench, and PaperBanana in several 2 ×H200 cells. By contrast, evaluated-only quality is often flatter for ResearchBench and parts of DeepFund, indicating that many completed-and-evaluated artifacts retain similar quality even as fewer jobs survive the service condition. The 4 ×H200 regime mitigates some effective-quality loss but does not remove substrate dependence, especially for visual and interactive workloads. Some serving cells achieve lower runtime over portions of the load range, while others maintain stronger completion or execution-success behavior under the same offered load. The comparison is therefore not a single total ordering of backends. Instead, MASS YS exposes a service envelope: a substrate may be attractive for latency among completed jobs but less favorable in reliability, runtime-threshold exceedance, or backlog under heterogeneous mixed workloads. A deployment-relevant MAS benchmark should report these axes separately. Substrate-dependent workflow ranking reversals also appear in the main benchmark. On PinchBench at 4 ×H200 and 0.10 jobs/s, Chain achieves lower mean latency than FSM under vLLM, SGLang, and ORLA+SGLang, whereas FSM is faster under Continuum and ORLA+vLLM on the five-cell matched successful-job intersection (14 Chain and 7 FSM jobs; Table 9), and the cross-substrate Chain/FSM reversal recurs in seed 43 on the native 4 ×H200 runs (Chain faster under SGLang, FSM faster under Continuum and vLLM; Appendix F). We further audited all 3,255 submissions across the original 45 benchmark runs to distinguish execution failures from evaluation-infrastructure failures. Of the 492 jobs without valid evaluations, 490 resulted from execution failure or deadline termination, while only two encountered evaluation failures after successful execution. Overall, 2,763 of 2,765 execution-successful jobs received valid numerical scores. Thus, the missing-score component of the effective-quality gap stems almost entirely from execution and delivery failures instead of evaluator errors (Appendix G, Table 10). The distinction between effective and evaluated-only quality also persists without LLM-based judging. Result 4: trace decomposition identifies where substrate effects arise. Trace metrics reveal that the same final runtime can be caused by different mechanisms. Fig. 9 (Appendix C) decomposes mean critical-path latency across all five serving cells on 2 ×H200 and 4 ×H200 into backend prefill, backend decode, backend queue wait, backend other time, ORLA forwarding and backend time, tool execution, and agent/client overhead. At light and moderate load, critical-path time is dominated by backend decode together with tool execution and client overhead. At the highest load, backend queue wait and forwarding/client overhead become prominent. Combined with the tool-layer evidence in Fig. 8, this decomposition shows why MASS YS records execution traces alongside scalar scores: slow or failed MAS executions can arise from backend decoding, queueing, tool calls, orchestration overhead, or their interaction along the MAS graph. 4.3 DISCUSSION 

Fast substrates and robust substrates are not always the same. The results separate properties that are often conflated in benchmark reporting. A serving cell can have favorable runtime among completed jobs while showing weaker completion, execution success, or backlog behavior, or higher runtime-threshold exceedance under heavier load. Conversely, a substrate with higher latency may preserve a more stable service outcome in part of the operating range. This motivates reporting MAS benchmark results as service envelopes instead of a single backend or candidate score. 

Backlog is an evaluation outcome. The fixed service-window view makes queue growth and unfinished work visible. Under heavy load, Fig. 6 shows that runtime-threshold exceedance rate, run-completion elapsed time, and concurrent-job pressure increase along with tail runtime. For interactive MAS applications, this is not a bookkeeping artifact. A delayed worker branch can block a verifier, a delayed verifier can block the final aggregation step, and a delayed final answer can turn an otherwise successful execution into an unusable service result. MASS YS therefore treats deadline behavior and unfinished-at-window-close evidence as first-class service metrics. 

The tool layer is part of MAS serving. Fig. 8 shows that tool calls are neither uniform nor negligible. Some tools are frequent and lightweight; others are less frequent but dominate latency tails or reliability variation. This matters because MAS candidates differ in how they allocate work across search, reading, editing, execution, browser control, and verification. A model-only benchmark would miss this source of variation and may incorrectly attribute tool-layer effects to model quality or agent topology. 

Failure attribution should be part of the benchmark report. Table 2 separates task outcome, service outcome, and failure evidence. This separation is necessary for substrate-aware evaluation. A failed MAS run may reflect task reasoning, agent coordination, tool behavior, environment constraints, queueing/timeout, resource pressure, backend/runtime behavior, or judge/format issues. MASS YS 

therefore records structured trace evidence and avoids collapsing all unsuccessful executions into a generic failure label. This design makes it possible to distinguish service-induced failures from model, tool, environment, or task-specific failures. 

## 5 CONCLUSION 

We presented MASS YS , a substrate-aware benchmark for multi-agent LLM systems. MASS YS 

executes controlled MAS candidates over mixed-domain workloads under paired serving substrates and records task outcomes, service outcomes, and trace-derived failure evidence. The reported sweeps show that workflow rankings change under resource bottlenecks, load creates heavy-tail runtime and timeout pressure, and serving cells expose different completion–latency–reliability envelopes. The workload and trace analyses further show that token distribution, tool mix, queueing, and orchestration overhead are essential parts of the benchmark outcome. These findings suggest that future MAS benchmarks should report substrate, load, hardware, workload structure, and trace evidence together with model and topology choices. 10 Preprint

## A REPRODUCIBILITY 

Execution protocol. Within each hardware–load–seed block, candidate MAS plans are generated once, and the identical task assignments, candidate configurations, and scheduled arrival offsets are replayed across all serving cells without replanning. Actual queueing, model responses, and tool execution remain independent across cells. The original sweeps use seed 42; to quantify variability across independent workload realizations, we additionally executed seeds 43 and 44 across all five serving cells and five offered loads on 2 ×H200 (50 new runs) and across the three native backends (vLLM, SGLang, and Continuum) at 0.05 and 0.10 jobs/s on 4 ×H200 (12 new runs; Appendix E). The runner releases jobs at the frozen arrival offsets without a benchmark-level concurrency semaphore; native cells rely on the backend scheduler, while Orla uses per-backend concurrency and queue capacities of 1,000, chosen not to add a smaller front-end admission cap. The 30-minute window stops new arrivals and defines completion, but is not a global kill deadline: already submitted jobs drain until termination, subject to a 1,200 s per-job deadline. Model-call transport errors are retried for at most six attempts with randomized exponential backoff between 1 and 60 s. 

Models and decoding. Each served model instance is deployed within one H200 (tensor parallelism one). We use BF16 weights without quantization and do not set an additional backend context-length cap, so the model/backend native context limit applies. Language and vision agents use temperature 0, a 4,096-token output cap, and disabled Qwen thinking mode; Qwen-image uses its image-generation defaults with temperature 1.0. The PlanAgent uses temperature 0 and an 8,192-token output cap. Backends start fresh for each run without an explicit warm-up, after which prefix caches accumulate within the run. 

Software and artifacts. The released setup uses Python 3.11 and ORLA 1.2.15. The runtime envi-ronments use PyTorch/Transformers 2.11.0/5.6.2 for vLLM, 2.9.1/5.5.4 for SGLang, 2.10.0/4.57.6 for vLLM-Omni, and 2.8.0/5.6.2 for Continuum; the corresponding PyTorch builds target CUDA 13.0 or 12.8. vLLM is 0.19.2.dev0+gf150107.local (commit f150107 ); the custom SGLang, vLLM-Omni, and Continuum source trees are included in the code release. Model identifiers are listed in Table 3. The serving cells integrate existing frameworks with local compatibility modifications and do not independently reimplement their inference engines. ORLA retains its original scheduler with our runtime/client integration. For Continuum, we ported its scheduling, tool-duration estimation, and KV-retention mechanisms from the original vLLM 0.10.2-based release to a fork of the newer vLLM baseline used in our experiments so that Qwen3-family models share a matched underlying engine version across cells. Pinned package versions, launch configurations, and adapted backend source trees are available in the public code repository. 

Task-quality evaluators. ResearchBench uses text-embedding-3-large with 1,024-dimensional embeddings and cosine similarity. PinchBench uses the task’s released automated grader, LLM rubric, and grading weights; its LLM judge is GPT-4o at temperature 0 and receives the task prompt, execution transcript, and task-specific rubric. PaperBanana uses GPT-4o at temperature 0 with the released PaperBanana prompts to score instruction faithfulness, conciseness, readability, and aesthetics on a 0–10 scale. SWE-Bench uses its per-instance Docker test harness. DeepFund maps the stored realized/next-trading-day outcome to profit/flat/loss and then to 1/0.5/0. Evaluator prompts, rubrics, inputs, and structured outputs are retained in the code or trace releases. Service aggregates are deterministically recomputable from the released traces. Repeating DeepFund against live data sources can change the market snapshot; the paper therefore uses the stored outcome labels. Exact commands, sanitized configurations, and artifact schemas are documented with the code and trace releases. 

## B LIMITATIONS 

MASS YS is intended to expose substrate effects rather than to exhaustively rank all MAS frameworks or serving systems. The current benchmark covers five workload families and a controlled set of 16 Preprint MAS topologies, but it does not represent the full space of deployed agent applications, especially long-running enterprise workflows, human-in-the-loop tasks, and safety-critical interactive settings. The reported substrate sweeps also focus on a finite set of serving cells and hardware regimes; additional backends, schedulers, accelerators, and production admission-control policies may expose different trade-offs. Moreover, MASS YS separates execution success from task quality, but task-quality evaluation remains benchmark-specific and can depend on the fidelity of execution-based checks, structured validators, or judge models. Finally, failure attribution is trace-based rather than causal: the traces identify evidence for queueing, tool, resource, backend, or judge/format failures, but they may not fully isolate root causes when multiple failures interact along the same MAS graph. These limitations motivate extending MASS YS with broader workload sources, additional serving substrates, and stronger task-specific evaluators.

D.2 WORKFLOW DEFINITIONS 

We evaluate five fixed workflow structures: • Star: Fourteen parallel workers independently process long-context inputs, followed by one aggregation call (15 model calls in total). • Chain: Eight sequential model calls, with later stages operating on compressed intermediate context (8 calls). • DAG: Two dependency waves, each containing six parallel worker calls, followed by a reducer (13 calls). • Tool-ReAct: Eight agents, each performing eight sequential model steps interleaved with local JSON-processing operations (64 calls). • Debate: Two rounds involving two debater calls per round, followed by a synthesis/judge call (5 calls). The dependency structures and call counts are fixed across all experimental conditions. Star, DAG, and Chain use a 64-token per-call output cap; Tool-ReAct uses a 16-token cap and local processing steps; Debate uses a 256-token cap. These workflows deliberately differ in their degrees of parallelism, sequential dependencies, context requirements, and local computation. D.3 SERVING CONDITIONS

## F WORKFLOW RANKING ANALYSIS IN THE MAIN BENCHMARK 

F.1 CROSS -S UBSTRATE WORKFLOW RANKING REVERSALS 

To examine whether substrate-dependent workflow ranking reversals also occur in the main bench-mark, we compare Chain and finite-state-machine (FSM) workflows on PinchBench at 4 ×H200 and 0.10 jobs/s (seed 42). To avoid backend-specific differences in successful-job selection, la-tency is computed using jobs successfully executed across all five serving cells for each topology (14 Chain and 7 FSM jobs). Table 9 reports the mean end-to-end runtimes and topology-specific execution-success counts. Chain achieves lower mean latency under vLLM, SGLang, and ORLA+SGLang, whereas FSM is faster under Continuum and ORLA+vLLM.
