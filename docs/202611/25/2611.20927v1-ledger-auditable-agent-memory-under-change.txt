# LEDGER: Auditable Agent Memory Under Change 

Md Aidul Islam, Md Nasir Uddin Shuvo, Muhammad Waseem, Pekka Abrahamsson 

Faculty of Information Technology and Communication Sciences Tampere University 

Tampere, Finland {mdaidul.islam, nasir.shuvo, muhammad.waseem, pekka.abrahamsson}@tuni.fi 

Abstract —Agent memory systems are mostly evaluated on fixed histories, and only their final answers are scored. In real use, facts change, sources differ in reliability, and users ask the agent to forget things. We present L EDGER , a memory layer in which a language model proposes facts and explicit rules decide which value is current, which source to trust, and what to delete. Each fact keeps its source and the period in which it held. L EDGER +E P

adds a search over raw conversation turns for questions the ledger does not cover, and scrubs these turns on deletion. We compare both against no memory, full-history replay, retrieval over raw transcripts, and Mem0, with the same answering model and prompt, on a synthetic multi-session coding-agent workload and a 210-question subset of LongMemEval, and we score both the evidence each memory sends to the model and the answer. On the coding workload, L EDGER +E P answers 94.3% of questions correctly on five development seeds and 91.1% on five held-out seeds, against 82.1% and 83.3% for full replay, the strongest baseline. When a deletion request only describes the fact, no deleted value reached our systems’ evidence in any evaluated probe. On LongMemEval, L EDGER +E P has the same observed accuracy as full replay (74.8%) with 1% of its context. The main limitation is that the coding workload is synthetic and built by us; on LongMemEval, the differences between the strongest systems are within the confidence intervals. 

Index Terms —LLM agents, agent memory, evaluation, prove-nance, deletion 

I. I NTRODUCTION 

Coding agents work on the same repository across many sessions [1], [2]. The repository and its documentation remain available, whereas conversational context from earlier sessions is not automatically carried forward not [3]. Without memory, the agent has to recover these facts again, or the user has to repeat them: which database a service uses, which branch it deploys from, who is on call. A persistent memory carries such facts from one session to the next. Most of these facts change over time. They appear in user messages, tool output, documents, and code changes. A fact may be updated, restated, or contradicted by a stale docu-ment [4],or by the agent’s own earlier erroneous inference [5]. Sometimes the user asks the agent to forget it [6]. A memory that returns an old value next to the current one, trusts a guess over the user, or brings back a deleted value can carry that error into later sessions [6], [7]. Two simple approaches are the standard baselines in recent memory benchmarks [8], [9]. Full-history replay sends the whole past conversation with every question. Nothing is lost, but the context grows with the history, and old, wrong and deleted values reach the model with the current one. Retrieval over transcripts (transcript RAG) sends only the few past turns most similar to the question. The context stays small, but the search can miss the right turn or return an outdated one. In both cases, the model has to decide on every question which value is current. Dedicated memory systems [3], [10]–[12] reduce what the model reads, but the model still decides when a stored fact is replaced or removed, and their described mechanisms do not generally provide explicit, user-configurable source-reliability rankings. To the best of our knowledge, no prior benchmark jointly evaluates memory correctness, source trust, deletion compli-ance, and evidence-level provenance in multi-session coding or conversational agent settings. Existing benchmarks such as LoCoMo and LongMemEval evaluate long-term memory primarily through downstream question answering; LoCoMo additionally reports retrieval recall, but neither benchmark [8], [13] audits whether the evidence ultimately provided to the model reflects the current, trusted, and non-deleted state of the underlying facts. The objective of this study is to test whether an agent memory can stay correct when facts change, when sources differ in reliability and when users ask to forget, while sending the model far less text than full replay. We ask three questions:  

> •

RQ1: How well does the complete system, with LLM extraction and routing, keep stale, contaminated and deleted values out of the evidence it sends to the model?  

> •

RQ2: Does such a memory answer better than replay, transcript RAG and an existing memory system under the same answering model and prompt?  

> •

RQ3: As the history grows, does it stay correct, and how do its context, storage and model cost grow? We move some decisions out of the model. In L EDGER , a language model still extracts candidate facts and routes each question to stored facts. Fixed rules then decide which value is current, which source wins a conflict, and what a deletion erases. L EDGER +E P adds a search over raw conversation turns for questions the ledger does not cover. Our contributions are: 1) Memory design. We propose L EDGER , a fact-centric memory system that maintains current values, validity intervals, provenance, and deletion state under five in-gestion rules governing updates, conflicts, and source precedence. L EDGER +E P extends L EDGER by retaining 1arXiv:2611.20927v1 [cs.MA] 16 Nov 2026 raw turns, which are scrubbed upon deletion. 2) Evidence-level evaluation. We introduce an evaluation protocol that audits both the evidence packet supplied to a fixed answering model and the resulting answer, clas-sifying retrieved errors as stale, conflicting, untrusted, or deleted. The protocol reports answer accuracy, re-trieval correctness, token use, cost, latency, and storage overhead on a synthetic coding-agent workload with controlled updates, conflicts, deletions, and a simulated 540-day replay. 3) Controlled comparison. We compare LEDGER and LEDGER +E P with no memory, full replay, transcript RAG, and Mem0 under identical model, prompt, and token-budget conditions. Evaluations cover development and held-out coding-workload seeds and a 210-question LongMemEval subset. Section. IV-D states which challenge requirements we cover and which, such as a downstream agent task, we do not. II. P ROBLEM DEFINITION AND SCOPE 

A. Problem setting 

An agent works with one or more users over many sessions. Each session produces a stream of events : user and assistant messages, tool calls, tool results, documents and code changes. Every event has an id, a user, a session and a timestamp. Our replay uses these timestamps as a logical clock: sessions are ingested in timestamp order, events with the same timestamp keep their stream order, and an event counts as ingested at its timestamp. Some events state facts : a property of an entity whose value can change, such as the database a service runs on. A memory reads these events. When the agent asks a question, the memory returns a small amount of evidence for an answering model, or abstains. Facts have two kinds of time. Valid time is the period in which a value was true. Recording time is when the memory learned it; on the replay clock, this is the timestamp of the event that stated it. A question is asked at a time t. It can ask about now, or about an earlier time t′ (as of t′). The correct answer is the value that was valid at t′ (or at t), based only on what was recorded up to t. L EDGER uses a restricted form of this setting, in which the two times are the same (A4). When a value changes, the old value is not removed: its valid time ends at the change, so it leaves current answers but still answers questions as of an earlier date. Deletion removes a value from both.

D. Assumptions and scope 

LEDGER guarantees the properties only under four assump-tions: A1 Correct extraction. For every event that states a fact, the extractor returns a claim with the right value and the same slot key each time the fact is mentioned. It returns no claim for text that does not assert a value, such as a question, a plan or a negation. A2 Correct routing. Each question and deletion request is mapped to all the slots it is about, and to no other. 2A deletion request whose source events were extracted does not need routing. A3 Trust order. The source ranking matches how reliable sources are. A document that is newer and correct but conflicts with the user is disputed, not accepted. A4 Valid time starts when a value is stated. We do not read dates written in the text. Each entry stores only a start time, the timestamp of the event that stated the value, and an end time, the timestamp of the event that replaced it; on the replay clock, the recording time equals the start time. A change reported late, such as “we migrated last Tuesday”, is therefore dated to the message that reports it. A1 and A2 are idealised conditions. Our extractor and router are LLM calls and do not always meet them; when they fail, the properties that depend on them can fail too, and Sec. V-F counts how often. LEDGER +E P keeps I7, and I1 with one open case; the other properties hold for its ledger facts but not for the raw turns it adds. We study facts with one current value each, in English text, from coding-agent sessions and from LongMemEval chats. III. LEDGER A RCHITECTURE AND MECHANISMS 

A. Architecture overview 

Figure 1 shows the components. An extractor reads each ingested session and proposes claims : this event states that this property has this value. The ledger core applies fixed write rules to each claim, and it alone decides what is current, trusted or deleted. A router maps each question or deletion request to the slots the ledger knows. In our main setup the extractor and the router are calls to a language model. A rule-based extractor serves as a model-free floor. We evaluate three variants:  

> •

LEDGER : the ledger alone. It returns one fact line per matched slot, or abstains.  

> •

LEDGER +E P fallback : adds an episode store of raw turns. It returns the ledger’s facts whenever the ledger has any, and BM25-ranked turns [14] only when it has none.  

> •

LEDGER +E P augment : always returns the ledger’s facts first, then fills the rest of the token budget with turns. The episode store exists because the ledger models only facts with one current value. Some questions are not about such facts: what the assistant recommended, a one-off detail in a long chat, a count across sessions, or a fact whose first statement the extractor missed. Raw turns are not filtered by the rules, so they can carry an old or less trusted value; Sec. III-D states when each mode adds them. 

B. Data model and time 

Memory is partitioned by user. A slot is a prop-erty of an entity, keyed entity/attribute (e.g. 

payments-service/database ). Each value a slot has held is an entry with a validity interval [from , to ) [15]. The interval starts at the timestamp of the event that states the value (A4) and ends when a newer value supersedes it. A question asked at t as of t′ returns the entry that was valid at t′ and recorded by t. An entry also keeps the source kind and trust of the event that set it, and the ids of every event that stated it. When a more trusted source restates the value, the entry takes the higher trust, so a later conflicting document is disputed. Besides entries, the ledger keeps three kinds of records that are never retrieved: disputed values from less trusted sources, kept for audit; unconfirmed values, held until a trusted source states a value; and tombstones , which record that a slot was deleted but not its value. 

C. Ingestion and conflict resolution 

Extraction. For each ingested session, the extrac-tor makes one structured-output call and returns claims 

⟨event , slot , value ⟩. It sees the user’s known slots and their current values, and is asked to reuse a known key for the same property. Keys are normalised only in form, so synonyms such as “inventory” and “inventory-service” become two slots. Claims are applied one at a time in the order of their events. Events already ingested are skipped by id (I4). The ledger core never reads free text. Two safeguards check the extractor’s output before any rule applies: 1) Enumerated event ids. The output schema lists the ids of the batch’s events, so a claim can only cite an event that exists. 2) Grounding check. A claim is kept only if its value occurs as text in its event, ignoring case and punctuation. This drops invented or copied values, but not a value in a negation or a sentence about another service. A third safeguard concerns deletion. 

Write rules. The core applies one of five rules to each claim, in stream order: restate same value as the current entry, from any source: add the event to its provenance and keep the higher of the two trust levels; no new value entry (I4); supersede different value from a source at least as trusted as the current entry’s: close the current entry at the claim’s time and open a new one (I2); the closed entry still answers historical questions (I3); dispute different value from a less trusted source: kept for audit, never retrieved (I5); introduce no current value, source trust ≥ 2: open an entry; hold no current value, source trust < 2: keep the value as unconfirmed. If a trusted source later states the same value, it becomes an entry valid from the trusted statement; if it states a different value, the held value becomes a dispute. D. Retrieval and abstention 

The router maps the question to slot keys chosen from a list of the user’s known slots, so it cannot invent a slot. For each matched slot, the ledger returns the one entry valid at the question’s as-of time and recorded by the time it is asked, as a single line with its validity and source. Matched slots without such an entry are left out. When none of them has one, the ledger abstains with a reason: “no known slot matches”, “deleted at the user’s request” or “only an unconfirmed claim” (I6). Under A1 and A2, the evidence therefore never contains a disputed, unconfirmed or deleted value. In L EDGER +E P, the episode store ranks the user’s stored turns with BM25 and adds the top five, each with its date and source kind, while they fit in the token budget left after the facts. Turns are not filtered by the as-of time. Fallback mode searches only when the ledger returns no fact; augment mode 4always adds turns after the facts. A question that matches only deleted or empty slots is refused in both modes. If it matches a deleted slot and a live one, augment mode still adds turns, so here only episode scrubbing keeps the deleted value out. 

E. Deletion 

Affected slots. If the request carries source event ids, the affected slots are those with any entry, dispute or unconfirmed value from these events. An id cannot single out one fact of an event that states several, so all slots stated by these events are affected; in our coding workload each event states at most one fact. If there are no ids, or the extractor never turned these events into claims, the router maps the description to known slots. As a third safeguard, we also add every slot the description names outright. One routing call can return no slot, and a missed slot is a privacy failure. 

Ledger deletion. For each affected slot, the ledger erases every entry, dispute and unconfirmed value recorded up to the request, past values included (I1). Each affected slot keeps a tombstone without its value. The extractor is never shown an erased stored record again; a value the user states after the request opens a new entry, while questions about earlier times still abstain. 

Episode scrubbing. LEDGER +E P removes from the episode store every event behind an erased value, every turn that mentions an erased value, every turn up to the request that names a deleted slot outright, and every assistant or tool-call turn up to the request that names an entity the request is about. The last two rules cover what the ledger never extracted. Scrubbing more turns lowers the risk of exposure but can also remove useful details; we did not measure this loss of recall. Every removed event is blocked, so a replay after a crash cannot ingest it again. 

Guarantee and limits. After a deletion, no value recorded before the request is returned again, for current or past questions, by L EDGER or by either mode of L EDGER +E P.This holds when the affected slots are found (A2) and the extractor captured the statements of the value (A1). One case remains open in L EDGER +E P: a trusted turn whose value the extractor missed, and which names neither the deleted slot nor any erased value, stays in the episode store and can still be returned. Deletion does not reach earlier snapshots, the response cache or run logs, which a deployment would also have to clear. 

F. Persistence and isolation 

Each store writes its full state, including tombstones and blocked ids, to one JSON file and can restore it; L EDGER +E P

writes both stores to the same file. In our runs a snapshot is taken after every checkpoint; the file is not written atomically, and we did not test a crash during a write. All state is partitioned by user, and retrieval and deletion only touch the partition of the user id they are given (I7).

IV. E VALUATION DESIGN 

A. Coding-agent workload with planted ground truth 

A seeded generator produces multi-user, multi-session coding-agent timelines. Each user owns several services; each service has 3–5 facts drawn from nine kinds (database, test command, deploy branch, staging host, runtime, message queue, CI provider, cloud region, on-call owner). A state machine writes each fact’s history as mutations : introduce, restate, update, contradict (from a document or the assistant only) and delete (from the user only). Every mutation is rendered by a template of its source: user message, tool output, code diff, document, or assistant message, alongside chit-chat, tool calls and distractors that name a topic without a value. At checkpoints the generator asks probes of six types: current ,

post-update , historical (with an as-of time), contamination ,

post-delete and abstention . The complete generator settings (mutation weights, source mix, probe counts per type) are in the supplement (S1). 

Ground truth. Expected answers come from a function of the workload code that reads only each mutation’s kind and time: the answer is the last introduced or updated value at the target time, after the last deletion. It never calls a memory system and never reads event kinds or trust. A text check verifies that no event mentions a value it does not carry, and values are unique per user. We wrote the workload, the oracle and L EDGER together, and the workload encodes the same trust policy: contradictions come only from documents and the assistant. It therefore tests whether a memory follows this policy, not whether the policy is right (A3). Held-out seeds and LongMemEval are our checks against fitting the workload. We use two presets (Table IV): small for the main com-parison and ablations, and long , a simulated year and a half of sessions, for behaviour over time. Seeds 5–9 of the small preset are held out: no design decision was made on them. 

B. LongMemEval 

LongMemEval_S [8] has 500 questions, each after a history of about 48 chat sessions. We group the questions into seven categories (six question types and abstention) and draw 30 from each with Python’s random.sample and seed 0 5(210 questions; ids in the artifact). Each history is replayed session by session in date order into a fresh store, and the question is asked at its date. Answers are judged with the benchmark’s own prompts, verbatim, on its judge model 

gpt-4o-2024-08-06 at temperature 0; the only change is that the judge returns yes /no in a JSON field. Before the main run, a 14-question pilot, drawn in the same way, chose between the fallback and augment modes; we report both. Ten pilot questions are also in the 210, so mode selection saw part of the evaluation set and we do not treat it as untouched test data. Without them, accuracy changes by at most one point per system (augment 75.0%, full replay 74.0%), and no conclusion changes; the ten ids and these scores are in the artifact. To check the judge, one author audited 60 of its decisions without knowing the system: for full replay, transcript RAG and L EDGER +E P in augment mode, 10 the judge accepted and 10 it rejected, covering all seven categories. The judge agreed with the human on 59 of 60 (98.3%, Cohen’s κ = 0 .97 ). Mem0, L EDGER and fallback mode were not audited, so this agreement does not validate every system’s score. 

C. Protocol 

Systems. No memory; full replay (the whole history, un-bounded); transcript RAG (BM25 over events, top 5, within the budget); Mem0 [10] (OSS release 1.0.11, unmodified, with a local vector store, text-embedding-3-small and our extraction model; top 10), and the same with its list of personal fact types replaced by our extractor’s definition of a coding fact, fixed before any run ( coding prompt ); L EDGER 

with the LLM extractor and with a rule-based extractor (four hand-written regular expressions, a model-free floor, not a tuned baseline); and L EDGER +E P. Bounded systems share one evidence budget (2,000 tokens on the coding workload, 4,000 on LongMemEval); the runner truncates whole items, but in our runs it never cut any evidence (see below). 

Shared answerer. Every system’s evidence goes to the same model ( gpt-4.1-mini-2025-04-14 , temperature 0, fixed seed) with the same prompt, memory first and question last. The answer is structured (value, abstain flag), so on the coding workload abstention is read from a field and answers are scored deterministically against the planted truth with no LLM judge. An empty or refused answer counts as an abstention. 

Two scores. Each probe of the coding workload is scored twice. The evidence verdict scores what memory sent to the model; the answer verdict applies the same rules to the shared model’s answer. A value counts as present when its text, or a fixed alias such as “PG N ”, appears as a whole phrase, ignoring case. Each forbidden value is labelled by why it is wrong: resurrected (stated before the last deletion), and after it stale (set before the target time), future (set after the as-of time) or contaminated (from a contradiction). In a historical question, the value valid at the as-of time is the correct answer, not a forbidden one. Verdicts follow a fixed order. For a probe with an expected value: false abstention if the system abstained; otherwise 

correct (the value appears, no forbidden value does), polluted 

(both appear), wrong (only a forbidden value) or missed 

(neither). For a probe whose truth is to abstain: leaked if a forbidden value appears, even if the system also abstained; otherwise correct if it abstained, or no abstention . Deleted-value counts are read from the evidence, whatever the verdict. At the evidence level only an explicit abstention by the memory counts, so systems without an abstention signal (no memory, full replay, transcript RAG) score no abstention on these probes. Only correct counts as a success. 

Aggregation and intervals. Evidence and answer accuracy are the share of correct verdicts over all probes of a seed. We report the mean and sample standard deviation over seeds; counts are pooled over seeds, and a probe counts once for each type of forbidden value it contains. On LongMemEval, each system runs once on the same 210 questions; accuracy describes the balanced subset, not the benchmark’s own mix. Its 95% interval is a percentile bootstrap over questions (2,000 resamples), and two systems are compared with a paired bootstrap on the same questions. We do not correct for multiple comparisons, so these comparisons are exploratory. 

Cost and efficiency. The runner, not the system, measures latency, counts all injected tokens, and converts model usage to dollars with prices pinned on 2026-10-19 (input charged as uncached, an upper bound). All token counts are model tokens of the answering model’s tokenizer ( o200k_base ). Our runs counted words and punctuation marks when fitting the budget; the largest bounded evidence set was 205 model tokens on the coding workload and 2,538 on LongMemEval, so neither count cut any evidence, and we recount every logged evidence set with the model tokenizer. Latency is wall-clock time around each system call on one laptop (Apple M5, 16 GB), one call at a time, including model and embedding calls; LLM timings come from uncached repeats, because a cached replay is not a timing. We report write cost per session or history, read and answering cost per question, injected tokens, latency and store size. 

Reproducibility. Extraction, routing, Mem0’s writes and answering use gpt-4.1-mini ; every logged response re-ports the snapshot gpt-4.1-mini-2025-04-14 . Sam-pling is pinned (temperature 0 and a fixed seed); every response is cached on disk under a hash of provider, model, prompt and schema, so a run replays at zero cost. Five seeds give variance across workloads; repeated runs with the cache bypassed measure the model’s own noise. Code, workloads, pinned prices, all run logs, sampled ids, per-seed results, the pilot analysis, the cost breakdown and the supplement are available at https://anonymous.4open.science/ r/memory-challenge-4482/. 

D. Coverage of the challenge requirements 

We measure directly persistence across sessions and restarts, provenance, update, supersession and deletion, bounded evi-dence and abstention (R1); an established benchmark, required 6baselines under the same model, prompt and budget, and quality, tokens, cost, ingest time, latency and storage (R2); and checkpoints, typed stale errors, growth, pinned models and repeated runs (R3). We cover four only in part: our traces are heterogeneous but generated from templates; latency growth over time is not reported, because the long-preset replays were cached; the judge audit covers three of seven configurations; and, the main gap, no agent performs a downstream task. A shared model answers questions at checkpoints, so we measure whether memory provides the right facts, not whether an agent fixes a bug or deploys a service better with memory. The full mapping is in the supplement (S2). V. R ESULTS 

A. Wrong values in the evidence (RQ1) Trust. With the whole history in context, full replay’s evidence is clean in only 21.9% of probes (Table V). Its answers are right in 82.1% of probes, but 65 of them contain a forbidden value. In 45 of these the model sides with a stale document or with the assistant’s own guess over the user, and it answers only 31 of 67 contamination probes. L EDGER answers 62 of 67, because the less trusted claim never reaches the context. Its evidence is correct in 91.7% of probes. Four of its answers contain a forbidden value, all stale values from updates the extractor missed. 

Model-decided updates. Mem0 lets the model add, update or delete each extracted fact. An update overwrites the memory in place, so the value an earlier date needs is gone: Mem0 answers 27 of 93 historical questions (L EDGER 69, full replay 74), and 27 of its answers give a later value for an earlier date. With the coding prompt it answers more current questions (96 instead of 86 of 112), but its contaminated answers rise from 10 to 27. Mem0 and L EDGER also differ in extraction, routing and retrieval, so this comparison does not isolate one cause. 

Deletion. When deletion requests carry only a description, the transcript baselines remove nothing. Full replay sends the deleted value to the model in 46 probes and repeats it to the user in 4; transcript RAG sends it in 39. At answer level the leak is mostly hidden, because the model also sees the “forget it” message. For Mem0 the request is handled only by its ordinary update step, which kept the value: it reached the model in 18 probes and the user in 17 (16 and 13 with the coding prompt). This is a result for the evaluated configuration. LEDGER and L EDGER +E P sent no deleted value, in either mode.

D. Operational reliability 

Restarts. We tested five systems: full replay, transcript RAG, L EDGER with both extractors, and L EDGER +E P in augment mode. After every checkpoint of the long preset, we wrote each store to disk, restored it into a fresh instance and continued. For every system, all 1,379 probes got the same verdict and evidence as in the run without restarts. Snapshots stay under 270 KiB and restore in at most 63 ms. 

Model change. In L EDGER +E P (augment mode, long pre-set, seeds 0 and 1), we switched the model behind extraction and routing from gpt-4.1-mini to gpt-4.1 after the fourth of eight checkpoints and kept the store. No migration was needed. Second-half accuracy rises from 92.0% (mini throughout) to 95.4%, within 0.3 points of a run on gpt-4.1 

throughout (95.7%), at $1.18 for extraction and routing against $1.89 on gpt-4.1 throughout. 

Run-to-run noise. We ran L EDGER and L EDGER +E P (fall-back) three times per seed, twice with the response cache bypassed. In 12 and 8 of the 512 probes, the answer verdict differed in at least one run. The standard deviation of accuracy across repeats is 0.7 and 0.4 points per seed, far below the differences between systems.

H. Limits of the results 

The coding workload is synthetic, built by us, and phrased by templates, and our lead over full replay is about four points smaller on held-out seeds. Its histories stay short (about 4.4k tokens per user at the end), so the long preset tests growth in facts and updates more than in context length. The runs include extraction and routing errors, so they show how close the full system comes to the guarantees of Sec. II, not that they hold. Restarts happen only between checkpoints, and the model change covers one upgrade within one model family, on two seeds. 9VI. D ISCUSSION 

The evidence–answer gap. The answering model hides much of the difference between memories. It often picks the right value from noisy evidence, so full replay answers 82.1% of the coding probes while its evidence is clean in only 21.9%. This repair weakens as history grows, and it never helps privacy: a deleted value that the model does not repeat has still been sent to the provider. In our runs, the largest differences between memories came from deciding what is current, which source wins and what was deleted, more than from finding facts. Memory should therefore be judged on its evidence as well as on its answers. 

Configuration trade-offs. The variants differ in who is responsible for correctness. The ledger alone sends only values that passed its rules, but abstains when it has no fact. Fallback mode adds raw turns only on those questions, so it keeps forbidden evidence low (16 probes against 193 for augment) at almost the same accuracy; we recommend it where facts change and sources disagree. Augment mode relies on the answering model to prefer the fact line and suits long chats with many one-off details, as on LongMemEval. Construct validity. We built both the coding workload and the system, so the workload may favour our design. Every system runs on the same timelines with the same answerer, and we also report LongMemEval, which we did not design. Our workload states every change when it happens, so it never tests A4, and how often real traffic breaks A3 or A4 is untested. The LongMemEval judge is a model, audited for three of the seven configurations. 

Internal validity. We developed the rules and safeguards while looking at failures on seeds 0–4, and we report results on these seeds. Held-out seeds 5–9, run once, show that the results do not depend on the timelines we inspected, but not that they hold outside the generator, because new seeds use the same templates, fact kinds and mutation rules. The LongMemEval mode choice used a pilot that overlaps the evaluation set. 

External validity. The coding workload uses templated phrasings and nine kinds of facts. Real traces are messier, and other fact kinds or phrasings may be harder to extract and route. All extraction, routing and answering use one model family ( gpt-4.1-mini , and gpt-4.1 in the model-change run), and all text is English. Other model families may extract differently. Besides the baselines, we compare against one memory product, Mem0; Zep and A-MEM are not evaluated. 

Conclusion validity. The coding results use five seeds, and the standard deviation of our systems is up to 5.5 points. The LongMemEval subset is 210 of 500 questions. Differences of a few points, such as between L EDGER +E P and Mem0 or full replay, lie within the paired confidence intervals, which are not corrected for multiple comparisons; small differences should not be read as rankings. VIII. R ELATED WORK 

Persistent agent memory. Several systems give agents memory that lasts beyond one context window. MemGPT [3] moves text between the context and external storage, and the model edits its own memory through function calls. Mem0 [10] extracts facts from each session and lets the model add, update or delete them. A-MEM [12] stores notes that the model links and rewrites over time. Zep [11] keeps a temporal knowledge graph whose edges record when a fact held, and uses the model to find contradicting edges. Other work stores reflections [16], reusable skills and workflows [17], [18], or a graph index for retrieval [19]. In all of these systems the model decides when a stored fact is replaced or removed; in LEDGER it only proposes claims, and fixed rules decide. Zep is closest to our design, since it also keeps when a fact held, and it also tries to read such dates from the text, which our ledger does not. Mem0 is closest to our pipeline, but an update overwrites the stored text, so the value an earlier date needs is gone. 

Temporal and provenance-aware data management. The ideas we use for storage are well established. Temporal databases keep the time during which a fact was true (valid time) apart from the time it was recorded, so a change can be entered after it happened, and they close an interval instead of overwriting a row [15]. Our ledger uses only a restricted form: valid time starts when a value is stated (A4), so it does not recover the real date of a change reported later. Provenance research records which source produced each piece of data [20]. Our contribution is to bring them into agent memory, where the facts come from a language model and not from a trusted application. This requires parts that a database does not have: a trust order over sources that decides which value wins, a lexical check that rejects claims whose value does not appear in their source event, and deletion that also removes matching raw turns and blocks their source events from being written again. 

Memory evaluation. LoCoMo [13] tests recall over very long conversations. LongMemEval [8] tests five abilities, in-cluding knowledge updates, temporal reasoning and absten-tion. MemoryAgentBench [9] adds conflict resolution and finds that no current method masters all of its competencies. These benchmarks score the final answer, and their histories contain no deletion requests. Our evaluation also scores the evidence, labels each wrong value by why it is wrong, and tests deletion by description, restarts and a model change. IX. C ONCLUSION 

We presented L EDGER , an agent memory in which a model proposes facts and explicit rules decide which value is current, which source wins and what is deleted, and L EDGER +E P,which adds raw turns. Our strongest supported finding is about 10 evidence: on a coding workload with planted changes, con-flicting sources and deletion requests, L EDGER +E P in fallback mode sent a forbidden value in 16 of 512 probes, against 249 for full replay, and no deleted value, while answering more questions correctly on both development and held-out seeds. On LongMemEval it reached the same observed accuracy as full replay with 1% of the context.
