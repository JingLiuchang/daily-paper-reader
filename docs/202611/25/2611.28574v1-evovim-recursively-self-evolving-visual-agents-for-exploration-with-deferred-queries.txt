## Abstract 

Multimodal large language model (MLLM) agents have shown promising capabilities in task-oriented environ-ments. However, they still struggle when queries are de-ferred until after exploration, requiring them to retain vi-sual evidence before knowing which details will matter. We introduce EvoViM, a recursively self-evolving framework in which a frozen multimodal model turns its own interaction experience into one visual program for memory and skills. The program retains images and computes directly on pix-els, and its operations decide how this evidence is used in each task. During memory evolution, the same model traces failures in its visual trajectories to the operations that lost or misused evidence and revises them. It also rewrites the notes and analysis tools that guide later revisions, which then build on earlier findings and skip changes that have already failed. We evaluate EvoViM with three multimodal models on six tasks covering visual matching, spatial recall, and sequential decision-making, including three tasks with deferred queries. Across the six tasks, EvoViM improves the average score over AutoMem, the strongest baseline in the main comparison, by 31.3–47.6 points on held-out episodes. Programs written once from the initial environ-ment instructions perform substantially worse, highlighting the value of interaction experience in shaping how visual evidence is retained and used. Code and dataset are avail-able at https://evovim.github.io/ .

## 1. Introduction 

Multimodal large language model (MLLM) agents have made rapid progress in task-oriented environments, where they navigate websites [41], operate computers [30], and play video games [14, 21] from screenshots. In these en-vironments, the instruction is given before interaction be-gins and guides what the agent looks for and remembers. 

> *Corresponding author.

However, some tasks require an agent to explore before it receives the question [11]. For example, an agent may walk through a gallery and later be asked where a re-photographed painting hung, although its instructions never mentioned the paintings (Figure 1(b)). We study explo-ration with deferred queries, in which the queries are re-vealed only after the agent has explored the environment. Existing agents keep past observations in memories that are either designed by hand or evolved from experience. Hand-designed memories store text notes or frames [5, 17, 27], and their designers fix how the stored evidence is re-trieved and used. Even when such memories store ev-ery frame, they adapt poorly to different tasks. Memory-evolution methods learn the rules from experience and adapt them to the task [28, 31], but the memory they evolve is text, which cannot record the visual details that separate near-identical images [4, 22]. These methods therefore break down when the decisive evidence is hard to put into words. In this paper, we study exploration with deferred queries in multimodal settings and propose EvoViM, a recursively self-evolving framework that learns memory and skills from interaction as one visual program. We treat memory and skills as two uses of experience. The program holds the ob-servations of the current episode, and its operations, shaped by earlier episodes, decide what to keep and how to use it. These operations process pixels directly to retrieve evi-dence from past observations or to suggest actions from the current state. In EvoViM, one frozen MLLM executes tasks with the current program and revises the program between generations. During revision, it reads the visual trajectories of development episodes, traces each failure to the opera-tion that lost or misused the evidence, and rewrites that op-eration. It also rewrites the notes and analysis scripts that guide later revisions, so that it can build on earlier findings and avoid repeating failed changes. We first construct three interactive visual tasks with de-ferred queries. The agent must retain visual details that are difficult to describe in words, then use them to answer ques-tions revealed after exploration. ## 2. Related Work 

2.1. Multimodal Agents 

Multimodal agents use visual observations to act in games, websites, and desktop environments. Cradle uses screen-shots with keyboard and mouse control to play games and operate desktop software [21]. SeeAct combines screen-shots with HTML elements to ground actions on live web-sites [41], and OSWorld evaluates agents on real com-puter tasks, including workflows that span several ap-plications [30]. Game benchmarks such as BALROG, VideoGameBench, and GameWorld show that long-horizon play remains difficult [14, 16, 37]. Some decisions re-quire evidence from observations that have already left the screen [3]. OpenEQA directly evaluates the use of past observations through questions about previously explored physical environments [11]. These works do not address how agents can improve their visual memory from experi-ence gained during interaction. 

2.2. Agent Memory and Skills 

To reuse past observations, many agents keep them as tex-tual records or summaries [15, 18, 29], which can omit vi-sual details needed for later tasks [4, 22]. Visual mem-ories retain images for retrieving past experience [27] or recalling explored places [17, 33], while VISTA archives every frame [5]. Experience can also be reused through learned operations. Voyager accumulates executable action skills [25], and MemSkill evolves skills for building and up-dating textual memory [38]. AtlasVA connects visual mem-ory to skill learning by evolving spatial maps from trajec-tory statistics and using them to guide reinforcement learn-ing [26]. However, the rules for organizing and using visual evidence in these systems are still predefined.

## 3. Why Do Existing Memory Designs Fall Short with Deferred Queries? 

Current MLLM agents can follow instructions to complete tasks in visual environments. With deferred queries, how-ever, the agent explores with only basic environment in-structions and receives the questions afterward. It must de-cide what to retain without knowing which visual details will matter or how those details will be used. We build three tasks to examine how existing memory designs handle this setting. We compare evolved text memory with a hand-designed vi-sual memory, then test whether the model can infer the re-quired operations from the initial instructions alone. We find three key limitations that cause existing memory de-signs to fail in exploration with deferred queries. 

Text descriptions lose visual distinctions. Text mem-ory evolved from experience [28] answers most DMV-Hard questions about photo details but almost none about gener-ated patterns (Figure 4). Its descriptions of one pattern often fit several others, so the stored notes cannot distinguish the queried item. On MC Gallery and Poster Maze, its scores are no higher than those obtained by answering not seen to every question (Table 1). 

A visual match does not ensure a correct answer. To preserve these distinctions, we test a hand-designed vi-sual memory based on VISTA [5] that keeps every frame for later inspection. This archive alone still scores below evolved text memory on DMV-Hard. Adding a matcher that runs at every step lets it answer most DMV-Hard ques-tions, as the matched page identifies the product. In MC Gallery and Poster Maze, the matcher usually retrieves the right view for previously seen pictures, but the agent often fails to answer correctly. The program lacks operations that associate the match with a location and determine whether the queried picture was seen at all. 

One-shot programs often prepare for the wrong ques-tions. We therefore test whether the model can infer the required operations from the initial environment instruc-tions alone. One gallery program records the order of the doors passed, whereas the later questions ask where each painting hung. On MC Gallery and Poster Maze, these pro-grams show no clear gain over the initial set of basic image tools. The questions encountered during interaction provide the experience needed to revise what the program keeps and how it uses that evidence. 

## 4. Method 

EvoViM turns the experience of an agent into a visual pro-gram for memory and skills (Figure 2). Within an episode, the program stores observations and maintains state. Its op-erations, which decide what to store and how to use it, are shaped by earlier episodes. One frozen MLLM executes tasks with the program and, between generations, revises these operations from development episodes. It also revises the guidance and analysis tools used to diagnose failures in later generations, so the evolution is recursive. 

4.1. Memory and Skills in One Visual Program 

The visual program defines memory operations and image-processing tools in Python, with prompts that guide the model in using them. The code and prompts remain fixed during an episode, while stored observations and state are updated through interaction. These memory contents are reset at the start of the next episode. In MC Gallery (Fig-ure 2), for example, the evolved program instructs the model to save a view at each door during the walk. When a query painting appears, a matching tool compares it with the saved views and reports that the best match lies to the left of door 7. The model then submits this answer. The starting program stores lossless frames with text metadata and has no pixel matcher. Evolution can change what frame memory retains and how it is organized, allow-ing the program to store whole views, object crops, or pixel features linked to locations. Pixel computation lets it pro-cess this stored evidence alongside the current image. These operations preserve the visual distinctions between similar images that text notes lose (Section 3). To make stored evidence available at a decision, visual recall places selected frames, crops, or montages in the next model request. Revisions can change which text and images appear in each prompt, so the program determines what the model sees when it uses memory. The same code can read the current frame and the accumulated state to score candi-date actions or suggest the next action. In Card Matching, for example, the program combines remembered card loca-tions with pixel matching to suggest the next flip. During task execution, the model uses these operations in a Record phase followed by an Act phase (Algorithm 1). It first examines the observed outcome of its previous action and decides what to record, then consults memory to choose the next action. Each phase starts a new conversation, while the episode memory remains available through the program. Within that conversation, every request includes the current image, and tool results enter the next request. The model then submits its chosen action through the fixed interface. The model and this execution procedure remain fixed during evolution. 

4.2. Revising Programs from Interaction Feedback 

The development episodes recorded during task execution provide the evidence for revising the program. We first run the starting program to obtain the episodes used by the first revision. At every generation, the model uses a command-line coding tool to inspect the parent program and its devel-opment episodes, including frames labeled by step, memory snapshots, and tool results. Records of earlier candidates show how previous changes affected task outcomes on the development episodes. To help the program generalize to new episodes, each revision uses evidence from two development seeds. The model is asked to check each proposed change against both episodes and explain why it should work on unseen in-stances. The revision instructions prohibit embedding facts from development episodes in the code and require the pro-gram to obtain episode-specific information from observa-tions during execution. Feedback reports results separately for each seed, so later revisions can identify changes that help one episode at the expense of another. Enhanced feedback guides revision by connecting task outcomes to how the program handled visual evidence. Episode digests summarize the outcomes, while tool-use statistics show which memory operations the agent called. A candidate that passes these checks then runs on the same two development seeds as its parent, with one episode per seed. The gate accepts a candidate if its mean development score is higher. For a score tie, the candidate must succeed on every development seed and use fewer steps or tokens without increasing the other. If the candidate fails the code checks or the gate, the model revises the same parent once more using the rejected code and failure evidence. After the final generation, the last accepted program is fixed and evaluated on held-out seeds disjoint from the de-velopment seeds. DMV-Hard adapts the product-browsing task of DMV-Bench [22]. Metrics. We report the fraction of pairs cleared for Card Matching and answer accuracy for DMV-Hard. MC Gallery asks about six seen paintings and two unseen lures. Poster Maze asks about at most six clearly observed posters and two lures, so the number of questions depends on explo-ration. Both tasks divide the number of correct answers by eight, and a lure counts as correct only when answered not seen . Always giving this answer scores 25%. For Tetris and Pac-Man, we use GameWorld’s normal-ized task progress. Tetris awards points for both dropping pieces and clearing lines. Scores are reported as percentages, with equal weight given to each task in the overall average. We compute 95% confidence intervals using 10,000 paired bootstrap resam-ples of the held-out seeds within each task. 

Baselines. We choose baselines by how they retain past observations and whether their memory operations evolve. The No memory baseline provides a reference without stored observations, while Rolling summary compresses past interactions into text in the style of ReSum [29]. Hand-crafted text provides a note-taking tool and is the starting program for AutoMem. Hand-crafted visual provides five tools for frame storage, annotation, metadata search, recall, and deletion. EvoViM starts from this program. These four baselines keep their memory mechanisms fixed. Au-toMem [28] evolves a text memory program from inter-action. To evaluate AutoMem in visual environments, we provide the current image at each execution request while retaining its original text memory design. For this compar-ison, we use the same MLLM to execute and revise its pro-gram. AutoMem accepts a candidate only when its mean development score improves. 

Models and protocol. We use GPT-6.1 Sol [13], Claude Haiku 5.5 [2], and the open-weight Qwen3.8-27B [19]. Claude Haiku 5.5 revises its programs in Claude Code [1], while GPT-6.1 Sol and Qwen3.8-27B use Codex [12]. Both evolving methods develop a separate program for each task and model over three generations on the same two develop-ment seeds. Each generation allows one candidate and at most one retry. 

5.2. Main Results 

Overall performance. EvoViM exceeds AutoMem, the strongest baseline in the main comparison, by 31.3 to 47.6 points in average score (Table 3). The paired bootstrap con-fidence intervals for this improvement exclude zero with all three models. When scores are averaged within each abil-ity group, EvoViM also ranks first, except for sequential decision-making with GPT-6.1 Sol. 

Visual matching. On DMV-Hard, EvoViM answers questions about photo details and generated patterns with similar accuracy, while AutoMem succeeds mainly on photo details (Figure 4). A matched page directly iden-tifies the product through its URL, so VISTA-style mem-ory answers most questions when a matcher automatically searches its stored frames at every step. Every EvoViM agent clears Card Matching, where evolved text memory leaves many pairs unmatched. With Qwen3.8-27B, the flip count on every held-out board matches that of RNG-Bench’s greedy policy with perfect memory and row-by-row exploration. 

Spatial recall. With Claude Haiku 5.5 and Qwen3.8-27B, EvoViM outperforms VISTA-style visual memory on MC Gallery and Poster Maze even when it is given a generic matcher. The evolved programs link stored views to lo-cations and use these associations to answer queries. On Poster Maze, the fixed visual memories almost never lo-cate a previously seen poster correctly, whereas EvoViM identifies the correct wall for most of them. Text memory remains competitive when descriptions are distinctive and stable across observations, as on Poster Maze with GPT-6.1 Sol. 5.4. Failure Analysis 

Attributing score loss. To locate where the gains come from, we assign each point lost on a held-out episode to the first stage that failed (Figure 12). We use the recorded frames and memory contents to check observation and stor-age, asking whether the required evidence was seen clearly and retained. We then inspect the tool results to determine whether retrieval supplied a usable match. An incorrect choice based on usable evidence counts as a decision fail-ure, while failure to submit a valid answer or carry out the chosen action falls under execution. For text memories, a stored entry must identify the relevant location, card cell, or product, with a description where recognition requires one. If the record exists but its description does not distinguish the item from similar ones, we assign the loss to retrieval. The allocation rule depends on the task. In MC Gallery and DMV-Hard, each incorrect answer loses its share of the total score. Poster Maze also loses points for recall ques-tions that were not asked because the relevant posters were not seen clearly. For Card Matching, we distribute the score loss from unmatched pairs across stages in proportion to the failed second flips. For Tetris and Pac-Man, each failed action is weighted by the episode’s average points per pro-ductive action. The remaining shortfall is assigned to the decision stage as low-yield play, in which productive ac-tions earn too few points. AutoMem loses most at retrieval, where its descriptions often fail to distinguish visually similar items. EvoViM’s reductions in storage and retrieval failures account for most of its lead over this baseline. Its remaining losses are con-centrated in observation and decision-making (Figure 13). 

Text retrieval. On DMV-Hard, generated patterns share the same palette, and AutoMem’s stored descriptions re-peatedly use those color words. In the Claude Haiku 5.5 lineage on Poster Maze, the sec-ond revision identifies lure rejection as a gap but cannot de-termine which failed questions are lures. A wrong location answer receives zero credit whether the query shows a seen poster or a lure. No threshold is validated, so the revised program still has no rejection rule. The Qwen3.8-27B start-ing program answers every development question with not seen , receiving credit only for lures. These score changes provide labels for checking a rejection threshold.

## 6. Conclusion 

In this paper, we studied exploration with deferred queries. We found that textual descriptions lose visual distinctions, while stored images need task-specific operations to support later decisions. Programs written from the initial environ-ment instructions alone often prepare for the wrong ques-tions. To address these problems, we proposed EvoViM, in which a frozen MLLM examines its visual trajectories to identify and revise the operations that lost or misused evi-dence. The model also rewrites the playbook and extends the analysis tools used in later revisions, so both the pro-gram and the revision process evolve. We treat memory and skills as two uses of experience carried by this visual program. Its operations retain evidence for later questions and support action selection from the current state. Across six tasks and three models, EvoViM achieves the highest average score. From the same starting program, evolution produces operations suited to each task, with memory and skills combined in programs such as the Card Matching agent that recalls seen cards to suggest the next flip. We be-lieve EvoViM could extend to embodied environments and EvoViM (full)

Implementation and Revision Instructions 

Execution settings. The two execution phases are called 

LOG and PLAN in the implementation, corresponding to 

Record and Act in the main text. The record phase is skipped at the first step, before any action has been taken. Each phase allows up to 20 model requests per step, with a limit of 4,096 output tokens per request. Requests time out after 180 seconds, or after 300 seconds for the locally served Qwen3.8-27B. Qwen3.8-27B uses temperature 0.7, top-p

0.8 and top-k 20. Candidate code can import the Python standard library, NumPy, SciPy and Pillow, and can access only the public observation fields supplied by the host. The environment executes the action committed by the model. This accounts for 27,551 of the 27,555 held-out steps. In the remaining four steps, all on DMV-Hard, the model committed no action and the host used the default action of the environment. 

Revision and code checks. Revision runs in Claude Code for Claude Haiku 5.5 and in Codex for GPT-6.1 Sol and Qwen3.8-27B, using the same model as task execution. Be-fore evaluating a candidate, the host replays recorded ob-servations with a stub model that calls every registered tool. These checks exercise the tool interfaces and restoration of episode state without making model requests. A retry starts from the same parent and receives the rejected code together with its failure records. 

Selection rules. EvoViM accepts a candidate with ahigher mean development score. A tied candidate is ac-cepted only if it succeeds on every development seed and uses fewer steps or tokens without increasing the other. Au-toMem requires a strictly higher mean score and rejects a candidate if the rate of malformed requests or fallback ac-tions rises by more than five percentage points. Section E reports how these rules affected candidate selection.

## F. Control Implementations 

F.1. One-Shot Programs 

The one-shot control starts from the same program and in-terfaces as EvoViM but receives no interaction records or revision experience. References to recorded episodes are removed from its instructions, and the analysis questions remain only as design considerations. The model can test its code on synthetic inputs, but there are no recorded ob-servations for offline replay. It writes one candidate without a retry, which is evaluated on the same held-out seeds as EvoViM. Table 21 gives the scores and answer counts. 

Spatial tasks. The one-shot MC Gallery programs mea-sure changes between consecutive frames but do not match query paintings to stored images in code. The Claude Haiku 5.5 agent saves one frame across ten episodes. Qwen3.8-27B saves 156 frames and recalls 105, but gives only one correct location among 60 seen queries. On Poster Maze, both programs focus on a map of cells and routes. Claude Haiku 5.5 stores no frame and Qwen3.8-27B stores 16 across ten episodes. They receive 22 and 24 questions about seen posters, respectively, but neither identifies the correct wall. Their correct answers all come from lures. 

DMV-Hard. The one-shot Claude Haiku 5.5 program represents each photo with an 8 × 8 average hash and the shares of 12 color names. Qwen3.8-27B compares color clusters and hue histograms. These summaries of whole photos answer 69 and 29 of the 134 detail questions, but only 0 and 5 of the 106 pattern questions. The Claude Haiku 5.5 program also introduces a mis-match between its prompt and parser. Its record prompt requests DONE , while the parser accepts only command-form responses. This causes 1,458 protocol errors and 2,139 model requests per episode. The page records are still writ-ten, so the mismatch mainly increases request use. 

F.2. Fixed Visual Memories 

Each fixed visual memory replaces the starting program and runs without evolution on the same host and held-out seeds. The execution phases and limit of 20 requests per phase remain unchanged. We evaluate the archive and its two matcher variants on MC Gallery, Poster Maze and DMV-Hard. 

Frame archive. The archive follows the interface of VISTA [5] and saves every observation losslessly by step. 

INSPECT shows up to eight stored frames side by side, or crops the same region from each at full resolution. 

READ PIXELS returns the exact colors in a region. The text-memory files of the starting program remain available for notes. 

Matcher variants. The tool variant adds MATCH , which searches stored frames using color zero-normalized cross-correlation. It removes a near-uniform border from the query image or a region chosen by the model, then searches 12 template widths from 8.5% to 79% of the frame width. The search tests rotations of −15 ◦, 0◦ and 15 ◦. It returns the five best steps with scores and positions, and shows the query beside the three best regions. The same routine is used for all three tasks without an acceptance threshold. The every-step variant runs this search automatically be-fore the first model request of each step. It requires no ad-ditional model request and inserts the three best matches into every prompt of that step.
