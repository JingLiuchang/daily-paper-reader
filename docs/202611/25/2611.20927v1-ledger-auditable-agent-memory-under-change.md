## 摘要
智能体记忆系统大多在固定历史记录上进行评估，且仅对其最终答案评分。在实际使用中，事实会发生变化，来源的可靠性各不相同，用户还会要求智能体遗忘某些内容。我们提出 LEDGER，这是一种记忆层：由语言模型提出事实，并由显式规则决定哪个值当前有效、应信任哪个来源以及删除什么。每条事实都保留其来源及其成立的时间段。LEDGER+EP 增加了一项搜索：针对账本未覆盖的问题，在原始对话轮次中检索，并在删除时清理这些轮次。我们在一个合成的多会话编程智能体工作负载以及 LongMemEval 的 210 题子集上，将二者与无记忆、全历史重放、基于原始对话记录的检索以及 Mem0 进行比较，使用相同的回答模型和提示，并同时评估每种记忆发送给模型的证据以及最终答案。在编程工作负载上，回退模式下的 LEDGER+EP 在五个开发种子上的答题正确率为 94.3%，在五个留出种子上的正确率为 91.1%；而最强基线全历史重放分别为 82.1% 和 83.3%。当删除请求仅描述事实本身时，在任何已评估的探测中，都没有被删除的值进入我们系统的证据。在 LongMemEval 上，增强模式下的 LEDGER+EP 与全历史重放具有相同的观测准确率（74.8%），但仅使用后者 1% 的上下文。主要局限在于：编程工作负载是由我们构建的合成数据；在 LongMemEval 上，最强系统之间的差异处于置信区间内。

## Abstract
Agent memory systems are mostly evaluated on fixed histories, and only their final answers are scored. In real use, facts change, sources differ in reliability, and users ask the agent to forget things. We present LEDGER, a memory layer in which a language model proposes facts and explicit rules decide which value is current, which source to trust, and what to delete. Each fact keeps its source and the period in which it held. LEDGER+EP adds a search over raw conversation turns for questions the ledger does not cover, and scrubs these turns on deletion. We compare both against no memory, full-history replay, retrieval over raw transcripts, and Mem0, with the same answering model and prompt, on a synthetic multi-session coding-agent workload and a 210-question subset of LongMemEval, and we score both the evidence each memory sends to the model and the answer. On the coding workload, LEDGER+EP in fallback mode answers 94.3% of questions correctly on five development seeds and 91.1% on five held-out seeds, against 82.1% and 83.3% for full replay, the strongest baseline. When a deletion request only describes the fact, no deleted value reached our systems' evidence in any evaluated probe. On LongMemEval, LEDGER+EP in augment mode has the same observed accuracy as full replay (74.8%) with 1% of its context. The main limitation is that the coding workload is synthetic and built by us; on LongMemEval, the differences between the strongest systems are within the confidence intervals.

## 1. 核心问题与整体含义（研究动机与背景）

- **背景**：编码智能体需要跨多个会话在同一代码仓库上持续工作，而会话上下文不会自动保留。没有记忆时，智能体必须反复重新推断或让用户重复事实（如某服务使用哪个数据库、从哪个分支部署、谁值班）。
- **现实痛点**：这类事实会随时间变化，可能出现在用户消息、工具输出、文档、代码变更中；可能被过时文档或智能体自己早先的错误推断污染；用户还会要求“忘记”某些内容。
- **现有基线的问题**：
  - **全历史重放（full-history replay）**：不丢失信息，但上下文随历史线性增长，旧值、错误值、已删除值会与当前值一起进入模型。
  - **原始对话检索（transcript RAG）**：上下文小，但可能漏检正确轮次或返回过时轮次。
  - 二者都把“哪个值当前有效”的判定推给回答模型。
- **现有记忆系统的问题**：MemGPT、Mem0、A-MEM、Zep 等虽减少模型读取量，但仍由模型自行决定事实何时被替换或删除，且普遍缺乏**显式、用户可配置的来源可信度排序**。
- **评测缺口**：LoCoMo、LongMemEval 等基准主要看下游问答（LoCoMo 另报检索召回），但**没有审计最终送入模型的证据是否反映“当前、可信、未删除”的事实状态**。据作者所知，尚无基准联合评估记忆正确性、来源信任、删除合规性与证据级溯源。
- **研究目标与三问**：
  - RQ1：完整系统能否把过时、污染、已删除的值挡在证据之外？
  - RQ2：在相同回答模型与提示下，是否优于重放、transcript RAG 与现有记忆系统？
  - RQ3：随历史增长是否仍保持正确，上下文、存储、模型成本如何增长？
- **核心主张**：把部分决策从模型移出——模型只“提出事实/路由问题”，**固定规则决定当前值、冲突胜者与删除范围**。

## 2. 方法论

### 2.1 核心思想
- **职责分离**：LLM 提取器提出 claim（`⟨event, slot, value⟩`），LLM 路由器把问题/删除请求映射到槽位；**账本核心（ledger core）只按固定规则决定什么是当前、可信、已删除**，且从不读取自由文本。
- 两种变体：
  - **LEDGER**：仅账本，每个命中槽位返回一行事实，或弃答。
  - **LEDGER+EP**：增加原始轮次的情节存储（episode store，BM25 检索 top-5），分 **fallback**（仅当账本无事实时检索）与 **augment**（事实优先，再用轮次填满预算）两种模式；删除时同步清洗。

### 2.2 数据模型与时间
- 按用户分区；**槽位 slot = entity/attribute**（如 `payments-service/database`）。
- 每个历史取值是一条 entry，带有效期区间 `[from, to)`：起点为陈述该值的事件时间戳（假设 A4），终点为被更新值取代的时间戳。
- entry 还记录来源类型与信任度、以及所有陈述过该值的**事件 id（溯源）**。
- 三类不参与检索的记录：**disputed**（低信任冲突值，留审计）、**unconfirmed**（未确认值）、**tombstone**（仅记录槽位已删除，不存值）。
- 问题在时刻 t 提出、可带 as-of 时间 t′，返回“在 t′ 有效且在 t 前已记录”的 entry。

### 2.3 写入规则（五条，按事件流顺序逐条应用）
1. **restate**：同值（任意来源）→ 加入溯源、取较高信任度，不新建 entry（I4 去重）。
2. **supersede**：不同值且来源信任度 ≥ 当前 entry → 关闭旧区间、开新区间（I2）；旧值仍可回答历史问题（I3）。
3. **dispute**：不同值但来源信任度更低 → 仅留审计，永不检索（I5）。
4. **introduce**：无当前值且来源信任 ≥ 2 → 开新 entry。
5. **hold**：无当前值且来源信任 < 2 → 存为 unconfirmed；若后续可信来源给出同值则转为正式 entry，给出异值则转为 dispute。

### 2.4 来源信任策略（表 III）
- 用户消息、工具结果、代码变更 = **trust 3**（可引入、可更新任意值）。
- 文档 = **trust 2**（可引入，但只能更新信任 ≤ 2 的值，**不能覆盖用户**）。
- 助手消息、工具调用 = **trust 1**（不能设值，只能 hold 或被 dispute；LEDGER+EP 不把它们送入提取器，只留情节存储）。

### 2.5 提取器的三重防护
1. **枚举事件 id**：输出 schema 列出本批事件 id，claim 只能引用真实存在的事件。
2. **接地检查（grounding）**：claim 的值必须以文本形式出现在其事件中（忽略大小写与标点），过滤编造/复制值。
3. **删除侧防护**：见 2.7。

### 2.6 检索与弃答
- 路由器只能从“用户已知槽位列表”中选择，不能凭空发明槽位。
- 每个命中槽位返回一行（含有效期与来源）；无有效 entry 的槽位被略去。
- 全部落空时弃答并给出理由：无匹配槽位 / 用户已请求删除 / 仅有未确认 claim（I6）。
- 在 A1、A2 成立时，证据中不会出现 disputed、unconfirmed 或已删除值。
- **注意**：原始轮次不按 as-of 时间过滤；augment 模式下若问题同时命中已删除与存活槽位，只能靠情节清洗阻止泄漏。

### 2.7 删除机制
- **定位受影响槽位**：优先用请求携带的源事件 id；否则由路由器按描述映射；再加第三重保险——把描述中直接点名的槽位全部纳入（漏一个槽位即隐私失败）。
- **账本删除**：抹除该槽位在请求前记录的所有 entry、dispute、unconfirmed（含历史值），保留无值 tombstone；被抹除记录不再展示给提取器；用户此后重新陈述才开新 entry，对更早时间的提问仍弃答。
- **情节清洗**：移除被抹除值背后的事件、提及被抹除值的轮次、请求前点名被删槽位的轮次、请求前提及相关实体的助手/工具调用轮次；被移除事件加入 **blocked ids**，防止崩溃重放时再次写入。

### 2.8 保证与假设
- 七条期望属性：I1 删除、I2 取代、I3 时序、I4 去重、I5 抗污染、I6 弃答、I7 用户隔离。
- 四条假设：A1 提取正确、A2 路由正确、A3 信任序正确、A4 有效时间始于陈述时刻（不解析文本中写的日期）。
- 保证是**按槽位**的：规则只在“找到正确槽位”后保证正确，路由是独立一步。
- 持久化：全状态（含 tombstone、blocked ids）写入单个 JSON，按用户分区；快照非原子写，未测试写入期间崩溃。

## 3. 实验设计

### 3.1 数据集 / 场景
- **自建合成编码智能体负载**（种子生成器，多用户多会话）：
  - 每用户多个服务，每服务 3–5 个事实，来自 9 类（数据库、测试命令、部署分支、staging 主机、运行时、消息队列、CI 提供商、云区域、值班负责人）。
  - 状态机生成事实历史：introduce / restate / update / contradict（仅文档或助手）/ delete（仅用户），按来源模板渲染，并混入闲聊、工具调用、只提主题不给值的干扰项。
  - 探测 6 类：current、post-update、historical（带 as-of）、contamination、post-delete、abstention。
  - 两种预设：**small**（seeds 0–4 开发，5–9 留出；约 1.8k–2.4k tokens/种子）；**long**（540 模拟天、6 用户 × 60 会话、8 个检查点、3 seeds、1,379 探测）。
  - 真值来自工作负载代码的纯函数（只看变更种类与时间），不调用任何记忆系统。
- **LongMemEval_S**：从 500 题中按 7 类（6 种题型 + 弃答）各抽 30 题，共 **210 题**（`random.sample`, seed 0），每题历史约 48 个会话（95k–104k tokens），按日期逐会话重放。

### 3.2 评测基准与指标
- **双层打分**：
  - **证据判定
