# VistaTree: Question Answering over Long Multimodal Documents with Image-Derived Summary Trees 

Yexiang Cheng Xiaochen Zheng David Tokar Tatyana Y. Doktorova 

Translational Safety Assessment and Computational Toxicology, Roche, Basel, Switzerland 

yexiang.cheng@roche.com 

Abstract 

Answering questions over long multimodal documents requires locating relevant evidence across pages containing text, tables, and fig-ures. When the document exceeds the model’s context window, selective retrieval becomes necessary. We introduce VistaTree, a docu-ment question-answering agent that builds a summary tree directly from rendered page im-ages. VistaTree segments documents into con-tiguous page spans, recursively groups them into a topic hierarchy, and refines sibling sum-maries to distinguish neighboring sections. At query time, the agent uses node summaries to select relevant nodes and reads the correspond-ing pages, using hierarchical navigation when the full outline exceeds the context budget. Ex-periments on MMLongBench-Doc and Long-DocURL evaluate answer quality and retrieval cost using a locally hosted vision–language model, and quantify the performance gap be-tween global and hierarchical access to the in-dex. 

1 Introduction 

Question answering over long multimodal docu-ments requires finding a small amount of evidence within a much larger source. Clinical study re-ports, for example, can approach a thousand pages and contain sensitive patient information, which may restrict their processing with externally hosted models. Locally hosted vision–language models offer an alternative, but processing all page im-ages at once can exceed their input budget. Longer contexts also do not guarantee effective use of the available evidence (Liu et al., 2024). These con-straints motivate selective access to evidence across pages and modalities. Retrieval-augmented generation (RAG) ad-dresses the input constraint by providing selected passages to a language model (Lewis et al., 2020). Dense retrievers typically rank passages through similarity in a shared embedding space (Karpukhin et al., 2020). In long technical documents, repeated topics and terminology can produce many com-peting candidates. Passages discussing these top-ics may occupy nearby regions of the embedding space even when they refer to different entities, re-porting periods, or measurements. Similarity can therefore capture topical overlap while leaving the distinctions that determine relevance to a question unresolved. Instruction-following retrieval evalu-ations likewise show that retrievers can struggle with detailed relevance conditions (Weller et al., 2025). Increasing the number of retrieved chunks broadens coverage while consuming more of the model’s limited context with potentially redundant or unhelpful material. More retrieved text does not necessarily produce better answers (Liu et al., 2024; Jin et al., 2025). This motivates a search pro-cess that compares candidate regions against the question and selects which content merits closer reading. Beyond selecting relevant passages, text-based retrieval faces the challenge of preserving informa-tion from multimodal pages. Document parsers such as MinerU, Docling, and olmOCR recover text and document structure from pages (Wang et al., 2024a; Livathinos et al., 2025; Poznanski et al., 2025a). However, the text supplied to re-trieval may omit visual information carried by charts, figures, and spatial relationships on the page. Fixed-size chunks can also separate a result from the context needed to interpret it. These limitations motivate deriving a searchable representation di-rectly from rendered pages and retaining access to the original visual evidence. We introduce VistaTree, an agent that builds and searches a summary tree directly from rendered document pages. A vision–language model identi-1arXiv:2611.29419v1 [cs.CL] 22 Nov 2026 fies consecutive spans of related content, summa-rizes them, and recursively groups their summaries into broader topics. Each node remains linked to its underlying page range. At query time, the agent uses the node descriptions to select relevant spans and reads their page images to gather evidence. It can inspect additional spans before producing an answer. To distinguish spans with overlapping topics, the agent rewrites each node’s title and summary using its content together with its siblings’ summaries. The tree structure and page ranges remain fixed. Flat selection presents all leaf summaries together for comparison across the document. For longer documents whose complete outlines may exceed the context budget, hierarchical navigation reveals broader topics first and provides child descriptions as the agent descends. We evaluate VistaTree on MMLongBench-Doc (Ma et al., 2024) and LongDocURL (Deng et al., 2025) using the same locally hosted model. These benchmarks allow both flat selection and hierarchical navigation to operate, enabling us to quantify the answer-quality gap between global and progressive access to the index. Flat selec-tion outperforms DocAgent on both benchmarks and Chunk-RAG and RAPTOR on LongDocURL. Summary rewriting improves answer quality for both navigation modes. Hierarchical navigation uses a smaller initial outline, with total query cost varying across datasets. Increasing the passage budget of the retrieval baselines improves evidence coverage more than answer quality, reinforcing the importance of selecting useful context. Our contributions are: (1) We introduce VistaTree, a document question-answering agent that constructs a hierarchical summary index directly from rendered page images using a locally hosted vision–language model. (2) We develop summary rewriting that uses sib-ling context to distinguish related document spans, together with flat and hierarchical search procedures that guide the agent to page images for evidence gathering. (3) We evaluate VistaTree on two public bench-marks, demonstrating the benefits of summary rewriting and global access to document sum-maries, and characterizing the trade-offs be-tween answer quality and context usage. 

2 Related Work 

Retrieval-augmented generation (RAG). 

Retrieval-augmented generation supplies a lan-guage model with information selected from an external collection (Lewis et al., 2020). Dense retrieval commonly performs this selection by ranking passages according to their embedding similarity to a question (Karpukhin et al., 2020). Answer quality therefore depends on how well the model uses the retrieved passages. Liu et al. (2024) show that language models can struggle to use relevant evidence within long contexts. In retrieval-augmented settings, Jin et al. (2025) further find that increasing the number of retrieved passages can reduce answer quality by introducing hard negatives. Their findings highlight how related but unhelpful passages can interfere with the model’s use of evidence. 

Visual document understanding. Document un-derstanding also requires interpreting how infor-mation is presented on a page, including the ar-rangement of text, tables, and figures. Donut (Kim et al., 2022) and Pix2Struct (Lee et al., 2023) demonstrated that document representations can be learned directly from pixels without a sepa-rate OCR stage. For text-based retrieval, docu-ment parsers convert pages into structured text such as Markdown or JSON. Modular toolkits such as MinerU (Wang et al., 2024a) and Do-cling (Auer et al., 2024; Livathinos et al., 2025) recover text, layout, and document structure. End-to-end models such as Nougat (Blecher et al., 2024) and olmOCR (Poznanski et al., 2025a,b, 2026) transcribe page images with a single vi-sion encoder-decoder or fine-tuned vision-language model. These outputs can be linearized and chun-ked for text-based retrieval; information carried by figures and page layout may not survive this step, and parsing errors can propagate to retrieval. General-purpose vision-language models such as Qwen3-VL (Bai et al., 2025) offer an alternative by answering questions directly from page im-ages. VistaTree follows this route: a single vision-language model reads page images both to build the index and to answer questions. Its node de-scriptions guide the selection of page spans, while evidence is read from the rendered pages. 2Hierarchical document retrieval. RAP-TOR (Sarthi et al., 2024) recursively clusters and summarizes text chunks into a multilevel index that connects related content across adocument. It retrieves passages and summaries by embedding similarity through either tree traversal or collapsed-tree search. PageIndex (Zhang and Tang, 2025) organizes document sections and their descriptions into a hierarchical index that a language model navigates through reasoning-based retrieval. It uses extracted document text to generate node descriptions. VistaTree builds its hierarchy and summaries directly from rendered pages, allowing visual content to inform the index as well as the final reading stage. We further rewrite each summary in the context of its siblings to distinguish related regions while retaining the same tree and page ranges. 

Agentic document question answering. Agen-tic methods give a language model tools for choosing which document content to inspect. PDFTriage (Saad-Falcon et al., 2024) combines document-structure metadata with retrieval func-tions, allowing the model to request context by structure or content. DocAgent (Sun et al., 2025) constructs an outline from parsed document con-tent. Its actor navigates this outline and uses tools to retrieve individual elements for multimodal read-ing. In VistaTree, index construction follows an agent loop: the model reads pages sequentially and decides whether to continue the current span or close it and create a node. At query time, the agent navigates the resulting summaries, reads selected page images, and decides whether to gather more evidence or answer. 

3 Method 

VistaTree uses a vision–language model within an agent loop to construct and search a summary tree. Figure 1 shows the two phases of VistaTree: summary-tree construction and question answering. Given rendered pages D = ( p1, . . . , p N ), Vista-Tree constructs a tree whose nodes contain a title, a summary, and a page range. The title and sum-mary together form the node description used for navigation. Each leaf represents a span of consecu-tive pages covering related content, while internal nodes summarize groups of child nodes. At query time, the agent uses the node descriptions to se-lect relevant spans and opens their page images to gather evidence. 

3.1 Constructing the summary tree 

The vision–language model first divides the ren-dered document into consecutive page spans to create leaf nodes. It then recursively groups nodes and summarizes their content to build a hierarchy whose depth depends on the resulting groups. To identify the spans, the model reads the doc-ument in an agent loop. At each step, it receives the next page image together with a short running description of the current span. It updates this de-scription as long as new pages continue the current section or topic, and closes the span when it identi-fies a transition. When a span closes, the model cre-ates a leaf node with its page range and generates the node’s title and summary from the accumulated description and the span’s page images. Reading then continues with a new span until the document has been processed. If a new span begins partway through a page, adjacent spans can share that page. To build the next level, the model examines the leaf summaries in document order, deciding which consecutive nodes belong together and where a new group should begin. It creates a parent node for each group, generating its title and summary from the children’s summaries and retaining their com-bined page range. The model then processes the parent summaries in the same way to construct fur-ther levels. This process repeats until the number of top-level nodes falls below a configured threshold or a safety limit is reached. The completed tree can be reused across ques-tions. Sampling rules and construction settings are given in Appendix A. 

3.2 Summary rewriting 

Neighboring spans often cover similar topics, mak-ing them difficult to distinguish from their sum-maries alone. For example, two spans in a clinical study report may both be summarized as “liver function test results,” even though they report out-comes for different dose groups. During hierarchi-cal navigation, the agent chooses among sibling nodes that share a parent. Using their summaries as context when rewriting each node helps make these distinctions explicit. During a second summarization pass, the agent rewrites each target node’s title and summary us-ing its siblings’ summaries as context to make the nodes more distinguishable during retrieval. 3.3 Searching and reading 

Given a question, the agent uses the visible node descriptions to select relevant page spans and reads their images to gather evidence. After reading a span, the agent can use what it has found to select another span or produce an answer. Its main action, 

expand_node , returns child summaries for an internal node and page images for a leaf. Hierar-chical navigation additionally supports go_back 

to revisit an ancestor and explore another branch. As the search progresses, images from earlier turns are removed from the conversation to leave room for newly retrieved pages. The nodes presented to the agent, together with their descriptions and page ranges, form an outline. The outline, conversation history, and selected page images share the model’s context window. Flat selection presents all leaf descriptions together, allowing comparisons across the document. For substantially longer documents, such as clinical study reports that can exceed a thousand pages, the complete outline may no longer fit within the avail-able context. Hierarchical navigation addresses this constraint by exposing the tree progressively. We compare both configurations on the public bench-marks to assess how hierarchical navigation affects answer quality and total input tokens. 

Flat selection. The initial prompt lists every leaf with its title, summary, page range, and its parent’s title. The agent can compare spans across the doc-ument and open a leaf directly. The parent title supplies broader context for interpreting each leaf description. This provides global visibility, but the initial outline grows with the number of leaves. 

Hierarchical navigation. The initial prompt lists only the top-level nodes. The agent uses 

expand_node to inspect their children and de-scend toward relevant page spans, and go_back 

to return to an ancestor and explore another branch. By revealing the tree progressively, hierarchical 4navigation reduces the size of the initial outline compared with flat selection. However, reaching relevant page spans requires additional routing deci-sions based on the summaries visible at each step. 

4 Experimental Setup 

Benchmarks. We evaluate VistaTree on two benchmarks for question answering over long multimodal documents. Table 1 summarizes the datasets used in our experiments. MMLongBench-Doc (Ma et al., 2024) covers seven document categories, including academic papers, financial reports, brochures, and guidelines. Its questions draw on text, tables, charts, images, and layout, with evidence located on a single page or spread across multiple pages. It also includes unanswerable questions, testing whether a system can recognize when the document does not supply an answer. LongDocURL (Deng et al., 2025) organizes its questions into document understanding, numeri-cal reasoning, and cross-element locating, with 20 subtasks spanning text, tables, figures, and layout. Questions can require combining evi-dence across pages or identifying relationships be-tween document elements. Its longer median docu-ment length complements MMLongBench-Doc’s broader length range, allowing us to examine how document length affects navigation and context cost. 

Models. We use Qwen3-VL-8B-Instruct (Bai et al., 2025) for both tree construction and question answering, balancing tree-construction speed with the visual capability needed to extract useful docu-ment information. Query experiments use a locally hosted deployment with a 98,304-token context limit and temperature zero. We additionally evalu-ate Claude Opus 4.8 for question answering using full documents, evidence windows, or summary trees constructed by the local model. Appendix A gives further configuration details. 

Retrieval baselines. We compare VistaTree with passage retrieval, summary-based retrieval, and agentic document search. Chunk-RAG retrieves passages from extracted text by embedding simi-larity. RAPTOR (Sarthi et al., 2024) builds and searches a multilevel index of text chunks and re-cursively generated summaries. DocAgent (Sun et al., 2025) retrieves document content through an interactive interface over a structured outline.

5.1 Overall performance 

Table 2 compares VistaTree with retrieval base-lines and evidence-conditioned references. Vis-taTree with flat selection achieves 43.5 F1 on MMLongBench-Doc and 43.2 on LongDocURL, outperforming DocAgent on both benchmarks and Chunk-RAG and RAPTOR on LongDocURL. Hi-erarchical navigation scores 42.1 and 38.5, respec-tively. The gold-page oracle provides an empirical upper-bound reference for the local model under ideal evidence selection. It achieves 61.0 F1 on answerable MMLongBench-Doc questions with valid evidence-page annotations and 58.1 on Long-DocURL. The window reference achieves 50.4 F1 on MMLongBench-Doc and 52.2 on Long-DocURL. We also examine whether a stronger model can reuse the locally constructed trees to reduce input-token usage. With Claude, VistaTree achieves 56.8 F1 on MMLongBench-Doc and 45.6 on Long-DocURL while using fewer input tokens than full-document input on MMLongBench-Doc and evidence-window input on LongDocURL (Ap-pendix Table 5). This reduction in input-token usage is accompanied by lower answer quality than the corresponding full-document and evidence-window references. 

5.2 Navigation and summary rewriting 

We compare flat selection and hierarchical navi-gation on both benchmarks. With rewritten sum-maries, hierarchical navigation scores 1.4 F1 points lower on MMLongBench-Doc and 4.7 points lower on LongDocURL. Flat selection also achieves higher F1 with the original summaries (Table 3). Summary rewriting improves F1 for both naviga-tion modes on both benchmarks. Because the tree structure and page ranges remain fixed, the gains suggest that refining node descriptions can improve answer quality without modifying the underlying index structure.

5.4 Retrieval budget and evidence relevance 

We vary the passage budget to examine whether re-trieving more content ranked by similarity provides better evidence for answering the question (Fig-ure 3). Increasing Chunk-RAG’s budget from 2k to 26k raises F1 from 38.1 to 40.4. RAPTOR peaks at 39.1 with an 8k budget and scores 38.9 at 26k. Answer quality therefore changes only modestly despite the much larger retrieved context. The retrieval diagnostics help explain this lim-ited return. In the 30-document sample, both meth-ods reach 99.5% evidence-page recall at the largest budget, while Chunk-RAG’s passage precision falls from 15.2% to 3.5% and RAPTOR’s from 20.8% to 5.3%. Higher budgets thus cover more evidence pages while substantially expanding the context drawn from other pages. Moreover, page-level re-call credits passages that share an annotated ev-idence page even when they do not contain the answer-bearing information. These results highlight a limitation of similarity-based retrieval: passages that resemble the ques-tion may provide little evidence for answering it. Broader evidence-page coverage therefore does not necessarily translate into more useful context for question answering. 

6 Discussion 

Hierarchical navigation is intended for longer doc-uments whose complete outlines may exceed the 7context budget. Our benchmark comparisons mea-sure the gap relative to flat selection, which gives the agent access to all leaf summaries at once. Hi-erarchical navigation achieves lower aggregate F1 while requiring a smaller initial outline. However, the additional navigation and reading calls mean that this smaller outline does not consistently re-duce total query input. This trade-off is particularly relevant to long con-fidential documents that must be processed locally. Clinical study reports, for example, can approach or exceed a thousand pages. Our public-benchmark evaluation, however, includes documents only up to 468 pages. Evaluation at clinical-report scale is needed to establish whether the tree remains use-ful for evidence selection and how navigation af-fects answer quality and context usage as document length increases. 

7 Conclusion 

We introduced VistaTree, a document retrieval agent that uses a locally hosted vision–language model to construct and search summary trees from page images. Experiments on two public bench-marks demonstrate the effectiveness of VistaTree and quantify the gap between flat selection and hi-erarchical navigation, which is intended for longer documents whose complete outlines may exceed the context budget. Summary rewriting further improves performance while preserving the tree structure and page ranges. This approach supports document question answering in settings where confidentiality restricts external processing. 

Limitations 

Document length and evaluation scope. Our evaluation uses two public benchmarks of English-language documents and a single local model. The longest documents contain 468 pages in MMLongBench-Doc and 149 in LongDocURL. Evaluation on substantially longer documents, in-cluding clinical study reports approaching a thou-sand pages, remains future work, as does evaluation in other languages and with different local models. 

Index construction and query cost. Tree con-struction incurs an upfront inference cost for segmentation and summarization, with summary rewriting requiring an additional pass. Although the index can be reused, documents receiving few queries offer less opportunity to amortize this cost. Each query also incurs navigation and reading costs that depend on the search process. 

Instruction following. The 8B model can strug-gle to follow multi-step navigation instructions and maintain the required tool-call format. Reliable ex-ecution depends on carefully designed prompts that specify the available actions, their arguments, and the navigation procedure. This dependence may require further prompt adaptation when changing the model or tool interface.

A Implementation Details 

Tree construction. The tree builder operates on rendered page images. It processes one page per segmentation call, carrying a short running descrip-tion of the current span. A forced split prevents a span from continuing beyond the configured accu-mulation limit, set to 30 pages by default. If the model identifies a topic boundary within the pre-ceding page, that page can be shared by adjacent leaves. Leaf summarization uses at most ten images, se-lected across the span, together with the running description. Higher levels group consecutive child nodes from their titles and shortened summaries, then generate a description of each group. Lists exceeding 80 nodes use windowed grouping. Con-struction aims for fewer than ten top-level nodes and includes a depth safety limit. Tree construc-tion uses the 8B model with a 65,536-token server context and a twelve-image server limit. 

Summary rewriting. Each node is rewritten against a frozen snapshot of its siblings’ descrip-tions. Leaf nodes use up to ten sampled page im-9ages, while internal nodes use their children’s orig-inal summaries. The implementation permits up to three sibling inspections per node and retains the original text if rewriting fails. In the reported MMLongBench-Doc build, 3,773 of 3,780 nodes were rewritten, seven retained their original text, and no sibling inspections were requested. Tree shape, node identifiers, and page ranges were un-changed. Mean summary length increased from 234 to 352 characters. 

Navigation and history. The agent allows up to ten tool rounds before requesting a final an-swer. Flat selection exposes all leaves at the outset, whereas hierarchical navigation starts with the top-level nodes. The implementation retains recent interactions, removes older images as needed, and compresses older tool outputs when the estimated history budget is exceeded. Earlier page images are removed to conserve context, while the agent’s textual observations and reasoning remain in the conversation, subject to history compression. The default limit on images retained in the conversation is 32. The query-serving deployment permits up to 40 images per request. 

Reviewer. The optional reviewer receives the question, proposed answer, and pages viewed by the VistaTree agent. It labels the answer as sup-ported, contradicted, or absent from the supplied pages. An unsupported answer is returned to the agent with feedback for reconsideration. The re-view configurations allow one such review round. 

B Baseline Configurations 

Chunk-RAG and RAPTOR. Text passages tar-get approximately 100 tokens, with sentence bound-aries preserved where possible. Chunks end at page boundaries, so passages can be shorter than the tar-get length. RAPTOR uses UMAP and Gaussian-mixture soft clustering, selects the number of mix-ture components by BIC, summarizes clusters re-cursively, and retrieves across the collapsed tree. Both use multilingual E5 embeddings (Wang et al., 2024b), and RAPTOR uses the 8B model as its summarizer. Chunk sizes and passage budgets are estimated from text length using four characters per token. We evaluate both baselines under multiple passage budgets. 

DocAgent. We use the official DocAgent imple-mentation with the locally hosted Qwen3-VL-8B-Instruct model for question answering and the same answer extractor used for the other systems. Ta-ble 4 separately reports the published DocAgent result with Claude 3.5 Sonnet.
