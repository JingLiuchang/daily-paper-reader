# ABSTRACT 

Memory systems for production LLM agents mostly store semantic memory (facts about users and domains) or episodic memory (earlier interactions). Research systems such as Trace2Skill, WikiSkill, and SkillRevise learn procedures from agent runs, package them as Skills, and evaluate them on benchmarks. We describe Zep Agent Skills, a production service that gives deployed agents this procedural memory. The service uses only verified attempts as evidence, cites the supporting events for each field of a Skill, and governs the admission and distribution of each Skill version. The service records each task attempt as a Trace with ordered events, an outcome, and a verification strength. A compiler with separate Reflector and Curator roles turns verified Traces into versioned Skills. Scans and admission gates control which candidates become active, and verified use outcomes change the search rank of each Skill. The Agent Skills format is an open standard that Anthropic originated and donated to the Agentic AI Foundation, so any host of the format can load a compiled Skill. Agents retrieve Skills through lexical search with progressive disclosure, over an API or MCP. We evaluate Zep Agent Skills on τ 3-bench banking, AppWorld, and EnterpriseOps-Gym. Skills compiled from the Traces of a teacher model increase the pass rate of three weaker executor models on the same tasks, at every reasoning effort, by 4.5 to 18.8 points. Most of the gain is on the tasks that the teacher solved. On ALFWorld, Skills compiled from the runs of a small model give a gain similar to or larger than the gain that prior work reports for continuous fine-tuning, with no training. 

# 1 Introduction 

Engineers can write a prompt or a Skill for a stable, known process. A deployed agent also meets variations and exceptions of a process, changes to a process over time, and processes that are new. A support agent gets a ticket type that its instructions do not cover, and an operations agent must follow a changed approval rule. Each run of a large language model (LLM) agent starts from the same weights and the same prompt, so a successful run does not change the next run. The agent must solve the same problem again, and it can make the same errors again. Two common answers are fine-tuning and retrieval of earlier transcripts. Fine-tuning on successful runs changes the weights, but it needs training rounds, it is tied to one model, and it is difficult to inspect or to undo. Each change to a process needs a new training round. Retrieval of earlier transcripts (episodic memory) is cheap, but a transcript is long, it carries the values of one instance, and it can carry data that a later user must not see. Procedural memory is a third answer (Section 3.1). Research systems such as Voyager [Wang et al., 2023], Agent Workflow Memory [Wang et al., 2024], ExpeL [Zhao et al., 2023], and ACE [Zhang et al., 2025] show that procedures learned from experience can increase task success. The Agent Skills format [Agent Skills, 2026] gives agents a portable package for procedures: a folder with a SKILL.md 

file, frontmatter with a name and a description, and optional files. Agent harnesses such as Claude Code [Anthropic, 2026a], Claude Cowork [Anthropic, 2026b], and OpenAI Codex [OpenAI, 2026] load a Skill with progressive disclosure: the agent first sees the name and the description, and it reads the body only when the Skill applies. Anthropic published the format as an open standard in December 2025 and donated it to the Agentic AI Foundation (AAIF) of the Linux Foundation in October 2026 [Anthropic, 2026c]. The AAIF also holds the Model Context Protocol (MCP) [Model arXiv:2611.01386v1 [cs.AI] 1 Nov 2026 Learning by Doing: Autonomously Compiling and Curating Agent Skills from Verified Traces A P REPRINT 

Context Protocol, 2026a]. The format defines how a Skill is packaged and loaded. The format does not define how a Skill is learned from runs, verified, versioned, or governed, and in most deployments a human writes each Skill. A production service that learns Skills has requirements in addition to those of a research system. The service must learn only from verified attempts. Each claim in a Skill must trace to its evidence. A new version must not silently replace a version that works. A Skill must not carry the instance data of one user or organization to another. Deletion of a source must remove its effect. The service must work with any agent framework and any model, and it must accept Traces from existing trace stores such as Braintrust and LangSmith. We evaluate the service with a teacher-executor protocol. A strong model solves each task, Zep compiles Skills from its verified Traces, and weaker models then do the same tasks with and without the Skills. This protocol models a production pattern: a strong model solves a task one time, and a cheaper model then does it again. Skills increase the pass rate of each executor at each reasoning effort, mostly on the tasks that the teacher solved. The main benchmarks do not test transfer to new tasks. The contributions of this paper are: 1. A resource model for procedural memory: namespace, Trace, Skill, Skill version, and Skill use (Sections 3 and 4). 2. A compiler that turns verified Traces into structured Skill contracts with event citations for each field, and that makes local edits to existing Skills (Section 5.3). 3. An admission and lifecycle model: scans, gates, maturity tiers, and a search weight from verified use (Section 5.4). 4. A retrieval and delivery path: lexical search, progressive disclosure, and MCP delivery of packages in the Agent Skills format (Section 5.5). 5. A teacher-executor evaluation protocol with paired arms and leakage controls, and results on four benchmarks (Sections 6 to 8). Section 2 reviews related work. Sections 3 to 5 describe the problem and the design. Sections 6 and 7 give the evaluation, Section 8 gives the analysis, and Section 9 gives the limits and the future work. 

# 2 Related work 

Memory for LLM agents. CoALA [Sumers et al., 2023] divides agent memory into working, semantic, episodic, and procedural memory. Semantic memory systems store facts about users and domains (MemGPT [Packer et al., 2023]), in some systems in a knowledge graph with validity times (Graphiti [Rasmussen et al., 2025]). Zep [Rasmussen et al., 2025] offers a context layer: a temporal knowledge graph that combines structured and unstructured enterprise data, with access control, versioning, and retention management. Semantic memory is one application of this layer. Episodic memory systems retrieve earlier attempts or reflections on them (Reflexion [Shinn et al., 2023]). Zep now also offers Zep Agent Skills, which supplies procedural memory and does not replace the other types. 

Learning procedures from experience. Voyager [Wang et al., 2023] stores verified programs as a skill library and improves them with execution feedback. ExpeL [Zhao et al., 2023] extracts insights from successful and failed attempts. Agent Workflow Memory [Wang et al., 2024] induces reusable workflows from trajectories and abstracts the values of each instance. MemP [Fang et al., 2025] studies how procedural memory is built, retrieved, and updated. LEGOMem [Han et al., 2025] places procedural memory in multi-agent systems. Skill-Pro [Mi et al., 2026] learns reusable skills from interaction experience without weight updates. AutoSkill [Yang et al., 2026] consolidates interaction experience into skills over many sessions, and Trace2Skill [Ni et al., 2026] consolidates many execution trajectories into one skill directory. 

Curation and revision of skill libraries. A survey of dynamic skill libraries [Li, 2026] describes a lifecycle of evidence acquisition, proposal, verification and admission, storage, retrieval, maintenance, and governance. It also reports weak verifiers, and retrieval over a flat list of skills that degrades as libraries grow. ACE [Zhang et al., 2025] separates a generator, a reflector, and a curator that make incremental edits to a context playbook. Anything2Skill [Pan et al., 2026] compiles external knowledge, such as manuals, logs, and trajectories, into structured skill contracts in a versioned skill bank. SkillRevise [Liu et al., 2026a] revises an initial skill from execution traces and keeps the version with the best measured utility. SkillLift [Kang and Wen, 2026] learns rubrics from sparse evaluation results to reduce the rollouts that skill revision needs. WikiSkill [Tang et al., 2026] and Procedural Graphs [Lu et al., 2026] consolidate knowledge and procedure structure across many runs, and both keep a record of rejected proposals for later proposals. Zep Agent Skills follows the lifecycle of the survey. transactional admission, and governance. Unlike Voyager, SkillRevise, and SkillLift, it does not execute candidate Skills (Section 5.4). 

Portable skill packages. The Agent Skills format [Agent Skills, 2026] and the draft MCP Skills extension SEP-2640 [Model Context Protocol, 2026b] define how an agent harness discovers and loads a Skill. Zep Agent Skills emits packages in this format. 

Continuous fine-tuning. Methods such as Retrospective Self-Distillation (RSD) [Zhou et al., 2026] train the weights of a model on its own runs in several rounds. Section 7.6 compares the gain of RSD with the gain of Skills on ALFWorld.

# 3 Problem setting 

3.1 Setting and terms 

We consider a deployed agent that performs tasks over time. Each attempt produces observable events and an outcome, and an external system can verify some outcomes. Zep Agent Skills supplies procedural memory [Sumers et al., 2023]: when to use a procedure, its steps, and when to stop. Zep Agent Skills does not train model weights, execute Skills or application code, or store hidden model reasoning. A Trace contains only observable events, and self-reflection alone does not verify an outcome. The service turns verified task evidence into cited, versioned procedures. It admits and retrieves these procedures within the access and applicability boundaries of its namespace. 3.2 Threat model 

A production agent acts on what it retrieves. When the retrieved content is a procedure, the agent follows it as instructions, often with tools that change data, send messages, or move money. Memory-poisoning attacks show this risk for agent memory. AgentPoison [Chen et al., 2024] puts malicious records with a trigger into the memory or knowledge base of an agent. A later query that contains the trigger retrieves the records, and the records steer the agent to the action of the attacker. MINJA [Dong et al., 2025] gets the same result without access to the memory store: an attacker who only sends queries to the agent makes the agent write the malicious records itself. Skills are a direct path for this type of attack. Skill-Inject [Schmotz et al., 2026] reports attack success rates of up to 80% against frontier models through instructions in skill files, and a study of 98,380 public skills found 157 malicious skills [Liu et al., 2026b]. A service that learns Skills from Traces has the same exposure. A Trace contains tool output and user text that an attacker can control, and the service can admit a Skill without a human. We consider five threats: 1. Instance-data leakage. A Skill can copy a name, identifier, credential, or private URL from a Trace. 2. Instruction injection. Tool output or user text in a Trace can contain instructions that a compiler model keeps in a Skill. 3. Unverified or poisoned outcomes. An agent can report success for a failed run, or a caller can assert verification without authority. An attacker can then make a harmful procedure look successful. 4. Cross-boundary flow. Evidence from one namespace or organization can enter a Skill that another principal reads. 5. Unsafe procedures. A Skill can direct an agent to change data, send messages, or move money. Section 5.6 maps each threat to its controls.

A human can review candidates when the namespace requires review. 5. Serve. The agent searches active Skills, reads the selected procedures, and records their use with the task outcome. Each namespace owns its Traces and Skills, and each Skill has immutable versions with evidence links. The API exposes capture, retrieval, review, and version management. # 5 Design of Zep Agent Skills 

Several stages of the lifecycle use LLMs. Each LLM output is a claim that deterministic code checks before it has an effect. We call this code trusted code .

5.1 Traces and verification 

The agent harness records ordered events while a task runs, for example model turns, tool calls, and tool results. At the end of the task, the harness closes the Trace with the outcome that it reports. An agent can report success for a task that failed, so Zep stores the reported outcome separately from its verification. A verifier is the party that checks an outcome: the agent itself, a tool, a human, or an external system such as a test suite. Zep sets the verification strength from the identity of the caller that submits the verification, and it ignores a strength that the caller only states. An agent can submit only self-reported verification. A tool or an external system must first be registered as a verifier of the namespace, with the strengths that it may assert. A human must have the permission to verify outcomes. Traces that Zep imports from an LLM observability or evaluation platform, such as Braintrust or LangSmith, can carry the scores of that platform. The import maps a score to an outcome with a threshold that a human sets. When a human registers the import as a verifier, the score is external verification, and it is strong. Zep authenticates the origin of a verification result, but it does not prove that the result is true. When two verification records of a Trace conflict, Zep does not admit Skills from the Trace automatically. A retry of the task inherits the attempt family of its parent Trace, and compilation counts attempt families. A failure and its successful retry therefore count once as support. After a Trace closes, an LLM writes a Trace summary. The summary records the objective, the outcome, the approach, the effective and ineffective steps, the errors, the recoveries, and the tools used. A summary is specific to one task and can keep the instance values that explain the attempt. Each claim of the summary cites the Trace events that support it, and trusted code removes each claim that it cannot match to an event. Like the insights of ExpeL [Zhao et al., 2023], summaries condense experience. The compiler uses summaries to select relevant attempts, and then it checks each supporting claim against the events. A summary is thus never evidence by itself. The task family sets the scope of compilation and retrieval: the compiler learns Skills for one family at a time, and search returns the Skills of the requested family. A caller can declare the family. Otherwise, Zep infers the family from the objective, the summary, and the names of the tools and operations of the Trace. The inference input has no tool arguments, tool results, identifiers, or URLs, so instance data cannot decide the family. Zep assigns a known family only when a calibrated score meets a threshold. Otherwise, the Trace stays unassigned and does not enter compilation. When enough distinct attempt families stay unassigned, Zep can propose a new family. 

5.2 Skill representation 

Zep stores each Skill version as a structured contract. The contract separates applicability from procedure: • Applicability fields state when to use the Skill, when not to use it, its preconditions, and the tools and environments where it applies. • Procedure fields give the ordered steps, the decisions, the expected observations, the outputs, the completion criteria, the stop conditions, and the failure modes with their recovery. The fields follow the activation, execution, and termination conditions of Skill-Pro [Mi et al., 2026] and the structured contracts of Anything2Skill [Pan et al., 2026]. Typed fields let the compiler check and edit one part of a Skill at a time. A field can be empty. For example, the evidence for a new Skill can show no failure mode. Zep renders each version from the contract into two Markdown forms: • The full form is for review. It marks the evidence for each cited field. • The agent view is a SKILL.md package in the Agent Skills format. It has no evidence markers, and it leaves out the sections of empty fields. 5.3 Compilation 

The compiler turns verified Traces into proposed changes to the Skills of one task family. Figure 3 shows the stages. Two LLM roles do the work. The Reflector writes proposals, and the Curator checks the proposals against the evidence and the current Skills. Trusted code checks the output of each role. One model call could write and check a Skill. We separate the roles because claim checking is a narrower task than procedure generation, and separate verdicts give an audit record. The two roles can also use different models or efforts. ACE [Zhang et al., 2025] uses related generator, reflector, and curator roles. 6Learning by Doing: Autonomously Compiling and Curating Agent Skills from Verified Traces A P REPRINT 

Evidence selection. A compilation run reads the evidence of one namespace and task family. Compilation runs on a schedule, when a Trace closes, or on request. The evidence has four parts: • the current Skills of the family; • stale Skills, which are earlier Skills that new evidence contradicts; • the Trace summaries and their events, from Traces that earlier runs did not consume (see “Cite-or-retain rule” below); • the outcome history of earlier proposals (see “Outcome history” below). Only successful attempt families with strong verification can support a new Skill. The selector removes duplicate retries and keeps failed attempts as contrast, as ExpeL [Zhao et al., 2023] does. Each part has a size limit, and the selector shortens long tool results. It keeps the events that a summary cites, the decisions, and the verification events. Each Trace that a run reads as evidence is a source of the run. The run records each source that it read and each source that it left out. A human reviewer can then tell missing evidence from evidence that did not support a proposal. 

Reflector. The Reflector can propose five operations: add a Skill, patch a part of a Skill, merge related Skills, report a conflict between new evidence and a current Skill, or make no change. Each proposed claim cites its supporting events. A patch changes only the fields that new evidence supports and keeps the rest of the Skill. Local patches follow ACE [Zhang et al., 2025], which reports that full rewrites can lose details. The Reflector replaces instance values, such as names and identifiers, with placeholders. 

Validation. Trusted code validates the structure of each proposal and matches each citation to a stored event that the namespace can read. It can repair a citation when the correct event is certain. For example, an event identifier in the text of a claim moves into the citation of the claim. A repair does not change a claim or add evidence, so a repair cannot make an unsupported claim acceptable. Trusted code records each repair and checks support again after it. A new Skill must apply beyond the values of one instance. When one attempt family supports a Skill, the checks are stricter. The procedure must not keep identifiers from the source events, and its applicability must stay within the tools and environments of the evidence. A failure mode can cite failed attempts. Failed attempts cannot support a procedure step. 

Scanners. A scanner uses deterministic checks and a model. It checks content for instance data, such as names, identifiers, credentials, and private URLs, and for instructions that come from tool output. The proposal scanner checks each proposal before the Curator reads it. The artifact scanner checks each rendered candidate before admission. A scanner rejection stops the proposal or the candidate. The summary model, the Reflector, the Curator, and the scanners read Trace content, summaries, and proposals as data, and they do not follow instructions in that content. Model providers give the same rule for tool output [OpenAI, 2025, Anthropic, 2026d]. Some events carry content from a restricted resource, for example a document that only some users or agents of the namespace may read. Zep stores such an event as a reference with no content, and the compiler does not read it. No Skill can contain its content. An application that must learn from such evidence uses a separate namespace. 

Curator. The Curator gives a verdict of supported or unsupported for each claim, from its citations and the current Skills. Then it decides each proposal. It can add or patch a Skill, merge Skills, replace a Skill with a new Skill, record a conflict, reject the proposal, or make no change. A recorded conflict removes the affected Skill from search until the conflict is resolved. An unsupported claim rejects only its proposed change. The Curator compares each candidate with the current Skills, so that a weaker rewrite does not replace a Skill that works. It prefers a patch of a compatible provisional Skill (Section 5.4) to a second, similar Skill. The Curator returns the related changes of one run as a result group , which admission applies together. 

Cite-or-retain rule. After a run, the compiler can consume a source, and a consumed source is not offered to later runs. The cite-or-retain rule consumes failed sources, unverified sources, and verified sources that an admitted change cites. The rule retains a successful source that no admitted change cites, so that a later run can use it. When the source stays unused, the rule consumes it. Later runs can thus revisit evidence, and unused evidence does not stay in the pool indefinitely. 

Outcome history. The compiler records the final outcome of each proposal for each task family: admission, scanner rejection, Curator rejection, human rejection, evaluation failure, or a failed model call. WikiSkill [Tang et al., 2026] and Procedural Graphs [Lu et al., 2026] report that a record of rejected proposals improves later proposals. The compiler gives the Reflector a short history as untrusted context. The history can help the Reflector avoid a change that was rejected, but it cannot support a proposal. 5.4 Admission, maturity, and trust Admission gates. Before admission, Zep checks the verification of the evidence, the applicability, the conflicts, and the required evaluations. A candidate that fails a check is not admitted automatically and waits for a human to review it. 

Approval modes. Each namespace uses auto or manual approval. In auto mode, Zep admits each candidate that passes the gates. In manual mode, a human must approve each candidate. A namespace can limit automatic approval to selected task families, and it can require a human to approve each Skill that uses selected tools. An approval must come from an authenticated human. An API credential cannot approve. Sharing a Skill with another namespace also requires a human. We chose auto as the default so that an admitted procedure can help on the next run. Manual approval would delay each candidate until a human reviewed it. The gates and the search weight (below) limit the risk of automatic admission. Verified failures lower the rank of a Skill, and a scheduled maintenance job can retire a provisional Skill that agents do not use. Search does not return a retired version. 

Evaluations. Zep does not run application code, verifiers, or evaluations. Voyager [Wang et al., 2023], SkillRevise [Liu et al., 2026a], and SkillLift [Kang and Wen, 2026] improve skills by execution of candidates. Execution would need a sandbox and the tool credentials of each application, which is impractical for a production service. A namespace can instead require evaluations for the candidates of a task family. The application reads the evaluations that each candidate needs, runs them in its own environment, and records each result on the candidate through the API. The record names the evaluator and its version, the environment, the verdict, and a reference to the evidence. Zep accepts a result only from a caller with access to the namespace. A failed evaluation rejects the result group, and the outcome history records the failure. A candidate without a passing result for each required evaluation stays a candidate. Scores from observability and evaluation platforms also enter as verification of the Traces themselves (Section 5.1). 

Group admission and versions. A human reviewer sees the complete result group. Admission applies every change of the group in one transaction or applies none, so an approval cannot leave out a related conflict. Each admitted change creates an immutable Skill version. Earlier versions stay readable, and a restore of an earlier version creates a new version. SkillRevise [Liu et al., 2026a] also keeps versions and selects among them by measured utility.

A trial is a full or partial use of a Skill whose outcome is a success or a failure with strong verification (Section 5.5 describes how an agent records a use). Other uses are not trials, for example a use in an abandoned attempt, a use with an unknown outcome, or a use whose outcome only the agent reports. The trust value of a Skill is the lower bound of the 95% Wilson score interval for its success rate over trials. The bound stays low until the Skill has enough trials. A Skill becomes established when its trust value meets the threshold. 

Search weight. Search ranks a compiled Skill with a second value, the search weight . The search weight is the posterior mean of the success rate. The prior uses the number of supporting attempt families n and a constant prior strength k:

w = k · nn+1 + sk + t

Here, s is the number of successful trials and t is the total number of trials. The prior mean n/ (n + 1) increases with the number of supporting families, and k sets how many trials the prior is worth. Each trial changes w, and verified failures can lower w below the prior mean. The trust value is conservative and controls maturity. The search weight changes with each trial and controls rank. Trials associate outcomes with Skill versions, but only a controlled evaluation can estimate the causal effect of a Skill. 

Single-source Skills. Some procedures run rarely, so the first verified success can be the only evidence for a long time. A service that waits for several attempt families leaves the agent without the procedure until then. A service that admits a Skill from one attempt family risks a procedure that holds only for that instance, for example a step that depends on a value of that task. Zep admits a single-source Skill , which is a Skill that one attempt family supports, and it limits the risk in three ways. First, the compiler applies the stricter checks of Section 5.3: the procedure must not keep identifiers from the source, and its applicability must stay within the tools and environments of the evidence. starts as provisional and has a lower search weight than a Skill with more support. Third, when later attempt families support a compatible procedure, the Curator patches or merges the Skill, and its maturity increases. 

5.5 Retrieval and use 

An agent searches with an objective. The request can also include optional filters, such as a task family, tools, and an environment. An application that declares the task family of its Traces (Section 5.1) can pass the same family to search. Search first keeps only the active Skills of the namespace that the caller may read and whose applicability fields match the request. It excludes candidates, retired versions, and Skills with an unresolved conflict. Relevance cannot override these filters. Search then matches the objective against a full-text index of a short descriptor of each Skill: its name, its description, and its applicability. Search ranks each result by its lexical score times its search weight (Section 5.4). The search weight changes the order of eligible Skills, and it cannot make an ineligible Skill visible. Retrieval has two steps, as in the progressive disclosure of the Agent Skills format [Agent Skills, 2026, Anthropic, 2026a]. First, search returns the descriptors of the matching Skills. The agent reviews the descriptors and selects the Skills that apply to its task. Second, the agent reads the body of each Skill that it selected. The agent thus loads a full procedure only for a Skill that it will use. Retrieval alone is not evidence that the agent used a Skill. The agent harness records a Skill use , which links a Skill version to the Trace of the task. The use outcome inherits the verification of the Trace only when the two outcomes match and the verifier is still registered. Uses with a strongly verified outcome are the trials of Section 5.4. We did not use vector retrieval. A descriptor is short, curated text with explicit names and use conditions, and we did not expect embedding similarity to select Skills better than lexical search on this text. Topic similarity can also return a Skill whose preconditions do not match the task. The experiments do not compare the two methods. A survey of dynamic skill libraries [Li, 2026] reports that selection from a flat store, which has no hierarchy or filter, can degrade when a library reaches tens to hundreds of skills, because each new skill adds distractors. The structured filters of Zep Agent Skills reduce the set of descriptors that the agent reviews. 

5.6 Governance and safety 

A poisoned Skill is more dangerous than a poisoned memory record, because the agent follows a Skill as instructions (Section 3.2). Zep Agent Skills can admit a Skill without human review (Section 5.4), so each control is an automatic check. Table 3 maps each threat of Section 3.2 to its controls. Most controls are part of the stages above. This section adds the controls for access, sharing, and deletion.

# 6 Evaluation method 

6.1 Research questions 

The evaluation answers six questions: • RQ1. Do Skills that Zep compiles from teacher Traces increase the pass rate of an executor agent on repeated tasks? • RQ2. Does a higher reasoning effort give the same gain as Skills? • RQ3. Do Skills change the reliability over repeated trials? • RQ4. Do Skills change the tokens and the latency for each passed task? • RQ5. Which tasks get the gain: tasks that the teacher solved, or tasks that the teacher did not solve? • RQ6. How does the gain from Skills compare with the gain from continuous fine-tuning of the model weights? The main experiments do not measure transfer to tasks that the compiler did not see, because of the design of the benchmarks. In τ 3 and EnterpriseOps-Gym, most tasks share little similarity with the other tasks of the benchmark, and in AppWorld only the variants of one scenario are similar. A split of these benchmarks into train and test tasks would leave few test tasks with a procedure that a train task teaches. Section 7.5 gives the limited transfer evidence that the experiments contain. 

6.2 Protocol 

Each main benchmark uses the same five stages: 1. Teach. A teacher agent runs each task. The harness records each run as a Trace with ordered events, an outcome, and external verification from the benchmark checker. 2. Compile. The harness sends the Traces to a Zep namespace. The production compiler (Section 5.3) compiles Skills from the Traces. Admission is automatic. 3. Freeze. The harness exports the active Skills to a snapshot file and records the SHA-256 digest of the snapshot. The executors read only the snapshot, so continued compilation cannot change an arm. 4. Execute. Each executor runs each task under two conditions, the two arms of the experiment. The no-Skills arm is the baseline and has the benchmark tools only. The Skills arm has the same tools, a Skill index in the system prompt, and a read_skill tool that returns the Markdown body of one Skill from the snapshot. The Skills arm thus differs from the baseline in three ways: the Skill content, a longer system prompt, and one more tool. The experiments do not separate these effects (Section 7.4). 5. Compare. The analysis pairs the two arms on the same task and trial. The teacher-executor configuration also models a deployment pattern for production. An application can send a task that it has not seen before to a stronger model. Zep Agent Skills compiles the verified successes of that model into Skills, and a cheaper and faster model then uses these Skills when the task occurs again. The experiments measure the second step of this pattern: the gain of the cheaper executors from the Skills of the teacher. The Skills arm uses progressive disclosure (Section 5.5), but the harness does not call search. It puts the Skill index in the system prompt. The index holds the name and the description of each Skill. The agent selects a Skill from the index and reads its body with read_skill . The harness does not insert a Skill body into the prompt. A cell is one executor model at one reasoning effort on one benchmark. The two arms of a cell run at the same time, because model APIs and serving change between runs. A paired interval within one run does not include this drift between runs. Different cells ran at different times and at different concurrency, so a latency comparison is valid only between the two arms of one cell. The scope of the Skill index is different for each benchmark (Table 4). When a request names a task family, search returns only the Skills of that family (the family index). The EnterpriseOps-Gym harness used the family index. The τ 3

and AppWorld harnesses gave the agent the Skills of all task families, so the agent had to select from a larger catalog than a family search gives. This catalog is the flat store of Section 5.5. 10 Learning by Doing: Autonomously Compiling and Curating Agent Skills from Verified Traces A P REPRINT

A Skill must carry a procedure and must not carry the answer of a scored task. The harnesses enforce these controls: • Tool isolation. The executor gets only the benchmark tools, read_skill , and a finish tool. The executors have no web access. • Teacher isolation. No agent sees the checker SQL, the reference solutions, or the database IDs. • Leakage scans. 6.6 ALFWorld setup 

The ALFWorld experiment differs from the main experiments in four ways: 1. Skill delivery. The harness inserted the top three search results as Skill bodies. The harness did not use the index and read_skill .2. Self-teaching. Qwen3-8B is the teacher and the executor. The teacher ran 34 train games of each of the six task types (204 Traces), and Zep compiled 22 Skills. RSD also learns from the runs of the same model. 3. Weak model. Qwen3-8B is a small model. We used it because the RSD paper reports its results on Qwen3-8B, so we can compare the two methods on the same model. 4. No controlled comparison with RSD. We rebuilt the RSD harness from the paper text (Appendix A). Thus the comparison uses the gain of each method over its own base. Each ALFWorld game is a household task in one of six task types, for example “put an object in a place” or “heat an object and put it in a place”. The prompt of each game includes one demonstration: the full steps of a different game that is solved. The choice of the demonstration changes the base score by about 32 points. The experiment reports two setups: • fixed : each game gets the same demonstration, a solved “put an object in a place” game. Thus, a heat game gets no example of how to heat an object. This setup is the weak base (42.8%). • typed : each game gets a demonstration of its own task type. For example, a heat game gets a solved heat game. This setup is the strong base (74.6%). The RSD paper reports 62.9% for Qwen3-8B before RSD training. This score is between the scores of the two setups.

# 8 Analysis 

Zep Agent Skills is designed so that an agent does not solve a task again after another agent solved it and a verifier confirmed the result. The results in Section 7 support this design on the tasks that the teacher solved, and they show the cases where Skills do not help. Zep Agent Skills helps in five ways. 

A weaker model repeats the work of a stronger model. Skills increase the pass rate in all 26 cells (Section 7.2), and each executor moves toward the teacher. For example, Claude Haiku 5.5 at medium effort on τ 3 goes from 21.1% to 36.6%, against 57.2% for the teacher. On EnterpriseOps-Gym, DeepSeek V4.1 Flash with Skills passes more tasks than the single teacher run (56.8% to 58.3%, against 52.8%). This is the production pattern of Section 6.2: a stronger model solves a task one time, and a cheaper model then does the task again with the Skill. On EnterpriseOps-Gym, Skills at the lowest effort also pass more tasks than no Skills at the maximum effort, for all three executors (Section 7.3). 

The gain comes from the verified procedure. The Skills arm also has a longer prompt and one more tool. These differences are the same for each task, but the gain is largest on the tasks whose own successful Trace a Skill cites (Section 7.5): • τ 3: +17.0 points on the tasks that the teacher passed in all four trials, against +0.6 on the tasks that it never passed. • AppWorld: +5.9 to +22.2 points on the tasks whose Trace a Skill cites, against −1.4 to +2.1 on the other tasks of the same scenarios, except +9.0 for GPT-6 Luna low .Thus, the content of the Skill is the most probable cause of most of the gain. The failure types agree with this result. In EnterpriseOps-Gym, the Skills arm has fewer episodes that end in a wrong final state, and fewer episodes that stop for missing information, in all nine cells (Section 7.7). A Skill gives the executor the steps and the information sources that the teacher used. 

The result is more repeatable. Skills increase the τ 3 tasks that pass in all four trials in 7 of 8 cells, and the AppWorld scenario pass rate in 9 of 9 cells (Section 7.3). 

Long tasks use fewer tokens. On τ 3, Skills decrease the tokens for each passed episode in all eight cells, by 7.0% to 44.6% (Section 7.4). On these long tasks, the steps that a Skill saves cost more than the Skill index adds. 

A model learns new procedures without training. On ALFWorld, the Skills from the runs of Qwen3-8B on train games increase its success on games in new rooms by 32.6 points from the weak base. They remove 57% of the failures, and RSD removes 37% (Section 7.6). From the strong base, they remove 32% of the failures. The gain is on the task types that the base did not know: for example, the heat type increases from 4% to 65%. The Skills come from other games, so this result is also the clearest evidence of transfer. The EnterpriseOps-Gym tasks that the teacher failed give weaker evidence: they gain +2.0 to +5.6 points (Section 7.5). Zep Agent Skills does not help in four cases. 

Tasks that the teacher did not solve. The τ 3 tasks that the teacher never passed gain only +0.6 points [ −2.2, +4.0] (Section 7.5). The compiler uses only strongly verified successes, so these tasks get no Skill of their own. The ability of the teacher thus limits the gain. See Section 9 for a future research direction. 21 Learning by Doing: Autonomously Compiling and Curating Agent Skills from Verified Traces A P REPRINT 

Tasks that the agent already knows how to do. When the base agent already has the procedure, a Skill adds little. AppWorld is saturated: the no-Skills arm passes 68.5% to 92.7%, and in eight of nine cells the gain is 4.5 to 7.7 points (Section 7.2). On ALFWorld, the gain from the strong base is +8.2 points on valid_unseen and +1.7 [ −4.5, +7.9] on

Losses from the Skill text. In each EnterpriseOps-Gym cell, Skills lose 14 to 32 tasks, against 73 to 94 wins (Section 7.7). The observed loss mechanism is a risk of the compiler design: a merge of two procedures that are similar but have opposite rules can keep the incorrect rule for one task (Section 5.3). This risk is an area of ongoing work. 

Short tasks with a full Skill index. On AppWorld, the tokens for each passed episode increase in seven of nine cells, because the index of all 62 Skills adds about 2,300 prompt tokens to each model call (Section 7.4). A production agent uses Skills search, not this index. 

# 9 Limitations and future work 

Transfer. The main experiments score the tasks that the teacher ran, and most of the gain comes from the tasks that the teacher succeeded on. They show that compiled Skills help an agent repeat a known task, and they do not show a gain on new tasks. The benchmarks limit this test: most of their tasks share little similarity with the other tasks (Section 6.1). A transfer test needs tasks that share procedures but differ in their instances. 

Learning only from successes. The compiler uses only strongly verified successes as support (Section 5.3). A task that the teacher never solved thus gets no Skill of its own, and its gain is small or 0 (Section 7.5). A failed Trace can still contain parts that succeeded, for example a sub-goal that a verifier checked before a later step failed. Future work will compile Skills from these verified parts of failed Traces. The sub-goals can come from checks that a verifier records during the task, or they can be inferred from the Traces of the task family. 

# 10 Conclusion 

Memory systems for production LLM agents mostly store facts and earlier interactions, not procedures that a verifier has tested. Zep Agent Skills captures each task attempt as a Trace, compiles strongly verified successes into versioned Skills that cite their evidence, curates them against the current library, admits them through trusted checks, and serves them in the open Agent Skills format. Automatic controls address the risks of a service that can admit a Skill without human review: instance-data leakage, instruction injection, poisoned outcomes, and flow across boundaries. On τ 3-bench, AppWorld, and EnterpriseOps-Gym, the compiled Skills increase the pass rate of each executor model at each reasoning effort, by 4.5 to 18.8 points. The gain is largest on the tasks that the teacher solved, which agrees with a design that learns from verified successes, so the success of the teacher limits the gain. The Skill index of the benchmark harness adds a cost to each model call, and Skills cause a small number of losses. On ALFWorld, Skills from the runs of a small model give a gain similar to or larger than the gain that a fine-tuning method reports. Two questions remain open: transfer to new tasks in the main benchmarks, and learning from tasks that the agent fails.
