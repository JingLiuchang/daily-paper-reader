# ABSTRACT 

Task success, retrieval quality, and cost do not show whether an LLM agent used a delivered memory or what followed from that use. We introduce MemUse, which evaluates memory at its point of use in recorded trajectories: each memory deliv-ery is compared with what the agent could already see and followed through the agent’s later actions and their consequences. An agentic judge rates each delivered entry’s relevance, accuracy, novelty, influence, and observed effect; programmatic checks enforce complete reading of cited evidence, and fixed rules aggregate the ratings into verdicts linked to memory histories and delivery cost. On 8,000 SWE-bench Verified episodes from three memory systems, resolve rates stay within 0.4 percentage points of a no-memory baseline, yet MemUse shows that most deliv-ered entries were irrelevant, most relevant entries went unused, and in two systems most deliveries restated content the agent could still see. It also surfaces effects that outcomes hide: 23.2% of episodes with beneficial memory use still failed, and 5 of 16 with harmful use still succeeded. 

# 1 INTRODUCTION 

As large language models (LLMs) become more capable, agents built on them are increasingly deployed on long-running tasks, such as repository-level software engineering (Jimenez et al., 2024; Huang et al., 2026) and multi-step workflows in terminal environments (Merrill et al., 2026; Desai et al., 2026). These tasks can accumulate more information than an agent’s finite context window can hold, and even within this limit, an agent’s performance can decline as the context grows (Du et al., 2025; Xia et al., 2026). Earlier decisions, codebase knowledge, and lessons from previous attempts often remain useful within and across tasks. Memory systems, such as MemGPT (Packer et al., 2024), Mem0 (Chhikara et al., 2025) and MemGovern (Wang et al., 2026), preserve and organize this information for repeated delivery during agent execution. Delivery, however, does not guarantee that the agent uses the memory or benefits from it, and delivered memory occupies part of the same finite context whose growth can degrade performance. This raises a central question: 

when does delivered memory help the agent, remain unused, or misdirect it? 

Existing memory evaluations provide only a partial answer, especially for agents performing com-plex, long-running tasks. Benchmarks such as LongMemEval (Wu et al., 2025) and LoCoMo (Ma-harana et al., 2024) primarily assess memory through question answering over conversation histo-ries, with LoCoMo additionally evaluating event summarization and dialogue generation. However, these benchmarks do not directly assess how retrieved information guides agents’ actions during task execution. Moving beyond conversational QA, VibeMemBench (Fan et al., 2026) evaluates mem-ory systems on repository tasks with executable tests, comparing memory-equipped agents with a matched memory-off baseline. Such comparisons measure differences in overall task performance, but not how individual memory deliveries influence agent behavior during execution. Useful guid-ance may be followed even when the agent ultimately fails a task, while harmful guidance may be corrected before it succeeds. Outcomes also cannot explain null results: when memory systems fail to beat the memory-off baseline, as in eleven of twelve VibeMemBench pairings, it remains un-clear whether the delivered memory was redundant, ignored, or helpful at some steps but harmful at others. Moreover, apparent memory gains can be inflated by evaluation artifacts (Son et al., 2026). 1arXiv:2611.01718v1 [cs.AI] 1 Nov 2026 Work in Progress Recent studies diagnose memory at a finer grain, evaluating memory operations, failures, and use (Hao et al., 2026; Deng et al., 2026; Cao et al., 2026; Liu et al., 2026). Behavioral analyses further examine whether retrieved facts appear in executed tool-call arguments and how memory-induced actions persist or are corrected (Mishra & Mishra, 2026; Chen et al., 2026). These diag-nostics rely on gold answers, reference operation traces, annotated use targets, known fact values, or controlled memory interventions, so applying them to an existing agent workflow requires refer-ence information or additional executions beyond its execution record. Meanwhile, reference-free trajectory evaluators such as TRACE (Kim et al., 2026) avoid this requirement by assessing reason-ing and tool use against accumulated execution evidence, but they do not explicitly distinguish the availability of specific information from evidence of its use and subsequent consequences. These studies leave open how to evaluate individual memories dynamically delivered during agent execu-tion, without reference answers or controlled memory interventions. Evaluating memory from execution records alone raises three challenges. First, the same entry may be delivered many times and in different forms, such as its full text or a search preview, so an evaluation must identify exactly what the agent saw. Second, the agent may already have the same information in its visible context, so an action that matches the memory does not by itself show memory use. Third, memory may shape actions many steps later, and those actions may be corrected or reversed, so its effects must be followed through the rest of the trajectory. To address these challenges, we introduce MemUse , a framework for evaluating individual memory deliveries in recorded agent trajectories as shown in Figure 1. Our central idea is to judge each memory delivery in context, rather than assessing stored entries in isolation. For each delivery, MemUse identifies exactly which text the agent received, compares that text with what the agent already knew, and follows what the agent did next through the rest of the trajectory. This separates the quality and novelty of the delivered information from evidence that the agent used it and from what that use led to. To our knowledge, MemUse is the first reference-free framework to jointly assess the use and observed effects of individual memory deliveries without a dedicated memory benchmark, reference solution, task label, or additional execution. To make these assessments verifiable, an agentic judge supports its assessments with cited trajectory evidence. Programmatic checks enforce evidence-access and coverage requirements, while fixed rules produce verdicts and retain uncertainty when evidence is insufficient. Linking these verdicts to memory histories and delivery costs helps identify irrelevant or redundant content, useful guidance that remains unused, and misleading guidance associated with unproductive actions. A memory bridge and a pass-through trajectory recorder support these assessments across agent harnesses and memory systems, covering both memory injected by the host and memory retrieved by the agent. We examine what outcome comparisons miss by applying MemUse to 8,000 recorded episodes, each a single agent execution of a task. These episodes cover all 500 tasks of SWE-bench Veri-fied (Jimenez et al., 2024) and four configurations of three memory systems: MemGovern (Wang et al., 2026), Mem0 (Chhikara et al., 2025), and TencentDB Agent Memory (Tencent Cloud, 2026). In these evaluations, the judge also receives each task’s gold patch through the optional reference-solution mode. Task outcomes barely separate the four configurations, since their resolve rates lie within 0.4 percentage points of a no-memory baseline, less than the spread across the baseline’s own runs. MemUse nonetheless separates the systems and reveals patterns consistent with these small outcome differences. Most delivered entries were irrelevant, 51–80% of the relevant ones remained unused in each system, and the entries that the agent acted on helped it far more often than they misdirected it. Task outcomes also concealed these effects, since 23.2% of episodes with beneficial memory use still failed, and 31.3% of those with harmful use still succeeded. 

# 2 RELATED WORK 

Memory systems for LLM agents. Memory systems for LLM agents differ in how they rep-resent, organize, and reuse past information. Generative Agents (Park et al., 2023) and Reflex-ion (Shinn et al., 2023) use stored observations or verbal reflections to guide later behavior. Others focus on memory organization: MemGPT (Packer et al., 2024) manages information across memory tiers, Mem0 (Chhikara et al., 2025) extracts and updates conversational facts, and EverMemOS (Hu et al., 2026a) and Hindsight (Latimer et al., 2026) organize interaction histories into structured long-term memory. Beyond conversational facts, MemGovern (Wang et al., 2026) distills GitHub issues, 2Work in Progress pull requests, and patches into reusable experience cards, and TencentDB Agent Memory (Tencent Cloud, 2026) shares skills and knowledge across agents. Complementing these efforts, MemUse evaluates whether and how individual memory deliveries guide agents’ subsequent actions. 

Memory evaluation benchmarks. Many memory benchmarks evaluate memory by end-task per-formance. LongMemEval (Wu et al., 2025) tests chat assistants on abilities such as knowledge updates and abstention, LoCoMo (Maharana et al., 2024) probes temporal and causal reasoning over long, multi-session conversations, and MemoryAgentBench (Hu et al., 2026b) uses incremen-tal interactions to evaluate retrieval, test-time learning, long-range understanding, and selective for-getting. For executable tasks, VibeMemBench (Fan et al., 2026) evaluates coding agents with and without memory on repository tasks where prior experience was observed to improve performance in a reference setting. Its main memory-system comparison provides one top-ranked retrieved ex-perience before execution and attributes underperforming cases to coverage misses, ranking misses, form degradation, or use failures. Such comparisons must also control for leakage, confounds, and run-to-run noise (Son et al., 2026). MemUse evaluates memory delivered during execution, whether injected by the host or retrieved by the agent, and judges each delivery through recorded actions and consequences, so it can surface useful guidance in failed runs and harmful detours in successful ones. 

Fine-grained memory diagnosis. Diagnostic benchmarks localize memory failures that aggregate scores hide. MemOps (Hao et al., 2026) evaluates lifecycle operations against gold operation traces, and MemTrace (Deng et al., 2026) uses gold answers to trace failed cases back to decisive faulty operations. EvalMem (Liu et al., 2026) separates encoding, retrieval, and generation defects using reference facts and oracle evidence, and MemCalib (Cao et al., 2026) measures proposition-level over-use and under-use against annotated target levels. Two studies examine agent actions more di-rectly. MERIT (Mishra & Mishra, 2026) measures how often agents act on a correctly retrieved fact in their tool calls, and Entry–Propagation–Recovery (E-P-R) (Chen et al., 2026) compares paired tra-jectories under varied memory content and injection schedules to locate where memory first diverts an action, whether the diversion persists, and whether the agent recovers. Each of these diagnoses relies on ground truth prepared in advance or on additional controlled runs. MemUse works from the recorded run alone and evaluates naturally delivered memories from recorded execution evidence. 

Trajectory-level agent evaluation. Trajectory evaluators provide a broader basis for examin-ing agent behavior. TRACE (Kim et al., 2026) scores efficiency, hallucination, and adaptiv-ity against an evidence bank of the agent’s earlier tool calls and observations, with no refer-ence trajectory. TRAIL (Deshpande et al., 2025) benchmarks error identification and localization, Who&When (Zhang et al., 2025) benchmarks the localization of errors and failure-responsible steps in agent traces, and TrajDebug (Qi et al., 2026) traces errors through their resolution and terminal impact. Agent-as-a-Judge (Zhuge et al., 2025) extends LLM-as-a-judge (Zheng et al., 2023) with artifact inspection and evidence retrieval to check task requirements. Attributing behavior to a spe-cific memory delivery requires an additional distinction: an action consistent with retrieved guidance may already have been planned before that delivery. MemUse adapts agentic inspection to this at-tribution problem. Its judge compares exactly what each delivery exposed with the agent’s earlier context, and programmatic checks confirm that every judgment cites fully read trajectory steps and covers the steps it requires, making each attribution verifiable against the recorded trajectory. 

Memory valuation and credit assignment. Another line of work scores individual memory en-tries to guide memory management. MemLens (Wei et al., 2026) approximates each memory unit’s Shapley-style contribution to a lightweight proxy model’s judged response quality and retains high-value units. Hindsight Memory-PRM (Jia et al., 2026) assigns entry-level credit from retrieval logs, answer citations, and controlled deletion-and-reanswer probes, then propagates it along ver-sion chains as a proxy reward for training a memory manager. Causal Memory Policy (Behnam & Wang, 2026) randomizes retrieval exposure with known propensities to estimate utility for memories in an exposure pool, including entries missed by the original retriever. All three measure an entry’s contribution through scored answers under deliberately altered memory contexts (sampled subsets, targeted deletions, or randomized exposure). MemUse instead gives an observational account of realized use. For each delivered entry, it reports whether and how the agent used the entry and what followed, linked to its history in the memory graph and the estimated size of its delivered text. 3Work in Progress Trajectory Recorder Data Processing

# 3 METHODOLOGY 

MemUse evaluates memory at its point of use. Its unit of evaluation is a memory delivery in context .This unit combines a delivered memory entry with the context that the agent already had, the actions that the agent took next, and the consequences of those actions. Figure 1 outlines how MemUse builds and judges these units. We first record memory operations and model calls, and we reconstruct each delivery in context from these records. An agentic judge then assesses the entries of eligible spans. Programmatic checks verify that the judge read the required evidence, and fixed rules convert the checked assessments into span verdicts. Finally, the memory graph links each verdict to memory histories and resource use. 3.1 MEMORY DELIVERY IN CONTEXT 

An agent solves a task q through interleaved model calls and tool interactions (Yao et al., 2023). An episode is one execution of the agent on a task, represented by a trajectory τ = ( s1, . . . , s T ).Each step st = ( xt, y t, o t) contains one completed model call with its input xt, its response yt,and the resulting tool observations ot. The exposed text limits the evaluation to the content that the agent received. The prior context holds everything else that the agent could see at that call, including earlier messages, tool results, and other memory deliveries. It is the reference for relevance and novelty. Together with earlier steps, it also separates memory use from actions that prior information or plans explain. Later steps show consequences, including corrections and reversals. We characterize each entry along three separate aspects. Information comprises its relevance, accu-racy, and novelty; use is its influence on actions; and consequence is the observed effect of that use. Repeated identical deliveries form injection spans , and each entry receives one assessment per span. Fixed rules aggregate these assessments into a span verdict, which pairs a triage label with an entry-share profile. The verdict describes observed behavior in the recorded episode, not a counterfactual effect on task success. The default evaluation needs neither a reference solution nor a reference trajectory. 3.2 RECORDING MEMORY DELIVERIES 

Evaluating a delivery requires two records: which input text came from memory, and what the agent actually received. The memory bridge identifies memory text through adapters for agent harnesses and memory systems. It annotates memory creation, updates, searches, and deliveries. For each delivery, it records every placement , a piece of memory text at one location in the model request. A placement proof , such as a digest of the carrying message or a path into the request, identifies this location. For memory systems that are built into a harness or run behind their own proxy, an observer emits the same annotations. A pass-through trajectory recorder captures what the agent actually received. It records requests and responses at the model-API boundary, including memory that a harness inserts into an outbound request but does not save in its history. The recorder normalizes calls into a common event log, keeps the model calls of the memory system out of the agent-step sequence, and retains reported token usage and cost when available. It checks each placement proof against the recorded request and links the delivery to the model call that carried it, the consuming call . When this call completed an agent step, that step is the attributed consuming step of the delivery. The recorder also logs when the harness removes or rewrites earlier messages, which shows when memory text leaves the input of the agent. 3.3 CONSTRUCTING THE EVALUATION CONTEXT 

From these records, we construct the evaluation context of Eq. (1) for each delivered entry. We recover the exposed text and the prior context, group repeated deliveries into injection spans that are judged once, assign a credit window to each entry of a span, and decide which spans the judge receives. 

Exposed text and prior context. Within each episode, we match each delivery to its verified consuming call and compare each entry with the recorded placement text to decide its exposure. The judge always sees the placement text. For full or clipped exposure, it also receives the exposed text of the entry. For unknown exposure, it does not receive the stored value. Type labels and confidence scores that exist only in the annotations are also withheld, because the agent never saw them. We reconstruct Bd from the recorded consuming input by removing the text of delivery d.The prior context therefore contains only text that is still present at step td. An entry delivered earlier but no longer in the input is not part of Bd. Steps that a context rewrite removed are also not part of 

Bd, but the judge can still read them to check what the agent did or planned before the delivery. 

Injection spans. Memory is often delivered repeatedly, for example when a host inserts the same entries before every model call. An injection span groups such repeats into one unit. A delivery joins an existing span only under two conditions. First, it repeats the entries of the span exactly, with the same order, the same placements, and the same exposure. Second, an earlier copy is still visible in its consuming input. Otherwise, the delivery starts a new span. The judge assesses each eligible span once. Credit windows. Credit windows divide the action credit for an item among the spans that deliver it. The window WS (m) starts at the first consuming step of S. It ends when an entry of the same item in a later span takes over the credit, or at the end of the episode if no entry does. For verified exposure, a later entry can take over when its text equals or contains ϵS (m). It must add text or an identifier, arrive when the earlier copy is no longer provably visible, or be a separately recorded full read reached through an explicit selection. Otherwise, a later copy that adds nothing to still-visible content receives an empty window, and WS (m) continues. When either exposure is unknown, the boundary rule uses item identity. A window only limits which actions an entry can claim. A credited action must occur inside the window, but its consequences are followed to the end of the episode. A test run after the window closes can therefore still show that an action inside the window helped or harmed. Removal of the entry text from the input does not close the window, because the agent can still act on guidance that it read earlier. The span has at least one entry and an attributed consuming step, at least one of its entries has a nonempty credit window, and its episode passes the recording checks below. A span whose entries all have empty windows, such as S3 in Figure 2, receives an automatic neutral triage label. The recording checks confirm which input text came from memory and what the agent saw at each consuming call. A check fails when a placement proof is missing, duplicated, or invalid. An agentic judge assesses every entry in an eligible span using the five signals in Table 1. These sig-nals distinguish information quality, attributable use, and observed consequences. Observed effect is assessed only when the entry was acted on. 

Evidence package and tools. For each eligible span, we prepare an evidence package containing the task, the exposed entries and their credit windows, and the prior context. Step files provide model responses, tool calls, and recorded results, with references to memory text stored separately. Following Agent-as-a-Judge (Zhuge et al., 2025), we use an LLM agent to inspect this evidence through two read-only tools: search evidence locates text, and read evidence reads files. The prompt requires a rationale for each signal value and instructs the judge to treat recorded text as evidence rather than instructions. 

Information quality. Relevance asks whether the exposed text applies to the task or the agent’s subgoal at delivery. Sharing a topic, file, or function is insufficient; information drawn from another situation must state a shared mechanism or an applicable procedure. Relevance is independent of accuracy, since an incorrect claim can still address the current task. Accuracy asks whether the recorded evidence confirms or contradicts the entry’s claim. The ev-idence must come from the situation the claim describes. For example, a claim about a bug in an earlier release requires evidence from that release, because later changes may behave differently. Claims about the current task are checked against its recorded state, and general claims about system behavior can be checked in any recorded case that meets their stated conditions. The judge assigns 

corroborated when evidence confirms the claim and contradicted when evidence refutes it. When neither conclusion is supported, the judge assigns uncontradicted , meaning that the claim remains unverified. Novelty measures what the entry adds to the recorded prior context BS . Content is novel when it adds new information, confirming when it settles an open hypothesis expressed by the agent, and 

redundant when it repeats established information. Novelty remains undetermined when a missing or unread source prevents the comparison. 

Attribution. To assess influence, the judge compares candidate actions with the task, the prior context, and the steps before the span’s first consuming step. Content is memory-specific when the entry supplies a specific fact or instruction that no prior source states for the same purpose. General advice, such as inspecting code or running tests, also matches ordinary task execution. An action matching such advice therefore requires evidence linking a specific detail of the action to the entry. 7Work in Progress An entry is acted on if the agent uses its memory-specific content in an executed action (e.g., a search, inspection, edit, or test), explicitly credits the entry for an action, or switches from a recorded prior direction to one the entry specifies immediately after delivery. An entry is selected if its only established use is retrieving a fuller version of the same memory item through its exposed identifier or preview, and that version is recorded as a separate memory deliv-ery; otherwise, the retrieval counts as acted on . Because the fuller delivery is assessed separately, selected entries receive a null observed effect. A selected entry does not compete with its fuller de-livery for content they share, whereas independent task instructions, prior decisions, and other prior sources remain competing explanations. If neither action nor selection is established, an entry is referenced when the agent mentions or quotes it. Influence remains undetermined when incomplete reads prevent a decision or the evi-dence cannot distinguish the entry’s contribution from another source. The judge assigns none only after reading the full credit window and finding no reference, selection, attributable action, or unde-termined attribution. 

Observed effect. Observed effect is assessed only for entries labeled acted on . The judge follows the consequences of actions guided by the entry through the end of the episode, including conse-quences observed after the credit window closes. An improved assessment requires a recorded check or subsequent use that demonstrates how these actions benefited the task or execution process. An investigation prompted by the entry can produce a useful finding even when it disproves the pro-posed solution. The benefit comes from using that finding to advance later work, for example by identifying the actual cause of a failure. Successful execution or a generic test pass alone is in-sufficient. The evidence must connect the benefit to the specific output or behavior shaped by the entry. 

Harmed requires evidence linking the entry’s guidance, through an action, to a harmful consequence such as a false lead, lost work, or unproductive behavior; mistakes introduced by the agent and unrelated execution failures do not by themselves establish harm. No effect requires evidence that an action guided by the entry neither made a difference nor added work; unlike influence none , it presupposes established use. The effect remains undetermined when the evidence does not establish the consequences of an attributed action. An entry that both helps and harms is labeled harmed , and its rationale describes both consequences. Accuracy and observed effect are assessed separately, with the overall task outcome serving only as supporting evidence. Appendix A.2 provides the full rubric and an attribution example. 3.5 CHECKING EVIDENCE AND DERIVING VERDICTS AND SCORES 

A judge answer enters the results only after programmatic checks accept its format and evidence coverage. Fixed rules then derive the span verdict from the accepted signals. A span verdict pairs a triage label, which flags the span for inspection, with an entry-share profile, which scores its entries for information quality, use, and consequence. 

Evidence checks. Structural checks require exactly one assessment per entry and valid signal values. An anchor cites the step of an action that the entry shaped and must lie within the entry’s credit window. Entries labeled acted on or selected must provide at least one anchor, and entries labeled none must provide none. Each step cited in an anchor or in the structured evidence list must be read in full, including its referenced tool results. Table 5 specifies the evidence required for each claim. Every answer requires complete reads of mandatory evidence, including the task, the prior-context index, and the first consuming step with its preceding step. Determined novelty or acted-on influence also requires complete reads of all sources in the prior context BS . Influence labeled selected , referenced , or none requires a complete read of the entry’s credit window. A determined observed effect requires every step from the start of that window through the end of the episode. Coverage counts only text that the read tool returned and that remains in the judge’s context, so search excerpts provide no coverage. The checks certify evidence access and coverage, and the judge interprets the evidence. Entry-share profiles. A triage label reflects the most consequential usage label in a span but not how many entries reached it. They count relevant entries with uncontradicted accuracy, relevant entries with undetermined novelty, entries with undetermined influence, and acted-on entries with undetermined effects. These shares show how much signal uncertainty accompanies the profile scores. 

Aggregate scores. The aggregate score in Eq. (3) weights each profiled span equally, regardless of how many entries the span contains or how often its delivery is restated. A search that returns many entries therefore cannot dominate the score, and restatements add no weight. Mean shares describe the composition of deliveries, while entry yields count contributions. Benefit and harm yields give the number of beneficial and harmful entries per 100 profiled spans. Token efficiency gives the number of beneficial entries per million estimated tokens of delivered memory text. Its denominator counts all memory text delivered in the evaluated scope, including restatements and spans without profiles, so text that received no assessment still counts as cost. Episode coverage reports the share of recorded episodes, including episodes without deliveries, that contain at least one relevant, beneficial, or harmful entry. # 4 EXPERIMENTS 

We apply MemUse to recorded SWE-bench Verified (Jimenez et al., 2024) runs of three memory systems to examine what it reveals that task outcomes do not. We first compare the memory profiles of configurations with similar resolve rates and then ask whether task outcomes reflect observed memory effects. Next, we trace benefit and cost to delivery forms, repeated delivery, and memory histories. Appendix A.6.8 reports judge follow-ups and resource use. 4.1 EXPERIMENTAL SETUP 

Tasks and agent. We use all 500 tasks of SWE-bench Verified (Jimenez et al., 2024), drawn from 12 Python repositories, and order them to approximate ongoing development work. Every run, with or without memory, executes the same sequence one task at a time. Systems that write memories start each run with an empty store, and each system decides how to update it as the sequence proceeds, so later tasks can use memories from earlier ones. Within each repository, tasks follow pull-request creation order, so each project’s tasks arrive in their historical order. The sequence also interleaves the repositories, as a developer who maintains several codebases moves between them, and each system’s own scope rules determine whether memories from one project can reach tasks in another. The agent is mini-SWE-agent (Yang et al., 2024) with gpt-6-luna 1, and the SWE-bench harness evaluates its final patches. 

Memory systems. We evaluate three systems in four configurations, which together cover the host-scheduled and agent-directed delivery routes. MemGovern (Wang et al., 2026) serves a fixed corpus of experience cards distilled from GitHub issues discussions, pull requests, and patches, and no run writes to it. The agent decides when to consult the corpus, using exp search to obtain pre-views of the ten best-matching cards and exp read to read one card in full. MemGovern’s prompt suggests this retrieval after the agent reproduces the issue and before it edits code. An audit of de-livered cards found overlap with benchmark source discussions and repair details; Appendix A.6.7 reports the evidence and provenance limits. Mem0 (Chhikara et al., 2025) starts each task with a task recall, in which the host searches the repository scope with the task text and places the results in the system message, where they remain for the whole episode. During the task, the agent can also search or save memories through a tool. After each episode, Mem0 extracts memories from the conversa-tion, excluding tool calls and their outputs, and stores them in the repository scope before the next task begins. The local configuration, Mem0 (L), limits memory to repository and episode scopes. The local plus global configuration, Mem0 (L+G), additionally permits a global scope shared across repositories, which the agent must request explicitly. TencentDB Agent Memory (Tencent Cloud, 2026) (TencentDB) keeps one store per run that all repositories share. Its model proxy inserts into every model call a persona block of general working principles, a scene index listing documents for recurring problem types, and a skill catalog of procedures distilled from earlier tasks. The agent can open scenes and search or open skills with shell commands. After each task, background extractors create and revise these memories from the agent’s conversation on the system’s own timers, which we shortened for these runs.

Second, 51.3–79.7% of the relevant entries remained unused, meaning that the agent did not act on, select, or reference them within their credit windows. Redundancy explains only part of this non-use, because many unused entries were novel relative to the agent’s prior context. Table 9 puts this novel share at 48–59% in MemGovern and Mem0 and at 90% in TencentDB. As a result of both bottlenecks, the agent acted on only 0.40–4.08% of a span’s entries on average, and beneficial entries reached only 3.65–7.05% of episodes. When the agent did act on an entry, benefit was far more common than harm. Of the 714 acted-on entries, 421 were beneficial, 16 were harmful, and 64 had no effect, while the remaining 213, or 29.8%, had an undetermined effect, including 132 of TencentDB’s 321. Use also often came late, as the first credited action followed the first consuming step for 51.8% of acted-on entries. A.1 RECORDING AND EVALUATION CONTEXT 

Recorded model inputs, memory annotations, and agent steps determine the evidence available for judging. The rules below establish what each entry exposed, which prior sources were visible, and which actions the entry can claim. A.1.1 RECORDING AND ANNOTATION 

Recording interface. The memory bridge connects a host adapter, which reports task boundaries and delivery opportunities, to a provider adapter, which performs memory storage and retrieval. It annotates these operations in the recorder’s event log. Episode boundaries come from bridge lifecycle events or episode-scoped session annotations. Generation events record memory-writing operations, and change events record item creations, updates, and deletions. Search events retain queries and results. Delivery events link the delivered text to its source searches and input slots. Portable item references connect these operations across tasks. The trajectory recorder captures model calls at the API boundary and normalizes supported APIs into a common log of turns, messages, and tool executions. Retraction and history-rewrite events preserve changes to the visible input, allowing each consuming request to be reconstructed. Call records retain timing, status, request and response data when available, and reported usage and cost. Role bindings separate agent, memory-system, and embedding calls. Completed agent turns define the step sequence, while operation references associate memory generation and search with their model calls. 

Consuming-step attribution. The recorder binds a delivery to the model call that carried it. A bound call that completed an agent step is an observed consuming call , and its step is the delivery’s 

attributed consuming step . An incomplete bound call provides no attributed step. An unbound delivery may receive a provisional step from adapter metadata or neighboring recorded steps for audit. Judging requires an observed consuming input. 

Placements and proofs. A delivery places text in named slots , such as a system-context block, prompt message, or tool result. The text in one slot is a placement ; the message containing it is its host message . A placement proof identifies either a message in the recorded history or a JSON-pointer location in the request, together with a digest of the corresponding text. The adapter or observer supplies the proof, and the recorder verifies it against the bound request. Judging requires each placement to resolve to one visible host message and one unique interval within it. This permits the delivered text to be separated from the rest of the input. Placements declared absent or adapter-defined remain unverified and cannot satisfy this requirement. 

Observed native memory. For memory systems embedded in a harness or proxy, an observer con-structs the same annotations from recorded calls and available store snapshots. It preserves exposed item identifiers and assigns identities to rendered or synthesized items when none are available. Thus, a synthesized retrieval answer can be recorded even when its stored sources are unknown. A request-only delivery becomes assessable once its call has an observed response and passes the placement checks. Store snapshots establish item states and net changes between captures, leaving intermediate mutations and undisclosed source identities unobserved. A.1.2 EXPOSURE MATCHING 

Exposure is determined by matching an entry’s recorded value against each placement separately. It is full when a placement contains the complete value and clipped when the longest match is a prefix of at least eight characters. The minimum prefix length limits coincidental matches on short openings. Otherwise, exposure is unknown , including when the value or placement text is missing. The matched value or prefix defines ϵd(m). Matching never joins text across slots. 

Text matching. A placement may encode an entry as a JSON string or line-numbered file view. Full matching therefore proceeds through three stages. The matcher first tests verbatim containment, 19 Work in Progress then lossless decoding, and finally restricted normalization. Decoding covers up to four nested JSON-string levels, consecutive numbered lines in tool results, and one character-entity decoding per XML text node. Each decoded string, line run, or node is searched separately. Normalization collapses whitespace and removes Markdown escapes only for values without quotes, backslashes, tabs, or line breaks, preserving meaningful syntax in code and structured text. If full matching fails, prefix matching uses only the original and decoded texts, which retain an exact correspondence to the recorded value. A.1.3 PRIOR CONTEXT AND RECORDING VALIDITY 

The prior context BS contains the first consuming input of span S with the target delivery removed. We reconstruct it by replaying the agent’s messages, retractions, and history rewrites in recorded order. A trailing retraction above any retained prefix is a known removal. Missing positions within the visible history, retractions without visible targets, and invalid retained prefixes are reconstruction gaps. 

Recording validity. Before judging, each episode must satisfy three conditions. First, every nonempty delivery with an attributed step must have an observed consuming call and a gap-free input. Second, every placement in an observed consuming call must have exactly one slot-matched proof resolving to one visible host message. Third, placement text must occur exactly once in its host message, with no unresolved proof naming that message as a possible host. A failure makes every nonempty span with an attributed step in the episode an error span. This episode-wide check is necessary because the spans share delivery and step records. Unresolved episode boundaries or assignments also produce errors, as does a missing task for a nonempty span with an attributed step. Spans rejected by these recording checks receive no judge call and are excluded from triage rates. A.1.4 INJECTION SPAN CONSTRUCTION 

An injection span groups deliveries with identical ordered entries, placements, and exposure. Entry equality uses namespace, item identity, identity scheme, portable version identifier, and content digest. Operation-local version identifiers are excluded because they cannot establish equality across operations. When neither a portable version nor a digest is available, equality uses namespace, item identity, and recorded value. Item identity falls back to the display key only when no item identifier is recorded and the key is not itself an operation-local version. Placements must agree in order, slot name, kind, and text, using a digest when text is unresolved. Grouping also requires an earlier copy of every entry to remain visible in the consuming input. Each entry’s exposed text must match in full within a proven placement of that copy, and any displayed key must remain visible in the copy’s placements. This requires an observed, gap-free consuming input. Unknown exposure cannot establish continued visibility and therefore starts a new span. Within each episode, deliveries are processed by consuming step and then recorded position. A span can continue across intervening steps and unrelated deliveries while equality and visibility hold. Alternating unchanged profile and skill blocks, for example, form one span per block. A change in an entry version, membership, order, placement, or exposure ends the current span of every item in the new delivery. Returning to the earlier content starts a new span, as does re-entry after visibility is lost. Each new span uses the prior context of its own first consuming step. Empty deliveries and deliveries without an attributed step use a restricted rule because their visibility cannot be checked. They join only the span of the immediately preceding delivery, provided that ordered entries, placements, exposure, and attribution status agree. Later deliveries within a span are restatements. They add delivery volume but no further assessments. A.1.5 PER -ENTRY CREDIT WINDOWS

The five signals distinguish information quality, attributable use, and observed consequences. Each entry receives all five signals under the rules below. 

Relevance. Relevance asks whether the exposed content applies to the task or current subgoal. A stated cause, diagnosis, or remedy for the current failure is relevant even when incorrect. A technique or check from another library can also be relevant if it applies as delivered. For an account of another failure, the text must supply a shared cause, failure mechanism, or applicable action. Shared topics, symptoms, or identifiers alone do not establish that connection. The judge assigns true when it can identify the applicable instruction or mechanism and false otherwise, including uncertain matches. 

Accuracy. Accuracy assesses a claim in the situation it describes. An account of a problem and its fix refers to the source situation even without a time qualifier and requires evidence about that source state. Current code or successful application alone cannot verify the historical account. Gen-eral claims can be checked wherever their stated conditions hold. Accuracy is corroborated when evidence confirms the claim, contradicted when it refutes the claim, and uncontradicted otherwise. Applicability to the current task remains a separate relevance judgment. 

Novelty. Novelty compares the entry’s propositions with the task, user updates, and visible sources in BS . Earlier deliveries count while visible, whereas same-input copies do not establish prior knowledge. Related facts, derivability, and expected task outputs alone do not establish a proposition or solution mechanism. Novelty is confirming when the entry settles an expressed open hypothesis, 

redundant when its content was already established, and novel when that content is absent. It re-mains undetermined when a missing or unread source prevents comparison. Expressed uncertainty takes precedence over other visible supporting facts. All material claims contribute to novelty, including irrelevant claims. A multi-claim entry is redun-dant only when every claim was established. Among the remaining claims, confirming applies if all were open hypotheses and novel applies otherwise, unless a context gap prevents a decision. 

Influence. Influence records what the entry demonstrably shaped within its credit window. The judge first checks prior sources , including the task, visible input, and earlier reasoning, commands, queries, and results. A competing source must state the same specific fact or instruction for the same 22 Work in Progress purpose before the first consuming step. Derivability, outside knowledge, and content first recorded after exposure do not qualify. 

Memory-specific content is a mechanism, location, identifier, value, command, check, or remedy supplied by the entry and absent from those sources. Routine practices such as reproducing failures or running tests qualify only when an action uses a detail supplied solely by memory. The judge inspects commands and results alongside reasoning to identify uses within the window, then assigns one of the following labels. • Acted on . An action uses memory-specific content, the agent explicitly credits the entry for an action, or the agent changes from a recorded prior direction to the direction specified by the entry immediately after delivery. Reading, searching, or editing a location named only by the entry qualifies even if its proposed remedy goes unused; what the agent finds there is the action’s result. When an action combines sources, credit is limited to its memory-specific component. A decision receives credit only when subsequent execution carries it out. • Selected . The exposed identifier or preview prompts retrieval of fuller memory content that appears as a separate recorded delivery, with no other use of the entry’s content. The fuller content is assessed in its own delivery. Retrieval whose result is not a recorded delivery, or inspection of repository code or task data at a path supplied by the entry, is acted on because no other span assesses the returned content. • Referenced . The agent mentions or quotes the entry using its exposed identifier, distinctive content, or list position, but no action is established. A comment about the entire result list does not reference an individual entry unless it was the only entry shown. A mention that merely confirms an existing plan remains referenced. • Undetermined . An action uses information stated in both the entry and a prior source, but the record does not show which guided it. This ambiguity can arise when the agent had expressed only an unverified hypothesis, question, or search query before delivery. It can also occur when the same information was stated in an earlier source but the agent had not acted on it. The label also applies when incomplete reads of prior sources or the credit window prevent an attribution decision. The note identifies the action and quotes the competing source, or specifies the unread evidence. • None . A complete read establishes no reference, selection, or attributable action, and no action has undetermined attribution under the preceding rule. An action that simply follows the task instructions or implements a decision or action made before delivery is explained by that prior source. An open possibility leaves attribution undetermined because it does not establish a prior decision. None denotes unestablished attribution, not a demonstrated zero effect. Three allocation rules complete the definition. First, other items already present in the agent’s input are competing sources, while identical same-item copies arriving in one input form a single source. Second, shared content is assigned to a selected fuller delivery. The same convention applies when a wider delivery takes over the window of an earlier visible copy, even without selection. The earlier copy is then excluded as a competing source for shared content, while independent task instructions, prior decisions, and other sources remain competitors. A selecting preview remains selected unless it shaped an action before the handoff or through content only it exposed. Third, action anchors must fall inside the credit window of the entry. 

Observed effect. Observed effect records the consequences of anchored actions for the task out-come or execution process. It is assessed only for acted-on entries; all other entries receive null .• Improved . Subsequent work demonstrates a benefit from the action, including use of its finding to select or reject a course of action. A finding can contribute even if it disproves the entry’s proposed remedy. The judge cites a check or subsequent use of the output or property shaped by memory. A recorded assertion, before/after reproduction, or down-stream use must demonstrate the memory-shaped property. Episode coverage. Episode coverage divides by the number E of selected recorded episodes, including episodes without deliveries. An episode is profiled when it contains a profiled span. It is relevant, beneficial, or harmful when one of its profiled spans has a nonzero count on that axis. Spans outside every recorded episode keep their delivery cost but establish no coverage, and the report counts them separately. A few items that the memory system delivers in many episodes, such as a profile block inserted before every task, can account for most relevance coverage. A frequency diagnostic therefore marks an item, identified by namespace and item identity, as recurring when it is delivered in at least max(2 , 0.1E) distinct episodes. The report gives the share of relevant entries from recurring items and the relevance coverage that remains without them, and the diagnostic leaves every profile unchanged. A.4.3 MEMORY HISTORIES 

The memory graph links operations by namespace and item identity across trajectories. Items whose creation was not recorded retain an unobserved origin. Multiple versions of one item in a delivery share an item-level recall link, while their assessments retain their distinct versions and exposures. Observed updates, deletions, and recreations extend this history; unavailable intermediate mutations remain unobserved. A.4.4 TOKEN USAGE , M ONETARY COST , AND TEXT VOLUME 

Recorded call and operation usage. Token accounting uses recorded input, output, and cache counters. Cache and reasoning tokens are subsets of input and output and are not added again. Operation references assign model and embedding usage to memory generation or search, counting a search once even when several deliveries reference it. Monetary accounting distinguishes provider-reported cost from cost calculated at configured rates. Unavailable usage and cost remain unknown in the underlying call records. The accounting covers observed model calls and excludes unreported service work and hosting charges. 

Delivered text volume. For span S, CS sums placement characters across all deliveries, including restatements and wrapper text. Because token counters belong to whole model calls, delivery volume uses the auxiliary estimate bTS = ⌊CS /4⌋. This estimate supports comparisons of delivered text and is separate from monetary accounting. Redacted placements without recorded sizes contribute zero and trigger a warning. Every span’s volume is retained under its outcome class, including error, unjudged, empty, and unassessable spans. A.5 EXPERIMENTAL DETAILS 

The experiments use one fixed task sequence, four runs per configuration, and a common judge protocol. The details below specify how memory persists across tasks and how results are pooled. A.5.1 TASKS AND AGENT 

Task order. All runs execute the 500 SWE-bench Verified tasks from 12 repositories in the same order. Within each repository, tasks follow pull-request creation time, with the pull-request number breaking ties. The bridge merges these streams while preserving their internal order. It prioritizes placing source tasks before related tasks in other repositories, achieving this order for 55 of 66 pairs identified before the runs. The next priority is to place tasks before superficially similar tasks they should not help, followed by balancing the repositories across the sequence. Tasks run sequentially, with memory retained between episodes. 

Agent. The agent is mini-SWE-agent 2.4.6 with gpt-6-luna with medium reasoning effort through LiteLLM 2. Each task runs in its SWE-bench Docker image with limits of 250 steps, 1,200 seconds overall, and 60 seconds per shell command, without a monetary cap. The SWE-bench harness evaluates each final patch with a 1,800-second test limit. Testing timed out for three memory episodes, which count as non-resolved in the resolve rate but are excluded from analyses requiring completed test results.

A.5.2 MEMORY SYSTEMS 

MemGovern. MemGovern serves a fixed corpus through a pinned server. The agent retrieves previews of the ten best-matching cards with exp search and a full card with exp read . Its prompt suggests searching after reproducing the issue and before editing code. The corpus remains fixed throughout every run. 

Mem0. Mem0 2.2.1 runs in open-source local mode from an empty store. Before each task, the host searches the repository scope using the task text and waits up to two seconds. Results occupy at most 4,000 characters in the system message, including the surrounding frame. During execution, 

mem0 memory supports search, addition, update, and deletion with the default search settings. After each episode, gpt-6-luna extracts memories from user and assistant messages, excluding tool calls and outputs, and stores them in the repository scope. Mem0 (L) permits repository and episode scopes. Mem0 (L+G) also permits an explicitly requested global scope, but none of its 3,997 searches used that scope. 

TencentDB. TencentDB Agent Memory runs in its native proxy profile with memory and skills, starting from an empty store. The proxy inserts a persona block, scene index, and skill catalog into each model call. The agent uses shell commands to search and read skills or read scenes. Background extractors use gpt-6-luna to build memories from these conversations. We reduce the idle trigger from 600 to 60 seconds, the delay before second-stage extraction from 90 to 10 seconds, and the minimum interval between second-stage runs from 900 to 60 seconds. The proxy uses Chat Completions for agent calls, while the other configurations and baseline use Responses. An observer reconstructs memory deliveries from the recorded model calls.
