## 摘要
任务成功率、检索质量和成本并不能说明 LLM 智能体是否使用了已交付的记忆，也不能说明这种使用带来了什么后果。我们提出 MemUse，在记录轨迹中的记忆使用点对其进行评估：将每次记忆交付与智能体当时已经能够看到的内容进行比较，并沿智能体后续动作及其后果追踪该记忆的影响。一个智能体评审器对每个交付条目的相关性、准确性、新颖性、影响力和观察到的效果进行评分；程序化检查确保完整阅读所引用的证据，固定规则将评分汇总为与记忆历史和交付成本相关联的判定。在来自三个记忆系统的 8,000 个 SWE-bench Verified 任务实例中，解决率与无记忆基线的差距保持在 0.4 个百分点以内，但 MemUse 表明，大多数交付条目无关，大多数相关条目未被使用，并且在两个系统中大多数交付只是重述了智能体仍然能够看到的内容。它还揭示了结果所掩盖的效应：在有益记忆使用的任务实例中，仍有 23.2% 失败；在有害使用的 16 个实例中，有 5 个仍然成功。

## Abstract
Task success, retrieval quality, and cost do not show whether an LLM agent used a delivered memory or what followed from that use. We introduce MemUse, which evaluates memory at its point of use in recorded trajectories: each memory delivery is compared with what the agent could already see and followed through the agent's later actions and their consequences. An agentic judge rates each delivered entry's relevance, accuracy, novelty, influence, and observed effect; programmatic checks enforce complete reading of cited evidence, and fixed rules aggregate the ratings into verdicts linked to memory histories and delivery cost. On 8,000 SWE-bench Verified episodes from three memory systems, resolve rates stay within 0.4 percentage points of a no-memory baseline, yet MemUse shows that most delivered entries were irrelevant, most relevant entries went unused, and in two systems most deliveries restated content the agent could still see. It also surfaces effects that outcomes hide: 23.2\% of episodes with beneficial memory use still failed, and 5 of 16 with harmful use still succeeded.

# 《Delivered, Not Used: Evaluating Agent Memory at Its Point of Use》论文总结

## 1. 核心问题与研究动机

- **背景**：LLM 智能体被 increasingly 部署于长时任务（仓库级软件工程、终端多步工作流），任务积累的信息超过有限上下文窗口，且上下文增长本身会降低性能。MemGPT、Mem0、MemGovern 等记忆系统通过重复"交付"（delivery）来保留和复用信息。
- **核心矛盾**：**交付不等于使用**。记忆被放进模型输入，不代表智能体使用了它，更不代表它带来收益；而且交付的记忆本身占用同一份有限上下文。
- **现有评估的不足**：
  - 任务成功率、检索质量、成本只能给出聚合结果，无法说明单条记忆是否被使用、如何被使用、带来了什么后果。
  - LongMemEval、LoCoMo 等基准以对话问答形式评估记忆，不直接考察记忆如何指导任务执行中的动作。
  - VibeMemBench 比较"有记忆 vs 无记忆"的整体表现，但无法解释零结果（12 组配对中 11 组未胜出）究竟是冗余、被忽略，还是某些步骤有益、某些步骤有害。
  - MemOps、MemTrace、EvalMem、MemCalib、MERIT、E-P-R 等细粒度诊断依赖金标准答案、参考操作轨迹、标注使用目标或受控记忆干预，无法直接用于已有执行记录。
  - TRACE 等无参考轨迹评估器不区分"信息可得"与"信息被使用及其后果"。
- **核心研究问题**：**交付的记忆何时帮助智能体、何时未被使用、何时误导智能体？**
- **整体含义**：论文主张把记忆评估从"结果指标"转向"使用点"（point of use），即逐条交付、结合当时可见上下文、沿后续动作与后果进行归因评估。

## 2. 方法论（MemUse）

### 2.1 核心思想
- 评估单元是**上下文中的一次记忆交付**（memory delivery in context），形式化为：
  $$c_d(m) = (q,\ B_d,\ \epsilon_d(m),\ W_d(m),\ \tau)$$
  其中 $q$ 为任务，$B_d$ 为消费输入去掉本次交付文本后的先前上下文，$\epsilon_d(m)$ 为条目 $m$ 的暴露文本，$W_d(m)$ 为信用窗口，$\tau$ 为完整轨迹。
- 将**信息质量**（相关性、准确性、新颖性）、**使用**（影响力）、**后果**（观察效果）三个维度分离评估，避免"内容好"与"被使用"与"产生收益"相互混淆。

### 2.2 记录与上下文构建
- **Memory Bridge**：通过 agent harness 适配器与记忆系统适配器，标注记忆的创建、更新、搜索、交付；对内置或代理式记忆系统由 observer 产生相同标注。
- **Pass-through Trajectory Recorder**：在模型 API 边界记录请求与响应（包括 harness 插入但未保存到历史中的记忆），归一化为统一事件日志，保留 token 用量与成本，并记录历史重写/撤回事件。
- **Placement 与 proof**：每次交付记录"放置"（文本+槽位）及其证明（消息摘要或 JSON 指针），并与实际请求校验，确定**消费步骤**。
- **暴露匹配**：full（完整包含）、clipped（前缀匹配，至少 8 字符）、unknown（无法判定）；支持 JSON 解码、行号视图、受限归一化。
- **注入跨度（injection span）**：将条目、顺序、放置、暴露完全相同的重复交付合并为一个评估单元；后续重复为"重述"（restatement），只计成本不计判定。
- **信用窗口**：从跨度首个消费步骤开始，到同条目后续交付接管（文本包含原暴露文本、新增文本/标识、或原副本不再可见）或 episode 结束；窗口只限制可归因动作，后果追踪至 episode 结束。
- **资格判定**：跨度需有至少一个条目、有归属消费步骤、至少一个非空信用窗口，且 episode 通过记录检查；空交付、无消费步骤的交付单独计数，不进入 triage 比率。

### 2.3 评审信号（五维）
| 维度 | 信号 | 取值 |
|---|---|---|
| 信息 | 相关性 | true / false |
| 信息 | 准确性 | corroborated / uncontradicted / contradicted |
| 信息 | 新颖性 | novel / confirming / redundant / undetermined |
| 使用 | 影响力 | acted on / selected / referenced / none / undetermined |
| 后果 | 观察效果 | improved / no effect / harmed / undetermined（仅对 acted on 评估） |

- **归因规则**：要求"记忆特异内容"（特定事实、位置、标识、命令、检查或补救措施），且先前上下文未以同一目的陈述；区分 acted on（执行动作使用）、selected（通过标识/预览检索更完整内容，单独评估）、referenced（提及/引用）、none（完整读取后无归因）、undetermined（竞争来源无法区分）。
- **效果规则**：improved 需有记录检查或后续使用证明收益（即使证伪原方案也可算有益）；harmed 需有证据将指导经动作链接到有害后果（误入歧途、丢失工作、无效行为）；no effect 需肯定性证据；同时有益有害判为 harmed。

### 2.4 证据校验与判定聚合
- **程序化检查**：每个条目恰好一个评估、信号取值合法、acted on/selected 必须有落在信用窗口内的锚点、所有引用步骤必须完整读取（含工具结果）、新颖性/影响力判定需完整读取 $B_S$ 全部来源、效果判定需完整读取窗口起点至 episode 结束。
- **固定规则**：条目使用标签 → 跨度 triage 标签（优先级：negative > positive > unresolved > neutral）。
- **Entry-share profile**：六轴（relevance、corroboration、information gain、acted on、benefit、harm），统一以跨度全部条目为分母，另设四个不确定性份额；聚合时每个 profiled span 等权。
- **附加指标**：benefit/harm yield（每 100 profiled spans 的有益/有害条目数）、token efficiency（每百万估计交付 token 的有益条目数）、episode coverage、recurring item 诊断。
- **Memory Graph**：将交付链接到条目跨轨迹历史（创建/更新/删除），标记未观测起源；并报告 token 用量与成本，交付文本量以放置字符数 ÷4 估计。

## 3. 实验设计

- **数据集/场景**：SWE-bench Verified 全部 **500 个任务**，来自 **12 个 Python 仓库**；任务按 PR 创建时间排序并交错仓库，模拟持续开发；记忆系统在任务间保留记忆。
- **智能体**：mini-SWE-agent 2.4.6 + **gpt-6-luna**（medium reasoning effort），经 LiteLLM 调用；每任务 SWE-bench Docker 环境，250 步、1200 秒、单条 shell 60 秒限制；harness 测试限 1800 秒。
- **对比的记忆系统（4 种配置，覆盖宿主注入与智能体检索两条路径）**：
  - **MemGovern**：固定经验卡语料，智能体用 `exp search`（10 条预览）与 `exp read`（全文）检索。
  - **Mem0 (L)**：任务开始时宿主按仓库范围检索并放入 system message；运行中可搜索/保存；episode 后抽取记忆，限仓库与 episode 范围。
  - **Mem0 (L+G)**：额外允许显式请求全局范围（实际 3,997 次搜索中从未使用）。
  - **TencentDB Agent Memory**：代理每次调用注入 persona 块、scene 索引、skill 目录；智能体可用 shell 打开 scene/skill；后台抽取器更新记忆（缩短了触发间隔）。
- **基线**：无记忆基线。
- **运行规模**：每种配置与基线各 **4 次运行** → **8,000 个记忆 episodes + 2,000 个基线 episodes**。
- **评审器**：**DeepSeek-V4.1-Flash-1017**，temperature 0、medium thinking；提供任务 gold patch 作为可选参考解，但不提供 harness 结果；单跨度预算 250 次模型调用、272K 上下文、32,768 输出 token、最多两次修复（每次 4 次调用）、5 跨度并行。
- **统计方法**：配对 bootstrap（500 任务重采样、5,000 次重复）给出 95% 置信区间；运行间变异用样本标准差。
