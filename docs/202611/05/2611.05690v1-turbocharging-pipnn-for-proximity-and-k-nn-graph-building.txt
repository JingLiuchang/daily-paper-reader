Abstract 

Graph-based Approximate Nearest Neighbor Search (ANNS) in-dexes such as HNSW and Vamana deliver state-of-the-art query performance at the cost of large indexing times. The recently in-troduced PiPNN method drastically accelerated index construction by way of a partitioning-based algorithm which leverages efficient dense matrix multiplication and top-k aggregation kernels. In this paper, we unlock the full potential of PiPNN’s hardware-friendly algorithm design. We introduce PiPNN II, which optimizes multiple steps of the PiPNN recipe, giving up to 8 × speedups for graph-based ANNS index construction. In addition, we present GPiPNN, a GPU implementation of PiPNN, which builds compa-rable ANNS indices up to 43 .7× faster than Jasper and up to 50 ×

faster than CAGRA. We also extend PiPNN II and GPiPNN to com-pute high-quality 𝑘 -nearest-neighbor ( 𝑘 -NN) graphs directly, which unlocks massive speedups over methods used in many existing sys-tems for clustering, anomaly detection, and more. For 10-NN graph building at 90% recall, we obtain up to a 13 × speedup on CPUs and 6.6× on GPUs as compared to the prior best methods. PiPNN II can build a billion-scale 10-NN graph in under 16 minutes. Common to both PiPNN II and GPiPNN is the use of quantization 

to reduce memory traffic and leverage fast low-precision matrix operations. Top-𝐾 emerges as a new bottleneck, which we optimize by specializing the code to the specific 𝐾 , as well as fusing with the matrix kernel to avoid materializing the distance matrix to memory. For CPUs, we demonstrate further performance improvements by leveraging our matrix kernels in the RobustPrune procedure originally proposed in Vamana and used in PiPNN. On GPUs, we flatten recursive partitioning into segmented batches, use one fused top-𝐾 abstraction for partitioning and leaf scoring, and prune with already-witnessed direct edges rather than a new candidate-to-candidate scoring pass.

Fast index construction is not merely a convenience: build time is often a major factor in the total cost of the system. Indexes must be rebuilt as data drifts, parameters need to be tuned across datasets, and ANNS appears as an inner loop in fundamental tasks including accelerated 𝑘 -means [60], hierarchical clustering [12, 67], minimum spanning trees, and single-linkage clustering [1, 3, 5, 7]. Small modifications to graph-index construction also yield high-quality 𝑘 -NN graphs [8], a primitive that we directly target in this paper. An indexing method that takes hours or days is simply unusable in many modern workflows. The recently introduced Pick-in-Partitions Nearest Neighbors (PiPNN) method significantly speeds up high-quality index con-struction by replacing build-time graph search with regular partition-local scoring work [56]. It recursively partitions the input vectors into small overlapping collections (termed “leaves”), generates candidate edges through batched all-pairs distance com-parisons and top-𝐾 aggregation inside each leaf, and streams those candidates through an online history-independent pruning procedure (HashPrune) to retain sparsity. The bulk of PiPNN’s construction is comprised of all-to-all comparisons over small, cache-resident sets of vectors; an operation far more amenable to modern hardware than the irregular pointer-chasing of incremen-tal graph construction [17, 30, 40]. Despite these significant improvements in build times, the first version of PiPNN fails to leverage modern hardware to its full potential. For instance, it keeps vectors in full-precision float32 form to perform GEMM (General Matrix Multiply) and materializes the full distance matrices to memory to perform per-row top-𝑘 

reduction. In this paper we significantly optimize the entire ap-proach from first principles. We start by leveraging quantization 

to replace the full-precision vectors with compact integer codes that are cheaper to compare [14, 27, 32, 35, 41, 61]. Quantizing the vectors not only speeds up memory accesses, but it also enables low-precision multiply-accumulate instructions. Decoding cost may seem concerning at first glance, but is easily amortized over many distance computations. Lastly, we fuse the GEMM kernel with top-k reduction in register, to avoid materializing an 𝑀 × 𝑁 distance ma-trix to memory. While fused distance computation and in-register

The aforementioned opportunity and challenge carries over to hardware acceleration using GPUs. Compared to existing GPU ANNS systems [42, 50] which struggle to leverage the full potential of the hardware due to relying on either beam search or iterative refinement on graphs, PiPNN’s batched many-to-many structure is an ideal fit for tensor cores. However, implementing PiPNN on GPUs presents non-trivial challenges: PiPNN’s recursive partition-ing produces irregularly-sized subproblems whose control flow is not handled well by the GPU scheduler and must be flattened into uniform passes; the vectors needed for each local comparison are scattered in device memory and must be gathered into dense batches; and the HashPrune reservoirs for each point must be maintained without the use of locks. 

In this paper we realize the full potential of PiPNN by carefully restructuring PiPNN’s construction pipeline around fused quantized batched top-𝐾 kernels . We instantiate this de-sign on both shared memory CPU systems ( PiPNN II 1) as well as GPUs ( GPiPNN ), thus cashing in on the promise for hardware-accelerated ANNS builds within the PiPNN framework. Our results show that our GEMM kernels take full advantage of the hardware: the CPU score-and-select kernels run near instruction through-put roofline, whereas the corresponding GPU kernels are memory bound for high-dimensional vectors typical of modern embeddings. On GPUs, PiPNN flattens the recursion used in PiPNN’s par-titioning routines by refactoring them as radix sorts over leader-assignment keys. In addition, it processes multiple collections of points in a single kernel using a segmented top-𝐾 primitive, which ameliorates workload imbalances. Finally, it avoids a costly final prune, by way of a novel DirectEdgePrune over the cached dis-tances in the HashPrune structure. Our extensive experimental study establishes PiPNN II and GPiPNN as the new state of the art for proximity-graph index construction on CPUs and GPUs, delivering large speedups over the strongest prior methods while preserving high-recall query

2 Preliminaries and Prior Work 

Approximate Nearest Neighbor Search (ANNS). Let X ⊆ R𝑑 be a collection of 𝑛 vectors and let 𝑑 (· , ·) denote a dissimilarity measure on R𝑑 (e.g. Euclidean distance or the negative of an inner product). Definition 1. (𝑘 -nearest neighbor search) Given a query 𝑞 ∈ R𝑑 ,the 𝑘 -nearest neighbor set of 𝑞 in X is the set K ⊆ X of size 𝑘 ≤ |X| 

containing the 𝑘 points of smallest dissimilarity to 𝑞 :

∀𝑝 ∈ K , ∀𝑝 ′ ∈ X \ K , 𝑑 (𝑞, 𝑝 ) ≤ 𝑑 (𝑞, 𝑝 ′).

We assume K is unique. In ANNS, the goal is to return a set K′

that approximates K as efficiently as possible. Definition 2. (𝑘 @𝑘 ′ recall) Let K be the exact 𝑘 -nearest neighbor set of query 𝑞 and let K′ ⊆ X be a returned set of size 𝑘 ′. The 𝑘 @𝑘 ′

recall of K′ is | K∩K ′ || K | .

We focus on 10@10 recall and use recall to denote this quantity; the recall of a query set 𝑄 is the mean recall over all queries in 𝑄 .

Graph-based ANNS. Graph-based ANNS methods build a sparse 

proximity graph over the points, with outgoing edges to a small set of nearby neighbors. The graph need not exactly equal the 𝑘 -NN graph; it must only be navigable enough that a local search can locate the nearest neighbors. HNSW and Vamana are canonical Turbocharging PiPNN for Proximity and 𝑘 -NN Graph Building 

examples, both constructed via greedy graph traversal [30, 40]. A long line of work has refined proximity-graph constructions [13, 15– 17, 28, 29, 39, 43, 46, 64, 66, 70], developed parallel or disk-resident variants [35, 41, 59], accelerated query-time search [10, 20, 26], and ported graph indexes to GPUs [34, 42, 50]. 

Beam search. The standard graph-query procedure is beam search. It maintains a beam 𝐵 of the 𝐿 best points seen so far; at each step it expands the best unvisited point in 𝐵 , inserting its neighbors into 

𝐵 and truncating back to size 𝐿 . The search terminates when every point in 𝐵 has been expanded, and the final beam is returned or used as candidates for reranking (see code in Appendix A, Algorithm 5). 

The “search bottleneck”. Prior to the introduction of PiPNN, the highest-quality graph indexes were built by searching during con-struction : HNSW and Vamana insert points incrementally, travers-ing the partial index to find candidate neighbors for each point, then pruning for sparsity [30, 40]. This produces excellent graphs but creates a search bottleneck : beam search is rife with random mem-ory accesses and cache misses, so traversal dominates construction time. PiPNN’s partitioning approach breaks altogether from prior solutions which used distance-comparison-skipping heuristics and cheap graph-initialization. It builds indexes up to 11 .6× faster than the efficient ParlayANN implementation of Vamana [41]. 

2.1 Quantization 

Quantization is a lossy compression technique that maps high-precision vectors to a smaller, discrete set of representative points. Broadly speaking, three types of quantization methods are widely-used in the ANNS literature: scalar uniform quantization, which independently maps each vector coordinate to an 𝑋 -bit integer; product quantization, which partitions a vector into subvectors and performs lookups in learned codebooks [23, 31]; and rotation-based quantizers, which apply a random rotation and leverage distributional properties of the rotated vectors, including RaBitQ [18, 19, 21], DRIVE/EDEN [6, 62, 63], and TurboQuant [68]. In this paper, we consider two quantization methods: RSQ8 (rotated scalar quantization with 8 bits per coordinate) and TQ4 , a 4-bit variant of TurboQuant, which we outline next. 

TurboQuant. TurboQuant is a scalar quantizer with non-uniform codebook. It first applies a random rotation and then quantizes each post-rotation coordinate independently with a scalar Lloyd– Max codebook trained against the post-rotation marginal [68]. This achieves near-optimal distortion across bit widths and dimensions, but the resulting inner-product estimator is biased because the MSE-optimal codebook is not matched to the inner-product ob-jective. The original TurboQuant addresses this with a two-stage estimator that applies a 1-bit JL quantizer to the residual to recover an unbiased dot product. 

TurboQuant variant. We adopt TurboQuant’s rotation-plus-scalar-quantizer structure but replace the QJL residual with an extra codebook bit and a per-vector rescaling factor 𝜎 . We first normalize the vector before quantization, so to get the correct dot product, 

𝜎 is the ratio of the original norm to the quantized norm. The estimator multiplies the dot product from the decoded vectors by the two scaling factors 𝜎 𝑞 and 𝜎 𝑑 (for the query and database vectors, respectively). The rotation is done with a Fast Walsh–Hadamard Transform composed with a small random orthogonal matrix, so encoding runs in 𝑂 (𝑑 log 𝑑 ) and is data-oblivious. Post-rotation quantization is done by independently mapping each coordinate to its nearest codebook entry. With TQ-4 we use an int8 version of the codebook scaled to [− 127 , 127 ]. For further details, we refer to the original paper. For the remainder of this paper, the important part is that we can quickly decode vectors from 4-bit to int8 with a 16-entry codebook, in-register using the vpshufb shuffle instruction. A goal of this paper is to develop fast kernels in which the distance computation relies on an integer inner product plus a small per-vector correction. Related quantizers such as RaBitQ, DRIVE, EDEN, [6, 62, 63] all fit this template and could be used instead. We use the TurboQuant variant because it has fast encoding time, and after decoding, maps cleanly onto integer dot-product instructions on CPUs (VNNI) and GPUs (WGMMA); any quantization fitting the template plugs into the same kernels.

The AssignLeaders Kernel. PiPNN partitions via Randomized Ball Carving (RBC) : given a subproblem P ⊆ X , RBC samples a subset of P𝑠𝑎𝑚𝑝 · |P | points as leaders . The ProcessLeafTop2 Kernel. Within each leaf 𝑏 𝑖 , we compute all |𝑏 𝑖 |2 pairwise distances and extract the top-2 neighbors per point. Each point participates in multiple leaves (typically 30), so a small per-leaf 𝑘 = 2 is sufficient to deliver a diverse set of candidate neigh-bors [56]. Because each pairwise comparison can symmetrically update the top-2 of both endpoints, bi-directing these edges yields on average 4 candidates per point per leaf. ProcessLeafTop2 is typically the bottleneck in PiPNN.

RobustPrune. RobustPrune selects a sparse out-neighbor set from a candidate list via a greedy occlusion rule [30]: it repeatedly picks the nearest remaining candidate 𝑝 ∗, adds it as a neighbor, then discards any candidate 𝑝 ′ satisfying 𝛼 · 𝑑 (𝑝 ∗, 𝑝 ′) ≤ 𝑑 (𝑝, 𝑝 ′)—meaning 𝑝 ∗ already “occludes” 𝑝 ′ from 𝑝 . The parameter 𝛼 ≥ 1controls pruning aggressiveness; larger 𝛼 retains more edges and yields denser, more navigable graphs. PiPNN applies a Robust-Prune pass over each reservoir to impose the DiskANN 𝛼 -rule. Because each reservoir is already small ( ≤ ℓ𝑚𝑎𝑥 entries), this pass is relatively cheap compared to graph-based builders that invoke RobustPrune on much larger candidate lists [56]. 

Building 𝑘 -NN Graphs with PiPNN. A by-product of the par-titioning phase is that each point already accumulates a pool of nearby candidates within its leaves, which we can use to produce a 

𝑘 -NN graph directly. Many prior graph-based approaches to build-ing 𝑘 -NN graphs take a build-then-search approach: they first con-struct a full navigable index over X and then issue a beam-search query for each base point, doubling the work and making the query pass dominant. In this paper, we study using PiPNN to retain the top-𝑘 neighbors per point directly from its leaves and skip the search pass entirely. We show in Sec. 6 that this strategy matches the recall of build-and-search at a fraction of the cost, and surpasses NN-Descent which is the most popular method for direct 𝑘 -NN construction. 

4 Quantized and Fused Top-𝐾 CPU Kernels 

The primary bottleneck of PiPNN is computing distances between query points and data points during top-𝑘 assignments (either leaders during partitioning, or leafmates during leaf processing). Naively, this could be done by materializing a large distance ma-trix, which is costly due to writing and subsequently re-reading to post-process the distances, e.g., reducing to the top-𝐾 neighbors. To eliminate this bottleneck, PiPNN II fuses the distance compu-tation with the downstream reduction. Registers with computed distances for a subset of the neighbors in the distance matrix are im-mediately consumed instead of being written out to an explicit dis-tance matrix. In this section we describe the matrix-multiplication structure (Sec. 4.1), then the reduction kernels for partitioning (Sec. 4.2), and finally leaf processing (Sec. 4.3). 

4.1 Vectorized Quantized MatMul Structure 

Overview. In this subsection we describe our core matrix mul-tiplication primitive. Before diving into the technical details, we give a high level overview. Our goal is to enable PiPNN II to work directly over the quantized data. The inputs to the kernel are TQ coordinates, which we decode on-the-fly with an i8 codebook. The loop structure of the matrix multiplication iterates over queries in the outer loop, database points in the middle loop and reduces on dimensionality in the inner loop to obtain the dot product between query and database point. For efficiency, we use SIMD vector instructions to compute par-tial dot products. A SIMD vector register consists of multiple lanes ,where each lane corresponds to one data item, e.g., a 512-bit AVX register holds 16 i32 lanes which can be processed in parallel with a single instruction. The performance driver of our code is a dot-product instruction from VNNI (Vector Neural Network Instruc-tions) which requires us to make some adaptations to the data layout. We give a detailed description of our approach next.

Data Layout for Vectorization. The quad instruction computes 16 independent 4-dimensional dot products, one per i32 lane, so scoring 16 database points at once requires each lane to hold a different point. A row-major layout stores each point’s coordinates contiguously, which spreads a single point across the lanes rather than 16 distinct points, forcing a costly horizontal reduction per point and one point per instruction. We instead interleave the database into contiguous blocks called panels : a panel groups 𝐿 = 16 database points and a panel tile stores one 4-dimension (quad) coordinate group from each, so 64 consecutive bytes hold the same 4 dimensions across all 16 points (Fig. 2). A panel tile is then scored against a broadcasted query quad in a single instruction, yielding 16 partial dot products, one per lane. 

Loop Structure. We want to perform the inner reduce on the dimensions so that we materialize a finalized dot product after the loop. Hence, we do not have to spill partial dot products to memory before down-stream consumption in the top-𝐾 aggregation. This motivates our loop structure to process queries in the outer loop, database points in the middle, and dimensions in the inner loop, as shown in Algorithm 2. We omit cache tiling as it slightly hurts performance: the inputs are small enough to remain L2-resident. Note that the pseudocode shows the process for computing neg-ative dot products as the distance. When we use L2 distance, we precompute the squared norms of the datapoints to compute L2 from dot product.

4.2 AssignLeaders Kernels

5 Accelerating PiPNN on GPUs 

Overview. GPUs are highly effective on tasks where many threads can operate on dense data with regular, contiguous memory access patterns. They provide high throughput for tiled matrix products, bulk copies, reductions, and global sorts. On the other hand, they Turbocharging PiPNN for Proximity and 𝑘 -NN Graph Building 

do poorly on workloads of widely varying size, on recursive calls, and on lock-heavy data structures. As on the CPU, the dominant cost for our GPU implementation of PiPNN II ought to be top-𝐾 computation. GPUs can perform bulk top-𝐾 very efficiently, but the rest of the work performed in PiPNN II — recursive partitioning, HashPrune reservoirs with locks, and the final RobustPrune — are difficult to implement performantly. 

GPU background. GPUs are built from many streaming multi-processors (SMs), the general-purpose cores that run threads. Each SM has a register file (64K 32-bit registers on the H100 we use). It also has a small shared-memory scratchpad, shared by a group of cooperating threads, that we use to stage data that is read fre-quently. For matrix multiplication, the SM provides tensor cores ,units that multiply and accumulate a small tile in a single instruc-tion. Two asynchronous copy engines move data into shared memory without occupying the SM’s compute units so that copies overlap with computation: cp.async performs ordinary per-thread copies from global memory, whereas the Tensor Memory Accelerator ( TMA )copies a whole tile characterized by a copy descriptor containing the base address, shape, stride, and swizzle to be performed. Software groups threads at three levels: a warp is 32 threads that execute in lockstep, the GPU analogue of a SIMD register; a warpgroup is four warps (128 threads) that together issue one tensor-core instruction, 

wgmma ; and a thread block is one or more warps scheduled onto a single SM, sharing its registers and shared memory. We call threads operating within a warp lanes .With this in mind, we change a number of PiPNN’s algorithmic and implementation details to map it onto the GPU. (1) We flatten the recursion into a fixed number of assignment-and-sort rounds (Sec. 5.1). (2) We regularize bucket sizes during partitioning and leaf building into fixed-size work units called score tiles (Sec. 5.2). Each scores a group of queries against a block of database points and maps one-to-one onto a thread block. (3) We compute every distance through a single top-𝐾 primi-tive that scores directly over the vectors without ever ma-terializing a score matrix (Sec. 5.3). This is segmented , in the sense that it is one kernel that computes a top-𝐾 over many independent subproblems of varying size at once. (4) We replace the lock-based HashPrune with sort-and-merge accumulation (Sec. 5.4). This requires a transient buffer bounded by the per-batch slab cap rather than by the full candidate set (Sec. E.9). (5) We replace RobustPrune with a relaxation, Direct-EdgePrune, that reuses already-witnessed distances rather than recomputing them (Sec. 5.5). While DirectEdgePrune produces denser graphs than RobustPrune (Tab. 7), we find that this does not affect index quality. 

5.1 Flattening Recursion 

PiPNN partitions points by recursively assigning each point to one or more leader points. Because recursion is a poor fit for GPUs, we replace the explicit recursion with a fixed number of assignment passes. In each pass, we assign points to their nearest leaders within a given subproblem, then sort by the induced keys. This gives us the same partitioning structure without explicit recursion. More formally, we first sample top-level leaders, assign every point to its 𝑓 0 nearest leaders, then sort the memberships by leader so that each top-level bucket is a contiguous run. Second, within each top-level bucket, we sample bucket-local sub-leaders, assign each member to its 𝑓 1 nearest sub-leaders, and sort again to expose the second-level buckets as contiguous runs. We set the GPiPNN fanout to 𝑓 0 = 8 at the top level and 𝑓 1 = 4 at the second, so each point appears in up to 𝑓 0 · 𝑓 1 = 32 leaf memberships, comparable to the roughly 30 in PiPNN II (Sec. 4.2). Each round costs a device-wide sort. Additional assign-then-sort rounds are possible, but two were adequate to achieve high recall. Fig. 9 reports the effect of recursion depth on index quality. 

5.2 Regularizing Bucket Sizes 

Flattening eliminates recursion from GPiPNN but does not address skew in subproblem sizes: some top-level buckets are large, some second-level buckets exceed the maximum leaf size, and some leaves are nearly empty. Because a GPU runs thousands of thread blocks concurrently and a launch completes only when its slowest block finishes, a kernel whose per-block work tracks this long tail would let a few oversized buckets dominate the launch while many near-empty leaves leave their SMs idle, so utilization collapses toward the worst-case bucket rather than the average. We reshape the un-even buckets into nearly-uniformly-sized leaves, which we process within fixed-size score tiles (Sec. 5.3). 

Reshaping buckets. We reshape both the partitioning buckets and the final leaves the same way. We radix-sort points by bucket id, run-length-encode to recover each bucket’s size, then split over-sized buckets and merge undersized ones to a target size ( ≈ 1024), mirroring the leaf-balancing step of PiPNN [56]. Because the sizes are normalized, one fixed-tile kernel handles every leaf, so we never specialize or relaunch per bucket size. We score each leaf as one segment and launch the leaf kernel on batches of these segments, which keeps the tensor cores occupied and amortizes launch over-head.

5.4 From Online HashPrune to Sort-and-Merge 

Recall that HashPrune keeps, for each point, a bounded reservoir of nearby candidates with diverse residual directions. On the CPU we implement it by simply protecting the structure using a lock. Unfortunately on GPU this leads to significantly worse contention Turbocharging PiPNN for Proximity and 𝑘 -NN Graph Building 

and thus degrades performance meaningfully. We therefore replace the synchronized update with a sort. This sort-and-merge runs once per batch of leaves during leaf scoring, and each batch’s candidates merge into a global HashPrune datastructure that the final prune sparsifies into the graph. For every candidate neighbor we emit two fixed-size records, one per direction, each carrying a short sketch of the residual direction from source to target, and we radix-sort the records by owner row and distance. The sort operates on a transient buffer of two records per candidate edge, bounded by a memory parameter (the per-batch slab cap, ≈ 6 GB in our runs) and reused across batches—it does not grow with the full candidate set. After the sort, every owner’s candidates are contiguous, so we update each row’s bounded accumulator in a single sequential pass with no concurrent writes: we de-duplicate repeated targets. For colliding hashes, we keep the nearer candidate. We describe the sketch construction and record layout in more detail in Sec. E.9. 

5.5 Pruning Without Candidate Recompute 

ANN builds need a final sparsification step after candidate accumu-lation. Exact RobustPrune tests whether an accepted neighbor 𝑝 ∗

occludes a candidate 𝑝 ′ for source 𝑝 . This test needs the distance 

𝑑 (𝑝 ∗, 𝑝 ′). Recomputing such distances for every row would add a new irregular candidate-to-candidate scoring stage. We instead use an approximation we call DirectEdgePrune. When we prune the neighbors of point 𝑝 , we check whether the accepted neighbor 𝑝 ∗ already has 𝑝 ′ in its own neighbor-list. If that edge exists then we use the stored distance as the witnessed value for 𝑑 (𝑝 ∗, 𝑝 ′) and apply the usual 𝛼 -prune test; if the edge was not witnessed then we proceed to the next neighbor. All rows consult a read-only snapshot of the completed candidate accumulator. Each row writes its accepted neighbors to separate scratch storage; after all pruning decisions finish, a second pass compacts these outputs into the final graph. This relaxation of RobustPrune has one-sided error: it can miss a domination that exact RobustPrune would have found, because the needed candidate pair may be absent from the accumulator. It never prunes an edge that would have been retained by Robust-Prune. The effect on degree and query quality is measured in Tab. 7: DirectEdgePrune yields denser graphs of quality comparable to those produced by a final RobustPrune. 

6 Experimental Evaluation 

Our experiments are organized around three goals: (1) quantify-ing the speedups we achieve for index building and 𝑘 -NN graph construction (Sec. 6.1 and 6.2), (2) demonstrating that the quantiza-tion and algorithmic changes employed by PiPNN II and GPiPNN preserve high index quality (Sec. 6.2 and 6.3), and (3) explaining which components in the implementations are responsible for the observed speedups (Sec. 6.3 and 6.4). In particular, we find that: (1) On CPU, PiPNN II is the fastest method for both the ANNS-index and 𝑘 -NN tasks: on average for ANNS-index build it beats the strongest quantized Vamana baseline by 5.9 × and unquantized Vamana by 40.7 ×. For 𝑘 -NN building it beats quantized Vamana by 10.3 × and PyNNDescent by 5.9 × at equivalent recall (Sec. 6.1). (2) On GPU, GPiPNN is also the fastest method: on the ANNS-index task it beats Jasper by 8.1 × on average ( 13.3 × with quantization) and unquantized CAGRA by 16 × (27 × with quantization). On the 𝑘 -NN task it beats Jasper, NN-Descent, CAGRA, and IVF-PQ8 by geometric means of 7.1 ×, 2.9 ×,

9.8 ×, and 49.8 × respectively (Sec. 6.2). (3) Using quantization in the build keeps query performance essentially unchanged: PiPNN-TQ and PiPNN-RSQ8 match PiPNN-FP32’s QPS at any given recall within geometric-mean ratios of 0.98 and 0.99 (Sec. 6.3). (4) We trace the speedups to our highly-optimized kernels: we show that our leaf-2-NN kernel achieves a 12.4 × speedup over PiPNN’s prior approach. It runs at near-peak instruc-tion throughput on CPU, and it is bandwidth-bound at high dimension on GPU, reaching 82–95% of memory through-put at 𝑑 ≥ 1536 (Sec. 6.3 and 6.4). 

Machines. We use a Google Cloud c4-highmem-288 (288 vC-PUs, 2.2 TB DRAM, Intel Granite Rapids) for billion-point datasets, and a c3-highmem-192 (192 vCPUs, 1.5 TB DRAM, Intel Sapphire Rapids) for smaller datasets. For GPU measurements we use an 

a3-highgpu-1g instance: one NVIDIA H100 80 GB HBM3 SXM5 (cc 9.0, 132 SMs, 3.35 TB/s HBM3) on a 26-vCPU Sapphire Rapids host with 234 GB DDR5, CUDA 12 with driver 580. GPiPNN is com-piled for Hopper SM90a and run as a single-H100 builder. Datasets that exceed the 80 GB device memory are reported on CPU only. 

“High-quality” indexes. We measure quality in terms of query throughput and recall. Specifically, we consider an index high-quality when its QPS-vs-recall curve is comparable to that of an unquantized ParlayANN-Vamana graph. The first version of PiPNN was shown to produce high-quality indexes, and we show in this paper that it continues to do so for quantized points. 

CPU Methods. Our primary baseline is Vamana [30] as imple-mented in the ParlayANN library [41]. To the best of our knowl-edge, this is the most performant shared-memory graph-based ANNS index publicly available. We restrict our comparison to Va-mana because previous work [56] already showed that it builds indexes faster and of equivalent or better quality than HCNNG [46], HNSW [40], MIRAGE [64], and FastKCNA [66]. We also consider an unpublished version of ParlayANN’s Va-mana [51] that uses 8-bit scalar quantization (SQ8) for distance computations and reranks a smaller set with float precision. For dimensionalities > 512 it further uses a filtering technique based on precomputed Johnson-Lindenstrauss (JL) sketches [33] that further speeds up beam search. Quantization and filtering offers signifi-cantly faster builds and queries than unquantized Vamana while producing indexes of identical quality. Hence, we use this version when computing QPS-vs-recall curves on CPUs. For 𝑘 -NN graph construction, we additionally compare with a parallel implemen-tation of NN-descent PyNNDescent [43] also in the ParlayANN library [41] that uses SQ8. The per-dataset build parameter config-urations for CPU methods are detailed in Sec. G (Tab. 16 and 17).

Leaf 2-NN kernel. We evaluate the leaf 2-NN kernel described in Sec. 4.3 on a single core of an Icelake CPU by scoring a leaf of 800 points gathered from a dataset of 1M 768-dimensional points. Fig. 6 divides runtime into three components: prepare , the dot-product 

GEMM , and top-2 filtering . Prepare covers work done before the inner loop runs: decoding and packing the database vectors into the transposed panel layout, and zero-initializing the top-2 trackers. The original PiPNN [56], which scores the leaf with Eigen’s float32 GEMM and extracts top-2 with Highway’s VQSort, runs in 12 .90 ms. As we apply each optimization, the dominant cost increasingly shifts to the top-2 filtering step, until SIMD Scatter addresses that bottle-neck. TQ Flat replaces the float32 GEMM with an int8 dot prod-uct using vpdpbusd over the baseline’s data layout (rows=points, columns=dimensions). Pruning kernel. Recall that PiPNN II uses the RobustPrune pro-cedure from DiskANN [30]. With the leaf and partitioning kernels accelerated, RobustPrune becomes a non-negligible part of the run-time. We compare three implementations which differ in how they compute distances between RobustPrune candidates. The baseline “Naive TQ (vectorized)” computes the distances between a candidate and all prior survivors using one-to-many TurboQuant. “Distmat (panel-based)” precomputes the full 𝐶 × 𝐶 candidate–candidate distance matrix in a single GEMM pass using the techniques from Sec. 4.1, then prunes using those distances. Note that this approach is not able to exit early when a candidate gets pruned. “Fused (panel-based)” is a variant where we store only survivors and the next query batch (size 6) in the panel layout. We then compute distances from the next query batch against the survivors and itself. After pruning, we copy over the survivors from this batch. Compared to Distmat, this eliminates redundant work by only comparing with pruned candidates in the same query batch. Compared to the naive version, however, a query still does not exit early if pruned. As can be seen in Fig. 7, both panel-based strategies provide significant speedup over the Naive method (DistMat gets a 2 .1×

improvement on average over Naive). Additionally, leveraging the Fused version gives a 1 .08 × improvement over Distmat. 

6.4 GPU Ablations 

Fig. 8 in Appendix E.7 shows per-stage and per-kernel runtime breakdowns on GPU. Leaf processing dominates the runtime on GPU as well, though less than on CPU. We perform a Speed of Light (SOL) analysis to identify the % of system utilization with respect to the theoretical hardware peak. 

Leaf 2-NN kernel. The performance bottleneck of the kernel on the H100 GPU shifts depending on the vector dimension. At higher dimensions ( 𝑑 ≥ 1536, e.g., openai-2M and dbpedia-3072), data streaming for candidate comparisons saturates the L2 cache band-width. Unified memory throughput reaches 82–95%, indicating that L2 is the limiting tier rather than DRAM, which remains at 37–52%. Meanwhile, the SM pipelines hold steady at 46–49%, falling below Nsight Compute’s (NCU) 60% threshold for a compute-bound state. For intermediate dimensions ( 𝑑 = 768, e.g., wiki-all-10M), neither the compute nor memory pipelines saturate: the SM sits at 50% and the memory hierarchy at 41%. Here, NCU attributes the perfor-mance gap to latency rather than throughput. The kernel achieves only 26–28% occupancy, tightly constrained by its 28% theoretical limit due to high shared-memory pressure and an allocation of 96 registers per thread. This occupancy limitation persists at the lowest dimensions ( 𝑑 = 96, e.g., deep-10M; Tab. 9). The working set resides entirely within cache which drops DRAM traffic to 4% and leaves the kernel strictly occupancy-bound. 

Index Quality. Fig. 5 shows QPS vs recall on a low- and a high-dimensional dataset. Across the recall range GPiPNN’s curves sit on or above those of Jasper and CAGRA, and the same holds on the full benchmark set (Fig. 12). Using DirectEdgePrune produces 30–58% denser graphs, since the method does not prune some edges that RobustPrune would. Still, index quality is comparable between the two pruning methods (Tab. 7). DirectEdgePrune cuts GPU build time by up to 1 .4×

on the high-dimensional datasets. While DirectEdgePrune could increase memory footprint, the maximum degree between the two pruning methods is identical, so in the Jasper query implementation there is no difference in terms of allocated memory. 

7 Discussion & Conclusion 

PiPNN introduced a fast, hardware-friendly route to high-quality proximity-graph construction, but its original implementation left substantial performance on the table. In this paper we fully realize PiPNN’s potential by accelerating the GEMM and top-𝐾 steps, via quantization, fusing GEMM with per-query top-𝐾 selection into a single in-register pass, as well as vectorizing and tailoring the Turbocharging PiPNN for Proximity and 𝑘 -NN Graph Building 

top-𝐾 selection to the specific 𝐾 . Instantiating this design on shared-memory CPUs as PiPNN II and on GPUs as GPiPNN yields large speedups over the strongest prior state-of-the-art methods on both platforms while preserving equivalent query performance. In future work we plan to scale beyond a single machine and port the design to other accelerators. PiPNN’s structure is well-suited to the distributed setting: partitioning creates independent sub-problems, leaves can be processed independently, and HashPrune merges candidate sets without coordinating on global state.

A Beam Search Pseudocode 

For completeness, we provide pseudocode for the standard beam-search graph-query procedure described in Section 2. Given a navi-gation graph over points X, a beam search is a greedy search with intermediate storage (called the beam). Given a source node 𝑠 in the graph and a query point 𝑞 , a beam search with beam width 𝐿 

works as follows. We maintain two sets: a set 𝐵 containing up to 𝐿 

encountered points that are closest to 𝑞 (often called the “beam”), and the set 𝑉 of all points visited. Visiting a point 𝑝 ∈ 𝐵 \ 𝑉 adds all its unseen neighbors to the beam, then adds 𝑝 to the visited set. The algorithm begins by initializing the beam with only the source 

𝑠 and an empty visited set. We then visit the unvisited node in the beam closest to 𝑞 , repeating until every node in the beam has been visited. Because the distance of the points in the beam to the target decreases monotonically, this process converges, at which point we return the final state of the beam.

B HashPrune Pseudocode 

Here we document and give pseudocode for the HashPrune on-line pruning procedure used by PiPNN (Sec. 3). The algorithm is reproduced verbatim from [56]. 

Motivation. Pruning ensures that each vertex connects to neigh-bors in many different directions, so that greedy search can route quickly from any point to any other. HashPrune achieves this with locality-sensitive hashing (LSH) [9]: it discards candidate edges that are directionally similar to edges already kept. Working with relatively low dimensional hashes ( ≈ 12) also lets the procedure operate on low-dimensional sketches rather than full vectors, so pruning avoids fetching high-dimensional data. 

Residualized hashing. HashPrune draws a fixed set of random hyperplanes through the origin. For each point 𝑝 it derives an individualized hash ℎ𝑝 that hashes the residual 𝑐 − 𝑝 of a candidate 

𝑐 : the 𝑖 -th bit records which side of the 𝑖 -th hyperplane the residual falls on. Two candidates collide under ℎ𝑝 with probability (1 −

𝜃 /𝜋 )𝑚 , where 𝜃 is the angle between 𝑐 − 𝑝 and 𝑐 ′ − 𝑝 and 𝑚 is the number of hyperplanes [9]. Hashing the residual thus draws probabilistic cones centered on 𝑝 , and the number of hyperplanes controls how finely those cones partition direction space. 

Insertion. To prune the candidate stream V for a point 𝑝 , Hash-Prune maintains a reservoir 𝑀 of size at most ℓ𝑚𝑎𝑥 keyed by hash value. For each candidate 𝑐 it computes ℎ𝑝 (𝑐 ). If the bucket is al-ready occupied, it keeps whichever of the two candidates lies closer to 𝑝 . Otherwise it inserts 𝑐 , and when the reservoir is full it evicts the candidate farthest from 𝑝 . The reservoir therefore retains the nearest point in each cone while never exceeding ℓ𝑚𝑎𝑥 entries, which bounds memory up front and lets it be allocated in a single contiguous block rather than grown dynamically. 

History independence. The final reservoir depends only on the candidate set, not on the order candidates arrive in: dropping the size limit leaves exactly the nearest point in each bucket, and the size limit only ever evicts the farthest retained candidate. History independence lets candidates be merged in arbitrary order, partition by partition, without fragmenting the graph, and makes PiPNN’s partitioning-based construction deterministic.

E GPiPNN Kernel Details 

This appendix collects implementation detail deferred from Sec. 5. 

E.1 Flattened routing keys 

Sec. 5.1 flattens PiPNN’s recursion into two scoring assignment passes joined by radix sorts. The current implementation has no third assignment or refinement pass: after the second-level assign-ments, oversized second-level buckets are split by the bin-packing walk described below. 

Pass 1: top-level leaders. Every point scores against the sampled top-level leader set and keeps its 𝑓 0 best leaders (default 𝑓 0 = 8). The kernel emits 𝑓 0𝑛 pairs (𝐿, 𝑝 ) with key 𝐿 , and a radix sort makes each top-level bucket a contiguous run. The point array is also permuted by each point’s best top-level leader; all later graph work uses this permuted row space until the final export remap. 

Pass 2: sub-leaders. Inside each top-level bucket, the host sam-ples a bucket-local sub-leader candidate set. Each bucket member scores against only that bucket’s sub-leaders and keeps its 𝑓 1 best (default 𝑓 1 = 4). The pass emits (𝑠, 𝑝 ) pairs keyed by the group-local sub-leader label 𝑠 ; sorting and run-length encoding these keys ex-poses the second-level buckets. With the default fanout, a point can therefore appear in up to 𝑓 0 𝑓 1 = 32 leaf memberships. 

Bin packing. The second-level buckets are then packed into leaf-sized work units. This step does not introduce new leaders or new geometric assignments. It only splits oversized buckets and merges small adjacent buckets within the same parent range so the leaf scorer sees regular batch sizes. The implementation uses a count/assign/broadcast walk over the sorted bucket runs: first count the bins each parent range will produce, then assign compact leaf ids to runs, then broadcast those ids back to the membership array. The broadcast keys are monotone, so no second post-pack sort is needed. Sub-leader sampling is keyed by the global top-level bucket id, so changing the number of streamed leader groups changes memory use but not the sampled partition. 

E.2 Partitioning-pass operand staging 

As is discussed in Sec. 5.1, the assignment passes are expressed as segmented top-𝐾 scoring. Here we provide more details on how the slabs of segments work. 

Top-level leader slab. The top-level pass samples 𝐿 0 leaders (auto-tuned up to 4096) and gathers those rows once into a dense leader slab. The single segment then scores all points against that slab and emits 𝑓 0 synthetic leader labels per point. The synthetic labels avoid self-skip behavior in the shared scoring primitive, since a sampled leader must be allowed to assign to itself. 

Sub-leader slabs. For each streamed range of top-level buckets, the host samples sub-leaders inside each bucket and resolves them to permuted row ids. All sub-leaders for the group are gathered into one dense slab, and the launch contains one score segment per nonempty top-level bucket. Each segment points to its bucket’s contiguous sub-leader slice with an offset and count. This lets one scoring launch handle buckets with different candidate counts while keeping the operand layout dense. 

E.3 Decoded rows across precisions 

The host-side TurboQuant encoder stores TQ4 and RSQ8 in their packed code formats, but the GPU pipeline expands them before the assignment and leaf scoring stages. TQ4 is decoded through its 16-entry codebook into signed INT8 rows, RSQ8 is copied into the same signed-byte decoded layout, and padding beyond the true dimension is zeroed in the decoded domain. The segmented top-𝐾 

primitive therefore sees the same decoded INT8 row contract for both TQ modes. The unquantized supplement uses the same decoded-base inter-face. The loader reads float32 rows, normalizes each row to unit length, records the original norm, and the device decode converts the normalized base to fp16 or tf32 rows. The scoring primitive then switches operand traits while the surrounding gather, accu-mulation, canonicalization, pruning, and export stages remain the Tobias Rubel, Richard Wen, Guy Blelloch, Laxman Dhulipala, Lars Gottesbüren, Jakub Łącki, and Vahab Mirrokni 

same. The TQ paths are validated by bitwise-equality tests against a reference decode; the unquantized fp16 and tf32 supplement paths, which are not bit-exact, are validated by recall-threshold tests. 

E.4 Scoring pipeline modes 

The segmented top-𝐾 primitive of Sec. 5.3 runs in two pipeline modes behind one interface. In the unified mode a single warpgroup performs both the copies and the matrix products, synchronizing on shared memory once per stripe; we use it for small segments, where it is the simplest and fastest path. In the warp-specialized mode a dedicated producer warp issues the TMA and gather copies while the consumer warpgroups compute, so loads and matrix products run on separate warps. The two modes produce identical results. In either mode two consumer warpgroups can share a thread block to score a 128-row query tile ( 𝑀 = 128) against one shared-memory ring of database-point rows, so each row is loaded once and reused across both 64-row halves. We use this variant for the small-𝐾 builds (𝐾 ≤ 4). We stage the query operands into shared memory once and reuse them when a 64-row query tile fits—up to 768 bytes of decoded operand per row—and stream them alongside the database points above that width. The same kernel serves the quantized i8 

builds and the unquantized fp16/tf32 modes, which differ only in the operand type and accumulator (Sec. E.3).

E.10 Direct KNN-graph mode and build-time scaling 

We also use the same pipeline to build direct KNN graphs. In KNN mode we set the leaf top-𝐾 and accumulator capacity to the re-quested 𝑘 , disable same-sketch HashPrune filtering, and dedupli-cate only repeated target ids, keeping the nearer copy. We then skip the final prune and export the canonicalized accumulator as a directed graph; this avoids the build-then-search pattern that graph-index baselines use for KNN construction (Tab. 3 and 5). For harder KNN cells we run several rounds. Round 0 creates the permuted row space; later rounds resample the top-level partition with new seeds but keep the row order fixed, so their witnesses merge into the same accumulator and export through the same id map, changing the candidate set without creating incompatible row spaces. We plan the remaining scaling choices before alloca-tion: a memory planner chooses how many top-level bucket ranges to stream and bounds the leaf and accumulation buffers, keeping output-neutral choices (such as the number of streamed ranges) separate from quality-coupled ones (such as candidate capacity).
