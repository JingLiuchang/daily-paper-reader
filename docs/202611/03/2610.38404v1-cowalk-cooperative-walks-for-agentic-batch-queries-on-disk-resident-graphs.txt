## Abstract 

Workloads such as query rewriting, deep research and group-relative policy optimization (GRPO) issue batches of seman-tically related vector queries. Existing disk-resident approxi-mate nearest neighbor (ANN) systems process these queries independently. On three workloads, 31 to 67 percent of the I/Os of a batch fetch a page that another query of the batch has already fetched. A page cache shared by the batch re-moves these I/Os, yet it makes a single-thread search only 1.1 to 1 .2× faster, because the search time goes to distance computation and the cache does not change the walk of any query. We present CoWalk, which runs the queries of a batch as cooperating walks on one thread. Every query keeps its own candidate list, a page is read once per batch, and the full-precision vector on every fetched page is ranked by ev-ery query of the batch. A query therefore reaches the target recall with a shorter candidate list, which computes fewer distances and issues fewer I/Os. At recall@10 of 0.95, CoW-alk answers a batch on one thread 1.6 to 1 .9× faster than the fastest per-query baseline and issues 2.8 to 6 .9× fewer I/Os. On a server it serves 3.0 to 6 .9× the throughput of that baseline at a similar batch latency. 

## 1 Introduction 

Modern LLM agents now issue batches of semantically re-lated vector queries. Query rewriting sends 𝑁 paraphrases of a question in parallel [17, 32] (Figure 1). Deep-research agents decompose a task into concurrent retrieval sub-tasks. Anthropic’s Research system spins up 3–5 subagents in par-allel and the subagents use 3+ tools in parallel [2], and Paral-lelSearch [37] trains the agent with RL to decompose a ques-tion and issue the sub-queries concurrently. Post-training algorithms such as GRPO [28], applied to search agents [12], sample multiple rollouts from the same prompt and produce semantically related searches. HQI [20] reports that Apple’s vector search workloads often need to be processed in a batch setting. In all of these patterns the batch members come from one intent and share semantic substance. We measure this on three workloads, deep research (OpenResearcher [16]), conversational Q&A (QuAC+CANARD [5, 7]), and narrative reading comprehension (NarrativeQA [15]). Contributions. This paper makes four contributions. 

• We characterize agent batch retrieval on three work-loads. We quantify the intra-batch similarity and the repeated I/Os it causes on both graph and cluster disk indexes, and we show why a graph index is the better base for batches (Sec. 2). 

• We show that a batch-scoped page cache removes the repeated I/Os but leaves most of the latency, and we identify what it leaves unused (Sec. 2.5). 

• We design CoWalk, which runs a batch as cooperat-ing walks on one thread that share pages and exact distances while every query keeps its own candidate list (Sec. 3). 

• We evaluate CoWalk on three workloads, reaching 1 .6to 1 .9× lower latency than PipeANN at recall 0 .95, and we measure how much each form of cooperation and each rejected design alternative contributes (Sec. 5). The source code of CoWalk is available at https://github. com/OhhhhPi/SWARM .

## 2 Background and Motivation 

2.1 Disk-Resident ANN Indexes 

Graph indexes. Disk-resident graph ANN indexes store the dataset as a Vamana graph [30]. Each vector becomes a node with 𝑅 out-edges to other vectors, and the graph is laid out on SSD so that one I/O returns one node’s full-precision vector together with the identifiers of its 𝑅 neigh-bors. A compressed product-quantization (PQ) code of every vector is held in DRAM and supports fast approximate dis-tance computation against any candidate node. A search query maintains a length-𝐿 candidate list sorted by PQ dis-tance and runs a beam search. At each hop the query pops up to beam_width unvisited nodes, fetches them from disk, PQ-scores the fetched nodes’ neighbors against its own lookup table, and inserts the results back into the candi-date list. The walk terminates when no unvisited nodes re-main, and the query ranks the nodes it fetched by exact dis-tance. DiskANN [30] introduced this layout. PipeANN [11] pipelines the I/O and compute stages of the walk so that SSD latency is overlapped with PQ scoring. We use PipeANN as our per-query baseline throughout. 

Cluster indexes. Cluster-based indexes such as SPANN [4] and SPFresh [36] partition the dataset into clusters. The cen-troids stay in memory, and the full-precision vectors of each cluster are stored together on SSD. A query ranks the cen-troids, reads the nearest clusters, and computes the exact distance to every vector it read. The clusters to read are known before the first I/O is issued. No compressed code filters the vectors of a cluster, so probing a cluster reads all of them.

2.2 Agent Batch Workloads 

Six concrete agentic patterns drive the shift to batched re-lated retrieval. Query rewriting generates 𝑁 paraphrases for a single question, hedging against embedding-space brittle-ness [17, 32]. Post-training algorithms like GRPO [28], when applied to memory or deep-research agents [12], sample mul-tiple rollouts from the same prompt and naturally produce semantically related searches. HyDE [10] prompts an LLM to draft 𝑁 hypothetical answers and uses each answer’s embed-ding as a separate query. Sub-question decomposition splits a complex question into atomic sub-questions, each issued as its own retrieval call [25, 38]. Plan-and-execute deep-research agents , exemplified by Perplexity Deep Research, OpenAI Deep Research, and Anthropic Skill agents [1, 23, 24], dis-patch 5 to 20 retrieval sub-tasks in parallel per planning step. Claim-grounded fact-checking treats each generated sentence as a separate query for evidence grounding [19, 35]. The shared property across all six patterns is that the batch members originate from one intent and vary in surface form rather than in semantic substance. In our three evaluation workloads the mean batch size is 33 .5 (OpenResearcher), 7 .2(QuAC+CANARD), and 29 .7 (NarrativeQA). 

Batch members are close. If a batch genuinely comes from a single user intent, its queries should be measurably closer in embedding space than random pairs drawn from the same workload. We test this on the three datasets below. 

OpenResearcher [16] is a deep-research-agent bench-mark. It provides 97 ,630 multi-turn research trajectories, each one an offline deep-research session run by a GPT-OSS-120B agent and averaging 33 .5 retrievals issued as browser.search 

tool calls. Its corpus consists of 14 .9M FineWeb web-crawl passages. 

QuAC+CANARD is a conversational QA workload over Wikipedia. Each dialog is a sequence of follow-up ques-tions that drill into a single Wikipedia article. CANARD [7] rewrites each turn to stand on its own, so every one of the 5,644 dialogs becomes a batch of self-contained queries that retrieve independently yet still probe the same article (40 ,527 queries in total). 

NarrativeQA [15] is a reading-comprehension workload over 1 ,572 books and movie scripts with 46 ,765 human-written questions. For OpenResearcher we use its official corpus embed-dings produced by Qwen3-Embedding-8B (4096d) and en-code queries with the same model. For QuAC+CANARD we use the 21M-passage DPR Wikipedia corpus [13] as the un-derlying collection. For NarrativeQA we chunk the original corpus at 100-word granularity. On QuAC+CANARD and NarrativeQA we encode queries and passages with e5-base-v2 (768d). In all three, every query is self-contained and independent of the other queries of its batch. 2.3 Per-Query Search Repeats I/Os 

Queries that are close search the same part of an index. On a graph index their walks start from the same entry point and expand many of the same nodes. On a cluster index they rank many of the same centroids first. A system that processes each query on its own issues these I/Os once per query. We count the repeated I/Os on both index families on the first 1 ,000 batches of each workload. For the graph index we run PipeANN per query at recall@10 of 0 .95 and give each batch a page cache that never evicts. The cache misses of a batch are then its distinct pages and the hits are its repeated I/Os. For the cluster index we measure offline and build nothing on disk. We partition each corpus with 𝑘 -means into clusters of 64 vectors on average, replicate boundary vectors into nearby clusters as SPANN does, and rank the centroids for every query. A cluster index ranks the vectors it reads by exact distance, so the recall of a query is the fraction of its true top-10 that lies in the clusters it probes. We let every query stop as early as the ground truth allows. A query probes clusters in centroid order until 9 of its true top-10 are found, but never more than 344, 715, and 369 clusters on the three workloads, the single depth at which the mean recall over all queries reaches 0 .95. 2.4 Graph or Cluster Index 

Even after a batch removes every repeated I/O, a cluster index has worse lower bounds on batch latency and throughput than per-query PipeANN. If it keeps only its centroids in memory, as SPANN does, it reads every full-precision vector of a probed cluster from SSD. Even if each query stops as soon as the ground truth allows, after 72 to 146 clusters on average, a deduplicated batch reads 5 .0 to 7 .2× the data of PipeANN without deduplication (Figure 3), and reading it at the 11 .0 GB/s of one thread takes 1 .9 to 7 .0× the batch latency of PipeANN. If it keeps PQ codes in memory instead and reranks only the best candidates from SSD, its recall still requires the probed clusters to contain the true neighbors, so on OpenRe-searcher every query probes about 1 ,500 clusters and scans about 150K codes to reach a mean recall of 0 .95. Before any I/O, a batch then takes at least 6 .3× the single-thread latency of PipeANN with 8-bit codes and 1 .2 to 1 .7× with 4-bit codes. Queries that probe the same cluster read the same codes but compute their own distances, so ranking the candidates reranked by the whole batch still leaves 1 .1 to 1 .4×.A graph index avoids both costs because its edges lead toward the query, so it scores only the neighbors of the nodes it expands and reads only the nodes among its 𝐿 best. On OpenResearcher PipeANN reaches recall 0 .95 with about 190 I/Os and 12 ,500 PQ distances per query. We therefore build CoWalk on a graph index. 

2.5 A Page Cache Is Not Enough 

On a graph index the direct way to remove the repeated I/Os is a page cache shared by the queries of a batch. We build this baseline on PipeANN and call it GLRU (Sec. 5.1). On one thread it reads every distinct page of a batch exactly once. Yet on one thread GLRU answers a batch only 1 .1 to 1 .2×

faster than PipeANN (Sec. 5.3). On one thread the search time is computation. For every fetched node a query computes the exact distance of the node and the PQ distances of its neighbors, and the I/Os of later nodes complete in the meantime. PipeANN overlaps I/O and computation by keeping several I/Os in flight per query. With 32 I/Os in flight it only waits for I/Os 16%, 13%, and 21% of its time on the three workloads. A cache that removed all of this waiting would make a batch at most 1 .19, 1.15, and 1 .26 × faster. A cache therefore removes only I/Os whose latency is already hidden, and it leaves the computation unchanged. The computation is set by the path of the walk, because the path decides which nodes a query fetches and how many distances it computes. The cache is passive and serves only the I/Os the walk has already decided to issue, so it does not change the path. As a result GLRU reaches the same recall as PipeANN at the same 𝐿 and computes as many distances. We measure this gain in Sec. 5.3. The cache leaves the full-precision vectors on its pages unused. We let every query of a batch walk on its own with a short candidate list, 𝐿 of 70, 304, and 248, while the batch reads each page once. The walk of a query then misses 9 .3%, 8.5%, and 7 .7% of its true top-10, and 48%, 29%, and 38% of the missed neighbors lie on pages that a batch-mate read. These pages are already in memory, but a cache returns each page only to the walks that select it, so the query never ranks these neighbors. 

## 3 CoWalk Design 

3.1 Overview 

CoWalk answers a batch of 𝐵 queries on one thread with the same disk-resident Vamana index, PQ codes, and parameters as PipeANN. It runs one walk per query. Each walk keeps its own candidate list of length 𝐿 sorted by PQ distance, selects its own next nodes from that list, keeps up to four I/Os pending, and stops when its list holds no unexpanded node and none of its I/Os is pending. A query’s walk therefore selects nodes by the same rule as a per-query search, from a list which is only filled by its own expansions. A batch of one query has no batch-mate, and its walk would keep only 4 I/Os in flight, so CoWalk runs it with PipeANN. The walks share three things (Figure 4). They share I/Os, so a page that several walks select is read once (Sec. 3.2). They share exact distances, so every query ranks every node that any walk of the batch read (Sec. 3.3). They share one thread, which keeps the I/Os of all walks in flight and processes whichever page completes first (Sec. 3.4). The walks do not share the neighbors they discover, and Sec. 3.5 explains why. Figure 4 follows the thread through one round. Each query selects the best node from its candidate list ①. If the batch has already read the selected node, CoWalk expands it at once from the neighbor list it keeps in its cache, as 𝑞 1 does for node 𝑏 , which was read for 𝑞 2. Otherwise the thread issues an I/O for the node’s page ②. When an I/O completes ③,CoWalk PQ-scores the neighbors of its node for the queries that selected it and inserts them into their candidate lists ④.The first time a node is read, CoWalk also adds a row for it to the batch’s exact-distance table, with its exact distance to every query ⑤. 3.2 Sharing I/Os 

When a walk selects a node, CoWalk looks up the page that holds it. If another walk has already issued an I/O for that page, the query joins that I/O and issues nothing. If the page has already been read in this batch, CoWalk expands the node for the query at once. Only otherwise does it issue a new I/O. When an I/O completes, CoWalk copies the neighbor list of its node into a record that stays in memory until the batch ends (Sec. 4). A page is therefore read at most once per batch. Expanding a node works as in a per-query search, but only for the queries that selected it. For each such query, CoWalk computes the PQ distance to every neighbor of the node and inserts the neighbor into that query’s candidate list if it ranks among the top 𝐿 . Other queries do not see these neighbors. Each query skips the neighbors it has already PQ-scored, because a second score gives the same distance and cannot change its list.

A page holds the full-precision vector of a node. The first time any walk reads the node, CoWalk computes the exact distance from that vector to every query of the batch and stores the distances as one row of the batch’s exact-distance table, which has one column per query. This includes the queries whose walks have already stopped, because a node that a batch-mate reads later can still be one of their nearest neighbors. 3.4 One Thread for All Walks 

All walks issue their I/Os to one io_uring instance on the thread. The thread waits until at least one I/O completes and expands the node of every completed page for the queries that selected it. It then lets every walking query with fewer than four pending I/Os select more nodes, and it submits all I/Os queued in this round with one system call. Only then does it compute the exact distances of the nodes read for the first time in this round, so the new I/Os are in flight while it does. The exact distances never enter a candidate list, so computing them after the submission leaves every selection unchanged. Figure 5 shows this loop for three queries with two I/Os each. On the CPU lane a grey block is the PQ work for one query that selected a page, and a red block is the exact distances from the page’s node to the whole batch. A page is expanded as soon as it completes, whichever walk it belongs to, so the I/Os of one query complete while the thread works on the pages of the others. A completed I/O waits (hatched) only while the thread is busy, and the thread blocks only when none of the I/Os of the 𝐵 walks has completed. When 

𝑞 2 selects a node whose page 𝑞 1 is already reading, 𝑞 2 joins that I/O, and the page gets a grey block for each of them and one red block. With 𝐵 walks the thread has up to 4 𝐵 

I/Os in flight (2 𝐵 in Figure 5 for clarity), so four per query keep it computing where a single PipeANN query needs up to 32 (Sec. 2.5). More I/Os per query would not help, because a query selects all of its pending I/Os from the same candidate list, before their neighbors arrive, so each extra I/O is more likely to fetch a node the query would no longer select (Sec. 5.3). The alternative is a walk in synchronous hops. Every query issues its I/Os for the hop, and the thread waits for all of them before it processes any page. One slow I/O then holds up every walk of the batch, and the thread idles while the last I/Os of a round are in flight. Sec. 5.3 runs this schedule with the same sharing. 

3.5 What CoWalk Does Not Share 

A read page holds both the vector of a node and its neighbor list. Both arrive with the same I/O, so a natural design would also share the neighbor list and PQ-score its neighbors for every query of the batch. CoWalk shares only the vector. The query that selected a node ranked it among its 𝐿 best by distance to its own vector, so the neighbors of the node are the most promising candidates that query has. A batch-mate receives these neighbors through a node ranked by distance to another query vector, and even its nearest batch-mate lies at some distance from it, so they are less promising for it than the neighbors of the nodes it selected itself. In an earlier hop-synchronous version of the walk that scored every neighbor for the whole batch, 16%, 14%, and 10% of the neighbors of a query’s own nodes entered its candidate list, but only 5 .6%, 7 .3%, and 6 .0% of the neighbors of the nodes its nearest batch-mate selected, and 3 .5%, 5 .6%, and 4 .1% excluding neighbors that its own nodes also list. Scoring them for the whole batch would add 𝐵 PQ distances per neighbor, and PQ is already the largest stage of the walk. The value of an exact distance does not depend on which query selected the node. It costs one distance per query and read node, and it ranks the node exactly for every query of the batch (Sec. 3.3). Sec. 5.3 measures a variant that scores the neighbors for the whole batch. 

## 4 Implementation 

We implement CoWalk in the code base of PipeANN and reuse its index format, PQ distance code, and io_uring 

reader. 

Cross-query SIMD kernel. The exact distances of a node go to every query of the batch. CoWalk computes them with an AVX-512 kernel that loads each block of the node vector once and multiplies it into four accumulators, one per query. The vector is thus read once per four queries, and the four independent fused multiply-adds overlap in the pipeline.

A thread enters a page in the table when it issues the I/O, so another thread that picks the page waits for that I/O and does not read it again. During the walk a thread computes exact distances only for its own walking queries. After all walks end it fills in the rest, including the nodes the other threads read, so the records also keep the node’s vector.

5.4 More SSDs 

Our node has more cores than one SSD can feed, so on many threads both systems stop at the device (Figure 13). We project what more SSDs would buy on OpenResearcher from two measured quantities per system, the peak QPS of one SSD and the QPS of one thread. Throughput is the smaller of a device bound, which grows with the SSD count, and a CPU bound of 128 threads times the per-thread QPS. Each SSD carries 18 .8K QPS of CoWalk and 2 .6K of PipeANN. One CoWalk thread serves 510 QPS on the batches of the thread ladder (518 on the first 1 ,000 batches in Sec. 5.3), and one PipeANN thread with 32 I/Os in flight serves 277. CoWalk runs out of cores between three and four SSDs, at about 65K QPS. PipeANN needs about thirteen SSDs to keep the same threads busy and stops near 35K QPS. The ratio narrows from the peak ratio of 7 .1× on one SSD to the per-thread ratio of 1 .8× once both are bound by CPU. The projection assumes that throughput grows linearly with threads, which CoWalk does within 7% up to 16 threads, and that a PipeANN thread keeps its single-thread QPS. 

## 6 Related Work 

Agentic retrieval workloads. LLM agents turn one in-tent into many retrieval calls. Query rewriting and HyDE issue 𝑁 paraphrases or hypothetical answers [10, 17, 32], decomposition issues one call per sub-question [25, 37, 38], deep-research agents fan out across subagents [2, 23], fact-checkers ground each generated sentence [19, 35], and RL post-training samples many rollouts per prompt [12, 28]. These works treat retrieval as a black box and pay for each call in full.

PipeANN [11] overlaps I/O with PQ, Starling [33] co-locates a walk’s nodes on disk, and FreshDiskANN [29] and SPFresh [36] add streaming up-dates. These target single-query latency, so a batch reruns the search 𝐵 times, refetching the same pages, and each query ranks only the nodes its own walk fetched. GPU indexes such as CAGRA [22] batch many independent queries for throughput but still run each query’s walk separately rather than sharing it across a related batch. CoWalk keeps the in-dex format of DiskANN and the pipelined I/Os of PipeANN, reads each page once per batch, and lets every query rank every node the batch fetched. 

Multi-vector retrieval. A parallel line of work indexes each item as a set of token embeddings under the Chamfer (MaxSim) score [14]. Most systems pool every token into one single-vector index and query it per token, as in Col-BERTv2 [27], PLAID [26], and EMVB [21]. MUVERA [6] instead encodes each set as one fixed-dimensional vector, DESSERT [8] as an LSH sketch, and IGP [3] and GEM [31] build proximity graphs over token sets. This line is orthog-onal to CoWalk. Multi-vector retrieval returns one ranked list per set-valued query, whereas CoWalk serves a batch of single-vector point queries that share an intent but keep independent top-𝐾 results. 

## 7 Discussion and Limitations 

Idle cores. A per-query system with idle cores can spread the 𝐵 queries of a batch over 𝑇 threads. Figure 14 compares this batch-parallel PipeANN with CoWalk on one thread. At recall 0 .95 batch-parallel PipeANN on 2 threads takes 65, 27, and 71 ms, against 62, 25, and 71 ms for single-thread CoWalk. With 4 threads it is faster on all three workloads, and with 32 threads it finishes a batch in 16, 9, and 11 ms. It pays for this with 𝑇 cores and unchanged I/Os per query, so it gives up the throughput of Sec. 5.2. CoWalk can also spread a batch over 𝑘 threads (Sec. 5.2). On 8 threads with one batch at a time it finishes a batch in 10 .8, 10 .2, and 15 .3 ms, against 24 .3, 10 .5, and 23 .2 ms for batch-parallel PipeANN on 8 threads. Unrelated queries. CoWalk gains only when the queries of a batch search the same region of the graph. The agentic batches of Sec. 2.2 have this property. Batches of unrelated queries do not. Figure 15 replaces each workload’s batches with 𝐵 queries drawn at random from all its queries. CoWalk then reads at most 14% fewer pages per query than PipeANN, against 65 to 88% fewer on the original batches, and its recall at equal 𝐿 is up to 0 .015 lower than that of PipeANN. On one thread CoWalk is then slower than PipeANN. At recall 0 .95 it spends 1 .2 to 1 .4× more time per query for 𝐵 of 4 and 16 and 1 .5 to 2 .5× more for 𝐵 =64, while it spends 1 .6 to 2 .2×

less on the original batches. On 128 threads, where the SSD limits both systems, its throughput on random batches of 16 is 1 .10 ×, 1 .26 ×, and 1 .28 × that of PipeANN. Unrelated batches thus make CoWalk slower than PipeANN on one thread and remove most of its gain on many threads. 

Read-path-only implementation. CoWalk shares the read path only. Concurrent inserts and deletes during a walk fall back to the per-query update path of PipeANN, and a joint update path is left to future work. This fits our target setting, where agent retrieval is read-dominated and index refresh runs in the background. 

## 8 Conclusion 

LLM agents issue batches of related queries drawn from a single intent. On three workloads, queries of the same batch lie 1 .3 to 2 .4× closer than random pairs, and 31 to 67% of the I/Os of per-query search fetch a page that a batch-mate already fetched. A page cache shared by the batch removes these I/Os but leaves the walk of every query and its distance computations unchanged. CoWalk runs the queries of a batch as cooperating walks on one thread. Every query keeps its own candidate list, a page is read once per batch, and every query ranks every node the batch fetched, so a query reaches its recall with a shorter candidate list. At recall@10 of 0 .95, CoWalk answers a batch on one thread 1 .6 to 1 .9× faster than the strongest per-query baseline, and on a server it serves 3.0 to 6 .9× its throughput at a similar batch latency. We see CoWalk as a step toward retrieval back ends designed for batched agent retrieval.
