## Abstract 

As large language model agents increasingly undertake complex, long-horizon tasks, memory has become an important component for supporting sustained decision-making and action. Existing methods primarily focus on memory storage, updating, and retrieval, but often overlook how memory scheduling affects task execution: the main agent must identify memory needs, initiate retrieval, and wait for results while advancing the task, increasing both scheduling burden and execution time. To address this problem, we propose MemSidecar, which decouples memory scheduling from task execution through two independently selectable modes. Hooks directly delivers bound memory to the main agent when execution events match predefined conditions. Foresight uses an independent agent to predict potential queries, retrieve results in parallel, and store them in a cache, delivering matching and valid results when actual requests arrive. Hooks and Foresight achieve scores of 41.23% and 44.34% on MCP-Persona, respectively, while effectively reducing execution costs and latency and improving the efficiency of long-horizon agent execution. 

Keywords: LLM Agents, Agent Memory, Long-Horizon Agents 

## 1 Introduction 

Large language model agents are moving from answering ques-tions to sustained task execution: browsing requires combining clues across pages, application use requires connecting successive operations, and project work requires carrying earlier decisions and progress forward [12, 32]. As task horizons grow, continuity across steps and sessions becomes an important basis for sustained execution. For Web application tasks, we study memory schedul-ing during long-horizon agent execution so that relevant memories can be delivered automatically and continually support subsequent decisions and actions. Memory provides historical information that remains available throughout long-horizon tasks. Prior studies retain histories, sum-marize experience, and recover information across sessions to sup-port continued decisions [18, 22]. Once information is stored, it must also be retrieved and delivered at the appropriate execution point. This raises two related problems. 

First, retrieval timing and waiting overhead. In a typical on-demand workflow, the main agent identifies memory needs from the current instruction or query, then constructs a retrieval query and accesses memory [21]. In long-horizon tasks, identi-fying access needs only from the current input may overlook earlier constraints, task state, or cross-task dependencies, or delay

Second, retrieval coverage. In long-horizon tasks, the current instruction may not explicitly contain all the historical cues needed to complete the task. Relevant constraints, prior progress, and cross-task dependencies may be distributed across memories and expressed differently from the current instruction. Constructing queries solely from that instruction may therefore miss relevant information, making task goals and visible context necessary for determining what to retrieve. As a task unfolds, a planning step may need long-term constraints, whereas a later tool action may depend on recent progress or an earlier artifact. The relevant memory set therefore changes with execution, even when the user does not introduce a new instruction. Existing memory research emphasizes storage, updating, and retrieval. In a typical on-demand interface, the main agent still initiates memory access inside its task loop. We study this sched-uling coupling: the agent makes task decisions while identifying memory needs, constructing queries, and initiating and waiting for memory access. This adds scheduling burden to the main agent, while memory recall waits block task progress and increase over-all execution latency. We assign memory scheduling to a separate module that uses task goals and visible context to determine re-trieval content and organizes triggering, preparation, and delivery around task execution. ## 2 Related Work 2.1 Agent Memory 

Long-horizon tasks require using historical information across steps, for example by integrating previously gathered clues during persistent browsing. However, models’ use of contextual informa-tion still depends on information position and task complexity; larger context windows do not ensure effective use of their contents [8, 17]. Existing research primarily studies how to store, organize, and update memory. Historical events and user characteristics can be retained through continual updates [36], while task feedback can be distilled into experience for subsequent attempts [25]. Knowl-edge graphs connect pieces of information to support retrieval and integration of scattered clues [13]; hierarchical context and multi-stage consolidation manage information across timescales [6, 21]. State memory further preserves execution progress and tool evi-dence, while learned maintenance improves memory updates for subsequent tasks [15, 34]. Procedural memory also distills success-ful executions into reusable skill compositions and uses task state to guide skill selection [37]. Memory use also depends on current decisions and access costs. Systems research examines the connections between memory, ac-tions, and decisions, as well as the costs of representation, extrac-tion, routing, and maintenance [26, 38]. Overuse or underuse of memory and differences in retained history also affect task per-formance [2, 9]. For Web tasks, Synapse stores successful interac-tion trajectories as exemplar memory and retrieves similar exem-plars to guide subsequent actions [35]; Agent Workflow Memory induces reusable workflows from past interactions and incorpo-rates them into memory to guide subsequent web tasks [29]. Along-side what to retain, it is therefore necessary to consider when this information can support the current task. MemSidecar uses Global Memory to store knowledge and user preferences across tasks, and Workspace Memory to store workspace experience and task state. We further study when to prepare and deliver these two types of memory: what information current and subsequent steps need, and when to provide it to the main agent. Hooks triggers memory delivery in response to events, while Foresight predicts needs and prepares memory in advance, allowing memory access to support subsequent decisions as tasks progress. 

## 2.2 Information Retrieval and Scheduling 

Retrieval scheduling connects need formation, access timing, and result delivery. Retrieval-augmented generation integrates exter-nal information into generation, while black-box augmentation supports configuring a retriever outside a frozen model [14, 24]; scheduling also changes the distribution of construction, retrieval, and generation costs [20]. Prior work forms queries as tasks progress by decomposing follow-up questions or interleaving reasoning with retrieval [23, 27]. FLARE anticipates information needs from predicted continuations [11]. Self-RAG uses reflection tokens to guide retrieval [1]. Adaptive-RAG selects retrieval strategies by question complexity [10], while CRAG evaluates retrieved evidence and chooses corrective actions [31]. Together, these mechanisms place retrieval decisions both before information access and after the initial evidence has returned. Query construction and triggers jointly shape timely access. MemSidecar places memory scheduling alongside execution, using event-triggered Hooks or independently predictive Foresight to study when task memory is prepared and returned to execution.

## 3.2 Dual-Layer Memory 

The layers distinguish information by its scope of reuse. Global Memory stores knowledge and user preferences reusable across tasks. Workspace Memory stores knowledge, skills, experience, and task state within a particular workspace. They address what knowledge and user preferences are reusable and what experience and progress are available in the current workspace, respectively. The store is ℳ = ( ℳG, ℳW). Here ℳℓ,𝑡 is the state of layer ℳℓ

at step 𝑡 , with ℓ ∈ { G, W}.Memory extraction and maintenance. At a stage or task bound-ary, the sidecar extracts useful facts and task state from observed interactions and tool results. Each entry expresses a reusable fact or a coherent piece of state, together with its applicability condi-tions. General knowledge and user preferences enter Global Mem-ory; project procedures, completed work, and pending steps enter Workspace Memory. Extraction, duplicate checking, and necessary updates are performed in one maintenance pass. Existing entries are retained when they already capture the information; new observations add missing facts or revise changed state. For example, a travel entry can record a confirmed booking and its dates, while a project entry records the finished step and next dependency. The trajectory is organized into these fact and state entries, with useful content and applicability conditions preserved. Global Memory: a topic-organized knowledge graph. Global Memory ℳG is represented by graph 𝒢 G, comprising a topic index and knowledge nodes. Topics provide coarse-to-fine access paths, while knowledge nodes hold content for decisions and its applicability conditions: 

𝒢 G = ( 𝒱 T ∪ 𝒱 K, ℰG). (5)

Parent–child topic relations form a hierarchical index: a parent topic groups related needs, and its children narrow the access direction. A knowledge node can con-nect to several related topics, allowing different tasks to reach the same content through their respective topic paths. Knowledge nodes are the basic units of reuse. Each node orga-nizes content around a specific proposition and records the condi-tions under which it applies. Knowledge nodes record reusable un-derstanding or user preferences. The topic index determines where to look, while knowledge nodes determine what information to supply. Global Memory can hold user information, user preferences, and cross-task knowledge, with applicability conditions support-ing interpretation and reuse. Workspace Memory: skills and working memory. ## 3.3 Hooks: Functional Triggers Based on State and Action 

Hooks binds host events and checkable conditions to memory en-tries. During execution, the sidecar reads relevant state and pend-ing actions; a matching condition directly delivers the bound en-try’s text at the current decision point. Functional activation draws on HASP’s use of state and candidate actions to determine skill ap-plicability [16]. The main agent uses the bound content to continue planning and execution without first issuing a memory query. Adding a Hook to a memory entry. At memory writing or con-figuration time, an LLM generates an executable predicate from the entry’s content and applicability conditions, then binds it and the corresponding host event to that entry. For example, “run unit tests before deploying this project” can bind to a pre-tool event whose condition identifies a deployment action for that project. A match directly supplies the convention so the main agent can check test status first. One entry can carry multiple Hooks for different uses. ## 4 Experiments 

We compare MemSidecar with traditional memory systems and harness memory policies on MemoryArena and MCP-Persona, evaluating task quality and execution efficiency. Memory-layer ablations, task-stage analysis, retrieval intervention, and a case study examine the roles of memory organization and scheduling. Hooks and Foresight are evaluated independently. 

## 4.1 Experimental Setup 

4.1.1 Evaluation Tasks. MemoryArena organizes dependent tasks across sessions [7]. It contains 701 task sequences and 4,850 stages, covering bundled web shopping, group travel planning, Progres-sive Web Search, and mathematical and physical reasoning. Later stages require earlier shopping requirements, group arrangements, search evidence, or reasoning progress. MCP-Persona provides stateful simulators for personal appli-cations [28]. Its 173 English tasks contain 724 checkpoints and cover collaboration platforms (CP), content management (CM), social media (SM), email (EM), and cross-server Lark, Rednote, and Mixed tasks. Agents must use historical information to perform queries, content management, and collaboration across applications. 

4.1.2 Compared Methods. As agent harnesses connect persistent memory to session management, context assembly, and tool calls, runtime frameworks have become another way to provide memory capabilities. We therefore compare traditional memory systems and harness memory policies, covering both independent memory components and mechanisms integrated into host execution flows. Traditional memory systems provide memory organization, writing, and retrieval as separate components. 

• Mem0: fact extraction, consolidation, and vector retrieval [3]. 

• A-Mem: structured notes, associative links, and memory evolution [30]. 

• LightMem: sensory, short-term, and long-term stages that compress and organize information, with offline long-term consolidation [6]. Harness memory policies connect persistence to host sessions, context management, or tool calls.

## 5 Conclusion 

We formulate memory scheduling as identifying needs and coor-dinating memory preparation and delivery during long-horizon execution. MemSidecar separates these decisions from task execu-tion through two independently selectable modes. Hooks delivers bound memory when conditions match. Foresight predicts upcom-ing queries and prepares results in the background. Experiments on MemoryArena and MCP-Persona show improved accuracy and efficiency, with shared-backend comparisons further supporting the value of scheduling. Memory scheduling is therefore an im-portant issue in designing long-horizon agents, and MemSidecar offers a viable approach to improving long-horizon task execution through independent memory scheduling.

## A.2 Complete Scheduling Algorithms 

Algorithm A1 checks delivery conditions on a new query or before tool execution; successfully delivered Hooks do not fire again within that task. In the algorithm, fired contains successfully delivered Hook indices, and used contains the Hook indices cor-responding to the packed memory content; used joins fired only after successful delivery, and both entry points share the latest set. Algorithm A2 predicts queries and prepares a cache in the background. An LLM matches actual queries to predicted memory needs, reusing valid results or retrieving normally otherwise. Observed writes refresh the visible directory, and background preparation uses the remaining task-wide budget. Both modes maintain observed memory at stage/task boundaries.

## B.3 Memory Filtering and Joint Scheduling 

This experiment asks whether Hooks and Foresight can be com-bined as complementary scheduling methods within the same task. Condition-based delivery and predicted queries cover memory needs in different ways. We compare joint scheduling with each standalone mode to assess whether combining them improves task quality and what additional Retrieve Token and Runtime it requires. Hooks+filtering provides an additional comparison that checks the applicability of Hook-matched entries without enabling Foresight. We compare only Hooks, only Foresight, Hooks+filtering, and Hooks+Foresight joint delivery. Filtering checks the applicability of content selected for delivery. Joint delivery enables event-based delivery and predicted queries, merging and deduplicating the two streams within the shared budget. On MCP-Persona, Hooks+filtering gains 0.90 percentage points over only Hooks, reduces Retrieve Token by 0.07K, and adds 9.1 sec-onds of Runtime. Filtering trades additional time for more selective delivery and a higher score. Joint scheduling reaches 46.13% Over-all, exceeding only Foresight by 1.80 points while adding 0.19K Retrieve Token and 12.6 seconds. Joint scheduling improves task scores and increases preparation and delivery costs. On MemoryArena, Hooks+filtering gains 0.71 percentage points over only Hooks, reduces Retrieve Token by 0.46K, and adds 50 seconds of Runtime. Joint scheduling reaches 16.12% SR, exceed-ing only Foresight by 0.71 points while adding 3.29K Store tokens, 1.22K Retrieve Token, and 36 seconds. Joint delivery increases suc-cess rate and incurs additional memory maintenance, preparation, and delivery costs.
