## Abstract 

Distributed vector databases increasingly support security-sensitive applications, yet existing systems primarily pro-tect index integrity or replica availability rather than the trustworthiness of retrieved results. Consequently, a com-promised replica can return a plausible but manipulated re-sult that remains cryptographically valid, while conventional replication and Byzantine defenses do not directly establish whether the retrieved results are trustworthy. We present TRUST ANN, a middleware layer that provides query-level trust for distributed approximate nearest-neighbor (ANN) re-trieval without modifying the underlying ANN algorithm. TrustANN introduces three complementary protocols: T RUST -BIND , which verifies retrieval trust from authenticated, con-sistent, and failure-domain-independent replica evidence; C O-

> ORD

SHIFT , which asynchronously constructs reusable coor-dination epochs outside the query critical path; and A VAIL -GUARD , which performs bounded recovery when replicas are unavailable, stale, or conflicting while preserving the trust criterion. Queries are marked T RUSTED only when sufficient independent evidence exists for every relevant shard; other-wise, TrustANN returns U NVERIFIED . On an AWS deploy-ment using distributed FAISS HNSW, TrustANN reduces retrieval attack success rate from 1.000 to 0.000 under the tested Byzantine-retrieval attack with two-of-three replica ver-ification. The verification layer increases clean p95 latency by only 9.36%. Under replica crashes, TrustANN maintains trusted retrieval through 33% failures and correctly returns UNVERIFIED when sufficient evidence is unavailable. 

## 1 Introduction 

Distributed approximate nearest-neighbor (ANN) retrieval has become a core substrate for retrieval-augmented generation, recommendation, semantic search, and other vector-intensive applications [18, 38]. Modern ANN systems scale by par-titioning vector collections across machines and replicating shards, while indexes such as HNSW, IVF/PQ, and DiskANN provide efficient large-scale search [14, 21, 27]. Recent dis-tributed vector systems further improve scalability through parallel execution, communication optimization, and resource disaggregation [1, 32, 34, 41]. However, distributing retrieval also expands its trust boundary: a query result may depend on multiple shards, replicas, and workers whose behavior cannot necessarily be assumed correct. Thus, scalable distributed retrieval raises a fundamental question beyond performance: 

when can a distributed ANN result itself be trusted? 

First, authenticated state does not imply trustworthy re-trieval. Authenticated data structures can establish that stored state is consistent with an authenticated representation [11], and recent verifiable ANN systems extend this principle to ap-proximate search. ANNProof, VLAH, and CD-ANN provide mechanisms for verifying ANN search results or protecting index/vector state using authenticated structures and, in some cases, blockchain anchoring [20, 29, 37]. These approaches establish important foundations for verifiable retrieval, but their primary abstraction is verification of an index or an indi-vidual search execution. In a distributed ANN fabric, however, a worker may possess a valid authenticated index while still omitting candidates, returning stale results, manipulating rank-ings, or providing inconsistent responses. Thus, authenticated state does not necessarily imply trustworthy distributed re-trieval . What is missing is query-level retrieval trust : whether the distributed participants involved in a query provide suffi-cient independent evidence to justify accepting its result. This distinction is also broader than retrieval poisoning. Poisone-dRAG and related work demonstrate that malicious retrieved content can substantially manipulate RAG systems [16, 42], but a retrieval participant can also compromise the result with-out injecting poisoned content, for example by suppressing, replaying, or selectively manipulating results. Establishing such trust, however, creates a second chal-lenge: coordination latency. A natural response to untrusted participants is to require them to agree before accepting a re-sult. Byzantine-fault-tolerant consensus provides strong guar-antees against faulty replicas, but requires communication and synchronization among participants [9]. Blockchain-based 1arXiv:2610.34608v1 [cs.DC] 25 Oct 2026 distributed systems similarly use replicated agreement to es-tablish trusted state [15,36]. Putting such coordination directly on the ANN query path, however, couples retrieval latency to distributed agreement. This conflicts with the design objective of ANN systems, where parallelism and communication effi-ciency are central to low-latency search [21, 27, 41]. Existing blockchain-anchored verifiable ANN systems demonstrate the value of authenticated state [20, 37], but do not address how to maintain reusable trust state without making distributed coordination a prerequisite for each retrieval operation. The challenge, therefore, is not simply to establish trust, but to establish reusable trust state without placing consensus-scale coordination on the latency-critical query path .Finally, failures make replica availability an insufficient basis for trust. Even when coordination is kept off the query path, replication provides availability rather than sufficient trustworthy evidence. Distributed vector systems replicate data to tolerate failures and sustain retrieval [1, 34, 41], yet surviving replicas may crash, become unreachable, return stale state, or produce conflicting responses. A system that simply accepts any available response can therefore mistake availability for correctness, whereas lowering the integrity threshold when replicas fail weakens the very guarantee the system is intended to provide. Byzantine-resilient systems traditionally make the fault bound explicit when determin-ing whether sufficient replicas support an operation [9]. For distributed ANN, the analogous requirement is to distinguish 

having an answer from having enough evidence to trust that answer . A trustworthy retrieval system must therefore pre-serve its evidence threshold under failures, attempt bounded recovery using surviving replicas, and explicitly reject a result when sufficient evidence cannot be established. 

Proposed Solution. Existing systems address distributed ANN execution [1,32,34,41], authenticated ANN state [20,29, 37], federated retrieval confidentiality [39], or malicious re-trieval content [16,42], but do not provide query-level retrieval trust with reusable coordination and failure-aware evidence recovery. We present TrustANN, a middleware layer that op-erates above existing ANN indexes without modifying the underlying search algorithm. TrustANN separates retrieval execution from retrieval trust and background coordination from query-level safety by three tightly coupled components. First, TrustBind establishes trust per shard from authenti-cated replica evidence by requiring sufficient, mutually consis-tent, and failure-domain-independent responses. Second, Co-ordShift asynchronously constructs reusable retrieval epochs through randomized, failure-domain-aware coordination; its state is cached and consumed by queries, but it is not the query-level safety boundary. Finally, AvailGuard performs bounded recovery by seeking additional independent evidence without weakening the trust threshold. If sufficient evidence cannot be established, TrustANN returns U NVERIFIED . Thus, coordination and recovery remain supporting mechanisms, while the query-level trust decision is independently deter-mined by retrieval evidence. We implement TrustANN over an existing HNSW-based distributed ANN substrate and evaluate it on Deep10M [19] using a multi-node AWS deployment, covering retrieval at-tacks, evidence ablations, failures, fan-out, recovery, and asyn-chronous coordination. In summary, this paper makes the following contributions: 

(i) Query-level retrieval trust. We introduce TrustBind, which establishes per-shard retrieval trust from authenticated, consistent, and failure-domain-independent replica evidence. 

(ii) Asynchronous coordination. We introduce CoordShift, which builds reusable, failure-domain-aware retrieval epochs asynchronously without placing coordination on the query critical path. 

(iii) Bounded failure recovery. We introduce AvailGuard, which recovers additional independent evidence under replica failures without weakening the trust criterion, returning U N-

## 3 System Design 

TrustANN is a middleware architecture for trustworthy distributed approximate nearest-neighbor (ANN) retrieval. Rather than replacing the underlying ANN index or search algorithm, TrustANN operates above an existing distributed ANN deployment and introduces a query-level retrieval-trust layer across its shards and replicas. The design targets en-vironments in which retrieval workers may be unavailable, stale, or adversarial. The design addresses three challenges. First, authenticat-ing ANN index state does not establish trustworthy retrieval: a worker may possess valid index state while returning in-complete, stale, or manipulated candidates. Second, placing distributed agreement directly on every query introduces ad-ditional communication and synchronization latency. Third, replica failures can leave a query operationally available while providing insufficient independent evidence to establish re-trieval trust. TrustANN addresses these challenges through three com-plementary components: TrustBind , CoordShift , and Avail-Guard . TrustBind establishes query-level trust from mutually consistent and independently attributable replica evidence. CoordShift maintains reusable retrieval epochs using asyn-chronous, randomized coordination with fault-domain diver-sity, while keeping its correctness outside the query-time safety boundary. AvailGuard performs bounded recovery by seeking additional independent evidence without weakening the trust threshold. Figure 1 presents the overall architecture.

## 3.2 Architecture Overview 

As Figure 1 illustrates, TrustANN separates background coor-dination from query-level retrieval trust. CoordShift periodi-cally samples workers and publishes a cryptographically au-thenticated retrieval epoch reference using a diversity-aware quorum. Authentication establishes the provenance and in-tegrity of the epoch reference; it does not certify the semantic correctness of its state digest. TrustBind and AvailGuard oper-ate on the query path, where the router selects relevant shards and replicas and workers perform ordinary ANN retrieval. When a query arrives, contacted workers return candidate sets and authenticated metadata. TrustBind validates the re-sponses and constructs an evidence graph for each relevant shard. For each shard, it seeks a sufficiently large set of mu-tually consistent responses whose provenance spans the con-figured independent failure domains. A result is considered TRUSTED only when the trust condition is satisfied for every relevant shard. If sufficient evidence is unavailable for one or more shards, AvailGuard selects additional replicas for the affected shard subject to the same independence requirements and a bounded recovery budget. It does not lower the trust threshold and does not allow evidence from one shard to substitute for missing evidence from another. If the required evidence cannot be established within the recovery budget, TrustANN returns UNVERIFIED .The retrieval and coordination paths interact only through the authenticated epoch reference, but their safety strengths are deliberately different. CoordShift does not provide a Byzantine-safe certification of the epoch contents. A sam-pled coordination quorum may occasionally be influenced by faulty workers; such an event affects coordination state but does not itself establish query trust. TrustBind independently validates retrieval evidence for every query. Consequently, a failed or adversary-influenced coordination round does not 4directly cause a query to be trusted.

TrustBind protocol. An authenticated ANN index establishes the authenticity of a worker’s state but does not establish that its returned neighbors are trustworthy. Moreover, simple replica counting can incorrectly treat mutually inconsistent responses as equivalent evidence. CoordShift protocol. Requiring Byzantine consensus or syn-chronous agreement for every retrieval epoch would introduce coordination overhead into a latency-sensitive ANN query path. The CoordShift protocol (i.e., Protocol 2) instead main-tains reusable coordination state asynchronously. Its purpose is not to provide a new Byzantine consensus protocol, but to amortize repeated coordination cost and reduce correlated exposure through diversity-aware randomized selection. Most importantly, CoordShift is not part of the query-time safety boundary. Even if its sampled quorum is influenced by Byzantine workers, the TrustBind protocol (Section 3.3) does not accept a retrieval result solely because it is consistent with the resulting coordination digest.

## 3.5 Independence-Aware Evidence Recovery 

AvailGuard protocol. Replica failures can preserve opera-tional retrieval availability while reducing the evidence avail-able to establish retrieval trust. A recovery mechanism that simply collects additional responses may incorrectly interpret correlated or jointly compromised replicas as independent support. The AvailGuard protocol (i.e., Protocol 3) therefore treats independent evidence , rather than response count alone, as the recovery objective. 

Design. Suppose the TrustBind protocol (Section 3.3) can-not establish Trusted j(q) for a relevant shard j. AvailGuard retains the valid evidence already collected for that shard and selects additional replicas that provide new fault-domain coverage. Replicas from domains already represented by sus-picious or conflicting evidence are deprioritized. Each recovery step therefore attempts to increase the inde-pendence of the evidence set rather than merely its cardinality. Importantly, evidence recovery is performed independently for the affected shard; responses from other shards cannot be used to satisfy the trust condition for shard j. Recovery is bounded by Kmax . The threshold θ and the consistency and di-versity requirements remain unchanged throughout recovery. ## 3.6 Correctness and Safety Properties 

TrustANN deliberately separates coordination properties from query-level retrieval safety. The three protocols described in Sections 3.3–3.5 provide the following system-level proper-ties. 

(1) Coordination does not determine retrieval trust. The CoordShift protocol (Section 3.4) provides an authenticated, reusable epoch reference but does not provide a Byzantine-safe state certificate. Query-level trust is instead established independently by the TrustBind protocol (Section 3.3); there-fore, an adversary-influenced coordination round cannot by itself cause a retrieval result to satisfy Eq. 8. 

(2) Trust is established independently per shard. The Trust-Bind protocol (Section 3.3) evaluates evidence separately for every relevant shard. Under the assumed bound in Eq. 4, a corrupted minority within a shard cannot alone satisfy the support threshold, and evidence from another shard cannot compensate for insufficient evidence. 

(3) Evidence must satisfy consistency and independence. 

TrustANN does not equate replica identity with independent evidence. The TrustBind protocol requires sufficient response consistency and failure-domain diversity as defined in Eqs. 5– 7. Responses from the same correlated domain therefore do not automatically increase the trust level. 

(4) Failure recovery never weakens trust. The AvailGuard protocol (Section 3.5) may obtain additional evidence after failures or insufficient evidence, but it never lowers θ or re-moves the consistency and independence requirements. If sufficient evidence cannot be established, TrustANN returns UNVERIFIED . Increasing Kmax therefore provides additional recovery opportunities without allowing evidence from an unrelated shard to satisfy Eq. 8. 

(5) Recovery is bounded. AvailGuard performs at most Kmax 

additional retrieval rounds, providing a bounded query-side recovery cost rather than waiting indefinitely for unavailable replicas. Recovery improves availability only when sufficient independent replicas remain available; if all available inde-pendent domains for a relevant shard are compromised or un-available, TrustANN returns U NVERIFIED . TrustANN does not formally guarantee that a T RUSTED result has the same recall as an ideal unpoisoned corpus. Its guarantee concerns the sufficiency and consistency of the observed distributed retrieval evidence under the stated fault model. 

## 3.7 Communication and Performance Model 

TrustANN communication consists of three logically sepa-rate classes: retrieval, evidence verification, and background coordination. Retrieval traffic includes ANN requests, can-didate responses, and bounded AvailGuard fallback rounds. Evidence processing includes authentication, provenance val-idation, consistency computation, and evidence-set selection. Coordination traffic consists of state-summary requests and responses associated with the CoordShift candidate pool and selected quorum. For a query serving F = |Jq| relevant shards with replica-tion factor r, the initial worst-case response fan-out is 

Bq ≤ Fr , (13) when all replicas are contacted. With selective fan-out, the actual cost is determined by the configured initial replica set. If a full replica set is contacted in each recovery round, a theoretical upper bound with Kmax additional rounds is 

Bq ≤ Fr (1 + Kmax ). (14) The implementation normally uses selective recovery, so these expressions serve as worst-case communication bounds rather than measured costs. CoordShift is amortized across queries because its epoch is reused until superseded. Its communication and computation are therefore measured separately from query-path retrieval and evidence processing. This separation enables TrustANN to evaluate three distinct costs: (1) query-level evidence veri-fication, (2) background coordination, and (3) failure-induced 7recovery. In a distributed deployment, these costs can be mea-sured using actual inter-node communication rather than treat-ing local process execution as a proxy for distributed behavior. 

## 4 Implementation 

We implement TrustANN as a middleware layer above an existing distributed ANN index, without modifying the un-derlying ANN search algorithm. The prototype [30] is imple-mented in Python and comprises approximately 1.7K lines of code, excluding configuration files and experiment scripts. The system consists of a coordinator and distributed ANN workers connected through gRPC. Each worker hosts a replica of one ANN shard and independently executes the local ANN search. The coordinator implements the query router, Trust-Bind, AvailGuard, and the asynchronous CoordShift service. 

Distributed ANN substrate. We use HNSW as the un-derlying ANN index, with M = 16, e fConstruction = 200, and e f = 64. The ANN layer is unchanged by TrustANN. TrustANN intercepts the retrieval result and attaches compact authenticated evidence identifying the worker, shard, replica, and index epoch. This separation allows TrustANN to operate as a middleware layer over existing ANN implementations. 

TrustBind implementation. For each query and shard, Trust-Bind constructs an evidence consistency graph whose ver-tices represent valid replica responses. Edge weights com-bine candidate-set overlap and ranking consistency. Rather than solving a maximum-clique problem, we use greedy evi-dence selection: the initial response is chosen from the most-supported candidate set, and subsequent responses are added according to their marginal consistency gain while satisfy-ing the configured failure-domain independence constraint. A shard is trusted only when its selected evidence satisfies the configured support threshold, consistency threshold, and failure-domain coverage requirements. Signature and epoch checks are performed before graph construction. 

CoordShift implementation. CoordShift executes asyn-chronously and does not participate in the query critical path. At each coordination epoch, a seeded randomized candidate pool is formed, and a diversity-aware selection procedure chooses the coordination quorum. The selection favors dis-tinct configured failure domains before filling the remaining quorum positions. Workers return signed state summaries, from which CoordShift derives the most strongly supported state reference for each shard when a majority exists. The resulting epoch is cached and reused by subsequent queries. A failed coordination round leaves the previously accepted epoch active. 

AvailGuard implementation. AvailGuard handles unavail-able, stale, or conflicting replica evidence. Instead of low-ering the TrustBind threshold, it selects additional replicas that maximize independent evidence relative to the already observed responses. Newly obtained evidence is evaluated within its corresponding shard and cannot be pooled with un-related shards to satisfy another shard’s threshold. Recovery terminates after a bounded number of attempts. If sufficient independent evidence cannot be obtained, TrustANN returns 

Unverified rather than silently weakening the trust condition. 

Fault injection and deployment. The prototype runs as in-dependent processes on a multi-node AWS cluster, with each worker deployed on a separate EC2 instance and communi-cating through gRPC. We use Linux traffic control and netem 

to introduce network delay and loss. The implementation sup-ports crash-stop failures, unreachable replicas, stale epoch references, corrupted retrieval results, and corrupted coordi-nation summaries. These mechanisms allow the evaluation to exercise TrustBind, CoordShift, and AvailGuard under both availability and integrity faults. 

## 5 Evaluation 

We evaluate TrustANN on the Deep10M benchmark [19] using a multi-node AWS deployment. We examine: (Q1) whether TrustBind rejects corrupted retrieval; (Q2) whether CoordShift operates off the query critical path; (Q3) whether AvailGuard maintains trustworthy retrieval under failures; (Q4) the overhead of verification and distributed retrieval; and (Q5) whether failure-domain-aware coordination improves quorum diversity. 

## 5.1 Experimental Setup 

Dataset and ANN configuration. All experiments use the Deep10M benchmark [19]. Deep10M contains 10M 96-dimensional float32 vectors generated from deep neural-network features. For the multi-node AWS experiments, we use a 100K-vector subset while retaining the original 96-dimensional representation and L2 distance. Ground-truth nearest-neighbor results are used to identify retrieval attacks. The data are partitioned across shards and replicated across worker nodes. Each worker maintains a local FAISS HNSW index with M = 16, e fConstruction = 200, and query-time 

e f = 64. We use these fixed, moderate settings to provide a stable ANN substrate while balancing search quality, con-struction cost, index size, and query latency [10, 22]. HNSW is used only as the underlying ANN backend for our evalua-tion. TrustANN’s trust layer is independent of the underlying ANN indexing method and can be deployed above other ANN backends. Unless otherwise stated, the deployment uses three shards with three replicas per shard ( r=3), evidence threshold 

θ=2, fallback budget Kmax =1, and CoordShift quorum size 

k=9. The same query set and random seeds are used across corresponding configurations. 

Baselines. For quantitative comparison, we use an Unver-ified Distributed ANN baseline implemented on the same distributed HNSW substrate, dataset, workload, and AWS deployment as TrustANN, but without retrieval-level verifi-cation. This controlled baseline provides an apples-to-apples 8comparison for measuring the cost and benefit of TrustANN’s query-level trust mechanisms. The systems summarized in Table 1 are not used as direct experimental baselines because they target different system abstractions and provide differ-ent verification or coordination semantics. In particular, Dis-tributedANN [1] distributes a single logical DiskANN [13] graph across machines, whereas TrustANN is an index-independent trust layer evaluated here over replicated HNSW shards. ANNProof [20] and VLAH [29] focus on search/index verification, CD-ANN [37] incorporates Byzantine coordina-tion, and PBFT [9] provides general Byzantine consensus rather than distributed ANN retrieval. Directly reimplement-ing or integrating these systems would therefore not provide a controlled comparison of TrustANN’s retrieval-trust mecha-nisms. 

Testbed. TrustANN is deployed as a multi-node cluster on AWS EC2. A dedicated coordinator hosts the query router, TrustBind verifier, AvailGuard, and CoordShift, while inde-pendent EC2 worker instances host replicated ANN indexes. Workers communicate with the coordinator through gRPC, en-suring reported query latency includes distributed communica-tion and coordinator-side verification. Unless otherwise noted, the default deployment consists of three shards with three replicas per shard, utilizing nine worker instances (though separate scale-out experiments expand this up to 144 work-ers). Fault experiments terminate, isolate, or disable selected workers to emulate crash-stop and Byzantine conditions, and experiments use 100–150 queries per configuration.

## 5.4 Failure-Resilient Retrieval 

We evaluate AvailGuard under progressively increasing replica failures. The experiment measures whether TrustANN can preserve trustworthy retrieval when the initially contacted replicas are unavailable. We uniformly increase the fraction of crashed replicas and record trusted query rate, fallback acti-vation, and query latency. AvailGuard retains θ=2 throughout and attempts to obtain additional independent evidence rather than weakening the trust criterion. Table 8 shows that the trusted-query rate remains 1.000 through the 33% crash configuration, with fallback activated at the nonzero failure levels. At 49% crashed replicas, however, the trusted rate falls to zero because the remaining deployment cannot provide sufficient evidence. Thus, AvailGuard extends retrieval availability by locating additional evidence while preserving the same trust requirement. The lower latency at higher crash rates results from fewer live workers participating in retrieval and should not be interpreted as improved system capacity.

## 6 More Related Work 

Distributed ANN and verifiable retrieval. Distributed ANN systems such as Milvus [31], CoTra [41], HARMONY [32], DistributedANN [1], DistVS [34], and GaussDB [28] pri-marily optimize scalability, partitioning, communication, and resource management. Verifiable systems including AN-NProof [20], VLAH [29], and CD-ANN [37] further authenti-cate search or index/vector state. However, these approaches generally do not determine whether distributed shards and replicas provide sufficient independent evidence to trust a re-trieval result . TrustANN instead makes the retrieval operation itself the trust boundary and establishes trust at query time. 

Federated and Byzantine-robust protection. C-FedRAG [2], FRAG [40], and RAGRoute [12] address decentralized retrieval and privacy, while RAGuard [16] and PoisonedRAG [42] target malicious retrieved content. Byzantine-robust aggregation [8, 17, 33] and P2P defenses such as SybilGuard and X-Vine [24, 25, 35] protect aggre-gation or overlay membership. These mechanisms address complementary security dimensions, but do not establish 

retrieval-evidence sufficiency under replica failures, stale state, or retrieval-time manipulation. TrustANN bases its trust decision directly on authenticated replica evidence. 

Byzantine coordination and fault tolerance. BFT pro-tocols and ledgers [7, 9, 15, 36] provide strong replicated agreement but introduce communication and synchronization costs unsuitable for latency-critical ANN queries. More prior work [3–6, 23] similarly explored lightweight consensus, au-thenticated state, and provenance for trustworthy distributed computing. TrustANN instead separates coordination from re-trieval: TrustBind establishes query-level trust from replica ev-idence, CoordShift maintains reusable epochs asynchronously without consensus on the query path, and AvailGuard pre-serves the evidence threshold during bounded recovery. Thus, TrustANN determines whether available retrieval evidence is sufficient to trust the result without placing consensus in the ANN query path. 

## 7 Conclusion and Future Work 

TrustANN provides a distributed trust layer for approximate nearest-neighbor (ANN) retrieval that separates query-level retrieval trust from background coordination and failure re-covery. T RUST BIND establishes trust from authenticated, con-sistent, and failure-domain-independent replica evidence on a per-shard basis, while C OORD SHIFT asynchronously main-tains reusable coordination epochs without placing coordina-tion on the query critical path. A VAIL GUARD further provides bounded, independence-aware evidence recovery when repli-cas are unavailable, stale, or conflicting, without lowering the trust threshold or relaxing the consistency and independence requirements. As a result, TrustANN explicitly distinguishes between a retrieval result supported by sufficient distributed evidence and one for which such evidence cannot be estab-lished, returning U NVERIFIED rather than weakening the trust decision. Our prototype demonstrates that these mechanisms can be implemented as a middleware layer above an existing ANN in-dex without modifying the underlying ANN search algorithm. Experiments on distributed FAISS HNSW deployments show that TrustANN can reject the tested Byzantine retrieval attack while preserving trusted retrieval under the evaluated replica failure conditions, with a 9.36% increase in clean p95 latency. More broadly, the results demonstrate that retrieval-level trust can be established through explicit evidence requirements while keeping global coordination and recovery decoupled from the latency-critical retrieval path. As future work, we will investigate adaptive adversaries, larger-scale and more dynamic failure and reconfiguration scenarios, and stronger retrieval-level guarantees.
