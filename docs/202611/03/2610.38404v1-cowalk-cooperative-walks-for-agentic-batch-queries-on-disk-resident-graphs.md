## 摘要
查询重写、深度研究和组相对策略优化（GRPO）等工作负载会发出成批的语义相关向量查询。现有的磁盘驻留近似最近邻（ANN）系统独立处理这些查询。在三种工作负载上，一个批次中 31% 到 67% 的 I/O 所获取的页面已被该批次中的另一个查询获取过。由该批次共享的页缓存可以消除这些 I/O，但仅使单线程搜索快 1.1 到 1.2 倍，因为搜索时间花在距离计算上，而缓存不会改变任何查询的游走过程。我们提出 CoWalk，它在单线程上将一批查询作为协同游走执行。每个查询保留自己的候选列表，每个页面每批只读取一次，每个被获取页面上的全精度向量都会被该批次中的每个查询排序。因此，查询能以更短的候选列表达到目标召回率，从而计算更少的距离并发出更少的 I/O。在 recall@10 为 0.95 时，CoWalk 在单线程上回答一个批次的速度比最快的逐查询基线快 1.6 到 1.9 倍，且 I/O 少 2.8 到 6.9 倍。在服务器上，它以相近的批次延迟提供该基线 3.0 到 6.9 倍的吞吐量。

## Abstract
Workloads such as query rewriting, deep research and group-relative policy optimization (GRPO) issue batches of semantically related vector queries. Existing disk-resident approximate nearest neighbor (ANN) systems process these queries independently. On three workloads, 31 to 67 percent of the I/Os of a batch fetch a page that another query of the batch has already fetched. A page cache shared by the batch removes these I/Os, yet it makes a single-thread search only $1.1$ to $1.2{\times}$ faster, because the search time goes to distance computation and the cache does not change the walk of any query. We present CoWalk, which runs the queries of a batch as cooperating walks on one thread. Every query keeps its own candidate list, a page is read once per batch, and the full-precision vector on every fetched page is ranked by every query of the batch. A query therefore reaches the target recall with a shorter candidate list, which computes fewer distances and issues fewer I/Os. At recall@10 of 0.95, CoWalk answers a batch on one thread $1.6$ to $1.9{\times}$ faster than the fastest per-query baseline and issues $2.8$ to $6.9{\times}$ fewer I/Os. On a server it serves $3.0$ to $6.9{\times}$ the throughput of that baseline at a similar batch latency.

# CoWalk 论文结构化总结

## 1. 核心问题与研究背景

- **应用背景**：LLM 智能体（Agent）在查询重写、深度研究（Deep Research）、HyDE、子问题分解、事实核查、GRPO 强化学习后训练等场景中，会一次性发出**一批语义相关的向量查询**（batch），这些查询源自同一意图，只是表面形式不同。
- **核心矛盾**：现有磁盘驻留 ANN 系统（如 PipeANN、DiskANN、SPANN）对每条查询**独立处理**。由于批内查询在嵌入空间中高度接近（批内余弦距离比随机查询对紧 1.3–2.4 倍），它们的游走会反复访问图索引的同一区域，导致 **31%–67% 的 I/O 是重复读取同一页面**。
- **关键洞察（反直觉）**：最直接的修复——批内共享页缓存（GLRU）——虽然几乎消除了重复 I/O，但单线程仅加速 **1.1–1.2 倍**。原因是单线程下 I/O 延迟已被流水线隐藏，时间主要花在 PQ 距离与精确距离计算上，而**缓存是被动的，不改变任何查询的游走路径与计算量**。
- **研究意义**：论文主张为"智能体批量检索"这一新兴负载重新设计检索后端，而非继续沿用逐查询范式；目标是把批内 I/O 冗余转化为**协同搜索收益**，同时降低 I/O 与距离计算。

## 2. 方法论：CoWalk 协同游走

### 2.1 核心思想
- 在**单线程**上把一批 B 条查询组织为 **B 条协同游走**：每条查询仍保留自己的候选列表、自己选择下一节点、独立返回 top-K，但在三个层面共享：**共享 I/O、共享精确距离、共享一个线程的 I/O 流水线**。
- 与缓存式方案的本质区别：缓存只去重 I/O；CoWalk 让**每个被读页面的全精度向量被批内所有查询排序**，从而缩短每条查询达到目标召回所需的候选列表长度 L，进而减少展开节点数、PQ 计算与 I/O。

### 2.2 关键技术细节
- **共享 I/O（每批每页只读一次）**：查询选中节点后查页表；若该页正被其他 walk 读取则"加入"该 I/O；若本批已读过则直接从内存记录展开；否则才发起新 I/O。页面完成后邻居列表复制到批内生命周期记录，供后续任意查询零 I/O 展开。
- **共享精确距离（核心创新）**：某节点**首次**被本批任一 walk 读取时，计算其全精度向量到**批内所有查询**的精确距离，写入"精确距离表"（一行一节点、一列一查询），包括已停止游走的查询。最终每条查询返回自己列中精确距离最小的 K 个。
  - 重要约束：精确距离**只用于最终排序，绝不进入候选列表**，因此不改变任何查询的游走路径，远离批中心的查询不会被"拉偏"。
  - 代价：每读一节点需 B 次精确距离计算，随 B 增长。
- **单线程流水线调度**：所有 walk 的 I/O 提交到同一 io_uring；每查询保持 4 个 I/O 在途（而非 PipeANN 单查询需 32 个）；线程等待"任一 I/O 完成"即处理，先提交本轮新 I/O、再计算精确距离，使新 I/O 在计算期间飞行。相比 hop-synchronous（等整轮 I/O 全部完成）避免了慢 I/O 阻塞全批。
- **刻意不共享邻居列表**：虽然邻居列表与向量同页到达，但实验表明对全批 PQ 打分邻居会使单线程慢 1.3–2.4 倍（PQ 已是最大耗时阶段），故只为"选中该节点的查询"打分。
- **实现优化**：AVX-512 内核一次加载向量块对 4 条查询做 FMA；已打分邻居用哈希数组去重；多线程时每批 k 线程轮询分查询，通过原子页表无锁共享，游走后补齐其余精确距离。

### 2.3 算法流程（文字版）
1. 初始化每条查询候选列表为入口点，建立空的精确距离表 E。
2. 循环直到无 pending I/O：
   - 等待至少一个 I/O 完成；
   - 对完成页，为选中该页节点的查询做 PQ 邻居扩展并插入其候选列表；
   - 让每个仍在游走且 pending I/O < 4 的查询继续选点、提交 I/O；
   - 对本轮首次读到的节点，补齐到全批查询的精确距离行。
3. 每条查询输出自己列中精确距离最小的 K 个节点。

## 6. 主要结论与发现

- **单线程**：recall@10=0.95 时，CoWalk 回答一批耗时 62/25/71 ms，比 PipeANN 快 **1.9×/1.8×/1.6×**，比 GLRU 快 1.8×/1.8×/1.6×；I/O 少 **2.8–6.9×**（901/1849/5007 vs. 6210/5362/14020 级别）。
- **服务器**：knee 处吞吐为 PipeANN 的 **6.9×/4.0×/3.0×**，批延迟为 PipeANN 的 0.74–1.08×；等延迟约束下仍达 6.9×/3.6×/2.6×。
- **成本**：每美元查询数为 PipeANN 的 **3.0×/2.7×/2.0×**（正文 k 配置），k=1 时达 7.0×/4.0×/4.0×。
- **加速来源分解**：单线程加速主要来自精确距离共享带来的更短候选列表（减少计算）；多线程/高并发下才主要来自 I/O 减少（SSD 成为瓶颈时 6.9× I/O 差转化为约 7.1× QPS 差）。
- **耗时结构**：PQ 比较仍是最大阶段（占 walk 时间 51–59%）；精确距离占比随 B 从 3% 升至 25%；I/O 等待从 26% 降至 7%。
- **边界条件**：批内查询越相关收益越大；批越大收益先增后减（OpenResearcher B≥60 时降至约 1.4×）；不相关随机批次会使 CoWalk 单线程慢于 PipeANN。

## 7. 优点

- **问题刻画精准**：用三负载实测量化"批内相似性 → 重复 I/O → 缓存不足"的因果链，明确指出现有方案瓶颈在**计算而非 I/O**，动机极具说服力。
- **设计克制且有依据**：只共享"页面 + 精确距离"，刻意不共享邻居列表，并用实验（PQ 占时过半、邻居命中率仅 3.5–7.3%）证明该取舍，避免"共享一切"的直觉陷阱。
- **不改变游走语义**：精确距离仅参与最终排序、不进入候选列表，保证各查询独立性与结果正确性，设计优雅。
- **系统实现扎实**：单线程多 walk 流水线把 4 I/O/查询变成 4B 在

途 I/O 的并行度，在单线程下仍能隐藏延迟；AVX-512 内核、哈希去重、原子页表等工程细节使设计在真实硬件上落地。
- **负结果诚实**：主动报告随机批次下性能倒退，并给出"批内相关性"这一明确适用前提，避免过度宣称通用性。
- **可复现性好**：公开数据集来源、索引参数、硬件配置、成本计价口径，所有系统共享同一索引与 I/O 引擎，对比条件清晰。

## 8. 局限与不足

- **适用前提较强**：方法收益依赖批内查询语义高度相关；对随机、不相关批次不仅无收益，单线程下还会因额外精确距离计算而变慢 1.2–2.5×，实际部署需先做批相关性判定或回退机制。
- **批大小存在收益拐点**：OpenResearcher 上 B≥60 时加速降至约 1.4×，说明大 batch 下每节点 B 次精确距离计算的线性成本开始侵蚀收益，论文未给出自适应选择 B 或采样部分查询计算距离的策略。
- **精确距离计算随 B 线性增长**：每读一节点需对全批查询算距离，B 很大时该阶段占比升至 25%，是潜在扩展性瓶颈；作者虽用 AVX-512 批处理缓解，但未探索近似或分层计算。
- **实验覆盖有限**：仅单机单 SSD，未在真实多副本/分布式集群或 NVMe 阵列上端到端验证（多 SSD 仅为投影估算）；基线仅 PipeANN 与自建 GLRU，未与 SPANN/SPFresh 等簇索引或 GPU 批量方案 CAGRA 实测对比。
- **部分曲线样本稀疏**：按批大小分桶后个别桶仅 ≤6 批，延迟曲线抖动，统计置信度有限；QPS 测量重复次数说明不充分（仅消融取三次中位数）。
- **未涉及更新/动态场景**：索引视为静态，未讨论插入删除、增量更新下的批协同行为。
- **单线程与多线程语义差异**：多线程模式下每批用 k 线程分摊查询，需"游走后补齐其余精确距离"，实现复杂度上升，论文对该路径的正确性与开销分析相对简略。

## 9. 启示与展望

- **负载驱动设计范式**：论文示范了从"新兴上层负载（LLM Agent 批量检索）"反推后端系统设计的路径——先量化负载特征（批内紧密度、重复 I/O 比例），再针对瓶颈（计算而非 I/O）设计机制，而非套用通用优化。
- **"共享计算"优于"共享缓存"**：GLRU 实验构成有力反例，说明被动缓存去重 I/O 不足以提速，主动让共享数据参与所有查询的排序才能缩短搜索路径，这一思路可迁移到其他批量相似查询场景（如推荐召回、多模态检索）。
- **保持查询独立性的共享设计**：精确距离只用于最终排序、不进候选列表的约束，是在共享与正确性/鲁棒性之间取得平衡的优雅范式，值得在批处理系统中借鉴。
- **未来方向**：自适应批大小与相关性感知调度、精确距离的近似/采样计算、分布式多副本下的批协同、动态索引更新支持，以及与 GPU 批量检索方案的混合部署，都是自然的后续工作。

## 10. 总体评价

CoWalk 是一篇问题刻画精准、设计克制、实验较扎实的系统论文。其最大贡献不在于某项单点技术，而在于**识别出"LLM 智能体批量查询"这一被忽视的负载形态，并用实测数据纠正了"重复 I/O 是主要瓶颈、缓存即可解决"的直觉误判**，进而提出以"共享精确距离缩短搜索路径"为核心的协同游走机制。方法在三个真实负载上取得 1.6–1.9×（单线程）与 3.0–6.9×（服务器吞吐）的加速，且通过负结果实验诚实界定了适用边界。主要不足在于对批相关性前提的依赖、大 batch 下的收益衰减、以及实验规模（单机单 SSD、基线数量）的限制，但这些不影响其作为"面向智能体负载重构检索后端"这一方向的开创性价值。
