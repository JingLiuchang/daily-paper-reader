## ABSTRACT 

Vector search has become a database operator with many physical implementations: different index families, build-time and search-time parameters, and compressed or disk-resident variants. Each trades cost against fidelity , the fraction of a query’s exact top-𝑘 

nearest neighbors that a configuration returns. Deployments never-theless choose one configuration offline and use it for every query, so they are sized for their hardest queries and overpay for the rest. On a 5.8M-item LAION benchmark with four embedding models, running each query on the cheapest configuration that suffices for it would roughly halve the cost in a typical setting. Exploiting this requires predicting each configuration’s fidelity before running it, which is hard because fidelity is defined by the very exact search that approximate indexes avoid. Relational optimizers solve the analogous problem for cardinality with offline synopses; we pro-pose one for vector search. A fidelity synopsis divides the embedding space into cells around a set of landmarks and records, for every cell and configuration, how often that configuration met a fidelity target on a sample of queries. At query time, one nearest-landmark lookup yields a calibrated estimate for every configuration, and an optimizer chooses configurations so that the workload misses the target no more often than its requirement allows. We test the two premises the synopsis relies on, that fidelity varies smoothly across the embedding space and that its loss is specific to each configuration. Held to the same requirement a static deployment is built to meet, synopsis-guided selection lowers cost in all 16 combinations of model and query direction, to a median of 0.72 ×

the static deployment, with a batched lookup of 21–32 𝜇 s per query. The saving persists against the best static choice among the same indexes, and within a single index at no extra memory. 

## 1 INTRODUCTION 

Dense vector representations have become the common currency of search. Text retrievers such as DPR [21] and ColBERT [22] map queries and documents into a shared embedding space, and con-trastive vision–language models such as CLIP [38] and SigLIP [49], together with more recent multimodal embedders [28, 47], do the same across images, text, and visually rich documents, so that a text query can retrieve images and vice versa. In all of these set-tings, answering a query means finding its nearest neighbors in a large collection of vectors. Exact search compares the query with every vector and quickly becomes too slow; approximate nearest-neighbor (ANN) indexes such as HNSW [32], IVFPQ [9, 17], and O-IVFPQ [11] return most of the true neighbors at a fraction of the cost. The same indexes underpin retrieval-augmented genera-tion [26].

Vector search has consequently moved into database systems. Purpose-built vector databases such as Milvus [43], analytical en-gines such as AnalyticDB-V [46], and extensions such as pgvec-tor [1] for PostgreSQL treat similarity search as a query operator; VBase [50] and ACORN [37] study how it composes with relational predicates, and [35] surveys the landscape. These systems offer many physical implementations of the same operator: a collection can be indexed with different index families, each with build-time parameters (graph degree, number of partitions, code length) and search-time parameters ( efSearch for HNSW, nprobe for IVF in-dexes), kept in memory or compressed and placed on disk [8, 24]. Each choice trades latency, memory, and energy against fidelity , the fraction of a query’s exact top-𝑘 nearest neighbors that the chosen 

configuration (an index family with its parameter values) actually returns. Semantic query processing systems such as LOTUS [36] and Palimpzest [30] go further and compose retrieval with LLM-based filters, maps, and joins in declarative pipelines that are optimized for cost and quality; related systems process multimodal data under ac-curacy budgets [18] or optimize document-processing pipelines [41]. In these systems and in vector databases alike, however, the vector-search operator itself is executed in one fixed way. A configuration is chosen when the collection is indexed, typically by tuning for average recall on a sample workload, and every query then runs under it. The search-time parameters are exposed, but as session-or collection-level settings; no component chooses them per query. In relational terms, the operator has several access paths but no optimizer that chooses among them. A fixed configuration is costly because queries differ in how hard they are to approximate. Yet for every model, most queries would meet the target on a configuration costing at most a third as much, and running each query on the cheapest configuration that suffices for it would cost less than half as much as the static plan. Early-termination methods address part of this problem. LAET [27] learns to predict, per query, when a search can stop, and DARTH [5] terminates each search once a declared target recall is predicted to be met. Both adapt how long a search runs within an index that has already been chosen, and both can only stop a search early: they cannot help when the chosen index cannot reach the target at all, and DARTH explicitly assumes that it can. In our measure-ments this assumption often fails. Even the most accurate HNSW configuration in our catalog reaches a fidelity of 0.7 on only 69% of OpenCLIP image-to-text queries, and for some text-to-image queries no configuration reaches it at all (Table 1, column “none”), consistent with the observation that cross-modal queries fall outside the distribution an index is built over [7, 29]. Measures of query hardness, such as local intrinsic dimensionality [4] and Steiner-hardness [45], describe how difficult a query is, but they are not calibrated estimates of fidelity under a specific configuration and cannot tell an optimizer which configuration will suffice. What is missing is a way to predict, before running anything, how each can-didate configuration will perform on a given query. This is hard for a basic reason: fidelity is defined relative to the exact top-𝑘 , which is precisely what approximate indexes exist to avoid computing. 

Our approach. Relational optimizers face the same problem when choosing among access paths: they estimate each plan’s output size from synopses, such as histograms, that are built offline and consulted at plan time. We propose such a synopsis for vector search, which we call a fidelity synopsis (Figure 1). It divides the embedding space into cells around a set of landmarks , representative points obtained by clustering the corpus. Offline, a sample of queries is run once through exact search and through every configuration in the catalog, and for every pair of cell and configuration the synopsis records the distribution of fidelity among the sample queries in that cell. At query time, the query’s nearest landmark identifies its cell, and the synopsis gives, for every configuration at once, the estimated probability that it meets the fidelity target, before any configuration is run. An optimizer then runs each query on a cheap configuration where that probability is high and on a more reliable one where it is low, so that the workload as a whole misses the target no more often than its requirement allows. Exact search is paid once, offline, on the sample. The synopsis rests on two premises, which we state and test rather than assume. The first is smoothness : fidelity varies slowly enough across the embedding space that a cell’s statistics represent the queries that fall into it. The second is configuration specificity :how the local geometry of the data translates into lost fidelity differs between index families, since graph navigation and quantization fail in different ways, so the synopsis must keep separate statistics for every configuration.

• We identify per-query choice of ANN configuration as an optimization opportunity and quantify it across four embed-ding models, nine configurations, and four combinations of query and corpus modality: serving the same queries as a static plan, the per-query optimum costs a median of about half as much (Section 5.1). 

• We cast pre-execution fidelity estimation as the vector-search analogue of cardinality estimation and propose the fidelity synopsis, which stores 𝑂 (𝐾 (𝑑 + 𝑚𝐵 )) numbers for

## 2 PRELIMINARIES 

This section fixes the setting and notation, defines fidelity, and states the plan-selection problem. Table 2 summarizes the notation. 

## 2.1 Corpus, Models, and Queries 

A corpus 𝐶 is a collection of items, each an image, a text, or both. An embedding model 𝑀 maps items and queries of either modality into a shared vector space, in which similarity is measured by a fixed function; in our experiments, embeddings are L2-normalized and compared by Euclidean distance, which ranks items exactly as cosine similarity does. Each model induces its own embedding space and hence its own nearest neighbors, so everything below is defined for a single model, which we leave implicit. A query 𝑞 is an image or a text, embedded by the same model as the corpus. Searching a corpus of one modality with a query of one modality gives four query directions : image-to-image (i →i), text-to-text (t →t), image-to-text (i →t), and text-to-image (t →i). The first two are uni-modal , the last two cross-modal . The distinction matters because an approximate index is built over the distribution of the corpus vectors. Uni-modal queries come from roughly that distribution; cross-modal queries often do not, because contrastively trained models place the two modalities in partly separated regions of the embedding space [29], so a query of one modality may lie far from the items of the other [7]. The extent of this separation varies across models. We call a pair of model and query direction a 

setting .

## 2.2 Index Families and Configurations 

Approximate nearest-neighbor (ANN) indexes avoid comparing a query with every item, at the price of sometimes missing true neighbors. We consider three widely deployed index families, which approximate search in different ways and therefore lose accuracy for different reasons. 

HNSW. HNSW [32] builds a multi-layer proximity graph over the corpus vectors and answers a query by greedy best-first tra-versal, keeping a candidate list of size efSearch . Its build-time parameters are the graph degree 𝑀 and efConstruction . HNSW keeps full-precision vectors, so its losses come from navigation: the traversal can stop in a region that does not contain all true neighbors, particularly for queries far from the data the graph was built on [7, 45]. 

IVFPQ. IVFPQ [9, 17] partitions the corpus around 𝑛 list centroids and compresses each vector with product quantization into a short code. A query probes the nprobe partitions whose centroids are closest to it and ranks their contents by approximate distance. It loses accuracy in two ways: true neighbors may lie in partitions that are not probed, and quantization may misorder those that are. 

O-IVFPQ. O-IVFPQ applies a learned rotation (OPQ [11]) before product quantization, which reduces quantization error for a given code length; otherwise it behaves like IVFPQ. 

Configurations, catalog, and cost. A configuration 𝐴 is an index family together with values for its build-time and search-time pa-rameters. A catalog A = {𝐴 1, . . . , 𝐴 𝑚 } is the set of configurations available for a corpus and model. Configurations that differ only in search-time parameters share one built index; all others need separate indexes. Each configuration has a per-query cost 𝑐 (𝐴 ),such as its mean search latency on a given platform. Cost depends on the model, for instance through the embedding dimension, so the cost order of a catalog can differ between models. Memory is a per-index cost and is reported separately. 

## 2.3 Fidelity 

Let Top-𝑘 KNN (𝑞 ) be the 𝑘 items of 𝐶 nearest to 𝑞 , computed by exact search, and Top-𝑘 𝐴 (𝑞 ) the 𝑘 items returned by configuration

Fidelity is what the ANN literature calls recall@ 𝑘 against exact search; we use a separate name to distinguish it from recall against human relevance judgments. It isolates the loss caused by approxi-mation: the model determines which items are nearest, and fidelity measures how many of them a configuration recovers. Computing it requires the exact top-𝑘 , which is affordable offline for a sample of queries but is exactly what approximate indexes avoid at query time. A configuration is dominated if another configuration is no more expensive and has at least its mean fidelity, with one of the two strictly better, for the same model and query direction. A dominated configuration is never the better choice for the workload as a whole, but it can still be the cheapest configuration that meets a target on individual queries.

## 3 THE FIDELITY SYNOPSIS 3.1 Overview and Intuition 

The fidelity of a configuration on a query is determined by the geometry of the corpus around the query: how densely its true neighbors are packed, how far they lie from it, whether they fall within one IVF partition or straddle several, and how well connected the part of the HNSW graph that contains them is. Two queries that land close to each other in the embedding space largely share these surroundings, and often many of their true neighbors, so we expect them to fare similarly under a given configuration. This suggests estimating fidelity by location. We divide the em-bedding space into regions and record, for each region and each configuration, how that configuration performed on a sample of queries that fell into the region; a new query is located and the record of its region is read off. This is the idea of a histogram in a relational optimizer, which records statistics per bucket of a col-umn’s domain so that the selectivity of a new predicate can be read off without scanning the table. Here the buckets are regions of the embedding space, and the statistic is fidelity. hnsw_low ivfpq_low

Two properties make this more than a density estimate. First, the statistics are measured, not modeled: they capture whatever com-bination of density, partitioning, and graph structure determines fidelity in a region, without our having to know which. Second, they are kept separately for every configuration, because the same region can be easy for one index family and hard for another: a dense region whose neighbors straddle partition boundaries can be hard for IVFPQ and easy for HNSW, and a sparse region far from most data can be the reverse. The approach rests on two premises, which Sections 5.2 and 5.3 test directly: 

• Smoothness : fidelity varies slowly enough across the space that the sample queries in a region represent the queries that will fall into it later. This is least plausible near the boundary between regions and for queries far from all data, such as cross-modal queries under models that separate the modalities strongly. 

• Configuration specificity : the same region can have very different fidelity under different configurations, so statistics must be kept per pair of region and configuration. The synopsis is built once per model in an offline stage and consulted once per query in an online stage (Figure 1). Only the offline stage uses exact search, and only on a sample of queries.

Since the estimates depend only on the cell, the rule’s choice is fixed per cell and can be precomputed, so Step 3 reduces to a table lookup. The rule generalizes the static plan. With a single landmark (𝐾 = 1), every query falls into the same cell and receives the same configuration: the cheapest one whose violation rate on the sam-ple meets the requirement, which is the static plan. With more landmarks, the choice varies across cells: cells where cheap con-figurations suffice are served cheaply, and cells where they do not are served by costlier ones. Simpler rules. Section 5.4 compares the budget rule with two simpler ones. The mean rule picks the cheapest configuration whose estimated fidelity ˆ 𝐹 reaches 𝜏 , and the one with the highest estimate if none does; it ignores how fidelity is spread within a cell. The

## 4.2 Embedding Models 

We use four open-weight embedding models (Table 3), chosen to differ in properties that affect approximate search: their architec-ture (SigLIP2 [42] and OpenCLIP [10] are contrastively trained dual encoders, Jina-v4 [13] and Qwen3-VL [28] embedders built on vision–language models), their dimension, which affects the cost of every configuration and of the synopsis lookup, and how strongly they separate the two modalities, which determines how far cross-modal queries lie from the corpus they search [29]. Every structure (indexes, exact neighbors, landmarks, synopses) is built separately for each model; using four models tests whether our conclusions hold across independently built embedding spaces. 

## 4.3 Configuration Catalog 

For each model, we build three configurations of each index fam-ily, low , moderate , and high , giving nine configurations (Table 4), with FAISS [19] 1.15.1 (official cuVS build, with AVX2). The three tiers of a family differ in their build: HNSW in graph degree and 

efConstruction , the IVF families in code length. They were cho-sen by a parameter sweep on a 50,000-vector sample to reach mean fidelity bands of 0.65–0.75 (low), 0.75–0.85 (moderate), and at least 0.85 (high), averaged over the two directions an index serves; the search parameter was then set per model at full scale, on 5,000 con-struction queries. At full scale every IVF-family tier lies in its band, but hnsw_low lies below its band for every model. Three tiers per family give a choice between cheap and expensive configurations both within and across families, while keeping the catalog small enough to run every configuration on every construction query. Reaching the bands requires nprobe values of 2,048–4,096 for SigLIP2 and OpenCLIP but only 16–256 for Jina-v4 and Qwen3-VL. For SigLIP2 and OpenCLIP, every IVF-family configuration is therefore several times as expensive as hnsw_low , and most of them are dominated; for Jina-v4 and Qwen3-VL, the low and moderate IVF tiers cost between hnsw_low and hnsw_mod . No configuration is removed, since a dominated configuration can still be the cheapest sufficient one for individual queries. ## 4.4 Cost Measurement 

All costs are measured on dedicated nodes with an AMD EPYC 7763 processor (128 logical CPUs, 64 used) and 1 TB of RAM, with all indexes in memory; exact search and 𝑘 -means run on NVIDIA A100-SXM4-80GB GPUs. We measure two regimes: single query ,one query at a time on one thread, and batched , batches of 4,096 queries on 64 threads. Every measurement uses the same 5,000 queries drawn at random from 𝑄 test , after an untimed warm-up of 500 queries. In the batched regime, passes over the sample are repeated until at least 20 s and three passes have been timed, and we report the median pass; in the single-query regime, we report the mean and the 99th percentile. The cost 𝑐 (𝐴 ) of a configuration is its mean per-query latency for the given model and direction. The lookup cost 𝑐 est is timed with the same harness, queries, batch size, and number of threads, in a separate run on the same type of node. All headline results use the batched regime.

## 4.7 Statistical Analysis 

With 341,071 held-out queries per setting, almost any difference is statistically significant, so we lead with effect sizes and confi-dence intervals and use hypothesis tests as supporting evidence. We compute 95% bootstrap confidence intervals with 1,000 resamples; since queries in the same cell share their estimate, we resample cells rather than individual queries. Each comparison uses a paired test suited to its outcome: the Wilcoxon signed-rank test on per-query squared error for estimation error (synopsis against global average in RQ2, keyed against shared synopsis in RQ3), the same test with Pratt’s handling of zero differences for shortfall (RQ4), and McNemar’s test on per-query outcomes for violations (RQ4). Within each family of tests, 𝑝 -values are corrected across settings with the Benjamini–Hochberg procedure at a false discovery rate of 𝑞 < 0.05. 

Robustness. Over three seeds of the landmark clustering, at 𝐾 =

10 ,000 and 𝜏 = 0.7, the standard deviation of skill, Brier skill, relative cost, and violation rate is small in every setting (at most 0.008 for skill and 0.010 for Brier skill, 0.03 for relative cost, and a quarter of a percentage point for violation rates), so no conclusion depends on the seed.

## 5.1 RQ1: How much can per-query plan selection save? 

Before evaluating the synopsis, we measure the opportunity it targets: how much cheaper a workload would be if every query ran on its cheapest sufficient configuration. Table 7 reports, for each setting at 𝜏 = 0.7, the static plan, how the held-out queries are distributed by the cost of their cheapest sufficient configuration, and the cost of the per-query optimum. We use the matched optimum, which serves at least every query the static plan serves and is therefore the like-for-like comparison; the unconstrained optimum also pays for queries the static plan misses, and can cost more. 

The opportunity is large in most settings. At matched service, per-query selection would lower cost in every setting, and to about half of the static plan in a typical one. The settings fall into three groups (bold and grey in Table 7). ## 5.3 RQ3: Must the synopsis be kept per configuration? 

The configuration-specificity premise says that the same region can be easy for one configuration and hard for another, so statistics must be kept for every pair of cell and configuration. We compare the synopsis with a shared variant that keeps one difficulty value per cell: the average, over configurations, of how far the cell’s mean fidelity lies from the configuration’s global mean. The shared synopsis knows which regions are harder or easier than average, but assumes they are equally so for every configuration. Table 9 reports both per index family. 

Keeping the synopsis per configuration is always better. The keyed synopsis has higher skill than the shared synopsis for every model and index family, with confidence intervals for the difference that ex-clude zero and every per-configuration test significant. The shared synopsis is not useless, since its skill is positive in all but one combi-nation: some regions are harder than others for every configuration alike. But one value per cell captures only part of what the keyed synopsis captures. 

The gap follows the index families. The shared offset averages over all nine configurations, six of which are IVF-family, so it mostly describes how IVF-family configurations behave. For Jina-v4 and Qwen3-VL, the two synopses are therefore close for the IVF families but far apart for HNSW, whose pattern of easy and hard regions differs. For SigLIP2 and OpenCLIP, the gap is large for the IVF families as well: there, HNSW and IVF-family configurations agree much less on which regions are hard (Figure 6), so no single offset fits both. ## 5.4 RQ4: Does synopsis-guided selection reduce cost without missing the target? 

Table 11 compares the static plan with four ways of using the synopsis at 𝜏 = 0.7: the mean rule, the coverage rule, and the budget rule at the static rate and at the requirement. Figure 7 shows, for each setting, the full trade-off between cost and violation rate as the coverage rule’s 𝜌 or the budget rule’s 𝜆 varies. 

Under the requirement, the synopsis lowers cost in every setting. 

Held to the requirement, at most 10% of queries missing the target, the budget rule is cheaper than the static plan in all 16 settings, at a median of 0.72 × its cost, and recovers more than half of the saving that the optimum at the requirement achieves in a typical setting. Its violation rate on the held-out queries stays within the requirement in every setting; in half of them, the upper end of its confidence interval exceeds 10%, by at most a little over one percentage point. The comparison is fair because both selectors face the same requirement: the static plan misses less often than it is allowed to only because a catalog offers few configurations, and the synopsis spends that unused allowance on cheaper configurations where its estimates say they are safe. Figure 7 places each selector on the full trade-off curve, so that the comparison can also be read at any other violation rate. 

At the static plan’s own violation rate, it still saves in most settings. 

Held to the lower violation rate the static plan actually incurs, the budget rule has less room. Where that rate is reachable on 𝑄 (14 settings), it meets it on the held-out queries and is cheaper than the static plan in 12, by at least 8% in 10. It recovers a smaller share of the matched optimum’s saving, about a fifth in a typical setting. 

The simpler rules fall short. The mean rule is cheap only because it misses often: a cell mean at the target leaves many of the cell’s queries below it, and the rule misses the target on more than 10% of queries in most settings (italic). The coverage rule controls misses, as its calibration predicts, but not cost: requiring coverage 𝜌 in every cell rather than over the workload moves cells where the static plan’s configuration falls short to costlier ones, and it costs more than the static plan in nine settings (grey). Against the mean rule, its per-query shortfall is significantly lower in every setting (Wilcoxon–Pratt, Benjamini–Hochberg 𝑞 < 0.05), mostly because it misses far fewer queries; the queries it does miss fall less far below the target in half of the settings ( †). 5.4.1 Does the saving need the full catalog? Per-query selection requires every configuration it may choose to be built and kept in memory. Our nine-configuration catalog occupies 140–376 GB per model, most of it in the three HNSW indexes (Table 13). We ask how much of the saving survives with less, using two smaller catalogs and one larger one: 

• HNSW-only : the three HNSW configurations, still three separately built indexes. 

• Single index : the index of hnsw_high , searched with three values of efSearch . The highest is hnsw_high ’s own; the two lower ones are, per model, the first values of the param-eter sweep at which mean fidelity over the four directions reaches 0.7 and 0.8 ( efSearch of 192 and 384 for SigLIP2, 256 and 1,024 for OpenCLIP, 48 and 96 for Jina-v4, and 64 and 128 for Qwen3-VL). All three share one index, so per-query selection adds no memory. Their costs were mea-sured on one node together with hnsw_high and put on the scale of the main benchmark through it.

The synopsis uses the same landmarks; only the configurations it records change. ## 6 RELATED WORK 

Approximate nearest-neighbor indexes and their tuning. Graph-based indexes such as HNSW [32] and DiskANN [24], and partition-and quantization-based ones such as IVF with product quantiza-tion [11, 17], SPANN [8], and ScaNN [15], cover a wide range of trade-offs between cost and fidelity. Benchmarks and surveys com-pare them by their average recall over a workload [3, 35, 44], and tuners such as VDTuner [48] search index types and parameters for a workload-level target of throughput and recall. All of these choose one configuration for a workload; they produce a better static plan. Our synopsis takes a catalog as given and chooses among its con-figurations per query. The two are complementary: a better-tuned catalog gives the synopsis better options, as the union catalog of Section 5.4.1 shows. 

Adaptive search within an index. Learned adaptive early termina-tion [27] predicts, per query, when a search has found its neighbors, and DARTH [5] terminates a search once a declared target recall is predicted to be met. Both adapt how long a search runs inside an index that has already been chosen, and both need that index to be able to reach the target. Plan selection makes the earlier de-cision, which index and which settings to use, before any search runs, and it can move a query to a different index family when the default one cannot reach the target. The approaches compose: an early-termination method can run inside whichever configuration the synopsis selects. 

Query hardness. Local intrinsic dimensionality [4] and Steiner-hardness [45] characterize how hard a query is for nearest-neighbor search, the latter for graph indexes specifically, and work on cross-modal search observes that queries of one modality lie outside the distribution of the other [7, 29]. These measures explain why some queries are hard, but they are not calibrated estimates of whether a particular configuration will meet a particular target, which is what plan selection needs. The synopsis measures that quantity directly, per region and per configuration; in our experiments, local density alone predicts fidelity much less well (Section 5.2). 

Cardinality estimation and synopses. Cost-based optimizers choose among access paths using estimates of each plan’s output size [40], obtained from synopses such as histograms built offline and con-sulted at plan time [16], and more recently from learned models [23]; the quality of these estimates largely determines the quality of the chosen plans [25]. The fidelity synopsis applies this design to vector search, with cells of the embedding space as buckets and fidelity as the statistic. Unlike selectivity, which is a property of the data and the predicate, fidelity also depends on the physical plan, so the synopsis is keyed by configuration as well as by region. 

Accuracy-aware query processing. A broad line of work trades accuracy for cost under an explicit target: approximate query pro-cessing with error bounds [2], including over multimodal data [18]; cheap filters and model cascades for machine-learning inference [20, 31]; cascades and routing among language models [6]; and optimiz-ers for semantic operators that choose models and plans for cost and quality [30, 36, 41]. Our work brings this view to the vector-search operator itself, with a per-query choice among physical configurations and a workload-level requirement on how often the fidelity target may be missed. 

Vector search in database systems. Vector databases and exten-sions such as Milvus [43], AnalyticDB-V [46], and pgvector [1] expose index types and search parameters, typically as settings for a collection or session [35]. Work on hybrid queries, such as VBase [50] and ACORN [37], chooses how to combine vector search with relational predicates, based on the predicates’ selectivity. To our knowledge, no system chooses the vector-search configuration itself per query from an estimate of its fidelity. Adithya Ramanatha, Sanskar S. Singh, and Maya Ramanath 

## 7 LIMITATIONS AND CONCLUSION 

Limitations. Half of the variation in fidelity lies within cells, so the synopsis captures only part of the per-query optimum’s saving, and less when held to the static plan’s realized violation rate than to the requirement. The comparison at the requirement lets the synop-sis spend an allowance the static plan leaves unused; we report the stricter comparison as well. Building the synopsis requires labeling a large construction sample with every configuration, a one-time cost that is substantial for a large catalog and much smaller for a single index. With an exact scan of the landmarks, the single-query lookup is too slow for high-dimensional models. Finally, the size of the opportunity depends on the catalog: part of it, for some models, comes from how the catalog’s HNSW tiers were built, although the synopsis’s advantage persists against the best static choice among all the indexes we built. 

Future work. Three directions follow directly. A faster nearest-landmark search, such as an approximate index over the landmarks, would make single-query lookups cheap for high-dimensional mod-els. Search-parameter grids chosen per query direction, rather than per model, would remove the coarse steps that limited the single-index catalog. And reducing the labeling cost, by sampling cells adaptively or by transferring a synopsis between catalogs that share an index, would make the synopsis cheaper to build and to keep current as the corpus changes. 

Conclusion. A static ANN deployment must be sized for its hard-est queries and therefore overpays for the rest. We showed that a query’s location in the embedding space predicts how each con-figuration will perform on it, that this prediction must be kept per configuration, and that a compact synopsis of it, consulted with a single nearest-landmark lookup, lets an optimizer choose con-figurations per query while meeting the same requirement as a static deployment, at a median of 0.72 × its cost. The saving persists against the best static choice among the same indexes and within a single index. A fidelity synopsis is to vector search what a his-togram is to relational selectivity estimation: a statistic built once, offline, that an optimizer consults before executing any plan.
