## ABSTRACT 

As a core component of modern RAG systems, approximate nearest neighbor (ANN) search has been extensively studied for decades. In practice, deploying ANN often requires symmetric privacy, where the querier’s query and the database owner’s data must remain hidden from each other, necessitating a secure multi-party computa-tion (MPC) solution. So far, most MPC-based ANN protocols follow a cluster-based approach: they evaluate distances for the query over a large candidate set and rely on heavyweight primitives such as distributed ORAM to hide access patterns. As a result, each search typically requires 𝑂 (√𝑁 ) time. We propose HNSecW , a novel MPC protocol for ANN search that achieves the 𝑂 (log 𝑁 ) search time for the first time. We first study the single-query setting. Starting from HNSW, the state-of-the-art ANN algorithm, we redesign its control flow and data structures to achieve fully data-independent execution. To further achieve logarithmic search time, we employ offline reshuffling and partial database duplication. Furthermore, we extend our protocol to support multiple sequential queries by introducing a “double visited” caching structure that eliminates re-dundant cross-query memory accesses, thereby avoiding per-query online shuffling. In addition, we develop a batch-query protocol that exploits higher parallelism to reduce both round complexity and the circuit’s critical path. Our experiments show that HNSecW 

preserves the high accuracy of plaintext HNSW ( ≥ 90% recall) and delivers over a 20 × efficiency improvement over prior work on million-scale datasets.

## 1 INTRODUCTION 

Efficient approximate nearest neighbor (ANN) search [22] over vec-tor databases is a basic data analytical primitive and becomes a cor-nerstone of modern AI applications such as Retrieval-Augmented Generation (RAG) [27], which enhances Large Language Models (LLMs) by incorporating external knowledge at inference time. So far, designing an efficient ANN algorithm for a large-sized high-dimensional database has been well studied for decades [29, 30, 43]. However, in real-world ANN applications, security and privacy concerns arise [6, 31, 48]. Without a protective protocol, either the querier submits the query in plaintext to the database owner, who executes the ANN algorithm, or the computation is delegated to the querier, which typically requires the database owner to reveal (at least part of) its data to enable search. The former violates query privacy, whereas the latter compromises database privacy. This motivates a symmetric private ANN model that simultaneously protects both the query and the database. We illustrate the need for symmetric privacy through two representative scenarios: 

Example 1.1. In a joint healthcare study, a research institute (querier) prepares a drug trial by querying a hospital’s (database owner) private gene-expression database for similar patient profiles. The hospital returns only the top records allowed by the data-use agreement, and the institute uses them as LLM context to generate a trial plan. During the collaboration, disclosing the query may reveal the institute’s research details; disclosing the hospital’s database and patient data would violate regulations such as HIPAA. Example 1.2. During a cyber incident, a security team (querier) queries a vendor’s (database owner) private threat intelligence data-base for the closest matching attack reports and indicators, and uses the results to identify the threat and respond promptly. Disclosing the query can reveal what systems were hit; if the database is disclosed, it can expose sensitive intelligence sources and customer incidents. 

A naive approach to achieving symmetric privacy is to introduce a trusted third party, such as a cloud provider: both the database owner and the querier submit their plaintext vector database and queries to the third party, which then performs the ANN search and returns only the results to the querier. However, delegating all sensitive information in plaintext to a single, fully trusted entity may violate privacy regulations like GDPR and introduce severe risks of data breaches or misuse. This motivates people to seek cryptographic solutions that can remove the need for trusted third parties. One natural solution is to implement ANN search in the secure multi-party computa-tion (MPC) model [47]. In these solutions, the database owner and the querier secret-share the vector database and queries across multiple servers. The servers then jointly execute the ANN search protocol on these shares. The security of MPC ensures that no sin-gle server can reconstruct any input. Several recent efforts pursue this direction. However, most existing solutions either relax pri-vacy guarantees by assuming a public database [50], or incur high computational overhead [11, 28]. Specifically, the two closest MPC solutions to our setting [11, 28] rely on cluster-based ANN pipelines: the database of size 𝑁 is partitioned into clusters, and the proto-col identifies and searches the clusters most relevant to a query. Their efficiency depends heavily on the number of clusters, which is typically set to √𝑁 to balance cluster selection and in-cluster search costs. As a result, their search time becomes 𝑂 (√𝑁 ) for each query. This quickly becomes impractical at modern database scales, because under MPC, each additional vector access incurs heavy communication, particularly for high-dimensional vectors. Earlier secure 𝑘 NN works [34, 36, 38, 53] target smaller-scale or specialized two-party settings rather than scalable secret-shared ANN. This motivates us to develop a more efficient MPC ANN pro-tocol. The natural idea is to deploy a state-of-the-art hierarchical graph-based ANN algorithm, such as HNSW [32], under the MPC setting. By building a multi-layer graph index over the database, such algorithms enable efficient search: the query starts at the top layer, takes only a few steps per layer, and then moves to lower layers. It is widely accepted that, in practice, these indexes visit only 𝑂 (log 𝑁 ) out of 𝑁 vectors per query in expectation, where 𝑁 

is the database size. However, implementing this hierarchical graph-based search in MPC is very challenging. At a high level, we must make two parts of the algorithm oblivious: (i) the search logic, e.g., when to stop the search, and (ii) the access pattern. The stopping condition in HNSW is highly data- and query-dependent and replacing it with data-independent predicates without careful consideration totally compromises efficiency. For the access pattern, the search process may revisit the same node or vector multiple times, creating highly non-uniform and query-dependent memory accesses. Some naive approaches to hide such redundant access patterns, such as ORAM [18], would incur prohibitive communication overhead. Therefore, this naturally raises a fundamental research question:

Among them, Hierarchi-cal Navigable Small World (HNSW) [32], achieves state-of-the-art query performance for high-dimensional data [32]. The core of HNSW is a multi-layered graph structure G =

{G 0, G1, . . . , G𝐿 −1}, where each layer Gℓ = (V ℓ , Eℓ ) denotes a graph whose nodes correspond to vectors in the dataset D. The layers form a sequence of nested subsets of D: V𝐿 −1 ⊂ V 𝐿 −2 ⊂· · · ⊂ V 1 ⊂ V 0 = D. The number of nodes decreases geometrically from bottom to top, resulting in 𝐿 = 𝑂 (log 𝑁 ) layers. The edges are constructed from the nodes’ underlying vector representations, and each Gℓ serves as an out-degree bound 𝑀 = 𝑂 (1) approximation of a Delaunay graph. This hierarchical graph G is an efficient index for the vector database D. Its design enables a two-phase search strategy: upper, sparser layers support coarse-grained navigation, ensuring high search efficiency, while lower, denser layers provide fine-grained refinement, ensuring high search accuracy. For query 𝑞 ⃗∈ R𝑑 , HNSW starts at a random entry point in the top layer G𝐿 −1. Each layer search locates the locally closest node to 𝑞 ⃗ , which becomes the entry point for the next lower layer. After searching the base layer G0, the algorithm returns the 𝑘 nearest neighbors of 𝑞 ⃗ from all visited nodes. To implement this idea, at each layer the search maintains three data structures: a candidate set 𝐶 ,which stores potential nodes for further exploration; a result set 𝑊 ,which stores the closest nodes found so far, where |𝑊 | = ef with 

ef = 1 for non-base layers and ef = 𝑂 (𝑘 ) for the base layer; and a visited set 𝑉 , which records all visited nodes to prevent revisits. All these data structures are initialized with the entry point 

ep , and the search then proceeds iteratively. At each iteration, we extract the nearest candidate 𝑐 from 𝐶 , explore each unvisited neigh-bor 𝑒 of 𝑐 , and add them to 𝑉 . If 𝑒 is closer to 𝑞 ⃗ than the farthest node in 𝑊 , it is inserted into both 𝐶 and 𝑊 , and 𝑊 is kept at size at most 

ef . The search terminates when no candidate in 𝐶 is closer to 𝑞 ⃗ than the farthest node in 𝑊 , or when 𝐶 becomes empty. Algorithm 1 gives the detailed procedure. We abstract HNSW into three key components: the search logic flow , the data structures , and the graph and vector access . The logic flow specifies how the search proceeds within each layer. In each step, it moves to the nearest candidate node and then explores all its neighbors. The search stops when no candidate is closer to the query than the current results. The data structures support this process. At each layer, the algorithm maintains three sets: a candidate set 𝐶 , a result set 𝑊 , and a visited set 𝑉 . Finally, the logic flow interacts with the underlying graph index and vector database. For each candidate 𝑐 , the search first accesses the graph index to retrieve its neighbor list, then accesses the vector database to obtain these neighbors’ vectors for distance computation. 

## 2.4 Secure Multi-Party Computation 

Secure multi-party computation (MPC) enables multiple parties to jointly compute a function over their private inputs while only re-vealing the output to designated parties [47]. We use secret-sharing MPC protocols where, for each intermediate value 𝑥 , all parties hold its secret sharing denoted as ⟦𝑥 ⟧. The security ensures that the ad-versary cannot learn the value even when corrupting some number of parties as allowed by the threat model. Our system treats MPC protocols as black boxes; thus, we describe computation directly over secret shares. In particular, we use ⟦𝑥 ⟧ + ⟦ 𝑦 ⟧ and ⟦𝑥 ⟧ × ⟦ 𝑦 ⟧

to denote addition and multiplication in MPC over secret-shared values. Typically, given network bandwidth BW and round-trip time RTT , MPC protocols follow this online latency model: 

𝑇 online ≈ Round · RTT + Communication BW + Computation .

Here, Computation is each party’s local, non-interactive work and is often almost free. Communication is the total data exchanged and scales linearly with the multiplication gate count. Round is the number of sequential interaction steps, determined by the circuit’s multiplicative depth. 

Making Algorithms Oblivious. Under MPC, oblivious execution has three requirements: (1) Logic flow. For fixed public parameters, the algorithm follows the same sequence of operations. For example, each loop runs for a fixed number of iterations. (2) Data structures. For fixed public parameters, intermediate data structures have the same sizes and update schedule. (3) Data access pattern. For fixed public parameters, physical-address sequences are indistinguishable across private inputs. 

Oblivious Access in MPC. Among these requirements, oblivious data access has been widely studied as a general primitive. MPC pro-tocols based on secret-sharing can typically support any circuit, but random accesses are expensive to represent as circuits. To support private accesses on large arrays without incurring a cost linear to the array, one would need to use an Oblivious RAM (ORAM) [18] by executing the ORAM client in MPC [19]. This protocol is also called Distributed ORAM (DORAM). Given a secret-shared array ⟦𝑣 ⃗⟧ and secret-shared index ⟦𝑖 ⟧, DORAM enables parties to jointly compute 

⟦𝑣 ⃗[⟦ 𝑖 ⟧]⟧ (the secret-shared value at secret-shared position) with-out revealing the index or the value to any party. DORAM has been optimized in different ways, including circuit-based minimization (e.g., [44]) and protocol-level adaptation (e.g., [14]). Although the most efficient construction can achieve 𝑂 (log 𝑁 ) communication overhead [39], DORAM still incurs an 𝑂 (𝑁 ) computational cost. Moreover, DORAM accesses are stateful and often sequential, mak-ing batched accesses difficult to parallelize. Therefore, rather than directly adopting generic DORAM in our MPC protocol, we propose a specialized algorithm to implement an oblivious access pattern.

## 3.2 Single-Query 

Even when all vectors and their distance to the query are kept secret, a single HNSW query is not oblivious in its control flow, data structures, or graph and vector access patterns, all depending on the underlying graph and query. Achieving obliviousness to prevent leakage requires a dedicated analysis of the performance features that HNSW presents, since a generic method that follows only worst-case conditions would introduce prohibitive overhead. In our protocol, we design customized optimizations to make each part oblivious by taking advantage of its unique features. For a single query, we traverse each layer without revealing the access pattern. At every layer, we use our oblivious data structure to maintain the search state, and we terminate the traversal using a tailored termination condition that prevents information leakage. We outline the key ideas here, with full details in Section 4. 

• Control flow. We eliminate data-dependent stopping condi-tions by replacing them with a fixed iteration bound derived from a detailed analysis of HNSW’s stopping behavior, ensuring oblivious-ness with only negligible recall loss (Section 4.1). Although there is no theoretical bound on the iterations, we found that in the specific context of RAG, we could set a tight upper bound on the number of iterations without degrading the end-to-end performance. 

• Data structure. We observe that both the candidate set and the result set exhibit a monotonic exclusion property: once a node is excluded, it will not be included in these sets again. Using this monotonicity, we design an oblivious data structure for both sets that keeps them at a fixed size and removes farther nodes through fixed-size tail truncation after oblivious sorting (Section 4.2). 

• Graph and vector access pattern. We use the fact that HNSW naturally avoids revisiting a node more than once per layer. To further reduce redundant access across the layers, we assign each layer an independently shuffled graph and vector tables so every address is accessed at most once, yielding fully oblivious access patterns. 

## 3.3 Multiple-Query 

Extending the single-query protocol to multiple queries introduces a fundamentally new challenge: different queries may revisit the same graph node and its associated vector. Hiding these repeated visits would require reshuffling the graph and vector tables after every query. However, such per-query reshuffling is impractical in an online setting due to the significant latency it entails. To address this, we rely on the insight that once data has been accessed, it can be cached and reused across queries rather than accessed repeatedly. We propose to use two global cross-query visited structures, one for graph neighbor lists and one for vector contents. These structures serve as a secure shared cache: once any query retrieves a node or vector, it is stored in the global visited array. Subsequent queries check this array first and reuse the cached data. As a result, each graph or vector access first scans the cache and then performs a real or dummy data-access step. Under this design, every node and vector is accessed at most once from the underlying shuffled tables globally, while subsequent revisits are served through oblivious cache scans. Combined with one-time random pre-shuffling, this keeps the overall access pattern oblivious; see Section 5. 

## 3.4 Parallel-Enhanced Batch Model 

Furthermore, we consider how the oblivious HNSW search can be executed in parallel. The single-query protocol already exhibits high parallelism, but its multiple-query extension is designed to process the 𝑈 queries sequentially, giving a linear circuit depth of 𝑂 (𝑈 ). In a batch setting where many queries are available si-multaneously, it is natural to ask whether the computation can be reorganized to reduce this depth to better exploit parallel execution. As in the multiple-query setting, the fundamental challenge is to avoid accesses to the same nodes and vectors across queries. A naive approach is to cache every accessed element (neighbor lists and vectors), as in the sequential protocol. But in the batch setting, such a large cache is unnecessary. Our key insight is that, because all queries proceed in synchronized iterations, we do not passively wait for cache hits and reuse; instead, we force 𝑈 · 𝑀 accessed vectors to be evaluated against 𝑈 queries: if a query later needs that vector, it can skip the inner path; if not, the extra evaluation does not affect correctness. This eliminates the need for a massive cache and naturally prevents redundant accesses. As a result, the batch-query protocol achieves a depth of 𝑂 (log 2 𝑈 +log 𝑁 ), coming from the oblivious duplicate removal of the 𝑈 · 𝑀 neighbors per iteration plus the 𝑂 (log 𝑁 ) HNSW layers. 3.5 Implementation & Experiment Summary

## 4 SINGLE QUERY PROTOCOL 

As discussed in Section 2, we decompose HNSW search into three components: the search logic flow, the data structures, and the graph/vector access patterns. In this section, we briefly outline how to make each component oblivious. Section 4.1 makes the control flow data-independent by replacing the original data-dependent stopping conditions with a fixed iteration bound. Section 4.2 re-designs the visited, candidate, and result structures as fixed-size arrays with uniform update rules. Section 4.3 ensures oblivious graph and vector access by avoiding repeated retrievals through per-layer reshuffled tables. Finally, Section 4.4 assembles these build-ing blocks into the complete oblivious single-query protocol. 

## 4.1 Making Logic Flow Oblivious 

We first make HNSW’s search logic flow oblivious. At each layer, original HNSW iteratively finds the nearest candidate node and ex-plores all its neighbors. The logic flow is inherently data-dependent. The first source of data dependence is varying node degrees: exposing this variation would leak information about the graph and query. Fortunately, this dependency is easy to remove. Since HNSW enforces an out-degree upper bound 𝑀 per node, we pad each node’s neighbor list with randomly selected nodes from the same layer to obtain a fixed length of 𝑀 . This padding does not reduce search quality: all real neighbors remain available for selection. The more subtle challenge lies in the termination condition. In HNSW, the search stops when no better candidate remains (line 7-8 in Algorithm 1), or when the candidate set becomes empty (line 4 in Algorithm 1). Both conditions are inherently data-dependent. At first glance, this seems similar to the bounded-degree case, since the original HNSW paper [32] suggests that each layer can be tra-versed in a constant number of hops. One may use that constant as a fixed upper bound and pad execution with dummy searches. How-ever, unlike node degree, this constant is not a worst-case bound; it arises from an expected-case analysis in [32] that assumes each layer forms a perfect Delaunay graph [13]. Real HNSW layers only approximate such structures, so the constant-hop guarantee does not hold in general. In fact, the best-known asymptotic bound for HNSW on arbitrary data is still 𝑂 (𝑁 ). A practical, data-independent iteration bound must therefore be derived from the actual termina-tion behavior. The first termination condition (lines 7–8 in Algorithm 1) trig-gers when the closest candidate can no longer improve the current result set. This can only happen after ef search steps. ## 4.2 Making Data Structures Oblivious 

We next make the data structures of HNSW oblivious. Recall that each layer individually maintains three structures: the visited set 

𝑉 , the candidate set 𝐶 , and the result set 𝑊 . However, the sizes and update frequencies of the three sets are inherently data- and query-dependent during search. We therefore redesign them into oblivious counterparts. 

4.2.1 Oblivious Result Set 𝑊 . The result set 𝑊 is easier to make oblivious than 𝐶 and 𝑉 because original HNSW already bounds its size by ef . The only data-dependent behavior is the conditional insertion rule, i.e., inserting a node into 𝑊 when it improves the current ef results and passes the visited check (line 13 in Algorithm 1). We remove this data-dependent condition by obliviously consid-ering every node for insertion, at a cost of 𝑂 (ef ) per node. 2 Overall, this naive approach costs 𝑂 (𝑀 · ef ) in each iteration. For practical efficiency, we instead insert all 𝑀 elements, apply oblivious sorting, and then reduce the size back to ef , incurring only 𝑂 (ef log 2 (ef )) 

complexity. Since log 2 (ef ) is much smaller than 𝑀 in our setting, this approach outperforms the naive alternative in practice.

4.2.2 Oblivious Visited Set 𝑉 . The visited set 𝑉 records explored nodes to prevent later revisits. In the original HNSW, 𝑉 is a dynamic set whose size and insertion pattern are both query- and data-dependent, since nodes are inserted only when first encountered and their growth is unpredictable. To eliminate this dependence, we observe that 𝑉 can safely contain duplicate nodes. We therefore replace the set, whose size is unpredictable, with a list whose size increases by exactly one after each exploration. More precisely, each iteration appends all 𝑀 neighbors, regardless of whether they have appeared before, so that 𝑉 contains exactly 𝑀 · 𝑇 + 1 entries after 𝑇 iterations. A full linear scan of this list performs a visited check at a cost of 𝑂 (𝑀𝑇 ), which is scalable and independent of 𝑁 .

4.2.3 Oblivious Candidate Set 𝐶 . The candidate set 𝐶 stores the nodes awaiting expansion and is also a fully dynamic set. In the original HNSW, its size is inherently data-dependent: each iteration extracts one node from the set but may insert zero, a few, or up to 

𝑀 new nodes. The insertion condition is also data-dependent, since neighbors are added to 𝐶 only when they pass the visited check and could improve the result set 𝑊 (line 10, 13 in Algorithm 1). To make 𝐶 oblivious, we leverage the fixed iteration 𝑇 established in Section 4.1. Since at most 𝑇 candidates will be extracted, entries beyond the top-𝑇 positions cannot be used and need not be retained. We therefore replace the dynamic set with a fixed-length array of size 𝑇 . In every iteration, all 𝑀 neighbors, whether real or dummy after the visited check, are appended to 𝐶 . We then perform an oblivious sort by distance and retain only the top-𝑇 entries. As we discussed earlier, since dummy nodes carry a maximum distance 

𝑑 max , they always expand to other dummy nodes. They cannot influence the result set 𝑊 even if they are selected after the real nodes are exhausted in 𝐶 . This fixed-size and fixed-update design of 𝐶 eliminates data-dependent behavior while preserving original HNSW’s functionality. 

## 4.3 Making Access Patterns Oblivious 

The HNSW search process involves two types of data access: vector access and graph access. During the search, a node first incurs a vector access where its distance to the query is evaluated. If the node is later selected for expansion (extracted from the candidate list 𝐶 ), it then incurs a graph access to retrieve its neighbor list. A straightforward way to make both accesses oblivious is to store the graphs and the vector database in DORAM. However, this incurs significant overhead, as each access requires 𝑂 (log 𝑁 ℓ ) time. To design a more efficient solution, we recall that achieving obliv-ious access requires two properties: data anonymization, which can be easily achieved through pre-shuffling, and non-repetitive access, where no address is revisited within a query. In this single-query setting, we assume that both graph and vector data have been anonymized through offline reshuffling. Therefore, if each item is retrieved at most once, the access is oblivious. We now analyze where repeated accesses arise and how to avoid them. Within a single layer, both graph and vector accesses are non-repetitive. The visited set prevents revisiting any node, so its neigh-bor list and its vector are retrieved at most once. Across layers, the search may revisit a logical node because each layer builds a separate, increasingly refined neighborhood structure, and the same node provides different information at each layer. So its data may be reused along the search path. For graph access, this causes no address repetition: each layer stores its own graph with inde-pendently reshuffled addresses, so expanding the same logical node in different layers always reads unrelated locations. For vector ac-cess, however, standard HNSW implementations keep all vectors in one global table for space and cache efficiency, so re-evaluating a node across layers hits the same physical address. To avoid this, we assign each layer its own independently reshuffled vector table of size 𝑁 ℓ . Notably, within a single layer, the graph and vector tables are reshuffled independently, so a node’s graph and vector entries occupy unrelated physical addresses, avoiding graph-to-vector tran-sitions by reusing an address. With this per-layer duplication and independent reshuffling, both graph and vector access become fully non-repetitive.

## 5.1 Double Visitor Arrays 

The challenge in the multiple-query setting is that later queries may need to access nodes and vectors that earlier queries already accessed. As noted above, the single-query protocol prevents re-peated data access with an array 𝑉 tracking previously accessed nodes. Moving to the multiple-query setting, one straightforward idea is to simply make 𝑉 global, so that each node can be accessed by only one query. However, queries may have overlapping search paths, so simply globalizing 𝑉 would make multi-query HNSW search incorrect. To address this issue, we propose two global cross-query caches recording all nodes and vectors accessed so far. Specifically, we maintain a graph-side visited set 𝑉 G

ℓ and a vector-side visited set 

𝑉 D

ℓ , which store the neighbor information of visited nodes and the contents of visited vectors, respectively. When exploring a node 

𝑣 in graph Gℓ , we first check whether 𝑣 ∈ 𝑉 G

ℓ . If so, the neighbor information of 𝑣 is retrieved from 𝑉 G

ℓ , followed by a dummy graph access. Otherwise, 𝑣 and all its neighbor information are read from 

Gℓ and stored in 𝑉 G

ℓ for future use. After obtaining the neighbor information, we access each neighbor’s vector to compute its query distance. Similarly, for each vector access, we first check 𝑉 D

ℓ . If the vector is already present, it is retrieved from 𝑉 D

ℓ , followed by a dummy vector access. Otherwise, it is loaded from Dℓ and appended to 𝑉 D

ℓ . Moreover, before processing multiple queries, we pre-shuffle both the graphs and the vector databases so that all nodes and vectors, including dummy ones, remain anonymous. More precisely, for each graph access, we first perform a linear scan of 𝑉 G

ℓ . Then, depending on whether the target node is already in the cache, we access either the real node or a dummy node in the graph. Finally, we access 𝑉 G

ℓ again to store the newly retrieved real node or a dummy entry. Notably, we generate 𝑈 × 𝑇 dummy nodes so that each graph access can use a different dummy node. Similarly, for each vector access, we first scan 𝑉 D

ℓ , then access either a real or dummy vector, and finally store it in 𝑉 D

ℓ .

5.1.1 Security Sketch. The multi-query protocol extends the single-query protocol with cross-query caches for repeated graph and vector accesses. We explain why this extension remains oblivious. To hide whether a lookup hits a cache, both cases follow the same fixed schedule. With this design, the control flow is identical for ev-ery graph access. Regarding the access pattern, all nodes, including dummy nodes, are accessed at most once, thereby guaranteeing non-repetitive access. In addition, the graph is pre-shuffled to ensure data anonymization. By the same argument, these vector accesses are also non-repetitive and data-anonymized, and hence oblivious. Thus, the multi-query protocol securely realizes 𝑈 sequential in-vocations of the ideal functionality in Figure 2. The full proof is in the extended version [49]. 

5.1.2 Complexity Analysis. For 𝑈 queries, at the base layer we keep ef = 𝑂 (𝑘 ) and run 𝑇 = 𝑂 (𝑘 ) iterations per query. Each itera-tion performs: 𝑀 = 𝑂 (1) distance evaluations in R𝑑 ; 𝑀 oblivious scans over 𝑉 D and 𝑉 G of size 𝑂 (𝑈 𝑘 ); and two oblivious sort net-work evaluations over 𝐶 and 𝑊 , each of size 𝑂 (𝑘 ). Thus, both communication and local computation costs at the base layer are 

𝑂 (𝑈 𝑘𝑑 + 𝑈 𝑘 2 log 2 𝑘 + 𝑈 2𝑘 2), and for the 𝑂 (log 𝑁 ) non-base layers with ef = 1 they are 𝑂 (( 𝑈 𝑑 + 𝑈 2) log 𝑁 ). Therefore, the multiple-query protocol has total communication and local computation costs 𝑂 (︁ 𝑈 𝑘 (𝑑 + 𝑘 log 2 𝑘 + 𝑈 𝑘 ) + ( 𝑈 𝑑 + 𝑈 2) log 𝑁 )︁ .

## 6 BATCH QUERY PROTOCOL IN PARALLEL 

The preceding multiple-query protocol processes queries sequen-tially. We further consider the batch setting, where 𝑈 queries arrive together. We propose a batch protocol that processes the 𝑈 queries in parallel, reducing the round complexity from 𝑂 (𝑈 ) to 𝑂 (log 2 𝑈 ).The key idea is to share vectors fetched by any query across all 

𝑈 queries, so every query steps forward together by updating its own 𝐶 and 𝑊 . Each iteration has two stages. First, the protocol obliviously deduplicates the nearest candidate from each query’s 

𝐶 , replaces duplicates with dummies, and issues 𝑈 distinct graph accesses. Second, it obliviously deduplicates the 𝑈 · 𝑀 returned neighbor IDs and fetches 𝑈 · 𝑀 vectors. Each query evaluates its distance to all 𝑈 · 𝑀 fetched vectors, regardless of which query requested each vector. The batch therefore performs 𝑈 2 · 𝑀 dis-tance evaluations in parallel. These distances update the query’s own candidate set 𝐶 and result set 𝑊 . The protocol records all fetched vectors in one global visited array 𝑉 shared by all queries. Each of the two oblivious deduplication steps sorts 𝑂 (𝑈 ) elements, requiring an oblivious sort network of depth 𝑂 (log 2 𝑈 ), which de-termines the per-iteration round cost. The full algorithm and the round-complexity proof appear in the extended version [49].

## 7.1 Experimental Setup 

MPC Backends. HNSecW can be instantiated with any semi-honest MPC protocol tolerating 𝑡 corruptions among 𝑠 servers. We evaluate two common configurations: 

• Semi-honest 2PC ( 𝑠 = 2, 𝑡 = 1). Our 2PC uses ABY’s semi-honest mixed-protocol backend [12]. Arithmetic sharing handles distance computation. Boolean sharing handles visited checks. Yao’s garbled circuits handle comparisons, sorting, and candidate updates. ABY provides secure conversions among these representations. 

• Semi-honest 3PC ( 𝑠 = 3, 𝑡 = 1). Our 3PC uses MP-SPDZ’s semi-honest replicated secret-sharing protocol over a 64-bit ring [25]. 

Hardware and Network Environment. All experiments run on a single server with an AMD EPYC 9554P CPU (64 physical cores, 3.1 GHz) and 565 GB of RAM, where each MPC party runs as a separate single-threaded process. We emulate two networks: a LAN with 4000 Mbps bandwidth and 1 ms RTT (a standard MPC LAN setting [11, 28]), and a WAN with 320 Mbps bandwidth and 50 ms RTT, following typical U.S. East–West latency per cloudping.co 3.

Datasets. We evaluate on 10 widely-used ANN benchmarks [3, 37] (Table 3), spanning 𝑁 ∈[ 6×10 4, 10 9], 𝑑 ∈[ 96 , 960 ], and both ℓ2 and cosine metrics. The selected scale range covers the practical RAG deployment regime. Due to space limitations, the main text re-ports four representative datasets covering both scales (SIFT-1M, GIST-1M, BIGANN-1B, DEEP-100M); results for the remaining six datasets are provided in the extended version [49]. All recall exper-iments use 10 3 queries per dataset and report the 95th percentile.

PANTHER [28] is a notable exception: like our protocol, its search algorithm is fully oblivious. We compare the asymptotic performance of PANTHER’s cluster-based search and our graph search under the same security model. Figure 9 reports PANTHER’s original cost and the adaptation over-head separately. Pacmann [50] is another related graph-based ANN algorithm for query-private search, but it assumes a public database and graph index, with the client retrieving entries through PIR and searching locally in plaintext. ## 8 RELATED WORK 

Approximate Nearest Neighbor (ANN). ANN enables scalable similarity search in high-dimensional embedding spaces where exact 𝑘 NN is often too expensive [29, 30, 43]. Classical methods include tree-based partitioning [5], locality-sensitive hashing [22], and vector quantization [23]. Graph-based indexes, such as HNSW [32] and NSG [17], dominate in practice, building proximity graphs for greedy query traversal. Recent systems extend graph-based ANN with improved indexing and retrieval strategies [24, 42, 52], while vector databases deploy these methods at scale [10, 20, 40]. 

Secure ANN. Prior work considers secure ANN under several threat models. When the database is public but the query is private, Tiptoe [21] searches a small candidate subset selected via clustering, trading accuracy for sublinear bandwidth and latency. Wally [2] fur-ther improves this pipeline’s throughput by batching queries, while Preco [35] reduces communication using two non-colluding servers. Pacmann [50] goes beyond clustering-based ANN methods by build-ing a graph-index under query privacy. When both the database and query are private under a single owner (encrypted outsourcing), Compass [51] directly uses ORAM only to hide the server-side data access pattern, while executing the search logic in plaintext on the client. Instead, HERS [15] scans the encrypted database with FHE at high computational cost. SANNS [11] and PANTHER [28] use se-cure two-party computation between a server owning the database and a client owning the query. SANNS proposes a clustering-based secure ANN with optimized distance computation and top-𝑘 selec-tion, while PANTHER further improves end-to-end performance. In contrast, HNSecW secret-shares the query, database, and index among computation servers and achieves the same logarithmic complexity as the non-private setting. Notably, both SANNS [11] and PANTHER [28] can be adapted to secret-shared inputs. How-ever, both approaches have 𝑂 (√𝑁 ) complexity. Moreover, several early works [34, 36, 38, 53] studied secure 𝑘 NN protocols, but they either target smaller-scale settings or apply only to the specialized secure settings discussed above. 

## 9 CONCLUSION 

We present HNSecW , an MPC ANN protocol with 𝑂 (log 𝑁 ) online time and symmetric privacy for the query and database. It supports single-query, sequential multi-query, and batch-query settings. Fu-ture work includes more efficient secure index construction and dynamic graph updates. Currently, the database owner builds the in-dex locally before queries arrive. For secure offloading, MPC servers can insert the 𝑁 vectors into the graph one by one and reuse our oblivious search to find neighbors. This requires 𝑁 graph searches, 

𝑂 (𝑁 log 𝑁 ) time, and 𝑂 (𝑁 𝑀 ) space for degree bound 𝑀 [32].
