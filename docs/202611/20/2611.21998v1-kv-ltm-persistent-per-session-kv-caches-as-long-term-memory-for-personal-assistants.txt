Abstract 

Personal assistants accumulate months of conversations, but today’s long-term memory stacks put derivation or selection between a question and its evidence. In a system-level comparison on LongMemEval, two commercial assistants scored well below the same model reading the history offline [1] — consistent with, but not isolating, content loss between write and read. We propose KV-LTM: a memory tier storing each session’s raw text plus its KV cache under a fixed reader model, answering by restoring cached sessions and appending the question — comple-mentary to, not a replacement for, retrieval and indexing. Text is the memory of record; the cache is a recompute-free prefill accelerator, degrading gracefully to text. We specify the design — storage record, budget-derived retention, append-only read path, bounded aggregation. We size it analytically: across pinned BF16 full-attention (GQA) and latent-cached MLA configurations, per-token state spans ≈31K–328K bytes (the pinned KDA+MLA hybrid differs: ≈8.1K bytes/token plus a fixed per-session recurrent term), giving ≈0.34–3.6 TB per user-year at a declared 30K-token/day scenario, against ≈49 MB of raw text; per-query cost is modelled as regime-conditional transfer, attention, decode, aggregation, and compute. We define an evaluation protocol needing no persistent-cache implementation for log-ical QA evaluation: per-session prefill emulates valid cache reuse under the same model/input-state contract and ideal arithmetic, with named arms, controlled base-lines, and a preregistered reader-model gate; a separate minimal real-cache replay tests numerical equivalence and measures the cost axis, outcomes not assumed. KV-LTM trades storage for avoided re-prefill compute and write-time fidelity, within a declared retention budget. 

# 1 Introduction & Positioning 

## 1.1 The personal-assistant memory problem 

A personal assistant (PA) agent accumulates months of interactions: preferences stated once, decisions made in passing, constraints given casually. When the user later asks “what did we decide about X?”, the answer depends on evidence the system can still reach. Today’s long-term memory (LTM) stacks differ in what they retain, derive, and select. Extracted-fact memory (e.g., Mem0 [2]) stores LLM-distilled facts; temporal graphs (e.g., Zep/Graphiti [3]) store entities and edges; rolling summaries compress history into running text — these transform content at write time. RAG-style indexing and verbatim archives (e.g., MemPalace [4]) keep the raw text but select a subset 1arXiv:2611.21998v1 [cs.AI] 16 Nov 2026 at read time through a retrieval index; answering without one means re-reading ev-erything. Both paths cost the PA, at write time or at read time. KV-LTM targets this trade-off directly (§1.2). Public QA measurements show the pattern. On LongMemEval, GPT-4o reading the history offline scored 0.918 vs 0.577 for ChatGPT(GPT-4o) and 0.330 for Coze(GPT-4o) online with their memory pipelines, on a 97-question comparison [1, Fig. 4a]. On LoCoMo, long-context and RAG systems remain far behind human accuracy [5]. On the same benchmark, the full-context reader scores J≈72.9 vs 66.9 for Mem0 and ≈61 for the best RAG variant, as reported in Mem0’s own (vendor-authored, ECAI 2025) evaluation under its own protocol [2]. These are system-level comparisons — consistent with, but not isolating, content loss between write and read (§3 develops the quantitative evidence). For orientation, we distinguish four memory modes, not an accuracy ranking or an established taxonomy: L1, live context only , with no memory retained outside it; 

L2, retrieval or derived memory , including indexed verbatim archives, extracted facts, graphs and summaries; L3, full-history text reading , which reads the entire retained history jointly for each question; and L4, the proposed KV-LTM tier , which restores per-session native state to avoid repeated session-text prefill. Systems may combine these modes. Under the §2.2 contract, a restored session read is equivalent to prefilling that same session with the same suffix, not to L3’s joint attention across the whole history (§4.7). In the LongMemEval and Mem0-reported LoCoMo comparisons above, offline or full-context reading scored higher than the selected memory-system baselines [1, Fig. 4a][2]. This is not a universal ordering: Zep’s separate comparison favours its re-trieval system (§3.2, §8.1). KV-LTM targets repeated session-prefill work while retain-ing original text; its storage, transfer and read costs are modelled in §5–§7, and its answer quality remains to be evaluated (§8). 

## 1.2 Thesis: a persistent per-session KV-cache tier 

We propose KV-LTM : a per-session long-term memory tier that stores, for every ses-sion, (i) the raw session text and (ii) the session’s KV cache under a fixed reader model. At query time the system restores cached sessions and appends the question — reading the session’s native activation state without re-prefilling its text. Two properties define the design: • Text is the memory of record. The raw session text is always preserved, in every variant of the design. What is preserved at write time is the full session content as source text; the native cache state differs by architecture class (full-attention/MLA models keep per-token state; hybrid models mix a fixed-size re-current state with per-token MLA state). • KV is a recompute-free prefill accelerator. The cache removes repeated pre-fill of the session text; §7 shows when that saving dominates and when byte trans-fer does instead. The cache is never the only copy: if it is evicted, expired, or invalidated by a model change, the system degrades gracefully to reading the original text. 2GPT-4o offline read (L3) ChatGPT (GPT-4o) (L2) Coze (GPT-4o) (L2)

KV-LTM does not replace indexing, retrieval, or compressed memory. It complements them in two concrete ways, both developed in §4: • (a) Bounded recent evidence-preserving tier. For the recent retention win-dow, KV-LTM answers by reading retained sessions directly — no retrieval index is involved on this reference path. • (b) Verifier/reranker over retrieval candidates. Behind an existing retrieval system, KV-LTM reads the cached KV of the candidate sessions the retriever re-turns — verifying and reranking them against full session content instead of re-prefilling their text. In both roles, the KV tier changes how evidence is accessed, not its fidelity relative to an identical full prefill. Reading the full session avoids dependence on selected or derived views (chunks, facts, summaries); whether that improves answers is mea-sured in §8. The reference path requires no index; the optional hybrid variant adds a pre-load prefilter over text/metadata (§4). The reference tier defers question-directed interpretation of retained session con-tent to read time rather than replacing it with a write-time summary or extracted facts. It does not eliminate compute: canonical prefill occurs at ingestion, and restore, suf-fix processing, decoding and aggregation remain query costs (§7). Its fidelity claim is relative to the same reader prefilling the same session and suffix under §2.2; reten-tion, reader errors, bounded evidence outputs and aggregation still limit end-to-end answers (§8). On this reference path, the reader searches each retained session through atten-tion over its native state rather than through a retrieval index. This is a per-session read, not joint attention over the archive. Selection still occurs through retention (§4.8), bounded evidence aggregation (§4.6), the joint tier (§4.7), and the optional prefilter (§4.5). We propose per-session reading from persistent KV caches as another search tool for personal assistants, complementary to indexes, RAG, grep and generated search code; its practical value is to be evaluated under §8. 

## 1.4 Scope 

• In scope: text available to the reader model, including textual documents the assistant processes. • Out of scope: any claim that visual, table, or audio meaning survives preprocess-ing into text; such transformations are excluded or separately evaluated. Session identification — how raw interaction is segmented into sessions — is a separate problem and is out of scope; we acknowledge it as a dependency (§9).

# 2 Background & Related Work 

## 2.1 KV-cache semantics: what “reuse” means 

In a causal transformer (in standard full-attention designs), each layer caches key/value tensors per token — the KV cache. Computing a session’s cache once and reusing it later avoids re-running prefill over the session’s tokens. Two reuse regimes matter: • Prefix-exact reuse. The cached tokens form an unmodified prefix of the new computation. The new tokens are appended , continuing the cached position in-dices. This is the only regime KV-LTM uses on its reference path. • Non-prefix reuse. Cached segments are fused, reordered, or repositioned: CacheBlend fuses independently computed chunk caches and reports restoring quality by se-lectively recomputing a fraction of the KV rather than reusing everything, with TTFT gains in its tested setup [6]; EPIC reuses caches position-independently [7]; TurboRAG relies on altered masks/positions plus fine-tuning [8]; Prompt Cache reuses modular attention states at schema-reserved positions [9]. These meth-ods change masks, positions, or both, so their reuse is not guaranteed identical to a fresh prefill under the original sequence’s positions and masks; they approx-imate or change the computation. They are related work, not our mechanism. 

## 2.2 The exactness lemma (scoped) 

Statement. Take a session cached by a fixed model, and a question. Restoring the cached session and appending the question is mathematically identical, under ideal arithmetic , to a full prefill of (session ‖ question) — provided: the same complete token prefix (including fixed instructions), the same model weights, continued position indices (cache holds 0..N−1, query takes N..N+Q−1), pinned RoPE base/scaling/max-position, the same attention masks, and the same native cache state. 

Boundaries. (i) Post-hoc quantization or pruning of the cache is a distinct variant; a matching dtype label is necessary but not sufficient for equivalent state evolution. (ii) Real engines use non-deterministic or batch-variant kernels, so practical equality is verified with tolerances by a small real-cache replay (§8), not assumed. (iii) The lemma is per-architecture: exactness under valid reuse gives no inter-architecture quality guarantee (the RoPE condition is itself per-architecture — a hybrid model’s MLA layers may be position-free). ## 2.5 KV-reuse prior art 

Persisting and reusing KV state is established engineering. Cache-Augmented Genera-tion (CAG) [22] precomputes knowledge-prefix KV and appends queries — the nearest prefix-exact prior art. Serving systems built the infrastructure: PagedAttention/vLLM [23], RadixAttention/SGLang [24], CacheBlend [6], CacheGen [25], LMCache [26], Mooncake [27], MemServe [28], EPIC [7], TurboRAG [8], modular Prompt Cache [9], and SSD-backed Tutti [29]. Memorizing Transformers used a kNN memory over in-ternal K/V pairs — a related but distinct mechanism [30]. A recent survey maps the field [31]. 

Novelty. How is KV-LTM different from CAG or a persistent prompt cache? The 

mechanism — a persistent prefix cache — exists. The mechanistic delta: CAG keeps one static corpus prefix that must fit one context; KV-LTM keeps many growing per-session caches, reads them independently, aggregates the answers, and manages them with a retention policy and a text fallback. The contribution is what wraps the mechanism: a per-session retention/eviction policy derived from a PA storage and latency budget, a read/aggregation protocol (append-only per-session reads, bounded source-aware aggregation, text fallback), a PA-scale cost model (bytes/token, TB/year, per-query regimes), and an evaluation protocol that measures the logical read path on LTM benchmarks without an implementation. KV-LTM is positioned as 7policy + protocol + cost model + evaluation — not a new memory primitive.

This chapter specifies the KV-LTM design: what is stored, under which conditions a stored state is valid, how writes and reads work, how answers are aggregated, and how the store is retained, invalidated, and gracefully degraded. Figures 2 and 3 show the write and read flows; §5–§7 then size it. 

## 4.1 Storage record 

Each session is stored as one record: Field Content 

state The session’s native cache state under the reader model: per-token K/V (or MLA latent) for attention layers, plus the fixed-size recurrent state for hybrid layers (§2.3, §5), plus any runtime auxiliary state required for replay — in a versioned state format 

text The raw session text — the memory of record 

meta Timestamps, session ID, model/config hash 

serialization Versioned schema: roles, timestamps, prompt template, tokenizer version, metadata schema version 

text_digest / state_digest Separate integrity hashes over the serialized text and the native state. Bad or missing state is rebuilt only from verified-intact source text; if source 

verification fails, the session is recovered from a known-good copy or marked unavailable/out-of-coverage — damaged text is never silently trusted (§4.4, §4.8) Serialization is versioned so that a record remains decodable across software up-grades. We distinguish faithful replay (the entire §4.2 contract holds and the saved state is intact → the state is reusable as-is) from migration (a tokenizer change inval-idates the old state but not the recoverability of the retained source text, which can always be re-prefilled — §4.8). 

## 4.2 Cache-validity contract 

A stored state is reusable for a read when the read preserves the §2.2 conditions — the contract treats them as the operational checklist (the lemma states sufficiency, not necessity; practical equality is verified with tolerances by replay, §8): the same com-plete token prefix (including fixed instructions), the same model weights, continued 14 position indices (cache holds 0..N−1, the appended query takes N..N+Q−1), pinned RoPE base/scaling/max-position for the layers that are position-parameterized (a hy-brid model’s MLA layers may be position-free, §2.2), the same attention masks, the same numerical configuration, and the same native cache state — restored exactly as the writing model computed it, in its native form, with no format conversion, post-hoc quantization, or pruning between save and restore (§2.2 boundary i). A matching dtype label is necessary but not sufficient for equivalent state evolution. The model that writes the state is the model that reads it; the PA/answering/aggregator model may differ. (Engineering note, uncited mechanism remark: some engines show first-token/attention-sink artefacts when the leading prefix is dropped — the fixed-prefix contract prevents this.) 

## 4.3 Write path 

At session end, the system persists the session record. The defining invariant is: 

state = prefill_reader(fixed_prefix ‖ serialize(text)) — the state is a canonical prefill of the serialized record under the reader model. A live serving cache is reused only when the reader is the serving model and the serialized context is identical; otherwise the tier prefills the session text (assistant turns included as text tokens) under the reader model at session end. This one-time ingestion compute is the amortized term in §7 — writes add no summarization or extraction step, but they do add this prefill. Checkpoints are taken per session : the stored state is the canonical reader prefill of the complete serialized session at its boundary (assistant turns included as text tokens). Under ideal arithmetic this equals the live cache only in the reuse case above. The fixed instruction prefix is shared across sessions ; its bytes are counted once in §5 only if physically deduplicated, immutable, compatible prefix blocks are shared — a hybrid’s recurrent boundary state remains per session. A session the user resumes later can be extended by prefix-exact appending under the same contract.

Optional query-suffix hints. The appended question and query-time instructions may also carry bounded retrieval-derived hints without changing the stored session prefix. For example, ranked entity candidates with dated status may help interpret an ambiguous reference. Hints are clearly delimited, unverified interpretation aids, not session-local evidence: their rank is not proof, and the reader must support its output from the session or abstain while retaining relevant partial evidence. Repeating a hint across session outputs does not create independent confirmation. These provenance distinctions also apply at aggregation (§4.6). A hint producer is outside the unaugmented reference path; any evaluated hint-augmented variant freezes its source, generation and ranking rules, suffix format and token cap before testing (§8). Comparisons must declare and control hint access, report producer and repeated suffix-processing costs (§7), and preserve the context-fit rule (§4.7, §8.3). This permits query-side composition with retrieval methods, not a guarantee of equal or better answer accuracy. A question supported within one session can be handled by the per-session reader 17 and bounded aggregator without a joint read. Cross-session partials may also suffice for aggregation; otherwise the declared §4.7 trigger may invoke a bounded joint-text read or follow-up. This dispatch is a protocol choice, not a claim that every single-fact question succeeds or that every comparison requires joint attention. 

## 4.5 Read path — optional hybrid variant and the verifier/reranker role 

Hybrid variant. A pre-load prefilter over text/metadata (metadata filters, lexical match, or a dense embedding variant) selects candidate sessions before any state is loaded. Only the prefilter avoids cold-cache I/O: a query-conditioned 1-token probe still loads and reads each candidate cache — it saves decode, not cold reads. The prefilter method and any embedder are frozen protocol parameters, fixed before evaluation runs ; a dense variant’s index is not assumed small; selection effects are measured and reported (§8). The exhaustive path remains the reference; the hybrid is an optional, separately reported variant. 

Verifier/reranker role. KV-LTM can also sit behind an existing retrieval system: the retriever ranks candidate sessions, and KV-LTM reads their cached state — ver-ifying and reranking candidates against full session content instead of re-prefilling their text. The role applies to candidates with valid state; other candidates fall back to text prefill. This is complementarity mechanism (b) of §1.3; mechanism (a) is the index-free reference tier above. 

## 4.6 Aggregation contract 

The aggregator is part of the method, specified enough to be evaluated: • Inputs: the question; dated, source-linked per-session evidence; abstain flags (abstention triggers are protocol parameters, §8). Answer abstention is not evi-dence absence: sessions that abstain from answering keep their bounded partial evidence and session IDs in the pool; only no-relevant-evidence records reduce to counts. • Bound (explicit and declared): at most S source evidences, each capped at 

e tokens, output ≤ o tokens; abstain flags are not truncated. Overflow follows a declared rule — staged/tree aggregation or a documented ordering — frozen across arms A, A_k, O and reported. S, e, o are protocol parameters fixed before runs (§8); their storage/latency consequences are computed in §7. • Policy: a bounded, source- and recency-aware synthesis over dated evidence. 

Majority voting is not truth resolution : repeated stale facts cannot override a supported newer fact by frequency alone. • Outputs: a supported answer with source links | abstain | follow-up (including original-text fallback). • Protocol: the aggregator’s model, prompt, and budget are fixed across arms A, A_k, O (§8). 

## 4.7 Cross-session questions 

Per-session reads cannot jointly attend across sessions. For joint-evidence questions, a second tier selects the top-k_joint relevant sessions — drawn from the sessions 18 whose per-session outputs carried relevant evidence, including partial evidence from sessions that abstained from answering — and re-prefills them from text for a joint read. (A bounded reselection over source text under a frozen rule is allowed when per-session evidence is insufficient.) The tier is invoked on the aggregator’s follow-up output or by question type; the joint read must fit the reader’s context in-cluding instructions, query, and output reserve — otherwise the system abstains or follows up (§8 reports joint-fallback limits separately; arm C, full-concat, is a different system used for contrast, not this tier). Concatenating independently cached sessions into one cache is non-exact — it misses cross-session attention [6, qualitative]; naive concatenation also breaks position indices (our own technical observation) — so the joint path works from text, not from fused caches. (Optimization note: an already-stored first session’s cache may prefix the joint input only when that complete saved prefix matches the actual joint serialization under the entire §4.2 contract —joint template, leading instructions, positions, masks; otherwise the whole joint input is prefilled.) 

## 4.8 Retention, invalidation, fallback 

• Retention. The store holds the recent set R(N months) ∪ the older set L(M). The capacity invariant applies to the deduplicated union , including native-state and metadata overhead: bytes(R ∪ L) plus per-query modelled latency must fit the budget derived in §6/§7. Under exhaustive reference reads, recency-of-load is vacuous (every retained session is read every query), so “use” is defined as evidence use : a session is used when it contributed supported evidence the aggregator cited — including cited partial evidence from answer-abstaining ses-sions — or scored a verifier/reranker hit; L(M) is ordered by last-used under this definition, which is a frozen protocol parameter. When either the byte or the latency budget is exceeded, the older-set allowance shrinks first and the recent window follows — “N months” becomes achievable-N ; overflow sessions drop to text-only. KV eviction is not text deletion: evicted sessions remain readable from their text. • Invalidation. A model, tokenizer, config, fixed-prefix/prompt-template, or serialization-version change invalidates the stored state; affected sessions are re-prefilled from text in the background (migration cost quantified in §7). • Fallback. Evicted or invalid state still leaves the original text: full-prefill reading, or RAG over it when full reading is infeasible. Degradation preserves availabil-ity ; the fidelity property holds only on paths that read the full session — the RAG branch inherits §3.1’s query-time selection exposure.

# 8 Evaluation Design: Testing Without Implementation 

This chapter defines how KV-LTM’s logical read path can be measured on public long-term-memory benchmarks without implementing persistent caching — per-session prefill stands in for state restoration (§2.2’s lemma), so the read path is em-ulated exactly under ideal arithmetic, with practical equality tested later by a small real-cache replay. 

Framing caution. No arm below is a guaranteed bound on another. Published re-sults already show a retrieval system outscoring full-context reading on LongMemEval-S (Zep 71.2% vs full-context gpt-4o 60.2% [3, vendor preprint]) — more context is not automatically better. We therefore compare defined systems , not claimed ceilings. The Zep figures are vendor-reported under that study’s evaluation protocol, not a con-trolled KV-LTM experiment. Evaluation labels and judges can change reported scores (§9.1); the comparison is a framing caution, not a bound on any arm.

## 8.3 Benchmark × arm feasibility mapping 

Per benchmark and question, we record two properties: joint-evidence require-ment and arm/model feasibility . Joint evidence is annotated from gold evidence/session IDs (sessions spanned), not inferred from the question-type label — a temporal or multi-hop question can be answerable within one session, and cross-session evidence may be handled by aggregation without joint attention. Feasibility is conditional on actual session lengths, the reader’s effective context, the bounded joint fallback, and budget. Infeasible (arm × benchmark × reader) triples are marked N/A with the coverage stated — never silently truncated — and distinguished from attempted-but-failed answers. Aggregation impact is probed by the §8.2 sensitivity contrasts, not pre-declared (the A−O contrast alone mixes distractor exposure). Expected ab-stention is reserved for absent-evidence questions, not merely difficult ones.

## 8.8 What this chapter does not claim 

No accuracy result is reported here — this is a protocol. No arm is called an upper bound or ceiling. The plan’s feasibility rests on declared workload budgets (§8.4) and the preregistered gate (§8.5), both of which are stated, not assumed away.

## 9.2 Limitations 

• Model-version lock-in. A stored state is valid only under the §4.2 contract; a model, tokenizer, or config change invalidates it, and migration is a re-prefill from text, linear in archive token volume for fixed/bounded session-length processing (§4.8, §7.1). The reader model is effectively frozen for the retention window. • Session-length cap. One cached session is bounded by the reader’s effective context — among the §5 candidates, MiniCPM3-4B (32,768, config value) and DeepSeek-V2-Lite (≈32K, model-card guidance) are the 32K-class cases, while Llama-3.1-8B publishes 131K; in every case the effective value is what §8.5’s gate decides (§5.2). Longer sessions need segmentation, which interacts with session identification. • Storage growth. The store grows with retention; §6 frames it as a bounded cost under a declared budget, with achievable-N degradation (§4.8, §6.3). • Per-architecture exactness. The §2.2 lemma guarantees equality for that model’s own computation, under the reuse contract and ideal arithmetic ; it gives no inter-architecture quality guarantee — reader quality is established per checkpoint by the §8.5 gate, and no universal MLA-vs-GQA ordering is claimed (§2.3). • Text-only scope. No claim that visual, table, or audio meaning survives prepro-cessing into text (§1.4). • Session identification is deferred. How raw interaction is segmented into sessions is a separate problem; the design depends on it (§1.4 scope; §4), and §8.3’s per-question annotation assumes benchmark-given boundaries. This is a stated dependency, not a solved component. • The reader-sufficiency hypothesis is unproven at drafting. §8.5 states and gates the “<70B-class reader suffices” hypothesis; it remains a hypothesis until the preregistered gate runs (§8.5, §8.7). • Privacy — data protection. The store holds raw text plus derived state — a high-value personal-data surface. GDPR Art. 17 [53]: per-session deletion helps but is 38 not a compliance guarantee ; derived copies must be erased or invalidated as applicable, and selective source redaction may require a state rebuild. Learned cache-erasure methods exist (KVEraser [54]) and are noted bibliographically — no deletion guarantees are claimed. • Privacy — threat model. We assume a conservative sensitive-state threat model; no state-to-text inversion is claimed. (Author assumption — no public source is cited for it.) • Privacy — instruction integrity. Persisted instructions are treated as untrusted historical data. 

## 9.3 Next steps 

1. A source-traced released-item instance of write-time loss (item ID, pinned pipeline and configuration, metadata-intact stored state, logged reader context, answer and evaluation; source-reported versus reproduced artifacts distinguished), as a future upgrade to the §3.2 mechanism evidence. 2. Controlled in-house runs of arms A, A_k pre/A_k probe (the §8.1 prefilter/probe variants), C, O, R on the pinned Tier-1 benchmarks (§8.4–§8.6), with the §8.2 sen-sitivity contrasts — plus the planned mis-bounding sweep : a frozen boundary-perturbation policy (splits/merges that do not change source tokens) over a fixed benchmark subset, reporting accuracy and coverage against the injected mis-bounding rate, with reader, selection, and aggregation budgets held fixed. The sweep is proposed here, not implemented; numerical rates are later-run pins. 3. The minimal real-cache replay : tests practical equality with tolerances (§2.2) plus the §8.7 measured cost axis — replay reader, runtime, state format, toler-ances, and residency pinned beforehand; the outcome is not presupposed. 4. Bounded question decomposition : a future optional planner could split a com-plex question into a bounded set of sub-questions, read selected sessions from unchanged checkpoints, and combine source-linked evidence against the origi-nal question. Its quality and full query-time cost would be evaluated separately, with the planner, query and round limits, and budgets frozen before runs. This is proposed here, not implemented.
