Introduction
As AI-based coding agents become increasingly integrated into software engineering, developer-
agent collaboration has transitioned from a series of isolated prompts to a continuous, multi-
session, and multi-project workflow [12, 36, 50]. Throughout this ongoing collaboration, developers
routinely return to the same codebase across multiple sessions and rapidly switch between disparate
projects, relying on the coding agent to maintain and carry forward relevant context. This shared
history constitutes the agent’s working and long-term memories1, which dynamically shapes its
code reasoning, generation, and planning across diverse contexts [45, 59, 61]. Developers expect
these memory systems to exhibit precise contextual awareness. Each of their interaction with the
coding agent can produce diverse specifications, ranging from global, programmer-level stylistic
preferences to local, project-specific architecture conventions [36]. Accordingly, when developers
establish, scope, or delete these rules, they assume the agent will strictly match their mental model:
reliably retaining instructions, applying them only within their valid boundaries, and immediately
purging them upon revocation. In practice, however, essential cross-session context may be dropped,
project-specific rules may leak into unrelated workspaces, and obsolete guidelines may continue to
shape the agent’s outputs. These issues often go undetected because agent memory states are not
easily accessible or legible on conventional programming interfaces [29, 43]. We term this invisible
gap between what the developer expects the agent to remember and the system’s actual memory
state Developer-Agent Memory Misalignment.
Such misalignment stems from a structural breakdown in metamemory regulation. In cognitive
psychology, Nelson and Narens conceptualize this regulation process as a closed-loop system
operating across two memory levels: a meta-level that scrutinizes what memory contains, and
an object-level that executes information storage and retrieval [42]. In human cognition, this
loop is sustained by monitoring (informing the meta-level of object-level contents) and control
(steering object-level actions according to meta-level understanding). Recent work has extended
this framework to human-AI interaction, characterizing the monitoring and control demands that
generative AI places on its users [52]. Developer-agent collaboration splits this loop in co-coding
practices: the developer makes meta-level judgments (deciding what memory entry to keep, which
scope it applies to, or when to obsolete it), while the agent operates at the object-level (updating
stored memory entries, retrieving context, and applying them to code generation). We refer to
this distributed loop as developer-agent metamemory. Largely opaque object-level states sever
both pathways of the loop. Developers can neither clearly inspect stored and used context nor

Empirical human-computer interaction (HCI) studies show that developers highly value agency
and control over AI outputs [25, 32]. Many of them currently rely on three common but inadequate
practices to manage cross-context coding memory. Manual Context Injection (i.e., manually pasting
code, locating files, or repeating rules) preserves user control, but it is restricted to a single session.
When entering a new session, developers need to decide what knowledge and context to carry
over and manually recreate them, imposing high metacognitive demands [52] alongside output
verification effort [19, 41, 57]. Static Configuration via files such as CLAUDE.md and .cursorrules
allows the developer and the agent to co-edit memory instructions in natural languages [9],
but monitoring is limited to the file itself. Which rules the agent applied or ignored during a
generation turn remains hidden [8, 28]. Automatic Memory Extraction employed by tools such as
Cursor [4], Claude Code [3], and Codex [43] autonomously persists conversational history across
workspaces, which relieves manual effort but strips user control [10, 43]. More crucially, bringing
static configurations or automatic memories across workspaces unchanged can cause outdated rules
to conflict with new project-level conventions [55], adding to the misalignment. Research on AI
agent memory systems tried to address these challenges by making stored items visible [14, 26, 75],
editable [14, 26, 64, 75], reusable [14, 64, 75], and conflict-aware [14, 56]. Still, developers cannot
monitor which memory entries are selected during a generation turn or whether/how they shape
code outputs, leaving the critical loop between the developer’s mental model and the agent’s active
memory operations unclosed. This gap leads to the following research questions:
• RQ1: In cross-context collaboration with AI coding agents, what do developers want to monitor
and what do they want to control in agent memory?
• RQ2: What interaction design can help developers monitor and control agent memory across
contexts?
• RQ3: How does memory co-management affect developer-agent memory alignment and task
performance in cross-context collaboration?
To answer RQ1, we conducted a formative study with 12 developers from industry and academia
who regularly use coding agents across multiple projects. The study yielded five findings, covering
how memory should be represented and what developers can monitor and control across four
dimensions of memory use: evolution (how memory changes), selection (what is retrieved for a turn),
execution (how it is applied), and impact (its effect on the output). Guided by these requirements, we
designed MemoSync, a co-management system that actualizes agent memory as a shared, operable
representation jointly navigated and modified by both the developer and the agent (RQ2). To manage
boundaries across workspaces, MemoSync associates each memory item with a scope (i.e., personal,
project, or session). Upon context switches, the system abstracts specifications from past instances,
proposes their provisional scopes for developer review, and transforms them for the destination
codebase. MemoSync closes the metamemory loop by pairing explicit monitoring with direct control
across each of the four identified memory dimensions. It allows developers to authorize proposed
changes, inspect and dynamically adjust the context selected for every code-generation turn, trace
rule application in real time, interrupt the process whenever spotting an error, and audit the final
output’s compliance with memory specifications. To evaluate MemoSync’s efficacy on fostering
metamemory regulation in developer-agent collaboration (RQ3), we conducted a between-subjects
study (𝑁= 132) comparing the system against an automatic memory baseline (e.g., ChatGPT- and
Claude-style memory) and a static configuration baseline (e.g., developer-maintained Markdown
memory files). During the study, participants completed two distinct, full-stack projects, each
encompassing two development sessions. We also deployed MemoSync with nine developers on
their own projects for one week.

2
Related Work
2.1
AI-Assisted Programming and Human-Agent Collaboration
Code completion and generation. In workflows centered on code completion and generation,
developers use model suggestions to accelerate implementation or explore alternative solutions [5],
while reading, interpreting, and inspecting generated code to decide whether to incorporate it
into their implementation [41]. Research on programming question answering also shows that
users may overlook errors in AI-generated answers, highlighting the need for effective verification
support [30]. Prior systems provide anchored explanations [62], live execution feedback [21], and
multidimensional code evaluation [37] to help developers understand, verify, and revise gener-
ated code. However, this support primarily concerns local code: translating overall goals into
specific requests and coordinating successive generations to satisfy task requirements still depend
substantially on developers’ own efforts [66].
Conversational programming and structured steering. Natural-language and conversational
programming enable developers to progressively clarify requirements and refine implementations
through continued interaction [27, 48]. To connect high-level goals with implementation details,
prior systems make task decompositions, plans, and the model’s interpretation of user intent
inspectable and editable [31, 66, 69]. Interactive explanations and dataflow visualizations extend
this control to intermediate operations [22, 54, 60]. For implementation choices that remain open,
branching and merging and structured design exploration help users compare and refine alterna-
tives [2, 39, 67], while sketch-based and component-level editing support local revisions [35, 65].
These mechanisms strengthen understanding and intervention within the current task. However,
ongoing revision of task representations does not fully address knowledge reuse across tasks: when
goals or projects change, further interaction support is needed to select, adapt, and carry forward
established requirements, design decisions, and experience.
Collaboration with AI Agents. Coding agents further expand the scope of work that developers
can delegate. Developers can specify higher-level goals and allow the agent to choose concrete steps,
invoke tools, and carry out sequences of file modifications and code execution [12]. Developers
can consequently reduce their direct involvement in individual operations while maintaining
control through planning, incremental delegation, and result inspection [25]. Related systems
also explore proactively offering suggestions based on task context, using status cues and edit
previews to help developers coordinate these interventions [13, 46]. Other systems organize agent-
discovered program dependencies into annotated traces to help developers understand the answers

prior agreements the agent is carrying forward. As implementation decisions and context selection

2.2
Metamemory in Human-AI Collaboration
Metamemory focuses on people’s understanding and regulation of their own memory states and
processes. Nelson and Narens describe two interrelated levels: the object level carries out memory
activities such as learning, storage, and retrieval, while the meta level maintains a dynamic model
of these activities. Monitoring informs the meta level about object-level states, and control adjusts
object-level activities according to meta-level judgments [42]. Within individual cognition, these
pathways connect people’s judgments about memory with the memory processes they regulate.
HCI research has drawn on the broader concept of metacognition to examine how users monitor
and regulate their cognitive activities during interaction. Chen et al. incorporate metacognitive
experiences, knowledge, and skills into a model of visualization, explaining how users assess their
understanding and adjust their exploration strategies [11]. In human-AI interaction, Tankelevitch
et al. characterize prompting, output evaluation, and workflow adaptation as activities that place
metacognitive demands on users, and discuss how explainability and customizability can help
address these demands [52]. These accounts provide a theoretical basis for designing metacognitive
support, while leaving open how users’ judgments can remain connected to an agent’s persistent
memory operations across contexts.
Building on this perspective, we conceptualize developer-agent memory co-management as a
regulatory loop distributed across a human-agent interaction boundary: developers judge what to
retain, where it applies, and when to update it, while the agent stores, retrieves, and applies memory.
We therefore investigate how interfaces can help developers observe these memory operations
and translate their judgments into effective interventions, supporting memory alignment across
sessions and projects.
2.3
Memory Management in AI Agents
Research on automated agent memory focuses on information extraction, organization, retrieval,
and updating to support experience accumulation and improve long-term task performance [59, 61,
70]. These studies primarily evaluate memory mechanisms in terms of experience reuse and task
performance, giving less attention to how users participate in deciding what information should
be retained and under what conditions it should be used. In human-AI collaboration, however,
memory also carries users’ preferences, goals, and constraints, and decisions about its retention
and updating need to be grounded in user intent [56]. Information accuracy and task benefits alone
are therefore insufficient to establish whether memory continues to match users’ expectations.
HCI research on interactive memory management further examines how users participate in
these decisions. Prior work presents conversational memories as visible, editable objects that
users can inspect and revise [26, 64], and uses conflict detection and local revision to help users
understand and manage the consequences of memory updates as their intentions change [56].
Interactive memory management also helps users decide which experiences to reuse and how to
apply them to new tasks. Reusable content includes conversation excerpts, cognitive workflows
derived from collaboration, and domain knowledge implicit in historical code [14, 64, 74]. In addition,
Knoll allows users to configure accessible knowledge modules and inspect the knowledge sources
associated with responses [72]; Cerebra links knowledge items, code snippets, and execution results
to help users inspect and revise how knowledge is applied [74].

3
Formative Study
To understand what developers want to monitor and control in agent memory (RQ1), we conducted
a formative study.
3.1
Participants, Procedure, and Data Analysis
We recruited 12 developers who regularly use AI coding agents across multiple projects (demo-
graphics in Table B1), as they are most likely to encounter the cross-context memory challenges
this study investigates. All sessions were conducted remotely and lasted approximately 60 minutes.
Before the session, we collected from each participant a recent agent-assisted project with its con-
versation logs and configuration files (e.g., CLAUDE.md, AGENT.md). Following a contextual inquiry
approach [6], the session was divided into three parts:
• Semi-structured Interview: We asked participants about their current collaboration pat-
terns with the agent, including session structure, cross-project workflows, and configuration
practices (∼15 min).
• Artifact Walkthrough: The participant and researcher jointly examined conversation logs,
configuration files, and the agent’s automatically extracted memory. Participants identified
information they wished to persist and annotated its scope and portability, revisited their
experiences with cross-project migration and long-term maintenance, and pointed out
moments where they could not monitor or control the agent’s memory (∼30 min).
• Design Expectations Interview: Participants described what visibility and control they
wanted over memory management, including what they needed to see, when to intervene,
and how to handle deviations (∼15 min).
Details for each part can be found in Appendix B.2. Each participant received ∼$10 for their time.
This study adhered to the Declaration of Helsinki and was approved by the Human Research Ethics
Committee. We recruited iteratively and stopped after 12 participants when no new codes emerged.
Two researchers independently coded the transcripts using an inductive approach and iteratively
refined codes through discussion (Appendix B.3).

developers had no independent way to check the completeness of the selection. Participants wanted

started, with the ability to modify the selection (N=9). P11 suggested: “Before it starts generating,

Finding 4. Developers cannot see which memory the agent is acting on during execution;
a wrong memory may take effect before they can stop the agent. During execution, the
agent might act on an outdated memory the developer did not expect in the current conversation.
Participants could not observe which memory the agent was following as it generated (N=12). In
most cases the agent did not indicate which memory it was acting on, and errors surfaced only
when the developer inspected the finished output. Only when the agent happened to mention a
piece of information in its reply, and that information conflicted with the developer’s expectations,
could the participant catch the problem mid-execution and interrupt the generation. Participants
wanted to see in real time which memory the agent was applying, so they could stop and correct
the agent on the spot and resume from where it stopped (N=12).
Finding 5. Developers cannot evaluate whether their memory took effect in the agent’s
output. Eleven participants (N=11) reported that they could not tell whether a specific memory
item was used, ignored, or misapplied. P4 described a typical experience: “I noticed something was
off in its reply, went back and checked, and it clearly didn’t follow what I had set up. I asked it why, and
it just said sorry, I’ll fix it. Then it made the same mistake again.” This inability to attribute results to
specific items made repair indirect: developers could only re-emphasize the relevant memory in
the next prompt without knowing whether the agent would follow it. Participants wanted each
output to show which memory items shaped it and which were violated, so that they could trace
the result to specific entries (N=12).
3.3
Design Goals
Based on these findings, we propose five design goals (Figure 2). They converge on a core principle:
agent memory should serve as a shared operable representation that both the developer and the agent
can read, modify, and act on. DG1 addresses the representation of memory itself; DG2 through DG5
correspond to the four dimensions identified in the formative study: evolution, selection, execution,
and impact.

DG1. Design memory as a structured representation with explicit scope and progres-
sively loadable detail, compatible with developers’ existing tools. Building on F1, the system
should represent each memory item as a structured entry with an explicit scope and detail that the
agent loads on demand, and should stay in sync with formats such as Markdown, so that developers
can import existing configuration files and export memory for use elsewhere.
DG2. Evolution: prioritize durable knowledge, detect staleness and conflicts, require
developer confirmation before writes, and support abstraction-aware cross-context trans-
fer. In response to F2, the system should propose memory items from the conversation, favoring
preferences, constraints, decision rationales, and lessons over execution traces and temporary
information, and require developer confirmation before any write. It should detect stale, redundant,
or contradictory entries and propose fixes for the developer to review. When a memory item mi-
grates to a new context, the system should abstract it from its source, rewrite it for the destination,
and propose a landing scope, so that the developer reviews each form before the item crosses the
boundary.
DG3. Selection: make per-turn memory selection transparent and adjustable, and state
the expected use of each item. In response to F3, the system should expose the proposed memory
set and the expected use of each item before generation. Developers should be able to remove
irrelevant items, add missing ones, or ask the agent to revise the selection, and confirm it before
generation starts.
DG4. Execution: show memory use in real time during execution and support immediate
interruption and correction. In response to F4, the system should expose memory use during
generation. When developers spot a deviation, they should be able to stop execution at that point,
supply a correction that the resumed run must follow, and resume from that point.
DG5. Impact: audit memory use after each output and attribute the result to specific
memory items. In response to F5, the system should report, for each injected memory item,
whether it shaped the turn, was violated, was not applicable, or had no visible effect, and it should
judge this independently of the agent’s own report, since the agent may claim to follow a rule
while breaking it. Developers should be able to trace a verdict to the place in the output where the
item was applied, and to mark an item as mandatory for the next turn. Audit results should feed
back into the store for ongoing maintenance.

MemoSync
MemoSync integrates developer monitoring and control of agent memory into the coding agent’s
task execution through a shared, operable memory representation. Around each turn2, MemoSync
supports memory review before execution, intervention during execution, and auditing after
completion. Figure 3 illustrates this workflow. Before execution, A Long-term Memory Management
presents the memory review preceding the turn, and C Working Memory for This Turn lists the
memory items confirmed for the current turn. During execution, D inline citations in the agent’s
reply indicate relevant memory items. After execution, E Memory Use Audit reports how those
memories were used. The right sidebar contains the F Memory Record for reviewing memory
activity across turns, with a B Memory Board button at the top for accessing the persistent memory
store for viewing and editing.

After the approved changes update the store, Working Memory for This Turn previews the items

Implementation
MemoSync is implemented as a TypeScript web application with a React frontend, a Bun backend,
and SQLite storage for memory items and their histories. Built on Kanna7, an open-source agent
framework, it supports both the Claude Agent SDK8 and the Codex CLI9 as the underlying coding
agent. All memory operations run through the existing coding-agent runtime without requiring a
separate LLM API integration. These operations use model calls in forked conversations that share
the active session’s context prefix, retaining task context and enabling prompt-cache reuse.
Figure 9 shows the orchestration. A new user prompt triggers parallel branches for candidate
extraction, transfer suggestions, and memory-change checks, while the frontend presents their

5
User Study
To evaluate MemoSync and explore how memory co-management affects developer-agent memory
alignment and task performance in cross-context collaboration (RQ3), we conducted a between-
subjects study comparing MemoSync against two baselines: an automatic memory extraction
system that represents how current coding agents manage memory autonomously (referred to as
the Auto condition), and a static configuration file system that represents how developers manage
agent memory through shared Markdown files (referred to as the Static condition). Participants
collaborated with an AI coding agent in a browser-based coding workbench to complete the task. We
measured memory alignment, monitoring accuracy, control accuracy, task performance, memory
application gap, interaction activity (monitoring and control action counts), perceived workload,
and system usability.
5.1
Task Setup
We selected two full-stack web development projects from FullStack-Bench [38]: an apartment-
rental application and a car-rental application (Figure D1). Each project used a Next.js frontend,
a NestJS backend, and a PostgreSQL database. We chose full-stack development for two reasons.
First, it is a prevalent use case for AI coding agents and involves multi-file, multi-layer reasoning
where accumulated context directly affects output quality. Second, the benchmark provides an
official scoring rubric, enabling reproducible performance measurement. To keep the study duration
manageable (approximately two hours), we limited the design to two projects with two sessions
each.
The two projects share a similar application structure (browsing, booking, and transaction
management) but differ in business logic and data models, so that memory from the first project
could apply to the second only after adaptation. Each project was divided into two consecutive
sessions. The first session established the project’s core functionality, while the second extended
the same codebase with additional transaction and management features. Session 2 built on the
code produced in Session 1: the two sessions within a project shared the same workspace directory,
and Session 2 did not reset the codebase. Session 1 was scored from its own frozen snapshot,
so subsequent changes in Session 2 did not retroactively affect Session 1 scores. Session 2 was
evaluated on the cumulative workspace. The four sessions had different maximum scores (9, 5, 11,
and 5 points, respectively; see Appendix D.2 for the full rubric), but the required knowledge and
task complexity are equivalent, as our task difficulty evaluation shows (Appendix C).
Project order was counterbalanced across participants, with Session 1 always preceding Session 2
within each project. This design provided both within-project continuity for memory accumulation
and a cross-project boundary for memory transfer. In each session, participants read the task brief,
described the requirements to the agent in natural language, iterated on the implementation, and

verified the result through an embedded browser preview. At the end of the session, they submitted
a frozen workspace snapshot as the final artifact (see Section 5.3 for the detailed flow).
To calibrate task difficulty, we used the same agent configuration as in the study (DeepSeek
V4 Flash, reasoning effort: high; see section 5.2 for the full specification) and ran it without any
accumulated memory ten times per session. The mean score was approximately 50% of the session
maximum, indicating that the tasks were neither trivial nor out of reach for the agent alone (see
Appendix C for details).
5.2
Conditions
Participants were randomly assigned to one of three conditions. All conditions used the same
coding agent, browser-based workbench, and task materials, differing only in how agent memory
was presented and managed. The workbench was built on the open-source Kanna framework, and
each participant ran in an isolated Docker container with separate transcripts, memory data, and
project workspaces. The coding agent was Claude Code (v2.1.170) via the Claude Agent SDK, using
DeepSeek V4 Flash as the underlying model with high reasoning effort, and could access workspace
files, the shell, and the web.
• Auto (Automatic Memory). After each successful agent turn, the agent could create,
update, or reinforce memory entries, and these changes were applied automatically without
participant review. Memory was stored in a SQLite database. At the start of each turn, all
active memories for the current project were injected into the agent’s context as a plain-text
Markdown block. When participants switched projects, the first project’s memory was
copied once into a separate project-level store. Participants could view an LLM-generated
summary of the current memory state and request memory changes through natural-
language conversation, but could not directly edit individual entries (Figure A1a). This
condition reflects the automated memory management approach used by agents
like Claude, ChatGPT, and Kimi.10
• Static (Static Configuration). Participants and the agent shared plain-text Markdown
files in the workspace root (MEMORY.md), similar to CLAUDE.md. At the start of each turn,
the full contents of these files were injected into the agent’s context together with a fixed
maintenance instruction. Participants could edit the root MEMORY.md directly from the
sidebar or ask the agent to edit the files through the main conversation (Figure A1b). This
condition represents the common practice of using configuration files such as
CLAUDE.md to manage agent behavior across sessions and projects.
• MemoSync. Participants used the MemoSync system described in Section 4, with developer
review and control over memory management throughout the interaction. This condi-
tion operationalizes monitoring and control across memory evolution, selection,
execution, and impact.

Analysis
We tested normality with Shapiro–Wilk separately within each condition (42 tests: 14 measures ×
3 conditions). Thirty-one tests were significant. We therefore used non-parametric tests for group
comparisons, except for the count-based activity measures modeled separately below. Per-measure
𝑊and 𝑝values are reported in the supplementary material. Three-group comparisons used Kruskal–
Wallis 𝐻, followed by all three pairwise Mann–Whitney 𝑈tests (MemoSync vs. Auto, MemoSync
vs. Static, Auto vs. Static). We applied Holm correction to the three pairwise comparisons for each
measure at each level of aggregation, but did not apply additional correction across measures
or positions. All pairwise 𝑝values reported below are Holm-corrected. Omnibus effect sizes are
reported as 𝜖2, and pairwise effect sizes as signed rank-biserial 𝑟𝑟𝑏. The supplementary material
reports the full test statistics for every outcome, the negative-binomial models for the activity counts,
all components of the mediation model, and the per-measure normality tests. Monitoring Activity
and Control Activity were overdispersed count measures, with variance-to-mean ratios of 13.7–
27.4 and 2.4–6.4, respectively. We therefore modeled both using negative-binomial regression
with HC3 robust contrasts. We report incidence rate ratios (IRRs) with Holm-corrected pairwise
contrasts. The exploratory mediation analysis treated Memory Alignment (Content+Scope)
as the outcome and Monitoring Accuracy and Control Accuracy as simultaneous mediators. Path
coefficients were estimated with OLS and HC3 robust standard errors; indirect effects were tested
with BCa 95% CIs from 50,000 condition-stratified bootstrap resamples [24]. This analysis used
the 123 participants with complete scores (see the footnote in the Measures subsection for the
derivation of 𝑁= 123). For the two workload measures, we additionally ran equivalence tests
(TOST) [33] with a margin of 𝑑= 0.5 to test whether MemoSync’s workload was equivalent to each
baseline within a medium effect. All analyses used Python 3.12.7 with SciPy 1.16.2 and statsmodels
0.14.5.

Finding 7: Memory alignment and task performance traded off between Auto and Static;

similar projects, even though developers gradually lost track of what the file contained (Figure 13).

explanation is that continuous accumulation and cross-project transfer kept its memory rich, while
the mixed-initiative proposal mechanism kept developers aware of the agent’s memory and its
scope.
6.3
Interaction Activity, Workload, and Usability
Finding 8: MemoSync participants performed significantly more monitoring and control
actions, yet no condition differences were detected in workload, usability, or task time.
MemoSync participants performed on average 70.3 monitoring actions over the four sessions
(𝑆𝐷= 43.9), compared with 7.3 under Auto (IRR = 9.64, 95% CI [6.20, 14.97], 𝑝H < .001) and 8.7
under Static (IRR = 8.06, 95% CI [5.25, 12.36], 𝑝H < .001; Figure 17a). They also performed 25.3
control actions (𝑆𝐷= 11.1), compared with fewer than one under Auto (IRR = 30.14, 95% CI
[13.32, 68.20], 𝑝H < .001) and Static (IRR = 101.36, 95% CI [40.32, 254.82], 𝑝H < .001; Figure 17b).
Kruskal–Wallis tests detected no condition differences in monitoring workload (𝐻(2) = 0.38,
𝑝= .829, 𝜖2 < .01), control workload (𝐻(2) = 0.52, 𝑝= .771, 𝜖2 < .01), system usability (𝐻(2) = 1.34,
𝑝= .511, 𝜖2 < .01), or active task time (𝐻(2) = 3.22, 𝑝= .200, 𝜖2 = .01; Figure 17c–f). Equivalence
tests supported equivalence within a medium effect for both monitoring and control workload
against both baselines (all TOST 𝑝≤.047). As described in the Introduction, developer-agent
collaboration splits the meta-level and object-level of traditional metamemory apart, delegating
object-level memory operations to the agent. Under Auto and Static, users had to self-initiate
checks on this external object-level state. MemoSync’s mixed-initiative design surfaced object-
level state changes at each interaction point, allowing the monitoring-control loop to operate
without requiring users to initiate across this boundary. We conjecture that this design allowed the
substantially increased activity to proceed without a perceived increase in workload.

supported adjustments to the current task, how these actions fit into ongoing development work,
and how developers reused memory across their own projects and parallel sessions. To investigate
these questions, we conducted a week-long deployment study.

7.1
Participants and Procedure
Nine developers participated in the deployment study (P1 to P9, demographics in Table F1), using
MemoSync to work on their ongoing projects over one week. Before the study, we provided a user
manual and asked participants to spend at least two hours using the system. System logs recorded
participants’ monitoring and control actions, agent execution, and context switches. At the end of
the week, each participant completed a semi-structured interview lasting approximately 30 minutes,
covering their overall experience and specific interaction episodes selected by the researchers from
their logs. Participants received unlimited LLM API access to use MemoSync on their own projects
throughout the study and a $50 USD honorarium upon completing the exit interview.

participants used memory co-management in their daily work. Figure 18 presents each participant’s
activity sequence over the week, with the horizontal axis indicating normalized sequence position.
Below, we draw on these sequences and interviews to describe how developers incorporated
memory co-management into daily work.

them judge whether the next steps matched their expectations. P1 felt that the pre-execution
expected-use statements gave them “a greater sense of control over the task,” while P2 found
per-turn working-memory selection smoother than editing files beforehand or asking the agent
to pause the current task to retrieve context. In comparison, P4, P5, P6, P8, and P9 more often

subsequent execution. P5 explained that outputs often deviated from requirements only in particular

mark the relevant memory item as mandatory for the next turn to “make small adjustments to the
work.” P3 combined both tendencies, often beginning with inspection after execution while also
frequently modifying memory. System-initiated proposals further integrated these adjustments
into the current task. P8 had previously checked memory only after outputs went wrong, and their
Markdown file had grown beyond 2,000 lines, making it almost impossible to review in full. With
MemoSync proposing new items and changes during work, P8 felt that the system “helped me
better manage my memory store.” These uses connected memory maintenance to the task at hand:

Discussion
MemoSync treats persistent memory as a shared operable representation that developers and agents
jointly monitor and control. Drawing on the formative, controlled, and deployment studies, we
discuss memory co-management in four parts: how it supports selective oversight of accumulated
memory and the bias and accountability issues raised by the agent’s selection (Section 8.1), how it
builds human-AI common ground through layered memory representations (Section 8.2), how it
re-establishes memory across sessions and projects (Section 8.3), and how it lets people shape their
extended cognition (Section 8.4).

8.1
From Memory Visibility to Selective Oversight
8.1.1
Monitoring as the Bottleneck of Metamemory Regulation. Metamemory connects people’s
understanding of memory with memory processes through monitoring and control: monitoring
informs the meta level about object-level states, and control guides storage and retrieval accord-
ingly [42]. When the agent carries out memory operations, this regulation crosses the human-agent
interaction boundary. Developers judge what should be retained and where it applies, while the
agent stores, selects, and applies that information. In this loop, control is guided by monitoring;
without accurate monitoring, control lacks an informed basis.
Our findings indicate that monitoring is the main bottleneck in developer-agent metamemory
regulation. In the controlled study, Control Accuracy was high across all three conditions, whereas
Monitoring Accuracy varied much more. The exploratory mediation analysis also identified sig-
nificant indirect effects through Monitoring Accuracy. Static participants could inspect and edit
the full memory file, yet their Monitoring Accuracy was the lowest. In the formative study, as
configuration files grew, participants rarely read them in full and struggled to confirm which
rules the agent actually followed. This finding suggests that the accumulated information made it
difficult for developers to identify which memories needed attention in the current task. Formative
participants also had difficulty identifying which memories the agent selected for each turn and
often restated requirements in prompts after errors appeared. These findings suggest a need for
selective oversight: developers need to identify task-relevant content within accumulated memory
and judge whether its use matches their expectations.
8.1.2
Agent-Supported Selective Oversight. Our work suggests that agents can proactively support
this selective oversight, helping developers judge which memories are relevant to the current task
and whether their use matches expectations. Prior interactive memory systems support users in
retrieving, organizing, reusing, and revising memory [26, 64], but users still largely initiate reviews
to identify which memories need attention in the current task. In MemoSync, the agent proposes
which items to use and explains how it expects to use each one. Developers check for missing
or irrelevant items, while citations and audits connect those items to their actual application.
Developers and agents jointly identify which memories to monitor and check how they are used in
the output.
Selective oversight can help developers monitor memory more accurately with little difference
in perceived workload. In the controlled study, MemoSync participants’ judgments of memory
application were closer to actual application. They also performed significantly more monitoring
and control actions, with little difference in perceived workload compared with the baselines.
Deployment participants’ feedback (Finding 1 in Section 7) suggests that the system organized
accumulated information around the current task, leaving developers to make judgments about
specific items. This means that monitoring support involves both presenting information and
helping people identify what currently needs attention. AI can help direct attention to relevant
memories, connecting people’s judgments with specific control actions in the current task.
8.1.3
Flexible Control across Collaboration Stages. Monitoring and control in metamemory do
not occur at a single point in time. Nelson and Narens describe monitoring judgments and the
corresponding control across the acquisition, retention, and retrieval of memory, such as allocating
study time, selecting a search strategy, and deciding when to stop a search [42]. In developer-agent
collaboration, regulation is likewise distributed before, during, and after each turn: developers
can intervene when reviewing the working memory for the turn, when seeing citations during
execution, or after the audit results appear. In the deployment study, some participants resumed
oversight through shared records after delegating execution, and a participant stopped execution


MemoSync: Co-Managing Developer-Agent Metamemory Across Contexts
33
immediately after seeing the agent cite an incorrect memory item (Finding 2 in Section 7). This
suggests that selective oversight also involves choosing when to intervene. Developers do not need
to continuously follow execution; they can adjust how they intervene according to how much they
delegate and still find grounds for intervention when needed.
8.1.4
Bias and Accountability. Selective oversight also allows the agent’s selection to shape what
developers see. Which memories the agent selects depends on the judgment of the underlying
model, and current language models tend to assign uniform priority to instructions, which makes it
difficult to distinguish their importance [51, 58]. People who rely on automated aids also tend to miss
problems that the aids do not flag [44]. In the deployment study, participants wanted the system to
proceed directly when instructions were simple, with fewer repeated confirmations (Section 7). As
delegation increases, developers’ confirmations cover only part of the agent’s decisions, and the
model’s biases are more likely to enter human judgment through its selection.
This influence also changes the distribution of responsibility. In human-machine systems, re-
sponsibility for an action may be attributed to a human operator who had limited control over the
behavior of the automated system [18]. In selective oversight, the agent shapes which memories
developers can see and act on, while developers make the approvals. Selective oversight needs
to make the selection itself open to inspection, showing which memories were not selected and
why, and distinguishing decisions made by the agent from those made by developers, so that
responsibility corresponds to actual influence.
Implications. From this metamemory perspective, human oversight of AI involves people
and agents jointly identifying which information needs attention, when to intervene, and who
is responsible for these decisions. Agents with persistent memory can propose which memories
need attention in each turn and explain how they expect to use them, keep shared records that let
developers resume oversight during and after execution, and show which memories were selected
and which were not. Selective oversight offers a way to organize human-AI interaction around
the current task, connecting relevant memories, human judgments, and direct control so that
developers and agents can continue to regulate how accumulated experience is used.
8.2
Building Human-AI Common Ground through Layered Memory Representations
People and agents differ in their capacity to process information. Human reading and judgment are
limited by working memory capacity and time [17, 47], while LLMs can process large amounts of text
within their context windows and use specific details to complete tasks. Effective communication
is based on a shared understanding sufficient for the current task [16]. In memory co-management,
developers need to understand the requirements expressed in memory and their scopes, while
the agent uses detailed content to carry out those requirements. Developers and agents can build
common ground around the same requirement using representations at different levels of detail.
Existing automatic memory and static configuration practices typically use a single memory
representation to support both developer understanding and agent execution. Our controlled study
included Auto and Static as baselines representing these two practices. The results showed a trade-
off: Auto participants had higher Monitoring Accuracy and Memory Alignment for Content than
Static participants, whereas Static participants achieved significantly higher task performance
than Auto participants. Prior work has found that LLM agents can improve their performance
as they accumulate experience [71], whereas compressing contexts into concise summaries or
repeatedly rewriting them loses domain-specific details needed for execution [68]. Together with
these findings, our results suggest that Auto’s summaries and storage cap helped developers
maintain an overview of memory while limiting the details available for the agent to reuse, affecting
task performance. Static retained implementation details that may have supported subsequent

tasks, but the growing content exceeded what developers could review, making it harder for them
to monitor and understand what the memory file contained.
MemoSync uses linked, layered representations of the same memory: developers review sum-
maries and scopes, while the agent loads task-relevant details on demand. Links between these
levels allow developers to review specific details when needed and inspect their application through
citations and audits. This design builds common ground around the same requirement while allow-
ing developers and agents to use information at different levels of detail. In the controlled study,
MemoSync achieved the highest Memory Alignment and task performance (Finding 7 in Section 6).
As memory accumulates, developers can understand requirements through concise representations,
while the agent retains the implementation details needed for execution.
Implications. Layered memory representations let people understand and regulate accumulating
knowledge around task requirements, allowing human-AI common ground to expand in ways
that accommodate human cognitive capacity and agents’ ability to process detailed information.
Systems can organize information for people according to the purpose of collaboration, show
implementation details when people need to review them, and apply developers’ revisions to the
memory used in execution. Future work could explore how the level of detail can change with
tasks and collaboration experience, so that people and agents can understand and jointly use the
growing knowledge stored in memory.
8.3
Re-establishing Memory across Contexts
To reuse memory in another context, it needs to be separated from the context in which it was
formed and re-established in the context where it is used [1]. Agents with persistent memory can
take part in extracting, rewriting, and applying memory, making it easier for memory to move
across sessions and projects. A practice from one project can be adapted for another project, and a
requirement can extend from the current session to the whole project. Memory reuse thus involves
changes in both its content and the scope in which it applies.
8.3.1
Abstracting and Localizing Memory across Projects. Cross-project transfer shows how content
is re-established in a new context. In the formative study, participants typically copied existing
context documents with little revision when switching projects and assumed that the agent would
interpret them correctly, but this often led to unexpected behavior. They wanted guidance on which
memories could transfer directly, which needed rewriting, and which should remain in the original
project. MemoSync first abstracts a source memory into a principle, removing implementation
details specific to the source project, then rewrites it for the destination project, and presents the
source, abstract, and localized forms for developer review. In the controlled study, MemoSync
participants’ Memory Alignment for Content was significantly higher than both baselines in all
four sessions across the two projects.
8.3.2
Refining Scope through Later Use. Scope determines how widely memory content can con-
tinue to be used. Crossing a boundary can extend the use of a memory item or limit it to a more
specific scope: MemoSync allows developers to move a session memory to the project scope, and to
keep content transferred from another project in the current session only. These decisions require
anticipating where a memory will be used in later work; Ackerman and Halverson note that such
anticipation remains difficult, although people do it every day in their work [1]. In the controlled
study, at the project boundary, MemoSync participants’ Memory Alignment for Content remained
significantly higher than both baselines, while their Memory Alignment for Scope was close to
Auto’s and was significantly higher than both baselines in the second session of each project. The
different trajectories of the two dimensions suggest that content can be re-established during trans-
fer, whereas scope continues to become clearer through later use after memory enters a new context.

Systems can connect scope adjustment with how memory is actually used, allowing developers
to keep, extend, or narrow its scope according to new task requirements. The re-establishment of
memory in the destination context also continues into later work as the project progresses.
8.3.3
From Individual to Group Memory. Our study focused on individual developers reusing
memory across their own sessions and projects. In practice, much development work is carried
out by multiple people. Contributors to open-source repositories follow project conventions when
submitting pull requests, and development in companies needs to meet team coding standards.
As coding agents become part of everyday workflows, these conventions are increasingly written
as Markdown files or packaged as skills that agents read and follow. These conventions become
group memory shared by team members and their agents, and the scope of memory extends
from individuals to teams. Group memory crosses boundaries in two directions. Experience that a
member develops in a task needs to be separated from the details of that member’s work before it
can become a team convention; when team conventions enter each member’s specific task, they
need to be re-established for that task, a process increasingly carried out by agents. As development
progresses, where a convention applies also becomes clearer through members’ own use. Some
conventions extend to the whole team, while requirements set only for a particular task are retired
when the task ends.
Implications. Agent memory should be continually re-established in new contexts as collab-
oration progresses, allowing past experience to adapt to changing task requirements. Systems
can let memory move across sessions, projects, and team members as collaboration continues,
re-establishing its content and adjusting its scope each time it crosses a boundary, while preserving
links to where it came from and where it has been used, so that the experience individuals develop
in collaboration can be shared and developed more widely.
8.4
Supporting Extended Cognition through Metamemory Co-Regulation
People have long relied on notes, documents, and digital tools to record past experience, organize
thought, and coordinate action. Through continued use, these external resources become part of
people’s cognitive activity, extending what they can remember, understand, and accomplish [15, 49].
AI agents with persistent memory take on a more active role in this relationship: they retain require-
ments and decisions from collaboration, proactively organize and retrieve relevant information,
and apply it to subsequent tasks. As people increasingly rely on this accumulated information in
their work, AI memory gradually becomes part of their extended cognition.
Metamemory co-regulation lets people shape this part of their extended cognition. Developers
use monitoring to understand what information influences their work and control to decide how
it should be retained, revised, and applied. These judgments guide the cognitive system formed
by people and AI as people’s goals and contexts change. In this process, people also learn to
organize and use external cognitive resources: judging when to rely on what the agent remembers,
connecting knowledge across tasks, and adjusting the division of cognitive work as new needs
arise. Collaboration with AI includes people’s active participation in shaping their own cognition.
The deployment study showed how developers participated in this process (Section 7). Partic-
ipants used shared records to resume oversight after delegating execution (Finding 2) and used
memory to reuse and pass information across projects and parallel sessions (Finding 3). Developers
reorganized some of their record-keeping and coordination around AI memory and used the infor-
mation preserved by the system to keep track of that work. Shared memory and records of its use
supported both ongoing work and developers’ judgments, allowing them to regulate these external
resources while using them in their everyday development work.

Salomon et al. note that working with intelligent technologies can affect people beyond their
performance during the collaboration, leaving lasting effects on their abilities [49]. Building on this
view, our work suggests that people’s ability to shape their extended cognition provides a basis for
further human augmentation. As collaboration continues, people can connect knowledge across
tasks to develop new understanding and revisit past decisions and their outcomes to revise their
judgments and ways of working.
Implications. Future AI memory systems can support people in continuing to shape their ex-

work. People can benefit from the information agents retain and use while continuing to decide
how these resources are used in their thinking and actions, allowing their extended cognition to
develop with their goals and needs.
8.5
Limitations and Future Work
First, we selected automatic memory and static configuration as baselines grounded in existing
practices to examine the overall value of MemoSync as a complete memory co-management
approach in collaboration. Memory updating, selection, application, and auditing are interconnected
stages, and feedback from audits can also influence memory management in subsequent turns.
Our comparison therefore cannot disentangle the contributions of individual mechanisms and
their interactions to task performance and memory alignment. The deployment study provided
specific insights into how these mechanisms were used in practice, but could not establish their
independent causal contributions. Future work could combine stage-specific comparisons with
interaction tracing across turns to examine how memory mismatches are introduced, detected, and
corrected, and how these processes affect subsequent memory use.
Second, our cross-context findings are bounded by the task settings and study duration. The two
projects in the controlled study were chosen to share a technology stack and overlapping features
so that transfer could occur; this leaves untested how the system behaves when projects differ
enough that transfer should be suppressed. The overall difference in scope alignment between
MemoSync and Auto also did not reach statistical significance. The week-long deployment with nine
developers primarily provided accounts of everyday memory reuse, maintenance, and oversight.
Future work should examine more heterogeneous projects and longer collaborations to investigate
whether systems can continue to preserve useful experience, limit inappropriate transfer, and
sustain developers’ understanding of memory.
Third, MemoSync’s candidate extraction, transfer rewriting, and auditing all depend on the
judgment of the underlying model. Current language models tend to assign uniform priority to
instructions and to comply with them [51, 58], which is consistent with deployment participants’
feedback: to avoid errors, the system requested confirmation even for simple instructions. This
limits the system’s ability to judge the scope and severity of a memory change, and such judgment
is a prerequisite for adapting the division of initiative to developer feedback. Future work could
explore letting the model or a separate mechanism estimate a change’s impact and decide which
operations can proceed directly.
9
Conclusion
In this paper, we present MemoSync, a system for co-managing developer-agent metamemory
across sessions and projects. Informed by a formative study with 12 developers, MemoSync treats
agent memory as a shared, operable representation that pairs monitoring with control across
evolution, selection, execution, and impact, with explicit scopes to support cross-context reuse.
A between-subjects study (𝑁= 132) found that MemoSync participants achieved significantly
higher task performance than participants using automatic memory or static configuration and the

highest mean memory alignment, with no detected condition differences in perceived workload
despite increased monitoring and control activity. A week-long deployment with nine developers
further illustrated how co-management supported ongoing memory maintenance, cross-context
reuse, and the resumption of oversight after stepping away. Together, these findings highlight
memory as a continuing site of human-agent collaboration, where developers can understand and
shape how accumulated experience informs subsequent work. As agents become more capable
and autonomous, people may become less directly involved in task execution. We hope this work
serves as an exploratory step toward preserving human agency over what agents remember and
how those memories are applied across contexts.

B.3
Formative Study Data Analysis
All sessions were audio-recorded and transcribed verbatim. Two researchers independently coded
the transcripts using an inductive approach [53]. In the first pass, both researchers conducted
open coding, generating initial codes from participants’ descriptions of their actual practices and
artifacts without imposing predefined categories of memory problems. Example codes included
‘repeatedly re-explains project context,” ‘does not know which stored rule the agent follows,” ‘wants
confirmation before memory write,” ‘asks agent what it remembers,” ‘cannot see memory use during
generation,” and ‘cannot tell whether a memory affected the output.”
After independently coding the first four transcripts, the two researchers compared their codes,
discussed differences in interpretation, and merged overlapping codes into a shared codebook. They
then applied this codebook to the remaining transcripts, adding new codes when new phenomena
emerged and refining existing definitions through continued discussion. Recruitment and analysis
proceeded iteratively; we stopped recruitment after 12 participants when subsequent interviews no
longer produced new codes.
After coding was complete, we grouped the codes by the stage of memory use at which the
reported issue occurred; these stages were also how the walkthrough was organized. This yielded
five themes. The first concerned the representation of memory itself, including the sources from
which developers currently infer the agent’s memory state and how they want memory to be
organized, inspected, and modified (→F1). The remaining four corresponded to four stages of
memory in collaboration: how memory is created, updated, becomes stale, and transfers across
contexts, or evolution (→F2); how the agent determines which memories to use for the current turn,
or selection (→F3); how memory guides agent behavior during generation, or execution (→F4);
and how developers determine whether memory was applied correctly in the output, or impact
(→F5).
Within each theme, we further distinguished what developers could currently observe or adjust,
the resulting visibility and control gaps in existing practices, and the forms of support participants
wanted. This analysis produced the five findings reported in the main text and informed the
corresponding design goals. Participant counts reported in the paper (e.g., N=12) indicate the
number of participants whose transcripts contained at least one code supporting that observation.

C.2
Condition Performance Relative to the Baseline
The agent-only runs also provide a reference point for the three conditions. Averaged over the four
sessions, the agent alone scored about 50% of the maximum with no memory and no developer
involvement. Participant outputs were scored with the same evaluator and judge, so the overall
scores in Table C2 can be read against this reference. Auto participants scored 47.7%, slightly below
the agent-only runs; Static participants scored 51.1%, on par with them; and MemoSync participants
scored 59.8%, about ten percentage points above.
Auto participants could iterate over multiple turns, yet automatic memory brought no net gain.
The memory injected into each session consisted of high-level summaries produced by the extraction
pipeline, and the storage cap replaced accumulated detail as new items arrived. Participants could
neither see nor edit what was injected, so stale decisions from earlier sessions could be carried
forward uncorrected. Static preserved the full detail that developers and the agent had written into
the Markdown file, but offered no mechanism for deciding which of it applied to the current turn,
and its benefit stayed close to the agent-only level. MemoSync’s advantage came from both sides
of this trade-off: retained memory kept its detail because developers confirmed the content and
scope, and each turn injected only the items selected for the current task. The agent-only runs
were single-shot and involved no developer, so this comparison is descriptive and we did not test it
statistically.

Task Specifications and Evaluation Rubrics
D.1
Task Specifications
The two study projects are tasks 000038 (apartment rental) and 000098 (car rental) from FullStack-
Bench [38].14 Each benchmark task provides a natural-language instruction and three sets of official
test items: UI test tasks, each consisting of a user action and an expected result; backend API test

each official instruction by functionality into two session briefs. In the apartment-rental project,
Session 1 covers apartment browsing, search, and filtering, and Session 2 adds booking and booking
records. In the car-rental project, Session 1 covers car browsing and booking, and Session 2 adds
payment and order management. The theme-color requirement of each task was placed in the
Session 1 brief, and each Session 2 brief asked participants to extend the existing implementation
while preserving its functionality and visual design.

E
Implementation Details
Section 4.6 describes the orchestration in Figure 9. This appendix adds the implementation details
behind it.
E.1
Technology Stack
The frontend uses React 19 and TypeScript 5.8, and the backend runs on Bun (v1.3.5+). The main
agent session is created through the Claude Agent SDK’s query() interface, which accepts an
asynchronous prompt queue, session fork handles, system prompts, MCP server configurations,
and tool permissions. For the Codex backend, memory tools are converted into Codex dynamic
tools, and the Memory Block is injected into developer_instructions at the start of each turn.
Both backends support session forking.
E.2
Forked Branches and Speculative Precomputation
Beyond prompt-cache reuse, running memory operations as forked branches has two further effects.
A branch sees the full project context accumulated in the main session, and it keeps the coding
agent’s tools, so it can read files or run commands to verify a proposal against the actual codebase
instead of reasoning only from what is already in context.
The three branches in Figure 9a start at the same time, and downstream branches do not wait
for upstream reviews. While the developer reviews candidates, the transfer and memory-change
branches have already completed their analyses. Each review decision reaches the downstream
branches as a short follow-up message in their own conversations. Because a branch already holds
its analysis in context, it only needs to output what changed, so each review step is followed by
one brief model call rather than a fresh analysis.
E.3
Working-Memory Selection and Context Isolation
After the approved changes are persisted, a further branch selects the working memory for the
current turn from the updated store and produces the expected-use statement for each selected
item. All memory reasoning thus happens in branches. The main session grows only by the user
prompt, the Memory Block, and the agent’s reply, so memory co-management adds no reasoning
transcripts to the main context.
E.4
Citations and Audit
Memory citations are not tool calls. The system prompt instructs the coding agent to cite a memory
item by writing its identifier in square brackets, such as [M-07], whenever it acts on that item. The
frontend parses the streamed reply for this fixed pattern and renders an inline citation only when
the identifier matches an item in the store. When the developer interrupts a run, the corrective
prompt continues in the same main session, with any item marked Enforce this run attached.
The audit branch forked after the turn serves context isolation only: it runs after execution, so it
gains nothing in latency, but its output stays out of the main session.
