Abstract
We present ExtractBench Pro, a schema-guided document extraction benchmark that tests six challenging modes of
extraction underrepresented in existing datasets. It is created following a framework for synthetic document generation,
in which deterministic document generators assemble challenging components into documents that are designed to be
difficult at a level calibrated for frontier systems. We synthesize 100 realistic documents spanning a diverse range of
styles. On this data, we evaluate ten coding agents and eight extraction API configurations for accuracy, grounding,
and their ability to perfectly extract documents. No extraction system extracts more than 61% of documents error-free.
The strongest general-purpose coding agents, Claude Code Opus 5.5 and Codex GPT-6 Astra, outperform specialized
extraction APIs on both perfect-document rate and Value F1, but at a higher cost per page. Among specialized extraction
APIs, LlamaExtract spans the lower-cost frontier, with Agentic Plus Max Effort approaching the strongest coding agent
on both perfect-document rate and Value F1 at lower cost per page. Our analysis of coding agent traces identifies
intelligent image processing and programmatic reasoning, but also failures in applying document-specific definitions
and recovering relationships from diagrams. We release ExtractBench Pro and these evaluation results as resources for
the future development of improved frontier extraction systems.

Introduction
An initial task in many automated document processing
workflows is to convert an unstructured PDF document
into a structured JSON object, while following a schema.
It enables valuable automation in domains such as fi-
nance, legal, and manufacturing, on documents such as
tax forms, case filings, and spec sheets. However, the
standard of quality needed for many of these applications
is perfection. Mistakes incur costly additional human re-
view and correction, especially if they are not caught until
later in a workflow. Therefore, accuracy and price, in that
order, tend to be the most important metrics to measure in
the task of schema-guided document extraction.
Accuracy is measured, sometimes alongside cost, on
benchmarks such as ExtractBench [25], LongArray-
Extract [6], and VAREX [2]. Each benchmark typically
targets a set of challenges representative of a specific set
of real-world extraction workloads. However, many ex-
tractors now rank above 95% on the headline metrics of
most existing benchmarks [7, 15], driven by advances in
vision language models (VLMs) and their harnesses. De-
spite this, many real-world documents still suffer poor ex-
traction performance, even with the most powerful mod-
els. Domains such as engineering and planning feature
documents containing non-textual elements like relational

diagrams, charts, and maps. Private documents also tend
to have custom terminology and interpretation rules that
change the meaning of even textual elements. This con-
stitutes a long tail of document extraction, and a gap in
existing benchmarks that makes it difficult for practition-
ers to assess which extractor is best suited to real-world
applications. A benchmark is needed that can controllably
target challenges in the long-tail gap, at a difficulty level
appropriate for evaluating frontier systems.
In this work, we present ExtractBench Pro, a bench-
mark for the long tail of document extraction. To meet
frontier benchmarking needs, it is constructed following a
framework for synthetic document generation, using cod-
ing agents to write deterministic generators that produce
documents, schemas, and ground truth extractions from
simple inputs. We refer to real-world long-tail documents
to design a set of reusable components that can be instanti-
ated into elements which are challenging to extract. These
elements are composed to form documents, with precise
control over style and difficulty. The resulting dataset con-
sists of 100 documents split into six challenge groups:
interpretation rules, custom terminology, conditional ag-
gregation, relational diagrams, charts and maps, and long
single pages.

agents on ExtractBench Pro.

Related Work
Methods for Document Extraction.
Single-pass ex-
traction involves a general-purpose or specialized VLM
reading the document and generating its output without
iterative inspection. Context and output limits are chal-
lenges for long tasks [8, 17] such as those found in this
work, excluding these approaches from our evaluation.
Coding agents combine a VLM with a general-purpose
harness and tools. Applying those tools toward document
extraction, an agent can inspect documents repeatedly,
compute intermediate results, access files, and revise its
outputs. Codex and Claude Code accept the document and
schema as files and can use code to navigate pages, pro-
cess records, and check a candidate answer [1, 18]. These
operations are relevant when evidence is distributed, or
requested values require calculations. However, repeated
inspection and computation increase cost and may delay
completion.
Meanwhile, specialized extractors provide managed
workflows for document processing and structured out-
put. Services such as Datalab, Extend, LlamaExtract, and
Reducto handle document ingestion and schema-guided
extraction through an API; some also return source loca-
tions [3, 5, 16, 20]. We evaluate these services alongside
coding agents to measure how their different approaches
handle the same combinations of reasoning, visual inter-
pretation, and long-document navigation.

for
Document
Extraction.
Early
document-extraction benchmarks evaluate a single pre-
defined set of fields. FUNSD and SROIE study forms
and receipts [10, 11]; Kleister extends extraction to long
documents [23], while DocILE and RealKIE add business
layouts, line items, and enterprise domains [22, 24].
Schema-guided benchmarks test whether systems can
adapt to a set of fields provided at extraction time. Contex-
tual AI’s ExtractBench emphasizes schema breadth and
nested outputs [8], ExStrucTiny examines reformulated
requests and answer localization [21], and VAREX and
UniKIE-Bench vary schemas, layouts, and document con-
ditions [2, 12]. LongArray-Extract tests recovery of com-
plete record arrays as their length, formatting, and page
organization vary [6].
LongExtractionBench evaluates
completeness and execution failures on long reports and
filings with large, repeated tables [17].
The main basis of this work, ExtractBench, extends
schema-guided evaluation across varied extraction tasks
and document conditions [25]. It introduces the simulta-
neous evaluation of systems along value accuracy, source
grounding, and cost. Table 1 compares their challenge
coverage and evaluation measures.
ExtractBench Pro
builds on these evaluation axes to target the long tail of ex-
traction tasks that remain difficult for frontier systems. We
use controlled synthesis to calibrate task difficulty while
preserving realism and diversity.
Synthetic
Document
Generation.
Synthetic
docu-
ments support evaluation by pairing known ground truth
with controllable content and presentation. They let one
construct rare or difficult cases that are hard to collect,
and vary selected properties while holding others fixed
to isolate failure causes, as VAREX does with document
representations [2]. The challenge is to achieve this con-
trol while capturing the diversity and fidelity of real-world
documents.
Prior work has progressed from layouts mined from
real documents to configurable components and schemas,
as in DocCreator and FlexDoc [4, 13, 19]. Achieving re-
alism through these approaches depends on increasingly
sophisticated construction rules. DocGenie and DocD-
jinn use reference images to guide VLM-generated con-
tent and layout, with DocDjinn also producing task an-
notations [9, 14]. This offers flexibility, but generative
models within document generation can introduce hallu-
cinations and reduce reproducibility [9]. Our approach
uses coding agents to make sophisticated generation pro-
grams practical to implement and refine, grounded in real
documents. The resulting programs jointly produce doc-
uments, schemas, and annotations through deterministic
execution, with configurable content and presentation that
let us compose difficult tasks for frontier extraction sys-
tems.

Controllable Synthesis of Extrac-
tion Tasks
To evaluate targeted extraction challenges, we need tasks
that reflect real documents and whose content and pre-
sentation can be varied to control difficulty. We intro-
duce a synthesis framework that turns structures and con-
ventions from real documents into configurable genera-
tion programs (Figure 2). We first formalize the extrac-
tion task (Section 3.1). The framework uses a hierarchy
of reusable elements, pages, and documents to control
content and presentation, while jointly generating docu-
ments, extraction schemas, and annotations from shared
data (Section 3.2). Coding agents implement and refine
these programs using real references and validation feed-
back (Section 3.3).

3.1
Task Definition
Given a PDF document and a user-supplied JSON
schema, an extractor system must return all requested val-
ues and records that are evident from the document, in the
form of a JSON object. The schema specifies the fields,
types, and descriptions; the document supplies the evi-
dence needed to determine their values. Descriptions may
include clarifying information such as instructions for for-
matting, when to extract null, or even restrictions on what
counts as evidence. Each scalar value (null, text, num-
ber, boolean) in the extracted object may also be anno-
tated with one or more page indices or bounding boxes
indicating where the evidence for that field is located in
the document.
3.2
From Real Documents to Synthetic
Tasks
Grounding in real documents.
Real reference docu-
ments guide both the structures we reproduce and the in-
formation we ask an extractor to recover. We encode their
layouts and interpretation conventions in reusable, deter-
ministic programs called generators. Each generator pro-
duces a family of tasks with related schemas.
When executed, a generator begins by filling a fictional
underlying data model according to a generator-specific
schema. This data model supplies both the values pre-
sented in the document and the ground-truth extractions.
Hierarchical composition and control.
The document
is populated from the data model and assembled follow-
ing a multi-level hierarchy. This separation allows con-
tent, visual style, and evidence placement to vary within
reusable structures:
• Elements. Reusable document components such as ta-
bles, charts, diagrams, and prose are instantiated with
data from the data model and styling from the con-
figuration.
We render components using SVG and
HTML/CSS. These components are shared across mul-
tiple generators.
• Pages and sections. Layouts arrange elements into
pages and sections, controlling where related evidence
appears. Additional flavour text and brand-identifiable
elements inspired by reference documents are fiction-
alized and regenerated by the generator to protect the
anonymity of the original source. Pagination can cause
tables and prose to be broken across pages, which can
add extraction difficulty.
• Document.
At the top level, the pages are assem-
bled, potentially with perception-related transforma-
tions, and rendered as PDFs.
4


Joint generation from shared data.
Using seeded ran-
domness, the generator selects names and categories from
predetermined fixed pools, and samples dates and numeric
values within configured ranges and domain constraints.
The document, extraction schema, and annotations are
generated jointly from this data model. Derived values
are traced in deterministic code, making their derivation
reproducible even when extraction requires multiple rea-
soning steps. Different seeds and configurations produce
instances with varied records and presentation.
3.3
Generator Development with Coding
Agents
Constructing a generator requires encoding a document’s
layout, content, and interpretation rules in reusable code.
Coding agents make this practical across diverse docu-
ment families by adapting the generation program to the
details of each reference. They inspect real documents,
implement reusable components and layouts, execute the
generator, and refine its code by comparing rendered out-
puts with the references. This process combines atten-
tion to document-specific detail with explicit controls over
content and presentation.
We explicitly supervise generator development through
task requirements and validation feedback. Coding agents
depend on these external signals to determine what to re-
produce and which outputs are acceptable. First, we pro-
vide the agent with reference documents and a description
of the intended document, extraction schema, or reason-
ing required for extraction. Within the joint-generation
structure and hierarchy described in Section 3.2, the agent
develops the data model, rendering components, and an-
swer logic needed for that document family.
Second, we specify validation criteria for the intended
use case and use an ensemble of verifiers to assess gen-
erated outputs. We combine programmatic checks with
agent and human review to assess visual fidelity, schema
validity, and whether the rendered document supports the
ground-truth extractions and evidence annotations. We
return verification failures as feedback, which the agent
uses to refine the generator’s visual fidelity and task be-
havior. The resulting program encodes the rendering and
answer-computation logic explicitly. We then execute it
to generate further instances deterministically while vary-
ing their records and presentation. Section 4 describes the
requirements and selection criteria used to construct Ex-
tractBench Pro.

4.1
Benchmark Construction
Design goals.
We construct ExtractBench Pro around
three goals: realism, diversity, and difficulty. Documents
should reflect real extraction use cases, and schemas
should express realistic information needs. Tasks should
vary across domains, layouts, and reasoning require-
ments, while remaining difficult for frontier systems and
answerable from the document and schema. Suitable dif-
ficult documents are scarce, access can be restricted by
privacy and intellectual-property constraints, and manual
annotation can introduce errors. Synthesis allows us to
control task difficulty and generate annotations from the
underlying data.
Challenge mining.
We direct coding agents to conduct
an automated search through real documents, published
definitions, and schemas for structures and interpretation
conventions that pose extraction challenges.
These in-
clude document-specific rules, dependencies across sec-
tions, and visual structures that require precise reading.
For terminology tasks, we also probe frontier models on
candidate rule sets and retain the sets that produce the
most errors. We adapt the selected rules for aggregation
tasks.
Task construction.
Using the framework in Section 3,
we prompt coding agents in parallel to implement gen-
erators across domains and document types.
The gen-
erators share a bank of configurable components derived
from the mined references and jointly produce documents,
schemas, and annotations. We compose challenges so that

We run an ensemble of pilot ex-

We target tasks

rendering failures. These findings guide revisions to the
generators and tasks.
Dataset composition.
The resulting benchmark con-
tains 100 PDF documents produced by 90 generators,
with 2,622 pages and 144,141 expected scalar values. It
spans 7 domains: finance, energy, government, supply
chain, healthcare, law, and real estate. Each document is
paired with a JSON extraction schema and ground-truth
output. Table 2 summarizes the six challenge groups and
their document, page, and field counts. Grounding an-
notations are available for 81 documents, with bounding
boxes covering 78% of expected values across the bench-
mark.

Evaluation Metrics
Value F1.
We reuse the ExtractBench scorer [25],
which aligns repeated records, normalizes values, and
compares scalar fields with the expected output. A value
is correct if it matches the expected value or an accepted
alternate after normalization. For a document d, let Cd be
the number of correct scalars, Md the number of predicted
scalar fields, and Gd the number of expected scalar fields
in the ground truth. Then Value F1 is

We report the mean across documents. Failed or empty
runs score zero, as do late runs under the main scoring
cutoff (Section 5.1).
Perfect Value F1.
Perfect Value F1 reports the propor-
tion of 100 ExtractBench Pro documents with no scored
value errors (that is, F1,d = 1). Intuitively, it represents
the proportion of documents that the user of an extrac-
tor system may expect to need no corrections. An error
in any part of a document prevents a perfect score, even
when many other fields are correct.
Grounding F1.
Grounding F1 is computed similarly to
Value F1, but a scalar counts as correct only if it satisfies
the Value F1 rules and is correctly grounded according to
the ExtractBench scorer [25].
Cost per page.
Cost per page is measured using a docu-
ment’s recorded total cost in USD (including spending on
failed and late runs), divided by its page count. Across
the entire dataset, we follow ExtractBench conventions
and macro-average this across all documents with equal
weighting per document.

5.2
Overall Results
Overall, the top extraction systems on ExtractBench Pro
extract at most 61% of documents perfectly: 61 by Claude
Opus 5.5, 59 by Codex GPT-6 Astra, and 56 by Lla-
maExtract Agentic Plus Max. Interestingly, it is not the
same documents which are extracted perfectly by all sys-
tems, demonstrating clear advantages and tradeoffs be-
tween systems; combined, 84 documents are extracted
perfectly by at least one of the 3 aforementioned systems,
and 91 by at least one of the 18 systems evaluated in this
paper. Therefore, there is room for future advancements
combining those strengths to surpass the 61% frontier.
For comparison, applying ExtractBench’s 30-minute
scoring cutoff to the same saved outputs reduces Opus’s
Perfect Value F1 from 61% to 51%, and Value F1 from
93.1% to 75.4% (Table 7). All extraction APIs except
Datalab retain their scores under this cutoff, consistent
with their generally lower latency, while non-Codex cod-
ing agents incur the largest accuracy losses.

Separating results by challenge group explains why no

5.4
Trace Analysis
We inspected saved tool calls, generated scripts, and inter-
mediate outputs by coding agents. The agents constructed
sophisticated task-specific programs that combined ex-
tracted observations with document-defined rules. For ex-
ample, on a fund-structure document, Codex Astra tran-
scribed ownership relationships from handwritten dia-
grams, extracted funding amounts from tables, and prop-
agated contributions through the resulting structure using
exact-decimal arithmetic.
Visual extraction also involved explicit measurement
and image processing. On a scanned time–location chart,
Astra corrected image skew, traced activity lines, and
mapped their endpoints to the document’s week and dis-
tance rulers. It then used geometric intersections to calcu-
late progress and crossing counts.
Despite these impressive programs, coding agents are
still susceptible to multi-hop reasoning, as a single mis-
take made at any stage is enough to render the resulting
extractions incorrect. A common mistake that triggered
this failure was the incorrect interpretation of a rule, such
as inclusion in an aggregation condition.
Coding agents also still struggled to provide evidence
8


for derived answers. Systems are biased towards citing
labels that appear in literal form in the document, while
omitting calculated fields. A correct grounding of those
answers would require identifying the many source values
and rules used in the calculation.
5.5
Realism
To evaluate the realism of the generated documents, a
small study was conducted asking six non-expert volun-
teers to compare ExtractBench and ExtractBench Pro to
real customer-submitted documents sent to a specialized
extraction API. The study presented the user with a pair
of pages, consisting of one page sampled from real ex-
traction traffic, versus one page sampled from the dataset.
Each participant was asked to identify the real page, or ab-
stain. Detection rates were 23.8% for ExtractBench and
37.9% for ExtractBench Pro. Therefore, while Extract-
Bench Pro documents are easier than ExtractBench to dis-
criminate from real documents, it is still well below 50%
(a random coin toss), demonstrating a reasonable degree
of realism.
From qualitative inspection of the pages, the main gaps
of fidelity were found to be handwriting and the lack of
brand intellectual property such as logos. Synthetic hand-
writing was easy to distinguish from real handwriting due
to the use of fonts. Meanwhile, brand IP is questionable
to use in fake documents due to privacy and confidential-
ity concerns, and was deliberately avoided in this bench-
mark.
6
Conclusion
We introduce ExtractBench Pro, a benchmark of 100
documents built using configurable, deterministic docu-
ment generators. This approach lets us compose extrac-
tion challenges that remain difficult for frontier systems
while generating documents, schemas, and ground truth
together. The strongest system extracts only 61% of docu-
ments perfectly, while specialized tiers such as LlamaEx-
tract narrow the accuracy gap with general-purpose cod-
ing agents at lower per-page cost, and the three leading
systems collectively succeed on 84%, suggesting room
for improvement by combining their strengths. Our trace
analysis shows that coding agents can perform sophis-
ticated visual measurements and computations, yet still
fail through incorrect interpretation of document-specific
rules. These results motivate extraction systems that can
reliably identify and carry those rules through every step
of a task, alongside benchmarks that measure complete
document extraction rather than average value accuracy
alone.
Limitations.
Pilot performance influenced document
selection, and some of those same extractors were then
evaluated on the same dataset. Despite being composed of
realistic elements, challenge-dense documents do not rep-
resent ordinary workloads. Diversity was not measured,
nor was human extraction performance studied. We re-
port one result per system and document, so variability
was not studied.

B
Generator Details
B.1
Sources of the Challenges
With the goal of identifying challenging document elements and patterns, we asked coding agents to inspect real
documents, published definitions, and extraction schemas. The agents recorded where the information needed for an
answer appeared, how records were linked across pages, and which rules affected their interpretation. After running
a set of pilot extractors on a selection of those documents and schemas, we identified incorrect or missing fields and
traced each error back to the relevant pages and schema. This let us describe candidate reasoning paths a reader might
have to follow, such as finding an amendment before deciding which version of a table to use. Moreover, we could
predict likely errors an extractor might make if it fails to follow the entire reasoning path. For example, when a value
is amended, returning the pre-amendment value would suggest that the extractor missed or misapplied the amendment.
Targeting those candidate reasoning paths, we turned those observations into candidate extraction tasks, using cod-
ing agents to produce document generators following the same method described in Section 3.3. Pilot extractors
extracted each of the candidate documents, and the coding agent’s goal was to make the pilot extractor fail. After
enough attempts, if a likely failure could not be induced in enough extractors, then the candidate reasoning path was
rejected as not challenging enough.
At the same time, towards visual fidelity, agents gathered examples of layouts, tables, and styles of the reference
documents, so we could reproduce similar diversity later in our synthetic documents. We ran pilot extractors, including
coding agents and specialized extraction APIs, on the generated PDFs and their schemas. We compared their outputs
with the expected answers and inspected errors on fields that depended on the element. Where possible, we computed
the answer under a simpler reading and checked whether it explained the observed errors. We also checked for
ambiguous instructions, wrong annotations, and rendering defects. The pilot results helped us decide which designs
to keep and which to revise and test again.
B.2
Challenging Elements
The result of the investigation in Appendix B.1 identified the following collection of elements and features which were
most successful at inducing extraction difficulty. The elements and transformations below can be combined in a single
document and reused across challenge groups.
Some elements create difficulty by inducing multi-hop reasoning:
• Rules. A rule tells the reader how to interpret context elsewhere in the document. In our reference documents, they
are found in the form of legends, units, exclusions, and amendments, and so on. Difficulty can be increased by
placing them in faraway sections during document assembly.
• Jargon. Document-specific definitions can override familiar meanings of terms, or clarify otherwise vague words.
For example, in one grain trade rule, “prompt” shipment means within ten calendar days. Useful terminology is
found by searching domain-specific terms, or common patterns of internal organizational jargon. To verify the
difficulty, we wrote short questions about candidate terms and asked models to answer them without the governing
definitions. Then, to exploit that difficulty, we created rules that would force a model to use an interpretation it is
not used to.
• Aggregation. Rather than copying the value from a page, aggregation combines multiple values into a single
derived value such as by counting or summing them. This is frequently found in real requests encountered by
extraction services. It can be made more difficult by setting conditions on which values contribute to counts and
sums (e.g., which ballots count as valid). This can be done through rules supplied by the schema or the document.
Other elements require careful visual precision to interpret:
• Handwriting. We use eight open-license handwriting-like fonts to fill in handwritten fields in synthetic table and
note templates.
• Charts and maps. Extracting values from a chart or map requires precisely identifying the position of a mark
relative to axis markings. We found many examples of such charts and maps in the reference documents, and
developed component implementations to recreate each of them. To stay compatible with the ExtractBench task
format, which has a finite set of accepted values per field, we discretize these extractions into a choice between
predetermined intervals aligned with axis ticks.
23


• Relational diagrams. Many diagrams in real documents are relational diagrams, which use lines (edges) to show
how entities (nodes) are connected. Examples of these include family trees, electrical circuits, and water networks.
Relationships can be directional, or labelled with various types and quantities. We integrate these into larger multi-
hop reasoning chains by introducing inferred relationships, or derived values that are conditional on relationships.
• Extreme aspect ratios. We take inspiration from document formats designed to be printed as continuous sheets,
including wireline logs and railway track charts. The resulting PDFs would be several metres long if printed, so a
full-page view can make the contents too small to read, while a crop can lose long-range context like axis scales.
Finally, a set of perception-related transformations can be used to create obstacles and distractions that must be
handled before the document can be cleanly processed.
• Scan artifacts. The way that a document is physically materialized and digitized can make it more difficult to
visually interpret a page. Faded toner, for example, can make small text hard to distinguish from the background.
We recorded skew, fading, and bleed-through while inspecting reference scans. Our capture recipes simulate scan-
ner, photocopy, fax, aging, and phone-photo effects. To ensure that text is still legible, a readability gate checks
evidence-text size and contrast and reduces degradation when needed.
• Unreliable scans. A scanned PDF can contain an invisible OCR layer added by the scanner that differs from the
visible page. For example, it might record a zero as the letter O, or vice versa. A system relying on the hidden
text can therefore return a wrong value from an otherwise legible page. To simulate unreliable scans, we randomly
substitute letters in simulated text layers with commonly mistaken alternatives that have similar glyphs.
• Page arrangement. In practice, scanned documents are assembled by humans who may introduce duplicated,
rotated, misplaced, or unrelated pages by mistake. Sometimes, scanners combine multiple pages together in a
single image. A reader that blindly trusts such a PDF to represent a page-by-page structure may produce incorrect
extractions. We noted places in reference documents where separate subdocuments were bundled together and
where page numbering restarted. Then, we reproduced these features in synthetic documents by sampling random
swaps, duplications, insertions, and compositions.

B.4
Validation
We check that the rendered document supports the expected answers. Text checks compare quoted evidence with its
assigned page region. For graphical readings, some checks use specially modified rendering. For example, a second
wireline-log render assigns distinct colours to curves so that the requested grid-cell readings can be verified more
easily.
When the printed instructions support more than one interpretation of the schema and document, we require the
ground truth to accept the answers corresponding to each supported reading. Additional readings were often discovered
at the pilot extractor stage of validation. The generator implementations support this by computing answers for all
acceptable readings from the same underlying data model.
C
Evaluation Protocol
C.1
Systems and Data Versions
All evaluated systems received the same PDF and schema for each document. Coding agents ran through vendor
command-line tools in an isolated working directory containing those files. They could use local tools, with network
access restricted to the model API, and were prompted to return the page and box supporting each value. Codex
GPT-6 Astra used the highest reasoning setting, GPT-6.1 Sol the lowest, and GPT-6 Luna and GPT-6.1 Terra the
medium setting; Muse Code ran Muse Ember 1.0 at the high setting; Gemini CLI ran Argon at medium thinking
and Hydrogen at high thinking with vision enabled; Claude Code used medium effort for Opus 5.5, Sonnet 5.5, and
Haiku 5.5. Extraction APIs received the inputs through their public interfaces with evidence enabled where available.
LlamaExtract’s Agentic Plus and Agentic tiers, Datalab Accurate (with phrase-level citations), and Reducto Deep use
their November 2026 releases; LlamaExtract Agentic Plus Max Effort uses the published November 2026 run; Extend
Operator and Pulse Effort use the October 2026 snapshot.
The main results use a consistent three-hour execution limit per document, including retries. The selected runs
include the successful repairs of the earlier one-hour Sonnet and Muse timeouts. Saved predictions are evaluated
against the same answer key and scorer revision.
Failed and empty runs remain in the accuracy denominators. Completed outputs beyond three hours also score zero.
The 30-minute comparison uses the same selected outputs and changes only the scoring cutoff.

Cost and Latency
We use prices per page from the public ExtractBench Pro leaderboard. For Claude Code Haiku and Muse Code Ember,
we average the recorded cost per page across documents.
Page count can understate the work required by an oversized chart. Each long chart sheet counts as one page, so its
cost per page equals its cost per sheet. The most expensive sheet cost Codex GPT-6 Astra $20. Latency is recorded

E
Failure Cases
E.1
Case Selection
The qualitative case review focuses on documents for which completed outputs disagree. For each challenge, we
originally selected the three documents with the largest Value F1 spread among finished runs in the initial twelve-
system snapshot. For the examples below, we inspect the outputs selected for the reported evaluation, comparing
returned values with the answer key and, for coding agents, inspecting the final message. They distinguish what was
returned from what the error pattern suggests.
E.2
Examples
Interpretation rules.
The reviewed outputs omit records. On the patient record, Luna returned 91 of 1,277 result
rows and stated that it had included only the first weekly report. On the investor report, Reducto returned only one or
two revenue rows per company where the document contains up to 52.
Custom terminology.
Several errors occur on fields whose meanings are defined locally. On the import-duty rec-
onciliation, one reviewed Codex output matched the ordinary reading rather than the packet’s definition, while Sol
returned null for every duty and refund field. On the spread-betting account, Luna stated that the settlement schedule
and definitions appendix were absent and left the computed fields null. Sol’s race points were wrong by exactly one
on 29 of 58 lines, consistent with substituting decimal odds for odds to one. On the subscription-seat review, Reducto
classified three unpaid order forms as paid. These patterns locate the errors without proving which definitions a system
read.
Conditional aggregation.
Incorrect totals reflect both rule application and transcription problems. In the election
packet, short ballots belong in the district total but not the valid-ballot count. Sol assigned between 1,816 and 2,573
additional ballots to the valid category in every district. On the library-aid claim, Luna matched neither the defined
count nor the simplified count. It also misread a month code in the scan. On the engine-utilization return, Sol
overcounted cycles in every month, consistent with missing exclusions.
Relational diagrams.
The reviewed outputs leave diagram-dependent fields unanswered. On the HVAC balancing
report, Luna left all 72 per-floor values null and stated that it could not resolve the totals from the diagram. On the
fiber-splice record, Extend listed every circuit but returned null for splice counts, losses, and lengths.
Charts and maps.
The reviewed chart cases contain incorrect readings or selections, but their causes are not always
identifiable. On the tower-coverage credit, Sol’s zone counts disagree with the expected counts from the coverage
map. These patterns suggest chart or map-reading errors but were not all verified through page inspection.
Long single pages.
Empty outputs can arise from both provider restrictions and unsuccessful extraction. Datalab
rejected two reviewed sheets because their width exceeded 7,200 pixels and returned null for every value on the third,
while Extend completed all seven sheets without a reported execution error but returned only null values. These
outcomes all receive zero, but a provider rejection is distinct from an incorrect reading of an accepted input.
