# EGO USE BENCH : Benchmarking Computer-Use Agents under Evolving First-Person Contexts 

> Yurun Chen, Biao Yi, Qihang Yu, Keting Yin, Shengyu Zhang

Zhejiang University   

> Project Page Code Dataset

Abstract 

AI wearables, such as smart glasses, extend the context available to agents beyond digital environments to users’ everyday physical surroundings. With these devices, computer tasks can originate from users’ ongoing real-world activities rather than solely from explicit instructions. Through first-person observations, agents can identify objects and activities relevant to user requests and ground digital tasks in the surrounding context. We call this interaction paradigm Ego Use . However, first-person observations are limited by the wearer’s viewpoint and may provide incomplete or ambiguous evidence of ongoing activities. As new observations arrive, agents may need to revise their understanding of the physical context and user intent, and reassess whether prior digital actions remain valid. Whether current agents can reliably handle these changes remains insufficiently evaluated. We introduce EgoUseBench, a benchmark for evaluating Ego Use across three interaction settings with different levels of first-person context. Computer-Use relies on explicit instructions, Offline Ego Use provides prerecorded first-person context before execution, and Online Ego Use provides continuous observations as user intent evolves. Based on over 74 hours of real-world first-person recordings, we construct 693 tasks across the three interaction settings. To capture task evolution, we track first-person observations, user requirements, and website state separately. We further group tasks by how information changes during execution, resulting in three types: Graft (revised user requirements), Refresh (new first-person observations), and Clarify (agent-initiated information seeking). We evaluate several advanced models and find that average success rates in Online Ego Use are 26.3% lower than in Computer-Use. This result reveals the difficulty of keeping task execution aligned with evolving first-person context and user intent. 

1 Introduction 

When a user asks a personal assistant to “ find one like this, ” the request may depend as much on what the user sees as on what they say. First-person AI wearables, such as Ray-Ban Meta and Looki L1 [1, 2], provide visual context to help assistants understand such requests. With this context available to the agent, users can refer directly to objects and activities around them, without describing the scene in detail or translating their needs into explicit digital instructions. The agent then grounds the user’s instruction in the first-person context and uses it to guide digital actions. We define this interaction paradigm as Ego Use .Figure 1 illustrates three interaction settings distinguished by the availability of first-person context during task execution. (1) Computer-Use: agents perform computer tasks through graphical user interfaces based on explicit user instructions, which may include descriptions of task-relevant context [3–8]. (3) Online Ego Use: agents receive continuous first-person observations during task execution, while user intent may evolve through ongoing interaction. They must therefore continuously update their understanding of the physical context and user intent, and adapt their digital actions accordingly. However, existing benchmarks provide limited evidence on reliable task execution in this dynamic first-person setting. Online Ego Use poses challenges in grounding incomplete observations, tracking evolving user intent, and adapting ongoing actions. Consider a user preparing a snack who asks an agent to add the tortillas they are using to an online grocery cart. However, the first-person view captures only part of the package, leaving the exact product uncertain. The agent must infer the intended item from incomplete visual evidence rather than rely on an unambiguous view ( Context Grounding ). As the user subsequently asks it to add a spread as well, the agent must interpret this follow-up in relation to the ongoing task and maintain a coherent understanding of the user’s evolving intent ( Intent Continuity ). Crucially, subsequent observations may reveal that the initially selected tortillas do not match what the user is actually using, requiring the agent to revisit its earlier interpretation and determine whether its previous selection should be replaced ( Execution Adaptation ). New evidence or revised requirements can change which earlier choices remain valid, while the website retains the effects of actions already taken. This motivates our central question: Can agents reliably complete computer tasks as first-person observations and user intent evolve during execution? 

We introduce EgoUseBench, a benchmark built from over 74 hours of real-world first-person recordings. It comprises 693 tasks across three interaction settings, including 293 Online Ego Use tasks, 200 Offline Ego Use tasks, and 200 Computer-Use tasks. The tasks span three categories: product selection, tutorial retrieval, and place bookmarking. The benchmark has two key design features. (1) Asynchronous State Evolution. The environment maintains three evolving states: first-person observations, user requirements, and website state. Observations are replayed at fixed intervals, user requirements change according to predefined schedules, and website states evolve through agent actions. (2) Dynamic Information Updates. We introduce three mechanisms for information updates during task execution: Graft modifies user requirements, Refresh 

provides new first-person observations for revising prior decisions, and Clarify allows agents to seek additional information. These mechanisms capture user-driven changes, environment updates, and agent-initiated information seeking. We conduct extensive experiments on EgoUseBench with multiple advanced models to evaluate their 2performance across different interaction settings. Average success rates are 63.4% in Online Ego Use, 64.2% in Offline Ego Use, and 86.1% in Computer-Use, revealing a substantial performance gap between Ego Use and Computer-Use. We further examine how agents handle the information updates that distinguish Online from Offline Ego Use. Agents struggle more when new visual evidence invalidates an earlier choice than when it first reveals a target. More request changes do not consistently reduce success. Scene-change alerts and descriptions improve success, while longer visual histories offer no consistent benefit. These findings point to the difficulty of maintaining consistent decisions as first-person context and user intent evolve. Agents need to recognize how new information affects earlier choices and revise them accordingly. Our contributions are threefold. (i) Ego Use. To our knowledge, we are the first to introduce Ego Use, in which agents use first-person observations to interpret user requests and perform computer tasks. We distinguish Offline and Online Ego Use, with the latter involving evolving observations and user intent during execution. 

(ii) EgoUseBench. We introduce a benchmark of 693 executable tasks across three interaction settings. It models first-person observations, user requirements, and website state as separate evolving states, and supports updates to observations and requirements as well as agent-initiated clarification. (iii) Extensive Experiments. We evaluate multiple advanced models through cross-setting comparisons and execution-trace analysis. Our analysis reveals how information updates affect task success and the difficulty of keeping task execution aligned with evolving first-person context and user intent. 

2 Related Work 

Computer-Use. Computer-use agents carry out user-specified computer tasks through graphical user interfaces (GUIs). Mind2Web [3] introduced a large-scale dataset for web agents. WebArena [4], Visual-WebArena [5], and WebVoyager [6] study multi-step interaction and visual grounding across realistic web environments and live websites. OSWorld [7] extends evaluation to desktop applications and cross-application workflows. These studies advance interface understanding, task planning, and digital execution, with agents acting primarily on user-specified goals and feedback from the digital environment. 

Offline Ego Use. First-person video provides context for both understanding user needs and carrying out tasks. Ego4D [11] and EgoLife [12] advance long-horizon activity understanding and personal memory, while WAGIBench [13] studies how to infer user goals from multimodal context. Ego2Web [9] grounds web tasks in prerecorded egocentric video, and EgoBench [10] adds tool use and multi-turn user interaction. These benchmarks connect physical observations to digital actions, but provide the visual evidence in advance rather than updating it as the computer task unfolds. 

Online Ego Use. Recent work studies understanding and interaction under continuous first-person observation. EgoSAT [14] evaluates temporal reasoning over streaming video. Vinci2 and its EgoServe benchmark [15] study proactive assistance under continuous observation. ProactEgoMem [16] focuses on information capture and state tracking in streaming video, while OmniAssistBench [17] evaluates multi-turn interaction with multimodal assistants. These studies focus on understanding evolving context, offering timely assistance, or maintaining memory. EgoUseBench instead evaluates whether agents can reliably complete computer tasks while first-person visual information and user intent evolve during execution.

3.1 Task Definition 

The prompt asks the agent to complete the wearer’s request and describes the actions available across all task types: search or inspect the website, change its state, ask a question, or finish. To separate the effects of those actions from changes in the task, let 𝑥 denote the current website state and G the set of states that satisfy the resolved request. New visual evidence or a revised request can change G while leaving 𝑥 intact: 

(𝑥, G− ) −→ ( 𝑥, G+), (1) where G− and G+ are the acceptable states before and after the update. 

Refresh holds the request fixed. Its Replace subtype introduces visual evidence that invalidates an earlier choice, whereas Retain leaves that choice valid. Graft instead changes the user’s request. Refine adjusts the requested attributes or quantity, Augment adds a requirement while preserving earlier ones, Replace substitutes one requested choice for another, and Drop withdraws a requirement. 

Clarify presents multiple plausible referents for the wearer’s intended target. A reviewed reply to an agent question resolves the ambiguity without naming a website item. Position uses spatial location, Sequence uses temporal order, and Variant uses visible attributes such as color or size. Across all three task types, the agent must reach an acceptable final state within the step budget. 

3.2 Task Construction 

Design. We construct 293 Online Ego Use tasks, comprising 200 tasks based on Graft, Refresh, or Clarify and 93 tasks that combine them. We also construct 200 Computer-Use and 200 Offline Ego Use tasks for matched comparisons, keeping the websites and final goals fixed. Tasks are constructed from candidate activities in Ego2Web [9], CaptainCook4D [18], HD-EPIC [19], EgoOops [20], EgoLife [12], HoloAssist [21], and EgoSchema [22]. Source coverage is provided in the supplementary material. For Refresh, we select an observed change and hold the wording fixed, checking whether the later scene changes the answer. For 4Graft, we write a follow-up that edits a specific requirement at a plausible point in the activity. For Clarify, we select an opening scene with multiple plausible referents and write an answer that resolves the distinction. We review the entire replay window: the opening must support the request, and intervening frames must not reveal later evidence early. The request specifies what to accomplish on the website and under what constraints. The footage supplies the referent. Before selecting listings, we decide how closely a website item must match that referent. We use only the request to search for candidates. If the results all share an attribute that the agent should infer from the footage, we broaden the search so that the catalog alone does not determine that attribute.

> 3.3 Interactive Environment

Websites. We build local simulations of Amazon, YouTube, and Google Maps that reproduce the interfaces and interactions used in our tasks. The sites use publicly available product, video, and place information and support operations such as search, adding products to a cart, and saving videos or places. Agents are instructed to stay within these sites. Search ranks public fields with BM25. The rendered pages and agent-visible details use the same website data. Source annotations, answer roles, and evaluation labels are not exposed to the agent. Each episode starts from an isolated website state that persists throughout the interaction. 

Input. At each decision step, the agent receives three inputs: (1) first-person observations of the wearer’s surroundings, (2) the current webpage screenshot and accessibility tree, reflecting previous actions, and (3) user messages in their original wording, labeled by delivery step (Figure 3). Each decision permits one JSON action. Element-based actions use IDs from the current accessibility tree. Each active step advances the recording by 8 s of source footage, independently of model latency. Frames are sampled at 1 fps and normally tiled four per image. Task-specific single-frame layouts and image-size limits are fixed across models and conditions. Episodes allow up to 20 decision steps in the main evaluation and 30 in the composite evaluation (Section 4.5). 5Figure 3. (a) Inputs at an action step. (b) The three visual history conditions. The opening batch and the two most recent delivered batches are kept intact in all three conditions. Only the representation of older batches changes. 

Because information relevant to later decisions may appear in earlier observations, we retain a rep-resentation of each delivered batch, following prior work on visual-history compression in streaming assistants [23, 24]. All conditions preserve the opening batch and the two most recent batches in full. For older batches, as illustrated in Figure 3, we compare three history policies. (1) Full history retains all frames. (2) Compressed history, our de-fault, retains every other frame (0.5 fps) using the same task-specific layout. (3) Summarized history replaces each older batch with a short textual sum-mary generated by the acting model alongside its action. The summary becomes available only after the corresponding batch leaves the recent-history window. None of these policies uses task annota-tions to select frames. The Retention comparison in Section 4.4 varies this policy while holding frame sampling and observation delivery fixed. 

Delivery. The replay schedule sets when new information becomes available. Whether the agent is still working determines how it receives that information. (1) Concurrent change. During active execution, a Graft follow-up arrives with the batch containing its reviewed onset, and a Refresh change arrives with the later scene. The follow-up in Figure 2 arrives at step 4. To give the agent time to act after a Refresh change, we retain only the final 16 s of longer waits between scenes and exclude windows whose opening scene alone makes the change too late. The recording does not loop. (2) Wake-up change. If the agent finishes before a scheduled Graft follow-up, the episode enters standby. The follow-up resumes execution with the same website state. Standby consumes no action steps, and skipped batches are logged without being delivered. Later Refresh frames do not resume a finished episode. 

Questions. All Online task types allow a question. The first question in Clarify returns the reviewed reply before the next decision. In Graft and Refresh it returns no additional task information. Questions consume decision steps. The reply is fixed rather than generated from the question, so this interface measures whether the agent seeks clarification, not the quality of its wording. The supplementary material lists the full action interface and fixed replies.

4 Experiments 

Our evaluation addresses four research questions: RQ1: How reliably do agents complete Online Ego Use tasks? RQ2: How do success rates and token costs differ across Computer-Use, Offline Ego Use, and Online Ego Use? RQ3: Which online input conditions affect task completion? RQ4: How do agents perform under combinations of information updates? 

4.1 Experimental Setup 

(1) Models. We evaluate GPT-6.1 Terra [25], Gemini 3.8 Flash [26], Doubao Seed 2.1 Pro [27], DeepSeek-V4.1-Flash [28, 29], Kimi K2.6 [30], and qwen3.5-27b [31] using a shared BrowserGym action interface. We also evaluate the smaller UI-TARS-1.5-7B, with results in the supplementary material. (2) Evaluation protocol. 

The main Online evaluation uses 200 tasks from distinct recordings: 142 Graft, 30 Refresh, and 28 Clarify. Each task is run once per condition with up to 20 decision steps. Replay and compressed history follow Section 3.3. (3) Metrics. Our primary metric is success rate (SR), the fraction of valid runs whose final website state satisfies Eq. 3. Overall SR weights tasks equally. Paired comparisons report SR differences (ΔSR, %) with 95% confidence intervals. 

Task quality. To validate task quality, two independent reviewers examined 40 stratified tasks, including 32 main and 8 composite tasks. They checked whether the recordings supported the requests and whether the answer sets were correct and covered reasonable alternatives. Tasks accepted by both reviewers account for 90% of the sample. Detailed review criteria and task-type counts are provided in the supplementary material.

5 Conclusion 

We introduce EgoUseBench, a benchmark of 693 tasks across Computer-Use, Offline Ego Use, and Online Ego Use. Our analysis reveals two main difficulties in Online Ego Use. Agents struggle to identify the user’s intended target from first-person observations and to update website state as requirements change. In particular, they sometimes find a valid new option while retaining earlier choices that no longer satisfy the request. These findings point to a broader challenge in Ego Use. Agents struggle to keep their website actions aligned with the user’s current intent and evolving physical context. EgoUseBench provides a controlled testbed for studying this alignment. More broadly, Ego Use offers a research direction for bringing first-person agents into a wider range of everyday settings, where what people see and do guides computer tasks and agents adapt as circumstances change.

> A.2 Task Annotation

Visual grounding. Annotations identify the physical referent and the evidence needed to interpret each request. Object identity, attributes, actions, and temporal relations are specified at the level supported by the released frames. Exact commercial identities require distinguishing evidence beyond generic color or shape. Source events and authored user requests are annotated separately. Graft follow-ups express plausible changes to the wearer’s requirements. Refresh annotations identify whether later visual evidence changes the acceptable choices. Clarify replies distinguish the intended physical referent without naming a website entity. The complete replay window is checked for premature disclosure of later evidence. 

Website matching. Candidate review considers plausible alternatives in the public catalog. Accepted entities require positive evidence of relevance or compatibility. Missing specifications are treated as unresolved rather than as evidence of incompatibility. Tutorial relevance is established from public descriptions, chapters, subtitles, or captured previews. Brand and model constraints are retained only when supported by the request or visual evidence. Rendered pages and agent-readable observations use the same website facts. Source annotations and answer labels are excluded from both. Tasks reference website entities, and the evaluator accepts all verified alternatives satisfying the request. 

Validation. An independent Coding Agent first records a solution without access to the proposed answers, then reviews answer coverage and information shortcuts. Development runs with Qwen3.5-Flash, including text-only shortcut tests, informed task revisions before model evaluation. Revisions are checked against the source recording and public website evidence. Each reported comparison uses its fixed task and website version. 15 A.3 Human Quality Review 

Two independent human reviewers assessed the same 40 tasks from 40 distinct recordings: 14 Graft, 10 Refresh, 8 Clarify, and 8 composite tasks. Sampling was stratified by task type without considering model outcomes. For each task, the review interface presented the requests in temporal order, sampled frames from the complete reviewed window, the standard clarification reply where applicable, all registered acceptable outcomes with quantities and fields, and the corresponding website candidates and details. Model results and previous review comments were not shown. Reviewers checked whether the visual evidence supported the request, whether the registered answers were valid and covered reasonable alternatives, and whether the updates and clarification were natural and meaningful. Each task received one of three judgments: Acceptable , Problem , or Uncertain . Problem and uncertain judgments required a short explanation. Reviewer 1 marked one Graft task as problematic and another as uncertain. Reviewer 2 marked one Clarify task and one composite task as uncertain.

> A.4 Evaluator Tests

Evaluator tests apply controlled modifications to accepted states. Removing required content, adding unrelated content, changing a required quantity, or retaining an obsolete choice produces a failure unless the result matches another accepted alternative. Verified alternatives remain valid under entity ordering and registered packaging equivalences. Scoring uses the terminal website state. Corrected intermediate errors do not affect success, whereas errors remaining at termination do. A clarification question and a separate submit action are not scoring requirements. Runs without terminal evidence are excluded from scored outcomes.

B.3 Input Variants 

Computer-Use requests state the final requirements without website answer identifiers or action sequences. Offline Ego Use provides the same reviewed recording window before execution. Overall SR gives each task equal weight. Paired comparisons use tasks scored in all required conditions, with the same tasks and weights on both sides. C.6 Replay Pace 

The pace comparison uses 120 tasks: 69 Graft, 23 Refresh, and 28 Clarify. Each step delivers eight frames spanning 4, 8, or 16 seconds, corresponding to sampling rates of 2, 1, and 0.5 fps. The decision budget is 20 steps. Tasks whose change enters the opening batch at any tested pace are excluded. Each model has 360 scored episodes. Table S21 reports success and update receipt. Each step contains the same number of frames, so advancing more source seconds spaces the frames farther apart and covers more of the recording within the decision budget. At 16 seconds per step, all 92 Graft and Refresh updates reach each model. At 4 seconds per step, some runs never receive the update. More coverage does not yield the same best setting for every model: Terra has the most successes at 8 seconds, while DeepSeek and Kimi have the most at 16 seconds.

D.1 Resource Accounting 

Costs are measured on the same episodes used for the success results. Input and output tokens are summed over logged requests, including repeated history. Per-task total token cost is their sum, averaged over all valid task episodes, including failures. Input totals include cached tokens and any image tokens counted by the provider. Output totals use the provider-reported completion count. Images are counted each time they are sent. Token comparisons are made within a model because token accounting differs across providers. Each decision step in these episodes corresponds to one logged model request. Transport retries within a request are excluded from this count. E.1 Error Categories 

Figure 6 of the main paper groups failures by the three challenges in the Introduction. Table S26 defines the five underlying error categories. To assign a category, we align the delivered observations and requests with browser actions, feedback, and website state. We label the earliest error that contributes to failure and remains uncorrected. 32 Table S26. Failure categories and their observable distinctions in trajectory analysis. Category Observable distinction Perception Behavior adopts a visual property contradicted by already delivered frames. Intent The agent commits to an unresolved referent or explicitly follows an obsolete requirement. Linking The selected webpage entity conflicts with the active request, or a compatible candidate is explicitly rejected. State Control An invalid action or unrecovered execution error occurs, or an evidenced target is not realized through state edits. Verification An observable completion error causes failure, such as destroying a correct state without recovery. 

For presentation, Perception and Linking are associated primarily with Context Grounding, Intent with Intent Continuity, and State Control and Verification with Execution Adaptation. 

E.2 Attribution Procedure 

The final-state checker determines which runs fail. The read-only gpt-6-luna Judge then assigns an error category using the delivered requests and frames, public agent responses, browser observations, action feedback, and website state. The Judge receives the scoring goal and reference answer separately from the evidence available to the agent at each step. It identifies the decisive step and its supporting evidence, or leaves the category unassigned when the evidence is insufficient. We retry failed Judge calls before human review. A reviewer uses task and trajectory summaries to assign a label when the Judge result is uncertain or unavailable. Final-state scores are unchanged. 33 E.3 Failure Counts
