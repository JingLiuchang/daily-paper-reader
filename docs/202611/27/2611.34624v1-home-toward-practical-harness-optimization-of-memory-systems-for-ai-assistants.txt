Abstract 

The behavior of memory systems for long-running AI assistants is governed by a harness, which con-sists of the code, prompts, and configurations for memory construction, maintenance, retrieval, and an-swer generation. However, optimizing the harness of a memory system remains largely manual, and un-restricted editing alone does not ensure structural improvements. In this paper, we introduce HoMe, an evaluation-driven framework that iteratively evaluates candidate harnesses and derives each new candidate from any previously evaluated harness by editing any part of it. HoMe combines session-level memory versioning with execution traces to identify shared failure mechanisms across cases and localize them to the responsible sessions and harness components. It encourages early structural exploration through candidate gating and reduces evaluation cost through smoke tests, adaptive sampling, and the reuse of constructed memory. We validate HoMe with the open-source memory system ReMe on two large-scale long-horizon memory benchmarks, LongMemEval-S and BEAM. With six formal candidate evaluations per benchmark, after a full initial evaluation, HoMe discovers harnesses that improve end-task performance over the originally strong harness while consuming far fewer query-time tokens. The code is available at 

https://github.com/agentscope-ai/ReMe .

# 1 Introduction 

Long-running AI assistants accumulate conversational and episodic experience through continued interaction, and they depend on a memory system to turn that experience into consistent and personalized behavior across sessions (Packer et al., 2023; Chhikara et al., 2025; Xu et al., 2025; Zhong et al., 2023; Wang and Chen, 2025). In practice, memory is not merely persistent storage but a standalone system built around a language model, exposing interfaces for a target agent to store and retrieve information as needed. Many such systems are file-native, i.e., maintaining memory as files (Zhou et al., 2026). Three components govern the system behavior: the code that implements memory construction, maintenance, retrieval, and answer generation, along with associated evaluation and recovery mechanisms; the prompts that instruct the language model at each stage; and the configurations that determine the memory schemas, indexes, thresholds, etc. We call this collection of code, prompts, and configurations the harness of a memory system. Different AI assistants often have different demands on memory data management. For example, a med-ical assistant stores symptom histories and medication details that must be preserved faithfully, whereas a scheduling assistant stores event states that are revised repeatedly and should be superseded rather than accu-mulated (Wu et al., 2024; 2026). Hence, the harness of a memory system must be optimized before deploy-ment to achieve acceptable results on application-specific evaluations (Yao et al., 2026; Zhang et al., 2026).

This process is extremely time-consuming due to the huge search space and is still carried out manually, which raises a timely and important question: how can the harness of a memory system be optimized automatically? Prior work has largely treated the harness of a memory system as an artifact to be designed. Most efforts propose new architectures and retrieval strategies (Packer et al., 2023; Guti´ errez et al., 2024; Xu et al., 2025; Rasmussen et al., 2025; Pan et al., 2025; Kim et al., 2025; Fang et al., 2025; Sun et al., 2026), or grant the target agent control over memory operations, such as deciding what to write and when to retrieve (Zhang et al., 2024; Hu et al., 2025). Recent work automates memory harness optimization. EvolveMem (Liu et al., 2026b) optimizes retrieval strategies through autonomous research. MemPro (Liu et al., 2026c) optimizes memory construction and retrieval, largely delegating failure diagnosis and revision planning to its evolving agent. MStar (Pan et al., 2026) jointly optimizes memory schemas, read and write code, and instructions through population-based search. However, full-harness editing alone does not ensure structural exploration. In our ReMe-based optimization experiments, all candidates proposed by MemPro modify prompts or parameters, despite executable-code edits being permitted. This motivates explicit mechanisms that connect failures across cases to the responsible harness components and guide structural exploration under a limited budget. In this paper, we move one step further and introduce HoMe, an evaluation-driven framework that guides free-form memory-harness optimization through cross-case mechanism diagnosis and early structural exploration. Our framework is inspired by Meta-Harness (Lee et al., 2026), a general scheme that delegates harness optimization to a code agent, which reads a harness with its evaluation evidence and returns a revised harness. At each iteration, HoMe diagnoses the optimization history, including all the harnesses proposed so far, the memories they constructed, and their evaluation results. It then performs arbitrary edits to propose a new candidate harness and evaluates it accordingly. The loop continues until it reaches the iteration limit and selects a final harness. However, applying such a flexible harness optimization scheme to a memory system for AI assistants is not viable, because the system operates over a long horizon (e.g., exceeding thousands of messages (Tavakoli et al., 2025)), which raises two challenges . First, accurate diagnosis is essential yet difficult (Yan et al., 2026). A query is answered from memory accumulated over hundreds of preceding sessions, and a low score may originate in how a session was segmented and written, in a later revision that overwrote relevant content, or in the retrieval procedure that selected what was returned. Without locating the responsible part of the harness, there is little guidance on what to change, and iterations are easily wasted on unrelated edits. Second, evaluation is prohibitively expensive. For each candidate harness, evaluation constructs memory over all preceding sessions, answers the evaluation queries, and invokes a judge on every case, where a case comprises one or several queries. Evaluation therefore dominates the runtime of the optimization process. For failed queries, HoMe reads the execution trace to determine at which stage the evidence was lost, whether it was never written, later overwritten, or stored but not retrieved. It inspects the implicated sessions’ diffs to confirm the cause and traces the failure to the responsible harness component. We further aggregate the diagnoses across cases to distinguish recurring harness defects from isolated failures. Second, HoMe lowers the evaluation cost along three axes: smoke tests reject broken harnesses, while candidate gating reserves early evaluations for structural exploration; adaptive sampling restricts each evaluation to the most informa-tive cases, reducing the number of cases per evaluation; and constructed memory is reused when a candidate leaves memory construction behavior unchanged, reducing the construction cost per case. We also extend version control to the optimization itself: the harness edits and the diagnosis reports of every iteration are committed together, so that each iteration builds on prior attempts rather than rediscovering them. We implement HoMe on the open-source memory system ReMe (Cao et al., 2026) and evaluate it on the long-horizon benchmarks LongMemEval-S (Wu et al., 2024) and BEAM (Tavakoli et al., 2025). Evaluat-ing only six candidate harnesses per benchmark in several hours, HoMe discovers harnesses that outperform the original one by 2.8 and 5.4 percentage points (pp) in evaluation score while reducing query-time token consumption by 59% and 41%, respectively. Compared with MemPro, HoMe improves scores by 10.4 pp on LongMemEval-S and 1.1 pp on BEAM, while reducing query-time tokens by 81.5% and 7.6%, respec-tively. The harness optimized on BEAM-100K also remains effective on BEAM-1M conversations, which 2are about 8× longer on average than those in BEAM-100K, showing it generalizes across memory scales. To summarize, our major contributions are the following. 

• We introduce HoMe , an evaluation-driven framework that guides memory-harness optimization through cross-case mechanism diagnosis and early structural exploration, enabling effective revisions under a limited evaluation budget. 

• We identify two challenges that arise in the long-horizon setting, namely accurate diagnosis and evaluation cost, and address them through session-level memory versioning with diff-based diagnosis for the former, and candidate gating, adaptive sampling, and memory reuse for the latter. 

• We evaluate HoMe on ReMe using LongMemEval-S and BEAM. By evaluating only six candidate har-nesses per benchmark, HoMe identifies harnesses that score higher than the strong original harness while consuming fewer query-time tokens. The harness optimized on BEAM-100K also generalizes to BEAM-1M, where conversations are about 8× longer on average.

We consider a file-backed memory system built around a language model that serves a target agent through two interfaces: memory construction and retrieval. Let mt denote the persistent memory state after session st, including the memory files and indexes. Harness of a memory system. The harness of a memory system is a triple h = ( c, p, θ ) ∈ H , where c

denotes the executable code, p denotes the prompts, and θ denotes the configuration values such as memory schemas, indexing options, and thresholds. These components jointly determine memory construction, re-trieval, and answer generation, i.e., Ch, Rh, and Ah, including their language model calls, internal control flow, and recovery mechanisms. The search space H consists of the harnesses that preserve the interfaces in Eq. 1, whereas the language model remains fixed and lies outside h.

# 3 Diagnosable and Efficient Harness Optimization 

## 3.1 The HoMe Framework 

HoMe is an evaluation-driven framework that optimizes the harness of a file-native memory system. As shown in Figure 1, it consists of three major components. The Developer Agents take the role that human developers play in manual harness optimization: they diagnose the failures of evaluated candidates and edit a harness to produce a new candidate. The Experiment Manager records all candidates and their evaluation results, controls the Developer Agents’ access to tools, and decides how each candidate is evaluated. The 

Evaluation Environment executes evaluations in isolated sandboxes. In each iteration, the Developer Agents submit a candidate, the Experiment Manager screens it and plans its evaluation, the Evaluation Environ-ment evaluates it, and the Experiment Manager records the results for subsequent iterations. In HoMe, the Developer Agents and the Experiment Manager jointly realize Π in Eq. 3, and the Evaluation Environment computes Eval in Eq. 2 for each candidate admitted to formal evaluation. 

Developer agents. The Developer Agents consist of an Optimizer Agent that generates candidates and a Diagnoser Agent that attributes failures to memory construction, retrieval, or answering (Section 3.2). All candidates originate from the initial harness h0, which is evaluated on the full D and stored as the root commit of a Git repository maintained by the Experiment Manager. We call this repository the harness repository ,and each of its branches tests one optimization hypothesis. In each iteration, the Diagnoser Agent reads the optimization history Ob together with the diagnoses attached to earlier commits and then diagnoses the failures of the most recently evaluated candidate hb. Based on these diagnoses, the Optimizer Agent selects an evaluated candidate hj with j ≤ b as the parent of the next candidate. The choice of parent determines how the search proceeds: extending the latest candidate on a branch refines the hypothesis of that branch; starting a new branch pursues a different hypothesis and may begin from an earlier candidate when the current hypothesis fails to improve performance; and merging two branches combines changes that address complementary failures. HoMe leaves this choice to the Optimizer Agent. 

Experiment manager. The Experiment Manager maintains the harness repository, controls the evaluation of each candidate, and provides the Developer Agents with a unified tool interface for code inspection within a permission boundary. A candidate is admitted to evaluation only if it passes a smoke test (Section 3.3). A rejected candidate is returned to the Optimizer Agent with the rejection reason and consumes no formal evaluation budget. To reduce the evaluation cost for an admitted candidate hb+1 , the Experiment Manager judiciously samples an evaluation subset Db+1 ⊆ D or reuses the cases and memory states from the nearest evaluated ancestor with an equivalent construction process. It then evaluates hb+1 on Db+1 and returns the 4evaluation record (yb+1 , eb+1 , κ b+1 ). We refer to this step as a formal evaluation , which consumes one unit of the budget B. Since the repository provides complete provenance for every candidate and records their evaluation trajectories and diagnostic information, each iteration can build upon previous attempts while retaining the evidence and reasoning that motivated earlier harness revisions. 

Evaluation environment. The Evaluation Environment executes smoke tests and formal evaluations. In a formal evaluation of hb+1 , each case xi ∈ D b+1 runs in an isolated Docker sandbox that performs memory construction, retrieval, answering, and scoring with the fixed judge J. All cases run concurrently, and a pool of warm sandboxes reduces startup overhead. During construction, the sandbox commits the memory files after every session and thus produces the memory repository of xi. When the Experiment Manager permits memory reuse for xi, the sandbox restores the memory constructed for the selected ancestor and runs only retrieval, answering, and scoring using the same persisted memory state as that ancestor. 

## 3.2 Long-Horizon Failure Diagnosis 

In each iteration, the Developer Agents analyzes the failed cases of the most recently evaluated candidate hb,where a case fails if any of its queries receives a low score. For the failed cases, it identifies the cause of the failure and the responsible part of the harness. However, a low evaluation score does not reveal the cause. The required information may never have been written to memory, may have been corrupted or deleted by later maintenance, may be present in memory but not retrieved, or may be retrieved but used incorrectly during answering. A direct diagnosis must therefore examine the evaluation trajectory of the case, which consists of the query execution logs and the intermediate memory states (see Eq. 1). The query execution logs are typically short, but the intermediate memory states span many processed sessions. These states are expensive to examine in full and can far exceed the context window of a single agent. The difficulty is compounded because an evaluation often contains many failed cases. HoMe addresses these difficulties with three designs. 

Session-level memory versioning. This design makes the intermediate memory states compact and in-spectable on demand. During construction, the Evaluation Environment commits the memory files of each case xi to a Git repository after every session. The commits of this memory repository are checkpoints of the intermediate memory states mi,t , and the diff between two consecutive checkpoints records exactly what one session changed. An agent can therefore retrieve any intermediate state or any single-session change without reading the entire history or loading every checkpoint into its context. 

Trajectory-guided attribution. An agent attributes failures by tracing a case’s evaluation trajectory back-ward from each low-scoring query q and using session-level memory checkpoints to inspect relevant changes (Wang et al., 2026; Zhai et al., 2025). It first checks whether the retrieved information rq and the final memory state mi,T i contain the information required by q. If rq contains the information, the failure lies in answering. If only mi,T i contains it, the failure lies in retrieval. Otherwise, the failure lies in construction. For a con-struction failure, the agent locates the source sessions si,t that contain the required information and inspects the diffs between mi,t −1 and mi,t to determine whether it was written to memory. If it was, the agent follows subsequent changes to the files that stored it to identify the session in which it was corrupted or deleted. The agent summarizes its findings in a compact case diagnosis that records each failure’s cause, any implicated sessions, and the responsible harness component, together with the evidence supporting the attribution. 

Parallel case diagnosis. A dedicated Diagnoser Agent investigates failed cases and produces a diagnosis report for the Optimizer Agent. This division of labor keeps detailed case investigations out of the Optimizer Agent’s context so it can focus on mechanism-level revisions to the harness. The Diagnoser Agent uses a map-reduce workflow. In the map phase, it invokes a batch tool that runs Case Study Agents in parallel. Each agent applies trajectory-guided attribution to one case in an independent context and returns a compact case diagnosis. This reduces latency and avoids reprocessing earlier case histories. In the reduce phase, the Diagnoser Agent compares the diagnoses and looks for corroborating evidence across cases before inferring a shared cause. It groups the case diagnoses by failure mechanism and prioritizes the groups supported by the most cases to identify shared harness defects. This helps distinguish recurring harness failures from case-specific effects and limits the influence of individual diagnostic errors on the overall attribution. The diagnosis report links the supported shared causes to the responsible harness code. 53.3 Efficient Evaluation of Candidate Harness 

The overall evaluation cost depends on three factors: the number of formal evaluations, the number of cases per evaluation, and the average cost per case. HoMe reduces these factors through smoke test and candidate gating, adaptive case and query sampling, and construction-aware memory reuse. 

Smoke test and candidate gating. HoMe screens a candidate harness with two checks that cost far less than a formal evaluation. First, it runs a smoke test that executes the candidate on real cases deterministically truncated to a few sessions and queries. This rejects candidates with implementation failures such as runtime exceptions. Second, we develop a gate that decides whether a candidate may enter formal evaluation. We observe that an unconstrained optimizer initially proposes many candidates that edit only prompts or config-urations, because such edits are cheap to produce. Such edits can bias search toward local fixes rather than shared failure mechanisms. Later code changes may also invalidate early prompt or configuration tuning. We therefore prioritize structural exploration before refinement, devoting the first B/ 2 budget units to exploration and the rest to refinement. During exploration, the gate prioritizes changes to runtime mechanisms, such as memory representation, construction, and retrieval, while also admitting necessary fixes to execution failures. The gate inspects the candidate diff and affected runtime paths, rejecting prompt-only or parameter-only tun-ing and superficial code edits that leave information flow and control flow unchanged. During refinement, the gate is lifted, allowing candidates that modify only prompts or configurations as well as those that continue to modify code, building on the mechanisms and evaluation evidence established during exploration. 

Adaptive case and query sampling. To reduce the cost of each formal evaluation, HoMe restricts it to a subset Db+1 ⊆ D selected by an adaptive sampler. The sampler treats each case and query as a sampling unit , indexed by v. Intuitively, recently failed or persistently low-scoring units reveal the limitations of the current harness more often than units that consistently pass. However, evaluation is stochastic, and harness changes can cause correct units to regress. The sampler therefore prioritizes high-loss units while preserving coverage of the remaining units. This evolving focus broadens exposure to failures and reduces the risk of repeatedly tailoring revisions to the same cases. Memory construction dominates the cost of evaluating a case. However, many edits leave construction unchanged, such as edits confined to retrieval. For a candidate h = hb+1 , HoMe identifies the nearest evaluated ancestor h′ with an equivalent construction process by checking that the diff changes no code, prompt, or configuration used during construction. If such an ancestor exists, HoMe reuses its evaluated cases and constructed memory states with probability ρ, rather than always, to account for stochasticity in memory construction. The evaluator restores those memory states and reruns retrieval, answering, and scoring for the new candidate. Otherwise, it resamples and constructs from scratch, enabling broader case coverage and fresh construction outcomes across successive rounds of candidate evaluation. 

## 3.4 Implementation 

We implement HoMe on ReMe (Cao et al., 2026), an open-source file-native memory system whose original harness already performs strongly (see Table 1). Improving on this harness therefore provides a stringent test of HoMe. During construction, ReMe extracts information from each session, revises existing content, and writes memory files. In the query stage, it combines retrieval and answering into a single agentic pro-cess, in which an Answer Agent repeatedly invokes hybrid search and file-reading tools over the memory files before generating an evidence-grounded answer to the query. Inspired by the Everything-is-a-Plugin de-sign (DeepSeek-AI, 2026), we restructure ReMe into a shared runtime and application-specific plugins. The runtime provides infrastructure unrelated to memory management, such as task execution, model access, and storage. Each plugin instantiates an application-specific harness h = ( c, p, θ ) of the memory system. This separation has two advantages. First, it enables an accurate evaluation of HoMe. The Evaluation Environment runs the same runtime with the candidate plugin, and performance differences on an application thus reflect changes to the harness rather than to the infrastructure. Second, it simplifies evaluation on new applications. Because the runtime instantiates and dispatches registered plugins according to a job configuration, support-ing a new application requires only a new plugin. Various memory designs can be easily implemented by replacing the modules, and HoMe can optimize the resulting harnesses through the same evaluation-driven optimization loop, without modifying the framework or its developer-agent workflow. 

# 4 Experiments 

## 4.1 Experimental Setup 

Benchmarks. We use LongMemEval-S 1 (LME) (Wu et al., 2024) and BEAM (Tavakoli et al., 2025). LongMemEval-S contains 500 single-query cases with average 115K history tokens, spanning six question types. All BEAM variants share ten question types, with independent data across variants. BEAM-100K and BEAM-1M contain 20 and 35 cases, respectively, with 20 queries per case and average histories of 131K and 1.04M tokens. The longest BEAM-1M history reaches 1.52M tokens. We randomly split LongMemEval-S equally into training and test sets; for BEAM, we train on BEAM-100K and test on BEAM-1M. All methods are evaluated on the test sets. 

Baselines and evaluation. We compare against A-MEM (Xu et al., 2025), SimpleMem (Liu et al., 2026a), ReMe (Cao et al., 2026), and MemPro (Liu et al., 2026c), an automated harness-optimization baseline. We manually tune ReMe separately for each benchmark. For optimization on a given benchmark, both MemPro and HoMe start from the same ReMe harness manually tuned for that benchmark, including in the cross-benchmark transfer experiments. Both methods keep the ReMe runtime fixed and optimize only plugins on the training sets, with their code agents using the same LLM and AgentScope CLI. An LLM judge (Zheng et al., 2023) scores answers following the official protocol. We report all query-stage input and output tokens without deducting KV-cache hits. ReMe-based methods use agentic query loops with growing contexts, allowing more prefix reuse than other methods.

## 4.2 Main Results 

4.2.1 Optimization Effectiveness 

HoMe achieves the highest answer score on both benchmarks (Table 1). Relative to the initial ReMe har-ness, the LongMemEval-S score rises from 0.888 to 0.916 as query-stage tokens fall from 43.9K to 17.9K. On BEAM-1M, the score rises from 0.650 to 0.704 as tokens fall from 101.8K to 60.4K, even though test histories are about 8× longer on average than those used for optimization. 4.2.2 Optimization Efficiency 

On BEAM, HoMe completes optimization in 10.4 hours, compared with 11 hours 23 minutes for MemPro. Under high API concurrency, wall-clock times are sensitive to network fluctuations and rate limiting. Total optimization token consumption is 185.2M for HoMe versus 331.2M for MemPro, a 44.1% reduction. We examine this efficiency in terms of optimization iterations, evaluation workload, and time per evaluation. 

Strong harnesses emerge within a few iterations. Figure 2 shows the evaluation results of BEAM can-didates on the full training set, measured retrospectively after optimization. The second candidate lies on the Pareto frontier, and candidates two through four offer different trade-offs, reaching a score up to 0.73 or a query cost as low as 31.8K tokens. The optimization discovers competitive harnesses within only a few iterations. The final two candidates do not extend the frontier, indicating that additional iterations may not make improvements. As edits accumulate, optimization may become more sensitive to random variation in sampled evaluations and more prone to overfitting. 

Adaptive sampling reduces evaluation workload. On BEAM, each formal evaluation uses 10 cases and 100 queries, representing 50% fewer cases and 75% fewer queries than MemPro. On LongMemEval-S, HoMe evaluates 28 cases per iteration compared with MemPro’s 50, a 44% reduction. With smaller evaluations, HoMe achieves higher test scores and fewer query-time tokens than MemPro on both benchmarks (Table 1). Because the sampled subsets differ across candidates and prioritize historically difficult units, their aggregate answer scores are not directly comparable. HoMe therefore relies on the Optimizer Agent to judge candidate answer quality from accumulated evaluation evidence, considering shared-case/query comparisons, coverage, and difficulty. Across six BEAM candidates, sampled and full-set query-token reductions are positively correlated (Pearson r = 0 .870 ), suggesting that sampled evaluations reflect full-set token savings. 

Formal evaluation time falls sharply. Table 3 shows cumulative time savings per formal evaluation. Par-allelism reduces full evaluation time by over 90%; sampling reduces case counts, and reuse avoids recon-struction. Reuse saves 94% on LongMemEval-S, reflecting the construction cost of single-query cases, and applies to five LongMemEval-S candidates and four BEAM candidates. These per-evaluation savings do not 9include the initial full evaluation, diagnosis, editing, and debugging that also contribute to total optimization time. HoMe reaches the BEAM Pareto frontier after 6.3 hours. 

## 4.3 Case Study 

HoMe modifies memory structures, code, and the system prompt. Figure 3 illustrates four revisions that change the evidence available to the Answer Agent. The first two were independently discovered on different datasets, while the last two are specific to LongMemEval-S and BEAM, respectively. Additional improve-ments and the failure patterns they address in each benchmark are described in Appendix A.2. 

Case 1: Improving cross-session evidence coverage. The Diagnoser Agent found recurring errors on sum-marization and enumeration questions spanning multiple dates. Hybrid search retrieved relevant passages but missed pertinent sessions within its small retrieval window. Daily topic summaries competed with raw conversations and were not reliably retrieved. The Optimizer Agent modified the search tool to compile sum-maries into a compact, date-grouped topic list. The answering prompt directs the Answer Agent to survey this list for relevant sessions across dates, avoiding repeated searches that cover only part of the question. 

Case 2: Diversifying the retrieval window. The Diagnoser Agent observed that hybrid search often re-trieved multiple chunks from the same file. Long raw transcripts occupied several slots, reducing source diversity. The Optimizer Agent introduced per-file slot limits, stricter for raw transcripts than for memory notes. Once a file reaches its limit, chunks from other files fill the remaining slots. This gives the Answer Agent evidence from more sources within the same retrieval budget. 

Case 3: Indexing user actions on LongMemEval-S. The Diagnoser Agent found that many questions re-quire precise user-action details buried in broader session notes. The Optimizer Agent added a line summa-rizing the user’s own actions to each note during construction. A separate inverted index over these lines lets the Answer Agent search action descriptions for notes containing potentially relevant evidence. 

Case 4: Compressing retrieved evidence on BEAM. To reduce retrieved context, the Optimizer Agent introduced query-guided line selection within retrieved chunks. The search tool scores lines by question keywords and replaces lower-scoring lines with placeholders preserving line numbers. The Answer Agent receives shorter results and can use the line numbers to recover omitted text when a passage requires closer inspection. Retaining source paths and line numbers thus reduces query-time tokens while keeping omitted evidence accessible through targeted reads on demand. These studies show how cross-case diagnosis leads to new retrieval mechanisms and memory structures. Independent optimization runs on both benchmarks found related mechanisms, suggesting that source diver-sity and broader access to stored evidence may offer general design principles for memory systems. The benchmark-specific changes show that HoMe can identify distinctive patterns in each dataset’s questions and histories and adapt the harness. By changing which evidence the Answer Agent sees and how much text it must inspect, these mechanisms improve evidence utilization and enable token savings, supporting the stronger trade-offs between scores and token consumption observed in the main and transfer results. 

# 5 Conclusion 

This paper presents HoMe, an evaluation-driven framework that guides free-form harness revisions through cross-case diagnosis and early structural exploration. HoMe traces failures to the responsible sessions and harness components through session-level memory versioning and reduces evaluation cost of candidate har-nesses through smoke tests, candidate gating, adaptive sampling, and memory reuse. With only six evaluated candidates per benchmark, HoMe extends the strong original harness of ReMe with new mechanisms such as fact-level memory indexes and source-aware retrieval. The resulting harnesses improve end-task accuracy by 2.8 pp while reducing query-time tokens by 59% on LongMemEval-S, and by 5.4 pp while reducing query-time tokens by 41% on BEAM-1M. 4. Extend the catalog to individual facts while retaining both levels. A one-line description is necessarily lossy: an additional graduation, a particular island, or a precise bedtime may appear only in the note body. The expanded index scans notes and splits self-contained Markdown list items into fact entries. Matching entries are quoted inline, allowing the agent to use the fact without another read call. Fact and catalog layers calculate term frequencies and rankings separately, so adding the finer layer does not silently change how the coarser one behaves. Facts already visible in the normal retrieval window are suppressed in the index to avoid duplication. The catalog remains useful because a question phrased in terms of a session’s topic may share no content word with the answer sentence. The layers answer complementary questions: “Which note might matter?” and “Which statement in it matters?” 5. Keep the inexpensive index available, vary its width, and state what a match proves. The run briefly gated index delivery to enumeration questions or explicit requests to reduce irrelevant matches. Case-by-case inspection showed that the gate did not cause the improvements initially attributed to it; withholding the index instead prompted repeated blind query rewrites and higher total token use. The final design kept the index available for every question, returned a shorter list for point queries and a wider one for enumeration, and warned in the index header that keyword overlap is only a lead. A nonempty list does not establish that the entity or event in the question exists; each entry must be checked against the requested 15 fact. Query wording alone did not predict where evidence was stored. For a cheap index, controlling output size and clarifying evidential meaning proved more useful than gating access by question form. 6. Diagnose “the evidence was found” separately from “the answer was correct.” In several cases the agent read the right note but abstained because it demanded a completion confirmation that memory would never record. In others, it corrected a false premise yet still supplied the value that the false premise requested. Answering rules were calibrated to anchor relative times, use newer records for current state, respect entity boundaries, and reject the requested value when its premise is false. Rules without case-level evidence were later removed because their prompt cost recurred at every ReAct step. A memory answer can fail at construction, retrieval, evidence interpretation, or final decision. More retrieved material is unlikely to repair a decision error once the correct evidence is already visible. 

A.2.2 BEAM: Coverage, Order, and Access to Evidence in Long Conversations 

1. Reserve room for both curated memory and primary evidence in the retrieval window. The system stores condensed notes alongside verbatim transcripts, which account for roughly 95% of indexed chunks. A window filled solely by the highest-scoring chunks is therefore easily dominated by transcripts, leav-ing out the notes that integrate information across passages. The optimized ranking favors notes while reserving slots for transcripts, so the answering agent can use the consolidated account and still check exact wording, numbers, and chronology. This rearrangement changes the order of candidates without discarding any. Crucially, it happens before the system marks returned chunks as seen: otherwise, a chunk displaced from the window could be recorded as already shown and become unreachable in later searches. In a mixed memory store, the source composition of the window matters as much as the ranking of individual chunks. 2. Compress search responses without cutting off access to the original text. Long transcript chunks make repeated searches expensive, yet a simple truncation can hide the line containing the answer. The first measure placed a character budget on responses while retaining the path and line range for each result; text that did not fit remained available through an explicit pointer for targeted reading. When truncation from the beginning repeatedly omitted facts in the middle or end of a note, selection moved to the line level. Lines were scored using the distinctiveness of query terms, numbers, and heading cues. The budget first covered multiple evidence-bearing lines, then used any remaining space for adjacent context. When a semantic match had no lexical overlap, the title and summary were still retained. Effective compression thus has two requirements: show the most useful evidence now, and make every omitted passage straightforward to locate later. 3. Give coverage questions a global view instead of repeatedly enlarging top-k. Answers to questions such as “Which topics did I mention?” may be spread across many sessions. Similarity search can return highly relevant chunks without establishing that all matching occurrences have been found. The optimizer therefore derived a compact chronological index from all notes, appended it to ordinary retrieval results, and delivered it automatically at most once per question. Entries carried paths for verification. Near-duplicate entries from overlapping notes in one session were consolidated while their paths remained accessible. To control cost, automatic delivery was routed only for coverage questions after offline checks. A measured regression exposed the index’s limit: a thematic summary can look sufficient for a question about the first-mention order while omitting precisely the ordering evidence needed to answer it. A global index can support “what was mentioned” without automatically serving as an answer to “in what order.” 4. For ordering questions, provide a reading route rather than a summary that invites an immediate answer. Ordering evidence spans dates and sessions, so one note seldom contains all relevant mentions. An earlier summary-style index encouraged the agent to answer from its overview, saving tokens but getting the sequence wrong. The revised route listed note paths in chronological order and then annotated each path with the line range of its conversation-flow section. The agent could read the passages that recorded mention order and speaker identity without loading every entire note. ## A.4 Stability 

Two independent BEAM searches with the same initial harness, hyperparameters, and evaluation budget produce stable gains: the final harnesses score 0.704 and 0.720 on BEAM-1M, using 60.4K and 68.3K query-stage tokens, respectively. Both improve on ReMe and lie on the empirical Pareto frontier (Figure 4). Paired bootstrap resampling over the same BEAM-1M test queries shows significant gains over ReMe (0.650) for both runs. The improvements are +0.054 (95% CI: [0.028, 0.082], p = 0 .0002 ) and +0.070 (95% CI: [0.042, 0.090], p < 0.0001 ), respectively. Consistency extends to both diagnoses and proposed improvements (Table 8). Both runs identify similar con-struction and retrieval defects and propose related changes to evidence selection, indexing, and information preservation, although their implementations differ. This stability is supported by independent case investigations and cross-case synthesis, which reduce the in-fluence of individual attribution errors. Git preserves promising alternatives, while gating encourages mech-anism exploration before refinement, reducing premature convergence on local prompt patches.

We report total optimization token consumption on BEAM-100K by stage and model.
