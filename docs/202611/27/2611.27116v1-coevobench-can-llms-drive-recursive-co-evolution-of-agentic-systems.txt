## Abstract 

The performance of an LLM agent depends on both its model and its harness, the code that mediates its interaction with tools and environments. Can LLM researchers drive this co-evolution as a recursive improvement process, deciding round after round which component to change when each change alters the value of the other? Existing benchmarks evaluate post-training or data research with the harness out of scope, or harness optimization with the model fixed, leaving this joint decision unmeasured. We introduce CoEvoBench, a benchmark that evaluates LLMs as researchers co-evolving the model and harness of a target agent across five agentic domains. Researchers start from a common base model and initial harness, train and revise within a 24-hour budget, and submit a model–harness pair that is scored on separate test tasks. Across five frontier researchers, the strongest closes more than four fifths of the gap to an instruction-tuned reference system, and co-evolution succeeds on interaction tasks but rarely on long-horizon coding. These results suggest that current LLMs can make a strong first improvement, but cannot yet turn feedback from an improved system into the next one. CoEvoBench provides a controlled testbed for measuring the research capabilities that recursive co-evolution requires.

## 1 Introduction 

LLM agents now repair software, operate terminals, and carry out workflows in applications and services [1–5], and their performance depends as much on the harness that mediates their interaction with tools and environments as on the model itself [6]. Building such an agent therefore means improving both. Developers run the agent, read its execution traces, decide whether a failure calls for a harness fix or more training, and take the revised system as the starting point of the next round. Because each change to one component alters the value of the other and shifts the system’s failure modes, the hard part is keeping this loop going, turning feedback from an already improved system into the next gain. The loop is still run largely by hand. An LLM researcher that could run it would automate agent development and realize a concrete, measurable form of recursive self-improvement (RSI) [7–9]. This raises a central question: Can LLM researchers drive this recursive improvement process and achieve further system gains through successive iterations?

Existing benchmarks cannot answer this question, because each covers only one side of the loop. PostTrain-Bench [10] measures post-training on reasoning tasks, RSIBench-Data [8] measures data-centric research for post-training, and related benchmarks target algorithm design and agentic RL engineering [11, 12]. All of them leave the execution harness out of scope. Meta-Harness [6], DarwinX [13], and related systems [7, 14] optimize the harness around a fixed model. Recent co-evolution methods update both components through specific pipelines [15–18], but do not evaluate whether LLM researchers can drive this process on their own. As Figure 1 illustrates, model-centric improvement updates weights alone, while improving an agentic system updates both the model and the harness. None of these works tests the key challenge of recursive improvement. No existing benchmark gives an LLM researcher both levers and asks it to turn feedback from an already improved system into further gains, round after round. To address this challenge, we introduce CoEvoBench , a benchmark that places LLM researchers in the agent developer’s position. A researcher drives the recursive loop end to end, training the model, revising the harness, and choosing each next step from development feedback, and the benchmark records both the system it delivers and the trajectory that produced it. CoEvoBench thus measures how much a researcher improves an agentic system and how its gains arise over successive rounds. CoEvoBench spans five agentic domains: software repair, terminal operation, application interaction, interactive service workflows, and multi-turn tool use with memory. In each domain, researchers start from a common base model and initial harness, train and revise within a fixed compute budget, and submit a model–harness pair that is scored on separate evaluation tasks. We evaluate five frontier LLMs as researchers, each developing a system three times in every domain on two target models from different model families, Qwen3.5-9B-Base and MiniCPM5-2B-Base. Our main contributions are: • We formulate agent development as a measurable instance of recursive self-improvement. ## 2 Related Work 

Automated AI research and evaluation. Automated systems conduct scientific research [19], while benchmarks assess ML experimentation, engineering, expert research, and paper replication [20–23]. Recent suites evaluate post-training, data research, algorithm design, and agentic RL [8, 10–12], alongside agent construction under business and serving constraints [24]. The post-training, data, algorithm, and RL suites improve the target model and leave the harness that executes it unchanged. 

Harness-level agent improvement. With fixed model weights, agents improve through feedback and reusable skills [25, 26], prompt and program search [27, 28], and evolving control logic and context management [6, 7, 13, 14]. Benchmarks also assess transfer from retained experience and skill libraries to later tasks [29, 30]. 

Agent training and model–harness co-evolution. Agent training uses trajectory tuning and exe-cutable environments [31, 32], with harnessed RL preserving deployment interactions [33]. Co-evolution combines feedback-directed intervention and harness-conditioned training [15–17, 34], scientific-agent learn-ing and operator composition [9, 18], and expert correction for model–harness compatibility [35]. ## 3 CoEvoBench 

CoEvoBench evaluates whether a researcher R can improve a target agent by running the development loop an agent developer would run. The researcher may change any part of the agent, learns only from development feedback, and is judged by the submitted system on unseen tasks. We represent the target agent as S = ( θ, H ), where θ denotes model weights and H is the executable harness governing tool use and environment interaction. 3.1 Benchmark Suite 

The domain set D comprises five agentic benchmarks: SWE-bench Verified [1], TB-Lite [2], AppWorld easy [3], 

τ 2-bench Telecom base subset [4], and BFCL-V4 multi-turn and memory tasks [5, 36]. They cover software 4repair, terminal operation, application interaction, interactive service workflows, and multi-turn tool use with memory, respectively. We call the first two coding tasks, which need long-horizon edits and command sequences, and the last three interaction tasks, which involve structured exchanges with applications, services, and tools. For each domain b ∈ D , we partition the task pool Db into three disjoint sets:

The visible set Dvb provides material for failure analysis and development. The selection set Dsb allows researchers to assess how well their modifications generalize to unseen tasks. The test set Dtb supports final evaluation. Ac-cessible materials Ib include initial instructions, system and tool documentation, and visible-set task materials. We stratify SWE-bench Verified by repository and TB-Lite by difficulty. For AppWorld, we assign each scene’s variants to the same split and stratify scenes by their normal or challenge source. Telecom is stratified by operation type. For BFCL, we group multi-turn variants by task family and keep each memory scenario, its cross-backend QA records, and prerequisite conversations in one split.

The researcher nominates a final system S⋆b = ( θ⋆b , H ⋆b ) within the 24-hour development budget and may stop early. CoEvoBench’s experiment execution and evaluation infrastructure uses sandbox isolation and benchmark-data access restrictions during development. Researchers modify models and harnesses in isolated workspaces with 5network access enabled, while datasets that directly expose benchmark task data are blocked. Visible-set materials are supplied through the platform. Selection and test data remain protected, and selection-set task contents and execution trajectories are withheld. 

3.4 Evaluation and Scoring

4.2 Main Results 

Overall performance. LLM researchers substantially improve the target agent, but their effectiveness varies widely (Table 1). GPT-6 Astra closes more than four fifths of the gap between the initial system and the Instruct + Reference Harness system, Claude Opus 5 more than half, and the remaining three researchers less than a third. On AppWorld, Astra and Opus both surpass the reference system from an initial score of zero. Every researcher starts from the same system and budget, so this spread reflects differences in research capability. Across the three runs, researchers show a clear gap in capability, with Opus and Astra well ahead of Kimi, Qwen, and GLM. MiniCPM5-2B-Base in Table 1 shows a similar gradient. 

Per-domain performance. Where researchers separate depends on the domain. On interaction tasks, the strongest researcher pulls far ahead. Astra closes most of the gap on τ 2-bench Telecom and nearly all of it on BFCL-V4, far more than any other researcher. Coding tasks compress the field. Opus and Astra are tied on SWE-bench Verified, and on TB-Lite four researchers finish within six points of one another, with the best closing only about half the gap. The smaller MiniCPM5-2B-Base target widens this contrast. No researcher exceeds 10% on SWE-bench Verified or 2% on TB-Lite, whereas Astra reaches 96.1% on τ 2-bench Telecom, and Opus and Astra again surpass the reference system on AppWorld. The harness lifts MiniCPM mainly on interaction tasks. 

## 5 Analysis 

5.1 Diminishing Returns in Recursive Improvement 

In recursive improvement, each candidate builds on the previous system, so gains should accumulate. Yet development trajectories show that most of the improvement arrives at once. 

Feedback-driven iteration adds limited gains. In most runs, the first candidate already captures most of the gain. The feedback-driven iterations that follow add comparatively little. We split each run into initial development, which ends with the first candidate evaluated on the selection set, and feedback iteration, which carries that candidate to the best one. Deeper development yields fewer new gains. The further a run progresses, the harder each next gain becomes. Gains come quickly after the first candidate, and in the long stretch that follows only two candidates improve on the best. Both late gains come from coordinated updates, in which the researcher first revises the harness and then retrains the model for it (Section 5.2). What researchers lack is not the ability to improve a system once, but the ability to turn feedback from an already improved system into the next improvement. 

5.2 Model–Harness Co-Evolution 

Model and harness do not contribute independently. Which component should carry a gain depends on the task, and every change to one alters the value of the other. Of the 75 runs on Qwen3.5-9B-Base, 73 both revise the harness and launch training, and 54 submit trained weights. Table 2a shows that training carries over 80% of the gain on BFCL-V4, while the harness carries most of the gain on the other four tasks, where the same harness with Qwen3.5-9B-Instruct still scores 6 to 33 points higher. 

Frontier researchers struggle to train for long-horizon coding. On coding tasks, the strongest systems come mainly from the harness, and training has yet to pay off. Harness revisions, spanning control flow, output parsing, prompts, decoding, and tool interfaces, let Base apply capabilities it already has, raising SWE-bench Verified and TB-Lite by 12.4 and 13.8 points (Table 2a). Long-horizon coding demands end-to-end behavioral consistency, and today’s frontier researchers rarely manage to train it into the target model. 

Harness and training advance in alternation on interaction tasks. On interaction tasks, the two components divide the work. The harness makes the environment usable, for example through authentication, pagination, and interaction-history management, and training then teaches the model to act well within it. Training adds gains on all three interaction tasks, 4.1 points on AppWorld, 1.6 on Telecom, and 10.1 on BFCL-V4, where the trained systems beat Instruct with the same harness by 4.4 points (Table 2a). The strongest researcher’s choices show the contrast with coding. Astra submits trained weights in 7 of its 9 interaction runs, which beat Base under the same harness by 13.0 points on average (Table 3). In an Opus AppWorld run, harness revisions raise test success from 0/51 to 3/51, and training then raises it to 12/51, three times the harness gain (Appendix K). Short, structured action sequences turn successful trajectories into direct learning signals, so on these tasks training pays off once the harness works. 

Harness revisions reshape the value of training. A harness revision can turn a helpful training update into a harmful one. In an Astra AppWorld run, a training update first solves five more selection tasks than Base. After a harness revision, the same weights fall four tasks behind Base, and retraining on trajectories collected under the revised harness restores a gain of four tasks (Figure 5). GLM shows the same dependence on AppWorld. Weights trained under an earlier harness score below Base, while weights retrained after a revision more than double Base’s score (Appendix K). Training data are trajectories collected under one harness, and the behaviors learned from them fit that harness. A revision breaks the fit. Cross-evaluating the 35 systems with trained weights in Table 2b shows that the coupling is general. The reference harness lifts Instruct from 30.2% to 37.8% but drops the trained weights from 19.8% to 2.6%. Every harness revision reopens the training decision. Task characteristics thus decide whether current researchers can achieve co-evolution, and to what degree. On long-horizon coding, researchers rarely make training pay off, and improvement rests mainly on the harness. On short, structured interaction tasks, harness and training advance in alternation. Even where co-evolution succeeds, the two components stay coupled, and a change to either one resets the value of the other. Every further gain therefore requires deciding anew which component to change, based on what the current system reveals. 5.3 Where the Loop Breaks 

Comparing the strongest researcher, GPT-6 Astra, with Qwen3.8-max, representative of the weaker researchers, shows where the research loop breaks. Table 3 shows that stronger researchers revise the harness more and train less, while weaker researchers launch more training jobs and submit trained weights more often, yet gain far less from the weights they submit. Qwen carries out every research step. In nearly every run, it diagnoses why the initial system fails, revises the harness, trains the model, and compares weights under the same harness. Yet these results do not shape the three decisions that matter: which direction to take, when to abandon it, and which system counts as better. 

Training is chosen before it is tested. Qwen decides to train before checking whether training is needed. On SWE-bench Verified, both researchers find that Base cannot follow the required action format. Astra first asks what the system can do without training. An interface rewritten to fit Base shows that the harness alone goes a long way, and when a brief LoRA trial falls below Base, Astra drops training. Qwen first asks how to train. It settles on fine-tuning before testing it, rebuilds the harness around public training trajectories, and compares against Base only late in the run. On coding tasks, where the harness carries the gains, this unexamined choice is the wrong one, and because gains are front-loaded, it costs most of the run. 10 Negative results change details, not the route. When results go against its route, Qwen changes the details, never the route. On TB-Lite, its fine-tuned model shows no gain over Base. Qwen adds loop detection, generates a larger training set, and trains again, each time attributing the stall to insufficient data. It uses results to swap checkpoints and adjust data, but never to question the decision to train. Astra, after a single comparison in which training lowers the score, abandons training and submits Base with its harness. The two runs end at nearly the same test score, and scaling up training changes nothing. Under a fixed budget, the most valuable conclusion a researcher can reach is that a route does not work, and Qwen never draws it. 

Candidates are judged on the tasks they were trained on. Qwen judges its candidates on the visible tasks, the same tasks its training data come from, so it cannot tell a real improvement from memorization. This is not a submission formality. Every round of recursive improvement rests on deciding whether the new system is better than the old one. Judged on data the model has seen, iteration accumulates overfitting, and the nomination, the only scored decision, makes the error final. Qwen often picks its submission by visible-task scores, and when two checkpoints tie on the selection set, it lets the visible set decide. Astra treats the selection set as a measuring instrument. Before submitting, it re-evaluates its finalists on the full selection set, overturns a smaller subset’s ranking, and picks its strongest SWE-bench Verified system. Judging improvement on tasks the model was not trained on lets iteration accumulate gains. This is what makes a loop recursive. Astra lets each result decide the next step, which is why its first jump comes early and large. Yet as Section 5.1 shows, even Astra finds it increasingly hard to extract the next step from an improved sys-tem. Turning results into decisions is where recursive improvement stalls, for the weaker researcher from the start and for the strongest one after its first jump. 

## 6 Conclusion 

We introduced CoEvoBench, a benchmark that places LLM researchers in the agent developer’s position and asks whether they can drive the recursive co-evolution of model and harness across five agentic domains. The strongest researcher closes more than four fifths of the gap to an instruction-tuned reference system, but whether co-evolution happens, and to what degree, depends on the task. On long-horizon coding, the strongest systems rely mainly on the harness, as today’s frontier researchers train only with offline fine-tuning and cannot yet make training pay off. On interaction tasks, harness and training advance in alternation, and each harness revision changes what training is worth. Researchers differ most in judgment. A weaker researcher completes every research step, yet its results rarely change its decisions, while the strongest lets each result decide the next step, though even it finds further gains harder after its first jump. Automating agent development, a concrete form of recursive self-improvement, depends on this judgment. Future work can extend CoEvoBench to more target models and to researchers that use reinforcement learning. We release the full protocol and the task splits, so that new researchers and specialized co-evolution pipelines can be evaluated under the same rules. 11 Reproducibility statement

E.1 Researcher Configurations and Resources 

We use GPT-6 Astra, GLM-5.3, Qwen3.8-max, Kimi K3, and Claude Opus 5, all with high reasoning effort. Astra runs through Codex, while the other models run through Claude Code. Each researcher configuration comprises the model and its command-line tool. Each development run receives a budget of 24 hours and four NVIDIA H20 GPUs, with early stopping permitted. Training, rollout generation, and model serving share these resources. The launcher sets the deadline, and the researcher can query the remaining budget. 

E.2 Initial Target Agents 

Target agents start from Qwen3.5-9B-Base. Researchers may retain the original weights or train deriva-tives using permitted data. Qwen3.5-9B-Instruct is used to construct the reference systems. Harness improvements include prompts, tool interaction, memory, and execution loops, relating to the harness optimization studied in Evo-Bench [37]. 

Software repair and terminal operation. SWE-bench Verified starts from the SWE-agent agent– computer interface, while TB-Lite starts from the terminal-oriented Terminus harness. Both connect to the evaluator through the minisweagent interface, exposing action parsing, tool interaction, observation formatting, context management, and the execution loop. The initial SWE-bench Verified configuration uses strict action parsing, truncated observations, and a context limit. The selected local model generates target-agent responses. 

AppWorld. The initial harness provides a minimal code-generation protocol. Researchers may modify agent construction and next-code generation, while the application environment and scorer remain fixed. The reference uses ReAct with full demonstrations and solving instructions. 

BFCL. The initial harness combines a fixed execution loop with editable prompting and history-selection policies. It retains one ordinary user turn and uses replacement-style memory notes. Telecom. The initial harness uses text-based ReAct and generates strict JSON actions. Native tool-schema injection and automatic action repair are disabled. E.4 Choice of Target Model and Starting Point 

We fix a 9B open target model so that the community can reproduce the benchmark. A full development run on the 9B target, including full fine-tuning, fits within four GPUs and 24 hours, whereas a larger target would multiply training cost. Absolute scores should therefore be read against the same-scale reference, Qwen3.5-9B-Instruct with a reference harness, which anchors each domain in Table 1. Leaderboard results on these benchmarks come from much larger frontier models. Against this reference, Opus raises SWE-bench Verified from 0.40% to 24.11%, over 80% of the reference (29.25%), Astra and Opus surpass it on AppWorld, and Astra nearly matches it on BFCL-V4. Starting from Base with a weak harness leaves measurable headroom on both the model and the harness sides. Starting from Instruct with the reference harness would already reach 98.89% on Telecom and leave no post-training headroom to measure, whereas the best researcher mean on TB-Lite (24.43%) remains far below the reference (46.48%). The improvements also carry over to a stronger model. Paired with Instruct, the evolved harnesses surpass the reference harness on AppWorld (Table 2). 

## F Permitted Research and Researcher Instructions 

F.1 Editable Components and Data Boundary 

Researchers may modify weights, the harness, or both. Available operations include diagnosing Visible failures; adjusting prompts, parsers, memory, and context; constructing and filtering training data; generating rollouts; selecting training recipes; and comparing and revising candidates. Data construction and selection relate to data-centric research in RSIBench-Data [8]. Visible tasks support debugging, trajectory generation, and training. Network access is enabled, with datasets that directly expose benchmark task data blocked. Researchers may independently acquire per-mitted public or synthetic training material and record its sources and transformations. Selection/Test solutions, private tests, and per-task trajectories are protected: researchers may not retrieve them or construct data targeted at those instances. The benchmark infrastructure runs every Visible task in a sandbox that returns its reward and supports over 1,000 concurrent rollouts, so researchers can train with reinforcement learning as well as supervised fine-tuning. The fixed qwen3.8-27b teacher may generate permitted training data within a $100 calling budget per development run; evaluation tasks are executed by the target student model. Research uses the supplied Base or its permitted derivatives within the assigned workspace and resources. 

F.2 Development Feedback and Candidate Freezing 

Researchers receive execution details on Visible and score feedback on Selection. Selection task statements and trajectories remain hidden. Development evaluations record task subsets and repetition counts; Test is 20 reserved for final evaluation. Because researchers evaluate many candidates on the same Selection set and keep the best, Selection scores are optimistic estimates of Test performance. In Astra AppWorld Run 2, for example, the final candidate solves 42/51 Selection tasks and 22/51 Test tasks, still above the reference system’s 33.33%. Only the Test set, used once after nomination, measures generalization. One model–harness pair is frozen at the end of development. The researcher nominates a candidate in 

out/<benchmark>_final/ ; without an explicit nomination, the submission is the workspace harness and the weights selected by model_path.txt at the deadline, defaulting to Base. The operator records candidate identities, supplies replay metadata, and runs Test. Ordinary final evaluation leaves the frozen weights and harness unchanged; weight reversion required by the integrity policy follows Appendix J.

## M Audit Procedure and Findings 

Procedure. After each run, an agent applies the same audit skill to the complete development trajectory, including tool calls, file reads and writes, commands, training data lineage, and network logs during evaluation, and screens the whole trajectory regardless of its length. The skill defines six checks: obtaining protected Test or Selection material, substituting unauthorized weights, training on prohibited data, task-specific harness customization, reading files outside the workspace, and the integrity of the evaluation chain. Each check returns one of four verdicts, confirmed, blocked, not found in scope, or insufficient evidence, and only a confirmed verdict counts as a violation. We then review every piece of evidence the agent flags. To prevent and detect Selection or Test instances obtained from the web or other sources, development blocks data sources that directly expose the task pools, and the audit scans downloads, training corpora, and code for protected task IDs, problem text, and n-gram fragments.
