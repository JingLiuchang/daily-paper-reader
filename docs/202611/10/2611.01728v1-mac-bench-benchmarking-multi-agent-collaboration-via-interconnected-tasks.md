## 摘要
基于大语言模型（LLM）的多智能体系统（MAS）通过在各智能体之间分工并协调其对共同目标的贡献来处理具有挑战性的任务。因此，评估这些系统需要基准测试，不仅评估任务求解性能，还评估其处理相互依赖工作的能力。然而，现有基准往往强调任务难度而缺乏实质性的协作要求，或仅评估有限范围的预定义协作模式。本文提出 MAC-Bench，一个通过互连任务评估多智能体协作的综合基准。MAC-Bench 不强制预设智能体角色或通信协议，而是将协作要求直接嵌入任务依赖关系和共享资源约束中。具体而言，我们从选定的基准任务中在两个层面挖掘可复用的协作结构。局部协作模式刻画子任务之间反复出现的交互，而全局任务结构刻画这些交互如何贡献于完整工作流。通过由粗到细的组合，这些结构被重组为结合不同协作要求的任务图。任务在可执行环境中实例化，并对部分进展和完整任务解决进行自动验证。

## Abstract
Large language model (LLM)-based multi-agent systems (MAS) tackle challenging tasks by dividing work among agents and coordinating their contributions toward shared objectives. Evaluating these systems therefore requires benchmarks that assess not only task-solving performance but also the ability to handle interdependent work. However, existing benchmarks often emphasize task difficulty without substantial collaboration requirements or evaluate only a limited range of predefined collaboration patterns. In this paper, we introduce MAC-Bench, a comprehensive benchmark for evaluating multi-agent collaboration through interconnected tasks. Rather than imposing predefined agent roles or communication protocols, MAC-Bench embeds collaboration requirements directly into task dependencies and shared-resource constraints. Specifically, we mine reusable collaboration structures from selected benchmark tasks at two levels. Local collaboration patterns capture recurring interactions among subtasks, while global task structures characterize how these interactions contribute to complete workflows. Through coarse-to-fine composition, these structures are recombined into task graphs combining different collaboration requirements. Tasks are instantiated in executable environments with automated verification of partial progress and complete task resolution.

## 1. 核心问题与整体含义

- **研究背景**：基于 LLM 的多智能体系统（MAS）通过任务分解、角色分工与智能体间通信来扩展单体能力，已广泛应用于推理、软件工程、工具使用等场景。随着系统快速演进，亟需严谨的基准来衡量协作进展并指导系统设计。
- **现有基准的两难困境**：
  - **困境一：复杂度不等于相互依赖**。任务难度与执行长度可通过串行工作堆叠，而不产生需要协调的实质分支。作者抽样分析发现，GAIA 与 SWE-bench Verified 中 98%、Terminal-Bench 2.0 中 74% 的任务属于单一或主要串行工作，仅 22% 的 Terminal-Bench 样本存在确认的相互依赖分支。
  - **困境二：有限模式约束协作覆盖**。MAS 专用基准多通过模板变体或环境机制生成协调需求，只测试选定的交互模式，无法刻画真实协作的复杂性。
- **核心问题**：如何构建可执行任务，以测试**多样组合的协作需求**？
- **整体含义**：MAC-Bench 不预设智能体角色或通信协议，而是把协作要求直接嵌入**任务依赖关系**与**共享资源约束**中，从而将"协作能力"转化为可由任务结构客观检验的属性，分离"部分进展"与"完整解决"两个评价维度。

## 2. 方法论

### 2.1 核心思想
从现有高质量基准任务中挖掘**可复用的协作结构**，在局部与全局两个层级建立结构库，再通过**由粗到细的组合**重组成包含不同协作需求组合的新任务图，最后在可执行环境中实例化并自动验证。

### 2.2 三阶段流水线

**阶段一：依赖感知的任务结构挖掘**
- **任务图抽象**：递归分解任务为子任务 $t=\langle g_t, i_t, o_t, a_t\rangle$（目标、输入、输出、共享资源读写访问），形成任务树 $H$；叶子子任务集 $U$ 上推断两类关系——有向**依赖** $t \prec t'$（输出供给或资源条件建立）与无向**耦合** $t \leftrightarrow t'$（对共享资源的相互影响修改），得到标注依赖图 $G=(U, E_{dep}, E_{cpl})$。
- **局部协作模式挖掘**：用加权 k-medoids 对叶子子任务聚类为类型 $\tau$（综合语义、接口、层级、图位置四类距离）；枚举 2–3 节点连通子图，用置换下的字典序最小规范编码 $M=\min_{\sigma\in P_k} e_\sigma(G_{sub})$ 合并相同模式；记录模式间重叠对齐 $\psi$ 形成连接规则 $(M, M', \psi)$，并按跨任务支持度过滤。
- **全局结构提取**：将任务树内部节点的子组收缩为粗图节点，保留边界接口（外部输入、输出、共享资源访问）；在非根节点上抽取**精化规则**，多输入节点提供**集成模板**，共享资源交互提供**耦合模板**；按组功能类别 $r$（foundation / capability / integrate / deliver）索引局部模式，链接两个库为 $K=(L_L, L_G)$。

**阶段二：由粗到细的任务组合**
- **全局结构组合**：从 $L_G$ 采样整任务粗图与分组树，通过精化、集成、耦合三类操作扩展；以目标偏差函数 $D(C)=\sum_j w_j \max\{\ell_j - z_j(C), 0, z_j(C)-u_j\}$ 衡量与目标组数/集成数区间的距离，配合惩罚项 $\rho_k$ 做目标引导搜索，满足接口兼容与无环性约束。
- **局部模式组合**：对每个终端组按类别 $r$ 以支持度平滑分布 $p(M|r)=\frac{c_r(M)+\alpha}{\sum_{M'}(c_r(M')+\alpha)}$ 采样种子模式，再按连接规则支持度分布 $p(M'|\psi|M)$ 反复附着扩展，直至满足组规模与边界接口覆盖。
- **接口约束图组装**：将组边界映射到局部图中兼容节点，实例化粗依赖与耦合，经接口、资源一致性、无环性检查后输出 $(H^\star, \tilde{G})$。

**阶段三：环境落地的任务实例化**
- 将组合图精化为具体场景：$(d, x_0, V)=\text{Ground}_\Omega(H^\star, \tilde{G})$，产出任务描述 $d$、初始环境状态 $x_0$ 与结果验证器 $V$。
- **结果验证**：基于最终环境状态与产物进行检查，不规定动作序列；区分**目标检查**（请求的变更）与**保留检查**（受保护记录或既有行为不被破坏）。
- **任务校验**：检查需求与操作对应性、加载/重置/初始未完成状态，并用合法替代、非法结果校准评分。

### 2.3 评价指标
- **Progress Score (PS)**：任务内目标组通过比例的任务平均，$PS_i=\frac{1}{|Q_i|}\sum_{q\in Q_i} b_{iq}$。
- **Resolved Rate (RR)**：完全解决任务的比例，完整解决还须满足适用的保留约束。

## 3. 实验设计

- **基准构成**：48 个测试任务，覆盖 6 个类别、每类 8 个：
  - 商业运营（24 个）：财务管理、服务管理、项目管理；
  - 软件工程（24 个）：应用开发、库开发、开发者工具。
  - 另有独立开发集用于方法适配与预算选择，与测试集分离。
- **环境形态**：软件任务暴露项目工作区与终端操作；商业任务通过应用发现、工具描述/调用/结果检索暴露原生应用记录。
- **对比方法**（共 4 个系统 × 2 个骨干）：
  - 单智能体基线 **ReAct**；
  - 三个 MAS：**AOrchestra**（协调者+委派 ReAct worker）、**Magentic-One**（任务/进度账本+发言选择+停滞重规划）、**Meta-Team**（软件用 planner/developer/reviewer，商业用 chairman+3 workers）。
- **骨干模型**：GPT-6 Luna 与 DeepSeek-Flash，同一 run 内所有智能体与辅助调用共用同一骨干。
- **运行协议**：每个 system–backbone–task 组合从重置环境运行 1 个 episode，指令与工具权限一致；按工作量预分配 5M/10M/15M token 上限（所有系统共享），墙钟限制 4 小时；温度 0.0–0.2，最大输出 8,192–32,768 token。
- **补充实验**：
  - 任务级 PS 差异分析（20,000 次任务 bootstrap）；
  - 资源使用与停止条件统计；
  - 协作分析：9 个商业任务、14 个依赖检查 + 6 个共享资源检查、4 个系统（DeepSeek-Flash），共 3,504 个对象级检查、2,840 次对象级比较；
  - 结构复用分析：100 个挖掘任务 + 50 个 held-out 任务，10 条嵌套挖掘序列、41 个不同库；
  - 受控图组合实验：两种图规模 × 60 请求，对比本文组合、Direct LLM、Fixed-global、无目标引导变体、不同操作上限与四种接受准则；
  - 场景实例化比较：30 个业务背景 × 2 请求 × 3 方法 = 180 次尝试；
  - 评分校准：12 个任务 × 6 种条件 = 72 次评估。

## 6. 主要结论与发现

- **性能整体很低**：最优配置仅解决 3/48（6.25%）任务；Meta-Team 在 PS 上领先（GPT-6 Luna 下 22.63% vs ReAct 17.74%；DeepSeek-Flash 下 23.88% vs 21.88%），AOrchestra 与 Magentic-One 的 PS 反而低于 ReAct。
- **进展与解决排序不一致**：PS 高不必然带来更高 RR
