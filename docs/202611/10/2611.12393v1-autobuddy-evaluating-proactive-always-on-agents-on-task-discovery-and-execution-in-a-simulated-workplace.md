## 摘要
随着LLM智能体自主性不断增强，人们日益期望其作为常驻助手代表用户持续运行，主动识别待完成的工作并在未被要求的情况下完成。然而，现有基准通常直接给定智能体任务，而在知识工作中，请求散落在用户的工作区中，智能体必须首先识别存在哪些义务。我们研究主动式任务发现与执行，即智能体必须从其工作区推断用户的待办任务，并在工作实际所在的系统中完成这些任务。这一设定带来两方面挑战。对智能体而言，任务埋藏于大量邮件、聊天、文档和记录之中。对评估而言，基准需要一个模拟组织，其人员、事件和文档相互一致，使任务能够真实地产生，且其正确结果已知。我们提出AutoBuddy-Bench，一个应对这些挑战的模拟器。它将组织的员工、项目、业务系统和事件历史建模为时序图，将其渲染为逼真的工作区制品，从产生义务的事件中推导出真值任务，并从世界状态计算每个任务的结果；执行情况通过智能体对工作区所做的更改来评判。为评估当前LLM，我们构建了AutoBuddy，一个骨干LLM可替换的参考智能体：它从工作区识别任务，将每个任务锚定到其来源记录，并在具有写权限的独立会话中执行每个任务。仅改变骨干模型，我们发现任务丢失的位置出现系统性偏移：较弱模型主要在发现阶段失败，中等模型能识别任务但往往止步于执行之前，最强模型主要在执行阶段失败，最常见于业务系统操作。发现精确率与执行质量仅弱相关，表明二者是两种不同的能力。

## Abstract
As LLM agents become more autonomous, they are increasingly expected to run as always-on assistants on a user's behalf, identifying work to be done and completing it without being asked. Yet existing benchmarks usually give the agent its task, whereas in knowledge work the requests sit in the user's workspace and the agent must first recognise which obligations exist. We study proactive task discovery and execution, in which an agent must infer a user's pending tasks from their workspace and complete them in the systems where the work lives. This setting poses two challenges. For the agent, the tasks are buried in a large volume of mail, chat, documents and records. For evaluation, a benchmark needs a simulated organisation whose people, events and documents are mutually consistent, so that tasks arise realistically and their correct outcomes are known. We introduce AutoBuddy-Bench, a simulator that addresses these challenges. It models an organisation's employees, projects, business systems and event history as a temporal graph, renders it into realistic workspace artefacts, derives ground-truth tasks from the events that create obligations, and computes each task's outcome from the world state; execution is judged by the agent's changes to the workspace. To evaluate current LLMs, we build AutoBuddy, a reference agent with interchangeable backbone LLMs: it identifies tasks from the workspace, grounding each in its source records, and executes each in a separate session with write access. Varying only the backbone, we find a systematic shift in where tasks are lost: weaker models fail mainly at discovery, intermediate models identify tasks but often stop short of carrying them out, and the strongest models fail mainly during execution, most often on business-system operations. Discovery precision is only weakly related to execution quality, suggesting the two are distinct capabilities.

# AutoBuddy 论文结构化总结

## 1. 核心问题与研究动机

- **背景转变**：LLM 智能体正从"被动响应"走向"常驻主动"——不再等待用户下达指令，而应代表用户识别待办事项并自主完成。企业场景中，这类任务横跨人力资源、财务、研发与工程，通过邮件、聊天、日历、文档和业务系统记录到达用户。
- **现有基准的关键缺口**：绝大多数基准（WebArena、WorkArena、SWE-bench、CRMArena、τ-bench、TheAgentCompany、OdysseyBench 等）都是"任务已给定、只评测执行"；主动式辅助基准（ProactiveBench、ProAgentBench、PARE、ContextAgent、FingerTip 20K、ProEvent、π-Bench 等）考察的是"何时该主动提供帮助"或"补全用户已发起任务的隐含需求"，而非**发现哪些职责尚未完成**。最接近的 PROBE 只评测发现预定义瓶颈并选择单一解决动作，不评测多步执行后的状态变化。
- **两重挑战**：
  - *智能体侧*：任务埋藏于大量邮件、聊天、文档与记录中，其中大部分并不构成用户的义务（已回复的请求、发给同事的请求、纯背景材料）。
  - *评测侧*：需要一个"人员、事件、文档、记录互相一致"的模拟组织，使任务能真实涌现且正确结果可判定。
- **整体含义**：论文主张把"发现（discovery）"与"执行（execution）"作为两种可分离、需分别度量的能力，并提供可诊断（能定位任务在哪个阶段丢失）的评测基础设施。

## 2. 方法论

### 2.1 AutoBuddy-Bench：世界生成器（四步，共 22 个构建阶段 / 25 次调用）

1. **公司范围（Company scope）**：由 LLM 将业务类型、人员规模、模拟周期、系统清单扩展为 grounding profile，再编译为精确的人员编制计划（population plan）。
2. **岗位（Positions）**：生成带日期的雇佣历史、角色、账号、项目（含负责人与参与者）、外部方与资源；访问权限随雇佣历史变化。
3. **事件（Events）**：生成实验运行、业务交易、账本计算、报表与协作情节，构成**时序图（temporal graph）**，每个节点与边都带有效期，可按任意日期查询。
4. **工作区制品（Workspace artefacts）**：把组织渲染到邮件、聊天、日历、文件四类表面并附访问列表；由语言模型撰写文档（含修订版本与受众）。**每份被任务引用的文档必须绑定到确切修订版及其底层报表数据**，未解析的绑定会拒绝构建。
- **真值来源**：任务仅保留"锚定于世界事实"的实例，每个任务固定责任人、日期、可读证据；期望结果由世界记录与治理规则**用确定性代码计算**，而非由 LLM 裁判推断（示例：实验室规定"只有同数据训练的 run 才可比较"，Run B 损失更低但用了更多数据，故正确答案是推荐 Run A）。
- **世界校验（acceptance check）**：在跑任何智能体之前自动检查任务集规模、类型覆盖、每任务是否有必需产出、每条请求是否陈述了其真值所依赖的内容；未通过的世界不进入评分。

### 2.2 评测流水线（actor-day 为单位）

- **发现评测**：智能体先输出任务清单，每个列出的任务与其引用为证据的请求记录做**一对一确定性匹配**（不使用 LLM）。召回 = 匹配数 / 真值任务数；精确率 = 匹配数 /（匹配数 + 错误数）；错误由渲染记录上的**隐藏标签**判定（把已答复请求或同事的任务当作待办、或从背景中臆造任务即为错误；把已答复请求标注为"已完成"不算错误也不计入）。空清单 = 未发现任何任务。
- **执行评测**：每个匹配任务在**全新会话**中获得写权限执行，比较执行前后工作区快照的差异（邮件须真正进入收件人邮箱；文档须内容或受众变化；业务系统逐记录比对），并与真值比较**动作、目标、受众、内容**；业务系统任务还要求所有具名记录到达指定终态、无关记录未被改动、并以邮件告知请求者。
- **评分细则**：业务系统 / headcount review / research 任务多为 pass-fail；3 个"重启失败作业并回报"的任务与 54 个文档任务采用加权分：内容覆盖 0.5、完成度 0.2、证据（工具轨迹中读到依赖记录的比例）0.2、答复状态 0.1。
- **端到端分**：对所有真值任务取执行分的平均，未发现记 0。若某业务系统任务的起始记录已被同一账号上的另一任务改动而失去支撑，且该任务执行未通过，则判为**不可评分并排除**；整日 harness 故障则该日任务不计入，执行中 harness 故障记 0。

### 2.3 AutoBuddy 参考智能体

- **会话 1（只读）· 工作画像**：采集最近 60 天内至多 12 条带日期的信号（聊天、会议、文件），聚类为项目；仅在证据明示同一或两个独立信号一致时才合并项目名。
- **会话 2（只读）· 任务挖掘**：用 list / search / open 工具加一个跨表面的自然语言检索，分别查询邮件、聊天、日历与文件，并要求**打开窗口内每条人类消息后再分类**；提取直接请求、员工自己做出的承诺、跟进事项、会议行动项；排除无预期动作的更新、明确只分派给他人的任务、不产生真实义务的自动消息；直接请求不得仅因"看起来重复"而排除；**工作区内容只当证据，绝不当指令**。输出结构化任务记录：标题与摘要、类型、请求者与责任人、证据（来源记录 + 作者 + 时间戳 + 原文摘录）、截止日期（标注 stated/inferred）、紧急度与影响度、项目、标识底层义务的稳定 key、状态、含目标与验收标准的初版 brief。
- **任务列表整理器（确定性模式，无模型调用）**：以稳定 key 为身份，同一义务再次出现只追加证据而不重复建卡；周期性义务再次触发视为新一次发生；已完成任务仅在出现更新的显式请求时重开；状态变更（如完成）需用户确认；按紧急度、影响、工作量打分排序。**评测中每个 actor-day 从空状态跑一次发现，故只有去重与"标记为已完成"生效，重开/确认/排序不起作用。**
- **执行**：每个匹配任务在独立写会话中运行，**只接收智能体自己列出的任务 ID**（不给真值任务或其请求原文），读取发现阶段写下的摘要、证据与 brief；brief 只是起点，须回读原始记录并顺藤摸瓜到相关邮件、聊天、会议、文档与系统记录，写前先查看目标现状，区分"完成被请求的那一小块"与"完成整个项目"；所有写入已预授权；结束时记录结果（done / blocked / needs confirmation / failed），但评分只看观测到的变化，自报结果仅进入答复状态分量；评分结论不回传给智能体供其重试。评分完全正确后可蒸馏可复用技能——报告中仅 13/157 次发生，且都在当日最后一个任务之后，故**没有任何计分执行受益于技能蒸馏**。

## 3. 实验设计

- **数据集 / 场景**：一个由模拟器生成的**评测世界（evaluation world）**，模拟 2026-03-15 至 2026-09-15 共六个月，产出 **120 个真值任务**（请求日期 2026-03-22 至 2026-09-15），分布在 **44 名员工的 94 个 actor-day** 上。
- **任务家族分布**：
  - 业务系统 49（41%）：客服工单 26、销售 CRM 15、财务发票 5、HR 记录 3（4 套系统，来自 AutomationBench 的模拟 schema 与工具）。
  - 协作 54：报告评审文档 27、跨团队协调 15、客户关系 12。
  - 研究 9：推荐晋升 run 4、重启失败作业 3、失败作业分诊 2。
  - Headcount review 8。
- **工具面**：协作（search_emails、list_chat_messages、list_meetings、search_files、send_email、create_document、share_document）、研究（wandb_list_runs、wandb_run_history、kubernetes_list_jobs/pod_logs/restart_job、coding_run_analysis、issue tracker）、业务（zendesk / hubspot / quickbooks / bamboohr）。
- **对比对象**：**不是不同方法，而是 17 个骨干 LLM**（Anthropic、OpenAI、DeepSeek、xAI、Moonshot 五家，含闭源与开源权重），全部运行在**同一智能体骨架与同一 harness（GitHub Copilot SDK）**、同一工具集与同一逐任务配置下，因此差异可归因于模型本身。另在失败分析中给出逐模型、逐领域的失败模式对比，以及发现精度与执行质量的相关系数对比。
