Abstract 

Multi-vector retrieval represents each query and document as a set of embeddings and scores relevance via fine-grained set-to-set interactions such as MaxSim (Chamfer similarity). This expressive-ness improves retrieval quality over single-vector representations, but makes search substantially more expensive. Existing systems address this challenge primarily through proxy representations or filter-and-rerank pipelines that reduce candidate generation to single-vector search. In this work, we study the complementary direction of building a native IVF-style index directly over multi-vector data. We introduce MV-IVF , an inverted-file index for multi-vector retrieval built on MV-Lloyd , a new Lloyd-style algorithm for cluster-ing point clouds under a Chamfer objective. Our key observation is that once point clouds are assigned to clusters, the center-update step reduces to a standard single-vector clustering problem over the flattened embeddings in each cluster. This enables efficient construction of a hierarchical IVF tree whose internal nodes are represented by center point clouds. At query time, MV-IVF performs best-first beam search over the tree to identify promising leaf clusters, then scores the documents in those leaves. We further accelerate search using low-bit quanti-zation, query compression, and cache-efficient batched search. We implement MV-IVF as part of MVSIC , an optimized C++ library and unified evaluation framework for multi-vector retrieval that includes several major multi-vector retrieval approaches. Across BEIR and LoTTE text retrieval benchmarks, MV-IVF achieves strong latency–recall tradeoffs, the best batched throughput frontiers, and favorable build-time and index-size profiles. At 90% Recall-10@10, MV-IVF achieves up to 8 .03 × lower single-query latency and up to 173 .5× higher QPS than the baselines, demonstrating that native IVF-style indexing is a practical and effective approach for scalable multi-vector retrieval. 

1 Introduction 

Multi-vector retrieval has emerged as a powerful paradigm for mod-ern retrieval systems, in which each query and document is repre-sented not by a single embedding, but by a set of embeddings (i.e., a point cloud). Such representations arise naturally in late-interaction models for text retrieval (e.g., ColBERT [11, 14]), where relevance is computed via token-level interactions using operators such as MaxSim, as well as in region-based representations for images and other modalities (e.g., ColPali [8]). This added expressiveness yields significantly better retrieval quality than single-vector encoders (e.g., on standard benchmarks such as BEIR [18], LoTTE [14], and ViDoRe [8]) but the increased complexity of the representation makes search substantially more expensive. The gold-standard multi-vector similarity, introduced by Col-BERT [11] and used by most subsequent late-interaction models, is MaxSim. At scale, the central challenge is therefore to recover the top-𝑘 documents under MaxSim without exhaustively scoring the entire collection. A large body of recent work has focused on making multi-vector retrieval under MaxSim efficient. Most practical approaches follow a common philosophy: rather than indexing point clouds directly, they reduce candidate generation to a simpler proxy or filtering problem built using single-vector retrieval techniques, and reserve exact multi-vector scoring for a smaller set of candidates. For ex-ample, PLAID [13] and its follow-up, WARP [15], use single-vector search over clustered token centroids to generate candidates, which are then scored using quantized and exact MaxSim; Dhulipala et al. [5] formalize this style of pipeline as the single-vector heuristic

MUVERA [5] instead constructs fixed-dimensional encod-ings (FDEs), large single-vector representations whose inner prod-ucts provably approximate multi-vector similarity, thereby reducing the problem to standard single-vector MIPS. These approaches are highly effective, but the quality of the final top-𝑘 results depends on how well the surrogate representation or candidate-generation stage preserves documents that rank highly under MaxSim. This motivates a complementary direction: can we build scalable indexes that operate directly over multi-vector representations while accurately preserving the top-𝑘 results under MaxSim ? A smaller body of work has explored such native multi-vector indexing through hashing- and graph-based approaches, including DESSERT [7] and IGP [4]. In this work, we investigate a different direction: extend-ing clustering-based inverted-file (IVF) indexing, one of the most widely used paradigms for large-scale single-vector retrieval [6, 10], to multi-vector data. IVF is an appealing candidate for this setting. In the single-vector case, an IVF index partitions the dataset into clusters and probes only those whose representatives are most relevant to the query. This organization is simple and scalable to build, has low indexing overhead, exposes substantial parallelism, and is naturally suited to arXiv:2611.09040v1 [cs.IR] 6 Nov 2026 Kishen N Gowda, Laxman Dhulipala, Lars Gottesbüren, and Rajesh Jayaram 

high-throughput batched search. These properties are particularly attractive for multi-vector retrieval, where scoring each candidate is substantially more expensive. However, extending IVF to multi-vector data is non-trivial: how should we cluster point clouds, and what representatives should we use to route queries to the resulting clusters? 

We address these challenges through a set of contributions cen-tered around MV-IVF, our native IVF-style index for multi-vector retrieval.

In this sense, MV-IVF is a native multi-vector index: both the indexed objects and the routing representatives remain point clouds, rather than being reduced to single-vector surrogates. The key algorithmic ingredient is MV-Lloyd . We then develop MV-Lloyd, a practical Lloyd-style algorithm for this problem. Our key observation is that, once the point-cloud assignments to clusters are fixed, finding the optimal center point cloud for a cluster reduces exactly to a weighted 𝑠 -median problem over the flattened embeddings of the point clouds assigned to that cluster. This allows the center-update step to leverage standard, highly optimized single-vector clustering machinery. MV-IVF recursively applies MV-Lloyd to construct a tree-structured partition of the document point clouds and stores the resulting center point clouds at internal nodes for routing. At query time, MV-IVF performs a best-first beam search over the tree to identify a small number of promising leaf clusters and scores only the docu-ments contained in those leaves. We further accelerate search using low-bit quantization, query compression, and early termination. For high-throughput workloads, many queries probe overlap-ping sets of leaves, creating an opportunity to reuse leaf data across queries. Rather than processing each query independently, we group queries that probe the same leaf and score them together, allowing the leaf data to be reused while cache-resident. To further explore the design space of native multi-vector in-dexes, we also develop MV-Vamana , a graph-based index extend-ing the Vamana algorithm [17] to operate directly over point clouds. MV-Vamana builds a proximity graph over document point clouds and performs beam search using multi-vector scores directly. We find that it is highly competitive in the single-query regime, where graph-based search is effective at minimizing the number of expen-sive point-cloud comparisons. Finally, we develop Multi-Vector Search, Indexing and Clustering (MVSIC , pronounced “music”), an optimized C++ library and uni-fied evaluation framework for multi-vector retrieval. MVSIC in-cludes implementations of SVH, MUVERA, MV-Vamana, and MV-IVF using a common framework, optimized scoring kernels, and evaluation pipeline, and also supports direct comparison with PLAID and IGP. We evaluate MVSIC on eight text retrieval datasets from BEIR and the pooled LoTTE benchmark, using ColBERTv2 multi-vector embeddings. We measure retrieval quality against the exact MaxSim ranking, with particular emphasis on Recall-𝑘 @𝑘 , which measures how accurately the full exact top-𝑘 neighborhood is recovered. Across these datasets, MV-IVF achieves strong latency–recall tradeoffs and the best batched throughput frontiers across recall metrics. At 90% Recall-10@10, MV-IVF achieves up to 8.03 × lower single-query latency and up to 173 .5× higher QPS than MUVERA, SVH, and MV-Vamana; the corresponding geometric-mean improve-ments are 1.22 –1.55 × in latency and 2.07 –4.01 × in throughput. MV-IVF also has a favorable build-time and index-size profile, with practical construction times and moderate index size. MV-Vamana is highly competitive in the single-query regime, although its con-struction is substantially more expensive. We additionally compare against FastPLAID and IGP on arguana and fiqa , where MV-IVF achieves substantially higher batched throughput, including over one and two orders of magnitude over IGP and FastPLAID, respec-tively. Taken together, our results show that native IVF-style indexing provides a practical route to scalable, high-quality multi-vector re-trieval: MV-IVF accurately recovers the top-𝑘 neighborhood under MaxSim, supports both low-latency and high-throughput search, and retains the practical build-time and space properties that make IVF attractive in the single-vector setting. To the best of our knowl-edge, MVSIC provides the most comprehensive evaluation of multi-vector retrieval methods across a wide range of datasets to date.

4 Multi-Vector IVF Index (MV-IVF) 

In this section, we describe MV-IVF, a clustering-based retrieval method that generalizes the inverted-file (IVF) framework to multi-vector data. During indexing, the data point clouds are recursively partitioned using MV-Lloyd, producing a tree-structured IVF index whose internal nodes are represented by centroid point clouds. During search, a query is routed to relevant leaf clusters, and the document point clouds contained in those leaves are scored to obtain the final candidates. The key distinction from standard single-vector IVF is that both the indexed objects and the routing representatives are point clouds. Thus, routing decisions are made directly in the native multi-vector space, using MaxSim between the query point cloud and the cen-troid point clouds stored in the tree. 

4.1 Index Construction 

Given the point clouds P associated with a node 𝑢 , the construction proceeds as follows. If |P | ≤ ℓmax , where ℓmax is the maximum leaf size, then 𝑢 becomes a leaf and stores P. Otherwise, we run MV-Lloyd on P with branching factor 𝑏 and centroid point cloud size 

𝑠 , obtaining a partition Π1, Π2, . . . , Π𝑏 together with centroid point clouds 𝐶 1, 𝐶 2, . . . , 𝐶 𝑏 . We create one child for each cluster Π𝑖 , store the corresponding centroid point cloud 𝐶 𝑖 at that child, and recurse on Π𝑖 .In this way, MV-IVF builds a tree whose leaves contain document point clouds, while the internal node store centroid point clouds used for routing. The resulting structure is a direct multi-vector analogue of a standard 𝑘 -means tree, except that clustering and routing are done over point clouds. 

4.2 Search 

To identify the top nprobe leafs to probe for a query point cloud 

𝑄 , we perform a greedy beam search over the tree, prioritizing nodes by their MaxSim score with 𝑄 . The search maintains a beam of active internal nodes, truncated to size beam_size , and a list 

L of the best nprobe leaves encountered so far. At each step, it expands the highest-scoring internal node, scores its child centroid point clouds, and inserts the most promising child nodes into the appropriate collection: internal nodes into the beam, and leaves into L.We also employ the following early termination strategy. Sup-pose the algorithm has already found nprobe leaf nodes. If the best remaining internal node in the beam has MaxSim value no larger than the worst leaf currently in L, then the search terminates. In-tuitively, this indicates that the remaining frontier is unlikely to contain a better probe leaf, and further exploration is unlikely to improve the final probe set. We note that this rule is a heuristic: the centroid point cloud stored at an internal node is used as a routing representative, rather than a certified upper bound on the scores of all leaves in its subtree. Empirically, however, this early termination substantially reduces search time with little effect on retrieval quality. Algorithm 2 summarizes the greedy search procedure. Once the top nprobe leaves have been identified, MV-IVF scores the document point clouds contained in those leaves using MaxSim and returns the top-𝑘 results overall. 

4.3 Batch Search 

In high-throughput settings, queries either arrive in, or can be read-ily grouped into batches . A naive approach for this batch setting is to simply run the single-query algorithm independently per query, but this misses significant optimization opportunities as many queries end up probing the same leaf clusters, and repeatedly loading the same leaf data, wasting memory bandwidth. This structure is partic-ular to IVF-style indexes: unlike graph-based beam search, whose traversal is irregular and query-dependent, IVF exposes shared leaf-level work that can be batched and scored with good locality. To exploit this structure, MV-IVF uses a batched search procedure that preserves the logical behavior of the single-query algorithm, but reorganizes the work to improve locality and vectorization. The input is a batch of query point clouds 𝑄 1, 𝑄 2, . . . , 𝑄 𝑚 , where each query may have its own search parameters such as 𝑘 and nprobe .For each query, the goal is still to identify a set of probe leaves, score the document point clouds in those leaves, and return the final results. The difference is that MV-IVF schedules the expensive scoring work across queries so that shared tree and leaf data can be reused while it is cache-resident. 

Batched probe generation. At the root, every query must score the same set of child centroid point clouds. We therefore compute these scores for the entire query batch together, turning root scoring into a many-to-many MaxSim computation. After the root, each query continues its own greedy search independently. Although the same batching idea could be applied deeper in the tree, doing so requires additional synchronization and gives diminishing returns as queries quickly diverge to different subtrees. 

Leaf-grouped scoring. After probe generation, each query has a set of leaves that it needs to scan. Rather than processing each query–leaf pair independently, MV-IVF groups the work by leaf. For each leaf 𝑢 , we collect all queries whose probe set contains 𝑢 , load MV-IVF: Multi-Vector Retrieval via Multi-Vector Clustering 

the document point clouds stored in 𝑢 , and score them against all queries assigned to that leaf. This improves cache locality by reusing the same leaf data across multiple queries and avoids repeatedly streaming large point-cloud data from memory. 

Gathering results. The leaf-grouped organization introduces a final gathering step: after each leaf has scored the queries assigned to it, the resulting candidates must be collected back into per-query result sets. We implement this by having each leaf-scoring kernel produce local top candidates for its assigned queries, then scatter these candidates into per-query buffers. Each query then aggregates the candidates returned from all of its probed leaves, keeps the best 

𝑘 candidates, and returns them as the final top-𝑘 results. This scatter-and-gather step adds synchronization and memory traffic, but in our setting this overhead is outweighed by the improved locality from grouping leaf scans and reusing leaf data across multiple queries. The common computational primitive in both batched probe generation and leaf-grouped scoring is a many-to-many MaxSim problem: a group of query point clouds must be scored against a group of document point clouds stored in the same leaf. For exact scoring, we decompose this into a sequence of vectorized matrix multiplications and reduction operations, using optimized linear-algebra kernels where appropriate. We also use standard systems techniques such as cache-aware blocking and software prefetching to reduce memory stalls during leaf scans. Nevertheless, exact many-to-many MaxSim scoring remains expensive, especially for large leaves and long point clouds. In Section 5, we describe how the same batched organization is combined with quantization, compact representations, and specialized low-bit scoring kernels. Overall, batched search keeps the same retrieval semantics as single-query MV-IVF. The advantage is in how the work is orga-nized. By grouping queries by leaf and using vectorized many-to-many MaxSim kernels, MV-IVF better exploits cache locality, mem-ory bandwidth, and SIMD parallelism in high-throughput retrieval workloads. 

5 Practical Optimizations 

In MV-IVF, multi-vector scoring remains the expensive bottleneck because each query-document comparison involves many vector interactions. In this section, we describe the main optimizations used in our implementation to accelerate routing, leaf scoring, and batched retrieval. 

5.1 Quantization 

A key bottleneck in multi-vector retrieval is the cost of comput-ing Chamfer distances, which requires evaluating many pairwise single-vector distances. We leverage three quantization schemes at different points on the accuracy–compression tradeoff curve. All three share the same preprocessing step: a randomized rotation via a Fast Hadamard Transform (FHT) with random sign flips, following the approach used in RaBitQ [9] and TurboQuant [20]. 

Rand-1bit. Here we quantize each rotated coordinate to a single bit by simply taking its sign. This yields 𝐷 ′/8 bytes per vector (i.e., 32 × compression over float32). Because the rotation isotropizes the coordinates, sign bits after random rotation preserve angular relationships between vectors: the expected fraction of differing sign bits between two vectors is arccos (⟨ 𝑥, 𝑦 ⟩)/ 𝜋 , so the Hamming distance of the sign-bit codes is a faithful proxy for angular distance. Rand-1Bit is amenable to very fast SIMD implementations as the distance kernel reduces to XOR plus population count, avoiding all multiply-add arithmetic. On hardware supporting VPOPCNTDQ, each inner-loop iteration processes 512 dimensions via a single XOR and a single per-64-bit-lane popcount. Furthermore, the per-cloud running minimum in the Chamfer computation can be maintained entirely in integer arithmetic, with a single conversion to floating point at the end. 

TurboQuant 4-bit. We integrate an existing 4-bit scalar quanti-zation scheme [3] that uses a fixed, non-uniform codebook of 16 centroids (8 positive, 8 negative, symmetric about zero) whose spac-ing is tailored to the approximately sub-Gaussian distribution of coordinates after rotation. Each rotated coordinate is mapped to the nearest centroid and two 4-bit codes are nibble-packed per byte, giv-ing 𝐷 ′/2 bytes per vector. Queries are encoded asymmetrically at 8-bit precision. We adapt the single-vector SIMD kernels from this implementation to the multi-vector setting by tailoring the GEMM kernel to small matrices, circumventing the heavy cache-blocking machinery and unrolling. We pre-transpose database vectors into panels of sub-vectors to compute 16 4-dimensional dot products per instruction using VPDPBUSD.

In particular, since each dimension occupies a full byte, the SIMD kernel requires no codebook lookup or nibble un-packing. The multi-vector panel layout and GEMM micro-kernels are similar to the 4-bit case. 

Other methods. We also explored other popular quantization strategies, including Product Quantization with FastScan-style opti-mizations and RaBitQ [9]. We discuss these variants, together with some empirical comparisons, in Appendix B.2. 

5.2 Query Compression 

Query point clouds often contain substantial redundancy, so many MaxSim computations can be accelerated by scoring a smaller rep-resentative set of query vectors. Following this observation, also used in [5], we compress each query point cloud before routing and leaf scoring. Given a query 𝑄 , both compression methods considered below produce a partition B = {𝐵 1, . . . , 𝐵 𝑟 } of the query embeddings, and replace each block 𝐵 𝑖 by a single representative ¯ 𝑞 𝑖 := Í𝑞 ∈𝐵 𝑖 𝑞. 

The compressed query is then ¯ 𝑄 = { ¯𝑞 1, . . . , ¯𝑞 𝑟 }. Using sums rather than averages preserves the scale of the original MaxSim score: a block with more query embeddings contributes proportionally more to the final score. Larger compression thresholds produce fewer representatives and faster scoring, but can reduce retrieval quality.

6 Experiments 

We evaluate MV-IVF through MVSIC, our unified framework for 

Multi-Vector Search, Indexing, and Clustering (pronounced “mu-sic”). Our evaluation focuses on four questions: (1) how does MV-IVF compare with existing multi-vector retrieval methods in single-query latency; (2) how does it perform for high-throughput batched search; (3) what are its indexing time and space requirements; and (4) how do its main design parameters and optimizations affect performance? 

6.1 Experimental Setup 

Datasets. We evaluate on eight text retrieval datasets from BEIR [18] and the pooled LoTTE benchmark from ColBERTv2 [14]. All docu-ments and queries are encoded using ColBERTv2, yielding one point cloud of token embeddings per document or query. The datasets are summarized in Table 1. 

Metrics. Search quality is measured with respect to the exact top-𝐾 

documents under MaxSim. We report Recall-1@ 𝐾 , the fraction of queries for which the exact nearest neighbor appears in the returned top-𝐾 set, and Recall-𝐾 @𝐾 , the average fraction of the exact top-𝐾 

set recovered. While much of the multi-vector retrieval literature emphasizes Recall-1@ 𝐾 , Recall-𝐾 @𝐾 is the natural analogue of the standard approximate top-𝐾 retrieval metric: it measures how well the full top-𝐾 neighborhood under MaxSim is preserved. We restrict the reported operating points to latency at most 100 ms 

and throughput at least 10 QPS , keeping the Pareto curves focused on practically relevant regimes. 

Methods. We compare MV-IVF against three multi-vector retrieval methods representing different indexing strategies: (1) SVH is the single-vector candidate-generation approach un-derlying PLAID [13] and WARP [15]. It indexes the flattened document embeddings using a single-vector ANN index and performs an independent ANN search for each query embed-ding. Within each search, vectors from the same document are deduplicated by retaining their maximum similarity; these scores are then summed across query embeddings to obtain an approximate MaxSim score for each candidate document. The highest-scoring candidates are then reranked using MaxSim to produce the final top-𝑘 results. (2) MUVERA [5] maps each query and document point cloud to a fixed-dimensional encoding (FDE) whose inner product ap-proximates their MaxSim score. It indexes the document FDEs using a single-vector ANN index and searches this index using the query FDE to generate candidate documents. The highest-scoring candidates are then reranked using MaxSim to produce the final top-𝑘 results. (3) MV-Vamana is our native graph-based baseline. It extends Vamana [17] to point-cloud data by constructing a proximity graph over document point clouds and performing beam search directly using MaxSim scores. 

Implementation and parameter settings. All four methods are implemented in MVSIC and use the same document/query em-beddings, shared optimized scoring infrastructure, and evaluation pipeline. For SVH and MUVERA, the underlying single-vector ANN index is Vamana. For MUVERA, we use 𝑑 FDE = 10240, except on 

msmarco , where we use 𝑑 FDE = 2560, following [5]. For the Vamana indexes, we use standard build parameters from ParlayANN [12]. The rest of the build and search parameters are described in Ap-pendix B.1. 

Quantization. We use low-bit quantization to accelerate scoring for all methods. For MV-IVF, we use TQ-4bit during tree search, Rand-1bit for coarse leaf scoring, and Rand-8bit for reranking. For SVH, MUVERA, and MV-Vamana, we use TQ-4bit during Vamana search and Rand-8bit for reranking. The quality and performance of the quantization schemes used in our implementation are evaluated in Appendix B.2.

6.2 End-to-End Search Performance 

Latency Experiments. We first evaluate query latency. For each method and dataset, we sweep the method’s search parameters and plot the Pareto frontier of latency versus Recall-1@10, Recall-10@10, and Recall-100@100. The system uses only a single core here. Figure 1 shows these curves on a representative subset of the datasets; see Appendix B.4 for full results. The three recall metrics highlight different aspects of the retrieval problem. For Recall-1@10, SVH is a particularly strong baseline. This is expected: SVH performs candidate generation at the level of individual embedding vectors, and is therefore well suited to finding documents with a small number of highly matching token-level interactions. After reranking, this is often enough to recover the nearest document under MaxSim. The picture changes for Recall-10@10. On most datasets, SVH is no longer competitive, indicating that recovering the full top-10 neighborhood requires more than finding a few high-signal token matches. In this regime, MV-IVF, MV-Vamana, and MUVERA are all competitive on the larger datasets ( hotpotqa, lotte ), while MV-IVF outperforms all methods on the smaller datasets ( nfcorpus, scifact, arguana, scidocs, fiqa ). The main exception is nq ,where SVH remains strong even for Recall-10@10. This suggests that on this dataset, the top-10 documents are often recoverable from a small number of strong token-level matches, making single-vector candidate generation unusually effective. Recall-100@100 gives the most demanding test of approximate multi-vector retrieval. Here, the goal is to preserve a much larger neighborhood under MaxSim. In this regime, SVH struggles even on 

nq , consistent with the view that token-level candidate generation is most effective for recovering the very top of the ranking, but less effective for preserving a broader neighborhood under MaxSim. On larger datasets, MV-Vamana often gives the best single-query latency frontier, consistent with the advantages of graph-based indexes in minimizing the number of point-cloud score evaluations. At the same time, MV-IVF is competitive with the best method across datasets for Recall-100@100, showing that the clustering-based partition preserves enough multi-vector structure for high-quality routing. We note that SVH remains strong on msmarco even for Recall-100@100. This may partly reflect that msmarco is part of the train-ing data for ColBERTv2, making token-level matching unusually effective on this dataset. Overall, at 90% Recall-10@10, MV-IVF is 1 .33 × faster than MU-VERA, 1 .55 × faster than SVH, and 1 .22 × faster than MV-Vamana in geometric mean, with maximum speedups of up to 4 .76 ×, 8 .03 ×,and 5 .13 ×, respectively.

6.3 Build Time and Index Size 

We next compare the preprocessing cost and storage overhead of each method. Figure 4 reports wall-clock build time and final on-disk index size across datasets. Overall, MV-IVF has a favorable build-time and index-storage profile. Its construction is practical across datasets and is often substantially faster than methods that use single-vector retrieval machinery as a black box. The IVF tree introduces little additional storage beyond the center point clouds and leaf-level membership information. MV-Vamana produces the smallest index, but its con-struction is substantially more expensive because building the graph requires many multi-vector comparisons. Thus, MV-IVF provides a useful middle ground: it retains native multi-vector routing while keeping both preprocessing time and index size moderate.

7 Conclusion 

We presented MV-IVF, a native IVF-style index for multi-vector retrieval. The key ingredient is MV-Lloyd, a Lloyd-style cluster-ing primitive for point clouds under a Chamfer-based objective, which lets us build an IVF tree whose routing representatives are themselves point clouds. Together with quantized scoring, query compression, and cache-efficient batched search, MV-IVF gives a practical clustering-based approach to multi-vector search. We also presented MV-Vamana, a native graph-based index, and MVSIC, a unified C++ framework for implementing and evaluating multi-vector retrieval methods. Our experiments show that MV-IVF pro-vides strong latency–recall and throughput–recall tradeoffs while maintaining moderate build time and index size. Several directions remain open. First, the clustering problem underlying MV-Lloyd deserves further study, including approxi-mation algorithms, initialization schemes, and variants based on different normalizations or set-to-set similarities. Although clus-tering with non-metric objectives is generally hard, it is not clear whether existing hardness results fully capture the structure of Chamfer objectives arising from multi-vector embeddings. Second, the design space for multi-vector IVF is still far from exhausted: spilling, probe allocation, and reranking strategies may lead to further improvements, especially on larger datasets. Finally, MV-Vamana is a promising direction in its own right. While its build time is high and its irregular search pattern is less favorable for batching, graph-based search is effective at minimizing expensive multi-vector comparisons, and merits deeper study.

B Experiments (continued) 

In this section, we continue the discussion of the experiments from the main paper. 

B.1 Baselines and Parameter Settings 

We compare MV-IVF against three methods: SVH, MUVERA, and MV-Vamana. SVH is a single-vector candidate-generation base-line: it indexes the flattened document embeddings with a single-vector ANN index, retrieves candidate documents through their individual embeddings, and reranks the resulting candidates using multi-vector scoring. MUVERA reduces each point cloud to a fixed-dimensional encoding and performs candidate generation using a single-vector ANN index over these encodings. MV-Vamana is our native graph-based baseline, obtained by building a Vamana-style graph directly over document point clouds. All four methods are implemented in MVSIC and use the same document/query embeddings, scoring kernels, and evaluation pipeline. For SVH and MUVERA, the underlying single-vector ANN index is Vamana. For MUVERA, we use the parameter settings recom-mended in [5]; for all Vamana graphs, we use standard settings from ParlayANN [12]. For each method, we sweep the search-time parameters listed in Table 2 and report the Pareto frontier over all resulting operating points. Thus, the main comparisons are based on the best recall–efficiency tradeoff achieved by each method over its specified parameter grid, rather than on a single hand-tuned setting. 

B.2 Quantization 

We evaluate several quantization paradigms used throughout the paper. In addition to the TQ, Rand-1bit, and Rand-8bit variants described in Section 5, we also compare against PQ FastScan-style kernels [1, 2] and RaBitQ [9]. For RaBitQ, we use the publicly avail-able RaBitQ library implementation [9]. 

Single-vector over-retrieval benchmark. We first evaluate the quantizers on single-vector inner-product search. For each quan-tized scorer, we retrieve the top 𝑘 ′ candidates under the approximate scores and report Recall-10@ 𝑘 ′ with respect to the exact top-10 neighbors. This measures how much over-retrieval is needed for the quantized scores to preserve the true nearest neighbors. Figure 7 reports the resulting recall curves. In the plot labels, FS-4 𝑏 , FS-8 𝑏 , etc. denote the block-size vari-ants used by our FastScan implementation; in this notation, FS-4 𝑏 

corresponds to one bit per coordinate, while FS-8 𝑏 corresponds to one half-bit per coordinate. We also include both Rand-1bit and Rand-1bit-asym: Rand-1bit quantizes both database and query vec-tors, while Rand-1bit-asym uses an asymmetric query variant. We observe that Rand-8bit and RQ-8bit preserve quality extremely well, making them suitable as high-fidelity reranking quantizers. RQ-4bit and TQ-4bit provide a good medium-quality tradeoff and are well suited for candidate generation, while Rand-1bit, RQ-1bit, FS-2 𝑏 ,and FS-4 𝑏 are lower-quality but substantially cheaper scorers. 

Multi-vector over-retrieval benchmark. We next evaluate the same quantizers inside the multi-vector retrieval pipeline. Figure 8 reports the resulting recall–over-retrieval curves. An interesting observation is that the quantizers perform com-paratively better in the multi-vector setting than in the single-vector setting. One reason is that MaxSim aggregates many query-token contributions into a single query-document score. As a result, er-rors in individual inner-product estimates can partially smooth out at the level of the full point-cloud score. This makes even relatively low-precision quantizers useful for coarse multi-vector scoring, especially when the goal is to recover a sufficiently large candidate set rather than exactly match the full-precision ordering. 

B.3 Query Compression 

Multi-vector scoring is linear in the number of query embeddings, and many queries contain redundant token vectors. We therefore compress each query point cloud before scoring. Given a query 𝑄 ,both compression methods considered below produce a partition 

B = {𝐵 1, . . . , 𝐵 𝑟 } of the query embeddings, and replace each block 

𝐵 𝑖 by a single representative ¯ 𝑞 𝑖 := Í𝑞 ∈𝐵 𝑖 𝑞. The compressed query is then ¯ 𝑄 = { ¯𝑞 1, . . . , ¯𝑞 𝑟 }. Using sums rather than averages preserves the scale of the original MaxSim score: a block with more query em-beddings contributes proportionally more to the final score. Larger compression thresholds produce fewer representatives and faster scoring, but can reduce retrieval quality. 

Ball Carving. Ball carving is the greedy query-compression method used by MUVERA [5]. Given a distance threshold 𝜏 , the algorithm repeatedly selects an unassigned query embedding 𝑞 , forms a block consisting of all currently unassigned embeddings within distance 

𝜏 of 𝑞 , replaces this block by the sum of its vectors, and removes the block from the active set. This process continues until all query embeddings have been assigned. Thus, the number of compressed query vectors is not fixed in advance; it is determined by the geom-etry of the query and the threshold 𝜏 .

Ward’s Method. We also consider compression based on Ward’s agglomerative clustering [19]. Each query embedding is initialized as a singleton cluster. We then repeatedly merge the pair of clus-ters that causes the smallest increase in within-cluster variance, stopping once the next merge exceeds a threshold 𝜏 . As with ball carving, each final cluster is represented by the sum of its embed-dings. Ward compression tends to form more balanced and coherent groups of query vectors, and in our experiments gives a slightly better quality–compression tradeoff. 

Discussion. Figure 9 compares the two compression methods as the threshold is varied. Both methods are effective: moderate com-pression reduces the number of query embeddings substantially with little effect on recall.
