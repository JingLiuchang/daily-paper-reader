Abstract 

Large language model (LLM)-based multi-agent systems (MAS) tackle challenging tasks by dividing work among agents and coordinat-ing their contributions toward shared objectives. Evaluating these systems therefore requires benchmarks that assess not only task-solving performance but also the ability to handle in-terdependent work. However, existing bench-marks often emphasize task difficulty without substantial collaboration requirements or eval-uate only a limited range of predefined collab-oration patterns. In this paper, we introduce 

MAC-Bench , a comprehensive benchmark for evaluating multi-agent collaboration through interconnected tasks. Rather than imposing predefined agent roles or communication pro-tocols, MAC-Bench embeds collaboration re-quirements directly into task dependencies and shared-resource constraints. Specifically, we mine reusable collaboration structures from se-lected benchmark tasks at two levels. Local collaboration patterns capture recurring interac-tions among subtasks, while global task struc-tures characterize how these interactions con-tribute to complete workflows. Through coarse-to-fine composition, these structures are recom-bined into task graphs combining different col-laboration requirements. Tasks are instantiated in executable environments with automated ver-ification of partial progress and complete task resolution. 

1 Introduction 

Large language model (LLM)-based multi-agent systems (MAS) combine task decomposition, spe-cialized roles, and inter-agent communication to ex-tend the capabilities of individual agents (Li et al., 2023a; Wu et al., 2023; Hong et al., 2023; Qian et al., 2024; Feng et al., 2026). Recent systems further automate team organization and adaptation, achieving strong performance in reasoning, soft-ware engineering, and tool use (Ruan et al., 2026; Yang et al., 2025b; Hao et al., 2026; Cao et al., 2026). The rapid advancement of LLM-based MAS calls for rigorous benchmarks to measure collaborative progress and guide system design on complex, long-horizon tasks. Benchmarks used to evaluate MAS fall into two categories: (1) General-purpose agent benchmarks 

offer complex, multi-step tasks for evaluating MAS (Ruan et al., 2026; Yang et al., 2025b; Hao et al., 2026), spanning reasoning (Hendrycks et al., 2021), software engineering (Jimenez et al., 2024), and interactive tool use (Mialon et al., 2024; Trivedi et al., 2024; Li et al., 2023b; Yao et al., 2024; Merrill et al., 2026; Zhou et al., 2024; Xie et al., 2024b). Their difficulty and execution length moti-vate division of work to improve overall task per-formance. (2) MAS-specific benchmarks construct explicit collaboration requirements (Zhu et al., 2025; Grötschla et al., 2025; Du et al., 2026; Ke et al., 2026), including distributed-information and privacy-constrained exchange (Zhang et al., 2026; Ossowski et al., 2025; Park et al., 2026), role-separated execution (Kim et al., 2026), joint action in games (Xu et al., 2024b; Agashe et al., 2025; Sun et al., 2025), and integration of separately devel-oped features (Khatua et al., 2026). Recent efforts extend evaluation to long-horizon workflows and scalable task generation (Kim et al., 2026; Shu et al., 2026; Tessera et al., 2026). Tasks are ex-panded through variants of curated templates (Kim et al., 2026; Shu et al., 2026), or by generating co-ordination requirements from environment-specific mechanisms (Tessera et al., 2026). Despite this progress, constructing tasks for MAS collaboration evaluation presents two dilem-mas. (1) Complexity does not imply interdepen-dence (Dilemma 1) . Difficulty and execution length can increase through serial work without creating substantial branches that require coordi-nation (Kim et al., 2025; Anthropic, 2025). (2) Limited patterns constrain collaboration coverage

2 Preliminary Study 

Before presenting MAC-Bench, we examine task structures for evaluating multi-agent collaboration and their coverage in existing benchmarks. 

2.1 What Tasks Test Collaboration? 

Evaluating multi-agent collaboration requires ex-amining how agents coordinate different parts of a task toward a shared outcome (Hong et al., 2023; Qian et al., 2024). We describe these parts as branches, each involving sustained work toward a local goal and producing intermediate results. Separately progressable branches support division of work and parallel execution (Anthropic, 2025; Carlini, 2026). However, parallel progress alone 2does not establish the ability to coordinate interde-pendent work (Kim et al., 2025). When branches depend on one another’s outputs or modify shared resources, local decisions can constrain work in other branches (Anthropic, 2026). Agents must then reconcile their contributions, as misalignment and integration conflicts can prevent joint comple-tion (Cemri et al., 2025; Khatua et al., 2026). Tasks combining substantial branches with these depen-dencies allow evaluation of local progress and co-ordination toward task completion. 

2.2 Do Existing Benchmarks Cover Such Tasks? 

We next examine how frequently benchmarks com-monly used for MAS evaluation contain substantial branches with cross-branch dependencies. We an-alyze 50 uniformly sampled tasks from each of GAIA, SWE-bench Verified, and Terminal-Bench 2.0 (Mialon et al., 2024; Jimenez et al., 2024; Mer-rill et al., 2026), distinguishing serial work, in-dependent branches, and interdependent branches (Appendix G.3.1). As shown in Figure 2, single or primarily serial work accounts for 98% of sam-pled tasks in both GAIA and SWE-bench Verified and 74% in Terminal-Bench 2.0. Only 22% of the Terminal-Bench samples have confirmed interde-pendent branches, motivating explicit construction of such tasks. For MAS-specific benchmarks, we consider how different collaboration requirements are combined within complete tasks. Template-based expansion varies task content or initial conditions within es-tablished workflows (Kim et al., 2026; Shu et al., 2026), while procedural environments generate co-ordination requirements through their own mechan-ics (Tessera et al., 2026). Reusing a complete workflow preserves the connections among task branches, but carries over their original organiza-tion. An interaction alone, however, leaves unspeci-fied the work that produces and consumes its result. Assessing such combinations calls for tasks that link local interactions to substantial work across branches. These analyses motivate selecting tasks with sub-stantial, interdependent branches as material for benchmark construction. Benchmarks of profes-sional work and multi-component software devel-opment provide candidates for such selection (Shi et al., 2026; Ren et al., 2026; Xu et al., 2026b; Deng et al., 2026). We can then mine and recombine their constituent structures to create new combinations of collaboration requirements within coherent, exe-cutable tasks. 

3 MAC-Bench 

MAC-Bench evaluates multi-agent systems on ex-ecutable tasks involving substantial and interde-pendent work. This section presents their format, evaluation, and construction. 

3.1 Task Format and Evaluation 

As illustrated in Figure 1, each MAC-Bench task involves multiple interconnected work components toward a common objective. An evaluation in-stance provides a task description, an initialized environment, and permitted operations. The eval-uated system determines how to organize and co-ordinate the work, without prescribed agent roles or workflows. Construction graphs and reference materials remain hidden. MAC-Bench contains 48 test tasks across six categories in business operations and software en-gineering, alongside a separate development set. Private outcome verifiers assess partial progress and complete resolution through observable envi-ronment states and artifacts. We construct these tasks through a three-stage pipeline that combines diverse work dependencies. 

3.2 Benchmark Construction 

The construction process consists of three stages: (1) Dependency-aware Task Structure Mining 

abstracts tasks from existing benchmarks into graphs and builds a reusable library of local collab-oration patterns, global task structures, and com-position rules. (2) Coarse-to-fine Task Compo-sition uses this library to recombine global struc-tures and expand them with local patterns into new task graphs. (3) Environment-grounded Task Instantiation refines the composed graphs into environment-supported scenarios and prepares task descriptions, initial environment states, and out-come verifiers. The task graphs specify work re-quirements and dependencies; agent organization is left to the evaluated system. Figure 3 illustrates the construction process.

3.2.2 Coarse-to-fine Task Composition 

Local patterns provide reusable interactions, while global structures specify how they are organized within complete tasks. Using K, we first compose group-level structures from LG, expand each group with patterns from LL, and assemble local graphs using coarse dependencies and couplings. 

Global Structure Composition. We sample a whole-task coarse graph from LG with a corre-sponding grouping tree. Refinement replaces a group with its child-group graph through stored boundary mappings; integration inserts a multi-input group; coupling introduces shared-resource interactions. The tree records containment sepa-rately from graph interactions. Target-guided search applies compatible rules to meet group and integration count ranges while preserving interfaces and dependency acyclicity. Accepted outputs comprise a grouping tree H⋆ and a coarse graph G⋆, whose nodes correspond to ter-minal tree groups and retain category r, local size targets, and boundary interfaces.

4 Experiments 

We evaluate agent performance, analyze collabo-ration, and examine benchmark validity through three research questions: RQ1 (Benchmark per-formance): How do agent systems perform on MAC-Bench across task domains and backbones? 

RQ2 (Collaboration analysis): How do agent sys-tems handle task dependencies and shared-resource constraints? RQ3 (Benchmark validity): Does MAC-Bench provide valid, diverse tasks for multi-agent collaboration evaluation? 

4.1 Experimental Setup Benchmark. The main evaluation uses all 48 test tasks in MAC-Bench, with eight tasks in each of six categories across Business Operations and Soft-ware Engineering (Section 3.1). Development tasks are separate from the test set. 

Baselines. We compare single-agent ReAct (Yao et al., 2023) with three MAS: AOrchestra (Ruan et al., 2026), Magentic-One (Fourney et al., 2024), and Meta-Team (Hao et al., 2026). Each system is evaluated with GPT-6 Luna and DeepSeek-Flash; the same backbone is used for all agents and auxil-iary model calls within a run. 

Evaluation Protocol. We run one episode per system–backbone–task combination from a reset environment with identical instructions and tool access. Task caps of 5M, 10M, or 15M input/out-put tokens are preassigned by workload, cover all model calls, and apply to all systems and back-bones. Meta-Team adapts on development tasks and freezes teams before testing. Further settings appear in Appendix G.1. 

Evaluation Metrics. We report Progress Score (PS) and Resolved Rate (RR) . PS averages the fraction of achieved goals across tasks; RR is the fraction of fully resolved tasks. Automated checks assess final environment states and artifacts; full resolution also requires applicable preservation constraints. We report both as percentages by cate-gory and overall (Appendix G.2).

4.4 Benchmark Validity (RQ3) 

We validate MAC-Bench through task-structure analysis, reference execution, and scoring calibra-tion. Across all 48 tasks, we examine branches, de-pendencies, and shared-resource constraints. Refer-ence solutions pass complete task grading on all 48 tasks; none of the untouched initial states passes. For scoring calibration, we select two tasks per category and evaluate six conditions: a reference result, a legal alternative, missing work, a broken relation, a preservation violation, and a correspond-ing repair. These yield 72 evaluations; procedures and interventions are detailed in Appendix D.

6 Conclusion 

MAC-Bench provides substantial, interconnected tasks across business operations and software en-gineering by mining and composing reusable task structures. Tasks combine varied dependencies, in-tegration, and shared-resource constraints; targeted checks show effects of selected relation violations. Across two LLM backbones, Meta-Team leads in progress, while AOrchestra and Magentic-One trail ReAct. No configuration resolves more than 6.25% of tasks. MAC-Bench separates partial progress from complete task resolution.

12 A Frequently Asked Questions 

How do task structures relate to agent organi-zation? Task structures specify how work results depend on one another; the evaluated system de-cides how agents produce and coordinate those re-sults. A system can assign several branches to one agent or divide a branch among multiple agents. It receives the public task description, initialized envi-ronment, and permitted operations, while construc-tion graphs and reference materials remain hidden. Outcome verifiers assess the required states and ar-tifacts. Relation-level analysis then connects these outcomes to the system’s actual division of work (Section 3.1 and Appendix G.3.2). 

How are task feasibility and scoring validated? 

We review the correspondence between public re-quirements, available task materials, and scoring checks. Reference solutions pass complete grading on all 48 test tasks. On twelve tasks, controlled scoring tests accept valid alternative results and repairs while rejecting missing work, broken re-lations, and preservation violations. Further tests examine shared-resource conflicts and missing up-stream records. Together, these checks assess whether tasks can be completed and whether scor-ing responds to the stated requirements (Table 2 and Appendix D). 

Why are task-resolution rates low? MAC-Bench tasks are demanding in specification length, workload, and coordination. Lengthy task de-scriptions and supporting materials contain re-quirements, exceptions, and constraints that sys-tems must interpret and track throughout execu-tion. Each task contains 3–10 substantial work branches, with a median of five. For example, the housing task covers 48 households: each needs an eligible flat, a reconciled account, a staffed key-collection appointment, and a consistent handover pack. Changing a flat assignment can affect the fee, collection location, and officer assignment. Soft-ware tasks similarly require interacting components to work together; the build-frontend task connects its CLI, build engine, and isolated environment. Complete resolution requires all task goals and ap-plicable preservation constraints to hold together, combining substantial local work with consistency across its results. Task structures and examples are detailed in Appendix B. 

Why use existing tasks to construct a new bench-mark? Existing tasks provide concrete examples of professional work and multi-component soft-ware development. We extract their local collab-oration patterns and global task structures, then recombine and instantiate them into new evalua-tion tasks. This allows recurring dependencies and resource interactions to appear in different task organizations. The mining and held-out corpora are separate from the 48-task evaluation collection. Source composition and structural reuse analyses appear in Appendices B.5 and E. 

B Benchmark Description and Statistics 

This section describes the final MAC-Bench task collection, its categories and work structures, and the validation protocol. Construction sources are reported separately from the evaluation tasks. 

B.1 Benchmark Overview 

The evaluation collection contains 48 test tasks, with eight tasks in each of six categories. D Additional Benchmark Validation (RQ3) 

MAC-Bench requires both completed local work and consistency across dependent results and shared resources. Validation therefore examines whether these requirements are stated in the task materials, can be fulfilled in the environment, and are reflected in scoring. Specification review and reference evaluation cover all 48 tasks. Controlled changes on twelve tasks test whether scoring ac-cepts valid alternatives and repairs while rejecting missing work, broken relations, and preservation violations. Further diagnostics trace these deci-sions to individual goals. Each goal is assessed by a group of checks; PS measures completed goals, while full resolution also requires applicable preser-vation checks. 

D.1 Task Specifications Requirements and scoring checks. We review the 283 goals across all 48 test tasks. For each goal, we identify its public requirement, the records or artifacts needed to fulfill it, and the checks used to award credit. Business tasks provide source records, policies, and recording guides; software tasks provide interface specifications, starter code, and public tests. Preservation requirements are reviewed alongside the requested changes. For software, the review examines selected behavior groups and targeted assertions against the supplied interfaces and specifications. We check this correspondence in both directions. Starting from a requirement, we examine whether the grader checks the requested behavior and its dependencies. Starting from a check, we locate the public basis for its rejection conditions, includ-ing permitted alternatives, required formats, and protected records or behavior. The resulting re-view records link each outcome to public source passages and grading entrypoints. 

Review examples. The review checks both condi-tional requirements and the availability of required outputs. In the riverbank activity-planning task, notices must match the chosen session and its site’s restrictions. We corrected a check that required a nesting-zone exclusion at two sites where none applied; it now tests the selected site’s restrictions. In the university support-allocation task, a required and graded budget summary was missing from the structured list of outputs. We added its entry to the recording interface. 

D.2 Reference Solutions Execution procedure. Business reference solu-tions begin from the task’s initial application state and use public tools to create or update the required records. We export the resulting state, apply the complete task grader, and reset the environment to check that the initial records are restored. Software reference solutions are installed in the supplied task environments, built with their prepared dependen-cies, and evaluated by the complete task grader, including checks of retained behavior. We sepa-rately evaluate the untouched application states and public software workspaces. Reference results pass on 48/48 tasks, with eight per category; no untouched initial state passes com-plete grading. All 24 software starters build suc-cessfully before their initial-state evaluation. All business environments pass reset checks after ref-erence execution and are closed after evaluation. 

Materials and execution records. Evaluation records link each task and grader version to the evaluated state or source artifact and its check and goal scores. Business records include the public-tool trace and exported final state. These supple-mentary checks use the revised release packages; the main-system evaluation uses the packages from its original runs. Housing and screening grader corrections are evaluated on the unchanged final states from their reference executions.

E Task Construction Analysis (RQ3) 

MAC-Bench constructs tasks by reusing and recom-bining structures of interdependent work. We ex-amine whether local patterns and connecting rules recur across tasks, whether composition expands the range of structures meeting specified require-ments, and how target guidance and acceptance criteria affect these results. Finally, we compare the scenario specifications produced by alternative instantiation procedures. 

E.1 Cross-task Structure Reuse 

Local patterns describe dependencies and coupling among two or three typed subtasks; connecting rules describe how two patterns overlap through shared subtasks. To examine their reuse beyond the mining corpus, we extract libraries from up to 100 tasks and measure coverage on 50 held-out tasks from disjoint source groups. A local occurrence is covered when its subtask types and relations match a library pattern. A connection is covered when both pattern types and their shared-node alignment match a stored rule. We compute each coverage fraction within a task, then average across tasks. Ten nested mining sequences use five corpus sizes, yielding 41 distinct libraries with a shared 100-task endpoint (Appendix G.3.3).

E.2.1 Target Guidance and Operation Limits 

Target guidance selects refinement, integration, and coupling operations that move the coarse graph to-ward the requested group and integration counts, stopping when the targets are met or no improving update remains. We remove this guidance while re-taining the same operation cap and local expansion routine. Acceptance under the resource-backed cri-terion drops from 80.0% to 5.0% at the smaller scale and from 91.7% to 26.7% at the larger scale, with no reduction in recorded request time (Ta-ble 11). 

Operation-limit sensitivity. We use the same 100-task structure library, both target scales, and 60 requests per scale, setting global operation caps to 0, 2, 4, 6, and 8. Paired requests share initialization and local random streams, while local expansion and resource checks remain fixed. The unguided variant removes both target-directed selection and target/positive-gain stopping. The zero-operation condition still performs source initialization and local expansion; Fixed global instead preselects eligible sources. The paired operation-cap protocol and uncer-tainty estimates are specified in Appendix G.3.4. 

Obs. 18. Target guidance matters beyond the operation count. As shown in Figure 13, guided composition reaches 80.0% attainment after two operations at the smaller scale and 91.7% after four at the larger scale. Without guidance, smaller-scale attainment falls from 26.7% at two operations to zero at eight; larger-scale attainment peaks at 26.7% at six. More operations alone do not ensure target attainment. Guided plateaus partly reflect stopping once targets are met.

F.3 Environment-grounded Task Instantiation Scenario refinement and task packaging. 

Given (H⋆, eG), refinement specifies concrete work in an environment Ω with suitable entities, arti-facts, and permitted operations. Objectives and resource conditions are adapted to the available ap-plication records or project interfaces; work may be merged, split, or rearranged. Business scenar-ios record these requirements in mechanism spec-ifications: descriptions of the entities, required work results, dependencies between results, and constraints on shared resources. Software tasks specify them through project requirements, public interfaces, and expected artifacts. The output follows Equation 5: a description d,initial environment x0, and verifier V . The task description states requested outcomes, constraints, and available evidence. Initial records or project files supply the starting resources and existing be-havior. Private verification materials remain out-side the solver workspace. The task package brings together these components and the permitted oper-ations. 

Outcome checks. Business checks inspect actual application records and designated result artifacts, 26 including returned identifiers, dates, amounts, as-signments, and applicable joint constraints. Soft-ware checks evaluate delivered implementations against required behavior and interfaces. Goal checks assess requested changes; preservation checks compare protected records or required exist-ing behavior with the starting state. The verifier re-ports goal decisions and complete resolution, with the score definitions in Appendix G.2. It does not require a prescribed action sequence. 

Validation of task packages. We review the cor-respondence between public requirements, avail-able operations, and outcome checks, then test load-ing, reset, and grading in the packaged environ-ment. Business reference solutions use public tools from the initial state and export their results for grading; software reference implementations are built and evaluated with the complete task grader. Constructed alternatives and violations test scoring decisions. Appendix D details the review, reference results for all 48 tasks, and controlled scoring tests.

Structural acceptance criteria. All four criteria use schema and interface checks, acyclic depen-dencies, and the same terminal-group range. Let 

N denote the terminal-group count. Common re-quirements include at least 2N − 1 leaf subtasks, at least ⌈(N − 1) /2⌉ groups with multiple leaves, an explicit coupling, a resource shared across groups, and capability and delivery groups. 

Initial. Count integration at non-delivery termi-nal groups with incoming bindings from at least two distinct upstream groups. This count must lie in the requested integration interval. 

Resource-backed. Count a subtask toward the work minimum only when it participates in a compatible explicit artifact dependency or shared-resource access. A shared resource requires at least two participating nodes and a writer; cross-group artifacts require a matching typed boundary bind-ing. At least 2N − 1 subtasks and ⌈(N − 1) /2⌉

groups with two such subtasks must qualify. Inte-gration is counted from artifacts supplied by dis-tinct upstream groups, using the same requested interval and excluding delivery groups. 

With delivery. Apply the resource-backed crite-rion but include delivery groups in the integration count. The upper and lower integration bounds re-main unchanged, so an added delivery group can push an output above the upper bound.
