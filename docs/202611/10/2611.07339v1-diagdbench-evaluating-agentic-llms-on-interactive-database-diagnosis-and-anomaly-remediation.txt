ABSTRACT
Database diagnosis and anomaly remediation are essential to re-
liable database management system (DBMS) operation. Despite
advances in large language model (LLM)-based database agents,
constructing live DBMS environments that reproduce diverse anom-
alies at scale remains challenging, limiting the availability of exe-
cutable samples for database agent training and evaluation. To this
end, we introduce DiagDBench, a large-scale benchmark for train-
ing and evaluating database agents on interactive diagnosis, anom-
aly remediation, and optional workload performance optimization
across diverse, realistic anomaly scenarios. Each sample pairs a user
request, comprising an issue description and an anomaly-verified
workload under which the issue was observed, with a self-contained,
executable DBMS environment that supports real-time monitor-
ing, interactive diagnosis, remediation, and workload execution.
To construct these samples at scale, we propose an LLM-based
framework with two complementary pipelines: Manual-Guided
Anomaly Synthesis, which sequentially synthesizes user requests,
database modifications, and anomaly-injection scripts grounded
in DBA manuals and official DBMS documentation; and Incident-
Guided Anomaly Reproduction, which reconstructs anomaly samples
end to end from real-world enterprise online diagnosis incidents.
Built using this framework with sample filtering, expert review,
and refinement, DiagDBench comprises 6,940 synthesized training
samples and a held-out test set of 454 expert-annotated samples,
spanning three hardware configurations, two DBMSs, and three
database schemas. Extensive evaluations of database agents pow-
ered by multiple LLMs demonstrate that even the best-performing
agent, ReAct with GPT-6 Astra, scores only 56.24, whereas most
agents score below 45, underscoring the difficulty of DiagDBench.

INTRODUCTION
Database diagnosis aims to identify the root causes of anomalous
behavior in database management systems (DBMSs) through sys-
tematic analysis of monitoring metrics, logs, and query executions,
thereby guiding targeted remediation of the underlying issues.
Prior Work and Remaining Limitations. Traditional rule-based
or machine-learning-based approaches [12, 19, 38] have focused
on detecting anomalies in time-series metrics and identifying their
root-cause categories. DBPA [9] supports the evaluation of such ap-
proaches by providing pre-collected metric data paired with anom-
aly labels, alongside fixed procedures for reproducing nine anom-
aly types. With the emergence of large language models (LLMs),
LLM-based systems [31, 43–45] have extended diagnostic capabili-
ties beyond root-cause categorization, enabling LLMs to emulate
database administrators (DBAs) by interacting with DBMSs and
generating comprehensive natural-language diagnostic reports that
combine causal-chain analysis with remediation recommendations.
However, unlike conventional classification tasks that support
training and evaluation on static datasets, evaluating interactive
database agents requires live DBMS environments that reproduce
the target anomalies. Moreover, time-series metric records col-
lected through routine monitoring can be readily assembled into
static training datasets, whereas constructing complete, executable
anomalous DBMS environments at scale for interactive database
agent training remains challenging. D-Bot [45] releases 539 anomaly
cases for PostgreSQL with detailed scenario descriptions, along-
side 2,819 static training records. More recently, DBA-Bench [2]
comprises 241 cases across PostgreSQL and TiDB for supporting
interactive database agent evaluation. Nevertheless, it contain only
a few hundred evaluation cases without separate training data.
Our Proposal. To bridge this gap, we introduce DiagDBench, a
large-scale benchmark for evaluating interactive database agents
on anomaly diagnosis, remediation, and workload performance

existing benchmarks through three core strengths: (1) Scenario
Diversity, encompassing diverse anomaly-injection mechanisms
and operational settings beyond fixed templates; (2) Large-Scale
Dataset, comprising thousands of executable anomaly samples;

Challenges and Solutions. Constructing a large-scale benchmark
that enables database agents to perform interactive diagnosis and re-
mediation within live DBMS environments while capturing diverse,
realistic anomaly scenarios presents the following key challenges:
(1) How can DiagDBench ensure the diversity and realism
of its anomaly samples? Addressing the limited availability of
executable samples for training and evaluating interactive database
agents requires expanding both dataset scale and the diversity of
anomaly definitions. To meet this demand, we collect source ma-
terial for anomaly samples through two channels: (i) we obtain
DBMS operational manuals from experienced DBAs and summa-
rize common anomaly definitions, enriched with error codes and
timeout information retrieved from official DBMS documentation,
to establish a public source; and (ii) we collect real-world enterprise
records of online diagnosis incidents as a private source.
(2) How can different anomaly sources be transformed into
complete, independently executable database anomaly sam-
ples at scale? Constructing complete, executable database anomaly
samples from above anomaly definitions and incident records at
scale is non-trivial, as this requires maintaining sample quality
and diversity while ensuring that the specific scenarios reflect real-
world database operations. To address this challenge, we propose an
LLM-based database anomaly sample construction framework with
two complementary pipelines tailored to the respective sources: (i)
Manual-Guided Anomaly Synthesis, which draws on official DBMS
documentation and DBA manuals to sequentially synthesize user
requests, database modification operations, and anomaly-injection
scripts, respectively; and (ii) Incident-Guided Anomaly Reproduction,
which reconstructs complete database anomaly samples end to end
from real-world enterprise online diagnosis incident records.
(3) How can we reliably evaluate database diagnosis agents
based on the simulative anomaly samples? LLM-based synthe-
sis may introduce hallucinations that lead to validity issues such
as (i) inconsistencies between user requests and anomaly-injection
scripts (e.g., reporting table corruption or duplicate-key errors when
the injection script only drops secondary indexes and holds locks,
without reproducing either reported issue), and (ii) failures to repro-
duce the intended anomalous state (e.g., expecting row-level locks to
block SELECT queries on a table while observing that all such queries
complete successfully). These validity issues compromise evalua-
tion reliability, making it difficult to determine whether an agent’s
failure stems from defects in the anomaly sample or limitations
of the agent itself. To this end, we filter the constructed samples
for anomaly-injection validity, and select challenging candidates
based on reference database agent’s diagnostic and remediation
performance. Following iterative expert review and refinement, 454
expert-annotated samples are retained as a separate held-out test
set for evaluating database diagnosis agents. Furthermore, strong
diagnostic reasoning does not necessarily translate into effective
remediation that directly modifies the anomalous environment. We
therefore evaluate database diagnosis agents using two complemen-
tary scoring components that assess both anomaly remediation
outcomes and diagnostic report quality: (i) Execution-Grounded
Remediation Evaluation scores remediation outcomes through com-
paring workload performance between the normal baseline and
post-remediation states, along with an LLM-as-a-judge assessment
of whether any agent-optimized workload preserves the identi-
cal semantics of the original anomaly-verified workload; and (ii)
LLM-Judged Diagnostic Report Evaluation uses the original anom-
aly sample as the ground-truth reference for LLM-based scoring
across four dimensions: root-cause accuracy, evidence-grounded
reasoning, remediation appropriateness, and operational safety.
DiagDBench. Building on these solutions, we construct Di-
agDBench, comprising 6,940 synthesized training samples and
a separate held-out test set of 454 expert-annotated samples, which
spans three hardware configurations, two DBMSs, and three data-
base schemas. Unlike conventional benchmarks for text-to-SQL [14,
16] and question answering [29], database diagnosis and anomaly
remediation require agents to inspect and modify the state of an
anomalous database. We therefore package each anomaly sample
as a self-contained sandbox providing an independent live DBMS
environment that supports system monitoring, interactive diagno-
sis, anomaly remediation, and workload execution. Each sample in
DiagDBench pairs this sandbox with a user request comprising an
issue description and an anomaly-verified workload for evaluation.
Contributions. Our main contributions are as follows:
• Benchmark for Interactive Database Agent Evaluation. We
introduce DiagDBench, a benchmark spanning three hardware
configurations, two DBMSs, and three database schemas, with
6,940 synthesized training samples and a held-out test set of
454 expert-annotated samples. Each anomaly sample pairs a user
request—comprising an issue description and the workload under
which the issue was observed—with an independent live DBMS
environment that supports performance monitoring, interactive
diagnosis, anomaly remediation, and workload execution.
• Database Anomaly Sample Construction Framework. We
propose an LLM-based framework with two complementary
pipelines to construct diverse anomaly samples at scale: Manual-
Guided Anomaly Synthesis follows a three-stage process grounded
in official DBMS documentation and DBA manuals, while Incident-
Guided Anomaly Reproduction reconstructs samples end to end
from real-world enterprise online diagnosis incident records.
• Comprehensive Experimental Evaluation. We conduct ex-
tensive evaluations of multiple database agents to assess their di-
agnostic and remediation capabilities. Even the best-performing
agent, built on the ReAct framework and powered by GPT-6 As-
tra, achieves only 56.24, while most other agents score below 45,
underscoring the challenges posed by DiagDBench.

2.2
ReAct Framework
ReAct [37], which underpins our LLM-based database anomaly
sample construction framework detailed in subsequent sections,
interleaves natural-language reasoning with task-specific actions
through a Thought–Action–Observation loop. Starting from task-
specific instructions, the LLM reasons about the next step (Thought),
invokes an external tool or interacts with the environment (Action),
and receives the resulting feedback (Observation). The accumulated
reasoning traces, actions, and observations provide context for
subsequent decisions, enabling the LLM to assess intermediate out-
comes, revise its plan, and adjust its actions until it submits its final
output or a predefined termination condition is met. By coupling
reasoning with execution feedback, ReAct supports adaptive task
execution grounded in observations from external environments.

• Manual-Guided Anomaly Synthesis (Section 4) instantiates

ficial DBMS documentation as executable samples through three
sequential stages: (i) inferring user-observable symptoms from

MANUAL-GUIDED ANOMALY SYNTHESIS
We propose the Manual-Guided Anomaly Synthesis pipeline to con-
struct diverse, challenging anomaly samples from abstract defini-
tions derived from DBA manuals and official DBMS documentation.
It comprises three sequential stages for synthesizing user requests,
database modifications, and anomaly injections, respectively.
4.1
Anomaly Sample Source
Explicit root-cause definitions grounded in real-world operational
experience are essential for instantiating concrete database anomaly
samples. To this end, we collect DBMS operational manuals in which
enterprise DBAs summarize their practical experience, and extract
17 single-anomaly root-cause definitions as presented in Table 1.
To account for anomalies with multiple root causes, we enumerate
combinations of these definitions (e.g., Schema and Index Design
Anomaly + Transaction Lock Contention Anomaly, where missing
indexes can cause UPDATE statements to scan more rows and hold
locks longer, causing blocking chains that delay other transactions
and intensify lock contention), yielding 833 general root-cause
definitions for synthesizing more diverse and challenging scenarios.
Since distinct diagnostic paths may converge on the same root
cause, a given root-cause definition can correspond to diverse user-
observable symptoms (e.g., error messages or execution timeouts).
To enrich these definitions into more concrete anomaly samples,
we build a knowledge base of user-observable symptoms through
collecting error-code explanations and timeout reason analyses
separately from the official documentation of PostgreSQL1 and
MySQL2, as presented in Table 2. Each entry is structured into a
symptom name, official description, associated root-cause analysis
and category, and effective remediation recommendations.
After constructing the knowledge base, we retrieve relevant
entries using formatted anomaly root-cause definitions as queries.
Our hybrid lexical retrieval approach comprises two components:
• Field-weighted BM25 [30] prioritizes key-field matches (e.g.,
symptom names and official descriptions) while accounting for
term rarity, frequency, and entry length to mitigate bias toward
long or repetitive entries.
• Term overlap quantifies both query-term coverage and the
proportion of entry terms shared with the query.

4.2
User Request Synthesis
Given an anomaly definition, we first synthesize a user request com-
prising a user-issue description and an anomaly-verified workload
under which the anomaly is observed. In practice, users may en-
counter unexpected performance degradation or execution errors,
thereby submitting online requests to DBAs for anomaly diagno-
sis and remediation. To simulate this process, we adopt the ReAct
framework to guide an LLM in iteratively generating the workload
and issue description from the anomaly definition. Specifically, the
prompt for user request synthesis comprises three components:
• Task Overview instructs the LLM to reason step by step and gen-
erate the workload that exposes the specified anomaly, together
with the corresponding user-issue description.
• Environment-Reset Skill guides the LLM in restoring the
database to its initialized state when needed, preventing earlier
changes from affecting subsequent validation.
• Sample-Relevant Information specifies the hardware con-
figuration (CPU, memory, etc.), the DBMS (PostgreSQL [26] or
MySQL [21]), the database instance and associated schema (TPC-
H [33], TPC-DS [32], or IMDB [15]), and the anomaly definition.
In particular, “Task Overview” specifies three constraints on
workload generation to extend database agent evaluation beyond
diagnosis and remediation to include performance optimization:
• Workload execution time should exceed one minute, prefer-
ably through complex analytical queries, to provide scope for
workload execution-time optimization.
• Workload execution consistency requires the workload to
produce consistent results across repeated executions, enabling
equivalence checks between the original user workload and the
workload optimized by database agents.
• Workload performance optimization could be feasible through
techniques such as index recommendation, SQL rewriting, etc.
Guided by this prompt, the LLM can choose between the follow-
ing two actions during iterative reasoning to generate and refine
the anomaly-verified workload and user-issue description:
• Verify Action leverages a workload verifier to execute the candi-
date workload repeatedly, collect execution results and latencies,
and determine whether the workload satisfies the above con-
straints. The above verifications are returned as observations to
guide subsequent refinement and action selection.
• Finish Action terminates the synthesis process and outputs the
finalized anomaly-verified workload and user-issue description
once the observations satisfy the verification criteria.
4.3
Database Modification Synthesis
To assess whether database agents can resolve anomalies without
making additional unnecessary changes to the database or altering
the original semantics of the user request, we require the SELECT
queries in the anomaly-verified workload to return non-empty
results, supporting workload consistency assessment based on com-
parisons of pre- and post-remediation execution results. Moreover,
some anomaly scenarios require specific data distributions (e.g.,
concentrating orders on a single buyer so that concurrent payment
transactions compete for locks on the same rows), thereby neces-
sitating targeted modifications to the given database instances as
well as enhancing their diversities across anomaly samples.
To this end, we synthesize database modification operations
through iterative reasoning and interaction within the ReAct frame-
work, with its prompt consisting of the following components:
• Task Overview guides the LLM’s step-by-step reasoning and ac-
tion selection for synthesizing database modification operations.
• Environment-Reset Skill and Sample-Relevant Informa-
tion remain unchanged from their counterparts in Section 4.2.
• User Request provides the user-issue description and associated
anomaly-verified workload synthesized in Section 4.2.
Guided by the prompt and available observations, the LLM se-
lects one of the following two actions at each reasoning iteration:
• Query Action takes one of two forms: (i) executing queries
to inspect relevant data characteristics of the target database
instance, such as whether any rows satisfy a specified predicate;
or (ii) executing candidate modification workloads to assess their
feasibility. In both cases, the execution results are returned as
observations to guide subsequent reasoning and action selection.
• Finish Action finalizes and outputs the database modification
operations once accumulated observations indicate that the in-
stance satisfies the target conditions. Additionally, the LLM also
summarizes the updated database characteristics most relevant
to the anomaly definition and user request in natural language,
forming part of the input to the anomaly-injection stage (e.g.,
identifying two hotspot rows accessed by the workload to guide
the construction of a concurrent transaction that acquires their
locks in reverse order to reproduce deadlock-induced failures).

4.4
Anomaly Injection Synthesis
After synthesizing the database modification operations, we pro-
ceed to the final and most critical stage: anomaly-injection script
synthesis. As in the preceding stages, we utilize a ReAct-based LLM
to construct and refine the script through successive rounds of
reasoning and interaction. To guide this process, the prompt for
synthesizing anomaly-injection scripts is structured as follows:
• Task Overview guides the LLM in constructing and validating
an anomaly-injection script through step-by-step reasoning and
action selection. Notably, since the self-contained environment
supports operating-system-level operations that may be not oc-
curred in real-world scenarios, we restrict anomaly injection to
DBMS-level operations that simulate business logic.
• Environment-Reset Skill, Sample-Relevant Information,
and User Request retain the same content as in Section 4.3.
• Database Feature Summary describes the updated database’s
sample-relevant data distributions presented in Section 4.3.
Guided by the prompt, the LLM iteratively constructs the anomaly-
injection script through selecting one of the following two actions:
• Evaluation Action submits the candidate anomaly-injection
script to an anomaly evaluator, which evaluates the script follow-
ing three steps: (i) executing the user workload in the initialized
self-contained environment and recording its baseline perfor-
mance; (ii) running the script to inject the anomaly; and (iii)
rerunning the same user workload to check for performance
degradation or execution errors, with the evaluation logs re-
turned as observations to guide subsequent script refinement.
• Finish Action returns the final anomaly-injection script when
the collected evidence indicates that the target anomaly has been
successfully induced, resulting in observable performance degra-
dation or execution errors in the anomaly-verified workload.

Single-Stage Anomaly Reproduction
Each online diagnosis incident record provides a detailed, concrete
description of an anomaly sample, supplying explicit context that
reduces reliance on speculative inference and helps mitigate halluci-
nation during LLM inference. Building on the preceding three-stage
synthesis pipeline, we adopt a simplified, single-stage process to
jointly construct and refine interdependent sample components
through multi-turn interaction, thereby accelerating construction
while maintaining consistency with the recorded incident.
To guide the LLM in interpreting the collected incidents and
constructing complete anomaly samples consistent with the source
records, we incorporate additional skills tailor to the incident record
into the input prompt, which comprises the following components:
• Task Overview guides the LLM through step-by-step reasoning
to construct a complete anomaly sample based on the incident.
• Environment-Reset Skill remains the same as in Section 4.2.
• User-Request Interpretation Skill clarifies record fields and
maps reported issues to common anomaly definitions. It also spec-
ifies the operational scope of self-contained environment: lock
contention, query plan degradation, and database resource pres-
sure are reproducible, whereas platform- and infrastructure-level
incidents (e.g., production network failures and resource sched-
uling faults) can only be approximated through database-visible
effects. Reported symptoms for evaluator check are classified as
performance degradation, blocking timeout, or execution error.

• Reproduction Protocol Skill defines the output specifications

DIAGDBENCH FOR DATABASE DIAGNOSIS
Leveraging this anomaly construction framework, we establish Di-
agDBench for interactive evaluation of database agents on anomaly
diagnosis, remediation, and workload performance optimization.
6.1
Benchmark Preparation
Building on 3,332 anomaly definitions and 1,086 online diagnosis
records, we utilize the framework described in Sections 4 and 5 con-
structing 8,836 candidate anomaly samples across different DBMSs
at scale. To promote linguistic diversity, we employ four LLMs for
synthesis: GPT-5.5 [24], o3 [23], GLM-5.2 [39], and DeepSeek-V4-
Pro [4]. Meanwhile, we allow up to 20 iterations per construction
stage while retaining the default setting of the underlying LLM.
Although an evaluator checks anomaly-injection success during
sample construction, its observations primarily guide subsequent
LLM reasoning rather than mandatory instructions to further refine-
ment after failure. Moreover, we observed that, for some samples,
the LLM reached the iteration limit without issuing the “Finish
Action”, leaving synthesis completion unconfirmed. Therefore, we
filter the constructed samples using anomaly evaluator presented in
Section 4.4, excluding those whose anomaly-verified workloads ex-
hibit no substantial performance change after injection. Following
anomaly validity filtering, we retain 7,394 valid samples in total.
From this pool, we curate challenging candidates for expert re-
view to establish a high-quality, independent held-out test set for
database agent evaluation. For each sample, we first measure the
anomaly-verified workload’s normal-operation runtime 𝑡0, then
employ an o3-based ReAct database agent to diagnose and remedi-
ate the injected anomaly, after which we rerun the workload and
record its execution time 𝑡1. Failed executions and timeouts are
assigned 𝑡1 = ∞. We rank samples in descending order of 𝑟= 𝑡1/𝑡0
that prioritizes greater residual performance degradation or fail-
ure to restore successful workload execution, selecting the top 600
candidates across DBMSs and construction pipelines for expert
annotation (Section 6.2). Expert review and refinement yield 454
held-out test samples, leaving 6,940 samples available for training.
For public release of the held-out test set, we package anomaly-
injection scripts in a protected form to reduce the risk of agents iden-
tifying root causes through code inspection rather than database
diagnosis. Meanwhile, the released artifacts preserve executable
entry points compatible with the original evaluation workflow
without directly exposing human-readable injection source code.
6.2
Expert Review
Following Section 6.1, we select 600 anomaly samples as candidates
for a held-out test set to support unified database agent evalua-
tion. Despite validity checks and difficulty-based agent selection,
these LLM-generated samples may still differ from real-world inci-
dents (e.g., claiming disk-full errors without reproducing storage
exhaustion, or login failures when the injected anomaly merely
slows down queries). We therefore invite a DBA with five years
of experience diagnosing and resolving user-reported production
database issues to review the candidates from four perspectives:
• Anomaly Scenario Reasonability assesses whether each oper-
ation reflects business purposes, maintenance requirements, or
plausible operational mistakes within a realistic scenario.
• Trigger Mechanism Correctness checks whether anomaly
injections conform to the target DBMS’s execution rules without
relying on operating-system-level interventions.
• Script Executability and Configuration Effectiveness as-
sesses whether the script executes successfully with its intended
effects. Specifically, the DBA inspects logs and database state for
execution errors and verifies that configuration changes apply
to the intended connections throughout workload execution.
• Consistency Between Anomaly Implementation and User
Request checks whether the reported symptoms match the injec-
tion operations and observed behavior. Unsupported claims, such
as stating with database deletion when none occurred or query
timeouts with completed execution, are corrected or removed.
Beyond these checks, the DBA may propose optional refinements
that increase diagnostic difficulty based on the original anomaly
injection mechanism, prioritizing related concurrent operations
rather than simply increasing workload intensity or waiting times.
For the 600 selected anomaly samples, together with their corre-
sponding anomaly-verification logs and collected system metrics,
the DBA may approve samples satisfying the above criteria, dis-
card low-quality samples, or recommend revisions for those worth
retaining, organizing any revision feedback into three components:
• Anomaly Double Check records unresolved validity concerns
and required verifications, such as checking whether an anomaly-
injection timeout due to insufficient execution budget was incor-
rectly treated as evidence of successful anomaly reproduction.
• Anomaly Modification identifies operations that violate the
above criteria and suggests corresponding targeted revisions.
• Anomaly Refinement specifies additional anomaly injections,
with supporting explanations, to increase diagnostic difficulty.
Guided by this, we leverage a ReAct agent powered by GPT-5.5 to
repair and refine the anomaly samples, incorporating further DBA
feedback iteratively until approval without additional changes.

performance optimization while providing a foundation for train-

from their own anomaly specifications. This framework supports
the construction of simulated scenarios tailored to specific produc-
tion environments and operational requirements, facilitating the
iterative development and improvement of database agents.

Experimental Setup
7.1.1
Baselines. We provide all database agents with a standard-
ized prompt template comprising the following three components:
• Task Overview guides step-by-step LLM reasoning and action
selection for database diagnosis and anomaly remediation. It
also encourages performance optimization through semantics-
preserving rewrites of the anomaly-verified workload or tuning
operations incorporated into the remediation code.
• Sample-Relevant Information specifies hardware configura-
tion, database instance, DBA credentials, and the user request
with an issue description and an anomaly-verified workload.
• Output Format requires database agents to submit a diagnostic
report, remediation code, and an optional optimized workload.
Specifically, we evaluate eight LLM-based database agents while
retaining the default hyperparameter settings of their underlying

ReAct-based Database Agents We instantiate five database agents
using the ReAct [37] framework with GPT-6 Astra [25], Qwen3.8-
Max [28], DeepSeek-V4.1-Flash [5], Kimi K3 [13], and GLM-5.3-
Flash [40] as the underlying models. Each database agent is limited
to 20 interactions per sample, and at each reasoning iteration, the
LLM can choose between the following two actions:
• Code Action generates a Bash script that is executed within the
sample container for database inspection, anomaly remediation,
or workload validation, with the execution output returned as an
observation to guide subsequent reasoning and action selection.
• Finish Action concludes the interaction with a diagnostic report,
reusable remediation code, and an optional optimized workload.

with GPT-6 Astra using its native agent loop and Model Context
Protocol (MCP) tools. Specifically, we supplement the standardized

diagnostic report, remediation code, and optional optimized work-
load. Each sample allows at most 20 database-tool actions.

diagnosis using its native multi-expert workflow, which dynami-

search reasoning and reflection, and cross-review findings before
generating final report. We supplement standardized inputs with 12
monitoring snapshots collected over time from the sample environ-
ment, such as resource utilization, database statistics, and blocking
relationships. Since native D-Bot produces diagnostic findings and

its implemented knowledge-based question-answering workflow.

Table 6 presents assessment results for eight database agents on

DiagDBench remains challenging even for frontier LLMs
paired with agent scaffolds. Experimental results demonstrate
that the ReAct-based database agent with GPT-6 Astra achieves the

56.24 out of 100. Apart from GPT-6 Astra paired with ReAct or
Codex, other approaches score below 47 on each supported DBMS,
highlighting the challenges of accurate diagnosis, effective remedi-
ation, and workload performance optimization on DiagDBench.
Database-specific diagnosis approaches achieve degraded
evaluation scores on DiagDBench. D-Bot and DBAIOps employ
knowledge-augmented diagnostic workflows primarily designed
for diagnostic reports generation. Although we use an LLM to
translate these reports into remediation scripts, D-Bot scores 20.09
on its supported PostgreSQL samples, while DBAIOps achieves
20.55 on the full test set. These observed performance suggests that
directly translating diagnostic reports into effective remediation
actions remains challenging, further motivating the significance of
interactive remediation that enables database agents to incorporate
execution feedback, refine their actions, and verify recovery.
Database diagnosis and remediation performance varies
across LLM backbones and agent scaffolds. With the ReAct
framework, input prompts, and available tools held fixed, GPT-6
Astra outperforms the second-best model, Qwen3.8 Max, by 11.32
points in overall score. Meanwhile, with GPT-6 Astra as the fixed
underlying model, ReAct achieves a higher overall score than Codex,
reaching 56.24 compared with 52.44. These results underscore the
importance of both the underlying LLM and the surrounding agent
harness in enhancing the capability of database agent.
Stronger performance on specific DBMS does not neces-
sarily translate into an advantage on others. Within the ReAct
scaffold, Kimi K3 scores 39.40 on PostgreSQL and 46.01 on MySQL,
whereas DeepSeek-V4.1 Flash achieves 42.25 and 43.98, respectively.
This reversal in their relative ranking demonstrates that overall
scores alone do not fully capture the models’ distinct strengths
across anomaly scenarios instantiated on different DBMSs.

Workload Optimization Analysis. Among successful recov-
eries with 𝑟𝑖< 0.8, we identify five categories of performance
optimization as follows: Workload Rewrite (O1; workload modi-
fications accepted as semantically equivalent), Index Recommend
(O2), Database Maintenance (O3; statistics updates and table or in-
dex maintenance), Knob Tuning (O4), and Other (O5). Figure 2(b)
reveals the characteristics of the optimization behavior as follows:
• Diverse Optimization Strategies. Database agents adopt vari-
ous strategies for workload performance optimization, with an
average speedup of 4.42×, thereby further mitigating residual
slowdowns beyond simply restoring workload functionality.
• Dominant Tuning Operations. Knob tuning is the most preva-
lent operation across most database agents, appearing in 47.1%–
81.8% of these samples, while index recommendation accounts for
9.1%–52.9%. These results suggest that frontier-LLM-based data-
base agents can leverage conventional database configuration
and indexing knowledge for workload performance optimization.
• Potential for Semantics-Preserving Rewriting. Compared
with failed samples due to semantic-equivalence violation, suc-
cessful cases satisfy this requirement while achieving substantial
latency reductions, thereby motivating further improvements in
database agents’ ability to enhance execution efficiency while
reliably preserving the original workload’s semantics.
7.4
Case Study
Figure 3 illustrates the interactive database diagnosis and remedi-
ation of an anomaly in an IMDB-based PostgreSQL environment
using the ReAct agent powered by GPT-6 Astra.
Anomaly Sample. In the PostgreSQL database IMDB, support-
ing movie-content management and analytics, an injected long-
lived transaction and recurring background workloads cause block-
ing and performance degradation. Specifically, users encounter
workload-wide slowdowns and transaction stalls when executing
a mixed workload combining five write-and-confirm transactions
with four analytical queries over large shared tables. These disrup-
tions stem from an uncommitted transaction blocking DDL, thereby
queuing subsequent readers, alongside four recurring bulk-update
clients and eight analytical clients operating under restrictive data-
base knobs. Together, these conditions combine lock-induced block-
ing, constrained query execution, and sustained resource contention
between foreground transactions and background analytics.
Database Diagnosis. Across ten iterations, the agent followed
a conventional DBA workflow by inspecting locks, performing
query and session cleanup, and refreshing statistics, yielding modest
performance gains. Despite identifying recurring updates, four
iterations of session-level diagnosis and backend cleanup failed to
manage upstream submissions, leaving remediation incomplete.
Beyond this failure, the “Human Database Administrator Re-
marks” in Figure 3 highlight three operational shortcomings: (i)
terminating active sessions risks disrupting ongoing work, whereas
transaction completion and DDL execution should be coordinated
with workload owners (R1); (ii) repeatedly removing replacement
connections addresses transient symptoms rather than tracing re-
curring updates to their submitting source and regulating workload
intensity according to resource demand (R2); and (iii) when unex-
pected slowdowns persist, DBAs routinely inspect DBMS knobs and
concurrent resource usage to address residual bottlenecks rather
than treating symptom removal as sufficient recovery (R3).
Discussion. In practice, production DBMSs routinely support nu-
merous concurrent sessions, requiring DBAs to resolve user-visible
disruptions while coordinating ongoing workloads and maintain-
ing system-wide performance. However, existing database agents
struggle to diagnose complex anomalies and coordinate interdepen-
dent sessions while preserving scheduling dependencies and using
shared resources efficiently. Even after successful anomaly reme-
diation, they tend to finish diagnosis once the superficial blocking
is resolved, without systematically checking for residual perfor-
mance bottlenecks. Reliable database agents must therefore in-
tegrate business-aware workload coordination with system-wide
performance optimization to restore functionality and expected per-
formance rather than merely alleviate symptoms, which motivates
further research into developing and refining these capabilities.

RELATED WORK
8.1
Database Anomaly Benchmarks
DBPA [9] defines nine common anomalies and reproduction pro-
cedures, collects monitoring metrics, and synthesizes compound
anomalies to construct training and test sets for root cause classifica-
tion. More recently, DBA-Bench [2] provides 241 production-fidelity
diagnosis samples for PostgreSQL and TiDB, evaluating database
agents through multi-turn interactions with live databases, but
offers limited samples without separate training data. In contrast,
DiagDBench provides 454 held-out evaluation samples and thou-
sands of training samples across diverse environmental settings.
8.2
Database Diagnosis
Traditional Methods Early studies predominantly formulate data-
base diagnosis into root cause classification through rule-based or
machine-learning-based methods. DBSherlock [38] maps structured
anomaly predicates extracted from monitoring metrics to a DBA-
informed causal graph, ranking candidate root causes and generat-
ing causal explanations through backward symptom tracing and
rule-based pruning of infeasible paths. iSQUAD [19] focuses on diag-
nosing intermittent slow queries (iSQ) in cloud databases through
extracting typed key performance indicators anomaly patterns,
then removing redundant dependencies, and grouping similar iSQs
by type-oriented pattern integration clustering. A Bayesian case
model is subsequently used to characterize each cluster, substan-
tially reducing labeling overhead while enabling online root-cause
diagnosis of incoming iSQs. AutoMonitor [12] identifies anomalous
metric windows using Long Short-Term Memory (LSTM) recon-
struction errors, detects metrics with significant distributional shifts
via the Kolmogorov–Smirnov test, and matches similar historical
anomalies using a weighted K-Nearest Neighbors (KNN) model.
LLM-based Methods. D-Bot [45] integrates anomaly monitoring,
profiling, diagnosis, and report generation within a multi-agent
framework, with GaussMaster [43] extending this paradigm to open-
Gauss. Given anomaly metrics, it retrieves documentation and tools
from knowledge base, combining tree-search reasoning, reflection,
and cross-agent review for report summarization. Panda [31] sup-
ports performance debugging through global and instance-specific
contextual grounding, evidence-based response verification, risk-
and impact-aware action assessment, and feedback-driven histori-
cal case integration. DBAIOps [44] explores and expands diagnostic
paths in heterogeneous knowledge graphs encoding DBA expertise,
supplying retrieved reasoning chains and anomalous metrics to an
LLM for root-cause analysis and remediation recommendations.
Despite the availability of D-Bot’s public dataset, early LLM-
based approaches lacked a unified benchmark for evaluating inter-
active diagnosis in live DBMSs. DiagDBench addresses this gap
with diverse, executable samples and separate training and held-out
evaluation sets, enabling unified assessment of diagnostic accuracy,
remediation effectiveness, and optional workload optimization.
9
CONCLUSION
We introduce DiagDBench for training and evaluating database
agents on interactive database diagnosis, anomaly remediation, and
optional workload performance optimization. DiagDBench simu-
lates diverse, realistic anomaly samples in self-contained, executable
DBMS environments spanning three hardware configurations, two
DBMSs, and three database schemas. To construct anomaly samples
at scale, we propose an LLM-based framework with two comple-
mentary pipelines: Manual-Guided Anomaly Synthesis, grounded
in DBA manuals and official DBMS documentation, and Incident-
Guided Anomaly Reproduction, derived from real-world enterprise
online diagnosis records. Built using these pipelines, DiagDBench
comprises 6,940 synthesized training samples and a held-out test set
of 454 expert-annotated samples. Experimental evaluations across
multiple database agents reveal persistent performance limitations,
underscoring the challenges posed by DiagDBench.
