Large language model (LLM) agents rely on persistent memory to plan tool calls and complete multi-step tasks, which exposes them to memory drift : an adversarial or misleading memory alters the execution path and final outcome. In this work, we investigate online memory-drift detection , which estimates each retrieved memory’s causal contribution to potential drift at serving time. We identify two fundamental challenges. 

❶ Content-level features are insufficient for causal memory-drift attribution , as perplexity or retrieval relevance alone cannot determine which retrieved memory would change agent behavior if neutralized; ❷

Counterfactual attribution is prohibitively expensive for online detection , as it requires replaying downstream agent and tool execution for each candidate memory, exceeding real-time serving budgets. To address these challenges, we propose DriftGuard, a two-stage framework that decouples offline causal supervision from online estimation. Specifically, DriftGuard first constructs causal supervision through repeated paired counterfactual replays, continuing the original and single-memory neutralized trajectory suffixes from a shared pre-action state. The resulting annotations are aggregated by component-wise majority voting into a memory drift score (MDS) that captures action change, attack removal, violation removal, and task recovery. Guided by this supervision, DriftGuard then learns an online risk model that estimates MDS from pre-action information and flags drift-inducing memories via its maximum component risk, without online counterfactual rollouts. Extensive experiments demonstrate that DriftGuard accurately identifies drift-inducing memories and enables efficient online defense.

## 1 Introduction 

Large language model (LLM) agents are increasingly deployed to complete multi-step tasks that involve tool use [1, 2], planning [3], and long-horizon reasoning [4, 5]. To sustain continuity and reuse prior experience across interactions, modern agents are commonly equipped with a persistent memory that stores past solutions, user preferences, and reusable workflows [6, 7]. At each action, the agent retrieves a small set of relevant records from this memory pool and conditions its plan on them. This mechanism now underpins a wide range of deployed LLM agents, from coding assistants that reuse codebase context [8] and web-navigation agents that retain browsing history across sessions [9], to personal assistants that maintain long-term user memories [6, 7]. Consequently, persistent memory has become a standard component of production-grade LLM agents. The central challenge in deploying such agents is thus to ensure that retrieved memories consistently drive the agent toward the intended behavior, as any adversarial or misleading memory can silently divert the execution path and cause harmful downstream consequences. Despite rapid progress in prompt-level and response-level safety detectors for standalone LLMs [10, 11, 12], these safeguards are largely blind to failures rooted in an agent’s persistent memory. Once an incorrect instruction or poisoned experience enters this memory, retrieval can repeatedly reintroduce it into otherwise benign tasks and silently divert agent behavior [13, 14, 15], a failure mode we refer to as memory drift . Recent evidence shows that memory drift is a rapidly growing threat: adversaries can plant persistent memories via a single tool call [16], contaminate memory purely through observed web content [17], or hide dormant payloads that only re-emerge in future sessions [18], all with high attack success rates against frontier agents [19]. Even recent memory-oriented defenses focus on filtering [20], provenance [21], or link enforcement [22] rather than pinpointing which retrieved 1arXiv:2611.25583v1 [cs.AI] 19 Nov 2026 memory is causally responsible for the drift. Consequently, when a session retrieves several correlated records and only one is the culprit, none of these signals can decide which record to quarantine or audit. This gap motivates online memory-drift detection , which aims to quantify each retrieved memory’s causal contribution to the potential drift at serving time. However, online memory-drift detection introduces two unique challenges that do not arise in conventional safety filtering. ❶ Content-level features of retrieved memories are non-causal for memory-drift attribution [12, 11]. Since multiple correlated records can co-occur with a harmful action, features derived from memory content alone (e.g. ,perplexity, retrieval relevance, attention, or output harmfulness) cannot decide which record would actually change the trajectory if neutralized, making memory-level localization unreliable. ❷ Counterfactual attribution is prohibitively expensive for online detection [23, 24]. Directly measuring each memory’s causal effect requires neutralizing it and replaying the remaining trajectory, which triggers up to K additional rollouts per action node and easily exceeds the strict end-to-end latency budget of real-time agent services. Collectively, the two challenges expose a fundamental tension between causal attribution and online deployment , calling for a memory-drift detector that provides causal attribution without exposing counterfactual rollouts to the online serving path. To address these challenges, we propose DriftGuard, a two-stage framework that decouples offline causal supervision from online estimation. First, at every action node, DriftGuard constructs offline causal supervision through repeated paired counterfactual replays. Each pair branches before the action, neutralizes one retrieved memory, and continues the original and counterfactual trajectory suffixes under matched conditions. To mitigate stochastic variations in agent execution, the resulting annotations are aggregated through component-wise majority voting into a memory drift score (MDS) that captures four causal events: action change, attack removal, violation removal, and task recovery. Then, guided by this supervision, DriftGuard trains an online risk model (ORM) that estimates MDS directly from pre-action information. At serving time, the ORM scores each retrieved memory in a single forward pass, and DriftGuard flags drifted memories via their maximum component risk without any online counterfactual rollout. Through this design, DriftGuard preserves the causal semantics of memory-drift attribution while maintaining an online cost comparable to a lightweight guardrail, jointly resolving challenges ❶ and ❷. Extensive experiments across diverse victim agents and attack benchmarks validate the utility of DriftGuard in causally attributing and efficiently defending against memory drift.  

> Contributions.

The main contributions of this work can be summarized as follows. ❶ We formulate online memory-drift detection as a critical yet under-addressed problem for memory-augmented LLM agents , which aims to reconcile causal attribution with online deployment constraints, and characterize two fundamental challenges— non-causal content-level features and prohibitively expensive counterfactual attribution —that separate it from existing memory-oriented defenses. ❷ We introduce DriftGuard to solve the online memory-drift detection problem. It constructs decomposed causal supervision through repeated paired counterfactual rollouts and majority-voted event annotations, then trains a single-pass online risk model that estimates the resulting MDS from pre-action information and flags drifted memories with its maximum component risk. ❸ We conduct comprehensive experiments to evaluate the efficacy of DriftGuard, where it accurately identifies drift-inducing memories, effectively defends memory-augmented agents against adversarial memories, and remains efficient enough to be deployed on the online serving path. 

## 2 Related Work 

This work aims to detect memory drift in LLM agents at serving time, i.e. ,quantifying retrieved memory’s causal contribution to the potential drift. It therefore sits at the intersection of three fields: memory poisoning in LLM agents, causal attribution for LLMs, and guardrails for LLM agents. Below, we review representative work from each field. 

2.1 Memory Poisoning in LLM Agents 

Application-integrated LLMs can ingest untrusted instructions from external content, allowing indirect prompt injections to influence later tool use even when the current user request is benign [13]. Recent work has extended this attack surface to the persistent memory of LLM agents, giving rise to a rapidly growing memory poisoning literature. Early studies focus on content-level poisoning , where a single crafted record is injected to steer future retrievals. For example, AgentPoison [14] and PoisonedRAG [15] show that few carefully crafted records can hijack retrieval-augmented agents, and MPBench [19] provides a systematic taxonomy across six attack classes and nine structural vulnerabilities. 2.2 Causal Attribution for LLMs 

Attributing observed language-model behavior to specific causes has been studied along two complementary directions. The first direction is internal causal attribution , which uses activation-level interventions to trace behavior to model components [23, 24]. Representative techniques include causal tracing [28, 29], activation patching, structural graph analysis, and causal discovery methods estimating dependencies among observed variables [30, 31, 32]. Recent studies further explore whether LLMs themselves can perform causal reasoning [33]. However, this line targets internal circuits, not external inputs, and cannot identify which retrieved memory causes a given behavior. The second direction, external causal attribution , complements the first by intervening on inputs to trace failures back to specific external artifacts, and is therefore most relevant to memory-drift detection. Causal Agent Replay [34] and CausalFlow [35] apply step-level counterfactual interventions to attribute agent failures; BACKTRACE [36] pairs each skill-conditioned answer with a matched no-skill counterfactual to quantify skill influence; MemAudit [37] combines a counterfactual memory-influence score with a memory-consistency graph to identify poisoned memories once harmful behavior has been observed; and Causal Analyst [38] learns a causal graph over prompt features via LLM encoding and GNN-based causal discovery to identify the direct causal drivers of jailbreak behavior. Nevertheless, these methods estimate causal effects offline or post-hoc via explicit counterfactual rollouts or graph learning, leaving unresolved the tension between causal attribution and online latency budget.

## 3 Motivation 

Persistent memory is increasingly used to provide LLM agents with reusable experience across interactions [14, 15]. However, existing safety detectors primarily assess queries [10, 39], retrieved context, or responses [11, 12], whereas attributing execution changes to specific memories requires interventions [34, 37]. Applying such interventions to every retrieved memory conflicts with online latency budgets, exposing two challenges: ❶ Content-level features of retrieved memories are non-causal for memory-drift attribution. Multiple correlated memories can co-occur with the same harmful action or task failure. Features such as perplexity, retrieval relevance, attention, or output harmfulness do not measure how neutralizing one memory changes the trajectory while holding task and context fixed. They therefore cannot reliably distinguish a drift-inducing memory from a suspicious but irrelevant record. ❷

Counterfactual attribution is prohibitively expensive for online detection. Testing K retrieved memories requires K

additional counterfactual rollouts, each replaying downstream actions and tools and reevaluating outcomes. This cost grows with the remaining workflow and can exceed online serving budgets, even when feasible for offline auditing. 

Case study. To substantiate the two challenges above, we examine an airline-booking agent in Figure 1 that retrieves five memories before flight search and payment. For challenge ❶, Figure 1(a) contrasts two memories: m(2) is a harmless decoy with high perplexity, relevance, and attention scores, whereas the routine-looking m(3) supplies an attacker-controlled payment endpoint. The agent follows m(3) , leaking user credentials while reporting a successful booking. Only neutralizing m(3) prevents the leakage, identifying the causal source for the drift. For challenge ❷,Figure 1(b) shows that testing all K memories requires K additional trajectory replays, each rerunning downstream actions and tools and reevaluating outcomes. To address these challenges, two research directions offer complementary capabilities. Controlled interventions reveal how a targeted change alters downstream model behavior and thereby support rigorous causal measurement [23, 24]. Learned guards [12] directly score observed inputs and outputs without replaying the entire victim workflow. Yet neither approach alone suffices: interventions remain too costly for online deployment, whereas observational guards lack intervention-derived supervision targets for memory-level effects. This gap motivates two key questions: How can controlled interventions define a metric of each memory’s causal contribution to behavioral drift? How can an 

4efficient online detector accurately estimate this metric without relying on counterfactual trajectories at serving time? 

## 4 Methodology 

In this section, we introduce DriftGuard, which separates accurate attribution from efficient deployment through offline causal metric construction and online risk estimation, as shown in Figure 2. Section 4.1 constructs paired trajectory suffixes by neutralizing one candidate memory before each action to expose its causal effect on downstream behavior. Building upon these paired suffixes, Section 4.2 introduces the decomposed memory drift score (MDS) to quantify four causal events induced by intervention. Section 4.3 then trains an online risk model (ORM) to estimate MDS directly from pre-action inputs, and Section 4.4 outlines the complete online workflow of DriftGuard for practical deployment.

4.2 Decomposed Memory Drift Score 

In this subsection, we introduce the memory drift score (MDS) to quantitatively characterize the causal effect exposed by each pair of counterfactual trajectories. The key is to decompose this effect into two complementary forms of drift: (1) action drift , which captures the proximal effect on the next executable decision, and (2) outcome drift , which captures the downstream effects on security and task consequences over the remaining trajectory. This decomposition 5follows recent agent-evaluation studies showing that interaction-level behavior and intermediate milestones provide information complementary to final security and utility outcomes [53, 54, 55], and rather than collapsing these heterogeneous effects into a manually weighted scalar, MDS retains their event dimensions separately.

These dimensions reflect complementary aspects of action correctness commonly evaluated in tool-using agents: selecting an appropriate tool, accurately grounding its arguments in the task context, and organizing the required calls into a coherent execution path [2, 1, 55]. 5.1 Experimental Setup  

> Datasets.

We evaluate DriftGuard in both offline memory-drift detection and online defense settings. For offline detection, we evaluate on three memory-poisoning benchmarks: MINJA [56] with EHRAgent subset, AgentPoison [14] with Agent-Driver subset, and MPBench [19]. We split data at the trajectory level into training, validation, and test par-titions, keeping all memories and causal labels derived from the same trajectory within one partition. For online defense, we additionally evaluate on Mem2ActBench [57], STATE-Bench [58], and DBBench from AgentMemoryBench [59, 60].  

> Baselines.

For offline detection, we compare DriftGuard against Random Ranking and frontier LLM rankers under both zero-shot and few-shot prompting. The LLM rankers include Gemini 3.1 Pro [61], GPT-5.6 Sol [62], and Claude Opus 5 [63]. We evaluate all detectors under three victim-agent backbones: Gemma-4-12B-IT [64], DeepSeek-V4-Flash [65], and GPT-5.6 Luna [62]. For online defense, we compare against No Defense, SMSR [66], A-MemGuard [67], and an LLM Memory Auditor that directly inspects retrieved memories before execution. We evaluate all defenses under three representative memory-poisoning attacks that cover distinct poisoning mechanisms: Direct Override, which appends explicit hijacking instructions to overtly redirect the agent; MemoryGraft [68], which grafts forged episodes into the retrieval store to bias tool selection; and Sleeper Memory [18], which plants dormant memories that activate only on sensitive triggers. More configuration details about the baselines are provided in Appendix B.2.  

> Implementation Details.

Across all benchmarks, the agent retrieves the top-4 memories at each retrieval step. For offline causal supervision, we use R = 3 paired counterfactual replays per candidate memory. The ORM is instantiated with Qwen2.5-7B-Instruct [69] equipped with four linear heads. We fine-tune the backbone via LoRA [70] on the query, key, value, and output projection modules with rank r = 16 , scaling factor α = 32 , and dropout 0.05 . Training is conducted using the AdamW optimizer [71] for a maximum of 3 epochs, with learning rate 10 −4, weight decay 0.01 ,cosine scheduling, batch size 16 , and early stopping based on validation AUPRC. The four head-level loss weights 

λ∗ are fixed to 1. For defense, we calibrate threshold γ on each benchmark’s validation split to maximize F1 against the overall drift label, i.e. ,the logical OR of the four MDS components, and freeze it before test-time evaluation. The resulting thresholds are γ = 0 .033 , 0.081 , and 0.093 for Mem2ActBench, STATE-Bench, and DBBench, respectively. Memories with aggregate risk at least the corresponding threshold are repaired by GPT-5.6 Sol [62] before being supplied to the victim agent. All experiments are conducted on Intel(R) Xeon(R) Platinum 8368 CPUs with 8 NVIDIA RTX 4090 GPUs. More details are provided in Appendix B.3.  

> Evaluation Metrics.

For offline detection, since drift-inducing memories generally constitute a small fraction of retrieved candidates, we use AUPRC [72] as the primary metric and additionally report AUROC [73] and recall at 10% false-positive rate (R@10%FPR). For online defense, we report attack success rate (ASR) and task success rate (TSR) to measure security and task utility, respectively. AUPRC, AUROC, R@10%FPR, and TSR are higher-is-better, whereas ASR is lower-is-better.

5.5 Online Defense Performance 

In this section, we evaluate whether the causal risk estimates produced by DriftGuard translate into effective runtime protection. Following the detect-neutralize-rollout workflow in Algorithm 1, we deploy DriftGuard as a runtime guardrail and report ASR and TSR in Table 5, with key observations as follows. ❶ DriftGuard substantially suppresses diverse memory-poisoning attacks while preserving task utility. Across all three benchmarks, DriftGuard maintains low ASR under every attack family ( e.g. ,on Mem2ActBench, ASR drops from 46.7% to 5.3% under Direct Override and from 77.4% to 3.3% under Sleeper Memory). These reductions are accompanied by improved task utility ( e.g. ,TSR rises from 47.7% to 77.3% under Direct Override on Mem2ActBench), suggesting that rewrite-based intervention removes task-hijacking influence while preserving useful memory content. Consistent effectiveness across explicit instruction overrides, forged experiences, and trigger-conditioned attacks further supports our premise that the ORM captures task-conditioned causal risk rather than attack-specific surface patterns. ❷ DriftGuard consistently outperforms competitive online memory defenses. SMSR provides moderate robustness gains through repeated retrieval perturbations and victim-agent execution, while the LLM Memory Auditor offers stronger protection by inspecting retrieved memories directly. Nevertheless, DriftGuard achieves the lowest ASR and highest TSR across all evaluated settings ( e.g. ,on Mem2ActBench, compared with the LLM Memory Auditor, ASR decreases by over 10 points and TSR increases by over 15 points under each of the three attacks). These results support causal, context-conditioned memory-risk estimation for more precise online intervention than repeated-retrieval robustness or content-level auditing.

5.7 Hyperparameter Sensitivity 

In this section, we examine the impact of three key hyperparameters on the performance of DriftGuard: loss weight 

λ of each supervision head, runtime risk threshold γ for online intervention, and the number of paired counterfactual replays R for offline causal supervision construction. 

Sensitivity to Loss Weight λ. We first vary the loss weight λ of each supervision head—Action, Attack, Violation, or Task—one at a time over {0.25 , 0.5, 1, 2, 4} while fixing the remaining three weights to 1, and measure AUPRC on three memory-poisoning benchmarks. The results are reported in Figure 7, with key observations as follows. ❶

DriftGuard is robust to moderate variation of individual loss weights. Varying any individual λ between 0.25 and 2

produces only modest changes in detection performance, with AUPRC remaining within a narrow range around the balanced λ = 1 setting across all three benchmarks. Different heads exhibit slightly different local optima, but no single weighting consistently dominates, indicating that DriftGuard does not rely on finely tuned head-level loss weights. ❷ Excessively emphasizing a single supervision objective degrades performance. When the weight of an individual head is increased to λ = 4 , AUPRC generally declines relative to the balanced configuration. This suggests that the four causal supervision signals provide complementary information, while overemphasizing one objective can weaken the shared risk representation. 

Sensitivity to Runtime Threshold γ. We then sweep the runtime risk threshold γ over a grid spanning [0 , 0.99] 

under the rewrite-based intervention policy, and measure ASR and TSR on three online benchmarks, with each curve averaged across three attack methods (Direct Override, MemoryGraft, and Sleeper Memory). The results are reported in Figure 8, with key observations as follows. ❶ Extreme thresholds sacrifice one side of the safety–utility trade-off. 

At γ → 0, nearly all candidate memories are rewritten and TSR collapses across all three benchmarks, whereas at 

γ → 1 almost no intervention is triggered and ASR approaches the No-Defense level. This indicates that γ directly controls the trade-off between security and task utility, and neither extreme provides a desirable operating point. ❷

Intermediate thresholds achieve a stable safety–utility balance. The dataset-specific validation-selected thresholds 14 maintain low ASR while preserving substantially higher TSR than aggressive intervention. As γ increases beyond this region, ASR rises rapidly as fewer risky memories are neutralized. ## 6 Conclusions 

In this work, we investigated the problem of online memory-drift detection for memory-augmented LLM agents, which seeks to quantify each retrieved memory’s causal contribution to potential drift under the latency budgets of online agent serving. We identified two fundamental challenges: non-causal content-level memory features and prohibitively expensive counterfactual attribution that jointly prevent existing memory-oriented defenses from reconciling causal attribution with online deployment. To address these challenges, we proposed DriftGuard, a two-stage framework that decouples offline causal supervision from online estimation. Specifically, DriftGuard constructs a decomposed memory drift score (MDS) via offline paired counterfactual rollouts that jointly capture action change, attack removal, violation removal, and task recovery, and trains an online risk model (ORM) that estimates MDS directly from pre-action information without invoking any counterfactual rollout at inference time. Extensive experiments across diverse victim agents and attack benchmarks confirm that DriftGuard accurately identifies drift-inducing memories, effectively defends memory-augmented agents against adversarial memories, and remains efficient enough to be deployed on the online serving path. 

Limitations & Future Works. This work has two primary limitations deserving further exploration. First, our offline supervision uses single-memory interventions and still requires agent, tool, and evaluator replays for data construction; it therefore does not capture interactions among multiple retrieved memories. Future work should develop more sample-efficient, interaction-aware supervision. Second, our evaluation focuses on tool-using agents, and neutralizing flagged memories is not guaranteed to remain safe under domain shifts or unseen attacks. Extending evaluation to broader settings and developing mitigation policies with explicit safety and utility guarantees are important directions.

## B Reproduction Details 

B.1 Dataset Descriptions  

> Offline Detection.

We use the EHRAgent subset of MINJA [56] for clinical tool use, the Agent-Driver subset of AgentPoison [14] for autonomous-driving planning, and MPBench [19], which covers six attack classes and nine structural vulnerabilities across heterogeneous agents.  

> Data Construction.

Each offline benchmark is split by trajectory into training, validation, and test sets at an 8:1:1 ratio, with all derived memory records and annotations kept in the same split. For each candidate memory, repeated paired counterfactual replays produce four-dimensional binary event annotations, which are aggregated through strict majority voting to construct the final MDS supervision labels. The default replay count is R = 3 . 

> Online Defense.

We use Mem2ActBench [57] for multi-turn memory-conditioned tool use, STATE-Bench [58] for long-horizon stateful workflows, and DBBench 3 from AgentMemoryBench [59, 60] for database operations.

21 B.2 Attack and Defense Details 

Attack Methods. ❶ Direct Override appends explicit hijacking instructions to retrieved memories under the B3 setting (three poisoned memories per task). ❷ MemoryGraft [68] inserts forged episodes that bias tool selection toward attacker-controlled routines, using the Forged Episode setting. ❸ Sleeper Memory [18] plants trigger-activated dormant memories, using the original Aggressive setting. 

Defense Methods. ❶ No Defense supplies retrieved memories directly to the victim agent without inspection or rewriting. ❷ SMSR [66] tests action stability through repeated memory perturbations and agent rollouts; memories whose removal significantly changes the majority-voted action are excluded before replaying the trajectory. ❸

LLM Memory Auditor uses GPT-5.6 Sol [62] to score each memory given the current task and safety instructions. Memories above a validation-selected threshold are neutralized with the same rewrite operator as DriftGuard. ❹

A-MemGuard [67] uses consensus-based validation to identify anomalous reasoning induced by retrieved memories, together with a dual-memory mechanism that stores and reuses lessons from detected failures. We adapt it to our online evaluation environments while preserving its core validation and lesson-memory mechanisms. 

B.3 Implementation Details 

Paired Counterfactual Construction Settings. For each candidate memory, we generate R = 3 paired replays. In each repetition, the original and counterfactual branches start from the same restored checkpoint, tool state, and environment snapshot and use the same decoding policy and seed; the intervention and pre-action state remain fixed across repetitions. Each pair yields four binary event labels. Final MDS labels are obtained by component-wise majority voting, with ties assigned negative labels. Action extraction E and neutralization I use GPT-5.6 Sol [62] at temperature 0 with Prompts B.3.1 and B.3.2, respectively. Pairs are retained only when neutralization removes the suspected mechanism while preserving benign task semantics and leaving non-intervened inputs unchanged. Prompt B.3.1: Action Extraction
