## 摘要
检索增强生成（RAG）是一种成熟范式，用于利用从外部语料库检索到的信息增强大语言模型（LLM）。然而，开发有效的RAG系统需要大量工程投入和迭代实验，因为有效的设计选择会因任务和领域而异。随着LLM智能体能力的快速提升，我们追问这些智能体能够在多大程度上自主构建RAG系统，以及它们能通过迭代多有效地改进这些系统。本文提出AutoRAGBench，这是首个评估LLM智能体如何在开放代码空间中从零开发RAG系统的基准。它包含九个RAG系统开发任务。对于每个任务，智能体在没有起始代码或预设策略的情况下从零构建RAG系统，并在单块H800 GPU上以六小时为预算限制。它们分析任务数据、实现RAG流水线，并基于实验反馈迭代优化设计。我们评估了九种智能体配置，并分析所得RAG系统的有效性及其开发轨迹。GPT-6.1 Sol搭配Codex CLI取得最高平均分56.1。复合Human-SOTA基线平均为44.4。这些结果表明，LLM智能体能够自动化有效的RAG系统开发。在七个任务上分别从人类设计的系统出发时，GPT-6.1 Sol搭配Codex CLI平均将分数提高16.6分。

## Abstract
Retrieval-augmented generation (RAG) is a well-established paradigm for augmenting large language models (LLMs) with information retrieved from external corpora. However, developing effective RAG systems requires substantial engineering effort and iterative experimentation, as effective design choices vary across tasks and domains. With rapid advances in LLM agent capabilities, we ask how well these agents can autonomously build RAG systems and how effectively they can improve them through iteration. In this paper, we propose AutoRAGBench, the first benchmark to evaluate how well LLM agents develop RAG systems from scratch in an open code space. It comprises nine RAG system development tasks. For each task, agents build RAG systems from scratch without starter code or prescribed strategies, under a six-hour budget on a single H800 GPU. They analyze task data, implement RAG pipelines, and iteratively refine their designs based on experimental feedback. We evaluate nine agent configurations and analyze both the effectiveness of the resulting RAG systems and their development trajectories. GPT-6.1 Sol with Codex CLI achieves the highest average score of 56.1. The composite Human-SOTA baseline averages 44.4. These results show that LLM agents can automate effective RAG system development. When starting from a human-designed system on each of seven tasks, GPT-6.1 Sol with Codex CLI improves the score by 16.6 points on average.

## 2. 方法论

### 2.1 任务形式化

- 任务规格：`T = ⟨C, D, B, K⟩`
  - `C`：外部知识源（检索语料）；`D = {(qᵢ, yᵢ)}`：训练划分的问答样例；
  - `B`：资源预算（时间、算力、内存、存储）；`K`：规则集（数据/网络/模型使用限制、提交系统的输入输出接口要求）。
- 智能体：`a = ⟨M_a, H_a⟩`，`M_a` 为底层 LLM，`H_a` 为承载工具调用与执行循环的 harness（脚手架）。
- 动作空间 `A_a`：读/写/编辑文件、检索文件内容、执行 shell 命令与脚本。
- 迭代过程：`u_t = π_a(T, h^{t-1})`；`o_t = E(u_t, h^{t-1})`；`h_t = h^{t-1} ⊕ ⟨u_t, o_t⟩`；最终 `S = Build(a; T)`。
- 优化目标：`maximize Q(S)`（下游答案得分），`minimize L(S)`（检索延迟）。

### 2.3 系统开发协议

- 每次 build 在**干净隔离容器**中运行，**无跨运行持久记忆**，智能体间不共享状态。
- 统一任务指令、**1×H800 GPU**、**6 小时**预算；**无起始代码、无预设流水线、无预设配置空间**；提前完成会被提示继续开发。
- 允许联网（装库、下模型），但**索引与检索只能使用给定语料**；提交系统须返回有序证据片段列表（文档 ID、标题、原文），生成的摘要/假设文档/中间答案只能用于引导检索，**不能替代语料证据**。
- 截止时冻结系统，评测期间禁止再训练或改动，且每个测试问题独立处理。
- 评测时开发自检使用 **Qwen3.5-4B** 作答。

### 2.4 反作弊审计

- 记录每一步动作与观察，形成**开发轨迹（development trajectory）**。
- 用 DeepSeek 自动审查轨迹与提交系统（是否用外部语料、是否下载测试集等），再由团队人工复核可疑运行。
- 违规者重跑一次；若仍不通过，该运行记为 **Naive BM25 RAG 基线分数**。

### 2.5 评测设计（双轨）

**(A) RAG 系统评测**

- **答案准确率**：5 个 held-out 作答模型（Gemma-4-E4B、Gemma-3-4B、Phi-4-mini、SmolLM3-3B、Llama-3.2-3B）在**同一份检索证据**上独立作答，按任务指标 `μ_k` 打分后对 5 个模型取平均：`Q(S_{a,k}; G) = (1/|G|) Σ_G Q(S_{a,k}; G)`；总分 = 9 个任务分的**非加权平均**（0–100）。
- **证据打包**：评测器校验并去重证据，按检索顺序打包为公共前缀（≤32,000 字符、≤12,000 Qwen token），须适配 5 个模型 32,768 上下文（各留 512 token 作答）；无效证据/超预算/生成失败计为无效预测。
- **排序稳定性**：检验更换作答模型是否改变系统相对排名。
- **检索延迟**：从接收问题到返回证据的时间（不含最终答案生成），上限 60 秒，超时记 60 秒。
- **服务接口**：`POST /retrieve`；每题最多 4 次 Qwen3.5-4B 调用、32,000 token、60 秒，第 5 次调用返回 429。

**(B) 开发过程评测**

- 四类活动：**Preparation**（读任务与环境）、**Implementation**（实现了哪些 RAG 方法/组件）、**Testing**（是否测系统或组件、选题策略、是否划分调优/验证集）、**Analysis**（如何诊断失败并决定下一步）。
- 迭代进展指标（同一次 build 内）：`Δdev = d_N − d_1`（首次→末次可比开发分）、`Δdrop = max_i d_i − d_N`（峰值→末次的回落）。
- 资源使用：各活动的时间占比、输出 token 占比、API 花费。
