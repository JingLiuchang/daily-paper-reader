Alibaba Group Personalized LLM agents must act on a user’s current preferences, which change across interactions and are rarely stated in full. Existing memory systems store and retrieve content from the interaction history and leave the agent to work out which preferences still hold and where they apply. Such content does not indicate whether a preference is still current or where it applies, so agents often act on outdated or misapplied preferences. We instead treat memory as the assistant’s belief about the user. Following Bourdieu’s account of habitus as durable but revisable dispositions, we model the user as a latent preference state that every interaction, including the current request, both reveals and updates. The belief summarizes what the history supports about this state, and memory consists of the individual beliefs that bear on the agent’s current decision, each with its evidence, scope, and status. We implement this view in HabitusMem, a trained writer that states these beliefs as text records for a frozen agent. Across two agent families, HabitusMem achieves the best results among memory systems on both PersonaMem-v2 and VitaBench 2.0. Controlled analyses show that learned request conditioning drives the answering gain, while auxiliary training tasks improve tool use.

1. Introduction 

Large language model (LLM) agents increasingly assist the user across many interactions, answering questions and carrying out tasks on the user’s behalf (Jiang et al., 2025a,b, Chen et al., 2026). Useful assistance depends on preferences and constraints that a new request rarely states in full. These preferences form through repeated choices, persist across situations, and change over time: a user who has moved supplies a new delivery address, a user who has lost interest in a topic asks the assistant to stop raising it, and a gift chosen for a friend reveals little about the user’s own taste. The agent must therefore act on the user’s current preferences, which it can only infer from what the user has said and done. Existing memory systems carry this information across interactions by storing content derived from the history: they extract facts, maintain notes or summaries, or retrieve and compress past passages for the current request (Zhong et al., 2024, Chhikara et al., 2025, Xu et al., 2026a, Lewis et al., 2020, Jiang et al., 2024). Such memory records what the user said or did rather than what the history implies about the user now (Figure 1), and it leaves three questions to the agent. How strongly does the history support a claim? 

Memory stores claims without their evidential basis, so a disposition confirmed across many interactions and an incidental or indirect observation enter in the same form, and the agent cannot weigh one against the other. Where does a claim apply, and does it still hold? Entries carry no scope or status. Which claims matter for the decision at hand? Memory is written or retrieved by salience and surface similarity rather than by relevance to the agent’s decision, so it can drop constraints the decision depends on and abstract away details that the action requires exactly. The underlying problem is that these designs represent the history, whereas personalization needs a representation of the user. Bourdieu’s concept of habitus describes what personalization targets: durable dispositions, formed through past experience, that generate practices in concrete situations (Bourdieu, 2020). These dispositions are durable but revisable, since new experiences are perceived through categories formed by earlier ones and in turn reinforce or modify them (Bourdieu and Wacquant, 1992, p. 133). For an assistant, this suggests modeling the user as a latent preference state shaped by the whole history and carried forward by every interaction, including the current request. A belief-state view makes this concrete (Berger, 1987): earlier interactions form the assistant’s belief about the user, each new interaction revises it, and the current belief summarizes what the history supports about the user’s present state. We express this belief as a set of individual beliefs, each a claim about the user’s preferences, circumstances, or constraints, and define memory as the subset of these beliefs that bears on the agent’s current decision, since the agent acts to minimize expected loss under the belief. Memory is thus composed of beliefs about the user rather than of content from the history. Each of the three questions then has a direct answer. A claim’s evidence conveys its credibility; its scope and status convey where it applies and whether later observations have left it active, superseded, or retracted; and the decision posed by the request determines which claims to include.

We instantiate this view in HabitusMem, a writer that composes memory from belief records of the form claim | evidence | scope | status , one belief per record, for a frozen agent. Reading the raw history and the current request, the writer answers the three questions directly: it cites the observations that support each claim, marks its scope and whether later interactions have superseded or retracted it instead of overwriting it, and keeps only the claims that bear on the request, with the exact choices and constraints an action requires. A single model learns these operations from four tasks that mirror belief tracking: direct writing infers claims and their evidence, state update revises them with new interactions, and request and action projection select those a question or transaction depends on. The resulting memory works with different agents without modifying them. Across two agent families, HabitusMem achieves the best results among memory systems on PersonaMem-v2 and VitaBench 2.0, and controlled analyses attribute its gains to learned request conditioning and the auxiliary tasks. Our contributions are as follows: • We reframe personalized memory as the assistant’s belief about the user following Bourdieu’s account of habitus. The resulting memory states how credible each preference is, where it applies, whether it has changed or been withdrawn, and whether it matters for the current decision, enabling the agent to act on the user’s current preferences. • We introduce HabitusMem, a writer that states each belief as a text record with its evidence, scope, and status for a frozen agent. A single adapter learns belief inference, belief update, and decision projection from four training tasks, which supports both personalized answering and task execution that depends on exact constraints. • On PersonaMem-v2 and VitaBench 2.0, with two agent families, HabitusMem is the most accurate compact memory for personalized answering and the most consistent for personalized tool use, where it also surpasses giving the agent the full history. 

2. Related Work 

Memory for LLM agents. Agent memory systems differ in their substrate, their cognitive analogy, and whose experience they store (Huang et al., 2026). User-centric systems maintain external stores of extracted facts, notes, or summaries that are retrieved for later requests (Zhong et al., 2024, Packer et al., 2023, Chhikara et al., 2025, Xu et al., 2026a, Rasmussen et al., 2025). Other designs organize memory after human cognition, for example through episodic event segmentation or Hebbian association (Fountas et al., 2025, Zhu et al., 2026), and agent-centric memory accumulates the agent’s own task experience (Wang et al., 2023, Ouyang et al., 2026, Wang et al., 2024c). A growing line learns memory operations, either by writing knowledge into model parameters (Wang et al., 2024b,a) or by optimizing memory edits against downstream reward with reinforcement learning (Yan et al., 2026, Wang et al., 2025, Yu et al., 2026). Retrieval augmentation and query-aware compression instead select or shorten passages for the current input (Lewis et al., 2020, Jiang et al., 2024, Xu et al., 2024). Across these designs, an entry records what was said or observed without stating how credible a claim is, where it applies, or whether a later observation has superseded or retracted it. HabitusMem keeps the raw history as the source of evidence and defines memory as the part of the assistant’s belief about the user that bears on the current decision, with these properties stated in each record. 

Personalized agents and benchmarks. Personalized agents extend LLMs with user profiles, memory, planning, and action execution (Xu et al., 2026b). 3. Methodology 

HabitusMem composes memory from the assistant’s beliefs about the user’s current preference state, selected for the decision the agent faces. As Figure 2 shows, a single writer reads the raw interactions together with the current request, infers beliefs with their evidence, scope, and status, and passes those that bear on the request to a frozen agent. Section 3.1 formalizes the belief and the decision it serves, Section 3.2 describes how the writer expresses the belief as text records, and Section 3.3 describes how it is trained to infer, revise, and select beliefs.

The belief determines how credible each claim about the user is, and the request determines, through the loss, which claims change the agent’s decision. A gardening preference is equally credible whether the user asks for a weekend activity or a train ticket, but only the first request makes it relevant. Conversely, an order can fail on a single wrong variant or quantity, so the memory must convey such details exactly. Under a fixed message budget, conditioning the memory on the request can only lower the best attainable risk. The formulation also determines what a textual memory should state. Each record in HabitusMem has four fields. The claim states a fact, preference, or constraint about the user. Its evidence , the observations that support it, lets the agent distinguish a disposition established by repeated explicit statements from one inferred from a single choice. Its scope , the situations in which the disposition guides behavior, prevents a choice made for one occasion from steering every later request, since a disposition is expressed differently across situations. Exact inference over natural-language histories is intractable, and HabitusMem neither estimates numerical posteriors nor optimizes Equation 2 through agent rollouts. 3.2. Memory construction 

Memory construction starts from the accumulated raw interaction log. New observations are appended to the log, and a position- and budget-based rule Tτ selects the view Xt = Tτ (Ht) that fits the writer’s input: on PersonaMem-v2 it keeps the beginning of each history, and on VitaBench 2.0 it keeps the beginning together with the most recent interactions. This rule determines which evidence the writer can see, and the writer decides what enters the memory. The writer receives the selected history, a format instruction I, and a suffix sτ (qt) containing the current request. For question answering, the suffix asks for facts and preferences that help answer the request. For agent tasks, an action suffix asks for explicit choices and fulfillment constraints, such as products, variants, quantities, addresses, and times, and asks the writer to keep explicit historical choices rather than inferred alternatives. The output is a list of records under a ## Beliefs header, one per line in the form claim | evidence: source | scope: context | status: state . The four fields are those defined above. Together, the fields separate an enduring disposition, a one-off instruction, and a withdrawn preference. For example, an oat-milk order scoped to this delivery only keeps its exact quantity without steering later requests, and a spicy-food preference marked retracted (message 61) no longer guides restaurant choices. We instantiate the writer with Qwen3.5-9B and one LoRA adapter shared across tasks. The writer generates the memory in one greedy decoding pass, and the agent acts on the records together with the current request,

Whenever the history or the request changes, the writer rewrites the memory from the selected raw log and keeps no persistent state between requests; repeated reads with the same history and request reuse the cached memory. 

3.3. Training 

We train the writer in two stages on the official PersonaMem-v2 training split. The first stage produces a parent writer that infers beliefs from a history and a request. The second stage uses this parent as a frozen teacher to construct examples of the operations it lacks, belief update and decision projection, and trains HabitusMem on all of these operations together. 

Stage 1: Parent writer training. Writing a useful belief requires both the record format and the ability to identify the preference a request depends on, so we teach them in turn. We first cold-start a Qwen3.5-9B

LoRA adapter on belief memories from a frozen DeepSeek-V4-Flash teacher, which writes one schema-valid memory at each of two positions in every training history. This substep teaches the record syntax without using preference annotations. The resulting writer then generates a static belief memory for each persona, and for each training request we place the request’s annotated preference at the top of this memory as a new record. The status of the record follows the annotation, marking a preference as active, as superseding an earlier one, or as retracted, in which case the record names the topic but not the revoked content. Training on these memories teaches the parent to surface the belief that a request depends on. The parent sees no update or projection examples, so it cannot revise stored records or select them for a decision. 

Stage 2: HabitusMem writer training. We initialize HabitusMem from the parent and train it on four tasks that cover inferring, revising, and selecting beliefs. Direct writing D1 retains the Stage 1 targets and teaches belief inference from evidence. State update D2 teaches belief revision. The parent processes each history chunk by chunk, a data builder merges the resulting records into a running state Sk, and each transition

Request projection D3 and action projection D4 teach the selection of beliefs for the current decision. From the final state, the parent writes the view that a request needs, and for requests that require execution the view must also preserve the exact choices and fulfillment constraints. 4. Experiments 

We evaluate HabitusMem on PersonaMem-v2 for personalized question answering and on VitaBench 2.0 for personalized tool use. Section 4.2 compares it with established memory systems, and Section 4.3 isolates the contributions of request conditioning, the auxiliary tasks, and the record fields. Appendices C–E further report training-mixture and inference sensitivity, computational cost, controlled probes of evidence, scope, and status, and case studies. 

4.1. Experimental setup Benchmarks and metrics. PersonaMem-v2 (Jiang et al., 2025b) evaluates personalized answering from long interaction histories, including changing preferences and requests to forget. We evaluate in the English 32k setting, whose test split contains 5,000 queries. The test queries span nine task scenarios. We report personalized QA accuracy on multiple-choice questions as the primary metric and a generation score assigned by an external Qwen3.5-9B judge. VitaBench 2.0 (Chen et al., 2026) contains 771 subtasks from 56 users, in which an agent uses tools to complete delivery, in-store consumption, and online travel tasks according to preferences implicit in past dialogues and behavior logs. We run four trials per subtask, with an external Qwen3.5-9B simulating the user and scoring the trajectory against the subtask rubric. We report average reward ( Avg@4 ), success in at least one of four trials ( Pass@4 , any-success ), and success in all four ( Pass 4,

4.2. Main results Personalized answering. Table 1 shows that HabitusMem is the most accurate memory method under both agents, at 0.537 with Qwen and 0.484 with DeepSeek, 4.8 and 4.6 points above the strongest baseline. That baseline changes with the agent and the scenario, whereas HabitusMem leads in five of nine scenarios with Qwen and eight with DeepSeek, so belief memory transfers more uniformly than content-based memory. Conditioning on the request does not explain this advantage by itself, since RAG also retrieves for the current request yet reaches only 0.460 and 0.391. Retrieval returns what the user said that resembles the request, whereas a belief record states what the history implies about the user for that request. In the Knowledge scenario, the memory-free base LLM with Qwen outperforms full context and every content-based memory, indicating that injected history interferes with questions the agent could otherwise answer, whereas HabitusMem conveys only the relevant beliefs and exceeds full context by 13 and 11 points. Full context remains more accurate, as expected of a condition that loses no evidence, but the generation score shows what evidence alone does not provide. Moving from the memory-free base LLM to full context raises accuracy with Qwen and DeepSeek from 0.446 and 0.263 to 0.569 and 0.522, yet generation stays nearly flat, from 0.256 and 0.291 to 0.227 and 0.302, while HabitusMem reaches 0.326 and 0.382. 5. Conclusion 

We treated personalized memory as the assistant’s belief about an evolving user state, conveyed as the part relevant to the current decision with the evidence, scope, and status of each claim. With one writer shared across benchmarks and two agent families, HabitusMem is the most accurate evaluated compact memory on PersonaMem-v2 and achieves the highest all-success among non-privileged VitaBench conditions. The component analysis separates the sources of these results: learned request conditioning is central to answering, the auxiliary tasks improve tool use, and structured fields provide an answering gain. 

Limitations. HabitusMem has three main limitations. First, its fixed input budget may exclude relevant evi-dence from long interaction histories. Second, belief extraction and application remain imperfect, particularly for retracted preferences and precise execution constraints. Third, we have not yet evaluated HabitusMem in broader applications, including email composition, personalized recommendations, and scheduling.

A. Decision-theoretic interpretation of belief memory 

Section 3.1 models the user as an evolving latent state and defines memory by expected loss under the belief, following Bayesian decision theory (Berger, 1987): the decision variable is a memory message, and its value depends on the actions it induces in a fixed agent. The formulation is a design rationale for what a record should state, and HabitusMem does not carry out the inference numerically. This appendix separates the evidential and decisional roles of the request, relates the formulation to habitus, and shows when conditioning the memory on the request helps. 

A.1. The request as evidence and as decision 

Let ¯bt(zt) = ∫︀ p(zt | zt−1) bt−1(zt−1) dz t−1 denote the belief predicted from the interactions before the request. Setting ot = qt in Equation 1 gives 

bt(zt) ∝ p(qt | zt) ¯bt(zt). (5) If the request carries no evidence about the user, its likelihood is constant in zt and the belief equals the prediction from earlier interactions. The request still enters the loss ℓτ (a, zt; qt) and can therefore change the ideal memory: a gardening preference can become central to an activity recommendation without becoming more credible because the user asks for an activity. A request that reveals a new circumstance, such as a changed delivery address, changes both the belief and the loss. In the implementation, input selection additionally determines which part of the history the writer sees. 

A.2. Habitus and the latent state 

Bourdieu describes habitus as durable dispositions, produced by past experience, that generate practices in concrete situations (Bourdieu, 2020), and as an open system of dispositions that new experiences either reinforce or modify (Bourdieu and Wacquant, 1992, p. 133). In our formulation, the interaction history is the record of practices from which the assistant infers the user’s state, the transition p(zt | zt−1) allows that state to change, and the scope field records the situations in which a disposition guides behavior. The computational state zt is broader than habitus, since it also includes facts and explicit constraints that are not dispositions. The belief represents the assistant’s uncertainty about the user rather than a model of the user’s own reasoning; habitus motivates the formulation, and the experiments evaluate the memory design that follows from it.

A one-bit example shows that the inequality can be strict. Suppose the history contains independent uniform bits (U, V) and a uniform request asks for one of them. A.4. Textual records and the learned approximation 

A record (claim , evidence , scope , status ) communicates a user-related assertion together with its source, applicability, and current standing. Its evidence field refers to an observation already present in the history and is not an independent observation in Equation 1. Likewise, the token probabilities in Equation 4 model textual continuations, not calibrated probabilities that the claims are true. The records therefore express the belief qualitatively, through the stated evidence and status of each claim, and not as posterior probabilities. The status field distinguishes changes that a truth probability alone cannot express. A correction changes what the assistant believes happened, a preference update changes what is currently desired, and a request to stop using information restricts its use without necessarily making it false. Explicit records make these distinctions available to the agent, and correct use depends on both the generated memory and the agent. Action-oriented supervision likewise consists of demonstrated textual memories whose effects are evaluated on downstream agent tasks; it does not train on observed user actions. 

B. Implementation and evaluation details 

B.1. Inference and history selection 

HabitusMem uses the same adapter on both benchmarks, with the inference settings of Section 3.2. Both evaluations use Hugging Face generation with greedy decoding and a serialized generation lock. The writer regenerates the memory whenever the history–request pair changes, so the memory can change during a VitaBench interaction without recursive updates to a persistent state; state-update and projection examples serve as training supervision only. The VitaBench selector reserves space for the instruction, the request suffix, and 32 additional tokens, and then combines an initial history segment, an elision marker, and the most recent interactions. The PersonaMem selector keeps the first 32,000 characters before the final token cutoff. 

B.2. Training and evaluation settings 

The LoRA adapter has rank 64, alpha 128, and dropout 0.05. The cold-start stage trains for two epochs at learning rate 5 × 10 −5 on 1,598 belief memories, which the DeepSeek-V4-Flash teacher writes at two history positions for each of the 799 training personas. D. Memory quality and agent behavior 

Belief memory exposes not only a claim, but also its evidence, applicability, and current status. We design diagnostics around these distinctions to examine two separate steps: whether the writer preserves the relevant fact and whether a frozen agent uses it in a decision. A constructed paired probe suite tests these steps under controlled history changes. 

D.1. Constructed probes of evidence, scope, and status 

We construct 90 probes per writer across ten topics and nine cells: a self-purchase and gift pair for attribution, unconditional and conditional preferences crossed with partner and solo questions for scope, and active,

retracted, and superseded preferences for status. Each topic therefore contributes two attribution, four scope, and three status probes. Within each history pair or triple, the question and four choices stay fixed while one history element changes. The full writer is evaluated with both agents; the matched plain-text writer is evaluated with Qwen. The suite is constructed rather than sampled from either benchmark because this design requires controlled alternatives for the same decision. The writer, agents, and inference configurations otherwise match the benchmark evaluations. The writer sees the history and question; the answering agent sees the generated memory and question without the raw history. What the fields preserve and what the agent applies. Table 6 separates record quality from downstream answers and shows that explicit fields preserve distinctions that plain records lose. The full writer records the conditional scope and the retraction in all ten corresponding memories and the supersession in nine to ten, whereas the matched plain-text writer marks no retractions. With Qwen, full records match or exceed plain records in every cell. They yield ten of ten correct conditional-solo answers against seven with plain records, nine of ten superseded answers against eight, and one of ten retracted answers against zero. The scope result illustrates the purpose of an explicit scope field, since a preference can remain valid without applying to the current situation. Explicit records also make the remaining errors diagnosable. DeepSeek answers all other scope questions correctly but only two of ten conditional-solo questions, and the two agents answer one and two of ten retraction probes correctly although the full writer marks the revocation. These results show that correct use also depends on the agent, and that an explicit status makes a constraint available without guaranteeing that a frozen agent obeys it. 

Interpreting the gift cell. Manual inspection confirms that all ten gift memories from both writers state “a birthday gift for the user’s sister.” The checker criterion expects the gift attribution and rejects memories that present the item as the user’s interest; this expectation is stricter than the history, which already contains the user’s earlier self-statement. A faithful memory can therefore contain both facts. The same memories receive one of ten correct judgments from the Qwen checker and nine of ten from the DeepSeek checker. The answer key is similarly strict, marking the item-based answer wrong in the gift condition despite the earlier interest. The resulting zero of ten correct answers with Qwen and one of ten with DeepSeek diagnose how the consumer weighs gift framing against existing interest. They do not estimate pure attribution accuracy or establish that the writer misrecords the gift. We treat the automatic checks as model-dependent diagnostics cross-checked by manual inspection. 

E. Case studies 

We select two cases, one from each benchmark, to analyze and illustrate clearly how HabitusMem works. Memory excerpts are verbatim and state how many generated records they show, and Chinese records and dialogues are translated. Together, the cases show why writing memory as beliefs helps an agent act on the user’s current preferences. In Case 1, the options differ only in whether they invoke a withdrawn preference, so a correct answer requires knowing both what was withdrawn and that it was withdrawn. The retracted record supplies both. It names the preference, which lets the agent recognize three different paraphrases of it, and its status tells the agent not to use it, while leaving the agent free to answer the question about architecture. A memory that deleted the preference could not identify these paraphrases, and a memory that kept it without a status could support the wrong options. In Case 2, the request supplies none of the arguments that the purchase needs. The guidance gτ names the constraints to extract and asks the agent to finish the transaction, but it contains no user-specific values. The records supply them, each stating one exact brand, flavor, size, or address that maps onto a tool argument, so the agent can fill the calls without asking again. The alternative record also lets the agent recover from missing stock with a choice from the user’s own history. In both cases, the records state what holds about the user, where it applies, and whether it still holds, so the agent acts on explicit beliefs rather than reconstructing preferences from raw content. Stated values can also keep an action repeatable across trials.
