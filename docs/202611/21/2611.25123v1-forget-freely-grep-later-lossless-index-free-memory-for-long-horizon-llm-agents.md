## 摘要
长程 LLM 智能体常常超出其上下文窗口，被迫丢弃之后可能需要的信息。现有的上下文管理策略依赖摘要、掩码或结构化记忆，需要在未来需求尚不明确时就决定保留什么以及如何检索。然而，这些方法可能引入有损压缩，从而可能丢弃未来任务所需的细节。为解决这一局限，我们提出 GrepMem，一种简单、无损且无索引的记忆机制，它由两个组件构成：记录智能体完整历史的仅追加纯文本日志，以及用于按需召回的正则表达式搜索工具。与结构化记忆系统不同，GrepMem 无需嵌入、检索索引、记忆抽取或额外模型。我们在五种上下文管理策略下使用强化学习训练 Qwen3.5-9B，并在多问题研究会话、长流召回和智能体轨迹问答上进行评估。GrepMem 在 ContextBench 上达到 95–97% 的准确率，而有损基线最高仅为 21%；在 BCP-Multi 上比 SUPO 的摘要方法高出 8.8 个百分点。GrepMem 能有效扩展到越来越长的输入流，同时在全部五项评估任务中始终位于准确率—token 成本帕累托前沿。我们的结果表明，纯文本日志与 grep 为长程智能体记忆提供了一种简单但具有竞争力的方法，且无需复杂的结构化记忆基础设施。

## Abstract
Long-horizon LLM agents often exceed their context windows, forcing them to discard information that may be needed later. Existing context management strategies rely on summarization, masking, or structured memory, requiring decisions about what to preserve or how to retrieve it before future needs are known. However, these methods can introduce lossy compression, potentially discarding details needed for future tasks. To address this limitation, we introduce GrepMem, a simple, lossless, and index-free memory mechanism built on two components: an append-only plain-text log of the agent's complete history and a regular-expression search tool for on-demand recall. Unlike structured memory systems, GrepMem requires no embeddings, retrieval index, memory extraction, or additional models. We train Qwen3.5-9B with reinforcement learning under five context management strategies and evaluate on multi-question research sessions, long-stream recall, and agent-trajectory question answering. GrepMem achieves 95-97% accuracy on ContextBench, versus at most 21% for lossy baselines, and outperforms SUPO's summarization by 8.8 percentage points on BCP-Multi. GrepMem scales effectively to increasingly long input streams while remaining on the accuracy-token-cost Pareto frontier across all five evaluation tasks. Our results show that a plain-text log and grep provide a simple but competitive approach to long-horizon agent memory, without requiring complex structured memory infrastructure.

## 一、核心问题与整体含义（研究动机与背景）

- **核心矛盾**：长程 LLM 智能体（如深度研究、多轮工具调用）的交互历史终将超出上下文窗口，必须在“腾出空间”与“保留未来可能需要的细节”之间做取舍。而在未来需求尚未出现之前，智能体无法预知哪些信息会被用到。
- **现有方案的三类路径及其缺陷**：
  - **上下文压缩类**：摘要（SUPO、ReSum）、观察掩码（Observation Masking）——有损压缩，可能丢弃后续任务所需的精确值、标识符或日志条目。
  - **结构化外部记忆类**：MemGPT、A-MEM、Mem0、Zep、HippoRAG 等——需要嵌入、检索索引、记忆抽取或额外模型，引入额外的组织与检索决策成本。
  - **直接保留全部历史**：ReAct 式做法在窗口填满后即停止，无法扩展到长流。
- **关键洞察**：数字存储成本极低，智能体完全可以保留完整交互历史；近期研究也表明，对原始历史做简单词法搜索可媲美结构化记忆系统。
- **研究问题**：能否用“完整数字记录 + 简单搜索工具”构成有效的智能体记忆，而无需结构化存储或检索索引？即重新审视短期上下文管理与长期记忆之间的边界——“当智能体可以记住一切时，它应该遗忘什么？记住一切究竟需要多少复杂度？”
- **整体含义**：论文主张**无损保存与有损压缩可以互补**——摘要维持紧凑工作上下文，完整日志保证被压缩掉的信息仍可按需召回，从而为长程智能体提供一种简单、透明、可竞争的记忆基线。

## 二、方法论：GrepMem

### 2.1 核心思想

- **双表示分离**：
  - **有界工作上下文**：沿用 SUPO 的摘要循环，上下文接近阈值时生成摘要，从“原始提示 + 摘要”重启推理。
  - **持久历史日志**：仅追加（append-only）的纯文本日志，逐字记录所有用户消息、工具调用、工具输出、摘要与智能体回复，**无损**保留完整交互历史。
- **按需召回**：首次压缩后开放 `grep_history` 工具，用正则表达式在日志中检索，弥补摘要丢失的细节。
- **零额外基础设施**：不需要嵌入、检索索引、记忆抽取或额外模型。

### 2.2 算法流程（Algorithm 1 文字化）

1. 初始化：上下文 `c` 与历史日志均写入系统提示与任务；禁用 grep。
2. 循环（交互预算内）：
   - **上下文压缩**：若 `c` 接近窗口上限，采样生成摘要 `s`，将 `s` 追加到日志，重置 `c` 为“系统提示 + 任务 + 摘要”，并**启用 `grep_history`**。
   - **行动或召回**：从 `c` 采样回复 `a`，追加到 `c` 与日志；若 `a` 含最终答案则返回。
   - **执行工具**：工具输出追加到 `c` 与日志；`grep` 读取日志。
   - 更新交互预算。
3. 预算耗尽后，要求模型在不调用工具的情况下给出最终答案。

### 2.3 `grep_history` 工具细节

- **匹配方式**：大小写不敏感正则表达式，逐行匹配日志文本；跳过此前 grep 输出的记录（避免重复匹配）。
- **输出格式**：按时间顺序返回匹配行，附带所属记录头（如 `[turn 4 tool get_document(...)]`）、记录内行号、前后上下文行（默认 1 行，最多 3 行），并给出总匹配数与分页偏移。
- **规模控制**：默认每页 10 条（最多 30 条），单次响应上限 6K 字符，匹配行两侧各裁剪至 300 字符，单次搜索超 10 秒报错。
- **计数模式**：`count=true` 仅返回匹配行总数，不返回内容，适合“计数类”问题。
- **使用约束**：仅调用 grep 的回复不计入回合预算（每 episode 最多 10 次此类回复），以鼓励检索而不挤占任务交互。

### 2.4 强化学习训练

- **训练目标**：用 GRPO 联合优化任务动作、上下文摘要与记忆检索，三者共享 episode 级奖励，**不对摘要或单次 grep 调用设单独监督**。
- **信用分配**：同一 episode 内所有训练序列（含压缩调用、记忆调用）共享同一 episode 级优势，使 RL 能把信用跨压缩步骤传播。
- **训练数据混合**：70% 单问题 OpenResearcher、15% 三问题 OpenResearcher 会话、15% 合成 ContextBench 风格长流，分别针对研究工具使用、跨问题信息保留、长历史精确查找与计数。
- **奖励**：OpenResearcher 用二元正确性（多问题取平均）；ContextBench 用官方程序化评分器。

## 三、实验设计

### 3.1 对比的上下文管理策略（5 种）

| 策略 | 机制 | 能否扩展超窗 | 是否保留全部 | 是否支持召回 | 是否需索引 |
|---|---|---|---|---|---|
| ReAct | 保留全部，窗口满即停 | ✗ | ✓ | ✗ | ✓ |
| Masking | 旧工具输出替换为占位符 | ✓ | ✗ | ✗ | ✓ |
| SUPO | 摘要后重启 | ✓ | ✗ | ✗ | ✓ |
| MemGPT | 摘要 + 工作记忆 + 可搜索消息历史 + 归档记忆 | ✓ | ✓ | ✓ | ✗ |
| **GrepMem** | 摘要 + grep 原始日志 | ✓ | ✓ | ✓ | ✓ |

- 所有策略用**同一 RL 配方、同一训练数据、同一任务工具、同一 32,768 token 窗口**分别训练 Qwen3.5-9B（thinking 模式）。

### 3.2 评估任务（5 个，覆盖“问题在输入前/后揭示”两类时序）

- **问题在输入前给出（可用问题引导保留与搜索）**：
  - **BCP-Multi**：由 BrowseComp-Plus 的 830 题固定种子打乱为 276 个不相交三元组（828 题），三题同 prompt 给出、共享 60 回合、100K 文档语料，测跨问题发现保留。
  - **AMA-Bench file**：208 条记录轨迹、2496 题，源轨迹作为外部文件通过 `grep_trajectory` 搜索（所有策略均提供该工具），每轨迹 12 题共享 60 回合。
- **问题在输入后给出（无法用问题引导保留）**：
  - **AMA-Bench stream**：189 条轨迹（≤128K tokens）、2268 题，轨迹以约 12K 字符块增量灌入，处理完后在最终状态的独立副本上逐题作答。
  - **ContextBench KV Store**：576 题，6 个长度级别（33K–968K tokens）× 4 随机种子，需精确取值。
  - **ContextBench Log Triage**：480 题，5 个长度级别 × 4 种子，需定位并计数满足条件的日志条目。

### 3.3 指标与评估方式

- **准确率**：BCP-Multi / AMA-Bench 由 `gpt-5.6-sol` 对照参考答案评分；ContextBench 用官方程序化评分器；报告 95% 置信区间（10,000 次配对 bootstrap，反映测试项变异而非训练随机性）。
- **成本**：所有模型调用的 prompt + 生成 token 总量；另报告 wall-clock 时间（Figure 6）。
- **训练中评估**：每 10 步评估一次，采样温度 0.7；每个条目平均 3 个样本（ReAct 为 2 个）。
