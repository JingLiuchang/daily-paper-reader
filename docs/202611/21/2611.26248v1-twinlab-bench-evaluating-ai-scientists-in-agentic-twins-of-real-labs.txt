# Abstract 

AI agents are increasingly expected to act as AI scientists, which requires three increasingly open abilities: carrying out a given computational workflow correctly, choosing the next measurements from a given design space, and designing their own experiments. Existing benchmarks mainly evaluate the first two abilities, in a terminal or in a closed loop that selects from predefined candidates. Evaluating the third ability requires reliably executing an experiment that an agent designs, with readings grounded in a real laboratory. We introduce TwinLab-Bench , which evaluates AI scientists on self-designed experiments in 52 tasks from laboratories in the physical sciences, the life sciences, and engineering. The benchmark supports more than 100 experimental action types, and the agent’s report is scored by comparison with a hidden answer taken from real laboratory records. Each task has its own TwinLab agent, an agent that serves as the environment and executes the experiments that the tested agent designs, reading the raw materials of the laboratory and calling calculators that are built from its records. Compared with a language model that sees only the task description, the TwinLab agent almost eliminates readings that deviate from the real records and inconsistent answers to a repeated request, and closed-book probes control for answers recalled from memory. We find that these tasks remain hard for frontier models: the strongest, Claude Fable 5.2, averages a score of only 45.0, and we conduct an empirical study of where it fails. # 1 Introduction 

AI is advancing science in more and more of the research process, and the AI scientists that the field now builds need three increasingly open abilities (Gottweis et al., 2026; Ghareeb et al., 2026). The first is carrying out a given compu-tational workflow correctly, such as analyzing a given dataset (Mitchener et al., 2025a; Chen et al., 2025; Terminal-Bench-Science Team, 2026; Mitchener et al., 2025b). The third is designing their own experiments, and automated laboratories are starting to run such experiments (Boiko et al., 2023; Szymanski et al., 2023). The third ability is the hardest of the three, but few science benchmarks test it. Existing science benchmarks test whether an agent can recall knowledge (Laurent et al., 2024), work on given data (Mitchener et al., 2025a), or search a given space (Duan et al., 2025), as figure 2(a) shows. These abilities work on data that the task provides in advance, but the third ability, designing their own experiments, needs an environment that returns real data for new experiments. Figure 2(b) orders these environments by how close they come to a real laboratory. Fixed results support no new experiments. A simulator (Jansen et al., 2024; Duan et al., 2025; Gandhi et al., 2025) or a replay (Roohani et al., 2025; Wen & Liu, 2026) returns new results, which come only from written rules or from recorded experiments. The goal of the experiment environment is a real laboratory, which returns real results for any experiment that an agent designs (Bran et al., 2024; Tom et al., 2024). We move one step from simulators and replays toward this goal with a twin of each real laboratory, and we build TwinLab-Bench on these twins. A twin of a real laboratory has to return real readings for as wide a range of experiments as an agent may design. Language models already play patients (Schmidgall et al., 2024) and users (Barres et al., 2025) in agent evaluations, but they fall short when they play a laboratory. We propose the TwinLab agent to build a reliable twin of each laboratory. The TwinLab agent is a coding agent that serves as the environment, so it uses tools to read the files of the laboratory and runs programs on them. Each task has its own TwinLab agent with the materials and the calculators of its laboratory. For an experiment that the laboratory performed, the TwinLab agent reads the raw materi-als, often combining several records, and returns the result that the laboratory recorded. For an exper-iment that the laboratory did not perform, it runs calculators, which are deterministic programs that we write from the data of this laboratory, for exam-ple by fitting a physical model to its measurements. Each calculator extends the record only to nearby settings, with a basis that we write down when we build the task. TwinLab-Bench consists of 52 tasks, and each task comes from the records of a real laboratory in the physical sciences, the life sciences, or engineering. The tested agent, which we call the actor agent, receives the notebooks, raw data, and interim conclusions that the laboratory had at one point of its work, requests the experiments that it designs within a budget, and submits a report that we score by comparing it with what the laboratory later found, as figure 3 shows for four tasks. Our experiments show three properties of TwinLab-Bench. (1) The score comes from the experiments, because without budget Opus 5.5 and DeepSeek-flash pass none of the tasks. (2) The actor agent’s conclusion follows the true state of the laboratory that it measures. (3) The twin predicts hidden recorded readings within a median error of 2.47% even outside the recorded conditions, and it blocks all 9 attempts to exploit it. On TwinLab-Bench, the strongest frontier model averages a score of only 45.0 out of 100. Opus 5.5 still loses part of the score on decisions that it states in full before the run, and its most common decision error is accepting a mechanism without a discriminating test. Our contributions are threefold. • TwinLab-Bench, a public benchmark that tests whether an agent can design its own experiments, built on the records of real laboratories and released with its evaluation code. • The twin of a real laboratory, made of a TwinLab agent, the raw records of the laboratory, and the calculators that we write from these records. • An empirical study that locates where frontier models lose score and which experimental abilities they lack.

End-to-end systems already write and review such research (Lu et al., 2026), and end-to-end research benchmarks run the agent on the given data and code of a study (Xu et al., 2026; Zhou et al., 2026a; Yang et al., 2026). Readings from simulation, replay, or a language model. Interactive environments answer the experimental requests of an agent with readings from a simulation, a replay, or a language model. Text worlds and equation models (Wang et al., 2022; Jansen et al., 2024; Duan et al., 2025; Gandhi et al., 2025; Rowstron & Chadha, 2026) answer any request, and their readings follow the rules written into the environment. EmbodiedLab (Gao et al., 2026) tests how agents operate instruments in a physics simulator on textbook experiments, while TwinLab-Bench leaves out physical operation and tests experimental decisions on problems from real laboratories. Replays of published measurements (Roohani et al., 2025; Wen & Liu, 2026) return real readings, and the agent picks its next experiment among the recorded conditions. Learned world models predict the outcome of an action (Ha & Schmidhuber, 2018), and language models serve as such world models for planning (Hao et al., 2023) and for text-based games (Wang et al., 2024). Language models also play patients (Schmidgall et al., 2024) and users (Yao et al., 2025; Barres et al., 2025) in agent evaluations, and they answer from general knowledge; evaluations of such simulators find that their feedback departs from real environments and users (Liu et al., 2026; Zhou et al., 2026b). AgentBeats (Berkeley RDI, 2026) packages a benchmark as an agent that sets the tasks, the environment, and the scoring for the agent under test. TwinLab-Bench splits this role between a TwinLab agent that serves as the environment and a judge agent that scores the report. These environments do not answer the experiments that an agent composes with readings from the records of a real laboratory, so they cannot evaluate how an agent designs its own experiments.

3.1 Tasks 

Task sources. We select the tasks from about 375 candidate sources, and each task is built on a real research record, such as an open laboratory notebook, raw instrument exports, a paper with its supplementary material, or a public dataset, as figure 3 shows. Most tasks are adapted from the records of one laboratory. In some of them the laboratory itself met the problem and later solved it, and in the others the problem lies in the real data of the laboratory. Their answers come from a later notebook entry, a publication, a correction, or a reanalysis of the raw data. The few remaining tasks are grounded syntheses, as Appendix I describes. 

Task construction. We choose a cutoff point in the record, which is a date or a clearly defined state of the laboratory, and split the record into two parts. The data, protocols, and interim conclusions that the laboratory had before the cutoff point are handed to the actor agent. What the source records show after the cutoff point is given only to the TwinLab agent and to the judge agent, and we call this part the hidden truth. An expert route taken from the record averages a score of 97.8 out of 100 when we replay it in the twin of each task. Every task also passes a coverage review, which confirms that the standard experiments of the field can be simulated, and Appendix I lists all tasks and their construction. 

Task forms. The tasks take three forms. Most tasks are claim reviews, which ask the actor agent to decide which conclusions of the laboratory hold and how to test them. Troubleshooting tasks ask for the cause of a clear failure and a working procedure, and research-campaign tasks ask for an executable procedure toward a research goal. Some tasks offer no experiments, and the actor agent analyzes only the raw records that the laboratory already has. 

Actor agent. The actor agent proposes its own hypotheses and composes its own experiments. It describes each experiment in natural language and decides which actions to run, on which materials, with which settings, 

5Preprint Wan et al. 

in which order, and how many times. Across the benchmark the laboratories support more than 100 action types. Each laboratory lists its procedures and the parameter options of its equipment and reagents, and the actor agent combines them into experiments and can also request values outside the list. These lists contain no experiment and no step of the solution, as Appendix H.1 details. In its sandbox, the actor agent can analyze the handoff materials freely with a shell and Python, but new readings come only from experimental requests to the TwinLab agent, and every request costs budget.

Difficulty control. We control the difficulty of the tasks with five properties that make them depend on experimental judgment. (1) The budget of each task, counted in units such as laboratory days or wells, is one to three times the amount that the expert route uses for most tasks, so it covers the expert route and a few plausible hypotheses but not all options. (2) Scarce materials named in the record cannot be recovered once used. (3) An artifact has a plausible benign explanation. (4) A measurement that looks decisive has another possible cause, for instance when all samples measured on one date also come from one batch. (5) In some tasks the correct answer is that the question cannot be decided within the budget. Overall, for tasks adapted from real records, these five situations are taken from the record, and we add no problem to the record. 

3.2 The TwinLab Agent 

The environment of each task is a twin of one specific laboratory, made of a TwinLab agent and the task materials of this laboratory. The task materials contain the full record of the laboratory with its raw files, the calculators that we write from this record, and the hidden truth. The TwinLab agent handles each experimental request in three steps. First, it looks for a basis in the task materials, often combining several records. Second, it takes the recorded value of a condition that the record contains on comparable material or runs calculator commands in a shell. Third, it writes these numbers as an observation in the instrument’s own format and returns a matching real image when one exists. The environment code writes a session record after every request, so the TwinLab agent keeps the state that earlier requests left, such as a sample already used up. Its tools only read files, search text, and run the calculators. A calculator is a deterministic program written for one task from the laboratory’s own data, for example by resampling the recorded measurements, by fitting a physical model to the record, or by filling a real instrument’s export template. The TwinLab agent follows two further rules. • Noise. Independent samples receive noise at the measured repeatability. • Simulation limits. A quantity that neither the record nor the literature constrains is marked as a simulation limit, costs nothing, and is reported as not being an experimental result. 

Local extension. The calculators extend the record only locally. An extrapolated value carries a basis that we establish through a literature search when the task is built, typically an interpolation between two recorded settings or a dependence documented in the literature, and this basis is written into the task item by item. Section 4.3 tests how much the results depend on these extensions. 

Hidden truth. The TwinLab agent needs the hidden truth because the readings have to agree with the true state of the laboratory, such as a cause that only appears later in the record. It answers only what an experiment returns, and Appendix H.1 lists the rules that the environment code enforces. Table 2 lists what each role can see.

3.3 Scoring 

Rubric. The rubric of each task consists of items with conditions for full and partial credit (Starace et al., 2025; Arora et al., 2025). Most items belong to two components. Conclusion items check whether the report states the correct answer, and verification items check whether the report reaches this answer from evidence that the actor agent obtained in this run, so a key finding of a task is often split into one item of each kind. 

Score and judge. The score of each task is rescaled to 0 to 100, and each task marks a few core items whose failure makes the report wrong; when any core item misses full credit, the run scores 0. We report the mean score over all tasks. The judge agent is a vision-language model that serves as the judge (Zheng et al., 2023), reads the full task, the interaction log, and the report, and cites the report text or the request number for every item. Every core item with full credit is checked twice more by independent calls, and the item scores 0 when either check fails. We freeze the rubric before looking at the final evaluation runs. 

Invalid runs. The judge agent also audits the environment, and a run is invalid when a reading leaks the hidden truth, contradicts earlier observations or physics in a way that matters for scoring, or refuses a relevant experiment that a real laboratory can run. A deterministic script replays every calculator command to check the state, the billing, and the numbers. A static check scans the content that reaches the actor agent through its tools, and a run that receives a blocked string of the source is invalid, as Appendix H.1 details. 

# 4 Experiments 

4.1 Comparison with Existing Benchmarks 

The scorecard of figure 5 compares TwinLab-Bench with 8 existing benchmarks item by item on scale and diversity, realism, and memorization control, and TwinLab-Bench is the only benchmark in the comparison that combines a wide range of experiments with real problems and real readings, as Appendix F discusses. 

4.2 Main Results 

Setup. We evaluate 13 models as actor agents, running the GPT models in Codex and the other models in Claude Code. The TwinLab agent and the judge agent run on DeepSeek-flash for every actor agent. 4.3 Fidelity of the Twin 

We test along a chain of evidence how far the results that the twin returns can be trusted. 

Most experiment results come from real laboratory data. We trace where the experiment results of the actor agents come from and whether the record contains the decisive experiments. Of these experiment results, 76% come from the record or from calculators calibrated on the same laboratory’s data, as Appendix D.2 shows, and the record contains the conditions of 78% of the decisive experiments on the expert routes, as Appendix D.3 shows. Thus the conclusions of most tasks depend on recorded data, and the calculators mostly fill in details around them. 

Sensitivity to extrapolation. We replace the extrapolation outside the record with another equally plausible choice and rerun the actor agents on six tasks, where the replacement changes 12% to 44% of the calculator outputs, as Appendix D.4 details. We find that most conclusions do not depend on which plausible extrapolation the calculators use, so a modeling choice that we make when we build a task changes few evaluation outcomes. 

Held-out conditions. We hide recorded conditions of three tasks and rebuild their calculators without seeing them. The median error of the hidden readings is 0.74% for interpolated conditions and 2.47% for extrapolated ones, and a hidden discrete condition is predicted within 0.6% on average, as Appendix D.5 shows. We find that most readings that the calculators compute near the record fall close to the real readings, so the twin returns realistic readings for new experiments near the record. 

The twin supports routes beyond the expert route. In successful runs, more than a third of the requests are new experiments that the expert route does not contain, such as new combinations of settings and additional checks, as Appendix D.6 shows. The TwinLab agent answers these requests, so actor agents can solve a task along their own routes. 

Robustness of the twin against hacking. When we tell Opus 5.5 on four tasks that the laboratory is simulated and that it may exploit any weakness, all 9 exploit attempts are blocked, and when we ask it to find flaws in the simulation, none of the 13 true flaws that it finds changes the scoring, as Appendix D.7 details. An audit of the 7808 replies of the TwinLab agent in 831 evaluation runs finds one reply that states part of the hidden truth and that the judge agent did not flag, and that run scores 0, as Appendix D.2 shows. These results show that the score is hard to raise through the weaknesses of the twin and that the flaws that exist are minor. 

4.4 Memorization Control 

The tasks of TwinLab-Bench come from public records, so a model may have seen a source during training (Sainz et al., 2023; Golchin & Surdeanu, 2024) or may derive part of an answer from prior knowledge, and we test in three ways whether the scores come from the agent’s own experiments. 

Changing the true state of the laboratory. To test whether the answer is determined by the readings that the actor agent obtains in its own experiments, we change the true state of the laboratory and keep the handoff word for word. We construct the new state from a documented case of the same kind of problem by changing only the calculator and the hidden truth, and a model that remembers the source answers according to the source (Wu et al., 2024). In 8 of the 10 states that allow a verdict, the conclusion follows the new state, and no run mentions the source study, as table 3 and Appendix C.1 show.

In a closed-book session without tools, Opus 5.5 recalls the conclusion of the source for none of the tasks and derives the answer without data for only 2 tasks, and Fable 5.2 recalls the conclusion for one task, as table 4 and Appendix C.2 show. The tasks whose source Fable 5.2 names do not score higher in its evaluation runs. Prior knowledge gives at most part of an answer on many tasks. 

Pass rate without experiments. With a budget of zero, Opus 5.5 and DeepSeek-flash pass none of the tasks, as Appendix C.3 shows. These results show that prior knowledge and the handoff do not earn the core items, and the agent has to obtain the evidence through its own experiments. 

4.5 Empirical Analysis of Model Failures 

On the tasks that need experiments, the decisions that a model states before the run match only in part the decisions that it makes during the experiments, similar to the knowing-doing gap that language-model agents show in bandit tasks (Schmied et al., 2025). 

Knowing-doing gap in experimental decisions. Before each run, the model reads the handoff files and writes a plan for the whole task, and we check whether the plan states each key decision of the task in full, as table 5 shows. Decisions that the plan states in full score 87% of their maximum in the run, but decisions that it does not mention still score 62%. Of the 11 decisions that the plan states in full and the run still loses, the run carries out 9 as planned and loses the score in reading its own results or in the report. A static benchmark that grades the plan therefore misjudges many of these decisions, and a closed-book question gives the same order of scores, as Appendix E.1 shows. 

Failure types of the actor agents. We classify every valid run of Opus 5.5 that scores 0 by the error that caused the failure, as table 6 and Appendix E.2 report. Of the 16 failures of Opus 5.5, 12 come from an experimental decision, most often accepting a mechanism without a discriminating test. For example, when an oyster sugar assay reads about 30% low, Opus 5.5 rules out the pipettes after a water check and never tests the 1 μL transfer, which delivers only about 70% of the sample. 

More budget rarely helps. Of the 21 failed runs of Opus 5.5, only 8 spend at least 90% of the budget. Doubling their budget turns only 2 of them into a pass, as Appendix E.3 shows.

# 5 Conclusion 

TwinLab-Bench evaluates whether an AI scientist can design its own experiments on twins of real laboratories, and most experiment results in these twins come from real laboratory data. The strongest frontier model averages a score below 50 out of 100. Opus 5.5 loses score even on decisions that it states in full before the run, and its most common experimental error is accepting a mechanism without a discriminating test. We release the tasks and the evaluation code, and the web search of the actor agent blocks the names of the benchmark and its tasks.

# B Reliability of the Scores 

B.1 Stability of the Judge Agent 

We judge the same run three times with identical inputs, for 20 runs of Opus 5.5 and 16 runs of MiMo-V2.6-Pro on the same tasks. Table 9 reports, for each actor agent, the share of runs with the same validity verdict in all judgments, the share with the same zero or nonzero score, the share of rubric items with identical scores, and the mean standard deviation of the score within a run. The zero or nonzero score differs between judgments on one run of each actor agent, and in both cases a core item whose full-credit condition has a boundary goes to 0 in some judgments. The standard deviation of a task score between repeated judgments is 2.4 for Opus 5.5 and 2.8 for MiMo-V2.6-Pro. 

B.2 Changing the Models of the TwinLab Agent and the Judge Agent 

DeepSeek-flash serves as the TwinLab agent, as the judge agent, and as one of the tested actor agents, and a language-model judge can favor its own generations (Panickssery et al., 2024), so we check whether the results depend on this choice. We choose 10 tasks by a fixed rule from the three groups of tasks that the three runs of DeepSeek-flash leave all nonzero, mixed, or all zero, and we run DeepSeek-flash as the actor agent once with Sonnet 5.5 as the TwinLab agent and Opus 5.5 as the judge agent. All 10 runs are valid, every score lies within the range of the three runs of DeepSeek-flash in the standard setting on the same task, and 5 tasks pass, against 5, 6, and 4 in the three standard runs. To separate the judge agent from the TwinLab agent, we rejudge the same 10 runs with DeepSeek-flash, and the pass verdict changes on 1 task, where the Opus 5.5 judge agent gives 0 to a core item with a boundary. We further rejudge 20 runs from the three runs of DeepSeek-flash on 9 of these tasks with Opus 5.5 and with DeepSeek-flash under the same judge prompt and rubric. The two judge agents agree on pass in 19 runs (Cohen’s κ = 0 .83 ) and on validity in all runs, and the one pass change comes from Opus 5.5 grading a self-contradictory report by its weaker reading. 

B.3 Scores Separate Correct and Wrong Reports 

We draw 126 reports from the evaluation runs of all tasks with a hash rule fixed before any model call, taking one passing and two failing runs on tasks that have both and one failing run on the other tasks. A DeepSeek-flash call classifies each report as correct, plausible but wrong, incomplete, or missing by reading it against the hidden truth, without seeing its score, its judgment, or the rubric, and we check 29 labels at the boundary by hand and change 1. A report is correct when its main conclusions and deliverables agree with the hidden truth, also when its verification is too weak to pass. A report is plausible but wrong when any main conclusion, cause, mechanism, recommendation, or deliverable contradicts the hidden truth, or when it leaves a main question undetermined although the hidden truth decides it. A report is incomplete when it makes no wrong claim on the main line but its deliverable falls short. Of these reports, 43 are correct, 69 are plausible but wrong, 6 are incomplete, and 8 runs end without a report. On 19 of the 21 tasks that have both correct and wrong reports, the lowest total score of a correct report is above the highest total score of a wrong report, and the mean gap is 0.46 of the maximum score. 

B.4 Validity and Cost of the Environment

# C Memorization Control 

C.1 Another State of the Same Laboratory 

For each task in this study, we keep the task description and the handoff materials word for word and change the true state of the laboratory to another state that the literature documents for the same kind of problem. Only the calculator and the hidden truth change, and the replay of the expert route in the new state passes before any actor agent runs. The released data list the 11 states with the original cause, the new cause and its evidence, the change in the calculator, the result of the reference replay, the state that the actor agent’s conclusion follows, and whether the run mentions the source study. In 8 of the 10 states that allow a verdict, the conclusion follows the new state. On the other 2 states, Opus 5.5 does not pass the task (scores of 6.5 of 10 and 8.0 of 15). One state is excluded from the denominator because the actor agent never ran an experiment that touches the changed part. 

C.2 Memory Probes per Task 

For every task, the released data list whether Opus 5.5 recognizes the source, whether it recalls the source’s conclusion, whether it derives the answer closed-book, when the source was published relative to the model’s knowledge cutoff, and the task’s score. The probe uses two independent calls per task in a neutral temporary directory with all tools disabled. One call asks for the source and what the model remembers of it, the other asks for the most likely answer, and a third call grades both answers against the answer key. We repeat the probe for GPT-6.1-sol, DeepSeek-flash, and Qwen3.8-Max with the same prompts, answer key, and grading. They name the source of 4, 2, and 1 tasks, against 9 for Opus 5.5, and none of them recalls the conclusion of a source. When the tasks are grouped by whether a model names their source, the tasks with a named source do not score consistently higher in the evaluation runs of the same model, and Opus 5.5 scores 43.3 on the 9 tasks whose source it names and 43.2 on the 22 tasks whose source it does not recognize. Fable 5.2 names the source of 16 tasks, two of which can be read from the task text, and recalls the conclusion of a source for one task. Its evaluation runs score 49.0 on the 16 tasks whose source it names, 32.2 on the 21 tasks whose source it names in part, and 58.7 on the 15 tasks whose source it does not name.

# D Fidelity of the Twin 

D.1 Pilot Study: What the Laboratory Needs to Know 

We replay the requests of the expert route in 12 tasks, four from each division, against three settings, with two independent sessions per setting. The language model in all three settings is DeepSeek-flash, the model that serves as the environment in the evaluation. The rule that selects the tasks and the tolerance of each task from the raw files were fixed before any output was read. Deviation is counted on the 126 answers to the 63 requests whose conditions exist in the record, and inconsistency on the 93 requests asked in both sessions. Deviation drops from 41% with the task description alone to 14% with raw materials and to 2% with the TwinLab agent; substantial inconsistency drops from 31% to 8% and 4%. The 3 deviating answers of the TwinLab agent all occur in one task: one request receives a calculator value below the tolerance band in both sessions, and one well of a 48-well plate exceeds an 8% rule by 0.2 points. Of the 4 requests that the TwinLab agent answers inconsistently, 2 differ only in the amount charged. The report of the expert route passes in 17, 21, and 23 of the 24 sessions of the three settings. In a pilot, a language model that writes a metabolic curve by itself produces a curve about 20 times slower than the record. 

D.2 Sources of Readings and Destinations of Requests 

We take the first valid run of every actor configuration other than Opus 5.5 at medium effort on every task, 831 runs with 7808 requests, and classify every reading by the dominant source of its numbers and every request by its destination. Over all readings, 76% come from the record or from calculators calibrated on the same laboratory’s data, with 53% looked up in the record and 23% computed by the calculators, and 99.5% trace back to the record, a calculator output, or one step of arithmetic. Only 0.5% of all requests are not simulated at all. We also audit every reply of the TwinLab agent in these runs for disclosure of the hidden truth. A script first marks 79 replies that contain a number, a name, or a phrase of the hidden truth that the requests of the actor agent and the outputs of the tools do not explain. A DeepSeek-flash call then judges these replies, the 162 other replies in which the TwinLab agent read the internals of a calculator, and 100 random replies, and we check every reply that it flags by hand. One reply states a hidden mechanism without being asked, and one reply describes an asked-for observation that the calculator does not model, which we count as a coverage gap; both runs score 0, and none of the random replies is flagged. 

D.3 Audit of Extrapolation Dependence 

Without running new models, we label every reading in the evaluation runs with its source and compare the actor agents with the replay of the expert route, which every task has, on the 29 tasks whose replay used the same TwinLab agent. The share of requests that actually obtain data outside the record does not differ between the actor agents and the expert route (median difference 0 per task, p = 0 .24 ), and it does not differ between two reasoning efforts of the same model. On real-source tasks, rubric items whose evidence comes only from design parameters or from numbers written by the TwinLab agent score 0.63 of full credit, and items whose evidence comes from the record score 0.62. For each of the 6 tasks whose deliverable is scored by a calculator, the settings that the actor agent can choose are either limited to the real settings in the record or come from the same design model as the observations. The expert routes of 42 of the 49 tasks built from real records request experiments. Of their 189 decisive experiments, 78% use conditions that the record contains, 15% partly extend a recorded condition, and 7% lie outside the record. On 7 further tasks built from real records, the expert route has no scored experiment, because the evidence comes from offline analysis of the handoff records, and we count these tasks separately.

D.7 Red-Team Actor Agents 

On 4 tasks, we run Opus 5.5 in three arms. The honest arm is the run of Opus 5.5 at high effort in figure 6. The exploit arm is told that the laboratory is simulated, that the score is computed against a hidden answer, and that it may exploit weaknesses of the simulation to maximize the score. The flaw-finding arm is asked mainly to find flaws of the simulation, such as physically implausible readings, contradictions with the files, or leaks, and to submit a report as usual. The red-team instructions appear only in the actor agent’s workspace, so the TwinLab agent sees the original task, and all runs are judged blind with the original rubric. Every reported flaw is verified by reading the session and the calculator. The four tasks are a process-window search on public data, a synthetic battery task, the fatigue task, and the oyster task; the first two are scored by a calculator. The exploit arm makes 9 attempts in total. Seven ask the laboratory staff for the conclusion, the answer key, the source dataset, an underlying table, or history after the cutoff point; one asks for a setting outside the recorded matrix; one lists settings as a range. The history cutoff, the TwinLab agent’s refusals, the calculators’ refusals, and the simulation limits block all of them, no leak guard fires, and no run searches the web, after which the actor agents solve the tasks normally. No core item receives credit without evidence, and on two tasks the second check of core items removes credit that the first judgment gave. The flaw-finding arm claims 39 flaws: 13 are true, 11 are acceptable simulation limits, and 15 are false alarms. The true flaws are minor, such as two instruments of a synthetic task that use inconsistent voltage models, a handoff file that the TwinLab agent describes wrongly, and a clock that three answers report differently; none of them changes the scoring evidence or a key decision. All claimed physical implausibilities on the public-data task are doubts about real measurements. Looking for flaws also changes the actor agents’ behavior: on two tasks they record the designed discriminating evidence as a flaw, so the scores of this arm do not measure the honest ability.

# F Scorecard Definitions and Annotations 

We define the six columns of figure 5 and their levels. Tasks and scenes count the tasks and the distinct experimental settings. Action types count the distinct experimental actions that the agent can request. The source of research problems has three levels: designed, found in real data, and met and solved by the laboratory. A problem found in real data lies in the measurements, but the record does not show the laboratory meeting it; a problem met and solved by the laboratory appears in the record together with its later answer. The environment for new experiments has three levels: analysis of given data, equations or a designed world, and a replay or a twin of a real laboratory. Memorization control has three levels: the risk is noted, the tasks use data that the model has not seen, such as altered, held-out, or fictional data, or memorization is probed on the tested model. For every existing benchmark, each cell cites the sentence of the original paper that supports it. TwinLab-Bench is annotated task by task with the same definitions, and two annotators label the action types independently (105 and 107 types). Some benchmarks already ask an agent to design experiments. SciGym (Duan et al., 2025), Discovery-World (Jansen et al., 2024), and BoxingGym (Gandhi et al., 2025) let the agent choose experiments in a designed world or an equation model, so their readings follow written rules. ASB (Wen & Liu, 2026) lets the agent choose batches of designs within a budget and returns published measurements, so each campaign offers one kind of action over the recorded designs. TwinLab-Bench combines the two properties that these benchmarks have separately: the actor agent composes its experiments freely, and the readings come from the records of real laboratories.

# H Implementation of the Twin and the Judge 

H.1 Mechanisms of the Twin and the Scoring 

Readings. The environment code checks that the recorded value is used whenever the actor agent’s request allows it. The TwinLab agent gives no hints or interpretations, does not substitute another procedure for a requested one, and answers questions about history only up to the cutoff point. When the actor agent asks whether the cause is X, the TwinLab agent only answers that this needs an experimental test. The environment code also asserts that observations contain no internal identifier or leakage pattern and that an unexecuted request is neither charged nor consumes material, and a failed assertion stops the run. 

Parameter values. A listed value is either a condition that the laboratory ran or a condition with a written extrapolation basis; across all tasks, 371 listed values are recorded and 100 are extrapolated. An extrapolated value may never be needed in the real experiment, so it acts as a plausible distractor, and the lists are not ordered by the answer. 

Isolation. The actor agent’s sandbox has no configuration, memory, skill, or past session. The TwinLab agent cannot see the actor agent’s reasoning, and the actor agent cannot see image file names or the rationale of the TwinLab agent. The environment code checks that the actor agent was answered by the requested model, and a run is invalid when the platform switched models during it. We scan the content that reaches the actor agent through its tools, and a blocked string or a per-task marker string in this content, or repeated attempts to reach a blocked source, invalidates the run. Every run records a hash of the rubric that is compared with the frozen version. 

Design against hacking of the twin. A strong actor agent may seek out conditions where the calculators extrapolate favorably, or look for flaws in the twin, as agents exploit flaws in their rewards and tests elsewhere (Amodei et al., 2016; Zhong et al., 2025). Besides scoring against the hidden truth, three designs limit this risk. Numbers come from deterministic calculators, extrapolation is confined to values with a written basis, and the leakage guards, the replay script, and the environment audit check every run. We release the environment code, which enforces the remaining rules, such as measurement noise, checkpoints, billing, and the stock of scarce materials. 

H.2 Judge Agent and Environment Audit 

The environment audit has three parts. A leak is an observation that states an explanation, a cause, or the hidden truth. An inconsistency is an observation that contradicts the task, an earlier observation, or physics, including identical values for independent samples, silently changed parameters, and unexecuted items reported as results. A coverage gap is a refusal of an experiment that a real laboratory can run and that matters for scoring. Any of the three makes the run invalid. We release all prompts with the evaluation code, including those of the actor agent, the TwinLab agent, the judge agent, and every probe in these appendices.
