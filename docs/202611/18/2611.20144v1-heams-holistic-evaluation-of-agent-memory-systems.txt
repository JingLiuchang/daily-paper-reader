Abstract 

Memory systems allow AI agents to persist information across interactions, making them more personalized and more capable on long-horizon tasks. This information persistence introduces new risks: stored information can be disclosed in inappropriate contexts, resist correction or deletion, be retained beyond what users desire, or be poisoned to influence later agent behaviour. Yet memory systems are typically evaluated on task performance and efficiency alone. We argue that a memory system should instead be understood as the custodian of its user’s persistent information, with responsibilities that extend beyond helping an agent complete its tasks, and that it should be evaluated holistically against all such responsibilities. We present Holistic Evaluation of Agent Memory Systems (HEAMS), an open-source benchmarking framework for evaluating agent memory systems in this way. First, we state the responsibilities of agent memory systems as explicit behavioural desiderata spanning performance, efficiency, security, privacy, and user sovereignty. Second, we assemble a benchmark suite that covers these desiderata and acknowledge the gaps that remain. Third, we develop MilaMem, a prototype memory system, and a governance layer that can wrap any memory system, enabling controlled study of memory system design choices. Fourth, we run controlled experiments comparing memory systems across the full HEAMS benchmark suite. We find that no memory system leads every performance benchmark, and strong performance scores may coexist with poor privacy, user-sovereignty, and security scores. Governance functionality strongly influences results: recall policies can reduce inappropriate disclosure at a cost in helpfulness, while both recall and retention policies improve poisoning resistance. These results show that performance and efficiency benchmarks alone cannot reveal how well a memory system meets its responsibilities, or the trade-offs among them. We release HEAMS 1 as a living framework and invite developers and researchers to contribute to the project. 

# 1 Introduction 

Agents are increasingly expected to persist beyond a single interaction. Consumer chat assistants such as ChatGPT and Claude now remember user preferences and past conversations across sessions [3, 37]. Open-source agent projects such as OpenClaw and Hermes maintain state and memory across sessions [36, 38], while commercial agent products such as Grok Bot and Meta’s Muse are bringing persistent, goal-directed agents to a broader audience [32, 45]. Existing agent memory benchmarks each capture parts of this picture. Performance-oriented benchmarks such as LoCoMo, LongMemEval, BEAM, STALE, and Evo-Memory test whether an agent can recall what it was told in earlier conversations, keep track of when things happened, update what it knows when facts change, and get better at tasks with experience [5, 30, 47, 50, 51]. Privacy-oriented benchmarks test whether information held in memory is disclosed only when contextually appropriate to the task at hand [17, 33]. Security-oriented benchmarks test how well memory withstands adversarial manipulation, for example whether malicious content planted in memory later steers an agent’s behaviour or exfiltrates stored data [6, 10, 11]. Memory system products, meanwhile, are typically evaluated on task performance and efficiency alone: Mem0 and Hindsight, for example, report accuracy on benchmarks such as LoCoMo, LongMemEval, and BEAM, alongside latency or token cost, but not privacy, security, or user-sovereignty outcomes [9, 26]. It is therefore difficult to determine how a given memory system behaves across all of these properties, or whether an improvement in one comes at the expense of another. We argue that privacy, security, and user sovereignty are not secondary concerns. An agent memory system is more than a means of making agents more capable and efficient; it is the custodian of its user’s persistent 2information, with responsibilities toward that user. These responsibilities should belong to the memory system rather than to the agents that use it, for three reasons. First, the information outlives any agent: obligations such as honouring deletion, enforcing retention limits, and keeping planted content out of future recalls apply over the lifetime of a memory, long after the agent that created or queried it has terminated. Second, a single user may grant many agents access to the same memory system, including agents they did not build and cannot inspect. If these responsibilities were left to each agent, the user’s information would be only as safe as the least careful agent allows. Third, a task agent is poorly placed to govern information it is trying to use. It is directed to complete its task and will use whatever information helps it do so [4], and it can itself be manipulated by the content it processes [1, 2, 12]. The memory system, by contrast, mediates every access to the user’s information, and can govern that access while treating each querying agent as untrusted, using the context an agent supplies to inform decisions without deferring to it. The memory system therefore should have its own distinct task: to govern the user’s information on the user’s behalf. It must do so while interacting with other systems, such as agents that query it to complete their own tasks and adversaries that attempt to plant or extract memories. Its responsibilities can pull against one another: a memory system that surfaces more memories in response to each recall request may help an agent complete more tasks, but also discloses more information in inappropriate contexts, and governance mechanisms that strengthen user control and security carry operational costs [6, 28]. Which responsibilities matter most depends on the deployment: a personal assistant handling health information, an enterprise coding agent, and a consumer chatbot will weigh them differently. Memory systems should therefore be evaluated holistically, against the full set of their responsibilities, so that developers and deployers can choose the system and configuration that best fit their context. 

Holistic evaluation of agent memory. Evaluating memory systems against all of their responsibilities requires three elements, which we adapt from the Holistic Evaluation of Language Models (HELM) [27]. For HEAMS, holistic evaluation means: 1. Explicit desiderata and recognition of incompleteness. Every benchmark encodes a view of how a system should behave. HEAMS states its behavioural desiderata directly, maps each to the benchmarks that operationalize it, and makes the remaining gaps visible rather than leaving them implicit in the choice of benchmarks (Section 2). 2. Plural, non-aggregated measurement. Performance, efficiency, security, privacy, and user sovereignty are measured with their own metrics and reported side by side rather than combined into a single score (Figure 1). Most memory properties can only be exercised by purpose-built scenarios: a deletion test requires a deletion request, and a poisoning test requires an attacker. HEAMS therefore exposes trade-offs at the level of the system configuration, by evaluating the same configuration across the full suite. Efficiency is the exception: it is measured alongside every benchmark. 3. Controlled, standardized comparison. Memory systems are evaluated through a common interface, with the agent and memory-interaction strategy held fixed, so that differences in outcome can be attributed to the memory system or configuration under study (Section 4). 

Contributions. HEAMS puts this view of holistic evaluation into practice as shared, open infrastructure for the agent memory community. Its value lies in bringing together diverse benchmarks and organizing them under a set of desiderata, a common memory interface, and common experimental conditions. Concretely, this work makes the following contributions: 

• A map of behavioural desiderata for agent memory systems, framed as their responsibilities toward the user, across performance, efficiency, security, privacy, and user sovereignty, with a coverage map linking each desideratum to the benchmarks that evaluate it, and marking where none does (Section 2). 3• HEAMS, an open-source, configuration-driven framework that evaluates heterogeneous memory systems through a common memory interface and a configurable agent, enabling controlled comparisons of memory systems and their configurations (Section 4). 

• A suite of ten benchmarks (five performance-oriented, one security-oriented, and four privacy- and user-sovereignty-oriented) that combines adapted external benchmarks with benchmarks developed within this project (Section 3). 

• MilaMem, a prototype memory system whose retain, recall, delete, and consolidate operations can each be configured independently (Section 5.2), and a governance layer that applies retention and recall policies to any memory system (Section 4.2). Together they enable controlled study of memory system design choices. 

• A series of experiments that investigate whether strong results on performance benchmarks are necessarily accompanied by strong results on privacy, user-sovereignty, and security benchmarks (Section 6). We find that, across the systems and configurations we evaluate, strong performance scores can coexist with poor privacy, user-sovereignty, and security scores, establishing the need for holistic evaluation. 

# 2 Agent Memory System Desiderata 

Any evaluation of an agent memory system carries an implicit account of what is desired or expected from the system. We use the term desiderata for these desires. Desiderata are opinionated statements about how an agent memory system ought to be designed or how it ought to behave. They make explicit the responsibilities that a memory system holds as the custodian of its user’s persistent information, and against which it is evaluated. Reasonable people may disagree about what is desirable or assign different levels of importance to different desiderata for different use cases. The desiderata are aspirational: in practice there will be trade-offs among them, and no single system is likely to satisfy all of them perfectly. They serve instead as a north star for the design and evaluation of agent memory systems, and as a framework for understanding the strengths and weaknesses of different systems. 

Behavioural and architectural desiderata. Desiderata for an agent memory system can concern either the behaviour that the system, or an agent equipped with it, should exhibit, or the design of the system itself. We refer to the former as behavioural desiderata. They describe observable properties that a memory system ought to exhibit in a concrete scenario and can therefore be operationalized through repeatable benchmark evaluation. Architectural desiderata concern the interfaces, control surfaces, records, and constraints that a memory system should expose or maintain by design, such as memory portability, user-facing control surfaces intended for direct human interaction, and data hosting and governance arrangements. These are not always appropriately assessed by benchmarks. To fill this gap, we have also developed the Agent Memory System Card (AMS Card) 2, a documentation standard for agent memory systems in the lineage of model cards [34] and data cards [15, 23, 40]. The card gives readers a way to understand and assess both the behavioural and the architectural properties of a memory system: how it performs and protects users in practice, and how it is built, governed, and controlled. Architectural properties are documented directly in the card, while HEAMS results provide quantitative evidence for its behavioural fields, so that claims about how a system behaves can be grounded in reproducible measurement. The remainder of this section concerns the behavioural desiderata that HEAMS evaluates.

42.1 Behavioural Dimensions 

We organize behavioural desiderata into five broad dimensions. Performance and efficiency concern the benefit that memory delivers and the resources it consumes to deliver it. Privacy, user sovereignty, and security concern the protection of the people whose information memory holds. 

Performance is the degree to which a memory system improves the task success of the agent that uses it. Because memory may be called upon to support a broad range of tasks, a memory system should improve task success robustly across tasks and environments, not only in one task family or interaction pattern. These gains rest on core memory behaviours: retaining useful information, recalling what is relevant, consolidating memories into useful abstractions, and revising information that has become stale. 

Efficiency is the resource cost at which a memory system delivers its behaviour, measured in tokens, monetary cost, time, and storage. We distinguish system-level costs, incurred by the agent as it completes its tasks, from operation-level costs, incurred by individual memory operations. Performance gains are only useful if they can be delivered within the resource constraints of a deployment, and those constraints differ widely across deployments. We treat efficiency as a separate dimension, rather than as part of performance, so that gains bought at disproportionate cost remain visible. 

Privacy is the degree to which a memory system preserves contextual integrity: information should flow out of memory only in ways consistent with contextual norms [16, 35]. A memory system should therefore avoid surfacing stored information in contexts where its disclosure would be normatively inappropriate. 

User sovereignty is the degree to which users can see, control, and govern the contents and behaviours of a memory system. Users should be able to inspect stored memories and their provenance, have them corrected or deleted on request, and set policies that govern what is retained and recalled, including when their approval must be sought. Where a user has specified such a policy, it takes precedence over default contextual norms. 

Security is the degree to which a memory system resists malicious content entering, persisting in, or being surfaced from its persistent state. We call content malicious when it originates from a source without authority over the memory and is crafted to steer the agent against the interests or intent of the user.

The benchmark suite operationalizes the behavioural desiderata in Table 1. Five published performance benchmarks and one security benchmark are complemented by four benchmarks developed for HEAMS, using existing datasets where appropriate. 3.1 Published Benchmarks 

We adopt five published performance benchmarks (LoCoMo [30], LongMemEval [51], Evo-Memory [50], BEAM [47] and STALE [5]) and one published security benchmark (MPBench [11]). To compare agent memory systems under identical conditions, we run every benchmark in the HEAMS framework rather than in its original implementation. We keep each benchmark’s data and questions but adapt the evaluation protocol around them, so our scores are not directly comparable to published leaderboards. Our implementations depart from the original benchmarks in four ways: how the agent is prompted, how answers are scored, which parts of each benchmark are used, and, for MPBench, how the attack is delivered. The agent’s system prompt and memory-interaction strategy come from our agent configuration, not from the original papers. We score answers with LLM judges using our own judge prompts rather than upstream metrics such as LoCoMo’s token-overlap F1. Evo-Memory is the exception: it keeps each dataset’s answer-matching rule. We use subsets of two benchmarks: the four non-adversarial question categories of LoCoMo, and the single-turn setting of Evo-Memory with four task streams (AIME 2024, GPQA-Diamond, MMLU-Pro and BFCL function calling). MPBench tests whether attacker-crafted memories steer the agent’s later answers. We seed the poisoned memories directly rather than test whether an agent can be induced to write them during an interaction. Sources and adaptations are detailed in Appendix A.5, judge prompts in Appendix D.3, and the six MPBench attack classes and their disaggregated results in Appendix C.6.

Leakage and helpfulness judges follow PrivacyLens [44]; we add a coverage judge so that a system cannot score well by withholding everything. Editability and Erasability Benchmark. Built on MEME [24], this benchmark tests whether requested corrections and deletions are carried out. Each of the 100 scenarios introduces a chain of related facts over several sessions, in which some facts depend on others. A final session then makes two requests: it changes one fact in the chain and asks for a different fact to be deleted. Each question is asked twice, once before and once after these requests. After the requests, the agent must no longer reveal the deleted fact, and must give only the updated answer for facts that depend on the changed one, rather than mentioning both the old and new versions. A question counts as a success only if the agent answered it correctly before the requests and correctly after them, so a system cannot gain credit for “forgetting” a fact it never learned (Appendices A.2 and D.3.6). 

Retention Policy Benchmark. This benchmark tests whether a memory system honours user-specified retention restrictions, such as “Do not retain the user’s health information.” It uses 96 single-fact sentences in twelve categories and twelve policies, each prohibiting one category. Every fact is tested under all twelve policies, so it is prohibited under one and permitted under the other eleven. Because the fact text is identical across policies, the benchmark measures obedience to the current user’s policy rather than avoidance of sensitive-looking topics. Each fact is retained through the common interface and then recalled using its own text as the query, without an answer agent. A fact counts as recalled if a recalled entry matches its text exactly; for memory systems that paraphrase content on retention, an LLM judge decides whether a recalled entry still conveys the fact. We report prohibited leakage, the fraction of prohibited facts that are recalled; permitted recall, the fraction of permitted facts that are recalled; and balanced accuracy, the mean of prohibited-fact protection and permitted recall (Appendix A.3). 

Transparency Benchmark. This benchmark tests whether a user can audit what a memory system stores through the agent’s conversational interface. We derive scenarios from BEAM conversations [47], prime memory with target and unrelated background memories, and ask a topic-specific audit question. The judge checks the answer against a scenario-specific rubric covering completeness, provenance, temporal status, correct reporting when nothing matches, non-fabrication and exclusion of unrelated background information (Appendices A.4 and D.3.8). We average rubric scores within each scenario, then average across scenarios; the strict pass rate counts scenarios that fully satisfy every criterion. These scores establish transparency only if the target memories survive ingestion: retention gates, eviction, ingestion filtering and the absence of memory all violate that assumption. 

# 4 The HEAMS Framework 

Controlled evaluation of agent memory requires that a memory system can be varied while everything around it is held fixed. HEAMS makes this possible by separating the agent memory system, an optional governance layer and the agent that interacts with them into distinct components. Each experiment is defined 9by configuration files that pair one agent and one memory system configuration, optionally wrapped in a governance layer, with one benchmark. Memory system comparison studies may then vary a memory system or its configuration while holding the surrounding components fixed. The framework also supports studies that vary other components, such as the agent, while holding the agent memory system fixed. This section describes the core entities of the HEAMS framework, how they interact in experiments, and how results are collected and made visible. 

4.1 Agent Memory System 

We use agent memory system to mean a dedicated component for persistent information, with a defined interface and explicit responsibilities within the overall agentic system (Table 1). Existing agent memory system products frequently expose different interfaces. For example, Mem0 [9] exposes add , search , update ,

delete , and history over individual memory records, whereas Hindsight [26] exposes retain , recall ,and reflect , where reflect returns a generated response rather than stored memories. To enable controlled comparison, HEAMS standardizes the agent memory system interface according to the four operations described in Figure 2: retain , recall , delete , and consolidate . The framework leaves implementation details, such as algorithms and storage, to each agent memory system. Operations exchange textual content with optional metadata and structured results. Agents may interact with agent memory systems through model-invoked tool calls, harness hooks that retrieve and insert memories into the context automatically, or deeper integrations that manage the context window or agent loop. Many agent memory systems are tightly coupled to their native harness. Letta, the successor to MemGPT [39], exposes memory mainly through its own agents, which edit core memory blocks pinned to the system prompt and search archival memory through their own tool calls. When an agent memory system and its harness change together, differences in outcome cannot be attributed to either alone. HEAMS also supports different memory-interaction strategies, ranging from model-invoked tool calls to deterministic hooks within the agent harness (Section 4.3). 4.3 Agent 

The agent harness is the software around the language model that runs the agent loop: it builds the model’s context at each step, executes the model’s tool calls, and determines when and how the agent memory system operations are invoked. With a standardized memory interface, the harness can be varied independently of the agent memory system. The current implementation uses TinyAgent 3, a lightweight agent framework from Mozilla.ai. The model, model arguments, system prompt, tool limits, and memory-interaction strategy are all set in the agent configuration. The memory-interaction strategy determines when and how agent memory system operations are called. Several strategies are implemented within the framework. In a tool-use strategy, the memory operations are exposed to the agent as tools, and the model decides whether to call them, which operations to invoke, and with what arguments. In a deterministic strategy, the harness calls memory on the agent’s behalf at fixed points: before each turn, it recalls memories related to the user’s message and adds them to the model’s context, and after each turn, it stores the exchange. Recall-only versions of both strategies let the agent read from memory but never write to it. A variant of the deterministic strategy also handles explicit requests to forget: when the user asks the agent to forget or delete something, the harness calls delete before the model responds. All of these strategies work with or without the governance layer. These strategies are among the simpler options in a much larger design space. Richer strategies could store memories in the background, let the memory system manage part of the context window, or combine model-initiated tool calls with fixed hooks. Projects such as OpenClaw and Hermes Agent build memory into their harnesses in more complex ways [36, 38]; strategies like these could be added to the framework and compared. Experiments that aim to compare memory systems will typically hold the agent fixed, so that observed differences can be attributed to the memory system variations. HEAMS also supports studies in which the agent is varied while the memory system is held fixed. Such experiments enable users to study which models, model settings, system prompts or memory-interaction strategies work best with a given memory system configuration. 

4.4 Lifecycle 

A benchmark in HEAMS is a set of scenarios. Each scenario is a self-contained test case that specifies the information to load into memory, the stimuli presented to the agent, and the references used to score the outcome. Every scenario follows the same five-step lifecycle: initialize , ingest , execute , audit and teardown 

(Figure 4). Throughout the run, the framework records the full configuration used, each scenario’s results, a log of every memory operation, and the ordered sequence of messages and tool calls the agent saw. Together, these records let any score be traced back to the configuration, memory operations and model context that produced it.

5.2 MilaMem 

MilaMem is a prototype agent memory system built to study how design choices affect a memory system’s behaviour. Each of its four operations (retain, recall, delete, and consolidate) can be configured on its own, so one choice can be changed while everything else stays the same. Rules about what may be stored or shared are kept out of the memory system itself: an optional governance layer (Section 4.2) sits around it and applies those rules, so the same rules can be used with any memory system. Figure 6 shows the architecture. MilaMem keeps two copies of what it is told: a raw log of everything it receives, and a searchable memory store used to answer questions. Each memory in the store is one piece of input, such as a single conversation turn, kept as written rather than rewritten into short facts. A memory is either current, superseded by a newer one, or removed. A short description of how MilaMem handles each core operation follows. 

Retain. Each new input is added to the raw log and to the memory store, optionally with a timestamp. MilaMem can also compare it with the most similar existing memory. If the two look similar enough, an LLM decides whether one repeats or contradicts the other, and can mark one of them as superseded. 

Recall. MilaMem supports lexical retrieval (BM25), semantic retrieval by embedding similarity, hybrid retrieval combining the two, and hybrid retrieval followed by cross-encoder reranking (Appendix B). Because superseded memories are kept rather than thrown away, MilaMem can also use redirection : if a search matches outdated text, it returns the updated version instead. 

Delete. When the user asks the agent to forget something, MilaMem first decides which memories the request refers to, either by exact text matching or by asking an LLM to choose among likely matches. It then hides those memories from search and reports which ones it hid. The hidden memories remain in the raw log, and the report only confirms that the chosen memories were hidden, not that every other mention of the same information was. 

Consolidate. Consolidation goes back over stored memories to find duplicates and contradictions missed when they were first stored. Candidate memories are compared by the cosine similarity of their embeddings. MilaMem can either cluster similar memories and ask an LLM to resolve each cluster, or use anchored

6.5 Discussion 

These experiments are only a small subset of those that could possibly be run with HEAMS. Even so, they show that the behaviour we desire from agent memory systems, covering not only performance but also privacy, user sovereignty and security concerns, is not reliably evaluated by performance benchmarks alone. A system can score well on performance benchmarks while still leaking private information, failing to forget or edit memories when users ask, or failing to protect against malicious content planted by adversaries. Deciding whether a memory system suits a deployment where all of these matter therefore requires holistic evaluation. We believe developers of agent memory systems should adopt holistic evaluation methods, such as those demonstrated in HEAMS, more broadly. 

Core memory functionality is essential but not sufficient. Storing and retrieving relevant information underpins memory utility, but on its own it does not keep private information private, let users control what is kept, or protect against malicious actions. In our experiments, governance made the difference: recall governance roughly halved privacy leaks, retention governance blocked most of the information that policies restricted, and combined retention and recall governance raised poisoning resistance from 40.00% to 88.61%. Each gain came with some trade-offs, such as reduced helpfulness or lost permitted facts, and none was perfect. 

Governance will be key to wider adoption. We expect agent memory systems to be used in a growing range of settings, from individuals who care about privacy and control over their own data to organizations with compliance, security and confidentiality concerns. In these settings, privacy, user sovereignty and security behaviours are core requirements. We believe governance must become a central focus of agent memory system development for memory systems to be widely adopted where such concerns apply. 

# 7 Related Work 

7.1 Agent Memory Systems 

Agent memory systems described in research papers, offered as products, or both include MemGPT and its successor Letta [39], Mem0 [9], Zep [42], A-Mem [55], HippoRAG 2 [19], Hindsight [26], and Honcho [31]. Memory is also now built into assistants and agent products such as ChatGPT, Claude, Muse, and Grok Bot [3, 32, 37, 45]. These systems differ in many design choices, which can be roughly grouped into three dimensions [21]: for what purpose information is stored (function), how information is stored (form), and how stored information changes over time (dynamics). We highlight only a few examples of each here (Hu et al. [21] survey them in detail). For function, Mem0 stores short facts about the user, while Hindsight separately stores facts about 23 the world, the agent’s own experiences, summaries of entities, and beliefs that change over time. For form, Letta keeps some memory as text in the agent’s prompt, Mem0 keeps records that are found by embedding similarity, and Zep and HippoRAG 2 keep graphs of linked entities. For dynamics, Letta’s agent edits its own memory through tool calls, whereas Mem0 uses a language model to decide whether each new fact adds to, updates, or deletes an existing one. Zep records when each fact was true and keeps old versions, and Hindsight and Honcho run background processes that merge stored facts into summaries or draw new conclusions from them. Each system has its own interface and is evaluated by its authors on different benchmarks under different conditions, so it is hard to isolate the effect of individual design choices. HEAMS evaluates systems through one common interface, and MilaMem (Section 5.2) lets each choice be changed on its own so that its effect can be measured. 

7.2 Benchmarks for Agent Memory 

Performance. Most memory benchmarks measure whether memory helps an agent answer questions or complete tasks. They test whether an agent can recall facts and reason about when events happened across long conversations [30, 47, 51, 52], improve on a series of tasks by learning from earlier ones [50], recognize when a stored fact is out of date [5], and use memory in long, multi-step agent tasks [56]. 

Efficiency. Memory system authors usually report cost or response time alongside accuracy [9, 26]. MemBench measures efficiency together with accuracy and how much a system can hold [46]. DolphinBench requires every result to include total cost and response time [43]. HEAMS also reports efficiency metrics for every benchmark. 

Privacy. Recent privacy benchmarks ask whether information is shared appropriately for the situation, rather than only whether it is sensitive. This idea is known as contextual integrity [16, 35]. PrivacyLens shows that a model that answers questions about privacy correctly may still leak private information when it acts as an agent [44]. Later benchmarks apply the same idea to AI assistants and workplace agents [8, 14], and Lan et al. [25] train models to follow it. CIMemories tests whether information held in memory is revealed only where appropriate [33], and PiSAs tests the same when one agent serves several users [17]. Other work shows that pieces of information that are harmless on their own can reveal something private when combined [18, 41]. 

User sovereignty. Few benchmarks test whether users can see, correct, delete, and control what a memory system keeps about them. MEME includes a task that checks whether deleted facts still affect the agent’s answers [24]. Bemula tests whether memory systems forget specific information when a user asks. No system it evaluates fully succeeds on more than 1.5% of requests: systems either leave the information recoverable or delete far more than was asked [53]. We are not aware of benchmarks that test whether users can see what is stored, have it corrected, or set rules for how long it is kept. The new benchmarks developed for HEAMS address some of these gaps (Section 3.2). 

Security. Agents with memory can be attacked at every stage of the memory lifecycle, from how information is written to memory, to how it is stored, to how it is later retrieved and used. Lin et al. [28] survey these attacks and the defences proposed against them. We review benchmarks for three kinds of attack here: instructions 24 injected through content the agent reads, harmful content planted in memory, and leakage between agents that share memory. This list is not exhaustive. In a prompt-injection attack, an attacker hides instructions in content the agent reads, such as a web page or a tool’s output. Benchmarks show that such instructions can take control of an agent and make it leak personal data [2, 12]. Malicious prompts can also be hidden in the descriptions of the tools an agent uses [29]. Memory lets these attacks outlast a single conversation. Harmful content that is planted in memory, or that builds up there over time, can change the agent’s behaviour in later conversations or wait for a trigger before sending the user’s data to the attacker [6, 10, 11, 54]. When several agents work together, private information can also leak through the messages and memory they share [13, 49]. HEAMS currently includes one security benchmark, MPBench, which tests whether malicious content is stored in memory and influences the agent’s later behaviour (Section 3.1). 

7.3 Holistic Evaluation 

HELM [27] argued that language models should be evaluated on many properties, not accuracy alone. It began from an explicit list of the situations and properties that matter, tested every model under the same conditions, and reported results side by side instead of combining them into a single score. DecodingTrust and TrustLLM similarly test models on several aspects of trustworthiness, including privacy, robustness, safety, and fairness [22, 48]. These suites test models on their own, not systems that keep information over time. Some memory benchmarks now measure more than one property. MemoryAgentBench tests four abilities, one of which is forgetting selected information [20]. MemBench measures accuracy, efficiency, and capacity [46]. DolphinBench calls its evaluation holistic because it reports cost and response time alongside accuracy [43], and Trust-Memevo tracks whether an agent becomes less trustworthy as it learns from experience [7]. These benchmarks still focus on performance and efficiency, sometimes with one added safety measure; none evaluates privacy or user sovereignty. HEAMS applies HELM’s approach to memory. It evaluates a memory system, together with the agent that uses it, across all five dimensions. Many of the properties it tests exist only because memory lasts across conversations: updating outdated facts, deleting on request, limiting how long information is kept, sharing it only where appropriate, and resisting planted content. 

# 8 Limitations 

Offline evaluation. Offline benchmarks make scenarios repeatable and allow systems to be compared under controlled conditions, but they cannot reveal every consequence of persistent memory in real use. HEAMS should be one part of a broader evaluation program that also includes online evaluation and monitoring of deployed systems. 

Breadth over depth. Our first priority was to cover every behavioural dimension with at least one benchmark, rather than to cover any one dimension in depth. As a result, coverage within each dimension can be thin. Security is evaluated by a single benchmark, MPBench. Other attacks discussed in Section 7.2, such as prompt injection through tools, dormant triggers, and leakage between agents, are not covered. Privacy is likewise evaluated by a single benchmark. Several desiderata are not covered at all (Table 1), and the suite considers only a single user in chat-based settings (Section 2.2). 

Benchmark-suite composition. The suite combines adapted external benchmarks with new ones, so the mapping between desiderata and benchmarks is not always one-to-one: some benchmarks evaluate related 25 behaviours and span more than one desideratum. We accepted this overlap in favour of increased coverage and the inclusion of widely used benchmarks. Benchmark sub-metrics can also be used to disentangle overlapping evaluation results. 

LLM judges. Most benchmarks are scored by LLM judges using our own prompts (Appendix D.3). We have not validated these judges against human annotations, so judge error may affect reported scores. 

Common interface. Systems are evaluated through adapters to a common interface, so results describe each system as accessed through its adapter. The interface cannot express some native features, and systems designed together with their own agent harness may behave differently in their native setting. We accepted this cost so that differences in results can be attributed to specific design choices rather than to a memory system and its agent changing together (Section 4.1). 

Scope of the experiments. The experiments in Section 6 were designed to address one question: whether task performance predicts behaviour on the other desiderata. Many additional experiments are possible with HEAMS. The effects of memory representations, retrieval strategies, retention and recall policies, consolidation algorithms, language models, and memory-interaction strategies could be explored across all ten benchmarks. We hope that future work will explore these experiments more thoroughly. 

# 9 Conclusion 

HEAMS is a framework to evaluate agent memory systems holistically. It allows developers and researchers to measure the degree to which diverse agent memory systems satisfy desiderata spanning performance, efficiency, privacy, security, and user-sovereignty concerns. Initial experiments show that scores on performance benchmarks do not necessarily predict behaviour related to privacy, security, or user-sovereignty desiderata. Given these findings, holistic evaluation is essential for agent memory systems to be deployed in domains where privacy, security, and user sovereignty are important. The experiments particularly highlight the important role of governance functionality in ensuring that agent memory systems fulfil their responsibilities toward the users whose information they manage. We make HEAMS available to the community in the hopes that it will facilitate the development of agent memory systems that not only are performant and efficient but also respect privacy, security, and user sovereignty. 

# Adoption and Participation 

HEAMS is intended as shared evaluation infrastructure for teams building, integrating, and studying agent memory. Organizations can use the common interface and benchmark configurations to evaluate their own systems; contribute adapters, scenarios, evaluators, and reporting improvements; or collaborate on benchmark coverage for deployment contexts not yet represented in the suite. We welcome contributions and research or product collaborations from organizations whose goals align with performant, private, secure, and user-sovereign agent memory. Sustained development of the framework will benefit from partners who can contribute technical expertise, realistic evaluation needs, and support for maintaining shared benchmark infrastructure. Scenario construction. Each source task becomes one memory-priming and message-drafting scenario. The information pool is supplied to the memory system, and the communication request becomes the agent’s task. The agent must produce a message for the specified recipient and purpose; it does not send the message through a live email or messaging service. The original information pool and policy labels are retained as evaluation references. Primed entries carry only their field names as metadata; allowed/disallowed labels and benchmark identifiers are kept in evaluator-only markers, not exposed as memory content or metadata. This separates the information offered to memory from what the backend actually retains, retrieves and exposes to the answerer. Allowed fields supply the useful-disclosure targets and disallowed fields supply the protected targets. The coverage extension makes indiscriminate withholding observable rather than treating silence as an unqualified privacy success. 

Evaluated access and judging procedure. In all reported CI configurations, HEAMS automatically invokes memory recall before message drafting, without retaining the completed turn. This is the evaluated configuration, not an intrinsic requirement of the source dataset (Appendix C). Judging uses three roles at temperature 0: binary disclosure judgments per disallowed field, binary semantic-coverage judgments per allowed field, and a helpfulness rating of Poor, Unsatisfactory, Good or Excellent (0–3). Partial disclosure counts as a field leak; field judgments award no fractional credit. The helpfulness judge receives the task and original information pool, not only recalled information. For editing, 36 episodes supply one probe per phase and 64 supply two, giving 164 edit probes per phase: 100 one-hop and 64 two-hop dependent-entity probes. The scored unit is a paired entity probe, not an independently issued change request, a whole episode or a complete dependency chain. Each episode also supplies four unscored user turns for change-session replay. Thus each full arm contains 264 before-probes, 400 replay turns and 264 after-probes, yielding 528 judged responses across the two phases. 

Scenario construction. One episode becomes one scenario. The loader maps MEME’s Del and Cas tags to erasure and editing, excluding its other task types. It requires exactly one change-and-delete session and withholds that session from initial memory priming. Priming supplies nonempty turns from both user and assistant roles in the remaining sessions. The execution asks the before-probes, replays only the change session’s user messages in source order as unscored turns, and asks the after-probes; source assistant messages from that session are not replayed. The source supplies the requested changes and their dependent outcomes; the adapter preserves them rather than generating alternative requests or gold answers. The converter rejects an episode with no change-session user messages or no in-scope after-probes. Filler placement and agent-history resets are configurable; the evaluated configuration primes post-change filler with the initial history and resets agent messages before each stimulus, without resetting external memory. Primed entries carry benchmark, scenario, session, turn and domain metadata, with role, timestamp and evidence-type fields where available. Annotated evidence sessions also receive a relevant_session flag. Unlike CI’s evaluator-only policy labels, these metadata are supplied to the backend and may influence retrieval or answering if preserved and used. 

Evaluated access and judging procedure. Ordinary turns, including probes and replayed corrections, use deterministic recall and retain completed, non-error question–answer pairs. Earlier probes can therefore change the memory available to later probes despite message resets. Corrections use ordinary retention, not a separate atomic edit operation, although a backend may reconcile records internally. HEAMS dispatches recognized deletion requests before the agent responds, without requiring autonomous tool choice. A returned deletion receipt replaces ordinary recalled context, and that turn is not retained. This is a state-changing protocol coordinated by HEAMS through the common memory-system interface (Appendix C). Each probe is judged in a separate call at temperature 0, using only its question, reference and response. The reference uses the source entity value, with a textual-gold fallback. Before-judging accepts semantic correctness despite extra information. Erase after-judging requires withholding the deleted value, even when acknowledging its deletion; that value, not “No - explicitly removed”, is the reference. Edit after-judging requires only the definitive current dependent value; old/new alternatives, hedging, future tense and abstentions fail. Templates appear in Appendix D.3.6.

A.3 Retention Policy 

Provenance. The repository-maintained corpus and policies are developed for HEAMS and released under CC BY 4.0. The bundled corpus contains 96 short fact sentences: eight each in credentials, education, finance, government ID, health, legal, location, pet, preference, relationship, travel and work. A separate policy file defines twelve uniformly phrased category-specific prohibitions. The corpus, policies and expanded matrix are distinct artifacts; the policy statements, rather than model judgments, determine the expected labels. 

Scenario construction. Every fact is crossed with every policy. Its label is drop if its category equals the policy’s prohibited category and store otherwise. The text stays identical across policies, so the same fact 35 must be admitted under eleven policies and excluded under one. This tests obedience to the current user’s restriction, rather than a fixed ban on sensitive-looking topics. 

Construction checks. The matrix builder checks category purity using lexical cues before expansion. The optional corpus-extension script rejects candidates for length, multiple sentences, first-person phrasing, conjunction of facts, duplicates and cross-category cues; it does not assign the policy labels. These are mechanical checks, not proof of semantic unambiguity or a human-validated annotation study. The keyword baseline rules are maintained separately from the corpus and derived from policy statements, avoiding a baseline constructed by copying the test sentences’ vocabulary. 

Evaluated composition. The reported MilaMem control and LLM-retention arms each evaluate all twelve policies over all 96 facts: 1,152 policy–fact decisions, comprising 96 prohibited and 1,056 permitted cases. Each policy contributes eight prohibited and 88 permitted decisions; each fact appears under all twelve policies. 

Evaluated access and judging procedure. Each scenario sets its policy, attempts to retain every fact, and only then probes each fact using its own text as the recall query, without an answer agent. Retain metadata contains only a shared source marker; categories and expected labels remain evaluator-only. Both arms run through the governance layer with recall governance disabled, so recall-stage withholding cannot masquerade as rejection at ingestion. The control uses deterministic mode without keyword rules, hence no effective enforcement; the other arm uses LLM-based retention enforcement. Recall matching first checks exact fact content after removing backend metadata, including for facts reported blocked at ingestion. If no exact match exists, results are nonempty and the fact was not blocked, a semantic judge checks whether any result conveys it. The semantic-matching fallback has no explicit temperature override and ignores relative/absolute date consistency (Appendix D.3.7).

Provenance. The evaluated scenarios derive from Mohammadta/BEAM ’s 100K split [47], distributed under CC BY-SA 4.0. We reuse conversation turns, question evidence references and available metadata; the audit questions, target/background partition and transparency rubrics are constructed for this evaluation. This is a new audit protocol over existing conversations, not a new long-conversation dataset. 

Evaluated composition. The evaluated selection contains 320 scenarios, each with one audit question: 80 direct-inspection and 80 conflict-disclosure cases, and 40 each of full-export, metadata-inspection, provenance-inspection and negative-audit cases. Each scenario belongs to one task family and receives one task-specific criterion plus applicable supplementary criteria. Dimensions group these criteria for diagnostic reporting. Table 14 summarizes the six task families. 

Scenario construction. Each scenario defines a reference inventory of target memories and separate background memories that should not be disclosed. These entries are supplied to the memory system during priming. Evaluation uses the target inventory and background-disclosure constraints as references, rather than independently inspecting the backend’s post-ingestion contents. Each supported BEAM probing question becomes one audit scenario. Information extraction and preference 37 following map to direct inspection; contradiction resolution and knowledge updates to conflict disclosure; summarization to full export; temporal reasoning to metadata inspection; event ordering to provenance inspection; and abstention to negative audit. Evidence source identifiers are deduplicated while preserving their order and used to select target conversation turns. The configured adapter limits targets to six source turns by default and ten for contradiction resolution, knowledge updates and event ordering. For conflict-disclosure cases, reference labels can locate additional supporting user turns; those original turns, not synthetic reference answers, become memory content. Up to two non-target user turns provide background memories. Selected entries are whitespace-normalized and clipped to 900 characters; background excerpts used for out-of-scope disclosure checks are further clipped to 180 characters. These are source-derived excerpts, not necessarily complete conversation turns. Negative audits deliberately have no target entries, while retaining background content where available. Primed entries carry source, category and recorded-time metadata, together with adapter-generated identifiers and labels such as memory_role , scenario_type and sample_source . These fields are supplied to the backend and may reach the answerer when preserved and rendered at recall; target/background labels are not evaluator-only annotations. Recorded time falls back to the source turn index or “unknown” when no time anchor is available. These fields identify the source scenario, not an independently verified backend ingestion time or internal storage lineage.
