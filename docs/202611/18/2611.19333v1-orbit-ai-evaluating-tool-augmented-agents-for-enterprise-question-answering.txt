ABSTRACT 

Enterprise information is commonly stored across multiple platforms rather than in one centralized lo-cation. Answering questions about workplace activities may require information from several sources, including project documents, task management systems, and team conversations. Conventional AI-based question-answering systems mainly focus on retrieving information from a single source, which also limits their ability to answer questions that depend on multiple sources. Therefore, we evaluate Orbit AI, a tool-based retrieval-augmented generation (RAG) system that uses a ReAct agent implemented with LangGraph to retrieve and combine information from three different workspace sources. The evaluation uses a deterministic benchmark of 100 questions based on a synthetic enterprise workspace. We compare three configurations: (1) a standalone LLM without retrieval, (2) document-based RAG, and (3) a multi-tool agent with access to all three sources.. The held out evaluation set contains 80 questions designed for Phase 3 workspace; Gem-ini 3.5 Flash Lite achieves an accuracy of 86.25% with complete agent. Document only RAG achieves 60.00 % (26.25 pp higher), and the plain LLM achieves 23.13 %. This gap is even larger for multi source questions, as the full agent answers 84.38%, while document only RAG answers 40.63%, a 43.75 pp increase. This is a successful outcome of the retrieval from all three workspace choices, where an answer is dependent on information spread over all three choices. The evaluated Llama 3.2 configuration with local inference achieves 5.50% overall correctness under rubric v2.2. The Llama 3.2 full agent configuration achieves a held out accuracy of 52.50%, which is 1.88 pp higher than the accuracy of document only RAG. The gain of Gemini is equivalent to 26.25 pp. The comparison must be taken with a pinch of salt, because Gemini was accessed via an API hosted by them, while Llama was run locally via Ollama and the models are of different size. It is therefore not possible to isolate out the cause of the performance gaps in this experiment. We present results for both evaluation and report on two full-agent responses from Gemini which were scored post-hoc. The paper also addresses the constraints of the evaluation such as the small artificial workspace and the similarity of the Q53 problem to a problem in the system prompt.

Given these developments in intelligent and distributed systems, we present in this paper Orbit AI, a multi-tool question answering system for retrieving and combining information from multiple sources in an enterprise workspace. LangGraph [62] was used to implement the system, which is a ReAct-based agent with access to three tools, 

search_workspace_tool for vector-similarity search over embedded documents, get_tasks_tool for SQL-based task lookup, and get_recent_chat_tool for retrieving recent chat messages. We evaluate each model on three settings: a standalone LLM, document-only retrieval augmented generation (RAG), and a full multi-tool agent. This evaluation examines the effect of having access to multiple sources of information and tools on the performance of answering questions, in comparison to document-based and standalone approaches.

1. Does a full multi tool agent access improves factual correctness over document only RAG on a workspace benchmark, particularly for multi source questions? 2. Does a smaller LLM derive same benefit from tool augmentation as a larger hosted model under the same benchmark? 3. What are the primary failure modes of each configuration? 

Primary Contribution. This work provides a deterministic benchmark consisting of 100 questions, which are assessed in a synthetic Phase 3 workspace with 3 documents, 16 tasks, and 16 chat messages. 2 Background and Related Work 

2.1 Retrieval-Augmented Generation 

Retrieved passages are used to bound the responses in RAG [1] for the purpose to minimize hallucinations on knowledge intensive tasks. In production, embedding similarity [65] is widely used. In recent surveys [2], RAG methods are categorized based on various factors, including retrieval granularity, query routing, and result fusion. In this study, we use the rag_docs_only configuration, which fetches the top-2 chunks from a pgvector store [66] and appends them to the system prompt. 

2.2 Labeling Tool Augmented and Agentic LLMs 

The model, Toolformer [3] showed that it can learn to use external APIs when generating. ReAct [4] introduces the combination of reasoning and using tools in an iterative manner and LangGraph [62] introduces a statefull agent graph 2OrbitAI : Evaluating Tool-Augmented Agents for Enterprise Question Answering A P REPRINT 

API for runtime whose agents can revisit previous steps. The full_agent setup uses a LangGraph based ReAct agent that can access all the three workspace sources. Also the tools it uses depends on the user’s query. 

2.3 Enterprise Question Answering 

Enterprise question answering involves challenges which are not commonly found in the open domain QA.Information may be spread across different sources, and the system must respect the privacy and restrictions while avoiding the answer that cannot be supported by available evidence in the knowledge base [67, 68]. In conventional RAG system , retrieval mainly focus on documents , leaving structured information from project management tool , and calendars which are outside the usual retrieval process.Orbit addresses this limitation by providing separate tools for accessing these sources, allowing the agent to retrieve the information needed to answer a query. 

2.4 Deterministic Evaluation 

Although flexible, LLM-as-judge evaluation [69] can be hard to interpret and can be prone to some bias. Instead, a rubric of a deterministic nature using a keyword match approach to evaluation (Section 4.3) is used. This decision constrains the range of semantically similar answers the scorer can identify, simplifies the scoring process and also enhances the process [70] 

3 System Architecture 

Figure 1 shows the main request flow in Orbit AI. The FastAPI backend receives a user query and directs it to one of the three evaluation configurations. In the full agent configuration, a LangGraph ReAct loop can call the three workspace tools. Whenever a configuration uses document retrieval, the top-2 retrieved chunks are inserted before model execution. 

3.1 Document Chunking 

The chunker ( backend/app/rag/chunker.py ) chunks the documents in a window of 1,000 words and an overlap of 50 words . Each of the three Phase 3 documents has only a few words (111, 108, and 120) and thus represents a single chunk. As a result, the benchmark provides limited evidence of retrieval of multiple chunks (or multiple larger documents) as well as of any precision over a large document collection. In the case of document enabled configurations, vector search will take the most similar top-2 chunks and add them to the system prompt.

4.3 Scoring Methodology 

A deterministic, keyword and regex based scoring system (Rubric v2.2 deterministic audited) is used. In the case of an answerable question, the scorer verifies the expected target values, the required concepts and absence of known forbidden values. If there are no contradictions, at least half of the required concepts are matched and all target-value groups are matched, a response earns 1.0. A response is awarded 0.5 if it matches at least half of the groups of values in the target, but not all. Also included are responses that match at least half of the groups of values in the target with only one contradiction in a partial match. A response will earn 0.0 if it does not contain the required information or if it contains information that contradicts the rubric’s conditions of incorrectness. If no target value has been given for the question, the scorer has as a last resort, the token overlap with the reference answer. If a question is not answerable, a response is considered to be correct with 1.0 if it contains a refusal signal or a required refusal concept, but does not assert a forbidden fabricated value. It is set to 0.0 if it does not accept that it is missing information, or claims an impossible made-up number. The scorer is not a full-fledged semantic evaluator; it relies on pre-determined lexical patterns, synonym normalization and contradiction checks. 

Faithfulness indicates whether the answer is based on the information for the model. Different configurations have different evaluation populations. In the case of plain_llm , faithfulness is computed using the 20 questions that do not have a correct answer, as there is no workspace retrieval evidence in this setting. For rag_docs_only and full_agent ,faithfulness is measured on all 100 questions, based on the evidence that is retrieved or provided to the model. When a question cannot be answered, a response is faithful if it admits that there is not enough evidence in the workspace to answer the question, but does not include any forbidden fabricated facts. When answers are required, the assessment determines if the target facts are supported by the evidence retrieved. Responses with no evaluable evidence or with execution errors are not included in the average for faithfulness. The scores for different configurations therefore cannot be directly compared and should not be interpreted as the same. 5OrbitAI : Evaluating Tool-Augmented Agents for Enterprise Question Answering A P REPRINT 

5 Experimental Setup 

5.1 Models 

• Gemini 3.5 Flash Lite [6]: Evaluated using the hosted Google Gemini API. • Llama 3.2 (3.2B) [7]: Evaluated locally using Ollama. 

5.2 Configurations 

The three configurations differ in the resources made available to the model: • plain_llm: The model has no access to workspace retrieval tools and generates responses using only its pretrained knowledge. • rag_docs_only: Similarity search retrieves the top two document chunks and adds them to the model context. The model has no access to task records or chat history. • full_agent: The model receives the same initial document context and can use a LangGraph ReAct agent to retrieve additional information from documents, task records, and recent chat messages. 

5.3 Infrastructure 

• Backend: FastAPI (Python), PostgreSQL, and Supabase with pgvector. • Gemini inference: Hosted Google Gemini API. • Llama inference: Local Ollama deployment. • Benchmark size: 100 questions evaluated across three configurations for each model, resulting in 300 evaluation attempts per model. • Experimental repetitions: Each question/configuration combination was evaluated once. 

5.4 System Prompt Proximity 

The complete agent system prompt includes an example of when the agent should invoke get_tasks_tool : " Priya’s document export task due date ". The task deadline specified in Q53 refers to the deadline of the document export feature and is assigned to Priya. The similarity between the sample and the question may lead to a possible prompt priming effect. We did not test a modified version of the original prompt and this is therefore treated as a limitation in Section 7. The answer to Q53 also depends on the release-candidate date which is therefore needed in order to answer the question.

6.7 Faithfulness 

Correctness and faithfulness measure different aspects of model performance. Correctness measures whether the response contains the expected benchmark answer according to the deterministic scoring rubric. Faithfulness measures whether the factual claims made by the model are supported by the evidence actually available to it. A response may be faithful but incorrect if it provides only partially supported information or appropriately acknowledges missing evidence without answering an answerable question. Conversely, a response may contain expected answer values while also introducing unsupported claims. The faithfulness evaluation is a deterministic evidence-consistency proxy based on retrieved evidence, expected target values, and predefined forbidden values. It is not a comprehensive semantic assessment of every factual statement in a response. Furthermore, the number and type of responses included in the faithfulness calculation vary by configuration. As a result, the values in Table 7 should not be compared directly across all configurations.

7.1 Multi-Surface Tool Access Substantially Improves Gemini Performance 

The results for multi source questions Q53–Q84 ( n = 32 ) show a clear difference between the three Gemini config-urations. The full-agent setup achieves 84.38% correctness, compared with 40.63% for document-only RAG. This corresponds to a gain of 43.75 pp, whereas the plain LLM does not answer any of these questions correctly (0.00%). One reason for this difference is that several questions require information from more than one part of the workspace. Q53 is a useful example. The Release Plan provides the release candidate date, but the feature owner’s due date is recorded separately in the task tracker. Document-only RAG can retrieve the first detail but misses the task deadline, earning 0.5. The full agent, on the other hand, accesses both sources through get_tasks_tool and

7.2 Observed Llama 3.2 Behavior Under Tool Access 

Llama 3.2 (3.2B, running locally through Ollama) shows a much smaller improvement from tool access. Under rubric v2.2-deterministic-audited, its gain over document-only RAG on the held-out set is 1.88 pp. For comparison, Gemini achieves a gain of 26.25 pp under the same evaluation. These results alone do not explain why the two models perform differently. The comparison involves two particular model configurations, rather than an experiment designed to isolate the effects of model size or architecture. There are also differences in their execution setups that may have affected the outcome: • Model configuration: Gemini 3.5 Flash Lite was accessed through its hosted API, while Llama 3.2 (3.2B) was run locally using Ollama. Since the two models were evaluated in different configurations, the experiment cannot isolate the effect of model scale. • Inference environment: The inference environments were also different. Gemini used a cloud API, whereas Llama ran locally through Ollama. The GPU specifications of the local machine were not recorded, which prevents us from assessing the possible effect of hardware on the results. • Context window: The Llama configuration had an 8,192-token limit. The difference in available context capacity may have influenced the results. • Tool-use capabilities: The models may differ in how they were trained to select and interact with external tools. These differences could affect their ability to identify and use the appropriate workspace tools, but the present experiment does not examine this factor independently. For these reasons, the observed gap should not be attributed exclusively to model size, architecture, or tool-use training. Separating the effects of these factors would require further experiments with controlled evaluation conditions.

The raw responses also reveal cases where the models provide details that cannot be supported by the available workspace information. Some examples are particularly noticeable: • Q85: Llama rag_docs_only introduces November 16, 2026, as the mobile app release date. Its response states, “The target production launch date is 16 November 2026,” applying a date incorrectly to a question about a mobile app. The full-agent configuration avoids this unsupported answer and responds, “Unfortunately, I don’t have information on upcoming releases of a specific Orbit mobile app version.” • Q93: The name “Omar” is introduced as the on-call engineer in the Llama full_agent response, despite the absence of supporting information. Llama rag_docs_only correctly identifies that the documents do not contain this information. The plain LLM also abstains, although this response is not counted as correct under rubric v2.2. • Q99: In the full-agent configuration, Llama invents an approval record: “The final press release wording was approved by Omar on 15 November 2026, at 10:00 AM UTC.” The plain LLM abstains, but its response is not credited as correct under rubric v2.2. The document-only configuration produces a different unsupported answer by referring to a “Release Manager” without identifying a name or date. This is classified as a mixed response and retains a score of 0.0. • Q91 and Q92: Both Llama rag_docs_only and full_agent provide specific dates for security incidents and EU regulation timelines that are not documented in the workspace. These cases are genuine hallucinations and are separate from the natural-language extractions corrected under v2.2-deterministic-audited. 

7.5 Gemini Scoring Correction 

The v2.2 correction affected the reported Gemini full-agent scores. On the complete dataset, the score changed from 72.50% to 74.50%. For the held-out cohort, it increased from 83.75% to 86.25%. The corrected figures are used throughout this paper, while the original v2.1 results have been retained in scored_phase3_benchmark_gemini_3 5_lite_20261025_165427.json .

8 Conclusion 

This study evaluated Orbit AI, a tool-augmented RAG system designed to answer questions by retrieving information from different enterprise workspace resources. Its performance was assessed using a benchmark of 100 questions and a deterministic scoring procedure. 

Primary findings from the held-out cohort (Q21–Q100): 

• In the full-agent configuration, Gemini 3.5 Flash Lite achieved 86.25% overall correctness and 84.38% on multi-source questions. On the same multi-source questions, document-only RAG achieved 40.63%. The resulting difference of 43.75 percentage points indicates the value of accessing multiple workspace resources when answering questions that combine information from documents, task records, and chat messages. • Llama 3.2 (3.2B), evaluated locally, recorded 52.50% overall correctness on the held-out cohort. Its im-provement over document-only RAG was considerably smaller, at 1.88 percentage points. This difference should be interpreted with care, since the two model setups also used different inference environments and context-window limits. • All 300 benchmark attempts completed successfully for both models, giving an execution success rate of 100%. Nevertheless, successful execution alone does not establish the correctness of a generated answer. 

Findings related to the evaluation method:

• Under rubric v2.2-deterministic-audited, Llama 3.2 achieves 5.50% overall correctness. One limitation of the scoring procedure is that its deterministic refusal detector may fail to identify some valid abstentions expressed in natural language. • Two Gemini responses from the held-out cohort (Q93 and Q99) were rescored following an update to the scoring rules. Consequently, the held-out cohort was not entirely independent of the scoring process. 

Future work will need to address both the scale of the evaluation and the limitations of the current methodology. Testing on larger and more diverse workspaces, together with repeated runs of each configuration, would make it possible to examine performance variability and report confidence intervals. Human evaluation could provide additional insight into borderline responses, while separate tool-level experiments could establish the individual contributions of document search, task lookup, and chat retrieval. The influence of the Q53 example in the system prompt also deserves investigation. In addition, evaluating Llama with GPU-accelerated inference could provide further insight into its performance under a different inference environment. Throughout this study, the reported findings have been kept consistent with the recorded experimental results. Claims that could not be verified were excluded, and the scoring changes introduced after the initial evaluation have been explicitly documented. 

8.1 Future Work and Scope 

The present evaluation also raises several directions for further investigation: 1. Larger workspace scale: The current evaluation uses a relatively small synthetic workspace. A useful next step would be to test Orbit AI on larger project environments containing thousands of documents, tasks, and chat messages. Such experiments could reveal how increasing workspace size affects retrieval precision, token consumption, and multi-step reasoning. 2. Multi-chunk document retrieval: In Phase 3, each document fits within a single chunk of approximately 1,000 words. This does not fully test retrieval across document boundaries or multiple chunks. Using longer documents split into several chunks would allow future experiments to examine cross-chunk retrieval, the combination of information from separate chunks, and retrieval precision at a larger scale. 3. Uniform question cohorts: Comparisons between RAG and agent configurations would benefit from using an identical set of questions throughout the evaluation. This is particularly relevant to Q01–Q20, where some answers were no longer available in the current workspace version, resulting in cohort misalignment. The held-out cohort provides a basis for evaluating the configurations more uniformly. 4. Improved refusal scoring: The deterministic v2.2 rubric could be expanded to cover a broader range of natural-language refusal expressions. This would reduce the likelihood of valid abstentions being marked incorrect simply because their wording does not match the existing refusal signal list. 5. Independent held-out evaluation: Scoring rules should ideally be finalized before examining responses from the held-out cohort. For example, the Gemini responses to Q93 and Q99 could be assessed using rules established in advance. This would reduce the influence of post hoc scoring changes and preserve greater independence between rubric development and held-out evaluation. 6. System prompt evaluation: The role of system prompt examples in model performance remains worth examining. One specific experiment could remove the example concerning “Priya’s document export task due date” and compare the resulting responses to Q53. This would help determine whether including that example influences performance on the question. 7. Repeated experimental runs: Each configuration was evaluated only once in this study. Running every con-figuration multiple times would provide a better picture of performance variability. The resulting measurements could also support confidence interval estimation and statistical significance testing. 8. Human evaluation: Automated scoring could be complemented by blinded human assessment. This would be particularly useful for responses involving partial refusals or answers containing valid information alongside unsupported details. Comparing human judgments with automated scores could also reveal disagreements in the evaluation process. 9. Controlled inference environments: A more comparable inference setup for Gemini and Llama would help investigate how much of the observed performance and latency difference comes from the execution environment rather than the underlying model architectures. 15 OrbitAI : Evaluating Tool-Augmented Agents for Enterprise Question Answering A P REPRINT 

10. Handling empty or malformed responses: The evaluation procedure also needs a consistent approach to responses that are empty or incorrectly formatted. One example is the Llama Q98 response in the full_agent 

configuration, which begins with “{}”. Further investigation could establish how such outputs should be processed and scored. 11. Improved scoring methods: The current keyword- and regex-based scoring procedure could be extended to recognize semantically equivalent expressions. It should also distinguish genuine contradictions from values that are mentioned only to provide additional context. This could improve the consistency of automated evaluation. 12. Broader evaluation scope: Finally, the evaluation could be extended to additional benchmarks, models, configurations, and scoring approaches. Testing across these different settings would help determine whether the observations from the current synthetic benchmark also hold in other environments.
