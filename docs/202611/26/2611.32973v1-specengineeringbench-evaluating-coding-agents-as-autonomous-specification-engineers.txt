# SpecEngineeringBench: Evaluating Coding Agents as Autonomous Specification Engineers 

Xingjian Wang 1, Shijian Wang 2, Minghao Liu 3, Ji Zou 2, Zetao Yang 1, Xinping Lei 1, Yiming Liang 1, Shen Yan 2, Enduo Zhao 4, Xiaoyang Shen 1, Weihao Xuan 1,3, Jiaheng Liu 2, Ge Zhang 11TokenWave AI †, 2Independent Researcher, 3The University of Tokyo, 4Monolith Management, US Autonomous specification engineering requires coding agents to translate functional requirements into executable tests and use the results to discover and validate defects. However, existing benchmarks evaluate coding agents on explicitly specified test generation tasks, commonly providing an issue description, a designated test entry point, or files to inspect, leaving the ability to determine what to test and where to investigate insufficiently evaluated. Relying on such clues bypasses the challenge of mapping requirements to implementations and proactively uncovering unknown defects. We propose 

SpecEngineeringBench , comprising 100 instances from 78 open-source Python repositories across 16 application categories, with multiple recorded defects in each instance. Two independent tasks evaluate complementary capabilities: generating test suites and discovering defects through execution analysis. The evaluation combines test validity, defect detection, and coverage with localization precision and recall. Across seven frontier coding agents, results reveal that test validity and coverage decouple from defect exposure: agents achieve a 91.47% Head Pass Rate and 80.48% Change-focused Coverage alongside a 26.36% Fail-to-Pass Rate, while localization recall drops from 78.11% at the file level to 51.29% at the function level. Autonomous test generation improves file, function, and hunk localization recall by 4.99, 2.77, and 2.69 percentage points over relying solely on existing repository test suites.

# 1 Introduction 

Coding agents driven by large language models (LLMs) increasingly perform complex software engineering tasks (Yang et al., 2024; Wang et al., 2025b; Chen et al., 2026). As agents write and modify production code, specification engineering verifies whether implementations satisfy intended behavioral requirements (Liang et al., 2026b; Rastenis et al., 2026). In realistic software development, assessing a prerelease candidate is fundamentally an exploratory, multi-defect investigation: specification engineers are not handed localized bug reports or specific failure traces; rather, they must independently interpret high-level product specifications (Long et al., 2026; Liang et al., 2026b), navigate codebases, author discriminating test cases, and write reproducible defect reports. This setting motivates our central research question: 

Given only functional specifications and an uninspected repository, can coding agents autonomously uncover, localize, and substantiate software defects with reproducible evidence?

Existing benchmarks address this question under two structural constraints (Figure 1): (1) Investigation scopes assigned in advance: Unit test generation and proactive defect search suites evaluate designated functions, entry interfaces, or target source files (Wang et al., 2025a; Zhang et al., 2024; Jain et al., 2025; Liu et al., 2026; Li et al., 2026). Fixing targets in advance evaluates localized code completion and omits the process of mapping functional requirements to production implementations. (2) Reliance on issue reports and single bug assumptions: Benchmarks driven by issue reports supply descriptions of faulty behaviors or stack traces (Jimenez et al., 2024; Mündler et al., 2024; Ahmed et al., 2024), while reproduction suites verify isolated, known bugs (Zhang et al., 2026b). Prerelease software testing involves multiple unknown defects within the same repository, requiring agents to determine which behavioral surfaces require verification. To bridge this gap, we argue that evaluating coding agents as autonomous specification engineers requires removing location hints and issue descriptions, requiring agents to derive test scopes and defect oracles from specifications. We introduce SpecEngineeringBench , a benchmark of 100 instances curated from 78 open-source Python repositories across 16 application categories, embedding 531 real-world defects (4–15 defects per instance). SpecEngineeringBench introduces four properties: Requirements-based exploration: 

Agents receive only a Product Requirements Document (PRD) specifying functional capabilities, boundary conditions, and error invariants, requiring them to determine what functionality to test. Unrestricted repository scope: The benchmark supplies no designated entry points or target files, evaluating exploration across the repository. Multiple coexisting defects: Each instance contains multiple defects, evaluating whether agents uncover coexisting issues across the codebase. Dual tasks: Task 1 (Test Generation) evaluates whether an agent authors executable test suites; Task 2 (Defect Discovery and Reporting) evaluates whether an agent executes tests, isolates root causes, and substantiates findings with reproducible evidence. Evaluating seven frontier coding agents (Anthropic, 2026b,c; OpenAI, 2026b,c; Z.ai, 2026; DeepSeek AI, 2026; Moonshot AI, 2026) across these tasks yields three findings on autonomous defect discovery: (1) Passing tests and broad coverage do not imply defect discrimination: Agents achieve high Head Pass Rates (91.47%) and Change-focused Coverage (80.48%), while the Fail-to-Pass Rate is 26.36%. In 67.44% of test outcomes, tests execute across both defective and repaired snapshots without detecting defects, as agents encode existing implementation outputs into assertions, treating the implementation rather than the specification as the source of truth, and omit discriminating oracles derived from the PRD. # 2 SpecEngineeringBench 

SpecEngineeringBench evaluates coding agents under the conditions of specification conformance verification. Agents derive test scopes and defect oracles from product specifications without target hints or issue reports. The benchmark defines two complementary tasks: Task 1 (Test Generation) measures whether an agent authors valid and discriminating test suites from specifications; Task 2 (Defect Discovery and Reporting) 

measures whether executing and analyzing tests enables an agent to trace failures to root causes. Table 1 compares this benchmark with existing testing and repair suites.

> SpecEngineeringBench

Each instance contains 4–15 defects, with a median of 5 and a mean of 5.31. > Repository scope and requirements.

The 78 repositories represent 16 application categories under the repository inventory’s classification. Figure 2 shows the instance distribution across these categories, instance-level defect counts, and localization scopes. Their defective snapshots have a median of 80,449.5 non-documentation source lines (Table 2). Each instance pairs its snapshot with a product requirements document (PRD) describing the specified capabilities, expected results, boundary conditions, and error behavior, together with a Docker execution environment. The PRD specifies what should work; the agent must determine where and how to test it. Submitted suites distinguish unit, integration, and acceptance tests to exercise components, interactions, and observable behavior.  

> Defect scope and reference annotations.

The recorded defects span a median of 5 reference files and 11.5 edit hunks per instance, requiring reports to identify multiple locations within the same repository. Our analysis covers 17 observed defect types in three families: incomplete feature implementation (5 types),

3.3 RQ2: Agents Leave Substantial Gaps in Distinct Bug Localization  

> Agents localize less than half of reference bugs.

Across evaluated frontier models, the percentage of reference bugs successfully localized ranges from 33.14% to 49.04% (Table 5). GPT-6-Astra attains 85.85% recall at the file level (Table 3), while localizing 49.04% of distinct reference bugs across scored instances. Identifying an affected file through test execution does not isolate the underlying defective functions and code modifications. Authoring tests that trigger visible runtime exceptions can expose repository files without covering the specific boundary inputs required to localize the full defect.  

> Defects spanning multiple files show lower localization.

Localization rates depend on bug scope. Across models, agents localize 40.63%–59.05% of bugs located within a single file, while localization rates decrease to 2.00%–7.84% for bugs spanning multiple files (Table 5). Multi-file defects involve contract mismatches and state transformations across component boundaries. Agents primarily write unit tests for isolated functions, producing test suites that omit execution paths traversing multiple modules. When a test fails, the agent investigates the immediate exception frame, leaving callers and dependent components uninspected.  

> Distribution of localized defects across instances.

In instance-level evaluations, agents localize every evaluable bug in 4.00% to 11.00% of instances. In 70.71% to 88.89% of instances, submissions contain a combination of localized and unlocalized defects. After localizing at least one bug in an instance, GPT-6-Astra leaves remaining coexisting bugs unlocalized in 83.00% of instances. 3.5 RQ4: Behavioral Failure Modes in Test Construction and Localization 

Existing implementation behaviors replace specification-based oracles. Assertion mismatches account for 31.6% of reviewed Task 1 failure mechanisms, and misconfigured mocks account for 37.5%; invalid input or setup accounts for 7.4%, API or parameter errors for 22.8%, syntax or collection failures for 1.5%, and runtime exceptions for 3.7%. Inspection of execution trajectories indicates that agents infer test oracles from repository outputs, default fixtures, and existing return patterns, leaving requirements from the PRD unencoded in assertions. The resulting test suites execute cleanly while validating existing defective behaviors, failing to produce assertions that distinguish defective implementations from repaired ones. 

Causal tracing halts at initial failure locations. Among reviewed localization failure mechanisms, premature search termination accounts for 36.0%, evidence underuse for 30.9%, and dependency truncation for 25.0%. These failure modes reflect a shared pattern: upon observing a test failure or exception traceback, an agent anchors on the first visible error frame or entry point and halts exploration. Agents omit inspection of upstream caller hierarchies, cross file data flows, and execution logs needed to isolate the root cause. Submitted defect reports record immediate symptom locations while leaving the underlying defect path unexamined. 

Defensive reporting trades completeness for precision. Reporting at an incorrect granularity accounts for 4.4% of reviewed localization failure mechanisms, while conservative omissions account for 19.9% and identifying symptoms as causes accounts for 25.0%. # 4 Related Work  

> Coding Agents.

Agents based on large language models (Yang et al., 2024; Wang et al., 2025b; Chen et al., 2026) use tool environments to search repositories, edit source files, and execute commands over multiple turns. Existing benchmarks evaluate code generation (Liang et al., 2026a), repository level issue resolution (Jimenez et al., 2024), complex feature implementation (Zhou et al., 2026), and lifecycle workflows (Guan et al., 2026); SWE-smith (Yang et al., 2026) expands training distributions for software engineering agents. Executing 11 existing tests evaluates command execution without measuring an agent’s ability to determine which behaviors require testing (Shang et al., 2026; Chen et al., 2026). SpecEngineeringBench evaluates this test design capability under the configurations specified in Section 3.1.  

> Benchmarks for Test Generation.

Automated test generation includes regression testing (Rastenis et al., 2026), search methods (Deljouyi et al., 2026), and iterative generation with execution feedback (Zhang et al., 2026a; Xu et al., 2026; Rastenis et al., 2026). Existing benchmarks evaluate agents on specified targets: TestEval (Wang et al., 2025a), TestBench (Zhang et al., 2024), and TestGenEval (Jain et al., 2025) isolate individual functions, classes, and source files, while CLOVER (Xu et al., 2025) examines coverage on specified components. Issue based benchmarks such as SWT-Bench (Mündler et al., 2024) and TDD-Bench Verified (Ahmed et al., 2024) evaluate translating issue descriptions into reproduction tests (Zhang et al., 2026b; Guo et al., 2026; Fei et al., 2026). In proactive defect discovery, TestExplora (Liu et al., 2026) supplies entry interfaces, Active-SWE (Li et al., 2026) restricts inspection to review files, and SWE-sweep (Lieret et al., 2026) grades patches without evaluating executable test evidence. Coverage and execution metrics can overlook subtle defects (Xue et al., 2026; Zhao et al., 2026; Ahmed et al., 2026). SpecEngineeringBench 

evaluates requirements-based testing on prerelease repositories with multiple coexisting defects. 

# 5 Conclusion 

We introduce SpecEngineeringBench , a benchmark for evaluating coding agents as autonomous specification engineers through requirements-driven testing of repositories containing multiple real-world defects. Its two independent tasks assess generated test quality and defect localization without supplying issue descriptions or investigation targets. Evaluations reveal a gap between test validity and defect detection: most submitted tests pass on repaired implementations, while substantially fewer expose defects. Higher coverage and larger test suites do not consistently translate into better defect detection or more precise localization, so each capability requires direct assessment. Relying solely on a repository’s existing test suite reveals fewer defects than allowing agents to explore the repository and generate additional tests, demonstrating the value of active investigation beyond existing test coverage. As requirements are increasingly expanded into specifications automatically, verifying implementations against those specifications becomes the bottleneck of autonomous development. SpecEngineeringBench provides an empirical foundation for this verification capability, with future extensions to agent-generated specifications and additional programming languages.

# A Task Packaging and Instruction Specification 

The Harbor evaluation framework To ensure consistent task execution and reproducible evaluation, all tasks in SpecEngineeringBench are evaluated using the Harbor framework. Each task package contains the following components: • task.toml : Stores task metadata and execution configuration, with separate sections for the environment, agent, and verifier. These settings specify how Harbor runs the task, including applicable execution limits; they do not describe the defects the agent should discover. • instruction.md : Defines the agent-facing objective, workspace paths, required actions, and submission format. In Task 1, it requests an executable test suite and test case metadata; in Task 2, it additionally requests execution evidence and a structured defect report. The task instructions are supplied alongside the instance-specific PRD, which describes the functionality to assess. • environment/ : Contains the Dockerfile and the repository and PRD inputs used to initialize the task container. The environment exposes the unrepaired repository at /workspace/repo and the requirements at /workspace/prd.md , with dependencies configured for test execution. Agent-authored tests and reports are written to /workspace/submission/ .• tests/ : Contains the verifier entry point, tests/test.sh , and the scoring implementation for the corresponding task. Task 1 evaluates submitted tests on the defective and repaired snapshots to measure validity, defect detection, and coverage; Task 2 compares reported locations with reference annotations at file, function, and hunk granularities. These verifier resources are distinct from both the repository’s existing test suite and the tests authored by the agent. • solution/ : Retains solution/solve.sh , the solution entry point in the Harbor package layout. It provides a separate location for a packaged solution script, while the evaluated agent writes its own test suite or report to the submission paths specified in instruction.md .The agent works with the unrepaired repository; repaired snapshots, reference patches, and defect annotations are reserved for evaluation. Task 1 corresponds to the task1/ package and Task 2 to the task2/ package. 

Task instruction specification. Each task specifies the agent’s objective, workspace, and required submission. The PRD is available at /workspace/prd.md , the repository at /workspace/repo , and the submission directory at /workspace/submission/ . Original Markdown syntax and indentation are retained; long lines wrap automatically for presentation.
