# Taxi: Analyzing Agents at (Real) Scale 

Technical Report 

Guy Dar 

Rival Research 

guydar@rivalsecurity.io 

In this technical report, we present Taxi – a system for debugging, clustering, and monitoring agents at scale. Taxi scales easily to millions of steps efficiently, without spurious expenses. This is made possible by a combination of scalable analysis methods. Taxi relies primarily on clustering to gen-erate a taxonomy over steps for a structured overview of the data, and provides full SQL access for engineers and automated agents to ask complex questions. Clustering and querying are best used to-gether in a hybrid pipeline guided by a coding agent. Taxi also includes an experimental integration of Jev-style decision models: models that map state and bounded questions directly to typed, prob-abilistic decisions. They add low-cost semantic routing and evaluation where embeddings or literal queries alone are insufficient. In addition, Taxi provides an extensible ecosystem, including built-in evaluators and daily reports. To accommodate growth, Taxi is designed to be modular, hackable, and easy to plug-and-play for individuals and teams. 

## 1 Introduction 

Agents now run for hours or days [18], chaining together planning, tool use, and error recovery across long trajectories. Every run leaves a rich record of what the agent did that goes beyond just success and failure. Agent runs contain a costly yet elusive class of problems. To name a few examples: behavioral bugs that never raise an error, agents that quietly exceed the scope of what they were asked to do, the same unnecessary step repeated across thousands of independent runs, unexpected tool results, and other undesired phenomena. These phenomena are not necessarily easy to predict in advance. Some failure modes lead the agent astray, resulting in wrong conclusions [38]. Others may be local and recoverable, but they still come at the cost of extended work [17]. At production scale, a single undetected recurring “soft failure” pattern is a burden, whether it is an actual mistake or just wasted tokens [11, 6]. The solution to both lies in observability. Trajectory logging is common practice today. But for real observability, we contend there are, at minimum, two more things we need: (a) structured overview of agent behavior across the corpus, and (b) letting users 

query that behavior and ask arbitrarily complex questions. Modern products are emerging that fulfill these criteria to a certain degree [20, 22, 27]. Unfortunately, they all rely heavily on language models touching every trajectory (or a limited sample, for affordability), which is prohibitive at production volumes, due to costs, rate limits, latency, and limited coverage. Research pipelines that induce taxonomies with LLMs similarly have a model read each trajectory or a sample of them [26, 8, 16]. Taxi is built with scalability as a first-class citizen. Even with a production-grade workload and relatively limited resources, Taxi won’t falter. Taxi is designed for individuals and teams, with out-of-the-box support for a range of sophisticated features, detailed below. Upon community interest, we will open source it. 

## 2 The Taxi System 

2.1 Data Layer 

Data sources. A data source holds a team’s corpus of trajectories (complete agent runs). Each trajectory is an ordered sequence of steps – messages, tool calls, and observations. A text embedding is computed and assigned to each step. The corpus is loaded from an external origin through a loader (LangSmith, Hugging Face, JSON export, and similar). All loaders write the same schema, so supporting a new origin just means adding a loader. Loader-specific extra information is captured under the metadata field. Data sources are shared across the team – everyone reads the same trajectories and embeddings, and nobody re-ingests the same logs for their own copy. Origins that keep producing new runs (LangSmith is one) are syncable : each sync bumps a monotonic data version, and every trajectory records which version first contained it. 

Projects. A project is a personal view over one data source. It belongs to a single user and can apply its own filters (e.g., a project filtered by a specific run name). That split lets the team pay the cost of ingestion once, while each person keeps a separate workspace. The main artifact in a project is a taxonomy :a hierarchical tree of step clusters (Section 2.3). Each cluster has a short label and description, and each 2RIVAL RESEARCH 

step is assigned to one cluster, or left unassigned when no rule matches. Taxonomies are versioned and immutable once published – editing the tree means publishing a new taxonomy version. After a data-source sync, a project can pull the new trajectories and assign their steps under its current taxonomy version; the cluster definitions and assignment rules stay as they were, and only membership of new steps is filled in. Decoupling data evolution (via data versions) and taxonomy evolution is desired to keep the two orthogonal – the steps of an old trajectory can be discretized into new clusters, and a new trajectory can be discretized with an old taxonomy. 

2.2 Design 

Architecture. Taxi is organized in three layers (Figure 1). At the bottom there’s a shared database of trajectories broken into steps, with embeddings and (when present) a taxonomy of step clusters. All the other layers use the database. The middle layer is a set of a few dozen tools exposed over MCP [2]. These tools support querying a project, building or editing a taxonomy draft, publishing evaluators and insight definitions. On top sit skills [3] – short instruction documents that tell a coding agent or chat model which tools to use, and how, for a particular job (explore the data, build a taxonomy, write an eval, produce a daily report). All clients, web UI, scheduled jobs, and others, use the same pool of tools. The point of the split is that analysis methods change faster than the data model – a new way to taxonomize or a new kind of report is usually a new skill or a tool, not a rewrite of storage or every client. 

Scaling. Taxi combines two established methods with a Jev-style path: • Embedding and Clustering – vector clustering over embeddings is cheap and scales easily enough to run over every step in the corpus [4, 12], giving us a structured overview with no LLM calls (Sec-tion 2.3). • Querying and Textual Regularity – much of agent behavior is searchable as plain text: tool names, error strings, argument shapes. SQL and pattern matching over steps answer a surprisingly wide range of questions with no need for AI (Section 2.4). • Jev-style Decision Models – when a category is semantic rather than geometric or lexical, a decision model can answer a bounded choice or yes/no question directly, returning probabilities without gen-erating an explanation. Taxi uses this interface both to route steps through taxonomy levels and to evaluate trajectories. Its cost profile permits semantic decisions to be applied far more broadly than generative-model calls, giving it the potential to become the main approach for semantic analysis. The first two methods remain Taxi’s established core. When a remaining task requires a generative-model judgment, Taxi can use clusters and queries to narrow the relevant set before sampling it; this is a cost-control tactic rather than a separate analysis approach. Agentic Taxonomy Construction. This method can be used by any agentic harness. It builds and refines the cluster tree, rather than running a single clustering pass. The procedure is an agent skill : a short instruc-tion document that steers the model over relevant MCP tools. The full details of the pipeline are provided in Appendix C. The main pieces are: • Corpus exploration – SQL over the scoped views, plus TF-IDF term lists that surface recurring vo-cabulary in the steps (and, when useful, inside clusters). • Embedding-based clustering – k-means over step embeddings to propose a partition at the root or under an existing cluster. • Regex-based clustering – clusters defined by patterns over step text, when a behavior has a stable surface form; We defer more details to Appendix C. • Jev-based routing – clusters defined by natural-language labels and descriptions. A decision model chooses among the sibling definitions, with an explicit “none of these” option and a confidence thresh-old. This is useful when membership is semantic but the categories are already known. • Jev-based construction (experimental) – discovers Jev categories from the corpus instead of taking them as given: the decision model makes every decision and an LLM only writes the categories it decides to change (Appendix D). • Scoped refinement – the above tools can be restricted to one cluster’s members (TF-IDF inside a cluster, split by another k-means call, merge near-duplicates, and so on), so the agent can iterate until clusters are interpretable and distinct. 

Discretization. Apart from being a goal unto itself, taxonomization plays a few more roles. First, it provides a starting point for an agent or human analyzing the dataset, giving them context for understanding the domain and behaviors worth looking into during query-based work (Section 2.4). Second, it discretizes the steps – breaks them into a finite set of discrete clusters. This opens up a new world of possibilities – now trajectories can be interpreted as coming from a state machine , and the transition map can be analyzed, and tools for analyzing discrete trajectories can be used, including tools from process mining [29, 30], motif analysis [7], and anomaly detection [10].

2.5 Ecosystem 

Until now, we have discussed the core of Taxi, which is based on a unified trajectory-step-embedding database and clustering procedures. On top of that common ground, many extensions can be designed. Below we describe two such built-in extensions that we designed. Due to the ease of developing such extensions with little concern to the underlying core, we view them as Taxi’s ecosystem .

Evaluators (Appendix E) are regression checks over trajectories. Once a behavioral bug is understood – an agent that skips a required tool, leaks a secret into a user-facing report, or repeats a pattern that was already fixed – the team writes a check that fails when that pattern shows up again. This way, past bug fixes can be turned into checks. A coding agent can even create the evaluation check on its own. If given access to recent code changes, it can identify bug fixes in the code and design an evaluator automatically. Evaluator criteria may be SQL or regex queries, or a Jev-style yes/no question applied per trajectory or per step. SQL remains useful for cheap narrowing before semantic judgment. 

Insight reports (Appendix F) answer a different question. It focuses on periodically keeping an eye on recently generated trajectories. It finds surprising or otherwise relevant agent behavior in trajectories created after the last report. This complements other approaches that focus on the aggregate behavior. Insights can run as a scheduled routine. Findings focus around how the agents acted, but in some cases can highlight interesting outcomes of the inspected agents themselves. 5RIVAL RESEARCH 

## 3 Limitations and Outlook 

Taxi relies on the correctness of its clusters. Clustering long text is hard – steps may contain long code blocks that do not contribute to the axes we care about, and hyperparameters are hard to set well. The agentic approach improves precision substantially but can still miss nuances. Trajectory behavior may also drift over time [14]; an old taxonomy can force a stale lens on new data. Jev-style routing and evaluator criteria have only recently been integrated into Taxi and have not yet been tested end to end across the full system; for now we therefore mark these paths experimental. Finally, Taxi does not yet handle multi-agent systems out-of-the-box. These are limitations of Taxi’s current behavior , not its architecture. Its modularity can accommodate multi-agent support, better taxonomization instructions, and other extensions without redesign. Taxi is fully operational and under active development with feedback from our internal agents team. We believe it is ready to integrate into both academic and commercial pipelines, while also open to further improvement in parallel. 

## 4 Conclusion 

We presented Taxi, a system for interpreting agent trajectories at scale, built on a queryable relational back-bone that serves as the integration point for every part of the system. Its main contribution is scalability – integrated into every design decision, while not excluding potential use of heavier methods when required. Alongside embedding-based clustering and literal querying, the system now supports Jev-style typed deci-sions for semantic taxonomy routing and evaluation. This extends the same scale-first design to semantic judgments and may become the primary path for them. We discussed several key points in our design, fur-ther elaborated in the appendices. We additionally discussed how we maintain modular structure to make the method suitable for extension and flexible. We hope our system is useful to others building an interpretive science of agent behavior at production scale, as well as to more modest scales. 

## Ethics Statement 

The trajectories analyzed in this work come from the authors’ own agentic systems and public data, and do not involve human-subjects data.

## C Taxonomy Construction in Detail 

A taxonomy is a named tree of step clusters – one lens on a trajectory corpus, not a replacement for SQL over the same steps (Section 2.1). It serves two jobs at once: a birdseye overview of what agents actually do, and a stepping stone that gives a human or an agent enough grasp of the dataset’s shape to write targeted queries afterward. Both construction paths below produce the same artifact shape (a versioned tree in Postgres); they differ in where summarization of “what behaviors exist” happens, and in how much human or agent judgment sits between a clustering call and a published label. 

Shared Taxonomy Tree. Embedding-based, regex-based, and Jev-based clusters can sit in the same tree, including as siblings of different parents, but at any one level all siblings share a single routing method. • Embedding clusters. k-means over step embeddings proposes a partition; the geometry itself is the summarization of the corpus. Coverage at an embedding level is exhaustive among steps that have embeddings: every such step is assigned to the nearest centroid. Large scopes may subsample to compute centroids (reported explicitly in the tool response); at publish, every embedded step is still routed by nearest centroid regardless. • Regex clusters. Each cluster is a case-insensitive pattern over step action text. Summarization is a separate, upstream step – currently TF-IDF over the corpus ( get_tfidf_terms ), with room for other 15 RIVAL RESEARCH 

vocabulary methods – after which an agent (or a human) designs the patterns. Coverage need not be exhaustive: a step matching no sibling pattern is simply left unclustered at that level, and that is fine. • Jev clusters. Each sibling is defined by a short label and a natural-language description. The config-ured Jev-style decision model receives the step’s action text and a Choice question whose options are those sibling definitions plus “None of these.” The chosen sibling wins only when the returned confi-dence clears a configurable threshold. Thus these levels express semantic categories directly, without requiring a centroid or a lexical pattern. The asymmetry matters for method choice. Much of what an agent emits is templated – tool names, argu-ment shapes, stereotyped observations, recurring error strings – and for that material a literal pattern names a behavior exactly where a semantic neighborhood only approximates it. Embedding proximity is useful when the categories must first be discovered from the corpus. Once categories can be stated as definitions, Jev routing can assign variable wording directly against those definitions. The taxonomizer is free to use any operator per region of the tree rather than once for the whole corpus. In particular, a regex parent can cheaply pre-filter a Jev child level, so only steps that reach that branch require a model decision. 

Routing. After publish, every step is assigned by walking the tree from the root: • Regex siblings: first matching pattern wins (order among siblings is significant). • Embedding siblings: nearest centroid wins. • Jev siblings: the model chooses among labels and descriptions; “None of these” or a low-confidence answer produces no match at that level. • A step that matches a parent but no child stays at the parent. • A step matching nothing at the root is unassigned. The same tree-walk is what later sync uses: new steps are routed through the published version without rebuilding it (Section 2.1). 

Simple flat clustering. The default non-agentic pipeline is one k-means pass over the project’s embedded steps, followed by an LLM label for each cluster from a small sample near its centroid, then an atomic publish. There is no examination loop between proposal and name – the clustering call is the partition, and each label is written in isolation, blind to sibling clusters. Despite that myopia it is often useful in practice; most of the production cases in Appendix G came from flat k-means taxonomies. It remains available as a first pass and as a baseline the agentic path is meant to improve on. 

Agentic construction. The taxonomizer skill (Appendix B) treats every clustering call as a proposal to examine , not a result to accept. There is no scoring rubric to optimize: the tools return evidence (samples, distinctive terms, cohesion and nearest-cluster statistics), and the agent decides what is a coherent cluster, what is a grab-bag, and what is one theme split in two. The loop, summarized in Figure 2, is: 1. Orient. Corpus size via SQL; hundreds of TF-IDF terms (distinguishing vocabulary lives well down the ranking); raw step samples. Get a feel for the behaviors present before imposing structure. On a redesign, load the published tree first ( get_taxonomy_context / draft_from_taxonomy ). 2. Propose. Cluster at a granularity that matches the thematic richness just seen – enough clusters to separate real behaviors, not a deliberately small k to patch later. A rough root range is often 8–30 depending on corpus size and diversity; k is adjusted up (split) and down (merge) as evidence arrives. Embedding, regex, and Jev operators all accept a parent_id , so a propose step can be scoped to 16 RIVAL RESEARCH 

one cluster’s members. Jev categories are most natural once exploration or embedding clusters have revealed definitions worth routing against. 3. Examine. For each cluster, read centroid samples (the core), edge samples (farthest from the centroid – where a grab-bag shows itself), diverse samples, distinctive cluster_terms , and the triage numbers 

cohesion and nearest_sim . A handful of centroid samples plus top terms is not enough evidence to name or accept from. 4. Revise. Confirm against the text before acting: • Low cohesion, or edge samples that read like a different activity than the core → grab-bag; split with cluster_by_embedding(parent_id=...) or, if the split is cleanly describable, 

split_draft_cluster with regex patterns or Jev descriptions. • High nearest_sim , or find_similar_clusters pairing two clusters whose terms and samples overlap → one theme fragmented; merge_draft_clusters .• A dominant cluster holding a large share of the corpus → usually several behaviors collapsed; go deeper. • An empty cluster, or a child that covers almost all of its parent → remove it / do not nest there. Sub-cluster only where distinct sub-behaviors earn a deeper level, not to hit a depth. 5. Name as a set. Settle membership before naming. Name from centroid samples and distinctive terms, never from a handful of stray examples. Then read all names together: consistent abstraction level, parallel form, clear contrast. Prefer behavioral names (“Searching AWS for Lambda functions”) over structural ones (“step contains serverless JSON”). The description stored on a cluster is a 1–3 sen-tence definition of what those steps are or do – never a process log (“split from cluster X”). For a Jev cluster, this text is also the routing criterion and must be sufficient to decide membership. 6. Publish. publish_taxonomy commits the draft atomically as a new taxonomy version, assigns all project steps by the tree-walk above, and clears the draft. Before calling it, present the proposed tree – name, size, routing rule per cluster – and say explicitly what was left broad, dropped, or unembedded. Prefer clean coverage over forced coverage: a smaller set of strong, distinct clusters beats padding the tree to cover every last step. 

Draft vs. published. While the loop runs, the tree is session-local draft state (Appendix B). Other clients and the project’s published taxonomy are untouched. Publish is the only transition that makes the tree durable, and it is all-or-nothing: version row, cluster rows, and step assignments land in one Postgres trans-action, or none do (Appendix J). Prior versions remain readable; sync of newly ingested steps always targets the version the project currently uses. 

Relation to the flat pipeline. The agentic path reuses the same operators and the same publish/routing machinery as the flat pipeline. What it adds is everything between propose and name: scoped re-clustering, examination against evidence, merge and split, and naming with visibility into sibling clusters. The flat pipeline is the propose-and-name fragment of Figure 2 with the middle boxes removed; the taxonomizer skill is the full loop, written as methodology over the MCP surface rather than as a second clustering subsystem.

Online construction. The scope’s steps stream in a fixed random order, a batch at a time. Each new step is assigned once, with the same question routing uses, to one of the current categories or to “new behavior.” After each batch, the decision model answers yes/no questions over all the steps seen so far: • Fits? Does a category’s description fit its member steps? • Mixed? Does a category hold more than one behavior? • Overlap? Do the members of two categories fit both equally well? Candidate pairs come from asking which other category is closest to each category, and from how often two categories competed for the same steps. • Uncovered? Do the uncategorized steps share a behavior no category covers? The answers’ probabilities rank the candidates, and only the top few edits per batch are made. An LLM then writes each one: a rewritten description, the parts of a split, a merged category, or a new category. The LLM sees the other categories, so it does not recreate one that exists. A split is kept only if the decision model can tell its parts apart, and only the steps an edit touched are assigned again. 

No target count. The number of categories is not fixed in advance. Two share bounds, relative to the steps seen, frame the level: a category above the upper bound is split ahead of others, and no merge may create one; a category below the lower bound is dropped. Within those bounds, the count is whatever the decisions above produce. An optional ceiling is available. 

Stopping and the final pass. The level is settled once its size has held for a few batches and the last batch created no category, so construction usually reads only part of the sample. Every step read is then assigned once more to the finished categories, so the sizes and examples reported are what publishing will produce; a category left empty is dropped. 18 RIVAL RESEARCH 

Optional hierarchy. With a depth above one, every category with enough member steps gets children, constructed the same way over its own members, with share bounds relative to its own steps. A node that keeps fewer than two children stays a leaf, so depth and width come from the data. The result is written into the draft as ordinary Jev clusters, routed and published like any other level. Construction runs as a background job and checkpoints after every batch, so an interrupted job resumes where it stopped.

Evaluation then proceeds in three stages, each narrowing the previous: scope, then filter, then criterion. If 

filter_sql is set, the scope is intersected with the ids it returns, and an empty filtered set yields skip rather than pass, since nothing was actually tested. The filtered set is intersected with the criterion, of which exactly one form may be given. SQL criteria retain the existing behavior: with success_sql the evaluator passes iff every filtered trajectory is a hit, and with failure_sql it passes iff none is. A success or failure 

mapping may instead contain a jev yes/no question. By default the decision model sees all actions in a trajectory in order; with per: step , it sees one action at a time and the trajectory is a hit when any step reaches the probability threshold. An optional state query can select other text or structured state while preserving the same trajectory identifiers. SQL filters and state queries therefore continue to perform cheap exact narrowing before any model call. Results are reported as n_success /n_filtered together with a failure count. There are four possible outcomes: success, fail, skip, and error. Skip means the filtered set was empty, and error is reserved for problems with the definition rather than the corpus — an unresolvable or ambiguous scope name, SQL that does not execute, or a failed discrimination check. Error is deliberately distinct from fail because the two demand different responses: a fail is a finding about the agents, an error is a bug in the check. Ids listed under failure_examples are verified before the live corpus result. Each must exist in scope, match the filter SQL, and be classified as a failure by the criterion. Beyond hand-written invariants, the same format supports turning engineering history into checks, and that methodology is documented in the evaluator skill document. Candidates come from reading a commit log or closed tickets broadly. Then the agent is tasked with translating that into an observable signature , i.e., something we can query over trajectories. 

## F Insight Reports 

An insight is a recurring investigation of one or more data sources, defined in YAML, published to Postgres, and run by an agent on a schedule. A definition names the insight, the data sources it covers (a list, or "*" 

for every source), and the channel its digest is posted to; anything else in the document is carried through to the investigating agent as context. As with evaluators, publishing upserts by name. There are three modes covering three cases: if no report already exists for this data source, a bootstrap run runs over last week’s trajectories; any other case gets everything from the data version its last report covered, unless there was no new data ingested, which immediately receives an up-to-date verdict and stops. Each investigation saves one Markdown report plus a short summary that a Slack digest can quote. Findings are ordered by how much they would surprise a competent reviewer, and a corpus’s own outcome tallies are background rather than the headline unless the rate itself is the surprise. Agent behavior is the 20 RIVAL RESEARCH 

subject — strategy, tool choice and sequencing, instruction following, wasted or repeated action, recovery, stopping behavior — rather than a catalog of the tasks or artifacts the agents happened to touch. When a batch is small enough to read end to end it is read end to end rather than sampled, and every number must come from a query run in that same investigation.

## H Taxi on SastBench 

This appendix walks through one corpus with Taxi, layer by layer: querying, vocabulary, taxonomies, state machines, decision-model questions, and analyses built on top of the discretized runs. Each part shows what a capability surfaced, and every claim was checked against its obvious confounds before being kept. 

Setup. Four agents — Claude Sonnet 4.5, Gemini 3 Pro, Gemini 2.5 Pro and DeepSeek R1 — triage the same 2,737 static-analysis findings of SastBench [13] with the same ReAct harness (read, grep, symbol lookup, a vulnerability-pattern tool, at most 20 steps), deciding whether each finding is a true or a false positive. That gives 10,515 runs and 87,140 steps, loaded as one corpus with a view per agent. 89% of the findings are false positives. Step text is each step’s reasoning and tool call; the tool’s output is kept as the step’s observation. 

H.1 Querying the corpus 

Errors are shared, not idiosyncratic. Grouping runs by finding in SQL, 574 findings are judged wrong by all four agents, against about 120 if each agent erred independently at its own rate. 

One repository behind half of the shared errors. A text search over the file paths the agents read places 265 of those 574 findings (46%) in a single PHP repository, which contributes 803 of the 2,737 findings across 42 commits. Its findings are labeled true positive 5% of the time, yet the agents call 58% of them vulnerable, and the code their verdicts cite reads as genuinely exploitable (request parameters concatenated into SQL, class names instantiated from request input). Either labels in that repository deserve another look, or the benchmark labels issues that predate a commit as false positives. Excluding it, errors remain shared: 309 findings wrong for all four agents against about 65 expected (4.8 ×). 

Tool-failure profiles. Pattern matching over observations separates the agents: Claude’s failures are mostly empty searches (51%), the Gemini models mostly hit file-size limits (38–39%) and missing paths (28–35%), and Gemini 3 Pro and DeepSeek R1 produce malformed tool calls (303 and 245 steps). After a failure, Claude and Gemini 2.5 Pro usually adjust the same call (55% and 62%), DeepSeek R1 usually switches tools (60%), and almost none retry the identical call.

H.5 Decision-model questions 

Some questions are semantic and polar, which keyword rules cannot capture: a pattern for “input is sani-tized” also matches “ htmlspecialchars only prevents XSS, not. . . ”. A Jev-style decision model answers them directly. 

Verdicts without an attacker path are half as precise. Asked of 1,546 sampled “vulnerable” verdicts — does the agent show how attacker-controlled input reaches the flagged code, or only that a risky pattern is present? — verdicts that show a path are right 18% of the time (95% interval 15–22%, resampling commits), and those that do not, 9% (7–12%). Claude and Gemini 2.5 Pro show a path in half their “vulnerable” verdicts, DeepSeek R1 and Gemini 3 Pro less often (38% and 43%). Even with a path, “vulnerable” calls are mostly wrong here. 

Most investigations are silent until the verdict. Asked at two points of 1,200 sampled runs (after the first observation, and 60% of the way through) whether the reasoning leans toward a vulnerability, toward a false positive, or neither yet (Table 5): Claude states a position mid-run in half its runs, Gemini 3 Pro in one in six, its “vulnerable” verdicts appearing only at the end. A position, once stated, is the final verdict 90% of the time.

H.6 Beyond the taxonomy 

The task shapes the investigation more than the model. Comparing the behavior profiles of runs (cosine similarity of their behavior histograms), two different models on the same finding are twice as similar (0.58) as one model on two different findings (0.29); unrelated runs score 0.23. 

Models that disagree investigated the same way. Within each finding, pairs of models that reach opposite verdicts are less similar in behavior than pairs that agree by only 0.022 (95% interval 0.009–0.034), a fraction of the gap between task and model. On one container finding, Claude and DeepSeek read the same three compose files in the same order and query the same pattern; from the same evidence one calls an unrestricted database volume a vulnerability, the other a false positive. With errors shared across models (Appendix H.1), disagreement and error live in the judgment, not in the investigation. 

H.7 Anomalies as a spotlight 

Outliers in the discretized runs are not failures in themselves, but they point at subsets worth reading, and some of those are fixable. • Unusual runs go to unusual places. The runs least likely under each agent’s own transition model read test files, templates and configuration; most end in a correct “non-production code” dismissal. 29 RIVAL RESEARCH 

• Failed lookups are evidence, but not for every agent. Rare transitions into a verdict lead to verdicts issued right after a failed read or search (4–14% of verdicts). Claude, DeepSeek and Gemini 2.5 Pro then call “vulnerable” less (38% against 47–50%), and only on false-positive findings (47% to 36%; unchanged on true positives), using the empty result as evidence. Gemini 3 Pro does not adjust, even after its own malformed calls. • Runs that hit the step limit are symbol hunts. They over-represent symbol-definition searches 2.1– 2.9 × and repeat a behavior longer; for Gemini 2.5 Pro a fifth of their steps are error recovery. The fix suggested is in the symbol-lookup tool, not the model.

## I Related Work 

Agent trajectory clustering and its taxonomization have been studied extensively. For example, [31, 19, 26], and others cluster conversations and create hierarchical taxonomies with natural language descriptions. Their focus was on taxonomizing trajectories as a whole, while our work operates at the granularity of steps, closer to [28], though they worked on a single input prompt at a time. That work belongs to the field of interpretability: it targeted chains-of-thought of simple problem solving tasks in order to understand the various methods a model takes in solving the problem. More broadly, LLMs have been used to induce topics and goal-driven clusters described in natural language [23, 32], to generate and validate taxonomies with humans in the loop [25], and to organize a given set of entities into a taxonomy [34]. A related line of work uses LLMs to describe in natural language how two text corpora differ [35, 37], and to fit statistical models, including clustering, whose parameters are natural-language predicates rather than embedding centroids [36]. 30 RIVAL RESEARCH 

TypeSafe AI introduced Jev as a “System One” model for decisions inside software [1]. Rather than produce free-form text, it accepts application state and typed questions and returns choices, scores, or yes/no proba-bilities. The interface is intended for classification, routing, filtering, and gating at substantially lower cost than generative-model calls. Taxi adopts the interface rather than depending on the original model: through-out this report, Jev-style includes any compatible decision model capable of answering these bounded ques-tions. Over the years, many agent debugging tools have emerged. Laminar [20] and Docent [22] are open source frameworks that use LLMs to identify problems in agentic traces. Recently, LangSmith announced its own LangSmith Engine [27], similarly addressing this problem. All of them now include querying abilities to varying degrees of expressivity. None of them uses clustering as a central step; they use it post hoc, to aggregate results only for better human digestibility. Another related line of work focuses on agent taxonomies [9, 15, 5]. Most of them are constructed manually or at least semi-manually. They are designed to capture behavior on a global level, not tailored to the specific dataset explored. Cemri et al [9] focus on multi-agent failures. Gao et al [15] focus on agent actions in general, closer in spirit to us, rather than just failures. Ashury-Tahan et al [5] focus on failures, and they propose ErrorAtlas, a closed taxonomy, and ErrorMap, a taxonomy construction pipeline based on LLMs. Closer to Taxi in that the taxonomy is tailored to the data, AdaMAST [8] uses LLMs to induce a failure taxonomy from an agent system’s own execution traces, and Gupta et al [16] discover failure taxonomies from robot deployment logs by having a vision-language model explain each failed trajectory and clustering the explanations. Both target failures rather than behavior in general, and both rely on a model reading the trajectories, whereas Taxi’s embedding and regex paths assign steps to clusters without any model call. It will be interesting in the future to absorb such a taxonomy into Taxi, as a set of pre-defined constructs ,that Taxi will then modify or refine for the specific use case.
