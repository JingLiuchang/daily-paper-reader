## 摘要
自主规格工程要求编码智能体将功能需求转化为可执行测试，并利用测试结果发现和验证缺陷。然而，现有基准在明确指定的测试生成任务上评估编码智能体，通常提供问题描述、指定的测试入口点或待检查文件，导致其确定测试内容和调查位置的能力未得到充分评估。依赖此类线索绕过了将需求映射到实现以及主动发现未知缺陷的挑战。我们提出 SpecEngineeringBench，包含来自 78 个开源 Python 仓库、覆盖 16 个应用类别的 100 个实例，每个实例记录有多个缺陷。两个独立任务评估互补能力：生成测试套件，以及通过执行分析发现缺陷。评估结合测试有效性、缺陷检测和覆盖率，以及定位精确率和召回率。在七个前沿编码智能体上，结果表明测试有效性和覆盖率与缺陷暴露相脱钩：智能体取得 91.47% 的 Head Pass Rate 和 80.48% 的 Change-focused Coverage，同时 Fail-to-Pass Rate 为 26.36%；而定位召回率从文件级的 78.11% 下降到函数级的 51.29%。与仅依赖现有仓库测试套件相比，自主测试生成将文件、函数和 hunk 定位召回率分别提高 4.99、2.77 和 2.69 个百分点。

## Abstract
Autonomous specification engineering requires coding agents to translate functional requirements into executable tests and use the results to discover and validate defects. However, existing benchmarks evaluate coding agents on explicitly specified test generation tasks, commonly providing an issue description, a designated test entry point, or files to inspect, leaving the ability to determine what to test and where to investigate insufficiently evaluated. Relying on such clues bypasses the challenge of mapping requirements to implementations and proactively uncovering unknown defects. We propose SpecEngineeringBench, comprising 100 instances from 78 open-source Python repositories across 16 application categories, with multiple recorded defects in each instance. Two independent tasks evaluate complementary capabilities: generating test suites and discovering defects through execution analysis. The evaluation combines test validity, defect detection, and coverage with localization precision and recall. Across seven frontier coding agents, results reveal that test validity and coverage decouple from defect exposure: agents achieve a 91.47% Head Pass Rate and 80.48% Change-focused Coverage alongside a 26.36% Fail-to-Pass Rate, while localization recall drops from 78.11% at the file level to 51.29% at the function level. Autonomous test generation improves file, function, and hunk localization recall by 4.99, 2.77, and 2.69 percentage points over relying solely on existing repository test suites.

## 1. 核心问题与整体含义

- **研究动机**：编码智能体越来越多参与真实软件工程任务，但“规格工程”要求智能体仅依据功能规格，自主判断**测什么、查哪里、如何证明缺陷存在**。现有基准通常提供 issue 描述、指定测试入口、目标文件或函数，绕过了从需求到实现映射、主动发现未知缺陷的核心挑战。
- **核心问题**：仅给定产品需求文档（PRD）和未检查的仓库，编码智能体能否自主发现、定位并用可复现证据证实多个软件缺陷？
- **整体含义**：论文提出 **SpecEngineeringBench**，将评估场景从“按 issue 修复/按目标生成测试”推进到“预发布软件的多缺陷探索性验证”，强调需求驱动探索、无位置提示、多缺陷共存和可执行证据。

## 2. 方法论

### 2.1 核心思想

- 每个实例形式化为 \((r_i, d_i, e_i, B_i)\)：
  - \(r_i\)：未修复仓库快照；
  - \(d_i\)：产品需求文档 PRD；
  - \(e_i\)：隔离 Docker 运行环境；
  - \(B_i\)：共存的参考缺陷集合，每实例至少 4 个。
- 智能体只能访问 \((r_i,d_i,e_i)\)，**不提供 issue 描述、目标文件、函数或入口提示**。
- 设置两个独立任务，分别评估测试生成与缺陷发现/报告能力。

### 2.2 任务与指标

- **Task 1：测试生成**
  - 智能体生成可执行测试套件 \(T_i^{(1)}=A(r_i,d_i,e_i;\pi_1)\)。
  - 评测器在缺陷快照 \(r_i\) 与修复快照 \(r_i^+\) 上分别执行测试。
  - 指标：
    - **HP（Head Pass Rate）**：在修复快照上通过的测试比例，池化测试计数；
    - **F2P（Fail-to-Pass Rate）**：在缺陷快照失败、修复快照通过的判别性测试比例，按实例平均；
    - **EC（Entry Coverage）**：覆盖参考目标功能可执行文件-行对的比例；
    - **CFG（Change-focused Coverage）**：覆盖参考修复变更行比例；
    - **Num**：平均提交测试数。
- **Task 2：缺陷发现与报告**
  - 智能体主动编写并执行临时测试探针，提交结构化诊断报告 \((T_i^{(2)},R_i)=A(r_i,d_i,e_i;\pi_2)\)。
  - 报告需包含可复现执行日志、源码位置、根因分析等。
  - 按 **file / function / hunk** 三个粒度计算定位召回率 LR 与精确率 LP。
  - 文件按规范化路径匹配；函数需函数名匹配；hunk 匹配要求同文件且报告行与参考编辑行距离不超过 \(\tau=3\) 行。
- **Distinct Bug Localization**
  - 一个缺陷被视为成功定位，需匹配全部参考文件、函数符号（含 `<module>`），且覆盖超过一半参考 hunk。
  - 分别统计总体、单文件缺陷、多文件缺陷的定位比例。

### 2.3 评测执行

- 使用 **Harbor v0.23.0** 容器化框架打包任务，保证验证器在带外执行。
- 试验在隔离容器中运行，禁用出站网络。
- Task 1 与 Task 2 独立评测，Task 2 不接收 Task 1 产出的测试。
- 任务包包括 `task.toml`、`instruction.md`、Docker 环境、验证器 `tests/`、参考解目录等；PRD 位于 `/workspace/prd.md`，仓库位于 `/workspace/repo`，提交写入 `/workspace/submission/`。

## 6. 主要结论与发现

- **测试有效性与缺陷暴露脱钩**：
  - 平均 HP 达 **91.47%**，CFG 达 **80.48%**；
  - 但平均 F2P 仅 **26.36%**。
  - 在 49,317 个测试中，67.44% 在修复快照通过且未在缺陷快照失败；仅 24.17% 满足 F2P；8.39% 在修复快照失败。
- **高覆盖率不等于缺陷判别**：
  - 即使 CFG 处于 80–100% 区间，平均 F2P 仍仅约 24.24%–37.82%。
  - 测试可执行到修复相关代码，但未提供触发缺陷的输入或未检查受影响行为。
- **定位召回随粒度细化明显下降**：
  - 文件级 LR 平均 **78.11%**；
  - 函数级降至 **51.29%**；
  - hunk 级为 **51.88%**。
  - LP 从文件级 75.33% 降至函数级 53.77%，hunk 级回升至 68.78%。
- **Distinct bug 定位不足**：
  - 各模型成功定位的参考缺陷比例仅 **33.14%–49.04%**；
  - 单文件缺陷定位率 40.63%–59.05%，多文件缺陷仅 **2.00%–7.84%**。
  - 智能体常定位部分缺陷后停止探索。
- **缺陷类型存在共同盲区**：
  - 不完整数据处理、缺失输入验证、不完整错误处理、输出相关缺陷等 cohort 的 function/hunk 召回偏低；
  - 输入验证和配置类缺陷即使文件已定位，函数/hunk 遗漏率仍较高。
- **自主测试生成可提升定位召回**：
  - 相比仅运行仓库现有测试，agent-authored tests 将文件、函数、hunk 定位召回分别提升 **4.99、2.77、2.69 个百分点**；
  - 但精确率分别下降 **2.74、1.60、3.25 个百分点**，报告位置增长快于被确认位置增长。
- **失败机制**：
  - Task 1 中常见断言 oracle 来自现有实现而非 PRD，导致测试验证了缺陷行为；
  - Task 2 中常见过早停止搜索、证据利用不足、依赖截断；
  - 报告策略上存在防御性报告：以粗粒度或省略候选位置换取精确率。

## 7. 优点

- **任务设计贴近真实预发布验证**：去除 issue 和位置提示，仅给 PRD、仓库和环境，更接近规格工程师的探索性验证。
- **多缺陷共存**：每实例多个真实缺陷，能评估智能体是否会在发现首个缺陷后停止。
- **双任务独立评估**：区分“生成有效测试”与“执行分析并报告缺陷”，避免单一指标混淆能力。
- **多粒度定位评分**：file/function/hunk 三级召回与精确率，能揭示“找到文件但找不到函数/修改点”的关键短板。
- **分层分析丰富**：按覆盖率区间、缺陷类型、单/多文件缺陷分析，提供细粒度诊断。
- **配对比较有说服力**：同一模型、同一 100 实例上比较仓库现有测试与自写

测试的定位效果；由于实例、模型与 harness 固定，该比较能较直接地估计自主测试对定位召回率和精确率的影响。
- **评测基础设施可复用**：Harbor 任务包、缺陷/修复双快照执行、带外验证器和结构化提交目录等设计，可迁移到其他规格工程、缺陷发现与测试生成基准。
- **诊断性较强**：论文不只给出模型排名，还通过 HP/F2P/覆盖率、三级定位指标和失败轨迹揭示“高覆盖但低判别”“文件可定位但函数/hunk 遗漏”“多文件缺陷盲区”“防御性报告”等机制，对 agent 设计具有直接指导意义。
- **定性案例补充定量结果**：6 个案例研究展示了智能体探索、停止和报告策略，有助于解释指标背后的行为模式。

## 8. 补充局限与后续方向

- **语言与生态范围有限**：当前仅覆盖 Python 仓库，结论能否推广到 Java、C/C++、JavaScript/TypeScript 或跨语言项目仍需验证。
- **PRD 与缺陷构造的生态效度**：PRD 的完整度、缺陷注入/回退方式和参考修复质量会直接影响任务难度；未来可引入真实预发布缺陷、不同 PRD 粒度及多版本演化场景。
- **评分阈值敏感性**：hunk 定位采用固定行距离阈值 \(\tau=3\)，不同缺陷类型和代码结构下可能产生误判；可报告多阈值敏感性分析。
- **报告评分可能激励策略性行为**：精确率与召回率并重时，智能体可能倾向少报或粗报；未来可加入证据充分性、可复现性和遗漏惩罚等过程性指标。
- **缺少人类专家基线**：若加入规格工程师或测试专家的表现，可更直观判断任务难度与 agent 差距。
- **后续可扩展方向**：多语言与多模态仓库、多轮交互式澄清、动态依赖环境、harness 消融实验、多次运行方差与显著性检验、训练数据污染检测，以及更细粒度的探索过程评估。

## 9. 总体评价

SpecEngineeringBench 将编码智能体评估从“按 issue 修复”推进到“仅凭 PRD 自主探索多缺陷并提交可复现证据”，任务设计贴近预发布规格验证，指标覆盖测试有效性与多粒度定位，实验规模较大且诊断性丰富。其核心发现——高覆盖率并不等于缺陷判别、定位召回随粒度细化显著下降、多文件缺陷仍是明显盲区——对后续 agent 架构、测试 oracle 设计和规格工程研究具有较高参考价值。
