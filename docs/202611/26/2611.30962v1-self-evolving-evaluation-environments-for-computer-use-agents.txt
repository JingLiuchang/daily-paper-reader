Abstract 

Computer-use agents (CUAs) are rapidly improving, yet their evaluation remains largely static. Existing bench-marks provide a strong foundation, but fixed difficulty ceilings, limited feature coverage, and coarse aggregate scores progressively weaken their discriminative and diag-nostic value. We introduce CUA-SEE, a closed-loop eval-uation environment that co-evolves tasks and executable verifiers from rollout evidence. It disentangles three ob-jectives: benchmark evolution expands evaluation scope through cohort-calibrated difficulty and coverage growth; diagnostic evolution increases resolution through agent-conditional capability-boundary probes; and verifier evo-lution improves precision by translating changing require-ments into state-grounded checkpoints with adversarial val-idation. Across multiple agents, applications, and rounds, CUA-SEE generates challenging, measurable tasks while preserving process-level evidence. Our results position adaptive evaluation as a scalable counterpart to evolving CUAs, continuously tracking what agents can do, where their boundaries lie, and how reliably progress is measured. 

1. Introduction 

Agent evaluation, which underpins both scientific progress and real-world deployment, has long been a fundamentally yet challenging problem [6, 11, 14, 21]. For computer-use agents (CUAs) [8, 10, 19, 23], evaluation is harder because success must be verified against intricate software-specific states and multifaceted task requirements, rather than tex-tual responses (e.g., search agents [2, 7, 9]) or binary exe-cution results (e.g., code agents [5]). Current benchmarks [18, 20] have established an essential foundation for CUA evaluation by manually curating realistic tasks and task-specific verifiers. However, this human-authored, one-shot construction paradigm is costly to scale and renders both tasks and verifiers largely fixed as agent capabilities evolve, giving rise to several critical limitations [4, 17, 22]. This static paradigm creates three consequential limita-tions: (1) A fixed task set imposes a difficulty ceiling : once agents master its tasks, scores saturate and cease to distin-guish further progress. (2) Manual construction provides limited feature coverage ; in our audit of core OSWorld ap-plications, the existing tasks exercise less than 20% of the available software-feature taxonomy. (3) Static benchmarks lack evaluation dynamics : they neither track a moving ca-pability boundary nor actively search for newly emerging weaknesses, shortcut behaviors, and generalization gaps. These limitations reveal the necessity of an evaluation sys-tem that evolves in tandem with the LLM agents it assesses. To address the aforementioned challenges, we propose 

CUA-SEE , a Self-Evolving Evaluation environment for computer-use agents. CUA-SEE reconceptualizes evalua-tion as a dynamic, closed-loop process where tasks, exe-cutable verifiers, and agent rollout evidence continuously inform and refine one another. At each round, agents in-teract with the current task-verifier pairs; validity-filtered trajectories and checkpoint outcomes update the measure-ment state; and this evidence determines what tasks should be measured in the next round and how the corresponding verifiers should be implemented. Specifically, our frame-work is designed around three core components that work in concert to disentangle three dimensions often conflated in conventional task-hardening pipelines: evaluation scope, diagnostic resolution, and measurement precision .

Scope. To address the fixed difficulty ceiling and feature coverage, we expand the evaluation scope of static bench-marks by introducing an evolution operator, called Bench-mark Task Evolution , which constructs a shared, model-neutral benchmark from aligned trajectories of a heteroge-neous agent cohort. It retains all replicates, separates ex-ecution validity from task success, and uses cohort agree-ment and disagreement to calibrate whether a source task is mastered, discriminating, unstable, or confounded. Resolution. The second operator, called Diagnostic Task Evolution , is agent-conditional and concentrates evaluation budget near uncertain capability boundaries. A batch-level planner aggregates longitudinal evidence into capability, software, and feature maps to dispatch targeted experiments over seven calibrated dimensions such as precision control and state-dependent reasoning, as detailed in Appendix A. The task-level evolver realizes each experiment as a natural task with one primary dimension at a controlled intensity. The search is adaptive rather than monotonically harder: Clean successes and failures prompt upward and downward probes, respectively; partial or censored runs trigger decon-founding. This adaptive bracketing refines where an agent’s pass-fail transition lies, turning coarse benchmark scores into locally attributable capability evidence. 

Precision. Both task operators share a requirement-preserving measurement backbone, termed as Verifier Evo-lution . The third component uses task-agnostic software adapters to probe native state-export surfaces and normal-ize them into a shared CanonicalState schema. Over this substrate, an information-isolated verifier agent gen-erates atomic requirement-level checkpoints while a pass agent independently realizes a valid completion state; their adversarial cross-review improves checkpoint completeness and PRE/PASS discrimination [12, 16]. Verifier evolution thus determines how faithfully evolving agent behavior is measured while exposing process-level signals for diagno-sis and future dense-feedback learning. Extensive experiments across five SOTA agents demon-strate that CUA-SEE continuously restores evaluation infor-mativeness. Over four evolution rounds, the macro-average agent score decreases from 60.6 to 47.5 while trajectory length increases from 27.4 to 39.3 steps, and exact feature coverage expands by 3.65 ×. Beyond producing harder and broader tasks, CUA-SEE adaptively concentrates diagnos-tic probes near each agent’s capability boundary, revealing agent-specific and software-specific weaknesses obscured by aggregate scores. Meanwhile, the evolved checkpoint verifiers achieve 84.0% agreement with human trajectory judgments. To summarize, our main contributions are: 1. We formulate self-evolving evaluation for CUAs as a closed loop in which task demand, measurement instru-ments, and validity-filtered rollout evidence are updated jointly across rounds, addressing the mismatch between continually improving agents and static benchmarks. 2. We introduce two complementary task-evolution oper-ators: a cohort-grounded benchmark operator that ex-pands evaluation scope through measurable frontier and feature-coverage growth, and an agent-conditional di-agnostic operator that increases resolution through con-trolled, adaptive capability-boundary probes. 3. We develop a requirement-preserving verifier evolution pipeline that improves measurement precision by con-verting evolved task obligations into executable, state-grounded checkpoints, enabling validity-aware capabil-ity estimation and richer process supervision than termi-nal scalar rewards alone.

Evidence integrity is modeled independently of task outcome: valid successes and failures provide clean evidence, step-limit runs are retained as censored obser-vations, and setup, controller, or environment failures are marked as invalid. Using scores, termination states, check-point transitions, regressions, and path diversity, we classify each source lineage as universally easy, mostly mastered, discriminating, universally hard, unstable, or confounded. This cohort-level state determines the admissible strength of evolution while preventing transient or model-specific er-rors from becoming benchmark objectives. 

Bi-Objective Round Planning. Evolution jointly opti-mizes difficulty-frontier and feature-coverage growth at the round level. Difficulty growth requires a measurable in-crease in one or more calibrated capability demands with-out material regression of the overall task, whereas cover-age growth requires a strict set addition on either the ex-act software-taxonomy-operation surface or the capability-intensity surface. Required action families are tracked sep-arately as exposure rather than treated as agent capabilities. A shared lineage and coverage registry coordinates paral-lel workers and prevents repeated references to an already measured feature from being counted as new breadth. Indi-vidual tasks may specialize in difficulty or coverage, but the selected batch must advance both objectives in aggregate. 

Lineage-Anchored Evolution Directions. For each el-igible source, we construct candidates with four direc-tions: difficulty escalation , coverage expansion , transfer with measurable escalation , and their coherent combina-tion . Every candidate preserves a lineage anchor, the se-mantic demand that makes cross-round comparison mean-ingful, while allowing values, targets, scale, context, and supporting subgoals to change. Purely horizontal transfer is excluded: a transferred task must introduce an indepen-dently measurable demand or coverage cell. Candidates may increase precision, dependence, procedural depth, or verification requirements, but unrelated feature grafts and superficial elaboration do not constitute evolution. 

Candidate Selection Gates. A candidate is eligible only if it preserves the lineage anchor, avoids material difficulty regression, remains feasible within the interaction budget, admits a uniquely observable final state, and is justified by model-neutral evidence. Eligible candidates are ranked by feasibility, verifiability, calibrated difficulty, coverage gain, model neutrality, and naturalness; step requirements above 0.85 of the available budget are rejected. The out-put remains a general benchmark task proposal until every evolved obligation is instantiated by an executable verifier. 

3.2. Resolution: Diagnostic Task Evolution 

Diagnostic task evolution increases the resolution of evalua-tion around an individual agent’s capability boundary. This multi-agent system follows a hierarchical process: a batch-level planner converts longitudinal rollout evidence into agent-specific diagnostic dispatches, and a per-task evolver realizes each dispatch as a controlled task proposal. The ob-jective is not maximal difficulty or scope (i.e., Benchmark Evolution), but a locally attributable observation that nar-rows the agent’s pass-fail boundary. 

Target Diagnostic Cell. To allocate well-targeted dis-patches, the batch planner first separates pass, partial, con-founded, and invalid outcomes, using only observations with valid setup and verifiers as clean boundary evidence. It then aggregates multiple analytical views to identify sta-ble, failing, or insufficiently supported regions. Each dis-patch targets a diagnostic cell defined by software, feature, primary capability, and intensity, together with control di-mensions and confound limits. Priority is given to decon-4founding blocked evidence, resolving uncertain transitions, testing transfer of suspected weaknesses, expanding under-supported cells, and replicating non-monotonic results. 

KNN-Inspired Evolution Candidate Realization. For one dispatched source lineage, the task evolver constructs a local neighborhood of candidates: the requested inten-sity, a cleaner lower-intensity fallback, and, when feasible, an adjacent higher-intensity or alternate-factor probe. Each task is defined by a primary demand dimension and sev-eral secondary dimensions, all drawn from the 7D capabili-ties: scale consistency, precision control, target grounding, state-dependent reasoning, procedure following, feature in-tegration, or verification and control . Intensities are scored from 0 to 5 using dimension-specific factors derived from the instruction, initial state, and verifier obligations; they describe task demand rather than predicted agent perfor-mance (detailed in Appendix A). 

Adaptive Probe Policy. The probe direction is evidence-driven rather than assumed to be monotonically upward. Clean passes or failures adjust intensity upward or down-ward, respectively, while ambiguous results trigger correc-tive actions like deconfounding, simplification, or replica-tion. Each proposal records expected failure modes and ex-plicit verifier requirements, and it updates the agent’s ca-pability boundary only after verifier evolution and a valid rollout make the resulting evidence eligible. 

Confound-Controlled Candidate Selection. Capability demand is factorized from nuisance variables including step budget, context load and verifier risk. Candidates that vio-late dispatch limits, exceed the step budget, or lack an ob-servable outcome are redesigned or rejected. Remaining ones are ranked by dispatch alignment, diagnostic cleanli-ness, secondary coverage value, etc. This criterion deliber-ately favors a slightly weaker but cleanly attributable probe over a harder task which cannot resolve agent boundaries. 

3.3. Precision: Unified Verifier Evolution 

Verifier evolution co-evolves the measurement instrument with each task so that increased task demand remains faith-fully observable. The objective is to maximize coverage of the evolved task contract while preserving verifier lineage, grounding every check in observable state, and explicitly representing verification gaps. 

Requirement-Centric Contract Decomposition. We re-construct the evolved task contract as a set of indepen-dently testable outcome requirements derived from the ex-plicit evaluator requirements and atomic clauses of the in-struction. Target values, ordering constraints, artifact states, preservation conditions, and prohibited side effects are re-tained as first-class obligations rather than silently omitted or merged into coarse success criteria. 

State Grounding and Observability. Each requirement maps to an observable state field or artifact, a planned checkpoint, and one of three coverage states: covered, partially observable, or unverifiable. State paths must be supported by the application’s state catalog or captured snapshots; proxy checks based only on file existence, file-names, setup state, or unavailable pre-action values are disallowed. Unsupported clauses remain explicit cover-age gaps rather than unsound surrogates, avoiding selec-tion bias against complex, harder-to-inspect applications that discarding such tasks would introduce. 

Checkpoint-Lineage Transformation. Given the source verifier, each existing checkpoint receives an explicit lin-eage operation: K EEP for an unchanged obligation, M OD - 

> IFY

for a changed target or expected value, and R EMOVE for an obligation absent from the evolved task; A DD introduces checkpoints for newly required effects. The original OS-World evaluator may provide semantic evidence about in-tended facts, tolerances, and conjunction structure, but the evolved task contract remains authoritative. Optional tra-jectories and checkpoint histories are used to confirm state paths and expose regressions, while an individual failed rollout is not treated as sufficient evidence of verifier error. 

Executable Verifier Construction. To construct a veri-fier, each software is equipped with a task-agnostic adapter that probes native state-export interfaces (e.g., debug pro-tocols) to extract and normalize its snapshot into a shared 

CanonicalState schema. The transformed contract is compiled into distinct schema-grounded checkpoints, each of which checks one task effect and returns a specific expected-versus-actual reason. Every requirement must map to a checkpoint or be declared as an explicit observ-ability gap, prohibiting shortcuts like unconditional passes or inference-based fallbacks. A partially observable task remains rollout-ready when at least one meaningful target effect is soundly verified and all omissions are declared. 

Validation and Adversarial Audit. Validation separates three static gates (i.e., syntax and imports, structural con-tract, and static schema), from two behavioral gates (i.e., PRE/PASS discrimination and checkpoint-wise negative fixtures). An information-isolated pass agent independently realizes an executable PASS state and audits checkpoint necessity and completeness, while a verifier agent audits whether that state genuinely satisfies the task without access to the pass implementation. 4.3. Validation of Evolved Verifiers 

Trajectory-Level Verifier Agreement. We manually as-sess convergent validity on 400 Kimi trajectories across four evolution rounds in Figure 9. Human judgments and check-point verifiers agree on 84.0% of runs (Cohen’s κ = 0 .640 ), with agreement increasing from 81% to 89%. Continuous scores also show moderate concordance. Audited disagree-ments mainly arise from incomplete adapter state, partial verifier coverage, and state-field mismatches, highlighting the remaining observability limitations. 

Verifier Statistics. Figure 8 and Supplementary Figure 12 confirm that evolved verifiers stay tightly aligned with growing task contracts rather than collapsing into minimal checks. Across 962 tasks (4.82 checkpoints/task), atomic requirement coverage reaches 92.5% overall—exceeding 85% in nearly all apps, with lower coverage isolated to native-adapter limits (e.g., Thunderbird). Moreover, check-point counts track requirement counts along the y = x di-agonal ( r = 0 .55 –0.65 ), with P ARTIAL tasks still grounding 3–7 checkpoints; the independent trajectory audit (Figure 9) further validates behavioral precision. 

4.4. Evaluation Reliability and Evolution Efficiency 

Evaluation Reliability. Under live-VM budget and na-tive observability limits, cross-round and cross-agent com-parisons remain fair and discriminative: (1) Out-of-cohort generalization: held-out Qwen ( −26 .9) and GPT ( −24 .0)match the cohort’s difficulty progression without driving evolution. (2) Calibrated co-evolution: K EEP /M ODIFY in-heritance, isolated PASS-state solvability gates, rising hu-man agreement ( 81% to 89% ), verifier-independent 2×

step, and 2–3.5× token growth rule out verifier drift. (3) Partial-verifier symmetry: retaining sound P ARTIAL ver-ifiers preserves hard-to-inspect apps while applying identi-cal checks across all agents without artificial score defla-tion. (4) Structured discrimination: while low R4 pass rates (13 –19% ) narrow the macro spread, continuous scores lift boundary informativeness ( +20 .8 pp to 69 .7) and expose 

20 –37 pp per-app rank reversals masked by scalar means. 

Evolution Efficiency. In Figure 10, we measure the to-ken usage and API-equivalent cost of successful task and verifier evolution runs, aggregated across rounds for three diagnostic agents and the multi-agent benchmark. Costs are estimated from cached input, uncached input, and output tokens using GPT-5.5 API rates. Verifier evolution exhibits stable costs across agents, while benchmark task evolution is more expensive due to its larger shared context, indicat-ing that context construction—not verifier generation—is the primary efficiency bottleneck. 

5. Conclusion 

We present CUA-SEE, a closed-loop evaluation frame-work that co-evolves tasks and executable verifiers from computer-use agent trajectories. Benchmark evolution ex-pands difficulty and coverage, diagnostic evolution probes 8agent-conditional capability boundaries, and verifier evo-lution grounds changing requirements in audited check-points. Experiments across agents, applications, and rounds show that adaptive evaluation remains informative beyond static benchmarks while producing attributable capability evidence. These results establish evolving evaluation as a practical counterpart to increasingly capable, self-evolving agents.

A. Core Taxonomies, Capability Rubrics, and System Boundary 

This section defines the foundational taxonomies, ordinal capability rubrics, and invariance boundaries that anchor CUA-SEE across evolution rounds. 

Feature Taxonomy. As illustrated in Figure 11, we or-ganize the feature space as a four-level hierarchy spanning software, feature families, functional categories, and con-crete operations. Capability Dimensions and Intensity Rubric. Indepen-dent of software features, task demand is parameterized over seven orthogonal capability dimensions scored on an ordinal 0–5 rubric (Table 4). B. Experiment Details and Prompts 

B.1. Experimental Setup 

Evaluation scope. We evaluate benchmark evolution and diagnostic evolution on realistic Ubuntu desktop environ-ments derived from OSWorld. As shown in Figure 1 and Figure 3, CUA-SEE’s shared measurement substrate ex-pands the eight core OSWorld applications (Chrome, GIMP, LibreOffice Calc, LibreOffice Impress, LibreOffice Writer, Thunderbird, VLC, and Visual Studio Code) with twelve additional native-CanonicalState -instrumented desk-top environments—Blender, VSCodium, JupyterLab, Krita, Draw.io, SMPlayer, OBS Studio, ONLYOFFICE, Open-Screen, ComfyUI, Zotero, and Brave—bringing total soft-ware breadth to 20 applications across browsers, office suites, IDEs, creative/3D studios, diagramming, media pro-duction, and research workflows. To ensure strict task-lineage correspondence with the original R0 benchmark without confounding cross-round metrics with newly in-troduced software domains, the longitudinal multi-round panel ( R0–R4) and diagnostic matrices ( R0–R3) track the eight core OSWorld applications, while the full 20-application substrate supports broader benchmark synthesis and scope expansion. Benchmark evolution is evaluated on a heterogeneous panel of five computer-use agents: Kimi-K2.6, Seed-2.1-Pro, Gemini-3.5-Flash, Qwen-3.7-Plus, and GPT-5.5. Diagnostic evolution focuses on three represen-tative agents—Kimi-K2.6, Seed-2.1-Pro, and Gemini-3.5-Flash—because it constructs a separate, agent-conditional task sequence for each target agent. 

Benchmark-evolution protocol. We start from a fixed panel of 100 OSWorld task lineages and evolve each lin-eage for four rounds, producing the original benchmark R0

and evolved suites R1–R4. Every round retains the same 100 lineage identifiers and is evaluated by all five agents, yielding 500 task–agent observations per round and 2,500 observations over the complete trajectory. This paired de-sign prevents changes in aggregate performance from being attributed to a changing task sample. Each evolved task is also annotated with a seven-dimensional capability-demand vector on a 0–5 scale and with exact software–taxonomy– operation cells, enabling difficulty and coverage to be mea-sured independently. 

Diagnostic-evolution protocol. Diagnostic evolution is run independently for each target agent. The current ex-periment contains four 100-task rounds for Kimi and three 100-task rounds each for Seed and Gemini, for a total of 1,000 evolved task profiles. The primary diagnostic matri-ces pool a matched 100-task R0 baseline with R1–R3 for each agent, yielding 1,200 planned agent–task–round slots before rollout availability and validity filtering. Kimi R4

is included only in task-generation and verifier analyses be-cause it is outside the R0–R3 matrix scope. Profiles with-out eligible rollouts are retained as missing or unavailable evidence rather than imputed as failure. 

Rollout parameters. Each episode is limited to 50 environment-interaction steps. The environment records the complete action trajectory, the terminal normalized task score, and state-hook checkpoint traces. Concurrent orchestration. Batch analysis is performed once before each diagnostic round, after which independent task workers consume the resulting dispatch.jsonl in parallel. Benchmark tasks and task-specific verifiers are parallelized similarly, while shared feature and capability registries use atomic claims to prevent duplicated cover-age gains. The reusable runners default to three concur-rent Codex workers, a two-second launch stagger, a 45-minute per-task timeout, and resumable execution that skips already validated terminal artifacts; bounded repair and ver-ifier jobs may raise concurrency to ten. Machine-readable run summaries record task status, duration, token usage, re-tries, validation errors, and the exact output directory. 

Hybrid Codex backends. We use GPT-5.5 for task and verifier synthesis and explicitly set reasoning effort to high 

for the reported runs. Workloads are distributed across two isolated execution modes: a ChatGPT/Codex subscription backend authenticated through a persistent CODEX HOME ,and an API backend using an OpenAI-compatible Re-sponses interface through Routify. A worker uses exactly one backend; credentials and provider-specific environment variables from the other backend are removed, and there is no silent cross-backend fallback. This hybrid deployment allows subscription and API capacity to be combined at the campaign level without changing the skill, prompt contract, model identifier, or output schema. 5Validation and provenance. Task workers must produce structured task, capability-profile, analysis, and task-card artifacts, all of which pass schema and semantic consis-tency checks before entering a round. Verifier workers addi-tionally run syntax, interface-contract, schema-grounding, PRE/PASS discrimination, and negative-fixture checks be-fore a task is marked rollout-ready. Source identifiers, lin-eage operations, model/backend settings, token accounting, and rollout paths are preserved in machine-readable sum-maries. This artifact-first design makes every plotted value traceable to a task profile, one selected rollout, and one val-idated verifier.

Capability–intensity matrix. Rows are the seven capa-bility dimensions and columns are task-demand intensities 1–5. A task contributes to its primary dimension and to ev-ery supporting dimension with a positive recorded intensity. Thus, a cell answers the question “How well did the agent perform on tasks that required capability d at intensity z?” It does not estimate the causal effect of increasing intensity, because tasks in adjacent columns may differ in software, feature, and lineage. Intensity zero is omitted because it denotes no meaningful demand on that dimension. 

Software–capability matrix. Rows are applications and columns are capability dimensions. A task contributes to every positive capability demand recorded in its profile, using the same primary/supporting attribution rule as the capability–intensity matrix. The value therefore summa-rizes performance on tasks coupling a particular application with a particular capability demand. It is not a software-only score and does not imply that failures are uniquely caused by that capability. 

Software–feature matrix. Each row is an application and each cell corresponds to one top-level taxonomy feature family required by at least one profile. All required features are included, with primary and supporting roles weighted equally; leaf operations are collapsed to the top-level fam-ily only for readability. The printed percentage is the rounded mean checkpoint score over clean tasks exposing that software–family pair. A task requiring multiple feature families contributes its episode score to each corresponding cell. 

Software–action matrix. Columns represent required in-teraction families such as click, type, shortcut, menu nav-igation, dialog entry, numeric-widget manipulation, drag, and scroll. The matrix records planned action exposure from the task profile, not actions inferred from a trajectory. Its color is the mean whole-task checkpoint score for tasks requiring that action family; it is therefore not an action-localized success rate. One task may contribute to several action columns, and R0 contributes no action cells because the original tasks do not have compatible action-exposure annotations. 

Missing cells and evidence maturity. In the compact pa-per matrices, a gray cell means that no eligible clean score is available; it may be genuinely unexposed or may have planned profiles whose rollouts are censored, confounded, invalid, or missing. The annotated companion plots sepa-rate these cases: P is the number of designed profiles as-signed to a cell, V is the number of clean rollout observa-tions, gray denotes P = 0 , and light blue denotes P > 0 but 

V = 0 . We additionally report three coverage layers. Ex-posed means that at least one task profile occupies the cell, 

valid means that at least one clean observation occupies it, and well-sampled requires at least three clean observations drawn from at least two distinct base-task families. 

Matched R0 reconstruction. The original OSWorld tasks were not authored with diagnostic primary-dimension or action labels. For each agent, the R0 capability axis is reconstructed from the one-to-one R1 profile: we use the dimension selected as the R1 primary probe and that task’s recorded source-demand intensity. The full source-demand vector supplies supporting dimensions, while feature cells come from the curated R0 taxonomy sidecar. This produces a matched baseline with one observation per lineage, but it should not be interpreted as an independently annotated R0

diagnostic plan. No R0 action matrix is reconstructed. 

Diagnostic-resolution metrics. The separate diagnostic-resolution plots use manual task-level judgments and ex-plicitly exclude checkpoint scores. Only judgments marked eligible for capability analysis are included. Boundary-region density is the fraction of scores strictly between 20 and 80. Upward-probe transition yield is the fraction of clean-pass source tasks whose higher-intensity successors become partial or fail. A strict empirical boundary bracket occurs when an upward probe changes pass to partial/fail or a downward probe changes partial/fail to pass; bracket width is the absolute difference between the two capability intensities, and a width-one event localizes the boundary to adjacent levels. READY indicates that the verifier passed syntax, interface-contract, schema-grounding, and static validation gates; it is an implementation-validity sta-tus, while empirical PRE/PASS and negative-fixture tests provide the behavioral discrimination evidence. 

Uncertainty estimates. For paired R0–R4 benchmark comparisons, confidence intervals are obtained by 5,000 task-level bootstrap resamples. Intervals for changes re-sample paired per-task differences, preserving lineage cor-respondence across rounds. Diagnostic matrices report cell means together with evidence counts or evidence-maturity layers rather than confidence intervals because many cells are intentionally sparse during adaptive exploration.
