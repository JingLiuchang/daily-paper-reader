Who Remembers What? Multi-Granularity Memory Extraction for
Multi-User, Multi-Agent Interaction
Yunzhe Wang1,2*, Mesut Erhan Unal1, Sheng Zhang1, Shabnam Ghadar1, Peng Tang1∗∗
1AWS Agentic AI
2University of Southern California
{yunzhewa,meunal,szhangml,shabnam,tangpen}@amazon.com
Abstract
Self-evolving agents improve their own skills,
memory, and harness code from experience
without retraining the base LLM, and group-
evolving agents go further by sharing these
lessons across agents. Yet most such systems
overlook that sharing across users and hetero-
geneous agents requires deciding who can ben-
efit from each lesson and what information
must remain private. We present MIXUA, a
memory system that distills independent user-
agent trajectories into lessons and assigns each
lesson to a user-agent pair, user, agent, or
global scope according to whom it benefits and
what it may disclose. For evaluation, we in-
troduce CROSSLEARNBENCH, a mixed-user-
agent benchmark that pairs established agent
tasks with user preferences and privacy probes
that test whether private facts leak into mem-
ory other users can read. With five users and
seven agents, MIXUA raises pass rates by up to
16 points over no memory and 5 over a single
global memory, even on tasks previously tried
only by other users on other agents. It retains
up to 90% of previously stated preferences, and
at most 0.02% of privacy probes find a planted
private fact in a forbidden scope. We hope
MIXUA offers a scalable path toward a global
system where users and agents co-evolve.

The step from self-evolving agents to self-
evolving populations remains open (Fig. 2). Multi-
agent teams improve collectively but serve one
principal within one trust boundary (Zhang et al.,
2026; Bhattacharyya et al., 2026). Systems that
pool experience across users fix who receives it in
advance. SkillClaw (Ma et al., 2026) broadcasts
validated skills to everyone, FederatedSkill (Yang
et al., 2026a) exchanges distilled skill patches be-
tween clients that each bundle one user with one
agent, and Collaborative Memory (Rezazadeh et al.,
2025) separates private from shared memory under
access policies. A lesson can generalize along two
independent axes, across users and across agents.
Treating each axis as either specific to the lesson’s
origin or open to the whole population yields four
audience scopes, namely one user-agent pair, one
user across agents, one agent across users, and the
whole population. Existing memory systems cover
only subsets of these scopes (Table 1).
In this work, we introduce MIXUA (Sec. 3),
a cross-learning memory for mixed populations,
such as a team sharing coding assistants or a plat-
form serving many customers with heterogeneous
agentic products, where each user’s privacy must
be protected. We cast cross-learning as deciding
who reads each lesson (Sec. 3.1) and give memory
four scopes, by whether a lesson is user-specific,
agent-specific, both, or neither (Sec. 3.2). MIXUA
writes and reviews scoped entries, keeping private
evidence with its owner (Sec. 3.3), and retrieves the
most relevant ones each pair may read (Sec. 3.4).
To evaluate, we introduce CROSSLEARNBENCH
(Sec. 4), modifying established agent tasks with
planted user preferences and private facts in a
mixed-user-agent co-learning setup, evaluating util-
ity, personalization, and privacy together. To the
best of our knowledge, CROSSLEARNBENCH is
the first benchmark to measure cross-user and
cross-agent learning under privacy and preference
constraints. Our experiments (Sec. 5) show that
(1) memory sharing helps beyond private mem-
ory: four-scope memory gains up to 16 points of
pass rate against 4 for memory private to each pair,
and up to 14 even on tasks previously attempted
only by different users with different agents; (2) the
gain extends to new tasks: on tasks no user-
agent pair had attempted before, MIXUA gains
10.1 points over no memory, nearly twice the 5.5
of a single global memory; (3) utility gains coex-
ist with personalization and privacy: MIXUA
retains up to 90% of previously stated preferences,
and no more than 0.02% of probes find a planted
private fact in a forbidden scope; and (4) store
review sharpens placement, mostly improving
utility, preference retention, and privacy at once.
Our contributions are (1) MIXUA, a four-scope
memory that learns where each lesson belongs and
holds task knowledge, environment facts, and pref-
erences in one store; (2) CROSSLEARNBENCH, a
benchmark measuring utility, transfer, preference

Related work
Self-evolving agents.
Self-evolving agents turn
their own trajectories into lasting improvements
without retraining the base model, through test-
time adaptation, reusable skills and memory, or
changes to their own harness (Fang et al., 2025;
Acikgoz et al., 2026; Wang et al., 2024; Lin et al.,
2026; Yin et al., 2025; Packer et al., 2023). Multi-
agent teams extend this loop to a fixed group under
one principal (Zhang et al., 2026; Bhattacharyya
et al., 2026), and recent systems pool experience
across independent users (Ma et al., 2026; Yang
et al., 2026a). Table 1 maps representative memory
systems onto our four scopes. In most work, who
reads a memory is fixed by design, from memo-
ries serving one pair or user (MemGPT, A-Mem,
MIRIX) to shared or federated stores (G-Memory,
SkillClaw, FederatedSkill, ShareMem), while Col-
laborative Memory and AIM set it by access policy.
Agent memory and multi-user agents.
A-Mem
(Xu et al., 2025) adaptively builds, links, and
evolves memory notes, and G-Memory (Zhang
et al., 2025) retrieves a cooperating team’s hierar-
chical experience per agent. MIXUA adds explicit
ownership and audience routing, and the disclo-
sure boundaries that independent users, unlike one
team, require. Multi-user agents, in which one
agent serves several users, make access control and
memory governance central (Yang et al., 2026b;
Ren et al., 2026), and contextual-privacy bench-
marks ask whether information reaches an inappro-
priate recipient (Ruzzetti et al., 2026). We extend
these concerns to a population with many users
and heterogeneous agents, and measure leakage in
released evidence and stored memory. In addition,
LongMemEval (Wu et al., 2025) tests extraction,
multi-session and temporal reasoning, updates, and
abstention in assistant memory.
3
Method
MIXUA turns independent trajectories into one
shared memory (Fig. 3). We cast cross-learning as
deciding who reads each entry, then describe how
we write, review, and retrieve entries in four scopes
(Appendix C, Appendix H).
3.1
Problem formulation
A population has users U and agents A, where
each agent is a fixed LLM-harness configuration
and a pair (u, a) ∈U ×A is one user working with
one agent. Each attempt of a task by a pair yields
a trajectory τ and a verifier outcome y ∈{0, 1},
and a memory writer distills task trajectories into
structured memory entries e. Each entry has an
authorized audience Aud(e) ⊆U × A, the set of
user-agent pairs permitted to access it. Following
Sec. 1, an entry has a generalization scope G(e),
the pairs for which it is valid, and a disclosure
boundary D(e), the pairs it may reach without ex-
posing its origin user. We require
Aud(e) ⊆G(e) ∩D(e),
(1)
so that useful knowledge reaches every pair it can
while private knowledge stays with its owner.
3.2
Multi-granularity scopes
An entry written by pair (u, a) can be kept to its
user or opened to all users, and kept to its agent
or opened to all agents. The four combinations
give four scopes, ordered by inclusion (Fig. 16 in
Appendix C). PAIR ({u} × {a}) is read only by the
user-agent pair itself, USER ({u} × A) by the user
with any agent, AGENT (U × {a}) by the agent
with any user, and GLOBAL (U × A) by everyone.
A pair’s view V (u, a) is thus its own PAIR memory,
its user’s USER memory, its agent’s AGENT mem-
ory, and GLOBAL, never another user’s USER mem-
ory or another pair’s PAIR memory. Only opening
the user axis exposes an entry to other users, so
only that step is gated on privacy (Fig. 16).

Intuitively, each scope suits a different kind of
knowledge. GLOBAL holds what helps everyone,
such as a library defect or even the fix for one task,
and USER holds a user’s preferences, such as a
document format. AGENT holds advice for one
agent, such as a tool-calling quirk or a mistake it
tends to make, and PAIR holds a user’s preferences
that conflict across agents, such as asking a verbose
agent for terse replies but a terse one for detail.
3.3
Memory writing
In a deployed system, user-agent interactions arrive
at any time and each may hold a valuable lesson,
so memory should learn from every interaction and
periodically review the whole store. We simulate
this in rounds (Fig. 3). In each round, every pair
attempts its tasks with the memory it may read, and
the round’s trajectories are then written into the
store one at a time before the next round begins.
Dual-stream writing.
After each round, we split
each trajectory into a reusable and a protected
stream and send them to two isolated writers, so
that a writer that sees protected content never writes
a shared entry. We do not rely on the writer to label
its own entries. Instead, we label each entry by the
stream it was written from, so a protected entry can
land only in its owner’s USER or PAIR memory.
Each writer then writes memory entries based on
one stream. An entry consists of a situation (when
the lesson applies), the lesson, a scope, and prove-
nance (the originating tasks, pairs, rounds, and out-
comes). We require every lesson to be conditioned
on a situation, so that lessons stay organized and
retrieval can match them to the tasks they apply to.
To test whether the design depends on how entries
are produced, we implement two writers, an LLM
writer that returns all operations in one response
and an agentic writer that can inspect the sample
and the store and make multi-turn edits.
Periodic store review.
Since a writer sees one tra-
jectory at a time, it can scope a lesson too narrowly
or too widely, and different trajectories can yield
duplicate lessons. We therefore add an optional
periodic store review, which after every round re-
scopes each entry with the whole store in view and
then merges entries within each destination.
3.4
Memory retrieval
Before each attempt, we retrieve from the user-
agent pair’s view V (u, a). By default, we rank
the entries of each scope by the cosine similarity
between the embeddings of their situation and the
task prompt, and add them to the prompt up to a per-
scope character budget. In the file-based variant,
we instead place the pair’s view in the container as
one file per scope and instruct the agent to read or
grep it for relevant entries.

CROSSLEARNBENCH
CROSSLEARNBENCH has two layers. (1) Tasks
from established benchmarks test agents’ task suc-
cess, and (2) a user layer tests what memory retains
and leaks, which the verifiers do not measure.
4.1
Dataset
We source tasks from seven established datasets
(Appendix B, Fig. 14): AutoCodeBench (Zhou
et al., 2026a), FeatureBench (Zhou et al., 2026b),
4


SpreadsheetBench (verified) (Ma et al., 2024),
SWT-Bench (verified) (Mündler et al., 2024), US-
ACO (Shi et al., 2024), Terminal-Bench 2.0 (Mer-
rill et al., 2026), and VMax Tasks (VMax AI, 2026).
We modify the Harbor framework (Harbor Frame-
work Team, 2026) and run tasks in Docker sand-
boxes, keeping each environment, instruction, and
verifier unchanged and standardized.
4.2
Privacy injection
Cross-user sharing is safe only if private content
never reaches a scope that other users can read.
Since the source benchmarks contain no private
information and do not evaluate privacy, we test
privacy leakage by planting private facts into the
task execution environment of existing tasks, per-
sonalized for each user based on a real-world sur-
vey. We give each user a synthetic persona with
nine always-private items of personally identifiable
information (PII) and one fact per category of a
privacy survey (Pew Research Center, 2014). We
take each fact’s privacy label from per-user survey
responses, so the same category can be private for
one user and not for another, which forces a learn-
ing system to judge privacy on a per-user basis. We
plant these facts ambiently, in files with neutral
names at the project root of the task environment,
to simulate a messy workspace in which private
information is more likely to leak unexpectedly as
the agent naturally explores the environment. For
example, a half-filled loan application is planted as
form.txt (Algorithm 3). We then measure expo-
sure, how often the agent opens a planted file, and
leakage, whether a planted fact appears in the tra-
jectory passed to the memory writer, in the user’s
own memory store, or in another user’s memory
store (Appendix G).
4.3
Preference injection
Beyond privacy, sharing must also preserve person-
alization. A memory that pools lessons across users
can raise task success while forgetting how each
user expects work to be done. We similarly modify
benchmark tasks by asking the model to write a
summary document upon completion of each task,
and give each user four document preferences: a
filename, a sign-off date format, an ordered set
of sections, and one banned markup, such as em
dashes. A user has consistent preferences across
rounds but can have conflicting preferences when
using different agents. We state each user’s pref-
erences only in round 1, and later rounds rely on
memory to carry them. For scoring, we use an auto-
matic parser to check the written document and its
adherence to each user’s preferences. Appendix E
lists the exact tasks, survey data, users, and both
injection procedures, and Appendix F defines every
metric.
5
Experiments
5.1
Experimental setup
We pair synthetic users with seven LLM-harness
combinations (Claude Code with Opus 5 or Son-
net 5, Hermes and OpenClaw with Sonnet 5, and
Codex with GPT-5.6 Sol, Luna, or Terra). We
compare no memory, four single-scope stores
(GLOBAL-only, USER-only, AGENT-only, and
PAIR-only), and MIXUA with an LLM or a Codex
agent as memory writer, each with and without
store review (Table 19).
Importantly, a single-
scope store writes only its one scope but is not
limited to that scope’s usual kind of knowledge,
and it can record every lesson its audience may
read. GLOBAL-only, for example, can keep a les-
son specific to one user or agent by naming them in
the entry (when user A is working on [situation]).
Similarly, the USER-only store can write pair-style
entries by mentioning the specific agent. Since
no existing system evaluates a mixed user-agent
population on general-purpose agent tasks, these
stores also stand in for memory design in prior
work: PAIR-only for an assistant memory such as
MemGPT, USER-only for a personal memory such
as MIRIX, AGENT-only for a team memory such
as G-Memory, and GLOBAL-only for a broadcast
skill library such as SkillClaw (Table 1). We fur-
ther ablate what each scope adds by removing it
from MIXUA, which leaves combinations of the
remaining scopes (Sec. 5.3). The memory writer
uses Claude Opus 5, and retrieval uses Titan Text
Embeddings v2 (Appendices C and D). We test
scheduled task assignment (Table 2), random task
assignment with five users (Fig. 6), and a user-
scaling experiment with 20 and 100 users (Fig. 5).

Random tasks.
The scheduled assignment above
relies on repeating earlier tasks. To get closer to a
real deployment, we also evaluate under random
task assignment for eight rounds, where each round
draws 60 tasks from a 546-task pool and gives each
to a random pair. It tests whether memory also
helps on a task that no pair has attempted, where
only lessons learned on other tasks can help. We
run it for no memory, PAIR-only, GLOBAL-only,
and MIXUA (LLM) + review at 20k characters per
scope (Appendix A.2).
Metrics.
We report three main metrics: (1) util-
ity, the pass rate under each source benchmark’s
verifier; (2) preference retention, the rate of satis-
fied document checks after the round-1 statement
is withdrawn; and (3) privacy, the share of memory
probes finding a planted private fact in a forbidden
scope or a user’s preference in another user’s mem-
ory (Appendix G). Gains are in percentage points
(pp), with exact McNemar significance marked
∗p < 0.05 and ∗∗p < 0.01. Appendix F defines
each metric, and Table 9 adds context size, cost,
and efficiency.

5.3
Ablations
What each scope adds.
To evaluate what each
memory scope contributes, we test scope combi-
nations by removing one scope at a time from
MIXUA (LLM), so that removing GLOBAL, for ex-
ample, leaves USER, AGENT, and PAIR (Table 4).
Importantly, as in the single-scope baselines, the
remaining scopes can still record what the miss-
ing scope would have held. For example, without
AGENT, a GLOBAL entry could read when agent X
builds .... On utility, removing GLOBAL causes
the largest drop, cutting ∆from 15.3 to 9.0 points
and ∆cross from 13.0 to 4.6. On preferences, remov-
ing USER causes the largest drop (90% to 81%).
Although all four scopes together are best or within
run-to-run noise of the best on every measure, we
find that removing AGENT or PAIR changes rela-
tively little. We therefore build these situations as
scope probes (Appendix A.3). Crowd pass is the
share of build probes passed when each agent needs
its own build mode and every scope’s retrieval bud-
get fits about one entry. Spillover is, at the normal
budget, the share of probes whose memory shows
another agent’s mode; and leak is the share of a
user’s tasks on their other agents whose memory
shows a work context the user asked to keep with
one agent. Without AGENT, crowd pass falls from
89% to 40% and spillover rises from 44% to 67%;
without PAIR, leak rises from 22% to 95%. Both
scopes are therefore needed, where AGENT keeps
an agent’s own lessons retrievable and away from
other agents, and PAIR keeps a user’s context with
the agent it was meant for.
Held-out scope masking.
To check that each
scope holds the knowledge it is meant to, we freeze
each evolved store and, on the 20 held-out tasks,
show the agent one scope, all scopes, or a shuffled
user’s memory (Fig. 7). Although most entries are
GLOBAL task lessons, GLOBAL or AGENT alone
retains preferences no better than an empty store
(8-12%), so a user’s conventions live in USER and
PAIR. All scopes together retain 84-90% after re-
view, near the 99% of restating the preferences,
whereas a shuffled user’s memory retains about a
quarter at the same pass rate.
Robustness to memory reading and writing.
We next ask whether the performance gain comes
from the four level scopes or merely because the
four-scope store writes more text. Varying the re-
trieval budget rules this out (Table 3). We find
that at 10k characters per scope, MIXUA deliv-
ers 23k per task, under 60% of GLOBAL-only, yet
still gains more (13.1 versus 11.5 points), and on
held-out tasks 20k per scope matches the 40k pass
rate at about 20% lower cost, though preference
retention keeps rising with the budget. Replacing
retrieval with searchable files, as coding harnesses
commonly do, gains nearly as much (14.5 points),
but agents take more turns (17.0 versus 13.9) and
retain fewer preferences (75% versus 90%).
6
Conclusion
We introduced CROSSLEARNBENCH, a bench-
mark for cross-learning among heterogeneous users
and agents, and MIXUA, a memory system that as-
signs memory entry to the scope whose pairs it ben-
efits while protecting privacy. Our results show that
knowledge shared across users and agents improves
performance beyond what any single user-agent
pair gets in isolation, and this improvement relies
on the complementary roles of the four scopes. As
humans and agents increasingly coexist at scale, in-
telligence becomes collective, and knowing where
a lesson belongs may matter as much as learning it.

Limitations
Independent users and agents.
We model users
as independent principals and agents as indepen-
dent configurations, so every private fact belongs
to exactly one user and every disclosure bound-
ary stops at that user. In reality, users are related
and organized in hierarchies, from teams to de-
partments to whole organizations, each sharing its
own projects, conventions, and secrets, as with a
project secret shared within one team. Agents are
similar: sharing could happen among base models,
harnesses, versions, and even role-playing personas.
Knowledge owned by a team is neither pair-level
private nor global, which our privacy boundary rule
cannot express. Modeling relations and hierarchies
among users and agents, with sharing and disclo-
sure boundaries at each level, is future work.
Audiences between one and all.
Even within our
model, an audience is one user or all users, and one
agent or all agents, so a lesson valid for a subset,
such as one team or the agents built on one model,
must sit either at USER or AGENT, where it reaches
too few, or at GLOBAL, where it reaches too many.
Group scopes need a way to discover or declare
groups, and every audience between one and all
adds a disclosure boundary that the privacy gate
must judge. We leave group scopes, and a richer
lattice of audiences that keeps every readership
auditable, to future work.
Scale of the population.
We envision an open co-
learning system that anyone can join, but our study
has 5, 20, or 100 synthetic users, seven agents, and
at most 546 tasks over eight rounds. At global
scale the store grows without bound, many lessons
compete for one budgeted context, and a review
that reads the whole store no longer fits in one
pass. At a larger scale, memory writing could incur
a large cost. In addition, real users bring richer
needs and preference requirements. Scaling the
store, retrieval, and review of cross-learning to an
open population with real users, and bounding the
writing cost as the store grows, are future work.
Ethical Considerations
All users and personal facts in this study are syn-
thetic, which gives us known probe targets without
collecting real personal records. A deployed shared
memory would also need consent before a user’s
experience is shared, a way for users to inspect and
delete what was learned from them, and defenses
against contributors who write misleading lessons
on purpose; our design records provenance, which
makes inspection and deletion possible, but we do
not evaluate these mechanisms. Low leakage in our
probes does not justify deploying shared memory
without access control and privacy review.

A.1
Scheduled task assignment
Fig. 8 splits the gain by who tried the task before
and by agent, Tables 5 and 6 give these gains in full,
and Fig. 9 shows whose memory each agent reads.
Tables 7 and 8 and Fig. 10 report every held-out
arm, Table 9 and Fig. 11 the resources, and Fig. 12

Reading the held-out arms.
The held-out stage
complements the evolution stage rather than replac-
ing it. Evolution is itself an online test, since every
attempt is graded before the store learns from it,
and there MIXUA (LLM) + review gains the most
of any condition, both overall (16.3 points) and
on tasks tried before only by pairs sharing neither
user nor agent (13.9; Tables 2 and 5). The held-out
stage then freezes each store after round 3 and, on
20 tasks that no pair met during evolution, asks two
further questions: whether the memory still helps
with learning off, and, by masking scopes, where
each kind of knowledge lives.
On the first, MIXUA keeps the utility of a shared
store and adds the user’s preferences to it (Ta-
ble 7). With all scopes visible, its LLM store gains
the most of any store (9.4 points, against 8.0 for
GLOBAL-only and 6.2 for PAIR-only), and every
MIXUA store retains 78-90% of the preferences,
against 10% for GLOBAL-only (Table 2). Each
single-scope store is again strong on at most one
side: GLOBAL-only comes closest on pass rate but
retains no more than an empty store, and PAIR-only
comes closest on retention (79%) but gains less. Re-
stating the preferences to an empty store raises pass
rate by 3.1-5.0 points, and three of the four MIXUA
stores gain 2.5-4.5 points more than that, so the
learned memory adds to what the stated preferences
alone give. The gain also reaches datasets the re-
ceiving agent never met during evolution, where
only other agents’ experience can help (Table 8):
three of the four MIXUA stores gain significantly
there (6.9-8.6 points), and no single-scope store
does (GLOBAL-only 6.6, PAIR-only 3.0).
On the second, the masks recover the division of
labor that the four scopes are designed for (Fig. 10).
GLOBAL or AGENT alone retains preferences no
better than an empty store (8-12%), while USER
alone retains up to 91% and all scopes together
76-95%. Handing every scoped entry to the wrong
owner (shuffled user) keeps the pass rate but cuts
retention to 21-33%, so the task knowledge helps
whichever user receives it, while each user’s con-
ventions help only their owner and stay in that
user’s own USER and PAIR memory. Together,
the two stages show a gain that is earned online,
persists with learning off, and reaches datasets the
receiving agent never met, with each user’s prefer-
ences kept with that user.
A.2
Random task assignment
Design.
The pinned schedule repeats a round-1
task in 149 of 171 round-2 attempts and 154 of 171
round-3 attempts, so it measures transfer mostly on
tasks that some pair has met before. Random task
assignment draws every round afresh, sampling
60 distinct tasks from a 546-task pool (the training
split of the seven datasets, minus ungradeable tasks)
and giving each to one of the 35 pairs at random, so
a task returns in a later round only by chance and
almost never to the same pair. All four conditions
face the same task sequence, with round 1 executed
once and replayed to the others, so task difficulty
cancels in every paired comparison. We run two
seeds, each fixing every draw and assignment, for
eight rounds (480 attempts per condition and seed),
with the same users, agents, writer, privacy split,
and evaluations as scheduled task assignment and a
store review after every round, but at 20k characters
per scope, the budget that reaches the 40k held-out
pass rate (Sec. 5.3), and without a held-out stage,
since first attempts are held out along the whole
curve. Per condition, 1.4-2.0% of the attempts in
rounds 2-8 are ungraded.
Results.
Table 11 summarizes each condition,
Table 12 splits the gain by dataset, Fig. 13 shows
how the stores grow, and Table 13 varies the num-
ber of users (Fig. 5). Over rounds 2-8, MIXUA
passes 82.3% of attempts against 70.5% without
memory (11.4 points, p < 10−14), and both shar-
ing conditions need fewer turns than no memory
while PAIR-only does not. The GLOBAL scope of
MIXUA grows like GLOBAL-only (680 and 688 en-
tries after round 8) and fills its budget from round 2,
while its USER memory grows to 120 entries and
nearly fills its budget by round 6, so its delivered
context rises from 27k to 44k characters per task.

Implementation
Algorithm 1 summarizes the loop, Table 19 the
conditions, and Fig. 16 the four scopes as regions
of the user-agent matrix.
Store and delivery.
The store is flat, with one
partition for the global audience, one per user, one
per agent configuration, and one per pair. Writers
commit entries one sample at a time; the review is
a separate round-level pass. Retrieval embeds each
entry’s situation and the task prompt with Titan
Text Embeddings v2, ranks each scope’s autho-
rized entries by cosine similarity, and admits them
until the scope’s character budget is reached. The
selection is delivered as a prompt section with one
# Learned memory: <scope> header per scope
and is never written into the task workspace.
Models.
The splitter, the LLM writer, and the
store review call Claude Opus 5, and the privacy
judge calls Claude Sonnet 5; the agentic writer
runs a helper coding agent with the same store
interface. The writer sees the trajectory with the
verifier’s outcome and output tail, since why an
attempt failed makes it learnable. Appendix H
summarizes their prompts.

Experimental Details
This section gives the settings needed to rerun the
study, and Table 20 lists every model and harness.
Sampling and limits.
No temperature, top-p,
seed, or output-token limit is passed to any agent
or memory-side call, so every model runs at its
provider’s and harness’s defaults, including the de-
fault reasoning effort. Claude Code and Hermes
stop after 150 turns; Codex and OpenClaw have
no turn limit and are bounded by the task timeout.
Memory-side calls request the model’s maximum
output length, except the privacy judge, which is
capped at 1,000 tokens. Host-side model calls use
a 600 s read timeout with up to three attempts, and
the writer is re-asked up to three times when its
reply cannot be parsed.

Personas.
Each user also receives a hand-written
persona of nine PII values (name, email, phone,
home address, occupation, birth date, age, social

which are always private, and one short note-style

any match is attributable to one owner; each fact’s

Preference injection
Table 24 gives the four option pools. The filename
pool excludes the names agents choose unprompted
(e.g., SUMMARY.md), so the no-memory floor cannot
satisfy it by habit, and options are dealt rather than
drawn independently, so two users share a value
only when a pool has fewer options than there are
users. Each user is dealt one option per pool, and
the date format is overridden per harness, so the
same user expects a different date format from each
harness (Table 25).

round, so every memory condition sees the same
files, facts, and preferences for the same attempt.

Prompt Templates
We summarize the five key prompts below, con-
densed from the templates the system renders at
run time, which also give output examples and field
rules. Every memory-side prompt opens with the
same system description, so each call knows its
place in the loop, and the agentic writer and agen-
tic review receive the same rules as skill files for a
helper coding agent.
Shared preamble
You are part of a cross-learning system in which different
users send tasks to different agents. A privacy splitter divides
each graded trajectory into a reusable and a protected stream,
a memory writer turns that evidence into scoped entries, and
a store reviewer periodically re-scopes and merges entries.
Each later run reads only the entries its user and agent may
read.
Privacy splitter
Role.
Read one graded trajectory and decide who each part
may be shared with, not how much to share. Put every detail
worth keeping into exactly one of two streams.
Reusable.
The transferable technical lesson, phrased so that
a different user on a similar task could act on it, namely what
the task required, what failed, what fixed it, and what the
verifier said. Keep commands, flags, error messages, and ver-
sions. Generalize an identifying detail rather than delete it,
so /home/alice/proj/run.sh becomes <path>/run.sh.
Protected.
What is true of this user rather than of the task,
such as who they are, their employer, team, project, and
timezone, and their conventions for output, naming, and
tools. Write it to be useful, since only this user reads it.
Never.
Identity numbers or the value of any credential, in
either stream.
Output.
A reusable section and a protected section under
fixed markers, with both markers always present.
Memory writer
Role.
Given the evidence from graded runs and the entries
their user and agent can already see, decide what is worth
remembering and who may read it.
Entry.
A situation, saying when it applies in words a dif-
ferent run would recognize, and a lesson, saying what to do
with the exact filename, flag, or error text. Write only what
the run taught; an empty list is a valid answer.
Scopes.
GLOBAL is read by everyone and holds anything
not tied to one user or agent; USER by this user on every
agent; AGENT by every user on this agent; PAIR by this user
on this agent. Place by scope, not breadth, so a fact about
a single task belongs in GLOBAL. The protected call may
write only USER and PAIR.
Evidence.
The recorded verdict overrides the agent’s own
claims; a graded failure is strong evidence, while a timeout
or error establishes nothing. The benchmark’s summary
document and the memory files are not evidence about the
task.
Conflicts.
When the same user wants different things from
different agents, add a PAIR entry and keep the other. Revise
an entry the run sharpens, and delete one only when the run
disproves it, with a reason.
Never.
Identity numbers or the value of any credential, at
any scope.
Output.
A JSON array of entries (sample, situation, lesson,
scope, entry revised) or deletions (sample, entry, reason).
Store review, stage 1 (re-scoping)
Input.
Every entry with its id, scope, user, agent, stream,
situation, and lesson, but no counts or outcomes, so the text
alone is the evidence.
Moves.
One step at a time, widening from PAIR to USER or
AGENT and from either to GLOBAL, or narrowing back. Ask
whom the lesson serves rather than who produced it; two
entries stating one fact under different scopes are a reason
to widen both.
Narrowing.
Narrowing is not free. Keep a convention the
user wants from every agent at USER, and move it to PAIR
only when the user wants something different on another
agent.
Privacy cap.
A protected entry may sit at PAIR or USER,
never at AGENT or GLOBAL.
Output.
A JSON array of changed entries only (entry,
current scope, new scope, a short rationale).
Store review, stage 2 (merging)
Input.
The entries of one destination, sharing scope and
owner, in similarity-ordered slices when the destination is
large.
Rule.
Merge only entries that describe the same situation
and recommend the same behavior; similar wording is not
enough. Keep apart a do and a do-not about one tool, facts
that hold under different conditions, and a hedged claim and
a flat one.
Text.
Remove redundant wording only, keep the exact
specifics, and add nothing new; the system carries every
origin over.
Output.
A JSON array of merges (entries, merged situation,
merged lesson, a short rationale); an empty list is common.
Privacy judge
System.
You are a privacy leak auditor. Given DATA and
one question about a user, decide using only the data, and
reply YES or NO.
Question.
Does DATA reveal the candidate fact, including
through a paraphrase or equivalent wording? The candidate
is a comparison value, not evidence.
