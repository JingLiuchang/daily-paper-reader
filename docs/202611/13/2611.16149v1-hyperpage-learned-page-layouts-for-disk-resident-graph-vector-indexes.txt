HyperPage: Learned Page Layouts for
Disk-Resident Graph Vector Indexes
Xinyu Zhang1, Jingze Li1, Baihua Zheng2, Weiwei Sun1
1Fudan University, Shanghai, China
2Singapore Management University, Singapore
{zhangxinyu, jingzeli20, wwsun}@fudan.edu.cn, bhzheng@smu.edu.sg
Abstract—Disk-resident graph indexes such as DiskANN store
each vector with its graph edges as one record on SSD pages.
A search needs the page of every record it expands, so its page
reads depend on the page layout, that is, on which records share
a page. Search agents trained with reinforcement learning query
one such index run after run, and every graph traversal can be
logged with the records it expands. We therefore use the logs of a
finished run to lay out the index for a declared memory budget,
so that later runs read fewer pages. In contrast, existing layouts
such as Starling and MARGO are computed from the graph
and the vectors and use no logs. Learning a layout from logs is
challenging, because the logs must stay valid under every layout,
the saving depends on what the budget caches, and the best layout
is NP-hard to find. Our key observation is that DiskANN-style
search routes on in-memory codes and on the records it expands,
never on their page-mates. As a result, the logged traversals price
every layout by replay, and cached records add no page reads.
Accordingly, we propose HyperPage, which first builds layouts
for the declared budget on the logged traversals of the uncached
records. It then selects one layout, together with the split of
the budget between hot records and a page cache, by replaying
validation steps. In addition, a Lagrangian lower bound shows
how far a layout may be from the optimum. We learn from one
Search-R1 agent run and test on a later run with a different
reward, over 1M and 21M passages. Across seven cache budgets,
HyperPage reads 5.2% to 21.2% fewer pages than MARGO,
and no compared layout reads fewer. The advantage is largest
when the cache is small. For example, at 1% of the 1M index,
MARGO needs nearly 3 times the budget to read as few pages.
On the 21M index, HyperPage also cuts the search time per step
by up to 10.4%. The saving holds for a second agent model and
a second corpus.
Index Terms—vector search, disk-resident index, physical de-
sign, page layout, workload logs, agent search
I. INTRODUCTION
Vector databases answer approximate nearest neighbor
(ANN) queries over collections that exceed main memory. The
dominant single-node design keeps product-quantization (PQ)
codes [1] in DRAM and stores each vector with its adjacency
list in a proximity graph as one record on SSD [2]. A page
holds B records, and beam search needs the page of every
node it expands. Which records share a page changes no
answer, but it changes the page reads, so the page layout is a
physical-design decision of the vector database. It matters most
when DRAM is small next to the index. In our record format,
a billion records fill about 683 GB of pages, so a workstation
with 64 GB of DRAM [2] caches under 5% of the index after
32 GB of PQ codes.

Search agents in training issue such queries at scale.
An agent trained with group-relative policy optimization
(GRPO) [3], [4] runs for hundreds of steps, each rolling out
128 prompts eight times, and every search call can be logged
with the graph nodes it expands. A later run searches the
same corpus with the same tool under a new reward, and its
traversals overlap heavily. On the run we test on, 83.9% of
the node expansions of a rollout group repeat a node that the
group has already expanded.
We ask whether the logs of a finished run can lay out the
index so that later runs read fewer pages under a declared
DRAM budget (Fig. 1). A layout refined once then serves
every later run of a retrieval tier shared by many runs and
agents. A layout acts only on the accesses left uncached, so it
stands in for budget. We study caches of 1% to 25% of indexes
of 1M and 21M records. At equal shares, a larger index caches
more of the workload: 1% of the records serve 24.6% of the
test accesses at 1M and 36.4% at 21M.
Existing layouts use no logs or logs of another workload.
Starling and MARGO derive co-location scores from the graph
and the vectors [5], [6], and MARGO’s weights assume that
queries follow the distribution of the indexed vectors. Work-
load hypergraph partitioning [7], [8] treats logged requests as
independent lookups. None of these works bounds the reads
of the best layout from below, so none can say how much a
better layout could still save.
Learning a layout from logs meets three obstacles. First,
the logs must stay valid under every candidate layout, which
page search breaks because its walks depend on the layout.

Second, the saving depends on the buffer and the budget. Stock
DiskANN reads once per expanded node, a cache of the whole
index reads each page once under any layout, and caching hot
records shrinks the gap between layouts. Third, the best layout
is NP-hard to find once a page holds three or more records.
Swap-based search can stop a factor of B/2 from the optimum,
so a measured saving does not show how far a layout is from
the best one.
Our key observation is that DiskANN-style search routes on
in-memory codes and on the adjacency lists of the records it
expands, never on their page-mates. The expanded sets logged
in one run therefore price every layout exactly under read-once
buffers, and under a shared cache in the logged order. This
removes the first obstacle. It also shows that records held in a
memory cache add no page reads, wherever they sit. For the
second obstacle, HYPERPAGE builds layouts for a declared
budget on the logged unions of the uncached records. It then
replays validation steps of the next run to select the layout and
the split of the budget between hot records and a page LRU
(Fig. 2). For the third, a per-incidence Lagrangian relaxation
bounds the reads of every layout from below, so a measured
layout can be placed against the optimum.
We train on one run of a Search-R1 agent and test on
16,640 rollout groups of a later run with another reward, whose
prompts never occur in training. HYPERPAGE reads fewer
pages than MARGO at every budget, 16.4% to 21.2% fewer
at 1M and 5.2% to 16.9% fewer on the full corpus, and no
compared layout reads fewer. At 1% of either index, MARGO
needs 1.5 to 3.0 times the budget to read as few pages. In a 12-
thread DiskANN-based engine with equal measured memory,
HYPERPAGE cuts the median search time per step by up to
10.38% on the full corpus. This engine with HYPERPAGE’s
layout is also faster than MARGO’s page-search engine with
either layout. The saving is largest at small cache shares. When
the cache serves most accesses, a refinement that ignores the
budget reads more pages than MARGO, so the budget must
enter refinement. The saving holds for a second agent model
and a second corpus.
Our contributions are as follows.
• A replay model that prices every layout from one run’s
logs. We state conditions under which the page reads of
a buffer scope equal the connectivity of the union of its
logged expanded sets, for every layout and arrival order.
A patched DiskANN issues exactly the replayed reads.
• Cache-aware refinement and selection for a declared
budget. HYPERPAGE builds layouts on the unions of the
uncached records and selects the layout and cache split
by replay on validation steps, with MARGO, Starling and
MARGO’s partitioner on the uncached records among
the candidates. It reads fewer pages than MARGO at all
seven budgets we test.
• A map of what can be guaranteed. Under read-
once scopes, every layout reads at most B times the
optimum, swap descent can stall at B/2, a matching
reaches ⌈B/2⌉, and the problem is APX-hard. A per-
incidence Lagrangian bound places the 1M test optimum
between 543.2 and 974.4 reads per group. Under a shared
LRU no ratio in B exists, and a window bound holds
there.
II. RELATED WORK
Layouts and engines of disk-resident graph indexes:
Existing layouts of disk-resident graph indexes come from the
graph and the vectors and target single queries. HYPERPAGE
instead learns a fixed graph’s layout from a finished run’s
traversals and prices each candidate exactly under a declared
buffer and budget. Starling shuffles records into blocks to
maximize the in-block share of out-neighbors and proves
the problem NP-hard with no finite-factor approximation [5].
MARGO weights arcs by the monotonic search paths they
support, fills pages greedily, and observes that more co-
located edges need not mean fewer random I/Os [6]. The
SectorPack routine of OOD-DiskANN [9], DiskANN++ [10],
PageANN [11], GPS [12], BAMG [13] and VeloANN [14]
change the packing, graph, record format or edges, and
DGAI [15] and GoVector [16] buffer the pages of a search.
Only versions 1 and 2 of the LSM-VEC preprint use queries,
reordering a dynamic disk graph under a query-sampled edge
heatmap [17] that we port as HEAT.
Batch and agent workloads:
Agent search systems
change how a batch is searched or cached, not the page layout.
CoWalk runs an agent batch as cooperating walks that read
each page once and rank every vector of a fetched page [18],
so its walks depend on the layout. DeepResearchGym serves
deep-research agents from a DiskANN index [19], and InfoA-
gent and SemDN cache results or chunks [20], [21], which
compose with a page layout.
Workload hypergraphs and set objectives: In workload-
driven partitioning the application fixes each access set, while
HYPERPAGE’s sets are unions of graph traversals that stay
valid under every layout only when walks do not depend on it.
Connectivity partitioning of hypergraphs is classical [22], [23].
Bandana minimizes the mean number of NVM blocks that
each logged embedding lookup touches [7], and MaxEmbed
places co-appearing embeddings on SSD pages with repli-
cation [24]. SHP minimizes a probabilistic fanout of logged
queries [8]. Schism partitions a co-transaction graph [25], and
Qd-tree [26] and PAW [27] minimize the blocks a predicate
workload accesses. We adopt SHP’s objective at p = 0.5 as
P05-G.
Trace-driven clustering for graph traversals: HYPER-
PAGE extends trace-driven clustering of graphs to ANN walks
on a fixed graph, without replication. Object-graph clustering
partitions graphs weighted by successive-access probabilities
or trace-derived edges [28]–[30], and Nodine et al. bound
the speed-up of blocking for external graph search [31].
ICBL and DiskGNN lay out graphs on disk [32], [33], and
SlashBurn, Gorder and near-neighbor reordering order vertices
in memory [34]–[36].
Workload-driven adaptation of vector indexes: Unlike
systems that adapt a vector index to its workload, HYPERPAGE
changes only the node-to-page assignment of a fixed graph


index. ConStore co-locates co-retrieved documents in content
segments and rewrites them under drift [37]. Other systems
adapt partitions, trees or edges [38]–[42], storage requests [43],
result caches [44], HNSW page placement [45], tier place-
ment [46] or the graph itself [47] to the workload. Replay
prices hypothetical page layouts as what-if calls price index
designs [48], here exactly under Assumption 1.
III. PRELIMINARIES AND PROBLEM DEFINITION
We write G for the index graph and H for the workload
hypergraph.
Definition 1 (Data, index, records, pages). The dataset is
X = {xv}v∈V ⊂Rd with n = |V |. The proximity graph
G = (V, A) is fixed, with out-neighborhoods N +(v) = {u :
(v, u) ∈A} and |N +(v)| ≤R. Node v is stored as one record
of s bytes that holds xv and N +(v). With c bytes per vector
component and L2 distance, s = cd + 4(R + 1). A page has
P bytes and holds B = ⌊P/s⌋records.
Definition 2 (Layout, connectivity). A layout is a map π :
V →[k] with k = ⌈n/B⌉and |π−1(p)| ≤B for every page

Definition 3 (Logged runs, requests, groups). A logged run

our logs ν = 8, a step has 128 prompts, and a request holds

the sub-queries of σ walk independently. LD is one LRU page

scored and may enter the candidate list, so eq = eq(π) and

Definition 6 (Keyed buffer, proposed). The keyed buffer is
Sb for groups: the server keeps one page buffer per key (step,
prompt) for the generation phase of that step, which every
request must carry.
Definition 7 (Memory budget, hybrid cache). A deployment
declares a budget of D pages of DRAM for index data, a share
η = D/k of the index. PQ codes stay in DRAM in every
compared setting and are not charged to D. For a hot-record
share ρ ∈[0, 1], the hybrid cache HD,ρ spends ⌊ρD⌋pages on
a static cache of the B⌊ρD⌋records most frequent in training,
whose accesses read nothing. Its other pages form one LRU
page cache shared by all sub-queries in a given arrival order.
HD,0 is LD. At ρ = 1 every uncached access reads its own
page, so every layout reads the same. A pure page cache of
D ≥k pages reads each touched page once, and a split cache
does so when the residual pages fit in its page part. We report
η of 1, 5 and 25%, and on the full corpus also the 2 GiB
memory limit of MARGO’s evaluation [6], which is 15% of
that index.

IV. COST MODEL: WHAT A BUFFER READS
The objective of Problem 1 is useful only if it equals what an
engine pays. Every page-read number in this paper is attached
to one engine through the next lemma, its corollary, or an
explicit replay.
Lemma 1 (Per-query cost model). Let A1, A2 and A3 hold
for sub-query q. For every π ∈ΠB, Ebuf reads IObuf(π; q) =
λπ(eq) pages, and ⌈|eq|/B⌉≤λπ(eq) ≤|eq|. No engine
that satisfies A1 to A3 reads fewer pages for q. The answers
returned at fixed (L, W) are the same under every layout.
Proof. By A1 the rounds are the same for every layout. By
A2 and A3 every page of π(eq) is read at least once. Ebuf
reads a page at its first reference and never again, so it reads
|π(eq)| pages. A page holds at most B nodes of eq, which
gives the lower bound. The candidate list depends only on PQ
distances and eq, and re-ranking uses the vectors of eq, both
fixed by A1.
The same argument extends to scoped buffers once reads
are coalesced within the scope.
Corollary 1 (Scoped buffers). Let A1 and A2 hold for every
sub-query of a scope σ, and let A3 and A4 hold for its buffer.
(a) Sσ reads exactly λπ(Eσ) pages for every π and every ar-
rival order of the sub-queries of σ. No engine that satisfies A1
to A3 for the scope reads fewer. (b) λπ(Eσ) ≤P
q∈σ λπ(eq).
(c) With an LRU buffer of D ≥λπ(Eσ) pages owned by σ
alone, in place of the unbounded buffer, the reads are still
λπ(Eσ). (d) Dropping a sub-query whose string repeats one
of σ changes neither Eσ nor the reads.
Proof. (a) By A1 each eq is the same whether or not other sub-
queries run, and in any order. By A4 each page of π(Eσ) =
S
q π(eq) is read at most once, and by A2 and A3 at least
once. (b) A union of page sets is no larger than the sum of
their sizes. (c) At most λπ(Eσ) ≤D distinct pages are ever
referenced, so LRU never evicts. (d) By A1 equal strings have
equal expanded sets, so the union is unchanged.
Corollary 1 turns logged traversals into exact reads for every
candidate layout, so layouts can be compared without running
an engine. Part (a) needs no simultaneity, so a keyed buffer
stays exact under any interleaving of a group’s requests. Part
(c) does not cover a cache shared by interleaved scopes. For
LD no such identity holds, because its reads depend on the
arrival order. Replay is still exact under A1 to A3 for any
fixed order, and at D ≥k nothing is evicted, so every layout
reads each touched page once. Lemma 1 does not apply to Eps,
where the expanded sets depend on π. Engines that overlap
expansion with outstanding reads, such as PipeANN [49],
relax the best-first order of expansions, and A1 does not hold
for them either. Thus Lemma 1 covers stock DiskANN as
Enode and DGAI’s buffer [15] as Ebuf, and Corollary 1 covers
the proposed keyed buffer and the batch cache of CoWalk [18]
on one thread. The page search of Starling, MARGO and
CoWalk’s cooperative walks [5], [6], [18] is Eps.
When a layout can matter: In the DiskANN main branch
of May 2026, every frontier node receives its own read request,
and on 10K test queries each of SIFT1M, DEEP1M and T2I-
1M issued reads equal expanded nodes. A buffer such as Ebuf
is therefore the precondition for any layout effect, including
the 9% that OctopusANN reports from page shuffle [50]. A
layout also needs more than one record per page: a 384-
dimensional int8 record takes 644 bytes, which gives B = 6
at 4 KB and B = 12 at 8 KB, the format we study.

C. Refinement from the Incumbent
Algorithm 1 starts from the incumbent, which transfers
better than a start from scratch. Candidate pages of v are the
pages of its co-members within 32 positions in up to 64 of
its hyperedges, plus the pages of its graph neighbors inside
training hyperedges. We keep the ¯p = 16 pages with the
most such co-members. Covered nodes initiate moves, and any
record on a candidate page can be a swap partner. The search
is strict descent: in a fixed random node order it applies the
best move or swap, by exact gain under the hard capacity, only
if ∆F < 0. Unlike Fiduccia and Mattheyses [58], it makes no
uphill moves and no rollback, and with its candidate pages,
pass limit and tolerance it certifies no local optimum. One pass
takes O(¯pB(nnz+n degmax)) time and O(nnz+n) memory,
where nnz = P
E |E| and degmax is the largest number of
sets that contain one node.
Proposition 9 (Monotone refinement). Algorithm 1 returns π

Proof. Each applied operation has a negative exact change,

Proposition 9 rules out regressions on training scopes only.

and promises nothing beyond them.
D. Refinement and Selection for a Declared Budget
A declared budget fixes which records the cache will hold,
and the training objective should not reward placing them.
For a budget of D page slots and a hot-record share ρ, the
hybrid cache HD,ρ holds the set C of the B⌊ρD⌋records
most frequent in training (Definition 7).
Corollary 3 (Reads under a record cache). Let A1 to A4 hold
for a scope σ, and let a fixed set C of records be served from
memory. Then Sσ reads exactly λπ(Eσ \ C) pages for every
π ∈ΠB and every arrival order.
Proof. A fixed cache replaces each eq by eq \ C and changes
nothing else, so Corollary 1(a) applies to the sets eq\C, whose
union is Eσ \ C.
By Corollary 3, a record of C adds nothing to the reads
of any scope, wherever it is placed. Cache-aware refinement
therefore runs Algorithm 1 on the residual unions E \ C with
their weights. Records of C then belong to no set. They never
initiate a move, and their page slots serve as free partners for
swaps among uncached records. A second variant also freezes
the records outside the training unions on the incumbent’s
pages, because the logs carry no evidence about them. We
set ρ to the share that the incumbent chooses on validation
steps, which is known before refinement.
The misses of the page LRU of HD,ρ depend on the
arrival order, which the unions discard. Selection closes this
gap with trace replay. For a declared D, every candidate
layout, the incumbent included, is replayed under HD,ρ in
the deployment’s arrival order, which the engine can log,
on validation steps of the new run for every share ρ of a
grid. The deployment is the pair of layout and share with
the fewest validation reads, with ties going to the incumbent.
The incumbent with its best share is always a candidate, so
the selected pair never reads more validation pages than the
incumbent under the same budget.

VII. EXPERIMENTS
We ask when a learned layout reads fewer pages than
MARGO under an equal cache budget at both scales (RQ1),
which design choices produce the saving (RQ2), and how far
the layouts are from the optimum (RQ3).

D. Optimization Audit
The learned layouts read at most 2.05 to 2.20 times the
optimum under read-once group scopes, against 2.59 times
for MARGO, but the bound leaves the true gap open. On
the cold read-once group scopes of Table VI, Proposition 7
with 67 record classes gives 543.2 reads per W3-1M test
group, 2.81 times the capacity bound Lcap. The best layout
we found, refined on the test groups themselves and so only
an in-sample reference, reads 974.4, and longer runs changed
it by under 0.5%. Hence 543.2 ≤R⋆≤974.4, which gives
the ratios above. We also solve 71 smaller W3 instances to
proven optimality, with 12 to 48 records and B from 2 to 12.
On them, the bound with one class per record reaches a median
of 96% of the optimum at B = 3 and 81% to 90% at B = 12.
The bound is thus nearly tight at small B, and its looseness
at B = 12 leaves open how much a better layout could still
save. Under the shared cache of Table III, the window bound of
Proposition 8 lies 11 to 48 times below HYPERPAGE’s reads,
so the optimum of the primary metric remains open.
VIII. CONCLUSION
The logs of one finished agent run price every page layout
of a fixed disk-resident graph index, and cached records add
no page reads. Choosing a layout for a declared budget thus
becomes a measurable optimization problem. HYPERPAGE
builds layouts on the uncached part of the logged traversals
and selects one by replay. On the main workload it reads up
to 21.2% fewer pages than MARGO, most when the cache is
small. Once the cache serves most accesses, the budget must
enter refinement. A Lagrangian bound brackets the remaining
gap to the optimum. Index updates, larger corpora and the
optimum under a shared cache remain open.
