Abstract
In most LLM agents, weights are fixed after
deployment, so new information must be re-
tained in external memory. Existing approaches
often rely on predefined records and fixed or-
ganizational rules, which can not readily ac-
commodate evolving tasks and interactions.
This raises the question: can LLM agents or-
ganize their own memory using ordinary doc-
uments? We introduce self-organized memory
(SOMEM), a framework that stores memory
in linked documents. The agent decides what
to summarize, how to group related informa-
tion, and when to revise existing topics, and
every summary it produces stays linked to the
original interactions as evidence. The runtime
validates updates and automatically derives
temporal, relational, and recent-memory views
from the organized content. At query time, the
agent chooses what to search and read, fol-
lowing document links and inspecting origi-
nal evidence as needed. On LoCoMo, BEAM-
100K, and LongMemEval-S, SOMEM outper-
forms the strongest baseline by 2.66, 3.10, and
2.00 percentage points, respectively. The con-
structed memory can be reused across mod-
els, and additional reasoning effort can fur-
ther improve answer quality. These findings
demonstrate the feasibility of agents organiz-
ing and using their own persistent memory
through ordinary documents. Code is available
at: https://github.com/Qi202/SoMem.

Introduction
During deployment, LLM agents encounter new
information, including user preferences, task
progress, and changes in the environment. This
information is not incorporated into their fixed
model parameters. External memory preserves in-
formation across interactions and supplies relevant
records as context for later requests (Zhong et al.,

†Corresponding author.
2024; Packer et al., 2023). This allows an agent to
personalize its responses, continue earlier activities,
and use background knowledge acquired through
experience (Zhong et al., 2024; Park et al., 2023).
As conversations extend across sessions, such con-
text can include facts and events that are absent
from the current request but necessary for inter-
preting it (Maharana et al., 2024; Wu et al., 2025).
This persistent context makes information from
earlier interactions available alongside the model’s
pretrained knowledge.
Designing agent memory requires deciding what
to save, how to organize and update it, and how
to access it for a task (Du, 2026). These decisions
are connected: the information retained during con-
struction determines the evidence available during
retrieval and reading (Wu et al., 2025). Complete
histories preserve detail but require the agent to
locate relevant exchanges; compact records reduce
the amount of text to inspect but may omit quali-
fications or context needed later (Wu et al., 2025;
Fang et al., 2026). New interactions can also revise
an earlier fact, connect separate events, or change
the period during which a statement holds (Wu
et al., 2025; Li et al., 2026). A memory system
must therefore support both concise access to accu-
mulated information and recovery of the evidence
needed to interpret changes.
Existing methods address these requirements
through different representations and operations.
MemoryBank and Mem0 extract and update com-
pact records, while Mem0 also offers an entity–
relation graph (Zhong et al., 2024; Chhikara et al.,
2025). A-Mem generates attributed notes and
revises their associations as new memories ar-
rive; LightMem and TiMem consolidate informa-
tion through processing stages or temporal hier-
archies (Xu et al., 2025; Fang et al., 2026; Li
et al., 2026). Model-controlled memory operations
are also established in MemGPT and the vector-
backed semantic file interface of LSFS (Packer

We propose self-organized memory (SOMEM),
in which the model controls semantic organization
and the runtime maintains evidence and access con-
sistency. First, the agent chooses how to group and
revise information in Topic documents, which ref-
erence immutable Source records and from which a
small Core is promoted for persistent context. Sec-
ond, the runtime applies the same validation checks
to every revision. Once a revision is accepted, it
rebuilds the access views from the updated content
and metadata. This allows semantic grouping to
change without requiring the model to maintain
separate versions for each access structure. Third,
the agent selects further searches and reads from
its observations, returning to original records when
organized content is insufficient. The same agent
can write and read memory, and other models can
reuse the resulting workspace through the same
interface.
Our contributions are as follows:
• We formulate self-organized memory as editable
semantic content that retains links to its support-
ing evidence. Let the model decide how that con-
tent is grouped, while the runtime maintains the
access structures that serve retrieval.
• We develop a reorganization procedure that val-
idates edits and reconstructs access views, cou-
pled with sequential inspection of the evidence
needed to answer a question.
• We demonstrate the effectiveness of SOMEM
through comparisons with baselines on LoCoMo,
BEAM-100K, and LongMemEval-S, using a
shared GPT-6 Luna Reader. We also show that
SOMEM works across multiple backbones and
that the constructed memory can be reused across
models.

Method
SOMEM lets an agent organize persistent memory
through editable Markdown documents (Figure 1).
The agent uses Source records to construct and
revise Topic documents, from which a small Core
is promoted for persistent context. Deterministic
code derives Graph, Timeline, and Recent views
from Topic. The agent retrieves evidence using
search and document access tools. Implementation
details are provided in the Appendix A.

2.1
Self-Organizing Memory Documents
Information about the same person, activity, or task
can accumulate across many interactions, and later
observations may change how earlier information
should be grouped. Predefined memory schemas
constrain how this grouping can change (Xu et al.,
2025), while storing information as isolated records
can leave related evidence scattered across separate
items (Ji et al., 2026). We therefore let the agent
organize memory in editable, linked documents
whose subjects and internal structure can evolve
with the content.
At update t, the system archives new interac-
tion records xt as Source records, preserving their
original content for later reference. The agent uses
Source and existing memory to update Topic and
Core:
St = Append(St−1, xt),
(Tt, Ct) = Organize(St, Tt−1, Ct−1).
(1)
Here, St contains the archived Source records, and
Tt is the Topic document collection. Core, denoted
by Ct ∈Tt, is a size-bounded Markdown file
within this collection. The agent promotes long-
term preferences, standing requirements, and fre-
quently needed background from Topic documents
into Core. Core is placed in the initial context
of every query. The agent reads relevant Source
records and existing documents to decide what to
retain and where it belongs. It can create or re-
vise paragraphs and documents, adjust headings,
split broad topics, and regroup related information.
Edits are staged before acceptance. The runtime
checks Source immutability, document structure,
and the resolution of evidence references and links,
then installs accepted edits and rebuilds the derived
views; rejected edits preserve the prior memory
state. Periodic organization revisits changed Topic
files, while an optional final pass reorganizes the
complete Topic collection.

2.2
Automatic Memory View Derivation
Questions may access memory by relation, time, or
recency (Wu et al., 2025), which a single topical
organization does not directly support. Maintain-
ing a separate representation for each access pat-
tern, however, requires propagating every revision
across them and increases update overhead (Fang
et al., 2026). In SOMEM, the runtime derives access
views from the Topic documents maintained by the
agent, using paragraph references, event times, and

the creation order of memory units:
Gt = Graph(Tt),
Lt = Timeline(Tt),
Rt = RecentK(Tt).
(3)
Here, Gt, Lt, and Rt denote Graph, Timeline, and
Recent, respectively. These operations construct the
views without requiring the model to write each
representation separately.
Graph.
Each Topic memory unit is a node iden-
tified by bi; a reference bj ∈Li defines a directed
edge from unit i to unit j. The system parses these
references into a Relations index that records out-
going links and backlinks for each node. The agent
can therefore access both the memories cited by a
paragraph and those that cite it. Graph thus uses the
existing Topic structure without a separate relation
extraction step.
Timeline.
For each evidence annotation, the sys-
tem groups its statement sij into a Markdown file
according to the event time τij, retaining its Source
references Rij. File paths preserve the original
temporal precision: years, months, and days corre-
spond to timeline/YYYY.md, timeline/YYYY/MM.
md, and timeline/YYYY/MM/DD.md, respectively.
Each file begins with a level-one heading specify-
ing the corresponding time, followed by individual
event entries. Each entry contains the event state-
ment, a reference to its original Topic paragraph,
and references to the supporting Source messages.
Recent.
The system records the creation order
of each memory unit. RecentK uses this order to
select the K most recently created memory units
from Topic. The resulting view retains each unit’s
paragraph content, Topic location, and source refer-
ences. Recent updates automatically with memory
writes and is included in the initial context of each
query.
2.3
Multi-View Memory Retrieval
Relevant evidence depends on the question: a topic
match may miss temporal constraints, while a com-
pact fact may omit needed context (Wu et al., 2025).
Such evidence is often identified only after related
memory has been read, so a single retrieval before
answering may be insufficient. SOMEM provides
read-only operations for content search, file listing,
and document reading:
F = {Search, List, Read}.
Content search.
The agent retrieves Topic and
Source passages with BM25 (Robertson and
Zaragoza, 2009) lexical matching or dense seman-
tic search, choosing the mode for each query. Op-
tional path and date-range filters restrict the search
to relevant documents or periods. Each result pro-
vides a passage and its location, allowing the agent
to inspect the surrounding context.
Document and view access.
File-listing and
reading operations let the agent locate documents
and inspect their contents, including selected line
ranges. The agent can inspect Topic sections, read
Timeline files for relevant dates, or consult Graph
links and backlinks to locate related paragraphs.
Source references in Topic and Timeline allow it to
check statements against the original interactions.
These operations can be combined according to the
question, without a prescribed retrieval sequence.
Given a question q, the agent receives Core, Re-
cent, and a file inventory as its initial memory con-
text. The question date is also provided when avail-
able. It uses these tools to retrieve relevant memory
and generate an answer supported by the evidence:
Mt = (St, Tt, Ct, Gt, Lt, Rt),
y = Agent(q; Mt, F).
(4)
Here, Mt comprises the documents and views con-
structed above, F denotes the available read-only
access operations, and y is the generated answer.
The documents and views remain available for fur-
ther inspection through the same tool interface.

3.3
Ablation Study
Table 5 compares Full with component removals
on all LoCoMo evaluation questions. We freeze
memory and fix the Reader (GPT-6 Luna without
reasoning effort) and query settings, changing only
query-time access; w/o Topic restricts the Reader
to Source records. Additional settings, context mea-
surements, and paired results are provided in Ap-
pendix C.1.
Removing either Topic or Source reduces over-
all accuracy, with paired confidence intervals ex-
cluding zero in both cases (Table 9), supporting
the complementary roles of organized content and
original evidence. Topic groups dispersed facts into
thematic entry points, and Source preserves the
original details and context needed to verify them.
Removing Source produces the larger decline, indi-
cating that organized content complements rather
than replaces the original records.
The remaining components mainly shift accu-
racy across question types: removing Core or any
single derived view changes overall accuracy by
at most 1.30 points, and the paired intervals in-
clude zero (Table 9). Core is a small, bounded
subset of Topic that holds long-term preferences,
standing requirements, and frequently needed back-
ground, and that the Reader receives at the start of
every query, much like a system prompt. LoCoMo
contains no question type dedicated to preferences
or standing instructions, so removing Core leaves
overall accuracy unchanged; its role is to carry per-
sistent constraints rather than to supply factual evi-
dence. Removing Recent lowers single-hop accu-
racy from 94.53 to 92.51 while raising temporal
accuracy from 88.16 to 89.10. Recent preloads en-
tries selected by memory creation order, provid-
ing readily available factual cues for direct recall.
Removing this preload substantially shortens the
input to the final answer-producing call while leav-
ing the average call count similar (Table 8). The
Reader can therefore continue to inspect Topic and
Source with a more compact input, consistent with
the different evidence-selection demands of tempo-
ral questions. Removing Timeline or Graph each
lowers temporal accuracy to 86.92, consistent with
time-ordered entries and cross-document links both
helping to relate events. Together, these results indi-
cate that Topic and Source are the main contributors
to overall accuracy. The derived views provide ac-
cess paths for specific question types, while Core
carries persistent constraints that LoCoMo rarely
tests. The effects of the derived views and Core
on overall accuracy remain within sampling uncer-
tainty.

3.5
Scaling
We vary the Reader’s requested reasoning effort
while reusing constructed memory and fixed ques-
tion sets within each sweep. We measure actual
usage as the mean cumulative input and output to-
kens across Reader calls per question, excluding
memory construction and evaluation.
Increasing reasoning effort generally improves
answer quality, with more sustained gains on
BEAM’s longer histories (Figure 3). These tasks
require locating clues, following up on original
records, and integrating evidence distributed across
the history, leaving more scope for additional rea-
soning to support evidence acquisition and synthe-
sis. By allowing the Reader to continue searching
and reading as needed, SOMEM provides a way
to use additional inference resources over existing
memory.
The gains nevertheless exhibit saturation and
occasional reversals. On LoCoMo, some Readers
continue to improve at higher effort levels, whereas
others plateau or decline at the highest tested set-
ting. Additional computation therefore does not
necessarily translate into more effective evidence
use: once the available information is sufficient,
further reasoning may offer limited benefit. The
appropriate budget depends on both the Reader and
the task, rather than always favoring the highest
effort level.
Higher reasoning effort need not increase total
token usage either. On BEAM-100K, increasing
GPT-6 Luna’s requested reasoning effort from High
to xHigh improves answer quality while reducing
searches, document reads, Reader calls, and cu-
mulative token usage. This pattern is consistent
with more targeted query and reading decisions re-
ducing repeated lookups and the repeated input of
accumulated context across calls. Thus, stronger

Related Work
4.1
Memory Representation and Organization
Long-term memory systems differ in what they
store from an interaction and how they connect it
to earlier information. MemoryBank (Zhong et al.,
2024) and Mem0 (Chhikara et al., 2025) retain
compact records, and LangMem (LangChain Team,
2025) provides tools with which an agent adds,
updates, deletes, and searches memories, comple-
mented by background extraction and consolida-
tion. Nemori (Ma et al., 2026) decides what to re-
tain by how poorly an experience is predicted, and
A-Mem (Xu et al., 2025) adds attributes and asso-
ciative links to notes. MemMachine (Wang et al.,
2026b) instead stores raw conversational episodes
with limited LLM-based extraction and retrieves
them together with their surrounding dialogue.
LightMem (Fang et al., 2026) separates memory-
processing stages to reduce online cost. TiMem (Li
et al., 2026) consolidates information across tempo-
ral levels, and Mnemis (Tang et al., 2026) combines
similarity retrieval with top-down selection over hi-
erarchical graphs. Zep (Rasmussen et al., 2025)
maintains a temporal knowledge graph. Memo-
ryOS (Kang et al., 2025) moves memory through
short-, mid-, and long-term tiers, and MemOS (Li
et al., 2025) manages memory as an operating-
system resource. Infini Memory (Ji et al., 2026)
maintains topic documents through buffered writ-
ing and consolidation; ByteRover (Nguyen et al.,
2026) uses an LLM-curated context tree with ex-
8


plicit relations and provenance. SOMEM focuses
on the consistency of revision: the model edits se-
mantic content, original interactions remain acces-
sible, and the runtime reconstructs access views
after accepting a semantic edit.
4.2
Retrieval and Agent-Controlled Access
Lexical and embedding retrieval select evidence
according to its similarity to a query. Iterative ap-
proaches interleave retrieval with reasoning: IR-
CoT (Trivedi et al., 2023) retrieves with each rea-
soning step, ReAct (Yao et al., 2023) alternates rea-
soning traces with tool actions, and Self-RAG (Asai
et al., 2024) decides when to retrieve and critiques
the retrieved passages. Progressive observation also
appears beyond text: GUI-Lens (Fu et al., 2026)
lets a general-purpose VLM choose the region and
scale of each successive view for GUI grounding.
For agent memory, E-mem (Wang et al., 2026a)
reconstructs evidence within selected episodic con-
texts before answering, and MIRIX (Wang and
Chen, 2025) assigns six memory types to dedicated
manager agents coordinated by a meta manager.
MemGPT (Packer et al., 2023) exposes memory op-
erations to the LLM, LSFS (Shi et al., 2025) studies
model-operated file access, and DeltaMem (Zhang
et al., 2026) trains a single agent with reinforce-
ment learning to manage persona memory end to
end. These methods establish that memory use can
include further operations after the first retrieval
result. LLM-as-Code (Qi et al., 2026) argues that
deterministic control flow belongs in program code,
with the LLM invoked only for reasoning or gener-
ation; SOMEM applies a similar division to mem-
ory, leaving semantic organization to the model
while code validates edits and derives access views.
SOMEM combines continuing access with agent-
organized documents and resolvable source refer-
ences.
5
Conclusion
Through SOMEM, we demonstrate the feasibility of
LLM agents organizing their own persistent mem-
ory. The agent uses ordinary Markdown documents
to decide how information is summarized, grouped,
and revised, while the runtime preserves source ev-
idence and maintains consistent access structures.
Experiments on three memory benchmarks demon-
strate the effectiveness of this approach, and Lo-
CoMo component analyses clarify the roles of orig-
inal evidence and organized Topic documents. The
resulting memory can be reused by different Read-
ers and supports further improvements through ad-
ditional reasoning effort, with lower token con-
sumption in some settings. These findings show
that LLM agents can both read external memory
and shape how it is organized and evolves, pro-
viding a reusable knowledge base for subsequent
tasks.
6
Limitations
Full-dataset comparisons on three benchmarks and
component ablations on LoCoMo primarily evalu-
ate memory-based question answering over con-
versation histories; they do not fully cover sus-
tained personalization or task execution during
long-term interaction. Reasoning-effort analyses
use fixed subsets, and their trends warrant valida-
tion on larger question sets and across repeated
runs. Evaluation relies on LLM judges without sys-
tematic human calibration and may be affected by
judge biases.
Component ablations restrict access to frozen
memories rather than testing how memory would
be reconstructed or reorganized after removing a
component; each condition is a single run, and
the overall effects of Core and individual derived
views on LoCoMo fall within sampling uncertainty.
Reasoning-effort settings also differ in implementa-
tion across models and providers, so their labels do
not represent equivalent compute budgets; cross-
model comparisons reflect performance under the
respective configurations.
Memory construction, maintenance, and multi-
round reading incur additional overhead, whose
trade-off with answer quality depends on the model,
task, and access strategy. The runtime checks ev-
idence references and structural consistency but
cannot guarantee the semantic correctness or com-
pleteness of memory content. Detecting and cor-
recting omissions or errors during continued up-
dates therefore remains an important direction for
further study. Practical deployment additionally re-
quires access controls, retention policies, and iso-
lated tool execution for the stored conversations.

Implementation Details
Validated memory updates.
Free-form editing
by an LLM can silently break the structure that
later queries rely on, for example by dropping an
evidence reference or pointing a link to a miss-
ing paragraph. SOMEM therefore stages every edit
and installs it only after the runtime checks Source
immutability, Topic paragraph structure, the res-
olution of source references and links, temporal
values, and allowed paths; Core additionally passes
reference and capacity checks. Accepted edits are
normalized, relative links affected by moves are
repaired, and Graph, Timeline, Recent, and the file
inventory are rebuilt, while a rejected edit leaves
the previous state unchanged. These checks pre-
serve document structure and resolvable evidence
links during reorganization; factual interpretation
remains the responsibility of the model.
Incremental organization.
New interactions are
archived as Source before the Writer integrates
their information into existing Topic and Core
content. Periodic organization revisits Topic files
changed since the preceding pass, allowing the
agent to revise grouping and document structure
as related information accumulates; an optional
final pass covers the complete Topic tree. Both
integration and reorganization use the validation
procedure above, so the runtime reconstructs ac-
cess views from the accepted content. An optional
post-write probe asks a factual question about a
new interaction and triggers targeted repair when
the memory cannot answer it.
Query interface.
At query time, the agent
receives Core, Recent, the file inventory, and the
question date when available, and can list and read
files, run exact-text, BM25, or embedding search,
and inspect Source records directly. No fixed order
of operations is imposed, so the agent can enter
through a Topic document, a Timeline date, or
a search hit, and then follow links and source
references as needed. The split search interface ex-
poses
bm25_search
and
embedding_search,
together
with
list_memory_files
and
read_memory_file;
the
latter
accepts
line
offsets and limits. A combined search inter-
face exposes lexical and dense modes through
memory_search. All main experiments use the
split interface. The read-only shell interface
supports file listing (ls, find), literal search (rg,
grep), and reading (cat, sed). These interfaces im-
plement the search, listing, and reading operations
described in Section 2.3. Figure 4 illustrates one
update and the corresponding evidence inspection.

LoCoMo Answer Judging
Your task is to label an answer to a question as ‘CORRECT’ or ‘WRONG’. You will be given the following data:
(1) a question (posed by one user to another user),
(2) a ‘gold’ (ground truth) answer,
(3) a generated answer
which you will score as CORRECT/WRONG.
The point of the question is to ask about something one user should know about the other user based on their prior
conversations. The gold answer will usually be a concise and short answer that includes the referenced topic, for example:
Question: Do you remember what I got the last time I went to Hawaii?
Gold answer: A shell necklace
The generated answer might be much longer, but you should be generous with your grading - as long as it touches on the
same topic as the gold answer, it should be counted as CORRECT.
For time related questions, the gold answer will be a specific date, month, year, etc. The generated answer might be much
longer or use relative time references (like “last Tuesday” or “next month”), but you should be generous with your grading -
as long as it refers to the same date or time period as the gold answer, it should be counted as CORRECT. Even if the
format differs (e.g., “May 7th” vs “7 May”), consider it CORRECT if it’s the same date.
Now it’s time for the real question:
Question: {question}
Gold answer: {gold_answer}
Generated answer: {generated_answer}
First, provide a short (one sentence) explanation of your reasoning, then finish with CORRECT or WRONG. Do NOT
include both CORRECT and WRONG in your response, or it will break the evaluation script.
Just return the label CORRECT or WRONG in a json format with the key as “label”.

D.1
Reader Scaling Details
Tables 14 and 15 give the numerical values plot-
ted in Figure 3, on the same 100 LoCoMo and
200 BEAM-100K questions. Input and output are
summed over the Reader calls contributing to each
adopted answer and then averaged over questions.
Input includes cached, cache-creation, and repeated
context; reported reasoning tokens are included in
output once. Construction, judging, abandoned at-
tempts, and separate auxiliary session requests are
excluded. These are token-usage measurements,

settings.
D.2
Construction and Query Resources
The following resource measurements supplement
the Reader-only scaling analysis. Construction is
counted once, whereas query resources accumulate
over answered questions.
Cost is concentrated in reusable input context.
On the full LoCoMo benchmark, SOMEM reaches
88.96% LJ accuracy at a total reference cost of
$229.73, compared with $6.75 for Mem0 (80.32%),
$6.46 for LightMem (77.99%), and $35.19 for A-
Mem (60.06%) (Figure 6). Of this cost, $118.85
is one-time construction, and querying costs about
$0.07 per question. Input context dominates the
usage, and 66.3% of input tokens are cache hits
across the recorded calls; charging cached input at
10% of the input price lowers the total to $96.33.
The cross-model reuse experiment in Section 3.4
shows how a construction cost can be shared across
subsequent queries and Readers. In separate Reader
runs, querying averages 5.2–7.4 model calls and
about 20 seconds per question (Table 16).
