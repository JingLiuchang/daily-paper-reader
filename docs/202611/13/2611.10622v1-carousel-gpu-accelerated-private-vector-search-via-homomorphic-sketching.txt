ABSTRACT
Vector search on untrusted infrastructure exposes the query embed-
ding, a faithful summary of the user’s intent. Fully homomorphic
encryption can hide the query, but existing approaches still require
a full scan followed by ranking of encrypted scores. Scalable private
systems avoid encrypted ranking by either sending scores from
a single cluster to the client or moving the search to the client,
which must first stream the entire vector index for preprocessing.
We present Carousel, which instead scores the full corpus under
encryption and compresses the results for client-side ranking. The
server scores every vector under encryption, raises the scores to a
power that preserves their order by magnitude while suppressing
all but a handful, and compresses the resulting sparse vector into a
logarithmic number of ciphertexts using homomorphic additions
alone. Because every vector is scored, Carousel incurs no recall
loss from discarding candidates. Since clients hold no database-
dependent state, insertions and deletions take effect immediately at
the cost of a single vector write. Carousel searches 1 billion vectors
of BIGANN SIFT1B across multiple GPUs and achieves recall@100
of 0.9715. At 100 million SIFT vectors, it achieves recall@100 of
0.9845 with a query latency of 3.735 seconds on a single GPU.

INTRODUCTION
Modern information retrieval systems increasingly rely on vector
similarity search as their principal operation. Documents, images,
code, and product catalogs are embedded into a high-dimensional
space in which semantic similarity is inner-product proximity, and
a query is answered by finding the stored vectors nearest to the
query’s embedding. Search engines, recommendation systems, and
retrieval-augmented generation pipelines all depend on this primi-
tive, and vector databases serving hundreds of millions of embed-
dings are now routine infrastructure [31]. The first step of every
such query, however, is to hand the query embedding to the server
and that embedding is a faithful summary of what the user wants
to know. This is a privacy risk as search queries reveal sensitive
personal information such as where they are, what they are doing,
or what they are living through [5, 13].
Efficient vector search algorithms [27] typically rely on query
dependent access patterns, which requires that the query remain in
plaintext. For a search to be completely private, the server’s actions
must be completely independent of the query itself. This means the
server cannot skip over any part of its index, because the decision to
skip would reveal information about the search i.e. which part of the
index were not relevant to the query. Private search therefore forces
a linear scan on every request, and recent literature is organized
around either paying for that scan or avoiding it by preprocessing.
Every approach considered so far in the literature costs something
that the user notices.
These costs usually appear as either massive communication
overhead or reduced search accuracy. Systems that offer the strongest
privacy, where the server learns nothing at all about the query, face
this tradeoff clearly. For example, Tiptoe [15] suffers from a drop
in search quality, while PACMANN [33] relies on heavy prepro-
cessing that requires the server to stream the whole index to the
client. Even relaxing the privacy guarantees does not solve the
problem. Wally [6], which uses weaker differential privacy, does
not improve search quality significantly. Thus, the fundamental
challenge remains unsolved, providing complete privacy and high
search accuracy without a heavy communication cost.
To resolve this challenge, this paper presents Carousel, a GPU-
accelerated vector search system that achieves complete privacy
with high search accuracy and low communication overhead. The
tradeoff prior systems face is not strictly necessary. Rather, it arises
from how they choose to reduce communication overhead. The fun-
damental problem is that an exhaustive scan produces a relevance
score for every document, creating a response far too large for
transmission. Prior systems (Tiptoe, Wally) address this by pruning
the database before the query arrives, estimating which documents
are relevant and this filtering causes loss of accuracy. Carousel
avoids this by scoring every document and compressing only the
final answer, discarding nothing before ranking is complete.
Carousel executes this secure scan using Fully Homomorphic
Encryption (FHE) [9, 12], which enables the server to perform ad-
ditions and multiplications directly on ciphertexts. Selecting the
best matches from the resulting scores, however, requires compar-
ison, which FHE does not support natively. A single comparison
must be approximated by a high-degree polynomial, making the
sort needed to rank even a few hundred encrypted scores cost sec-
onds [28]. Avoiding this sort leaves the server unable to select the
top matches, so it would have to return every score for the client to
rank. To overcome the bottleneck of returning millions of encrypted
relevance scores, Carousel employs a sketch, a compact summary
of a large number of vectors that preserves its largest entries for
later recovery. However, sketching techniques fundamentally rely
on data sparsity, assuming that the vast majority of entries are near
zero. A list of relevance scores violates this assumption as most
documents exhibit a modest, non-zero similarity to the query, and
even the top matches sit only marginally higher than this baseline.
To make the score list sparse without altering which documents
rank highest, we introduce a step called sharpening. The server
raises every encrypted score to a power, preserving their ordering
by absolute magnitude. Since all scores fall between -1 and 1, larger

values shrink far more slowly than smaller ones. After this opera-
tion, the broad middle of poor-to-modest matches collapses rapidly
toward zero, while the highest scores retain their magnitude. This
widens the numerical gap between the top matches and the rest,
allowing a sketch to compress the results while preserving high
retrieval accuracy.
The sketch itself is constructed using only addition, the cheapest
operation FHE offers. The server compacts the sparse scores into
a few compact summary rows and returns those in place of the
millions of initial scores. The client then decrypts the rows and
recovers the top matches locally. Therefore, every comparison in
the system occurs on the client after decryption. This ensures that
the server never has to compare or sort encrypted values, avoiding
the step that is expensive under encryption.
The matches the client recovers, however, are positions in the
index rather than the documents themselves. To fetch the indexed
data without revealing which the client wants, it uses private infor-
mation retrieval (PIR), a protocol that allows a client to read an entry
from a server-held database while the server learns nothing about
which entry was read [16, 24, 32]. Carousel addresses only the
ranking step and composes with any PIR scheme for the retrieval
that follows. The two together form an end-to-end private pipeline,
the query stays hidden during search, and the retrieved documents
stay hidden during retrieval.
Carousel’s design also enables efficient online updates. It main-
tains a flat array of vectors, without a clustering or graph index to
update. Insertions append a vector, and deletions zero its coordi-
nates. When encoded diagonals are cached, only the affected blocks
need to be refreshed. These changes require no client-side refresh of
corpus-dependent search metadata. Tiptoe [15] describes support
for continuous updates by assigning new or modified documents to
clusters and distributing updated centroids and metadata to clients,
but does not evaluate update latency or query performance under
concurrent updates. We evaluate both the cost of insertions and
deletions and their impact on query latency under sustained update
workloads.
We implement Carousel using CKKS [9], a fully homomorphic
encryption scheme, and support both single- and multi-GPU exe-
cution. On MS MARCO, Carousel reaches an MRR@100 of 0.303,
matching a non-private graph index and exceeding Tiptoe at 0.13,
Wally at 0.18, and Pacmann at 0.266. On SIFT-100M, it achieves re-
call@10 of 0.9785, compared with 0.90 for Pacmann, and completes
each query in 3.735 seconds on a single GPU. On BIGANN SIFT1B,
Carousel searches all 1 billion vectors across multiple GPUs and
achieves recall@100 of 0.9715.
Carousel makes the following contributions:
• A private vector-search design that compresses the answer
with a sketch rather than pruning the database, matching
non-private search quality with logarithmic communica-
tion and cryptographic query privacy.
• An encrypted pipeline that sparsifies scores through power-
based sharpening and moves all ranking to the client, avoid-
ing encrypted comparison.
• A dynamic, GPU-accelerated implementation that supports
single-write updates and multi-GPU execution, evaluated
on SIFT, MS MARCO, and GIST at scales up to 109 vectors.

BACKGROUND AND PRELIMINARIES
2.1
Private Vector Search
A vector search index holds a database D = {𝑣1, . . . , 𝑣𝑁} of 𝑁
vectors in R𝑑, obtained by passing documents, images, or other
content through a pretrained embedding model. A client holding a
query vector 𝑞∈R𝑑wants the identifiers of the 𝑘database vectors
most similar to 𝑞, which for the embedding models used in this
paper means largest inner product ⟨𝑞, 𝑣𝑖⟩. All vectors are normalized
to unit length, so the inner product coincides with cosine similarity
and lies in [−1, 1].
In the private version of this problem, the server must learn abso-
lutely nothing about the query, 𝑞. We guarantee this using standard
semantic security for the query. Our threat model assumes a single
semi-honest server that follows the protocol, but still attempts to
deduce the query from its observations.
Definition 2.1 (Query privacy). Let ViewS∗[C(𝑞)] denote the
view of a server S∗in its interaction with a client that searches for𝑞.
A private vector search protocol satisfies query privacy if, for every
S∗and every pair of queries𝑞0,𝑞1, the distributions ViewS∗[C(𝑞0)]
and ViewS∗[C(𝑞1)] are computationally indistinguishable.
The view includes every message the server receives, the mem-
ory it touches, and the sizes and timing of the responses it returns.
Definition 2.1 forces all of these to be independent of the query,
which is the formal statement of the linear scan requirement dis-
cussed in Section 1. Table 1 collects the notation used throughout.
2.2
Fully Homomorphic Encryption
Fully homomorphic encryption (FHE) allows a server to compute
on encrypted data without decrypting it. Given an encryption of
𝑚and public evaluation keys, the server can evaluate a supported
function 𝑓to obtain an encryption of 𝑓(𝑚), without interacting
with the key holder. Many practical schemes derive their security
from the ring learning with errors assumption [26].
We use CKKS [9], which supports approximate arithmetic on
real or complex numbers and is well suited to computing similarity
scores. A fresh ciphertext consists of two polynomials in the ring
𝑅𝑄= Z𝑄[𝑋]/(𝑋𝑛+ 1), where 𝑛is a power of two and 𝑄is the
ciphertext modulus. CKKS packs up to ℓ= 𝑛/2 values into the slots
of a single plaintext polynomial, allowing additions and multipli-
cations to operate on all slots simultaneously in a SIMD manner.
During encoding, a scaling factor Δ controls the precision with
which these values are represented in the integer polynomial ring.

Decryption and decoding recover approximate values, and homo-
morphic operations introduce and propagate numerical errors. The
encryption parameters must therefore provide sufficient precision
for the intended computation.
CKKS supports a bounded number of multiplication stages through
a modulus chain, 𝑄= 𝑞0𝑞1 · · ·𝑞𝐿. Multiplying two ciphertexts at
scale Δ produces a ciphertext at scale Δ2. A subsequent rescaling
operation divides the scale and modulus by one prime, bringing
the scale back near Δ and consuming one level. The circuit’s mul-
tiplicative depth, the largest number of sequential multiplication
stages along any computation path, must therefore fit within the
available level budget. Longer computations require bootstrapping
to refresh the ciphertext and restore usable levels, at substantial
computational cost. We design Carousel to complete its encrypted
computation within the initial level budget, avoiding bootstrapping
entirely.
Table 2 lists all the standard homomorphic operators we use in
our system, along with their required keys and relative computation
costs. These costs vary widely and this variation directly shapes how
we design our pipeline. For example, rotation is highly expensive
because it relies on key switching, which dominates both runtime
and memory. Every distinct rotation shift requires the server to
hold a separate, multi-megabyte evaluation key. In our setup, each
key is about 10 MB, so minimizing the total number of rotation
keys is a critical goal. Finally, computation cost scales with the size
of the ciphertext, meaning it is always cheaper to compute at a
lower multiplicative level than at a higher one.

The asymmetry in computational costs among FHE operators
introduces two fundamental constraints that shape our system ar-
chitecture. First, an operator built exclusively from Add and MulPt
consumes no evaluation keys, adds no depth, and introduces no key
switching error, which makes it qualitatively cheaper than one that
uses rotations. Second, comparison is not a native FHE operation.
Sign, minimum, maximum and argmax must be approximated by
compositions of high degree polynomials [10], each consuming sev-
eral levels, which is why selecting the top 𝑘entries of an encrypted
vector is expensive even for a few hundred candidates [28]. This is
the reason Carousel performs no comparison under encryption.
2.3
Prior Approaches to Private Vector Search
Private nearest-neighbor search splits into two families. Interactive
protocols built on secure multi-party computation can exploit an
index and so avoid touching the whole database, at the price of many
rounds and of trust assumptions such as non-colluding servers.
Non-interactive protocols built on homomorphic encryption need
one round and one server, but must compute over every record.
Carousel belongs to the second family.
Private search over a public corpus. Our design directly com-
pares to existing architectures that hide only the query while relying
on a public corpus and a single untrusted server. Coeus [1] first
posed the problem for text, privately scoring Wikipedia articles with
tf-idf at a cost that does not reach web scale. Tiptoe [15] replaced
tf-idf with semantic embeddings, reducing private search to private
nearest-neighbor search, and answered it with a preprocessing-
friendly linearly homomorphic scheme [16] together with cluster-
ing to bound the response size. Clustering partitions the corpus
offline, typically by 𝑘-means, which groups vectors around a set
of centroids so that each vector belongs to the centroid nearest it.
At query time the client probes only the cluster whose centroid
is closest to its query, so the server effectively scores a fraction of
the corpus rather than all 𝑁. Tiptoe [15] uses
√
𝑁clusters, and a
relevant document outside the probed cluster cannot be retrieved.
Wally [6] keeps the clustering and relaxes the guarantee instead,
revealing the probed cluster under differential privacy using cover
queries routed through an anonymity network. Its overhead falls as
the concurrent client population grows but it requires an anonymity
network to strip identifiers and shuffle requests. Pacmann [33]
moves graph traversal to the client. Starting from an entry node,
the client repeatedly uses preprocessing PIR [32] to fetch the neigh-
bor list of the node closest to the query until the search converges.
This shifts most computation and state to the client and before
querying, it must stream the entire graph index and store 0.6 GB of
hints for three million vectors or 2.9 GB for one hundred million.
Each query also requires 20–30 sequential network rounds. These
three systems form our baselines.
Other private nearest-neighbor protocols. Another line of work
uses interactive multi-party computation (MPC). SANNS [8] com-
bines distributed oblivious RAM and garbled circuits, while Pan-
ther [25] reduces communication through batch PIR. Both use a
single server and prevent the client from learning anything about
the corpus beyond the search results. Servan-Schreiber et al. [30]
instead require two non-colluding servers to obtain sublinear com-
munication. Compass [34] considers a different setting, where the
client encrypts and uploads its own corpus, protecting it from the
server. GraSS [21], the first fully homomorphic graph index, still
takes hours per query on datasets much smaller than ours. Because
of this cost, prior work viewed fully homomorphic scans as im-
practical. HANNS [29] also assumes that non-interactive search
requires a full scan, but lowers its cost by ordering clusters to reduce
encrypted comparisons and quantizing vectors to reduce storage.

3.3
Encrypted Scan
Query expansion. The scan needs one copy of the query aligned
to each of the 𝑑diagonals. The client uploads only one ciphertext,
so the server produces the rest itself. The uploaded query repeats
with period 𝑑, so rotating it by one slot advances every slot to the
next coordinate. The server therefore builds copy 𝑘by rotating the
uploaded query 𝑘slots, giving RQ[0], . . . , RQ[𝑑−1]. Every copy

3.4
Sharpening the Score Vector
The vector inner products after the scan are not sparse. A large
number of documents score modestly and the good matches are
only slightly above them. A linear sketch cannot compress scores
with this distribution. We therefore reshape it by raising every score
to a power 𝑝, which the server does by squaring nsq = log2 𝑝times.
Each squaring costs one level and one relinearisation. Squaring
contracts every score, but it contracts small scores faster than large
ones. A score of 0.95 raised to the power 16 becomes 0.44, while
a score of 0.60 falls to 2.8 × 10−4 and a score of 0.30 to 4.3 × 10−9.
The gap between the head and the bulk therefore widens by orders
of magnitude. After nsq squarings only a handful of entries remain
within a few percent of the peak, and the rest are numerically zero.
The score vector is now sparse enough for the sketch to compress.
The operation also preserves the order of the surviving scores,
so sharpening costs no accuracy in the ranking. This holds for non-
negative scores. An even power maps −𝑠and 𝑠to the same value,
so a score close to −1 would survive sharpening and be reported
as a strong match. In practice this does not arise, because the most
negative score a query encounters is far smaller in magnitude than
its largest positive score and the ratio is suppressed by the power 𝑝.
The exponent depends on the distribution of the cosine scores of
the corpus. A small 𝑝leaves the bulk uncrushed, and the decoder
cannot separate the true matches. On the other hand, a large 𝑝drives
even the strong scores below the noise floor, where they are lost.
The usable range depends on how cleanly a corpus’s true neighbors
separate from the bulk, and on the corpus size. The exponent also
fixes the encryption level, 𝐿enc = nsq + 1, so changing 𝑝changes
the depth of the modulus chain.

In the ideal case, a heavy item occupies a given slot in exactly
one block ciphertext, while every other block ciphertext holds a
value near zero at that position. The client decrypts the rows and
inspects row0 to identify the heavy slots. For each candidate slot,
the client evaluates which of the remaining rows contain a large
value and which remain near zero. This binary pattern directly
reconstructs the codeword of the originating block ciphertext. For
example, consider slot 3 in Figure 5, where all block ciphertexts ex-

values across all rows at this slot yields the vector ⟨𝛼, 0, 𝛼, 𝛼⟩. By
matching this non-zero pattern to the known codewords, the client
determines that the item originated from block ciphertext 6.
The idealised assumption fails due to two reasons. First, the block
ciphertexts that do not hold the heavy item do not contribute zero.
Each row sums many block ciphertexts, and every block carries
a residual bulk left over from sharpening, so a slot that should
contain a near zero value instead holds the accumulated bulk of
all the block ciphertexts added into that row, together with the
encryption noise of CKKS. Therefore the entries are not exact but
large and small values, and the more block ciphertexts contribute
to a row, the larger the small values grow. Reading each row as
an exact bit becomes unreliable due to noise corrupting some of
the values. Second, two heavy items can occupy the same slot in
two different block ciphertexts. Their codewords are then added
together, and the client sees the sum of two codewords rather than
one. As a result, the collision of two heavy items in the same slot,
introduces a secondary challenge for the client-side decoding phase.
The first problem is resolved by replacing standard binary la-
bels with a more robust codeword assignment. With plain binary
codewords, two block codewords can differ in a single bit, for ex-
ample, codewords of blocks ciphertext 4 and 5 differ only in the last
position. This means a single unreliable row can turn one block’s
pattern into another’s. The solution is to read the rows not as exact
bits, but as a pattern to be matched to the nearest codeword. To en-
sure that this nearest match remains unambiguous under noise, we
draw the codewords from a code of minimum Hamming distance
three[20]. Because any two codewords now differ in at least three
positions, the true codeword stays closest to the observed pattern
even if one row is completely corrupted. This spacing makes the
decode robust to the residual bulk and encryption noise.
Carousel constructs the robust codewords using a randomized
procedure. It begins with the 𝑚-bit representation of each block ID
and repeatedly samples a random linear combination of the ID bits,
appending the resulting bit to every block’s codeword. Sampling
continues until every pair of codewords has Hamming distance at
least 3, producing an 𝐿-bit base codeword. Carousel then samples
𝑟𝑝additional combinations in the same manner and appends them
as extra measurement bits, yielding a codeword 𝑐(𝑏) of length
𝐿+ 𝑟𝑝. Each codeword position defines one fold row, so together
with the all-ones row0, the server returns 𝑅= 1 + 𝐿+ 𝑟𝑝rows.
The augmented codewords form the columns of 𝑀∈0, 1(𝑅−1)×𝐵.

3.6
Updates
Carousel maintains a flat index which is a array of vectors divided
into many blocks. These blocks are encoded into diagonals and
each query reads from these encoded diagonals. Each group of 𝑑di-
agonals contain coordinates from ℓvectors of the same block. Since,
a vector contributes one entry to each of its block’s 𝑑diagonals,
the cost of an update is re-encoding of these 𝑑diagonals.
Insert. An insert appends the new vector to the array. If the last
block has available rows, the vector fills the first spare row. Other-
wise, a new block is allocated for it. Because the vector index and
the downstream PIR store share a single identifier space, they must
remain synchronized. The record is appended to the PIR store first,
and then the new vector is added to the vector index. This ordering
guarantees that every identifier returned by the search is already
present in the PIR. Consequently, the underlying PIR scheme must
support append operations [22, 23]. If the block count 𝐵increases
after any insertion, the fold matrix 𝑀and the number of rows 𝑅also
need to be recomputed. Since 𝑀is public and entirely generated by
a shared seed, the server transmits only the new 𝐵and each client
regenerates 𝑀locally.
Delete. A delete zeroes all of the 𝑑coordinates of the target vector.
A zero vector has inner product zero with every query, so the vector
scores zero before and after sharpening, and has no effect on the fold
row. Thus, once the block is re-encoded the index of the vector is
unreachable. Because the search never exposes the identifier again,
the matching PIR record does not need to be removed immediately.
It can be lazily reclaimed later during compaction.

scalability, and update performance. We also conduct various abla-
tion studies to examine its principal tradeoffs, including projection
width versus retrieval quality and response size versus recall. Finally,
we compare Carousel with prior private vector-search systems.
Experimental setup. We run all server-side computations on a
single NVIDIA RTX 5090 GPU with 32GB of device memory under

4.4
Updates and Freshness
Section 3.6 describes Carousel’s update mechanism: insertions ap-
pend vectors to the database, while deletions zero the corresponding
rows. Ensuring next-query freshness presents different challenges
in the cached and recompute modes. We evaluate the update cost
and behavior under sustained write loads in each mode below.
Recompute mode. When the encoded diagonals exceed device mem-
ory capacity, Carousel constructs them on demand for each query.
Although recomputation increases query latency, it simplifies up-
dates because each update is an 𝑂(𝑑) write to the flat vector array.
Because the next query constructs its diagonals directly from this
array, it automatically observes the updated data without cache
invalidation or derived-state maintenance. We measure this write
path against the SIFT-100M database, which contains 100𝑀128-
dimensional vectors and occupies 25.6 GB. A single insertion takes
4.00𝜇s, corresponding to 250,000 insertions per second and a dele-
tion takes 3.25𝜇s, or 308,000 deletions per second. Batching further
amortizes the write overhead: batches of 10,000 insertions and dele-
tions complete in 8.8𝜇s and 7.2𝜇s, corresponding to throughputs of
1.14 and 1.38 billion updates per second, respectively. Concurrent
updates have little effect on query performance in the recompute
mode. When the writer is running on a separate CUDA stream,
SIFT-100M query latency increases from 3.7244s (without updates)
to 3.7341s at 10000 updates per second and 3.7538 s at 50000 updates
per second. These increases correspond to overheads of only 0.26%
and 0.79%, respectively.
Cached mode. When the encoded diagonals fit in device memory,
Carousel caches and reuses them across queries. An update can
therefore make the cached representation of the affected block stale.
An update can therefore make the cached representation of the
affected block stale. Append-only insertions only affect the final
block, whereas random deletions can make blocks throughout the
dataset stale. To preserve next-query freshness, Carousel marks
that block as dirty and re-encodes it before it is next read. Because
each vector contributes to every diagonal of its block, modifying a
single row requires re-encoding the entire block. This takes 3.35 ms
on MS MARCO-256 and 3.53 ms on GIST-256. Multiple updates
to the same block before it is next read coalesce into a single re-
encoding.

Figure 9 shows how refreshing dirty blocks in cached mode
affects query performance. Without concurrent updates, caching
reduces server latency from 90.3 to 33.8 ms on GIST and from
211.7 to 44.8 ms on MS MARCO. At 10 updates per second, cached
execution remains 2.44× faster on GIST and 4.39× faster on MS
MARCO. At 100 updates per second, the cached mode remains 1.42×
and 2.54× faster than the recompute mode on GIST and MS MARCO,
respectively. As the update rate increases, more blocks become
dirty between queries and must be re-encoded. GIST reaches the
recompute baseline near 3,000 updates per second. On MS MARCO,
the writer saturates at 1,851 updates per second, where cached
execution remains 1.13× faster than recomputation. Separate batch-
size measurements indicate that its crossover would occur only near
3 × 105 updates per second. Thus, lazy re-encoding preserves the
caching benefit over a wide range of update rates while maintaining
next-query freshness.
For write-heavy deployments, Carousel can move re-encoding
off the query path. Updates accumulate into batches, while a back-
ground CPU thread performs the encoding. The query thread then
transfers the re-computed diagonal encodings to the GPU and swaps
them into the cache. This makes query latency largely independent
of the update rate. Even at 10,000 updates per second, query latency
remains nearly unchanged, increasing from 33.8 to 35.1 ms on GIST
and from 44.8 to 50.3 ms on MS MARCO. This mode trades fresh-
ness for throughput. Queries continue using the previous cached
version of an affected block until its replacement is ready, producing
staleness windows of 1.9 s on GIST and 3.7 s on MS MARCO.

scaling from 100 million to one billion vectors requires additional
hardware rather than additional query latency.
Communication grows much more slowly than the corpus. The
upload remains 5.24 MB because the client sends one ciphertext re-
gardless of 𝑁, and the server generates the remaining rotations. The
download increases by only 25%, from 12.58 to 15.73 MB, because

putation increases with corpus size. Query construction remains
unchanged, while decryption and decoding increase only slightly,
from 12.0 to 15.8 ms. The matched-filter stage grows more substan-
tially, from 31 to 375 ms, because it scores candidate slots against
codewords from ten times as many blocks. This measurement uses
a single CPU core, and the work can be parallelized across addi-
tional cores to reduce the latency. On the other hand, reducing the
number of candidate slots from 𝐶= 2000 to 𝐶= 200 substantially
lowers the matching cost with negligible loss in recall@10. These
two options mitigate the dominant client-side computation cost at
one billion vectors.
Retrieval quality remains stable even at this scale. True recall@100
decreases from 0.9845 to 0.9715, while recall@10 decreases from
0.9785 to 0.9699. The loss is concentrated in a small subset of queries
as median recall remains 0.990, the 95th percentile remains 1.000,
and the fraction of queries achieving at least 0.95 recall decreases
from 97.3% to 95.7%.

DISCUSSION AND LIMITATIONS
Carousel has four main limitations. Two of them are related to
sharpening and two to deployment. Although ordinary insertions
and deletions require no client action, changes to the encryption
parameters require clients to re-upload their evaluation keys. The
server stores three such keys per client: a multiplication key for
sharpening, a rotation key for query expansion, and a conjugation
key for the packing split. When there is change in the sharpening
exponent 𝑝, it alters the modulus-chain depth and invalidates the
existing keys. As the corpus grows, folding combines scores from
more blocks, increasing the accumulated bulk noise that sharpening
must suppress and potentially requiring a larger 𝑝. Section 4.2
shows a transition from 𝑝= 64 to 𝑝= 128 beyond 29 million
vectors, after which 𝑝= 128 remains sufficient through 1 billion
vectors. This is Carousel’s only nonincremental reconfiguration.
Across our SIFT scaling experiment, it occurs only once, requires
no re-indexing, and transfers less than 32 MB of replacement keys
per client. A second limitation is that sharpening orders scores by
absolute magnitude rather than signed value. Because the exponent
is an even power of two, a strongly negative score could become
heavy and returned as a match. In practice, this issue does not arise,
as the most negative score a query encounters is consistently much
smaller in magnitude than its largest positive match. While using
an odd exponent would preserve the sign, it requires one additional
ciphertext multiplication and increases the overall multiplicative
depth. This configuration is omitted as no corpus requires it.
The remaining constraints are deployment-driven. Device mem-
ory limits whether encoded diagonals can be cached, forcing larger
configurations to use recompute mode. Client decoding scales with
the block count 𝐵and the candidate budget 𝐶, the number of slot
candidates the client evaluates. Matched-filter latency increases
from 31 ms at 108 vectors to 375 ms at 109, where it dominates
client cost. Reducing 𝐶lowers this latency but can reduce recall.
6
CONCLUSION
Carousel shows that single-round private nearest-neighbor search
with FHE is practical at billion-vector scale. Prior systems avoid
fully homomorphic evaluation and instead use linearly or some-
what homomorphic encryption.By using GPU-accelerated CKKS,
Carousel makes exhaustive FHE scanning practical and acheives
high recall by not discarding potential candidates. However rank-
ing those scores still remains expensive, so Carousel introduces
sharpening and folding to complete the private search pipeline
efficiently. Carousel also keeps no corpus-derived state on the
client. The client holds only its keys and a public projection, so
a change to the corpus invalidates nothing it holds. This makes
updates practical, whereas prior work in this setting either treats
them as an open problem or briefly discusses them as an expensive
operation. Overall, this design achieves the highest retrieval qual-
ity among private search systems, matching that of a non-private
index, and is the only one scalable upto a billion vectors. Carousel
could be applied to a wide range of applications including private
web search, recommendation, and retrieval-augmented generation.
