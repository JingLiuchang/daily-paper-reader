## 摘要
大语言模型智能体正越来越多地以多智能体系统的形式部署，而非作为在单一上下文中运行的独立模型。近期的智能体执行框架允许模型实例化工作智能体，并编写协调这些智能体的可执行工作流，从而将系统结构的设计从开发者转移到运行时的模型。因此，这种组织方式的质量构成了一种独立能力，但现有基准要么衡量端到端任务完成情况，要么评估在预先指定结构下的协调。我们将这一能力形式化为工作流编排，并推出 WorkflowArena——一个包含 145 个长时程任务的基准，覆盖 8 个专业领域，从软件工程、形式数学到法律分析和 3D 制作。每个任务规定一个初始工作区和一个由相互依赖组件构成的集成交付物，并由隐藏验证器进行评估。智能体自主决定是否以及如何委派，所有委派都会被记录，从而能够联合评估交付物质量与底层工作的组织方式。对九个模型的实验表明，没有任何单一配置在所有领域都表现最佳，且不同系统表现出不同的委派策略：在高投入模式下，Claude Code 中的 Claude 模型调用工作流的频率较低，但工作智能体组更大；而 Codex 中的 GPT 模型则以更小单元更频繁地委派。当在具有挑战性的任务子集上固定执行模型时，由 Claude Opus 5.5 编写的工作流显著提升了较弱执行器的表现，这表明工作流组织本身就是任务表现的一个可测量决定因素。

## Abstract
Large language model agents are increasingly deployed as multi-agent systems rather than as a standalone model operating within a single context. Recent agent harnesses allow the model to instantiate worker agents and to author the executable workflow that coordinates them, shifting the design of system structure from developers to the model at run time. The quality of this organization therefore constitutes a distinct capability, yet existing benchmarks either measure end-to-end task completion or evaluate coordination under structures specified in advance. We formalize this capability as workflow orchestration and introduce WorkflowArena, a benchmark of 145 long-horizon tasks spanning 8 professional domains, from software engineering and formal mathematics to legal analysis and 3D production. Each task specifies an initial workspace and an integrated deliverable composed of interdependent components, which is assessed by a hidden verifier. Agents determine autonomously whether and how to delegate, and all delegation is recorded, enabling joint evaluation of deliverable quality and the organization of the underlying work. Experiments with nine models show that no single configuration performs best across all domains and that systems exhibit distinct delegation strategies: at high effort, Claude models in Claude Code invoke workflows less frequently but with larger worker groups, whereas GPT models in Codex delegate more frequently in smaller units. When the executing model is held fixed on a challenging subset of tasks, workflows authored by Claude Opus 5.5 substantially improve weaker executors, indicating that workflow organization is itself a measurable determinant of task performance.

# WorkflowArena 论文总结

## 1. 核心问题与整体含义

- **背景趋势**：LLM 智能体正从“单模型、单上下文”的形态转向多智能体系统；新一代 agent harness（如 Claude Code、Codex）允许模型在运行时自行实例化 worker agents，并**由模型自己编写协调这些 worker 的可执行工作流**。系统结构的设计权因此从开发者转移到模型。
- **被忽视的能力**：这种“把任务如何切分、每个 agent 拿到什么上下文、中间结果如何校验与整合”的组织能力，作者形式化为 **workflow orchestration（工作流编排）**，认为它是独立于单 agent 解题能力的一种系统级能力。
- **现有基准的缺口**：
  - 端到端 agent 基准（AgentBench、SWE-bench、GAIA、WorkArena 等）把 agent 当作单一整体评分，**看不到工作如何被切分**；
  - 多智能体基准（MultiAgentBench 等）评估的是**基准设计者预设的协作协议**；
  - 工作流基准（FlowBench、WorFBench、OrchBench）多在**离线或仿真**中评估生成的计划，决策不会真正作用于真实工件。
- **核心研究问题**：*LLM 智能体能在多大程度上自主编排多智能体工作流，以完成真实的长时程任务？*

## 2. 方法论

### 2.1 核心思想
- 构建一个让“组织方式本身会改变结果”的基准：任务包含大量可分离但相互依赖的工作单元，评分针对**集成交付物**，且**所有委派都被记录**，从而把交付物质量与工作组织方式放在一起评估。
- 五个设计需求：组织必须有后果（consequential）、自主（autonomous）、集成敏感（integration-sensitive）、组织成本计入预算（cost-accounted）、组织可观测（observable）。

### 2.2 任务形式化
- 任务定义为五元组：`τ = (s0, g, U, E, B, V)`，分别为初始环境状态、目标指令、公开动作/工具面、工件与执行环境、资源预算、独立验证器。
- 智能体只能看到 `(s0, U, E, B)` 的公开部分，**看不到验证器、金标准与隐藏测试**。
- 执行产生轨迹 `hT` 与终态 `sT`，奖励 `r = V(sT, hT) ∈ [0,1]`；奖励取决于任务结果与必要的过程约束，**不取决于 worker 数量或工作流形状**，因此单 agent 顺序执行也是合法工作流。

### 2.3 基准构建流程（图 2）
1. **真实来源**：开源仓库与 PR、Lean/mathlib4 形式化蓝图、科学挑战与论文、SEC 10-Q 文件、并购协议与判决书、公开影片与报告、支出数据、建筑图纸与场景等；需要受控状态转移的场景使用“作者编写的场景”，依赖关系被完全指定。
2. **适用性筛选**：要求工作量大、单元间存在依赖或共享约束、需要非平凡整合。
3. **任务构造**：给出目标与约束，但**不规定工作流**；移除目标工作（如删除功能实现、留空证明、去掉 iXBRL 标签），保留上下文；公开输入与隐藏参考/检查分离。
4. **验证与发布**：专家评审清晰度/工作量/集成性；验证器需同时通过参考解与“应当失败”的提交（空输出、组件正确但未整合、结果正确但过程非法），确保集成敏感性与过程约束有效。

### 2.4 评估协议
- **统一 4 小时墙钟预算**，由主 agent 与其所有 worker 共享；环境准备与评分不计入。
- **Workflow 工具**：可后台启动最多 16 个并发 worker，支持 `WorkflowList / WorkflowOutput / WorkflowStop / WorkflowControl` 等接口，可查看、停止、修改工作流；程序由 `agent / parallel / pipeline` 原语加普通 JavaScript 控制流组成。
- **worker 是 agent 自身的新实例**（同模型、同 harness、同 effort），上下文全新、仅共享 workspace，因此“给每个 worker 什么上下文”本身是被评估的行为。
- **原生 sub-agent 机制被禁用**，所有委派必须经过 Workflow 工具并被记录；是否委派完全由 agent 决定。
- **评分**：单任务连续分 `St = 100·rt ∈ [0,100]`；领域分 `S̄d` 为该领域任务分均值；Overall Score 为 8 个领域分的等权平均。**主指标为 Overall Resolved**（满足该领域全部验收标准的任务比例），同样按领域等权平均；连续分作为补充，用于奖励部分进展。
- **评分器**：内容类与 3D 交付物由 Gemini-3.8-Flash 按任务 rubric 评分；其余领域使用程序化验证器。

### 2.5 工作流迁移实验（分离编排质量与执行能力）
- 固定执行模型，只改变工作流来源：源模型只读任务与干净 workspace、**不编辑 workspace**，写出 Workflow 程序或动态发起/修改工作流；所有实际工作由执行模型的 worker 完成；工作流生成也计入同一时间预算。
- **静态模式**：源模型写完冻结程序后停止，程序在新 workspace 中执行（分支、循环、并行仍生效）。
- **动态模式**：源模型启动工作流、观察 worker 结果并持续修改（类似 Claude Code dynamic workflows）。
- 对照设置包括执行模型“自己作为源”的 Self 动态模式。
