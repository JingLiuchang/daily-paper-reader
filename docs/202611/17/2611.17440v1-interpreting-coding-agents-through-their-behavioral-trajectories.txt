# Abstract 

Standard coding-agent benchmarks primarily evaluate binary task success, treating execution as a black box and obscuring the behaviors that produce those outcomes. We analyze a large corpus of 143,209 execution trajectories from 125 agent configurations spanning 117 unique models. To enable comparisons across heterogeneous agent interfaces, we develop a rule-based parser that maps raw execution traces to high-level actions such as repository search, file editing, and test execution, and audit its predictions against a six-model consensus reference on 500 events. We find that agents with similar solve rates can nevertheless differ substantially in how they explore, modify and verify code. Moreover, without using task outcomes, token counts, or tool names as features, aggregate behavioral profiles retrieve the corresponding agent stack across disjoint repository sets and programming languages, although task composition is not fully controlled in the cross-repository setting. Through analyses of frontier models and agent scaffolds, we further show that scaffold choice and reasoning effort systematically shift agents’ search, editing, and testing behavior. We release the deterministic parser together with the full annotation and analysis pipeline alongside an annotated trajectory subset. 

# 1 Introduction 

Coding-agent benchmarks typically reduce a complex, multi-step interaction to a binary outcome: whether the agent resolves the issue and passes the tests (Jimenez et al., 2024). Aggregated across tasks, this produces a solve rate that is useful for ranking systems but offers limited insight into how they operate. The differences in behavior matter for diagnosing failures and understanding how different models approach the problems. Moreover, scaffolding can substantially alter both workflow and success rates (Yang et al., 2024), showing that behavior depends on the entire system, not just the underlying model. Analyzing these behaviors at scale is challenging. Execution traces are heterogeneous: harnesses expose different tools, use different command formats, and record interactions under different schemas. Direct comparisons based on tool names or raw commands therefore conflate semantic actions with implementation details. A cross-system analysis requires a shared representation that captures what an agent is doing, independently of how a particular harness records that action. In this work, we develop such a representation and apply it to 143,209 execution trajectories from SWE-rebench (Badert-dinov et al., 2025), covering 125 agent configurations and 117 unique models. We introduce a rule-based parser that maps heterogeneous trace events to a common taxonomy of high-level actions. We audit the parser on a sample of 500 events and use the resulting annotations to compare agent workflows at scale. Our analysis shows that solve rate does not uniquely characterize agent behavior. Configurations with similar perfor-mance can differ substantially in how often they search, inspect, edit, and test. We further find that aggregate behavioral profiles contain enough information to predict the underlying model and harness on held-out repositories, even without task outcomes, token counts, or tool names. Finally, we examine frontier models and agent scaffolds to show how scaffold choice and reasoning effort systematically shift patterns of exploration, modification, and verification. arXiv:2611.17440v1 [cs.SE] 12 Nov 2026 Our main contributions are as follows: • We introduce a deterministic trajectory normalization pipeline, annotate 143,209 trajectories from 117 models, and release the deterministic parser, analysis pipeline, and an annotated trajectory subset. • Through outcome-matched comparisons, we show that nearly identical solve rates can conceal large and repro-ducible differences in observable workflows. • We show that, without using outcomes, token counts, or native tool names as retrieval features, aggregate behavioral profiles can retrieve the deployed stack across disjoint repository sets and programming languages; task composition across repository splits remains a potential confound. • We use the taxonomy to characterize how model choice, scaffolding, and reasoning effort affect agents’ explo-ration, modification, and verification patterns. 

# 2 Related Work 

Recent efforts in software engineering benchmarks have expanded execution-based evaluation toward multi-dimensional assessments (Kapoor et al., 2025) and contamination-resistant environments (Badertdinov et al., 2025). Because repeated rollouts on identical issues exhibit substantial behavioral divergence (Bjarnason et al., 2026), understanding the underlying execution trajectory is essential to explain how different models and harnesses actually resolve code tasks. Process-level analysis of coding agents investigates intermediate execution patterns beyond final pass rates. Prior work examines intermediate task progress (Ma et al., 2024), stage-based workflow labeling (Sahoo et al., 2026), and human-validated behavioral vocabularies (Gao et al., 2026). Other approaches represent execution rollouts via process-flow graphs (Liu et al., 2026) or programmatic procedural traces (Oderinwale, 2026). Recent studies also highlight how task composition influences behavior (Mehtiyev and Assunção, 2026) and analyze specific stage bottlenecks across code search, reading, and editing (Shu et al., 2026; Kim et al., 2026; Bouzenia and Pradel, 2025; Majgaonkar et al., 2025; Chen et al., 2026; Ceka et al., 2026). Trajectory failure analysis has increasingly moved toward temporal and structural breakdowns. Zhao et al. (2026) model error accumulation and recovery as dynamic processes, while TrajAudit uses reference-aware signals to identify exact failure points (Wang et al., 2026). Furthermore, Raj et al. (2026) emphasize that agent capabilities are tightly bound to the interaction harness, tool definitions, and runtime execution environment rather than standalone model weights. Building on these diagnostic foundations, we ground our approach in an empirical analysis of over 140,000 execution trajectories. Existing work has developed taxonomies, process representations, and failure diagnostics for coding-agent trajectories. We complement these efforts with a large-scale cross-stack analysis, using outcome-matched comparisons to isolate workflow differences from performance and rollout variability, and testing whether execution profiles remain stable across disjoint repositories and programming languages. 

# 3 Study Design and Behavioral Measurement 

Our study analyzes execution trajectories of coding agents evaluated on tasks from the SWE-rebench Leaderboard. 1

The dataset comprises 860 Python tasks across 413 repositories (spanning January 2025 to May 2026) and a multilingual set of 111 tasks across Go, Java, Python, Rust, and TypeScript. In total, we analyze a large-scale corpus of 143,209 complete execution trajectories (134,329 on Python and 8,880 on multilingual tasks) spanning 125 distinct agent configurations built upon 117 unique base models. 2 For each task, the benchmark records the initial repository state, issue description, and an isolated test environment.

3.1 Action Classification 

The basic unit of analysis is an individual tool call. We implement a rule-based parser that categorizes shell commands, scripts, and API tool invocations via pattern matching into four attributes: 

Primary operation , classifying the core action from ten categories: exploration, search, file reading, file mutation, formal test execution, workspace inspection ( git diff , git status , git show ), package builds, other op-erations, no repository operation, or unknown; Target file role , classifying paths via path-based heuristics (such as tests/ , test_* , *_spec , conftest ) into non-test repository files, conventional test files, mixed targets, unresolved destinations, or not applicable; Mutation type , classifying modifications into create, edit, delete, or mixed mutations; and Read mode , distinguishing direct file reads from viewport continuations (with read_scope

3.2 Core Workflow Metrics 

We evaluate six workflow metrics in their native units: • Operational actions: Total attempted nonterminal tool calls per rollout, including malformed or rejected attempts. • Exploration share: Proportion of executed semantic actions spent on repository exploration, searching, and file reading. • Non-test repository writes: Executed file modifications targeting non-test repository paths with no observed failure (excluding events with nonzero exit codes, failed tests, or execution errors). • Formal-test invocations: Count of recognized test-framework invocations contained within executed events (which may exceed one in compound events). • Consecutive repeated failures: Count of strictly adjacent failed attempts sharing the same canonical signature (ordered operations, normalized command, and sorted paths; a subsequent success is not required). • Unproductive tail: Attempted nonterminal actions after the agent’s final productive event (either a counted non-test write or a passing test). We aggregate metrics across five runs per task for outcome-matched and case-study panels (and two rollouts per task in the configured-effort panel) before computing task averages. 3.4 Outcome-Matched Pair Design and Null Control 

To test whether agents with equal performance follow different workflows, we compare pairs of agent configurations that share the same scaffold but differ in their base model, requiring an aggregate solve-rate difference |∆solve | ≤ 1.0

percentage points across at least 50 shared tasks. To distinguish between-stack behavioral differences from run-to-run variation across repeated rollouts, we establish a split-half null control. For each stack, we repeatedly partition its multiple rollouts into two equal, independent halves (four of the five rollouts per task; see Appendix B) across 100 random split seeds. Measuring the divergence between halves of the exact same configuration yields an empirical baseline for same-stack run-to-run variation, serving as an A/A test. Differences between distinct model pairs are then compared with this empirical null baseline (Section 4.1). 

# 4 Empirical Results 

We organize the empirical analysis around three objectives: (1) quantify workflow differences between agents with closely matched solve rates; (2) characterize behavioral shifts associated with model choice, scaffolding, and reasoning effort; and (3) evaluate whether aggregate behavioral profiles remain discriminative across disjoint repositories and programming languages.

4.3 Behavioral Profile Retrieval Across Repositories and Languages 

We evaluate whether aggregate behavioral profiles remain stable across environments and are sufficiently distinctive to retrieve the corresponding agent stack on disjoint repository and language splits. 

Feature Representation and Retrieval Protocol. For cross-repository retrieval, we construct an 8-dimensional profile summarizing execution style: four normalized action coordinates (exploration, file reading, non-test repository writes, and formal-test invocations) alongside four sequential verification features (normalized entropy, tool-switch rate, post-write workspace inspection, and unverified termination; see Appendix C.1). These vectors strictly exclude solve outcomes, total action counts, token volume, and native tool names. To test cross-repository transfer, we partition the 413 Python repositories into two disjoint halves (207 vs. 206). Evaluating 111 stacks via cosine nearest-neighbor retrieval across splits (222 queries), the full behavioral profile achieves 85.1% Top-1 recall and 96.8% Top-3 recall against a 0.9% random baseline (Table 5), showing that profiles remain discriminative across these repository splits. However, repository-disjoint splits alone do not control for differences in task composition across stacks. These differences may contribute to retrieval performance, so this result does not establish task-independent behavioral signatures. 

Cross-Language Generalization. We apply the same cosine-retrieval protocol across a balanced panel of 16 agent configurations evaluated on Go, Java, Python, Rust, and TypeScript (111 tasks, 8,880 trajectories). Across all ten 3-vs-2 language splits, cross-language profile matching achieves 90.3% Top-1 recall and 98.8% Top-3 recall (against a 6.25% random chance baseline). This indicates that operational signatures remain distinct across substantially different programming languages. Because action composition alone already reaches 87.5% Top-1 in this panel (Table 5), 7we interpret these profiles as low-level operational signatures of the deployed stack rather than as evidence about higher-level problem-solving strategies or internal reasoning. See Appendix C for feature ablations and scaling checks. 

# 5 Discussion and Limitations 

Our results support three main conclusions. First, aggregate solve rate provides an incomplete description of agent behavior: similarly performing stacks can exhibit substantially different observable workflows. Second, observable behavior reflects the entire agent stack, with systematic shifts associated with the underlying model, scaffold, and configured reasoning effort. Third, behavioral profiles remain discriminative across the evaluated repository and language splits, although task-composition differences may contribute to the cross-repository result. Together, these findings motivate treating execution behavior as a complementary dimension of agent evaluation alongside task success. This perspective becomes relevant as agents operate over longer horizons and perform more actions without direct human intervention. Final outcomes reveal whether an agent succeeded, but not how it reached that outcome or what behaviors emerged along the way. Execution trajectories therefore provide process-level evidence for diagnosing and comparing agent systems. For example, trajectory audits could surface reward hacking or superficial hardcoding; behavioral profiles could reveal shared or changing operational patterns across models and scaffolds; and structured trajectory signals could provide supervision for process-based reward models and reinforcement-learning objectives. Relating behavioral profiles to token cost and latency would further show which workflows are preferable in practice. We leave these applications to future work. However, behavioral profiles are heuristic summaries rather than semantic ground truth and may be over-interpreted as evidence about latent reasoning or used for unintended system attribution. Our study has several limitations. First, we audit our parser against a consensus of frontier LLMs rather than human annotators; agreement varies across fields (from 96.6% for read mode to 77.0% for target-file role and 68.8% for mutation type), and shared systematic model biases remain possible. Second, deterministic rule-based matching captures coarse operational structure but may miss semantic context or intent in non-standard command executions. Third, our analysis focuses strictly on explicit tool calls and environment interactions, omitting internal chain-of-thought reasoning and intermediate model text. While tool calls capture concrete side effects, free-form verbal planning may contain additional context regarding model intent and latent failure modes. Fourth, all trajectories are collected in a single benchmark regime. SWE-rebench draws tasks from recent repository activity, which reduces but does not eliminate contamination, and models may also recognize the evaluation setting itself; profiles may therefore partly reflect task familiarity or benchmark-specific policies and need not transfer unchanged to real-world deployments. Fifth, matching on aggregate solve rate does not control which tasks each agent solves; matching on per-task outcomes would give a stricter comparison. Finally, our behavioral taxonomy is tailored specifically to software engineering benchmarks. While these action categories generalize well across programming languages, other domains—such as open-ended scientific research or interactive design—would require enriching the parser implementation. 

# 6 Conclusion 

Coding-agent performance answers whether a system succeeds, but not how it operates. Across 143,209 trajectories, we show that nearly outcome-matched agent stacks can exhibit reproducibly different workflows, that model/scaffold/effort choices systematically shift observable execution, and that aggregate behavioral profiles remain discriminative across repositories and programming languages. Together, these results motivate treating trajectory behavior as a complemen-tary dimension of agent evaluation alongside task success. We release the parser, analysis pipeline, and an annotated trajectory subset to support further work on behavior-centered evaluation and diagnosis.

A.1 Observable-Event Codebook and Metric Definitions 

The parser assigns each tool invocation a primary_operation from ten core categories: • exploration and search: EXPLORE_REPOSITORY , SEARCH_REPOSITORY ;• reading and mutation: READ_FILE , MUTATE_FILE ;• testing and inspection: RUN_FORMAL_TEST , INSPECT_WORKSPACE_CHANGES ;• other: PACKAGE_OR_BUILD , OTHER_OPERATION , NO_REPOSITORY_OPERATION , UNKNOWN .For applicable operations, the parser independently tags three orthogonal attributes: • target_role : distinguishes non-test repository files, conventional test files, mixed destinations, unresolved paths, or not applicable. • mutation_kind : classifies file modifications into create, edit, delete, mixed, or not applicable. • read_mode : differentiates direct file reads from viewport continuations, while read_scope separately tags full-file vs. bounded line-range reads ( sed -n , head , or API limits). 

Action Counts and Proportions. Total operational actions include all attempted nonterminal tool calls, including malformed or rejected commands. In contrast, action proportions compute the share of executed semantic operations, excluding UNKNOWN and NO_REPOSITORY_OPERATION events. Specifically: • Exploration share combines repository navigation, search commands, and file reads. • Non-test repository writes count executed events containing a recognized mutation to at least one resolved non-test repository path with no observed failure. • Formal tests count executed invocations recognized as project test frameworks. 

Consecutive repeated failures. This metric counts consecutive duplicate failures for events sharing the same canonical signature. For example, consider the sequence: 

(A, fail ) → (A, fail ) → (B, fail ) → (A, success ) → (A, fail )

Here, the second A adds 1 repeated failure. Command B starts a separate chain. The successful fourth call resets the counter for A, and the final failed A starts a new sequence. The total count for this rollout is therefore 1. A sequence ending immediately after two failed A calls also adds 1; a subsequent success is not required. 

Unproductive Tail. The unproductive tail measures attempted nonterminal tool calls after the agent’s last productive step (either a counted non-test repository write without observed error or a passing formal test). Read → Counted Non-test Write → Failed Test → Read → Passing Test → Read → Submit The passing test marks the final productive action. The tail contains only the single subsequent read; the terminal submit action is excluded. # C Agent Behavioral Signatures and Cross-Task Retrieval 

C.1 Behavioral Feature Representation 

To characterize each agent’s problem-solving style independently of task outcomes or specific tool syntaxes, we construct an 8-dimensional behavioral vector from its executed semantic actions. It combines four normalized action coordinates (exploration, file reading, non-test repository writes, and formal-test invocations) with four sequence and verification features: • Normalized action entropy: Normalized Shannon entropy H/ log( Kobserved ) across observed primary opera-tions (imputed to 0 in the aggregation pipeline when fewer than two distinct categories are observed). • Tool-switch rate: The frequency with which consecutive actions switch between different operational categories. • Post-write workspace inspection: An indicator marking whether the agent attempted a workspace-inspection op-eration ( git diff , git status , or git show ) after the final counted non-test repository write (evaluating to false if no write occurred). • Unverified termination: The boolean unverified-termination indicator, 3 marking rollouts that modified repository files without a subsequent passing formal test. We compute these metrics per rollout and average them across runs for each agent configuration.

C.3 Multilingual Behavioral Retrieval 

To test whether behavioral signatures transfer across programming languages, we evaluate 16 agent configurations on a multilingual benchmark spanning Go, Java, Python, Rust, and TypeScript (111 tasks, 8,880 total trajectories). 

Evaluation Protocol. We evaluate cross-language retrieval across all ten possible 3-vs-2 language splits. For each split, we build an agent’s behavioral profile using tasks from three languages and retrieve the matching configuration against candidates evaluated on the remaining two held-out languages (and vice versa, yielding 320 directional queries). The multilingual representation uses a frozen 12-feature vector comprising normalized action entropy and switch rate over a ten-category general-action sequence, together with the corresponding ten action shares: repository exploration, code search, file reading, source-file creation, editing, deletion, workspace-diff inspection, other shell operations, package/build operations, and other non-shell tools. Events containing formal-test invocations are excluded from this general-action sequence, and action entropy is normalized by log(10) .4

Features are computed per rollout and averaged across runs for each task–configuration pair. Each feature is centered across configurations within each task and averaged across tasks to construct language-level profiles. Before cosine retrieval, features are scaled using the root-mean-square magnitude estimated from the query-language task-centered values, applying the same query-derived scale to candidate profiles.
