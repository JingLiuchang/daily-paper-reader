## 摘要
文档编辑是最常见的知识工作任务之一，然而现有用于评估自主智能体在 Word 文档编辑方面表现的基准测试提供的都是完全明确指定属性修改的指令。它们并未评估智能体从文档上下文中推断合适属性的能力，而这种能力在真实编辑场景中至关重要，因为用户期望在无需逐一说明每个属性的情况下保持一致性。我们提出 WordInferBench，一个包含 280 个基础文档编辑实例的基准测试，每个实例配有三种指令条件：描述型（指令明确列出每一项属性更改）、指代型（指令指向另一个对象作为示例）和推断型（智能体必须检查文档上下文以推断应应用哪些属性）。为评估上下文属性推断能力，每个基础实例的构造都确保目标格式可从文档内示例中恢复。这些实例源自从 Common Crawl 收集的真实 Word 文档，涵盖 13 种对象类型和 81 种属性。我们评估了六个近期编码智能体系统，发现表现最佳的被评估系统 Claude Code with Opus 4.6 在描述型变体上达到 62.9% 的任务级通过率，但在推断型变体上仅为 40.7%，这表明当所需格式更改必须根据文档上下文确定时，当前系统完成任务可靠性较低。

## Abstract
Document editing is among the most common knowledge-work tasks, yet existing benchmarks for evaluating autonomous agents on Word document editing provide fully specified attribute-modification instructions. They do not evaluate agents' ability to infer the appropriate attributes from document context, a capability essential in real-world editing where users expect consistency without spelling out every attribute. We introduce WordInferBench, a benchmark comprising 280 base document-editing instances, each paired with three instruction conditions: descriptive (the instruction explicitly lists every attribute change), referential (the instruction points to another object as an exemplar), and inferential (the agent must examine document context to infer what attributes to apply). To evaluate contextual attribute inference, each base instance is constructed so that the target formatting is recoverable from an in-document exemplar. The instances are derived from real Word documents collected from Common Crawl and cover 13 object types and 81 attributes. We evaluate six recent coding-agent systems and find that the best-performing evaluated system, Claude Code with Opus 4.6, achieves a 62.9% task-level pass rate on descriptive variants but only 40.7% on inferential variants, indicating that current systems complete tasks less reliably when the required formatting changes must be determined from document context.

## 一、核心问题与研究动机

- **背景**：文档编辑是知识工作中最常见的任务之一。智能体正越来越多地自主操作办公软件，因此评估其 Word 编辑能力成为重要研究问题。
- **现有基准的缺口**：OSWorld、Windows Agent Arena、WorldGUI、OfficeBench、DocFormEval、DocFormBench、OfficeEval 等基准中的 Word 任务，几乎都提供**完全显式指定**的格式修改指令（如“把字体改为 Times New Roman”），只考察“指令解析 + 执行”，不考察“从上下文推断应改什么”。
- **真实需求**：用户插入新形状或粘贴内容后，通常只期望“与文档现有格式保持一致”，而不会逐条列出每个属性。因此**上下文属性推断**是真实编辑场景的核心能力。
- **核心研究问题**：当指令不再显式给出属性（甚至不给出参照对象）时，智能体能否通过浏览文档上下文，自行定位格式范例并推断出应修改的属性与取值？
- **整体含义**：论文将“信息充分程度”作为一个可控变量引入 Word 编辑评测，提出三档指令条件的配对基准，用以诊断智能体在“格式执行”与“上下文推断”两个环节上的能力边界。

## 二、方法论

### 2.1 核心思想

- 每个**基础实例**由三部分组成：输入文档（目标对象属性已被重置为默认值）、留出的参考文档（保留原始格式，仅用于打分）、三条指令变体。
- 智能体只看到输入文档和一条指令，需将目标对象恢复为参考文档中的状态。
- 通过“重置—恢复”的构造方式，使真值确定、可精确比对，同时天然产生“格式可从文档内范例恢复”的推断条件。

### 2.2 三种指令条件（信息量递减）

| 条件 | 指令内容 | 考察能力 |
|---|---|---|
| **描述型 Descriptive** | 逐条列出所有属性变更（含具体取值） | 指令解析 + API 精确执行 |
| **指代型 Referential** | 只指出“使 X 与 Y 一致”，不列属性 | 读取范例属性、判断相关属性、保证覆盖完整 |
| **推断型 Inferential** | 只给出目标对象位置 | 自主探索上下文、定位范例、推断属性集合 |

### 2.3 数据构造流程（关键技术细节）

1. **语料来源**：从 Common Crawl 采集真实 Word 文档（异源网页文档，排版结构多样）。
2. **候选筛选**：解析 docx 的 XML 识别对象类型，保留同类对象 ≥2 的文档，每类抽样约 1,000 篇。
3. **属性抽取**：通过 Word COM 提取所有对象的原始属性。
4. **重置与差分**：对每个候选对象在独立副本中重置为默认值，计算重置态与原态的差异，得到“需修改属性集”。
5. **配对构造**：在同一文档内配对**同类型、格式签名完全相同但内容不同**的对象，形成 (target, reference) 对。这保证原始格式至少可从文档内一个范例精确恢复，并支持确定性的精确属性比对。
6. **贪心集合覆盖采样**：迭代选择“能覆盖最多未覆盖属性”的对象，平局时优先覆盖更多低频属性，且每篇文档每类对象最多贡献一个实例，以最大化 81 个属性的覆盖多样性。
7. **指令生成**：用 LLM 生成三条变体——
   - 描述型：先把结构化属性差分转为人类可读表示（如枚举常量 `fill type 3` → "Gradient"），再由 LLM 改写为自然语言，并做第二轮“精简改写”；
   - 指代型：仅基于位置信息（类型、页码、内容）描述目标与参照对象，禁止提及属性；
   - 推断型：仅给出目标对象位置，要求智能体自行审查文档并推断修改方案。

### 2.4 质量与隐私控制

- **PII 处理**：图像层面渲染页面截图做 LLM 人脸检测，含人脸文档整体剔除；文本层面按 8 类 PII（账号、住址、邮箱、人名、电话、URL、日期、密钥）检测并替换为占位符；替换后复检目标对象属性未受影响，否则剔除该条目。
- **人工校验（盲评优先）**：9 名标注员分 3 组，每组标注全部样本但只标注一种指令条件（条件与子集在组间轮转以平衡组效应）。标注员**先不看参考答案独立完成编辑**，再对照参考，评分子维度：指令清晰度、参考正确性、自产结果与参考的一致性、PII、文档质量。
- **剔除规则**：某一组 3 人一致判定有问题即剔除；非一致情形人工复核并修订。最终 312 个候选中保留 **280 个（89.7%）**，剔除 9 个 PII、15 个参考问题、12 个指令不清（含 4 个重叠）。

### 2.5 评测指标

- **任务级通过率（Task-Level Pass Rate）**：目标对象所有被评测的变更属性全部正确才算通过（严格全对）。
- **属性级准确率（Attribute-Level Accuracy）**：正确更新的属性占需修改属性的比例，按任务宏平均。
- **非目标保持率（Preservation）**：独立评估输出是否误改非目标对象的内容/格式。
- **比对方式**：参考文档与预测文档走同一套 COM 抽取管线，统一单位、枚举名映射、`wdUndefined` 视为缺失；因读取的是 Word 渲染引擎解析后的**有效属性值**，样式继承与直接格式被等价比较；无法打开的文件计 0 分。

## 五、实验数量与充分性

**规模**：主实验为 6 系统 × 3 条件 = 18 组设置，每组 280 任务，共约 **5,040 次智能体运行**；另有 1 组人类基线（2,520 条有效标注）、2 组启发式定位基线、3 组诊断/探测实验（范例定位、属性路径、视觉检测）、按 13 类对象的分解、81 属性的逐项统计、6 系统 × 3 条件的保持率表。整体实验体量与层次**较为充分**，且“描述—指代—推断”的配对设计构成天然的**受控消融**（同一实例只改信息量），因果解释力较强。

**客观性与公平性**：

- **优点**：每变体全新沙箱、统一提示、统一超时、统一评测管线；人类与智能体用**同一自动打分器**；参考文档对智能体与人类标注员均不可见；条件与标注组的轮转设计平衡了组效应；人工盲评先行，避免“照着答案改”。

## 六、主要结论与发现

1. **推断型显著更难**：所有 6 个系统在推断型上的通过率均低于描述型与指代型。最优系统 Claude Code + Opus 4.6 描述型 62.9%、指代型 77.1%、推断型仅 **40.7%**；平均 60.2%（属性级 76.4%）。
2. **描述型本身也不高**：即使属性与取值全部显式给出，最优系统也只有 62.9%，Codex + GPT-5.5 仅 55.4%，说明“格式执行”本身就是瓶颈，失败不能全部归因于推断。
3. **指代型可能优于描述型**（Opus 4.6：77.1% vs 62.9%），作者推测原因是**程序化复制范例属性比解析自然语言属性规格并映射到精确 API 参数更简单**；但该模式并非所有系统一致（Codex GPT-5.5 指代 43.6% < 描述 55.4%），反映各系统在指令跟随与代码生成上的差异。
4. **推断失败是双重来源**：范例定位本身就有错（GPT-5.5 仅 81.2%，最近邻启发式 50.6%、多数投票 45.8%），且即使给出属性路径，通过率也只从 43.6% 升到 45.4%，说明**执行环节同样是主要瓶颈**。
5. **对象类型差异明显**：**表格最差**（需跨多单元格处理边框、底纹、垂直对齐、文本格式的深层属性层级）；WordArt、图片、自选图形等形状类也偏低。
6. **视觉路径不可靠**：GPT-5.5 截图比对 precision 0.740 但 recall 仅 0.351，常漏掉行距、段间距、字体、阴影等视觉微弱差异，警示**不要依赖纯截图判断或纯视觉 LLM 评委**。
7. **典型失败模式**：
   - 绕过 Word API 直接解压改 XML 再打包，导致命名空间前缀被重写、引用断裂、文件损坏或修改被静默丢弃；
   - 误解 API 参数语义（如散点图误用枚举 74「带直线和标记的散点」而非 −4169；`LeftIndent` 实为左缩进与悬挂缩进之和）；
   - 属性覆盖不完整（改了外层却漏掉段内 run 级格式、单元格级样式、形状内部文本格式）。
8. **附带损害**：即使只改单个目标，仍会发生连带修改（Opus 4.6 推断型保持率 89.6%），常见

的连带修改包括：调整目标段落时波及相邻段落或整篇样式、移动/缩放形状时改变其锚点与环绕方式、替换文本时丢失原有 run 级格式或域代码，以及在表格中操作时破坏合并单元格结构。这说明当前智能体普遍缺乏“最小改动”意识，即在执行编辑前先界定影响范围，并在编辑后自检非目标区域。

9. **人类与智能体的能力剖面不同**：人类在属性级准确率上略高于最优智能体（76.9% vs 76.4%），但任务级通过率反而更低。作者归因于人类更倾向于“只改自己看得出的明显差异”，对行距、阴影、3D 效果等细微属性系统性漏改；而智能体一旦定位正确，往往能一次性写全属性，但也更容易整段改错。这一对比说明**任务级全对指标对“保守型编辑者”不利**，也提示真实场景中“漏改”与“改错”是两类需要不同干预的失败。

10. **属性难度呈现明显的“可见性梯度”**：字体族、字号、加粗、填充色等强视觉属性准确率最高；行距、段前段后间距、字符间距、阴影/发光/倒影/3D 等弱视觉或需多参数协同的属性准确率最低，且人类与智能体在这些属性上**同时表现差**，说明瓶颈部分来自 Word 对象模型的复杂度而非模型能力。这一发现对基准设计有直接含义：若不报告逐属性分解，仅看总通过率会掩盖“模型已掌握易属性、卡在难属性”的结构性事实。

11. **定位与执行是相对独立的两个瓶颈**：范例定位准确率（81.2%）明显高于端到端推断型通过率（40.7%），而补充属性路径只带来约 2 个百分点的提升，二者共同指向“即使知道改什么、参照谁，仍难以通过 COM API 精确落地”这一结论。作者据此主张，Word 智能体的改进重点不应只放在检索/定位模块，更应放在**属性到 API 参数的可靠映射与验证闭环**上。

## 七、局限性与批判性讨论

- **单次运行、无方差估计**：每个变体只跑一次，未报告置信区间或多次采样的一致性，因此模型间小于 5 个百分点的差异（如 40.7% vs 43.8%）不具备统计意义。这是该基准作为“排行榜”使用时最需要补强的一点。
- **样本量与对象类型不均衡**：280 个实例分布在 13 类对象上，图片仅 9 个、页眉 13 个，按类型分解的结论（如“表格最差”）在少数类别上统计功效有限。
- **语料来源单一**：全部来自 Common Crawl 的网页导出 docx，排版风格偏向网页转换产物，与真实办公中人工排版的合同、报告、论文等文档分布存在差异，可能影响结论的外部效度。
- **属性覆盖有限**：81 个属性虽已覆盖主要格式族，但未涉及样式（Styles）、编号多级列表定义、域代码、批注/修订、节属性（分栏、页边距）等同样高频且更难的编辑对象。
- **指令由 LLM 生成**：尽管经过人工盲评与剔除，描述型指令的自然语言改写仍可能引入“过度显式”或“表述歧义”，使描述型条件不完全等同于真实用户指令。
- **人类基线规模有限**：9 名标注员、2,520 条有效标注，且标注员同时承担数据质检，可能存在疲劳与学习效应；作者虽用条件轮转平衡组效应，但未报告标注员间一致性指标（如 Cohen's κ）。
- **诊断实验覆盖不足**：三项诊断（定位、属性路径、视觉检测）均只在 Codex + GPT-5.5 上执行，无法判断这些中间结论对不同智能体架构的普适性。
- **未评估多轮交互与工具使用**：所有设置为单轮、固定提示、600 秒超时，未考察智能体在获得执行反馈后自我修正的能力，而这恰是真实 Office 自动化的常态。

## 八、对领域的启示

- **评测范式的贡献大于榜单本身**：把“信息充分程度”作为可控自变量、用配对实例构造受控消融，这一设计可平移到 Excel、PowerPoint、PDF 等其他文档智能体基准，用于区分“指令理解”与“上下文推断”两类能力。
- **“重置—恢复”是一种可复用的真值构造方法**：通过把目标对象重置为默认值、保留同签名范例作为参考，既保证了真值确定性，又天然制造了“文档内可推断”的条件，避免了对人工标注格式真值的高成本依赖。
- **对智能体设计的直接提示**：应优先构建“读取范例 → 提取属性 → 映射 API → 回读校验”的闭环，而非直接生成 XML 补丁；同时应加入影响范围界定与编辑后自检，以抑制连带损害。
- **对评测者的提示**：纯截图视觉判分 recall 偏低（0.351），不宜作为唯一评分手段；任务级全对与属性级准确率应并列报告，否则会系统性低估保守型编辑策略。

## 九、总体评价

论文定位清晰、构造严谨，其核心价值在于**把“格式推断”从一个隐含能力拆解为可测量、可归因的实验变量**，并用“描述—指代—推断”三档配对条件给出了较强的因果解释力。数据构造管线（同签名配对、贪心集合覆盖采样、PII 处理、盲评优先的人工校验）体现了较高的工程与伦理标准，失败模式分析也具有实践指导意义。

主要不足集中在统计严谨性（单次运行、无置信区间、未控制解码参数）与覆盖面（语料单一、属性与对象类型不均衡、诊断实验仅单系统）两方面，这些使其更适合作为**诊断性基准**而非精确排名工具。总体而言，该工作为文档智能体评测提供了一个可扩展的方法论模板，并诚实地揭示了当前最强系统在“上下文格式推断 + 精确 API 执行”上仍存在显著差距（最优推断型通过率仅 40.7%）。
