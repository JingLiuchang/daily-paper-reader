Abstract 

Long-horizon LLM agents can coordinate tools and applications to complete complex, multi-step tasks. As their interaction histories grow, effective context management becomes essen-tial for reliable and efficient execution. Existing methods reduce context through summariza-tion, pruning, or history selection. However, shorter contexts do not necessarily support bet-ter decisions: summaries can omit exact de-tails needed for later actions, while retaining entire interactions can carry substantial irrel-evant information. We propose CarryOn, a lightweight context manager that pairs com-pact execution state with fine-grained, source-linked evidence. A learned selector and adap-tive retention policy keep relevant evidence available without additional LLM calls for con-text management. We introduce two com-plementary evaluation metrics: Sα prioritizes task success while accounting for resource use, and normalized cost per success (NCS) measures the resources spent per successful task. Across AppWorld, OfficeBench, and Tau2 Telecom with three LLM Actors, Car-ryOn achieves 75.7% macro-averaged task suc-cess, exceeding the strongest baseline by 6.7 percentage points. It also achieves the best average scores on both metrics. Project repos-itory: https://anonymous.4open.science/ r/CarryOn-0816/ .

1 Introduction 

Long-horizon agents built on large language mod-els (LLMs) (Yao et al., 2022; Hu et al., 2025; Wang et al., 2024c) have made substantial progress in solving complex, multi-step tasks. These capa-bilities support applications ranging from every-day digital tasks (Trivedi et al., 2024) to office workflows (Wang et al., 2024b) and customer sup-port (Barres et al., 2025). The Actor records progress and next steps in a com-pact control state, while an evidence manager se-lects fine-grained units from original observations and preserves their source references. A learned selector and adaptive retention policy determine which evidence the Actor receives at each step, al-lowing earlier records to be brought back when they become relevant. 2 Related Work 

2.1 Long-Horizon LLM Agents 

Reliable long-horizon execution requires agents to turn goals into sequences of actions and adjust them using environment feedback. Agents interleave rea-soning and action (Yao et al., 2022) and use exe-cutable code to compose tool calls and respond to feedback (Wang et al., 2024a). Reflection on pre-vious attempts and state-driven workflows further structure execution (Shinn et al., 2023; Wu et al., 2024). A complementary direction reuses success-ful experience as executable skills or reusable work-2flows (Wang et al., 2023, 2024c). Hierarchical working memory further organizes ongoing execu-tion around subgoals (Hu et al., 2025). Evaluations that measure task length by human completion time highlight the difficulty of sustaining reliable exe-cution (Kwa et al., 2025). CarryOn supports long-horizon execution by adapting the Actor’s context to the information needed at each decision step. 

2.2 Context Management for LLM Agents 

Context management aims to keep useful infor-mation accessible within a limited working con-text. One approach uses a context manager separate from the Actor to construct its input through com-pression, selection, or structured memory. Prompt compression removes less informative content us-ing language-model scores or learned token clas-sifiers (Li et al., 2023; Jiang et al., 2023; Pan et al., 2024), while query-aware compression pri-oritizes information relevant to the current ques-tion (Jiang et al., 2024; Xu et al., 2024). Dia-logue systems also maintain memory by recur-sively summarizing previous exchanges (Wang et al., 2025b). For agents, learned observation pro-cessing and history summarization reduce the ma-terial passed to the Actor (Lee et al., 2025; Kang et al., 2025), whereas learned retention preserves selected action–observation steps (Zhang and Sun, 2026). Dependency-structured memory addition-ally connects past steps to the earlier information they rely on, supporting selective retrieval and sum-marization (Wu et al., 2026). Another line trains the acting LLM to man-age and use memory through recurrent consoli-dation, progress-aware retention, or indexed re-trieval (Zhou et al., 2026; Jiang et al., 2026; Wang et al., 2026b). ReSum-GRPO trains the Actor to continue from summarized contexts (Wu et al., 2025). Our work focuses on external context man-agement. CarryOn selects fine-grained fragments from original observations and can revisit previ-ously omitted evidence, while maintaining a sepa-rate compact state for task progress. 

3 Method: CarryOn 

CarryOn maintains an execution context that com-bines compact task state with selected evidence from the interaction history. The control state provides a concise account of progress and next steps, while selected evidence preserves the con-crete details needed for action. An evidence man-ager adapts this working context to the current de-cision, and the Actor uses it to act and update its state. Figure 2 organizes the method into four re-gions: History (1), Evidence selection (2), Acting 

(3), and Selector training (bottom). Experimental configurations appear in Section 4.2. 

3.1 Problem Formulation 

At decision step t, let q denote the task, Ht the in-teraction archive, ot the current public observation, and mt the current control state. Let Wt be the se-lected older evidence and Rt the recent interactions always included in context. The Actor receives 

Xt = Compose( q, m t, W t, R t). (1) Here, Compose also includes system instructions and tool definitions. The Actor jointly produces an action at and a proposed state update emt+1 . The accepted update carries progress forward, while the action and its observation extend Ht.

3.2 History and Evidence Units 

Summarizing observations can omit exact details, while retaining whole interaction steps can include many unrelated records (Kang et al., 2025; Zhang and Sun, 2026). CarryOn therefore selects obser-vation fragments independently. In region 1 ( His-tory ) of Figure 2, the Archive stores raw action– observation steps, and Split [i] divides observations into units such as individual records. Each unit re-tains its original content, a reference to its source interaction, and the action that produced the obser-vation. Unselected evidence remains in the archive for later decisions.

3.4 Acting with State and Evidence 

A compact state tracks what to do next, while evidence supplies the concrete values needed to act, such as account identifiers, file paths, or user-provided facts (Appendix F). In the payment ex-ample in region 3 ( Acting ) of Figure 2, the state records that seven coworkers have been found and should each receive $20, while evidence supplies the recipients’ account identifiers. 

Context and state update. The Actor context 

brings these representations together with the task and Latest step (Eq. 1). The LLM Actor jointly produces Action and New state . In our implemen-tation, the Actor’s bounded MEMORY update has five fields: done records completed work, open

Adaptive recent retention. Recent interactions provide the context needed to continue execution and correct invalid responses. CarryOn always re-tains the latest interaction and extends this recent window when the Actor produces an invalid action or state update. This adjusts the Latest step input in region 3 of Figure 2. Interactions outside this win-dow remain candidates for selection. Appendix B.1 specifies the acceptance and retention rules. 

3.5 Selector Training 

Successful trajectories show how earlier evidence supports later actions. The bottom Selector train-ing region of Figure 2 uses these trajectories from official training splits to supervise selection. At the Future-use labels stage, evidence cited in state annotations or used in later actions provides pos-itive ranking examples. Candidates with neither signal serve as weak negatives. Next-action use labels identify evidence used in the immediately following action. The LoRA fine-tuning stage (Hu et al., 2021) first adapts a pretrained reranker for pairwise ranking. For a positive block u+ and a weak negative block 

u− from the same decision step, the loss is 

ℓrank = log  1 + exp( γ + r− − r+) , (4) where r+ = rt(u+) and r− = rt(u−) are their relevance scores, and γ is the ranking margin. We then jointly optimize this ranking objective and binary cross-entropy for next-action use prediction: 

ℓuse = −y log p − (1 − y) log(1 − p), (5) where p = pt(u) and y ∈ { 0, 1} labels whether block u is used in the immediately following ac-tion. Both stages use complete action–observation blocks, matching the evidence references in the an-notations. At test time, the Frozen selector scores individual fragments in region 2. Appendix B.2 gives the labeling and optimization details.

4 Experimental Setup 

4.1 Datasets and Baselines 

We evaluate CarryOn on AppWorld (Trivedi et al., 2024), OfficeBench (Wang et al., 2024b), and the Telecom domain of Tau2-Bench (Barres et al., 2025), covering cross-application tasks, office workflows, and conversational customer support. The evaluation sets contain 168, 95, and 40 tasks, respectively, with success determined by each benchmark’s official evaluator. 4.3 Evaluation Metrics 

Context management should support successful task completion while controlling execution cost. Success alone does not reveal the resources re-quired (Kapoor et al., 2024), while low total cost can reflect early failure. We therefore report Suc-cess with two complementary measures: Sα em-phasizes task capability while accounting for cost, and normalized cost per success (NCS) measures the resources spent per successful outcome. 5.2 Evidence Retention for Long-Term Dependencies 

The ranking objective in Eq. 4 teaches the selector to favor evidence cited in state annotations or used in later actions. At each decision, CarryOn recom-putes the relevance score rt(u) using the task and current observation (Section 3.3), allowing previ-ously omitted evidence to be selected again. Fig-ure 4 shows that evidence obtained at least ten Actor steps earlier accounts for 30.7% of selections in AppWorld, 31.2% in OfficeBench, and 48.8% in Tau2 Telecom. In 40.2% of task runs, evidence is selected again after being omitted for one or more steps. The payment case in Appendix G.1 illus-trates the role of relevance ranking: a previously omitted card record returns to the base evidence pack, and the Actor uses its details to add the card and refill the balance. Relevance ranking brings earlier evidence back when action requirements change. 

Temporary evidence expansion adds records pre-dicted to be used in the next action (Eq. 3). It supplements the base pack in 4.4% of Actor steps on AppWorld and 12.2% on OfficeBench. In an AppWorld example, expansion restores an omitted contact record, and the Actor immediately uses its phone number to send a message (Appendix G.3).

6 Conclusion 

CarryOn separates compact progress tracking from fine-grained evidence selection, keeping exact ob-servations available as action requirements change. Experiments across three benchmarks and three Ac-tors demonstrate its effectiveness and cross-Actor generalization. CarryOn achieves 75.7% mean task success, exceeding the strongest baseline by 6.7 percentage points, and leads both S0.8 and NCS on average. These results support adapting evidence to each decision while maintaining concise task state for long-horizon execution. 

Limitations 

Our evaluation covers three benchmarks with text-based interactions. Extending CarryOn to visual or multimodal observations would require adapting how evidence is represented and selected. We train a separate selector for each benchmark and reuse it across Actors. Generalization to new environments, particularly those with different tool interfaces and observation structures, remains to be explored. In real-world applications, retained observations 8may contain sensitive information, while missing or misinterpreted evidence may lead to incorrect actions. Deployment therefore requires appropriate access controls for stored history and user confir-mation for consequential actions.

10 A Experimental Details 

This appendix provides the dataset splits, configura-tion settings, and execution interfaces summarized in Section 4. 

A.1 Benchmarks and Task Splits 

AppWorld (Trivedi et al., 2024) uses the offi-cial test_normal split of 168 tasks, comprising 57 easy, 48 medium, and 63 hard tasks. Of-ficeBench (Wang et al., 2024b) uses the ACON-public test set of 95 tasks, comprising 42 L1, 22 L2, and 31 L3 tasks with 209 planned evaluator con-ditions. Tau2 Telecom (Barres et al., 2025) uses the official 40-task test set. We retain the benchmarks’ native tasks, tools, and official success criteria. Car-ryOn selector training uses successful trajectories from the official training splits, as described in Ap-pendix B.2. 

A.2 CarryOn and Execution Configuration Models and computation. Each local training job uses one NVIDIA H100 GPU. The selector has 0.6B parameters, while the Qwen and Gemma Ac-tors have 27B and 31B, respectively; CarryOn-E uses a 9B student. For the reported selectors, the two training stages together take approximately 4.87, 0.59, and 0.79 hours on AppWorld, Of-ficeBench, and Tau2, respectively, estimated from training logs. These are single-GPU wall times, excluding trajectory generation and evaluation. We report a single run per setting. 

Context construction. We use a base evidence budget of B = 16 ,384 characters and a temporary evidence expansion threshold of τ = 0 .5. The MEMORY capacity is 128 proxy tokens, counted locally as words and punctuation symbols. The recent-evidence window retains the newest inter-action after an accepted response and the two newest otherwise, limited to available history. Han-dling of public interaction boundaries follows Ap-pendix B.1. The budget covers the base evidence pack. 

Selector training. The selector backbone is Qwen3-Reranker-0.6B. We use Claude Sonnet 5 to generate the offline state annotations and their evi-dence references. The pairwise ranking margin is 

γ = 0 .2. Training objectives and label construction are specified in Appendix B.2. 

Execution interfaces. Actors use benchmark-specific action and output interfaces. Tau2 pairs the Actor with a Haiku 4.5 User simulator. The Actor and selector receive only public interactions, excluding private simulator state. 

A.3 Baseline Configurations 

We retain each method’s context construction and evaluate the resulting systems on the same task sets. Cost accounting is described in Appendix D.1. 

Simple history baselines. Full History retains the complete interaction history. FIFO-5 retains the five most recent action–observation pairs. Re-trieval selects four historical interactions using 

text-embedding-3-large and includes the latest interaction. FIFO-5 and Retrieval follow the imple-mentations in ACON (Kang et al., 2025). 

LLMLingua-2. We use LLMLingua-2 (Pan et al., 2024) as a local history compressor with a fixed keep rate of 0.3. 

ACON and AGORA. ACON (Kang et al., 2025) uses LLM-based context compression. AGORA (Zhang and Sun, 2026) uses a learned scorer to select historical interactions. 

SWE-Pruner. We use benchmark-adapted SWE-Pruner models (Wang et al., 2026a) with a pruning threshold of 0.4. Observations are pruned when the Actor provides a focus and otherwise retained.

B.2 Selector Supervision and Optimization Training examples and labels. We construct ex-amples at intermediate decision boundaries of suc-cessful trajectories from the official training splits. In the block-supervised path, each candidate is an earlier complete action–observation block. Rank-ing positives combine evidence references in offline state annotations with observed evidence-use sig-nals. AppWorld traces which earlier observations supply values to the next tool call. OfficeBench matches earlier evidence to arguments of the next action. Tau2 tracks evidence reuse in subsequent public interactions. For next-action use prediction, positive labels are restricted to evidence linked to the immediately following action. Uncited and unused evidence is treated as a weak negative. Offline labels use subsequent public inter-actions, while selector inputs contain the task and observations available at the current decision. 

Scoring architecture and objectives. The func-tions fϕ and gϕ in Eq. 2 share a pretrained back-bone with separate instructions for relevance rank-ing and next-action use prediction. The latter uses a learned linear head. The sigmoid is σ(z) = 1/(1 + exp( −z)) . The initial training stage adapts the reranker with LoRA using the pairwise rank-ing loss in Eq. 4. The backbone and margin are specified in Appendix A.2. The subsequent stage jointly optimizes this ranking objective and the next-action use loss in Eq. 5. This stage updates the ranker adapter as well as the new head. Whole-block training preserves the units refer-enced by the offline annotations. At deployment, the same query and candidate interface scores the finer units from Section 3.2, each paired with the action that produced its source observation. This transfers block-level supervision to fragment se-lection without requiring a separate annotation for every fragment.

I.2 Training and Evaluation Settings 

The student is initialized from Qwen3.5-9B and evaluated on all three datasets. Each aggregation round trains for one epoch over the accumulated data. The reported models use six rounds on Ap-pWorld, seven on OfficeBench, and five on Tau2. Student inference uses non-thinking mode, and dis-tillation uses only training-split tasks. Estimated cumulative training wall times, including initial supervised fine-tuning and all aggregation rounds leading to the reported models, are 54.00, 23.06, and 54.28 hours on AppWorld, OfficeBench, and Tau2, respectively, using one H100 GPU per train-ing job. These estimates exclude rollout collection and teacher labeling.
