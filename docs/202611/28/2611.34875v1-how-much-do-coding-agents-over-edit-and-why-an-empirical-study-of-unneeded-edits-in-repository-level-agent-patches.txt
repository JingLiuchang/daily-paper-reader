How Much Do Coding Agents Over-Edit, and Why? An
Empirical Study of Unneeded Edits in Repository-Level
Agent Patches
Aakash Goel*, Benjamin Steenhoek*, Yu Hu
Microsoft
{aakashgoel, bensteenhoek, yuhu}@microsoft.com
Agent patches are larger than developers’, which is widely read as over-editing. But patch size does
not say whether the extra edits are needed, what they are, or where they come from. We introduce
Delta Residue Attribution (DRA), which replays agent trajectories, traces every block (unit) of the final
patch to the step that wrote it, reverts each unit, and reruns the task tests to decide whether the unit is
needed. We apply DRA to 7,660 resolved GitHub Copilot CLI trajectories from 18 frontier models on
SWE-bench Verified (6,728) and DeepSWE (932), and grade developer patches using the same method.
Agent patches do change more lines than developers’; on SWE-bench Verified the majority of extra edits
add tests (61%) and documentation (13%) while on DeepSWE, most extra edits are code (58%). On both
benchmarks, agents’ code is on average at least as necessary as developers’ (mean NPcode 0.887 vs. 0.864
on SWE-bench Verified, where 11 of 18 models leave less unneeded code than developers, and 0.797
vs. 0.785 on DeepSWE). On average, 11% of an agent patch’s code units on SWE-bench Verified are
still unneeded, and 89% of those change behavior. Tests the agent adds detect most injected bugs (68%,
against 77% for the task tests); 5% of all injected bugs are caught by the agent’s new or strengthened
tests but missed by the task tests. Debug steps write almost none of the unneeded code. Code necessity
differs substantially by model; it is unrelated to resolve rate on SWE-bench Verified and negatively
correlated with it on DeepSWE (Spearman −0.59, p = 0.01). On SWE-bench Verified, pruning with
DRA using only the tests the agent can see (its own tests and the repository’s) removes the majority
of unneeded code but also some needed code (67% recall, 46% precision), and 89% of pruned patches
still resolve the task; asking the agent to audit its own diff is more precise but less effective (36% recall,
66% precision). We recommend that benchmarks report code necessity next to resolve rate and that
over-editing be addressed through model training and harness-level pruning.

Introduction
Language models are now routinely asked to edit existing code rather than write it from scratch. Passing tests
is necessary but not sufficient: a patch that fixes a three-line bug by rewriting fifty lines is harder to review
and more likely to carry unintended changes. In a maintainer study, roughly half of the SWE-bench-passing
patches would not have been merged (Whitfill et al., 2026), and many plausible patches behave differently
from the developer fix on inputs the tests do not cover (Wang et al., 2026). We call the tendency to change
more than necessary over-editing. On minimal function-level edits, models change far more than the task
requires (Zhu et al., 2026). At the repository level, successful agent patches contain about twice as many
changes as developers’ patches, and minimality prompts barely help (Luo et al., 2026). Larger agent patches
are therefore widely read as over-editing.
Preservation prompts (Zhu et al., 2026; Chai et al., 2026) and edit-aware training (Zhu et al., 2026; Yang
et al., 2026; Ke et al., 2026) reduce function-level over-editing. Patch size does not tell whether the extra edits
are needed, what kind of edits they are, or when in the trajectory they were written; the answers to these

them up. If they are tests, they may be welcome. If they are written into the fix, the model has to change.
We study over-editing in repository-level patches at the level of individual blocks and the trajectory steps that
wrote them. Our research questions are: RQ1: How much do agents over-edit compared with developers?
RQ2: What are the unneeded edits? RQ3: Where in the trajectory do they come from? RQ4: Which
models over-edit more, and does over-editing track resolve rate? RQ5: Can unneeded code be removed
automatically?
To answer these questions, we build DRA. DRA replays a resolved trajectory, splits the final patch into units
(contiguous blocks of changed lines that can be reverted on their own), and traces each unit to the step that
wrote it. It decides whether a unit is needed by reverting it and rerunning the task tests, in the tradition of
delta debugging (Zeller and Hildebrandt, 2002). The share of needed units is the necessity precision NP, and
NPcode is that share over code units. Because benchmark tests miss some needed behavior (Wang et al., 2026),
we also check unneeded code with behavioral probes (Section 3.4) and grade developer patches the same
way. We apply DRA to 7,660 resolved coding-agent trajectories of 18 models on SWE-bench Verified and
DeepSWE.
Findings.
Agent patches do change more lines than developers’, but on SWE-bench Verified the extra lines
are mostly tests (61%) and documentation (13%), while on DeepSWE most extra edits are code (58%; RQ2).
On code, on SWE-bench Verified 11 of 18 models leave less unneeded code than developers (mean NPcode
0.887 vs. 0.864), for four no significant difference is detected (which does not establish equivalence), and three
models leave more (RQ1, Section 5.1). On DeepSWE, agents are on par with developers (0.797 vs. 0.785), but
no model is significantly above the developer baseline. On average, 11% of an agent patch’s code units are still
unneeded, and 89% of those change behavior (RQ2). Debug steps (exploring, reproducing, or probing) write
almost none of the code residue (154 of 3,987 units); fix steps write 83% of it (RQ3). Code necessity differs by
model and does not correlate with resolve rate on SWE-bench Verified (Spearman −0.10), but on DeepSWE
it is anti-correlated (−0.59, p = 0.01; RQ4). On SWE-bench Verified, after generation, self-audit is precise
(65.7%) but finds only 35.5% of unneeded code, pruning with the agent’s own tests and the repository’s
regression tests finds 67.3% at lower precision (46.3%) on the 2,495 eligible patches, and stopping early barely
changes NPcode (0.700 to 0.710; RQ5). Our contributions are a block-level empirical study of over-editing
with developer patches graded the same way, the DRA method (Section 3), and implications for evaluation
and harness design (Section 6). Appendix A.1 lists our pre-registered hypotheses and our deviations from
them.

Related Work
Measuring over-editing.
Zhu et al. (2026) and PDB (Chai et al., 2026) measure unneeded edits against a
known minimal fix, mostly on single functions, CanItEdit (Cassano et al., 2024) measures how much of a
function edit the tests cover, and edit-aware training reduces it (Yang et al., 2026; Ke et al., 2026). At the
repository level, RECAP (Luo et al., 2026) compares patch sizes. Coverage metrics conflate “executed by
tests” with “required by the task”. DRA measures necessity by counterfactual removal and needs no unique
reference patch.
Why unneeded changes are costly.
Change size predicts defects (Nagappan and Ball, 2005; Kamei et al.,
2013), and tangled changes distort defect data (Herzig and Zeller, 2013). Reviewers favor small, focused
changes (Rigby and Bird, 2013; Bacchelli and Bird, 2013), and larger changes take longer to review (Sadowski
et al., 2018). Agent pull requests often need reviewer involvement or later rework (Peralta et al., 2026; Pham
and Ghaleb, 2026). Plausible patches often differ from the developer fix on untested inputs (Wang et al., 2026).
LLM refactorings that pass existing tests can still change behavior (Dristi and Dwyer, 2026). Both findings
motivate our behavioral checks.

Tracing Edits to Trajectory Steps: DRA
DRA has four steps: replay, unit provenance, step-role labeling, and necessity grading. Figure 1 shows the
pipeline on a small example (Appendix B.1), and Algorithm 1 gives pseudocode.
3.1
Definitions
An agent produces a trajectory of actions and observations; executing the first t actions of a task yields the
working-tree state St, and the submitted patch is ∆= diff(S0, ST). We decompose ∆into units U(∆) =
{u1, . . . , un} that can each be reverted on their own, and write ST ⊖u for the state with unit u reverted. An
oracle O accepts a state (O(S) = 1) if it passes some check. The task-test oracle Otest runs the SWE-bench
FAIL_TO_PASS and PASS_TO_PASS tests (Jimenez et al., 2024) (on DeepSWE, the task’s own tests). We
analyze only resolved patches, so O(ST) = 1. A unit is needed for O if reverting it causes rejection (nO(u) = 1,
written NEEDED), and unneeded otherwise (nO(u) = 0, written UNNEEDED). The necessity precision NPO of a
patch is its needed units divided by all its units:

an atomic piece of an edit. Unneeded code is an unneeded unit in a code file; units in test files are graded
separately (Section 3.2). NP inherits the oracle’s blind spots: a unit that the tests do not need may still serve
the developer’s intent (Smith et al., 2015). We therefore treat the share of unneeded units as an upper bound
on true excess, and we compare agents with developer patches graded the same way (Appendix B.2 separates
three notions of minimality).
3.2
Replay, Units, and Provenance
Agent trajectories record every tool call but not intermediate repository states. We replay the structured file-
editing calls on the task’s base files with line-level blame after each step, and we exclude trajectories whose
replayed final state does not match the submitted patch exactly (96.7% of SWE-bench Verified trajectories
replay). A unit is a contiguous block of changed lines in one file (blocks separated by at most one unchanged
line are merged), and a new or deleted file is one unit. Each unit is a code unit or a non-code unit (test,
documentation, configuration, or comment and formatting edits). SWE-bench grading resets test files, so test
changes don’t change the oracle’s result. We therefore report test edits separately from code as ungraded, and
call ungraded test edits and unneeded units together the patch’s extra edits. We use NPcode as the primary
measure (Appendix B.3 gives the rules). The introduction step t⋆(u) of a unit is the latest step that wrote or
deleted any of its lines, so a unit first written at a debug step and later revised at a fix step is attributed to the
fix.
3.3
Step-Role Labeling
Each step that introduces a unit gets a role. We group roles into three: DEBUG (explore, reproduce, and probe
steps), FIX (fix and refine steps), and CLEANUP (steps that revert earlier changes). Two deterministic rules run
first, and an LLM judge (GPT-6.1 Sol) labels the rest based on the issue, the condensed history, the action, and
the agent’s narration (Appendix B.4 gives the six fine-grained roles and the rubric).
3.4
Oracle: Grading Necessity
For each unit we revert its lines in the task container and rerun the task tests. We count reversions that cannot
be applied (they leave the base state or do not parse) as needed. Task tests do not exercise every input path,
so we also check unneeded code units with behavioral probes modeled on PatchDiff (Wang et al., 2026). We
report necessity under Otest and use the probes to validate its unneeded verdicts; the strengthened oracle
O+, which also rescues units whose reversion matches the developer patch, uses the same probe labels. For
each code unit that Otest marks unneeded, an LLM (GPT-6.1 Sol) sees the issue and the diff of the reversion,
without the task tests or the developer patch, and writes several differential calls: probe-script inputs that
call the changed code and print labeled outputs. We run them under the agent patch, the reverted state,
and the developer patch. A unit is needed under O+ if its reversion fails the task tests or makes the same
behavioral change as the developer patch. Appendix C.1 reports the breakdown. Units are reverted one at a
time (Section 6).

Study Setup
4.1
Data
We evaluate 18 models from four providers on SWE-bench Verified (Jimenez et al., 2024; Chowdhury et al.,
2024) (500 Python coding tasks) and DeepSWE (Huang et al., 2026) (113 long-horizon coding tasks in Go,
TypeScript, Python, Rust, and JavaScript), using the GitHub Copilot CLI (GitHub, 2026) coding agent.
SWE-bench Verified resolve rates range from 64.0% to 89.4%. The resolve rate of a model is the share of its
attempted tasks whose final patch passes the task tests. For each model we use all of its resolved SWE-bench
Verified instances whose trajectory replays exactly, and all of its resolved DeepSWE tasks. Model-level
DeepSWE statistics use the 17 models with at least 10 graded tasks. The study covers 6,728 SWE-bench
Verified patches (30,265 units; 482 distinct instances, 114 shared by all 18 models) and 932 DeepSWE patches
(26,209 units). We ran developer baselines on SWE-bench Verified (470 analyzed instances, 1,317 code units)
and on DeepSWE (103 graded tasks; four developer patches fail the task tests and are dropped). Other
harnesses and SWE-bench Pro are reported in Appendix D. All units are graded in the official evaluation
images under Otest; behavioral probes validate the unneeded verdicts (Section 3.4). Role and probe judges
are GPT-6.1 Sol. A second judge (Claude Opus 5.5) relabeled 10,000 randomly sampled steps and agreed
with the primary judge on 84.4% of role labels (κ = 0.69) and 89.1% of debug vs. non-debug labels (κ = 0.55;
Appendix B.4).
4.2
Research Questions and Analyses
For each research question, we pre-registered the outcome we expected (Appendix A.1), with thresholds
and deviations from the original experiment plan. A two-model pilot showed that most extra edits are test
edits, so we implemented separate analyses for code and tests, made code units the primary population, and
added the developer calibration.
5
Results
Appendix E.6 lists per-model results and Appendix D holds the secondary analyses referenced below.
5.1
RQ1: How Much Do Agents Over-Edit?
By size, agent patches look bloated. On SWE-bench Verified the median model changes 2.33 times as many
lines as the developer patch, in line with Luo et al. (2026). On code units alone the ratio is 0.86, and the
per-task median is 1.00. Outside test files, agents still change more lines than developers (median ratio 1.09).
By necessity, agents’ mean NPcode is 0.887, against 0.864 for developer patches on the same instances. So
agents produce more non-test changes, but most of the code they write is needed. Developer patches serve
as a baseline for the oracle: Otest alone calls 33% of developer code units unneeded, and the strengthened
oracle O+ calls 3% unneeded (Appendix C.1).
Figure 2 shows the gap ∆dev on both benchmarks. On SWE-bench Verified (Figure 2a), eleven models leave
significantly less unneeded code than developers (GPT-6 Astra only marginally, with a CI lower bound of
0.002), four show no significant difference (Kimi K3, Claude Haiku 4.5, GPT-6 Sol, GPT-6.1 Sol), and three
leave significantly more: Gemini 3.8, 3.7, and 3.6 Flash. On DeepSWE (Figure 2b), mean NPcode is 0.797,
against 0.785 for the 103 developer patches; only two models are significantly below the developer baseline
and none significantly above (mean gap −0.005). The sign of the SWE-bench Verified gap depends on the
oracle: under O+ it flips from +2.3 to −4.5 percentage points (Appendix C.1).

5.2
RQ2: What Are the Unneeded Edits?
Figure 3 shows the classes of extra edits. On SWE-bench Verified, 61% are test-file edits, 21% are code, 13%
are documentation, and 5% are comment or formatting edits. Test edits are pervasive (81.5% of agent patches
edit a test file) and ungraded, and a reviewer may welcome many of them. Counting them as unneeded
would dominate the all-unit NP, which then mostly tracks how many tests a model writes. On DeepSWE the
composition flips: tasks are feature implementations with about six times more units per patch. Code is 58%
of extra edits, and tests are 26% (Appendix D).
On SWE-bench Verified, among the 3,987 unneeded code units, the behavioral probes (run on 3,559 unneeded
agent units) show that 89% change behavior, for example by raising or swallowing an exception on nearby
inputs. The other 11% are inert guards or duplicate checks (Appendix C.1).
We use mutation testing (Jia and Harman, 2011; Just et al., 2014) to ask whether the tests agents add are
useful. Over the 271 SWE-bench Verified instances that pass our validity checks, we inject 1,962 mutants
(small artificial bugs) into the patched code with mutmut (Hovmöller, 2026). The agent’s added tests catch
68.1% of them: more than the existing regression tests in the same files (45.6%), but fewer than the task tests
(77.1%). They catch 73.2% of mutants in needed code and 31.2% in unneeded code. The agent’s tests also
catch bugs the task tests miss. Of the mutants that slip past the task tests, 22.7% (102) are caught by tests the
agent added or strengthened; this is 5.2% of all mutants (Appendix F.1). Most agent tests are written after the
fix, and few show a failing-then-passing run (Appendix D).

Finding 2. On SWE-bench Verified, beyond the code, patches mostly add tests (61%) and documentation (13%); on

5.3
RQ3: Where Do Unneeded Edits Come From?
If residue came mostly from debugging, it would enter the patch at debug steps and never be reverted. The
pooled debug share over all residue is ρ = 0.257, but 4,676 of the 4,898 debug-step residue units are test-file
hunks that the agent wrote before the fix as regression tests. On code, only 154 of the 3,987 code-residue
units (in 55 patches) come from debug steps, so ρcode = 0.039. Scratch scripts and debug prints almost never
survive into resolved patches.
Fix steps write 83% of unneeded code, and revision steps write 11%. Code written while revising a fix
is unneeded only slightly more often than code from the first fix (0.29 vs. 0.25), and revisions are rare
(Appendix D). On DeepSWE, over units with exact provenance, ρcode is 0.037.
Finding 3. Debug steps write almost none of the unneeded code (154 of 3,987 units, ρcode = 0.039); fix steps write 83%
of it, and code from revisions is unneeded only slightly more often than first-fix code (0.29 vs. 0.25).
5.4
RQ4: Which Models Over-Edit More?
Across the 18 models on SWE-bench Verified, the Spearman correlation between resolve rate and NPcode
is −0.10 (raw p = 0.69; 95% CI [−0.28, +0.05], bootstrap over each model’s instances). At nearly the same
resolve rate, Sonnet 5 (80.6%) has NPcode = 0.922 and Gemini 3.7 Flash (81.4%) has 0.789, so Gemini 3.7 Flash
leaves about 3.6 times as many unneeded code units per task (1.23 vs. 0.34).
The model effect survives controls for unit granularity and task selection (Appendix D.4). Multi-unit and
line-weighted variants keep the ranking, and task fixed effects leave the same three Gemini Flash models
below developers.
On DeepSWE the relation reverses: NPcode is negatively correlated with resolve rate (Spearman −0.59,
p = 0.01; −0.52, p = 0.03, task-adjusted), so models that solve more tasks leave more unneeded code. The
model ranking agrees moderately between benchmarks (+0.59), and Gemini 3.7 and 3.8 Flash are low on
both (Table 9).
Finding 4. The amount of unneeded code differs by model. It does not track resolve rate on SWE-bench Verified
(Spearman −0.10), even after controlling for unit granularity and task selection, but on DeepSWE models with higher
resolve rates leave more unneeded code (−0.59).

Self-audit.
We ask each model to justify every hunk of its final diff and drop the ones it cannot. Across all
resolved SWE-bench Verified patches (17 of 18 models; Appendix D.5), dropped code hunks match a unit
that O+ calls unneeded 65.7% of the time, but the audit finds only 35.5% of all such units (κ = 0.39); the
drops break 1.8% of resolved patches. Models are selective: they drop 40.5% of unneeded units that behave
like the patch without them, against 14.7% of those that behave like the full patch. Applying the drops raises
NPcode from 0.924 to 0.944.
Pruning with DRA.
Most agents run their own tests, and 4,860 of 6,728 trajectories reach a green run.
We run a simplified cumulative DRA that reverts a unit whenever the agent’s test command Oagent still
passes, and we also require the existing PASS_TO_PASS tests (Oagent+P2P). This applies to 2,495 of the 6,724
patches, because the others have no standalone test command or fail the baseline check (Appendix G.1). With
Oagent+P2P, pruning removes 67.3% of the unneeded code units, nearly twice the self-audit’s recall, but at
46.3% precision against the self-audit’s 65.7%. It raises NPcode from 0.936 to 0.975, and 89.1% of patches still
pass the task tests. With Oagent alone, pruning reaches 39.6% precision and 66.5% recall, and 86.6% of its
patches still pass the task tests. Most false drops are code units that implement behavior that neither the
existing tests nor the agent’s tests exercise.
Finding 5. On SWE-bench Verified, self-audit and test-based pruning trade precision for recall. Self-audits are precise
(65.7%) but find only about a third of unneeded code (35.5%), and their drops break 1.8% of resolved patches. Pruning
with the agent’s own tests and the repository’s regression tests finds about two thirds (67.3%) at lower precision (46.3%)
on the 2,495 eligible patches, and 89.1% of them still resolve. Early stopping barely changes the patch (NPcode 0.700 to
0.710), because most unneeded code is already in the patch when the agent’s tests first pass.
6
Discussion and Limitations
Does the metric measure what we claim?
We check the metric against the developer patch. A code unit is
outside-patch if it lies outside every function the developer patch touched. Of 14,591 agent code units on 6,596
instances, 2,607 are outside-patch. The DRA unneeded flag predicts outside-patch units with an AUROC of
0.718, against 0.478 for unit size (difference +0.24, 95% CI [0.21, 0.27]); it flags 3,753 units at precision 0.43
and recall 0.62. At the instance level, the unneeded-line fraction correlates with the outside-patch fraction at
Spearman 0.40, against 0.21 for edit distance and 0.25 for lines relative to the developer patch. The metric
flags code a developer would likely not have written better than patch size does, though fewer than half of

(Appendix D).
Implications.
The amount of unneeded code a model writes does not track its resolve rate on SWE-bench
Verified and is anti-correlated with it on DeepSWE, and most unneeded code changes behavior, so reviewers
cannot skip it (Section 5.2, Section 5.4). Because code necessity differs by model, coding benchmarks should
report NPcode with a developer-patch baseline alongside resolve rate. Size comparisons with developer
patches should separate test and code edits. Debug steps write little code residue, so in-loop cleanup
would have little to remove, although we did not test it, and post-generation cleanup is the more promising
target. Its two forms trade off: self-audit rarely drops needed code but misses most unneeded code, while
pruning with the agent’s and the repository’s regression tests finds most of it at the cost of more false drops
(Section 5.5). Because the unneeded code is written while constructing and revising the fix, we recommend
debloating training trajectories: drop units that the tests do not need before supervised fine-tuning, in line
with edit-aware training (Yang et al., 2026; Ke et al., 2026) and as PDB proposes (Chai et al., 2026).
Limitations.
Necessity depends on the oracle, and on DeepSWE and SWE-bench Pro it is an upper bound
on unneeded code (on DeepSWE the developer baseline is 0.785). Behavioral checks are LLM-written, and
oracle-unneeded code can still be wanted. Units are reverted one at a time, so jointly needed pairs and
mixed blocks can mislead. We study over-editing in successful trajectories, i.e., resolved patches, and leave
over-editing in unsuccessful trajectories to future work. Role labels were validated against a second LLM
judge only, with no human audit (Appendix B.4). The debug-share result rests on 154 of 3,987 code-residue
units, and the mutation results cover 271 instances (1,962 mutants). Provenance needs replayable trajectories:
3.3% of SWE-bench Verified replays are not exact (228 replay mismatches, 6 self-check failures, 5 binary
patches), and 33.4% of DeepSWE patches (311 of 932) contain at least one unit without provenance (14.9%
of units, 12.7% of code units). The main results use one harness, Copilot CLI (Appendix D covers others).
SWE-bench Verified is Python-only and may be contaminated.
Future work.
Human labels (Appendix B.5) would test whether reviewers agree with the oracle. Property-
based testing (MacIver et al., 2019) and LLM-generated differential tests (Hu et al., 2026) could extend
probe-based grading to benchmarks without developer patches. Repeating the experiment on open-source
harnesses such as OpenHands (Wang et al., 2025) and mini-SWE-agent (SWE-agent Team, 2025), using public
trajectories (SWE-bench Team, 2026), would show how harness design affects over-editing.
7
Conclusion
We took 7,660 resolved coding-agent trajectories and traced each block of the final patch to the step that
wrote it, then graded necessity with the task tests and validated unneeded code with behavioral probes.
Agent patches are larger than developers’, but on SWE-bench Verified the extra lines are mostly tests and
documentation. On code, on average about 11% of an agent patch’s code units are unneeded; on SWE-bench
Verified, 11 of 18 models leave less unneeded code than developers and the three Gemini Flash models leave
more, while on DeepSWE agents are on par with developers. The unneeded code that remains is written
while building and revising the fix, usually changes behavior, and differs by model, with no relation to resolve
rate on SWE-bench Verified and a negative one on DeepSWE. After generation, self-audit removes it precisely
but finds only about a third, while pruning with the agent’s own tests and the repository’s regression tests
finds about two thirds at lower precision on the patches where it applies. We recommend reporting code
necessity next to resolve rate and addressing over-editing through model training and harness-level pruning.

B.3
Replay, Units, and Grading Details
Replay.
For each instance we fetch the base version of every file the final patch touches and apply the
trajectory’s file-editing tool calls (edit string replacements, create, and patch-application calls) in order,
keeping for each line of each file the step that last wrote it and, for each deleted base line, the step that deleted
it. When a file was written by a shell command (for example sed or a heredoc), we attribute it to the last shell
command that writes and names that file and reconstruct the file state after it by undoing the later structured
edits; if that is not possible, the file’s units keep their necessity grade but have no provenance. A trajectory is
kept only if the replayed final contents equal the submitted patch for every file.
Units.
For each file we diff base and final contents with Python’s difflib (no autojunk) and merge
change blocks separated by at most one unchanged line. A created or deleted file is one unit. Units
are classified by path and content, in this order. Test: the file is in the official test patch, or its path is
in a test/tests/testing/__tests__/testdata/e2e directory or matches a test-file pattern (test_*.py,
*_test(s).py, conftest.py, *_test.go, *.test/spec.[jt]s(x), snapshots, tests.rs). Docs: the path is
under doc/docs, ends in .rst, .txt, or .md, or is a changelog, authors, or news file. Config: JSON, YAML,
TOML, lock, module, and similar files. Nonsemantic: a Python file whose AST, with docstrings removed, is
unchanged by the unit, or a C-like source file whose token sequence without comments and whitespace is
unchanged. Code: everything else. Developer patches, SWE-bench Pro patches, and other-harness patches
are unitized the same way, without replay.

Grading.
For unit k, the variant patch is the final patch with unit k restored to its base lines (or the file
removed or restored). Each variant is graded with the task’s FAIL_TO_PASS and PASS_TO_PASS tests in the
official evaluation image, together with a control run of the full patch; instances whose control run fails are
excluded. Units whose reversion would leave the base state are recorded as necessary without a run (742
units on SWE-bench Verified); reversions that do not parse are counted as necessary (39 units); and variants
whose test run hung repeatedly are recorded as failures, i.e., necessary (22 units). An evaluation status of
error counts as unresolved.

C.1
Strengthened Test Oracle and Behavioral Probes
Benchmark test suites do not exercise every path a developer fix touches (Wang et al., 2026). The primary
measure is NP under Otest (developer baseline NPcode = 0.864 over 1,317 code units), and behavioral probes
validate the unneeded verdicts. The strengthened oracle O+ uses the GPT-6.1 Sol probe judge. We probed
3,559 Otest-unneeded agent code units and 432 of the 434 Otest-unneeded developer code units (26 agent units
on 9 patches lie on tasks without a developer source patch and are unprobed). The pooled NP comparisons
under O+ below use the probe cohort of 18 models, 6,728 patches and 482 unique tasks (469 with developer
source patches), where Otest gives an agent mean NPcode = 0.887 against a developer baseline of 0.864
(∆dev = +0.023, p = 0.016). To separate untested but developer-equivalent fixes from truly unneeded code,
we use differential behavioral probes inspired by PatchDiff (Wang et al., 2026).
Probe results (GPT-6.1 Sol).
GPT-6.1 Sol wrote the probes. Of 3,559 probed unneeded agent code units,
3,151 (89%, 95% CI [87, 90]) change behavior when reverted, against 363 of 432 (84% [80, 87]) for developer
code units. On 388 units judged by both, Opus 5.5 finds 81% changing behavior and GPT-6.1 Sol 89%
(κ = 0.53; for developer units 70% vs. 80%, κ = 0.64), so the judge change makes the probe stricter about
inertness. Class agreement between judges is 93% (287 of 308).
Probe protocol and breakdown.
For each Otest-unneeded unit u of a final patch ST, the probe judge reads
the issue and the diff between ST and ST ⊖u (without seeing the hidden tests or the developer patch) and
writes a probe script that calls the changed code and prints labeled outputs. Each probe runs on ST, ST ⊖u,
and the developer-patched repository Sdev. On the 112 Otest-needed agent code units used as a positive
control, the probes detect a behavioral change on all 112 (100%; 119 of 119 with developer units, Table 7).
Among the 3,559 Otest-unneeded agent units, 3,151 (88.5%) change behavior when reverted: on 1,263 (35.5%),
Sdev matches ST rather than ST ⊖u (untested developer-aligned fix, needed under O+); on 1,586 (44.6%),
Sdev matches ST ⊖u (unrequested behavioral change); on 133 (3.7%) the evidence is mixed and on 169
(4.7%) Sdev matches neither version. The remaining 408 (11.5%) are inert on all probes. Under O+, the 2,296
remaining unneeded agent code units therefore split into 1,888 live divergences (82%) and 408 inert edits
(18%). Replacing Otest with O+ raises developer NPcode from 0.864 to 0.970 and mean agent NPcode from 0.887
to 0.925, so the developer-baseline gap flips from +2.3 to −4.5 percentage points (p = 9.6 × 10−5; −4.8 ± 0.7
with task fixed effects, p = 4 × 10−11; −11.0 on patches with at least two code units, p = 1.1 × 10−9).
Under the live-behavior oracle Olive (any behavior change counts as needed) agents are +0.8 points above
developers (0.978 vs. 0.970, p = 2.4 × 10−4). Per model, Olive puts 14 of 18 models above developers and one
below, while O+ puts 12 models below developers and none above. The 428 unneeded agent units that could
not be probed (234 have no developer code, 194 timed out) do not change the sign: restricted to patches with
all units probed, the Olive and O+ gaps are +1.5 and −3.8 points. Table 8 reports the per-model results with
95% bootstrap confidence intervals under the benchmark task tests (Otest) alone.

Four-arm mutmut protocol and mutant catalog.
To evaluate the fault-detection value of agent-edited test
units (Section 5.2), we used mutmut (v3.8.1, built on libcst v1.9.0) (Hovmöller, 2026; Jia and Harman, 2011;
Just et al., 2014) to enumerate syntactic mutants restricted to the line ranges of agent-modified Python code
units across all 6,728 resolved SWE-bench Verified patches (4,461 unique patched files; 198 files fail to parse).
Because mutmut 3.8.1 skips most decorated functions by default, we subclassed MutationVisitor to strip
node.decorators only while walking the function body, preserving mutations inside decorated methods
without mutating decorator arguments. Across all patches, mutmut produces 96,790 mutants: 77,549 in
Otest-needed code units and 19,241 in Otest-unneeded code units (Table 17).
For dynamic execution, we scaled to the 387-instance eligible frame of single-patch runs that edit both
Python source and test files (3,525 patches, 11 repositories). Of these, 271 instances pass the validity gates
G1–G4 (115 fail the G1 base guard, mostly environment differences in astropy, django and sphinx, and 1 fails
G4): worktree tree-hash parity with ST, zero-mutation control pass on T, ≥1 collected test in Ascope, and
≥1 evaluated non-stillborn mutant. Of 2,937 planned mutants, 1,962 were evaluated and non-stillborn (56
stillborn, 3 timeouts, 5 unresolved, 21 skipped by the run budget). Each mutant was tested under up to four
arms:
1. Held-out task tests (T, Otest): the benchmark’s FAIL_TO_PASS and PASS_TO_PASS tests run after resetting
test files and applying the developer test_patch.
2. Strengthened oracle (O+ = T ∪P): Otest combined with differential behavioral probes P (Section 5.2),
where P kills a mutant if the mutant alters any probe’s return value or exception outcome relative to the
unmutated patch ST. The probes are the GPT-6.1 Sol-judged PatchDiff probe scripts, executed in the task
container on every mutant; 98 instances (485 of the 2,937 planned mutants) are probe-eligible.
3. Baseline tests in agent-touched files (B): the unedited S0 versions of the test files modified by the agent.
4. Agent test files (A) and exact agent test units (Ascope): the agent-modified test files in ST, scoped to the
specific test functions or classes added or edited by the agent’s test units.
Before running mutants on an instance, a zero-mutation control run recorded baseline passing and failing test
IDs for each arm; a mutant is killed by an arm only if it causes a test that passed on the unmutated control to
fail or error, and mutants that fail collection or time out at import are excluded as stillborn.

Agent-Test Oracle and Removal Bounds
G.1
Repeatably Passing Agent-Test Oracle (Oagent) and Non-Passing Cases
Definition of repeatably passing (Oagent(ST) = 1).
A resolved patch ST has a repeatably passing agent-test
oracle (Oagent(ST) = 1) if the standalone test command extracted from the agent’s trajectory still exists in ST
and passes twice consecutively with a non-zero, identical passing test count when re-executed against the
unpruned final patch ST before reverting any units. Because post-generation cleanup tests each candidate
revert by checking whether Oagent(S ⊖u) = 1 (requiring the passing test count to match baseline), verifying
Oagent(ST) = 1 on the unpruned patch is a prerequisite: if Oagent(ST) = 0, every candidate revert would fail
the oracle check and no unit could be pruned.

deterministic no-ops from patch structure alone, without consulting O+ or Otest. Table 20 breaks down all
6,724 resolved patches (3,781 single-code-unit and 2,943 multi-code-unit) through trajectory test extraction

I
Extended Related Work
Measuring over-editing.
Recent work measures how much of an agent’s patch is unneeded by comparing
it with a reference patch, using edit distance or patch-level diffs (Zhu et al., 2026; Luo et al., 2026). These
measures treat every difference from the reference as unneeded. Our measure grades each unit with an
oracle, so a different but valid edit is not counted against the agent.
Training for minimal edits.
Synthetic task generation (Yang et al., 2025) and reinforcement learning with
verifiable rewards (Shao et al., 2024) could be shaped to reward smaller patches. Our results suggest what to
target: unneeded code is mostly part of the fix, not debugging scaffolding.
Agent harnesses and trajectories.
Open harnesses and their published trajectories (SWE-agent Team, 2025;
Wang et al., 2025; SWE-bench Team, 2026) let us compare patches across agents. We replay trajectories to
attribute each line to the step that wrote it, which final-patch comparisons cannot do.
Delta debugging and repair minimality.
Delta debugging reduces a failing input to a minimal one (Zeller
and Hildebrandt, 2002), and repair work favors small changes that keep the program correct (Mechtaev et al.,
2015), though test-passing repairs can still overfit (Smith et al., 2015). Our oracle-guided unit removal follows
the same idea for agent patches.
Tests and mutation testing.
Property-based testing (MacIver et al., 2019), LLM-written differential tests (Hu
et al., 2026), and mutation testing (Jia and Harman, 2011; Just et al., 2014; Hovmöller, 2026) measure whether
tests detect changes in behavior. We use them to strengthen the oracle and to ask whether the agent’s own
tests guard its code.
