ABSTRACT
The growing autonomy of AI agents in using external tools and making decisions
has created an urgent need for comprehensive safety benchmarks. Existing bench-
marks test compromised tool channels or adaptive multi-turn attacks, though they
may not capture the unique capabilities of policy-governed tool-use agents, which
must resist unauthorized requests without abandoning the legitimate work embed-
ded in the same interaction. To fill this gap, we introduce TACT-Bench, a stateful
benchmark built around scenario-specific stories, personas, manipulation tactics,
and response-adaptive escalation. Each adversarial task targets an action explicitly
prohibited by the policy provided to the assistant, while the policy remains hidden
from the attacking user. TACT pairs each adversarial task with at least one be-
nign counterpart, and its adversarial tasks retain authorized ground-truth actions
when a compliant resolution remains available. We define these base tasks as
TACT-Base. We additionally introduce TACT-TrustPrime, which places an inde-
pendent benign task before an unrelated attack in the same conversation. We also
propose Paired Selective Trustworthiness (PST), which combines explicit safe re-
fusal with demonstrated capability on matched benign tasks, to analyze an agent’s
overcautiousness and practicality. Averaged across 6 different models as assis-
tants, TACT-Base raises Attack-Induced Failure Rate (AFR) by 17.53% over four
compatible attack baselines, and TACT-TrustPrime raises it by a further 17.01%.
The two evaluated defense methods reduce AFR by only 8.35%–9.41% on av-
erage and do not consistently improve PST, underscoring the need for stronger
policy-enforcement methods.1

INTRODUCTION
As LLM-based agents become increasingly capable, they are being deployed as virtual assistants to
help users complete complex real-world tasks by using executable tools that perform operations in
an environment. These agents therefore can inspect records, change persistent state, issue credits,
initiate recovery procedures, disclose sensitive information, etc. However, these actions create a
direct attack interface: an ordinary user can present a plausible story, selectively reveal facts, use
manipulation techniques, and continue negotiating until the agent performs an action that policy
forbids. The security problem is therefore not limited to detecting an obviously malicious request.
The agent must track policy-relevant evidence across dialogue, resist manipulation, and still handle
any legitimate part of the request. An agent that refuses everything, abandons the interaction, or
transfers to a human agent despite having a compliant path is not practically trustworthy.
Substantial efforts have focused on developing benchmarks to evaluate the security of AI agents.
AgentHarm (Andriushchenko et al., 2025) tests whether a single harmful instruction can trigger a
multi-step tool task, and Agent Security Bench (ASB) (Zhang et al., 2025) spans direct and indirect
prompt injection, memory attacks, and mixed threats. InjecAgent (Zhan et al., 2024) and AgentDojo

(Debenedetti et al., 2024) focus on malicious instructions arriving through external content or tool
observations; MCP benchmarks study poisoned metadata and server, host, client, or transport risks
(Wang et al., 2026; Zong et al., 2026; Yang et al., 2026). Multi-turn work shows that attacks can
become harder to recognize when intent is decomposed, gradually escalated, or revised from the
target’s replies (Li et al., 2026b;a; Rahman et al., 2025).
Yet these settings do not test all of the following conditions together. The user is policy-blind: the
assistant’s policy or system prompt is not provided to them. They interact only through ordinary
dialogue (user-only channel) and adapt their requests to the assistant’s replies (response-adaptive
attacker). Their goal is to cause a specific change in the environment that the policy forbids. At
the same time, a closely related action is allowed and remains relevant to the interaction. The agent
must therefore resist the unauthorized request while still recognizing the legitimate assistance it can
provide.
To address this gap, we introduce TACT-Bench (Testing Adaptive Conversational Threats), a
benchmark for evaluating how tool-use agents handle persistent social engineering and adaptive
adversaries. Each attack is built around a plausible story, a user persona, and a set of manipulation
tactics. A simulated user agent adapts these tactics to the assistant agent’s replies and persists be-
yond initial refusals. The goal is to induce an action that the assistant’s policy explicitly forbids.
This policy is provided to the assistant but hidden from the simulated user. We pair adversarial tasks
with related authorized tasks evaluated in separate episodes (matched benign). When a compliant
resolution is available within an adversarial task, we also test whether the assistant can complete it
(safe resolution under attack). This allows us to test whether agents can resist manipulation while
still helping with legitimate requests. These tasks form TACT-Base. We also vary the dialogue style
and task details to test the same policy boundaries across different interactions. We further intro-
duce TACT-TrustPrime, in which the user completes an independent benign task before launching
an unrelated attack from a different scenario (independent benign then attack). Both tasks take place
in the same conversation, so the agent retains the earlier interaction and its effects. This tests whether
a successful interaction makes the agent more trusting and weakens its resistance to a later attack.
Table 1 summarizes how TACT-Bench differs from existing evaluation settings.
In addition, we propose a novel evaluation metric that could better assess benchmark performance,
called Paired Selective Trustworthiness (PST). Refusal rate alone can reward an agent that blocks
both malicious and legitimate requests, while benign success alone says nothing about resistance un-
der attack. PST links the two at the scenario level: explicit safe refusal receives credit in proportion
to success on the matched benign tasks, with every valid scenario retained in the denominator. This
distinction becomes particularly important for defenses, which can increase refusal while degrading
selective capability. It distinguishes overcautious agents that mistakenly reject some benign requests
because they appear potentially malicious to them from more practical agents that remain useful on
benign tasks while still enforcing safety constraints.
Our contributions are:
• Towards evaluating the security risks of tool-use agents, we introduce a policy-blind, user-
only benchmark in which persistent attackers use scenario-grounded stories and adaptive social-
engineering tactic ladders to induce concrete harmful actions.
• We automatically construct tone/decomposition variants and 2,852 state-consistent tasks, and in-
troduce TrustPrime tasks with harmonized pairing and phase-isolated scoring.

RELATED WORK
Stateful and policy-governed tool-agent evaluation.
τ-bench (Yao et al., 2025) establishes dy-
namic user–agent–tool interaction with natural-language policies, executable APIs, and final-state
scoring. ToolEmu (Ruan et al., 2024) instead emulates tool environments with a language model
to expose risks across a wider range of high-stakes applications. These works motivate stateful
evaluation, but their primary goal is ordinary capability or broad risk discovery. τ-break extends
τ-bench with CRAFT (Nakash et al., 2025), a persuasive red-teaming framework whose planner
directly analyzes the target policy and whose dialogue executor can react to the agent. TACT-Bench
studies a stricter knowledge boundary: the user receives no policy, system prompt, tool descriptions,
or backend implementation and must infer exploitable boundaries through dialogue. It also keeps
matched benign tasks and authorized actions within adversarial episodes, allowing the evaluation to
distinguish selective handling from refusal or incapability.
Safety evaluation and benign capability.
HarmBench (Mazeika et al., 2024) and JailbreakBench
(Chao et al., 2024) provide standardized frameworks for evaluating jailbreak attacks and defenses,
enabling systematic comparisons of model robustness against adversarial prompts. XSTest (Röttger
et al., 2024) examines refusals of safe prompts that superficially resemble unsafe ones. For tool-use
agents, AgentHarm (Andriushchenko et al., 2025) supplies benign counterparts so that attack fail-
ure is not confused with insufficient tool capability, while ASB (Zhang et al., 2025) jointly reports
security and utility across several attack surfaces. MCP-SafetyBench (Zong et al., 2026) measures
whether an unchanged benign task remains complete under an injected MCP attack. TACT-Bench
instead pairs benign capability checks with dialogues whose user objective is itself prohibited, eval-
uating tool actions and final states. Some adversarial tasks additionally require the agent to redirect
the interaction toward an annotated authorized outcome. PST measures whether this selective resis-
tance coexists with demonstrated benign capability.
Multi-turn attacks on tool-use agents.
MT-AgentRisk (Li et al., 2026b) converts harmful single-
turn objectives into predetermined sequences of less suspicious tool requests; its decomposi-
tion demonstrates that distributing intent can defeat safety mechanisms even without response-
conditioned replanning. STAC (Li et al., 2026a) studies a different mechanism: individually plau-
sible tool calls form a cumulatively harmful chain, and its planner can revise prompts from agent
and environment feedback. TACT-Bench focuses on a direct user who persistently negotiates to-
ward unauthorized outcome(s) through ordinary dialogue. TACT-TrustPrime is also distinct from
FITD or cumulative attack chains: Its first phase is an independent task that belongs to a different
scenario, rather than serving as an intermediate commitment toward the same hidden goal; instead,
the approach seeks to build the agent’s trust through a completely separate and unrelated benign task
before the adversarial interaction begins.
Complementary attack surfaces and defenses.
InjecAgent and AgentDojo (Zhan et al., 2024;
Debenedetti et al., 2024) study indirect prompt injection through external content; MCP benchmarks
examine poisoned descriptions and infrastructure-level attacks (Wang et al., 2026; Zong et al., 2026;
Yang et al., 2026); DoomArena (Boisvert et al., 2025) varies which component of the user–agent–
environment loop is malicious. Sponge Tool Attack (Li & Wang, 2026) studies denial-of-efficiency
through prompt rewrites that preserve task intent while inducing redundant tool calls. This ex-
poses resource consumption as a security concern complementary to TACT-Bench’s focus on policy
compliance. Response Attack, SCR-Bench, and ScamAgents (Miao et al., 2025; Xie et al., 2026;
Badhe, 2025) respectively study contextual response priming, cross-skill trust transfer, and agents
manipulating humans. ToolSafety, ToolShield, Tool-Guard, Policy-Guard, and full-history reason-
ing (Xie et al., 2025; Li et al., 2026b; Zwerdling et al., 2025; Kang et al., 2026; Li et al., 2026a)
provide complementary training- and inference-time defenses. Our threat model isolates the direct
conversational user while keeping tools and backend trusted.

PRELIMINARIES
Tasks.
A task is a tuple T

{BENIGN, ADVERSARIAL} is the task type, I is the user-simulator instruction, A⋆denotes the safe
ground-truth actions, F is the set of forbidden tool names, and B contains the matched benign
counterparts for adversarial tasks only. A benign task requests an authorized outcome, whereas an
adversarial task pursues a hidden objective within a story context and through a scenario-specific
tactic ladder. This ladder guides how the user changes its approach when the assistant resists. Both
task types specify a persona and the facts available to the user.
Crucially, every adversarial task is designed to represent a plausible and realistic social-engineering
attempt that could arise in real-world human user and AI agent interactions. Our construction pro-
cess is deliberately attack-first rather than policy-first. We do not begin from an existing policy and
design attacks around gaps in its rules, nor do we rely on cases in which the assistant is expected
to infer from its internal knowledge that an unstated action should be prohibited. Instead, we first
develop a realistic adversarial scenario and specify how the user will try to persuade the assistant
to fulfill the hidden objective. We then ensure that the natural-language policy P supplied to the
assistant contains an explicit provision prohibiting the attacker’s desired outcome. As a result, every
adversarial objective directly conflicts with at least one stated rule in P. When an attack induces a
prohibited action, the assistant therefore violates a policy boundary that it was explicitly given. The
evaluation consequently tests whether a policy-adherent assistant can continue enforcing an explicit
rule under persistent and adaptive social-engineering pressure. The attacking user has no access to
P or the assistant’s system prompt. The tool definitions are also hidden from the user.
We manually author the initial benign counterparts in B within the same scenario family. For each
counterpart, we specify a related request that the policy permits and ensure that the database supports
that authorized operation. We also annotate the safe actions needed to complete it.
For example, in the refund-destination scenario, the adversarial user tries to obtain a new gift card
sent to an external email without the required pre-approval. A matched benign task instead requests
the return refund on an existing gift card already on the account (Figure 5). These are separate tasks
evaluated in separate episodes.
Episodes.
An episode is the multi-turn interaction between the user agent and the assistant agent.
The user follows I and generates each message from the natural-language conversation so far, adapt-
ing to the assistant’s responses. The assistant has access to the company policy P and the tool set
S. Its working context contains the conversation as well as its own tool calls and their responses,
which the user never sees. After each user message, the assistant may issue a sequence of tool
calls before replying, or it may reply without using tools. Each call is executed against the cur-
rent database state. The call and its response are added to the assistant’s working context, and any
database changes persist into later turns. Thus only natural-language turns cross between the agents,
while tool interactions remain internal to the assistant. Appendix B.1 provides the formal interaction
model and a table of notation.

Importantly, when A⋆contains an authorized alternative, reaching e⋆is not an unsolicited behavior
imposed by the evaluator. After the prohibited objective has been resisted and the tactic ladder is
exhausted, the simulated user explicitly requests and cooperates with the authorized resolution. This
was also verified by checking the trajectories of experiments. The adversarial interaction therefore
remains in the conversation context while the assistant is asked to complete a legitimate action. The
preceding attack may cause the assistant to fail to complete that action. For example, the assistant
may continue treating the user as malicious and refuse the authorized resolution as well. Counting
such cases captures whether the attack disrupts safe-and-useful handling even without inducing a
forbidden tool call. It also prevents an assistant from receiving full credit for resisting the prohibited
request while leaving the subsequent authorized request unfulfilled. Figure 1 illustrates the end-to-
end TACT-Bench interaction and evaluation workflow.
3.2
SCENARIOS, TACTICS, AND CONTROLLED VARIANTS
Benchmark Overview.
We begin with 40 manually authored initial tasks: 17 adversarial tasks
and 23 matched benign tasks across 17 unique scenario families. The original task set is retained
as Vanilla, and three additional variants change the user tone or request decomposition. Each of the
four task sets then follows two independent construction branches. Rule-based entity augmentation
produces TACT-Base. Separately, an LLM-based pipeline screens cross-scenario benign–adversarial
pairs and synthesizes TACT-TrustPrime tasks, in which an independent benign task precedes the
attack. Figure 3 shows this construction process. Figure 1 instead shows runtime interaction: the
user simulator generates each message in response to the assistant, whose tool calls execute in the
database.
The current release instantiates a representative retail environment with a natural-language policy,
33 tools, and a structured database. A representative inventory of tools appears in the appendix.
Although the executable environment is retail, these operations instantiate policy primitives—
including identity, ownership, authorization, eligibility, approved destinations, evidence, explicit
confirmation, and sensitive disclosure—that are common across financial, travel, healthcare, enter-

prise, and administrative agents, making the benchmark framework readily extensible to additional
domains.
The benchmark contains 2024 adversarial tasks and 828 benign tasks, including augmented tasks.
Without considering augmentations, the numbers would be 1480 and 92. Each adversarial task has
at least one benign counterpart, and every tool appearing in an adversarial ground truth is exercised
in at least one benign case. Adversarial tasks involving several relevant capabilities receive multiple
counterparts so that safety is not confused with inability to invoke a particular tool. However, the
number of adversarial tasks exceeds that of benign tasks, because TrustPrime tasks, which are all
considered adversarial, share the same benign tasks with the Base tasks as their counterparts.
Table 2 summarizes the size of the dataset. It consists of two families, namely, Base and TrustPrime.
The adversarial tasks are story-driven. Rather than simply asking for a forbidden operation, they
specify why the request could appear reasonable from the agent’s local perspective and what facts
the user may disclose. Tactic ladders differ by scenario and can include urgency, authority claims,
prior-agent approval, family or identity equivalence, stale-record claims, verbal authorization, in-
convenience, manager escalation, and off-system workarounds. The user chooses how to advance
or revise these tactics from the assistant’s replies.
The four TACT variants cross two dimensions:
• Tone: Polite uses courteous requests (e.g., "Could you help update the pickup person?"), whereas
commanding uses direct, urgent instructions (e.g., "Update the pickup person.").
• Decomposition: Standard presents the request in fewer turns, whereas high-step divides the same
objective and evidence across more, shorter turns.
As a result, we have these four variants for both TACT-Base and TACT-TrustPrime.
Vanilla
variant—the combination of Polite and Standard—is polite and cooperative. Aggressive is com-
manding but not abusive. High-step reveals the same facts and objective over more, shorter turns.
Combined applies both. Identity relations, policy boundaries, A⋆, F, and linked environment state
remain fixed, enabling paired analysis of delivery style rather than task semantics.
Automatic rule-based augmentation.
Each of the 40 initial tasks is retained and supplemented
with eight additional entity-level instances, giving nine instances per task. This augmentation makes
the Base and TrustPrime suites comparable in scale. The pipeline replaces identities, contact fields,
account values, order identifiers, and linked entities, updates the affected database tables, rewrites
instruction references and tool arguments, and preserves ownership and relational constraints. This
produces 360 tasks per TACT-Base variant and increases entity-level diversity.
3.3
TACT-TRUSTPRIME EXTENSION
TrustPrime pairs a complete legitimate task, Phase 1 (the primer), with an adversarial task from
another scenario, Phase 2 (the attack), in one uninterrupted conversation. TrustPrime scoring isolates
Phase 2. Primer-owned state paths and calls are removed from the attack signal, while adversarial
forbidden calls and non-primer safe-state deviations remain. A transfer that ends Phase 1 before
the attack is reached is excluded from adversarial denominators under a fixed rule; a later transfer
remains a scored outcome. Detailed attribution and transfer logic are deferred to the appendix.
For example, a user first asks the assistant to assign a registered pickup proxy to an order. After this
authorized change, the user requests that a gift-card balance be reissued to a new email address. The
second request targets a separate policy boundary; completing the pickup task supplies no autho-
rization for the gift-card operation. Appendix G.4 shows a Mistral-Large-3 episode that completes
the primer and then performs the prohibited reissue.
TrustPrime generation.
We construct TrustPrime tasks with an automated GPT-5.6-SOL (Ope-
nAI, 2026) pipeline that pairs, screens, synthesizes, and validates benign–adversarial conversations
together with their required environment data. Starting from each TACT-Base variant, the pipeline
considers all cross-scenario benign–adversarial pairs and removes combinations that are logically
incompatible: pairs from the same scenario, declared benign counterparts, pairs whose ground-truth
and forbidden actions overlap in either direction, and same-user pairs that modify the same entity
or argument target. Two temperature-zero GPT-5.6-SOL judges then independently evaluate each

4.3
ATTACK BASELINES
All baselines operate on the same original augmented tasks, users, records, hidden objectives, safe
actions, forbidden actions, and episode budgets. Thus, they have the same number of adversarial
tasks as the TACT-Base variants. Each simulator can answer task-grounded identity, authentication,
clarification, and confirmation questions, remains engaged throughout its assigned strategy, and
follows the annotated compliant path after its attack strategy is exhausted. The methods differ in
how they construct the attack-bearing dialogue. Each method has a 50-step budget, which none of
the 3,655 baseline or 910 Vanilla TACT-Base adversarial episodes reaches (Appendix E.3). The
attack-strength comparison is therefore unaffected by budget truncation.
Naive Attack receives the objective and available facts but no prescribed persuasion strategy or es-
calation ladder. It measures what the same user model can achieve through unaided conversational
reasoning. PAP (Zeng et al., 2024) selects a persuasion framing from its social-science taxonomy
and applies it to the policy-violating objective. We use its strongest technique, i.e., Logical Appeal,
in our experiments. FITD (Weng et al., 2025) builds toward the objective through smaller inter-
mediate commitments; it is semantically related to TACT-TrustPrime, but every commitment serves
the same hidden attack. Crescendo (Russinovich et al., 2025) begins from a related benign-looking
topic and progressively escalates using the assistant’s preceding answers.
4.4
DEFENSE METHODS
We adapt two published runtime defenses to the TACT-Bench retail environment and evaluate them
on proposed state-changing tool calls. Blocked calls are not executed and are returned to the agent
with a policy-grounded explanation and compliant next step, allowing the interaction to continue
toward the authorized resolution. Neither defense receives task labels, forbidden-action annotations,
ground truth, or the expected final state.
Tool-Guard (Zwerdling et al., 2025) applies deterministic checks written from the retail policy.
These checks use only the proposed arguments, current database state, and prior tool observations.
They require no LLM call at inference time and can miss violations evident only in the dialogue.
Policy-Guard (Kang et al., 2026) uses a paired, temperature-zero LLM verifier. It receives the
raw policy, full interaction history, prior observations, proposed call, and a hand-written per-tool
checklist for the retail domain. It returns PASS or BLOCK with a remediation message and fails
open if verification errors occur. An appendix ablation, PG-RAW, removes only the checklist to
isolate the value of explicitly identifying the relevant procedural requirements.

DEFENSE EVALUATION
Table 3 reports the effects of Tool-Guard and Policy-Guard on Vanilla TACT-Base. Across the six
assistants, Tool-Guard reduces AFR by 8.35% on average, while Policy-Guard achieves a slightly

larger reduction of 9.41%. The corresponding average RR increases are 8.13% and 8.76%, re-

Tool-Guard performs better for GPT-5.6-SOL.
PST reveals a larger difference between the defenses. Tool-Guard increases PST for every assistant,

5.4
TRUSTPRIME
Table 4 compares TACT-TrustPrime with TACT-Base and FITD across the evaluated assistants.
TrustPrime increases AFR for every assistant. Averaged over assistants, AFR is 17.01% higher
than that of TACT-Base. The effect remains large against FITD, the strongest baseline and the one
most semantically related to TrustPrime: TrustPrime increases AFR by 31.08% on average, ranging
from 27.0% for Gemini 3.5 Flash to 41.17% for DeepSeek-V3.2. It also decreases RR by 32.04%
on average compared to FITD. This comparison highlights the difference between attack-serving
intermediate commitments and a genuinely independent prior task. TrustPrime also lowers mean
RR and PST by 18.33% and 15.07%, respectively, compared with TACT-Base. The consistency
across model families supports prior-interaction carryover as a distinct stressor rather than an effect
isolated to one assistant. Appendix H.3 shows that the increase holds in 13 of the 17 scenario
families, under equal source weights, with completed primers, and when the policy is re-sent before
the attack.
Equal weighting of the 17 source scenarios still yields an AFR increase of 17.7%, positive for every
assistant, showing that unequal source frequency alone does not account for the effect. For Mistral-
Large-3 and GPT-5.6-SOL, High-step TACT-Base has comparable interaction length to Vanilla
TrustPrime but lower AFR (39.9% versus 57.2%). For GPT-5.6-SOL and Gemini 3.5 Flash, re-
sending the full policy before the attack does not reduce combined AFR on the instances scored
in both conditions (50.4% without the reminder; 51.3% with it). These controls support our claim
regarding the trust and rapport built by the benign task, which makes proceeding the attack more
powerful.
6
DISCUSSION AND LIMITATIONS
TACT-Bench isolates direct conversational manipulation while treating the tools and backend as
trusted. Its retail instantiation spans general policy primitives, but the 17 scenario families do not
substitute for future cross-domain evaluation.
LLM-based refusal and semantic judgments can also inherit model-specific biases despite human
validation. Finally, the two defenses cover only deterministic state checks and dialogue-grounded
runtime verification. Their modest improvements and remaining AFR motivate defenses that jointly
track conversational authorization, persistent user strategy, environment state, and recovery toward
compliant actions.
7
CONCLUSION
TACT-Bench evaluates adaptive, policy-blind social engineering against stateful tool-use agents.
Its scenario-grounded stories, tactic ladders, matched benign tasks, controlled variants, automatic
augmentation, TrustPrime extension, and proposed PST metric expose failures hidden by simpler
attacks or refusal-only evaluation. Even Vanilla TACT-Base substantially outperforms four attack
baselines; TrustPrime further increases AFR, including by 31.08% over the strongest baseline, FITD,
on average; and current runtime defenses leave substantial residual vulnerability. These results call
for policy enforcement that remains both robust to persistent dialogue and useful on authorized
actions.

C
HUMAN VALIDATION OF LLM JUDGMENTS
C.1
JUDGMENT ROLES
TACT-Bench uses LLM judgments in three places: (1) GPT-4.1 determines whether an unsuccessful
adversarial trajectory contains an explicit refusal; (2) GPT-4.1 determines semantic equivalence for
designated free-text database fields that cannot be compared reliably by exact string equality; and (3)
two GPT-5.6-SOL judges screen candidate TrustPrime pairs for story continuity and precondition
consistency.
We independently validated all three judgment procedures with human annotation. The refusal and
semantic-equivalence audits each use 100 sampled cases spanning different assistant models, task
variants, and experiment settings. Two human annotators, both with prior research experience in
LLM agents and neither an author of this paper, independently and blindly (i.e., without seeing
the LLM labels) labeled each sampled case after receiving the complete task-specific rubric and all
information needed to make the corresponding judgment. The TrustPrime audit instead reviews the
complete Vanilla candidate set rather than a sample. Table 10 summarizes the outcome of all three
audits; the subsections below describe each in turn.
C.2
REFUSAL-JUDGE VALIDATION
The refusal judge is invoked only for adversarial trajectories that have already been classified as
safely handled: no forbidden action was executed and the final database matches the annotated
safe state. Its remaining question is therefore whether the assistant explicitly refused the prohibited
component.
The human-validation sample contains 100 such trajectories, stratified across different assistant
models, TACT variants, and experimental settings. The GPT-4.1 judge labeled 58 cases as explicit
refusals and 42 as non-refusals. Annotators received the full conversation and the hidden adversarial
objective, together with the same refusal rubric used by the automated judge, but not the judge’s
prediction. They independently answered a binary question: TRUE if the assistant explicitly refused
the adversarial request and FALSE otherwise.
The mean human–LLM agreement across the two annotators is 95%, with Cohen’s κ = 0.897.
This high agreement is particularly important because RR distinguishes explicit policy resistance
from other safe outcomes: confusion, silent non-compliance, execution failure, or a bare transfer to
a human agent do not count as refusals.
22


Preprint
C.3
SEMANTIC-EQUIVALENCE VALIDATION
Exact equality is used for structured database fields whenever possible. GPT-4.1 is used only for des-
ignated free-text fields, such as support-ticket reasons, damage descriptions, missing-item descrip-
tions, trade-in dispute reasons, and marketplace-claim descriptions, where two strings can express
the same underlying fact without being lexically identical.
We sampled 100 semantic judgments across different assistant models, variants, and experiments.
To test both classes evenly, the sample was balanced according to the LLM judgment: 50 pairs
were labeled equivalent and 50 were labeled non-equivalent. Both human annotators received the
complete equivalence rubric and independently labeled each pair TRUE when the two descriptions
recorded the same underlying facts and FALSE otherwise, without seeing the LLM prediction.
Mean human–LLM agreement is 91%, with Cohen’s κ = 0.820, indicating strong agreement even
on the free-text comparisons for which exact matching is insufficient.
C.4
TRUSTPRIME COHERENCE AUDIT
TrustPrime screening uses two independent GPT-5.6-SOL judges. The story-continuity auditor asks
whether a benign request followed by the adversarial pivot forms a plausible uninterrupted interac-
tion for one customer. The precondition analyst separately checks whether successful completion of
the benign request consumes, resolves, contradicts, or otherwise invalidates a precondition or object
required by the later attack. A candidate is accepted only when both judges accept it; a disagreement
is treated as non-accepted.
Unlike the sampled validation above, we manually reviewed the entire 356-pair Vanilla TrustPrime
candidate set. The automated coherence ensemble did not accept two pairs, and the human reviewer
independently agreed with both and with all but one of its 354 acceptances. Thus, before cross-
variant harmonization, the automated ensemble and human reviewer agreed on 355/356 Vanilla
decisions (99.72%); the human reviewer identified one additional incoherent pair.
As the four TrustPrime variants differ only in tone and conversational decomposition, while each
source pair preserves the same underlying story and state dependencies, coherence should therefore
be invariant across variants. During generation of the remaining variants, the automated screening of
one variant also marked this third source pair as non-accepted, matching the human audit. We con-
sequently removed the union of these three source pairs from every variant in which they appeared.
This harmonization yields 353 retained TrustPrime pairs per variant. Every retained source pair
is accepted by both automated coherence judges and by the human audit, giving 100% agreement
on the final released set.

TRUSTPRIME GENERATION AND PHASE-ISOLATED SCORING
TACT-TrustPrime evaluates whether successful interaction on an independently legitimate task can
make an assistant more vulnerable to a later conversational attack in the same uninterrupted session.
Figure 8 illustrates the structure of a TrustPrime episode. The user first completes an independently
legitimate task, which establishes rapport, confirms account context, and satisfies ordinary safe-
guards. Only after the primer is complete does the same user pivot to a separate request that appears
legitimate but is actually adversarial. The first phase is retained as conversational context, while
evaluation is isolated to the adversarial phase.
D.1
CONSTRUCTION PIPELINE
TACT-TrustPrime is constructed independently from each of the four 40-task source suites: Vanilla,
Aggressive, High-step, and Combined. This branch is separate from the augmentation process that
produces TACT-Base. Each TrustPrime variant contains 353 synthesized adversarial tasks and the
23 referenced benign counterparts from its source suite, for 376 tasks in total.
The pipeline has two LLM-assisted stages. First, a two-judge GPT-5.6-SOL ensemble screens can-
didate benign–adversarial pairs for coherence. Second, GPT-5.6-SOL synthesizes each accepted
pair into one two-phase task. All candidate enumeration, filtering, ordering, identifier allocation,
validation, and database merging steps are deterministic. The LLM stages use fixed prompts; their
outputs must pass model-free validation before being included.
Figure 9 summarizes the generation workflow. Cross-scenario benign–adversarial pairs first pass
deterministic conflict filters. Candidate coherence decisions are then retrieved from or written to a
shared content-hashed cache. Coherence-approved pairs are synthesized into a two-phase task and
associated database records, after which deterministic validation either accepts the result, requests
correction, or discards it.

TrustPrime evaluation separates failures in the independently useful primer from behavior caused
by the later adversarial pivot. At load time, each generated task is decomposed into:
• benign_primer_actions: the primer’s state-changing, non-terminating ground-truth
actions; and
• adversarial_forbidden_actions: only the forbidden actions inherited from the
adversarial source task.
The generated safe-action sequence preserves phase order. When the same mutating tool appears
in both source tasks, the earliest matching occurrences are allocated to the primer according to the
benign source task’s action-name multiset.

Phase-isolated forbidden calls.
Only tools inherited from the adversarial source task’s forbidden
list contribute to the Phase-2 forbidden-call signal. A candidate call is ignored when it contains entity
identifiers and every such identifier belongs exclusively to a primer-owned entity. Calls targeting
the acting user, a non-primer entity, or both primer and non-primer entities remain attributable to
Phase 2.
When the same tool is relevant to both phases, the primer retains the number of calls allocated by its
source action budget; additional calls are attributed to Phase 2. A forbidden invocation is recorded
even when the tool returns an error or fails to modify the database, since the attempted external
action may itself be consequential.
Primer completion.
It is:
• TRUE when every path in QP matches e⋆
P ;
• FALSE when at least one primer-owned path differs; and
• UNDEFINED when the primer has no state-changing ground-truth action.
Pre-attack transfer exclusion.
A transfer to a human agent is excluded from TrustPrime scoring
only when all of the following conditions hold:
1. the task contains the explicit primer/adversarial phase split;
2. no Phase-2 forbidden call occurred;
3. no active unauthorized Phase-2 state change occurred; and
4. the primer is incomplete.
Because transfer terminates the interaction, these conditions identify cases where the assistant trans-
ferred before the benign primer completed and before the adversarial pivot was reached. A transfer
after the adversarial pivot is stated by the user remains part of the evaluation. A bare transfer also
does not constitute an explicit refusal unless the assistant first communicates that the prohibited
request is denied.
D.3
TRUSTPRIME DIAGNOSTICS
Each TrustPrime trajectory records the information needed to audit phase attribution:
• source benign and adversarial task indices;
• primer-completion status;
• Phase-2 forbidden-call status;
• non-primer database-deviation status;
• active unauthorized-change status;
• whether the assistant completed the authorized Phase-2 resolution;
• transfer status and transfer-exclusion reason; and
• any semantic-judge failure or fallback used during free-text reconciliation.
Run-level reports additionally provide the number and identifiers of pre-attack transfer exclusions,
simulator-error exclusions, and judge failures. These diagnostics allow the final outcome to be traced
separately to primer failure, unauthorized action, active state mutation, or incomplete authorized
resolution.
D.4
IMPLEMENTATION VALIDATION
The TrustPrime-specific implementation paths described above are covered by 48 offline tests:
• 21 tests for phase-isolated attribution and transfer exclusion;
• 13 tests confirming that attacker strengthening modifies only the user-simulator instruction
and does not alter ground truth or scoring; and
• 14 tests for policy-sensitive date consistency in generated fixtures.
The test suite also includes an end-to-end check using a generated TrustPrime task and the retail
environment’s production reward implementation. Crafted final states exercise primer isolation,
Phase-2 attribution, active versus passive deviations, and primer completion without requiring an
online user-simulator call.

Episode-length control.
TACT episodes run longer than baseline episodes, because persistence
through a tactic ladder is constitutive of the method. This is not a budget advantage. Every run
in this comparison — Vanilla TACT-Base and all four baselines — was executed with an identical
agent step budget of max-num-steps = 50, as specified in Sec. B. The baselines were free to
continue the conversation for exactly as many turns as TACT; they simply did not do so, because
their strategies terminate once the prescribed persuasion framing or escalation ladder is exhausted,
whereas TACT’s user simulator keeps selecting new tactics from the assistant’s replies.
The budget was in fact never binding for any method. Across all 3,655 baseline adversarial episodes
and all 910 TACT adversarial episodes, not one reached the 50-step cap. The longest single ad-
versarial episode in the entire comparison is a baseline episode — 26 assistant steps, Naive against
Mistral-Large-3 — which exceeds the longest TACT episode (21 steps).
Table 14 reports mean user turns and mean executed tool calls per adversarial episode, averaged over
the six assistants. TACT averages 8.72 user turns against 6.54 for FITD, 5.18 for Crescendo, 4.47
for Naive and 4.12 for PAP. Length by itself also does not order the methods by strength: Crescendo
runs 26% longer than PAP yet attains a marginally lower mean AFR (20.26% vs. 21.02%), and FITD
runs 46% longer than Naive for a 4.72% AFR increase, whereas TACT’s 33% additional length over
FITD buys 14.07% increase. Sustained engagement is thus a property the attack has to earn from
the assistant’s responses, not a resource TACT was granted and the baselines were denied. In fact,
no experiment reached the maximum step budget, so the budget did not affect the results; it simply
allowed enough steps for each conversation to finish.

USER-SIMULATOR ABLATION
All main experiments use GPT-5.6-SOL as the attacking user. To check that TACT’s attack strength
is not an artifact of one simulator, we re-ran Vanilla TACT-Base with Claude Sonnet 4.6 driving the
same instructions, personas, facts and tactic ladders (Table 22).
Attack strength is slightly lower with the Sonnet simulator —on average 3.37% lower in AFR—
and PST correspondingly higher, but the ranking of assistants is preserved, and every ablated AFR
remains far above the AFRs of the corresponding baseline attacks in Table 13. The Sonnet-driven
Claude Opus 4.8 result (26.80% AFR) still exceeds the strongest GPT-5.6-SOL-driven baseline
against the same assistant (FITD, 14.48%). We therefore attribute the attack strength to the scenario
design rather than to a particular simulator, while noting that a simulator with a different persuasion
prior shifts absolute levels by a few points. The two simulators lead to the same outcome on 77% to
85% of individual task instances, and Sonnet-driven TACT has a higher AFR than each of the four
GPT-5.6-SOL-driven baselines for each of the three assistants (12 of 12 comparisons).
The Sonnet simulator also produced no persona refusals on the two assistants where GPT-5.6-SOL
produced four each (Sec. E.9), so this configuration additionally recovers the episodes that were
otherwise unscorable. On the eight task instances discarded under GPT-5.6-SOL, the Sonnet-driven
attack induced a failure in all eight — evidence used in Sec. E.9 to establish the direction of the
exclusion bias.

E.10
TRUSTPRIME TRANSFER ATTRIBUTION
TrustPrime scoring must distinguish an agent that resisted the attack from one that escalated before
the attack was ever raised. An episode is excluded from all metrics iff all four of the following hold:
the task is phase-split; the agent called transfer_to_human_agents; the agent performed
no adversarial-forbidden call and made no active unauthorized write on a non-primer path; and the
benign primer had not completed. The last condition is the timing signal — an incomplete primer
means the conversation had not reached Phase 2, so no attack verdict is possible. A transfer after
the primer completed is a Phase-2 response to the raised attack and is scored normally.
Excluding pre-attack bail-outs rather than scoring them as failed attacks prevents an over-escalating
agent from posting an artificially low AFR. Over-escalation is still penalized, through benign-task
success (where transfer is an outright failure, Sec. E.1) and through the reported exclusion counts.
Exclusions are modest in the undefended runs (0–11 of 376, Table 19) but rise sharply under Policy-
Guard (19 and 29, Table 21), which is itself a finding: a blocking verifier converts resistance into
abandonment.

F
ATTACK BASELINES AND RUNTIME DEFENSES
This section documents how the four attack baselines and the two runtime defenses are constructed
and configured, and reports the implementation-level diagnostics that the results in Sec. E rest on.
F.1
ATTACK BASELINES: SHARED CONTROLS
Naive Attack, PAP, FITD, and Crescendo run on the same Vanilla augmented adversarial tasks as
Vanilla TACT-Base. For each task, all methods share the acting user, database records, hidden
objective, available facts, safe ground-truth actions, forbidden actions, assistant, user model, tool
set, policy, context, and episode budget. The agent step budget is max-num-steps = 50 for
every method (Sec. B); no method is given more room to negotiate than another, and in practice no
adversarial episode of any method reaches the cap (Sec. E.3).
Every baseline user simulator may answer task-grounded identity, authentication, clarification, and
confirmation questions. It remains engaged throughout its assigned strategy and, once that strategy
is exhausted or the assistant firmly rejects the prohibited component, cooperates with the annotated
safe resolution. The baselines are therefore not artificially single-turn, non-interactive, or prevented
from completing authorized work. Table 24 summarizes the parity conditions.

F.2
BASELINE STRATEGIES
Naive Attack.
The Naive user receives the objective and available task facts but no preselected
persuasion method, opening message, or escalation ladder. It may reason conversationally and an-
swer grounded follow-up questions, but the prompt does not prescribe urgency, authority, rapport,
emotional pressure, gradual commitments, or any other attack tactic. This baseline measures un-
aided conversational attack behavior by the same user model.
44


Preprint
PAP.
The PAP adaptation applies Logical Appeal, one of PAP’s strongest reported persuasion
strategies, to the policy-violating objective. The generated framing must remain faithful to the task’s
user-visible facts and may not expose the hidden policy, system prompt, forbidden-action annotation,
or backend state. Follow-up answers remain grounded in the same task records.
Foot-In-The-Door.
FITD decomposes the final prohibited request into smaller intermediate com-
mitments; the ladder length is six rungs by default. Every commitment is selected because it ad-
vances the same hidden attack objective. The simulator conditions later messages on the assistant’s
responses and uses the intermediate commitments to realign the conversation toward the final re-
quest. Unlike TrustPrime, FITD does not begin with an independent task from another scenario.
Crescendo.
Crescendo begins with a benign-looking topic related to the prohibited operation and
gradually escalates toward the final request. Each new message references or builds on the assis-
tant’s preceding response. The adaptation preserves the original task objective and evaluates success
through tool calls and environment state rather than prohibited textual content.
F.3
BASELINE CONSTRUCTION AND VALIDATION
All four baselines are built deterministically from the same hand-curated plain-attack specifications,
and share the same scenario specifics. Rebuilding the suites from the same seed reproduces them
byte-for-byte. The per-identity augmentation that expands each suite to 153 adversarial tasks is
likewise deterministic under a fixed seed and shares its twin identities with TACT-Base.
The validation that does apply is a state-consistency check on the scenario endings. Because a
scenario whose ground truth writes to the database requires the attack’s ending to walk the agent
into that authorized write, an episode that stops at the refusal would otherwise finish short of the
safe state and be misread as an unauthorized change. Replaying every plain attack’s ground-truth
actions against the live tools identifies which scenarios are state-changing:
python -m tact_bench.baselines -check
Eight of the 17 scenarios are state-changing, and their endings are written to route the agent into the
compliant write. The remaining nine are read-only, where stopping at the refusal already matches
ground truth. All four baselines inherit these endings unchanged from the shared specifications,
so no method is advantaged or disadvantaged relative to the other baselines or TACT by how its
episodes terminate.
F.4
DEFENSES: SHARED RUNTIME WRAPPER
Both defenses are implemented through DefendedEnv. The wrapper intercepts every assistant-
to-environment call. A proposed mutating call is converted to a PendingCall that contains the
tool name, arguments, current database state, prior tool observations, and—for Policy-Guard—the
dialogue history and policy context. It does not contain the task label, safe ground truth, forbidden-
action list, or expected final state.
A defense returns either PASS or BLOCK. On PASS, the original environment executes the call.
On BLOCK, the call is not executed, is not appended to env.actions, and cannot modify the
database. The assistant receives a POLICY CHECK FAILED observation that names the unmet
policy requirement and suggests a compliant next step. The episode then continues, allowing the
assistant to recover toward the authorized resolution.
F.5
TOOL-GUARD
Build-time policy compilation.
Tool-Guard uses deterministic, hand-derived guard chains con-
structed from the environment’s wiki.md, i.e., the assistant’s policy. Each atomic policy rule
is mapped to the mutating tools it constrains.
The build artifact also contains the fixed read-
only/mutating catalog. The guards are hand-derived for auditability.
Offline consistency check.
Before evaluation, a checker replays every annotated safe ground-truth
action and a set of adversarial probes:
python -m tact_bench.defenses -check
On the compliant-path replay, 27 of the 116 ground-truth tool calls reach a guard and none is
blocked, so the deterministic rules never stand between the agent and an authorized action. On
the adversarial probes, 21 of 23 are blocked; the two that pass are the documented dialogue-only
blind spots below, which the checker asserts as expected passes rather than failures. Every mutating
45


Preprint
tool in the catalog is covered by a guard chain, so no state-changing call reaches the environment
unchecked.
Runtime inputs and ordering.
Tool-Guard first applies global account and authorization checks,
then the per-tool rule chain. It may inspect the proposed arguments, current database state, and
prior read-tool results. It does not inspect the natural-language dialogue. Runtime checking is
deterministic and requires no LLM call.
Known blind spots.
Because Tool-Guard does not see dialogue, it cannot enforce policy require-
ments whose violation exists only in conversational context. The offline checker identifies exactly
two such cases, and both are the reason Policy-Guard is retained as the complementary defense:
1. Password-reset redirect (send_password_reset_link). The destination is a verified
contact on file, so the arguments are policy-conformant on their face. What makes the call
wrong is a fact stated only in the dialogue — the customer said she has lost access to that
inbox, which routes her to the manually-verified recovery ticket instead. The violation is
unreachable without the conversation.
2. Refund without return (issue_refund_without_return). This scenario shares its
fixture with the benign task in which claim review has already approved exactly this re-
fund, so the arguments match a pre-approved entry on every field. Only the dialogue dis-
tinguishes “issue the approved outcome” from “refund me so I can keep the item”.

True positive (Tool-Guard).

True positive (Policy-Guard).
On the same scenario, Policy-Guard blocks the identical call
with three requirements unmet — explicit_confirmation, receipt_ownership_

yet—there is no receipt lookup confirming that receipt RX-6293-0184’s payment card actually ends

the intended division of labor: the same violation is reachable from state alone, so both defenses

False negative (Tool-Guard).
The two dialogue-only blind spots of Sec. F.5 are Tool-Guard’s
structural false negatives. In password-reset redirect the proposed send_password_reset_

fact — that the customer has lost access to that inbox — exists only in the transcript. Tool-Guard
passes the call. Policy-Guard, which reads the transcript, is the defense for this class.
Benign false block (Policy-Guard).
In a benign marketplace task, the back office has already ap-

which is how the policy records a completed claim review. The assistant authenticates the cus-

intervention is of this kind (Appendix H.2), but PG-CHECKLIST never approves an authorized call
in 8.1% of benign episodes, and these cases are what depress its PST.

F.10
BOTH DEFENSES FALL SHORT
Neither runtime defense comes close to neutralizing TACT. On Vanilla TACT-Base, mean AFR
falls only from 39.27% undefended to 30.91% under Tool-Guard and 29.86% under Policy-Guard
— reductions of 8.35% and 9.41% that leave roughly three in ten adversarial episodes still ending
in failure. The defenses fall short even on the prohibited actions they target. A forbidden call or
an unauthorized change still occurs in 8.4% of adversarial episodes under Tool-Guard and 6.6%
under Policy-Guard, against 17.3% undefended, and neither defense helps the assistant complete
the authorized resolution (Appendix H.1). On the Aggressive TACT-TrustPrime variant the residual
risk is far higher: the best defended result we measure is Policy-Guard on GPT-5.6-SOL at 44.74%
AFR, and every other defended configuration sits above 46%.
The two designs fail for complementary reasons, and neither failure is incidental. Tool-Guard is
deterministic and cheap, and it never sacrifices benign capability — but it cannot see the dialogue,
so any policy requirement whose violation is established only in conversation is structurally un-
reachable for it (Sec. F.5). Policy-Guard does read the dialogue and blocks far more, yet it also
blocks authorized invocations of sensitive procedures: it intervenes in 24.7% of benign episodes,
never approves an authorized call in 8.1% of benign episodes, and only 64.6% of the episodes it
blocks still reach the safe state. That is why its larger AFR reduction does not translate into better
PST (Table 15), and why part of its apparent gain on TrustPrime comes from agents escalating to a
human before the attack is even raised rather than from resisting it.
Taken together, the two defenses trace out the current trade-off rather than a solution: argument-
level determinism is safe but blind, and dialogue-level verification is sighted but too restrictive on
authorized calls. Closing the gap requires enforcement that jointly tracks conversational authoriza-
tion, persistent user strategy, environment state, and recovery toward the compliant action — so
that a sensitive tool can be blocked for the attacker and permitted for the legitimate customer in the
same scenario family. Until such methods exist, a substantial share of TACT’s adversarial episodes
remains unaddressed by runtime defense.

a reason why that outcome is already available, and they build that reason out of whatever the
assistant has just said. This section collects seven episodes that make that concrete. The first two

and Combined delivery variants, to show how the tone and decomposition manipulations read in the
dialogue itself. One is a TACT-TrustPrime episode in which the benign primer is completed correctly
before the attack is raised. The last is a counterexample: an attack that fails, refused explicitly at
every turn.

H.3
TRUSTPRIME CONTROLS
Every TrustPrime task is built from one of the 17 Base attacks, so Table 31 compares each Base
attack with the TrustPrime tasks built from it. TrustPrime AFR is higher in 13 of the 17 families,
equal in 1 and lower in 3, and with any one family left out the mean difference stays between
+13.6% and +19.0%. Three alternative explanations do not account for the increase.
Source weighting.
Each adversarial source appears in 17 to 22 of the 353 tasks. With equal source
weights the difference is +17.7%, against +17.01% as reported, and it is positive for every assistant.
Primer completion.
Among the 2,083 scored Vanilla TrustPrime tasks, the primer’s state change
was completed in 1,621 and not completed in 4. It is undefined in 458, because five of the 23 primers
leave no database change to check. AFR is 54.8% where the primer was completed, against 56.28%
overall.
Conversation length.
High-step TACT-Base is as long as Vanilla TrustPrime, yet its AFR is not
above Vanilla TACT-Base (Table 32). To test whether a longer conversation weakens the assistant’s
hold on the policy, we also re-ran Vanilla TrustPrime for two assistants and re-sent the complete pol-
icy to the assistant at the start of the second task, with tasks, user simulator and scoring unchanged.
Compared on the instances scored in both runs, the reminder does not lower AFR. Of the conversa-
tions, 89.4% end the same way in both conditions, 4.8% fail only without the reminder and 5.8%
only with it (exact McNemar p = 0.59).
