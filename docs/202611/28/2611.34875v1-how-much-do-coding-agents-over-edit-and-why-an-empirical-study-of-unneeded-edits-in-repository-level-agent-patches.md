## 摘要
智能体补丁比开发者补丁更大，这通常被解读为过度编辑。但补丁大小并不能说明额外编辑是否必要、它们是什么，以及它们从何而来。我们提出增量残差归因（Delta Residue Attribution, DRA），它回放智能体轨迹，将最终补丁的每个块（单元）追溯到写入它的步骤，回退每个单元，并重新运行任务测试以判断该单元是否必要。我们将 DRA 应用于 SWE-bench Verified（6,728 条）和 DeepSWE（932 条）上来自 18 个前沿模型的 7,660 条已解决的 GitHub Copilot CLI 轨迹，并使用相同方法评估开发者补丁。智能体补丁确实比开发者补丁改动更多行；在 SWE-bench Verified 上，大多数额外编辑是添加测试（61%）和文档（13%），而在 DeepSWE 上，大多数额外编辑是代码（58%）。在两个基准上，智能体的代码平均至少与开发者代码同样必要（SWE-bench Verified 上平均 NP_code 为 0.887 对 0.864，其中 18 个模型中有 11 个留下的非必要代码少于开发者；DeepSWE 上为 0.797 对 0.785）。平均而言，在 SWE-bench Verified 上，智能体补丁的代码单元中有 11% 仍是非必要的，其中 89% 会改变行为。调试步骤几乎不写入任何非必要代码。代码必要性因模型而异，差异显著；它与 SWE-bench Verified 上的解决率无关，而在 DeepSWE 上与其负相关（Spearman -0.59，p = 0.01）。在 SWE-bench Verified 上，仅使用智能体可见的测试（其自身测试和仓库测试）通过 DRA 进行剪枝，可以移除大多数非必要代码，但也会移除一些必要代码（召回率 67%，精确率 46%），且 89% 的剪枝后补丁仍能解决任务；要求智能体审查自己的 diff 更精确但效果较差（召回率 36%，精确率 66%）。我们建议基准测试在解决率之外报告代码必要性，并建议通过模型训练和评测框架级剪枝来解决过度编辑问题。

## Abstract
Agent patches are larger than developers', which is widely read as over-editing. But patch size does not say whether the extra edits are needed, what they are, or where they come from. We introduce Delta Residue Attribution (DRA), which replays agent trajectories, traces every block (unit) of the final patch to the step that wrote it, reverts each unit, and reruns the task tests to decide whether the unit is needed. We apply DRA to 7,660 resolved GitHub Copilot CLI trajectories from 18 frontier models on SWE-bench Verified (6,728) and DeepSWE (932), and grade developer patches using the same method. Agent patches do change more lines than developers'; on SWE-bench Verified the majority of extra edits add tests (61%) and documentation (13%) while on DeepSWE, most extra edits are code (58%). On both benchmarks, agents' code is on average at least as necessary as developers' (mean $NP_{code}$ 0.887 vs. 0.864 on SWE-bench Verified, where 11 of 18 models leave less unneeded code than developers, and 0.797 vs. 0.785 on DeepSWE). On average, 11% of an agent patch's code units on SWE-bench Verified are still unneeded, and 89% of those change behavior. Debug steps write almost none of the unneeded code. Code necessity differs substantially by model; it is unrelated to resolve rate on SWE-bench Verified and negatively correlated with it on DeepSWE (Spearman -0.59, p = 0.01). On SWE-bench Verified, pruning with DRA using only the tests the agent can see (its own tests and the repository's) removes the majority of unneeded code but also some needed code (67% recall, 46% precision), and 89% of pruned patches still resolve the task; asking the agent to audit its own diff is more precise but less effective (36% recall, 66% precision). We recommend that benchmarks report code necessity next to resolve rate and that over-editing be addressed through model training and harness-level pruning.

## 一、核心问题与研究动机

### 1.1 背景

- 语言模型已从"从零写代码"转向"编辑既有代码"。对这类任务，**通过测试是必要但不充分的**：一个用 50 行重写来修 3 行 bug 的补丁，审查成本更高，也更可能夹带非预期改动。
- 已有证据表明问题严重：
  - 维护者研究中，约**一半**通过 SWE-bench 的补丁实际上不会被合并（Whitfill et al., 2026）；
  - 许多"看似合理"的补丁在测试未覆盖的输入上行为与开发者修复不同（Wang et al., 2026）；
  - 仓库级成功补丁的改动量约为开发者的 **2 倍**，且"最小化提示"几乎无效（Luo et al., 2026）。

### 1.2 核心痛点（论文的立论起点）

> **补丁大小 ≠ 过度编辑。** 大小无法回答三个决定"该怎么修"的问题：
> 1. 额外编辑**是否必要**？
> 2. 它们**是什么类型**（测试？文档？调试残留？修复本身）？
> 3. 它们**来自轨迹的哪一步**？

不同答案对应完全不同的治理手段：
- 若是调试残留 → harness 可自动清理；
- 若是测试 → 可能是受欢迎的贡献；
- 若是写进修复本身的代码 → 必须改模型。

### 1.3 五个研究问题（RQ）

| RQ | 问题 |
|---|---|
| RQ1 | 相比开发者，智能体过度编辑了多少？ |
| RQ2 | 那些非必要编辑是什么？ |
| RQ3 | 它们来自轨迹的哪个环节？ |
| RQ4 | 哪些模型过度编辑更多？是否与解决率相关？ |
| RQ5 | 能否自动移除非必要代码？ |

### 1.4 与已有工作的区别

- 函数级研究（Zhu et al., 2026；PDB；CanItEdit）依赖"已知最小修复"作参考，把所有差异都算作多余；
- 仓库级 RECAP 只比较补丁大小；
- 覆盖率类指标混淆了"被测试执行"与"被任务需要"。
- **DRA 的差异**：用**反事实移除 + oracle 判定**度量必要性，**不需要唯一的参考补丁**，因此"不同但同样有效"的编辑不会被误判。

## 二、方法论：Delta Residue Attribution（DRA）

### 2.1 核心思想

回放已解决的智能体轨迹 → 把最终补丁切分为可独立回退的**单元（unit）** → 将每个单元**归因**到写入它的轨迹步骤 → **逐单元回退并重跑任务测试**，判定其是否必要 → 把非必要单元按"写入步骤的角色"分解为**调试残留**与**修复内多余**。

### 2.2 形式化定义

- 轨迹执行前 $t$ 步得到工作树状态 $S_t$，提交补丁 $\Delta = \text{diff}(S_0, S_T)$。
- 单元集合 $U(\Delta)=\{u_1,\dots,u_n\}$，$S_T \ominus u$ 表示回退单元 $u$ 后的状态。
- 必要性指示：
  $$n_O(u) = 1 - O(S_T \ominus u)$$
  $$NP_O(\Delta) = \frac{1}{|U(\Delta)|}\sum_u n_O(u)$$
- **NP = 1 当且仅当 $\Delta$ 是 1-minimal**（Zeller & Hildebrandt, 2002）：没有任何**单个**单元可被移除而不被 oracle 拒绝。注意：多个单元**联合**移除仍可能成立，这是明确承认的局限。
- 调试残留占比：$\rho = |E_{dbg}| / |E_{dbg} \cup E_{fix}|$，$\rho_{code}$ 限定为代码单元。
- 开发者校准差距：$\Delta_{dev} = NP_{code}(\text{agent}) - NP_{code}(\text{developer})$，配 95% 实例 bootstrap CI（B = 2000）。

### 2.3 四个阶段（算法流程）

**步骤 1：Replay（回放）**
- 轨迹只记录工具调用、不记录中间仓库状态，因此在 base 文件上重放结构化编辑调用（edit 字符串替换、create、patch 应用），维护**行级 blame**。
- 若文件由 shell 命令写入（sed / heredoc），归因到最后一次写入并命名该文件的 shell 命令，再"撤销"其后的结构化编辑以重建状态；无法重建则该文件单元保留必要性评分但**无 provenance**。
- **严格校验**：重放最终内容必须与提交补丁逐文件完全一致，否则丢弃（SWE-bench Verified 重放成功率 96.7%）。

**步骤 2：Units & Provenance（切分与溯源）**
- 单元 = 一个文件中**连续变更行块**，间隔 ≤ 1 个未变行则合并；新建/删除文件算 1 个单元。
- 分类优先级：test → docs → config → nonsemantic（AST/词法去注释后不变）→ code。
- **引入步骤** $t^\star(u)$ = 最后一个写入或删除该单元任一行的步骤。因此"先调试时写下、后在修复步骤改写"的单元归给**修复步骤**（保守设计）。

**步骤 3：Step-Role Labeling（步骤角色标注）**
- 六种细粒度角色：EXPLORE / REPRODUCE / PROBE / FIX / REFINE / CLEANUP。
- 归并为三组：**DEBUG**（explore, reproduce, probe）、**FIX**（fix, refine）、**CLEANUP**。
- 两条确定性规则先跑（如"新增文件并在 3 步内被执行"→ REPRODUCE；"新增行全是 print/log/breakpoint"→ PROBE），其余由 LLM judge（GPT-6.1 Sol）基于 issue、压缩历史、动作、观测、diff delta、后续叙述标注。

**步骤 4：Necessity Grading（必要性判定）**
- 在官方评测镜像中逐单元回退，重跑 FAIL_TO_PASS 与 PASS_TO_PASS。
- 特殊处理：回退后回到 base 状态、语法不解析、测试挂起 → 一律记为**必要**（保守）。
- **测试文件不计分**：SWE-bench 评测会 reset 测试文件，故测试编辑对 oracle 无影响，单独报告为"未评分"。因此论文定义 **extra edits = 未评分测试编辑 + 非必要单元**，主指标取 $NP_{code}$。

### 2.4 强化 oracle：行为探针与 $O^+$

- 任务测试覆盖不全，故对每个被 $O_{test}$ 判为非必要的代码单元，由 GPT-6.1 Sol（**不看隐藏测试、不看开发者补丁**）写出**差分探针脚本**，在三种状态下运行：agent 补丁 $S_T$、回退态 $S_T \ominus u$、开发者补丁 $S_{dev}$。
- 判定规则：
  - 回退后任务测试失败，或回退后的行为**与开发者补丁一致** → 在 $O^+$ 下算**必要**；
  - 与开发者补丁**不一致**（引入了未被要求的行为变化）→ 非必要（live divergence）；
  - 所有探针都无差异 → 惰性编辑（inert）。
- 另设 $O_{live}$（任何行为变化都算必要）作为敏感性分析。
- 正控制：112 个 $O_{test}$ 判定为必要的单元，探针 100% 检出行为变化。
