## ABSTRACT 

Cross-modal vector retrieval is widely used in multimodal systems, such as search engines and vector databases. It typically operates in out-of-distribution (OOD) settings, where query vectors follow a dis-tribution that differs from that of the vectors stored in the database. In such cases, conventional indexes suffer significant performance degradation, and even methods specially designed for OOD remain limited by inefficient use of query modal characteristics, restricted GPU parallelism, and inadequate support for dynamic updates. We present CORAL, a novel GPU-accelerated graph-based vector index for scalable cross-modal retrieval, featuring hierarchical memory management that spans GPU, CPU, and disk. Specifically, CORAL incrementally incorporates the characteristics of query modality and terminates index construction timely. Crucially, it introduces coverage-aware adaptive pruning to address the imbalanced cov-erage of the query vector’s neighbors. Moreover, CORAL presents a fully neighborhood-aware projection approach to efficiently uti-lize GPUs for highly parallel index construction, and a targeted connectivity enhancement method to refine the index structure. Besides, CORAL also supports modal-semantics-based vector inser-tion and topology-repairing deletion that restore node connectivity. Experimental results demonstrate that CORAL outperforms exist-ing methods with up to 1 .6× the throughput at matched recall while reducing construction time by up to 56%. Furthermore, it exhibits remarkable resilience under dynamic updates and remains effective at the billion scale.

## 1 INTRODUCTION 

Cross-modal vector retrieval plays a crucial role in multimodal data systems, such as search engines and vector databases [10, 20]. In these systems, unstructured data from different modalities are embedded into a shared high-dimensional vector space through ad-vanced multimodal representation learning approaches [25]. These high-dimensional vectors in the shared space allow queries in one modality to retrieve semantically similar instances in another, via approximate nearest neighbor search (ANNS). The typical approach to support ANNS is to use high-dimensional vector indexes [6, 8, 19, 21, 24]. Classical indexes assume that queries and indexed data follow similar distributions and locate 

doi:10.14778/3849423.3849426 arXiv:2610.11230v1 [cs.DB] 8 Oct 2026 nearest neighbors through local geometric proximity [1, 4, 11, 16]. Cross-modal retrieval violates this assumption because different modalities often follow distinct distributions, creating a modality gap that reduces search effectiveness [25, 28]. Recent graph-based indexes address out-of-distribution (OOD) search by adding query-guided links that better align the graph with the query distribu-tion [7, 36, 37]. RoarGraph projects query neighborhoods into graph edges, ParaGraph offloads filtering to GPUs, and CDMG enforces cross-distribution monotonicity. Nevertheless, the existing index methods optimized for OOD ANNS [7, 17, 36, 37] still suffer from critical limitations: 

L1 (Inefficient handling of skewed query coverage). As shown in Figure 1, query coverage refers to the extent to which the base dataset is covered by the retrieved 𝑘 -nearest vectors (kNV) of a set of auxiliary query vectors. These retrieved neighbors are used by existing methods to guide graph construction towards the query distribution. Due to the modality gap, the query coverage is highly skewed: many auxiliary queries repeatedly retrieve a small set of nodes, whereas many other base nodes are rarely retrieved and may remain isolated. As a result, the graph is over-optimized for frequently retrieved regions but remains weakly connected else-where, leading to lower recall, longer traversal paths, and reduced query throughput. Existing methods [7, 36] mitigate such skewed coverage by introducing more auxiliary queries into the indexes being constructed. However, this strategy incurs substantial con-struction overhead while yielding limited structural improvement, since the additional updates remain concentrated on the already well-connected nodes. 

L2 (Limited parallelism in index update and search). Existing indexes are mostly designed for CPUs and remain poorly adapted to GPU execution for both graph updates and searches. Graph updates are performed at fine granularity, where each query’s kNV affects only a small number of graph nodes, resulting in limited parallelism and hindering effective batching. As a result, even with advanced GPU-based methods, ParaGraph’s update performance remains limited [36]. In graph search, these graph-based indexes sequentially expand each node, which offers little parallelism and makes it difficult to exploit GPU acceleration [14, 15]. 

L3 (Poor maintenance of node connectivity for updates). Ex-isting indexes rely on auxiliary queries to construct the index. As shown in the left half of Figure 1, an inserted vector (orange dot) is assigned to the coverage region of certain auxiliary queries (dashed circle) and linked with other base vectors (blue dots) contained in the same region, thereby preserving node connectivity. However, such localized updates are insufficient to maintain connectivity between inserted vectors and the global graph, especially as the query/data distributions diverge. For deletions, existing methods typically use a lazy tombstone mechanism [23], in which obsolete nodes are marked invalid rather than explicitly removed. These stale nodes continue to occupy limited out-degree slots, preventing effective rewiring and causing the graph structure to gradually drift away from the updated data distribution. To overcome these limitations, we propose CORAL, a novel graph-based index for cross-modal vector retrieval that supports efficient construction, search, and robust updates. To address L1 ,CORAL employs an incremental construction framework that pro-gressively enriches the index using batched query workloads. As shown in Figure 1, queries are processed in a pipelined manner with a test mechanism that triggers early termination once information gain converges. In addition, we propose Coverage-Aware Adaptive Pruning (CAAP) to optimize query coverage across the base dataset. By promoting coverage in unexplored regions and pruning redun-dant updates on frequently visited nodes, our design maximizes per-query utility and eliminates extraneous computation without compromising retrieval accuracy. To tackle L2 , we propose a novel graph construction primitive called Fully Neighborhood-Aware Projection (FNAP). Unlike tradi-tional methods that rely on fine-grained, sequential updates, FNAP jointly leverages the structural topology within each kNV to re-formulate graph evolution into coarse-grained, bulk-synchronous operations, maximizing parallelism for GPU acceleration. To han-dle datasets exceeding device memory, CORAL integrates a het-erogeneous CPU-GPU co-processing scheme and a hierarchical index storage manager that orchestrates data movement across the GPU device, main memory, and disk storage. Complementing CAAP and FNAP, CORAL further introduces Targeted Connectiv-ity Enhancement (TCE), which repairs the residual isolated and over-concentrated hot nodes after coverage-aware pruning. To address L3 , we propose a topology-aware index update mech-anism to preserve graph quality during insertions and deletions. Insertions leverage auxiliary query vectors to integrate new data and enhance their connectivity with the entire graph through global search. Deletions perform targeted local topology repair rather than lazy tombstone removal. Together, these designs mitigate perfor-mance degradation over time and eliminate the need for costly periodic index reconstruction. We compare CORAL with state-of-the-art ANNS methods across datasets ranging from 1M to 1B in size to demonstrate the efficiency, scalability, and robustness of CORAL. CORAL outperforms existing methods with up to 1 .6× the throughput at matched recall while reducing construction time by up to 56%. For index updates, CORAL sustains Recall@100 around 98% after replacing 50% of the original dataset, while the best competitor’s recall drops below 90% after only 10% of the data is replaced. The main contributions are summarized as follows: 

• We propose CORAL, a novel graph-based vector index for cross-modal vector retrieval. The key feature of CORAL is an in-cremental graph index construction approach that integrates construction and refinement to reduce redundant kNV compu-tations and fully exploit neighborhood structural information (Section 3). 

• We propose novel topology-aware index update techniques, including vector insertion guided by modal semantics and dele-tion with topology repair, to preserve the quality of the graph index during runtime (Section 3.3). 

• We propose high-performance graph construction and search primitives to enable CPU-GPU co-processing, and a hierarchical index storage manager for large-scale data processing across the GPU, main memory, and disk (Section 3.4). 

• We conduct extensive experiments on datasets ranging from millions to billions of vectors, showing that CORAL consistently achieves better performance than state-of-the-art OOD and in-distribution (ID) baselines in terms of recall, efficiency, and scalability. We also conduct ablation studies to validate the contribution of each component (Section 4). In addition, Section 2 provides the background on ANNS and analyzes the limitations of existing methods; Section 5 reviews the related work; and Section 6 concludes our work. 

## 2 BACKGROUND 2.1 Out-of-Distribution ANNS 

Approximate nearest neighbor search (ANNS) is a fundamental primitive for vector retrieval. Given a query vector, ANNS aims to re-trieve its nearest vectors from a vector dataset (i.e., the base dataset) without exhaustively computing distances to all vectors (i.e., the base vectors). In graph-based ANNS, this is typically achieved by constructing a proximity graph over the base dataset and perform-ing greedy traversal for the query. To formalize the retrieval target, we first define the exact nearest vectors of a query.

under a distance function 𝛿 (· , ·) , such as Euclidean distance or inner product [9]. Formally, kNV (𝑞, 𝐷 ) = k-arg min 𝑖 ∈ [ 1,𝑁 ] 𝛿 (𝑞, 𝑣 𝑖 ), where 

|kNV (𝑞, 𝐷 )| = 𝑘 and 𝛿 (𝑞, 𝑣 𝑖 ) ≤ 𝛿 (𝑞, 𝑣 𝑗 ) for all 𝑣 𝑖 ∈ kNV (𝑞, 𝐷 ) and

The effectiveness of ANNS methods depends heavily on the relationship between the query distribution and the base distri-bution. Conventional ANNS indexes are mainly designed for the in-distribution setting, where queries and base vectors follow the same distribution. However, in cross-modal vector retrieval, queries and base vectors originate from different modalities and thus follow different distributions. This gives rise to out-of-distribution ANNS.

kNV (𝑞, 𝐷 𝑏 ) without exhaustively evaluating all pairwise distances. 

To address OOD ANNS, existing approaches incorporate aux-iliary query vectors during index construction [7, 36, 37]. Graph-based indexes use these query vectors to connect their nearest base vectors, even when these base vectors are not close in the vector space. These edges provide shortcuts for graph traversal during index search, thereby improving retrieval efficiency and accuracy. The typical construction workflow consists of three stages. 

Stage 1: Exact kNV computation for query vectors. To uti-lize query modal information for index construction, an auxiliary query-modal vector set 𝑄 𝑏 is ingested. For each query-modal vec-tor ˆ 𝑞 ∈ 𝑄 𝑏 , existing methods compute its kNV ( ˆ𝑞, 𝐷 𝑏 ). These base vectors in kNV ( ˆ𝑞, 𝐷 𝑏 ) are regarded as semantically related from the perspective of the query distribution. The neighborhood size 

𝑘 𝑏 affects query coverage, i.e., the extent to which the collective kNV sets of the auxiliary queries cover the base dataset. 

Stage 2: Neighborhood-Aware Projection (NAP). For each query ˆ𝑞 ∈ 𝑄 𝑏 , adjacency relationships are established among vectors in kNV ( ˆ𝑞, 𝐷 𝑏 ). NAP selectively connects these base vectors to con-struct a sparse graph while controlling the maximum out-degree of each node. Since a base vector can appear in the kNV sets of multi-ple queries, the projection process aims to introduce query-aware edges while preserving a bounded graph structure. 

Stage 3: Connectivity Enhancement (CE). After projection, the resulting graph usually still contains weakly connected or isolated components that hinder graph traversal. CE improves graph con-nectivity by using sampled base vectors as queries to search on the graph and identify additional edges. The ratio of nodes selected for CE is denoted by 𝜌 𝐶𝐸 . In traditional methods, 𝜌 𝐶𝐸 is typically set to 1, meaning that all nodes are exhaustively involved in CE. After construction, OOD ANNS is performed by greedy graph traversal, typically implemented as beam search. The search starts from entry nodes and iteratively expands the closest unvisited node under a bounded beam budget, returning the top-𝑘 closest visited nodes upon termination. Therefore, the effectiveness of OOD search directly depends on the structural quality of the graph. Query-aware edges act as shortcuts to regions relevant to the query modality, allowing beam search to reach high-quality candidates with fewer distance evaluations. In contrast, weak connectivity or isolated nodes can trap the traversal in local regions and cause recall loss. 

## 2.2 Problem Statement 

This paper studies the cross-modal vector retrieval problem, which is typically addressed through OOD ANNS approaches. In cross-modal vector retrieval, queries and indexed data originate from different modalities (i.e., the query modality and base modality). A representative example is text-to-image retrieval, where textual queries are used to retrieve relevant images. Data from the two modalities are embedded into a shared vector space to obtain query and base vectors, respectively [25]. We formalize the cross-modal vector retrieval problem as follows.

For example, RoarGraph commonly uses an auxiliary query set com-parable in size to the base dataset, while experiments show that reducing the auxiliary query set by 50% still yields comparable index performance. As shown in Figure 2(a), the recall of test samples con-verges after ingesting about 4.6M queries, reaching 85.25%, while construction cost keeps growing with query size. This suggests that the benefit of ingesting additional query vectors diminishes once the graph structure has gradually converged. Beyond this point, new queries mainly trigger redundant updates on already well-connected nodes. Therefore, the key challenge is not only to incorporate query modal information, but also to determine when sufficient query vectors have been ingested. 

Motivation 1. During index construction, incrementally ingest-ing auxiliary query vectors to acquire structural information and terminating early once the graph converges achieves a better trade-off between index performance and construction cost. 

Guided by this motivation, CORAL employs an incremental construction method that processes auxiliary queries in batches. As shown in Figure 1, each batch contributes query-induced structural information, while a test mechanism periodically evaluates the index. Once the evaluation metrics converge, CORAL terminates construction early, avoiding unnecessary kNV computation and graph updates while preserving retrieval performance. While early termination reduces unnecessary query ingestion, it does not ensure that the ingested queries are effectively utilized. As mentioned in L1 , query coverage is highly skewed: a small subset of base vectors repeatedly appears in many queries’ kNV sets, while many others are rarely covered. In the index construction of the T2I-10M dataset, RoarGraph leaves over 30% of nodes isolated after ingesting 1M queries, i.e., 100M retrieved-neighbor occurrences with 𝑘 = 100. Moreover, as shown in Figure 2(b), access to the top 1% of base nodes accounts for 15.04% of the total access, indicating a strong coverage imbalance. Such skew causes later queries to repeatedly update already well-connected nodes, while uncovered or weakly connected regions receive limited structural refinement. This skew may originate from the true query distribution, embed-ding hubness, data imbalance, or redundancy in the construction algorithm, yet its impact on construction is the same regardless of the source, since repeatedly retrieving already well-connected nodes yields little new structural information. This problem is fur-ther amplified by the construction methods of existing OOD ANNS graph-based indexes, in which each query’s kNV is exploited in a restricted, asymmetric manner under out-degree constraints. There-fore, the key challenge is to make kNV acquisition coverage-aware and increase the effective structural information provided by each query. 

Motivation 2. During index construction, reducing redundant retrievals of over-covered nodes in kNV acquisition and redirecting later kNV acquisition toward under-covered regions improve graph connectivity and enhance the effective utilization of query vectors. 

Guided by this motivation, CORAL introduces Coverage-Aware Adaptive Pruning . It records each base node’s occurrence frequency in kNV and monitors the fraction of newly covered isolated nodes in each kNV during construction. When this fraction is too low (i.e., below 10% ), CORAL rebuilds the kNV acquisition index by removing high-frequency nodes from subsequent acquisition. This redirects later kNV acquisition toward less-visited regions, allowing newly acquired kNV to provide more useful structural information. Beyond initial construction, cross-modal vector retrieval systems are also expected to handle update workloads where vectors are continuously inserted and deleted. As mentioned in L3 , the local-ized insertion of existing OOD ANNS methods, which is restricted by the query coverage, is insufficient to maintain effective connec-tivity between inserted vectors and the global graph. Meanwhile, a lazy tombstone mechanism [23] used for vector deletion causes local update stagnation, while directly removing deleted vectors destroys relevant local connectivity. As updates accumulate, the lack of maintenance of local and global connectivity caused by these operations degrades retrieval performance. 

Motivation 3. During index updates, maintaining both local and global connectivity for newly inserted and deleted vectors is crucial to preserving the robustness of index performance as data evolves. 

Guided by this motivation, CORAL introduces a topology-aware update mechanism. For insertion, CORAL augments localized query-aware connections with a refinement based on graph search to strengthen the inserted node’s global connectivity. For deletion, CORAL physically removes deleted nodes and repairs the affected local topology by reconnecting their neighbors. Overall, these de-signs preserve local structural consistency and global connectivity, mitigating performance degradation as data evolves.

## 3.2 Incremental Index Construction 

Workflow. Figure 3 illustrates the CORAL index construction workflow, which consists of four modules and incrementally ingests auxiliary queries in batches: (1) kNV acquisition for query vectors, (2) fully neighborhood-aware projection (FNAP), (3) convergence test, and (4) targeted connectivity enhancement (TCE). The kNV acquisition module computes the kNV of the ingested query vectors in the base dataset using indexes adapted to differ-ent data scales. To reduce redundant graph updates due to skewed kNV coverage, CORAL applies Coverage-Aware Adaptive Pruning, which periodically rebuilds the index for kNV acquisition by re-moving nodes that have been excessively retrieved. The resulting kNV sets are then consumed by FNAP, which updates the graph by establishing adjacency between nodes within each kNV. The convergence test module measures retrieval performance on sampled queries and monitors structural indicators such as the isolated node ratio and average out-degree. Based on these signals, CORAL decides whether further query-guided updates are still useful or whether construction should proceed to the next TCE step. This design avoids predefining the number of auxiliary queries and achieves a better trade-off between construction cost and index quality. The TCE module then mitigates the remaining structural defects by reconnecting isolated nodes and strengthening the connectivity of key routing nodes, informed by the index search. Moreover, to scale the index beyond the GPU’s memory capac-ity, CORAL adopts a hierarchical index structure across the GPU, main memory, and disk. The complete graph is stored on disk, and the main memory caches the active nodes. During graph updates, CORAL loads only the metadata of nodes that are necessary for dis-tance evaluation, candidate generation, and adjacency modification. We separate node metadata into read-only neighbor information and mutable adjacency lists. Neighbor information is suitable for sharing across computations, whereas exclusive access is enforced for adjacency-list updates to avoid conflicts. By aligning data trans-fer with FNAP and TCE at each batch, CORAL reduces unnecessary data movement while preserving correctness, enabling a scalable index on datasets ranging from million-scale to billion-scale. 

kNV Acquisition for Datasets of Different Scales. Existing ANNS indexing schemes often show skewed query coverage on the base dataset in OOD scenarios. CORAL addresses this problem with flexible kNV acquisition and coverage-aware adaptive pruning, which rely on improved use of query modal information. When the base dataset fits in GPU memory, CORAL computes exact kNV and stores the result in GPU memory. For larger datasets, exact kNV computation becomes inefficient due to frequent host-device data transfer. Thus, CORAL uses approximate indexes, such as IVF [2, 31] and IVFPQ [18], to acquire kNV. Since this stage aims to capture relatively close neighbors from the perspective of the query modality rather than achieve perfect recall, such an approximate acquisition of kNV is sufficient for indexing. To address skewed kNV coverage, CORAL introduces Coverage-Aware Adaptive Pruning (CAAP), which periodically rebuilds the kNV search index. During construction, CORAL records the access frequency of each base node, i.e., the number of times it appears in query kNV results, and monitors the fraction of newly covered isolated nodes. Once this fraction drops below a threshold 𝜏 , in-dicating that newly retrieved kNV is increasingly dominated by already well-connected nodes, the kNV search index is rebuilt. During rebuilding, the base nodes whose access frequency ex-ceeds a threshold 𝑡 are identified as hot nodes , as illustrated in Figure 4, and are excluded from subsequent kNV acquisition, while remaining in the graph as routing nodes. This operation directs subsequent queries toward less-frequently visited regions, so new kNV provides more useful structural information rather than re-peatedly updating the already optimized regions. The rebuild is lightweight, removing hot nodes from the candidate set for a Flat index or from the inverted lists for IVF/IVFPQ without retraining the coarse quantizer. Each construction run typically triggers 3 to 5 rebuilds, each taking about 5 s on T2I-10M versus 635 s total construction time. Neighborhood-Aware Projection (NAP) is a basic step for constructing graph-based ANNS indexes under out-degree constraints. Given a set of nodes, NAP establishes directed edges so that each node maintains a limited number of outgoing neighbors (out-neighbors) while preserving local connectivity for beam search. A typical instantiation is the pivot-centric NAP design, in which only the node closest to the query is selected as the pivot for each query kNV. As shown in Figure 5(a), the pivot connects to the remaining 𝑘 − 1 candidate nodes, and reverse edges are added selec-tively. However, connections among non-pivot nodes are ignored, and several candidate nodes are pruned under the out-degree con-straint without contributing to graph updates. This design has two limitations. First, the expensive query kNV results are only partially used, leading to information loss during graph construction. Second, updates are centered on a single pivot, which limits parallelism and is poorly aligned with GPU execution, where updates for multiple nodes in the same kNV set could be processed in parallel. As shown in Figure 5(b), FNAP generalizes NAP by allowing all nodes in a kNV to participate in adjacency updates as pivots. Given kNV ( ˆ𝑞, 𝐷 𝑏 ) = {𝑢 1, 𝑢 2, . . . , 𝑢 𝑘 } for an introduced query ˆ 𝑞 , FNAP treats each 𝑢 𝑖 as a pivot and updates its outgoing edges using other nodes in kNV ( ˆ𝑞, 𝐷 𝑏 ). This design exploits neighborhood informa-tion more completely and exposes parallelism across pivots. To avoid excessive degree growth and unstable updates to existing neighborhoods, FNAP further employs a candidate selection mech-anism that preserves out-degree constraints and graph stability. FNAP categorizes nodes in kNV ( ˆ𝑞, 𝐷 𝑏 ) into isolated nodes , which have no out-neighbors, and non-isolated nodes , which already have adjacency lists. For an isolated pivot, all other nodes in kNV ( ˆ𝑞, 𝐷 𝑏 )

are treated as candidates. For a non-isolated pivot, the candidate set contains its existing neighbors together with only the isolated nodes in kNV ( ˆ𝑞, 𝐷 𝑏 ). This design integrates new structural infor-mation while avoiding unnecessary updates of established edges. After candidate selection, FNAP applies the standard NAP prun-ing rule to obtain the final adjacency list, which preserves locality while satisfying the out-degree constraint. Since pivot updates are independent, FNAP naturally exposes parallelism for GPU acceler-ation, as detailed in Section 3.4. Overall, FNAP serves as a unified graph-update GPU primitive for index construction and update.

## 3.3 Topology-Aware Index Update 

Figure 6 illustrates the interaction between search and update oper-ations. All graph updates, including vector insertions and deletions, are applied via the graph update primitive FNAP. The objective of vector insertion is to integrate new vectors into the index while preserving graph connectivity. When an inserted vector 𝑣 is accompanied by a query vector ˆ 𝑞 , the system uses ˆ 𝑞 to retrieve approximate nearest neighbors from the existing index. FNAP is then applied to the node set comprising 𝑣 and its retrieved neighbors to establish adjacency relationships. If no query vector is available, the system identifies an accompanying query vector by searching a Flat index built on previously ingested query vec-tors. This lightweight index is retained from construction, with size 

|𝑄 𝑏 | ≪ | 𝐷 𝑏 | (about 0.7 GB for T2I-10M and 8% of the graph foot-print). It is maintained dynamically, appending query vectors upon insertions and removing queries whose retained kNV count drops below a threshold upon deletion, so its distribution evolves in sync with the base graph. The insertion process then proceeds in the same manner as when an accompanying query vector is present. In both cases, insertion is guided by the query modal semantics rather than solely by proximity to the base dataset’s data distribution. After insertion, CORAL enhances the new vectors’ global connec-tions similarly to TCE. Specifically, the inserted nodes are queried in the graph, and the nodes retrieved are treated as candidates for updating the neighbors of the inserted nodes. This operation also safeguards insertion quality: even if the surrogate query is imprecise, it only provides an approximate search direction, and the graph search independently discovers global connections and corrects any inaccuracy. The objective of vector deletion is to remove nodes from the index while preserving graph connectivity. CORAL physically re-moves the node to be deleted and repairs the affected graph topol-ogy. When a node 𝑑 is deleted, its in-neighbors and out-neighbors are collected. FNAP is then applied to reconstruct adjacency rela-tionships among these neighbors, compensating for the structural disruption caused by the removal of 𝑑 . This repair mechanism pre-serves reachability and avoids structural degradation.

Full-Expansion Beam Search on GPU. Index search follows a greedy beam search strategy. As shown in Figure 6, a fixed-size beam retains the current set of candidate nodes. At each iteration, the algorithm expands all unvisited nodes in the beam using their adjacency lists, rather than expanding only one node at a time, to expose more parallelism on the GPU. The newly discovered nodes are then ranked by their distances to the query and used to update the beam. This process repeats until the beam converges. The selection of entry points plays a critical role in improving performance. CORAL uses a hybrid entry strategy. Following the TCE design, half of the entry points are selected from the hot node set obtained during kNV acquisition. The remaining entry points are selected from the entire graph using Farthest-Point Sampling (FPS) based on hop distance, which improves coverage of regions not represented by hot nodes. Concretely, FPS maintains for each node its minimum hop distance to the current entry set and iteratively selects the node with the largest such distance as the next entry point. This yields a diverse set of entries with global graph coverage. Based on these entry nodes, CORAL performs beam search using a GPU-based parallel execution strategy. Each query is assigned to a single thread block, allowing the block to maintain the beam and intermediate candidates in shared memory. Within each block, all unexpanded nodes in the beam are expanded concurrently by each warp, and the threads in the warp evaluate their out-neighbors in parallel. In addition, CORAL maintains a visited bitmap to avoid expanding duplicate nodes and a dynamically updated distance threshold to guard against invalid candidate insertion, so nodes that cannot enter the beam are filtered early. These operations align the irregular control flow of graph search with GPU execution. As a result, CORAL can explore multiple routing paths in parallel while preserving the search semantics required for efficient high-recall retrieval with limited beam queue length.

## 4.1 Experimental Setup 

Hardware and software environment. Unless otherwise speci-fied, our experiments are conducted on a server running Ubuntu 24.04.1 LTS, equipped with one Intel Xeon Gold 5218 CPU, 256 GB of main memory, and one NVIDIA A100 PCIe GPU with 40 GB of HBM2 device memory. All GPU kernels are implemented and compiled using CUDA Toolkit 12.8. For large-scale CPU-only experiments on the T2I-100M and T2I-1B datasets, we use an Intel Xeon Platinum 8558 CPU for index construction and search. 

Datasets. We use five datasets: Text-to-Image (T2I) [29], Web-Vid [3], LAION [26], WIT [32], and CC3M [27]. T2I uses 200-dimensional vectors with ℓ2 distance, while WebVid, LAION, WIT, and CC3M use 512-dimensional CLIP embeddings with inner prod-uct, covering text-video and text-image retrieval scenarios. For T2I, we construct four subsets with 1M, 10M, 100M, and 1B base vectors to evaluate scalability across different storage hierarchies. Follow-ing CORAL’s hierarchical GPU-memory/main-memory/disk index (Section 3.2), the concrete layout follows the dataset scale: the 1M and 10M subsets fit entirely in GPU memory, the 100M subset fits in main memory, and the 1B subset exceeds main memory and is evaluated out-of-core with the complete graph on disk. The corre-sponding auxiliary query vector scales used for construction are 0.1M, 1M, 10M, and 30M, respectively. For the other datasets, we use 2.5M base vectors and 1M auxiliary queries for WebVid, 10M base vectors and 1M auxiliary queries for LAION, and 1M base vectors with 0.1M auxiliary queries for both WIT and CC3M. For evaluation, we use the official 10K query vectors for T2I and ran-domly sample 10K queries from the original data for the remaining datasets. We ensure that they are disjoint from the auxiliary queries used for index construction. 

Baselines. We compare CORAL with four OOD ANNS baselines: RoarGraph, ParaGraph, CDMG+, and OOD-DiskANN. We also in-clude three ID ANNS baselines: FAISS-IVF, CAGRA, and DiskANN. The methods differ in execution profiles: CORAL, FAISS-IVF, and CAGRA construct and search on the GPU; ParaGraph constructs on the GPU but searches on the CPU; RoarGraph and CDMG+ run en-tirely on the CPU; and OOD-DiskANN and DiskANN are CPU-only, residing in main memory and on disk, respectively. For fairness, for datasets with at most 10M vectors, we load the OOD baselines lacking native GPU search (RoarGraph, ParaGraph, CDMG+) into CORAL’s GPU search framework, so all methods share the same search kernel and hardware, and differences reflect only the graph structure. At the 100M and 1B scales, CORAL searches on the CPU to match OOD-DiskANN and DiskANN. At these scales, search latency is dominated by cross-tier data transfer rather than distance computation, making CPU search both fair and practical. Below, we describe the configuration of each baseline. 

• RoarGraph [7]: a cross-modal graph-based index with neigh-borhood size 𝑁 = 100 and maximum out-degree 𝑀 = 32. 

• ParaGraph [36]: a cross-modal graph-based index with a hy-brid CPU–GPU architecture. We adopt the same experimental configuration as the original paper. The query size used for index construction matches the base vector size, as required by its code. 

• CDMG+ [37]: the state-of-the-art cross-modal graph-based in-dex, using neighborhood size 𝑁 = 100 and maximum out-degree 

𝑀 = 32. 

• FAISS-IVF [19]: a GPU-accelerated partition-based index for ID ANNS. 

• CAGRA [22]: a GPU-accelerated graph-based index for single-modal ANNS with fixed out-degree 𝑀 = 32. 

• OOD-DiskANN [17]: a DiskANN variant designed for OOD queries, with 𝛼 = 1.2, max out-degree 𝑀 = 32, and search list size 𝐿 = 64. We use it as a baseline for the 100M-scale dataset. 

• DiskANN [33]: a disk-based ANNS method, enabling scalable and memory-efficient search over billion-scale vector datasets, with 𝛼 = 1.2, max out-degree 𝑀 = 32, and search list size 𝐿 = 64 during index building. We use it as a baseline for the 1B-scale dataset because OOD-DiskANN does not provide a runnable on-disk implementation of the 1B dataset. 

Implementation Details. For CORAL’s index construction, unless otherwise specified, we set 𝑘 𝑏 to 100 for kNV acquisition in CAAP, the maximum out-degree to 𝑀 = 32 in FNAP, and the hot-node ratio to 𝜌 𝐶𝐸 = 50% in TCE. These default settings balance search efficiency and construction cost, and their sensitivity is further analyzed in Section 4.4. 

Evaluation Metrics. We use Recall@ 𝑘 , the proportion of true top-𝑘 nearest neighbors among the top-𝑘 results, averaged over all queries, to measure retrieval accuracy in our evaluations. We use queries per second (QPS) to measure throughput and average hops (avg-hops) to measure computational cost during search. To thoroughly validate the efficacy of each method across diverse retrieval scenarios, we set 𝑘 to 10 and 100 for Recall@ 𝑘 . Unless otherwise stated, throughput is reported at Recall@100 = 95%.

We evaluate the contributions of CAAP, FNAP, and TCE in Table 1. Removing FNAP and reverting to the conventional single-pivot NAP causes the largest drop, reducing QPS from 10647.30 to 3397.55 on T2I-10M and from 3099.81 to 1703.87 on LAION-10M, which isolates the contribution of the GPU-oriented graph-update design. Relative to the variant without both CAAP and TCE, adding CAAP alone yields 1 .46 × and 1 .16 × speedups on T2I-10M and LAION-10M, respectively, while adding TCE alone yields 2 .63 × and 1 .69 ×

speedups. Full CORAL achieves 3 .28 × and 1 .82 × speedups over the same variant. Additional experiments show that as queries are incrementally ingested, CORAL with CAAP efficiently reduces the isolated-node ratio, leaving fewer than 10% of nodes isolated when the query scale reaches 1M. 

Summary. Overall, each component improves CORAL’s search effi-ciency. CAAP improves coverage efficiency by making better use of each query’s kNV, FNAP contributes the largest gain through GPU-oriented graph updates, and TCE provides further gains through targeted refinement. Together, these complementary mechanisms enable the full system to achieve the best performance on both datasets.

## 5 RELATED WORK 

OOD ANNS in Cross-Modal Scenarios. In cross-modal retrieval, distribution mismatch between query and base vectors degrades ID graph indexes such as HNSW [21], NSG [15], and DiskANN [33]. RoarGraph [7] guides construction with query modal information, and ParaGraph [36] and CDMG [37] further improve construction efficiency, yet all require costly kNV computation and redundant connectivity enhancement. Orthogonal to these graph-based in-dexes, LeanVec [34] addresses OOD search at the representation layer through query-aware projection with quantization. CORAL instead uses incremental, coverage-aware graph construction to effectively exploit query information at lower construction cost. 

Dynamic and Streaming OOD ANNS. FreshDiskANN [30] and SPFresh [35] support incremental insertions through buffering and rebalancing, while HNSW [21] and DiskANN [33] provide limited update support, and all of these methods target ID settings. In OOD settings, RoarGraph [7] uses localized insertion, limiting global integration, while its tombstone deletion accumulates redundancy and degrades search efficiency. CORAL instead combines local insertion with global refinement and physically removes deleted nodes through topological repair, preserving connectivity. 

GPU-Accelerated OOD ANNS. GPU systems such as Faiss [19] and CAGRA [22] accelerate graph search through parallelism. Para-Graph [36] adapts RoarGraph to GPUs for OOD search, but its pivot-centric construction limits parallelism and caps scalability at 10M vectors. CORAL instead combines GPU-friendly full-neighborhood projection, targeted refinement, and hierarchical storage for large-scale construction. 

## 6 CONCLUSION 

We presented CORAL, a GPU-accelerated graph index for cross-modal vector retrieval that combines incremental query-guided construction, CAAP, FNAP, TCE, and topology-aware dynamic updates. Experiments showed that CORAL improves retrieval ef-fectiveness, reduces construction time by up to 56% over existing baselines, remains robust under updates, and scales to billions of vectors. Future work will address evolving data distributions and optimize heterogeneous CPU–GPU–disk execution.
