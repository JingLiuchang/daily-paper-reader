Lakes

Abstract
Open model lakes may contain millions of reusable models, making it costly to identify
suitable models for a new dataset. This setting requires learning indexable representations
of models from heterogeneous evidence, including model and dataset metadata, lineage, and
historical evaluations. An important challenge is that this heterogeneous evidence is sparse
and concentrated around popular models and benchmarks. We present ModelLakeFishing,
a model-retrieval framework for queries that specify a target dataset, a prediction task, and
an evaluation metric. It consolidates model lake metadata and historical evaluations into a
model–dataset–task evidence graph, learns model and query embeddings with a relation-aware
graph encoder, and indexes model embeddings with Hierarchical Navigable Small World (HNSW)
search. At query time, HNSW retrieves 1k candidates without scoring every model in the lake.
A task-level prior computed only from training-side evidence then reranks the candidates for the
requested metric and returns the top 10 models. We evaluate the framework on a lake containing
3,016,439 models and 247,803 observed model–dataset performance pairs using three root-aware
splits in which test performance edges are held out from representation learning and retrieval.
ModelLakeFishing achieves a mean eligible-query gold@10 of 0.2968, recovering the observed-best
model among the ten returned models for 29.68% of eligible queries. This retains 93.47% of
the gold@10 achieved by an exhaustive baseline that applies the same scoring and reranking
procedure to every model in the lake. Given precomputed query embeddings, candidate retrieval
and reranking take 0.747 ms at the median and 1.102 ms at the 95th percentile. These results
show that sparse relational evidence can be distilled into an indexable representation space for
efficient retrieval over million-model lakes.1

Introduction
Recommendation over a large-scale model lake needs candidate discovery. Public model
hubs now resemble model lakes: large collections of reusable models accompanied by model cards,
configurations, lineage, and evaluation metadata (Pal et al., 2025; Dong et al., 2025). Hugging
Face alone hosts more than three million candidate models across diverse tasks, architectures, and
modalities. For a target dataset, trying every model is impractical, while computing a separate
query-specific relevance score for every model still requires traversing the full lake. The immediate
problem is therefore to find a small, useful shortlist before any candidate is downloaded or run.
Prior methods use different selection signals. Existing model-selection methods reduce the
cost of assessing candidates in different ways. Feature-based transferability estimators such as

LEEP (Nguyen et al., 2020), LogME (You et al., 2021), NLEEP (Li et al., 2021), and H-score (Bao
et al., 2019) avoid full fine-tuning yet still execute each candidate on target-dataset samples.
Other approaches use repository information to guide selection: TransferGraph uses learned graph
representations in a performance regressor (Li et al., 2024); ModelLens combines metadata and
evaluation records in a task- and metric-conditioned interaction scorer (Cai et al., 2026); and
HuggingR4 retrieves candidates from model-card representations for natural-language requests
before iterative refinement (Ma et al., 2025). Together, these works demonstrate interaction-based
ranking and metadata-based retrieval, leaving open how sparse model–dataset evidence can support
indexed candidate generation for dataset–task queries over the full lake.
Relation-aware learning makes evidence searchable. Historical performance records cover
only a small fraction of the model lake, so direct evaluations alone cannot support candidate
discovery throughout the collection. Model and dataset metadata provide descriptions that can be
crawled and enriched (Li et al., 2023c); observed performance, dataset similarity, and model lineage
provide complementary relations with different meanings. ModelLakeFishing brings these signals
together in a heterogeneous model–dataset evidence graph and trains a relation-specific GraphSAGE
encoder (Hamilton et al., 2017) to place models and dataset–task queries in a shared representation
space. Unlike TransferGraph’s downstream query–model performance regressor (Li et al., 2024),
our retrieval score is a direct inner product between independently computed representations. This
lets us index model representations offline with HNSW (Malkov and Yashunin, 2020), retrieve a
bounded pool for a dataset–task query, and apply a historical same-task prior only when reranking
that pool. Figure 1 summarizes this offline and query-time division.

A shortlist retains strong candidates. We assess candidate discovery by withholding performance
records for entire dataset roots (groups of related configurations of the same dataset)and asking
whether the returned top ten include the best model observed in those held-out records. This
observed-best recovery measure, gold10, is compared with a full-lake reference that uses the same
learned representations and reranking score but considers every model. Indexed retrieval retains
most of the reference’s recovery while limiting retrieval and reranking to a bounded candidate pool.
The lookup timing begins with a precomputed query representation, separating the cost of candidate
discovery from query encoding.

Related Work
Model lakes.
Model management systems record experimental artifacts, versions, and intermediate
results so that individual models can be reproduced, compared, or diagnosed (Vartak et al., 2018;
Mei et al., 2022). Provenance research studies derivation and reuse across model versions (Mu et al.,
2024). A model lake extends this scope from a controlled collection to reusable models, datasets,
metadata, lineage, and evaluation evidence at repository scale (Pal et al., 2025; Garouani et al.,
2024; Dong et al., 2025). For the massive model lakes we are considering, management and discovery
are coupled since exhaustively considering every model for a tasks is infeasible. A useful model
must be located before its artifacts can be inspected or evaluated, and evidence may be distributed
across metadata, related repositories (for example code repositories), and historical evaluations.
Public model lakes expose model cards and searchable repository metadata (Mitchell et al., 2019);
Macaroni crawls and enriches metadata from public model zoos (Li et al., 2023c). Model-card
documentation is nevertheless incomplete and uneven (Liang et al., 2024), limiting retrieval from
lexical descriptions or normalized fields alone. An alternative to using documentation for search is
to use behavior-based search (find models with a similar behavior) (Lu et al., 2023) or multimodal,
meta-learning-based retrieval (Li et al., 2023b). These methods extend what a query can express,
but the query itself still drives retrieval. Our setting is different: the evidence that makes a model
retrievable is not only in the query but also in the lake’s own relational structure — links among
models, dataset–task pairs, observed performance, and model lineage, evidence that is sparse but
structured. We ask how these relations can be distilled into an indexable search space over millions
of candidates.
Model recommendation.
Classical model selection ranks candidates through downstream
validation or fine-tuning, but evaluating every model becomes prohibitive as the size of the model
lake grows (Ding et al., 2018). Transferability estimators such as LEEP (Nguyen et al., 2020),
LogME (You et al., 2021), NLEEP (Li et al., 2021), and H-score (Bao et al., 2019) avoid the
expense of fully fine-tuning each candidate model on the target dataset, but still require running
each candidate forward on target-dataset samples to extract its outputs or feature statistics. They
therefore choose within an available pool, whereas our setting requires a shortlist from the full
3


lake before models are downloaded or run. HuggingR4 frames repository-scale selection as iterative
reasoning, retrieval, refinement, and reflection (Ma et al., 2025). ModelSearch uses structural
similarity between model-card tables to recommend models that are both relevant to the user’s
request and diverse (Dong and Miller, 2026). Historical model–dataset interactions provide a
complementary basis for recommendation without candidate execution: TransferGraph learns from
a graph of models, datasets, similarities, and observed performance (Li et al., 2024); ModelLens
combines heterogeneous metadata with task- and metric-conditioned interaction evidence at larger
scale (Cai et al., 2026). Both demonstrate that relational history improves recommendation, but
their reported final relevance functions score individual query–candidate pairs rather than expose
a query-independent model index. We ask how relational supervision can instead produce an
ANN-searchable space over millions of models.
Large-scale indexing.
Learned retrieval makes search indexable by encoding queries and candi-
dates independently, then comparing their vectors with a fixed similarity function. Sentence-BERT
makes candidate representations reusable for similarity search (Reimers and Gurevych, 2019); DPR
encodes the corpus offline and uses approximate nearest-neighbor search to obtain a bounded candi-
date set for each online query (Karpukhin et al., 2020). This factorization is the interface between
representation learning and indexing: unlike a joint query–candidate scorer, it lets candidate vectors
be computed once rather than rescored across the full collection. Approximate nearest-neighbor
systems reduce the cost of searching these spaces. HNSW provides high-recall search without an
exhaustive scan in the typical query path (Malkov and Yashunin, 2020); Faiss provides complemen-
tary exact and approximate indexes, vector compression, and hardware-oriented implementations
for large embedding collections (Douze et al., 2024). These methods assume relevance has already
been expressed in a searchable vector space. Our problem lies at that preceding boundary: sparse
model–dataset observations and heterogeneous graph relations do not directly define indexable
model vectors. ModelLakeFishing uses inductive graph representation learning (Hamilton et al.,
2017) to produce query-independent model embeddings and compatible dataset–task embeddings,
indexes models once with HNSW, and reserves query-conditioned task evidence for reranking only
the retrieved set.

Methodology
3.1
Problem Formulation and Overview
Candidate Discovery Task. Let D denote the dataset–task query nodes in the evidence graph.
Each query d = (normalize(dataset), t) ∈D identifies a canonicalized dataset and a prediction task
t Different tasks on the same dataset can therefore induce different model rankings. The objective
is to return k models from the candidate model lake M that recover strong candidates. We judge
strong candidates to be candidates that are ranked high in held-out historical evaluations. Table 1
summarizes the notation used.

Evidence Graph Construction. Historical evaluation records report how particular models
performed on particular dataset–task pairs, but cover only a small part of the model lake. We
organize these records into a graph with model nodes and dataset–task nodes. Each recorded
evaluation connects a model to the corresponding dataset–task node; dataset simialrity and model
lineage provide the other relations. This graph supplies the context from which we learn model and
query representations and is described in Section 3.2
Learning and lookup are separate. ModelLakeFishing constructs an evidence graph and
learns unit-normalized model and query representations offline. At query time, it retrieves a bounded
candidate pool from an index of model representations and reranks that pool using a same-task
historical prior. We collect historical model evaluation results from model cards and existing
evaluation collections. Each record identifies a model m, a dataset–task pair d, and a measured
performance score of m on d. After preprocessing, the score becomes ydm, and the corresponding
pair defines a performance edge. We partition these records by dataset into training, validation,
and test sets. The nodes, metadata, dataset-similarity edges, and model-lineage edges remain the
same. During training, 70% of the training performance edges are included in the message-passing
graph. The remaining 30% are held out of the graph, and their scores provide supervision for the
ranking loss. Validation and test performance edges are excluded from the training graph, and their
scores are not used for training. During testing, we measure recommendation quality on the test set.
Using the trained parameters, we compute model and query representations with all training and
validation performance edges as graph context, then retrieve and rerank models for each test query.
Test performance edges are held out of this graph in both directions; their recorded scores provide
the ground truth for evaluating the returned rankings.
3.2
Evidence Graph Construction
Node: Sparse records supply supervision. The evidence corpus combines Hugging Face crawls
dated August 18, 2026 with five historical evaluation graphs. We canonicalize model IDs and attach
dataset cards only through exact or unambiguous repository matches; otherwise, the dataset name
and task recorded in the evaluation record provide the description. We create a node for every
model in the crawl or referenced in the crawl. The referenced models include 12,680 absent from the
crawl but unambiguously referenced crawled model or dataset cards. We assign each node a fixed
integer ID and use it consistently for its feature row, graph-edge endpoints, and learned embedding;
model IDs also label entries in the search index.
We create a dataset–task node only when that pair appears in the evaluation records, whether or
not a dataset card is available. We group performance observations by dataset, task, and metric and
select one primary metric for each dataset–task node. Repeated observations are then aggregated,
normalized, and oriented so that higher values indicate better performance. The merged corpus
contains 247,803 observed model–dataset performance pairs with values notated as ydm, many fewer
5


than the number of candidate models. Appendix B.2 specifies metric selection, source resolution,
and per-node sampling.
Edges: Typed relations connect evidence. The graph has model and dataset–task nodes.
Its five directed relations comprise observed performance and its reverse, dataset similarity, and
parent-to-derivative lineage and its reverse. Performance edges represent recorded evaluations,
while similarity connects each dataset to its ten nearest neighbors by descriptor cosine and lineage
connects parent and derivative model nodes using resolved parent-model references in the model
metadata. These relations connect sparse observations with metadata and other structural evidence
without treating lineage or similarity as measured performance.
3.3
Relation-Aware Representation Learning
Metadata anchors both node types. Model and dataset–task inputs combine a name hash
and a text embedding from a sentence transformer (Wang et al., 2020) with learned type-specific
lookup features. Model text describes the repository name, family, and parameter size when known;
dataset text uses a matched card when available and otherwise uses its name and task. Dataset
nodes also include root-level statistics. The resulting model and dataset–task inputs have 480 and
486 dimensions, respectively. Node inputs contain neither performance statistics nor gold-eligibility
indicators; feature construction is detailed in Appendix B.2.
Figure 2: Representation learning and training. Model and dataset–task features pass through
type-specific projections, a relation-specific GraphSAGE encoder, and a shared projection head.
Ranking and global losses compare query–model pairs; model contrast compares model pairs.
Relation-aware aggregation yields indexable vectors. Indexable retrieval requires model vec-
tors that do not depend on the incoming query. We use a relation-specific GraphSAGE layer (Hamil-
ton et al., 2017) to independently compute model and query representations. Type-specific projec-
tions map both node types into a shared hidden space, followed by relation-aware neighborhood
aggregation and a shared output head. The resulting unit-length representations are scored by inner
product, sθ(d, m) = z⊤
d zm. The detailed encoder formulation is provided in Appendix B.5. The key
property of this architecture is that model and query representations are computed independently.
This means model vectors can be indexed once offline and searched for any query without rescoring
the full lake. The design achieves this by sharing a single output head across both node types, placing
models and queries in the same vector space, while keeping aggregation unweighted. Performance
values provide supervision and dataset similarity determines graph topology, but neither scales
the messages passed between neighbours. Hash and text features remain frozen; lookup tables,
projections, gates, and the shared head are learned.

3.4
Training with Held-Out Evidence
Root splits control evidence visibility. A dataset root groups configurations of the same dataset.
All nodes sharing a dataset root belong to the same training, validation, or test partition, so related
configurations do not cross evaluation boundaries. A disjoint portion of training performance edges
supplies supervision; the remaining training edges carry messages. Let Etr denote performance
edges from training roots. Validation message passing can use all training edges, and test message
passing can also use validation edges, but neither graph contains the performance edges of the
roots it evaluates. Reverse performance edges follow the same rule, while dataset similarity and
lineage remain fixed. Reported indexes and query vectors use the test message graph, making this
transductive retrieval with held-out performance evidence. The exact edge sets and split proportions
appear in Appendix B.3.

3.5
Indexed Retrieval and Reranking
Indexed Candidate Retrieval. The score in Eq. 8 uses model vectors that are independent of the
query, so we add every model vector to an inner-product HNSW index (Malkov and Yashunin, 2020)
offline. Given query vector zd, the index retrieves K = 103 nearby models from the full lake, forming
the candidate pool bPK(d). Only models in this pool proceed to task-prior reranking. HNSW is an
approximate search algorithm whose thoroughness is controlled by a parameter ef_search where
larger values explore more of the index and find neighbours closer to the true nearest neighbours, at
the cost of additional search time. We set ef by comparing HNSW’s retrieved candidates against
exact brute-force nearest neighbours — finding the smallest ef_search that recovers nearly all
exact neighbours — rather than tuning it directly against the gold evaluation labels. Details are in
Appendix C.3.
Historical Evidence-Based Reranker. For task t and model m, let ntm and Atm be the count
and sum of normalized evidence values on training and validation roots. Canonical task strings
define these groups; the scored test root and its sibling configurations are excluded. We use a fixed
shrinkage prior and fuse it with the normalized retrieval score. Unseen task–model pairs receive no
historical bonus, and no query-wise min–max rescaling is applied. Only retrieved candidates receive
prior lookups; a fixed label-free model order breaks exact ties before returning the top ten. This
reranker is deterministic and cannot recover a model omitted from the candidate pool. The exact
prior and score-fusion formulation is given in Appendix B.4.
4
Experiments
For each test dataset and task, we recommend ten models. We check whether the highest-scoring
model in the available test records is among those ten. We also measure how long it takes to search
the model lake. We repeat the test using three different train/validation/test splits. The two tables
below report results for one of these splits. Appendix C gives more details.
4.1
Evaluation Protocol
Dataset: Evaluation queries and data splits.
The lake is sparse: at least 92% of the 3,016,439
candidate models have no recorded performance pair, and model size is unknown for 72% of
candidates. This sparsity is the central challenge that ModelLakeFishing is designed to address.
Each query names a dataset and a task already in the graph. A dataset root groups related
configurations of one dataset. We divide the data into training, validation, and test groups in three
different ways and keep every configuration of a dataset in the same group. We retrain the model
for each split using the same initialization seed. For a test query, the model can see the dataset,
task, and their metadata, but it cannot see the links that record how models performed on that
dataset. We remove those links in both graph directions and use their scores only to check the
returned list. The task prior also uses no results from the test dataset or its related versions. The
corpus is constructed as follows. The snapshot has 1,008,417 dataset records. We make graph nodes
only for dataset–task combinations with recorded evaluations. After normalizing dataset names,
grouping records by dataset and task, and choosing one metric for each group, we have 18,729
dataset–task nodes. Removing duplicate or conflicting records and limiting records per node leaves
8


247,803 model–dataset performance pairs. Dataset cards match 3,928 nodes (21%). For testing, we
exclude reinforcement-learning tasks and placeholder dataset names, because reinforcement-learning
reward metrics have no consistent orientation, and placeholder names indicate unreliable dataset
provenance. Each test query must have at least three models with recorded scores that are not all
equal. We must also know whether higher or lower is better for the metric. The three different
splits contain 1,476, 1,101, and 1,545 test queries from 730, 495, and 473 dataset roots, respectively.
The splits differ in size because the 70/10/20 edge-proportion target is applied to dataset roots
of varying size, producing unequal test query counts. Appendix B.1 lists the six input sources.
Appendices B.2 and B.3 give the construction and training settings.
Baselines.
We compare three search methods using the same learned vectors and task prior.
The task prior uses a model’s past results on other datasets with the same task. The first method
(Exhaustive) scores and ranks all 3,016,439 models. The second checks similarity to every model
(Exact), keeps the closest 1k, and reranks that smaller set. The third (ModelLakeFishing) uses
the HNSW index to find 1k nearby models and reranks them. Comparing the first two shows the
effect of limiting the candidate set; comparing the last two shows the extra effect of approximate
nearest-neighbour search. LEEP, LogME, NLEEP, and H-score compute a score from the target data
for each candidate. TransferGraph and ModelLens also score each query–candidate pair. However,
these approaches do not scale to the massive data lake we consider here.
Lookup time.
We start the timer after the query vector has been computed. We stop it after
HNSW search, task-prior lookup, combining the scores, and sorting. The time does not include
computing the query vector, loading the index, or sending data over a network. The reported
full-lake scan was timed over a different set of steps, so its time cannot be used to calculate an
online speedup. Appendix C.4 gives the other recorded times and memory measurements.

5
Conclusion
Model lakes containing millions of reusable models present a retrieval challenge that exhaustive
scoring cannot meet. Identifying suitable models for a new dataset requires learning from evidence
that is sparse, heterogeneous, and unevenly distributed across a corpus too large to evaluate
candidate by candidate. ModelLakeFishing addresses this by learning indexable representations
from a model–dataset evidence graph. We combine performance records, model cards, dataset
descriptions, and model lineage into a structured graph. We index embeddings with HNSW so that
retrieval requires no candidate-wise execution at query time.
Evaluated on a lake of 3,016,439 models with a leakage-safe, root-aware protocol across three
dataset partitions, ModelLakeFishing achieves a mean gold@10 of 29.68% — recovering the
observed best model in the top ten for nearly 30% of eligible queries. It retains 93% of the gold@10
achieved by exhaustive scoring, with a median query latency of 0.747ms after query encoding. Nearly
all of the quality gap relative to exhaustive search comes from limiting the candidate pool to 1,000
models; the HNSW approximation itself costs less than 0.1 percentage points of gold@10. The
task-level prior is the dominant reranking signal: removing it drops gold@10 from 33% to 12% on
the seed-0 split, while pool coverage remains unchanged, confirming that the prior improves ranking
within the retrieved set rather than retrieval itself.
These results demonstrate that an ANN-searchable representation space over millions of models
can be learned from relational supervision alone, without executing any candidate model on the
target dataset. The evaluation measures recovery of historically observed models under sparse
supervision; the true best model for a query may be unobserved and unreachable by any retrieval
system operating over recorded evidence alone. Competitors do not scale to the size of graph we
have considered, but a full comparison with methods that score individual query–candidate pairs,
such as TransferGraph and ModelLens, on a matched candidate subset remains an important open
experiment

B.2
Evidence Corpus and Node Features
Construction of the evaluated lake.
The frozen hub snapshot contains 3,003,759 model records
and 1,008,417 dataset records. Historical evaluations contribute 12,680 additional model IDs to
the candidate universe. The parser reads 2,158,375 native metric rows, retains 2,097,081 finite and
parseable rows, and reduces these to 1,435,162 after within-key median deduplication. Across the six
retained evidence sources, the merge starts from 531,958 rows, removes 5,102 within-source duplicates,
resolves 1,502 cross-source conflicts, and applies per-dataset capping. The source breakdown is given
in Table 2; it describes data provenance rather than competing retrieval methods.
Metric and feature processing.
Native evaluation records are grouped by dataset, task, and full
metric name, retaining cutoff distinctions. Invalid numerical values are discarded; repeated model
observations are median-aggregated and min–max normalized within each group, with constant
groups assigned 0.5. Lower-is-better values are oriented as y = 1 −¯v. Each node selects one primary
metric, preferring known direction, then reward, then unknown; observation count and lexical
order break ties. Reward/unknown values (2.03% of retained performance edges) remain numerical
evidence for learning and priors but cannot define evaluation gold. Historical sources retain their
stored orientation: duplicate (source, node, model) records are median-aggregated and normalized
within each (source, node) group. Fixed source priority resolves overlapping model–node pairs, and
deterministic weight-stratified sampling caps each node at 200 observations.
Node inputs combine a frozen 64-dimensional name hash with a 384-dimensional embedding
from all-MiniLM-L6-v2. Model text contains the cleaned repository name, canonical family, and
a parameter-size phrase when known. Dataset text contains its cleaned name and task, matched
card task categories, up to ten non-colon tags, and at most 400 description characters when a card
match is reliable. Dataset nodes append a ten-slot statistics block whose only nonzero coordinate is
the seventh, log(1 + rd), where rd counts frozen dataset–task nodes sharing the same root. Learned
size and family lookups add 16 dimensions each to model inputs, with explicit unknown categories;

task-type, class-count, and arity lookups add 16, 8, and 4 dimensions to dataset inputs. The
resulting input dimensions are 480 and 486.

performance-derived input columns are zeroed in the evaluated configuration. The graph relation
counts appear in Figure 5. For training, each dataset keeps its ten nearest dataset neighbors
from a stored top-20 graph, and those links contribute equally; the stored count reflects the larger

Supplementary Evaluation Details
This section expands the protocol in Section 4.1 and the measurements in Section 4.2. It records
the interpretation of Figure 3; it does not report additional comparison runs or ablations.
C.1
Held-Out Query Eligibility
Eligible dataset–task queries have a known metric direction or a curated oriented source, exclude
reinforcement-learning tasks and placeholder dataset names, and have at least three nonconstant
observed held-out candidate values. The query counts in Section 4.1 are observations across three
root-aware splits; the same node may occur in more than one split. All queried nodes already exist
in the frozen graph, so this is a transductive historical-recovery evaluation, not a test of new-dataset
ingestion.
C.2
Additional Recovery Metrics
Figure 3(d) shows several readouts of the same returned model lists. gold@1 requires the observed
best model to rank first; top3@10 accepts any of the three best observed models among the returned
ten; gold-gap@10 accepts an observed model within 0.01 of the best oriented performance. The
18


root-balanced measure first averages queries within each dataset root and then averages roots. The
median reranked gold position, conditional on gold entering the candidate pool, is 4, 5, and 4
across the splits. The frozen candidate order resolves ties in the observed-best label; the same fixed
model-ID order resolves ties in diagnostic scoring.
C.3
Approximate-Search Calibration
The index uses inner-product search with HNSW construction parameters M
= 32 and
ef_construction=200, using eight construction threads. Search breadth is selected from 1k, 1,500,
2,000, 3,000, and 5,000: the first setting with mean top-1k neighbor-ID recall of at least 0.99 against
exact dense search is retained. This calibration does not read gold labels. The selected ef_search
values for the three splits are 1k, 1,500, and 1k; the corresponding neighbor-ID recall values are
0.9944, 0.9963, and 0.9928. The task-prior tables are built from training and validation roots only;
the test root and its siblings are excluded. This calibration checks search fidelity, not the ranking
benefit of the prior or of graph learning.

The formal evaluation ran on Linux with hnswlib 0.8.0. HNSW search and prior fusion used the

with eight threads; its recorded build interval includes initialization, insertion, and serialization.
