## 摘要
用于最近邻搜索的可导航图要么以增量方式构建——每个插入点搜索一个随构建过程而变化的图，要么在固定基底上批量构建，后者以构建时间为代价换来确定性与并行性。我们测量了这一代价，并找出其来源。通过对经过调优的 Vamana 和 PiPNN 进行插桩，并在一台 64 线程机器上以配对设计重复构建每个系统，我们将构建时间分解为工作量（距离计算次数）与每次计算的成本。让批量构建器的基底在 B 个同步块中发生变化，可以恢复增量构建的反馈回路，同时图仍然保持为（数据、随机种子、参数、B）的函数：八棵采用批量反馈的树可媲美三十二棵冻结树，且构建执行的距离计算量为 Vamana 的 0.88 倍。然而，其实际耗时却是 Vamana 的 1.55 倍，因为变化的基底使每次计算成本更高。进一步推进，我们发现一堵任何基于搜索的构建器都无法跨越的壁垒。它们中的每一个，无论增量还是批量，都以自适应方式计算距离，每次一个依赖性的随机访问，并且在 d≈100 时，在同一台机器上比稠密核低 20–27 倍；当数据驻留于缓存中时，则比稠密核低五到六倍。这一差距并非低维假象：自适应计算的成本为 d^{1.04}，而分块计算为 d^{0.63}，因此该壁垒以 d^{0.4} 增长，并且在 d=960 时是 d=128 时的两倍。PiPNN 构建速度高一个数量级的优势正来自该内核：它对每个点计算的距离数量相同，但以预先固定的稠密块进行计算。我们表明 beam 无法事后批量处理（锁步块的有效密度仅为 2–3%），将该壁垒表述为双上限 roofline，并界定其范围：当距离是黑盒或计算顺序依赖数据时，它就会形成约束。

## Abstract
Navigable graphs for nearest-neighbor search are built either incrementally, each inserted point searching a graph that mutates as construction proceeds, or in batch over a fixed substrate, which buys determinism and parallelism at a price in build time. We measure that price and find where it comes from. Instrumenting a tuned Vamana and PiPNN and building every system repeatedly in a paired design on one 64-thread machine, we separate build time into work (distance evaluations) and cost per evaluation. Letting the batch builder's substrate mutate in $B$ synchronous blocks recovers the feedback loop of incremental construction while the graph stays a function of (data, seed, parameters, $B$): eight trees with batched feedback match thirty-two frozen trees, and the build does $0.88\times$ Vamana's distance work. Yet it takes $1.55\times$ Vamana's wall-clock, because the mutating substrate costs more per evaluation.   Pushing further, we find a wall that no search-based builder crosses. Every one of them, incremental or batched, evaluates distances adaptively, one dependent random access at a time, and runs $20$-$27\times$ below a dense kernel on the same machine at $d \approx 100$, five to six times of it with the data resident in cache. The gap is not a low-dimension artifact: an adaptive evaluation costs $d^{1.04}$ and a blocked one $d^{0.63}$, so the wall grows as $d^{0.4}$ and is twice as high at $d = 960$ as at $d = 128$. PiPNN's order-of-magnitude build advantage is that kernel: it evaluates as many distances per point, but as fixed-in-advance dense blocks. We show the beam cannot be batched after the fact (the useful density of a lockstep block is 2-3%), state the wall as a two-ceiling roofline, and delimit it: it binds whenever the distance is a black box or the evaluation order is data-dependent.
