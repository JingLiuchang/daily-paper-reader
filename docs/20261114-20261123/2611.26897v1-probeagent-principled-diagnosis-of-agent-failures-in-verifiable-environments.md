## 摘要
改进智能体需要发现其失败之处并理解失败原因。智能体在变化的环境中跨多个步骤行动，因此诊断其失败不能仅检查大语言模型（LLM）的最终响应。相同的不成功结果可能源于任务难度，也可能源于智能体在不同任务中重复出现的错误。我们提出 ProbeAgent，一个自动化框架，用于发现智能体失败、检验其提出的原因，并识别共享的失败模式。ProbeAgent 从基准任务出发，构建可执行测试，并利用参考解决方案、自动检查和任务要求审查来验证这些测试。对于每条失败轨迹，它解释错误并构建新任务，在改变周围上下文的同时保留疑似原因。让智能体在这些任务上运行，可检验同一错误是否会再次出现。随后，ProbeAgent 将具有相似原因的失败分组，并生成能够区分其错误的描述。这一过程将单个失败的解释与可执行测试以及共享失败模式的描述连接起来。我们在来自 10 个基准的 22 种智能体配置上评估 ProbeAgent，收集了 1,244 个失败并生成了 536 个失败模式描述。这些描述能够区分宽泛结果（如工作未完成）中的具体错误，包括只规划不行动以及交付文件前停止。在人工评估中，标注者接受了分配给他们的描述中的 90.0%，并正确拒绝了 83.3% 的相似备选描述，这支持了所发现失败模式的准确性和特异性。

## Abstract
Improving agents requires discovering where they fail and understanding why. An agent acts over multiple steps in a changing environment, so diagnosing its failures requires more than inspecting the final response of a large language model (LLM). The same unsuccessful outcome can arise from task difficulty or from an error the agent repeats across tasks. We introduce ProbeAgent, an automated framework that discovers agent failures, tests their proposed causes, and identifies shared failure modes. Starting from benchmark tasks, ProbeAgent builds executable tests and validates them using reference solutions, automated checks, and review of the task requirements. For each failed trajectory, it explains the error and constructs new tasks that preserve the suspected cause while changing the surrounding context. Running the agent on these tasks tests whether the same error recurs. ProbeAgent then groups failures with similar causes and generates descriptions that distinguish their errors. This process connects explanations of individual failures to executable tests and descriptions of shared failure modes. We evaluate ProbeAgent across 22 agent configurations using tasks from 10 benchmarks, collecting 1,244 failures and producing 536 failure-mode descriptions. These descriptions distinguish specific errors within broad outcomes such as incomplete work, including planning without acting and stopping before delivering a file. In human evaluation, annotators accept 90.0% of assigned descriptions and correctly reject 83.3% of similar alternatives, supporting the accuracy and specificity of the discovered failure modes.

# ProbeAgent 论文结构化总结

## 1. 核心问题与研究动机

- **背景**：智能体（LLM + harness）已广泛用于改代码、操作网页、终端任务等真实工作流，但仍大量失败。仅看最终结果（benchmark 分数）无法解释失败原因。
- **核心问题**：同一个失败结果可能来自**任务本身太难**，也可能来自智能体**跨任务重复的行为错误**，二者需要不同的修复方式。现有方法（如 Who&When、AgentRx、AgentDebug）只对已观测轨迹做事后归因，**无法系统性地构造新任务去发现更多失败、也无法把失败组织成共享模式**。
- **目标**：构建一个自动化框架，同时完成三件事——(1) 建立可靠的可执行测试；(2) 区分任务特定困难与可复现的智能体行为；(3) 识别跨任务共享的失败模式并给出可区分描述。

## 2. 方法论

### 2.1 核心思想
将 ProbeLLM 的"主动探测 + 失败模式归纳"思路从单轮 LLM 响应扩展到**多步智能体环境**：用失败解释指导新测试的构造，再用复现结果反过来支撑/否定解释，最后按原因聚类生成失败模式描述。

### 2.2 三个阶段的流程

**阶段一：Establish failures（建立失败）**
- 从 benchmark 种子任务 `t` 构建 **probe** `s = (E, x, g, π*)`：环境、指令、二元 checker、参考解。
- **三重准入验证**：
  - **Executed**：参考解必须通过 `g(π*)=1`，空操作必须失败 `g(nop)=0`；
  - **Read**：检查 checker 源码，排除不可访问/外部断言；
  - **Reviewed**：独立只读 agent 检查捷径、缺失要求、答案泄漏。
  - 准入条件 `Λ(s) = λ_exec · λ_read · λ_review`。
- 运行目标智能体得轨迹 `z`，失败则用 LLM 生成**失败解释** `e = (b, ℓ, τ, δ)`：错误/遗漏动作、发生位置、触发条件、纠正动作。

**阶段二：Test failure recurrence（检验失败复现）**
- 构造 **sibling 任务** `s_j`：保持触发条件 `τ(r)(s_j)=1`，但改变领域、数据、工具、命名、输出格式（如 CSV 分析 → SQL 查询 → Python 脚本，但都要求保存结果）。
- 用 LLM 复现判定器 `H(r, z_{j,t})` 判断同一错误是否重现；每个环境多次 rollout 只计一次，得复现环境数 `ρ`。
- 判定：`ρ/m ≥ 2/3` 且 `m≥3` → **AGENT BEHAVIOR**；`ρ=0` → **TASK-SPECIFIC**；中间 → **WEAK**；`m<3` → **UNVERIFIED**。

**阶段三：Discover failure modes（发现失败模式）**
- **原因相似度**：将 summary、cause、corrective action、trigger、stage 拼成文本嵌入，去均值后归一化，计算中心化余弦相似度。
- **阈值校准**：用 LLM 配对判定器 `J` 标注样本，选 `τ+`（≥0.90 判同）、`τ-`（≥0.98 判异）；中间"模糊带"只对每个失败的 `k_nn=15` 近邻送 `J` 判定，控制调用成本。
- **密度约束分组**：建图后对连通分量检查 `d_in(K) − d_out(K) ≥ μ`；违反则按边权升序拆边直到断开，递归处理。该约束防止链式连接把不同失败合并。
- **生成描述**：对每组 `R`，取最近邻的排除集 `B`，LLM 生成描述 `c`，要求覆盖 `R` 全部、排除 `B` 全部，否则标记 UNRESOLVED。

### 2.3 搜索策略
- 在"探索新种子任务"与"测试 sibling"之间交替：每个新失败标签排队 3 个 sibling 构建；连续 3 次 sibling 后强制探索；探索时选择已准入 probe 最少的任务类别。
- 形式化目标：在测试预算 `B_test` 下最大化有效失败模式数量 `E[|I_θ(D_η)|]`。

## 6. 主要结论与发现

- **能发现多样且细粒度的失败模式**：在 1,244 个失败上生成 536 条描述；在 961 失败集上，固定分类法的最大类别含 264 个失败，而归纳组最大仅 11 个，说明能把"未完成工作"等宽泛结果拆成具体机制（如"规划了调用但从未发出"、"计算完但未交付文件"）。
- **描述准确性较好**：留出一致率 88.5%（μ=0.02）；人工接受率 90.0%，正确拒绝相似替代 83.3%。
- **probe 验证有效**：语义审查发现 565 轮"被奖励的捷径"，以及 323 轮 checker 未评估所需结果、255 轮强加未声明要求——这些是执行检查漏掉的缺陷。
- **sibling 测试能区分复现与任务特定**：119 个被测试解释中，40.3% 任务特定、16.8% 判为智能体行为、21.8% 弱复现、21.0% 证据不足。
- **密度约束关键**：去掉约束后 505 组坍缩为 23 组（最大组含 650/961 失败），留出一致率从 91.8% 降至 78.0%。
- **相关配置共享更多模式**：仅换模型版本或 harness 的 9 对配置中 44.4% 至少共享一个组，其他 181 对仅 14.4%（约 3.1 倍）。
- **匹配重放失败率差异大**：22.2%（Kimi K3）到 94.4%（GPT-5.4-nano），但样本小、区间宽。

## 7. 优点

- **闭环设计巧妙**：把"单条失败解释"转化为"可执行的新测试"，再用复现结果反过来验证解释，形成解释—测试—归纳的闭环，比纯事后归因更有说服力。
- **三重 probe 准入**：执行控制（参考解通过、空操作失败）+ 源码检查 + 独立语义审查，尤其语义审查能发现执行检查无法覆盖的"捷径奖励"问题，实验证据充分（565 轮）。
- **sibling 构造原则清晰**：明确"保持 trigger、改变 context"的可操作定义（Definition 5），并用复现比例给出四档判定，避免把任务难度误判为智能体缺陷。
- **密度约束分组有效**：针对链式合并问题设计组级相似度边际，消融显示一致率提升约 13.8 个百分点，是方法上的实质贡献。
- **成本控制意识**：阈值校准 + 近邻裁剪 + 缓存复用（8,655 个模糊带对中复用 7,150 个），减少 LLM 调用。
- **评估较严谨**：留出评估、盲评人工评估、匹配重放、质量审计多管齐下，并主动报告缺陷率（5% 硬错误、30% 错误或格式歧义）。

## 8. 不足与局限

- **缺乏与现有方法的定量对比**：未在统一数据上比较 AgentDebug、AgentRx、Who&When、MAST 等，难以判断相对增益。
- **LLM-as-judge 依赖过重**：构建、审查、轨迹分析、配对判定、描述生成、留出确认均由同一模型族完成，存在系统性偏差与"自我一致"风险；论文未报告 judge 与人类判断在配对任务上的一致性。
- **统计支撑偏弱**：565 组中 361 组（63.9%）仅含

1 个失败（单例组），组规模分布高度偏斜；大量模式只有单条证据支撑，既难以估计组内一致性，也使"共享失败模式"的统计检验（如配置间共享比例比较）缺乏功效；
- **阈值与超参数多为经验设定**：复现判定阈值 `2/3`、最小环境数 `m≥3`、`k_nn=15`、`μ=0.02` 等虽做了部分扫描，但缺少对判定边界稳定性的系统敏感性分析，不同阈值可能显著改变 AGENT BEHAVIOR 与 TASK-SPECIFIC 的比例（现有 40.3% vs 16.8% 的划分对阈值较敏感）；
- **sibling 构造的效度未独立验证**：论文用 `τ(r)(s_j)=1` 保证"触发条件保持"，但"改变领域/数据/工具"是否真的**不改变任务难度**缺乏独立度量，若 sibling 系统性变难或变易，复现率会被高估或低估；
- **结论的条件性**：所谓 AGENT BEHAVIOR 只是在当前 probe 分布与 sibling 构造策略下的**条件性判定**，换一批种子任务或换 sibling 生成方式，标签可能翻转，论文对此的措辞基本谨慎，但读者易将其误读为模型的固有属性；
- **成本偏高、难以常态化**：单次发现集即消耗 365M 输入 token，加上构建、审查、配对判定的大量 LLM 调用，作为持续集成式的回归诊断工具，运行成本与延迟都难以接受，论文未讨论轻量化替代方案（如小模型蒸馏 judge、缓存复用率进一步提升）；
- **缺少"修复验证"闭环**：论文验证了描述**能否区分**失败，但没有验证"按描述去修 harness/提示后失败率是否真的下降"，从诊断到改进的因果链条仍缺最后一环（matched replay 只是观测失败率差异，不是干预实验）；
- **时效性与可复现性风险**：涉及大量具体模型版本与商业 API，外部研究者难以完全复现；模型升级后结论可能失效，论文未提供版本无关的抽象结论或可复用的最小复现包说明。

## 9. 启示与可迁移价值

- **范式层面**："失败解释 → 构造可执行 probe → sibling 复现检验 → 按原因聚类"这一闭环，可迁移到软件工程 agent、Web agent、科研 agent 等任何有可执行 checker 的领域，是比"事后轨迹归因"更强的方法论框架。
- **评测层面**：三重门控（执行 + 源码 + 语义审查）对 benchmark 构建具有普适价值；尤其"被奖励的捷径"（565 轮）与"checker 未评估所需结果"（323 轮）说明，**仅靠单元测试式的 checker 会系统性高估 agent 能力**，语义审查应成为标准流程。
- **工程层面**：区分 TASK-SPECIFIC 与 AGENT BEHAVIOR 对开发者有直接的优先级意义——前者应改任务/工具，后者应改 harness 或提示；密度约束分组则提示"聚类算法本身需要防链式坍缩"这一通用教训。
- **分析层面**：相关配置（仅换模型版本或 harness）共享更多失败模式（44.4% vs 14.4%）说明失败具有**结构性来源**，而非纯随机，这为"harness 工程"提供了实证依据。

## 10. 总体评价

ProbeAgent 是一篇**方法论贡献大于实证结论**的工作：它把"主动探测"从单轮 LLM 扩展到多步 agent 环境，用可执行 probe 与 sibling 复现把"失败解释"变成可检验的假设，并以密度约束聚类产出细粒度失败模式，思路完整、闭环清晰，probe 准入与消融实验的证据也较扎实。其主要短板在于**缺少与同类方法的定量对比、LLM-as-judge 依赖过重、统计功效不足（大量单例组、样本小、区间宽）以及成本高昂**，因此其结论更适合读作"该框架能产出什么"的可行性证明，而非"各配置优劣"的定论。对关注 agent 可靠性、benchmark 构建与失败归因的研究者与工程团队，本文的**流程设计与门控思想**具有较高参考价值，具体数值结论则应谨慎外推。
