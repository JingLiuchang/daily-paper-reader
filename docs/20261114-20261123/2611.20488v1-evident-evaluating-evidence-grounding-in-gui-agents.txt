EVIDENT: Evaluating Evidence Grounding in GUI Agents
Yerin Nam1*, Minkyung Cho1*
MinKyu Kim1, SeungWoo Song1, Hangyeol Yoo1, Jihyo Kim1, KyungTae Lim1†
1Korea Advanced Institute of Science & Technology
{yerinnam,minkyung.cho,ktlim}@kaist.ac.kr
Abstract
GUI agents are increasingly evaluated by
whether they complete web tasks, but sur-
face success can hide a critical failure: the
final answer may not be supported by evi-
dence observed during navigation. We intro-
duce EVIDENT, an evidence-driven benchmark
for evaluating whether GUI agents ground
their decisions in observable web evidence.
EVIDENT contains 220 real-world English and
Korean tasks spanning semantic grounding,
contextual inference, and visual grounding,
each paired with human-curated evidence meta-
data specifying what must be verified. We
further separate surface task completion from
evidence-grounded success using three met-
rics: TSR, ESR, and GSR, which respectively
measure outcome success, required evidence
observation, and claim-level evidence support.
Experiments on commercial and open-source
GUI agents reveal substantial gaps between
surface success and evidence-grounded success,
especially in contextual and visual tasks. These
results show that current evaluations can over-
estimate agent reliability and highlight the need
to assess not only whether agents answer, but
whether they verify.1

This distinction is central to evaluating the relia-

2025); it cannot replace checking observable evi-
dence such as schedules, prices, reviews, product
specifications, badges, images, or layout cues. In
this sense, web-agent success is not merely a matter
of producing the right-looking answer; it is a matter
of using the web as an external source of evidence
to validate that answer.
This raises the central question of this work:
when a GUI agent appears to complete a web
task, can we verify that its final answer is sup-

web environment, where content changes and the
specific on-screen evidence matters, it is better
understood as a hidden failure (Arman et al., 2026).
To study this problem, we introduce EVIDENT,
an evidence-driven benchmark for GUI-agent eval-
uation. EVIDENT contains 220 real-world user
scenarios in English and Korean. Each task is
paired with human-curated evidence metadata that
specifies what information must be checked to
justify a reliable answer. Rather than evaluating
only whether an agent reaches a final answer,
EVIDENT asks whether the answer can be traced
back to evidence observed along the trajectory.
The core idea of EVIDENT is to separate sur-
face success from evidence-grounded success. We
distinguish whether the final answer appears to
complete the task, whether the agent observed the
necessary evidence during navigation, and whether
the final answer’s core claims are supported by that
evidence. This decomposition allows us to identify
cases where an agent produces a successful-looking
answer while skipping required evidence, or where
it observes relevant evidence but fails to ground its
final claims in it.

agents must reason over implicit user constraints or
non-textual visual cues. These findings suggest that
existing success metrics can substantially overesti-
mate the reliability of GUI agents, and that future
evaluation should measure not only whether agents

Related Work
Prior work on GUI and web agents has expanded
evaluation along three major axes: task comple-
tion in interactive environments, static GUI under-
standing, and trajectory-level behavior assessment.
These directions have substantially advanced agent
evaluation, but they mostly treat the web as an
environment to navigate or a screen to interpret.
In contrast, EVIDENT treats the web as an external
source of evidence: a successful answer should not
only satisfy the user request, but also be traceable to
information the agent observed during navigation.
2.1
Outcome-Oriented Benchmarks for Web
and GUI Agents
Benchmarks for web and computer-use agents
have primarily evaluated whether agents can reach
useful outcomes. Mind2Web studies action pre-
diction from web interaction traces (Deng et al.,
2023), while WebArena and OSWorld evaluate
end-to-end task completion in interactive web or
operating-system environments (Zhou et al., 2024;
Xie et al., 2024). Later benchmarks further expand
coverage to long-tail mobile tasks (Wu et al., 2026),
complex reasoning scenarios (Zheng et al., 2025;


Chen et al., 2026), and robustness under real-world
anomalies (Yang et al., 2026).
These benchmarks provide strong testbeds for
measuring navigation and task completion. How-
ever, outcome-level success alone cannot determine
how the final answer was produced. An agent may
solve a task by correctly interpreting the current
website, but it may output a plausible answer from
parametric knowledge or prior assumptions with-
out checking the necessary on-screen information.
Thus, conventional success rates capture surface
completion, but not whether the answer is grounded
in evidence observed during the trajectory.
2.2
Static GUI Grounding and Webpage
Understanding
A complementary line of work isolates model-level
GUI understanding. GUI grounding benchmarks
like ScreenSpot and SeeClick test whether mod-
els can localize interface elements from textual
instructions (Li et al., 2025; Cheng et al., 2024),
while webpage understanding benchmarks assess
structural and semantic comprehension of visual
web pages (Liu et al., 2024). These tasks capture
important perceptual abilities for web interaction.
However, single-screen understanding does
not guarantee evidence-grounded decision-making
across a multi-step trajectory. A model may identify
a UI element on a screen, yet still fail to gather or
use the evidence needed to justify its final answer.
EVIDENT builds on this line of work but shifts the
target from local screen understanding to whether
evidence observed across a trajectory supports the
agent’s final claims.
2.3
Trajectory-Level Evaluation
Since final success rates can hide intermediate
failures, recent work has turned to trajectory-level
evaluation. WebVoyager, AgentRewardBench, and
Mind2Web 2 use LLM-as-a-Judge or agent-as-a-
judge frameworks to assess the quality of web-
agent trajectories (He et al., 2024; Lù et al., 2025;
Gou et al., 2025), while process reward benchmarks
evaluate step-level execution correctness (Lin et al.,
2025). These methods move beyond binary out-
comes by asking whether an agent’s path is reason-
able or consistent with the task. This is a different
question from ours: trajectory judges ask whether
the path the agent took was plausible, whereas
EVIDENT asks whether the content of the final
answer is actually present in what the agent saw
on screen. A trajectory may look plausible, yet end
in an unverified claim, and a reasonable-looking
answer may have been reconstructed from prior
knowledge rather than from the page.
Yet trajectory quality and answer grounding are
distinct. A trajectory may visit a relevant page
without observing the specific evidence required for
the final answer; conversely, an agent may observe
relevant information but fail to connect it to its final
claims. Prior work has also reported investigative
hallucination, where agents claim to have discov-
ered information they never accessed (Arman et al.,
2026). EVIDENT targets this gap by evaluating
whether agents observed the required evidence and
whether the final answer is supported by it.
2.4
Observable Evidence Grounding
Benchmarks on underspecified or ambiguous user
requests often focus on whether agents can infer,
clarify, or align with user intent (Sun et al., 2026;
Xu et al., 2026). We study a complementary failure
mode: an agent may appear to complete the task
while silently bridging the gap between user intent
and website information using internal knowledge
rather than observable evidence.
We formalize this missing dimension as observ-
able evidence grounding. The key question is not
only whether the final answer is useful, but whether
it can be traced back to evidence actually observed
during navigation. To operationalize this, EVIDENT
pairs real-world tasks with human-curated evidence
checks and separates surface completion from
evidence observation and claim-level evidence
support. This lets us reveal hidden failures that
outcome-oriented, static grounding, or trajectory-
level evaluations might count as successful.

3.1
Overview
EVIDENT is designed to evaluate whether a GUI
agent’s final answer is supported by evidence actu-
ally observed during web navigation. Given a user
query, trajectory, and a final answer, our goal is
not only to determine whether the task appears
completed, but also whether the answer can be
traced back to evidence available on the visited
screens.
This requires addressing two challenges. First,
real-world user requests often contain a gap
between what the user says and what the website
explicitly provides. Second, the evaluation must

3.2
Task Taxonomy
We construct tasks around three recurring gaps
between user intent and website information.
Semantic Grounding.
The user’s everyday
expression does not directly match the website’s UI
labels or domain-specific terminology. The agent
must map the user’s intent to the appropriate site-
specific category, filter, label, or textual cue.
Contextual Inference.
Contextual Inference
requires identifying constraints implied by the
user’s situation. The agent must infer these con-
straints and verify them on the website, beyond
matching the user’s wording to website terminol-
ogy. For example, a request for “compact furniture
for occasional guests” (Appendix K) implicitly
requires identifying a piece that doubles as a sleep-
ing option without dominating a small room.
Visual Grounding.
The target cannot be identi-
fied solely through explicit text. The agent must use
visual cues such as icons, badges, images, colors,
spatial layout, or product appearance to select or
justify the answer.
These categories capture three common forms
of evidence gap in real-world tasks: semantic
mismatch, implicit constraint inference, and non-
textual visual evidence.

3.3
Human-Curated Evidence Metadata
To evaluate evidence grounding, we must know
what evidence an agent should have checked. For
each task, we therefore provide human-curated evi-
dence metadata: a set of evidence checks specifying
the observable information required to justify a
reliable answer.
Evidence metadata specifies what the agent must
observe to support its answer. For example, a
request for compact furniture for occasional guests
may require evidence that an item can serve as a
sleeping option, fits a small space, and has suit-
able dimensions. Different items can satisfy these
requirements, provided that the agent observes the
relevant website evidence. Appendix D describes
the annotation criteria, examples, and review pro-
cedure.
Checking annotation consistency.
The evidence
requirements should reflect what is needed to
answer the user’s request, rather than an individ-
ual annotator’s preferences. To assess their repro-
ducibility, we ask two annotators to independently
write evidence-check sets for 50 randomly sam-
pled tasks without seeing the original metadata.
A third annotator compares the sets for semantic
equivalence. Agreement is assessed over complete
requirement sets, rather than individual checks.
The independently authored requirements agree


on 48 of 50 tasks (96%). This result shows that
different annotators can reproduce the evidence
requirements from the task descriptions and shared
guidelines.
To assess whether the metadata satisfies the anno-
tation principles, the third annotator examines the
existing checks for the same 50 tasks. Each require-
ment must be observable in the website evidence,
necessary to justify an answer, and independent
of a particular answer or navigation path. The
metadata satisfies these criteria on 49 of 50 tasks
(98%). Together with the agreement between inde-
pendent annotations, this result supports the use of
human-authored evidence checks as reproducible
criteria underlying ESR and GSR. Section 4.2
separately assesses human–judge agreement, and
Appendix D.3 details the annotation procedure.
Alternative evidence paths.
The annotation cri-
teria distinguish the information needed to answer
a request from the actions used to obtain it. For a
request about a protection plan, checks can require
the plan’s name, price, accident coverage, and war-
ranty terms without prescribing a particular page or
sequence of clicks. Different plans and navigation
routes can satisfy these requirements. The checks
specify the information required to support an
answer while allowing different navigation paths.
A recommendation can differ from an annotator’s
preferred choice and still satisfy the requirements
when the observed website evidence supports the
user’s constraints.
3.4
Evidence-Aware Evaluation
Directly judging long multimodal trajectories is
difficult: trajectories can contain many screenshots,
actions, and intermediate observations, and asking
a judge model to reason over all of them at once
can introduce omissions or hallucinated evidence.
We therefore use a three-step evidence-aware eval-
uation pipeline.
First, the judge extracts observable evidence
from trajectory screenshots, including visible text
and relevant non-textual cues. Second, it maps
both the agent’s final-answer claims and the task’s
evidence metadata to the extracted evidence items.
Third, it verifies whether the mapped evidence
explicitly supports the required checks and final
claims. The evidence checks specify informa-
tion that must be verified on the website. The
judge therefore uses evidence from the trajectory
screenshots, rather than parametric knowledge, to
determine whether these checks are satisfied (see
Appendix F for an example). This pipeline sepa-
rates three questions often conflated in outcome-
based evaluation: whether the answer appears use-
ful, whether the necessary evidence was observed,
and whether the final claims are supported by it.
On the strictness of evidence grounding.
Evi-
dence grounding measures verification separately
from answer correctness. A correct but unver-
ified answer can achieve task success without
evidence success or grounded success. Our tasks
require time-sensitive or website-specific infor-
mation, including prices, availability, and visual
attributes, which parametric knowledge alone can-
not verify at execution time. ESR and GSR measure
whether the required evidence is observed and
supports the answer.

4
Experiments
4.1
Experimental Setup
Benchmark scope.
The benchmark contains 220
tasks across eight domains and 31 subcategories,
with 70 English and 150 Korean tasks. The lan-
guage subsets use different websites and are not a
matched test of language ability. We report them
separately to examine whether evidence-grounding
failures recur across these settings.
We test whether EVIDENT reveals hidden fail-
ures that outcome-oriented evaluation would over-
look. We compare closed-source and open-source
GUI agents in a unified browser pipeline. Each
agent starts from a specified URL, autonomously
interacts with the target website, and produces a
final answer to the user query. For each task, we log
the trajectory as a sequence of screenshots, actions,
and intermediate observations. We cap execution
at 50 interaction steps to prevent infinite loops.
Completed trajectories are scored using the
evidence-aware framework defined in Section 3.
The judge does not revisit the live website; it
only uses screenshots captured during the original
agent trajectory as static evidence. This design
avoids inconsistencies from dynamic web content
and ensures that all judgments are based on the
evidence actually available to the agent at execution
time. We use Qwen3-VL-235B as the main judge.
Reproducibility.
Recorded
screenshots
and
actions preserve the evidence available in each
trajectory, allowing judgments to be inspected and
recomputed without revisiting the site.
4.2
Agreement with Human Judgments
To validate the reliability of this automatic eval-
uation, we compare judge labels against human
annotations on a stratified subset of 126 trajectories
covering both languages and all three task types. As
shown in Table 3, the main judge reaches 91.27%
agreement with human labels (κ = 0.864), and
the average over three judge models is 90.48%
(κ = 0.851). Most disagreements occur at the
evidence success and grounded success criteria for
visual grounding, while outcome-level decisions
are nearly always consistent. Additional imple-
mentation details, model configurations, and judge-
robustness analyses are provided in Appendix A
and C.1.
Evidence
extraction.
Our
extraction
step
improves the judge’s agreement with human
judgments compared with using screenshots
directly. With the judge model and evaluated
trajectories held fixed, agreement ranges from 89%
to 97% with extracted evidence, compared with
58% to 72% with raw-image inputs (Table 4). The
improvement holds across all trajectory-length
groups, supporting our choice to extract evidence
before judging agent trajectories. Appendix F.1
describes the input settings.
Sources of disagreement.
Appendix I distin-
guishes extraction errors from differences in evi-
dence interpretation. In Figure 19, the product
photo supports the answer, but its visual details
are absent from the extracted catalog. Later stages
therefore lack the information needed to verify
those claims. In Figure 20, the human annotator
and GPT accept the answer based on search results,
while Qwen and Gemini require the city’s alerts
page. The first error concerns what the extractor
records, while the second concerns what evidence
the judge accepts.
4.3
Main Results: Surface Success
Overestimates Reliability
Table 2 reports TSR, ESR, and GSR across English
and Korean. Commercial agents substantially out-
perform open-source agents in both languages.
Gemini CUA achieves the highest GSR in both
English (55.71%) and Korean (45.33%).
However, the more important pattern is the
consistent gap between TSR and the evidence-
grounded metrics. For example, GPT CUA
achieves an English TSR of 70.00%, but its GSR
drops to 51.43% once we require the final claims to
be supported by observed evidence. Gemini CUA
shows an even larger gap: its English TSR reaches
87.14%, whereas its GSR is only 55.71%. In other
words, many answers that appear successful under
outcome-level evaluation no longer count as suc-
cessful when we require evidence observation and
claim-level grounding.
These results support EVIDENT’s central motiva-
tion. Outcome-level success can measure whether
an agent produces a useful-looking final answer,
but it cannot determine whether the answer is
justified by evidence observed on the website.

6
Conclusion
We introduced
EVIDENT, an evidence-driven
benchmark for evaluating whether GUI agents
ground their final answers in evidence they observe
during web navigation. Unlike outcome-oriented
evaluation, EVIDENT separates surface task com-
pletion from evidence observation and claim-level
grounding through TSR, ESR, and GSR. Our exper-
iments show that current GUI agents often achieve
high surface success while failing to verify the
evidence needed to support their answers. This
gap is especially large in contextual and visual
grounding tasks, where agents must infer implicit
constraints or use non-textual cues. These findings
motivate improvements in evidence collection and
claim verification alongside navigation.


Limitations
This work has several limitations. First, EVIDENT
covers English and Korean web tasks, with a larger
Korean subset. This design allows us to stress-test
evidence grounding in a non-English web environ-
ment that is less represented in existing GUI-agent
benchmarks, but it should not be interpreted as
a population-level comparison between English
and Korean web use. The two subsets may differ
in website conventions, layout density, and task
ecology. We therefore report results separately by
language and treat cross-language differences as
diagnostic rather than as controlled estimates of
language difficulty.
Second, EVIDENT is built on real-world web-
sites. This improves ecological validity, but it also
limits reproducibility because website content, lay-
outs, prices, schedules, and availability can change
over time. Our evaluation addresses this by judging
agents only against screenshots captured during
their original trajectories, rather than revisiting
the live website. As a result, EVIDENT evaluates
whether an agent grounded its answer in the evi-
dence it actually observed at execution time, but it
does not provide a permanently fixed snapshot of
each website.
Third, the evidence metadata is human-curated.
This is necessary for evaluating whether an answer
depends on task-relevant evidence rather than
merely matching a final string, but it also means
that the benchmark reflects annotator decisions
about which evidence checks are necessary. Some
tasks may allow alternative valid evidence paths
that are not fully captured by the current metadata.
Future versions could improve coverage by collect-
ing multiple independent annotations or explicitly
marking optional evidence checks.
Fourth, our evaluation relies on an LLM-based
judge for long multimodal trajectories. We reduce
this risk through a structured extraction–mapping–
judgment pipeline and validate the judge against
human annotations, but automatic judging can
still miss subtle visual cues, extract incomplete
evidence, or draw boundaries differently from
humans when deciding whether a claim is explicitly
supported. This limitation is especially relevant for
visual grounding tasks, where the relevant evidence
may be carried by images, icons, or layout rather
than text.
Finally, EVIDENT adopts a conservative defini-
tion of observable evidence grounding. This choice
is intentional: the benchmark is designed to reveal
cases where agents answer plausibly without ver-
ifying the website evidence their answers depend
on. However, this strict criterion may under-credit
answers that combine observed evidence with
reasonable commonsense inference. The result-
ing scores should therefore be read as diagnostic
measures of evidence-grounded behavior, not as a
complete measure of user satisfaction or practical
task usefulness.

A
Computer-Use Agents (CUAs)
A.1
CUA
A Computer-Use Agent (CUA) is a multimodal
agent that manipulates Graphical User Interfaces
(GUIs), such as web browsers or operating-system
screens, based on natural language instructions
from the user. A CUA observes the current screen,
selects the next action to take toward a given goal,
and then receives the updated screen as input to
determine its subsequent action. In other words,
a CUA accomplishes tasks through a repeated
interaction loop of observing the screen, generating
an action, executing it in the environment, and
updating the state.
A general vision-language model (VLM) can
accept images or screens as input and produce
descriptions, answer questions, perform OCR, and
perform visual reasoning. However, to be used in
a Web GUI environment, the model must also be
capable of outputting actions that can be executed
in a browser. Therefore, a model used in a Web
GUI CUA must be able to recognize elements
within the screen, bridge user instructions with the
current screen state, and generate actions, such as
clicking, typing, scrolling, navigating to a page,
selecting options, and producing a final answer, in
a predefined format.
The CUA system in this work consists of an
execution framework that connects the model to
the browser environment. At each step, the system
provides the model with the user query, a screen-
shot of the current screen, a textual observation, and
the history of previous actions. The model outputs
the next action to perform, and the system applies
it to a Playwright-based browser environment. The
system then records the updated screenshot and
metadata, which are used as the observation for
the next step. This process repeats until the model
produces a final answer or the task meets its termi-
nation condition.
In this work, all models are evaluated using
the same CUA execution pipeline based on Mol-
moWeb. Every model runs under identical settings
for the browser environment, observation format,
action schema, trajectory logging pipeline, and
termination rules. The only adjustments per model
are the tokenizer, image preprocessing, and output
parsing, adapted to match each model’s input and
output format.

D
Additional Details of EVIDENT
Construction
Appendix D provides additional details on task
collection and evidence metadata annotation. The
full judge prompts are provided in Appendix E.
D.1
Task Collection and Taxonomy
Assignment
We constructed EVIDENT from real-world user sce-
narios that require agents to bridge a gap between
user intent and website information. Each task
consists of a user query, a start URL, a task cat-
egory, and human-curated evidence metadata. We
assign each task to one of three categories: Seman-
tic Grounding, Contextual Inference, or Visual
Grounding.
Semantic Grounding tasks require mapping
everyday user expressions to website-specific
labels or terminology. Contextual Inference tasks
require inferring implicit constraints from the user
context and verifying them against website infor-
mation. Visual Grounding tasks require identifying
targets through non-textual cues such as icons,
badges, images, colors, or spatial layout.
When a task involved multiple types of gaps,
annotators assigned the primary category according
to the evidence most central to justifying the final
answer. For example, if a task required both inter-
preting a user’s preference and checking a visual
badge, annotators labeled it as Visual Grounding
when the visual cue was necessary to select the
final target.
D.2
Evidence Metadata Annotation
For each task, annotators created evidence meta-
data specifying the evidence that must be observed
to justify a reliable answer. Evidence metadata was
designed as a checklist of observable facts rather
than as a single gold answer. This allows different
valid final answers, as long as they are supported
by the required evidence.
Each evidence check was written to satisfy three
criteria:
1. Observability: the evidence must be verifi-
able from the website screen or trajectory
screenshots.
2. Necessity: the evidence must be necessary to
justify the final answer for the user query.
3. Answer-independence: the evidence check
should not force a specific wording of the
final answer, but should specify what must
be checked.
For example, for a task asking the agent to find
compact furniture for occasional guests in a small
apartment, the evidence metadata may require
checking that the item can serve as a sleeping
option, that it is suitable for small-space use, and
that visible product details such as dimensions or
functional descriptions were inspected.

## Annotator Guidelines: Writing Evidence Checks for GUI Agents
**Core Principle**
Focus on what information was verified. The evidence_checks define the critical pieces of information that
must be logically verified from the screenshot OCR data before the final answer.
---
### 1. Flexible Target Identification
Do not force a single rigid UI path. The check should evaluate whether the correct type of information or
candidate was found, regardless of the exact navigation path used.
| | Example |
|---|---|
| Bad | The search bar was used to search for 'sofa bed'. |
| Good | A compact furniture option suitable for sleeping was identified. |
---
### 2. Structured 3-Step Flow
Keep evidence_checks concise, typically around three items, following the logical flow of the task.
| Step | Name | Meaning |
|---|---|---|
| 1 | Intent Mapping | The ambiguous user request was translated into an appropriate constraint. |
| 2 | Target Identification | A valid candidate matching the required category or scenario was identified. |
| 3 | Condition Verification | The domain-relevant conditions necessary for the final judgment - such as
date/time, cost, eligibility, policy, rating, or availability - were verified. |
---
### 3. Indispensability Test
Ask whether the final answer would be a lucky guess if this specific fact had not been verified. If yes,
include it. If the condition is trivial or not necessary for the task goal, leave it out.
> **Example:** If the user asks for yoga clothes with sweat absorption and stretch, then material features
related to sweat absorption and stretch should be included as evidence checks.
---

E
Evidence-Aware Judge Pipeline
The judge model scores a completed agent tra-
jectory (it does not run the agent). It proceeds in
three steps: extracting observable evidence, map-
ping the answer’s claims and the human evidence
checks onto it, and checking evidence support
and assigning scores. The pipeline produces TSR,
ESR, and GSR together with a final label for each
trajectory. We detail each step below and illustrate
the evaluation process in Appendix F.
E.1
Step 1: Observable Evidence Extraction
In the first step, the judge model receives trajectory
screenshots and extracts observable evidence. The
output includes visible text, UI labels, buttons,
filters, list items, prices, ratings, dates, and other
screen-level information. For visual grounding
tasks, the judge also records non-textual cues
such as icons, badges, image content, color cues,
selected states, and layout positions.
This step is intentionally restricted to evi-
dence extraction. The judge is not allowed to
decide task success, compare the trajectory to the
final answer, or infer hidden information. Agent
thoughts are not treated as admissible evidence
unless the corresponding information is visible
on the screen. Appendix F (Step 1) shows the
evidence_catalog this produces for an example
trajectory.
E.2
Step 2: Claim–Evidence and
Metadata–Evidence Mapping
In the second step, the judge receives the extracted
evidence items, the agent’s final answer, and the
task’s evidence metadata. It decomposes the final
answer into core claims and maps each claim to
the evidence items that may support it. It also maps
each evidence metadata check to evidence items
observed in the trajectory.
The output of this step is a candidate alignment
between claims, required evidence checks, and
observed evidence. This alignment is not treated as
the final judgment; it is re-examined in Step 3.
E.3
Step 3: Rubric Judgment
In the third step, the judge verifies whether the
mapped evidence explicitly supports the required
evidence checks and final-answer claims. The
judge may only use information contained in the
extracted evidence items. It must not rely on
commonsense knowledge, assumptions about the
website, or the model’s parametric knowledge.
The final rubric contains three common dimen-
sions:
• Intent Grounding: whether the agent cor-
rectly understood the user’s core goal.
• Evidence Grounding: whether the agent’s
output is explicitly supported by observed
website evidence.
• Response Completion: whether the final
response completes the user’s request.
Task-type-specific
criteria
are
additionally
applied. Semantic Grounding checks whether the
user’s expression is mapped to the appropriate
UI label or site-specific terminology. Contextual
Inference checks whether implicit constraints are
correctly inferred and verified. Visual Grounding
checks whether non-textual cues are correctly inter-
preted and used to select or justify the target. The
rubric criteria are diagnostic and do not affect
the success metrics. Appendix F applies the three
steps to a Coursera task, showing how the evidence
checks and claims are evaluated and how the final
label is assigned.

Interpretation.
Under conventional outcome-
based scoring, this trajectory is a success: the agent
named a real, well-suited certificate, and the answer
reads as a thorough, helpful recommendation. Yet
the agent did not analyze the website. It idled for
two steps and then reconstructed the entire recom-
mendation from parametric knowledge. EVIDENT
localizes the failure precisely: the gap opens at
the evidence-observation stage (TSR−ESR), not
merely at claim grounding. This is the Hallucinated
Success region of Figure 4 and the Hallucinated
Success pattern discussed in Section 5: it is one
of the two hidden-failure modes EVIDENT sepa-
rates from genuine success, the other being Claim-
Ungrounded Success, where relevant evidence is
observed but the final claims remain ungrounded.
In a live setting, the very property the user cares
about (whether the program truly starts from the
basics) was never checked, so treating this as a
clean success would overstate the agent’s reliabil-
ity.
F.1
Visual Evidence Extraction Validation
Our evaluation pipeline consists of three stages.
First, a vision-language model extracts observ-
able evidence from each screenshot into structured
text. Next, the judge identifies the factual claims
in the agent’s final answer and verifies whether
each claim is supported by the extracted evidence
and satisfies the required evidence metadata (Sec-
tion 3.4).
We adopt this design because directly judging
long trajectories from raw screenshots is difficult
in practice. A judge processing all screenshots
simultaneously must either downsample images,
losing fine-grained visual details, or process screen-
shots in small windows, losing long-range context.
By extracting evidence from each screenshot indi-
vidually, later judgment operates on a complete
textual representation of the entire trajectory while
preserving visual details such as icons, badges,
colors, layouts, and product-image contents.
To evaluate this design, we compared our
extraction-based pipeline with three alternatives
that directly consume raw screenshots. We evalu-
ated all methods against the same human annota-
tions used in Appendix G, while keeping the judge
model (Qwen3-VL-235B) and agent trajectories
fixed. Only the judge input differed.
As shown in Table 4, our method consistently
achieves high agreement with human judgments
(89–97%) across all trajectory lengths, whereas
raw-image approaches perform substantially worse,
especially for longer trajectories. Structured evi-
dence extraction produces closer agreement with
human judgments than direct evaluation of screen-
shot sequences.
Nevertheless, the overall evaluation remains
bounded by the quality of the evidence extraction
stage. If a relevant visual cue is omitted during
extraction, a grounded answer may still be judged
as unsupported. Improving coverage of visual evi-
dence, including alternative evidence representa-
tions and richer visual element extraction, remains
an important direction for future work.

Detailed Scoring Criteria for Task
Difficulty
Tasks are assigned difficulty levels using a simple
quantitative heuristic based on constraint depth and
normalized instruction length. Starting from a base
score of 1, the total score directly determines the
final difficulty level: Level 1 (Low, 1 pt), Level 2
(Moderate, 2 pts), and Level 3 (High, 3 pts).
1. Constraint Satisfaction Depth (0–1 pt): We
measure the number of independent evalua-
tion conditions (N) an agent must satisfy to
complete the task. Tasks receive +1 point if
N ≥4, and 0 points otherwise.
2. Information Density (0–1 pt): We use
instruction length (L in characters) as a proxy
for linguistic and instruction complexity, as
longer prompts encapsulate highly specific
constraints and contextual backgrounds. To
normalize character-level information density
across languages, a 2.2× character multiplier
is applied to Korean prompts to match English
densities. Tasks receive +1 point if L > 170,
and 0 points otherwise.

each of the three task types defined in our bench-
mark: Semantic Grounding, Contextual Inference,
and Visual Grounding. For each task type, we
present one English and one Korean example,
detailing the user’s prompt, the underlying user
intent, and the explicit evidence checks used by the
human annotators to verify the task’s completion.
Korean examples show the original text in gray and
the English translation in black.

Contextual Inference
English
Task ID: ikea_small_apartment_guest_sleeping
Prompt: My apartment is tiny, but my cousin sometimes sleeps over. On IKEA, find a furniture option that can help with
occasional guests without taking over the room.
User Intent: The user wants a space-saving furniture solution for occasional overnight guests in a small apartment.
Evidence Checks:
• A suitable compact guest-sleeping furniture type was inferred and identified.
• The product page confirmed the item can function as a sleeping option without dominating the room during everyday
use.
• The recommendation considered visible product details (name, price, dimensions, functional description, or small-
space suitability).

Semantic Grounding
English
Task ID: weather_warning_board_alerts_synonym
Prompt: On the National Weather Service site, show me whether there is any storm warning board active around Oklahoma
City right now.
User Intent: The user says “storm warning board”, which should be mapped to weather alerts, warnings, watches, or
advisories.
Evidence Checks:
• Confirming that the Oklahoma City page, or a nearby-area weather page, was consulted on the NWS screen.
• Does the screen link the user’s phrase “storm warning board” to the alerts/warnings/watches/advisories UI?
• The screen’s confirmation of whether any warnings/advisories are active right now, or whether none are present.

Visual Grounding
English
Task ID: ebay_authenticity_badge_sneakers_varied
Prompt: I’m browsing for Nike Dunk sneakers on eBay, but I only trust the listings with the little authenticity guarantee
mark. Pick one where that badge is actually visible.
User Intent: The user wants a sneaker listing with a visible authenticity-protection marker, not just a normal listing.
Visual Target: Authenticity Guarantee badge/checkmark.
Evidence Checks:
• Confirming that the eBay screen showed Nike Dunk-related search results or a product detail page.
• Visual confirmation of an Authenticity Guarantee badge or checkmark on the product card or detail view.
• It was not inferred from the product name, brand, or price alone that the listing had authenticity-guarantee status.
