Abstract —Execution traces help diagnose AI-agent failures, but sharing them can expose customer identities. For example, detecting that an agent handled the wrong customer’s records requires knowing whether the records belong to the requested customer, but not necessarily knowing who that customer is. Our executable benchmark measures what a trace export reveals and whether a proposed repair restores the correct output in synthetic multi-tenant workflows. Conventional redaction can remove evidence needed for repair while leaving encoded iden-tifiers recoverable. Two exports preserve ownership comparisons by reporting the match as a comparison fact or by using pseudonyms consistent within each execution. Both preserve the original diagnostic program’s repairs. The tested identifier matchers identify no requested customer from either export. An independently written program produces correct outputs on 39 of 42 faulty cases with comparison facts and on all 42 with execution-scoped pseudonyms. Row counts still expose identities. With prior knowledge of customers’ row counts, an attacker uniquely identifies the requested customer in 97 of 240 executions under each of the 15 export policies. Removing selected counters from the comparison-fact export stops this attack and preserves the original program’s repairs. The benchmark lets engineers test what their diagnostic program can repair and what an attacker can still infer from the same export. 

Index Terms —AI agents, execution traces, data minimization, re-identification, fault diagnosis 

I. INTRODUCTION When an AI agent on shared data infrastructure returns the wrong customer’s records, an engineer must decide how much of its execution trace to share for diagnosis. The recipient needs to compare the request with the records to diagnose the ownership error. Sharing both enables that comparison but exposes identities. Deleting customer strings can remove the comparison and still leave an encoded identifier in a notification or tool argument. Engineers need to know what the recipient can fix and what an attacker can infer. Even a correct diagnosis can lead to an edit that leaves the output wrong. We measure disclosure and check the output after running the proposed repair. Existing work studies agent leakage and sanitization costs [1], retained audit information [2] and diagnostic teleme-try [3], [4]. OpenTelemetry warns of personal data in captured inputs and outputs [5]. Personally identifiable information

A. Roles, Outputs and Evidence 

The diagnostic program sees the export and a public list of allowed operations. It may choose at most two configuration operations at one stage. With an edit, the executor reruns the entire workflow on the copy. Without an edit, the original output is scored. The benchmark seals the decision before scoring the result against a private reference output. 

Task success means that the actual output passes the refer-ence scorer. Recovery means that an initially failing workspace becomes correct. These denominators differ because some injected faults leave the original output correct. We also distin-guish structural evidence, such as scan and write settings, value evidence, such as amount changes, and ownership evidence, such as whether records belong to the requested customer. Three author-constructed workloads use synthetic identities and faults with real file, SQLite and CSV operations. The 

file workflow parses CSV and delivers JSONL with a check-summed manifest. The reconciliation workflow imports rows, reconciles customer totals and exports CSV. The aggregation workflow reads partitioned transactions, joins a dimension table, aggregates decimal amounts and writes a report. Scoring checks canonical records and ownership, reconciliation source-table row counts, and file/aggregation source or input hashes. Each workflow has seven fault families, with two variants per family: adapter settings, stale bindings, incomplete scans, wrong write mode, changed values, wrong customer and cross-customer contamination. B. Exports and Diagnostic Programs 

Table II groups the 15 policies by what the diagnostic program receives and maps descriptive names to the frozen artifact identifiers. All full-metadata policies retain baseline measurements, statistics and relations. Measurements include counts, excep-tions, scan arguments, digests and reference equality. Statistics describe key multiplicity and string-length buckets. Relations describe cardinality order and key coverage. Two metadata-only ablations remove relations, then statistics. Raw retains requests, records, tool calls and byte snap-shots. Regex applies five frozen patterns for e-mail, 32-hex keys, phone, SSN and API keys, including decoded base64 byte fields. Schema removes owner_id , owner_email ,

billing_id , note and byte blobs. Typed projection retains stage summaries of counts, status, scan, write mode, reference equality and key multiplicity. The metadata-only export retains the measurements, statistics and relations described above. The post-hoc scrubber baselines use default Scrubadub [7] detectors and Presidio [6] recognizers. Comparison facts add content without fault labels. At each stage they report whether owners match the request (all, some, none, unknown or not applicable), distinct-owner count, a Boolean predicate for whether all amounts are whole dollars, and negative-amount count. Stage-pair edges retain endpoints, report whether transaction counts agree, and classify amount sums as equal, negated, scaled by 100, less or greater. Unavail-able amount comparisons are null. This added fact content omits raw sums and transaction counts but retains owner and negative-amount counts. Baseline metadata still retains counts, including the filtered row count used by the volume attacker. Optional owner tokens use a hash-based message authentication code with a split/run key or an execution-handle key that attackers do not receive. The encoding-aware pseudonym policies transform the orig-inal content. They map complete owner identifiers and e-mails consistently across all four notification forms and decoded payloads, with an analysis-run key or an execution-handle key. Both retain baseline metadata, original snapshot counts/digests and transformed-payload metadata. In contrast, dictionary sub-stitution does not consistently canonicalize notifications, and the fact-token variants add owner tokens to facts rather than retaining transformed records. Scrubadub, Presidio, dictionary substitution and both pseudonym scopes are the five post-hoc comparators, evaluated on the same executions. The rule-based program first checks ownership, then meta-data, then values. It derives comparisons from visible content or reads exported facts. Equal counts with unequal sums trigger sign, scale or rounding edits. For the file workflow’s source-row sum, it needs the visible requested owner to select records. Missing evidence is unknown. It ignores distinct-owner and negative-amount counts. Because this diagnostic program and the facts share a family-selected vocabulary, agreement alone is an incomplete test of usefulness. The independent constraint-based program tests whether another decision procedure can still repair (Sec. IV-B). 

C. Disclosure Endpoints 

Identifier matching ranks the 32 catalog candidates. Basic matching searches raw, lower-case, URL, URL-plus, base64 and hex forms plus length buckets. Normalized matching adds Unicode compatibility normalization, case, whitespace and at/dot handling. It credits full atoms, e-mail local parts and 12-character identifier fragments. Unique identification requires the requested target alone to score highest. Direct exposure 

requires a score of at least 10, reached by full identifier/e-mail matches regardless of ties. Fragment and shape matches rank candidates below that threshold. Thus exposed neighbors can reduce raw unique identification by creating ties. Target and neighbor exposure are scored separately. Uniform catalog guessing has reference probability 1/32 , or 1/3 among the three row owners. Linkage asks whether two traces share a customer and input cell. Generic linkage uses Jaccard similarity after re-moving near-universal strings in each same-policy batch. Identifier-aware linkage uses one frozen identifier-shape gram-mar on content and baseline metadata, including eligible orig-inal/transformed digests but excluding auxiliary-only strings and other token forms. A separate post-hoc dictionary-token extractor admits tok: strings. The area under the receiver operating characteristic curve (AUC) measures separation of positive same-cell and negative different-cell pairs within each workflow. Shared inputs make this customer/input linkage rather than isolated identity linkage. Known-volume matching compares the number of rows selected by the customer filter, before any scan limit or offset, with each catalog customer’s known row count. The export records this count as rows_in . Its auxiliary information associates each candidate identity with a count, including the three row owners and zero-volume decoys. It succeeds only if the requested target is the sole count match. This endpoint tests a metadata channel beyond string matching. 

D. Cohorts and Protocol 

The main scripted study uses disjoint seeds for 576 devel-opment, 48 validation and 240 final executions, comprising 210 faults and 30 clean cases. Ten original policies produce 2,400 final views. A master secret derives identities, forms and tokens and is released after scoring. Diagnosis and matching attacks use public views without target labels. A post-hoc replay scores retained final inputs under all 15 policies and a selected-counter fact ablation, with oracle/no-op controls. Identical execution/plan pairs share scored outputs. The independent diagnostic program uses a separate 48-case cohort. A primary 144-execution language-model cohort and a separate post-hoc 144-execution cohort test generated traces and interaction exposure. Counts describe finite cohorts, with shared cells limiting population inference. Artifact documen-tation preserves the full per-policy results. IV. REPAIR AND REMAINING DISCLOSURE 

A. Why Redaction Can Lose Evidence and Still Disclose 

Most structural diagnosis survives in metadata, but own-ership and some value diagnosis require content compar-isons. The metadata-only rules make identical decisions across the eight original policies with full metadata (0/240 dis-agreements). They detect 115/120 structural faults, falling to 110/120 without relations and 75/120 with measurements alone. The measurements-only view detects no write-mode faults. The rule-based program adds five amount-scale de-tections under raw, regex, schema and facts. Thus even a predominantly structural group contains a value-dependent case. The ownership comparison creates the clearest repair loss. The rule-based program detects all 60 wrong-customer/contamination faults under raw and facts, and none under regex, schema or metadata-only exports. Regex and schema detect 20/30 value faults because removing the re-quested owner prevents the file workflow’s source-row com-parison. Facts retain the exporter-computed result. Com-parison facts and both pseudonym scopes achieve 210/210 fault-task successes and 190/190 recoveries, compared with regex/schema’s 140/210 and 120/190 (Table III). Removing repair evidence does not ensure anonymity. Nor-malization increases regex unique identification from 49/240 under basic matching to 225/240, while schema reaches 221/240. B. Retention with an Independent Program 

The original rule-based program succeeded with both com-parison facts and pseudonyms. To see whether another pro-gram can use both exports, we test a separately written pro-gram that chooses edits using the export and public workflow rules. These rules give allowed settings and defaults, such as filtering for the requested customer. Any ticket contains only the retained request. The program enumerates allowed one-stage configurations, keeps plans addressing a listed candidate cause for every observed constraint, and ranks them by fewer operations then fewer unrelated changes. It acts only on a unique best plan. Missing or ambiguous support causes abstention, without workspace probing. On raw development traces, the program succeeds on 21/21 faults and 3/3 clean cases. Its source and criteria were frozen before the 48-case test, which uses two seeds per workflow, first fault variants and clean controls. The rule and constraint-based programs use different cohorts, so their aggregate scores do not isolate the effect of changing the program alone. C. Linkage and Counts after Identifier Matching 

The main cohort shows linkage even when identifier match-ing fails. Execution-scoped pseudonyms and facts have equal identifier-aware AUC in the file and reconciliation workflows (0.8750 and 0.5000). In aggregation, pseudonyms reach 0.9633 versus facts’ 0.6585. Run-scoped pseudonyms reach 1.0000 in all three. These feature sets include metadata digests. We did not isolate their contribution or test disclosure on the independent program’s cohort. To see how much linkage depends on the attacker’s choice of features, we also test generic similarity on comparison facts with run-scoped owner tokens. Generic linkage gives AUCs of 0.7797, 0.7898 and 0.7698 in the file, reconciliation and aggregation workflows, below the 0.95 minimum predicted in our protocol. On the same exports, the identifier-aware attack reaches 1.0000, 1.0000 and 0.9971. Each workflow has 80 views from 10 shared cells, giving 280 positive and 2,880 negative dependent pairs. Known-volume matching uniquely identifies 97/240 re-quested targets under every one of the 15 policies. A selected-counter fact ablation removes seven fields: measurement row/byte counts and statistic row/key/distinct-key counts. It retains baseline relations, distinct-owner count and negative-amount count. The count attack then has no match in 240/240 views, while rule-based program detection and fault-task suc-cess remain 210/210 and recovery remains 190/190. Identifier-aware linkage and outcomes for the independent program were not measured for this ablation. The result is specific to the stated volume rule. V. A SECONDARY LANGUAGE-MODEL CHECK The language-model study asks whether ownership diagno-sis and identifier matching show the same contrast on model-generated traces. Qwen2.5-3B-Instruct (4-bit, CPU, greedy) follows a ticket/runbook and calls native stages. The envi-ronment injects faults beneath its arguments. There are 96 development and 144 primary held-out executions. Calls are valid in 912/967 steps (94%), and all episodes complete the harness. Exports are evaluated by the same rule-based pro-gram and normalized matcher. A separate exploratory model classifier predicts seven fault families plus clean from at most 768 tokens. This study does not test model-based repair. The written protocol specifies at least 90% raw/fact owner-ship detection versus at most 10% for regex/schema/metadata-only, at least 50% normalized identification for regex/schema versus zero for metadata-only and fact variants, and at least 90% fact detection within each evidence group. These criteria are met. Facts detect 70/72 structural, 17/18 value and 36/36 ownership faults, with zero normalized unique identification. Regex/schema detect 0/36 ownership faults but uniquely iden-tify 113/144 and 137/144 targets. One eight-execution cell filters by e-mail instead of account ID and returns no rows. It remains in the primary analysis. Interaction content supplies a separate exposure channel. Restricting normalized matching to step index, explanation, tool, arguments and response, and clearing other content and metadata, still exposes the target in 127/144 schema-redacted primary executions and 130/144 separate post-hoc executions. Among nine primary episodes whose nonempty typed filter rows belong solely to a neighbor, four accepted simulated 

notify calls have a neighbor-matching e-mail and two match both account and e-mail. The separate new-seed cohort repeats these 4/9 and 2/9 counts without an execution-changing agent error. These retained simulated fields do not establish external delivery. Facts show no demonstrated improvement in exploratory model diagnosis. With invalid predictions counted incorrect, facts yield 30/144 correct predictions versus metadata-only’s 26/144. There are six fact-only wins and two wins with metadata alone (two-sided paired exact McNemar p = 0 .289 ). Excluding the eight filter deviations removes both wins with metadata alone and changes the counts to 29/136 versus 23/136. That selected sensitivity does not replace the primary result. Shared cells make the episode-paired test nominal. VI. USING THE BENCHMARK AND INTERPRETING ITS SCOPE To compare exports on new inputs, a researcher passes each view and the public edit schema to a diagnostic program and seals its decision before private replay and scoring. A two-row file example shows this interface with raw, execution-scoped pseudonym and metadata-only exports. The example and aggregate results for all 15 policies are in release v1.0.0 at https://github.com/AnthonyXu109/s2ai-2026-artifact. Full study materials are available on request. Exporters should audit encoded identifiers, counts and link-age separately, then check repaired outputs with their intended program and an independent implementation. Testing alter-native count summaries and execution-keyed digests would extend these results. The evidence comes from three synthetic workflows, seven injected fault families and bounded edits. The public defaults narrow the search for repairs. The rule-based program and facts share a selected vocabulary, while the independent diagnostic program tests only first fault variants on a different cohort. Pseudonyms cover the declared grammar searched by the matching attacks. Stronger auxiliary-data or model-based re-identification is outside these tests. The language-model evi-dence uses one small runbook-guided model and environment faults. Main and model studies retain protocols, manifests and deviations, but their prospective protocol timing could not be independently established. The independent diagnostic program’s source and criteria were frozen before its own final cases. VII. RELATED WORK 

Trace anonymization. Packet privacy [9], Crypto-PAn’s con-sistent keyed IP mappings [10], log anonymization [11] and unconventional identifier forms [12] concern trace publication risks. Secret Sharer tests memorization [13], while trace-canary audits test evidence of weight memorization [14]. Our identification endpoint concerns the requested customer in one execution and catalog. 

Agent privacy and auditability. LOPSIDED pseudonymizes prompts and reconstructs responses [15]. We evaluate post-execution exports. AgentLeak tests internal leakage and sani-tization costs [1]. RedAct protects procedural knowledge and evaluates audit fields and human-rated usability [2]. Source-aware redaction [16], identifier detectors [6], [7] and Open-Telemetry [8] supply mechanisms. AgentTelemetry counts telemetry-guided, agent-proposed, guard-checked patch inter-ventions in a SWE-bench Lite case study [4]. We pair replayed outputs with disclosure. 

Failure and task evaluation. AgentChaosBench tests runtime faults and sanitized-telemetry localization [17]. TraceElephant supplies 220 filtered, manually inspected public-benchmark failure traces without our requested-customer labels [18]. TelemetrySuffBench tests paired-view failure-origin suffi-ciency and nonunique origins [3]. We join diagnosis and post-decision output scoring with disclosure/linkage. Agent-Dojo [19] and computer-use probes [20] test injection secu-rity. τ 2-Bench tests task utility [21]. Our edits are bounded configurations. VIII. CONCLUSION An export can remove identifiers, lose repair evidence and still disclose the requested customer. Comparison facts and both pseudonym scopes preserve the rule-based program’s recoveries. The independent program loses three repairs with facts and retains them with execution-scoped pseudonyms. On the main cohort, those pseudonyms permit stronger linkage in the aggregation workflow. Dropping selected counters from the comparison-fact export stops the tested row-count attack and preserves rule-based repairs. The benchmark lets exporters test repair and remaining disclosure on the same exports.
