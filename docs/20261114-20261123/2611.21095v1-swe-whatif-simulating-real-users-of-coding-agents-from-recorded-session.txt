# SWE-WhatIf: Simulating Real Users of Coding Agents from Recorded Sessions 

Tae Soo Kim 1,2 Tongshuang Wu 3 Juho Kim 1,21KAIST 2SkillBench 3Carnegie Mellon University

Abstract 

Recorded sessions between users and coding agents offer a way to evaluate how agents com-plete real-world tasks and interact with users. However, these sessions cannot simply be re-played with new agents, because recorded user replies may no longer apply when an agent takes a different trajectory. We introduce SWE-WHAT IF, which replays recorded sessions with new agents by modeling the user’s intents, the criteria for satisfying them, and the conditions under which they arise. Using this model, a user simulator generates replies that adapt to unseen agent turns while remaining grounded in the recording. Across 89 real-world sessions, SWE-W HAT IF generated the replies most sim-ilar to those of real users and matched the strongest baseline when sessions were rewrit-ten. To test adaptation, we replay sessions with agents instructed to avoid or repeat actions that the recorded user pushed back on. SWE-WHAT IF produced the highest win rate for avoiding these actions (66.3%), significantly above chance. We further demonstrate its util-ity by ranking five LLMs as coding agents, where the highest-ranked model depended on how users specified and developed their intents, and a study with 16 users, where replaying their own sessions changed 14 participants’ rankings and informed their future agent use.

Developers increasingly use coding agents in real-world practice. Recent datasets release recordings of these sessions (e.g., SWE-chat (Baumann et al., 2026), DataClaw (DataClaw contributors, 2026)) that capture both the work users ask agents to do and how they steer them: what outcomes or in-formation they request, what work they accept or reject, and what leads them to change direction or give up. Each message responds to what the recorded agent did, like a user correcting an agent for prematurely committing a code change. If a new agent diverges from this observed trajectory (e.g., does not commit the code early), the real user would have replied differently, and the recorded message would no longer match the conversation. Prior user simulators can respond to unseen agent 1arXiv:2611.21095v1 [cs.CL] 16 Nov 2026 trajectories (Yao et al., 2025; Wu et al., 2025; Vijay-vargiya et al., 2026; Laban et al., 2026; Raghaven-dra et al., 2026; Trinh et al., 2026), but typically follow synthetic goals or personas that do not cap-ture a particular user’s work or steering. SWE-Together (Wu et al., 2026b) instead derives a simu-lator from a conditional script of the user’s recorded messages, which can choose when to send each message to a new agent but is constrained to their recorded content and order. Thus, a replay needs a simulator that can adapt to trajectories that the recorded agent never took while remaining faithful 

to why and how the real user steered it. We introduce SWE-W HAT IF, a framework that turns a recorded session into a replay task for new coding agents. Instead of a script of the recorded replies, SWE-W HAT IF extracts an intent model :the outcomes or information the user wanted ( in-tents ), the criteria by which they accepted or re-jected the agent’s work, and the conditions under which each intent was raised or dropped. During replay, the simulator tracks these intents and, after each agent turn, judges the agent’s actions against their criteria and conditions, updates the intent state, and generates the user’s next reply based on this state. As a result, the simulator reacts to what the new agent actually did based on reasons grounded in the recording (e.g., objecting to a commit only if it is actually early). We evaluate SWE-W HAT IF both intrinsically, by testing its faithful adaptability against three other user simulators, and extrinsically, by demon-strating its utility in two applications. For the in-trinsic evaluation, we use 89 real-world sessions released by SWE-Together (Wu et al., 2026b) and SWE-chat (Baumann et al., 2026). For replication and robustness, we compare simulated replies with real users’ replies on the original recordings and on versions rewritten in form but not in content. SWE-WHAT IF generated the most similar replies on the recordings, while matching the best baseline on the rewritten sessions. For adaptation, we replay each session with an agent instructed to avoid actions that the real user pushed back on and another in-structed to repeat them. With SWE-W HAT IF, the former agent achieved the highest win rate among the simulators in terms of task success and user burden, significantly above chance. For the extrinsic evaluation, we first use SWE-WHAT IF to replay 58 tasks with five LLMs as coding agents in the same harness (Anomaly, 2025). Our ranking agreed more closely with Agent Arena’s ranking from real-user sessions than with the other published rankings. The rankings also differed based on how users steered the agents (e.g., giving details upfront or raising requests only in certain situations). We then study whether re-playing developers’ own sessions can help them decide which coding agents to use and how to use them. In a user study, 16 coding-agent users pro-vided their own sessions and reviewed simulated replays with three different agents. After reading the replays, 14 of 16 participants changed how they initially ranked the agents, including 10 who changed their top-ranked agent. From the replays, participants also reported gaining insights for their future agent use—e.g., when cheaper models were sufficient, how each agent works differently, and how to steer agents. Our contributions are as follows: • We introduce SWE-W HAT IF, which turns recorded sessions into user simulators that faithfully adapt to new agent trajectories. • We propose evaluation methods to evaluate the faithful adaptability of user simulators by building tests from recorded sessions. • We demonstrate the framework’s utility by showing that LLM rankings differ based on user steering patterns and that replaying one’s own sessions can help real users choose agents for their own tasks. 

2 SWE-W HAT IF

2.1 Task Definition 

SWE-W HAT IF creates a replay task from arecorded session (i.e., user messages, agent mes-sages, and tool calls) and its starting environment 

(i.e., code repository and runtime when the ses-sion began). In this task, a new agent is given the starting environment and the user’s opening re-quest, and it must complete the user’s work from the recorded session while interacting turn by turn with a user simulator that steers it as the original user would. As the new agent can take any path, the simulator must respond to actions absent from the recording, but only in ways supported by the user’s recorded requests and reactions. We refer to this as faithful adaptability .

2.2 User Simulator 

Inspired by prior work on user simulators driven by representations of user intents (Schatzmann et al., 22007; Kim et al., 2026; Tack et al., 2026), SWE-WHAT IF builds an intent model from the recording to represent the outcomes the user sought and the conditions under which they raised or dropped re-quests. During replay, the simulator uses this model to decide which requests and reactions apply to the new agent’s actions. 

Intent Model. The intent model describes the user’s work as outcomes rather than turns. The model consists of a set of intents , each an outcome or piece of information that the user wanted during the session (e.g., a bug fixed, an explanation of why a test fails). Each intent has criteria that define what is needed to satisfy it (e.g., the fix must not skip the failing test). Each intent can also have 

conditions that capture what led the user to raise it: a dependency on another intent (e.g., creating a test after implementing a feature), a situation that arose in the session (e.g., a test failing), or information that the user gained from the agent (e.g., the agent’s assessment of a proposed fix). Conditions can also capture when the user drops 

an intent (e.g., a new fact leads them to give up one approach for another). Every criterion and condition is grounded in the user’s own turns or in outcomes that they implicitly accepted. 

Intent State. During a replay, the user simulator tracks and updates the state of the intents in the model at each turn. Each intent is blocked (i.e., its conditions are not yet met), open (i.e., the simulated user can now express it), raised (i.e., the simulated user has expressed it), dropped (i.e., it no longer applies), or abandoned (i.e., the agent has stopped making progress on it, so the simulated user gives up). Separately, each criterion of an intent is either 

met or unmet , so an intent can be fully, partly, or not yet satisfied. At the start of a replay, the intents in the user’s opening request are already raised. 

Style Profile. To generate each reply as the user would, the simulator also uses a style profile com-puted from the user’s messages in the recording (e.g., length, punctuation, formality). 

Building the Intent Model. SWE-W HAT IF

builds the intent model with LLM-based agents that draft, review, and revise it. A drafting agent reads all user messages in the recorded session and groups them into intents with their criteria and con-ditions. A reviewing agent then checks the draft for issues, such as overly prescriptive criteria that would penalize functionally equivalent approaches (e.g., requiring a particular function name) or cri-teria and conditions that cannot be satisfied in a replay (e.g., requiring an external private API). A fi-nal agent revises the draft based on this review. The style profile is computed directly from the user’s messages. Further details are in Appendix A.1, and an example intent model is in Appendix A.3. 

2.3 Turn-by-Turn Simulation 

After each agent turn, our user simulator takes three steps to generate a message (Fig. 2). (1) Assess: 

Inspired by LLM-as-a-Judge approaches (Zheng et al., 2023; Ye et al., 2024; Kim et al., 2024; Viswanathan et al., 2025), we use an LLM to judge the agent’s actions and message against the crite-ria of the raised intents and the conditions of the blocked intents. (2) Update: Then, based on the judgments, the simulator updates each intent’s state (e.g., an intent becomes open when its conditions are met, or abandoned if its criteria do not change for several turns). (3) Respond: An LLM selects which intents to express next and writes the user’s reply, guided by the style profile. The replay ends when every intent is satisfied, dropped, or aban-doned, or when no intent changes state for several consecutive turns (details in Appendix A.2). 

2.4 Scoring a Replay 

We score each replay on two aspects: success (i.e., whether the new agent completed the user’s work) and user burden , since two replays can reach the same outcome but one can require more steering from the user (Shen et al., 2026). To judge success, we adapt the goal-based judging used in SWE-Together (Wu et al., 2026b): an LLM writes a list of goals for each task from the recorded ses-sion alone, and an LLM judge marks each goal as met or not met from the replay’s final state (i.e., repository changes and the agent’s messages). We calculate the percentage of goals met as suc-cess, s. To account for burden, we multiply s by 

(nreal + 1) /(nsim + 1) , where nsim and nreal are the numbers of messages that the simulated user and the real user sent after the opening request. This burden-adjusted success penalizes a replay that needed more messages than the real session and rewards one that needed fewer.

Finally, when the agent’s trajectory changes in content, the simula-tor should respond differently but only as the user would ( adaptation ). To evaluate these dimensions, we build tests from the recorded sessions. For replication, we fol-low prior work (Dou et al., 2025; Wu et al., 2026a) and compare each simulator’s reply with the real user’s reply at each point of a session. For robust-ness, we repeat this comparison on versions of the sessions with turns paraphrased and merged. For adaptation, the recorded session does not show how the user would reply to a different agent, and an agent can depart from the recording in too many ways to test each one. However, the session reveals agent actions that the user pushed back on (e.g., a change that was later undone), and if the agent had avoided such an action, the user would not have needed to push back. Based on this, we replay each session with an agent that repeats these actions and one that proactively avoids them, where a faithful simulator should produce replays with the latter agent that achieve higher burden-adjusted success. These evaluations test SWE-W HAT IF intrinsi-cally . We also conduct extrinsic evaluations to demonstrate the framework’s utility: ranking LLMs as coding agents and examining how their rankings vary across sessions (§4), and studying whether replays of their own sessions can help users decide which agents to use and how to use them (§5). 

3.1 Setup 

Details on the setup, method, results, and prompts are in Appendix B and E. 

Tasks. We build tasks from recorded sessions that meet three requirements. First, the recording must show what the user wanted and how they reacted to the agent, so that an intent model can be built from it (e.g., contains real user messages and results of agent tool calls). Second, a new agent must be able to redo the work from the starting environment alone (e.g., without external resources like GitHub pages or APIs). Third, the user must have pushed back on at least one agent action, as the adaptation test builds on these actions. Based on these require-ments, we use 65 of the 109 sessions released by SWE-Together (Wu et al., 2026b) and 24 sessions from a newer release of SWE-chat (Baumann et al., 2026), for 89 tasks in all. 

User Simulator Designs. We compare SWE-WHAT IF, with and without the style profile, against three other user simulators, all run on the same LLM (GPT-5.6 Luna). For SWE-Together (Wu et al., 2026b) tasks, we use the simulator prompt released for each of its tasks, which lists the user’s later messages and in what conditions each one should be sent. For the SWE-chat tasks, we use an LLM (Claude Opus 5.5) to write prompts in the same form. This simulator also keeps a summary of each earlier agent turn. SWE-Interact (Raghaven-dra et al., 2026) role-plays a terse colleague who reveals a list of requirements one at a time. SWE-Interact derives this list from benchmark tasks (e.g., SWE-bench (Jimenez et al., 2024)). As our tasks come from recorded sessions, we use the intents 4and criteria from our intent model instead. Finally, the goal-prompted simulator receives the same intents and criteria, but without a persona. 

3.2 Method 

Each test compares simulators on the same tasks. 

Replication. At every user reply in the recorded sessions, we give each simulator the conversation up to that reply and have it generate the next re-ply. Simulators that keep a state across turns also receive the state built from the conversation so far (i.e., the intent states of SWE-W HAT IF and sum-maries of earlier turns for SWE-Together). An LLM judge (GPT-6.1 Sol) rates the similarity of each generated reply with the real user’s reply on content and style from 1 to 5, adapting the similar-ity ratings of SimulatorArena (Dou et al., 2025), and we scale the mean of the two ratings to 0–100. In a replay, however, each reply builds on the simu-lator’s own earlier replies rather than the real user’s. To test this, we also use a multi-turn setting, where each simulator writes three consecutive replies be-tween the recorded agent turns, and the judge rates the three against the real user’s three replies. 

Robustness. We rewrite each recorded session by using an LLM to paraphrase all turns and merging some consecutive user turns. We then run the same single-turn and multi-turn tests on the rewritten sessions, to check that a simulator does not rely on the exact wording and order of the recorded turns. 

Adaptation. For each task and user simulator, we replay the session with two agents (Claude Code on Claude Sonnet 5.5): one instructed to repeat the ac-tions that the user pushed back on ( observed policy )and one instructed to avoid them ( proactive policy ). Following prior work (Baumann et al., 2026; Tang et al., 2026b,a), we use an LLM (GPT-5.6 Terra) to identify these actions (e.g., ones that the user corrected, objected to, or reverted) and to write the instructions for each policy. For each user simu-lator, we replay sessions with each agent policy twice. We compare the burden-adjusted success (§2.4) of each proactive-policy replay with each observed-policy replay of the same task, and report the win rate of the proactive policy on a scale of 0 to 100, counting a tie as half a win (Vargha and Delaney, 2000). We use two-sided sign tests to assess whether the proactive policy wins signifi-cantly more often than it loses, with Holm correc-tion across the five simulators (Holm, 1979). 3.3 Results 

Table 1 gives the results of the three tests, and Fig-ure 3 plots each user simulator’s scores on the adap-tation test against the average of its replication and robustness scores. SWE-W HAT IF scored at least as high as SWE-Together on replication and robust-ness, while also being the simulator with which the proactive policy reached the highest win rate and won significantly more tasks than it lost. Thus, SWE-W HAT IF showed the most faithful adaptabil-ity among the simulators, replying as the real user did on the recorded sessions while still responding to a different agent as the user would. 

Replication. SWE-W HAT IF scored highest on the recorded sessions, both for single replies (53.2, against 51.3 for SWE-Together) and for three con-secutive replies (44.9 against 40.4), even though SWE-Together’s prompt provides the recorded user’s later messages verbatim. In comparison, SWE-Interact and the goal-prompted simulator scored lower in both settings. All simulators scored lower in the multi-turn setting than in single-turn. 

Robustness. On the rewritten sessions, SWE-WHAT IF and SWE-Together scored about the same (45.1 and 44.7 on average). On average, participants ranked the smaller model of each set higher than they had 7predicted, and Claude Opus 5.5 and GPT-6 Sol lower (Fig. 5a). Fifteen agreed that the replays taught them something they did not know about the agents, and 14 agreed that the replays would help them decide how to use coding agents (Fig. 5b). The most common lesson was that a smaller and cheaper model was enough for their session (12 of 16)—e.g., “Luna performed as well as Sol at a fraction of the cost.” Participants also saw that agents differed in how they worked with the user, and this could affect which agent they preferred (8 of 16). For example, P04 preferred an agent that “listened to what I had to say” over one that kept proposing its own ideas. Also, 4 participants confirmed or revised their harness preferences (e.g., Claude Code or Codex), and 2 learned that their steering shapes the result. For future use, 11 of 16 planned to choose models by task, including 5 who would start with a smaller model, 4 planned to change their steering, and 3 would keep their current harness. Thirteen of 16 participants agreed that their sim-ulated selves worded messages like them, and 13 agreed that they asked for things and reacted to the agent like them. Participants marked 49% of the simulated replies as “Sounds like me”, 38% as “Partly”, and 13% as “Not like me”. Where the sim-ulated user differed, 5 participants found it more formal or wordier than themselves (e.g., P15: “with a lot more formality than I would”), and 3 found that it kept insisting on the same thing when they would not have (Appendix C). 

6 Related Work 

Benchmarks for Coding Agents. Benchmarks for coding agents mainly assess fully specified tasks without a user (Wang et al., 2026b), such as SWE-bench (Jimenez et al., 2024) and App-World (Trivedi et al., 2024). As coding agents are increasingly used in practice, recent work adds sim-ulated users to these benchmarks (Pan et al., 2025; Kim et al., 2025a; Trinh et al., 2026; Wang et al., 2024) who reveal requirements when asked (Vijay-vargiya et al., 2026) or one at a time (Raghavendra et al., 2026). 

User Simulators. User simulation in task-oriented dialogue (Schatzmann et al., 2006) in-cludes agenda-based approaches (Schatzmann et al., 2007). Recent work prompts LLMs with goals (Yao et al., 2025; Barres et al., 2026; Wu et al., 2025) or personas (Raghavendra et al., 2026), or trains them to simulate users (Zhou et al., 2026b; Sun et al., 2026; Phan et al., 2026; Wang et al., 2026a). Further, simulators have also been de-signed to model specific user behaviors, such as progressive disclosure (Laban et al., 2026), evolv-ing intents (Kim et al., 2026; Tack et al., 2026), contextual preferences (Kim et al., 2025b), knowl-edge (Lee et al., 2026), and cooperation (Chopra et al., 2026). Others build simulators from real user data (Wu et al., 2026a; Naous et al., 2026), includ-ing inferred profiles (Wang et al., 2025; Zhou et al., 2026a), but simulated users can still differ from real users in their interaction behavior and failure patterns (Zhou et al., 2026c; Seshadri et al., 2026). 

Evaluation from Recorded Sessions. Recorded coding-agent sessions (Baumann et al., 2026; Data-Claw contributors, 2026; He et al., 2026) support analyses of user steering (Tang et al., 2026b,a) and evaluation on real tasks. SWE-Together (Wu et al., 2026b) replays these sessions by deciding when to send the recorded user’s messages, while preserv-ing their content and order. Instead, SWE-W HAT IF

generates replies from the user’s intents, criteria, and conditions, allowing it to respond to new agent trajectories. 

7 Conclusion 

We introduce SWE-W HAT IF, a framework for re-playing recorded user–agent sessions with new cod-ing agents by simulating users from their intents, criteria, and conditions. In tests of replication and robustness, SWE-W HAT IF generated the replies most similar to those of real users on recorded sessions and matched the strongest baseline when sessions were rewritten. In an adaptation test, our simulator most clearly distinguished agents that avoided actions that the real users had objected to from those that repeated them. By ranking five LLMs as coding agents and through a user study where participants replayed their own sessions, we demonstrate that replays can help researchers eval-uate agents on real users’ work and help developers choose agents for their own tasks. 

Limitations 

Our replays make the following assumptions about users. First, the user interacts with the agent only through the conversation. In practice, users may also open and edit files, run tests on their own, or look at external resources, but these are not shown in the recorded session. Second, the user implicitly 8accepted any outcome they did not object to, which ignores cases where the user might have been dis-satisfied but did not express it. Third, the simu-lated user does not react to anything for which the recorded session has no relevant evidence (e.g., if a new agent adds comments to the code but the user never reacted to code comments in the recorded session, the simulated user ignores them). Simi-larly, the simulated user only asks for what the user asked for in the recording, even when a new agent’s path might have led the real user to new requests. Finally, the simulated user reads every tool call and its result, while a real user may only skim the agent’s work. We leave relaxing these assumptions for future work. Our experiments also have the following limita-tions. The used sessions come from public releases, so they include only developers who chose to pub-lish their sessions (e.g., SWE-chat (Baumann et al., 2026) mostly includes early adopters working on open-source code, not on proprietary or enterprise code). For agent evaluation and ranking, we eval-uated only five models in a single agent harness, opencode (Anomaly, 2025). Our metric for burden-adjusted success approximates the user’s effort of writing and reading by counting messages, and the goals used to measure success are based on where the recorded session ended, but the user may have stopped midway instead of reaching the state they wanted. In the user study, participants saw only three agents that we chose, for up to three turns each, and these agents worked in environments par-tially reconstructed from the recording, which may not reflect their full capabilities. 

Ethical Considerations 

Our experiments use recorded sessions released publicly by SWE-Together (Wu et al., 2026b) and SWE-chat (Baumann et al., 2026). SWE-Together is released under the Apache 2.0 license, with ses-sions originally collected from SWE-chat (ODC-By), DataClaw (MIT), Pi, and Hyperswitch. We use these sessions to evaluate coding agents and user simulators, consistent with the purposes of these releases. However, recorded sessions can contain sensitive information, such as private code, credentials, and identifying details. Building user simulators from these sessions can further expose this information through their intent models, style profiles, and simulated replays. In our user study, participants gave informed consent before providing their sessions. Before up-loading, we replaced credentials and identifying de-tails on participants’ own computers and sent only the portions of sessions needed for the replays. Par-ticipants were informed that their sessions would be sent to the model providers that ran the agents and user simulator. After generating the replays, we deleted the uploaded sessions, intent models, style profiles, and starting environments. We do not release an artifact package containing the source sessions, code, intent models, style profiles, goals, or simulated replays. The study was approved by KAIST’s institutional review board. Beyond privacy, SWE-W HAT IF raises another concern because it simulates how a particular user communicates with and steers coding agents. Al-though we use these simulators only to evaluate coding agents, they could also be used to imitate the real users in other settings without their knowl-edge or consent. This risk is especially relevant when sharing intent models, style profiles, or sim-ulated replays that capture how a particular user behaves. We used AI assistants to help implement the user simulator, build the user study interface, revise the manuscript, and search the literature. The authors verified and revised all resulting content and read the cited papers.

A.1 Building the Intent Model 

We build each intent model with three LLM-based agents that draft, review, and revise it in turn, all Claude Code on Claude Opus 5.5. 

Input. Each agent takes the recorded session (i.e., every message of the user and the agent, and the results of the agent’s tool calls) and also the start-ing environment (i.e., the code repository with its history and its runtime). 

Drafting. The drafting agent writes the intent model through five steps (prompt in Fig. 14, with the rules in Fig. 17): (1) label what each user mes-sage does (e.g., a request, a correction, or an ac-ceptance of the agent’s work); (2) group messages into intents and write the criteria of each intent; (3) for each criterion, record the evidence in the session and what the simulated user could observe in a replay to judge it; (4) write the conditions; and (5) mark where in each session each criterion and condition was met. 

Main Rules. We instruct the drafting agent to follow specific rules that tie the intent model to the user’s own requests and decisions. The following are the main rules that are followed: • An intent or criterion should refer to names that were only named explicitly by the user, given in the opening request, or already held by the starting environment. • A criterion can require a specific approach to code changes only if the user requested that approach explicitly or they explicitly accepted when an agent took that approach. Otherwise, the criterion must be described so that it can be satisfied by other equivalent approaches. • A condition records what led the user to raise an intent in the conversation. • A question and the request that follows its answer are two intents, where the second has a condition that depends on the first. • If new information leads the user to replace one request with another, represent the orig-

LLM judges the criteria of every raised or dropped intent, and every condition written in text, includ-ing those already met (Fig. 18). For each judged criterion or condition, the LLM also describes its reasoning for its judgement. 

Update. The simulator then updates the intent state from the judgments, without an LLM. At the start of a replay, the intents in the opening re-quest are raised, the intents without a raising con-dition are open, and all other intents are blocked. A blocked intent becomes open when its raising conditions are met, and an open intent becomes raised only when the respond step expresses it. An intent becomes dropped when its dropping condi-tions are met, and satisfied when all of its criteria are met. Once a condition is met, it stays met. In contrast, a met criterion becomes unmet again if a later agent turn does work that undoes or conflicts with the criterion. A raised intent that is not satis-fied is abandoned when none of its criteria change for four consecutive agent turns. Blocked intents that depend on an abandoned intent are also aban-doned. A dropped or abandoned intent is never raised again. 

Respond. An LLM then chooses which intents to express among those that are open or already raised but with unmet criteria (Fig. 19). The LLM first writes what the reply should ask the agent to do, and then rewrites the reply to follow the user’s style with the style profile. The respond step is also given the assess step’s reasoning for the judgement of each unmet criterion, so the simulator can name what is missing (e.g., the agent built the binary but never ran it). 

Style Profile. We compute the style profile from the messages that the user typed in the recorded session with deterministic code. These messages include the opening request and leave out slash commands and pasted text (i.e., messages longer than 600 characters or with six or more lines). The 14 style profile covers the language used, whether the first letter is capitalized, the end punctuation, the use of backticks, the length in words, and the use of specific words (e.g., “please”, “pls”, “thanks”). For each pattern except length, the code counts the share of messages with the pattern and turns it into a fixed sentence (e.g., “None of their messages say please or thanks.”). For length, the code takes the median number of words per message and places it in one of four classes, which are a few words (up to 6), one sentence (up to 15), one to three sentences (up to 35), and several sentences. 

Ending a Replay. A replay ends when every in-tent is satisfied, dropped, or abandoned, or when no intent changes for seven consecutive agent turns. Intents that the user would want only if a situation arose (e.g., a test failing) are left out of this check while they are blocked. 

A.3 Example 

Figure 6 shows the intent model of one task and an excerpt of one of its replays. In the recorded session, the user asks for a small patch to the command-line tool of a Go repository, so that the command entire explain prints its help text when it receives an argument without any of its qualifier flags (i.e., the flags that name what to ex-plain). When the recorded agent starts to edit the code, the user rejects the edit and asks it to cre-ate a branch first. After the patch, the user runs 

/reviewer (i.e., a command defined in the reposi-tory that has the agent start a separate agent to re-view the changes). The review approves the patch and suggests a hint that explains why the help text is shown, and the user asks for the hint if it is small. The intent model keeps these requests as four in-tents. I2 has no raising condition, so it is open from the start of a replay. I3 is raised when I1 is satisfied, and I4 is raised only if a review suggests the hint (C1 ). In the excerpt, the new agent (Claude Code on Claude Sonnet 5.5) makes the patch, but its check also prints the help text when a qualifier flag is given. As criterion (b) of I1 is unmet, the simulated user asks for this missing part. In the third turn, the agent is unable to run /reviewer , as it has no tool to start another agent, which is a situation that was not present in the recording. Then, the simulated user instead asks it to review the changes itself so the agent provides a review that approves the patch without suggesting a hint. As a result, C1 is never met and the simulated user never asks for the hint. The replay ended after five agent turns, with I1 to 

I3 satisfied. In another replay with the same agent, the agent also does the same review but it instead suggested including a message that explains the help text. This led the simulated user to ask for the hint in its next reply.

B.2 User Simulators 

All user simulators run on the same LLM (GPT-5.6 Luna) and write one reply after each agent turn. 

SWE-Together. We use the simulator prompt that their released code provides for each task. For the SWE-chat tasks, which have no provided prompt, we use an LLM (Claude Opus 5.5) to write a prompt for each task in the form of the released prompts. 

SWE-Interact and Goal-Prompted Simulator.

B.3 Method 

This section gives the details of each test in Sec-tion 3.2. 

Replication. The LLM judge used to assess sim-ilarity of real user replies and simulated ones uses one prompt for single-turn replies and another one for the multi-turn setting (Figs. 22 and 23). When we run the judge, we run it twice, average the two ratings, and rescale each rating to 0–100 as 

100( r−1) /4. The recorded sessions of the 89 tasks contain 569 user replies that we used for evalua-tion. At each reply, SWE-W HAT IF starts from the intent state built from the conversation before the last agent turn, then assesses that turn, updates the 16 intent state, and writes the reply. For the multi-turn setting, we average the sets of three consecutive replies within each task, then average over the tasks that have at least one such set, which results in 71 tasks. 

Robustness. We rewrite a session in two ways, merging consecutive user turns and paraphrasing messages. For merging, we ask an LLM (GPT-5.6 Luna) whether each pair of consecutive user turns could have been sent as one message (Fig. 25). For such identified turns, we use an LLM to merge the turns with a short connecting phrase (e.g., “Also,”), which gives 153 merged turns over 72 tasks (Fig. 26). For paraphrasing, we use the LLM to paraphrase each user and agent message (Fig. 24). Then, for evaluation, we compare the simulated replies against the paraphrased versions of the real users’ replies. 

Task Goals. We use an LLM (GPT-5.6 Terra) to write the goals of each task from the recorded session alone, without the intent model (Fig. 27). Each goal cites the user’s messages that support it, and work that the recorded agent did on its own is left out. 

Policies. We use an LLM (GPT-5.6 Terra) to list, from the recorded session and its goals, every agent action that the user pushed back on (Fig. 28). We then use the same LLM to turn each action in this list into an observed instruction that repeats it in similar situations and a proactive instruction that avoids it (Fig. 29). For example, consider an agent that was corrected for committing all staged changes before asking the user which ones to com-mit. The observed instruction will tell the agent to always commit all staged changes, while its proactive counterpart would tell the agent to in-spect staged changes first and confirm with the user which ones to commit. 

Task Success. To score task success, an LLM judge (GPT-6.1 Sol) reads the goals, the changes that the replay made to the repository, and the agent’s messages and tool calls (Fig. 30). The judge does not read the messages of the real or simulated user, so that it judges each replay on the agent’s work alone. We run the judge twice on each replay. Success s is the percentage of goals met, averaged over the two runs of the judge, and burden-adjusted success follows Section 2.4. For the win rate, we compare each proactive-policy replay of a task with each of its observed-policy replays, counting a win as 1, a tie as 0.5, and a loss as 0, and average the four comparisons into the task’s score (Vargha and Delaney, 2000). The win rate is the mean of these scores over tasks. We test whether the proactive policy wins more tasks than it loses with a two-sided sign test, which leaves out tasks with a score of exactly 0.5, and apply a Holm correction across the five user simulators (Holm, 1979).
