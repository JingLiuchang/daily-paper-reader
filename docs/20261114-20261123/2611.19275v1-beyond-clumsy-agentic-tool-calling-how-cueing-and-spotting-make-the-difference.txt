A B S T R A C T 

LLM-based task-oriented agents depend on tools to interact with their environments, but may overlook execution feedback, repeat ineffective calls, or persist with unproductive strategies. These behaviors can hinder agents’ ability to use tools autonomously and sustain task progress. We characterize tool-use symptoms at two temporal granularities: local clumsy tool-use behav-iors and tool-use detours spanning multiple interactions. Towards greater autonomy in tool use, we present ToolPulse, an online middleware supporting autonomous tool use through cueing and spotting. ToolPulse tracks execution state and temporal interaction patterns, monitoring proposed calls before dispatch to tools and inspecting execution feedback prior to the agent resumes reasoning. It combines state-based rules, semantic sequence analysis, and interaction-feature similarity to identify intervention opportunities and provide verbal reminders, structured feedback, or context-specific advice from auxiliary models. Our process-oriented evaluation distinguishes trigger validity, behavioral cessation, and substantive correction alongside task outcomes and resource costs. Using SWE-agent with three backbone models, we evaluate 1,350 trajectories on 90 Python, C++, and Java bug-fix tasks, comparing unassisted execution with four assistance strategies. Substantive responses follow 61.6–90.9% of valid triggers for tool-use detours. Concise reminders achieve the highest observed aggregate substantive-response rate; more elaborate assistance offers symptom-dependent benefits and can be less effective. Aggregate repair outcomes remain close to baseline, with token savings in selected settings. These findings support proactive runtime assistance for autonomous tool use. The observed gap between behavioral adjustment and aggregate repair gains calls for careful decisions on intervention timing and assistance strategy in autonomous agents. 

## 1. Introduction 

In recent years, LLM-based task-oriented agents have emerged as autonomous actors that perceive, reason about, and interact with their environments to solve problems. Tool use underpins the autonomy of task-oriented agents: tools provide the means through which agents acquire information, turning reasoning into task execution, act on external environments, and observe the consequences of their actions. These capabilities support applications in areas such as scientific research, data analysis, embodied interaction, and software engineering (Guo et al., 2024; Chen et al., 2026; Sahu et al., 2025; Yang et al., 2024; Chen et al., 2025). Task-oriented agents typically rely on tool documentation in their context, including functional descriptions, parameter schemas, and a few invocation examples, to understand what tools do and how to use them (Wang et al., 2025a; Xu et al., 2025; Yuan et al., 2025). However, knowing a tool’s name, interface, or input format does not ensure that the agent can use the tool autonomously as a task unfolds. Tool descriptions convey basic declarative knowledge but cannot cover every situation encountered during execution. Moreover, agents often treat tool output as transient context for the next reasoning step in a loop of execution, observation, and further execution. The returned output is appended to the interaction history as an observation or tool-response message, leaving the model to interpret the feedback (Yang et al., 2024; Wang et al., 2026). When the agent fails to relate this feedback to the evolving execution state and earlier interactions, it may miss diagnostic signals, invoke an unnecessarily costly tool, or persist with a strategy that has ceased to work. Problematic tool-use behaviors are difficult to capture and understand from individual tool calls or isolated outputs, as they depend on the execution context and how interactions unfold over time. Tool use is commonly understood in terms of call accuracy and task success (Li et al., 2023; Patil et al., 2025; Yao et al., 2024), while how problematic

We identify two types of symptoms of difficulties in autonomous tool use: clumsy tool-use behaviors and tool-use detours . Clumsy tool-use behaviors are local interactions that are unnecessary or poorly matched to the available evidence and execution context. They include overlooking diagnostic information in tool feedback, invoking an unnecessarily costly tool, or repeating a failed call without addressing its reported cause. Tool-use detours occur across a sequence of interactions, when an agent persists with an unproductive strategy despite feedback that calls for adjustment. Such detours may involve recurring action patterns or repeated errors that the agent fails to use to revise its approach. Local missteps can accumulate into longer detours, while individually valid calls can also form an unproductive sequence. Both symptoms can undermine the agent’s ability to adjust its tool use and carry a task forward autonomously, potentially increasing execution costs. Mitigating these symptoms calls for adaptive support that responds to the agent’s evolving execution context and interaction patterns, helping it recognize when and how to adjust its tool use. Recent work has explored trajectory refinement, experience reuse, and offline training as approaches to improving agent capabilities (Antoniades et al., 2025; Mu et al., 2026; Pan et al., 2025). Their benefits depend on additional exploration, applicable historical experience, or parameter updates, motivating complementary support during ex-ecution. More directly, Wink periodically inspects agent trajectories and injects corrective guidance (Nanda et al., 2026), but emerging problems may remain unaddressed between inspections. LivePlan uses predefined rules to trigger corrective advice (Liu et al., 2026). However, its reliance on predefined rules can make it difficult to detect stagnation manifested through approximate repetition across recent interactions. These approaches demonstrate the value of online intervention while motivating closer attention to how tool interactions develop within the evolving execution state. We therefore focus on combining local evidence about tool use with temporal patterns across interactions to recognize clumsy tool-use behaviors and tool-use detours, and provide targeted assistance at the relevant interaction points. Although current task-oriented agents vary widely in architecture and workflow, their tool use typically involves a common cycle of invoking tools, interpreting feedback, and selecting subsequent tools. Investigating how to strengthen agents’ ability to use tools autonomously therefore requires concrete tasks through which their tool interactions and responses to runtime assistance can be observed and evaluated. Software engineering provides a representative setting for studying these symptoms because coding agents depend on sustained tool use to inspect and modify a repository while responding to execution feedback. Agents such as SWE-agent (Yang et al., 2024) and AutoCodeRover (Zhang et al., 2024) use tools to browse and edit code, compile and test programs, and manage versions. To fix a bug, for instance, an agent must locate relevant code, gather diagnostic information, modify the program, and validate the patch. Throughout this process, the suitability of a tool call depends on what has already been inspected, what has changed, and what earlier executions have returned. These observable changes in repository state together with test outcomes, make software engineering particularly suitable for examining how online assistance can help agents adjust their tool use and carry tasks forward autonomously. We therefore investigate how runtime assistance helps agents adjust their tool use and sustain autonomous task progress, using SWE-agent on repository-level bug-fix tasks as the experimental environment. Natural language offers a way to support these adjustments by drawing agents’ attention to relevant execution evidence and guiding their subsequent tool-use decisions. To explore how online linguistic intervention can support tool use while preserving agents’ decision-making autonomy, we introduce ToolPulse, a state-flow-tracking online tool-use assistance middleware designed as a fundamental support layer for autonomous tool use in task-oriented agents. ToolPulse tracks the agent’s execution context and temporal tool-use patterns across interactions. For each interaction, it monitors proposed calls before dispatch to tools and inspects execution feedback prior to the agent resumes reasoning. ToolPulse uses the evolving state, which allows it to adapt to the agent’s working rhythm, to identify clumsy tool-use behaviors and tool-use detours. When intervention is warranted, ToolPulse can intercept an insufficiently grounded call and deliver targeted assistance to the agent. Instead of imposing rigid, mechanical corrections or simply accumulating context, ToolPulse offers adaptive assistance in three forms: verbal cueing through brief reminders or guidance, visual cueing through structured presentation of textual information, and tactile spotting through context-specific suggestions from a fast auxiliary language model. As a weightlifting spotter would, it offers a cue, or lends a hand when needed while the agent remains responsible for carrying the task forward. 2.1. Tool Use and Interaction Interfaces 

The tool-use capabilities of LLM-based agents depend not only on how the backbone model selects and composes actions, but also on the design of the action space, interaction interface, and presentation of environmental feedback. CodeAct uses executable Python code to consolidate an agent’s actions into a unified action space, enabling the agent to compose multiple tools and revise or generate actions in response to new observations (Wang et al., 2024b). SWE-agent introduces a custom agent-computer interface (ACI) that enables agents to navigate repositories, edit code files, and execute tests and other programs, and investigates how interface design affects agent behavior and performance (Yang et al., 2024). AutoCodeRover performs structure-aware code search over an abstract-syntax-tree-based program representation and, when a test suite is available, uses spectrum-based fault localization to further narrow the context relevant to the root cause (Zhang et al., 2024). In web tasks, AgentOccam further shows that refining the observation and action spaces to better align with the capabilities of the backbone model can improve task performance (Yang et al., 2025). Another line of research improves agents’ ability to perform tasks in tool-mediated environments through training. SWE-Gym introduces an executable environment for training real-world software engineering agents and trains verifiers on agent trajectories to support inference-time scaling (Pan et al., 2025). R2E-Gym studies the scalable, procedural curation of executable training environments and combines execution-based and execution-free verifiers for hybrid test-time scaling (Jain et al., 2025). The studies reviewed above improve agents’ tool use through interaction design and training in executable environments. ToolPulse complements these approaches with runtime support for autonomous tool use. It tracks execution state and interaction patterns to identify tool-use difficulties as they emerge, then provides targeted assistance to help agents interpret feedback and adjust subsequent actions. 

2.2. Reflection and Experience Reuse 

Reflection mechanisms revisit an agent’s actions and the resulting feedback to inform subsequent decisions. Devil’s Advocate introduces anticipatory reflection before action execution, post-action alignment with subtask objectives, and a comprehensive review upon plan completion to anticipate potential failures, assess the suitability of executed actions, and refine future strategies (Wang et al., 2024a). Such methods show that feedback-driven adjustment can be incorporated at multiple points during task execution. Memory-augmented methods further investigate how experience from past interactions can be retained and reused. Agent Workflow Memory induces reusable routines, termed workflows, from interaction trajectories and supports both offline induction from training examples and online induction from test queries on the fly (Wang et al., 2025b). Dynamic Cheatsheet maintains a persistent, evolving external memory at inference time, storing accumulated strategies, code snippets, and general problem-solving insights for reuse across queries (Suzgun et al., 2026). The former primarily captures reusable action procedures, whereas the latter focuses on accumulating and reusing concise problem-solving knowledge across tasks. Subsequent studies further examine how experience should be represented, organized, and updated. Agentic Context Engineering treats context as an evolving playbook that accumulates, refines, and organizes strategies through generation, reflection, and curation, thereby supporting both offline and online adaptation (Zhang et al., 2026). Experiential Reflective Learning reflects on task trajectories and outcomes to generate transferable heuristics, and retrieves heuristics relevant to the current task at test time to guide execution (Allard et al., 2026). Hu et al. show that moving continual learning to external memory does not eliminate the challenges of experience reuse. Under a limited context window, old and new experiences compete during retrieval, while memory representation and retrieval organization jointly affect transfer and forgetting (Hu et al., 2026). Reflection and experience reuse provide agents with feedback-derived knowledge for subsequent decisions. ToolPulse shares this feedback-driven perspective and focuses on assistance triggered by observable tool-use symptoms within the ongoing task. It relates proposed actions and execution feedback to the accumulated interaction state, using this evidence to help agents recognize difficulties and revise their tool use at the relevant decision points.

Execution-trajectory analysis provides a basis for identifying behavioral problems and determining when an agent may require assistance. Bouzenia and Pradel conduct a large-scale empirical study of software engineering

AgentRx further automates the diagnosis of failed trajectories by synthesizing constraints, evaluating them step by step, and producing an auditable validation log of constraint violations, which is then used to localize the critical failure step and its category (Barke et al., 2026). The former focuses on characterizing agent behavior and anti-patterns, whereas the latter focuses on attributing failures in trajectories that have already failed. Wink asynchronously inspects agent trajectories at fixed step intervals to detect Specification Drift, Reasoning Problems, and Tool Call Failures, and injects targeted course-correction guidance into the coding agent; its production-scale evaluation provides empirical support for runtime behavioral assistance and a broader-grained precedent for our distinction between local clumsy tool-use behaviors and persistent tool-use detours (Nanda et al., 2026). Other work grounds recovery in runtime evidence associated with tool-use and execution failures. PROBE organizes telemetry from failed runs into structured evidence, structured diagnosis, and bounded recovery guidance for a subsequent attempt (Zhao et al., 2026). Outcome Monitors target silent tool failures in which an output arrives in the expected format but violates an outcome contract. They preserve the original result and issue a nonbinding receipt that identifies the violated property and the available public recovery tools, leaving the executing agent to determine the next action (Panthi and Abdelfattah, 2026). Dubey trains lightweight anomaly monitors on step-level telemetry and combines them with deterministic verification, rollback, and live re-execution to connect failure detection with repair (Dubey, 2026). These studies establish execution evidence as a basis for behavioral diagnosis and runtime assistance. ToolPulse combines local execution state with temporal interaction patterns to address clumsy tool-use behaviors and persistent tool-use detours. Its pre- and post-execution checkpoints connect proposed calls and returned feedback with targeted cueing and spotting. Under shared detection settings, we examine how four assistance strategies affect agents’ substantive tool-use adjustments, investigating how runtime support can help agents sustain autonomous task progress. 

## 3. Learning by Doing: a Half-successful Story 

To identify effective mechanism of online linguistic intervention that help agents adjust their tool use autonomously, we first conduct a pilot study to investigate a more basic question: whether a coding agent’s tool-use behavior can be improved through additional natural-language interventions during task execution. It is natural to consider experience-based interventions that help agents reflect on their tool interactions and adjust subsequent actions. This idea is grounded in experiential learning theory. Human engineers often become proficient with tools through sustained practice. Dewey’s notion of learning by doing (Dewey, 1916) emphasizes acquiring knowledge through action; building on this tradition, Kolb formulated an experiential learning cycle (Kolb, 1984) comprising Concrete Experience, Reflective Observation, Abstract Conceptualization, and Active Experimentation. This cycle offers a useful lens for learning to use software tools. Engineers act and observe the result; when problems arise, they revisit their actions, locate errors, consult documentation, and turn their observations and new knowledge into principles that they can test and revise in subsequent work. At this stage, natural language still remains a common medium for guiding agents. To study how linguistic guidance affects tool use during an ongoing task, we adopt the established ReAct interaction pattern (Yao et al., 2023). ReAct interleaves reasoning, actions, and observations in a recurring loop: at each step, the agent generates a thought and a command, executes the command, and incorporates the resulting feedback into subsequent decisions. As the agent carries forward the task through successive iterations of this loop, we take each reasoning–action–observation cycle as the basic unit of analysis and represent an individual task run as

This structure allows us to observe and assist tool use after feedback is returned and before the agent makes its next decision. We devise an online experiential tool-learning component for task-oriented agents. It treats each tool interaction as an experience that can be examined. Using the agent’s tool call, its execution result, and the current task trajectory, the component determines whether the latest interaction warrants attention: whether it involves repetitive tool use or forms part of an unproductive sequence of actions. Before producing its next thought, the agent therefore sees both the outcome of its previous action and a prompt about that action. It can then reflect on the interaction, extract a lesson, and adjust subsequent actions within the ongoing task. The pilot study tests whether such immediate linguistic feedback can help an agent revise its tool use and aims to provide an empirical basis for design of effective online linguistic interventions that support autonomous tool use. Although prior work (Nanda et al., 2026) has begun to examine misbehaviors in coding agents, existing studies and classifications remain broad. We still lack a fine-grained understanding and systematic classification of misbehaviors in coding agents’ tool use. To tie online assistance to observable tool interactions, we draw on preliminary observations of baseline trajectories and expert judgment to identify four action patterns. We try these patterns in the pilot study to flag interactions that may warrant attention, while gaining an initial sense of whether they can serve as actionable triggers for subsequent online assistance. Duplicate Action occurs when the agent issues two consecutive tool calls with exactly the same tool and arguments. Loop Action occurs when the agent repeatedly executes the same or a similar ordered sequence of tools. Failed Action occurs when a tool call returns an execution error. Custom Tool Candidate denotes a reusable operation sequence that can be encapsulated as a custom tool. The first three patterns mark tool interactions that may warrant reconsideration. Custom Tool Candidate instead identifies a positive opportunity to improve reuse through tool abstraction; it does not indicate anomalous behavior. To support this process, we provide the agent with two auxiliary tools: one creates custom tools, and the other invokes previously created custom tools. With this setup, we task the agent with fixing software bugs and examine how the interventions affect its tool use during task execution. 

3.1. Study Setup 

Agent and Models. We use SWE-agent as the base agent framework. Through an explicit Agent-Computer Interface, SWE-agent provides the language model with operations for code search, file navigation, program editing, and test execution. After each action, the environment returns feedback, yielding a structured record of tool interactions (Yang et al., 2024). We use DeepSeek-V4-Pro (DeepSeek-AI, 2026) and Qwen3-Coder-Plus (Qwen Team, 2025) as the language models underlying SWE-agent. DeepSeek-V4-Pro is a general-purpose model with capabilities in reasoning, code generation, and agentic tool use, whereas Qwen3-Coder-Plus is optimized for code generation and coding-agent tasks, with an emphasis on multistep interaction with the environment and tool use. Their different design emphases allow us to examine, on a preliminary basis, whether the effect of linguistic intervention is confined to one type of backbone model. All experiments use the same SWE-agent architecture and tool environment. 

Task. We draw our experimental tasks from the bug-fix subset of OmniCode. OmniCode is a multitask benchmark for software engineering agents that covers Python, Java, and C++ and includes bug-fix, test generation, code review fixes, and style fixes (Sonwane et al., 2026). These tasks make agents’ tool-use behavior observable through the tool choices and action sequences they employ to accomplish software engineering objectives. A bug-fix task requires the agent to understand an issue in an executable repository environment, locate relevant code, produce a patch, and validate the changes through testing. The successive activities of retrieval, editing, and validation make these tasks suitable for observing tool use during long-horizon task runs. Given the exploratory aim and computational cost, we select 30 instances from the Python bug-fix subset. To sample tasks across a range of complexity, we construct a proxy score from each instance’s gold patch, test patch, and issue description. Specifically, we extract the number of added and deleted lines in the gold patch ( patch_churn ), the number of added and deleted lines in the test patch ( test_churn ), the number of files changed by the gold patch (patch_files ), and the character count of the issue description ( problem_chars ). 3.2. Result 

We first evaluate how runtime natural-language interventions affect task completion. We observe that the agent successfully submitted a patch in all tasks, none of the three intervention strategies impairs the agent’s basic ability to complete the task. Then we measure task outcome by whether the submitted patch passes the issue-specific tests. As shown in Table 3, the differences between the intervention groups and the baseline are small in terms of pass rate. For DeepSeek-V4-Pro, the pass rates range from 70.0% to 73.3% across the four groups. For Qwen3-Coder-Plus, they range from 56.7% to 63.3%. Although the interventions change the outcomes of some tasks, enabling the agent to solve some tasks that remain unresolved under the baseline while causing a small number of previously solved tasks to fail, the improvements and regressions offset each other to some extent. These small differences are insufficient to show that any intervention consistently improves the task resolution. Finding 1. Runtime natural-language interventions preserve the agent’s ability to complete tasks, but the uncertainty in their effects on final task resolution deserves attention.

## 4. Online Assistance for Agentic Tooling: The Method 

4.1. Why Cueing and Spotting 

As the pilot study illustrates, agents use tools through context-dependent exploration, feedback interpretation, and recovery, calling for selective assistance that supports their autonomous adjustment as tasks unfold. We therefore use linguistic cues and context-specific guidance to help agents interpret execution evidence and revise their tool use, avoiding mechanical interventions that treat every repeated action or execution error as a problem. In problem solving, the agent remains responsible for understanding the task, selecting tools, interpreting feedback, and planning subsequent actions. Consider a lifter working with a spotter: the lifter controls the movement and bears the weight, while a spotter observes and assists when needed. Likewise, runtime support should allow the agent to respond to tool feedback independently, intervening when a local action is ill-suited to the current situation or a sequence of interactions develops into a detour. In exercise instruction, cueing and spotting are commonly delivered through verbal, visual, and tactile modalities. 1 A spotter may verbally prompt the lifter to adjust a movement, use a demonstration or visual signal to make a problem easier to notice, or provide physical assistance at a difficult point in the lift. Drawing on this analogy, we provide agents with three forms of assistance: verbal cueing, visual cueing, and tactile spotting. Verbal cueing provides lightweight support through brief natural language messages that draw attention to a problematic interaction or suggest an adjustment. Its effectiveness depends on the agent’s interpretation: generic reminders may offer little useful information, while misguided cues may disrupt reasonable actions. Visual cueing addresses information presentation. Tool calls and their outcomes are often scattered across a long trajectory, making consequential anomalies easy to overlook. Reorganizing and emphasizing relevant information helps the agent recognize the relationship among an action, its feedback, and a potential problem. Tactile spotting provides context-specific guidance, analogous to a spotter assisting at a difficult point in a lift. It offers a concrete, feasible direction for adjustment while the agent retains responsibility for carrying out the task. Delivering these forms of assistance during task execution requires determining when support is warranted and what it should address. Tailoring interventions to local clumsy tool-use behaviors and persistent tool-use detours requires tracking the agent’s evolving execution state and interaction patterns. The detection of clumsy tool-use behaviors and tool-use detours must account for differences in temporal scope and execution context rather than rely on a single uniform scale. These requirements motivate the design of a middleware support layer for autonomous tool use that connects symptom detection with selective, context-sensitive cueing and spotting.

## 5. Evaluation and Analysis 

5.1. Study Design 

We evaluate ToolPulse as runtime support for autonomous tool use, focusing on whether its assistance helps agents recognize tool-use difficulties, make task-relevant adjustments, and sustain task progress. The evaluation connects interaction-level behavior with task-level outcomes. At the interaction level, we examine whether detected symptoms are supported by the execution context and whether agents respond with substantive corrections. At the task level, we assess patch submission, successful repair, and resource expenditure. This complements the goal-oriented evaluation commonly used in agent benchmarks (Jimenez et al., 2024; Liu et al., 2025) with evidence about how agents adjust their tool use during execution. Evaluating such support requires interpreting behavior in its execution context and across time. Repeated calls can serve a legitimate investigative purpose, and an execution error can be part of intentional failure reproduction. Local interactions and persistent detours also require different scopes of evidence. We therefore assess symptoms using criteria suited to their temporal scope and distinguish detection validity, behavioral cessation, and substantive corrective responses. This distinction connects an observed change in action to whether the agent addresses the underlying difficulty. Task outcomes provide a further perspective on the practical consequences of these adjustments. We compare an unassisted baseline with four assistance strategies: reminder-only verbal cueing, guided verbal cueing, visual cueing, and tactile spotting. The baseline follows the original SWE-agent workflow without ToolPulse monitoring or additional assistance. The four assistance strategies share the same detection settings for Calling Repetition, Functional Cycle, Strategic Fixation, Blind Command, and Failure Inertia, and differ in the assistance delivered after a trigger. Wandering Flood is assessed offline after task completion, providing complementary evidence about exploration quality across the evaluated trajectories. The assistance conditions support three targeted comparisons. Guided versus reminder-only verbal cueing examines the contribution of an explicit adjustment direction. Visual versus reminder-only verbal cueing examines feedback organization while retaining the same reminder content. Tactile spotting versus guided verbal cueing examines the contribution of context-specific, model-generated advice. Together, these comparisons examine how the content and presentation of runtime support relate to agents’ subsequent behavioral adjustments. We retain the two pilot backbones for continuity and add a compact, open-weight model to examine variation across model settings. With the agent framework and tool environment held fixed, the experiment crosses three backbone models with three programming languages. We evaluate 90 bug-fix tasks, comprising 30 tasks each in Python, C++, and Java. Each model–task–condition combination is run once, yielding 3 × 90 × 5 = 1 ,350 trajectories: 270 baseline trajectories and 1,080 assisted trajectories. Within each backbone model, all conditions use the same task instances, enabling task-level comparisons to be paired by instance. The experiment reuses the 60 Python baseline trajectories for DeepSeek-V4-Pro and Qwen3-Coder-Plus from the pilot study. These runs use the same model versions, tool environment, and final evaluation procedure as the main experiment. The remaining 1,290 trajectories are generated for the main experiment. We then analyze the following research questions in detail: 

RQ1) To what extent can ToolPulse tackle clumsy tool-use behaviors and tool-use detours? 

RQ2) How do different forms of cueing and spotting affect clumsy tool-use behaviors and tool-use detours? 

RQ3) To what extent can ToolPulse support task completion, and what costs and limitations accompany its use?

It outputs trigger_validity (valid , invalid , or unclear ), behavior_after_trigger (persists , ceases , or

brief_reason . The last two fields record the steps supporting the judgment and a brief rationale. Calling Repetition and Blind Command have more explicit operational criteria. For Calling Repetition, consecutive repeated triggers within the same instance are merged into one episode. If the agent immediately switches to a different action after the trigger, behavior_after_trigger is assigned ceases . If repetition continues for several steps before stopping, it is assigned persists . If repetition continues until the trajectory ends, it is assigned unclear .If a new, nonconsecutive repetition episode occurs later in the same instance, corrective_response is assigned 

non_substantive ; otherwise, it is assigned substantive . For Blind Command, checking the target file before editing it again, or checking it without subsequently editing it, maps to ceases and substantive . Editing the file again without first checking it maps to persists and non_substantive . Neither checking nor editing it afterward maps to ceases and non_substantive . Thus, the rule-assigned trigger validity for these two categories is distinguished from the judge-assessed validity of the other three. Wandering Flood can expand exploration without a corresponding gain in task-relevant evidence, making it harder for the agent to narrow the problem scope and choose a productive next action. It is identified through a two-stage process of low-cost screening followed by LLM judgment, which is inspired by prior work (Sinha et al., 2024; Li et al., 2026). In the first stage, we examine the Retrieve actions listed in Table 2. For each language, we separately aggregate the observation lengths and tool execution times of Retrieve-type actions across the same 30 tasks for each backbone model, and calculate their 95th percentiles as screening thresholds. We then apply the thresholds for each backbone model to the corresponding task set. A step becomes a candidate if either its observation length or its tool execution time exceeds the respective threshold. In the second stage, we provide the candidate step, up to eight preceding steps, and up to three subsequent steps to an LLM judge. The judge determines whether the step constitutes Wandering Flood and outputs verdict (yes , no , or uncertain ), information_gain (sufficient , limited , or unclear ), and rationale , which records a brief reason for the judgment. To check for potential missed cases, we also sample at most two steps per instance that did not pass the first-stage screen but whose measures fall between the 90th and 95th percentiles, and assess them using the same judge.

5.3. RQ1 

We analyze the 1,080 trajectories produced under the four assistance strategies to assess ToolPulse’s ability to tackle clumsy tool-use behaviors and tool-use detours. For the five symptoms captured online, we examine detection validity, post-assistance cessation, and substantive corrective responses. We additionally assess Wandering Flood offline across all 1,350 trajectories and examine symptom occurrence rates across backbone models, programming languages, and task difficulty levels. 

ToolPulse has the ability to identify contextually supported clumsy tool-use behaviors and tool-use detours across the evaluated trajectories. As shown in Table 6, Strategic Fixation is detected in 570 of the 1,080 assisted trajectories, with 1,134 of its 1,841 triggers judged valid. Functional Cycle and Failure Inertia account for 29 of 48 and 110 of 154 valid triggers, respectively. Together with the rule-defined Calling Repetition and Blind Command events, these results show that ToolPulse captures both local tool-use problems and longer interaction patterns that warrant corrective attention. 

Agents often make substantive adjustments after receiving ToolPulse assistance for tool-use detours. 

Substantive responses occur after 19 of 29 valid Functional Cycle triggers (65.5%), 699 of 1,134 valid Strategic Fixation triggers (61.6%), and 100 of 110 valid Failure Inertia triggers (90.9%). Moreover, cessation generally corresponds to a substantive adjustment: all ceased Functional Cycle and Failure Inertia events receive such a response, as do 699 of the 715 ceased Strategic Fixation events (97.8%). These responses indicate that agents often move beyond merely interrupting a detected pattern and take corrective action within the observed post-trigger window. Failure Inertia shows the highest response proportion, indicating that repeated failures accompanied by an absence of recovery actions provide particularly actionable intervention opportunities. 

Local clumsy tool-use behaviors also respond to assistance, although the durability of correction varies. Blind Command ceases after 67 of 86 triggers (77.9%), and 41 of these cessation events involve a substantive response: the agent inspects the target file before a subsequent edit or inspects it without editing it again. Calling Repetition ceases after 80 of 164 triggers (48.8%). Of these 80 events, 20 satisfy the substantive-response criterion, whereas the remaining 60 are followed by another repetition episode later in the task. ToolPulse therefore supports immediate correction of both local symptoms, while sustained avoidance of repeated calls remains more difficult.

## 6. Discussion 

6.1. The Role and Value of ToolPulse in Agent Harness 

Developing autonomous agents requires a systems engineering approach that integrates model capabilities, tools, and runtime support into a coherent execution process. An agent harness serves as a programmable engineering tool for organizing, configuring, and extending the interactions among these components. It provides the execution infrastructure connecting model reasoning to tools, feedback, and task state. Designs for long-running agents show how this infrastructure sustains work through environment initialization, progress records, and session handoffs (Young, 2025). Within this infrastructure, ToolPulse serves as a runtime support layer for autonomous tool use. It maintains evidence about ongoing interactions and returns selective assistance, giving the harness an active role in helping agents adjust their tool use as tasks unfold.

6.2. Reference Implementation and Methodological Implication 

Our empirical findings support ToolPulse’s role in helping agents adjust their tool use during autonomous task execution. Extending this support to broader engineering settings requires accommodating variation in agent frame-works, tool interfaces, and execution workflows. We therefore provide a reference implementation of ToolPulse that translates the runtime assistance investigated in this study into reusable components for agent execution environments. It packages state-flow tracking, symptom detection, and assistance generation behind explicit interfaces connected to action proposal, tool execution, and feedback delivery. This organization makes integration concrete: the host supplies action interpretation, task-relevant semantics, and lifecycle connections, while ToolPulse maintains the interaction state and generates assistance. Figure 7 presents the component organization. Framework-specific adaptation comprises an action parser, a semantic labeler, and lifecycle integration. The parser translates host actions into a common representation; the labeler supplies functional categories, file-access information, and error signatures. The shared support layer maintains interaction history, observed file state, failure records, semantic sequences, and step features. These records support the MultiGranularityDetector , while HintProvider generates assistance and HintSink handles its delivery. The interaction interface exposes inspect_action() , observe_step() , and assemble_observation() for pre-execution inspection, post-execution analysis, and feedback assembly, respectively. To demonstrate ToolPulse’s integration at different levels of agent execution, we provide two examples: Minimal ReAct and SWE-agent. Minimal ReAct provides step-level integration: ToolPulse is explicitly invoked before tool execution and during post-execution analysis and feedback assembly within an editable interaction loop. Scripted decisions and executable in-memory tools make this sequence reproducible and expose each integration point. SWE-agent provides framework-level integration: a reusable adapter encapsulates the connections to an existing agent’s execution and message lifecycle, using repository-oriented semantics for Python, Java, and C++. It handles native tool calls and their response identifiers, execution retries, task initialization, and feedback assembly within the host’s output limits.

Motivated by our fine-grained findings on agents’ responses across tool-use symptoms and assistance strategies, we organize detection, hint generation, and feedback assembly as separately configurable components. Concise reminders provide a lightweight starting point, reflecting their highest observed aggregate substantive-response rate. Auxiliary-model advice remains separately configurable, reflecting its variable effectiveness relative to simpler cueing. This organization connects assistance choices to the adjustments agents need to make, rather than treating additional guidance or inference as an automatic improvement. Detection thresholds, recurrence rules, and host policies regulate intervention timing and action interception. Our continued development will focus on progress-aware detection and adaptive intervention policies that use the current execution state, detected symptoms, and prior responses to determine when to intervene, which assistance to provide, and how strongly to intervene. Research on agentic tooling benefits from examining how agents use feedback, adjust their actions, and sustain task progress alongside final outcomes. This study explores a process-oriented approach: operationalizing tool-use symptoms, introducing targeted assistance, and assessing trigger validity, behavioral cessation, and substantive

## 7. Threats to Validity 

Backbone and auxiliary models. The observed effects depend on the backbone’s repair capability, tool-calling habits, and responsiveness to external assistance. Task success is constrained by its ability to understand the defect and construct a correct patch, while its characteristic tool-use patterns shape the symptoms encountered and the opportunities for intervention. These properties may vary independently, allowing models with similar repair performance to respond differently to the same assistance. The three evaluated backbones consequently provide distinct conditions for assessing ToolPulse, and the relative value of assistance may vary with other models and execution configurations. Tactile spotting additionally depends on the complementarity between the backbone and auxiliary model, particularly whether the latter supplies useful guidance beyond what the backbone can infer from the existing context. 

Task selection and execution environment. We evaluate a subset of the benchmark selected through stratified random sampling according to estimated repair complexity, incorporating task and reference-patch characteristics. Complexity stratification provides coverage across the estimated difficulty levels, but defect types and repair scopes may still be unevenly represented within those strata. The computational cost of individual executions also makes exhaustive evaluation demanding: across the 30 sampled Python instances, unassisted DeepSeek-V4-Pro runs consume an average of 2,031,739 tokens, with a maximum of 11,952,141. The findings therefore depend on the task composition represented by the sample. Some sampled instances also require resources or platforms unavailable in the experimental environment. 2 Such prerequisites affect the conditions under which task completion and resource expenditure are assessed, alongside the intrinsic repair difficulty. 

Mission context and prompt formulation. The effects of runtime assistance depend on how prompt formulation aligns with the agent’s mission context. Mission objectives, operating conditions, and workflows shape the exploration, validation, and recovery required of the agent, influencing both the difficulties it encounters and the adjustments needed to sustain progress. Prompt wording, specificity, and information organization further influence how the agent interprets a cue and incorporates it into ongoing work. The observed response rates and relative effectiveness of assistance forms therefore reflect the evaluated mission context and concrete prompt implementations, and may vary across application settings and alternative formulations of the same assistance. 

Execution variability. Execution paths may vary even when the model, task instance, and assistance strategy remain unchanged. Different assistance conditions introduce further variation by influencing subsequent reasoning, tool selection, and feedback. Paired comparisons preserve task identity, while the resulting trajectories may diverge substantially. Observed differences in patch validation and token usage therefore reflect both assistance effects and execution variability, particularly when pass counts differ by only one or two instances. The paired bootstrap intervals for token usage quantify uncertainty in comparisons of the recorded runs; repeated executions of the same configuration may introduce additional variation. 

## 8. Conclusion 

We present ToolPulse, an online middleware that supports autonomous tool use by tracking evolving execution states and interaction patterns and providing reminders and guidance through cueing and spotting for clumsy tool-use behaviors and tool-use detours. Our experiments on long-horizon bug-fix tasks show substantive corrective responses to targeted assistance and provide evidence consistent with an overall no-harm profile at the task level. Concise reminders provide effective support, whereas more elaborate assistance offers symptom-dependent benefits and can even be less effective than concise reminders. Auxiliary-model advice provides no consistent advantage over simpler cueing. Resource savings are observed in selected settings and depend on the combination of backbone, task, and assistance form.

These findings motivate a broader engineering role for the agent’s runtime environment. An environment can contribute to task progress by maintaining evidence about how tool use unfolds and returning assistance when that evidence warrants attention. ToolPulse provides an initial realization of this role, with the executing agent retaining responsibility for subsequent decisions. This perspective makes supporting agents in adjusting their tool use and sustaining autonomous task progress an explicit design objective alongside task-solving capability. It also places the quality of assistance in the relationship between execution evidence, the agent’s response, and the resulting task outcome. A promising direction is to develop runtime support that adapts to the working rhythms of different agents throughout their agentic loops. Such support would need to determine when different levels of intervention help the agent resume productive task execution. ToolPulse offers a starting point for investigating whether these capabilities can become reusable infrastructure across agents and task settings. The longer-term opportunity is to develop an execution infrastructure in which agents, tools, and runtime support work together to sustain reliable autonomy across complex tasks and changing environments.

A.2. Detection Rules and Intervention Prompts 

Interaction timing. We distinguish a detection trigger from an injected reminder . A trigger satisfies a detection rule, whereas a reminder is a message that passes the online suppression policy and is actually delivered to the agent. If multiple Action types qualify at the same step, include all of them. 

Shared Action conditions. Duplicate Action occurs when two consecutive calls have exactly the same tool name and arguments. The pilot therefore uses a threshold of two consecutive identical calls. Argument equality follows raw-string or canonicalized comparison, including whitespace and key-order handling. Failed Action occurs when a tool call returns an execution error. The executable rule is tool-specific parsing rules. The treatment of expected test failures, intentional error reproduction, and infrastructure errors have exact exclusion rules. Tool names and error types are normalized using normalization rules and error-type taxonomy. Loop Action and Custom Tool Candidate depend on the trajectory representation. Their strategy-specific conditions are given below. For Custom Tool Candidate, the additional eligibility conditions are minimum recurrence and candidate-selection filters. The candidate-generation rule is separate from whether the agent subsequently creates or invokes a custom tool. 

Sequitur. We encode each tool name as one discrete symbol and apply Sequitur to the resulting sequence. A recurring grammar rule (with a minimum expansion length of 3) qualifies as Loop Action under minimum 3 occurrence count. The rule for selecting a recurring sequence as a Custom Tool Candidate requires a minimum grammar expansion length of 3 and 4 non-consecutive repetitions.
