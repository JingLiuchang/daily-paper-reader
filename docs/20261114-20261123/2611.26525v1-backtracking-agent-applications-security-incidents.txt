Abstract 

Agent applications are increasingly deployed, yet agent-specific attacks pose real threats to them. Upon a security incident, organizations backtrack to identify the CEP (com-promise entry point), remediate the damage, and prevent its recurrence. The main artifacts available for backtracking are trajectory logs, which record agent functionalities, and source code; app(lication)-specific function call logs are of-ten fairly limited. However, trajectory logs are at the agent functionality abstraction layer, while the CEP candidates are function calls at the app code execution layer. Due to this semantic gap, the analyst needs to manually inspect the relevant code for each CEP candidate to infer its cor-responding agent functionality. In this work, we present Origin, a backtracking tool for the analyst to submit a small number of queries to identify CEPs that existing tools can-not provide. Our approach poses two challenges: (1) define the intermediate abstraction that captures the mapping re-lationships between the two semantic layers; (2) determine the region-to-variable mapping for constructing the cross-layer graph defined in the intermediate abstraction. Each region is a specific group of agent functionalities. Origin addresses the challenges by (1) the cross-layer dependency graph ( CLDG ) that connects region-inferred functions at the semantic level to the variables in the low-level taint propa-gation subgraph, plus the associated query language, and (2) the region inference algorithm. Case studies on five popular agent applications across eight attack incidents show that an analyst using Origin correctly identifies all the CEPs.

1 Introduction 

Agent applications powered by large language models (LLMs) have been widely deployed. For example, an open-source agent application, GPT-Researcher , accumulated over 24,000 GitHub stars after release [6]. Moreover, enterprise agent applications may increase from under 5% in 2025 to about 40% by the end of 2026, according to a recent Gartner fore-cast [32]. 

> ∗Corresponding author.

Meanwhile, such agent applications are under threat from emerging agent-specific attacks, among which indirect prompt injection (IPI) [29, 36, 48, 76] and memory & context poison-ing (MC-Poison) [23, 63, 82] are the most prevalent two of the OWASP Top 10 threats for agent applications [54]. For instance, a number of IPI CVEs [1, 5, 9, 58] and MC-Poison-based red-teaming [34, 49, 57] have been reported across multiple commercial agent applications. When a security incident occurs in deployed agent ap-plications, organizations backtrack the incident in order to identify the CEP (compromise entry point), remediate the damage, and prevent its recurrence. The main artifacts avail-able for backtracking are: (1) trajectory logs, which record a sequence of agent observations and actions [81] mapping to agent functionalities, such as planning, acting by invok-ing tools, and recalling information from memory [46]; (2) source code of the compromised applications. It is worth noting that application-specific function call logs are often fairly limited: developers may not anticipate which calls are diagnostically relevant to emerging agent-specific attacks and consequently omit the corresponding log printing state-ments [74], or complete logging is disabled due to overhead thresholds and privacy considerations [75, 80]. 

Motivating example. Consider an MC-Poison security incident on GPT-Researcher , where an analyst received an incident report from a user/victim of the application (Sec-tion 3.1). There are three stakeholders: the analyst, the rem-edy administrator (usually the user), and the developers. The analyst aimed to backtrack the incident to identify the CEP, i.e., the function call that first introduced the malicious con-tent to the application (Section 4.3). When the corresponding input arguments of the CEP function call are already logged, the analyst can (1) provide the remedy admin with a concrete, actionable remedy, e.g., the exact poisoned file to remove from a knowledge base that may contain hundreds of docu-ments in various formats; when the corresponding function call log entry is missing, the analyst can (2) deliver to the developers the log printing statement placement around the CEP function call, enabling more efficient logging that makes the application diagnosable for future incidents. 

Identifying the CEPs requires significant manual effort from the analyst. The analyst first triaged and ex-amined the trajectory log and narrowed down the suspect cause to a particular agent functionality (i.e., knowledge-base retrieval). However, it remains difficult to identify the CEPs

based only on the agent functionality since one agent func-tionality typically corresponds to many function calls, and no trajectory log records concrete function calls (Listing 1). Fundamentally speaking, trajectory logs are at the agent functionality abstraction layer, while function calls are at a lower layer (i.e., the app code execution layer). Static anal-ysis on the source code of the application can complement trajectory-log-based agent-functionality-level diagnosis by pinpointing the CEPs through variable-level taint analysis. However, the analysis is hindered by a large set of CEP can-didates: only a small subset is associated with the suspected initial compromise. After log-based pruning, there are still 1,518 candidates left in GPT-Researcher source code; to infer if a candidate belongs to the suspected initial compromise, the analyst spent hours on manual code inspection, detailed in Section 3.1. The main reason is that the code around the candidates carries little agent functionality semantics, and the analyst needs to gather enough evidence along the cor-responding code paths before making a deduction. 

None of the existing approaches can provide stake-holders with the two “can provide” benefits mentioned in the motivating example , since trajectory-log-based failure diagnosis [52, 78, 81], detection-based failure attri-bution [24, 44, 79], and preventive information flow con-trol [28] do not provide the analyst with the CEPs but faulty agent execution state [52, 79, 81], faulty agent [78] or agent-owner [24], and LLM tool calls ( not function calls at the source code level) [28, 44] instead. 

Our approach can provide stakeholders with the two benefits because it backtracks the security incident. 

As mentioned in the motivating example, narrowing the CEPs during backtracking requires significant manual ef-fort since the analyst needs to do code inspection to recover the agent functionality semantics from the program source code. Our insight is to introduce a new intermediate abstraction (Section 4.4) that enables the analyst to write a few queries at the agent-functionality-level, and the query processing outputs can exclude irrelevant CEP candidates directly. However, identifying which CEP candidates seman-tically correspond to specific agent functionalities is hard since program structures and implementations vary, making it difficult to generalize how to identify the mapping rela-tionships. Fortunately, we observe that agent functionalities can be grouped into a small number of regions depending on the type of information source (Section 2) with which they interact. Each region is a set of program variables that imple-ment agent functionalities of the same group. The variables that receive the return values of the CEP candidates are also included. Based on this insight, we build a tool named Origin that realizes this abstraction as a graph across two layers. Origin takes as input the source code of an agent application and a small set of developer-provided la-bels, and produces the cross-layer graph that can be queried by analysts using a query language during security incident investigations: (i) narrow down candidates at the region lev-el/layer, (ii) identify the CEPs at the variable level. 

Challenges. Our approach poses two challenges. First, de-fine the intermediate abstraction that captures the mapping relationships between two semantic layers: the agent func-tionality layer vs. the application code execution layer. Since the implementation of the same agent functionality by dif-ferent agent applications varies (e.g., the functions/variables naming, the used agent frameworks), we believe such an in-termediate abstraction can provide an analyst with the same interface when backtracking security incidents of different applications. Second, constructing the cross-layer graph (de-fined in the intermediate abstraction) requires determining which region each variable belongs to. This is because a vari-able’s region is determined by which information source its data came from or flows into, but a variable’s name, type, or enclosing function does not carry these semantics. 

Solutions. For the first challenge, we design the Cross-Layer Dependency Graph ( CLDG ) (Section 5) that connects region-inferred functions to the underlying variables in the taint graph through cross-plane edges. We also design the as-sociated query language. As in BackTracker [45], the essence of backtracking is dependence analysis. Since the agent ap-plication CEPs are specific function calls, static taint analysis is suitable to identify the two types of dependencies a back-tracking tool can rely on: variable-level data dependencies and function-level data dependencies. For the second chal-lenge, we design region inference (Section 6.3) that mimics the analyst’s code inspection process by rules, which requires only a small set of developer-provided labels and automati-cally infers the regions for the variables. 

Contributions. We make the following contributions. 

• We design the CLDG plus the associated query lan-guage , a new intermediate abstraction that bridges the semantic gap between agent-functionality-level reasoning and program-variable-level application code execution. 

• We design region inference , a technique that maps pro-gram variables into the relevant regions by rule-guided propagation of label information to the relevant functions along tainted program paths. 

• We build and evaluate Origin on five real-world agent applications across eight attack incidents. Origin correctly identifies every CEP with a single candidate per incident, reducing the analyst’s inspection scope by 64–94% com-pared to the full taint graph and replacing exhaustive source code inspection with region-guided diagnosis. To foster research on this topic, we will release the source code of Origin to GitHub. 

2 Background 

Agent Applications. An LLM-powered agent application 

interacts with diverse information sources for implementing 

> 2

various agent functionalities (e.g., perceiving the user instruc-tions, planning, acting by invoking tools, and recalling infor-mation from memory) [46]. Such applications produce tra-jectory logs to record the invocations of agent functionalities during a concrete execution [52, 81]. Two types of information sources are: (1) external information sources outside the appli-cations, including but not limited to user inputs, interactions with humans or agents, sensor readings, network-accessible content (e.g., web pages and emails), and LLM-generated con-tent; (2) internal information sources within the applications such as knowledge bases and memory. The memory stores multi-round interactions between the user and the agent, persisted on disk in either original or summarized form, so that the agent can recall prior context across sessions [46]. 

Attacks on Agent Applications. Agent-specific attacks such as IPI [36, 48, 76] and MC-Poison [23, 54, 82] compro-mise the agent applications by injecting manipulated content into legitimate information sources of the applications. MC-Poison attacks usually involve two phases that occur in sep-arate executions: a poisoning phase , in which malicious data is written to an internal information source, and an exploita-tion phase , in which the stored data is retrieved and causes harm. In some incidents, poisoning occurs outside the appli-cation (e.g., an attacker directly modifies a knowledge base document), and only the exploitation phase is observable. 

Static Taint Analyzers. Existing taint-analysis frameworks such as Joern [7], Pysa [17], and CodeQL [4] can already com-pute propagation paths over program variables and expres-sions. These capabilities can be repurposed for backtracking agent application security incidents. However, they expose only program code-level semantics and do not provide ab-stractions aligned with agent functionalities. 

3 Motivation 

3.1 Motivating Example Security Incident. Consider GPT-Researcher , an agent ap-plication that conducts research for users and generates syn-thesized content [6]. A security analyst receives an incident report from a user of the application. The report states that the application produced a research synthesis containing incorrect information for one particular research task, while other tasks were completed correctly. The report includes: a description of how the application is used, a PDF of the research synthesis, a trajectory log [81] of the application (Listing 1), and the application’s source code. According to the user description, the application used both a knowledge base and web data for this failed task. The analyst listed three likely accident causes: the LLM was hallucinating, the scraped webpages were manipulated, or the knowledge base was poisoned, where the latter two are security-oriented. 

Three Stakeholders. There are three stakeholders in the incident: the analyst, the remedy administrator (usually the user), and the developers. The remedy admin needs a con-crete, actionable remedy for the damage, e.g., removing the exact poisoned file from the knowledge base with hundreds of documents; the developers need the log printing statement placement suggestion that makes the application more diag-nosable for future incidents, e.g., log the parameter values of the function call corresponding to the initial compromise im-mediately before that call (Listing 2, Line 83). To provide the two stakeholders with the two benefits, the analyst aimed to identify the CEP, i.e., the function call that first introduced the malicious content to the application (Section 4.3). 

Log Triage. To identify the CEP of the incident, the analyst first triaged the trajectory log (Listing 1), which records the user task, the application’s research plan, links to scraped webpages, and HTTP requests to an LLM provider. These coarse-grained traces were sufficient to rule out LLM halluci-nation and manipulated webpages, leaving knowledge-base poisoning as the remaining suspect cause. However, the log could not help identify which function call is responsible for the initial compromise (i.e., retrieving poisoned content from the knowledge base), because the trajectory log did not record concrete function calls. Fundamentally speaking, tra-jectory logs are at the agent functionality abstraction layer, while function calls are at the app code execution layer.

3.2 Limitations of Existing Approaches 

Existing approaches for analyzing and defending agent appli-cations cannot provide stakeholders with the two benefits illustrated above. The main reason is that trajectory-log-based failure diagnosis [52, 78, 81], detection-based failure attribution [24, 44, 79], and preventive information flow con-trol [28] do not provide the analyst with the CEPs . They instead provide the analyst with the faulty agent execution state [52, 79, 81] (e.g., an agent forming an incorrect plan), faulty agent [78] or agent-owner [24], and LLM tool calls (not function calls at the source code level) [28, 44]. 

4 Approach Overview 

4.1 Scope 

Existing agent applications can be classified into two cate-gories: predefined workflow (C1), where application source code rather than LLM decides control flow among agent functionalities; OpenClaw-like agents [2, 13, 15] (C2), where the LLM decides at runtime which agent functionality to invoke next. The C2 agents have recently emerged; however, most existing applications belong to C1. Our approach is directly motivated by C1, not by C2. Hence, the scope of this work is C1; C2 and agent library frameworks [8, 11, 65] are out of scope and remain an area for future research. 

4.2 Threat Model 

We assume that adversaries can launch two categories of agent-specific attacks by methods proposed in existing works: IPI [36] and MC-Poison [23, 30]. The two attack classes are the most prevalent among the OWASP Top 10 threats for agent applications and can cover all the risk categories in the report that target agent functionalities of the applica-tions [54]. The remaining categories are either risks inherited from traditional software security (i.e., remote code execu-tion, privilege escalation, and supply chain integrity), or those reside outside the application (i.e., inter-agent commu-nication protocol, social engineering, and insider threats). Note: the non-protocol part of the insecure inter-agent com-munication risk category can be caused by IPI and MC-Poison. Such an attack incident is investigated in Section 9.3. 

4.3 Compromise Entry Point 

The agent-specific attack classes in Section 4.2 share a com-mon characteristic: malicious data enters the application through the return value of an API call and propagates through data flow to cause harm. We define the compromise entry point (CEP) based on the characteristic and standard static taint tracking [73]. Given a security incident in an agent application, the CEP is identified by: (i) the name of the API call whose return value contains the malicious data, (ii) the name of the corresponding source code program file, and (iii) the line number of the call site. We also provide the analyst with a set of taint propagation paths, where each path starts from a variable receiving the return value of the CEP function call and ends at a variable capturing the at-tack effect. Each variable in the paths is contained in exactly one function. Mapping each variable to its enclosing func-tion gives a function-level path: the sequence of functions through which the data passes from entry to effect. 

4.4 Problem Statement Our insight: the need for an intermediate abstraction. 

As the motivating example illustrates, the analyst reasons about executed agent functionalities observed from the tra-jectory log (e.g., “which code retrieves from the knowledge base?”), while static taint analysis operates at the level of program variables. However, no existing static analysis tech-nique can determine which program variables semantically correspond to which specific agent functionalities, because program structures and naming conventions vary across applications, making it hard to generalize such a mapping. Fortunately, we observe that agent functionalities can be grouped into a small number of groups based on the type of information source (Section 2) with which they interact. For instance, retrieving from a knowledge base and recalling memory are distinct functionalities, but both interact with internal information sources; hence, they belong to the same group. We call such a group a region : a set of program vari-ables that collectively implement agent functionalities of the same group. An analyst can query at the region level (e.g., “which region is for retrieving content from the knowledge base?”); the query processing outputs can exclude irrelevant CEP candidates directly, without manual code inspection. Concretely, the intermediate abstraction is composed of four elements: (1) a region set that partitions agent function-alities into finite groups; (2) a region-to-variable mapping 

that associates each region with the program variables that implement it; (3) a region-level query interface (including the 

> 4

query language) through which analysts express their diag-nostic queries in terms of regions rather than variables; (4) a 

region-to-variable query mapping that translates region-level queries into variable-level queries, supported by existing static analysis infrastructure. The goal of this work is to design a tool that realizes the new abstraction. 

4.5 Challenges Challenge 1: Define the intermediate abstraction that captures the mapping relationships between two se-mantic layers: agent functionality layer vs. the appli-cation code execution layer. The implementation of the same agent functionality by different agent applications varies (e.g., the functions/variables naming, the used agent frameworks). We believe such an intermediate abstraction is needed so that an analyst can use the same interface for backtracking security incidents of different applications. 

Challenge 2: Constructing the region-to-variable map-ping. The abstraction requires a concrete mapping from regions to program variables (element 2). No existing static analysis technique can infer agent functionalities from pro-gram source code. As illustrated in Section 3.1, variable names, such as ret_data , loader_dict , and loader in the function _load_document , do not carry the hints that they are used for retrieving from a knowledge base. Therefore, it is hard to determine which region they belong to.

5 Cross-Layer Dependency Graph 

The CLDG realizes the intermediate abstraction as a directed graph of two planes: the function plane and the variable plane .

Definition 5.1 (Cross-Layer Dependency Graph) . Let 𝑃 be an agent application with the function set F . The Cross-Layer Dependency Graph 𝐺 = (R , 𝑉 fn , 𝜆, 𝐸 cross , 𝑉 var , 𝐸 var ) of 𝑃 is a two-plane directed graph, where: 

• Region set. R is a mapping from each region name to a set of agent functionalities. Each agent functionality is a mapping from the functionality name to a set of functions in the agent application program. Five representative regions (detailed in Appendix A) are: Per (Perceiving), PA (Planning & Acting), RR (Recalling & Reflecting), PK (Prompt Kitchen), and UNK (Unknown). 

• Function plane. 𝑉 fn ⊆ F is the set of functions reachable from all API calls in 𝑃 via taint propagation. 𝜆 : 𝑉 fn →R ∪ { UNK } assigns each function node its inferred region. 

• Variable plane. 𝑉 var is the set of program variables reach-able from all API calls in 𝑃 via taint propagation, and 𝐸 var ⊆

𝑉 var × 𝑉 var is the set of taint edges among them. The same variable in different code statements is treated as different nodes (with different identifiers) in the variable plane. 

• Cross-plane edges. 𝐸 cross ⊆ 𝑉 fn × 𝑉 var connects each func-tion node 𝑓 to every program variable defined/used in 𝑓 .

The region set R can be determined by the security ana-lyst as long as the mapping relation is provided. Our design is applicable to any analyst-defined region set. Once a partic-ular region set is adopted, Origin requires a corresponding function-to-information-source mapping table from develop-ers of the agent application (Section 6.1). In addition, every cross-function taint edge in the variable plane is naturally mapped to an edge connecting two functions. Such edges appear on the function-level paths mentioned in Section 4.3. 

6 CLDG Construction 

Constructing the CLDG involves two steps: (1) taint propa-gation to build its variable plane (Section 6.2) and (2) infer regions for nodes in the planes (Section 6.3). Step (2) requires developer knowledge as input (Section 6.1).

6.2 Taint Graph Construction 

With the developer labels in place, Origin constructs the graph. The variable plane ( 𝑉 var , 𝐸 var ) is produced by perform-ing context-, flow-, field-sensitive forward taint propagation from the return values of every API call (implementation described in Section 8). Because propagation starts from all API calls, any CEP function call that matches the definition in Section 4.3 lies on a path in the variable plane and is locat-able by queries against the CLDG . 𝑉 fn and 𝐸 cross are derived from the variable plane: 𝑓 ∈ 𝑉 fn if any of its variables appears in 𝑉 var ; 𝐸 cross connects each function to its variables. 

6.3 Region Inference 

The region inference algorithm implements the region-to-variable mapping element in the abstraction (Section 4.4). The goal is to classify the functions in the function plane of  

> CLDG

into the five regions detailed in Appendix A. We observe that a naive feature-based clustering approach, i.e., clustering by function names, API names, or program code syntactic features, is not suitable for this task: (1) func-tions/APIs of the same name could implement completely different agent functionality in different agent applications, and thus belong to different regions. For example, two func-tions named load may read a webpage (fall into the PA re-gion) or read a file from a knowledge base (fall into the RR 

region). Similarly, (2) syntactically similar string operations, e.g., x.format(y) , may be used for prompt assembly or for non-agent functionalities, e.g., composing an error message. Fortunately, we find that an analyst, fully aware of the semantics of the five regions, usually gathers evidence dur-ing code inspection to answer four questions, and the fusion of the answers can determine which region a function be-longs to: (1) does the function interact with information source(s)? (2) does the function read from or write to the information source(s), or do both? (3) if the function interacts with multiple information source(s), which type of informa-tion source dominates (Section 2)? and (4) is the function mainly assembling prompts to appear in the LLM context window? Origin uses two categories of rules to mimic the aforementioned analyst’s reasoning process during code inspection for region inference: 

Label propagation rules (3 in total) mimic the process of gathering evidence to answer the four questions about a function. Two rules propagate (along the tainted paths) the labels of the API calls that interact with information sources. Concretely, the two rules are: (1) if an API call reads an infor-mation source, propagate the label forward; (2) if an API call writes an information source, propagate the label backward. We also have a rule for propagating a special label of func-tion calls that assemble prompts rather than interact with information sources. Prompt-assembly-related function calls are assigned with such a label (e.g., text-composition func-tions like format ; function names or parameters with special names consisting of “prompt”). This rule propagates labels only within a function because we observe that prompt as-sembly is an agent functionality local to discrete function(s). 

Condition-action rules (9 in total, Table 1) mimic the an-alyst’s reasoning process of region determination by com-bining answers to the four questions against the gathered evidence. For example, if a function receives a user request, it gathers the label of an external information source and no label of prompt assembly according to the label propagation rules; consequently, it is classified into the Per region, which only passively reads external information sources. Our evaluation shows that the two categories of rules work well in practice (Section 10.4). Meanwhile, our condition-action rules are intended to be practical rather than exhaus-tive. Initially, we observed that agents usually prepare a prompt shortly before writing to the LLM context window.

7 Query Processing 

Given a constructed CLDG , the analyst investigates a security incident by issuing queries against it using a query language. 

7.1 Query Language 

The query language implements the region-level query inter-face element in the abstraction (Section 4.4). The full gram-mar is provided in Appendix B. Each query begins with the keyword CHECK , followed by one or more atomic formulas joined by logical connectives. An atomic formula consists of the predicate DEPENDS_ON ,which asserts a taint data flow between two terms. A term can be either a region name or a program variable identifier, allowing queries at the region level or the variable level. Log-ical connectives include AND and OR . For example, CHECK (PK DEPENDS_ON PA) AND (PA DEPENDS_ON PK) is a commonly used region-level query for backtracking IPI incidents by an analyst (Table 5). The atom PK DEPENDS_ON PA asks whether data from the PA region (e.g., the crawled webpage), can flow into the PK region (e.g., to assemble a prompt). Similarly, the atom PA DEPENDS_ON PK asks whether data in the PK region (e.g., the assembled prompt) can flow back to the PA region (e.g., the LLM takes the prompt as input and the generated content flows to write a document). The language also provides a chaining operator →: the formula after → is evaluated against the subgraph returned by the preceding formula, allowing the analyst to progres-sively narrow down the variable-level results. For example, after writing the aforementioned region-level query, an ana-lyst can write →, followed by a second region/variable-level query. Origin first evaluates the first query; if the result is not empty, it continues to evaluate the second query against the result of the first query (Section 7.2). 

7.2 Query Evaluation 

This subsection implements the region-to-variable query map-ping element of abstraction (Section 4.4). 

Region-Level Query Evaluation. A region-level query, such as CHECK PA DEPENDS_ON RR , returns a data depen-dency graph over function nodes through two steps: (1) iden-tify the variables in 𝑅 src functions and the variables in 𝑅 sink 

functions by using 𝜆 and 𝐸 cross ; (2) compute forward reacha-bility from the 𝑅 src variables and backward reachability from the 𝑅 sink variables in the variable plane, producing two sets of reachable variable nodes. The intersection of these two sets contains all variables that lie on some taint path from 

𝑅 src to 𝑅 sink . An edge (𝑓 1, 𝑓 2) appears in the result if a taint edge in 𝐸 var connects a variable in 𝑓 1 to a variable in 𝑓 2 within this intersection. When a query contains logical connectives, 

AND and OR combine result graphs by intersection and union of their node and edge sets, respectively. 

Variable-Level Query Evaluation. In a variable-level query, the source and sink are specified by their node identifiers in the variable plane (visible when the analyst inspects a function’s variables in the region-level query result). For ex-ample, CHECK node.5110 DEPENDS_ON node.4216 queries whether there is a taint path from variable 4216 to variable 

5110 . To evaluate the variable-level query, a naive graph slicing of the CLDG variable plane may include paths that are not feasible in any real execution. Origin uses the applica-tion’s call graph and control flow graphs constructed during  

> CLDG

construction to enumerate only the control-flow feasi-ble taint paths between the source and sink variables. The returned paths are variable-level taint paths. As mentioned in Section 4.3, the taint paths can be naturally mapped to the corresponding function-level paths. 

8 Implementation 

We implement Origin as a Python program ( ∼16 KLoC) on top of Joern (v4.0.360) [3], with type inference enhancement by Pyrefly (v0.45.0) [16]. We address three limitations of Joern that cause false negatives in taint propagation. First, Joern does not parse generator expressions; we rewrite yield 

and yield from to return before analysis. Second, taint stored in class instance variables (e.g., self.x ) is not tracked across functions; we propagate it explicitly via control-flow graph reachability. Third, Joern’s call graph is incomplete under dynamic dispatch. We first incorporate type-informed indirect call resolution by patching Pyrefly [16]; then we infer the targets of indirect calls by following Xia et al. [67] and Liu et al. [47] with two enhancements: context-sensitive type chain tracking in place of a global type-chain map, and value set analysis in place of full data-flow analysis.

9.1 Shared Backtracking Workflows 

The analyst’s backtracking workflows are similar across the investigated incidents, despite the diversity in attack classes and entry points. Specifically, the analyst (i) identifies the sus-pect agent functionality from the trajectory log, (ii) submits a region-level query, (iii) inspects the resulting graph to iden-tify variable-level taint source/sink candidates, (iv) selects the source/sink to submit a variable-level query, and (v) iden-tifies the CEP and the corresponding paths. Typically, a CEP identification requires two queries (Table 3): one region-level query to narrow down the scope and one variable-level query to pinpoint the CEP. We show in Section 9.2 that inspecting the resulting graph of a region-level query usually narrows down the source/sink candidates for a variable-level query to one or two, respectively. With the knowledge obtained from the trajectory logs, the analyst can have a suspect ranking for source and sink candidates (detailed in Appendix C). In our case studies, these help the analyst submit the correct variable-level query with minimal trials. Besides, for attack incidents that span multiple phases in separate executions (e.g., Quivr MC-Poison (M)), the analyst repeats steps (i)–(iv) for each phase before identifying the CEP. 

We observe that the variable-level query result, presented as a set of function-level paths, is typically sufficient for the analyst to identify and understand the CEP without inspect-ing the underlying variable-level taint propagation paths. In the Quivr MC-Poison (M) incident, the attack spans two phases (Section 2). The analyst submitted one variable-level query for each phase and obtained two valid function-level paths. Although the two paths correspond to two execu-tions within different time periods, the analyst identified the shared function call arguments (i.e., the chat_history table of Supabase) in the source node (blue, RR region) of Phase A path and sink node (blue) of Phase B path. This indicated that the malicious content can be first written to the agent memory in a chat with the attacker; then be retrieved back in another chat with the user. Therefore, the CEP is identified as the function call to the user-chat interface. The full incident and its backtracking process are detailed in Appendix C.1. For simpler single-phase incidents such as the motivating GPT-Researcher MC-Poison (KB) case, the analyst can di-rectly identify the CEP by examining the function-level paths returned by a variable-level query (detailed in Appendix C.2). 

9.2 Common Practices for Graph Inspection 

We report the common practices in step (iii) graph inspection, which replaces the time-consuming source code inspection: 

(a) Not all nodes in the resulting graph of a region-level query require inspection. The graph contains nodes from the regions specified in the query as well as nodes from other regions that appear because they lie on the taint paths between the queried regions. Each node is colored by its region, so the analyst usually focuses only on nodes whose colors correspond to the queried regions and skips the rest. For example, in the Quivr MC-Poison (M) incident (phase A), the region-level query returns a graph of 21 function nodes, but only the 3 Per nodes (green) and 5 RR nodes (blue) match the queried regions and need examination (Figure 2(a)). 

(b) Among the relevant nodes, it requires examining only a small number (usually less than 10) of function names and an even smaller number (usually 2 or 3) of variable-plane taint subgraphs corresponding to the functions. As in Figure 2(a), to identify the taint sink, the analyst examined the names of 3 green nodes of Per region, found create_question_handler 

relevant to the incident, and clicked it to reveal a variable-plane taint subgraph of a single node (Figure 3 in Appendix) that is identified as the sink candidate. The analyst then takes a similar process to identify the taint source candidate from the 5 blue nodes of RR region. The entire process requires only examining 8 function names and 2 taint subgraphs, which is a huge manual effort reduction compared to 2,615 LoC of Quivr’s source code inspec-tion (Table 2). Origin also provides features that help the analyst handle larger graphs more efficiently, which are de-tailed in Appendix C.2 (Figure 4) and Appendix C.4 (Figure 5).

10.5 Inspection Scope Reduced by Region-level Queries (RQ3) 

Region-level queries can significantly reduce the graph in-spection scope for the analyst. We measure this by comparing 

|𝑉 𝑞 |, the number of variable-plane nodes in the region-level query result, against |𝑉 var |, the full variable plane of the CLDG .Lower |𝑉 𝑞 |/| 𝑉 var | means the analyst encounters a smaller fraction of the taint graph. As shown in Table 5, across all incidents, region-level queries reduce the variable plane to between 6.49% and 35.76% of its original size. We note that: 

(a) PK is a key factor in this reduction and appears in 9 of the 11 region-level queries. This is because PK is where data from other regions converges to be assembled into the LLM prompt, and it typically contains very few functions (e.g., 1 in Quivr, 2 in aider, 3 in SWE-agent; more details in Appendix A). When a query involves PK, the returned graph is limited to function nodes that are transitively connected to this small set of PK functions, which substantially reduces the number of variable-plane nodes the analyst must inspect. 

(b) The reduction ratio also depends on the size of the regions involved in the query, which varies across applications. The IPI incidents across the four applications use the same query 

CHECK (PK DEPENDS_ON PA) AND (PA DEPENDS_ON PK) ,yet the ratios range from 9.56% (SWE-agent) to 35.76% (GPT-Researcher). Regarding the ratio difference, we observe that a larger PA in an application often gives a larger result graph: PA contains 133 of 244 functions in GPT-Researcher but only 64 of 160 in SWE-agent (more details in Appendix A).

11 Discussion 

Framework-Induced Indirect Call Resolution. Our static analysis cannot resolve framework-induced indirect call tar-gets (e.g., LangChain [8] tool dispatch). This causes the corre-sponding taint propagation path to be missing from the CLDG .Addressing this limitation requires either framework-specific modeling or dynamic analysis, which is future work. 

Agents with An LLM-driven Agentic Loop. Autonomous agents such as OpenClaw [15] and Hermes [13] are driven by an agentic loop in which, for each iteration, the LLM decides at runtime which agent functionality to invoke next. For such agents, static analysis alone cannot determine the CEP function call (e.g., which tool introduced the malicious data), except for the case discussed in Section 9.3, Finding (b). This remains an area for future research. 

12 Related Work 

Root Cause Analysis for Software Systems. Diagnos-ing the root cause of exploits and failures in software sys-tems is the first step to repairing programs. Most existing works are based on backtracking [20, 27, 70, 71], reconstruc-tion [26, 33, 38, 72], or statistical analysis [19, 42, 43, 55, 69]. These approaches focus on diagnosing the buggy code lo-cation(s) triggering memory safety violations [19, 20, 26, 27, 38, 55, 69–72] and data races [42, 43]. However, in agent application security incidents, the application code itself is not buggy in terms of condition expressions and statement orders. The problem is that the application lacks validation or sanitization at the boundary between untrusted external information sources and the application. Consequently, the attacker-controlled data is entered through a legitimate API call and propagated through the pipeline unimpeded. 

Causality Analysis for APT Attacks. A large body of work investigates APT attacks by constructing attack provenance graphs from OS-level audit logs [31, 35, 45, 53]. Subsequent work refines the granularity of logs by partitioning long-running processes into finer execution units [40, 50, 51] or by fusing application-layer logs with system audit data to recover application semantics [37]. The logs and audit data used in these systems are sufficient for analyzing traditional APT attacks. In agent applications, however, analysts rely on trajectory logs and static analysis on program code. Trajec-tory logs record agent behaviors at the agent functionality abstraction layer but miss the app-specific function call log-ging needed for pinpointing the CEP function calls. Static analysis does not provide the agent-functionality semantics that analysts need for reasoning. The bridging between the agent functionalities and the program code is difficult due to a semantic gap. Our work addresses this by implementing an intermediate abstraction that connects them. 

Agent Application Attacks and Defenses. Agent attacks have targeted a wide range of commercial and open-source agents [56], most notably IPI attacks [29, 36, 48, 76] and MC-Poison attacks [23, 63]. In real-world settings, adversaries often employ compound attacks that combine both methods across different stages of agent execution [77]. Defenses have been proposed at multiple layers: data-instruction separation-based LLM hardening [21, 22, 62] 

> 12

and prompt hardening [39] against IPI attacks, memory writes/retrieval-stage filtering against MC-Poison attacks [60, 64, 68], and application-level taint tracking and policy enforcement at runtime [25, 28, 41, 59, 66]. All these defenses, however, are preventive in nature and can still be bypassed. When an attack does succeed, we still need to backtrack the initial compromise of the incident. In addition, detection of IPI attacks and MC-Poison attacks has been investigated in [44, 79] and [61, 64], respectively. However, detection and diagnosis (through backtracking) are two different problems. 

13 Conclusion 

We present Origin, a backtracking tool for security incidents in agent applications. Origin implements a new interme-diate abstraction as CLDG , which connects region-inferred functions with variable-level taint subgraphs, and provides the associated query language that allows analysts to identify the CEPs with a small number of queries. Origin constructs the region-to-variable mapping in the CLDG by rule-guided region inference, which only takes a small set of developer-provided labels. Case studies on five applications and eight diverse attack incidents show that an analyst using Origin can correctly identify the CEPs of all incidents.

A Configured Region Set 

Region set. Our observations, consistent with prior work [81], show that program variables serving the same agent func-tionality cluster naturally into five regions as follows: 

• Perceiving (Per): Variables that receive input from external sources where the application does not initi-ate the interaction (e.g., user queries, incoming agent messages, sensor readings). 

• Planning & Acting (PA): Variables that store LLM-generated responses and variables involved in application-initiated interactions with external sources (e.g., tool invocations, outgoing messages to other agents). 

• Recalling & Reflecting (RR): Variables that retrieve information from internal sources (e.g., knowledge bases, experience repositories, execution logs) or store summarized experiences derived from prior activity. 

• Prompt Kitchen (PK): Variables that assemble prompts for the LLM context window, which combine informa-tion drawn from the other three regions into a coherent input. 

• Unknown (UNK): Variables that implement function-alities not belonging to the Per , PA , RR , or PK regions.

24 E Failure Analysis of Existing Tools 

Existing static taint analyzers do not support end-to-end CEP identification. We therefore provide the ground-truth CEP as the source and the operation capturing the attack effect as the sink. We evaluate whether their outputs satisfy the tool-specific success criteria for verifying the given CEP. We then examine the causes that prevent verification of the given CEP in Table 4. The used tool versions are: Joern 4.0.360, CodeQL CLI 2.27.0 with codeql/python-all 7.2.5, and Pysa 0.9.25. Table 11 reports the findings for every incident, phase, and tool; the following subsections explain selected examples. 

E.1 Unresolved Indirect Call Targets 

An incomplete call graph omits possible targets of a call. When an unresolved callee returns a tainted value, the ana-lyzer may fail to propagate that taint to the caller. In GPT-Researcher’s IPI case, scraper.scrape_async() 

retrieves webpage content and returns it to the caller, which assigns it to content (Listing 5, #6). Pysa cannot resolve which function this call invokes, so it cannot propagate the tainted webpage content returned by that function to content . Pysa’s fallback taint model propagates taint from arguments to a call’s return value. However, 

scrape_async() takes no explicit arguments: the webpage content is retrieved inside the callee, rather than passed into the call. The fallback therefore does not mark the returned value, or content , as tainted. Pysa also cannot resolve the target of browse_urls 

(Listing 5, #11), which prevents the returned tainted value from reaching scraped_content . In our diagnos-tic experiment, we added type casts to a copy of the application’s source code and reran Pysa. The casts tell Pysa to treat scraper as a NoDriverScraper and 

self.researcher.scraper_manager as a BrowserManager .With both casts, Pysa reported the call to write_md_to_pdf 

at main.py:28 , indicating that its report argument contains tainted webpage content. This call lies on the expected attack path and therefore satisfies our Pysa success criterion. With either cast alone, Pysa did not report this call.

E.2 Missing Data Dependencies Through Language Constructs 

Taint propagation can be interrupted when an analyzer does not fully represent the data dependencies of a language con-struct (e.g., nested dictionary accesses, comprehension). This includes argument binding, container accesses, object con-struction, and field access. In SWE-agent’s IPI case, tool_call["function"] ["arguments"] reads the tool call’s arguments through two nested dictionary accesses (Listing 7, #2). The first retrieves the dictionary describing the requested function; the second retrieves a JSON string containing the argu-ment names and values. json.loads converts this string into the Python dictionary values . Joern represents both accesses but omits the data-dependence edge from the first access’s result to the second access. Consequently, taint reaches the inner dictionary but not the argument string. In a source-code copy, we separated the accesses into function = tool_call["function"] and values = json.loads(function["arguments"]) . With the other diagnostic changes held fixed, Joern then propagated taint to values without an additional JSON-decoding model. In GPT-Researcher’s IPI case, CodeQL fails to propagate taint through an awaited tuple return. The tuple returned by scrape_async() contains webpage text, which the caller assigns to content (Listing 5, #5–#7). CodeQL does not carry the text’s taint across the await expression to this variable. E.3 Missing Data Dependencies Across API Calls 

An API call may read, transform, or store data. To follow tainted data through the call, the analyzer needs to know what the API does with it. The analyzer can obtain this information by analyzing the API’s implementation or using a summary that describes how data flows through the API. If the relevant behavior is neither analyzed nor summarized, the analyzer may lose track of the tainted data at the call. We include database insertion/readback within an API operation here; separate writes and later reads across application stages belong to Section E.4. In Quivr’s memory-exploitation case, the application sup-plies stored user and assistant messages to a model chain to generate a new answer. It then stores the answer in the data-base, constructs a ChatHistory object from the returned record, and returns that object from the handler. After we supplied rules connecting the configured history source to its message fields, CodeQL propagated taint to the model-chain input but not its result (Listing 8, #2). We added a summary relating the request dictionary to the call result. CodeQL then tracked taint into the generated answer and the record passed to the database insertion, but not into the returned database data (#5–#10). Adding a second summary relating the inserted record to the returned data allowed taint to reach the input of ChatHistory . E.4 Missing Data Dependencies Through Stored Data

1. Labeling task. The task is to determine the function’s EXT or INT label from its direct accesses to information sources. For each call in record.api_calls , the LLM re-ports whether it directly accesses an external (EXT) informa-tion source, an internal (INT) information source, both types, neither, or cannot be classified from the supplied evidence. The function’s label is then computed from these findings. An information source supplies or receives information used in the application’s tasks. EXT denotes a source through which the application obtains new task information or com-municates with users, LLMs, or external services, such as user input, model responses, or public web content. INT de-notes a source that the application maintains for use across tasks, such as its stored conversation history or knowledge base. A function can receive an INT label even when it ac-cesses information over a network. For example, a function that retrieves the application’s stored conversation history from a remote database accesses an INT source. 

2. Code and supporting information. The user message contains six components, each with a separate purpose. 

Function and call record ( record ). The function_key 

identifies the target function by file and name; api_calls 

lists the operations to classify. Each call has an identifier (a0–a5), a source location, and details recording the operation called, the object it is called on, and the arguments passed to it. The tmp names denote intermediate values in the analysis representation. For example, tmp0 holds the query built by the preceding database operations, so 

tmp0.execute() runs that query. This call is listed as a0. Call a5 represents adding each ChatHistory(message) 

value to the result list. The analysis makes this list-building step explicit as tmp5.append(ChatHistory(message)) ,where tmp5 is the result list. Thus, a5 refers to append ,which adds the value to the list; ChatHistory(message) 

creates the value being added. 

29 Labeling guidance ( knowledge.documents ). The prompt includes four documents containing rules and examples to help the LLM judge whether a call directly accesses an EXT or INT information source. Developers can extend this guidance by adding documents or updating the rules and examples to cover additional cases. The current documents explain how to classify only the outermost call in a nested call expression, exclude in-memory operations from information-source accesses, and determine whether a file or URL provides EXT or INT task information. For example, in items.append(read_file(path)) , the outermost call 

append only modifies an in-memory list; it does not perform the file access. Classifying read_file(path) requires additional evidence about the file: a public document is an EXT source, whereas the application’s stored conversation history is an INT source. 

Code excerpts ( source ). Code excerpts can help the LLM understand what each listed call does and how its inputs and outputs are used. The excerpts include the target function and its calling context, such as code around the call site, argument definitions, and uses of the returned values. Each excerpt includes an identifier for citation, its file path and line numbers, and the code itself. In this example, the target function queries the chat_history table using chat_id , and its caller passes self.chat_id as the argument. 

Static analysis results (supporting_evidence ). The prompt also provides program-analysis results that identify possible callees and show how values reach each call’s receiver and arguments. These results help the LLM trace which information source a call accesses. Each result identifies the listed call it describes and references the corresponding code excerpt. The supporting evidence also includes whether each call was resolved to an application-defined function. For example, a0, tmp0.execute() , is marked not_resolved_to_application , indicating that no application-defined callee was identified. 

Coverage summary ( overview ). Even when the full func-tion is supplied, the LLM may still need evidence from else-where in the application to determine whether a call accesses an EXT or INT information source. The coverage summary helps the LLM assess whether the supplied evidence is suffi-cient to classify each call. It reports the number of calls to be classified, the source-code line ranges supplied, and any evidence that could not be retrieved or was omitted. 

Response reminder ( next_action ). The LLM must return a finding for every listed call using the supplied evidence. It cannot request additional evidence or invoke tools. 

3. Decision rules. The LLM assigns one of six call-level decisions to each listed call based on the supplied evidence: 

• EXT : the call directly accesses an EXT source. 

• INT : the call directly accesses an INT source. 

• both : the call directly accesses both EXT and INT sources. This finding requires evidence of both accesses, rather than uncertainty between the two types. 

• application_call : all identified candidate callees are application-defined functions. Their information-source accesses are assessed separately within those functions. 

• no_source_access : the call does not directly access a task information source, such as a call that only formats text or modifies an in-memory list. 

• unresolved : the supplied evidence is insufficient to assign a finding. The LLM must state what information is missing. The available decisions depend on the callee information supplied for each call. A possible application-defined callee excludes EXT , INT , and both ; application_call is available only when all candidate callees are application-defined. In Listing 10, none of the six calls has an identified application-defined callee, so application_call is unavailable. Each decision applies only to the listed call. For a nested call expression, the LLM classifies the outermost call without attributing the inner calls’ information-source accesses to it. Every listed call must receive a decision, including calls in alternative branches. 

4. Required answer. The LLM returns a report explain-ing its call-level decisions for developer review. For each listed call, the report contains one of the six decisions de-fined above, a brief explanation, and references to supporting code excerpts. The report also provides an overall explana-tion, identifies the labeling-guidance documents used, and lists any missing information needed to classify unresolved calls.
