# How Much Should an Agent Remember? Deployment Lessons from Self-Distilled Memory for LLM Agents 

## K. R. Jayaram, Vatche Isahagian, Aswath Vaithinathan Aravindan, Vinod Muthusamy, Punleuk Oum, Gaodan Fang, Michal Ulewicz, Gegi Thomas, and Evelyn Duesterwald 

IBM 

Abstract 

LLM agents on long-horizon tasks fail in recurring, procedu-ral ways. They mis-paginate an API, resolve the wrong entity, or answer when no answer was asked. We built a pipeline that lets an agent learn from its own history. It first mines short 

lessons from the agent’s own trajectories, one to three per episode. It then consolidates those lessons into a smaller set of guidelines , where each guideline records how many lessons it merged. At inference the agent receives either all guidelines or a selected subset. The pipeline ships in the open-source altk-evolve library and is deployed in IBM’s CUGA agent and watsonx Orchestrate platform. We report what we learned building, measuring, and productizing it. Our primary instru-ment is the AppWorld benchmark, across models spanning 40–92% baseline task completion. The central finding is that the right amount of memory is a property of the model, not the memory. A strong model keeps improving as guidelines are added. DeepSeek-V3.2 gains +9.5 points of task completion and +16.1 points of scenario completion with its full 191-guideline set. A weak model gains less from the same full set than from a small selected subset. gpt-oss-120b starts at 39.9% task completion. It reaches 51.2% with all 199 of its guidelines but 55.4% (mean of two runs) with a selected subset of about 29. Around that result we report what went wrong: a high-support guideline that backfired, provenance silently dropped during consolidation, a swallowed API error that failed every task while producing a plausible log, and a baseline confound that nearly produced a misleading comparison with a prior method. We distill these into recommendations for teams de-ploying agent memory. 

## Introduction 

Agents built on large language models fail on realistic multi-step tasks in a distinctive way. We read hundreds of trajecto-ries of IBM’s CUGA agent and of the AppWorld reference agent. The failures are rarely knowledge gaps. The model knows the API, yet it mis-paginates it. It knows the user has contacts, yet it resolves the wrong one. It knows how to return an answer, yet it returns one when nothing was asked. These are procedural lapses, and they recur. That makes them look learnable from the agent’s own history. That observation is now widely shared. Recent systems let an agent write notes about its experience and read them back

later. Examples include ExpeL (Zhao et al. 2024), Agentic Context Engineering (ACE) (Zhang et al. 2026), and re-flective memory in generative agents (Park et al. 2023). In products, Anthropic’s “dreaming” consolidates memory for managed agents (Anthropic 2026). What remains scarce is an account of what happens when such a system is built, measured carefully, and shipped. This paper is that account. Our pipeline has three stages. It first extracts lessons from the agent’s own trajectories: short, imperative notes about what to do differently, one to three per episode. It then consolidates those lessons into guidelines ,a smaller set in which each guideline records how many lessons support it. Finally, it delivers guidelines to the agent at inference, either all of them or a selected subset. The pipeline is part of the open-source altk-evolve library (AgentToolkit 2026). It is deployed in IBM products, including the CUGA agent and the watsonx Orchestrate platform. To measure it we used AppWorld (Trivedi et al. 2024). AppWorld offers three things a deployment needs and a production log rarely provides: an authoritative pass/fail verdict per task, graded difficulty, and a clean train/dev/test separation. The method is not the contribution of this paper. Several of its pieces have precedents, which we credit below. The contribution is what we learned deploying it across models from 40% to 92% baseline task completion. In the spirit of this track, we focus on what went wrong: 

• The right amount of memory is a property of the model. A strong model keeps improving as guidelines are added. A weak model gains more from a small, selected subset than from the same full set (Insight 1). 

• Compressing memory to a tidy checklist discards most of its value. The value lives in one-off, situational lessons (Insight 2). 

• Selection is only possible if provenance survives consol-idation. During productization it silently did not, twice (Insight 3). 

• A frequently derived guideline can still be wrong. Support measures recurrence, not correctness (Insight 4). 

• Run-to-run noise on a fixed configuration is large enough to fabricate a “win” (Insight 5). 

• Comparing memory systems across different agent scaf-folds nearly produced a misleading headline (Insight 6). arXiv:2611.26361v1 [cs.AI] 19 Nov 2026 • Silent failures cost more calendar time than any model-ing problem: a swallowed HTTP error, an idle-dropped connection, and a write hook that never fired (Insight 7). We close with the practices we now apply and with a sec-tion on deployment in IBM’s products. That section reports CUGA benchmark results re-collected after the write-path bug described in Insight 7, with GPT-4.1 and GLM-5.3-Flash, and a qualitative example from watsonx Orchestrate. 

## The System: altk-evolve 

The library. altk-evolve is an open-source library for agents that learn from their own runs (AgentToolkit 2026). Its guideline generation builds on our group’s earlier work on trajectory-informed memory (Fang et al. 2026). It cap-tures trajectories in three ways. It can instrument common client libraries directly (OpenAI, LiteLLM, smolagents, and the OpenAI Agents SDK). It can sync traces from an observ-ability store such as Arize Phoenix. Or an agent can hand over a trajectory through an MCP tool at the end of a task. From each trajectory an LLM extracts short lessons, option-ally after segmenting the trajectory into subtasks. Lessons, and the guidelines consolidated from them, are stored as entities with metadata (category, rationale, trigger, source task, and support) in a pluggable backend: a filesystem store for development, or Milvus or Postgres with pgvector for semantic search. Consolidation clusters related lessons on their source-task embeddings and merges within each clus-ter with an LLM. It is support-conserving: every guideline records how many lessons it merged, and delivery can select by that count. Both are described below. Agents consume memory through an MCP server that exposes tools such as get_guidelines , get_relevant_guidelines ,and save_trajectory . A Python client, a CLI, and a web UI serve developers and reviewers. CUGA connects to the library over MCP. The rest of this section describes each stage as we ran it for this study. 

Extraction. We run the agent on the benchmark’s train and dev splits and keep every trajectory, successes and failures alike. For each trajectory, the extraction stage prompts an LLM to write one to three short imperative lessons about what to do differently next time. Whether a lesson counts as success- or failure-evidence comes from the task’s actual outcome, as judged by the evaluator. It never comes from the LLM’s self-report. For DeepSeek-V3.2, 147 train/dev trajectories yield 290 raw lessons. Of these, 62 come from failures and 228 from successes. 

Why consolidation is forced. Raw episodic memory does not stay small. Most of what accumulates is near-duplicate. Five different tasks discover pagination the hard way, and all five write it down. Left alone, this breaks the natural delivery mechanism, retrieval. The top-k slots fill with copies of the same lesson. Genuinely different guidance is crowded out. Irrelevant one-offs arrive as dead context. Consolidation is therefore not a cost optimization. It is what makes memory retrievable at all. 

Support-conserving consolidation. The consolidation stage embeds the lessons and clusters near-duplicates. It then prompts an LLM to merge only within a cluster, and only when following one lesson is equivalent to following the other. Each surviving guideline carries a support count: how many independent lessons collapsed into it. It also carries a merged evidence polarity (success, failure, or both). One in-variant is enforced: the sum of support over the output equals the number of raw lessons. Anything the LLM fails to cover is carried through unchanged. For DeepSeek this turns 290 lessons into 191 guidelines, of which 144 have support one. 

Delivery. A guideline set can be injected statically, or delivered by retrieval. In retrieval, a core of high-support guidelines (support ≥ 3) is always included. The top-k fur-ther guidelines are then added, chosen by how similar their 

source task is to the current task. Candidates already cov-ered by the core, or duplicating one another, are dropped. Thresholding by support (“sup2”, “sup3”) happens at selec-tion time and never deletes anything from the store. In altk-evolve these are configuration: consolidation_mode ,

min_support , core_support , retrieval_top_k ,and injection_mode .

Deployment constraint. altk-evolve generally uses the same model that the agent uses. In this study, the model that ran the agent is also the model that extracted its lessons and consolidated them. There is no separate teacher model and no human labeling. This mirrors the deployment we care about, an agent that improves from its own logs. It also makes the capability-dependence in Insight 1 an unavoidable design question rather than a curiosity. 

## Measurement Setting 

AppWorld simulates nine applications (email, payments, music, shopping, and others) behind 457 APIs and about a hundred simulated people (Trivedi et al. 2024). Its 750 tasks require writing and executing Python against those APIs. We use test_normal (168 tasks) throughout and 

test_challenge (417 tasks) where noted. The agent is the reference ReAct code agent. Each step is one model call that writes Python, and the environment returns the output. We report two metrics. TGC is the fraction of tasks that pass all of their evaluation checks. SGC is the stricter fraction of scenarios in which every task variant passes. Eight models were baselined and six were run with memory. All memory is mined from train/dev only. Because dev is consumed by min-ing, no held-out split was left for choosing a configuration. We compared configurations directly on test_normal :five for DeepSeek-V3.2, four for gpt-oss-120b, two each for GPT-5.5, GLM-5, and Gemma-4-31B, and one for Claude Opus 4.6. Table 2 therefore reports, next to each model’s best configuration, a fixed rule decided before any test run: inject all guidelines. Results are single runs, the benchmark’s con-vention, except where noted. Insight 5 quantifies what that hides.

What we changed. Lossless became the default consol-idation mode, and compression became an explicit opt-in. Insight 1 is the necessary qualifier. On a weak model the full long tail is exactly what drowns it. “Keep everything” is only right when delivery can select. 

Insight 3: Selection needs provenance, and provenance is easy to lose 

What we expected. That consolidation and selection were independent stages. 

What happened. They are not. Selection by support re-quires that support survive consolidation. Retrieval by source task requires that the source task survive it. When we pro-ductized into altk-evolve we found two independent ways this had already broken. An earlier version of the consoli-dation stage rebuilt each merged guideline’s metadata from a fixed field list. It silently dropped any provenance not on the list, including the support count and a generation-method tag another team was relying on. Separately, the first version of support attribution double-counted a member whenever the LLM repeated an index inside one merge. An automated code reviewer caught it before a person did. 

What we changed. Conservation is now an enforced invari-ant with a regression test, not a convention. Consolidation reports total support before and after. Any lesson the LLM fails to cover is carried through verbatim. The lesson gen-eralizes to any memory pipeline. If a later stage, such as selection, filters or ranks on a field, then every earlier stage, such as extraction and consolidation, must preserve that field as an invariant. 

Insight 4: Support is recurrence, not correctness 

What we expected. That a lesson derived independently by many episodes was safe to trust. 

What happened. A high-support pagination guideline read “loop until fewer than the page limit are returned.” The rule is correct only if the agent knows the page limit, and it did not. It assumed a limit of 20, while the API’s default page size was 5. The first page therefore held 5 items. Since 5 is fewer than 20, the agent concluded that it had seen the last page and stopped. It missed every later page. That was a regression on a task the baseline had passed. We fixed it by hand. The reworded guideline says “pass an explicit page limit and loop until a page comes back empty,” which no longer depends on guessing the default. The task recovered, and hard-tier TGC rose from 66.7 to 73.0. 

What we changed. Nothing automatic, and that is the in-sight. Support counts how often a lesson was derived. That is evidence of generality, not of correctness. A popular wrong lesson scores high. Our pipeline has no notion of a guide-line being contradicted, stale, or harmful. Systems designed as ongoing maintenance loops do. Anthropic’s dreaming re-solves contradictions in favor of the most recent value and prunes stale entries (Anthropic 2026). ExpeL lets the model down-vote an insight to deletion (Zhao et al. 2024). Genera-tive agents weight retrieval by recency (Park et al. 2023). We now regard a correctness or recency signal as the most im-portant missing component. We would not run an unattended memory loop without one. 

Insight 5: Measure the noise floor before believing a delta 

What we expected. That temperature zero and a fixed seed made runs comparable. 

What happened. Two runs of an identical gpt-oss-120b configuration scored 56.0 and 54.8 TGC. Across identical DeepSeek runs, roughly 32 of 168 tasks flipped outcome in one direction or the other while the aggregate barely moved. Sibling tasks in the same scenario flipped in opposite di-rections on unrelated prompt edits. Embedding similarity between a task and its retrieved guidelines did not predict which tasks improved. Improved and regressed tasks had mean retrieval cosine of 0.463 and 0.468. 

What we changed. We repeat runs wherever a claim rests on a small gap. We treat differences under about five tasks as noise. Concretely, this turned a “+1.2 TGC win over ACE” on gpt-oss into what it is: a tie on accuracy at one-seventh the token cost. That is both more defensible and, for a deploying team, more useful.

Insight 7: Silent failures cost more than modeling problems 

Three operational failures consumed more calendar time than any research question. First, a GPT-5-class model rejects a temperature of zero with an HTTP 400. The harness caught and swallowed the error. Every task “failed” after exactly one model call, and the run completed with a plausible-looking log. Second, consolidating hundreds of lessons in a single call exhausted the output budget on reasoning models, which returned truncated JSON. Chunked map-reduce to a fixed point fixed it. Third, multi-hour evaluations through a cor-porate proxy died whenever the network went idle, stranding jobs. In the CUGA integration, memory writes were never invoked on one code path. The store stayed empty, and mem-ory was silently read-only from cold start. None of these produced an error a person saw. Our recommendations are unglamorous. Fail loudly on any per-task exception. Assert a minimum number of model calls per task. Watchdog progress on long runs. Check that the memory store’s entity count ac-tually grows. 

## Related Work 

Learning from one’s own trajectories has a substantial lin-eage. Reflexion stores verbal self-reflections per episode (Shinn et al. 2023). ExpeL extracts cross-task natural-language insights from training tasks (Zhao et al. 2024). It maintains them with ADD, EDIT, UPVOTE, and DOWN-VOTE operations and an importance count that removes an insight at zero. That count is a model’s vote on an insight’s quality. Our support is instead a count of independent deriva-tions, conserved through merging. ExpeL also injects all in-sights at inference and retrieves only past trajectories by sim-ilarity. Agent Workflow Memory induces reusable workflows from trajectories (Wang et al. 2025). ACE grows a playbook through generation, reflection, and curation with incremental updates, explicitly to avoid brevity bias and context collapse (Zhang et al. 2026). Insight 2 corroborates that concern. In-sight 1 adds the case ACE does not study: the weak model that must be given less. Generative agents periodically reflect over a memory stream and retrieve by recency, importance, and relevance (Park et al. 2023). Our pipeline has the latter two and, as Insight 4 notes, lacks recency. Offline consoli-dation itself is older. It appears in the wake-sleep algorithm (Hinton et al. 1995), in DreamCoder’s sleep phase that refac-tors solved programs into a reusable library (Ellis et al. 2021), and in sleep-time compute for agents (Lin et al. 2025; Packer et al. 2023). Anthropic’s dreaming is the same idea produc-tized. It resolves contradictions by recency but, as far as its documentation shows, preserves no multiplicity (Anthropic 2026). All of these, and our episodic-to-semantic framing, descend from complementary learning systems theory (Mc-Clelland, McNaughton, and O’Reilly 1995). 

## Deployment in IBM’s Products 

CUGA. CUGA is IBM’s multi-agent assistant. Memory was integrated into three of its sub-agents: task analysis, API shortlisting, and task decomposition. Each receives agent-specific tips retrieved by task intent. An initial 50-task eval-uation found no statistically significant effect on pass rate or step count. We later found that it had run with the write-path bug of Insight 7, so the memory store never grew past its seed. With the write path repaired, we re-ran the CUGA inte-gration with two models. With GPT-4.1 we used two bench-marks and averaged over three trials. The first is AppWorld (Table 4). The second is the retail split of τ -bench (Yao et al. 2025; Barres et al. 2026), a customer-service suite of 74 training and 40 test tasks (Table 5). On AppWorld, loss-less consolidation raises task completion from 71.03% to 72.42% and scenario completion from 54.76% to 58.93%. Steps per task fall slightly, from 9.63 to 9.31. On τ -bench, our sup3 configuration (12 guidelines) lifts mean accuracy from 51.7% to 55.8%. It also lifts the stricter pass^3 measure, which credits a task only when all three of its trials pass, from 27.5% to 32.5%, at marginally fewer conversational turns per task. Each of these deltas is about two tasks per trial. That is below the noise floor of Insight 5. They show that the re-paired integration works end to end and that its effect points the same way on two benchmarks. ## Conclusion and Recommendations 

Memory distilled from an agent’s own history is worth de-ploying. With nothing but its own train-time trajectories, a mid-tier model gained +9.5 TGC and +16.1 SGC. A weak one gained +11.3 TGC with all of its guidelines and +15.5 with a selected subset. But the value did not come from the idea. It came from what we learned deploying it. For teams about to do the same: 1. Treat dose as a first-class parameter and measure it per model. Assume nothing about monotonicity. 2. Consolidate losslessly and select at delivery. Do not com-press by default. 3. Make every field a downstream stage ranks on an en-forced, tested invariant of every upstream stage. 4. Add a correctness or recency signal before running mem-ory unattended. Recurrence is not truth. 5. Establish the noise floor with repeated runs before reading any small delta. 6. Compare memory systems on a fixed scaffold, lead with deltas, and always report tokens. 7. Assume failures will be silent. Assert on call counts and store growth, and fail loudly.
