Abstract 

Improving agents requires discovering where they fail and understanding why. An agent acts over multiple steps in a changing environment, so diagnosing its failures requires more than inspecting the final response of a large language model (LLM). The same unsuccessful outcome can arise from task difficulty or from an error the agent repeats across tasks. We introduce PROBEAGENT, an automated framework that discovers agent failures, tests their proposed causes, and identifies shared failure modes. Starting from benchmark tasks, PROBEAGENT builds executable tests and validates them using reference solutions, automated checks, and review of the task requirements. For each failed trajectory, it explains the error and constructs new tasks that preserve the suspected cause while changing the surrounding context. Running the agent on these tasks tests whether the same error recurs. PROBEAGENT then groups failures with similar causes and generates descriptions that distinguish their errors. This process connects explanations of individual fail-ures to executable tests and descriptions of shared failure modes. We evaluate PROBEAGENT across 22 agent configurations using tasks from 10 benchmarks, collecting 1,244 failures and producing 536 failure-mode descriptions. These descriptions distinguish specific errors within broad outcomes such as incomplete work, including planning without acting and stopping before delivering a file. In human evaluation, annotators ac-cept 90.0% of assigned descriptions and correctly reject 83.3% of similar alternatives, supporting the accuracy and specificity of the discovered failure modes. 

## 1. Introduction 

Agents are increasingly used to modify code, navigate websites, and complete work in terminal en-vironments [28, 37, 55]. An agent combines a large language model (LLM) with a harness , which manages its context, execution flow, and termination. As agents become part of real-world work-flows, they still fail on many tasks. Studying these failures can guide improvement: we need to identify where agents fail and understand why. Benchmark scores summarize task success, but the final outcome alone does not explain the cause of a failure. The same outcome can arise for different reasons. For example, a missing report may result from a difficult computation, or simply because the agent stops before saving its result. These failures require different fixes. Improving

agents therefore requires not only measuring failures, but also systematically discovering them and diagnosing their causes. Existing automated evaluation methods often discover LLM failures by generating new questions or selecting informative tests [1, 11, 29]. ProbeLLM [23] goes beyond finding individual errors by explaining incorrect responses and organizing related errors into failure modes . Each mode de-scribes a shared error pattern supported by concrete failure examples. This connects the discovery of individual failures with an account of the patterns shared across them. For agents, existing methods diagnose failed trajectories after execution. For example, Who&When benchmarks failure attribution [54], while AgentRx and AgentDebug analyze trajectories , the se-quences of actions and observations, to locate errors or guide corrective feedback [8, 57]. These studies help explain observed failures, but leave open how to systematically construct new tasks to discover further failures and organize them into shared modes. We therefore ask: can we build an effective framework that automatically discovers and diagnoses agent failures? 

This requires addressing three challenges. (1) Building reliable executable tests. An LLM test can pair a question with a reference answer and a verifier. An agent test also needs a working environment in which actions change the task state, a solvable task, and a checker that evaluates the required outcome. Environment defects or shortcuts accepted by the checker can otherwise give misleading results [3, 45]. (2) Distinguishing task-specific difficulties from recurring agent behavior. A failed trajectory may reflect a difficulty in one task or a behavior that appears in many tasks. Explaining that trajectory alone does not distinguish the two. New tests must change the task context while preserving the condition thought to cause the failure, so that we can check whether the same agent makes the same mistake again. (3) Identifying shared failures across different tasks. Omitting a CSV export after data analysis and a JSON export after a database query can reflect the same error: completing the computation without delivering its output. A failed write can also leave a file missing, but requires a different correction. Diagnosis must distinguish the behaviors behind these similar outcomes. To address these challenges, we propose PROBEAGENT, an automated framework for discovering and diagnosing agent failures (Figure 1). It connects three stages. Establish failures constructs executable probes from benchmark tasks, validates their checkers and reference solutions, and explains failed trajectories. Test failure recurrence constructs sibling tasks : new tasks that preserve the proposed triggering condition while changing the domain, data, or output format. Running the same agent on these tasks tests whether the explained error recurs. Discover failure modes groups failures by their causes and generates descriptions that distinguish their errors. By using explanations to guide new executable tests, PROBEAGENT connects diagnosis of observed failures with discovery of further failures and the patterns they share. We evaluate PROBEAGENT across 22 agent configurations and 10 benchmarks, collecting 1,244 ex-plained failures and producing 536 failure-mode descriptions. These distinguish specific mistakes within incomplete work, such as planning without acting and stopping before delivering a file. Human annotators accept 90.0% of assigned descriptions and correctly reject 83.3% of similar al-ternatives. Review of generated tasks detects invalid tests that pass execution checks, and enforc-ing similarity within each group improves description agreement from 78.0% to 91.8% against the model-based reference. These results demonstrate that PROBEAGENT produces usable diagnostic tests and accurate, specific failure descriptions.

Definition 3 (Failure explanation) . A failure explanation 𝑒 = (𝑏, ℓ, 𝜏, 𝛿) identifies a proposed cause of one failure: the erroneous action or omitted action 𝑏 , the point in the task where it occurs ℓ, the task condition 𝜏 under which it arises (the trigger ), and a corrective action 𝛿 . Each field is supported by the trajectory 𝑧 .

Definition 4 (Failure-mode description) . A failure-mode description 𝑐 is a natural-language state-ment of a shared error. Write 𝑐(𝑟) ∈ {0, 1} for the judgment of whether failure 𝑟 exhibits that error. A failure mode is a tuple (𝑐, 𝑅, 𝐵) with nonempty supporting failures 𝑅 and disjoint contrasting fail-ures 𝐵 , for which the description satisfies

A failure explanation 𝑒 concerns one trajectory; a description 𝑐 states the pattern used to group failures. Section 3.3 specifies how these judgments are made. 

Example. An agent computes a total but stops without saving the required report. The failure 𝑟 

records this error and its trajectory. Its explanation 𝑒 identifies the omitted save after computation, the requirement to deliver a file, and the correction of writing that file. A failed write does not match this description.

## 3. The PROBEAGENT Framework 

PROBEAGENT connects three stages (Figure 2): Establish failures builds and validates probes, then explains failed trajectories; Test failure recurrence checks whether the explained error appears in new tasks; and Discover failure modes groups failures and describes their shared errors. Search alternates between the first two stages, and discovery of failure modes uses the collected failures. Appendix A specifies the LLM configuration for construction, review, explanation, and judging. 

3.1. Establish failures 

To diagnose an agent, we first need tests whose instructions, environment, and checker agree. We construct these tests from benchmark tasks and validate them before interpreting the agent’s errors.

Balance new tasks and sibling tests. PROBEAGENT alternates between exploring new tasks and testing sibling tasks. 3.3. Discover failure modes 

Different tasks can expose the same error, while similar unsuccessful outcomes can have differ-ent causes. PROBEAGENT groups the collected failures by cause, then generates a description for each group. We call this process induction . It uses failures from both seed-task probes and sibling tasks, including new errors found during sibling tests, and outputs modes (𝑐, 𝑅, 𝐵) (Definition 4; Figure 2(c)).

## 4. Experiments 

4.1. Experimental setup Models and harnesses. We evaluate 22 configurations combining 15 models and seven harnesses. The models include GPT-5.6 and GPT-5.4-nano [42, 43], Claude [6], DeepSeek-V4-Pro [12], Kimi K3 [39], GLM-5 and GLM-5.2 [52, 53], Qwen3.8-Max [4], Grok 4.5 [44], and MiniMax-M2.7 [38]. The harnesses are Terminus 2 [17], Codex [41], Claude Code [7], Goose [15], opencode [5], Open-Hands [46], and Aider [2]. Table 2 lists the exact model–harness pairings. Appendix A specifies the internal model configuration for construction, review, analysis, and induction. 

Tasks and protocol. We start from 14 seed tasks from 10 benchmarks spanning retrieval, code edit-ing, performance engineering, data pipelines, terminal operation, tabular and spreadsheet work, clinical tasks, customer service, and law (Appendix B). Each diagnostic search constructs and vali-dates new probe environments from these tasks, then collects failures from the agent’s trajectories. We group these failures and generate descriptions of their shared errors. For corpus analysis, we use the group-level similarity margin 𝜇 = 0.02 defined in Equation (7); ablations examine other values. Probes run as Harbor tasks [16] in Docker containers [13]. Search uses three rollouts per environment. Appendix A.3 gives the hyperparameters and execution details.

PROBEAGENT distinguishes failures within broad error categories. 4.3. Accuracy of failure-mode induction PROBEAGENT accurately characterizes failure modes. We evaluate description accuracy by testing whether each description correctly identifies matching failures. The induction judge assigns held-out failures using the descriptions, and the pairwise judge confirms each assignment against the selected group’s first member in corpus order. The classifier may return no match; agreement is measured among assigned failures. With 25% of failures held out before induction, PROBEAGENT 

9ProbeAgent: Principled Diagnosis of Agent Failures 

achieves 88.5% agreement on the 1,244-failure corpus at 𝜇 = 0.02 . These failures are excluded from centering, calibration, and description construction. The result supports the accuracy of the induced failure descriptions (Appendix C). 

Human evaluation supports description accuracy and specificity. We ask two annotators to eval-uate 30 failures, each paired with its assigned group’s description and a similar alternative from another group. Each annotator evaluates all 60 pairs. They accept 28 and 26 assigned descriptions, respectively, and each correctly rejects 25 alternatives, giving mean acceptance and rejection rates of 90.0% and 83.3%. These judgments support accurate descriptions that distinguish similar errors (Appendix C.5). 

4.4. Effectiveness of probe validation Review of task requirements detects defects that execution checks miss. Across 1,451 build rounds, the execution gate rejects 349 candidates, and the reviewer rejects a further 638 after exe-cutable controls pass. The most common finding is a rewarded shortcut that bypasses the intended task, observed in 565 rounds. Neither the reference nor null run attempts these shortcuts. In 323 rounds, the checker does not evaluate the requested outcome; in 255, it imposes an unstated re-quirement. Findings can overlap within a round. These findings show why both checks contribute to probe validation: execution tests whether the reference succeeds and inaction fails, while seman-tic review examines whether the checker rewards the work specified in the instruction. ## 5. Related Work 

Agent evaluation. Agent benchmarks cover repository repair, web interaction, desktop operation, and domain-specific tasks [e.g., 27, 28, 32, 48, 51, 55]. Recent work also examines how agents progress through a task. For example, AgentBoard measures intermediate progress, 𝜏 2-Bench studies coordination when users and agents share control, and Gaia2 evaluates dynamic, asyn-chronous environments [9, 14, 34]. Agent-as-a-Judge assesses intermediate work against task re-quirements, while AgentRewardBench compares automatic trajectory evaluations with expert as-sessments [33, 58]. Newer benchmarks test agents on longer and more specialized work. AutoLab evaluates long-horizon research and engineering tasks in which agents improve a working baseline through repeated experiments [49]. RSI Arena studies agents that post-train a base language model 

13 ProbeAgent: Principled Diagnosis of Agent Failures 

and then improve it with human preference votes [25]. JobBench grades workflows that experts in 35 occupations want to delegate [30]. In specialized domains, NARRA-Gym logs full interac-tive story episodes to evaluate narrative agents [24], and ChemCost scores chemical cost reasoning against exact ground truth, with stage-level diagnosis of grounding, retrieval, procurement, and arithmetic failures [47]. PROBEAGENT uses failed tasks to construct further tests, checking whether the same error recurs under changed task conditions. 

Task generation and benchmark validity. Generated environments expand the experience avail-able for agent training. For example, AgentGen synthesizes environments and planning tasks, while SWE-smith and R2E-Gym construct executable software-engineering tasks through repos-itory modifications, test generation, and commit-based synthesis [18, 26, 50]. LLM-driven data synthesis also produces training and evaluation data in other settings. DataGen combines attribute-guided generation with code-based label checks and retrieval-based fact checks [20]. ChemOrch synthesizes chemistry instructions with tool-grounded responses, and uses them both to train mod-els and to build tasks that reveal model weaknesses [19]. PersonaGym simulates multi-turn user interactions with evolving preferences for personalization [35], and AuraGen injects labeled risks into synthesized agent trajectories to train the Safiron guardrail [21]. Reliable verification is central to using such tasks. A different stream focuses on human validation and benchmark audits to iden-tify ambiguous specifications, weak tests, and exploitable evaluation logic [3, 40, 45]. PROBEAGENT uses task generation for diagnosis: it constructs validated tests around a proposed cause of failure and checks whether the error recurs. 

Automated probing and failure analysis. Dynamic evaluation moves beyond fixed test sets by adapting what is tested. For instance, Meta Probing Agents transform evaluation problems along cognitive dimensions [56]; AutoDetect coordinates examiners, questioners, and assessors to ex-pose model weaknesses [11]; AutoBencher optimizes dataset descriptions for criteria such as diffi-culty and novelty [29]; ACE selects informative capabilities through active learning [1]; and FACT-AUDIT adapts fact-checking assessments to model responses and evaluates both verdicts and justi-fications [31]. For agents, MAST organizes multi-agent failures into a taxonomy, and Who&When provides annotations of the responsible agent and decisive step [10, 54]. Failures can also emerge from the interaction among agents. In generative multi-agent systems, collusion-like coordination and conformity arise often across repeated trials of resource competition, sequential handoff, and collective decisions [22]. In enterprise workflows, agents that each act within their own permissions can jointly violate organization-wide constraints; EAIR tests these risks in executable micro-worlds and uses execution traces to locate and repair them [36]. AgentDebug combines critical-error de-tection with feedback for later rollouts, while AgentRx uses stepwise constraints to ground failure localization [8, 57]. These methods organize or locate errors in observed trajectories. ProbeLLM [23] discovers failure modes of LLM responses through active probing and verifiable test cases. PROBEAGENT extends this approach to agents: it constructs and validates environments, uses trajec-tory explanations to design new tasks, tests whether the same error recurs, and describes shared failure modes. 

## 6. Conclusion 

PROBEAGENT provides an automated framework for discovering and diagnosing agent failure modes. Across 22 agent configurations and 10 benchmarks, it collects 1,244 failures and produces 536 failure-mode descriptions. Its experiments demonstrate diverse failure discovery, accurate descriptions, and effective probe validation and grouping. By combining executable tests with tests of recurrence, PROBEAGENT helps identify specific agent errors and the task conditions in which they arise.

C.5. Human evaluation of failure descriptions 

We randomly sample 30 held-out failures assigned to groups with generated descriptions, keep-ing the descriptions fixed before annotation. Each failure is paired with its assigned description and a similar alternative from another group, selected by the maximum centered cosine similarity between the failure and any member of that group. Two annotators independently evaluate all 60 pairs, yielding 120 judgments. Each item provides the task requirements, the specified failure, relevant trajectory excerpts, checker feedback, and one candidate description; the full trajectory is also available. Items are shuffled and presented separately, with model and group identities, automatic judgments, and description type hidden. Annotators decide whether the description accurately characterizes the failure, answering yes, no, or insufficient information and giving a brief evidence-based reason. A match requires the described error and key task conditions to agree with the trajectory; different errors, incompatible conditions, or contradictory evidence receive a no judgment. Unresolved evidence receives insufficient information. Equivalent wording is accepted, while a shared broad outcome alone does not establish a match. Both description types use the same criteria. For each annotator, we divide yes judgments on assigned descriptions and no judg-ments on alternatives by 30, then average the respective rates across annotators. They accept 28/30 and 26/30 assigned descriptions and each reject 25/30 alternatives, giving mean acceptance and rejection rates of 90.0% and 83.3%, respectively.
