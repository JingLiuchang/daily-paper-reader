# Synapse: Optimizing Natural-Language Agent Skills through Program Repair 

LIJUAN LI, Nanjing University 

ZHENPENG CHEN, Tsinghua University 

CHENXI ZHANG, Xidian University 

YIHAO HUANG, East China Normal University

CHONG WANG, Nanyang Technological University Large language model (LLM) agents can improve task performance by optimizing reusable natural-language skills without updating model parameters. However, the execution feedback that guides this optimization identifies failed tasks without directly revealing which instructions should be modified, which other instructions a fault involves, or which other tasks an edit may break. For programs, fault localization, dependence analysis, and regression test selection answer these three questions. Our key insight is that, although a skill is not a program, the procedure it describes can be partly recovered as one, and that this partial program can serve as an editable view of the skill. We propose Synapse , which casts skill optimization as generate-and-validate repair over this view. A deterministic compiler that, like an island grammar, recognizes only the constructs of interest translates a skill into SkIR, a source-linked intermediate representation that exposes operations, conditions, and data references and keeps every other requirement in the text. Synapse localizes faults from traces of repair tests, the tasks with reference answers that guide the search, and relates each fault to neighboring instructions through control-flow and dependence relations derived from SkIR. It admits only typed SkIR mutations, which it writes back to the mapped spans of the instructions they target and recompiles. It screens each patch on related repair tests, including previously passing ones, before validation decides whether to accept it. Whatever the LLMs that execute the skill and propose patches return, every accepted patch yields a well-formed skill and leaves the source span of every untargeted instruction unchanged, and if the execution agent is one-hop local, the selected tests include every test that an edit can affect. On two single-turn question-answering benchmarks, DocVQA and LiveMath, with three execution models, Synapse improves task success rates over SkillOpt by 3.74–4.54 percentage points on DocVQA and 2.40–4.00 on LiveMath and outperforms Trace2Skill and SkillBoost in all six settings of benchmark and execution model. In an ablation, replacing SkIR-based repair and its test screening with constrained text editing screened only on failing tests reduces DocVQA success rates by 2.40 and 2.67 percentage points for GPT-5.6 Luna and GPT-6 Sol, respectively. In two recorded DocVQA repair runs, control-flow and dependence relations add related repair tests to the screening of 23 of 37 patches, and in one repair, a test added only through a control-flow relation exposes a regression that coverage of the edited instruction misses. Additional Key Words and Phrases: Large Language Models, Agent Skills, Intermediate Representation, Program Analysis, Skill Optimization 

1 Introduction 

LLM agents increasingly perform complex tasks by planning actions, invoking tools, and interacting with external environments [42, 55, 57, 63, 65], yet many tasks require procedural knowledge that is difficult to encode in the model itself. Agent Skills, introduced by Anthropic [4] and released as an open standard [1], supply such knowledge externally. A skill document tells an agent which steps to follow, when they apply, what information to check, and how to return an answer. Skills have been adopted by many agent products [1], and as of October 2026, the cross-agent directory skills.sh ranks about 1.5 million skills by installation [54].

Because skills are written in natural language, often by community authors or by LLMs, their quality is hard to guarantee. On SkillsBench, model-generated skills perform worse than no skill, whereas curated skills help [26]; skills that appear relevant can still cause a task to fail [14]; and in a study of three skill libraries, regressions offset 59% of the gains that skills bring [52]. Skills therefore need to be improved from their effects on task execution. Recent work on skill optimization revises a skill from tasks with reference answers so that an agent following it answers unseen tasks of the same kind correctly more often [29, 36, 64]. Improving a skill, however, takes more than rewriting its text. Consider a DocVQA skill whose 

value-span instruction tells the agent to return only the requested value span and to omit units unless the question asks for them. Asked for the total turnover in a document that prints “41,809.82 crores”, an agent that follows the skill answers “41,809.82” and drops the scale word “crores”, which multiplies the amount by ten million. A repair must answer three questions. Which instruction should change, and what kind of change does it need? Which other instructions does the failure involve, such as the condition under which this instruction applies? Which passing answers might the edit break, such as a receipt amount in words? Existing optimizers answer them only in part. These optimizers differ in how they find and make an edit. Trace-driven methods revise or patch skill documents from execution trajectories [36, 56, 64], attribution-guided methods first identify the sections, skills, or fields responsible for failures [13, 30], structure-aware methods apply typed operators to steps, rules, or workflow paths [33, 50], and library-level methods expand and consolidate skill collections [20]. Measured against the three questions, they share three limitations. 

(L1) Imprecise edit targets. Trace-driven and attribution-guided methods express the edit itself as rewritten text, and structure-aware methods, including the concurrent GraphSkillAA [44], apply typed edits to a separate structured representation of the prompt or skill [33, 50], which does not determine which span of an existing skill an edit replaces. To our knowledge, no skill optimizer ties an edit to a typed element of the existing skill, namely the instruction it modifies, the kind of change it makes, and the span it replaces. Without this tie, an optimizer has no declared target and kind of change against which to check an edit before running the edited skill, such as a rewrite confined to the value-span instruction in the turnover example. (L2) Implicit instruction dependences. 

Structure-aware and library-level methods organize instructions into steps, rules, workflow paths, or typed skill-graph edges [33, 44, 50] or manage relationships among skills [20], and SkVM extracts the dependencies between steps to run independent steps in parallel [10]. To our knowledge, no skill optimizer derives the control and data dependences among the instructions of an existing skill from its text, so an optimizer must infer which other instructions a failure involves. In the turnover example, the condition under which the value-span instruction applies is stated in a separate clause, so the repair model must also see a clause outside the instruction. (L3) Untargeted regression checks. Existing methods check an edit against the motivating failure [13], source tasks [20], a fixed task set [29, 64], or the examples that an update affects in a skill graph [44]. An edit can also change the answer to a task whose trace never covers the edited instruction, through a related instruction that the trace does cover. In the turnover example, the receipt is such a task, since its trace covers a neighboring condition but not the value-span instruction. To our knowledge, no skill optimizer selects the tasks to recheck through dependences recovered from an existing skill’s text, so such a regression is caught only if that task happens to be checked. For programs, generate-and-validate repair has an established answer to each of these limitations. Fault localization [23] and repair operators [25] determine where and how a patch changes a program (L1), dependence analysis reveals which statements relate to a fault [3, 16] (L2), and regression test selection identifies the tests that a change may affect [41] (L3). These techniques operate on programs, however, and a skill is a document. Structured skill representations [28, 62] Synapse : Optimizing Agent Skills through Program Repair 3

and work that treats prompts as programs [27, 43, 47] show that skills carry program-like structure, but none recovers this structure from an existing skill’s text and repairs the skill through it. Our key insight is that the procedure a skill describes can be partly recovered as a program that serves as an editable view of the skill. Like an island grammar [35], which parses only the constructs of interest in a text and skips the rest, a deterministic compiler can extract a skill’s operations, conditions, and data references and link each of them to its span in the document. Every other requirement stays in the text of its instruction, where the analyses ignore it but the agent that follows the skill still reads it. We call the result a partial program view .Even on this view, two properties of skills keep the program-repair techniques from transferring directly. First, instructions resist reliable parsing, so the recovered structure is incomplete, and an edit made on it must still land in the authored text. In the turnover example, the exception about units is not a recognized element, yet it is the text that the repair must change. Second, the interpreter of a skill, its execution agent , is an LLM agent. The interpreter cannot be instrumented, so which instructions it used is known only from its report, its answers vary across requests, and no static relation predicts the effect of an edit, so edits must be checked by running the skill. We present Synapse , which casts skill optimization as generate-and-validate repair over the partial program view of a skill. Synapse compiles a skill into SkIR, a source-linked intermediate representation, and derives its control-flow and dependence graphs. It localizes each failing repair test, a task with a reference answer that guides the search, to the instructions that the execution agent reports using. A second LLM, the repair model, sees each suspicious instruction together with its directly related instructions and may propose only typed mutations of SkIR elements, such as an instruction, a condition, or a dependency (L1, L2). Synapse writes each patch back to the mapped spans of the instructions it targets and recompiles the result, so every patch is checked for well-formedness before any test runs. To catch regressions that coverage alone misses (L3), it screens a patch on the repair tests that the reported coverage and the control-flow and dependence relations select. It accepts a patch only if it raises the pass count on a separate validation suite. Because a deterministic host checks every LLM result, the properties it enforces in each iteration hold whatever the LLMs return. For programming languages, the approach repairs a language with a partial grammar and an LLM interpreter, through a recovered view whose edits stay within their spans and whose test selection is safe under a weaker locality assumption than coverage needs. Following SkillOpt [64], we evaluate Synapse on DocVQA [34], which asks questions about documents, and LiveMath [19], which poses multiple-choice mathematical problems, with one repair model, three execution models, and held-out test tasks. The optimized skills improve test success rates over the initial skill by 4.28–14.71 percentage points on DocVQA and 4.80–9.60 on LiveMath, and exceed SkillOpt [64], Trace2Skill [36], and SkillBoost [29] in all six settings of benchmark and execution model, by 1.60–4.54 points over the strongest in each setting. In an ablation with two execution models, replacing SkIR-based repair and its screening with constrained text editing lowers success rates by 1.60–3.20 points. In two recorded DocVQA repair runs, control-flow and dependence relations add related repair tests to the screening of 23 of 37 patches, and in the turnover repair, a test selected only through a control-flow relation exposes a regression that coverage of the edited instruction misses. Only the final skill of Synapse answers the turnover question with “41,809.82 crores”. In summary, this paper makes the following contributions:

2 Synapse in a Nutshell 

Synapse recovers a partial program from a skill and repairs the skill the way a generate-and-validate tool repairs code (Figure 1). We first show what program structure a skill leaves implicit and then follow one repair of the turnover example through the steps of the figure. 

2.1 Implicit Program Structure in Skills 

A skill resembles a program but leaves its structure implicit. Its instructions describe operations, the conditions under which they apply, the information they use, and the form of the answer, often several in one instruction, as structured skill representations make explicit [28, 62]. For example, one instruction may say to return a selected value and when to omit units. No syntax marks an operation, a condition, or a value. A condition stated in one instruction may govern an operation described in another, and a value may be referred to by different phrases. Textual order gives the sequence of steps, but neither it nor authors’ labels reveal which condition governs which operation or which instruction supplies a value that another uses. Although no dedicated syntax marks these elements, document conventions mark part of this structure. A skill is a Markdown document, in which headings delimit sections, list items and paragraphs delimit instructions, and inline code marks the files, fields, and values that instructions refer to. Procedural prose adds conventional forms. An applicability clause such as “When to use” states when the next instruction applies, a conditional clause such as “if . . . ” or “provided that . . . ” restricts the action of its instruction, and an imperative verb names that action. Structure stated in these forms can be read off the text, whereas structure stated otherwise remains implicit.

2.3 How Synapse Repairs the Skill 

Figure 1 shows the repair iteration that this subsection follows for the value-span instruction. 

Compile and analyze. The repair needs an editable location, its context, and a neighborhood from which to select tests, so Synapse compiles the skill into SkIR and derives its graphs. The value-span instruction yields a return operation, linked by the source map to its span in the Markdown document, while the exception about units remains part of the instruction’s text. Its “When to use” clause yields a branch condition that governs this operation, and the control dependence graph (CDG) records the governing relation. The CFG also links the return to the condition “When several nearby strings look similar”. 

Localize. To decide which instruction to change, Synapse starts not from the turnover question, which is held out, but from failing repair tests whose answers likewise omit markers printed with the requested values. On each test, the execution agent reports which instructions it used. These reports, the recorded coverage of the tests, point to the value-span instruction, which becomes a suspicious location with a source span (L1). From the blanket requirement to omit units, the repair 6 Li et al. 

model hypothesizes that the returned span excludes markers of the requested value itself, not only markers supplied by the context. 

Patch and write back. To change the instruction without breaking the answers around it, the request for a patch supplies the text of the instruction together with these two conditions and passing tests that constrain the intended change (L2). From this request and the hypothesis, the repair model proposes a typed patch that rewrites the text of the value-span instruction (L1). The host offers this operator only at an instruction with a mapped source span, so before any test runs it knows that the patch replaces exactly this span. It replaces the unit-omission requirement by distinguishing markers integral to the value from markers supplied only by context. 

> Return only the requested value span. Preserve a currency symbol or measurement unit when it is visibly part of the selected value text or the same filled value field and semantically completes that value; otherwise omit nearby labels, category names, explanatory words, and symbols or units shown only in the question, a header, a separate column, unrelated text, or general context.

Writing the patch back replaces the span of this instruction and leaves every other instruction’s source span unchanged, and recompilation checks that the new SkIR is well formed. 

Select tests and validate. Addressing L3, Synapse screens the patch on more tests than the repair model names with it. The named tests are the failures that the patch should fix, control tests that pass, and boundary tests at the edge of the intended change. Synapse adds the tests whose recorded coverage includes the edited instruction and, through the CFG and dependence relations, the tests that cover related instructions. One of them, a receipt test about a written-out monetary amount, enters screening only through the CFG relation. Its recorded coverage maps to the neighboring condition for choosing among similar strings but not to the edited instruction, and the repair model did not name it. Under the patched skill, its previously correct answer gains a comma after “Pounds” and is scored incorrect. Because the patch still repairs the two failing repair tests that motivated it and keeps its control tests passing, screening keeps it, and because of the regression, it ranks behind any patch that fixes its failures without one. Validation on the separate suite then decides, and the patched skill passes more validation tests than the current skill, is accepted, and remains the final selected skill. Because “crores” is printed as part of the selected value text, the revised instruction keeps it as a marker of the value itself, and the final skill returns “41,809.82 crores” on the held-out turnover question. 

3 Skill Optimization with Synapse 

The repair techniques of the introduction assume a complete program and a deterministic interpreter, whereas Synapse works on an incomplete view of a skill whose interpreter is an LLM. This section formalizes skill optimization as generate-and-validate repair, motivates each step of an iteration under these conditions, and closes with the properties that hold whatever the LLMs return. 

3.1 Skill Optimization as Generate-and-Validate Repair 

We first formalize how an agent executes a skill and how its answers are judged, and then state skill optimization as repair over these executions. A skill is executed by an execution agent 𝐸 , which we treat as the interpreter of the skill 𝑆 . The agent is built on an LLM with fixed parameters, the 

execution model , and reads 𝑆 to answer a task. Changing 𝑆 is the only way to change how 𝐸 answers. The answers of 𝐸 are judged by tests. A test 𝑖 pairs a task input 𝑥 𝑖 with a reference answer, and a fixed scoring rule, the oracle, decides whether the answer that 𝐸 returns for 𝑥 𝑖 under 𝑆 passes. For a suite 𝐷 of tests, 𝐽 𝐷 (𝑆 ) is the fraction of 𝐷 that 𝑆 passes. Because the same input can receive different answers [38], 𝐽 𝐷 (𝑆 ), like every outcome in this section, refers to a recorded run. An incorrect answer may expose a fault in 𝑆 , but it may also come from a reading or reasoning error of 𝐸 that no change to 𝑆 removes. Skill repair seeks changes to 𝑆 that remove faults in 𝑆 .Synapse : Optimizing Agent Skills through Program Repair 7

Definition 3.1 (Skill repair). Given an initial skill 𝑆 0 and disjoint suites of repair tests 𝐷 rep and validation tests 𝐷 val , skill repair seeks a skill 𝑆 , obtained from 𝑆 0 by a sequence of patches, that answers unseen tasks of the same kind correctly more often than 𝑆 0. Since this rate cannot be observed, the repair tests guide the search and the validation tests decide whether each patch is accepted. A third suite 𝐷 test , held out, only estimates the final skill’s pass rate on unseen tasks. The repair tests play the part of the test suite in generate-and-validate repair [25, 40], and those that a skill 𝑆 fails, written 𝐹 (𝑆 ), point to the faults that a patch should remove. As in that setting, the repair tests are an incomplete specification, and a patch that makes them pass may still fail on other tasks [49]. Synapse therefore checks each patch on tests beyond the failure that motivated it and then on a separate validation suite. 

One repair iteration. Synapse repairs a skill iteratively, and each iteration follows the generate-and-validate loop. Algorithm 1 turns one skill version 𝑆 𝑡 into the next. An accepted patch yields 𝑆 𝑡 +1, and after a fixed number of iterations the final skill is evaluated on 

𝐷 test . The execution agent and the repair model are reached only through three procedures with different roles. Execute runs the skill, as running a test does in program repair, and is how Synapse observes the behavior of the skill, both to localize faults and to validate patches. Diagnose and Propose call the repair model, which plays the role of the patch generator. 

Definition 3.2 (Execution and repair procedures). Execution. Execute (𝑆, 𝑥 ) runs the execution agent 𝐸 on task input 𝑥 with the skill 𝑆 , extended by a deterministic address contract that labels its instructions and the data dependencies among them, and returns the answer of 𝐸 together with the addresses that 𝐸 reports using. Repair. The repair model 𝑂 is called through two procedures. Diagnose (Λ) receives a localization context Λ, which lists the failing repair tests and the suspicious instructions with their evidence, and returns repair hypotheses, each naming a failure mechanism, the failing tests it explains, and the instructions it affects. Propose (ℎ, Γ) receives a hypothesis ℎ

and an edit context Γ, which offers the edits allowed at each affected instruction together with the context needed to choose among them. It returns a patch Δ and the repair tests on which Δ is to be checked. These are the source failures 𝐹 Δ that it should fix, control tests 𝐶 Δ that pass and should not break, and boundary tests 𝐵 Δ at the edge of the intended change. These procedures are nondeterministic, and Synapse assumes nothing about which result a call returns. We write, for example, 𝑟 ∈ Propose (ℎ, Γ) when 𝑟 is a possible result of that call. The deterministic host builds every argument from SkIR, the dependence graphs, and the recorded traces, and checks every result before using it. It discards addresses that do not resolve, drops hypotheses whose tests are not current failures or whose instructions were not presented, type-checks patches, and validates named tests against the repair tests. We write 𝐻 for the hypotheses that Diagnose returns and that pass the checks on their tests and instructions. 

3.2 SkIR: A Partial Program View of Skills 

To localize a fault and relate it to other instructions, Synapse needs a skill’s operations, conditions, and data references as explicit program elements, yet the execution agent keeps reading the prose. Synapse therefore builds a partial program view of the skill. A deterministic compiler divides the document into instructions and applies a fixed set of recognizers that map parts of an instruction to program elements. It keeps all unrecognized content in the instruction’s text and records the source span of every instruction and element, so that a change made to an element can be written back to the text. Definition 3.3 (SkIR). A SkIR 𝐼 consists of a finite set 𝑁 of instructions and a finite set 𝑃 of program elements, which are operations, branch conditions, and the merge points that close the conditions. Each element 𝑝 ∈ 𝑃 is owned by the instruction own (𝑝 ) ∈ 𝑁 from which it was extracted, and each operation records the data items that it defines and uses. Each instruction keeps its text in full, including the content that no element represents, together with its section path and its attributes ,computed from its text alone, such as its modality ( MUST , SHOULD , MAY , or NEVER ) and trigger, the condition that opens a conditional instruction. 3.4 Dynamic Analysis and Fault Localization 

Static dependences describe how instructions may relate, but not which instructions a failing execution involved. Synapse obtains this dynamic evidence by running the current skill on the repair tests (line 2). Localizing a failure to source-linked instructions gives a patch its location (L1). Localization starts from coverage, as spectrum-based fault localization [23] does, except that coverage is reported by the interpreter itself rather than measured by instrumentation. 

Recording traces. To obtain this coverage, Synapse asks the execution agent to report which parts of the skill it used. The address contract of Execute assigns an address to every instruction and every recognized dependency. The trace 𝜏 𝑖 of test 𝑖 under 𝑆 records the input, the answer, its outcome, and the reported addresses of the recorded call Execute (𝑆, 𝑥 𝑖 ). Fault localization. The instructions covered by failing tests, Ð𝑖 ∈𝐹 (𝑆 ) cov (𝜏 𝑖 ), are the suspicious locations. Because a failing trace also covers instructions that played no part in the failure, Synapse grades each suspicious instruction by the strength of its evidence and retains those whose level reaches a fixed threshold. The evidence comprises reported uses and graph witnesses , which connect a failure to a candidate source instruction through a chain of execution evidence and graph relations checked by the host. Appendix A.6 gives the other kinds of evidence, the levels, and the thresholds. The localization context Λ𝑡 contains the failing tests and, for each retained instruction, its text, its one-hop CFG, CDG, and DDG relations, and the repair tests whose traces cover it, passing ones included, so that the repair model can see what a patch should preserve. 

Repair hypotheses. A patch should address a failure mechanism rather than a single failing test, so Diagnose groups the failures in Λ𝑡 into repair hypotheses (line 3). The repair model, not the host, decides which failures share a mechanism, since this judgment requires reading the wrong answers. So that every edit has a location the host can check, the host lists, for each instruction that a hypothesis affects, its repair targets , which are the instruction itself, its recognized elements and dependencies, and the insertion anchor after it, that is, the position immediately after its source span. Each target admits at least one repair operator. The condition that governs the value-span instruction belongs to a separate clause, so the targets of that instruction are the instruction itself and the anchor after it. A failure may yield several hypotheses, each leading to a separate patch, and a patch may coordinate edits to several interacting instructions.

3.7 Properties of an Iteration 

Because the execution agent and the repair model are reached only through calls whose results the host checks, three properties of every iteration hold by construction, whatever the LLMs return. The next skill compiles to a well-formed partial program view. An accepted patch leaves the source span of every instruction it does not target unchanged, since the host writes each mutation back only to the spans of its targets, which are disjoint from the spans of all other instructions (Lemma 3.10). The recorded validation pass rate never decreases and rises with every accepted patch, so the number of accepted patches is bounded by the number of validation tests that the initial skill fails. Appendix A.9 states them as a theorem and proves it. These properties and Proposition 3.13 answer the two difficulties of the introduction. An edit made on incomplete structure lands in the authored text without disturbing the rest, and although the interpreter is an LLM, the choice of screening tests is safe relative to a stated locality assumption, while acceptance rests on running the skill. 

4 Experiments 

We evaluate Synapse on three research questions and close with a case study of one repair. 

• RQ1: Skill Optimization Effectiveness. Can Synapse improve task performance com-pared with the initial skill and existing skill optimization methods, Trace2Skill, SkillBoost, and SkillOpt, across different benchmarks and execution models? 

• RQ2: Contribution of SkIR-Based Repair and Screening. What is the combined con-tribution of SkIR-based repair (L1, L2) and the screening of Synapse (L3), relative to constrained text editing screened only on failing repair tests? 

• RQ3: Repair Mechanism Analysis. Does SkIR-based localization tie repair targets to existing instructions and does write-back recover every well-typed patch in the text (L1), and does program-analysis-guided test selection add screening tests that coverage of the edited instruction misses (L3)?

All compared methods use the same partitions, which the sample identifiers and preparation scripts in the artifact define. Initial skills. All skill-based methods start from the same benchmark-specific initial skills, released with SkillOpt [64]. 4.3 Contribution of SkIR-Based Repair and Screening 

To measure the combined contribution of SkIR-based repair and the screening of Synapse (RQ2), we compare the full Synapse approach with a variant that replaces SkIR-based repair with constrained text editing and narrows screening. The comparison keeps the initial skill, repair tests, execution models, dataset splits, repair iterations, and the validation-based acceptance rule fixed. The w/o SkIR variant differs from Synapse in two respects. First, it removes SkIR, SkAST, CFG, CDG, DDG, source-map links, and typed SkIR mutations, which it replaces with constrained text editing, with the host limiting each patch to at most 120 line additions and deletions in total, while retaining execution traces. The repair model still receives the complete repair-test results of the current skill. 5 Discussion and Limitations 

Beyond single-turn question answering. The partial program view does not depend on the task format. Skills for multi-step tool use state the same kinds of elements, namely operations, the conditions under which they apply, and the data they pass on, and the address contract can label the instructions that request a tool call. What changes is the trace, which spans several turns, so coverage and outcomes would be recorded per turn and a test could fail at an intermediate step. 

Recognized structure. The analyses see only the structure that the fixed recognizers of Section 3.2 accept, so a skill that uses other verbs, refers to an item by different phrases, or describes iteration in prose yields sparser dependence graphs, and the initial skills of our benchmarks may suit these Synapse : Optimizing Agent Skills through Program Repair 19

Self-reported coverage and locality. Localization and test selection rely on the instruction usage that the execution agent reports, and test selection is safe only for a one-hop local agent (Proposition 3.13). The properties of Section 3.7 hold whether or not the reports are accurate, but this paper measures neither the reports nor the locality assumption. Counterfactual checks, such as removing an instruction and rerunning the tests that report using it, could validate coverage, and rerunning all repair tests for sampled patches would show how often locality fails. 

One-hop neighborhoods. The repair model sees, and screening adds, only the instructions one hop away from a suspicious or edited instruction. An effect that travels further, such as the influence of the condition that lies two hops from the return in Figure 2, is covered only if the agent’s reports or the named tests reach it. Neighborhoods that grow with the skill, or that follow dependence chains beyond the instructions a test covers, would trade a larger context for wider coverage. 

Acceptance on a small validation suite. Synapse accepts a patch when it passes at least one more validation test than the current skill. With small suites, such as the 53 and 17 validation tests here, and answers that vary across requests, a patch can be accepted by chance [9]. Requiring a margin or repeated validation runs would make acceptance more robust at a higher cost. 

6 Related Work 

Automatic skill optimization. Skill optimization continues work that improves LLM behavior from feedback without changing model parameters, such as the verbal reflections of Reflexion [48] and the feedback that TextGrad passes through a computation graph [66]. Trace-driven methods revise a skill from execution trajectories [56], SkillOpt bounds text edits and accepts them only after validation improvement [64], and Trace2Skill consolidates trajectory-local patches with conflict and format checks [36]. Attribution-guided methods first localize a failure to skill sections, fields, or mechanism relations [13, 30]. These methods express the edit as rewritten text, whereas Synapse localizes to source-linked instructions, edits them through typed mutations (L1), and relates them to other instructions through control and data dependences (L2). Structure-aware methods are the closest in how they edit. SEPO applies typed operators to the steps and rules of a prompt outline [33], and GraphSkillEvo mutates the step nodes and workflow paths of a graph-structured skill [50]. They edit a structured representation of the prompt or skill, whereas Synapse recovers structure from the prose of an existing skill and writes every edit back to it. We do not include SEPO, GraphSkillEvo, and GraphSkillAA as baselines, because their editing units are prompt outlines and graph-structured skills rather than shared skill documents. Library-level methods expand, consolidate, and relate skill collections [20], whereas Synapse revises the instructions within one skill. To check an edit, SkillBoost bounds regressions on a fixed task set [29] and SkillCommit rechecks source tasks [20]. The closest concurrent approach, GraphSkillAA [44], applies typed edits to an addressable skill graph and uses a Local Gate to retest affected examples. Synapse instead 20 Li et al. 

grounds both editing and test selection in a source-linked partial program view recovered from the authored skill text. Its source map confines typed edits to their mapped source spans and preserves the surrounding text, while control-flow and dependence relations derived from the same view select related repair tests, including those outside the edited instruction’s direct coverage (L3). 

Prompt and context optimization. Prompt optimization searches over instructions for a fixed task [39, 68], DSPy and GEPA optimize or reflectively rewrite the prompts of the modules of an LM program [2, 24], Trace propagates feedback along a workflow’s execution graph [11], SAMMO and MPO edit the components of a prompt separately [43, 45], and ACE revises playbook entries for agent contexts [67]. These systems optimize the components of LM programs, whereas Synapse analyzes the dependences among the instructions of one skill. 

Structured skill representations. Agent Workflow Memory learns reusable procedures from expe-rience [58], SSL organizes skills into usage conditions, steps, actions, and resources [28], SkillSmith compiles skills into runtime interfaces with operator contracts [62], SkVM extracts step depen-dencies to run independent steps in parallel [10], and SkillZip builds section graphs to compress skill libraries [51]. These approaches organize skills for reuse, execution, or compression, whereas Synapse uses recovered structure to modify an existing skill. 

Program analysis and prompts as programs. Synapse applies standard ASTs, control-flow graphs, and program dependence graphs [3, 16] to the structure extracted from skills. Like analyses of incomplete code [12] and island grammars [35], it analyzes only the recognized part of its input, and like origin tracking [53] and lenses [17], it carries edits made on a derived structure back to the source text. Prompt programming languages such as LMQL let authors write prompt structure explicitly [5], whereas Synapse recovers structure from existing prose, and empirical work shows that prompt programs need tool support [27]. PromptPex generates tests from the input specifications and output rules of a prompt [47], and ContextCov compiles agent instruction files into executable checks [46]. These works test or enforce what a prompt requires, whereas Synapse analyzes the instructions themselves to decide where to edit and which tests to rerun. 

Automated program repair. Generate-and-validate repair generates candidate patches with repair operators and validates them by running tests. GenProg mutates statements and ranks variants by a test-based fitness [25], and LLM-based repair keeps this structure with an LLM as the generator, from zero-shot patch generation [61] to agents and pipelines that localize faults, generate patches, and run tests [8, 60]. A plausible patch, which passes all tests used to develop it [40], can still fail on independent tests [49], so Synapse separates selection on repair and validation tests from estimation on held-out tests [9]. Section 3.6 discusses regression test selection and impact analysis [6, 32, 37, 41]. Unlike program repair, Synapse makes edits on a recovered structure while an LLM reads the text, so the source map carries each edit back to the skill, and running the skill shows its effects. 

7 Conclusion 

We cast natural-language skill optimization as generate-and-validate repair over a partial program view. Synapse compiles a skill into SkIR so that fault localization, dependence analysis, and regression test selection decide where to edit, what an edit relates to, and which tests to recheck. It writes every typed mutation back to the mapped span of its target, and the properties of each iteration hold by construction whatever the LLMs return. On DocVQA and LiveMath, Synapse achieves higher success rates than SkillOpt, Trace2Skill, and SkillBoost in all six settings, and an ablation of its SkIR-based mechanisms and broader screening lowers success rates in all four evaluated settings. The repair of the turnover example shows the pattern behind these results, a single rewrite at the mapped span of one instruction, informed by the condition that governs it and checked on a test reached only through its neighbor. More broadly, the approach shows how program repair can work on a language with only a partial grammar and an LLM as its interpreter, Synapse : Optimizing Agent Skills through Program Repair 21 

by editing a recovered view whose edits stay within their spans. Future work will apply Synapse to skills for multi-step tool use and to a broader range of agent tasks.

A.2 Compilation 

This subsection describes the identifiers, recognition rules, data references, source maps, and sentence splitting of the compiler and closes with a table of its compilation rules. 

Identifiers. Each instruction receives a sequential parsing identifier and a canonical identifier. The canonical identifier is formed by prefixing S to the first 16 hexadecimal characters of a SHA-256 digest over the normalized section path, inferred instruction type, normalized instruction text, and duplicate-occurrence index. Absolute source offsets do not enter this identifier, so an earlier edit that merely shifts an instruction’s span leaves its canonical identity unchanged, whereas changing its normalized text, section, type, or duplicate index may change it. Labels that the initial skill gives to instructions, such as D010 , are retained separately as external provenance. 

Action and condition recognition. Action recognition uses a fixed, word-bounded lexicon over the complete instruction text. The lexicon includes source verbs such as “read” and “load”, selection verbs such as “find” and “choose”, checking and transformation verbs such as “validate” and “normalize”, and output or mutation verbs such as “return” and “patch”. Recognized occurrences produce operations in their order in the text. Instructions beginning with “if”, “when”, “unless”, “in case”, or “for” are classified as conditional. The first three forms additionally expose a trigger when the condition ends at a comma, colon, or “then”. The compiler also recognizes postposed “provided that” and “only if” clauses, whose conditions govern the preceding action. Loop-related words such as “repeat”, “until”, and “while” also affect instruction classification. The authored loop-related requirements remain available in the retained instruction text. A.6 Localization and Repair Hypotheses 

This subsection gives the evidence levels of localization, the retrieval tools and repair memory available to the repair model, and the checks on hypotheses and repair boundaries. Synapse retains all failures of the current skill on the repair tests. Diagnose receives a record for every failure and reviews each record exactly once. The repair model determines which failures share a mechanism rather than inheriting a host-defined clustering. Graph witnesses provide evidence for localizing these failures by linking recorded execution facts to candidate source instructions through program relations. A runtime event is an execution record containing the run and task identifiers, the operation and its status, the record’s provenance, and any reported program-element identifier or observed condition, data, or artifact. The host represents runtime events and program elements as typed graph nodes. A registered edge is a relation stored in the host’s graph registry between registered nodes. To connect the execution evidence to the program analyses, cross-representation mappings link corresponding elements in the execution graph, SkAST, CFG, and applicable dependence graphs. The host checks that the witness path is connected by its recorded edges and that these mappings consistently identify the same recognized action and source instruction. These checks establish the structural consistency of the witness, while Synapse : Optimizing Agent Skills through Program Repair 29 

two distinct confidence scores assess the strength of its localization evidence. Binding confidence 

grades the runtime-to-program association according to the event’s provenance, whereas causal confidence grades the failure-specific evidence supporting the candidate localization, such as a recorded requirement violation or contrasting outcomes. The localization levels below use these deterministic, rule-based scores to grade evidence from graph witnesses. Activation contrasts—the difference between activation rates on failing and passing repair tests—help organize the evidence. Diagnose considers all distinct repair targets of the instructions retained by localization, rather than committing to the highest-scoring instruction. Strong evidence comprises requirement violations confirmed by the execution agent or complete graph witnesses with binding and causal confidence at least 0 .9. Medium evidence includes direct runtime usage, complete graph witnesses meeting the 0.6 thresholds but not Strong, and verified missing-capability insertion anchors. The evidence levels are ordered Weak, Medium, and Strong. Synapse uses Medium as the fixed retention threshold and supplies diagnosis with locations that meet or exceed it and have valid source mappings and mutation authorization. Each repair-model request supports one batched retrieval turn. After the model selects affected instructions, the host supplies an index of the earlier patches to these instructions. The index records original target IDs together with available canonical IDs rebuilt from the edited source span, so that earlier repair outcomes can be linked to the corresponding instructions across skill versions. Through a second tool call, the model can inspect earlier edits, fixed and broken tests, preserved and unresolved cases, and repair-boundary observations. The history does not determine the initial grouping of failures. Hypotheses have fields for the proposed mechanism, supporting failure records, and affected canonical instruction identifiers. Suppose the source edits satisfy the non-overlap conditions of Edit locality, every source span 𝑀 𝑡 (𝑛 ) for 𝑛 ∉ 𝑋 Δ is an unedited fragment as defined above, and C is segmentation-local for the patch. Proof. Edit locality preserves the characters of 𝑀 𝑡 (𝑛 ) at its shifted position. Each context-free attribute is a function of this text and section within the preserved syntactic class, so its value is unchanged. □
