## Abstract 

ITOps observability products must integrate data from different tools and systems. We present ITOps Observability Studio, a multi-modal multi-agent system that orchestrates observability work-flows through collaborative AI agents. Its three-tier architecture fea-tures inter-agent communication, specialized LLM-powered agents for data access, schema operations and visualization, and unified tool integration. The system supports natural language to GraphQL translation, GraphQL schema generation, schema mapping, trace data lifecycle management and multi-tool workflows for reliability engineering. Its agents are instrumented with agent analytics, so that their model and tool calls can be traced. We evaluate each agent on its own benchmark, scored against gold answers where they exist and by a model judge for schema mapping and chart quality. Query generation on a public benchmark and routing work well with a current open model, and the data lifecycle management agent solves most of its scenarios. The evaluation exposed defects that only appear when prompts, parsers and serving stacks are tested together, and we report them together with their fixes.

Autonomous Agents, IT Automation, Observability, GraphQL, Agent Protocols 

## 1 Introduction 

Large language models (LLMs) and vision language models (VLMs) are now used to automate workflows in data science and analytics. Yet even the most capable models struggle to perform real-world tasks that closely mimic human actions in these domains. These tasks often require operating several professional tools, and bench-marks like Spider2V [9] show the current limitations of multi-modal agents in automating complete, end-to-end data workflows. ITOps observability is one such real-world task. By observability we mean the ability to monitor, analyze and act on telemetry, the metrics, logs and traces that systems emit, in order to detect, resolve and prevent issues. The more an organization depends on its IT systems, the more it depends on observability and on automating it. The data for one operator question is often spread across several products, each with its own API, schema and naming conventions. To automate this, a system must turn an operator’s request into queries over each product’s schema, and turn the results into charts. Consider the workflow in Figure 1. GraphQL is a query language for APIs in which the client names exactly the fields it wants, so one query can gather related data that would otherwise need sev-eral API calls. Work on GraphQL query generation with LLMs shows that models often generate invalid queries when their grounding in the schema is weak [29]. In this work, we address these limitations with ITOps Observabil-ity Studio, a multi-agent system that integrates LLMs and VLMs for data science and engineering workflows. It is multi-modal in that its agents work with text and images, and with metrics and traces as semi-structured data such as JSON rather than flat tables. We focus on the Text to Dashboard workflow for ITOps observability, in which an engineer describes in words the dashboard they need. In our system, autonomous agents interpret these requests and re-trieve the relevant data from APIs and databases through a GraphQL data access layer. They then design and evaluate dashboards for reliability engineers. ## 2 Related Work Agentic AI frameworks 

Frameworks such as LangChain and LangGraph enable composi-tion of multi-step LLM workflows using chains, memory, and tool interfaces [52]. LangGraph extends this with graph-based control flows that support loops and branching, better suiting dynamic data workflows. Both rely on pre-indexed or manually curated schemas. CrewAI is a lightweight orchestration layer designed to simulate multi-agent teams with defined roles, goals, and tools [15]. AutoGPT pioneered autonomous workflows through iterative task decom-position and plugin integration [54]. Despite its flexibility, it often exhibits hallucinations and inefficiencies due to poor grounding in structured schemas. Microsoft’s AutoGen improves multi-agent or-chestration via role-based agents and conversational memory [73]. None of these frameworks maps schemas, integrates GraphQL-based APIs or manages the data lifecycle on its own. Hierarchical frameworks such as HALO (Hierarchical Au-tonomous Logic-Oriented Orchestration) [23] and Flow [48] use planning agents to spawn sub-agents, leveraging search-based strategies for workflow adaptation. Tools like AutoAgent [68] and AutoAgents [11] aim to translate natural language instructions into executable agents with no programming required. Many of these agents reason with chain-of-thought prompting [71] or interleave reasoning with actions as in ReAct [74], which our agents also use. To evaluate such systems, Sapkota et al. [57] introduce a taxonomy differentiating narrow task bots from orchestration-based agentic AI, identifying bottlenecks in coordination, hallucination control, and environment alignment. Gabriel et al. [21] propose metrics such as Tool-F1 and Structural Similarity Index for assessing per-formance in tool-driven agent tasks. AIOpsLab [14] and ITBench [28] provide environments and tasks for evaluating AI agents on cloud operations, site reliability and FinOps tasks. RCAgent [70] applies tool-augmented LLM agents to root cause analysis in the cloud. NL2KQL [69] translates natural language into Kusto queries over log and telemetry tables, a task close to our GraphQL query generation. These works benchmark agents on incident and operations tasks, while ours address data access, schema integration and visualization across several observability products. Two open protocols cover most agent communication. The Model Context Protocol (MCP), introduced by Anthropic in No-vember 2024 [4], connects LLM applications to tools and data over JSON-RPC. Its 2026-07-28 revision [45] makes the core stateless and moves further functionality into opt-in extensions, among them Tasks for long-running operations. The Agent2Agent (A2A) protocol [1, 22], introduced by Google in April 2025, standardizes how one agent discovers another through an agent card and delegates tasks to it, and has reached version 1.0. IBM’s Agent Communication Protocol (ACP) [8], a REST-based protocol, merged into A2A under the Linux Foundation in 2025. Our system uses MCP between agents and tools and A2A between agents, which matches this division of labor. Agent Skills [5] package instructions, scripts and resources that an agent loads only when needed, and complement MCP tools with procedural knowledge. 

## API Function Calling and Sequencing 

Several recent works improve the use of APIs in agent workflows. Saha et al. [56] focus on GraphQL schema design for sequential API function calling, enabling agents to chain requests in a structured manner. Mandal et al. [42] propose graph-based approaches for sequencing APIs using an API dependency graph, which helps agents reason over available endpoints. Basu et al. [6] study nested sequences of API calls, which arise in IT automation when several agents interact. Abdelaziz et al. [2] introduce Granite Function Calling to standardize function invocation across heterogeneous APIs. Basu et al. [7] also present a benchmark corpus for training language models on API detection and sequencing. Finally, Chen et al. [13] propose APIGen, a method to help agents to automatically discover and leverage suitable APIs for a given task. 

## Tool Use and API Integration 

AnyTool [20] presents self-reflective, hierarchical agents for large-scale API calls. ToolLLM [53] shows how LLMs can use many real-world APIs, and Gorilla [51] trains LLMs with API information. API-Bank [33] and SEAL [30] evaluate how LLMs use APIs, and Metatool [25] addresses whether and which tools to use. RestGPT [63] connects LLMs with RESTful APIs, as our data access layer does through GraphQL. TaskMatrix.AI [34] completes tasks by connecting foundation models with millions of APIs.

Several works provide foundational techniques relevant to schema mapping agents. Lu et al. [38] learn API mappings from documen-tation, and Liu et al. ## LLM Fine Tuning 

Our agents use prompted models without fine-tuning, and Section 4 names fine-tuning as future work. Full fine-tuning trains every parameter of a model and needs substantial compute, memory and training time. Instruction fine-tuning [75] trains a model on labeled instruction and response pairs so that it follows complex instructions more closely. Parameter-efficient methods train far fewer parameters. LoRA [24] adds small adapters to a frozen model, and QLoRA [17] also quantizes the model to 4 bits, so that models with more than 65B parameters can be tuned on a single GPU. 

## Visualization 

Natural Language Interfaces for Data Visualization (V-NLIs) let users create charts by describing them in natural language (NL). Existing approaches can be broadly categorized into (1) NL-guided systems, where visualizations are shaped by user queries, and (2) data-driven systems, which generate visualizations directly from data without NL input. Early NL-guided methods relied on rule-based NLP pipelines that mapped parsed queries to visualization pa-rameters using grammar rules and similarity metrics such as Leven-shtein and Wu-Palmer distances. For instance, BOLT [66] used rigid intent templates but struggled with vague or ambiguous prompts. Data-driven systems like Calliope [61] and Dashbot [16] applied Monte Carlo Tree Search and reinforcement learning, respectively, to generate dashboards from data alone. These approaches lacked semantic understanding, could not support hierarchical data, and produced static visualizations that were hard to interpret. Recent advances use LLMs to address these limitations. LIDA [18] employs a modular LLM-assisted pipeline for summarization, goal inference, and visualization generation, achieving a 3.5% Visual-ization Error Rate (VER) and strong GPT-4-based quality scores. NL4DV-LLM [55] handles ambiguous queries by inferring intents from prompt-engineered queries, reaching 87.02% accuracy on 740 annotated examples, albeit with higher latency. Chat2Vis [41] uses LLMs to generate Vega specifications from prompt examples, but suffers from high output variance and limited stylistic control. Despite these improvements, most methods lack robust eval-uation. Many rely on case studies or subjective metrics, limiting reproducibility. VisEval [12] addresses this by introducing an auto-mated evaluation framework that quantifies visualization quality along three axes, namely Validity (checks for crashes), Legality (verifies alignment with query intent), and Readability (assessed via GPT-4V). It provides a reproducible benchmark, revealing common pitfalls like invalid code, incorrect encodings, and poor layout qual-ity. Our evaluation of the visualization agent follows VisEval [12] and adds a usability criterion for SRE decision-making. 

## 3 Three-Tier Reference Architecture 

We build the Observability Studio as a multi-agent system, so that each task has its own specialized agent. Multi-agent systems have also been shown to simulate human strategic behavior more accu-rately than a single LLM agent [65]. Building on specialized agents, we introduce a three-tier reference architecture that coordinates multiple agents using an agent-to-agent communication protocol. While our implementation uses the Agent2Agent (A2A) protocol [22], the design adapts to any protocol with structured inter-agent messaging. The architecture coordinates data workflows across heterogeneous IT systems. Each agent, tool and protocol can be replaced on its own, and agents that change data, such as the DLM agent, ask the user before they apply a sampling policy. 

## Architectural Overview 

The architecture has three tiers. The presentation tier is an ADK-based UI chat agent that mediates interactions between the user and the backend agents. The agent coordination tier holds special-ized LangGraph agents that collaborate via a pluggable, protocol-agnostic communication layer. The tool integration tier consists of MCP servers that offer domain-specific functionalities through external tools and APIs. Figure 2 shows the three tiers, the agents’ tools and the data sources behind them. The tiers meet only through an abstract communication layer, so an agent can move to another agent framework or protocol without changes to other agents. 

## Agent Ecosystem 

We implement six specialized agents, grouped by function into data access agents, data consumption agents and an orchestrator. Three agents form the data access layer. The GraphQL Query Agent ex-tends the sequential API function calling approaches [42, 56] by generating contextually-aware GraphQL queries from natural lan-guage descriptions. Unlike traditional API sequencing methods, this agent uses LangGraph’s reasoning to understand the query requirements and to generate GraphQL operations over the target GraphQL schema. The GraphQL Schema Generation Agent gen-erates GraphQL schemas from the OpenAPI descriptions of data sources, so new sources can join the federated GraphQL layer, the single endpoint through which all sources are queried, as their APIs evolve. The GraphQL Schema Mapping Agent clusters schemas by domain and structure before it maps them (Section 4), extending embedding-based approaches [26] and foundation model methods [47]. Domain classification and structural analysis give it more context-aware mappings between heterogeneous schemas. Two agents consume this data. The Visualization Agent builds on the visualization frameworks of Section 2, combining data-driven generation with natural language guidance. Unlike LIDA [18] and Chat2Vis [41], this agent works on the GraphQL data layer, so data access and transformation happen within the visualization pipeline. The Data Lifecycle Management (DLM) Agent recommends and applies trace pruning policies (Section 4). It coordinates with data access agents to understand data lineage and with the visualization agent to present analyses of cost impact to the user. The ADK-based UI-Orchestrator Chat Agent is the orchestrator and user interface, using the Agent Development Kit (ADK) to provide a conversational interface while coordinating multi-agent workflows. It decomposes tasks, routes them and aggregates the results. Routing is decided in two stages. It first applies keyword rules, and if no rule matches, its LLM chooses an agent from the agent cards. We evaluate both routing stages in Section 4.

## Agent Analytics 

The agents are themselves software that needs observing. Five agents, the orchestrator and the query, schema mapping, visualiza-tion and DLM agents, initialize an agent-analytics SDK at start-up. The SDK builds on OpenTelemetry and records each agent’s LLM calls and tool calls as traces, which it writes to a per-agent log. These traces let us attribute latency and model calls to individ-ual agents, and connect a wrong answer to the routing decision, tool call or model call that produced it. Each agent writes its own log, so following a request across agents means joining the logs of the agents it reached, and propagating the trace context over A2A would make this direct. The same signals map onto the Open-Telemetry GenAI semantic conventions [49], a shared vocabulary for the telemetry of AI applications. Under these conventions, an agent invocation, a model call and a tool call each become a span (one timed step of a trace), and token usage and operation duration become metrics. The agents thus emit the same telemetry as the systems they observe, and the same tools can analyze them.

## GraphQL Schema Generation Agent 

The schema generation agent turns an OpenAPI specification into GraphQL schema definitions. It splits the specification into chunks of at most four operations, prompts the LLM to write their types and query fields, and assembles the result. We compare the gener-ated schemas with the hand-written GraphQL schemas maintained for three products, the only ones with both an OpenAPI specifica-tion and such a schema. The generator sees exactly the operations that the hand-written schema covers. We measure whether each generated file parses and builds, and match the object types and the fields within matched types against the hand-written schema. Table 2 shows the macro mean over the three products. The earlier output is the stored output of the first version of the agent, and the lenient build declares the JSON scalar before building. Every strict build failure comes from this undeclared scalar, which the prompt itself asks the model to use. Within matched types, fields agree well, but types agree poorly. The hand-written schemas are a curated query layer that renames types, adds connections and keeps only part of each API. These scores therefore measure agreement with a human design rather than with correctness. 

## GraphQL Schema Mapping Agent 

Schema mapping involves defining correspondences between the schemas of different APIs to create a unified, queryable interface. It aligns the fields of a source schema to those of a target schema, so that data types, formats and meanings are compatible. When integrating multiple APIs, schema mapping ensures that data from Autonomous Multi-modal Agents for ITOps Observability 

diverse sources, possibly with varying structures, naming conven-tions or data types, can be accessed through a single federated GraphQL endpoint. Approaches range from algorithmic rule-based methods to machine learning and language models. DynaMap [44] uses dynamic programming to search possible mappings, while [26] applies embedding-based similarity for table and attribute matching. Valentine [32] benchmarks them against gold matches. SMUTF [77] combines rule-based signals and se-mantic embeddings in an XGBoost classifier. The Learned Schema Mapper [76] fine-tunes a BERT encoder on schema metadata. Mag-neto [37] generates candidates with small language models and reranks them with an LLM, and ISResMat [19] fine-tunes a lan-guage model on pairwise samples. [47] phrases schema mapping as a prompt to a foundation model. Retrieval-augmented methods add context, either metadata documents from the target schema [60] or knowledge graph facts [40], and GraphRAGToolFusion [39] combines knowledge graphs with vector retrieval for tool selection. However, these approaches do not explicitly organize or cluster schemas based on API domain, functionality, or structural complex-ity. AnyTool [20] introduces a hierarchical retrieval architecture with three levels of agents. A meta-agent interprets user intent and routes queries, category-agents specialize in specific domains to narrow down relevant tools, and tool-agents assess and execute individual APIs. Inspired by this architecture, we built a modular, hierarchical framework for automating schema mapping. A toolkit of functions implements the mapping pipeline. When a mapping request arrives, the system first analyzes the source and target schemas to determine their domain and structural characteristics, and clusters them by domain and functionality. It then prompts an LLM to predict field correspondences. The responses are filtered and converted into a structured format, justifications are added, and mappings are ranked by semantic similarity to the source fields. For example, when given a natural language query such as “Map concert vulnerabilities to turbo entities”, the agent first computes semantic similarity scores between the query and all available schemas to shortlist the top ten candidates. From these, the source and target schemas are selected by an LLM based on the user’s intent. The toolkit is then executed on the selected schemas to identify relevant types and fields, and the resulting mappings are returned. Finally, the agent can invoke additional tools such as a Neo4j tool or a Wiki tool. The Neo4j tool stores the mappings in a graph database by hierarchically organizing them as product →

type → field, with field-level mappings represented as edges. Alter-natively, the Wiki tool generates hierarchical documentation pages for each schema and embeds hyperlinks to represent the discovered mappings. Two example mappings and their justifications follow.

The Schema Mapping Agent was tested on schema pairs from heterogeneous systems and evaluated by an LLM-as-a-judge, Mis-tral Large. The judge scores each mapped pair between 0 and 1 for joinability and for equivalence. Joinability indicates whether the output of one field can be used to populate or enrich the other, while equivalence indicates whether the two fields represent the same core function. A pair with a score above 0 .5 counts as correct, and accuracy is the share of correct mappings. The test set holds 289 schema mapping requests, whose schema pairs were selected by hand from the API descriptions. A judge has no gold answers, so the numbers estimate rather than measure correctness, and a gold-scored evaluation is future work. 

## Data Lifecycle Management (DLM) Agent 

The DLM agent builds on work in which LLMs call external tools. Toolformer [58] demonstrated how LLMs can teach themselves to call APIs. AnyTool [20] proposed a hierarchical, self-reflective agent that uses GPT-4’s function calling to orchestrate access to over 16 ,000 APIs. MARCO [62] introduced a framework for multi-agent real-time orchestration, with guardrails and symbolic planning, for the reliable execution of tasks across business workflows. The Data Lifecycle Management (DLM) agent is designed for ef-ficient trace monitoring and pruning. It integrates with monitoring systems to track costs across clusters, namespaces, applications, and services. Using trace volume management tools, the agent iden-tifies policies for trace reduction, recommends these policies to the user, and executes pruning actions accordingly. The agent is built with LangGraph, with tools deployed as MCP servers. These data points form the input context for the DLM Agent, which connects to the other tiers through A2A. The agent reaches the data access layer and the DLM tool through two MCP servers. A Kubecost server provides allocation and cloud cost data and cost alerts. A trace sampling server evaluates and applies sampling methods, which keep a representative subset of traces and drop the rest, cutting storage cost at the price of some detail. The DLM Agent can be triggered in two ways, system-initiated, where Kubecost generates alerts when telemetry volume causes high cloud costs, and user-initiated, where a user asks to reduce costs. Based on the telemetry data and cost, the agent evaluates trade-offs between cost and information retention. This is facilitated by the Trace API, which internally uses a Trace Volume Manager 

(TVM). The TVM supports multiple trace sampling algorithms and is designed to be extensible, allowing additional sampling strategies to be integrated as needed. The agent selects the recommendation that balances cost savings with an acceptable loss of trace visibility, deploys the policy and communicates with the tool for trace prun-ing. ## Visualization Agent 

The Visualization Agent automatically generates and assesses data visualizations in response to natural language queries about IT observability. It has three stages, preprocessing, visualization and postprocessing. Preprocessing cleans the input dataset by removing columns with more than 50% missing values and dropping redun-dant features. Redundancy is judged by an LLM, which reasons over the schema to find semantically overlapping fields. The visual-ization stage translates natural language queries into Vega-Lite 5 specifications, a format in which a chart is described declaratively as JSON, using Chain-of-Thought (CoT) prompting. The prompt includes syntactic constraints and a rationale for chart selection, inspired by the ReAct framework. The LLM is provided with the data schema, including column names and data types. The system supports five chart types, namely bar, line, area, pie and scatter plots. Postprocessing validates and evaluates the generated visual-izations. A syntactic check ensures that the Vega-Lite specification is compatible with the dataset, and valid specifications are then rendered and passed to a VLM for semantic evaluation. 

Evaluation. We assess the agent with one syntactic and five seman-tic metrics. The Visualization Error Rate (VER) is the proportion of Vega-Lite specifications that fail to render due to syntax or data mis-matches. For the semantic evaluation, a VLM assesses the quality of rendered charts across five dimensions. The first four come from prior NL2VIS work [12], and the fifth captures domain-specific us-ability in ITOps. Legality (yes or no) asks whether the chart matches the intended type with a correct logical mapping. Layout (yes or no) asks whether the layout is free of clipping, overlapping or a misplaced legend. Scale and ticks (0–5) asks whether the axes are appropriately scaled and labeled for interpretability. Readability (0–5) assesses visual clarity, including titles, labels, fonts, colors and spacing. Usability (0–5) evaluates whether the visualization supports the real-world decision-making of SRE teams. The original implementation used ibm/granite-3-2-8b-in struct [27] for the preprocessing and visualization stages and 

pixtral-12b-2409 [3] as the evaluation VLM. Neither is still served. We therefore run the deployed pipeline with Llama-3.3-70B and Granite-4-H-Small as text models and Mistral Medium as the judge, keeping the original prompts. We curated 30 natural language queries from interviews with SREs, of which 10 are generic and Autonomous Multi-modal Agents for ITOps Observability

Generic queries are broad requests that often need several charts, such as “Analyze the overall health and performance of the application.” Specific queries are targeted questions addressable via a single chart, such as “Create a scatter plot of mean latency vs. calls per second to identify performance bottlenecks.” The data are samples of Instana application and endpoint metrics. Supporting more chart types, or telling the user when a requested type is replaced, would fix this. During develop-ment, prompts that included detailed statistical summaries tended to give worse charts. Row-level preprocessing is not supported, because whole datasets exceed the LLM’s input length limit. 

## 5 Discussion Engineering Lessons 

An earlier evaluation of this system counted HTTP-level successes and used a hand-tuned quality score. Such measures show whether agents respond, not whether they are right, so every result in this paper is scored against gold answers or, for schema mapping and chart quality, a model judge. Scoring against answers is also what exposed the defects reported here, since an agent that returns no chart or calls the wrong tool still responds successfully at the HTTP level. The choice of metric matters as much as the choice of answers. Routing accuracy above 0.9 hides that the keyword router almost never routes GraphQL query requests correctly, because almost all requests are schema mapping requests that a single keyword catches. A router that ignored its input and always chose schema mapping would still score 0.82 accuracy, against a macro-F1 of 0.23. Macro-F1 and per-class recall reveal this, and they also show that rules that override the LLM can lower recall on the minor-ity GraphQL class. The same caution applies to reference-based scores for generated artifacts. The schema generation agent agrees with the hand-written schemas on fields far more than on types. Those schemas are one curated design, not the only correct answer. A functional test would measure correctness more directly than agreement does, for example by checking whether the queries SREs need can be answered over the generated schema. Model judges deserve the same scrutiny as the agents they score. Two of our results, schema mapping and chart quality, rest on a judge rather than on gold answers, and the judge’s own criteria shape the numbers. The chart judge marks a substituted chart type as illegal, so its legality score measures how closely a chart follows the request rather than how useful the chart is. The original system was judged by Pixtral-12B and the re-run by Mistral Medium, which is one reason the two sets of chart scores cannot be compared directly. Calibrating each judge against human labels on a sample of its inputs, and reporting the agreement, would turn these scores from estimates into measurements. The same labels would also serve as gold answers for later versions of the agents. Two agents had defects that appeared only when we measured them with current models. The visualization agent’s prompt and parser disagreed about Markdown code fences. The prompt told the model not to use them while the parser required them, so the deployed pipeline produced no charts. A contract test, which runs the parser on real model output, would have caught this. The DLM agent depended on the serving stack, the gateway and inference server that run the model. The same Llama model ignored tool results behind one gateway and not another, because of how its chat template formats system messages into the model’s input. Both defects sit between the model and the code around it, where unit tests with mocked model output pass by construction. Cemri et al. [10] group the failures of multi-agent LLM systems into speci-fication, inter-agent misalignment and task verification. The two defects here lie below these, between a single agent and the stack that serves its model. Testing on the target serving stack, with the prompts, parsers and chat templates that production uses, is part of testing an agent. It must be repeated when the model or gateway changes. Agent analytics supports this diagnosis. Its traces connect a wrong answer to the routing decision, tool call or model call behind it, and attribute latency and model usage to each agent. Re-running the system a year after it was built also tested the architecture in a way we had not planned. The Granite-3.x models that the agents were built on are no longer served, so every agent had to move to a new model. Each change this needed, described in the agent’s own section, stayed inside that agent, which is the isolation the three-tier design aims for. The move also showed that model retirement is an operational risk for agent systems. Prompts tuned for one model family can fail silently with another, as the code-fence defect did. Pinning model versions, keeping the evaluation harness runnable and re-running it whenever a model is replaced matter as much as the agents themselves.

## Limitations 

The data limit how far these results generalize. The DLM scenarios and their backends are synthetic, the visualization data are small samples, and the routing labels come from a dataset generator rather than human annotators. The requests themselves come from the same generator, so their phrasing may be more regular than that of real operators. Several per-class and per-type samples are small, and each result is one greedy run. IBM watsonx outputs are not bit-reproducible, so the same request can return slightly different answers, and small gaps deserve caution. Schema map-ping is judged by an LLM without gold answers, and the GraphQL benchmark uses general-domain rather than observability schemas. The original agents used Granite-3.x models no longer served, and we evaluate with Llama-3.3-70B and Granite-4-H-Small, so results for the original configuration are not reproduced. Finally, we eval-uate agents individually. End-to-end workflows, the overhead of the A2A and MCP layers, the scalability of a single orchestrator to many agents, and agent behavior when external services fail are not measured here. The DLM results show that the agent reasons and calls its tools correctly against deterministic mocks, not that it works with live Kubecost and live tracing systems. 

## 6 Conclusion 

We presented a three-tier reference architecture for coordinating data workflows in enterprise IT, which combines specialized Lang-Graph agents, MCP tool integration and A2A inter-agent commu-nication, and is instrumented with agent analytics. Its data access layer generates GraphQL queries and schemas and maps between product schemas, and its consumption agents build dashboards and manage trace retention. The agents share open protocols, so each can be replaced on its own. The evaluation shows that query generation on a public benchmark and routing work well with a current open model, and that the data lifecycle management agent solves most of its scenarios. Schema generation agrees with human designs on fields more than on types, and two agents had deploy-ment defects that were found only when measured. The fixes are to test prompts and parsers together, test on the target serving stack, and report macro metrics. Next we will apply these fixes, evaluate end-to-end workflows through the agent analytics traces, and adapt models to our schemas with parameter-efficient fine-tuning.
